# Chapter 12.4 - Hands-On with Burp Suite

> Goal: Learn the core web-security testing workflow with Burp Suite, strictly against a deliberately-vulnerable app you run locally (OWASP Juice Shop in Docker). Understand the intercepting proxy, the Burp tools, and how to run a structured *authorized* assessment, then map every finding back to the defenses from 12.3 so you can harden NYX Finance / Anneava.

---

## Start here - the absolute beginner on-ramp

If you've never opened Burp, the tool looks like a cockpit with a hundred buttons. Ignore 95% of them. Here's the whole thing in one mental picture.

**The "read the mail before it's delivered" analogy.** Normally your browser hands its request directly to the web server, like dropping a letter in a mailbox. Burp is a **trusted assistant standing at the mailbox** who, *with your permission and only for your own mail*, can:

- **Read** every letter going out and every reply coming back (see the raw HTTP).
- **Pause** a letter before it's delivered, so you can look at it.
- **Edit** the letter and *then* send it (change a field the website's form would never let you change).
- **Photocopy and re-send** a letter as many times as you like, tweaking it each time.

Burp is an **intercepting proxy**, software that sits between your browser and the server so you can see and modify the raw traffic. Everything else (Repeater, Intruder, Decoder, Comparer) is a convenience built on that one core capability.

**Why this is *the* web-security tool.** Websites do a lot of checking in the browser with JavaScript ("you can't transfer more than your balance," "that field must be a number"). But the browser is the *client*, and it's on the attacker's side of the fence. The only thing that actually protects an app is what the **server** does. Burp lets you send the server a request that the polite UI would never send, and watch what the server does. If the server *trusts* the bad request, that's a bug, and now you know to fix it in your own apps.

**The mindset shift (this is the real lesson).** You're not learning Burp to "hack." You're learning to ask one defensive question, over and over: *"If a malicious client sends a request your UI would never send, does your server still enforce the rules?"* Every Burp exercise below is a way to answer that question on a deliberately-broken practice app, so you build the instinct to verify it on NYX Finance and Anneava.

**The non-negotiable rule first** (and it's so important it has its own section right below): you only ever do this against an app you *own and run yourself*. For learning, that's OWASP Juice Shop in a Docker container on your own laptop. There is no one else's data or system involved. It's your mailbox, your letters.

If you remember one thing: **Burp shows you the raw HTTP the server actually receives, so you can verify security is enforced on the server, not just in the browser.**

---

## Ethics & legal - read this first, every time

**Testing a system you do not own or have explicit written permission to test is illegal** (in the US, the Computer Fraud and Abuse Act; similar laws elsewhere). This is not a gray area. Intercepting, tampering with, or probing someone else's web app can be a crime even if you "didn't break anything." So the rules to hold yourself to:

1. **Only test systems you own, or have explicit written authorization to test** (a signed engagement / scope document, or a bug-bounty program's published rules).
2. **For learning, use a deliberately-vulnerable app running locally**, OWASP **Juice Shop** is built for exactly this. It runs on *your* machine; you own it; there is no one else's data or system involved.
3. **Configure the proxy to scope only the local target** so you never accidentally intercept traffic to real sites.
4. **Goal is understanding and defense**, you learn how an attack works so you can recognize and *fix* it in your own apps, not to attack others.

Everything below assumes the target is `http://localhost:3000` (your local Juice Shop). Never point these tools at anything else without written permission.

## Theory

### What an intercepting proxy is, and why it's the core tool

Normally your browser talks straight to a web server. An **intercepting proxy** sits *between* them:

```
Browser  ⇄  Burp Proxy (localhost:8080)  ⇄  Web server (localhost:3000)
```

Every request and response flows through Burp, where you can **view, pause, and modify** it before it continues. Why this matters: the browser enforces lots of client-side rules (form validation, hidden fields, JS checks), but the *server* is the only thing that actually matters for security. The proxy lets you see and change the **raw HTTP** the server receives, *bypassing all client-side controls*. That's the core lesson of web testing: client-side validation is UX, not security; you verify the server enforces things itself.

This is also exactly how you think defensively: "what does the server do if a malicious client sends a request the legitimate UI would never send?" If the answer is "trusts it," that's a bug (broken access control, missing validation, 12.3).

### Why HTTPS needs Burp's CA certificate

To intercept *HTTPS*, Burp has to decrypt the TLS, which means it acts as a (consented, local) man-in-the-middle. Burp generates its own **CA certificate**; you install that CA into your browser/OS trust store so the browser trusts Burp's on-the-fly certs for the sites you're testing. **This is deliberately breaking TLS for yourself, on your own machine, for your own testing**, and it's exactly why a real attacker *can't* do this to you without already controlling your device or tricking you into installing their CA. (Defensive lesson: protect your trust store; HSTS + cert pinning resist this for real apps.)

Connecting this back to 12.2: what Burp does locally and *with your consent* is structurally the same as the MITM that TLS is designed to prevent. The reason it works is that you deliberately added Burp's CA to your own trust store, you broke the chain-of-trust on purpose, for your own box. That's the whole defensive insight: **TLS interception requires controlling the victim's trust store**, which is why protecting it (and using HSTS + pinning on real apps) is what stops a genuine attacker.

**5. Scope it** (Target → Scope → add `http://localhost:3000`), and set Proxy intercept to only act on in-scope items. This guarantees you're never tampering with anything but your local target.

### Installing Burp's CA certificate - the fuller, per-browser click-by-click

Step 4 above is the one beginners get stuck on, because "import a CA" differs per browser and OS, and getting it wrong means HTTPS sites throw certificate errors. **The easy path is to always use Burp's embedded browser (Step 3), which needs none of this.** But it's worth knowing the manual route once, both to understand *what* you're trusting and because the procedure is itself the defensive lesson (a CA install is exactly what an attacker would need to trick you into). Reminder: only do this on **your own machine**, and **remove the CA when done**.

**First, export Burp's CA cert (any browser):**
1. Make sure Burp is running and your browser's proxy is set to `127.0.0.1:8080`.
2. In the browser, go to **`http://burpsuite`** (this special page only loads while proxying through Burp).
3. Click **CA Certificate** (top right) → it downloads `cacert.der`.

**Firefox** (uses its *own* trust store, not the OS, simplest to reason about):
1. **Settings → Privacy & Security → Certificates → View Certificates…**
2. **Authorities** tab → **Import…** → choose `cacert.der`.
3. Tick **"Trust this CA to identify websites"** → **OK**.
4. *Cleanup when done:* same screen, select **PortSwigger CA**, **Delete or Distrust**.

**Chrome / Edge / Chromium** (use the **OS** trust store):
- **macOS:** double-click `cacert.der` → Keychain Access opens → add to **login** (or System) keychain → find **PortSwigger CA** → double-click → expand **Trust** → set **"When using this certificate" = Always Trust** → close (enter password). *Cleanup:* delete the PortSwigger entry from Keychain Access.
- **Windows:** rename to `cacert.crt` → double-click → **Install Certificate** → **Local Machine** → **Place all certificates in the following store** → **Trusted Root Certification Authorities** → Finish. *Cleanup:* `certmgr.msc` → Trusted Root → delete PortSwigger.
- **Linux:** `sudo cp cacert.der /usr/local/share/ca-certificates/burp.crt && sudo update-ca-certificates` (some browsers use NSS via `certutil` instead). *Cleanup:* remove the file and re-run `update-ca-certificates --fresh`.

**Safari (macOS):** uses the system Keychain too, so the macOS steps above cover it.

**Verify the install worked:** with intercept off, browse to `https://localhost:3000` (or any HTTPS site) through Burp, *no certificate warning* means the CA is trusted. A warning means the import didn't take (wrong store, or wrong browser's store). **Why this is also a defense lesson:** you just demonstrated that a trusted CA can silently MITM all your HTTPS, so on your *real* apps you rely on HSTS and (for high-value clients) certificate pinning, and you never install a CA you don't fully control. **Remove Burp's CA the moment you're done**, or your day-to-day browsing runs with an extra trusted root.

### First-run walkthrough - from zero to "I intercepted a request" (beginner, click by click)

The first time, the hardest part is just *getting traffic to flow through Burp*. Here's the exact path so you never fumble it. This assumes Burp Community is installed and Juice Shop is running (`docker run --rm -p 3000:3000 bkimminich/juice-shop`).

**Step A, Start a project.**
1. Launch Burp Suite Community.
2. On the start screen choose **Temporary project** → **Next**.
3. Choose **Use Burp defaults** → **Start Burp**. (Community can't save projects; temporary is fine for practice.)

**Step B, Open the pre-wired browser.**
1. Go to the **Proxy** tab.
2. Click the **Intercept** sub-tab. There's a toggle button labeled **Intercept is on / off**, leave it **off** for now (so you can browse normally first).
3. Click **Open Browser**. This launches Burp's bundled Chromium, already configured to route through Burp's proxy and already trusting Burp's CA. (Using this browser means you *cannot* accidentally proxy your real, personal browsing, a nice safety property.)

**Step C, Browse the target so Burp learns the app.**
1. In the Burp browser, go to `http://localhost:3000`.
2. Click around: open the product list, register a test account, log in, add something to the basket. Use *fake* throwaway credentials (it's all local and disposable).
3. Switch back to Burp → **Proxy** → **HTTP history**. You should see a growing list of every request the browser made. *This is the "you can see all the mail" moment.* Each row is one request/response; clicking it shows the raw HTTP at the bottom.

**Step D, Actually intercept one request.**
1. Proxy → **Intercept** → click the toggle so it reads **Intercept is on**.
2. In the Burp browser, do a single action, e.g., submit the login form.
3. Flip back to Burp: the request is **paused** and shown in the Intercept panel. Read it. This is the raw bytes the server is about to receive.
4. Click **Forward** to let it continue (or **Drop** to cancel it). Turn **Intercept off** again afterward so the browser doesn't freeze on every request.

**Step E, Set scope so you can never wander off-target.**
1. Go to **Target** → **Scope settings** (or the **Scope** sub-tab).
2. **Add** → enter `http://localhost:3000` (or use "Include in scope" from a right-click on a host in the site map).
3. Tick **"And URL Is in target scope"** style filters: in **Proxy → Intercept**, set it to only intercept in-scope items; in **HTTP history**, filter to in-scope. Now Burp ignores everything that isn't your local Juice Shop, a guardrail that backs up the ethics rule mechanically.

Once you can complete Steps A-E, you have the entire foundation. Everything else is variations on "capture a request, look at it, change it, resend it."

**Sanity-check the plumbing:** if HTTP history stays empty, the browser isn't going through Burp. Easiest fix: always use **Open Browser** (Step B) rather than your own browser. If you *must* use your own browser, you have to set its proxy to `127.0.0.1:8080` *and* install Burp's CA (the per-browser section above), more moving parts, more ways to get stuck.

### The Burp tools (what each is for)

- **Proxy**, the interceptor. Pause a request, read/edit it, forward or drop. The HTTP history tab logs everything that passed through (great for reviewing the app's traffic).
- **Repeater**, take any request and **replay it repeatedly with modifications**. This is where most manual testing happens: change one parameter, resend, observe the response. Tight feedback loop, no automation.
- **Intruder**, **automates** sending many variations of a request (e.g., iterate an ID, fuzz a parameter with a wordlist). *Concept only* in Community (it's rate-limited/throttled there; Pro removes the throttle). Useful for understanding fuzzing/enumeration, and a reminder of why your apps need rate limiting (09.4) and lockouts.
- **Decoder**, encode/decode data (URL, Base64, hex, HTML) and hash it. Handy for understanding tokens/parameters (e.g., is this "token" just Base64 of the user id?).
- **Comparer**, diff two responses byte-by-byte. Useful to spot how a response changes when you tamper input (e.g., authorized vs unauthorized response).
- **Sequencer**, collects many session tokens and runs **randomness/entropy analysis** on them. The defensive use: confirm your *own* app's session tokens are unpredictable (high entropy) and not sequential/guessable, a predictable token is a session-prediction risk (A07). Available in Community.
- **Target / Site map**, Burp builds a map of the app's endpoints as you browse, a structured view of the attack surface.
- **Scanner** *(Pro only)*, automated vulnerability scanning. Community doesn't include it; you do manual testing instead. (Mentioned so you know the landscape.)

---

### Where Burp fits - Community vs Pro, and the broader toolbox

So you know the landscape and don't over-reach with the free tool:

- **Burp Community (what you'll use):** Proxy, Repeater, Decoder, Comparer, Sequencer, the site map, all the *manual* workhorses. Intruder is present but **throttled**. No automated Scanner, no project saving, no extensions API at full power. For *learning the mechanism* and *defensively regression-testing your own app*, Community is plenty.
- **Burp Pro (what teams buy):** removes the Intruder throttle, adds the **active Scanner** (automated crawl + vuln detection), project saving, the **Montoya extension API**, and a REST API for automation. Worth it for a working AppSec role; unnecessary for self-study and personal apps.
- **Free alternatives worth knowing:** **OWASP ZAP** (a full-featured free proxy + scanner, the open-source counterpart to Burp, great for CI automation), and **mitmproxy** (scriptable Python proxy, the pick for unattended assertions, see the automation section). For *static* analysis there's **Semgrep/Bandit** (12.3); for dependency CVEs, **npm audit/pip-audit/Trivy**. Burp is the *dynamic, over-the-wire* tool; these others cover the static and dependency angles, defense in depth in your own toolchain.

The mental placement: Burp answers "what does the running server actually do when I send *this*?" That's complementary to reading the code (static analysis) and to checking dependencies, and on your own apps you want all three.

## Build it - a guided workflow on local Juice Shop

All steps target `http://localhost:3000` only. The aim is *understanding the mechanism and the defense*, not collecting exploits.

> **Beginner orientation:** the loop for *everything* below is the same four moves, **Capture** (Proxy/HTTP history), **Send to Repeater** (Ctrl+R / right-click → Send to Repeater), **Modify** one thing, **Resend** (the **Send** button) and read the response. Once you internalize that loop, you can do any of these steps without memorizing menus.

### 0. The Repeater loop - practice the core move once (do this first)

Before the security-flavored steps, let's make the Capture→Repeater→Modify→Resend loop automatic on a harmless request.

1. In the Burp browser, load `http://localhost:3000` so the product list appears.
2. Burp → **Proxy → HTTP history**. Find the request that fetches products (something like `GET /api/Products` or `/rest/products/search?q=`). Click it.
3. **Right-click → Send to Repeater** (or Ctrl+R). Switch to the **Repeater** tab, your request is sitting there in an editable pane.
4. Click **Send**. The response shows on the right. Notice the response is JSON product data.
5. Now *modify* something trivial and resend, change a query value, add a header, and watch the response change. That's the whole feedback loop. Repeater never touches anything but the request you explicitly send, to the host in the request. Safe and surgical.

This 60-second drill is the single most important habit in the chapter. Every "finding" below is just this loop pointed at a security-relevant parameter.

---

### Guided tour - Proxy → Repeater → Comparer → Decoder, each with a concrete Juice Shop example

The four tools you'll actually use form a natural pipeline: **Proxy** captures, **Repeater** experiments, **Comparer** proves, **Decoder** decodes. Let's walk each with a specific local Juice Shop example so the abstract "what each is for" list above becomes muscle memory. All of this is against `http://localhost:3000` only.

#### Proxy - capture the login and *see* what the UI hides

1. Intercept **off**, browse Juice Shop in the Burp browser, register `a@local` and log in.
2. **Proxy → HTTP history**. Filter to in-scope. Find `POST /rest/user/login`.
3. Click it and read the bottom panes. The **request** body is `{"email":"a@local","password":"..."}`. The **response** contains `{"authentication":{"token":"eyJ...","bid":...,"umail":"a@local"}}`.

*What the Proxy just showed you that the browser hid:* the exact shape of the auth flow, that the token comes back in the JSON body, and every header the server sees. **Concrete takeaway:** the login `POST` has no visible throttle and the token is a JWT, two things you'll examine next. (Maps to A07, identification & authentication failures.)

#### Repeater - replay the login with edits, no UI in the way

1. On that `POST /rest/user/login`, **right-click → Send to Repeater** (Ctrl+R).
2. In **Repeater**, click **Send**, confirm you get a 200 + token (your authorized baseline).
3. Now *modify and resend* to learn server behavior:
   - Wrong password → observe the error shape and status (is it a *generic* 401, or does it leak "user exists, wrong password"? Generic is correct, A07).
   - Send the same request 10× rapidly with the **Send** button → is there *any* rate limiting or lockout? (In Juice Shop, no, which is the intentional flaw you're here to recognize.)

*Concrete takeaway:* Repeater let you test the login *as a malicious client would*, bypassing the UI entirely. The lack of throttle and any "which field was wrong" leakage are findings. **Defense (A07, 09.4):** rate-limit per IP/account, add lockout/backoff, return a single generic "invalid credentials," use Argon2 verify in constant time.

#### Comparer - turn "I think it's different" into proof

1. Capture two responses you want to compare, e.g., **your own basket** (`GET /rest/basket/1` with your token) and a **tampered basket** (`GET /rest/basket/2`, see the IDOR section below).
2. Right-click each in HTTP history (or Repeater) → **Send to Comparer**.
3. In **Comparer**, select the two items, click **Words** (or **Bytes**).
4. Burp highlights every difference. If the tampered response contains *different user data* than yours, the highlighted diff **is the evidence** for the finding.

*Concrete takeaway:* Comparer converts a hunch ("that looked like someone else's basket") into a defensible, screenshot-able diff, exactly what a findings report needs. **Defense (A01):** the diff proving cross-user data access is the proof that the server isn't scoping by owner; fix is `WHERE owner_id = :current_user` + RLS.

#### Decoder - is that "token" actually a secret, or just encoded data?

1. From the login response, copy the JWT (the `eyJ...` string).
2. **Decoder** → paste it → it has three dot-separated segments. Select the **middle** segment → **Decode as → Base64**.
3. Read the JSON claims that appear: `{"status":"success","data":{"id":...,"email":"a@local","role":"customer","iat":...,"exp":...}}`.

*Concrete takeaway:* the token is **readable**, a JWT is *signed, not encrypted*. That is **not** a vulnerability by itself. It *becomes* one only if the server fails to verify the signature, or trusts a client-changed claim like `role: admin`. Decoder is also where you'd notice the classic bad pattern "this opaque-looking id is actually just Base64 of the user id" (predictable → enumerable). **Defense (A02/A07):** never put secrets in a JWT payload; always verify the signature server-side; never trust client-supplied `role`/`isAdmin`; reject `alg: none`.

**The pipeline in one sentence:** Proxy *finds* the interesting request, Repeater *experiments* on it, Decoder *inspects* its encoded parts, and Comparer *proves* the difference, and each example above ends in a named 12.3 defense, which is the only reason you ran it.

#### Bonus - Sequencer on your own session tokens (defensive entropy check)

A quick, purely-defensive use of **Sequencer** against *your own* local app: capture a request that issues a fresh session token, send it to **Sequencer**, point it at the token in the response, and **Start live capture**. Burp collects a few thousand tokens and reports an **entropy estimate**. What you want to see: high, consistent entropy with no detectable structure, meaning your tokens are unpredictable. A *finding* would be low entropy or visible patterns (e.g., a counter, a timestamp, Base64 of the user id), which means tokens are guessable → session prediction (A07). **Defense:** generate tokens from a cryptographically secure RNG (12.1) with enough length; never derive them from predictable inputs. This is you auditing your own app's randomness, not attacking anyone.

### 1. Intercept a login and inspect the request

- Proxy → *Intercept on*. In the Burp browser, submit the Juice Shop login form.
- Burp pauses the request. Read the raw HTTP: method, path (`POST /rest/user/login`), headers, and the JSON body `{"email": "...", "password": "..."}`.
- Forward it; in the *response* you find the **auth token** the server returns.

**What you're learning:** the shape of the auth flow, where the token lives, what headers carry session state. *Defensive takeaway (A07):* the token should be opaque and unguessable; the login should be rate-limited.

### 2. Inspect the token with Decoder

- Copy the auth token into **Decoder**. If it's a JWT, Base64-decoding the middle segment reveals the **claims** (it's signed, not encrypted, JWTs are *readable*).
- Observe what's in it (email, role, expiry).

**Defensive takeaway (A02/A07):** never put secrets in a JWT payload (it's readable); always *verify the signature* server-side and never trust client-supplied claims like `role` without re-checking server-side. A classic real bug is accepting a token with `alg: none` or trusting an unverified `isAdmin` claim.

### 3. Tamper a parameter to observe broken access control (IDOR)

- Browse to a resource tied to your user (e.g., view your basket: `GET /rest/basket/<your_id>`). Capture it.
- Send to **Repeater**. Change the basket id to a different number and resend.
- *If* the server returns another basket, that's **IDOR / broken access control (A01)**: the server fetched by id without checking ownership.

**Defensive takeaway (A01):** scope every query by the authenticated user; enforce ownership server-side; use Postgres RLS for tenant isolation. The fix is exactly the 12.3 A01 pattern. (Juice Shop is *designed* to have this flaw so you can recognize it; your job is to make sure NYX/Anneava never does.)

### 4. Observe an injection point

- Find an input that feeds a query (Juice Shop's product search / login is intentionally injectable).
- In **Repeater**, modify the parameter to include SQL metacharacters (e.g., a quote) and observe whether the response changes in a way that reveals the input reaches the SQL interpreter (an error, or altered result set).

**Defensive takeaway (A03):** any input that changes query *behavior* (not just data) signals string-concatenated SQL. The fix is parameterized queries (12.3 A03). You're confirming the *mechanism*, input crossing the data/code boundary, so you'll never write that pattern.

### 5. Use Comparer to confirm a finding

- Capture the authorized response and the tampered/unauthorized response.
- Send both to **Comparer** → diff. A clear difference (e.g., you received data you shouldn't) is the *evidence* for the finding.

### Step-by-step detail for the beginner: confirming an IDOR end to end

Let's write step 3 (the IDOR) out fully, because it's the canonical exercise and the one a beginner gets stuck on. (Juice Shop is *built* to have this flaw on the basket endpoint; that's the point of a practice target.)

1. **Set up two identities.** Register two throwaway accounts in Juice Shop (e.g., `a@local` and `b@local`). Log in as **A**, add an item to A's basket.
2. **Find A's basket request.** In **Proxy → HTTP history**, locate the request that loads the basket, something like `GET /rest/basket/1` with an `Authorization: Bearer ...` header (A's token). Note the basket id in the path.
3. **Send to Repeater** (Ctrl+R). In Repeater, **Send** once to confirm you get *your own* basket back (status 200, your items). This is your "authorized" baseline.
4. **Tamper the id.** Change the basket id in the path from `1` to a neighboring number (e.g., `2`), *but keep A's token*. **Send** again.
5. **Read the result.** If the server returns a *different* basket (one that isn't A's), that's **broken access control / IDOR (A01)**: the server looked up the object by id without checking it belongs to the caller.
6. **Capture the evidence.** Send the authorized response (basket 1) and the tampered response (basket 2) to **Comparer**, run the **Words/Bytes** diff, and screenshot it. The diff *is* the proof.
7. **Stop there.** You've demonstrated the mechanism on your own local app. Don't go enumerating every id, the point was understanding, not collecting other (simulated) users' data.

**Defensive translation (the whole reason you did this):** the fix is the 12.3 A01 pattern, `WHERE id = :basket_id AND owner_id = :current_user` so the query *physically can't* return someone else's basket, plus Postgres RLS as a second wall. Back on NYX/Anneava you'd write a regression test (the `test_idor_blocked` from 12.3 mini-project #2) that proves this can never happen.

### 5b. Session lifecycle - verify logout and expiry actually invalidate (local)

A subtle, common bug a proxy is perfect for catching on your *own* apps: does "log out" actually invalidate the token server-side, or does it just delete the cookie client-side and leave the token valid forever? The UI hides this; Repeater exposes it.

1. **Log in** and capture an authenticated request that carries the token; **Send to Repeater** and confirm a 200 baseline.
2. **Log out** in the app UI.
3. **Replay the *old* request in Repeater**, same captured token, unchanged. **Send.**
4. **Read the result:**
   - **Correct:** the server returns **401**, logout invalidated the token server-side. ✓
   - **Bug:** the server still returns **200** with your data, logout only cleared the client cookie; the token is a valid bearer credential forever (until natural expiry). That's a session-management finding (A07).
5. **Expiry check (optional):** decode the token's `exp` claim in Decoder; if there's no expiry, or it's far in the future, that's a weak-session finding even if logout works.

**Defensive translation (A07):** for stateful sessions, invalidate the session server-side on logout (delete/blocklist it). For stateless JWTs (which can't be "deleted"), keep access tokens short-lived and maintain a server-side revocation/denylist for logout, plus rotate refresh tokens. You'd regression-test this with a pytest: log in, log out, replay the old token, assert 401.

### 6. Cookie flags & CSRF posture - read them straight off the wire (local)

Two of the most common A05 findings are visible the instant you look at a `Set-Cookie` header in Burp, no tampering needed, just *reading* the response the proxy reveals. You do this on your own local apps constantly.

1. **Capture the login response** (Proxy → HTTP history → the `POST` that authenticates). Look at the `Set-Cookie` header in the response pane.
2. **Read the flags** on the session cookie and check each:
   - `HttpOnly`, present? If missing, JavaScript (an XSS payload) can read the cookie → session theft. *Defense:* set `HttpOnly`.
   - `Secure`, present? If missing, the cookie can ride over plain HTTP and leak. *Defense:* set `Secure`.
   - `SameSite=Lax|Strict`, present? If missing/`None` without good reason, the cookie is sent on cross-site requests → CSRF exposure. *Defense:* `SameSite=Lax` (or a CSRF token for state-changing requests).
3. **Map it:** every missing flag is an **A05 (security misconfiguration)** finding you'd write up for your own app, with the exact one-line fix.

```
# A GOOD session cookie response header looks like this (what I want to SEE in Burp):
Set-Cookie: session=...; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=3600
# A finding looks like this (flags missing):
Set-Cookie: session=...; Path=/
```

*Why you do this from the proxy and not the browser devtools:* the proxy shows you the **raw** header the server actually sent, before any browser normalization, and it's the same view you'd use to confirm the fix landed after you change your own app's cookie config. This is pure defensive reading: you're auditing your own server's output, not attacking anything.

### 7. CORS allowlist vs reflection - a two-request check (local)

The last quick A05 check you run on your own APIs: does the server **reflect** any `Origin` it's given back into `Access-Control-Allow-Origin`, or does it enforce an **allowlist**? Reflection (especially with credentials) means a malicious site could make authenticated cross-origin requests on a victim's behalf.

1. **Capture an API request** in Proxy and **Send to Repeater**.
2. **Add a forged Origin header:** `Origin: https://evil.example`. **Send.**
3. **Read the response headers:**
   - **Correct (allowlist):** `Access-Control-Allow-Origin` is *absent* or set to your real allowed origin (e.g., `https://app.nyxfinance.com`), **not** `evil.example`. ✓
   - **Bug (reflection):** the response sets `Access-Control-Allow-Origin: https://evil.example` (and worse if `Access-Control-Allow-Credentials: true` is also present). That's a CORS misconfiguration (A05).
4. **Defense:** validate `Origin` against a strict allowlist server-side; never reflect arbitrary origins; never combine a wildcard `*` with credentials. Regression-test it: send `Origin: https://evil.com` and assert the response does **not** reflect it.

This is the exact check that's already a row in mini-project #2's defensive table and the mitmproxy addon in mini-project #3, so a CORS regression fails CI, not "gets noticed later."

### Reading raw HTTP - the anatomy a proxy reveals

Burp shows you the *raw* request/response, which is worth internalizing because it's where security actually lives. A captured request looks like:

```
POST /rest/user/login HTTP/1.1
Host: localhost:3000
Content-Type: application/json
Authorization: Bearer eyJhbGciOiJ...        ← session credential
Cookie: token=eyJ...; lang=en               ← cookie-borne state
Content-Length: 54

{"email":"test@local","password":"hunter2"}  ← body the SERVER actually parses
```

Things to train your eye to notice (each maps to a defense in 12.3):

- **Where does authorization live?** A `Bearer` header or a `Cookie`. If it's a cookie, is it `HttpOnly` + `Secure` + `SameSite` (XSS/CSRF defense)? Burp's response shows the `Set-Cookie` flags.
- **What does the server trust from the client?** Hidden form fields, a `role`/`isAdmin` field, a price, a quantity, an account id in the path. Anything the client sends, a malicious client can change, so the server must re-validate/re-authorize it. The proxy is how you *see* the full set of inputs the UI hides.
- **Headers that matter for security:** `Content-Security-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options`, `Set-Cookie` flags, CORS `Access-Control-Allow-Origin`. Their *absence* in a response is itself a finding (security misconfiguration, A05). Review these on your *own* apps' responses constantly.

### Guided lab - manual input fuzzing in Repeater, the safe and methodical way (local)

Before reaching for Intruder's automation, the beginner skill is *manual* fuzzing in Repeater: send one carefully chosen value at a time, read the response, and reason about what it reveals. It's slower than automation but it builds the instinct, and it's exactly how you'd probe your *own* app's input handling to confirm validation is server-side. All local.

Pick one parameter that reaches server logic (a search term, a quantity, an id) and send this small, deliberate set, **predicting** each result:

| Input you send | What you're probing | Correct (hardened) response |
|---|---|---|
| A normal value (baseline) | the happy path | 200, expected data |
| A single quote `'` | does input reach a SQL interpreter? (A03) | no error/behavior change, treated as data |
| `<script>alert(1)</script>` | is output encoded? (XSS) | rendered inert / encoded, not executed |
| A 10,000-char string | length validation server-side | rejected (422/400), no crash |
| A negative or non-numeric where a number is expected | type/range validation | rejected (422/400) |
| Wrong type entirely (array where string expected) | schema validation | rejected, generic error |
| Removing a required field | required-field enforcement | rejected, generic error |

For each: **Send** in Repeater, read the **status code** and **body**, and ask the one question that matters, *"did the server enforce the rule, or did it trust the malformed input?"* A generic rejection (422/400, no stack trace) is the hardened answer; a 500 with a traceback, or accepted bad data, is the finding.

**Confirm with Comparer.** Send the baseline response and a suspicious response to **Comparer** and diff them. The diff turns "that long string did something weird" into concrete evidence (a different status, a leaked error string, altered data).

**Why manual first:** doing it by hand forces you to *understand each payload class and its named defense* (A03 → parameterize, XSS → encode + CSP, oversized/typed → server-side validation), instead of letting a tool spray a wordlist you don't understand. On your own apps, each row above becomes a pytest that asserts the hardened response, turning the manual probe into a permanent CI guarantee.

### Intruder - fuzzing/enumeration *concepts* (and why your apps must resist them)

Intruder automates sending a request many times with one or more positions varied from a payload list. The point here is to understand the *attack classes* it represents so you build resistance, not to weaponize it:

- **Sniper (one position, a wordlist):** e.g., iterate an `id` or fuzz a parameter. This is the engine behind **enumeration** (IDOR via sequential ids) and **brute force**. *Defense:* server-side authorization on every object (A01), rate limiting + lockout (A07, 09.4), and unguessable identifiers (UUIDs) so enumeration is infeasible.
- **Cluster bomb (multiple positions):** combinations, e.g., username × password lists, **credential stuffing**. *Defense:* rate limit, MFA, breached-password checks, account lockout/backoff.
- **Payload processing/grep-match:** Intruder can flag responses that differ (a different length/status), which is how an automated tool *finds* the one id/credential that worked. *Defense:* uniform responses that don't leak which guess was "closer" (generic 401/404, constant-time auth, ties to 12.1 timing attacks).

In Burp Community, Intruder is throttled, fine, because you only need to *understand* the technique. The real lesson is the mirror image: **every Intruder attack class has a named defense you already know from 12.3 and 09.4.** When you see how trivially a tool iterates ids or replays logins, "add rate limiting and server-side authz" stops being abstract.

### Automating with the Burp / Python ecosystem (orientation, not a how-to-attack)

Manual Repeater is where you *learn*; for *repeatable* checks you want code. The point of this section is to know the landscape so your own defensive verification can be scripted into CI, never to point automation at anything you don't own.

- **Burp's own automation surface.** Pro exposes a **REST API** and the **Montoya API** (Java extensions) so Burp can be driven programmatically and extended. The community marketplace (**BApp Store**) has extensions; the relevant defensive one to know is **Logger++** for richer request logging. Community edition is mostly manual by design, which is fine, because the *understanding* comes from doing it by hand.
- **The scriptable-proxy alternative: `mitmproxy`.** For automation you'll actually reach for `mitmproxy`, which is free, Python-scriptable, and does the same intercepting-proxy job. You can write an *addon* that asserts properties of your own app's traffic, turning "eyeball the headers in Burp" into an automated test:

```python
# headers_check.py - a tiny mitmproxy addon that flags MY OWN app's missing security headers.
# Run: mitmproxy -s headers_check.py   (then drive my LOCAL app through it)
from mitmproxy import http

REQUIRED = ["Content-Security-Policy", "Strict-Transport-Security",
            "X-Content-Type-Options", "X-Frame-Options"]

def response(flow: http.HTTPFlow) -> None:
    if "localhost:8000" not in flow.request.host_header:   # scope to MY local app only
        return
    missing = [h for h in REQUIRED if h not in flow.response.headers]
    if missing:
        print(f"[A05] {flow.request.path} missing: {', '.join(missing)}")
```

- **Plain `requests`/`httpx` for protocol-level regression tests.** You don't even need a proxy to assert server-side enforcement; you can hit your own local app directly and assert the security property, and *this* is what belongs in CI:

```python
# Defensive regression test - runs in CI, no proxy needed. Targets MY local app only.
import httpx
BASE = "http://localhost:8000"

def test_requires_auth():
    r = httpx.get(f"{BASE}/accounts/1")               # no Authorization header
    assert r.status_code == 401                        # fail CLOSED, not data

def test_idor_blocked(user10_token):
    r = httpx.get(f"{BASE}/accounts/2",                # account owned by someone else
                  headers={"Authorization": f"Bearer {user10_token}"})
    assert r.status_code == 404                        # not 200 + account 2

def test_security_headers_present():
    r = httpx.get(f"{BASE}/health")
    for h in ("Content-Security-Policy", "Strict-Transport-Security",
              "X-Content-Type-Options", "X-Frame-Options"):
        assert h in r.headers
```

**The division of labor:** Burp/mitmproxy are for *exploratory* verification ("what does the server do if I send *this*?"); the `httpx`/pytest suite is the *permanent* guarantee that re-runs on every PR. Automation here is pointed exclusively at your own local targets, the ethics rule applies to scripts exactly as to clicks.

### The defender's view - using Burp to *verify your own* hardening

The best use of Burp for you isn't offense; it's **regression-testing your own defenses** on a local copy of NYX/Anneava:

1. **Confirm client-side controls are also server-side.** Disable a button in the UI, then replay the request anyway in Repeater, does the server reject it? If a "you can't transfer more than your balance" check is only in JS, Repeater proves it (and you go fix the server).
2. **Confirm authorization holds under tampering.** Log in as a low-privilege test user, capture an admin-only request, replay it, the server must return 403/404. This is your IDOR/broken-access-control regression test.
3. **Confirm security headers are present.** Eyeball responses for CSP, HSTS, cookie flags, and correct CORS, missing ones are A05 findings on your own app.
4. **Confirm inputs are validated server-side.** Send over-long, wrong-type, or metacharacter-laden values in Repeater and verify Pydantic/validation rejects them with a generic error (no stack trace, A05).

Run against a *local* instance of your own app, this turns Burp into a security test harness you can fold into your dev process, the same mindset as the before/after review in 12.3, but verified from the outside over real HTTP.

### Mapping the workflow back to 12.3 defenses

This is the table to keep returning to: **every observation Burp gives you ends at a specific OWASP item and a specific 12.3 defense.** That mapping is the entire reason the tool matters defensively, a finding is only useful if it points to a fix you'll implement in your own apps.

| Burp observation (on local target) | OWASP item | Exact defense (from 12.3) |
|------------------|-----------|---------------------|
| Login has no throttle; many rapid Repeater sends accepted | A07, Auth failures | Rate limit + lockout/backoff (09.4); generic 401; Argon2 verify |
| Changing an `id` in Repeater returns another user's data | A01, Broken access control | Server-side ownership check (`AND owner_id = :current_user`) + Postgres RLS |
| A metacharacter (`'`) alters query behavior / errors | A03, Injection | Parameterized queries / ORM; never concatenate input into SQL |
| Reflected input renders as executable script | A03 (XSS family) | Output encoding + Content-Security-Policy + `HttpOnly` cookies |
| Decoder shows token is readable; `role` claim present | A02, Cryptographic failures | Don't store secrets in JWT; verify signature server-side; never trust client `role`; reject `alg:none` |
| Response missing CSP/HSTS/`X-Content-Type-Options`/cookie flags | A05, Security misconfiguration | Add the headers + secure cookie flags (`HttpOnly`/`Secure`/`SameSite`) |
| Verbose error / stack trace returned to client | A05, Security misconfiguration | Generic error to user, detail only to logs |
| `Origin: https://evil.com` reflected in CORS header | A05 / broken access | CORS allowlist, not reflection; never `*` with credentials |
| Predictable/sequential identifiers (Base64 of user id) | A01 enabler | Unguessable identifiers (UUIDs) so enumeration is infeasible |

The discipline: **don't record a finding without filling the right two columns.** "I changed an id and got someone's basket" is incomplete; "A01, fix with server-side ownership scoping + RLS, regression-tested by `test_idor_blocked`" is a finding you can act on.

### Guided lab - prove a JWT's signature is actually verified (local, end to end)

The Decoder section showed you a JWT is *readable*; this lab proves whether your own server actually *verifies the signature*, the single thing that separates "readable claims, fine" from "privilege escalation." Run against **your own local app** (the 12.3 secure starter) or DVWA/Juice Shop as a teaching target.

1. **Capture an authenticated request** in Proxy that carries `Authorization: Bearer eyJ...`. Send it to **Repeater**; **Send** once to confirm a normal 200 baseline.
2. **Decode the token** in Decoder (middle segment → Base64) and note a claim you'd love to escalate, e.g. `"role":"customer"`.
3. **Tamper the payload, keep the old signature.** In Decoder, change `"role":"customer"` → `"role":"admin"`, re-encode that segment to Base64, and paste it back as the new middle segment of the token (leaving the third/signature segment untouched). Put the tampered token in Repeater's `Authorization` header and **Send**.
4. **Predict and read the result:**
   - A **correct** server *rejects* it (401/403), the signature no longer matches the tampered payload, so verification fails. ✓ This is what you want to see on NYX/Anneava.
   - A **broken** server *accepts* it and treats you as admin, proving it does **not** verify the signature, or trusts the `role` claim blindly. That's the A02/A07 bug.
5. **Also test `alg:none`.** Re-encode the header segment with `"alg":"none"` and drop the signature entirely. A correct server rejects unsigned tokens; an old/broken library might accept them.

**Defensive translation:** the fix is to *always verify the signature server-side with the expected algorithm*, reject `alg:none`, and never trust a client-supplied `role`/`isAdmin`, re-authorize server-side from a trusted source. You'd encode this as a pytest that sends a payload-tampered token and asserts 401, so the protection can never silently regress.

### The whole local workflow on one card

When you sit down with Burp + a local target, this is the loop, every time:

```
1. SCOPE      Target → Scope → add http://localhost:<port> ONLY. (ethics backstop)
2. CAPTURE    Open Browser, browse the app, watch Proxy → HTTP history fill.
3. PICK       Find the security-relevant request (login, /basket/{id}, a search).
4. EXPERIMENT Ctrl+R → Repeater → change ONE thing → Send → read the response.
5. INSPECT    Decoder for tokens/encoded params; read Set-Cookie / CORS headers.
6. PROVE      Comparer to diff authorized vs tampered → that diff is the evidence.
7. MAP        Every finding → OWASP item + the exact 12.3 fix (the table above).
8. REGRESS    Turn each check into a pytest so it can't silently come back.
9. TEARDOWN   Stop the container; remove Burp's CA from any real browser.
```

Steps 1 and 9 are the ethics guardrails (scope only your own target; clean up the CA). Steps 4-6 are the craft. Step 7-8 are the *point*, a finding you can't map to a defense and a regression test isn't done.

## Mini-project #3 - A repeatable defensive proxy harness in CI (mitmproxy + your own app)

Mini-projects #1 and #2 are *interactive*, you click through Burp. The gap they leave is that you only catch a regression when you *remember* to open Burp. This project closes that gap: turn the manual header/authz checks into a **scripted proxy + assertion harness** that runs unattended, exclusively against your own local app. It's the natural endpoint of the "Automating with the Burp/Python ecosystem" section.

**1. Stand up your own app and an assertion proxy:**

```bash
uvicorn secure_starter:app --port 8000 &            # MY app (from 12.3), the only target
pip install mitmproxy
```

**2. Write an addon that asserts *defensive* properties of your own traffic** (extends the snippet above):

```python
# defense_assert.py - fails loudly if MY local app's responses miss security controls.
from mitmproxy import http

REQUIRED_HEADERS = ["Content-Security-Policy", "Strict-Transport-Security",
                    "X-Content-Type-Options", "X-Frame-Options"]
findings = []

def response(flow: http.HTTPFlow) -> None:
    host = flow.request.host_header or ""
    if "localhost:8000" not in host:                 # scope guard: my app ONLY
        return
    # A05: missing security headers
    missing = [h for h in REQUIRED_HEADERS if h not in flow.response.headers]
    if missing:
        findings.append(f"A05 {flow.request.path}: missing {missing}")
    # A05: verbose error leaking a stack trace
    if flow.response.status_code >= 500 and b"Traceback" in flow.response.content:
        findings.append(f"A05 {flow.request.path}: stack trace leaked to client")
    # A05: CORS reflecting an arbitrary Origin
    acao = flow.response.headers.get("Access-Control-Allow-Origin", "")
    if acao == flow.request.headers.get("Origin") and acao not in ("", "https://app.nyxfinance.com"):
        findings.append(f"A05 {flow.request.path}: CORS reflects arbitrary origin {acao}")

def done():
    for f in findings:
        print("FINDING:", f)
```

**3. Drive your own app through the proxy and let the addon assert:**

```bash
# Replay a small fixed set of MY requests through the proxy (curl with --proxy).
mitmdump -s defense_assert.py &
curl -s --proxy 127.0.0.1:8080 http://localhost:8000/health > /dev/null
curl -s --proxy 127.0.0.1:8080 -H "Origin: https://evil.com" http://localhost:8000/health > /dev/null
# Any "FINDING:" line printed = a defense regressed.
```

**4. The point, fold it into CI as a gate.** Wrap the above in a script that exits non-zero if any finding is printed, and run it in the pipeline. Now a PR that accidentally drops a security header *fails the build*, not "gets noticed in a Burp session three weeks later."

**Deliverable:** the addon, a recorded run showing zero findings on the hardened app and a deliberately-broken commit (remove one header) showing the harness catching it, plus a note: *Burp/mitmproxy interactive = exploration; this harness = the permanent, unattended guarantee, both pointed only at your own local app.*

## Common mistakes

Beginner foot-guns with the tool *and* the mindset:

- **HTTP history is empty.** Traffic isn't going through Burp. Use **Open Browser** from the Proxy tab (pre-wired), or set your own browser's proxy to `127.0.0.1:8080` *and* install Burp's CA.
- **The browser hangs on every page.** Intercept is left **on**. Toggle it off; only turn it on when you want to pause a specific request.
- **HTTPS sites show certificate errors.** Burp's CA isn't trusted by the browser. Use the embedded browser (already trusts it), or install the CA from `http://burpsuite` into the *right* store for that browser (Firefox uses its own; Chrome/Edge/Safari use the OS keychain). (And **remove it when done** if you installed it in your real browser.)
- **Installing the CA in the wrong trust store.** Chrome on macOS reads the system Keychain, not a Chrome setting, importing into Firefox won't fix Chrome and vice versa. Match the store to the browser.
- **Forgetting to remove Burp's CA afterward.** Leaving it trusted means your day-to-day browsing runs with an extra root CA that could MITM you. Delete it the moment testing is done.
- **Forgetting to set scope.** Without scope, Burp logs *all* your browsing. Set scope to the local target so you never even capture anything off-target, a mechanical backstop to the ethics rule.
- **Editing a request but not resending it.** In Repeater you must click **Send** after each change; the response doesn't update on its own.
- **Changing the `Content-Length` by hand and getting confused.** Burp updates it for you on Send in Repeater; don't fight it manually.
- **Thinking Community has the Scanner/active fuzzing at full speed.** It doesn't, Intruder is throttled and there's no automated Scanner. That's fine: manual Repeater testing teaches the mechanism better anyway.
- **Pointing automation (Intruder/mitmproxy/scripts) at something you don't own.** The ethics rule applies to scripts exactly as to clicks. Scope every addon/script to `localhost`, and never run it against a third party.
- **The biggest mistake: pointing it at something you don't own.** Re-read the ethics section. Local practice apps only, or a signed scope. Always.
- **Collecting exploits instead of understanding + fixing.** The deliverable is always "the mechanism + the defense," mapped back to 12.3, not a pile of payloads. A finding without its two mapping columns (OWASP item + 12.3 fix) is incomplete.

## On the job / interview angle

Hands-on familiarity with an intercepting proxy is increasingly expected even for general backend/full-stack roles, because "can you verify your app is secure server-side?" is now part of being production-ready, and security/AppSec roles treat Burp as a baseline skill.

**What teams expect (even from a junior):**

- Understand that client-side validation is UX and the *server* is the security boundary, and be able to demonstrate it by replaying a request through a proxy.
- Be able to capture a request, modify it, and reason about whether the server should accept it.
- Map an observed behavior (IDOR, reflected input, missing header) to its named defense (A01, XSS, A05) and the code-level fix.
- Use a proxy *defensively*, to regression-test your own app's authorization and headers, and to script those checks into CI.
- Know the legal/ethical line cold: only test what you own or are authorized (in writing) to test.

**Representative interview questions (with crisp answers):**

1. *"What is an intercepting proxy and why is it useful?"* → Software between browser and server that lets you view/modify raw HTTP; useful because it bypasses client-side controls so you can verify the *server* enforces security.
2. *"How would you test for IDOR?"* → Authenticate as a low-privilege user, capture a request for one of your objects, replay it in Repeater with another object's id, and check whether the server returns data you shouldn't see; fix with server-side ownership checks + RLS.
3. *"Why does intercepting HTTPS require installing a CA, and what stops a real attacker doing this to me?"* → The proxy must terminate TLS, so the browser must trust its cert; a real attacker can't unless they already control your device or trick you into installing their CA, and HSTS + cert pinning resist it.
4. *"You decode an auth token and can read `role: user`. Is that a vulnerability?"* → Only if the server *trusts* the claim without verifying the signature / re-checking authorization. Readable claims are fine (JWTs are signed, not encrypted) as long as the server verifies the signature and never trusts client-supplied roles; `alg: none` or unverified claims are the bug.
5. *"What's the difference between Repeater and Intruder?"* → Repeater = manual single-request replay with edits (the main workhorse); Intruder = automated many-variation sending (fuzzing/enumeration), throttled in Community. Every Intruder attack class maps to a defense: rate limiting, lockout, unguessable ids.
6. *(Defensive framing)* *"How do you use Burp on your own app?"* → As a regression harness: replay requests with auth removed/tampered to confirm 401/404, check security headers and CORS, send malformed input to confirm server-side validation, then encode those as automated tests in CI.
7. *"Walk me through the four core Burp tools and what each tells you."* → Proxy captures and shows raw HTTP the server actually receives; Repeater replays one request with edits for a tight experiment loop; Decoder decodes encoded parts (Base64/URL/JWT segments) to inspect tokens/params; Comparer diffs two responses byte/word-wise to *prove* a tamper changed the result. Pipeline: Proxy finds → Repeater experiments → Decoder inspects → Comparer proves, each ending in a 12.3 defense.
8. *"How would you make these security checks repeatable rather than manual?"* → Script them: hit the app with `httpx`/pytest to assert 401 on missing auth, 404 on IDOR, presence of CSP/HSTS, and a non-reflecting CORS header; optionally a mitmproxy addon that asserts response properties. Wire it into CI so a regression fails the build, Burp for exploration, the test suite for the permanent guarantee.
9. *"How do you install and then safely remove a CA cert across browsers?"* → Firefox has its own trust store (Settings → Certificates → Authorities → Import); Chrome/Edge/Safari use the OS store (macOS Keychain set to Always Trust, Windows Trusted Root, Linux `update-ca-certificates`). Remove it from the same store afterward; leaving an extra trusted root is a standing MITM risk.

## Exercises

All against **local** practice targets (Juice Shop / DVWA in Docker) or your own local app only. Easy → hard.

1. **(Plumbing)** Get Burp's embedded browser to load `http://localhost:3000` and confirm at least 5 requests appear in **Proxy → HTTP history**. What does an empty history mean?
2. **(Intercept)** Turn Intercept on, submit the Juice Shop login, and identify in the paused request: the method, the path, and where the credentials live (header or body).
3. **(Repeater loop)** Send a product-search request to Repeater, change the search term, and resend. Describe how the response changed.
4. **(Decoder)** Take the auth token returned at login and decode its middle segment in Decoder. List the claims you can read, and state why being able to read them is *not by itself* a vulnerability.
5. **(IDOR)** Using two throwaway accounts, follow the step-by-step IDOR walkthrough and confirm (or refute) that you can read another basket. State the exact server-side fix.
6. **(Headers as findings)** Inspect a response from your *own* local app and list which of CSP, HSTS, `X-Content-Type-Options`, `X-Frame-Options`, and the `Set-Cookie` flags are present. Which absences are A05 findings?
7. **(Client vs server)** Find a client-side validation in a local app (e.g., a max-length field), then bypass it by sending an oversized value in Repeater. Does the server reject it? What does the result prove about where security lives?
8. **(DVWA before/after)** On DVWA, demonstrate an injection at security level **Low**, then switch to **High** and show the same input is now inert. Name the defense that changed.
9. **(Comparer evidence)** Capture an authorized and an unauthorized response, diff them in Comparer, and write a one-paragraph "evidence" note suitable for a findings report.
10. **(Tool pipeline)** Run the full Proxy→Repeater→Decoder→Comparer tour on the Juice Shop login/basket flow and, for each tool, write one sentence: what it showed you and which 12.3 defense it pointed to.
11. **(CA install)** On your own machine, install Burp's CA into the correct store for your browser, confirm an HTTPS site loads without warning through Burp, then *remove it* and confirm the warning returns. Explain why this round-trip is itself a defensive lesson.
12. **(Cookie flags)** Capture the login response from your own local app and read the session `Set-Cookie` header. List which of `HttpOnly`, `Secure`, `SameSite` are present, and state the one-line fix and OWASP item for each that's missing.
13. **(JWT verification)** Tamper a JWT payload (change `role` to `admin`) while keeping the original signature, replay it, and report whether the server accepts it. What does each outcome tell you, and what's the defense?
14. **(Hard / synthesis)** Run the mini-project #2 defensive harness against your own FastAPI app, produce the filled pass/fail table, write the matching pytest for every check, and add the mini-project #3 mitmproxy addon to catch missing security headers in CI.

### Solutions

1. Use **Proxy → Open Browser** and visit the URL; history populates. An empty history means traffic isn't routed through Burp, wrong proxy setting, or you used a non-Burp browser without configuring its proxy + CA.
2. Method `POST`, path `/rest/user/login`, credentials in the **body** as JSON (`{"email":...,"password":...}`). The session token comes back in the *response*.
3. The JSON product list changes to match the new search term (or returns fewer/more results), confirming the parameter reaches the server's query logic and the loop works.
4. Base64-decoding the JWT middle segment shows claims like `email`, `role`, `iat`/`exp`. Readable ≠ vulnerable because JWTs are *signed, not encrypted*; it's only a bug if the server doesn't verify the signature or trusts a client-changed `role`.
5. Following the walkthrough: changing the basket id while keeping your token returns a basket you don't own → IDOR confirmed. Fix: scope the query to the authenticated owner (`AND owner_id = :current_user`), 404 otherwise, plus Postgres RLS.
6. List what's present vs absent; missing CSP, HSTS, `X-Content-Type-Options`, `X-Frame-Options`, or missing `HttpOnly`/`Secure`/`SameSite` on the session cookie are each **A05 (security misconfiguration)** findings on your own app.
7. The browser blocks the oversized value, but Repeater sends it anyway. If the server still rejects it (422/400) the server is the real boundary; if it *accepts* it, the validation was client-only, proving security must be enforced server-side.
8. At **Low** the quote produces a SQL error (string-concatenated query); at **High** the same input is inert because the query is **parameterized**, the data/code boundary is enforced. The defense that changed is parameterized queries (12.3 A03).
9. e.g., *"Authenticated as user A (token captured), a request for object id 2 (owned by user B) returned B's data (status 200). Comparer diff of the authorized response (object 1) vs the tampered response (object 2) shows distinct user data, confirming broken access control. Severity High; fix: server-side ownership scoping + RLS."*
10. Example: **Proxy** showed the raw `POST /rest/user/login` and that the token returns in the body → A07 (rate-limit the login). **Repeater** let you resend the login 10× with no throttle → A07 (lockout/backoff). **Decoder** showed the JWT payload is readable with a `role` claim → A02 (verify signature, don't trust claims). **Comparer** diffed your basket vs a tampered id and proved cross-user data → A01 (ownership scoping + RLS).
11. Install into the correct store (Firefox: its own Authorities; Chrome/Edge/Safari: OS keychain), browse an HTTPS site through Burp with no warning (CA trusted), then delete it and watch the warning return (no longer trusted). The lesson: a single trusted CA can silently MITM *all* your HTTPS, so on real apps you rely on HSTS + pinning and never install a CA you don't fully control, and you always remove a testing CA afterward.
12. Read the `Set-Cookie` header in Burp's response pane. For each missing flag: missing `HttpOnly` → XSS can steal the session → A05, fix `HttpOnly`; missing `Secure` → cookie leaks over HTTP → A05, fix `Secure`; missing/`None` `SameSite` → CSRF exposure → A05, fix `SameSite=Lax` (or a CSRF token for state-changing requests). The hardened header reads `Set-Cookie: session=...; HttpOnly; Secure; SameSite=Lax`.
13. A **correct** server rejects the tampered token (401/403) because the signature no longer matches the altered payload, readable claims are fine *because* the signature is verified. A **broken** server that accepts it (and treats you as admin) proves it doesn't verify the signature or trusts the client `role` claim, an A02/A07 privilege-escalation bug. Defense: always verify the signature server-side with the expected algorithm, reject `alg:none`, and never trust client-supplied roles; encode a payload-tampered-token-returns-401 pytest so it can't regress.
14. Produce the table from mini-project #2 Part 2 with real results, then write `test_requires_auth`, `test_idor_blocked`, `test_invalid_transfer_rejected`, `test_security_headers_present`, and a CORS test (assert `evil.com` is not reflected), exactly the 12.3 mini-project #2 suite, wire them into CI, and add the mitmproxy `defense_assert.py` addon scoped to `localhost:8000` so a dropped security header fails the build.

## Teach it back

1. **Why is testing only against a self-owned local target (and using a signed scope for anything else) non-negotiable, and what makes Juice Shop in Docker the right practice target?**
2. **Why does intercepting HTTPS require installing Burp's CA cert, which trust store does each browser use, and what real-world defense (in your own apps) makes this kind of interception hard for an actual attacker?**
3. **Client-side form validation looks fine in the browser, but an intercepting proxy bypasses it. What does this prove about where security must be enforced?**
4. **Walk the Proxy→Repeater→Decoder→Comparer pipeline on the Juice Shop login/basket flow, and for each tool name the 12.3 defense the observation pointed to.**
5. **Walk the Repeater workflow for confirming an IDOR, and state the exact server-side fix (and the defense-in-depth DB control).**
6. **How would you turn your manual Burp checks into an automated, unattended guarantee, what runs in CI, and what stays interactive, and why?**
7. **You decode an auth token and can read a `role: user` claim. Why is that fine *if* one thing is true server-side, and what's the dangerous assumption that turns it into a vulnerability?**
