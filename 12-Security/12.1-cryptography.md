## 🌱 Start here - the absolute beginner on-ramp

Before any math, let me ground this in something physical, because "cryptography" sounds intimidating and it really isn't at its core.

**The locked box analogy.** Imagine I want to mail a sensitive document to a friend.

- **Confidentiality** is putting it in a *locked box* so only someone with the key can open it. That's **encryption**.
- **Integrity** is adding a *tamper-evident seal* so my friend can tell if someone opened the box and changed the contents in transit. That's a **hash / MAC / signature**.
- **Authentication** is putting my *signature* on the document so my friend knows it really came from me, not an impostor. That's a **digital signature**.

Every single thing in this chapter is a more precise, mathematical version of "locked box," "tamper seal," or "signature." When a term confuses me later (AEAD, HMAC, PSS, OAEP), I come back here and ask: *is this a lock, a seal, or a signature?* It's always one of those three.

**Why this matters to me specifically.** NYX Finance moves money; Anneava touches health data (PHI). If I get crypto wrong, the failure mode isn't "a feature is buggy", it's "an attacker reads every customer's balance" or "I've committed a HIPAA breach that's legally reportable." Crypto is the one area where "it works in testing" tells me almost nothing, because a broken crypto system *still encrypts and decrypts perfectly*, it's just also readable by an attacker. So the goal of this chapter isn't to memorize APIs; it's to build enough intuition that I can tell when a design is *actually* safe versus merely *functional*.

**The two-sentence summary of the whole field.** (1) Use standard, vetted algorithms with sufficiently long keys, and keep the keys secret and random. (2) Almost every real-world break comes not from defeating the math but from a *misuse*, reusing a nonce, a fast hash on passwords, an unverified signature, predictable randomness. This chapter teaches the math so I respect it, and the misuses so I avoid them.

If I only ever remember one rule: **never roll my own crypto primitives, and never use a primitive without understanding the one rule that breaks it.**

## 📐 Theory

### The four goals (and the CIA triad)

When I say "I secured this data," I should be precise about *what property* I'm guaranteeing. There are four classic goals:

1. **Confidentiality**, only authorized parties can read the data. (Encryption.)
2. **Integrity**, the data wasn't tampered with. (Hashes, MACs, signatures.)
3. **Authentication**, the other party is who they claim to be. (Signatures, certificates, passwords.)
4. **Non-repudiation**, a party can't later deny having sent/signed something. (Digital signatures, *only* asymmetric, because a shared symmetric key proves nothing about *which* party acted.)

The **CIA triad** is the security-program framing of three of these:

- **C**onfidentiality
- **I**ntegrity
- **A**vailability ← note: availability is *not* a crypto goal; it's about uptime/DDoS-resistance (see 12.2). I keep these straight because audiences conflate "encrypted" with "secure."

A trap I want to avoid: **encryption alone gives confidentiality, not integrity.** An attacker can flip ciphertext bits even without reading the plaintext. That's why modern systems use **authenticated encryption** (AES-GCM), confidentiality *and* integrity in one primitive. More on that below.

### Kerckhoffs's principle

The security of a system must rest *only* on the secrecy of the key, never on the secrecy of the algorithm. Algorithms get published, peer-reviewed, attacked for decades. "Security through obscurity" of the algorithm is fragile. So: use **standard, vetted algorithms** (AES, SHA-256, RSA, X25519), keep the **key** secret.

### Symmetric encryption - one shared key

Both parties share one secret key `k`. Same key encrypts and decrypts. Fast (hardware-accelerated AES does GB/s). The problem: *how do both parties get `k`?* (That's what Diffie-Hellman solves later.)

#### Building intuition: the XOR cipher (and breaking it)

XOR (`^`) is the atom of symmetric crypto. Properties:

- `a ^ a = 0`
- `a ^ 0 = a`
- `(a ^ k) ^ k = a` ← encrypt then decrypt with the same key

So a "cipher": `cipher = plaintext ^ key` (byte by byte). Let me build it.

```python
def xor_cipher(data: bytes, key: bytes) -> bytes:
    # Repeat the key to cover the data (this is the WEAKNESS we exploit below).
    return bytes(b ^ key[i % len(key)] for i, b in enumerate(data))

key = b"SECRET"
ct = xor_cipher(b"attack at dawn", key)
pt = xor_cipher(ct, key)   # same function decrypts
assert pt == b"attack at dawn"
```

If the key is **as long as the message, truly random, and never reused**, this is a **one-time pad**, provably unbreakable (Shannon). The catch: you need to share a key as long as all data you'll ever send, which is impractical. So in practice people *reuse* a short key, and that's fatal.

**Why reuse breaks it.** If two plaintexts are XOR'd with the same keystream:

```
c1 = p1 ^ k
c2 = p2 ^ k
c1 ^ c2 = p1 ^ p2     # the key cancels out!
```

The key vanishes. Now I have the XOR of two English sentences, which is very crackable with frequency analysis. Let me break a *single*-message repeating-key XOR (classic "Vigenère on bytes") to feel it:

```python
from itertools import cycle

def break_single_byte_xor(ct: bytes):
    """Try all 256 keys, score by English letter frequency."""
    freq = b"etaoin shrdlu ETAOIN"  # rough common-letter set
    best = None
    for k in range(256):
        pt = bytes(b ^ k for b in ct)
        score = sum(byte in freq for byte in pt)
        if best is None or score > best[0]:
            best = (score, k, pt)
    return best  # (score, key_byte, plaintext)

# A message XOR'd with a single byte falls instantly:
secret = bytes(b ^ 0x42 for b in b"the quick brown fox jumps over")
score, k, pt = break_single_byte_xor(secret)
print(hex(k), pt)   # -> 0x42 b'the quick brown fox jumps over'
```

Lesson burned in: **short/reused keystreams die.** This is *exactly* why nonce/IV reuse in real ciphers (below) is catastrophic.

#### AES - the real symmetric cipher

AES (Advanced Encryption Standard, Rijndael) is a **block cipher**: it encrypts fixed 128-bit (16-byte) blocks under a 128/192/256-bit key. Internally it's a substitution-permutation network, repeated rounds of: SubBytes (S-box nonlinearity), ShiftRows, MixColumns (diffusion), AddRoundKey. I don't need to reimplement it (never roll your own AES), but the key idea: it's a **pseudorandom permutation**, for a fixed key, it maps the 2^128 possible blocks to a fixed, key-dependent shuffle that's computationally indistinguishable from random.

A block cipher only encrypts *one block*. To encrypt arbitrary-length data we need a **mode of operation**.

#### Modes: why ECB is forbidden, and what to use

**ECB (Electronic Codebook):** encrypt each block independently with the same key.

```
c_i = AES(k, p_i)
```

The fatal flaw: **identical plaintext blocks produce identical ciphertext blocks.** Structure leaks. The famous "ECB penguin", encrypting a bitmap with ECB still shows the penguin, because repeated regions encrypt identically. ECB is essentially the reused-keystream problem in block form. **Never use ECB.**

**CBC (Cipher Block Chaining):** XOR each plaintext block with the previous ciphertext block before encrypting.

```
c_0 = AES(k, p_0 ^ IV)
c_i = AES(k, p_i ^ c_{i-1})
```

The **IV** (initialization vector) is a random 16-byte value, fresh per message, that makes the first block unpredictable so identical messages don't produce identical ciphertext. CBC gives confidentiality but **not integrity**, and naive CBC + a "padding error" oracle leaks plaintext (the famous *padding oracle attack*). CBC alone is legacy.

**GCM (Galois/Counter Mode):** this is what I actually use. It's **authenticated encryption with associated data (AEAD)**:

- Turns AES into a stream cipher via a counter (CTR mode): `keystream_i = AES(k, nonce || counter_i)`, then `c_i = p_i ^ keystream_i`. No padding needed.
- Simultaneously computes an **authentication tag** (a MAC over the ciphertext + any associated data) using GHASH. On decrypt, if the tag doesn't verify, decryption *fails closed*, tamper detection built in.
- "Associated data" (AAD) lets me authenticate but not encrypt some context (e.g., a file header, a tenant ID), it's bound to the ciphertext so it can't be swapped.

**The one rule with GCM: never reuse a (key, nonce) pair.** Nonce reuse in GCM is catastrophic, it's the reused-keystream problem (recovers the keystream *and* the authentication key). So nonces must be unique per encryption. I'll use a random 96-bit nonce per message (safe up to ~2^32 messages per key; for huge volumes use a counter).

**IV vs nonce, in my words:** an **IV** needs to be *unpredictable* (random), that's CBC's requirement. A **nonce** needs to be *unique* (never repeated), that's CTR/GCM's requirement. They overlap (random 96-bit value is both unpredictable and almost-surely unique) but the security property each *requires* differs.

### Key exchange - Diffie-Hellman, derived

The whole problem with symmetric crypto: how do two people who've never met agree on a secret key over a public channel an eavesdropper is watching? Diffie-Hellman (1976) solves it with **modular exponentiation** and the **discrete logarithm problem**.

#### The math

Pick a large prime `p` and a **generator** `g` (a number whose powers mod `p` cycle through many residues). These are **public**.

- Alice picks secret `a`, sends `A = g^a mod p`.
- Bob picks secret `b`, sends `B = g^b mod p`.
- Alice computes `s = B^a mod p = (g^b)^a = g^{ab} mod p`.
- Bob computes `s = A^b mod p = (g^a)^b = g^{ab} mod p`.

**Both arrive at `g^{ab} mod p`, the shared secret.** An eavesdropper sees `p, g, A, B` but to get `s` must compute `a` from `A = g^a mod p`. That's the **discrete logarithm problem**, believed hard for large primes. The asymmetry (easy to exponentiate, hard to take the log) is the trapdoor.

#### Tiny worked example (so I can do it by hand)

Let `p = 23`, `g = 5`.

- Alice secret `a = 6`: `A = 5^6 mod 23`. `5^6 = 15625`. `15625 mod 23 = 8`. So `A = 8`.
- Bob secret `b = 15`: `B = 5^15 mod 23`. Compute stepwise: `5^2=25≡2`, `5^4≡2^2=4`, `5^8≡4^2=16`, `5^15 = 5^8·5^4·5^2·5^1 ≡ 16·4·2·5 = 640 ≡ 640 - 27·23 = 640-621 = 19`. So `B = 19`.
- Shared: Alice `B^a = 19^6 mod 23`. Bob `A^b = 8^15 mod 23`. Both equal `2`.

Let me verify in Python:

```python
p, g = 23, 5
a, b = 6, 15
A = pow(g, a, p)   # 8
B = pow(g, b, p)   # 19
s_alice = pow(B, a, p)
s_bob   = pow(A, b, p)
assert s_alice == s_bob   # both = 2
print(s_alice)            # 2
```

`pow(base, exp, mod)` is Python's built-in **fast modular exponentiation** (square-and-multiply), O(log exp) multiplies, which is why DH is feasible with 2048-bit numbers.

**Caveat:** raw DH is vulnerable to a **man-in-the-middle**: an attacker can run two separate exchanges (one with Alice, one with Bob) and relay. DH gives *secrecy* but not *authentication*. Real TLS *authenticates* the DH parameters with the server's certificate/signature (see 06.2 and 12.2). In modern TLS we use **ECDH** (elliptic-curve DH, e.g. X25519), same idea, smaller keys, faster, and **ephemeral** keys per session give **forward secrecy** (compromising the long-term key later doesn't decrypt past sessions).

### Asymmetric (public-key) crypto - RSA, derived

Each party has a **key pair**: a **public key** (shared freely) and a **private key** (kept secret). Encrypt with the public key → only the private key decrypts (confidentiality). Sign with the private key → anyone verifies with the public key (authentication + non-repudiation).

#### Deriving RSA from Euler/Fermat

The number-theory background:

- **Euler's totient** `φ(n)` = count of integers in `[1, n]` coprime to `n`. For a prime `p`, `φ(p) = p-1`. For `n = p·q` with `p, q` distinct primes, `φ(n) = (p-1)(q-1)`.
- **Euler's theorem:** if `gcd(a, n) = 1`, then `a^{φ(n)} ≡ 1 (mod n)`. (Fermat's little theorem is the special case `n` prime: `a^{p-1} ≡ 1`.)

RSA setup:

1. Pick two large primes `p, q`. Let `n = p·q` (the **modulus**). `φ(n) = (p-1)(q-1)`.
2. Choose public exponent `e` with `gcd(e, φ(n)) = 1` (commonly `e = 65537`).
3. Compute private exponent `d = e^{-1} mod φ(n)` (modular inverse, via extended Euclid). So `e·d ≡ 1 (mod φ(n))`, i.e. `e·d = 1 + k·φ(n)` for some integer `k`.

**Why decryption works.** Encrypt: `c = m^e mod n`. Decrypt: `c^d = m^{ed} = m^{1 + kφ(n)} = m · (m^{φ(n)})^k ≡ m · 1^k = m (mod n)`, using Euler's theorem. The trapdoor: to find `d` you need `φ(n)`, which needs the factorization of `n`. **Factoring large `n` is believed hard.** That's RSA's security.

#### Small worked example

`p = 61, q = 53`. `n = 3233`. `φ = 60·52 = 3120`. Pick `e = 17` (`gcd(17,3120)=1`). `d = 17^{-1} mod 3120 = 2753` (since `17·2753 = 46801 = 1 + 15·3120`).

- Encrypt `m = 65`: `c = 65^17 mod 3233 = 2790`.
- Decrypt: `2790^2753 mod 3233 = 65`. ✓

```python
def egcd(a, b):
    if b == 0: return (a, 1, 0)
    g, x, y = egcd(b, a % b)
    return (g, y, x - (a // b) * y)

def modinv(a, m):
    g, x, _ = egcd(a, m)
    if g != 1: raise ValueError("no inverse")
    return x % m

p, q = 61, 53
n = p * q                  # 3233
phi = (p - 1) * (q - 1)    # 3120
e = 17
d = modinv(e, phi)         # 2753
m = 65
c = pow(m, e, n)           # 2790
assert pow(c, d, n) == m
print(c, d)                # 2790 2753
```

**Real-world caveats (so I don't ship toy RSA):**

- Never use **textbook RSA** (`m^e mod n` raw). It's deterministic (same message → same ciphertext) and malleable. Use **OAEP** padding for encryption and **PSS** for signatures, they add randomness and structure.
- RSA encrypts small data only (≤ key size). In practice you use RSA to encrypt a *symmetric key* (hybrid encryption), then AES-GCM for the bulk data.
- Use **2048-bit minimum** (3072+ for long-term). For new systems, **elliptic-curve** (Ed25519 for signing, X25519 for key exchange) is faster with smaller keys.

#### Real RSA with the `cryptography` library

```python
from cryptography.hazmat.primitives.asymmetric import rsa, padding
from cryptography.hazmat.primitives import hashes, serialization

# Generate a real key pair
priv = rsa.generate_private_key(public_exponent=65537, key_size=2048)
pub = priv.public_key()

message = b"transfer $5000 to account 12345"

# Encrypt with OAEP (RANDOMIZED padding - secure, not textbook RSA)
ct = pub.encrypt(
    message,
    padding.OAEP(
        mgf=padding.MGF1(algorithm=hashes.SHA256()),
        algorithm=hashes.SHA256(),
        label=None,
    ),
)
pt = priv.decrypt(
    ct,
    padding.OAEP(mgf=padding.MGF1(hashes.SHA256()), algorithm=hashes.SHA256(), label=None),
)
assert pt == message
```

### Hashing - fixed-size fingerprints

A cryptographic hash `H(m)` maps arbitrary input to a fixed-size digest (SHA-256 → 256 bits). Required properties:

1. **Preimage resistance:** given `h`, infeasible to find any `m` with `H(m) = h`. (Can't reverse it.)
2. **Second-preimage resistance:** given `m1`, infeasible to find a different `m2` with `H(m2) = H(m1)`.
3. **Collision resistance:** infeasible to find *any* pair `m1 ≠ m2` with `H(m1) = H(m2)`.

Also **avalanche**: flipping one input bit flips ~half the output bits. Hashes give **integrity** (a changed file → changed digest) but **not confidentiality** (one-way, not reversible).

```python
import hashlib
print(hashlib.sha256(b"hello").hexdigest())
# 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
print(hashlib.sha256(b"hellp").hexdigest())   # one char -> totally different
```

**Why MD5 and SHA-1 are dead:** both have *practical collision attacks*. MD5 collisions are trivial; SHA-1 was broken by Google's "SHAttered" (two distinct PDFs, same SHA-1) in 2017. Collision resistance is gone, so they're unsafe for signatures/certificates/integrity. Use **SHA-256** (or SHA-3, BLAKE2/3). MD5/SHA-1 are acceptable *only* for non-security uses (e.g., a cache key, a checksum against accidental corruption), never for anything an attacker can influence.

#### HMAC - keyed hash for message authentication

A plain hash gives no authentication: anyone can recompute `H(m)`. To prove a message came from someone holding a shared key, use **HMAC** (Hash-based MAC):

```
HMAC(k, m) = H((k ⊕ opad) || H((k ⊕ ipad) || m))
```

The double-hashing structure defends against length-extension attacks that affect naive `H(k || m)`. HMAC gives **integrity + authentication** with a shared key.

```python
import hmac, hashlib

def sign(key: bytes, msg: bytes) -> bytes:
    return hmac.new(key, msg, hashlib.sha256).digest()

def verify(key, msg, tag) -> bool:
    return hmac.compare_digest(sign(key, msg), tag)   # CONSTANT-TIME compare!
```

**Critical:** use `hmac.compare_digest`, not `==`. A naive `==` returns early on the first differing byte, leaking timing info that lets an attacker forge a tag byte-by-byte (**timing attack**). Constant-time comparison defeats this.

#### Password hashing - *not* the same as fast hashing

For passwords I do **not** use SHA-256 directly. SHA-256 is *fast*, which means an attacker with a leaked database can try billions of guesses/second on a GPU. Password hashing needs to be **deliberately slow** and **salted**.

- **Salt:** a unique random value per password, stored alongside the hash. Defeats precomputed **rainbow tables** and ensures two users with the same password get different hashes.
- **Work factor (cost):** a tunable parameter that makes each hash slow (e.g., bcrypt cost 12). Tune it so a single hash takes ~250ms on my server, painful for an attacker, fine for one login.
- Use **Argon2id** (modern, memory-hard, resists GPU/ASIC) or **bcrypt** (mature, fine). Never plain SHA/MD5 for passwords.

```python
# pip install argon2-cffi
from argon2 import PasswordHasher
ph = PasswordHasher()                       # sensible memory/time defaults
hash_ = ph.hash("correct horse battery")    # includes salt + params, self-describing
ph.verify(hash_, "correct horse battery")   # raises on mismatch
# For NYX Finance login I'd store hash_ in the DB and verify on login.
```

#### Digital signatures - integrity + authentication + non-repudiation

Sign with the **private** key, verify with the **public** key. Because only the holder of the private key could produce the signature, it proves *who* signed (authentication) and they can't deny it (non-repudiation), properties HMAC *can't* give (HMAC's key is shared, so either party could have made the tag).

```python
from cryptography.hazmat.primitives.asymmetric import padding
from cryptography.hazmat.primitives import hashes

signature = priv.sign(
    message,
    padding.PSS(mgf=padding.MGF1(hashes.SHA256()), salt_length=padding.PSS.MAX_LENGTH),
    hashes.SHA256(),
)
# Anyone with the public key verifies; raises InvalidSignature if tampered:
pub.verify(signature, message,
           padding.PSS(mgf=padding.MGF1(hashes.SHA256()), salt_length=padding.PSS.MAX_LENGTH),
           hashes.SHA256())
```

We sign the *hash* of the message, not the message itself (RSA can only sign small data; the hash is a fixed-size stand-in, that's why a broken hash like SHA-1 breaks signatures: forge a hash collision, forge a signature).

### TLS - tying it all together (cross-link 06.2)

TLS (the S in HTTPS) is the canonical real-world combination of everything above. A simplified TLS 1.3 handshake:

1. **Key exchange:** client and server do **ECDHE** (ephemeral elliptic-curve Diffie-Hellman) to derive a shared secret, gives **forward secrecy**.
2. **Authentication:** the server presents a **certificate** (its public key, signed by a CA). The client verifies the cert chain up to a trusted root and checks the server **signed** the handshake with the matching private key, defeats the DH man-in-the-middle.
3. **Symmetric encryption:** the DH secret is run through a **KDF (HKDF)** to derive session keys; all subsequent traffic uses **AES-GCM** (or ChaCha20-Poly1305), fast authenticated encryption.

So TLS = DH (key exchange) + RSA/ECDSA signatures (authentication) + AES-GCM (bulk encryption) + SHA-256 (integrity/HKDF). Every primitive in this chapter shows up. Network-layer details and certs are in 12.2.

### Randomness & entropy - the foundation everything sits on

Keys, IVs, nonces, salts must be **unpredictable**. If an attacker can guess your randomness, all the crypto above collapses. Rules:

- Use a **CSPRNG** (cryptographically secure PRNG): `os.urandom`, Python's `secrets` module, `/dev/urandom`. **Never** `random.random()` (Mersenne Twister, predictable, reversible from outputs).
- "Entropy" = unpredictability the OS gathers (timing jitter, hardware events) to seed the CSPRNG. On boot or in fresh VMs/containers, entropy can be low, a real footgun for key generation on first boot (handled by modern kernels with `getrandom()` blocking until seeded).

```python
import secrets
key   = secrets.token_bytes(32)   # 256-bit AES key
nonce = secrets.token_bytes(12)   # 96-bit GCM nonce
print(secrets.token_urlsafe(16))  # URL-safe token, e.g. for password reset
```

## 💻 Build it - DH and RSA, toy then real

### Toy Diffie-Hellman (full, with safe-prime params)

```python
import secrets

# Public parameters (real systems use 2048-bit safe primes; small here to read)
p = 0xFFFFFFFFFFFFFFFFC90FDAA22168C234C4C6628B80DC1CD129024E088A67CC74020BBEA63B139B22514A08798E3404DDEF9519B3CD3A431B302B0A6DF25F14374FE1356D6D51C245E485B576625E7EC6F44C42E9A63A3620FFFFFFFFFFFFFFFF
g = 2

def dh_keypair():
    priv = secrets.randbelow(p - 2) + 2     # 2..p-1
    pub = pow(g, priv, p)
    return priv, pub

a_priv, a_pub = dh_keypair()
b_priv, b_pub = dh_keypair()

# Exchange pub values over the (public) wire, then:
s_a = pow(b_pub, a_priv, p)
s_b = pow(a_pub, b_priv, p)
assert s_a == s_b
print("shared secret matches:", s_a == s_b)

# Never use the raw DH integer as a key - run it through a KDF:
import hashlib
shared_key = hashlib.sha256(s_a.to_bytes((s_a.bit_length()+7)//8, "big")).digest()
```

### Real elliptic-curve DH with the library

```python
from cryptography.hazmat.primitives.asymmetric import x25519
from cryptography.hazmat.primitives.kdf.hkdf import HKDF
from cryptography.hazmat.primitives import hashes

alice_priv = x25519.X25519PrivateKey.generate()
bob_priv   = x25519.X25519PrivateKey.generate()

# Each derives the same shared secret from their priv + other's pub
a_shared = alice_priv.exchange(bob_priv.public_key())
b_shared = bob_priv.exchange(alice_priv.public_key())
assert a_shared == b_shared

# Always run the raw shared secret through a KDF to get a uniform key:
key = HKDF(algorithm=hashes.SHA256(), length=32, salt=None,
           info=b"nyx-session-key").derive(a_shared)
```

## 🧪 Mini-project - Encrypted + Authenticated File Vault

Goal: a CLI that encrypts a file so only someone with the password can read it, with tamper detection. Every decision is justified, this is the pattern I'd use for protecting sensitive exports in Anneava.

```python
#!/usr/bin/env python3
"""
vault.py - password-based authenticated file encryption (AES-256-GCM + Argon2id KDF)

Format on disk (all binary):
    MAGIC(4) | VERSION(1) | SALT(16) | NONCE(12) | CIPHERTEXT+TAG(...)

Usage:
    python vault.py encrypt secret.pdf secret.pdf.vault
    python vault.py decrypt secret.pdf.vault secret.pdf
"""
import sys, os, getpass, struct
from argon2.low_level import hash_secret_raw, Type
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

MAGIC = b"NYXV"
VERSION = 1

def derive_key(password: bytes, salt: bytes) -> bytes:
    # Argon2id: memory-hard KDF. Turns a weak password into a strong 256-bit key.
    # Tuned so derivation is ~slow enough to resist brute force, fine for one op.
    return hash_secret_raw(
        secret=password, salt=salt,
        time_cost=3, memory_cost=64 * 1024, parallelism=4,
        hash_len=32, type=Type.ID,
    )

def encrypt(infile, outfile):
    pw = getpass.getpass("Password: ").encode()
    if getpass.getpass("Confirm:  ").encode() != pw:
        sys.exit("Passwords don't match.")
    salt  = os.urandom(16)            # unique salt per file -> unique key
    nonce = os.urandom(12)            # unique nonce per encryption (GCM rule!)
    key   = derive_key(pw, salt)
    data  = open(infile, "rb").read()

    # AAD binds the header to the ciphertext so it can't be swapped/edited.
    header = MAGIC + bytes([VERSION]) + salt + nonce
    ct = AESGCM(key).encrypt(nonce, data, header)   # ct includes the 16-byte tag
    with open(outfile, "wb") as f:
        f.write(header + ct)
    print(f"Encrypted -> {outfile} ({len(ct)} bytes)")

def decrypt(infile, outfile):
    blob = open(infile, "rb").read()
    if blob[:4] != MAGIC:
        sys.exit("Not a vault file.")
    version = blob[4]
    salt  = blob[5:21]
    nonce = blob[21:33]
    ct    = blob[33:]
    header = blob[:33]
    pw = getpass.getpass("Password: ").encode()
    key = derive_key(pw, salt)
    try:
        # If the password is wrong OR the file was tampered, the GCM tag
        # fails to verify and this RAISES - decryption fails closed.
        pt = AESGCM(key).decrypt(nonce, ct, header)
    except Exception:
        sys.exit("Decryption failed: wrong password or file tampered.")
    open(outfile, "wb").write(pt)
    print(f"Decrypted -> {outfile}")

if __name__ == "__main__":
    if len(sys.argv) != 4 or sys.argv[1] not in ("encrypt", "decrypt"):
        sys.exit(__doc__)
    (encrypt if sys.argv[1] == "encrypt" else decrypt)(sys.argv[2], sys.argv[3])
```

**Security decisions, justified:**

| Decision | Why |
|---|---|
| **AES-256-GCM** (not CBC, not ECB) | AEAD: confidentiality *and* integrity in one. Tamper = decrypt fails. |
| **Argon2id KDF** (not SHA-256 of password) | Passwords are low-entropy; a memory-hard KDF makes brute force expensive. |
| **Random 16-byte salt per file** | Unique key per file; defeats rainbow tables; same password ≠ same key. |
| **Random 12-byte nonce per encryption** | GCM's cardinal rule: never reuse (key, nonce). Fresh nonce = safe. |
| **Header as AAD** | Version/salt/nonce are authenticated, attacker can't downgrade version or swap salt. |
| **`os.urandom`** | CSPRNG; predictable randomness would break the whole thing. |
| **Decrypt raises on bad tag** | Fail closed, never return unauthenticated plaintext. |
| **`getpass`** | Password never echoed/logged. |

**Extensions to try:** store the Argon2 params in the header (so I can raise the work factor later without breaking old files); add a `rekey` command; chunk large files so I don't load them fully into memory (each chunk gets its own counter-derived nonce).

## 🧪 Mini-project #2 - Hybrid "encrypt to a public key" envelope (for sharing)

The vault above is *password-based*, fine when the same person encrypts and decrypts. But a common real need is "encrypt a file so a *specific other person* can read it, using only their public key." That's **hybrid encryption** (the pattern PGP, age, and TLS all use): RSA/ECC can only encrypt tiny data, so I encrypt the bulk with AES-GCM and then encrypt *just the AES key* with the recipient's public key. This is how I'd let an Anneava service send an encrypted export to a partner who published a public key.

```python
#!/usr/bin/env python3
"""
envelope.py - hybrid encryption to a recipient's X25519 public key.

Idea ("digital envelope"):
  1. Generate a fresh random 256-bit AES key (the "content-encryption key", CEK).
  2. Encrypt the file body with AES-256-GCM under the CEK (fast, handles big data).
  3. Do an ephemeral X25519 key exchange with the recipient's public key, derive a
     "key-encryption key" (KEK) via HKDF, and AES-GCM-encrypt the CEK under the KEK.
  4. Ship: ephemeral_pub | wrapped_CEK(+tag) | nonce | body_ciphertext(+tag).
Only the holder of the recipient PRIVATE key can redo the exchange, derive the KEK,
unwrap the CEK, and decrypt the body. Ephemeral sender key => forward secrecy.
"""
import os, sys, struct
from cryptography.hazmat.primitives.asymmetric import x25519
from cryptography.hazmat.primitives.kdf.hkdf import HKDF
from cryptography.hazmat.primitives import hashes, serialization
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

MAGIC = b"NYXE"

def _kek_from(shared: bytes) -> bytes:
    # Derive a uniform 256-bit KEK from the raw DH secret. NEVER use the raw secret directly.
    return HKDF(algorithm=hashes.SHA256(), length=32, salt=None,
                info=b"nyx-envelope-kek").derive(shared)

def encrypt_to(recipient_pub: x25519.X25519PublicKey, plaintext: bytes) -> bytes:
    cek = AESGCM.generate_key(bit_length=256)            # fresh content key per file
    body_nonce = os.urandom(12)
    body_ct = AESGCM(cek).encrypt(body_nonce, plaintext, MAGIC)

    eph_priv = x25519.X25519PrivateKey.generate()        # ephemeral => forward secrecy
    shared = eph_priv.exchange(recipient_pub)
    kek = _kek_from(shared)
    wrap_nonce = os.urandom(12)
    wrapped_cek = AESGCM(kek).encrypt(wrap_nonce, cek, MAGIC)   # encrypt the CEK under the KEK

    eph_pub_bytes = eph_priv.public_key().public_bytes(
        serialization.Encoding.Raw, serialization.PublicFormat.Raw)
    return (MAGIC + eph_pub_bytes
            + struct.pack(">H", len(wrapped_cek)) + wrap_nonce + wrapped_cek
            + body_nonce + body_ct)

def decrypt_with(recipient_priv: x25519.X25519PrivateKey, blob: bytes) -> bytes:
    assert blob[:4] == MAGIC, "not an envelope"
    off = 4
    eph_pub = x25519.X25519PublicKey.from_public_bytes(blob[off:off+32]); off += 32
    (wlen,) = struct.unpack(">H", blob[off:off+2]); off += 2
    wrap_nonce = blob[off:off+12]; off += 12
    wrapped_cek = blob[off:off+wlen]; off += wlen
    body_nonce = blob[off:off+12]; off += 12
    body_ct = blob[off:]

    shared = recipient_priv.exchange(eph_pub)            # recipient redoes the exchange
    kek = _kek_from(shared)
    cek = AESGCM(kek).decrypt(wrap_nonce, wrapped_cek, MAGIC)   # unwrap CEK (fails if tampered)
    return AESGCM(cek).decrypt(body_nonce, body_ct, MAGIC)

if __name__ == "__main__":
    # Demo round-trip (in real use the recipient generates and publishes their pub key).
    recipient = x25519.X25519PrivateKey.generate()
    blob = encrypt_to(recipient.public_key(), b"PHI export: patient 42 lab results")
    print("envelope bytes:", len(blob))
    print("recovered:", decrypt_with(recipient, blob))
```

**Why each decision (this is the muscle I'm building):**

| Decision | Why |
|---|---|
| Fresh random CEK per file | Body key is never reused across files; compromise of one file's CEK leaks only that file. |
| **Ephemeral** sender key | Forward secrecy: even if the sender's long-term key later leaks, past envelopes stay sealed. |
| HKDF on the DH secret | Raw DH output isn't a uniform key; HKDF "evens it out" into a proper 256-bit key. |
| AES-GCM for *both* body and CEK-wrap | AEAD everywhere → tamper anywhere fails closed. |
| MAGIC as AAD | Binds the format/version so an attacker can't splice envelopes together. |

**Extensions:** support *multiple* recipients (wrap the same CEK under several public keys, one envelope, many readers); add a sender *signature* over the ciphertext so the recipient also gets authentication (right now this gives confidentiality, not "who sent it"); compare my hand-rolled format to the `age` tool's format and note where it's more careful than mine.

## ⚠️ Common mistakes

A box of the foot-guns I will actually hit, each with the fix and *why it's catastrophic, not cosmetic*:

- **Reusing a (key, nonce) pair with AES-GCM.** The single worst crypto mistake I can make. It recovers the keystream *and* the GHASH auth key, breaking both confidentiality and integrity. Fix: random 96-bit nonce per encryption, or a strict counter. Never derive the nonce from the plaintext.
- **Using `==` to compare MACs / tokens / hashes.** Leaks timing, enabling byte-by-byte forgery. Fix: `hmac.compare_digest` (constant-time).
- **Fast hashing passwords** (`sha256(password)`, even salted). GPUs do billions/sec. Fix: Argon2id or bcrypt with a tuned cost.
- **`random.random()` / `random.randint()` for keys, tokens, salts, nonces.** Mersenne Twister is predictable and *reconstructable* from a handful of outputs. Fix: `secrets` / `os.urandom`.
- **Textbook RSA** (`m**e % n` raw). Deterministic and malleable. Fix: OAEP for encryption, PSS for signatures.
- **Encrypt-without-authenticate** (plain AES-CBC/CTR). Confidentiality without integrity invites bit-flipping and padding-oracle attacks. Fix: AEAD (AES-GCM / ChaCha20-Poly1305).
- **Storing the IV/nonce as secret, or omitting it.** The nonce is *not* secret, it must be stored/sent with the ciphertext. The *key* is the secret. Confusing the two breaks decryption or leads to nonce reuse.
- **Trusting an unverified signature** (or a JWT whose signature you never checked, or `alg: none`). A signature you don't verify protects nothing.
- **Hardcoding keys in source / committing them.** Belongs in a secret manager; rotate on leak. (Ties to 12.3 A02.)
- **Using the raw Diffie-Hellman shared integer as a key.** It's not uniformly random. Always run it through a KDF (HKDF).
- **MD5/SHA-1 for anything an attacker can influence.** Collisions are practical. Fine only for non-security checksums.

## 💼 On the job / interview angle

Security awareness is now table stakes for entry-level engineers, not just "security engineers." If I'm building NYX/Anneava, *I* am the security engineer for my code, and interviewers increasingly probe this even for general backend roles.

**What teams actually expect a junior to get right:**

- Never store plaintext passwords; use bcrypt/Argon2; know *why* a fast hash is wrong.
- Know that HTTPS/TLS gives confidentiality+integrity in transit, but you still need encryption *at rest* for sensitive data.
- Recognize that "encrypted" ≠ "authenticated", reach for AEAD.
- Pull secrets from config/secret managers, not source.
- Use the standard library / a vetted crypto library, never a hand-rolled cipher.

**Representative interview questions (and the crisp answer):**

1. *"How do you store user passwords?"* → Argon2id (or bcrypt), per-user salt, tuned work factor (~250ms/hash); never a plain or fast hash; constant-time verify.
2. *"What's the difference between hashing and encryption?"* → Hashing is one-way (integrity/fingerprint), encryption is reversible with a key (confidentiality). You can't "decrypt" a hash.
3. *"Symmetric vs asymmetric, when each?"* → Symmetric (AES) for bulk data, fast, shared key; asymmetric (RSA/ECC) for key exchange and signatures where parties don't share a secret. Real systems combine them (hybrid/TLS).
4. *"Why can't I reuse a nonce/IV?"* → For GCM it recovers the keystream and auth key (total break); for CBC it leaks whether two messages start the same. Nonces must be unique; CBC IVs must be unpredictable.
5. *"What does a digital signature give you that an HMAC doesn't?"* → Non-repudiation: only the private-key holder could sign, so they can't deny it. HMAC's key is shared, so either party could have produced the tag.
6. *"How does TLS keep my login safe?"* → ECDHE for a forward-secret shared key, the server's certificate (signed by a CA) authenticates it and defeats MITM, then AES-GCM encrypts traffic. (Ties primitives together, see the TLS section.)

**Observability tie-in (increasingly expected):** I should be able to say *what I'd log around crypto operations*, auth successes/failures, key-rotation events, decryption failures (a spike can signal tampering or a misconfigured key), **without ever logging the secrets themselves**. That bridges this chapter to 13.1 and 12.3 A09.

## ✏️ Exercises

Work these in a scratch file; the math ones I should be able to do by hand first, then verify in Python. Easy → hard.

1. **(Warm-up)** Implement `xor_bytes(a, b)` for equal-length byte strings and use it to show `(p ^ k) ^ k == p`.
2. **(XOR break)** Take a sentence, XOR it with a single random byte, and use frequency scoring to recover the key byte and plaintext (extend `break_single_byte_xor`).
3. **(DH by hand)** With `p = 23, g = 5, a = 4, b = 3`, compute `A`, `B`, and the shared secret by hand, then verify with `pow`.
4. **(RSA by hand)** With `p = 11, q = 13`, pick a valid `e`, compute `n`, `φ(n)`, and `d`. Encrypt `m = 7` and decrypt it back.
5. **(Hash avalanche)** Hash `"hello"` and `"hellp"` with SHA-256 and count how many of the 256 output bits differ. Is it close to half?
6. **(Password hashing)** Hash the same password twice with Argon2 and explain why the two hashes differ even though the password is identical.
7. **(Timing-safe compare)** Write a deliberately *unsafe* tag check using `==`, then rewrite it with `hmac.compare_digest`, and explain in one sentence what an attacker exploits in the unsafe version.
8. **(GCM tamper)** Encrypt a message with AES-GCM, flip one byte of the ciphertext, and show that decryption raises. Then explain what would have happened with plain AES-CTR instead.
9. **(Hybrid)** Extend `envelope.py` to encrypt to *two* recipients with one shared body ciphertext (wrap the CEK under each recipient's public key).
10. **(Hard / synthesis)** Add a **detached signature** to `envelope.py`: the sender signs the body ciphertext with an Ed25519 key, and the recipient verifies it after decrypting. Explain which of the four security goals each piece now provides.

### Solutions

1. ```python
   def xor_bytes(a, b): return bytes(x ^ y for x, y in zip(a, b))
   p, k = b"hello!", b"\x13\x37\x42\x99\x01\x55"
   assert xor_bytes(xor_bytes(p, k), k) == p   # XOR is self-inverse
   ```
2. Reuse `break_single_byte_xor` from the chapter - it already tries all 256 keys and scores by English letters. The key byte is the one whose decrypt scores highest; for a single-byte key the correct one wins by a wide margin.
3. By hand: `A = 5^4 mod 23 = 625 mod 23 = 4`. `B = 5^3 mod 23 = 125 mod 23 = 10`. Shared `= B^a = 10^4 mod 23 = 10000 mod 23 = 18`; check `A^b = 4^3 = 64 mod 23 = 18`. ✓ `pow(5,4,23)==4`, `pow(5,3,23)==10`, `pow(10,4,23)==pow(4,3,23)==18`.
4. `n = 143`, `φ = 10·12 = 120`. `e = 7` (`gcd(7,120)=1`). `d = modinv(7,120) = 103` (`7·103 = 721 = 1 + 6·120`). `c = 7^7 mod 143 = 6`; `6^103 mod 143 = 7`. ✓ (use the chapter's `egcd`/`modinv`).
5. ```python
   import hashlib
   a = bin(int(hashlib.sha256(b"hello").hexdigest(),16))[2:].zfill(256)
   b = bin(int(hashlib.sha256(b"hellp").hexdigest(),16))[2:].zfill(256)
   print(sum(x!=y for x,y in zip(a,b)))   # ~128, close to half - avalanche
   ```
6. Argon2 generates a *fresh random salt* each call and embeds it in the output string. Same password + different salt → different hash. That's exactly what defeats rainbow tables and lets two users with the same password have different stored hashes.
7. Unsafe: `def check(a,b): return a == b`. Safe: `return hmac.compare_digest(a,b)`. `==` returns as soon as it finds a differing byte, so the *time taken* reveals how many leading bytes matched, an attacker forges the tag one byte at a time by measuring timing.
8. ```python
   from cryptography.hazmat.primitives.ciphers.aead import AESGCM
   k, n = AESGCM.generate_key(256), b"\0"*12
   ct = bytearray(AESGCM(k).encrypt(n, b"pay alice $5", None))
   ct[0] ^= 1
   try: AESGCM(k).decrypt(n, bytes(ct), None)
   except Exception as e: print("rejected:", type(e).__name__)
   ```
   With plain AES-CTR the flip would silently corrupt one byte of plaintext and decryption would "succeed" - no integrity, the bit-flip goes undetected.
9. Wrap the CEK once per recipient: store a list of `(eph_pub_i, wrap_nonce_i, wrapped_cek_i)` blocks, each from an ephemeral exchange with recipient *i*'s public key; the body ciphertext is shared. Each recipient tries to unwrap with their private key.
10. Generate `sign_priv = Ed25519PrivateKey.generate()`; after building `body_ct`, compute `sig = sign_priv.sign(body_ct)` and append it; on decrypt, `sender_pub.verify(sig, body_ct)` *before* decrypting. Now: AES-GCM gives **confidentiality + integrity** of the body, the X25519 wrap gives **confidentiality** of the key (only the recipient unwraps), and the Ed25519 signature adds **authentication + non-repudiation** (proves the sender, who can't deny it).
