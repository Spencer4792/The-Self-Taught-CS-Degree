## 🌱 Start here - the absolute beginner on-ramp

Network security feels like an alphabet soup (TLS, DMZ, WAF, DDoS, DNSSEC) until you anchor it to one picture.

**The castle analogy.** Picture your servers as a castle holding something valuable (customer data).

- The **firewall** is the gatehouse: it decides who's allowed through which door, and ideally the default is "the gate is shut unless you've explicitly opened it for a known visitor" (**default-deny**).
- **Segmentation / the DMZ** is having *inner and outer walls*: visitors from outside can reach the courtyard (web tier) but not the treasury (database). Even if a thief gets into the courtyard, there's another wall before the gold.
- **TLS** is sending messages in *sealed, signed envelopes* so a messenger can't read or forge them on the road. (The crypto inside the envelope is 12.1; here you care about running it correctly.)
- **A VPN** is a *private tunnel* under the wall that only trusted people with the right key may use, so you don't have to leave a public door open for your own admins.
- **IDS/monitoring** is the *night watch*: it assumes a thief will eventually get past a wall, so it watches for footsteps and rings a bell.

Two principles run through every section, and they're the whole philosophy:

1. **Least privilege**, give every door, user, and service the *minimum* access it needs. A breach then has a small "blast radius."
2. **Defense in depth**, never trust a single wall. Stack them so one failing doesn't mean game over.

**Why this matters.** A single mistake here, an SSH port open to the whole internet with password login, a database with a public IP, an expired certificate, is exactly the kind of thing automated bots find within *minutes* of a server coming online. Network security is mostly about *not leaving doors open by accident*, and then *watching* for the day prevention fails. The good news: most of the wins are cheap and checklist-able, which is why this chapter ends in a hardening checklist you can templatize for every NYX/Anneava host.

If you remember one thing: **assume the internet is constantly, automatically attacking every port you expose, so expose as little as possible, and watch the rest.**

## 📐 Theory

### Threat modeling - think before you firewall

Before configuring anything, ask four questions (the STRIDE-lite version):

1. **What are you protecting?** (Assets: customer PII, financial data, the database, API keys, the ability to serve traffic.)
2. **Who's the adversary, and what can they do?** (Opportunistic bot scanning the internet? A motivated attacker? A malicious insider? Each has different capabilities.)
3. **What are the attack surfaces?** (Open ports, the web app, SSH, DNS, dependencies, the cloud control plane, employees.)
4. **What's the impact, and how do you reduce likelihood/impact?**

**STRIDE** is a useful checklist of threat categories: **S**poofing (pretending to be someone), **T**ampering (modifying data), **R**epudiation (denying an action), **I**nformation disclosure (leaking data), **D**enial of service (taking it down), **E**levation of privilege (gaining rights you shouldn't have). For each asset, walk STRIDE and ask "how would each apply here, and what control stops it?"

The output of threat modeling is a prioritized list: *not* "secure everything equally," but "the database holds PII (high impact) and is reachable from the web tier (likely path), so segment it and lock it down first."

### Firewalls - controlling what traffic is allowed

A firewall enforces a policy on network traffic. There are three meaningful tiers:

#### 1. Packet-filtering (stateless)

Looks at each packet in isolation: source/dest IP, source/dest port, protocol (TCP/UDP/ICMP). Decides allow/deny per packet with no memory of connections. Fast, but dumb, it can't tell a legitimate reply from an unsolicited packet, so you end up writing rules for both directions of every connection, and it's easy to leave holes.

#### 2. Stateful

Tracks **connection state** (the TCP handshake, established connections) in a state table. Rule: "allow established/related traffic." This means you only write rules for *new inbound* connections; replies to outbound connections are automatically allowed because the firewall remembers you initiated them. This is what `iptables`/`nftables`/`ufw` and cloud security groups do. Much safer and simpler.

#### 3. Application-layer / WAF (Web Application Firewall)

Inspects **Layer 7**, the actual HTTP request: URLs, headers, body, cookies. A WAF (e.g., AWS WAF, Cloudflare, ModSecurity) can block SQL-injection patterns, known bad bots, request floods, and enforce rate limits. It understands *content*, not just addresses/ports. A WAF is a useful *additional* layer (defense in depth) but **not a substitute** for fixing the app, it's a filter, and filters can be bypassed. The real fix for SQLi is parameterized queries (12.3); the WAF is a net.

#### Default-deny - the single most important firewall principle

A firewall policy should **deny everything by default and explicitly allow only what's needed.** The opposite (allow-by-default, block known-bad) is a losing game, you can never enumerate all bad things. Default-deny means a service you forgot about isn't exposed; you have to *consciously* open each port. This is least privilege applied to the network.

#### Ingress vs egress

- **Ingress** = inbound traffic *to* your server. Obvious to lock down (only 443, maybe 22 from your IP).
- **Egress** = outbound traffic *from* your server. People forget this. **Egress filtering matters** because if a server is compromised, restricting outbound traffic limits what an attacker can do: they can't exfiltrate data to an arbitrary host, can't pull a second-stage payload, can't beacon to a command-and-control server. For a sensitive box (e.g., the Anneava DB host), allow egress only to the specific endpoints it legitimately needs.

#### How rules are evaluated

Rules are an **ordered list**; the first match wins (in iptables and most firewalls). So order matters: specific allows before the broad deny. A typical structure:

```
1. Allow loopback (lo)
2. Allow established/related (stateful)
3. Allow specific new-inbound services (22 from my IP, 443 from anywhere)
4. Default policy: DROP everything else
```

#### Concrete examples

**`ufw` (Uncomplicated Firewall, Ubuntu's friendly front-end to nftables):**

```bash
sudo ufw default deny incoming      # default-deny ingress
sudo ufw default allow outgoing     # (tighten egress later for sensitive hosts)
sudo ufw allow from 203.0.113.7 to any port 22 proto tcp   # SSH only from my IP
sudo ufw allow 443/tcp              # HTTPS from anywhere
sudo ufw enable
sudo ufw status verbose             # verify
```

**`iptables` (the lower-level, explicit version of the same idea):**

```bash
iptables -P INPUT DROP                                   # default-deny
iptables -P FORWARD DROP
iptables -A INPUT -i lo -j ACCEPT                        # loopback
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT   # stateful
iptables -A INPUT -p tcp -s 203.0.113.7 --dport 22 -j ACCEPT             # SSH from my IP
iptables -A INPUT -p tcp --dport 443 -j ACCEPT                           # HTTPS
```

**Cloud security group (the AWS/GCP equivalent, a stateful virtual firewall on the instance):**

```
Inbound:
  TCP 443  from 0.0.0.0/0          # HTTPS public
  TCP 22   from 203.0.113.7/32     # SSH from my office IP only
Outbound:
  TCP 443  to 0.0.0.0/0            # API calls, package updates
  TCP 5432 to sg-database          # Postgres, only to the DB security group
```

Security groups are **stateful** (return traffic auto-allowed) and reference *other groups*, so "the web tier may talk to the DB tier" without hardcoding IPs. This is segmentation done in the cloud.

### Network segmentation & the DMZ

Don't put everything on one flat network. **Segment** by trust level so a breach in one zone doesn't reach everything:

- **DMZ (demilitarized zone):** a perimeter network for internet-facing services (load balancer, reverse proxy). It can receive public traffic but has *limited* access into the internal network.
- **App tier:** web/API servers. Reachable from the DMZ, not directly from the internet.
- **Data tier:** databases, secrets. Reachable *only* from the app tier, never from the internet. The DB should have **no public IP at all.**

The principle: an attacker who pops the web server still can't reach the database directly, they're stopped at the segment boundary. This is **defense in depth** made concrete. For Anneava (HIPAA-aligned), keeping PHI on a private data tier with no internet route is essential, and demonstrable for compliance.

### VPNs - what they actually do (and don't)

A **VPN** creates an encrypted tunnel between two endpoints. Two distinct uses:

1. **Remote access:** an admin connects to a private network over the internet through an encrypted tunnel, so they can reach internal-only resources (e.g., the DB tier) without exposing those resources publicly. The traffic between laptop and VPN gateway is encrypted and authenticated.
2. **Site-to-site:** two networks (e.g., two cloud VPCs, or office↔cloud) joined over an encrypted tunnel.

What a VPN **does:** encrypt traffic in transit between the endpoints, and authenticate that you're allowed on the network. What it **doesn't do:** it doesn't make endpoints trustworthy, doesn't encrypt traffic *past* the VPN exit, and a consumer "privacy VPN" just moves trust from your ISP to the VPN provider. For your use case, a VPN (or better, a zero-trust access tool like Tailscale/WireGuard mesh) means you never expose SSH or admin interfaces to the public internet, they're only reachable through the tunnel. WireGuard is the modern choice: small, fast, modern crypto (X25519 + ChaCha20-Poly1305).

### TLS in practice (cross-link 06.2, 12.1)

12.1 covered the crypto; here's the operational reality.

#### Certificates and the chain of trust

A TLS certificate binds a **public key** to a **domain name**, **signed by a Certificate Authority (CA)**. Your browser trusts a set of **root CAs** (shipped with the OS/browser). The chain:

```
Root CA (trusted, self-signed, in trust store)
  └─ signs → Intermediate CA
        └─ signs → my leaf cert (nyxfinance.com)
```

When a client connects, the server sends its **leaf cert + intermediates**. The client verifies each signature up to a trusted root, checks the cert isn't expired, isn't revoked, and that the domain matches (SAN field). If any step fails → the browser warning. **A common misconfig is forgetting to serve the intermediate chain**, it works in your browser (which cached the intermediate) but fails for others. Always test with `openssl` (below), not just your own browser.

#### Let's Encrypt and ACME

**Let's Encrypt** is a free CA; **ACME** is the protocol clients use to get certs automatically. The flow:

1. Your client (`certbot`, Caddy, etc.) proves you control the domain, typically the **HTTP-01 challenge**: the CA gives a token, you serve it at `http://nyxfinance.com/.well-known/acme-challenge/<token>`, the CA fetches it. (Or **DNS-01**: you publish a TXT record, needed for wildcard certs.)
2. The CA issues a 90-day cert.
3. The client **auto-renews** before expiry (cron/systemd timer). Short lifetimes + automation = no more "the cert expired and took down the site" incidents.

```bash
# Caddy does this automatically with zero config; certbot is the manual route:
sudo certbot --nginx -d nyxfinance.com -d www.nyxfinance.com
# Renewal is installed automatically; test it:
sudo certbot renew --dry-run
```

#### Common TLS misconfigurations (the checklist to run)

- **Expired certs** → automate renewal, alert at 21 days left.
- **Missing intermediate chain** → serve full chain; verify externally.
- **Weak protocols/ciphers** → disable SSLv3, TLS 1.0/1.1; require TLS 1.2+ (prefer 1.3). Disable RC4, 3DES, export ciphers.
- **No HSTS** → send `Strict-Transport-Security` so browsers refuse plain HTTP and resist SSL-strip downgrade attacks.
- **Mixed content** → HTTPS page loading HTTP resources; breaks the security guarantee.
- **Self-signed/wrong-host certs in prod** → only OK for internal/dev.

#### mTLS (mutual TLS)

Normal TLS: the *client* verifies the *server's* cert. **mTLS:** the server *also* requires the client to present a valid cert, both sides authenticate. Used for **service-to-service** auth (microservices, a service mesh like Istio/Linkerd) where you want strong cryptographic identity for callers rather than just an API key. For NYX Finance internal services, mTLS means the payment service *cryptographically proves* it's the payment service, not just "knows a token."

### TLS handshake in practice - what actually happens on the wire (deep dive)

The bullet list above is the *what*; now for the *how*, step by step, because when a handshake fails in production you need to read the openssl output and know exactly which step broke. Let's walk a TLS 1.3 handshake (the modern default), then note where 1.2 differs, then map each step to a thing that can go wrong.

#### The TLS 1.3 handshake, step by step

```
Client                                                     Server
  |--- ClientHello ----------------------------------------->|   (1)
  |    supported TLS versions, cipher suites, SNI (servername),|
  |    a key_share (client's ephemeral ECDHE public key)      |
  |                                                           |
  |<-- ServerHello ------------------------------------------|   (2)
  |    chosen version + cipher, server's key_share            |
  |    {EncryptedExtensions}                                  |   (3) encrypted from here
  |    {Certificate}  (leaf + intermediates)                  |   (4)
  |    {CertificateVerify}  (signature proving key ownership) |   (5)
  |    {Finished}  (MAC over the handshake transcript)        |   (6)
  |                                                           |
  |--- {Finished} ------------------------------------------->|   (7)
  |                                                           |
  |==== application data (HTTP), AEAD-encrypted ============>|   (8)
```

1. **ClientHello.** The client proposes everything it supports and *already* sends its ephemeral ECDHE public key (the `key_share`). The **SNI** (Server Name Indication) tells the server which hostname you want, this is how one IP serves many TLS sites, and it's why `-servername` matters in `openssl s_client`. Forget the SNI and a multi-site server hands back the *wrong* (default) cert.
2. **ServerHello.** Server picks the version + cipher suite and sends its own `key_share`. Now *both* sides can derive the shared secret via ECDHE, and because the keys are ephemeral, this gives **forward secrecy** (capturing today's traffic and stealing the server's long-term key tomorrow still doesn't decrypt it).
3. **EncryptedExtensions onward are encrypted.** TLS 1.3 starts encrypting after ServerHello, so the certificate itself is no longer sent in cleartext (a privacy win over 1.2).
4. **Certificate.** The server presents its **leaf cert plus the intermediate chain** (it should *not* send the root, the client already has that in its trust store). This is the step that breaks when you "forget the intermediate."
5. **CertificateVerify.** The server signs the handshake transcript with the **private key** corresponding to the public key in the leaf cert. This *proves the server actually holds the private key*, owning the cert file isn't enough; you must prove possession of the key. Defeats a replay-the-cert attacker.
6. **Finished.** A MAC over the entire handshake transcript so neither side can have been tampered with mid-handshake (defeats a downgrade-injection MITM).
7. **Client Finished.** Client verifies the chain (signatures up to a trusted root, not expired, not revoked, SAN matches the SNI), then sends its own Finished.
8. **Application data** flows under an AEAD cipher (e.g., `TLS_AES_256_GCM_SHA384`), confidentiality + integrity in one.

**TLS 1.2 differences worth knowing:** the cert is sent in cleartext; key exchange is a separate `ServerKeyExchange`/`ClientKeyExchange` round trip (so 1.2 is a 2-RTT handshake vs 1.3's 1-RTT); and 1.2 *allowed* non-forward-secret RSA key exchange (now strongly discouraged, disable static-RSA suites). The 1.3 cipher list is tiny and all-good-by-construction, which is part of why "just require 1.3 where you can" is sound advice.

#### Lab: inspect a live handshake + the full cert chain with `openssl s_client`

Run against a site you run (or `localhost` with your own cert). Let's annotate every part of the output that matters.

```bash
# Full handshake, full chain, all certs printed:
openssl s_client -connect nyxfinance.com:443 -servername nyxfinance.com -showcerts </dev/null 2>/dev/null
```

What to read in the output, line by line:

```
CONNECTED(00000003)
---
Certificate chain                                ← the chain the SERVER sent me
 0 s:CN=nyxfinance.com                            ← (0) the LEAF, subject = my domain
   i:C=US, O=Let's Encrypt, CN=R11               ← issued by the intermediate
 1 s:C=US, O=Let's Encrypt, CN=R11               ← (1) the INTERMEDIATE
   i:C=US, O=ISRG, CN=ISRG Root X1               ← issued by the root
---
Server certificate                               ← (the leaf again, PEM)
-----BEGIN CERTIFICATE----- ... -----END CERTIFICATE-----
---
Acceptable client certificate CA names           ← only present if server wants mTLS
---
SSL handshake has read 4096 bytes and written 392 bytes
---
New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384   ← negotiated version + AEAD cipher
Server public key is 2048 bit
Verify return code: 0 (ok)                        ← THE LINE THAT MATTERS MOST
```

The single most important line is **`Verify return code: 0 (ok)`**, the chain validated against your local trust store. Common failure codes you'll actually see:

| Verify return code | Meaning | Fix |
|---|---|---|
| `0 (ok)` | Chain validates | (nothing) |
| `10 (certificate has expired)` | Leaf or intermediate expired | Renew (ACME automation), alert at 21 days |
| `20 (unable to get local issuer certificate)` | You didn't send the intermediate | Serve the **fullchain**, not just the leaf |
| `21 (unable to verify the first certificate)` | Same root cause, broken chain | Same: serve intermediates |
| `18 (self-signed certificate)` | Self-signed in prod | Use a real CA-issued cert |
| `62 (hostname mismatch)` | SAN doesn't include the host | Reissue with the right SAN(s) |

Now pull specific facts out of the cert without scrolling PEM:

```bash
# 1. Expiry dates, subject, issuer
echo | openssl s_client -connect nyxfinance.com:443 -servername nyxfinance.com 2>/dev/null \
  | openssl x509 -noout -dates -subject -issuer
#   notBefore=...   notAfter=...   subject= CN=nyxfinance.com   issuer= ...Let's Encrypt...

# 2. SANs - the exact hostnames the cert is valid for (must include the host I'm hitting)
echo | openssl s_client -connect nyxfinance.com:443 -servername nyxfinance.com 2>/dev/null \
  | openssl x509 -noout -ext subjectAltName
#   X509v3 Subject Alternative Name: DNS:nyxfinance.com, DNS:www.nyxfinance.com

# 3. Verify a specific protocol is REFUSED (TLS 1.0 should fail to negotiate)
openssl s_client -connect nyxfinance.com:443 -tls1 2>&1 | grep -i "no protocols\|alert\|handshake failure"

# 4. Confirm TLS 1.3 is offered and see the cipher
openssl s_client -connect nyxfinance.com:443 -tls1_3 </dev/null 2>/dev/null | grep -i "Protocol\|Cipher"

# 5. Inspect a local cert file directly (no network) - dump everything human-readable
openssl x509 -in /etc/letsencrypt/live/nyxfinance.com/fullchain.pem -noout -text | head -40

# 6. Verify a chain file validates against a CA bundle WITHOUT a live connection
openssl verify -untrusted /etc/letsencrypt/live/nyxfinance.com/chain.pem \
  /etc/letsencrypt/live/nyxfinance.com/cert.pem
#   cert.pem: OK
```

**What you're checking holistically:** `Verify return code: 0`, the chain actually *contains* the intermediate (entry 1 above), expiry comfortably in the future, the SAN matches your hostname, legacy protocols refused, and 1.3 negotiates a strong AEAD cipher. If a customer ever says "works in my browser but not on their phone," run command #1's `-showcerts` and look for a missing intermediate, the #1 cause.

### DNS security

DNS translates names to IPs, and classic DNS is **unauthenticated plaintext**, ripe for abuse:

- **DNS spoofing / cache poisoning:** an attacker injects a forged response so `nyxfinance.com` resolves to *their* IP. Now they can MITM or phish.
- **DNSSEC** adds **signatures** to DNS records, creating a chain of trust from the root zone down. A resolver can verify the response wasn't forged. It provides *integrity/authenticity* of DNS data (not confidentiality).
- **DoH/DoT** (DNS over HTTPS / over TLS) encrypt the *query* between client and resolver, that's confidentiality of your lookups, a different property from DNSSEC's authenticity.
- **Operational DNS hygiene:** lock the registrar account (MFA, registrar-lock), watch for **dangling records** (a CNAME pointing to a deprovisioned cloud resource someone else can claim → **subdomain takeover**), and monitor for unexpected record changes.

### DDoS - types and mitigation (tie to rate limiting, 09.4)

A **DDoS** (Distributed Denial of Service) overwhelms a target from many sources. Categories by layer:

- **Volumetric (L3/L4):** raw flood to saturate bandwidth, UDP floods, **amplification** (send small spoofed queries to DNS/NTP servers that reply with large responses to the victim). Mitigated upstream by the network/scrubbing provider; you can't absorb 1 Tbps on one box.
- **Protocol (L4):** **SYN flood**, half-open TCP connections exhaust the connection table. Mitigated with SYN cookies, connection limits.
- **Application (L7):** expensive requests (a flood of searches, login attempts, big report generations). Looks like real traffic. This is where **rate limiting** (09.4), caching, and a WAF earn their keep.

**Mitigations, layered:**

1. Put a **CDN/scrubbing provider** in front (Cloudflare, AWS Shield) to absorb volumetric attacks.
2. **Rate limit** per IP/per token at the edge and app (token bucket, see 09.4).
3. **Autoscale** so legitimate spikes don't tip into outage.
4. **Cache** aggressively so expensive operations aren't repeated.
5. Keep **availability** (the 'A' in CIA) as a first-class goal, graceful degradation beats hard failure.

### Intrusion detection basics

- **IDS (Intrusion Detection System):** *detects* and alerts on suspicious activity. **IPS:** also *blocks* it inline.
- **Network IDS (NIDS)** like Suricata/Snort watches traffic for known-bad signatures or anomalies. **Host IDS (HIDS)** like OSSEC/Wazuh watches a host: file-integrity monitoring, log anomalies, unexpected processes.
- **Signature-based** = matches known attack patterns (precise, misses novel attacks). **Anomaly-based** = flags deviations from a baseline (catches novel, more false positives).
- This is where observability work meets security: shipping firewall/auth/IDS logs into Elasticsearch/Splunk and alerting on patterns (repeated SSH failures, a spike in 403s, egress to a new country), see 13.1. Detection is the assumption that *prevention will sometimes fail*, so you need to *see* it.

### Secrets management & key rotation

Firewalls and TLS protect traffic; **secrets management** protects the credentials that traffic carries, DB passwords, API keys, TLS private keys, JWT signing keys, encryption keys. This is where a huge fraction of real breaches start (a key committed to git, an `.env` baked into a public image), so it deserves its own discipline.

#### Why secrets are special

A secret is a credential that grants access. Unlike most config, leaking one is often *game over* for whatever it protects, and, critically, **you can't un-leak it**; the only remedy is *rotation* (replace it and invalidate the old one). So the whole game is: (1) keep secrets out of places they leak from, (2) limit who/what can read each one (least privilege), and (3) make rotation cheap and routine so a leak is recoverable, not catastrophic.

#### Where secrets should and shouldn't live

| Anti-pattern (leaks) | What to do instead |
|---|---|
| Hardcoded in source / committed `.env` | A secrets manager; inject at runtime |
| Baked into a Docker image layer | Mount at runtime (env from secret store, file mount) |
| Plaintext in CI config / logs | CI secret store + masked variables; never `echo` a secret |
| Long-lived static keys, never rotated | Short-lived/dynamic credentials, scheduled rotation |
| One shared key for everything | Per-service, per-environment scoped credentials |

The tools that do this properly: **HashiCorp Vault**, **AWS Secrets Manager / SSM Parameter Store (SecureString)**, **GCP Secret Manager**, **Kubernetes Secrets backed by a KMS**. The common features that matter: **encryption at rest** (envelope-encrypted under a KMS root key), **fine-grained access policies** (this service may read *only* its own DB password), **audit logging** (every read is recorded, essential for Anneava/HIPAA), and **automatic rotation**.

#### Key rotation - the concept and the cadence

**Rotation** = replacing a secret with a new value and retiring the old one. Two reasons to rotate:

1. **Routine/proactive**, on a schedule (e.g., every 90 days) so the *exposure window* of any single key is bounded even if it leaked silently.
2. **Reactive/emergency**, immediately, when a key is known or suspected compromised (an employee leaves, a key appears in a log, a dependency is breached).

The hard part is **rotating without downtime**, and the trick is to **support two valid keys at once** during the cutover:

```
1. Generate the NEW key/credential (the manager can do this).
2. Make verifiers accept BOTH old and new (overlap window).
   - For JWT signing: publish both public keys (a JWKS with two `kid`s);
     sign new tokens with the new key, still verify old tokens with the old.
   - For a DB password: create a second credential, deploy it, then retire the first.
3. Switch signers/clients to the NEW key.
4. Once all old tokens/sessions have expired or all clients use the new key,
   REVOKE the old key.
```

This overlap-then-revoke pattern is why short token lifetimes and a **`kid` (key id) header** on JWTs matter: the `kid` tells the verifier *which* key signed a token, so it can hold several keys and rotate smoothly. (Cross-link 12.1: this is exactly how a JWKS endpoint works.)

#### Concrete examples

```bash
# AWS Secrets Manager: store, read, and rotate a DB credential.
aws secretsmanager create-secret --name nyx/prod/db \
  --secret-string '{"username":"nyx_app","password":"<generated>"}'

# App reads it at runtime (never hardcoded); IAM policy lets ONLY the app role read THIS secret.
aws secretsmanager get-secret-value --secret-id nyx/prod/db --query SecretString --output text

# Rotation: Secrets Manager can run a Lambda that creates a new password,
# updates the DB user, and flips the stored value - on a 30/90-day schedule.
aws secretsmanager rotate-secret --secret-id nyx/prod/db \
  --rotation-rules '{"AutomaticallyAfterDays":90}'
```

```bash
# Keep secrets out of git: scan before every commit (pre-commit hook).
pip install detect-secrets
detect-secrets scan > .secrets.baseline
# In CI, fail the build if a new secret-looking string appears:
detect-secrets-hook --baseline .secrets.baseline $(git diff --cached --name-only)
# (gitleaks / trufflehog do the same job - run one in CI.)
```

**If a secret *does* leak** (the incident runbook): rotate it *immediately* (don't wait to confirm exploitation), invalidate the old value, audit access logs for use of the leaked key, and, because git history is forever, rotate even after you `git rm` the file, since the value is still in history and in anyone's clone. Removing the file is *not* remediation; rotation is.

**For Anneava (HIPAA):** the encryption keys protecting PHI are themselves secrets that must be access-controlled, audit-logged, and rotated; a KMS with key policies + CloudTrail gives you the "who decrypted what, when" trail an auditor asks for.

### The two principles that tie it together

**Least privilege:** every component (user, service, network path, IAM role) gets the *minimum* access needed to do its job, and nothing more. Default-deny firewalls, no-public-IP databases, scoped IAM roles, SSH only from your IP, all instances of this. If the web server is breached, least privilege limits the **blast radius**.

**Defense in depth:** never rely on a single control. Layer them so that if one fails, others still protect you. Example for a single login request to NYX Finance: CDN/WAF → TLS → rate limit → input validation → parameterized query → least-privilege DB user → encrypted-at-rest data → audit logging. An attacker has to beat *every* layer. No single point of failure.

## 💻 Build it - firewall with ufw + verify TLS with openssl

### Configure a host firewall (default-deny, only what's needed)

```bash
# Start from a clean default-deny posture
sudo ufw --force reset
sudo ufw default deny incoming
sudo ufw default deny outgoing            # strict egress; we'll allow what's needed

# Loopback is fine (ufw allows it implicitly, but be explicit on iptables)

# Inbound: SSH only from my IP, HTTPS from anyone
sudo ufw allow from 203.0.113.7 to any port 22 proto tcp comment 'SSH from office'
sudo ufw allow 443/tcp comment 'HTTPS'

# Egress: DNS, NTP, HTTPS (for updates/ACME/APIs), Postgres to DB host only
sudo ufw allow out 53 comment 'DNS'
sudo ufw allow out 123/udp comment 'NTP'
sudo ufw allow out 443/tcp comment 'HTTPS out'
sudo ufw allow out to 10.0.2.10 port 5432 proto tcp comment 'Postgres to DB tier'

# Rate-limit SSH to slow brute force (ufw 'limit' = max 6 conns / 30s per IP)
sudo ufw limit 22/tcp

sudo ufw enable
sudo ufw status verbose numbered          # verify the ruleset and order
```

### Inspect and verify a TLS setup with openssl

```bash
# 1. Full handshake + chain. Look for "Verify return code: 0 (ok)" and the chain.
openssl s_client -connect nyxfinance.com:443 -servername nyxfinance.com -showcerts </dev/null

# 2. Check cert expiry dates
echo | openssl s_client -connect nyxfinance.com:443 -servername nyxfinance.com 2>/dev/null \
  | openssl x509 -noout -dates -subject -issuer

# 3. Confirm SANs (the names the cert is valid for)
echo | openssl s_client -connect nyxfinance.com:443 -servername nyxfinance.com 2>/dev/null \
  | openssl x509 -noout -ext subjectAltName

# 4. Verify a *specific* protocol is REFUSED (TLS 1.0 should fail to connect)
openssl s_client -connect nyxfinance.com:443 -tls1   # should error: "no protocols available"

# 5. Confirm TLS 1.3 is offered
openssl s_client -connect nyxfinance.com:443 -tls1_3 </dev/null | grep -i "Protocol\|Cipher"
```

What you're checking: `Verify return code: 0 (ok)` (chain validates), the chain includes the intermediate, expiry is comfortably in the future, the SAN matches the hostname, old protocols are refused, and TLS 1.3 negotiates a strong cipher (e.g., `TLS_AES_256_GCM_SHA384`).

## 🧪 Lab - build iptables rules with predict-and-verify (local, no cloud needed)

The fastest way to *understand* a firewall is to write a rule, **predict** what it will do, then **verify** with a real packet. Do this safely on a throwaway Ubuntu container (or VM) so a mistake can't lock you out of anything important. The discipline, predict *before* you check, is the whole point; it forces you to actually reason about rule order and state.

```bash
# A disposable Ubuntu box with iptables available. --privileged is needed for netfilter.
docker run --rm -it --privileged --name fwlab ubuntu:24.04 bash
apt-get update && apt-get install -y iptables iproute2 curl netcat-openbsd python3
```

### Step 1 - start permissive, baseline

```bash
# A tiny listener on 8080 so we have something to hit locally.
python3 -m http.server 8080 &
# Baseline: default ACCEPT, nothing filtered.
iptables -L INPUT -n --line-numbers
curl -s -m 2 http://127.0.0.1:8080/ >/dev/null && echo "PREDICT+VERIFY: reachable (no rules yet)"
```

### Step 2 - switch to default-deny and predict the breakage

**Predict first:** "If you set policy DROP on INPUT with no allow rules, even loopback traffic to your own listener will be dropped, so the curl should hang/fail."

```bash
iptables -P INPUT DROP
# VERIFY (expect FAILURE - that's the lesson):
curl -s -m 2 http://127.0.0.1:8080/ >/dev/null && echo "reachable" || echo "VERIFIED: blocked by default-deny"
```

It fails, even loopback. That surprises people, and it's exactly why every real ruleset starts by *explicitly* allowing `lo`.

### Step 3 - add rules one at a time, predicting each

```bash
# Rule A: allow loopback. PREDICT: curl to 127.0.0.1 now succeeds again.
iptables -A INPUT -i lo -j ACCEPT
curl -s -m 2 http://127.0.0.1:8080/ >/dev/null && echo "VERIFIED: loopback allowed" || echo "still blocked"

# Rule B: allow established/related (stateful). PREDICT: replies to MY outbound
#   connections (e.g., apt, curl to the internet) are now allowed back in.
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
curl -s -m 4 http://example.com/ >/dev/null && echo "VERIFIED: outbound reply allowed back (stateful)" || echo "blocked"
```

### Step 4 - the rule-ORDER trap (predict the bug)

This is the classic interview gotcha. First match wins; a broad ALLOW above a specific DROP silently defeats the DROP.

```bash
# Insert a broad allow for all TCP to 9090, THEN try to drop one source. PREDICT the bug:
iptables -A INPUT -p tcp --dport 9090 -j ACCEPT          # broad allow (appended = lower)
iptables -A INPUT -p tcp -s 10.1.2.3 --dport 9090 -j DROP # specific drop (appended = even lower)
iptables -L INPUT -n --line-numbers
# PREDICT: because the broad ACCEPT comes FIRST, the DROP for 10.1.2.3 never matches.
# FIX: order matters - put the specific DROP ABOVE the broad ACCEPT.
iptables -D INPUT -p tcp -s 10.1.2.3 --dport 9090 -j DROP
iptables -I INPUT -p tcp -s 10.1.2.3 --dport 9090 -j DROP # -I inserts at TOP
iptables -L INPUT -n --line-numbers
# Now the specific DROP is evaluated first. VERIFIED by reading the ordered list.
```

### Step 5 - count what each rule actually catches

```bash
# -v shows packet/byte counters per rule - proof of which rule is doing the work.
iptables -L INPUT -n -v --line-numbers
# A rule with 0 packets after real traffic = dead rule (wrong order, or unneeded).
```

### The same thing in `ufw`, with predict-and-verify

For day-to-day hosts you'll reach for `ufw` (it compiles down to the same netfilter rules). The predict/verify loop is identical:

```bash
sudo ufw --force reset
sudo ufw default deny incoming         # PREDICT: all inbound now dropped
sudo ufw allow 443/tcp                 # PREDICT: only 443 reachable
sudo ufw allow from 203.0.113.7 to any port 22 proto tcp  # PREDICT: 22 only from my IP
sudo ufw enable
sudo ufw status verbose numbered       # VERIFY the compiled ruleset + order
# From ANOTHER machine, confirm the prediction:
#   nc -vz <host> 443   -> should connect
#   nc -vz <host> 22    -> should connect ONLY from 203.0.113.7, refused elsewhere
#   nc -vz <host> 8080  -> should be filtered/refused
```

**Deliverable for the lab:** a short table of `rule | prediction | observed | match?` for each step. Every mismatch is a lesson about state or order. This predict-then-verify habit is exactly how you avoid the "I added a rule and *thought* it worked" class of firewall bug in production.

## 🧪 Mini-project - "Harden this server" checklist applied to a fresh cloud VM

Provision a fresh Ubuntu VM (any cloud) and apply each step. For every step, write *the threat it addresses*, that's the whole point.

### The checklist

| # | Step | Threat addressed |
|---|------|------------------|
| 1 | Create a non-root sudo user; **disable root login** | Limits blast radius; root is the #1 brute-force target (least privilege) |
| 2 | **SSH keys only, disable password auth** | Defeats password brute force / credential stuffing on SSH |
| 3 | Move SSH off 22 *and* restrict source IP | Cuts automated scan noise; restrict-by-IP is the real control |
| 4 | **Default-deny firewall** (ufw), open only 443 + SSH-from-your-IP | Minimizes attack surface (least privilege on the network) |
| 5 | **fail2ban** on SSH/web logs | Auto-bans IPs after repeated auth failures (slows brute force) |
| 6 | **Automatic security updates** (`unattended-upgrades`) | Closes the window on known/patched CVEs |
| 7 | **TLS via Let's Encrypt** + HSTS + TLS 1.2/1.3 only | Confidentiality/integrity in transit; resists downgrade |
| 8 | Database has **no public IP**; reachable only from app tier | Segmentation/DMZ, breach of web ≠ breach of data |
| 9 | **Least-privilege service accounts** (app runs as non-root, scoped DB user) | Contains a compromised app process |
| 10 | **Egress filtering** on sensitive hosts | Stops exfiltration / C2 beaconing post-compromise |
| 11 | Ship **logs to central store** (Elasticsearch/Splunk) + alerts | Detection when prevention fails (tie to 13.1) |
| 12 | **Secrets** in a vault/secret manager, never in code/env-in-repo | Prevents credential leak via repo or image |

### Apply the key steps

**1-3: SSH hardening.** Edit `/etc/ssh/sshd_config`:

```bash
sudo adduser spencer && sudo usermod -aG sudo spencer
# Copy my public key up first: ssh-copy-id spencer@<vm-ip>

sudo tee /etc/ssh/sshd_config.d/hardening.conf >/dev/null <<'EOF'
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
KbdInteractiveAuthentication no
MaxAuthTries 3
AllowUsers spencer
EOF
sudo systemctl restart ssh
# THREAT: SSH is the most-attacked port on the internet. Keys + no-password +
# no-root removes the entire password-guessing attack class.
```

**4: Firewall**, the ufw block from "Build it" above.

**5: fail2ban** (the *concept*: parse auth logs, ban IPs that fail repeatedly).

```bash
sudo apt-get install -y fail2ban
sudo tee /etc/fail2ban/jail.local >/dev/null <<'EOF'
[sshd]
enabled  = true
maxretry = 4
findtime = 10m
bantime  = 1h
EOF
sudo systemctl enable --now fail2ban
sudo fail2ban-client status sshd
# THREAT: even with keys-only SSH, fail2ban throttles scanners and protects any
# other auth surface (e.g., a login endpoint) from credential stuffing.
```

**6: Auto-updates.**

```bash
sudo apt-get install -y unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades
# THREAT: most breaches exploit KNOWN, already-patched CVEs. Auto-patching
# shrinks the exposure window from weeks to hours.
```

**7: TLS.** `sudo certbot --nginx -d nyxfinance.com`, then in nginx enforce:

```nginx
ssl_protocols TLSv1.2 TLSv1.3;
ssl_prefer_server_ciphers off;          # let TLS 1.3 pick; modern clients win
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
# THREAT: eavesdropping/MITM in transit; HSTS resists SSL-strip downgrade.
```

**11: Logging/detection.** Ship `/var/log/auth.log`, nginx logs, and ufw logs to Elasticsearch (Filebeat) or Splunk; alert on SSH-failure spikes, 403/401 spikes, and new-geo egress. *Threat: prevention isn't perfect, you need to see and respond.* (13.1.)

### Verify the hardening

```bash
sudo ufw status verbose                       # default-deny, minimal allows
sudo ss -tlnp                                  # what's ACTUALLY listening - surprises?
sudo grep -E 'PermitRootLogin|PasswordAuth' /etc/ssh/sshd_config.d/*.conf
sudo fail2ban-client status sshd               # jail active
systemctl is-enabled unattended-upgrades
# External view: scan my own VM's open ports (authorized - it's mine) to confirm
# only 443 (and SSH from my IP) is reachable.
nmap -Pn <vm-ip>
```

The deliverable is this filled-in checklist + the commands run + a one-line threat note per step. That's a defensible, repeatable hardening baseline you can templatize (Ansible/cloud-init) for every NYX/Anneava host.

## 🧪 Mini-project #2 - Build a 3-tier segmented network locally with Docker

You don't need a cloud account to *feel* segmentation, Docker networks make it concrete on your laptop. The goal: prove that a "database" container is reachable from the "app" container but **not** from a container that simulates the public internet, and that the app reaches the DB while the DB cannot reach out. This is the DMZ/least-privilege idea made tangible.

```bash
# 1. Three networks modeling three trust zones.
docker network create edge        # "internet-facing" zone (public)
docker network create app_net     # app tier (private)
docker network create data_net    # data tier (most private)

# 2. The database lives ONLY on data_net - no public exposure, no port published.
docker run -d --name db --network data_net \
  -e POSTGRES_PASSWORD=devsecret postgres:16

# 3. The app server sits on BOTH app_net and data_net (it must talk to the DB),
#    and is the only thing bridging toward the DB. We publish ONLY the app port.
docker run -d --name app --network app_net -p 8080:8080 nginx
docker network connect data_net app          # app gets a foot in the data tier

# 4. An "internet" container that should be able to reach the app but NOT the DB.
docker run -d --name internet --network edge alpine sleep infinity
docker network connect app_net internet      # internet can reach the app tier only
```

Now run the experiments and *predict each result first* (that's the learning):

```bash
# app -> db : SHOULD succeed (app is on data_net)
docker exec app sh -c "getent hosts db && echo 'app can resolve/reach db'"

# internet -> db : SHOULD FAIL (internet is not on data_net) - this is segmentation working
docker exec internet sh -c "getent hosts db || echo 'BLOCKED: internet cannot even see db'"

# internet -> app : SHOULD succeed (both on app_net)
docker exec internet sh -c "wget -qO- http://app:80 >/dev/null && echo 'internet reaches app'"
```

**What this teaches, mapped to the theory:**

| Observation | Principle |
|---|---|
| DB has no published port and no `edge` membership | No public IP for the data tier (segmentation) |
| `internet` container can't resolve/reach `db` | Breach of the edge ≠ breach of data (defense in depth) |
| Only `app` bridges `app_net`↔`data_net` | Single, controlled path; least privilege on the network |

**Extensions:** add egress control by giving the DB container `--network data_net` only and confirming it can't reach the internet (`docker exec db sh -c "wget -T3 -qO- http://example.com || echo 'egress blocked'"` after running it on an internal-only network); then translate this exact topology to cloud security groups (the AWS block in "Theory" is the same idea: the DB SG only accepts from the app SG). Write a short note: "in production, `edge` = ALB/WAF, `app_net` = private app subnet, `data_net` = isolated DB subnet with no route to the internet gateway."

## 🧪 Mini-project #3 - Defense-in-depth case study: hardening the NYX Finance stack end to end

The mini-projects above each isolate *one* idea. This one is the synthesis you'd actually present in a design review: take a single real stack (NYX Finance's transfer API + Postgres) and walk **every layer**, naming the control, the threat it stops, and what a compromise at that layer would expose if the control failed open. This is "defense in depth" stopped being a slogan and became a checklist with verification steps.

The stack: `Cloudflare/WAF → ALB (TLS termination) → app servers (private subnet) → Postgres (isolated subnet, no internet route)`.

### Layer-by-layer hardening table

| Layer | Control you apply | Threat it stops | If it fails open, exposure is… | How you verify |
|---|---|---|---|---|
| **Edge / DNS** | Registrar lock + MFA; DNSSEC; no dangling records | Domain hijack, cache poisoning, subdomain takeover | Attacker MITMs all traffic / phishes users | Audit DNS records monthly; `dig +dnssec`; alert on record changes |
| **CDN / WAF** | Cloudflare in front; managed ruleset; per-IP rate limit; bot mode | Volumetric DDoS, known-bad request patterns, scraping | Origin absorbs floods; injection patterns reach app | Confirm origin only accepts from CDN IPs; test a blocked pattern |
| **Transport (TLS)** | TLS 1.2/1.3 only, HSTS, full chain, auto-renew + 21-day alert | Eavesdropping, MITM, SSL-strip downgrade, expiry outage | Traffic readable/forgeable in transit | `openssl s_client` checks (above); SSL Labs A+; renewal dry-run |
| **Network (firewall/SG)** | Default-deny; only 443 public; SSH keys-only from your IP; egress allowlist | Exposed services, brute force, post-breach exfiltration/C2 | Any forgotten port internet-reachable | `nmap` your own host; `ss -tlnp`; review SG rules |
| **App authn/authz** | Server-side auth on every route; ownership checks; RLS | Broken access control / IDOR (12.3 A01) | One user reads another's data | Burp regression tests (12.4); pytest authz suite |
| **App input** | Parameterized queries, Pydantic validation, output encoding | SQLi (A03), XSS, malformed input | DB compromise / script execution | Repeater fuzzing; static analysis in CI |
| **DB / data tier** | No public IP; least-privilege DB user (no superuser); RLS; TLS to DB | Direct DB exposure, over-broad queries | Whole-database read/write from anywhere | Confirm no public IP; `\du` shows scoped role |
| **Data at rest** | Encryption at rest (KMS); encrypted backups | Stolen disk/snapshot reads PHI/PII | Plaintext data on a leaked volume | KMS key policy + CloudTrail; restore-test a backup |
| **Secrets** | Vault/Secrets Manager; per-service scope; 90-day rotation; pre-commit scan | Leaked credentials via repo/image/log | Long-lived key grants standing access | `detect-secrets` in CI; audit secret-read logs |
| **Detection** | Ship auth/firewall/WAF logs to Elasticsearch/Splunk; symptom alerts | Undetected intrusion (prevention failed silently) | Breach proceeds for weeks unnoticed | Trigger a test auth-failure spike; confirm the alert fires (13.1) |

### The walkthrough to narrate

"A transfer request hits **Cloudflare**, which absorbs floods and drops obvious injection patterns (but you never *rely* on it, the WAF is a net). It reaches the **ALB**, which terminates **TLS 1.3** with a full, auto-renewed chain, so the request was confidential and unforgeable on the wire. The ALB forwards to an **app server in a private subnet** the internet can't route to directly; the server's **security group** only accepts from the ALB's group (default-deny everywhere else). The app **authenticates and authorizes server-side**, it re-checks that this user owns this account, not trusting anything the client sent, and uses **parameterized queries**, so even a malicious body can't cross the data/code boundary. It talks to **Postgres on an isolated subnet with no internet route**, as a **least-privilege DB user** with **RLS** enforcing tenant isolation as a second wall. The data is **encrypted at rest**; the **DB password came from Secrets Manager**, scoped to this service and rotated on a schedule. Every auth and firewall event ships to **Elasticsearch**, where a **symptom alert** watches for the day one of these layers fails."

The point of writing it this way: **no single control is load-bearing.** If TLS were misconfigured, the DB still has no public IP. If authz had a bug, RLS still blocks cross-tenant reads. If a secret leaked, rotation and scoping bound the damage. That redundancy *is* defense in depth, and the "if it fails open" column is the discipline that proves you've layered rather than stacked single points of failure.

**Deliverable:** the filled-in table for one of your real stacks, with the *verify* column actually run (not just listed), and a one-paragraph honest assessment of which layer is currently your weakest, because the value is finding the thin layer *before* an attacker does.

## ⚠️ Common mistakes

- **Allow-by-default firewalls** ("block known-bad"). You can never enumerate all bad. Always default-deny and explicitly allow.
- **Forgetting egress filtering.** Everyone locks ingress; few lock outbound. Egress control is what stops data exfiltration and C2 beaconing *after* a breach.
- **Database with a public IP.** The #1 way to leak a whole database. The data tier should have no internet route at all.
- **SSH open to `0.0.0.0/0` with password auth.** The most-attacked surface on the internet. Keys-only, no root, restrict source IP, fail2ban.
- **Rule-order bugs in iptables.** First match wins; a broad ALLOW above a specific DENY silently defeats the DENY. Order specific→general, deny last.
- **Serving the leaf cert without the intermediate chain.** "Works in my browser" (it cached the intermediate) but fails for others. Always serve the full chain and verify with `openssl`, not your own browser.
- **Letting certs expire.** Automate renewal (ACME) and alert at ~21 days. An expired cert is a self-inflicted outage.
- **Leaving TLS 1.0/1.1, RC4, 3DES enabled.** Downgrade/weak-cipher exposure. Require TLS 1.2+ (prefer 1.3); disable legacy.
- **No HSTS.** Leaves room for SSL-strip downgrade. Send `Strict-Transport-Security`.
- **Treating a WAF as the fix for SQLi/XSS.** A WAF is a *net*, bypassable. Fix the app (parameterized queries, encoding, 12.3); the WAF is an extra layer.
- **Confusing DNSSEC and DoH.** DNSSEC = authenticity/integrity of records; DoH/DoT = confidentiality of the query. Different properties; you may want both.
- **Dangling DNS records.** A CNAME pointing at a deprovisioned cloud resource → subdomain takeover. Audit and remove stale records.
- **Secrets in git or baked into images.** A committed `.env` or a key in a Docker layer leaks to anyone with the repo/image. Use a secret manager; scan with detect-secrets/gitleaks; and remember `git rm` doesn't remove it from history, you must *rotate*.
- **Never rotating keys.** A static, never-rotated key means an old leak grants access forever. Rotate on a schedule, support two keys during cutover, revoke the old one.
- **Alerting only on causes (CPU/disk), never on symptoms.** Ship logs centrally and alert on auth-failure spikes, 403 spikes, new-geo egress, prevention isn't perfect.

## 💼 On the job / interview angle

For backend, DevOps, SRE, and cloud roles, network-security fluency is expected even at entry level, and observability of security events is increasingly part of "production-ready." Teams want to see that you can reason about *attack surface* and *blast radius*, not just recite tools.

**What teams expect a junior to do correctly:**

- Default-deny security groups; databases with no public IP; SSH keys-only behind a bastion/VPN.
- Automated TLS (Let's Encrypt/ACME) with renewal alerting; TLS 1.2+ only; HSTS.
- Secrets in a manager (never in code/images), scoped per-service, rotated.
- Ship security-relevant logs (auth, firewall, WAF) to a central store and alert on anomalies.
- Articulate least privilege and defense in depth with a concrete example.

**Representative interview questions (with the crisp answer):**

1. *"Walk me through hardening a fresh Linux server exposed to the internet."* → Non-root sudo user, disable root login, SSH keys-only + restrict source IP + fail2ban, default-deny firewall opening only what's needed, auto security updates, TLS, no public DB, central logging. (The checklist below is exactly this answer.)
2. *"Stateful vs stateless firewall?"* → Stateful tracks connections (allow established/related), so you only write rules for new inbound; stateless treats each packet alone and is error-prone. Cloud security groups are stateful.
3. *"How does HTTPS protect a request, end to end?"* → ECDHE key exchange (forward secrecy) + CA-signed certificate authenticating the server (defeats MITM) + AES-GCM for traffic. (Cross-link 12.1.)
4. *"What's the difference between a WAF and a network firewall?"* → Network firewall filters by IP/port (L3/L4); a WAF inspects HTTP content (L7), URLs, headers, body, and can block injection patterns and rate-limit. WAF is an additional layer, not a substitute for fixing the app.
5. *"How would you mitigate a DDoS?"* → Classify by layer: volumetric → upstream CDN/scrubbing; protocol (SYN flood) → SYN cookies/conn limits; application (L7) → rate limiting, caching, autoscaling, WAF. Treat availability as a first-class goal.
6. *"What is least privilege, and what's 'blast radius'?"* → Every component gets the minimum access it needs; blast radius is how far a single compromise can reach. Least privilege shrinks the blast radius.
7. *"How do you know your security controls work?"* (the observability angle) → Ship auth/firewall/IDS logs to Elasticsearch/Splunk and alert on SSH-failure spikes, 403/401 spikes, and unexpected egress, detection assuming prevention fails. (Cross-link 13.1.)
8. *"Walk me through a TLS handshake and tell me what `Verify return code: 20` means."* → ClientHello (versions/ciphers/SNI/key_share) → ServerHello (chosen cipher, key_share) → Certificate (leaf+intermediates) → CertificateVerify (proves key ownership) → Finished (transcript MAC) → app data under an AEAD cipher; ephemeral ECDHE gives forward secrecy. `Verify return code: 20` = "unable to get local issuer certificate" = the server didn't send the intermediate chain; fix by serving the fullchain.
9. *"How do you manage secrets, and how do you rotate a signing key without downtime?"* → Secrets live in a manager (Vault/Secrets Manager), scoped per service, audit-logged, never in code/images (scanned in CI). Rotate by overlap-then-revoke: publish both keys (JWKS with two `kid`s), sign new tokens with the new key while still verifying old ones, switch signers, then revoke the old key once all old tokens expire.
10. *"A secret got committed to a public repo. What do you do?"* → Rotate it *immediately* (assume compromised), invalidate the old value, audit access logs for use of the leaked key. `git rm` is not enough, the value persists in history and in clones, so rotation is the only real fix.

### Solutions

1. Accepted if: it's a reply to an established outbound connection (implicit stateful allow), OR destination port 443/tcp from anyone, OR port 22/tcp from `203.0.113.7`. Everything else hits the `deny (incoming)` default and is dropped.

4. `openssl s_client -connect host:443 -servername host -showcerts </dev/null` → look for `Verify return code: 0 (ok)` and the intermediate in the chain. SAN: pipe to `openssl x509 -noout -ext subjectAltName`. Refused TLS 1.0: `openssl s_client -connect host:443 -tls1` should error with "no protocols available."
5. It **cannot** reach `db`: `internet` is on `edge` and `app_net` but not `data_net`, and `db` lives only on `data_net`. With no shared network, Docker's embedded DNS won't even resolve `db` for it - segmentation by network membership.
6. DNSSEC = **authenticity/integrity** (signed records; defends against cache poisoning/spoofing). DoH/DoT = **confidentiality** of the query (defends against an on-path observer seeing/altering your lookups). They're complementary.
7. (a) Volumetric L3/L4 → upstream CDN/scrubbing provider (you can't absorb it on one box). (b) Protocol L4 → SYN cookies + connection limits. (c) Application L7 → rate limiting + caching + autoscale + WAF.
8. Example: **S**poofing → attacker forges a session to read PHI → strong auth/MFA + signed tokens. **T**ampering → modify a record → integrity controls/audit + parameterized writes. **R**epudiation → deny accessing a record → immutable audit log. **I**nfo disclosure → DB leak → encryption at rest + no public IP + RLS. **D**oS → flood the API → rate limiting + autoscale. **E**levation → low-priv user gains admin → least-privilege DB roles + server-side authz.
9. With keys-only SSH, fail2ban (a) cuts log noise and CPU from constant scanner traffic, and (b) protects *other* auth surfaces on the box - e.g., a web login endpoint - from credential stuffing, since fail2ban can watch any auth log, not just sshd.
10. Verify code `20` = "unable to get local issuer certificate" = the client can't find the issuer of the leaf, because the server only sent the leaf (entry 0) and **not the intermediate**. It "works in my browser" only because the browser cached the intermediate from another site. Fix: configure the server to serve the **fullchain** (leaf + intermediate), e.g., point nginx at `fullchain.pem`, and re-verify with `-showcerts` until entry 1 (the intermediate) appears and the code is `0`.
11. Generate the new key; publish *both* public keys in the JWKS so verifiers accept either; start signing new tokens with the new key (its `kid` in the header) while still verifying old tokens with the old key; once all old tokens have expired (bounded by the short token lifetime), remove the old key from the JWKS and revoke it. The `kid` (key id) in the JWT header tells the verifier *which* published key to use, which is what makes holding multiple keys - and thus smooth rotation - possible.
12. CDN/WAF (absorbs volumetric/blocks bad patterns) → TLS termination (confidentiality/integrity, defeats MITM) → rate limiter (throttles credential stuffing) → input validation (rejects malformed/oversized) → parameterized query (no SQLi) → least-privilege DB user (limits what a compromised query can do) → RLS/segmented data tier (no cross-tenant/public reach) → encryption at rest (a stolen disk is useless) → audit logging (detection). Failing open at TLS → eavesdropping/MITM; at the DB user → a single bug reads everything; at the data tier → public exposure of the whole database. No single hop is allowed to be the only thing standing.
