# Chapter 10.1 - Docker & Containerization

> Goal: Understand *exactly* what a container is at the Linux-kernel level, why it solves "works on my machine," and how to write tight, fast-building, secure Dockerfiles. By the end I can containerize a FastAPI app with a multi-stage build and stand up a full app + Postgres + Redis stack with `docker compose`.

I (Spencer) already run containers daily, but I've been treating Docker as magic. This chapter rips the lid off. No black boxes.

## 🌱 Start here (beginner on-ramp)

If you've never touched Docker, start with one analogy and one promise.

**The analogy: a shipping container.** Before standardized shipping containers, loading a cargo ship was chaos, every crate a different size, every port doing it its own way. The steel shipping container fixed that: one standard box that any crane, truck, train, or ship can handle without caring what's *inside* it. A software container is the same idea. Your app, its libraries, its Python version, its config, all packed into one standard box. Any machine running Docker can pick up that box and run it without caring what's inside. The crane doesn't need to know it's carrying bananas; the server doesn't need to know it's running Python.

**The promise: "it runs the same everywhere."** That's the entire payoff. You build the box once, and it behaves identically on your Mac, on a teammate's Windows laptop, on a Linux server, and in the cloud. No more "but it worked on my machine."

**The three words you'll use constantly:**

- **Image**, the box, sitting on a shelf, not doing anything. A blueprint. (Think: a recipe, or a class in code.)
- **Container**, the box opened up and running. A live instance of an image. (Think: a cake baked from the recipe, or an object created from a class.)
- **Dockerfile**, the instructions for *how to pack the box*. A plain text file you write.

**Your very first container, run this right now** (after [installing Docker Desktop](https://www.docker.com/products/docker-desktop/)):

```bash
docker run hello-world
```

What happens, step by step:
1. Docker looks for an image called `hello-world` on your machine. It's not there.
2. So it **pulls** it from Docker Hub (the default public registry).
3. It creates a **container** from that image and runs it.
4. The container prints a friendly message explaining it just did all that, then exits.

Expected output (trimmed):

```
Unable to find image 'hello-world:latest' locally
latest: Pulling from library/hello-world
...
Hello from Docker!
This message shows that your installation appears to be working correctly.
```

Now run something more interesting, a real web server, in one line:

```bash
docker run -d -p 8080:80 --name web nginx
```

Open `http://localhost:8080` in your browser. That's a full nginx web server, running in isolation, that you did not install, configure, or even think about. When you're done:

```bash
docker stop web && docker rm web
```

That's the whole beginner loop: `run`, see it work, `stop`, `rm`. Everything below explains *why* it works and how to build your own boxes. **Why it matters:** containers are how nearly all modern software ships and runs. If you can write a Dockerfile and run `docker compose up`, you can onboard onto almost any backend team on day one.

## 📐 Concept

### The problem: "works on my machine"

The classic failure mode: my FastAPI app runs fine on my Mac. I ship it to a Linux box and it explodes, different Python patch version, a missing `libpq`, a different `OPENSSL` version, `$PATH` pointing somewhere else, a config file that lives in a different place. The *code* is identical; the *environment* is not.

The old fixes were bad:

- **"Just document the setup steps."** Docs rot. Nobody reads them. Step 7 assumes you already did the thing in step 12.
- **Virtual machines.** Ship the whole OS. Works, but a VM is gigabytes and boots in tens of seconds. Running 30 microservices means 30 guest kernels, wasteful.

A container packages **the app plus its entire userland dependency tree** (libraries, interpreter, files, env vars) into one immutable artifact, while *sharing the host's kernel*. That's the whole trick: same isolation benefits as a VM for most purposes, but near-zero overhead because there's no second kernel.

### VMs vs containers: what's actually shared

```
   VIRTUAL MACHINES                    CONTAINERS
 ┌───────┐ ┌───────┐ ┌───────┐      ┌───────┐ ┌───────┐ ┌───────┐
 │ App A │ │ App B │ │ App C │      │ App A │ │ App B │ │ App C │
 ├───────┤ ├───────┤ ├───────┤      ├───────┤ ├───────┤ ├───────┤
 │ Libs  │ │ Libs  │ │ Libs  │      │ Libs  │ │ Libs  │ │ Libs  │
 ├───────┤ ├───────┤ ├───────┤      └───────┴─┴───────┴─┴───────┘
 │Guest  │ │Guest  │ │Guest  │      ┌───────────────────────────┐
 │ OS    │ │ OS    │ │ OS    │      │   Docker / container rt   │
 ├───────┴─┴───────┴─┴───────┤      ├───────────────────────────┤
 │       Hypervisor          │      │      Host kernel          │
 ├───────────────────────────┤      ├───────────────────────────┤
 │       Host kernel/HW      │      │       Host hardware       │
 └───────────────────────────┘      └───────────────────────────┘
```

A VM virtualizes **hardware**: each VM has its own kernel running on emulated/para-virtualized devices, managed by a hypervisor. A container virtualizes the **operating system's view**: all containers share the host kernel, but each gets its own *isolated slice* of it.

So what is "an isolated slice"? It's three Linux kernel primitives glued together. **A container is not a thing the kernel knows about**, there's no `container` syscall. Docker just configures these three features for a normal process:

#### 1. Namespaces - what a process can *see*

Namespaces partition kernel resources so a process group sees its own private instance. The important ones:

| Namespace | Isolates | Effect inside container |
|-----------|----------|-------------------------|
| `pid` | Process IDs | Your app sees itself as PID 1; can't see host processes |
| `mnt` | Mount points | Its own filesystem tree (the image) |
| `net` | Network stack | Own interfaces, routing table, ports |
| `uts` | Hostname | `hostname` returns the container's, not host's |
| `ipc` | Shared memory / semaphores | Can't touch host IPC |
| `user` | UID/GID mappings | Root *inside* can map to unprivileged *outside* |

You can play with these without Docker:

```bash
# Run bash in fresh PID + mount + UTS namespaces (Linux)
sudo unshare --pid --mount --uts --fork --mount-proc bash
# inside:
ps aux        # you see ~2 processes, not the host's hundreds
hostname box1 # changing hostname doesn't affect the host
```

That `ps aux` showing almost nothing is the *exact* magic Docker uses.

#### 2. cgroups (control groups) - what a process can *use*

Namespaces hide things; cgroups **limit and account** for resource usage, CPU, memory, block I/O, PIDs. This is how `docker run --memory=512m` works: Docker puts the container's processes into a cgroup with a 512 MB memory limit. Exceed it and the OOM killer fires *inside the container*, not on the host.

```bash
# Peek at a running container's cgroup limits
docker run -d --name lim --memory=256m --cpus=0.5 nginx
cat /sys/fs/cgroup/memory.max  # on host, in the container's cgroup path
```

#### 3. Union filesystems - how images stack

A container's filesystem is built from **read-only layers** stacked with a copy-on-write union filesystem (overlayfs on modern Linux). Each Dockerfile instruction adds a layer. At runtime Docker adds a thin **writable layer** on top. Writes go there (copy-on-write); the underlying layers stay immutable and *shared across containers*. That's why launching 10 containers from one image costs almost no disk.

Put the three together: **a container = a process (or process tree) running with its own namespaces, constrained by cgroups, rooted in a stacked union filesystem.** That's it. No magic.

### Images vs containers

- An **image** is the immutable, layered blueprint (a tarball of layers + JSON metadata). Like a class.
- A **container** is a running (or stopped) instance of an image with its writable layer. Like an object.

```
image  ── docker run ──▶  container (image layers + writable layer + namespaces + cgroups)
```

You can have many containers from one image. `docker commit` can freeze a container back into a new image, but you should almost never do that, use a Dockerfile so the build is reproducible.

## 💻 Build it: containerize a FastAPI app

Let's containerize a real FastAPI service, then optimize the Dockerfile properly.

### The app

`app/main.py`:

```python
from fastapi import FastAPI
import os

app = FastAPI(title="nyx-demo")

@app.get("/health")
def health():
    return {"status": "ok", "env": os.getenv("APP_ENV", "dev")}

@app.get("/")
def root():
    return {"message": "hello from a container"}
```

`requirements.txt`:

```
fastapi==0.111.0
uvicorn[standard]==0.30.1
```

### A naïve Dockerfile (and why it's bad)

```dockerfile
FROM python:3.12
COPY . .
RUN pip install -r requirements.txt
CMD uvicorn app.main:app --host 0.0.0.0 --port 8000
```

This *works* but: the image is ~1 GB (full Debian + build toolchain), it reinstalls dependencies on every code change (bad caching), and it runs as root. Let's fix all of it. First, every instruction explained.

### Every Dockerfile instruction, explained

| Instruction | What it does | Gotchas |
|-------------|--------------|---------|
| `FROM` | Base image; first real instruction. Sets the starting filesystem. | Pick a minimal/pinned tag (`python:3.12-slim`, not `python:latest`). |
| `RUN` | Executes a command *at build time*, committing the result as a new layer. | Each `RUN` = a layer. Chain related commands with `&&` to reduce layers and clean caches in the same layer. |
| `COPY` | Copies files from build context into the image. | Order matters for cache (see below). Prefer over `ADD`. |
| `ADD` | Like COPY but also untars archives and fetches URLs. | Avoid unless you need auto-extraction; surprising behavior. |
| `WORKDIR` | Sets the cwd for following instructions and the container. Creates the dir if missing. | Use it instead of `RUN cd ...` (cd doesn't persist across RUNs). |
| `ENV` | Sets environment variables at build time *and* runtime. | Baked into the image, don't put secrets here. |
| `ARG` | Build-time-only variable (`--build-arg`). | Not present at runtime. |
| `EXPOSE` | Documents which port the app listens on. | Purely informational/metadata, does **not** publish the port. You still need `-p`. |
| `CMD` | Default command/args if none given at `docker run`. | Overridden by args after the image name. |
| `ENTRYPOINT` | The executable that always runs; CMD becomes its default args. | Use ENTRYPOINT for "this image *is* this program," CMD for default args. |
| `USER` | Switch to a non-root user for following instructions and runtime. | Critical for security. |
| `HEALTHCHECK` | Command Docker runs to judge container health. | Surfaces as `healthy/unhealthy` in `docker ps`. |

#### CMD vs ENTRYPOINT - the one people fumble

Two forms exist: **exec form** `["uvicorn","..."]` (no shell, args are an array, preferred) and **shell form** `uvicorn ...` (wrapped in `/bin/sh -c`, which breaks signal handling so SIGTERM may not reach your app).

The mental model:

- `ENTRYPOINT` = the fixed program.
- `CMD` = default arguments to that program.

```dockerfile
ENTRYPOINT ["uvicorn", "app.main:app", "--host", "0.0.0.0"]
CMD ["--port", "8000"]
```

Now `docker run img` runs uvicorn on 8000. `docker run img --port 9000` swaps the port but still runs uvicorn. If you'd used only `CMD ["uvicorn", ...]`, then `docker run img bash` would replace the *whole thing* with bash, sometimes desirable (debugging), sometimes not. Pick deliberately.

### Layers & the build cache

Each instruction produces a layer keyed by (instruction text + the state of inputs). On rebuild, Docker walks instructions top-to-bottom and **reuses cached layers until the first one whose inputs changed**, then everything below is rebuilt.

Consequence: **put things that change rarely high, things that change often low.** Dependencies change rarely; my source code changes every save. So copy and install deps *before* copying the source:

```dockerfile
# deps layer - only invalidated when requirements.txt changes
COPY requirements.txt .
RUN pip install -r requirements.txt
# source layer - changes constantly, but deps stay cached
COPY . .
```

If I'd done `COPY . .` first, editing one line of `main.py` would bust the cache and reinstall all deps every build. The reorder turns a 90-second rebuild into a 2-second one.

### Multi-stage build (the optimized version)

A multi-stage build uses multiple `FROM`s. Early stages can have compilers and build junk; the **final stage copies only the artifacts it needs**, leaving the toolchain behind. The result ships nothing it doesn't run.

`Dockerfile`:

```dockerfile
# ---------- Stage 1: builder ----------
FROM python:3.12-slim AS builder

# Don't write .pyc, don't buffer stdout (better logs)
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1

WORKDIR /app

# Install into a virtualenv we can copy wholesale into the final stage
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"

# Cache-friendly: deps first
COPY requirements.txt .
RUN pip install --upgrade pip && pip install -r requirements.txt

# ---------- Stage 2: runtime ----------
FROM python:3.12-slim AS runtime

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    APP_ENV=prod \
    PATH="/opt/venv/bin:$PATH"

# Create an unprivileged user
RUN groupadd --system app && useradd --system --gid app --no-create-home appuser

WORKDIR /app

# Bring over just the built venv from the builder stage
COPY --from=builder /opt/venv /opt/venv

# Now the app source (changes most often → last)
COPY app ./app

# Drop root
USER appuser

EXPOSE 8000

HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD python -c "import urllib.request,sys; sys.exit(0) if urllib.request.urlopen('http://localhost:8000/health').status==200 else sys.exit(1)"

ENTRYPOINT ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

Why this shrinks the image: the `builder` stage may pull in pip caches, wheels, build deps, none of that lands in `runtime`. We only copy `/opt/venv`. From ~1 GB down to ~150 MB.

`.dockerignore` (matters, the build context is `tar`'d and sent to the daemon; don't ship junk or secrets):

```
.git
.venv
__pycache__/
*.pyc
.env
.pytest_cache
node_modules
*.md
```

### Build, run, inspect

```bash
# Build (the -t names+tags it)
docker build -t nyx-demo:1.0 .

# See the layer sizes
docker history nyx-demo:1.0

# Run, publishing host 8080 -> container 8000
docker run -d --name web -p 8080:8000 -e APP_ENV=prod nyx-demo:1.0

curl localhost:8080/health   # {"status":"ok","env":"prod"}

docker logs web
docker exec -it web sh       # shell inside (note: runs as appuser now)
docker stop web && docker rm web
```

`-p 8080:8000` is **port mapping**: it sets up a NAT rule (via the container's `net` namespace + iptables) forwarding host port 8080 to the container's 8000. `EXPOSE` alone does nothing here, it's just metadata.

### Volumes & bind mounts (persistence)

Containers are ephemeral: delete the container, the writable layer is gone. For data that must survive, mount storage from outside that writable layer.

- **Named volume**, Docker-managed storage (lives under `/var/lib/docker/volumes`). Best for databases and prod data.
  ```bash
  docker volume create pgdata
  docker run -v pgdata:/var/lib/postgresql/data postgres:16
  ```
- **Bind mount**, maps a host directory into the container. Great for development (live-reload your source) but couples you to the host layout.
  ```bash
  docker run -v "$(pwd)/app:/app/app" nyx-demo:1.0
  ```
- **tmpfs**, in-memory only, never hits disk (secrets, scratch).

Rule of thumb: bind mounts for dev convenience, named volumes for real persistence.

### Networking basics

Docker creates a default `bridge` network. Containers on the same **user-defined** network can reach each other **by container name** (Docker runs an embedded DNS). On the default bridge they can't resolve names, so always create a network:

```bash
docker network create appnet
docker run -d --name db --network appnet postgres:16
docker run -d --name web --network appnet nyx-demo:1.0
# inside web, "db" resolves to the postgres container's IP
```

### Image registries

An image lives locally until you push it to a **registry** (Docker Hub, GitHub Container Registry, AWS ECR). Tags encode `registry/namespace/name:tag`.

```bash
docker tag nyx-demo:1.0 ghcr.io/spencer/nyx-demo:1.0
echo "$GHCR_TOKEN" | docker login ghcr.io -u spencer --password-stdin
docker push ghcr.io/spencer/nyx-demo:1.0
docker pull ghcr.io/spencer/nyx-demo:1.0
```

### Security & best practices checklist

- **Run as non-root** (`USER appuser`). A container breakout as root is far worse.
- **Minimal base image**, `slim` or `distroless` or `alpine` (watch alpine's musl libc quirks with Python wheels). Fewer packages = smaller attack surface and image.
- **Pin versions** (`python:3.12-slim`, not `latest`) for reproducibility.
- **`.dockerignore`** so secrets/`.git`/caches never enter the build context.
- **Never bake secrets** into `ENV`/layers, they're recoverable from image history. Use runtime env vars or a secret manager.
- **Multi-stage** to drop build tooling.
- **Scan images** (`docker scout cves nyx-demo:1.0`, or Trivy), ties directly into the CI scanning I'll set up in 10.3.
- **One process per container** (mostly), let the orchestrator handle multiplicity.

## 🧪 Mini-project: app + Postgres + Redis with `docker compose`

Goal: a single command brings up my FastAPI app talking to a Postgres database and a Redis cache, all networked, with persistence.

`docker-compose.yml`:

```yaml
services:
  web:
    build: .
    ports:
      - "8080:8000"
    environment:
      APP_ENV: dev
      DATABASE_URL: postgresql://nyx:secret@db:5432/nyx
      REDIS_URL: redis://cache:6379/0
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started
    networks: [appnet]

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: nyx
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: nyx
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U nyx"]
      interval: 5s
      timeout: 3s
      retries: 5
    networks: [appnet]

  cache:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redisdata:/data
    networks: [appnet]

volumes:
  pgdata:
  redisdata:

networks:
  appnet:
```

Notice the wiring:

- `web` reaches the DB at host `db` and Redis at `cache`, those are the **service names**, resolved by Compose's DNS on the `appnet` network.
- `depends_on` with `condition: service_healthy` makes `web` wait until Postgres's healthcheck passes, not just until the container starts. (This avoids the classic "connection refused, DB still booting" race.)
- Named volumes `pgdata`/`redisdata` give persistence across `docker compose down`.

Extend the app to actually touch both (`requirements.txt` adds `psycopg[binary]` and `redis`):

```python
# app/main.py (additions)
import os, psycopg, redis
from fastapi import FastAPI

app = FastAPI()
r = redis.from_url(os.environ["REDIS_URL"])

@app.get("/count")
def count():
    n = r.incr("hits")
    with psycopg.connect(os.environ["DATABASE_URL"]) as conn:
        ver = conn.execute("SELECT version()").fetchone()[0]
    return {"hits": n, "pg": ver.split()[1]}
```

Run it:

```bash
docker compose up --build          # build + start everything
curl localhost:8080/count          # {"hits":1,"pg":"16.x"}
curl localhost:8080/count          # {"hits":2,...}  Redis counter persists

docker compose down                # stop + remove containers (volumes kept)
docker compose up                  # bring back up
curl localhost:8080/count          # {"hits":3,...}  ← persistence proven!

docker compose down -v             # -v also wipes volumes (counter resets)
```

The fact that `hits` survives a `down`/`up` cycle but resets on `down -v` is the whole lesson about volumes made concrete.

## 🔬 Guided walkthrough: from zero to a debugged container

Let me slow down and do one complete loop with the *expected output described* at each step, the way I'd actually work through a problem.

### Step 1 - see what's on the machine

```bash
docker images        # list local images (REPOSITORY, TAG, IMAGE ID, SIZE)
docker ps            # running containers only
docker ps -a         # ALL containers, including stopped/exited ones
```

A fresh machine shows empty tables. After the `nyx-demo` build, `docker images` lists `nyx-demo  1.0  <id>  ~150MB`. The first thing I check when "my container isn't running" is `docker ps -a`, a container that crashed shows up here with `Exited (1)` in the STATUS column, which immediately tells me it ran and died rather than never starting.

### Step 2 - run it and read the logs

```bash
docker run -d --name web -p 8080:8000 nyx-demo:1.0
docker logs web
```

Expected: uvicorn's startup banner, `Uvicorn running on http://0.0.0.0:8000`. If instead I see a Python traceback (`ModuleNotFoundError: No module named 'app'`), the logs just told me the bug: my `COPY` path is wrong or `WORKDIR` isn't set. **The logs are always the first stop.** Ninety percent of "the container doesn't work" is answered by `docker logs <name>`.

### Step 3 - get a shell inside

```bash
docker exec -it web sh
# now I'm inside the container's filesystem:
ls /app                 # is my source actually here?
env | grep APP_ENV      # are my env vars set?
whoami                  # should print "appuser", proving USER worked
ps aux                  # should show ~2 processes (PID 1 = uvicorn) - namespace magic
exit
```

`exec -it` runs a *new* process (a shell) inside the *already-running* container. `-i` keeps stdin open, `-t` allocates a TTY (so the prompt behaves). This is the single most useful debugging command, it lets me poke at reality instead of guessing.

### Step 4 - inspect the wiring

```bash
docker inspect web | grep -A5 '"Mounts"'      # what volumes/binds are attached
docker inspect web --format '{{.NetworkSettings.IPAddress}}'   # the container's IP
docker stats web      # live CPU/memory/network - the cgroups accounting, visualized
docker top web        # processes, mapped to host PIDs
```

`docker stats` is the cgroups concept made concrete: the MEM USAGE / LIMIT column is exactly the memory cgroup limit I discussed earlier.

### Step 5 - clean up like a professional

Stopped containers, dangling images, and unused volumes pile up and eat disk. The everyday hygiene commands:

```bash
docker stop web && docker rm web          # stop then remove one container
docker container prune                    # remove ALL stopped containers
docker image prune                        # remove dangling (untagged) images
docker system prune -a --volumes          # nuke everything unused ⚠️ aggressive
docker system df                          # how much disk is Docker using?
```

I run `docker system df` whenever my disk feels tight, it almost always reveals gigabytes of stale build cache and old images.

## ⚠️ Common mistakes

A box of the traps I (and everyone) hit, and the fix for each.

- **Using `FROM python:latest` (or any `:latest`).** `latest` is a moving target, a rebuild months later silently pulls a different version and breaks reproducibility. **Fix:** pin a specific tag, `python:3.12-slim`.
- **`COPY . .` before installing dependencies.** Busts the build cache on every source edit, so every build reinstalls all deps. **Fix:** copy `requirements.txt` and install *first*, then `COPY . .`.
- **Baking secrets into the image.** `ENV API_KEY=sk-123` or `COPY .env .` puts the secret in a layer that anyone can extract with `docker history` or by pulling the image. **Fix:** pass secrets at runtime (`-e`, `--env-file`, secret managers) and add `.env` to `.dockerignore`.
- **Forgetting `.dockerignore`.** Without it, `COPY . .` ships your `.git` history, `node_modules`, and `.env` into the image and the build context. **Fix:** always write a `.dockerignore`.
- **Running as root.** The default. A breakout from a root container is a host root compromise. **Fix:** create and switch to a non-root `USER`.
- **Expecting `EXPOSE` to publish a port.** `EXPOSE 8000` is *documentation only*; the port isn't reachable from the host. **Fix:** publish with `-p 8080:8000`.
- **Shell-form `CMD uvicorn ...`.** Wraps your process in `/bin/sh -c`, so SIGTERM hits the shell, not your app, and graceful shutdown breaks. **Fix:** use exec form, `CMD ["uvicorn", ...]`.
- **Storing data in the container's writable layer.** `docker rm` deletes it forever. **Fix:** named volumes for anything that must persist.
- **Containers on the default bridge can't resolve each other by name.** `web` can't reach `db` by hostname. **Fix:** create a user-defined network (or use Compose, which makes one for you).
- **`docker build` is slow every time.** Usually a cache-order problem (above) or no `.dockerignore` (huge context). Check `docker history` to see which layer is fat.

## 💼 On the job / interview angle

Docker is genuinely *daily* on the job, you'll write Dockerfiles, run `docker compose up` to spin up your local stack, and read other people's Dockerfiles in code review. It's also one of the most common interview topics for backend, full-stack, DevOps, and SRE roles. Be ready to *explain*, not just recite.

**What you actually do with it at work:**
- Containerize the service you own and keep its Dockerfile lean and secure.
- Use Compose to run the whole app (API + DB + cache + queue) locally with one command.
- Debug failing containers in CI and staging via `docker logs` / `docker exec`.
- Keep images small so CI builds and deploys are fast and registry costs stay low.

**Representative interview questions (and the crisp answer):**

1. *"What's the difference between a container and a VM?"* → A VM virtualizes hardware and ships a full guest OS with its own kernel; a container shares the host kernel and isolates via namespaces + cgroups. Containers are lighter and start in milliseconds.
2. *"What's the difference between an image and a container?"* → Image = immutable blueprint (like a class); container = a running instance with a writable layer (like an object).
3. *"How do you reduce Docker image size?"* → Slim/distroless base, multi-stage builds to drop the toolchain, combine `RUN` layers and clean caches in the same layer, a good `.dockerignore`.
4. *"What's the difference between `CMD` and `ENTRYPOINT`?"* → ENTRYPOINT is the fixed executable; CMD is its default arguments. Args after the image name override CMD but not ENTRYPOINT.
5. *"Why order matters in a Dockerfile?"* → Layer cache: put rarely-changing instructions (deps) above frequently-changing ones (source) so edits don't bust the dep cache.
6. *"`COPY` vs `ADD`?"* → Prefer COPY; ADD also auto-extracts tarballs and fetches URLs, which is surprising, use it only when you need that.
7. *"How do containers persist data?"* → Named volumes (Docker-managed, for prod data) and bind mounts (host dir, for dev). The writable layer is ephemeral.
8. *"How do two containers talk to each other?"* → Put them on a user-defined network; Docker's embedded DNS resolves container/service names to IPs.
9. *"How would you keep secrets out of an image?"* → Never `ENV`/`COPY` them in; inject at runtime via env vars or a secret manager; `.dockerignore` the `.env`.
10. *"What are the three Linux primitives behind containers?"* → namespaces (what a process can see), cgroups (what it can use), union filesystems (how layers stack).

**Tip:** if you can whiteboard the multi-stage Dockerfile from this chapter *and* explain why each line is there, you're ahead of most candidates.

## ✏️ Exercises

Work top to bottom, they ramp from warm-up to real. Solutions follow.

1. **(easy)** Run an interactive Ubuntu container, install `curl` inside it, then exit. Why is `curl` gone when you start a *new* `ubuntu` container?
2. **(easy)** Pull `redis:7-alpine`, run it detached, and use `docker exec` to open `redis-cli` inside it and `SET`/`GET` a key.
3. **(easy)** Write a one-line command that lists only the *names* of all running containers.
4. **(medium)** Write a Dockerfile for a tiny static site: base `nginx:alpine`, copy an `index.html` into `/usr/share/nginx/html`. Build, run on port 8080, and confirm with `curl`.
5. **(medium)** Take the naïve FastAPI Dockerfile from this chapter and measure its size with `docker images`. Convert it to the multi-stage version and measure again. Report the difference.
6. **(medium)** Prove the build cache: build the multi-stage image, edit one line in `main.py`, rebuild, and explain from the build output which layers were cached and which rebuilt.
7. **(medium)** Create a named volume `mydata`, run a `busybox` container that writes a file into it, remove the container, then run a *new* container mounting the same volume and show the file survived.
8. **(hard)** Create a user-defined network, run Postgres on it, and from a second container on the same network connect to Postgres *by container name* using `psql`.
9. **(hard)** Add a `HEALTHCHECK` to the FastAPI image, run it, and watch the STATUS column in `docker ps` transition from `(health: starting)` to `(healthy)`.
10. **(hard)** Constrain a container to 128 MB of memory and 0.5 CPU. Run a workload that exceeds memory and observe the OOM kill in `docker inspect` / `docker logs`.

### Solutions

1. ```bash
   docker run -it ubuntu bash
   apt-get update && apt-get install -y curl
   exit
   ```
   `curl` lived only in that container's writable layer. A new `ubuntu` container starts from the pristine image again - the writable layer is fresh and empty. Containers are ephemeral; changes don't persist into the image unless you build them in via a Dockerfile.

2. ```bash
   docker run -d --name cache redis:7-alpine
   docker exec -it cache redis-cli
   # inside redis-cli:
   SET hello world      # -> OK
   GET hello            # -> "world"
   ```

3. ```bash
   docker ps --format '{{.Names}}'
   ```
   The `--format` flag takes a Go template; `{{.Names}}` prints just the name column.

4. `Dockerfile`:
   ```dockerfile
   FROM nginx:alpine
   COPY index.html /usr/share/nginx/html/index.html
   ```
   ```bash
   echo '<h1>hello from a container</h1>' > index.html
   docker build -t mysite .
   docker run -d -p 8080:80 --name site mysite
   curl localhost:8080        # -> <h1>hello from a container</h1>
   ```

5. The naïve `FROM python:3.12` image lands around **~1 GB** (full Debian + build tools). The multi-stage `python:3.12-slim` version that copies only `/opt/venv` lands around **~150 MB**. Roughly a **6-7x reduction**, because the build toolchain and pip caches never reach the final stage. Confirm with `docker images | grep nyx-demo`.

6. After the first build, edit `main.py` and rebuild. The output shows `CACHED` next to the `FROM`, `ENV`, `RUN python -m venv`, `COPY requirements.txt`, and `RUN pip install` steps - because none of their inputs changed. The first non-cached step is `COPY app ./app` (your edited source), and everything below it reruns. The expensive `pip install` stayed cached, which is the entire point of the ordering.

7. ```bash
   docker volume create mydata
   docker run --rm -v mydata:/data busybox sh -c 'echo persisted > /data/note.txt'
   docker run --rm -v mydata:/data busybox cat /data/note.txt   # -> persisted
   ```
   The first container is gone (`--rm`), but the file lives in the named volume, so the second container reads it. That's the durability boundary: data outside the writable layer survives.

8. ```bash
   docker network create appnet
   docker run -d --name db --network appnet \
     -e POSTGRES_PASSWORD=secret postgres:16
   docker run --rm -it --network appnet postgres:16 \
     psql -h db -U postgres        # type the password "secret"
   ```
   Hostname `db` resolves via Docker's embedded DNS *only because both containers share the user-defined `appnet`*. On the default bridge this fails.

9. Use the chapter's image (it has a `HEALTHCHECK`):
   ```bash
   docker run -d --name web -p 8080:8000 nyx-demo:1.0
   docker ps        # STATUS: "Up 5 seconds (health: starting)"
   sleep 35
   docker ps        # STATUS: "Up 40 seconds (healthy)"
   ```
   Docker runs the healthcheck command on the interval; once it succeeds the status flips to `healthy`. Orchestrators (Compose `depends_on`, k8s readiness) build on exactly this signal.

10. ```bash
    docker run --name hog --memory=128m --memory-swap=128m \
      python:3.12-slim python -c "x=bytearray(300*1024*1024)"
    echo "exit code: $?"          # non-zero - killed
    docker inspect hog --format '{{.State.OOMKilled}}'   # -> true
    ```
    Allocating 300 MB inside a 128 MB cgroup trips the OOM killer *inside that container's cgroup*, not on the host. `OOMKilled: true` is the smoking gun.

## 🧪 Mini-project 2: a multi-service dev environment with hot-reload, override files, and a Makefile

Goal: a polished local dev setup I'd actually be happy handing to a teammate, live code reload, a clean separation between dev and prod Compose config, a one-time DB seeder, and a `Makefile` so nobody has to memorize commands.

The trick is Compose's **override** mechanism: `docker compose` automatically merges `docker-compose.yml` with `docker-compose.override.yml` if the latter exists. Keep the base file production-shaped and put dev-only conveniences (bind mounts, reload, exposed ports) in the override.

`docker-compose.yml` (base, same shape as prod):

```yaml
services:
  web:
    build: .
    environment:
      APP_ENV: prod
      DATABASE_URL: postgresql://nyx:secret@db:5432/nyx
    depends_on:
      db:
        condition: service_healthy
    networks: [appnet]

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: nyx
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: nyx
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U nyx"]
      interval: 5s
      timeout: 3s
      retries: 5
    networks: [appnet]

volumes:
  pgdata:
networks:
  appnet:
```

`docker-compose.override.yml` (dev-only, auto-merged):

```yaml
services:
  web:
    environment:
      APP_ENV: dev
    ports:
      - "8080:8000"
    volumes:
      # bind-mount source so edits reflect instantly inside the container
      - ./app:/app/app
    # --reload watches the bind-mounted source and restarts uvicorn on save
    command: ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--reload"]

  db:
    ports:
      - "5432:5432"      # expose Postgres to my host so I can connect with a GUI
```

`seed.sql` (run once to populate the DB):

```sql
CREATE TABLE IF NOT EXISTS accounts (id SERIAL PRIMARY KEY, name TEXT);
INSERT INTO accounts (name) VALUES ('alice'), ('bob') ON CONFLICT DO NOTHING;
```

`Makefile` (the human interface, `make up`, `make logs`, `make seed`):

```makefile
.PHONY: up down logs sh seed test rebuild

up:        ## start the dev stack (override auto-merged)
	docker compose up --build

down:      ## stop and remove containers (keep volumes)
	docker compose down

logs:      ## tail web logs
	docker compose logs -f web

sh:        ## shell into the web container
	docker compose exec web sh

seed:      ## load seed data into Postgres
	docker compose exec -T db psql -U nyx -d nyx < seed.sql

test:      ## run the test suite inside the web container
	docker compose exec web pytest -q

rebuild:   ## force a clean rebuild (no cache)
	docker compose build --no-cache
```

Run it and prove the hot-reload:

```bash
make up                       # base + override merged automatically
make seed                     # accounts table populated
curl localhost:8080/          # {"message":"hello from a container"}

# Now edit app/main.py - change the message string - and SAVE.
# Watch the logs: uvicorn prints "Reloading..." and restarts.
curl localhost:8080/          # new message, NO rebuild, NO restart command
```

What this mini-project teaches: the base/override split is exactly how real teams keep one Compose definition that works for both dev and prod without `if dev:` branches everywhere; bind mounts + `--reload` give the inner-loop speed of working locally *with* the isolation of containers; and a `Makefile` turns tribal knowledge into self-documenting commands (`make` with no args, plus the `##` comments, is a discoverable menu). Bonus stretch: add a `web` `HEALTHCHECK` to the override and make a tiny `wait-for` script so `make test` only runs once the app is healthy.
