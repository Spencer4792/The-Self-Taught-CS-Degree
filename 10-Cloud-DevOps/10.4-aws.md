## Start here (beginner on-ramp)

As of early 2026, AWS has ~200 services and a reputation for overwhelming people. Ignore 190 of them for now. The cloud is simpler than the menu suggests.

**The analogy: renting instead of owning.** Owning servers is like owning a car, big upfront cost, you maintain it, it sits idle most of the time, and scaling up means buying more cars. The cloud is like a ride-share + storage-locker + utility company rolled into one: you rent exactly what you need, by the second or by the gigabyte, and give it back when you're done. Need 100 servers for an hour? Rent them, pay for the hour, return them. Need to store a million files? Pay only for the bytes you store. **You stop buying capacity and start renting it on demand.**

**The handful of services that cover most real work** (learn these first, in this order):

- **S3**, a giant, cheap, durable hard drive in the sky. You put *files* (called "objects") in *buckets*. Photos, CSVs, backups, static websites.
- **EC2**, a rented computer (a virtual server). You get a Linux/Windows box you can SSH into and run anything.
- **Lambda**, run a *function* without renting a whole computer. AWS runs your code only when something triggers it, and you pay per run. "Serverless."
- **IAM**, the permissions system: *who* is allowed to do *what*. The thing you must get right, because mistakes here cause breaches.
- **RDS / DynamoDB**, managed databases (relational SQL / NoSQL key-value) so you don't run a database server yourself.

**The two ideas that prevent 90% of beginner pain:**

1. **Least privilege (IAM).** Give every person and program *only* the exact permissions it needs, never "admin, to make it work." This one habit is the difference between a secure account and a breached one.
2. **You pay for what's on.** A forgotten EC2 instance or a public S3 bucket full of data costs real money (or causes a real leak). Always know what's running.

**Your first ten minutes, store and retrieve a file in S3 from the command line** (after installing the [AWS CLI](https://aws.amazon.com/cli/) and running `aws configure` with credentials):

```bash
# Create a uniquely-named bucket (bucket names are global across all of AWS):
aws s3 mb s3://nyx-firsttest-$RANDOM

# Upload a file:
echo "hello cloud" > note.txt
aws s3 cp note.txt s3://<your-bucket-name>/note.txt

# List it, then download it back:
aws s3 ls s3://<your-bucket-name>/
aws s3 cp s3://<your-bucket-name>/note.txt downloaded.txt
cat downloaded.txt        # -> hello cloud
```

That's it, you just used cloud storage with no server, no setup, paying fractions of a cent. Expected output: `mb` prints `make_bucket`, `cp` prints `upload:`/`download:` lines, `ls` shows your file. **Why it matters:** AWS (and cloud skills generally) appears in a huge share of job postings, and "have you used AWS?" is a routine interview question. You don't need all 200 services, being fluent in S3, EC2, Lambda, IAM, and one database, plus *reasoning about cost and security*, is exactly what entry-level roles want. Everything below builds that fluency.

## Concept

### The cloud model

- **IaaS** (Infrastructure as a Service), raw compute/storage/network; you manage the OS and up. *EC2, EBS, VPC.* Most control, most ops.
- **PaaS** (Platform), you bring code, the platform runs it. *Elastic Beanstalk, App Runner, Lambda-ish.*
- **SaaS** (Software), finished app you just use. *Gmail, the AWS Console itself.*

The trend in this chapter is **serverless**: push the ops floor up so you write functions and tables, not servers.

### Regions and Availability Zones

- A **Region** (e.g. `us-east-1`) is a geographic area; pick for latency to users, data-residency laws, and price (regions differ in cost).
- An **Availability Zone (AZ)** is one or more discrete datacenters within a region with independent power/network. **Design across ≥2 AZs** so one datacenter failure doesn't take you down. This is the bedrock of HA on AWS.

### Shared Responsibility Model

The line everyone must internalize:

- **AWS** is responsible for security **OF the cloud**, hardware, the hypervisor, physical datacenters, managed-service internals.
- **You** are responsible for security **IN the cloud**, your IAM policies, security groups, encryption choices, patching your EC2 OS, not making your S3 bucket public.

Most breaches are on *your* side of the line, a too-open security group or a public bucket, not AWS's. Own that.

### IAM - and the mistake everyone makes

IAM controls *who can do what*. Core nouns:

- **User**, a long-lived human/service identity with credentials. Minimize these.
- **Group**, a bucket of users sharing policies.
- **Role**, an identity with **no permanent credentials**, *assumed temporarily* for a session. EC2 instances, Lambda functions, and CI assume roles to get short-lived credentials. **Roles are the right answer almost always.**
- **Policy**, a JSON document granting/denying actions on resources.

**The mistake everyone makes: over-permissioning.** People attach `AdministratorAccess` or `s3:*` because it "just works," then it ships to prod. **Least privilege** = grant only the specific actions on the specific resources needed.

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::nyx-uploads/*"
  }]
}
```

That allows only get/put on objects in one bucket, not `s3:*` on `*`. Also: hand applications **roles**, never baked-in access keys. A leaked long-lived key is a breach; an assumed role's credentials expire in minutes.

### EC2

Virtual servers (IaaS). You pick an instance type (CPU/RAM/network), an AMI (image), attach EBS storage, put it in a subnet, guard it with a security group. Pricing models: **On-Demand** (flexible, priciest), **Reserved/Savings Plans** (commit 1-3 yrs, big discount), **Spot** (spare capacity, up to ~90% off as of early 2026, can be reclaimed, great for fault-tolerant batch). Reach for EC2 when you need full control or long-running stateful processes; otherwise serverless/containers are less ops.

### VPC, subnets, security groups

- **VPC**, your private virtual network in a region, with a CIDR block (e.g. `10.0.0.0/16`).
- **Subnets**, slices of the VPC, each in one AZ. **Public** subnet (has a route to an Internet Gateway) vs **private** subnet (no direct inbound from internet; egress via a NAT Gateway). Put load balancers in public subnets, databases/app servers in private ones.
- **Security Group**, a *stateful* virtual firewall on an instance/ENI; rules allow inbound/outbound by port/source. Stateful = if you allow inbound, the response is automatically allowed out.
- **NACL**, *stateless* subnet-level firewall; coarser, less used day-to-day.

Mental model: public subnet for the front door, private subnets for everything sensitive, security groups referencing each other (e.g. "DB SG allows 5432 *only from* the app SG").

### S3 - object storage

Not a filesystem, a flat **object store**: buckets contain objects (key → bytes + metadata). Eleven 9s of durability (S3's durability claim as of early 2026). Uses:

- **Storage classes** by access pattern/cost: Standard (hot), Standard-IA / One Zone-IA (infrequent), Glacier Instant/Flexible/Deep Archive (cold, cheap, slower retrieval). **Lifecycle rules** auto-transition old data to cheaper tiers.
- **Static website hosting**, serve a SPA/static site straight from a bucket (front with CloudFront for HTTPS + CDN).
- **Presigned URLs**, a time-limited URL, signed with *your* credentials, that lets a client upload/download a specific object **without giving them AWS credentials**. This is the right way to let browsers upload directly to S3.

```python
import boto3
s3 = boto3.client("s3")
# A URL that lets the holder PUT one object for 5 minutes
url = s3.generate_presigned_url(
    "put_object",
    Params={"Bucket": "nyx-uploads", "Key": "user123/report.csv"},
    ExpiresIn=300,
)
# Client then: PUT the file bytes to `url` directly - never touches your server.
```

Default-deny public access (Block Public Access on), encrypt at rest (SSE-S3 or SSE-KMS), and use presigned URLs or CloudFront for sharing.

### RDS vs DynamoDB

- **RDS**, managed *relational* databases (Postgres, MySQL, etc.). AWS handles backups, patching, replicas, failover (Multi-AZ). Use when you need SQL, joins, transactions, a fixed schema. NYX's structured financial records → RDS Postgres.
- **DynamoDB**, managed *NoSQL* key-value/document store. Single-digit-millisecond latency at any scale, serverless (on-demand capacity), but you design around access patterns (partition key + sort key), not ad-hoc queries. Use for high-throughput simple lookups, sessions, event/feature stores.

Rule: relational + complex queries → RDS; massive scale + known key-based access → DynamoDB.

### Lambda & the serverless model

**Lambda** runs your function in response to an **event**, with no server to manage. You're billed per request + GB-seconds of execution; **scales to zero** (pay nothing idle) and scales out automatically.

Things to actually know:

- **Event-driven**, triggered by API Gateway (HTTP), S3 events, SQS/SNS, EventBridge schedules, DynamoDB streams, etc.
- **Cold starts**, first invocation (or scale-out) pays init latency (spin up the runtime + your init code). Mitigate with smaller packages, provisioned concurrency, and keeping heavy clients in the init scope (reused across warm invocations).
- **Limits** (current as of early 2026), max 15-min timeout, up to 10 GB memory (CPU scales with memory), payload size limits, `/tmp` ephemeral storage. Not for long-running or stateful workloads.

The canonical **serverless API**: **API Gateway → Lambda → DynamoDB**. API Gateway terminates HTTPS and routes; Lambda holds the logic; DynamoDB stores state. No servers, scales to zero, pay-per-use.

```
Client → API Gateway → Lambda function → DynamoDB
         (routes,        (your code)      (state)
          auth, throttle)
```

### SQS & SNS - decoupling

- **SQS**, a managed **queue**; one producer puts messages, consumers pull and process. Smooths spikes, decouples services, gives retries + dead-letter queues. Point-to-point.
- **SNS**, pub/sub **topics**; one publish fans out to many subscribers (other services, SQS queues, Lambdas, email). One-to-many.

Common pattern: **SNS → multiple SQS** (fan-out + buffered, independent consumers). Use these so a slow/failing downstream doesn't take the producer down.

### CloudWatch - observability

- **Logs**, Lambda/ECS/app logs land here (log groups/streams).
- **Metrics**, numeric time series (invocations, errors, latency, CPU); custom metrics too.
- **Alarms**, fire on a metric threshold → notify (SNS), trigger autoscaling, or run automation. This is how you get paged.

If it's not in CloudWatch, you're flying blind. Set alarms on error rate and latency, not just CPU.

### CloudFront - CDN

A global content delivery network: caches content at **edge locations** near users for low latency, offloads origin traffic, terminates TLS, and adds DDoS protection (with AWS Shield/WAF). Front S3 static sites and APIs with it.

### Cost awareness

Money-savers to keep top of mind:

- **Serverless scales to zero**, no traffic, ~no cost (Lambda, DynamoDB on-demand). Great for spiky/low-baseline workloads.
- **S3 lifecycle → Glacier** for cold data; don't pay Standard prices for logs nobody reads.
- **Data transfer / NAT Gateway** costs sneak up, egress to the internet and cross-AZ traffic are billed; NAT Gateways have an hourly + per-GB charge.
- **Right-size & use Savings Plans/Spot** for steady EC2; turn off dev environments at night.
- **Set Budgets + Cost Anomaly Detection alarms** so a runaway resource pages you, not your credit card statement.

## Build it

### A serverless REST endpoint: API Gateway → Lambda → DynamoDB

The handler (`handler.py`), a tiny "items" API:

```python
import json, os, boto3
from boto3.dynamodb.conditions import Key

# Heavy clients in init scope → reused across warm invocations (cheaper, faster)
ddb = boto3.resource("dynamodb")
table = ddb.Table(os.environ["TABLE_NAME"])

def lambda_handler(event, context):
    method = event["requestContext"]["http"]["method"]
    if method == "POST":
        body = json.loads(event["body"])
        table.put_item(Item={"pk": body["id"], "data": body["data"]})
        return _resp(201, {"created": body["id"]})
    if method == "GET":
        item_id = event["pathParameters"]["id"]
        res = table.get_item(Key={"pk": item_id})
        return _resp(200, res.get("Item", {}))
    return _resp(405, {"error": "method not allowed"})

def _resp(code, body):
    return {"statusCode": code,
            "headers": {"content-type": "application/json"},
            "body": json.dumps(body)}
```

Deploy with **AWS SAM** (`template.yaml`), IaC for serverless, declares the function, the API, the table, and *least-privilege* IAM all together:

```yaml
AWSTemplateFormatVersion: '2010-09-09'
Transform: AWS::Serverless-2016-10-31

Resources:
  ItemsTable:
    Type: AWS::DynamoDB::Table
    Properties:
      BillingMode: PAY_PER_REQUEST        # serverless: scales to zero
      AttributeDefinitions:
        - { AttributeName: pk, AttributeType: S }
      KeySchema:
        - { AttributeName: pk, KeyType: HASH }

  ItemsFn:
    Type: AWS::Serverless::Function
    Properties:
      Handler: handler.lambda_handler
      Runtime: python3.12
      MemorySize: 256
      Timeout: 10
      Environment:
        Variables: { TABLE_NAME: !Ref ItemsTable }
      Policies:
        # Least privilege: only this table, only these actions
        - DynamoDBCrudPolicy: { TableName: !Ref ItemsTable }
      Events:
        Post:
          Type: HttpApi
          Properties: { Path: /items, Method: POST }
        Get:
          Type: HttpApi
          Properties: { Path: /items/{id}, Method: GET }
```

```bash
sam build
sam deploy --guided          # provisions API Gateway + Lambda + DynamoDB + IAM

# Test
curl -X POST $API/items -d '{"id":"abc","data":"hello"}'
curl $API/items/abc          # {"pk":"abc","data":"hello"}
```

Why this is nice: scales to zero (pay only per request), the IAM is scoped to *this one table* (the `DynamoDBCrudPolicy` macro, not `dynamodb:*`), and the whole stack is one reviewable file.

### S3 upload with a presigned URL (boto3)

Server side mints the URL; the browser uploads directly to S3, your server never proxies file bytes:

```python
import boto3

s3 = boto3.client("s3")

def get_upload_url(user_id: str, filename: str) -> dict:
    key = f"uploads/{user_id}/{filename}"
    url = s3.generate_presigned_url(
        ClientMethod="put_object",
        Params={
            "Bucket": "nyx-uploads",
            "Key": key,
            "ContentType": "text/csv",
        },
        ExpiresIn=300,            # 5-minute window
    )
    return {"upload_url": url, "key": key}
```

```bash
# Client uses it directly - no AWS creds on the client:
curl -X PUT --upload-file report.csv \
  -H "Content-Type: text/csv" \
  "<presigned-url>"
```

The bucket stays private (Block Public Access on); access is granted per-object, time-boxed, signed by your role's credentials. This is the pattern for NYX's CSV uploads.

## Mini-project: architect NYX Finance's analytics app (ingest → store → serve)

Design a serverless-leaning AWS architecture for NYX Finance: users upload financial CSVs, the system processes them into analytics, and a dashboard/API serves results. Choose services and justify on cost + scaling.

```
                        ┌─────────────┐
  Browser ── presigned ─▶│  S3 (raw)   │ "nyx-raw" bucket
  (upload CSV)           └──────┬──────┘
                                │ S3 ObjectCreated event
                                ▼
                        ┌─────────────────┐
                        │ Lambda (ingest) │ parse/validate CSV
                        └───┬─────────┬───┘
                  bad rows  │         │  metrics/events
                            ▼         ▼
                     ┌──────────┐  ┌──────────────────┐
                     │ SQS DLQ  │  │  SNS topic        │ fan-out
                     └──────────┘  └───┬───────────┬──┘
                                       ▼           ▼
                              ┌──────────────┐  ┌────────────────┐
                              │ Lambda(aggr) │  │ Lambda (notify)│ email user
                              └──────┬───────┘  └────────────────┘
                                     ▼
            structured ──▶ ┌──────────────────┐   ┌──────────────┐
            financial      │ RDS Postgres     │   │ DynamoDB     │
            records        │ (Multi-AZ)       │   │ (hot lookups)│
                           └────────┬─────────┘   └──────┬───────┘
                                    │                    │
                                    ▼                    ▼
                           ┌───────────────────────────────┐
                           │ API Gateway → Lambda (serve)  │  query layer
                           └───────────────┬───────────────┘
                                           ▼
                              ┌────────────────────────┐
                              │ CloudFront → S3 (SPA)  │  dashboard frontend
                              └────────────────────────┘

  Cross-cutting: IAM roles per Lambda (least privilege) · CloudWatch logs/metrics/alarms
                 · S3 lifecycle raw→Glacier after 90d · AWS Budgets alarm
```

**Service choices and justification:**

| Layer | Service | Why |
|-------|---------|-----|
| Upload/ingest | **S3 + presigned URL** | Browser uploads directly; bucket stays private; cheap durable storage; pay only for stored bytes. |
| Trigger | **S3 ObjectCreated → Lambda** | Event-driven; no polling; scales to zero between uploads (spiky workload = ideal for Lambda). |
| Decoupling | **SNS fan-out + SQS DLQ** | Aggregation and user-notification consume independently; failed ingests land in a dead-letter queue for retry instead of being lost. |
| Hot reads | **DynamoDB (on-demand)** | Single-digit-ms dashboard lookups by user/key; scales automatically; pay-per-request fits unpredictable traffic. |
| System of record | **RDS Postgres (Multi-AZ)** | Structured financial data needs SQL joins, transactions, ad-hoc analytics queries; Multi-AZ for HA/failover. |
| Serve | **API Gateway → Lambda** | Serverless REST; scales with traffic, scales to zero overnight; no servers to patch. |
| Frontend | **S3 static site + CloudFront** | Cheap static hosting, global CDN latency, HTTPS + DDoS protection at the edge. |
| Observability | **CloudWatch logs/metrics/alarms** | Alarm on Lambda error rate + ingest DLQ depth → SNS pages you. |
| Cost guardrails | **S3 lifecycle → Glacier (90d), AWS Budgets + Anomaly Detection** | Old raw CSVs go cold-cheap; a runaway bill pages you early. |

**Cost/scaling story to defend:** the spiky, upload-driven ingest path is fully serverless (S3 + Lambda + DynamoDB on-demand), so at night with no uploads you pay essentially storage-only. The one always-on cost is RDS, justified because the analytics queries need relational SQL; you'd start on a small Multi-AZ instance and add a read replica only when read load demands it. NAT Gateway and cross-AZ transfer are the sneaky costs to watch, so keep the Lambdas' VPC footprint minimal and co-locate chatty components. Least-privilege IAM roles per function and a private-by-default S3 bucket keep you on the right side of the shared-responsibility line.

## Guided walkthrough: a least-privilege IAM setup from scratch

IAM is where everyone fumbles, so let's walk one correct setup end to end, the way you'd actually bootstrap an account safely. Each step says what to do and what you should see.

### Step 1 - stop using the root account

The email you signed up with is the **root** identity, godlike, and a disaster if leaked. After signup you should: enable **MFA** on root, then *never use it again* for daily work. Create an IAM **admin user** (or, better, an IAM Identity Center user) for yourself.

```bash
# Verify which identity your CLI is using - should NOT be root:
aws sts get-caller-identity
# {"Account":"1234...","Arn":"arn:aws:iam::1234...:user/spencer-admin"}
```

If the `Arn` ends in `:root`, stop and switch.

### Step 2 - give an application a *role*, not keys

An app should never carry long-lived access keys. It assumes a **role** and gets short-lived credentials that auto-expire. For a Lambda, the role has two parts: a **trust policy** (who may assume it) and **permission policies** (what it may do).

Trust policy (`trust.json`), "Lambda is allowed to assume this role":

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "lambda.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}
```

Create the role and attach a *scoped* permission:

```bash
aws iam create-role --role-name nyx-ingest-fn \
  --assume-role-policy-document file://trust.json

# A least-privilege inline policy: only PutItem, only on ONE table
cat > perm.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["dynamodb:PutItem"],
    "Resource": "arn:aws:dynamodb:us-east-1:123456789012:table/nyx-items"
  }]
}
EOF
aws iam put-role-policy --role-name nyx-ingest-fn \
  --policy-name put-items --policy-document file://perm.json
```

Notice what we did *not* write: not `dynamodb:*`, not `Resource: "*"`. Only the one action on the one table the function needs.

### Step 3 - read a policy like a sentence

Every policy statement answers four questions. Read them in order and you can audit any policy in seconds:

| Field | The question | Our example |
|-------|--------------|-------------|
| `Effect` | Allow or Deny? | Allow |
| `Action` | Which API calls? | `dynamodb:PutItem` |
| `Resource` | On which exact things? | one table ARN |
| `Condition` (optional) | Only when…? | (none here; e.g. `aws:SourceIp`) |

When reviewing someone's PR, the red flags jump out: `Action: "*"`, `Resource: "*"`, or `"s3:*"`. Those are "admin in disguise."

### Step 4 - verify, don't trust

AWS gives you tools to *prove* a policy does what you think:

```bash
# Simulate: can this role PutItem? (should be allowed)
aws iam simulate-principal-policy \
  --policy-source-arn arn:aws:iam::123456789012:role/nyx-ingest-fn \
  --action-names dynamodb:PutItem \
  --resource-arns arn:aws:dynamodb:us-east-1:123456789012:table/nyx-items
# evalDecision: "allowed"

# Can it DELETE the table? (should be denied - we never granted it)
aws iam simulate-principal-policy \
  --policy-source-arn arn:aws:iam::123456789012:role/nyx-ingest-fn \
  --action-names dynamodb:DeleteTable \
  --resource-arns arn:aws:dynamodb:us-east-1:123456789012:table/nyx-items
# evalDecision: "implicitDeny"
```

That `implicitDeny` is least privilege working: anything you didn't explicitly allow is denied by default. **Walkthrough wrap-up:** root locked down + MFA → roles not keys → scoped Action/Resource → simulate to verify. Do this and you're already more careful than most production accounts.

## Common mistakes

- **Using the root account for daily work.** Catastrophic if compromised. **Fix:** MFA on root, create an admin IAM user, never touch root again.
- **Over-permissioning IAM** (`AdministratorAccess`, `s3:*`, `Resource: "*"`). The #1 cause of cloud breaches. **Fix:** least privilege, scope Action *and* Resource.
- **Long-lived access keys in code or env files.** A leaked key is a standing breach. **Fix:** IAM roles (short-lived, auto-expiring credentials) for apps/CI/EC2/Lambda.
- **Public S3 buckets.** Accidentally exposing data is a classic headline breach. **Fix:** Block Public Access on by default; share via presigned URLs or CloudFront.
- **No encryption.** Forgetting SSE on S3 / RDS / EBS. **Fix:** enable encryption at rest (SSE-S3/KMS), it's basically free and often required.
- **Putting databases in public subnets / wide-open security groups** (`0.0.0.0/0` on 5432/22). **Fix:** private subnets for data; security groups that reference *each other* (DB SG allows 5432 only from app SG).
- **Forgetting things are *on*.** A `t3.large` left running, an idle NAT Gateway, a Multi-AZ RDS in a dev account, silent monthly bills. **Fix:** AWS Budgets + Cost Anomaly Detection; turn off dev at night.
- **Ignoring NAT Gateway / data-transfer costs.** They sneak up fast. **Fix:** minimize cross-AZ chatter and Lambda-in-VPC where avoidable; use VPC endpoints for S3/DynamoDB.
- **`:latest` thinking for Lambda packages / no versioning.** Hard to roll back. **Fix:** version functions/aliases; deploy via IaC (SAM/Terraform).
- **Deploying to one AZ.** One datacenter failure = outage. **Fix:** design across ≥2 AZs (Multi-AZ RDS, multiple subnets).
- **Click-ops in the console.** Not reproducible or reviewable. **Fix:** Infrastructure-as-Code (SAM/CloudFormation/Terraform).

## On the job / interview angle

"Cloud experience" is on a huge fraction of job listings, and AWS is the most common flavor. You don't need deep expertise for an entry-level role, you need to *reason* about the core services, IAM, and cost/security tradeoffs. On the job you'll deploy services, wire up S3/Lambda/queues, write IAM policies in code review, and (importantly) be the person who notices the bill is climbing.

**What you actually do with it at work:**
- Deploy and operate your service's AWS resources (often via IaC).
- Write and review least-privilege IAM policies and security groups.
- Use S3 for storage, CloudWatch for logs/alarms, and a managed DB.
- Keep an eye on cost; respond to budget/anomaly alarms.

**Representative interview questions (with crisp answers):**

1. *"IaaS vs PaaS vs SaaS?"* → Rent infrastructure (EC2, manage the OS) / bring code, platform runs it (Lambda, Beanstalk) / use a finished app (Gmail).
2. *"Explain the shared responsibility model."* → AWS secures the cloud (hardware, hypervisor, datacenters); you secure what's *in* it (IAM, security groups, encryption, OS patching). Most breaches are on your side.
3. *"IAM user vs role?"* → User = long-lived identity with credentials (minimize); role = no permanent creds, assumed temporarily for short-lived credentials. Apps/EC2/Lambda/CI should use roles.
4. *"What's the most common IAM mistake?"* → Over-permissioning (`*`); the fix is least privilege scoped to specific actions and resources.
5. *"What is S3 and how is it different from a filesystem?"* → Object storage: flat key→bytes buckets, 11 nines durability, no real directories. Not a POSIX filesystem.
6. *"What's a presigned URL and why use it?"* → A time-limited, signed URL letting a client PUT/GET one object directly, so the bucket stays private and the client needs no AWS credentials.
7. *"RDS vs DynamoDB?"* → Relational SQL with joins/transactions/ad-hoc queries (RDS) vs NoSQL key-value at massive scale designed around access patterns (DynamoDB).
8. *"What is Lambda good and bad for?"* → Great: event-driven, scales to zero, no servers. Bad: long-running (15-min cap), stateful, or latency-sensitive (cold starts) workloads.
9. *"What's a cold start and how do you reduce it?"* → First/scale-out invocation pays init latency; reduce with smaller packages, provisioned concurrency, and keeping heavy clients in init scope.
10. *"Region vs Availability Zone, and why ≥2 AZs?"* → Region = geographic area; AZ = isolated datacenter(s) within it. Deploy across ≥2 AZs so one datacenter failure doesn't take you down.
11. *"SQS vs SNS?"* → Queue (point-to-point, pull, retries/DLQ) vs pub/sub topic (one-to-many fan-out). Common combo: SNS → multiple SQS.
12. *"How do you control AWS cost?"* → Serverless scales to zero, S3 lifecycle to Glacier, Savings Plans/Spot for steady compute, watch NAT/data-transfer, set Budgets + anomaly alarms.

**Tip:** when asked to design something, narrate cost and security unprompted ("S3 stays private, presigned URLs, least-privilege role per Lambda, Multi-AZ for the DB, budget alarm"). That reasoning is what they're actually testing.

## Mini-project 2: a static site on S3 + CloudFront with HTTPS, plus a contact-form Lambda

The chapter's big mini-project was a backend analytics pipeline. This one ships a *complete public website* the cheap, serverless way, the pattern behind a huge number of real production sites (docs, marketing pages, SPAs, portfolios like Anneava's landing page).

**Part A, host a static site on S3 behind CloudFront.** S3 stores the files; CloudFront is the CDN that adds HTTPS, global low latency, and lets you keep the bucket *private* (best practice).

```bash
# 1. Create a private bucket and upload the site
B=anneava-site-$RANDOM
aws s3 mb s3://$B
echo '<h1>Anneava</h1><p>coming soon</p>' > index.html
aws s3 cp index.html s3://$B/index.html

# 2. Keep Block Public Access ON (do NOT make the bucket public)
aws s3api put-public-access-block --bucket $B \
  --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
```

Then create a CloudFront distribution with an **Origin Access Control (OAC)** so *only CloudFront* can read the bucket, and add a bucket policy permitting that. The key idea (the part beginners get wrong): the bucket stays **private**; the public reaches it *through* CloudFront, which terminates HTTPS at edge locations near them. A minimal bucket policy granting CloudFront read:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "cloudfront.amazonaws.com" },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::<bucket>/*",
    "Condition": { "StringEquals": { "AWS:SourceArn": "<distribution-arn>" } }
  }]
}
```

Visit the CloudFront domain (`https://d111abc.cloudfront.net`) → your page loads over HTTPS, served from a private bucket. Updating the site is `aws s3 cp` + a CloudFront cache invalidation:

```bash
aws s3 cp index.html s3://$B/index.html
aws cloudfront create-invalidation --distribution-id <id> --paths "/*"
```

**Part B, a serverless contact form.** Static sites can't run server code, so the form POSTs to an API Gateway → Lambda that stores the message and emails you. `template.yaml` (SAM):

```yaml
AWSTemplateFormatVersion: '2010-09-09'
Transform: AWS::Serverless-2016-10-31
Resources:
  MessagesTable:
    Type: AWS::DynamoDB::Table
    Properties:
      BillingMode: PAY_PER_REQUEST
      AttributeDefinitions: [{ AttributeName: id, AttributeType: S }]
      KeySchema: [{ AttributeName: id, KeyType: HASH }]

  ContactFn:
    Type: AWS::Serverless::Function
    Properties:
      Handler: contact.handler
      Runtime: python3.12
      MemorySize: 128
      Timeout: 10
      Environment:
        Variables: { TABLE: !Ref MessagesTable }
      Policies:
        - DynamoDBWritePolicy: { TableName: !Ref MessagesTable }   # least privilege
      Events:
        Post:
          Type: HttpApi
          Properties: { Path: /contact, Method: POST }
```

`contact.py`:

```python
import json, os, uuid, boto3
table = boto3.resource("dynamodb").Table(os.environ["TABLE"])

def handler(event, context):
    body = json.loads(event.get("body") or "{}")
    if not body.get("email") or not body.get("message"):
        return _r(400, {"error": "email and message required"})
    item = {"id": str(uuid.uuid4()), "email": body["email"], "message": body["message"]}
    table.put_item(Item=item)
    return _r(201, {"received": item["id"]})

def _r(code, b):
    return {"statusCode": code,
            "headers": {"content-type": "application/json",
                        "access-control-allow-origin": "*"},   # CORS for the browser
            "body": json.dumps(b)}
```

```bash
sam build && sam deploy --guided
curl -X POST $API/contact -d '{"email":"a@b.com","message":"hi"}'   # {"received":"<uuid>"}
```

Wire the static page's form to `fetch($API/contact, {method:"POST", body: JSON...})`.

What this mini-project teaches end-to-end: S3 is for the *static* bytes, CloudFront makes them fast + HTTPS *while the bucket stays private* (OAC, not a public bucket, the right way), and anything *dynamic* is a serverless API (API Gateway → Lambda → DynamoDB) with a least-privilege role and CORS so the browser can call it. The whole thing **scales to zero**, an idle portfolio site costs cents per month. Stretch goals: add a custom domain via Route 53 + an ACM certificate; add SES to email yourself each new message; rate-limit the API to deter spam.
