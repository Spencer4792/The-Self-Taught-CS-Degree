# Chapter 10.2 - Kubernetes

> Goal: Internalize the *one big idea* of Kubernetes, declarative reconciliation toward a desired state, then know every core object well enough to deploy, scale, roll out, and roll back the FastAPI app from 10.1 on a local cluster, and write a full manifest set for a 2-service app with config, secrets, and autoscaling.

Docker gives you one container on one host. The moment you want *many* replicas across *many* hosts that self-heal and update without downtime, you need orchestration. That's Kubernetes (k8s).

---

## Start here (beginner on-ramp)

Kubernetes has a reputation for being scary. It isn't, it's one idea repeated everywhere. Here's the idea before any YAML.

**The analogy: a thermostat.** You don't tell a thermostat "turn on the heater for 12 minutes." You tell it the *desired state*: "I want it to be 70°F." Then it watches the actual temperature and acts, heat on when too cold, off when warm enough, *forever*, without you. If someone opens a window and the room cools, the thermostat reacts automatically. You never issue commands; you declare a goal and a control loop chases it.

Kubernetes is a thermostat for your applications. You declare: "I want 5 healthy copies of my app, version 2.0." Kubernetes watches reality and acts forever: a copy crashes → it starts a new one; a whole machine dies → it moves those copies elsewhere; you change the desired version → it rolls out the new one. **You manage the goal; Kubernetes manages reality.** That single idea, *declarative reconciliation*, is 80% of understanding Kubernetes.

**Why it matters / when you'd even need it:** Docker runs one container on one machine. That's fine until you need many copies for traffic, automatic restarts when things crash, zero-downtime updates, and spreading across many machines so one failure doesn't take you down. Doing all that by hand is a full-time, error-prone job. Kubernetes does it as that tireless control loop. Most production backends at scale run on it, which is why it shows up constantly in job postings.

**The five words you'll hear constantly:**

- **Pod**, the smallest unit Kubernetes runs: usually one container. (Think: one running copy of your app.)
- **Deployment**, "keep N healthy pods of this app running, and handle updates." The object you'll write most.
- **Service**, a stable address that load-balances to your pods (which come and go with changing IPs).
- **Node**, a worker machine (VM or physical) where pods actually run.
- **kubectl**, the command-line tool you use to talk to the cluster (pronounced "cube-control" or "cube-cuttle"; nobody agrees).

**Your first ten minutes**, install [kind](https://kind.sigs.k8s.io/) (Kubernetes in Docker) and `kubectl`, then:

```bash
kind create cluster --name learn        # spins up a one-node cluster in Docker
kubectl get nodes                       # one node, STATUS Ready

# Run something with a single imperative command (great for learning):
kubectl create deployment hi --image=nginx --replicas=3
kubectl get pods                        # watch 3 nginx pods become Running

# Prove self-healing - delete a pod and watch it come back:
kubectl delete pod <one-pod-name>
kubectl get pods                        # a replacement is already being created!

# Clean up:
kubectl delete deployment hi
kind delete cluster --name learn
```

The moment a deleted pod reappears on its own, you've *seen* the thermostat. Everything below is detail on top of that one experience. Don't memorize objects yet, just hold onto "declare desired state, a loop makes it true."

## Concept

### Why orchestration exists

Suppose NYX Finance's API needs to:

- run **5 replicas** for throughput, spread across nodes;
- **restart** a replica that crashes or hangs;
- **reschedule** all replicas off a node that dies;
- **roll out** a new version with zero downtime, and **roll back** instantly if it's bad;
- **scale up** under load and back down when quiet;
- get **traffic load-balanced** across healthy replicas only.

Doing this by hand with `docker run` and a load balancer is a full-time job that gets it wrong at 3 a.m. Kubernetes does it as a control loop. You tell it *what you want* ("5 healthy replicas of image v2"); it continuously makes reality match.

### The mental model: declarative reconciliation

This is **the** thing to understand; everything else is detail.

You don't issue imperative commands ("start a container here"). You submit **desired state** (a YAML object) to the API server, which stores it in etcd. **Controllers** run an endless loop:

```
loop forever:
    desired = read spec from API server
    actual  = observe the world
    if actual != desired:
        take actions to converge actual -> desired
```

Kill a pod? The controller notices `actual=4, desired=5` and creates one. Node dies? It notices and reschedules. Bump the image in the spec? The Deployment controller rolls out the change. **You manage the spec; controllers manage reality.** This is why k8s is "self-healing", it's not magic, it's a reconciliation loop that never stops.

### Architecture

A cluster = a **control plane** (the brain) + **worker nodes** (where pods run).

```
        CONTROL PLANE                          WORKER NODE (xN)
 ┌────────────────────────────┐        ┌──────────────────────────┐
 │  kube-apiserver  ◀──────────┼────────┼─ kubelet                 │
 │   (the only thing you talk  │        │   (runs/monitors pods)   │
 │    to; REST + validation)   │        │                          │
 │                             │        │  kube-proxy              │
 │  etcd                       │        │   (service networking,   │
 │   (key-value store of ALL   │        │    iptables/IPVS rules)  │
 │    cluster state)           │        │                          │
 │                             │        │  container runtime       │
 │  scheduler                  │        │   (containerd/CRI-O)     │
 │   (assigns pods → nodes)    │        │                          │
 │                             │        │   ┌─────┐ ┌─────┐        │
 │  controller-manager         │        │   │ Pod │ │ Pod │  ...   │
 │   (runs the reconcile loops)│        │   └─────┘ └─────┘        │
 └────────────────────────────┘        └──────────────────────────┘
```

Control plane components:

- **kube-apiserver**, the front door. Every read/write goes through it (validation, auth, admission). `kubectl` talks only to this. Stateless; the state lives in etcd.
- **etcd**, distributed, consistent key-value store. The single source of truth for the entire cluster. Back this up; lose it and you lose the cluster's brain.
- **scheduler**, watches for unscheduled pods, picks a node based on resource requests, affinity, taints/tolerations.
- **controller-manager**, runs the built-in controllers (Deployment, ReplicaSet, Node, Job, ...). Each is a reconciliation loop.

Node components:

- **kubelet**, the agent on each node. Takes the pod specs assigned to it and tells the runtime to make those containers real; reports status back.
- **kube-proxy**, programs the node's networking (iptables/IPVS) so Service virtual IPs route to backing pods.
- **container runtime**, containerd or CRI-O, speaking the CRI (Container Runtime Interface). Docker-the-daemon is no longer used directly.

### Core objects (with YAML)

Everything is an object with `apiVersion`, `kind`, `metadata`, `spec` (desired), and `status` (observed, filled by k8s).

#### Pod - the atom

The smallest deployable unit: one or more containers that **share a network namespace** (same localhost + IP) and can share volumes. Usually one app container per pod (plus maybe a sidecar). You rarely create bare pods, controllers do.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web
spec:
  containers:
    - name: web
      image: ghcr.io/spencer/nyx-demo:1.0
      ports: [{ containerPort: 8000 }]
```

Pods are **mortal and disposable**, they get IPs that change, they die and get replaced. Never depend on a specific pod; that's why Services exist.

#### ReplicaSet - keep N pods alive

Ensures a specified number of identical pods exist. You almost never write one directly; Deployments create and manage them.

#### Deployment - the workhorse

Manages ReplicaSets to give you declarative updates, scaling, rollouts, and rollbacks.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nyx-web
  labels: { app: nyx-web }
spec:
  replicas: 3
  selector:
    matchLabels: { app: nyx-web }   # which pods this owns
  template:                          # the pod blueprint
    metadata:
      labels: { app: nyx-web }       # MUST match selector
    spec:
      containers:
        - name: web
          image: ghcr.io/spencer/nyx-demo:1.0
          ports: [{ containerPort: 8000 }]
```

How a rollout works: change the image, and the Deployment creates a *new* ReplicaSet for the new image, scaling it up while scaling the old one down per the rollout strategy. The old ReplicaSet sticks around (scaled to 0), that's what enables instant rollback.

#### Service - stable networking for ephemeral pods

Pods come and go with changing IPs; a Service gives a **stable virtual IP + DNS name** that load-balances to the current healthy pods matching its selector. Three main types:

- **ClusterIP** (default), internal-only virtual IP. Pod-to-pod. `nyx-web.default.svc.cluster.local`.
- **NodePort**, opens a high port (30000-32767) on *every* node, forwarding to the Service. Crude external access.
- **LoadBalancer**, provisions a cloud load balancer (an ELB on AWS) with an external IP. Production external access on managed clusters.

```yaml
apiVersion: v1
kind: Service
metadata: { name: nyx-web }
spec:
  type: ClusterIP
  selector: { app: nyx-web }   # routes to pods with this label
  ports:
    - port: 80                 # the Service's port
      targetPort: 8000         # the container's port
```

#### Ingress - HTTP routing at the edge

A Service of type LoadBalancer per app gets expensive (one cloud LB each). **Ingress** is L7 HTTP(S) routing: host/path rules in front of many ClusterIP Services, served by one Ingress Controller (nginx, Traefik, etc.).

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: nyx-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
    - host: nyx.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service: { name: nyx-web, port: { number: 80 } }
```

#### ConfigMap & Secret - externalized config

Don't bake config into images. **ConfigMap** holds non-sensitive key/values; **Secret** holds sensitive data (base64-encoded *at rest in etcd*, note: base64 is **encoding, not encryption**; enable etcd encryption-at-rest + RBAC for real protection).

```yaml
apiVersion: v1
kind: ConfigMap
metadata: { name: nyx-config }
data:
  APP_ENV: "prod"
  LOG_LEVEL: "info"
---
apiVersion: v1
kind: Secret
metadata: { name: nyx-secret }
type: Opaque
stringData:                       # plaintext here; k8s base64-encodes it
  DATABASE_PASSWORD: "s3cr3t"
```

Inject them into a pod as env vars or mounted files:

```yaml
      envFrom:
        - configMapRef: { name: nyx-config }
      env:
        - name: DATABASE_PASSWORD
          valueFrom:
            secretKeyRef: { name: nyx-secret, key: DATABASE_PASSWORD }
```

#### Namespace - logical partition

Virtual clusters within a cluster (`dev`, `staging`, `prod`, or per-team). Scopes names and lets you apply RBAC and resource quotas per namespace.

#### Volume / PersistentVolumeClaim

A container's filesystem is ephemeral. A **PersistentVolume (PV)** is a piece of storage in the cluster; a **PersistentVolumeClaim (PVC)** is a pod's *request* for storage. The pod mounts the PVC; k8s binds it to a PV (often dynamically provisioned by a StorageClass, e.g. an EBS volume on AWS).

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: pgdata }
spec:
  accessModes: [ReadWriteOnce]
  resources: { requests: { storage: 5Gi } }
```

### Health probes

The kubelet uses probes to decide pod health, this is how self-healing and zero-downtime rollouts actually work:

- **livenessProbe**, "is it alive?" Fails → kubelet **restarts** the container. Catches deadlocks.
- **readinessProbe**, "ready for traffic?" Fails → pod removed from Service endpoints (no restart). Catches "still warming up" / "lost DB connection." Crucial for rollouts: new pods get traffic only once ready.
- **startupProbe**, for slow starters; disables liveness/readiness until it passes.

```yaml
          livenessProbe:
            httpGet: { path: /health, port: 8000 }
            initialDelaySeconds: 10
            periodSeconds: 15
          readinessProbe:
            httpGet: { path: /health, port: 8000 }
            initialDelaySeconds: 5
            periodSeconds: 5
```

### Resource requests/limits & autoscaling

- **requests**, what the pod is *guaranteed*; the scheduler uses this to place pods.
- **limits**, the *ceiling*; exceeding CPU throttles, exceeding memory gets the container OOM-killed.

```yaml
          resources:
            requests: { cpu: "100m", memory: "128Mi" }
            limits:   { cpu: "500m", memory: "256Mi" }
```

(`100m` = 0.1 CPU core. `Mi` = mebibytes.)

The **HorizontalPodAutoscaler (HPA)** is itself a reconciliation loop: it watches a metric (e.g. CPU) and adjusts the Deployment's `replicas` to hold a target. Requires `requests` to be set (it measures utilization *against* the request) and a metrics server installed.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: nyx-web-hpa }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: nyx-web }
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }
```

### kubectl basics

```bash
kubectl apply -f deploy.yaml      # declarative: create/update to match file
kubectl get pods -o wide          # list pods + nodes/IPs
kubectl describe pod <name>       # events + state (first stop for debugging)
kubectl logs -f <pod>             # stream logs
kubectl exec -it <pod> -- sh      # shell into a pod
kubectl rollout status deploy/nyx-web
kubectl scale deploy/nyx-web --replicas=5
kubectl delete -f deploy.yaml
```

Prefer `apply -f` (declarative, k8s diffs to desired state) over `create`/`run` (imperative) for anything real.

## Build it: deploy the 10.1 app to a local cluster

### Spin up a cluster

```bash
# Option A: kind (Kubernetes in Docker)
kind create cluster --name nyx

# Option B: minikube
minikube start
minikube addons enable ingress      # gives us an nginx ingress controller
```

### Manifests

`k8s/deployment.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nyx-web
spec:
  replicas: 3
  selector:
    matchLabels: { app: nyx-web }
  template:
    metadata:
      labels: { app: nyx-web }
    spec:
      containers:
        - name: web
          image: ghcr.io/spencer/nyx-demo:1.0
          ports: [{ containerPort: 8000 }]
          env:
            - name: APP_ENV
              value: "prod"
          readinessProbe:
            httpGet: { path: /health, port: 8000 }
            initialDelaySeconds: 5
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /health, port: 8000 }
            initialDelaySeconds: 10
            periodSeconds: 15
          resources:
            requests: { cpu: "100m", memory: "128Mi" }
            limits:   { cpu: "500m", memory: "256Mi" }
---
apiVersion: v1
kind: Service
metadata: { name: nyx-web }
spec:
  selector: { app: nyx-web }
  ports: [{ port: 80, targetPort: 8000 }]
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: nyx-ingress }
spec:
  ingressClassName: nginx
  rules:
    - host: nyx.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service: { name: nyx-web, port: { number: 80 } }
```

### Deploy, observe, scale, roll out, roll back

```bash
# If using kind, load the local image into the cluster
kind load docker-image ghcr.io/spencer/nyx-demo:1.0 --name nyx

kubectl apply -f k8s/deployment.yaml
kubectl get pods          # watch 3 pods become Running + Ready
kubectl rollout status deploy/nyx-web

# Reach it (add 127.0.0.1 nyx.local to /etc/hosts, or port-forward)
kubectl port-forward svc/nyx-web 8080:80
curl localhost:8080/health

# Prove self-healing: delete a pod, watch a replacement appear
kubectl delete pod -l app=nyx-web --field-selector status.phase=Running | head -1
kubectl get pods -w       # desired=3 → controller recreates one

# Scale
kubectl scale deploy/nyx-web --replicas=5
kubectl get pods

# Rolling update to a new image
kubectl set image deploy/nyx-web web=ghcr.io/spencer/nyx-demo:2.0
kubectl rollout status deploy/nyx-web    # new RS scales up as old scales down
kubectl get rs                           # two ReplicaSets: old (0), new (5)

# Roll back (instant - old ReplicaSet still exists)
kubectl rollout undo deploy/nyx-web
kubectl rollout history deploy/nyx-web   # see revisions
```

The two-ReplicaSet view in `kubectl get rs` is the rolling-update mechanism made visible: rollback is just scaling the old RS back up and the new one down.

## Mini-project: full manifest set for a 2-service app + config/secrets + HPA

Two services: `api` (FastAPI) talking to `db` (Postgres) with persistence, config via ConfigMap, password via Secret, and an HPA on the API.

`k8s/full/`, apply with `kubectl apply -f k8s/full/`.

```yaml
# 00-namespace.yaml
apiVersion: v1
kind: Namespace
metadata: { name: nyx }
---
# 01-config.yaml
apiVersion: v1
kind: ConfigMap
metadata: { name: nyx-config, namespace: nyx }
data:
  APP_ENV: "prod"
  POSTGRES_DB: "nyx"
  POSTGRES_USER: "nyx"
---
apiVersion: v1
kind: Secret
metadata: { name: nyx-secret, namespace: nyx }
type: Opaque
stringData:
  POSTGRES_PASSWORD: "s3cr3t"
---
# 02-postgres.yaml  (Stateful-ish via Deployment + PVC for the lab)
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: pgdata, namespace: nyx }
spec:
  accessModes: [ReadWriteOnce]
  resources: { requests: { storage: 2Gi } }
---
apiVersion: apps/v1
kind: Deployment
metadata: { name: db, namespace: nyx }
spec:
  replicas: 1
  selector: { matchLabels: { app: db } }
  template:
    metadata: { labels: { app: db } }
    spec:
      containers:
        - name: postgres
          image: postgres:16
          envFrom:
            - configMapRef: { name: nyx-config }
          env:
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef: { name: nyx-secret, key: POSTGRES_PASSWORD }
          ports: [{ containerPort: 5432 }]
          volumeMounts:
            - { name: data, mountPath: /var/lib/postgresql/data }
          readinessProbe:
            exec: { command: ["pg_isready", "-U", "nyx"] }
            periodSeconds: 5
      volumes:
        - name: data
          persistentVolumeClaim: { claimName: pgdata }
---
apiVersion: v1
kind: Service
metadata: { name: db, namespace: nyx }
spec:
  selector: { app: db }
  ports: [{ port: 5432, targetPort: 5432 }]
---
# 03-api.yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: api, namespace: nyx }
spec:
  replicas: 2
  selector: { matchLabels: { app: api } }
  template:
    metadata: { labels: { app: api } }
    spec:
      containers:
        - name: api
          image: ghcr.io/spencer/nyx-demo:2.0
          ports: [{ containerPort: 8000 }]
          env:
            - name: APP_ENV
              valueFrom: { configMapKeyRef: { name: nyx-config, key: APP_ENV } }
            - name: DATABASE_URL
              value: "postgresql://nyx:$(DB_PW)@db:5432/nyx"
            - name: DB_PW
              valueFrom:
                secretKeyRef: { name: nyx-secret, key: POSTGRES_PASSWORD }
          readinessProbe:
            httpGet: { path: /health, port: 8000 }
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /health, port: 8000 }
            initialDelaySeconds: 10
          resources:
            requests: { cpu: "100m", memory: "128Mi" }
            limits:   { cpu: "500m", memory: "256Mi" }
---
apiVersion: v1
kind: Service
metadata: { name: api, namespace: nyx }
spec:
  selector: { app: api }
  ports: [{ port: 80, targetPort: 8000 }]
---
# 04-hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api-hpa, namespace: nyx }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }
```

Run and exercise it:

```bash
kubectl apply -f k8s/full/
kubectl -n nyx get all
kubectl -n nyx get hpa            # shows current vs target CPU + replica count

# Generate load to watch the HPA scale up (needs metrics-server)
kubectl -n nyx run load --image=busybox --restart=Never -- \
  /bin/sh -c "while true; do wget -q -O- http://api/; done"
watch kubectl -n nyx get hpa,pods
```

Notes worth remembering: the API finds Postgres at `db:5432` because of the `db` Service's cluster DNS; the password never appears in an image or in plaintext YAML committed to git (Secret); and the HPA needs `requests.cpu` set or it can't compute utilization.

## Guided walkthrough: debugging a broken pod (the skill that matters)

Anyone can `kubectl apply`. The skill that separates beginners from people who get hired is **debugging when a pod won't come up**. Here's an exact mental flow, which works for nearly every Kubernetes problem.

### Step 1 - `get pods` and read the STATUS column

```bash
kubectl get pods
```

The STATUS column is a diagnosis in one word:

| STATUS | What it means | First thing to check |
|--------|---------------|----------------------|
| `Running` (READY 1/1) | Healthy. | Nothing. |
| `Pending` | Not scheduled to a node yet. | Resources (no node has enough CPU/mem) or unbound PVC. |
| `ContainerCreating` | Pulling image / mounting volumes. | If stuck, image pull or volume problem. |
| `ImagePullBackOff` / `ErrImagePull` | Can't pull the image. | Typo'd image name/tag, private registry without creds. |
| `CrashLoopBackOff` | Container starts then crashes, repeatedly. | The app itself is erroring, check logs. |
| `Running` but READY `0/1` | Alive but failing its readiness probe. | Probe path/port, or app not actually ready. |

### Step 2 - `describe` for the events

```bash
kubectl describe pod <name>
```

Scroll to the **Events** section at the bottom, this is the single most useful debugging output in Kubernetes. It narrates what the scheduler and kubelet tried: `Failed to pull image "ngnix"` (a typo!), or `0/3 nodes available: insufficient cpu`, or `Liveness probe failed: HTTP 500`. Most problems are solved right here without ever looking at code.

### Step 3 - `logs` for application errors

```bash
kubectl logs <pod>                 # current container's logs
kubectl logs <pod> --previous      # logs from the PREVIOUS crashed container
kubectl logs -f <pod>              # stream live
```

For a `CrashLoopBackOff`, the `--previous` flag is gold: the current container may be too young to have logged anything, but the one that just died left the traceback. Classic finds: a missing env var, a bad `DATABASE_URL`, an unhandled exception on startup.

### Step 4 - `exec` in to poke around

```bash
kubectl exec -it <pod> -- sh
# inside:
env | grep DATABASE        # are the env vars/Secrets actually injected?
nslookup db                # does the Service DNS resolve?
wget -qO- http://localhost:8000/health   # does the app respond locally?
```

This is the same idea as `docker exec`, get inside reality instead of guessing.

### Step 5 - check the objects around the pod

```bash
kubectl get endpoints <service-name>   # is the Service actually pointing at pods?
kubectl get events --sort-by=.lastTimestamp   # cluster-wide recent events
kubectl get rs                          # ReplicaSets (during a rollout)
```

A *very* common gotcha: a Service with **zero endpoints**. That means its `selector` labels don't match any pod's labels, a one-character typo between the Service `selector` and the Deployment `template.metadata.labels`. The pods are fine; nothing routes to them.

**Walkthrough wrap-up:** `get` → `describe` (events) → `logs` (incl. `--previous`) → `exec` → check endpoints/labels. Internalize that order and Kubernetes stops being scary; it's just a system that tells you exactly what it's doing if you ask the right command.

## Common mistakes

- **Selector/label mismatch.** The Deployment's `selector.matchLabels` and the pod template's `labels` must match, *and* a Service's `selector` must match the pod labels. A typo means a Service with zero endpoints (silent no traffic) or a Deployment that owns no pods. **Fix:** keep labels identical; `kubectl get endpoints` to verify.
- **No resource `requests`, then using an HPA.** The HPA computes utilization *against* `requests.cpu`; with no request, it can't and silently does nothing. **Fix:** always set `requests` when autoscaling.
- **Liveness probe too aggressive.** A short `initialDelaySeconds` on a slow-starting app makes the kubelet kill it before it's up → `CrashLoopBackOff` forever. **Fix:** use a `startupProbe`, or raise `initialDelaySeconds`.
- **Confusing liveness and readiness.** Putting startup-dependency checks in a liveness probe causes restart loops instead of just removing the pod from rotation. **Fix:** "is it broken? → liveness (restart). is it ready for traffic? → readiness (remove from Service)."
- **Treating Secrets as encrypted.** They're base64-*encoded* in etcd, not encrypted. Committing them to git is the same as committing plaintext. **Fix:** enable etcd encryption-at-rest + RBAC, and use a secrets manager / sealed-secrets for git.
- **Using `:latest` image tags.** A pod restart can silently pull a different image; rollbacks become meaningless. **Fix:** pin immutable tags (git SHA).
- **`kubectl edit`/`kubectl scale` on production.** Imperative tweaks drift from your YAML in git; the next `apply` reverts them or fights them. **Fix:** change the YAML, commit, `apply` (GitOps).
- **Forgetting `kind load docker-image`.** On kind, a locally built image isn't in the cluster's nodes, so you get `ImagePullBackOff`. **Fix:** `kind load docker-image <img> --name <cluster>`.
- **One giant pod with many containers.** Cramming app + DB + worker into one pod defeats independent scaling and restarts. **Fix:** one app per pod; let the Deployment/Service model the rest.

## On the job / interview angle

Kubernetes is the lingua franca of running services at scale. On the job you'll write and review manifests, debug failing rollouts, read dashboards, and run `kubectl` against dev/staging clusters daily. It's a heavyweight interview topic for backend, platform, DevOps, and SRE roles, and even when you won't write much YAML, interviewers want to know you understand the *model*.

**What you actually do with it at work:**
- Own a Deployment + Service + ConfigMap/Secret for your service and keep them in git.
- Debug `CrashLoopBackOff` / `ImagePullBackOff` / zero-endpoint Services (the walkthrough above).
- Read rollouts: `kubectl rollout status`, and `rollout undo` when a deploy goes bad.
- Tune probes, requests/limits, and HPAs so the service is stable and cost-efficient.

**Representative interview questions (with the crisp answer):**

1. *"Explain Kubernetes in one sentence."* → A control loop that continuously reconciles the cluster's actual state toward the declarative desired state you submit.
2. *"What is a pod, and why not just deploy containers?"* → A pod is the smallest deployable unit (one or more containers sharing network + storage); Kubernetes schedules and heals pods, not bare containers.
3. *"Deployment vs ReplicaSet vs Pod?"* → A Deployment manages ReplicaSets to give declarative updates/rollbacks; a ReplicaSet keeps N identical pods alive; a pod is one running instance.
4. *"Pods have changing IPs, how does one service reach another?"* → A Service: a stable virtual IP + DNS name that load-balances to the healthy pods matching its selector.
5. *"ClusterIP vs NodePort vs LoadBalancer vs Ingress?"* → Internal-only VIP / a port on every node / a cloud LB with external IP / L7 HTTP routing in front of many Services.
6. *"Liveness vs readiness probe?"* → Liveness failure restarts the container; readiness failure removes the pod from the Service (no restart). Readiness is what makes rollouts zero-downtime.
7. *"How does a rolling update enable instant rollback?"* → It creates a new ReplicaSet and scales it up while scaling the old one down; the old RS stays at 0 replicas, so `rollout undo` just scales it back.
8. *"requests vs limits?"* → Requests = guaranteed/scheduling amount; limits = hard ceiling (CPU throttles, memory OOM-kills).
9. *"What's in the control plane?"* → api-server (front door), etcd (state), scheduler (places pods), controller-manager (the reconcile loops).
10. *"ConfigMap vs Secret, and is a Secret secure?"* → Both externalize config; Secret is for sensitive data but only base64-encoded by default, you need etcd encryption + RBAC for real security.

**Tip:** narrate the debugging flow (`get` → `describe` → `logs` → `exec`) unprompted. It signals you've actually operated clusters, not just read about them.

## Exercises

Use a local cluster (`kind` or `minikube`). Solutions follow.

1. **(easy)** Create a one-node cluster, run an nginx Deployment with 2 replicas imperatively, and list the pods with their node and IP.
2. **(easy)** Convert that imperative Deployment to YAML using `kubectl get deploy nginx -o yaml`, save it, delete the Deployment, and recreate it with `kubectl apply -f`.
3. **(easy)** Expose the nginx Deployment with a ClusterIP Service and reach it via `kubectl port-forward`.
4. **(medium)** Scale the Deployment to 4 replicas two ways: imperatively (`kubectl scale`) and declaratively (edit the YAML + `apply`). Explain why mixing them causes drift.
5. **(medium)** Deliberately break a Deployment by setting the image to `nginx:doesnotexist`. Diagnose it with `get`/`describe` and state the exact STATUS and Event you see.
6. **(medium)** Add a `readinessProbe` hitting `/` on port 80 to the nginx pod and watch the READY column go `0/1` → `1/1`.
7. **(medium)** Create a ConfigMap with `GREETING=hi` and inject it as an env var into a `busybox` pod that runs `env`. Confirm via logs.
8. **(hard)** Do a rolling update (change the image tag), then `kubectl get rs` to show two ReplicaSets, then `kubectl rollout undo` and confirm the rollback in `rollout history`.
9. **(hard)** Create a Service whose selector intentionally doesn't match any pod. Show it has zero endpoints, then fix the selector and show endpoints appear.
10. **(hard)** Set CPU `requests`, add an HPA (min 1, max 5, 50% CPU), generate load with a busybox loop, and watch `kubectl get hpa` scale the replicas up.

### Solutions

1. ```bash
   kind create cluster --name ex
   kubectl create deployment nginx --image=nginx --replicas=2
   kubectl get pods -o wide       # NAME, STATUS, NODE, IP columns
   ```

2. ```bash
   kubectl get deploy nginx -o yaml > nginx.yaml   # trim status/managedFields if you like
   kubectl delete deployment nginx
   kubectl apply -f nginx.yaml                      # recreated identically
   ```
   This is the bridge from imperative learning to declarative practice.

3. ```bash
   kubectl expose deployment nginx --port=80 --type=ClusterIP
   kubectl port-forward svc/nginx 8080:80
   curl localhost:8080        # nginx welcome page
   ```

4. `kubectl scale deploy/nginx --replicas=4` changes the live object; if your committed YAML still says `replicas: 2`, the next `apply` reverts it to 2. The cluster and git disagree - that's **drift**. The fix in real life: pick one source of truth (the YAML in git) and only change replicas there (or let an HPA own it).

5. ```bash
   kubectl set image deploy/nginx nginx=nginx:doesnotexist
   kubectl get pods         # STATUS: ImagePullBackOff (or ErrImagePull)
   kubectl describe pod <name>   # Event: "Failed to pull image ... not found"
   ```
   The old replica keeps serving (rolling update won't kill it until the new one is healthy), that's the rollout safety net protecting you.

6. Add to the container spec:
   ```yaml
   readinessProbe:
     httpGet: { path: /, port: 80 }
     initialDelaySeconds: 2
     periodSeconds: 3
   ```
   `kubectl apply`, then `kubectl get pods -w`: READY shows `0/1` for a few seconds until the probe passes, then `1/1`. Only then does the Service route to it.

7. ```bash
   kubectl create configmap greet --from-literal=GREETING=hi
   kubectl run probe --image=busybox --restart=Never \
     --overrides='{"spec":{"containers":[{"name":"probe","image":"busybox","command":["env"],"envFrom":[{"configMapRef":{"name":"greet"}}]}]}}'
   kubectl logs probe | grep GREETING       # GREETING=hi
   ```
   (In real manifests you'd use `envFrom: [{configMapRef: {name: greet}}]` in the pod spec - same effect, cleaner.)

8. ```bash
   kubectl set image deploy/nginx nginx=nginx:1.27
   kubectl get rs                 # two ReplicaSets: old (desired 0), new (desired N)
   kubectl rollout undo deploy/nginx
   kubectl rollout history deploy/nginx    # shows the revisions; you're back on the prior one
   ```
   Rollback is instant because the old ReplicaSet still exists at 0 replicas; undo just scales it back up.

9. Apply a Service with `selector: { app: typo }` while pods are labeled `app: nginx`:
   ```bash
   kubectl get endpoints nginx     # <none> - no endpoints
   # fix the selector to app: nginx, re-apply:
   kubectl get endpoints nginx     # now lists pod IPs:80
   ```
   This reproduces the #1 silent Kubernetes networking bug.

10. ```bash
    # ensure the Deployment has resources.requests.cpu: "100m"
    kubectl autoscale deploy/nginx --min=1 --max=5 --cpu-percent=50
    kubectl run load --image=busybox --restart=Never -- \
      /bin/sh -c "while true; do wget -q -O- http://nginx; done"
    watch kubectl get hpa,pods     # TARGETS climbs past 50% → replicas increase
    ```
    Requires `metrics-server` installed. The HPA is itself a reconciliation loop adjusting `replicas`.

## Mini-project 2: zero-downtime rollout you can *prove*, plus a CronJob

The earlier mini-project built a 2-service app. This one is about *proving* zero downtime during a rollout and adding a scheduled batch job - both extremely common real tasks.

**Part A - prove zero downtime.** Deploy the app with a proper readiness probe and a `RollingUpdate` strategy that never drops capacity, then hammer it with traffic *while* you roll out a new version and show zero failed requests.

`k8s/rollout-demo.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: nyx-web }
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0      # never drop below desired capacity
      maxSurge: 2            # add up to 2 extra pods during the roll
  selector:
    matchLabels: { app: nyx-web }
  template:
    metadata:
      labels: { app: nyx-web }
    spec:
      containers:
        - name: web
          image: ghcr.io/spencer/nyx-demo:1.0
          ports: [{ containerPort: 8000 }]
          readinessProbe:                    # traffic only when ready → no 5xx mid-roll
            httpGet: { path: /health, port: 8000 }
            periodSeconds: 2
          # graceful shutdown: finish in-flight requests before dying
          lifecycle:
            preStop:
              exec: { command: ["sh", "-c", "sleep 5"] }
---
apiVersion: v1
kind: Service
metadata: { name: nyx-web }
spec:
  selector: { app: nyx-web }
  ports: [{ port: 80, targetPort: 8000 }]
```

Prove it:

```bash
kubectl apply -f k8s/rollout-demo.yaml
kubectl port-forward svc/nyx-web 8080:80 &

# In one terminal, fire continuous requests and count failures:
while true; do curl -s -o /dev/null -w "%{http_code}\n" localhost:8080/health; sleep 0.2; done \
  | sort | uniq -c &

# In another, roll out a new version:
kubectl set image deploy/nyx-web web=ghcr.io/spencer/nyx-demo:2.0
kubectl rollout status deploy/nyx-web
```

If everything is configured right, the request counter shows essentially **all 200s and zero 5xx** across the rollout. The combination doing the work: `maxUnavailable: 0` (capacity never dips), the readiness probe (new pods get traffic only when ready), and the `preStop` sleep (old pods finish in-flight requests before terminating). Now flip `maxUnavailable: 0` to `maxUnavailable: 4` and remove the readiness probe, repeat, and watch failures appear - the contrast *is* the lesson.

**Part B - a scheduled job.** Real systems need recurring batch work (nightly reports, cleanup, cache warming). That's a **CronJob**, which creates a Job on a schedule, which runs a pod to completion.

`k8s/report-cron.yaml`:

```yaml
apiVersion: batch/v1
kind: CronJob
metadata: { name: nightly-report }
spec:
  schedule: "0 2 * * *"            # 02:00 every day (standard cron syntax)
  concurrencyPolicy: Forbid        # don't start a new run if the last is still going
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 2              # retry a failed run up to twice
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: report
              image: ghcr.io/spencer/nyx-demo:2.0
              command: ["python", "-c", "print('generating nightly report...')"]
```

```bash
kubectl apply -f k8s/report-cron.yaml
kubectl get cronjob
# Trigger one immediately instead of waiting for 02:00:
kubectl create job --from=cronjob/nightly-report manual-run
kubectl logs job/manual-run        # "generating nightly report..."
```

What this teaches: not everything is a long-running web server. CronJob → Job → Pod is the batch counterpart to Deployment → ReplicaSet → Pod, and `concurrencyPolicy`/`backoffLimit`/history limits are the knobs that keep scheduled work from piling up or silently failing. Stretch goal: make the report job write to a PVC and have the web Deployment serve the latest report file.
