## 🌱 Start here - the array as a row of numbered lockers

Before any math, let's build the picture you'll carry through the whole chapter. Picture a hallway at a gym lined with lockers. They're bolted together in a single unbroken row, all identical, and each one has a number painted on it: `0, 1, 2, 3, ...`. That row of lockers **is an array.**

```
  locker:   [  0  ][  1  ][  2  ][  3  ][  4  ]
  holds:      cap    keys   wallet phone  shoes
```

Here's the one property that makes a row of lockers special, and it's the entire reason arrays exist:

> If you're told "go grab whatever's in locker 3," you **walk straight to locker 3.** You don't open locker 0, then 1, then 2, checking each one. You know exactly where locker 3 is because the lockers are the same width and bolted in a row, so locker 3 is just "3 lockers' worth of distance" from the start of the hallway.

That's it. That's the superpower. Because the lockers are **identical in size** and **physically next to each other in order**, the position of any locker is something you can _calculate_ instead of _search for_. "Where's locker `i`?" is answered by arithmetic: start of hallway, plus `i` locker-widths. One step, no matter how long the hallway is, locker 3 or locker 3 million, same instant walk.

Now contrast that with a different way to store things: a **treasure hunt**, where the cap holds a note saying "your keys are behind the potted plant," and the keys hold a note saying "your wallet is under the doormat," and so on. To find the 4th item you must follow the chain of notes one by one. That's a **linked list** (next chapter), and the comparison is the whole story of this book: lockers give you instant jump-to-any-position; treasure hunts make you walk the chain.

A few terms we'll use constantly, grounded in the locker picture:

- **Index**, the number painted on a locker (`0, 1, 2, ...`). We start counting at **0**, not 1, for a reason that'll become clean arithmetic shortly: index `0` means "zero locker-widths from the start," i.e. the very first locker.
- **Element**, what's inside a locker (the cap, the keys).
- **Contiguous**, the fancy word for "bolted together in one unbroken row with no gaps." This is the property that makes the jump-to-any-locker trick work.
- **Capacity vs. size**, how many lockers the hallway _has_ versus how many you've actually _filled_. A 50-locker hallway with 3 things in it has capacity 50 and size 3. Keep these two separate in your head; half this chapter hinges on the difference.

**Why does this matter?** Almost every other data structure in this book is built on top of arrays, or defined by contrast with them. Lists, stacks, queues, hash tables, heaps, dynamic strings, the rows of a matrix, under the hood, a contiguous block of lockers. Get arrays in your bones and you've got the foundation for everything else. So let's now make the locker intuition rigorous: we'll prove the "instant jump" with actual address arithmetic.

## 📐 The theory: what an array actually *is*

Forget Python for a second. At the hardware level, an **array** is the simplest possible data structure: a single, unbroken block of memory holding `n` elements, each of identical size `s` bytes, laid end to end.

That word **contiguous** is the whole game. It means element `i` lives at a memory address you can _compute_, not search for:

```
address(a[i]) = base_address + i * stride
```

where `stride` (also called the element size) is how many bytes one element occupies. `base_address` is where element `0` starts.

Let's make sure you actually believe this, because it's the foundation everything else rests on.

### Why indexing is O(1) - derived, not asserted

Suppose you have an array of 32-bit integers (`stride = 4` bytes) starting at address `1000`.

- `a[0]` lives at `1000 + 0*4 = 1000`
- `a[1]` lives at `1000 + 1*4 = 1004`
- `a[2]` lives at `1000 + 2*4 = 1008`
- `a[i]` lives at `1000 + i*4`

To read `a[i]`, the CPU does **one multiplication and one addition**, then one memory fetch. That's it. The work does **not** depend on `i` and does **not** depend on `n` (the array length). Whether the array has 10 elements or 10 billion, computing the address of `a[7]` is the same fixed handful of operations.

A cost that doesn't grow with the input size is, by definition, **O(1), constant time**. That's the proof. Indexing is O(1) precisely _because_ the address is a closed-form arithmetic expression in `i`, and that's only possible _because_ the memory is contiguous and every element is the same size.

> **The mental hook:** Random access is free because the array is a _formula_, not a _search_. A linked list can't do this, its elements are scattered, so to find element `i` you have to walk `i` pointers. That's the entire reason arrays exist.

### Contiguity, made concrete in C++

Python hides addresses from you, so let's drop to C++ just long enough to _see_ the contiguity and the pointer arithmetic with your own eyes. This is the one place where pointers genuinely matter for understanding.

```cpp
#include <iostream>
#include <cstdint>

int main() {
    int a[5] = {10, 20, 30, 40, 50};

    // `a` decays to a pointer to its first element.
    // &a[i] is the address of element i.
    for (int i = 0; i < 5; ++i) {
        std::cout << "a[" << i << "] = " << a[i]
                  << "  @ address " << (void*)&a[i] << "\n";
    }

    std::cout << "\nstride (sizeof int) = " << sizeof(int) << " bytes\n";

    // Pointer arithmetic IS index arithmetic.
    // *(a + i) is exactly the same thing as a[i]. The compiler
    // literally rewrites a[i] as *(a + i).
    std::cout << "*(a + 2) = " << *(a + 2) << "  (same as a[2])\n";

    // Prove the address formula: base + i*stride
    uintptr_t base = (uintptr_t)&a[0];
    uintptr_t computed = base + 3 * sizeof(int);
    std::cout << "base + 3*stride = " << (void*)computed
              << "  should equal &a[3] = " << (void*)&a[3] << "\n";

    return 0;
}
```

Sample output (addresses vary per run, but the **pattern** is the point):

```
a[0] = 10  @ address 0x7ffd...c0
a[1] = 20  @ address 0x7ffd...c4
a[2] = 30  @ address 0x7ffd...c8
a[3] = 40  @ address 0x7ffd...cc
a[4] = 50  @ address 0x7ffd...d0

stride (sizeof int) = 4 bytes
*(a + 2) = 30  (same as a[2])
base + 3*stride = 0x7ffd...cc  should equal &a[3] = 0x7ffd...cc
```

Look at the addresses: `c0, c4, c8, cc, d0`, each is exactly `4` (the stride) past the last. **That's contiguity you can touch.** And the punchline, `a[i]` is *defined* in C++ as `*(a + i)`. The bracket syntax is sugar over pointer arithmetic. When you write `a[3]`, the compiler computes `base + 3*stride` and dereferences it. Exactly the formula.

This is also why arrays in C are 0-indexed, by the way: index `0` means "0 strides past the base," i.e. the base itself. 1-indexing would force an extra subtraction on every access. The math is cleaner from zero.

## 📐 Fixed vs. dynamic arrays

There are two flavors, and the distinction is the source of basically everything interesting in this chapter.

**Fixed-size array** (a raw C array, `int a[5]`, or Python's `array.array` if you don't grow it): the size is decided when you allocate, and it never changes. The block of memory is exactly big enough and that's all you get.

- **Pro:** zero overhead, perfectly contiguous, cache-friendly.
- **Con:** if you need a 6th element, you're out of luck. You'd have to allocate a new bigger block and copy everything over yourself.

**Dynamic array** (Python's `list`, C++'s `std::vector`, Java's `ArrayList`): looks like it can grow without bound. You just keep `append`-ing. But here's the thing worth examining closely, **the underlying memory is still a fixed-size contiguous block.** The dynamic array is a *lie we maintain on top of a fixed buffer.*

The trick: keep two numbers.
- **capacity**, how big the underlying buffer actually is.
- **size** (or length), how many slots are currently filled.

When `size` would exceed `capacity`, we secretly allocate a **new, bigger** buffer, copy everything over, and throw the old one away. The user never sees it. They think they have an infinitely growable array.

The entire art is in _how much bigger_ we make the new buffer, and the entire payoff is the amortized analysis that says this is cheap on average. Let's build it and find out.

## 💻 Build it: a dynamic array from scratch

We're going to build `ArrayList` on top of a **fixed-capacity buffer**. To keep us honest, no cheating with Python's already-dynamic `list` as the backing store, we'll use `ctypes` to allocate a genuine raw, fixed-size array of `object` pointers. This is as close to "a real fixed buffer" as Python lets you get.

```python
import ctypes


class ArrayList:
    """A dynamic array built on a fixed-capacity raw buffer.

    INVARIANTS (must hold before and after every public method):
      1. 0 <= self._size <= self._capacity
      2. self._capacity >= 1
      3. Slots [0, self._size) hold valid user elements.
      4. Slots [self._size, self._capacity) are unused (garbage / None).
      5. The buffer is contiguous: element i lives at offset i.
    """

    def __init__(self):
        self._size = 0           # number of elements the user has stored
        self._capacity = 1       # size of the underlying buffer
        self._buffer = self._make_buffer(self._capacity)

    # --- helpers -------------------------------------------------------

    def _make_buffer(self, capacity):
        """Allocate a raw fixed-size array of `capacity` object pointers."""
        # (capacity * py_object) is a ctypes ARRAY type; calling it allocates it.
        return (capacity * ctypes.py_object)()

    # --- O(1) operations ----------------------------------------------

    def __len__(self):
        return self._size

    def __getitem__(self, i):
        if not 0 <= i < self._size:
            raise IndexError("index out of range")
        # THE O(1) ACCESS: direct offset into the buffer. No scanning.
        return self._buffer[i]

    def __setitem__(self, i, value):
        if not 0 <= i < self._size:
            raise IndexError("index out of range")
        self._buffer[i] = value

    # --- the interesting one: append ----------------------------------

    def append(self, value):
        if self._size == self._capacity:
            # Buffer is full. Grow it. THIS is the expensive-but-rare step.
            self._resize(2 * self._capacity)   # geometric growth: DOUBLE
        self._buffer[self._size] = value
        self._size += 1

    def _resize(self, new_capacity):
        """Allocate a bigger buffer and copy everything over. O(n)."""
        new_buffer = self._make_buffer(new_capacity)
        for i in range(self._size):           # copy all n existing elements
            new_buffer[i] = self._buffer[i]
        self._buffer = new_buffer             # old buffer is now garbage
        self._capacity = new_capacity

    # --- O(n) operations: shifting ------------------------------------

    def insert(self, i, value):
        """Insert `value` at index i, shifting later elements right."""
        if not 0 <= i <= self._size:
            raise IndexError("index out of range")
        if self._size == self._capacity:
            self._resize(2 * self._capacity)
        # Shift elements [i, size) one slot to the RIGHT, working backward
        # so we don't clobber values we haven't moved yet.
        for j in range(self._size, i, -1):
            self._buffer[j] = self._buffer[j - 1]
        self._buffer[i] = value
        self._size += 1

    def delete(self, i):
        """Delete element at index i, shifting later elements left."""
        if not 0 <= i < self._size:
            raise IndexError("index out of range")
        removed = self._buffer[i]
        # Shift elements (i, size) one slot to the LEFT.
        for j in range(i, self._size - 1):
            self._buffer[j] = self._buffer[j + 1]
        self._buffer[self._size - 1] = None   # let the old reference go
        self._size -= 1
        return removed

    # --- niceties so it behaves like a real sequence ------------------

    def __iter__(self):
        for i in range(self._size):
            yield self._buffer[i]

    def __repr__(self):
        return "ArrayList([" + ", ".join(repr(x) for x in self) + "])"

    def capacity(self):
        return self._capacity
```

Notice what each method costs:

- `__getitem__` / `__setitem__`: one offset lookup. **O(1).** This is the C++ formula `base + i*stride` happening underneath ctypes.
- `append`: O(1) the vast majority of the time; O(n) on the rare resize. We'll prove the _average_ is O(1) next.
- `insert` / `delete`: that shifting loop runs up to `n` times. **O(n).**

### Traced walkthrough - watch the buffer double

Reading `_resize` is one thing; _watching_ it fire is what makes it stick. Let's hand-trace a fresh `ArrayList` through eight `append`s and draw the buffer after each one. We'll use `_` for an unused slot, and show `size` and `capacity` so you can see exactly when a resize is forced.

Start state, right after `ArrayList()`:

```
cap=1  size=0   buffer: [ _ ]
```

**append('a')**, is `size == capacity`? `0 == 1`? No. Just write and bump size.

```
cap=1  size=1   buffer: [ a ]          (no resize)
```

**append('b')**, `size == capacity`? `1 == 1`? **Yes, buffer full.** Resize to `2*1 = 2`: allocate `[ _ , _ ]`, copy the 1 existing element over, then write 'b'.

```
  resize 1 -> 2, copy 1 element:
  cap=2  size=1   buffer: [ a , _ ]    (after copy, before write)
  write 'b', size -> 2:
cap=2  size=2   buffer: [ a , b ]      (RESIZE happened)
```

**append('c')**, `2 == 2`? **Yes.** Resize to `4`, copy 2 elements, write 'c'.

```
  resize 2 -> 4, copy 2 elements:
  cap=4  size=2   buffer: [ a , b , _ , _ ]
  write 'c', size -> 3:
cap=4  size=3   buffer: [ a , b , c , _ ]   (RESIZE happened)
```

**append('d')**, `3 == 4`? No. Just write.

```
cap=4  size=4   buffer: [ a , b , c , d ]   (no resize)
```

**append('e')**, `4 == 4`? **Yes.** Resize to `8`, copy 4 elements, write 'e'.

```
  resize 4 -> 8, copy 4 elements:
  cap=8  size=4   buffer: [ a , b , c , d , _ , _ , _ , _ ]
  write 'e', size -> 5:
cap=8  size=5   buffer: [ a , b , c , d , e , _ , _ , _ ]   (RESIZE happened)
```

**append('f'), append('g'), append('h')**, `5,6,7` all `< 8`. No resizes; just three quiet writes.

```
cap=8  size=8   buffer: [ a , b , c , d , e , f , g , h ]   (no resize)
```

Now stare at the resize pattern across those 8 appends:

```
append #:   1   2   3   4   5   6   7   8
capacity:   1   2   4   4   8   8   8   8
resized?:   .   *   *   .   *   .   .   .     ('*' = a copy happened)
elems copied: 0  1   2   0   4   0   0   0    -> total copied = 7
```

Seven total copies to place eight elements. And notice the resizes get **rarer** as we go, they happen at append #2, #3, #5, and the next one wouldn't be until #9. The gaps double (1, 2, 4, ...). _That spacing is the amortized-O(1) proof in picture form_, the expensive steps are spread exponentially farther apart, so their total cost stays linear. We'll formalize this in the proof section; for now you've literally watched it happen.

#### And the other direction - `insert(0, x)` shifts everyone right

Resize is about running out of room at the **end**. `insert` is about opening a hole in the **middle** (or front), which is a different cost entirely. Say the buffer holds `[10, 20, 30, _]` (cap=4, size=3) and you call `insert(0, 5)`, put 5 at the front. There's room (no resize needed), but every existing element has to slide one slot right to make space at index 0. The loop runs **backward** so it never overwrites a value it hasn't moved yet:

```
start:        cap=4 size=3   [ 10 , 20 , 30 , _  ]
                                ^0   ^1   ^2   ^3

copy slot 2 -> 3:             [ 10 , 20 , 30 , 30 ]   (30 now in slot 3)
copy slot 1 -> 2:             [ 10 , 20 , 20 , 30 ]   (20 now in slot 2)
copy slot 0 -> 1:             [ 10 , 10 , 20 , 30 ]   (10 now in slot 1)
write 5 into slot 0:          [ 5  , 10 , 20 , 30 ]   size -> 4
final:        cap=4 size=4   [ 5  , 10 , 20 , 30 ]
```

Three shifts to insert one element into a 3-element array. Insert at the front of an `n`-element array does `n` shifts, that's the **O(n)** we derive properly later. Compare to `append`, which on a non-resize step writes one slot and shifts _nobody_. End-insertion is cheap precisely because nobody's in the way; front/middle insertion is expensive precisely because everyone is.

## 📐 The amortized O(1) append - *the proof*

Here's the tension that's easy to feel but hard to resolve. `append` is _sometimes_ O(n): when the buffer fills, we copy all `n` elements to a new buffer. So how on earth do people call append "O(1)"? Isn't that a lie?

No. It's **amortized** O(1), and there's a real theorem behind it. "Amortized" means: averaged over a long sequence of operations, the cost per operation is constant, even though individual operations vary. The expensive resizes are _rare enough_ that their cost, spread across all the cheap appends, comes out to a constant per append.

Let's prove it two ways, because seeing both makes it click.

### Method 1: the aggregate method (just add it all up)

Start with capacity 1, doubling each time it fills. Do `n` appends. Total cost = (cost of all the cheap writes) + (cost of all the copying during resizes).

**Cheap writes:** every append writes exactly one element into a slot. That's `n` writes total, cost `n`. Easy.

**The copying:** resizes happen when the buffer is full, at sizes 1, 2, 4, 8, 16, ... When we resize a buffer of size `k`, we copy `k` elements. So the resizes that occur during `n` appends copy:

```
1 + 2 + 4 + 8 + ... + (largest power of 2 < n)
```

This is a geometric series. The key fact about doubling: **the sum of all the powers of two up to `2^m` is `2^(m+1) - 1`**, which is _less than twice the last (and largest) term._ Concretely, if the largest copy is of size `≈ n`:

```
1 + 2 + 4 + ... + n  =  2n - 1  <  2n
```

> The intuition to burn in: **in a doubling series, the very last term is bigger than everything before it combined.** `1+2+4+8 = 15`, and `16` alone beats it. So the total copying work is dominated by the final resize and is at most about `2n`.

Total work over `n` appends:

```
Total ≤ n (writes) + 2n (copies) = 3n
```

Average per append:

```
3n / n = 3 = O(1)   ✅
```

There it is. The total cost of `n` appends is **linear in n**, so the cost _per_ append is **constant**. That's the proof. The expensive O(n) resizes are real, but each size only happens once and the sizes shrink geometrically going back, so they sum to a linear total, not a quadratic one.

### Method 2: the accounting (banker's) method - same truth, prettier

This one is a favorite because it's almost a magic trick. Instead of summing afterward, we **prepay**.

Charge each `append` a flat **3 credits** (an amortized cost of 3 = O(1)). Spend the credits like this:

- **1 credit** pays for the actual write of the new element.
- **2 credits** go into a savings account, attached to that element.

Claim: when a resize happens, there's always exactly enough saved money in the bank to pay for all the copying, so resizes are "free" (already paid for). If that holds, then every operation truly costs only its 3 prepaid credits, and amortized cost is O(1).

**Why the bank never runs dry:** Consider a buffer that just doubled from `k` to `2k`. Right after that resize, it's half full (it holds `k` elements). To fill it up to `2k` and trigger the _next_ resize, we must append another `k` elements. Each of those `k` appends deposits 2 credits → `2k` credits banked. The next resize copies `2k` elements (cost `2k`). The bank has exactly `2k`. **It pays for itself.** Every single time. The bank balance never goes negative, so our charge of 3 per op is always sufficient.

Since each operation is charged a constant (3) and that charge provably covers all real costs, **amortized append = O(1).** Same conclusion as Method 1, arrived at by prepayment instead of summation.

### Why *doubling*? Why not "grow by 10 each time"?

This is the question that makes sure you understood the proof rather than memorized it. Suppose instead of doubling, you grow by a **fixed amount**, say add 1 slot each time it fills (arithmetic growth).

Then every append triggers a resize, copying all `n` elements. Cost of `n` appends:

```
1 + 2 + 3 + ... + n = n(n+1)/2 = O(n²)
```

Per append: O(n). **Terrible.** Linear per append, not constant.

The magic of doubling (or any **geometric** factor > 1, like 1.5×) is that it makes resizes _exponentially rarer_ as the array grows, so their total cost stays linear. Geometric growth is the whole reason amortized O(1) exists. The growth factor is a real engineering knob: 2× wastes up to ~50% memory but minimizes copies; `std::vector` implementations often use 1.5× to allow reusing freed memory blocks. CPython uses roughly 1.125× (`newsize + newsize/8 + ...`), a smaller factor that trades a few more copies for tighter memory.

## 📐 Insert and delete: deriving the O(n)

`append` adds at the **end**, where there's no one in the way. `insert(i, x)` and `delete(i)` operate in the **middle**, and that changes everything, because of contiguity. The array's superpower (computable addresses) is also its curse: there are no gaps. To open a hole at index `i`, every element from `i` onward must physically slide over by one.

**`insert(i, x)`** must shift elements at indices `i, i+1, ..., size-1` one slot to the right, that's `size - i` moves. Worst case `i = 0` (insert at front): we shift **all `n`** elements. So:

```
insert cost (worst case) = n shifts = O(n)
```

**`delete(i)`** must shift elements at `i+1, ..., size-1` one slot to the left to close the gap, `size - i - 1` moves. Worst case `i = 0` again: shift `n-1 ≈ n` elements. So:

```
delete cost (worst case) = n shifts = O(n)
```

**Best case** for both is operating at the **end** (`i = size`): zero shifts, O(1). That's exactly why `append` (insert at the end) and `pop()` (delete at the end) are the cheap operations and front/middle operations are expensive.

> The deep lesson: an array is **fast to read anywhere, fast to modify only at the end.** If your workload is "constantly insert/delete at the front," an array is the wrong tool, you want a linked list or a deque. The data structure's shape should match the operations you actually do.

## 📐 Complexity table & invariants (the reference card)

The summary you'll want to be able to reproduce from scratch:

| Operation                | Time (avg)        | Time (worst)  | Space | Why |
|--------------------------|-------------------|---------------|-------|-----|
| Index read `a[i]`        | O(1)              | O(1)          | O(1)  | address = base + i·stride |
| Index write `a[i] = v`   | O(1)              | O(1)          | O(1)  | same offset arithmetic |
| `append(v)`              | **O(1) amortized**| O(n)          | O(1)* | worst case = a resize copies n elements |
| `pop()` (from end)       | O(1) amortized    | O(1)          | O(1)  | no shifting, just shrink size |
| `insert(i, v)`           | O(n)              | O(n)          | O(1)* | shift up to n elements right |
| `delete(i)`              | O(n)              | O(n)          | O(1)  | shift up to n elements left |
| `search` (unsorted)      | O(n)              | O(n)          | O(1)  | must scan; no structure to exploit |
| `len`                    | O(1)              | O(1)          | O(1)  | we store size explicitly |
| total storage            |, |, | O(n)  | buffer is ≤ 2n with doubling |

\* The amortized **extra** space per append is O(1); a single resize transiently allocates a second buffer (O(n) peak during the copy).

**Invariants** (restating, because invariants are how you prove a data structure is correct):

1. `0 ≤ size ≤ capacity`, never store more than the buffer holds; never claim more elements than exist.
2. `capacity ≥ 1`, there is always a real buffer to write into.
3. Slots `[0, size)` hold valid user data, in order.
4. Slots `[size, capacity)` are unused, never read them as data.
5. The buffer is **contiguous**, so element `i` is always at offset `i`. (This is what licenses the O(1) address formula.)

If every method preserves these on the way in and on the way out, the structure is correct. That's the whole correctness argument.

## 📐 ...and that's exactly what Python's `list` is

Here's the payoff that recontextualizes everything you use daily: **Python's built-in `list` is a dynamic array**, precisely the thing we just built. Internally (in CPython, file `Objects/listobject.c`) a list is a struct holding a pointer to a contiguous buffer of `PyObject*` pointers, an `ob_size` (our `size`), and an `allocated` field (our `capacity`). When you `.append()` past `allocated`, CPython calls `list_resize`, which over-allocates geometrically, exactly our `_resize`, just tuned to ~1.125× growth.

So everything transfers directly:

- `lst[i]` is O(1), offset arithmetic, just like ours.
- `lst.append(x)` is amortized O(1), same doubling-style proof.
- `lst.insert(0, x)` is O(n), it shifts every element, same as ours. (This is _the_ reason `list.insert(0, ...)` in a loop is a classic performance trap; use `collections.deque` for front operations.)
- `lst.pop()` (end) is O(1); `lst.pop(0)` (front) is O(n).

You never have to wonder about Python list performance again, you can _derive_ it. It's the structure in this chapter.

## 🧪 Mini-project: a typed dynamic array + benchmark vs. `list`

Two goals: (1) extend your `ArrayList` into a **typed** array that enforces every element is the same type (like `std::vector<int>` or `array.array`), and (2) **benchmark** your `append` against Python's native `list.append` and explain the gap.

### Part 1 - `TypedArrayList`

```python
import ctypes
import time


class TypedArrayList:
    """A dynamic array that enforces a single element type.

    Extra invariant (on top of ArrayList's):
      6. Every stored element is an instance of self._type.
    """

    def __init__(self, element_type):
        if not isinstance(element_type, type):
            raise TypeError("element_type must be a type, e.g. int or str")
        self._type = element_type
        self._size = 0
        self._capacity = 1
        self._buffer = self._make_buffer(self._capacity)

    def _make_buffer(self, capacity):
        return (capacity * ctypes.py_object)()

    def _check(self, value):
        # Enforce invariant 6. Reject bool sneaking in as int if exact match
        # is desired; here we use isinstance for the usual subtype semantics.
        if not isinstance(value, self._type):
            raise TypeError(
                f"expected {self._type.__name__}, "
                f"got {type(value).__name__}: {value!r}"
            )

    def __len__(self):
        return self._size

    def __getitem__(self, i):
        if not 0 <= i < self._size:
            raise IndexError("index out of range")
        return self._buffer[i]

    def __setitem__(self, i, value):
        if not 0 <= i < self._size:
            raise IndexError("index out of range")
        self._check(value)
        self._buffer[i] = value

    def append(self, value):
        self._check(value)                      # type gate before anything
        if self._size == self._capacity:
            self._resize(2 * self._capacity)
        self._buffer[self._size] = value
        self._size += 1

    def _resize(self, new_capacity):
        new_buffer = self._make_buffer(new_capacity)
        for i in range(self._size):
            new_buffer[i] = self._buffer[i]
        self._buffer = new_buffer
        self._capacity = new_capacity

    def __iter__(self):
        for i in range(self._size):
            yield self._buffer[i]

    def __repr__(self):
        return (f"TypedArrayList[{self._type.__name__}]"
                f"([{', '.join(repr(x) for x in self)}])")


# --- tests for the typed version --------------------------------------

def test_typed_accepts_correct_type():
```

### Reading the results - the part that actually teaches

Three honest observations:

**1. Your `ArrayList` is ~10-15× slower than Python's `list`, and that's expected.** Both are O(1) amortized, same _asymptotic_ class, but Python's list is implemented in C, doing the resize/copy in a tight compiled loop, while yours does the resize copy in interpreted Python with per-iteration bytecode overhead. **Big-O measures growth rate, not absolute speed.** Two O(1)-amortized structures can differ by a constant factor of 10×, and the constant factor is exactly what the C implementation wins. The *scaling* is the same; the *constant* is not.

**2. Both scale linearly.** If you rerun with `n = 400_000`, both your time and the native time roughly **double**, not quadruple. That's the amortized-O(1)-per-append proof showing up empirically: total work for `n` appends is linear in `n`. If append were secretly O(n) each (like arithmetic growth would give you), doubling `n` would **4×** the time. It doesn't. The proof predicted linear total cost, and the stopwatch confirms it. That agreement between theory and measurement is the most satisfying part.

**3. The type check costs a real but constant amount.** `TypedArrayList` is consistently a bit slower than `ArrayList` because of the extra `isinstance` call on every append. It's a fixed per-element cost, so it doesn't change the O(1) classification, it just bumps the constant factor. Safety isn't free, but here it's cheap and bounded.

> **The meta-lesson to take away:** asymptotic complexity tells you how something _scales_; benchmarks tell you the _constant factor_. You need both. "It's O(1)" and "it's fast" are related but not the same claim, and a senior engineer keeps them straight.

## ⚠️ Common mistakes

The traps worth recognizing on sight, most of them easy to hit, and every one of them traces back to something in this chapter.

1. **Calling `list.insert(0, x)` (or `pop(0)`) inside a loop.** Each front-insert is O(n) because it shifts every element right; do it `n` times and you've built an accidental **O(n²)** algorithm that looks innocent. Building a list front-to-back this way is a classic "why is my code slow?" moment. Fix: append to the end and reverse once at the finish, or use `collections.deque`, which is O(1) at both ends. (Tie this straight back to the contiguity invariant: there are no gaps, so opening one at the front means moving everybody.)

2. **Confusing `size` with `capacity`.** `size` is how many elements the user has stored; `capacity` is how big the underlying buffer is. Reading `buffer[i]` for `size <= i < capacity` returns garbage/`None`, not "the next element." Length is `size`, never `capacity`. Mixing them up is the root of a whole family of bugs.

3. **Off-by-one in the shifting loops.** In `insert` you must iterate **backward** (`range(size, i, -1)`); going forward overwrites values you haven't moved yet and smears one element across the tail. In `delete` you iterate **forward** (`range(i, size-1)`). Get the direction or the bounds wrong and you silently corrupt data, and `<` vs `<=` in the bounds check (`i <= size` for insert, `i < size` for delete/index) is its own off-by-one minefield.

4. **Forgetting to clear the freed slot on delete.** After `delete`, set `buffer[size-1] = None`. If you only decrement `size` and leave the old object reference sitting in the now-unused slot, you keep that object alive (a memory leak) and risk reading a stale value if a later bug peeks past `size`. Shrink the logical view *and* drop the reference.

5. **Assuming `append` is O(1) in the worst case.** It's amortized O(1), not worst-case O(1). Any single append that triggers a resize is genuinely O(n). In a hard **real-time** system (audio, control loops) that occasional O(n) spike can blow a deadline, there, you pre-allocate to a known capacity so no resize ever fires mid-loop. "Amortized" is an average-over-a-sequence guarantee, not a per-call one.

6. **Growing by a constant instead of a factor.** "Add 10 slots when full" feels frugal but makes every resize cost grow linearly, summing to **O(n²)** total over `n` appends (the `1+2+...+n` series). You *must* grow geometrically (×2, ×1.5) to keep append amortized O(1). Frugal-looking growth is the single most expensive mistake here.

7. **Mutable default arguments.** Writing `def __init__(self, items=[])` shares **one** list across every instance that uses the default, mutating it in one object silently affects the next. Always use `items=None` then `if items is None: items = []` inside. Not array-specific, but it bites array-backed classes constantly.

8. **Trusting index bounds you didn't check.** Negative indices, `i == size` (one past the end), and indices into an empty array are the usual `IndexError` sources. Your `__getitem__` guards with `0 <= i < size`; native Python silently wraps negatives (`a[-1]`) which is a feature *until* an unexpected negative from a computation quietly reads the wrong end of your array.

## 💼 On the job / interview angle

Arrays are the single most common substrate in technical interviews, not because interviewers love arrays for their own sake, but because array problems cleanly test whether you can reason about **indices, in-place mutation, and time/space trade-offs** without hiding behind a library. If you can talk about contiguity, amortized cost, and O(1)-space pointer tricks fluently, you signal exactly the fundamentals this chapter built.

A few patterns are worth naming up front because they recur everywhere:

- **Two pointers.** Keep two indices walking the array, either from both ends toward the middle, or one slow + one fast. This turns many "find a pair / partition / dedup" problems from O(n²) (nested loops) into O(n) time and O(1) extra space. It is the highest-use array trick to internalize.
- **In-place / O(1) space.** Interviewers love asking you to do something "without allocating a new array." That forces you to mutate the buffer directly using index arithmetic, the locker math from the start of the chapter, applied under pressure.

Common questions and how to *reason* about each (the approach matters far more than the memorized answer):

1. **"Implement a dynamic array / why is `append` amortized O(1)?"** This is the chapter itself. Reason: a dynamic array is a fixed buffer plus `size`/`capacity`; on overflow you allocate a geometrically larger buffer and copy. The total copy cost over `n` appends is a doubling series `1+2+4+...+n < 2n`, so per-append cost is constant. Be ready to *prove* it (aggregate or banker's method) and to explain why constant growth would make it O(n²).

2. **"Two-Sum (find two numbers that add to a target)."** On an **unsorted** array, the O(n) answer is a hash map: for each `x`, check if `target - x` was already seen. On a **sorted** array, use **two pointers**: one at each end, move left-pointer right if the sum is too small, right-pointer left if too big, O(n) time, O(1) space. The interviewer is usually probing whether you notice that "sorted" unlocks the pointer approach.

3. **"Rotate an array right by k, in place."** The slick O(1)-space trick is the **triple reversal**: reverse the whole array, then reverse the first `k`, then reverse the rest. Each reversal is O(n) with two pointers, total O(n) time, no extra array. The reasoning to verbalize: reversing the whole thing puts the last `k` at the front but backwards; the two sub-reversals fix the order within each part. Don't forget `k %= n`.

4. **"Remove duplicates from a sorted array in place."** Two pointers again, slow + fast: `slow` marks the end of the deduped region, `fast` scans ahead; when `a[fast] != a[slow]`, advance `slow` and copy. Return `slow + 1` as the new length. O(n) time, O(1) space. The insight: because it's sorted, duplicates are adjacent, so you only ever compare neighbors.

5. **"Dutch National Flag (sort an array of 0s/1s/2s in one pass)."** Three pointers, `low`, `mid`, `high`. `mid` scans; swap 0s down to `low`, swap 2s up to `high`, leave 1s. One pass, O(n) time, O(1) space. This is the generalization of the partition step in quicksort, and interviewers use it to see if you can manage three moving indices without losing track of invariants ("everything left of `low` is 0, everything right of `high` is 2").

6. **"Move all zeros to the end, keeping order."** Slow/fast two pointers: `slow` is the write position for the next non-zero; `fast` scans; each non-zero gets written to `slow` and `slow` advances; finally fill the tail with zeros (or swap as you go). O(n) / O(1). Tests the same write-index discipline as dedup.

The meta-skill: when you see an array problem, ask "can two pointers or a single in-place pass replace a nested loop?" and "what does *sorted* (if given) buy you?" Get those two reflexes and most array interviews collapse into O(n)/O(1) solutions.

### Solutions

**1. Reverse in place, two pointers from both ends.**

```python
def reverse_in_place(a):
    lo, hi = 0, len(a) - 1
    while lo < hi:
        a[lo], a[hi] = a[hi], a[lo]   # swap the two ends
        lo += 1
        hi -= 1
    return a

assert reverse_in_place([1, 2, 3, 4, 5]) == [5, 4, 3, 2, 1]
assert reverse_in_place([1, 2]) == [2, 1]
assert reverse_in_place([]) == []
```

Each swap fixes two elements and the pointers close in; the loop runs `n/2` times. **O(n) time, O(1) space.** This swap-the-ends loop is the primitive that the rotate trick (Q6) is built from.

**2. Max and min in one pass.**

```python
def min_max(a):
    if not a:
        raise ValueError("empty array")
    lo = hi = a[0]                 # seed both with the first element
    for x in a[1:]:
        if x < lo:
            lo = x
        elif x > hi:               # elif: if x<lo it can't also be >hi
            hi = x
    return lo, hi

assert min_max([3, 1, 4, 1, 5, 9, 2, 6]) == (1, 9)
assert min_max([7]) == (7, 7)
```

One scan, two comparisons per element at most. **O(n) time, O(1) space.** Seeding with `a[0]` (not `0` or `inf`) keeps it correct for all-negative arrays.

**3. Move zeros to the end (stable).** Slow/fast two pointers.

```python
def move_zeros(a):
    slow = 0                       # next write position for a non-zero
    for fast in range(len(a)):
        if a[fast] != 0:
            a[slow], a[fast] = a[fast], a[slow]   # swap non-zero down
            slow += 1
    return a

assert move_zeros([0, 1, 0, 3, 12]) == [1, 3, 12, 0, 0]
assert move_zeros([0, 0, 0]) == [0, 0, 0]
assert move_zeros([1, 2, 3]) == [1, 2, 3]
```

`slow` always points just past the last placed non-zero; swapping preserves relative order of non-zeros and pushes zeros rightward. **O(n) time, O(1) space.**

**4. Remove duplicates from a sorted array.** Slow/fast, write-on-change.

```python
def dedup_sorted(a):
    if not a:
        return 0
    slow = 0                       # last index of the deduped region
    for fast in range(1, len(a)):
        if a[fast] != a[slow]:     # sorted => dupes are adjacent
            slow += 1
            a[slow] = a[fast]
    return slow + 1                # new logical length

a = [1, 1, 2, 2, 2, 3, 4, 4]
n = dedup_sorted(a)
assert n == 4
assert a[:n] == [1, 2, 3, 4]
```

Because the array is sorted, equal values are neighbors, so comparing `a[fast]` to `a[slow]` suffices. **O(n) time, O(1) space.** Elements past the returned length are leftover and ignored, exactly the `size` vs. `capacity` idea.

**5. Two-Sum on a sorted array, converging two pointers.**

```python
def two_sum_sorted(a, target):
    lo, hi = 0, len(a) - 1
    while lo < hi:
        s = a[lo] + a[hi]
        if s == target:
            return (lo, hi)
        elif s < target:
            lo += 1                # need a bigger sum -> raise the low end
        else:
            hi -= 1                # need a smaller sum -> lower the high end
    return None                    # no pair found

assert two_sum_sorted([1, 2, 4, 7, 11, 15], 15) == (2, 4)   # 4 + 11
assert two_sum_sorted([2, 3, 4], 6) == (0, 2)
assert two_sum_sorted([1, 2, 3], 100) is None
```

Sortedness makes the moves monotonic: if the sum is too small the only way to grow it is to raise `lo`; too big, lower `hi`. No pair is ever skipped. **O(n) time, O(1) space**, beating the O(n²) brute force and needing no hash map.

**6. Rotate right by k in place, triple reversal.**

```python
def _rev(a, lo, hi):
    while lo < hi:
        a[lo], a[hi] = a[hi], a[lo]
        lo += 1
        hi -= 1

def rotate_right(a, k):
    n = len(a)
    if n == 0:
        return a
    k %= n                         # k larger than n wraps around
    _rev(a, 0, n - 1)              # reverse the whole array
    _rev(a, 0, k - 1)             # reverse the first k
    _rev(a, k, n - 1)             # reverse the rest
    return a

assert rotate_right([1, 2, 3, 4, 5, 6, 7], 3) == [5, 6, 7, 1, 2, 3, 4]
assert rotate_right([1, 2, 3], 4) == [3, 1, 2]      # 4 % 3 == 1
assert rotate_right([1, 2], 0) == [1, 2]
```

Whole-reverse puts the last `k` at the front (but each block internally backwards); the two sub-reverses restore order within each block. Three O(n) passes → **O(n) time, O(1) space.** No second array, which is the point of the trick.

**7. Merge two sorted arrays.**

```python
def merge_sorted(a, b):
    i = j = 0
    out = []
    while i < len(a) and j < len(b):
        if a[i] <= b[j]:           # <= keeps it stable
            out.append(a[i]); i += 1
        else:
            out.append(b[j]); j += 1
    out.extend(a[i:])              # one of these is empty
    out.extend(b[j:])
    return out

assert merge_sorted([1, 3, 5], [2, 4, 6]) == [1, 2, 3, 4, 5, 6]
assert merge_sorted([], [1, 2]) == [1, 2]
assert merge_sorted([1, 1], [1]) == [1, 1, 1]
```

Walk both with two indices, always taking the smaller front element. **O(n + m) time** and **O(n + m) space** for the output (this is the merge step of merge sort). Each element is examined once.

**8. Fixed-size ring buffer.** A flat array plus `head`, `count`; indices wrap with modulo. This version **rejects** pushes when full (stated choice).

```python
class RingBuffer:
    def __init__(self, capacity):
        if capacity < 1:
            raise ValueError("capacity must be >= 1")
        self._buf = [None] * capacity
        self._cap = capacity
        self._head = 0             # index of the oldest element
        self._count = 0            # how many elements are stored

    def __len__(self):
        return self._count

    def is_full(self):
        return self._count == self._cap

    def push(self, x):
        if self.is_full():
            raise OverflowError("ring buffer is full")
        tail = (self._head + self._count) % self._cap   # next free slot
        self._buf[tail] = x
        self._count += 1

    def pop(self):                 # remove & return the oldest (FIFO)
        if self._count == 0:
            raise IndexError("pop from empty buffer")
        x = self._buf[self._head]
        self._buf[self._head] = None
        self._head = (self._head + 1) % self._cap        # advance, wrapping
        self._count -= 1
        return x

rb = RingBuffer(3)
rb.push(1); rb.push(2); rb.push(3)
assert len(rb) == 3 and rb.is_full()
assert rb.pop() == 1               # FIFO: oldest out first
rb.push(4)                         # reuses the slot 1 just vacated (wraps)
assert [rb.pop(), rb.pop(), rb.pop()] == [2, 3, 4]
```

`push` and `pop` each do a constant amount of work, one modulo, one write. **O(1) time each, O(capacity) space total**, with no shifting ever, because the modulo lets the logical front/back wander around the fixed physical array. This is how OS keyboard buffers and audio queues are built.

**9. Amortized cost for 1.5× growth.** Same shape of proof as doubling, different ratio. Starting from capacity 1 and multiplying by 1.5 each resize, the sizes copied across `n` appends form a geometric series with ratio `r = 1.5`, largest term `≈ n`:

```
total copies = ... + n/1.5^2 + n/1.5 + n
             = n * (1 + 1/1.5 + 1/1.5^2 + ...)
             < n * (1 / (1 - 1/1.5))      [infinite geometric sum, |ratio|<1]
             = n * (1 / (1 - 0.667))
             = n * (1 / 0.333)
             = 3n
```

So total copying is `< 3n`, plus `n` cheap writes = `< 4n` total work over `n` appends → **`< 4` per append = O(1) amortized.** The general fact: for any growth factor `g > 1`, the copy total is `n · g/(g-1)`, a finite constant times `n`. With `g = 2` that constant is `2`; with `g = 1.5` it's `3`. Smaller `g` → more copying (bigger constant) but less wasted memory, the real engineering knob. Any `g > 1` keeps append amortized O(1); only `g = 1` (constant growth) breaks it into O(n²).

## 🧪 Extra practice - a 2D matrix stored in a flat 1D array

The chapter's mini-project was a typed dynamic array + benchmark. Here's a different one that hammers the **index-arithmetic** idea from the very start of the chapter: a 2D grid (matrix) that's secretly stored as a single flat 1D array. This is exactly how real numerical libraries (NumPy, BLAS) lay out matrices in memory, there is no "array of arrays" underneath, just one contiguous block plus arithmetic to translate `(row, col)` into a flat offset.

The key formula is **row-major order**:

```
flat_index(i, j) = i * cols + j
```

Read it back to the locker picture: lay all the rows end to end in one hallway. Row 0 occupies lockers `0 .. cols-1`, row 1 occupies `cols .. 2*cols-1`, and so on. To reach `(i, j)` you skip `i` whole rows (`i * cols` lockers) then step `j` into the current row. One multiply, one add, the same O(1) jump as 1D indexing, just with the offset computed from two coordinates.

```python
class Matrix:
    """A 2D matrix backed by ONE flat 1D list, row-major.

    INVARIANTS:
      1. len(self._data) == self.rows * self.cols   (exactly, always)
      2. element (i, j) lives at flat index i*cols + j
      3. 0 <= i < rows and 0 <= j < cols for every valid access
    """

    def __init__(self, rows, cols, fill=0):
        if rows < 0 or cols < 0:
            raise ValueError("dimensions must be non-negative")
        self.rows = rows
        self.cols = cols
        self._data = [fill] * (rows * cols)   # one flat block, not rows of lists

    def _index(self, i, j):
        if not (0 <= i < self.rows and 0 <= j < self.cols):
            raise IndexError(f"({i}, {j}) out of bounds "
                             f"for {self.rows}x{self.cols} matrix")
        return i * self.cols + j              # THE row-major formula

    def get(self, i, j):
        return self._data[self._index(i, j)]

    def set(self, i, j, value):
        self._data[self._index(i, j)] = value

    # support m[i, j] and m[i, j] = v as syntactic sugar
    def __getitem__(self, ij):
        i, j = ij
        return self.get(i, j)

    def __setitem__(self, ij, value):
        i, j = ij
        self.set(i, j, value)

    def row(self, i):
        """Return row i as a list. Contiguous slice of the flat buffer."""
        if not 0 <= i < self.rows:
            raise IndexError("row out of range")
        start = i * self.cols
        return self._data[start:start + self.cols]

    def col(self, j):
        """Return column j as a list. NON-contiguous: strided access."""
        if not 0 <= j < self.cols:
            raise IndexError("col out of range")
        return [self._data[i * self.cols + j] for i in range(self.rows)]

    def transpose(self):
        """Return a new Matrix with rows and cols swapped."""
        t = Matrix(self.cols, self.rows)
        for i in range(self.rows):
            for j in range(self.cols):
                t[j, i] = self[i, j]
        return t

    def __eq__(self, other):
        return (isinstance(other, Matrix)
                and self.rows == other.rows
                and self.cols == other.cols
                and self._data == other._data)

    def __repr__(self):
        lines = []
        for i in range(self.rows):
            lines.append("  " + " ".join(f"{x:>3}" for x in self.row(i)))
        return f"Matrix {self.rows}x{self.cols}:\n" + "\n".join(lines)


# --- tests with expected output --------------------------------------

def test_matrix():
    m = Matrix(2, 3)                 # 2 rows, 3 cols, all zeros
    assert m.rows == 2 and m.cols == 3
    assert len(m._data) == 6         # invariant 1: flat length = rows*cols

    # The flat-index formula, checked by hand:
    assert m._index(0, 0) == 0
    assert m._index(0, 2) == 2
    assert m._index(1, 0) == 3       # skipped 1 full row of 3
    assert m._index(1, 2) == 5

    # set / get via sugar
    m[0, 0] = 1
    m[0, 1] = 2
    m[0, 2] = 3
    m[1, 0] = 4
    m[1, 1] = 5
    m[1, 2] = 6
    assert m[1, 1] == 5
    assert m.row(1) == [4, 5, 6]
    assert m.col(2) == [3, 6]

    # transpose: 2x3 -> 3x2
    t = m.transpose()
    assert t.rows == 3 and t.cols == 2
    assert t.row(0) == [1, 4]
    assert t[2, 1] == 6              # was m[1, 2]

    # bounds checking
    try:
        m[2, 0]                      # row 2 doesn't exist (rows are 0,1)
        assert False, "expected IndexError"
    except IndexError:
        pass

    print("Matrix tests passed ✅")
    print(m)
    print("transpose:")
    print(t)


if __name__ == "__main__":
    test_matrix()
```

Two things this drives home. First, **a 2D structure is a 1D array plus arithmetic**, there's no special "2D memory," just `i*cols + j`. Second, the contiguity asymmetry is real and measurable: `row(i)` is a single contiguous slice (cache-friendly, fast), while `col(j)` jumps `cols` slots between every read (strided, cache-hostile). On large matrices, iterating row-by-row can be several times faster than column-by-column purely because of how the flat buffer sits in cache, the exact same "contiguity is the whole game" lesson from page one, now visible in two dimensions.
