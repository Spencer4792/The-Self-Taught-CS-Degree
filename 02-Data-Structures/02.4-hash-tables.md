## Why this one matters

If you remember only one data structure from this whole book under pressure in an interview, make it this one. Hash tables are the workhorse of practically every program you've ever written. Every Python `dict`, every `set`, every JavaScript object, every database index, every compiler's symbol table, every cache: hash tables underneath them all.

The promise is almost too good to believe: **average-case O(1)** insertion, lookup, and deletion. Constant time: ten keys or ten million, looking one up takes about the same amount of work. Arrays give you O(1) access *if you already know the integer index*. Hash tables give you O(1) access *by arbitrary key* (a string, a tuple, whatever), which feels like cheating.

But "average-case O(1)" hides a lot. The worst case is O(n). Whether you live in the happy world or the sad world depends entirely on the quality of your **hash function** and how you handle **collisions**. So that's the whole chapter: hash functions, collisions, two strategies for resolving them, and the math that tells us when O(1) holds and when it betrays us.

Let's build the intuition before any code.

---

## Start here: the coat-check analogy

Before touching a single formula, let's make this concrete.

Picture a theater coat-check. The naive way to run it: a giant pile of coats in a back room. When you hand in your coat, an attendant tosses it on the pile. When you come back, the attendant has to dig through the *whole pile* looking for yours. With 500 coats, that's a slog every single time. That's a list (or an unsorted array): to find something, you scan everything. O(n).

Now picture a smarter coat-check. There are 50 numbered hooks on the wall. When you hand in your coat, the attendant looks at your ticket number, say 4792, does a tiny bit of arithmetic (4792 mod 50 = 42) and hangs your coat on hook 42. No searching, no judgment about where it "should" go: the formula decided. When you come back, the attendant runs the same formula on the same ticket, gets 42 again, and walks straight to hook 42. Whether there are 50 coats or 50,000, finding yours takes the same amount of work, because the formula points right at the spot.

That formula, "take the key, do a little arithmetic, get a shelf number", is the **hash function**. The hooks are the **buckets**. That's the entire idea of a hash table: *instead of searching for where something is, you compute where it must be.*

A library works the same way. With no system, finding one book means walking every shelf. With the Dewey Decimal system, a formula maps the book's subject to an exact shelf location: you compute the address and walk straight there. You never search; you calculate.

O(1)-by-key lookup matters so much in practice because the questions you ask a computer constantly are lookups by name, not by position:

- "Is the username `spencer` already taken?" Look it up by the string, not by scanning a list.
- "What's the price of product SKU `A4792`?" Jump straight to it.
- "Have I seen this IP address before?" An instant membership test.
- "How many times does the word `the` appear?" Find the counter for `the` and bump it.

With a list, every one of those is "walk the whole thing and compare each item", O(n), and it gets slower as the data grows. With a hash table, each is "compute the address, look", O(1), flat no matter how big it gets. That flatness is the point. A million users, a billion log lines: a well-built hash table doesn't care. The cost of a lookup stays roughly constant.

The catch, and it's the rest of the chapter, is that two different tickets can produce the same hook number. Ticket 4792 and ticket 92 both give 42 under "mod 50." When that happens it's called a **collision**, and how we handle it is what separates a toy from a real data structure. But hold onto the coat-check picture: a formula tells you exactly where to look, so you never have to search. Everything below makes that picture robust and provably fast.

## The core idea: turn a key into an address

Imagine you have an array of `m` slots (call them **buckets**). You want to store key-value pairs. The trick is a function `h` that takes a key and spits out an integer in `[0, m)`. That integer is the bucket index. To store `(key, value)`, you compute `h(key)` and drop the pair in that bucket. To look it up later, you compute `h(key)` again (it's deterministic, so you get the same index) and read the bucket.

```
key  ──► hash function h ──► big integer ──► mod m ──► bucket index ──► array slot
```

If `h` distributes keys evenly and rarely sends two keys to the same bucket, every operation is just "compute a hash, index into an array", and both of those are O(1). Everything else in this chapter is a fight with the cases where two keys land in the same bucket.

Two separate jobs hide in there:

1. **Hashing**: turn an arbitrary key (string, int, tuple) into a big integer. This is `hash(key)` in Python.
2. **Compression**: map that big integer down into `[0, m)`. Usually this is `hash(key) % m`.

Keep these mentally separate because they fail for different reasons.

---

## What makes a good hash function?

A hash function `h(key) -> int` should satisfy four properties. Let's write them down and reason about each, because every one maps onto a real failure mode.

**1. Deterministic.** Same input → same output, every single time, within one run of the program. If `h("cat")` returned a different number on the second call, you could store a value but never find it again. This sounds obvious but it has a subtle wrinkle: it only has to be stable *within a single process run*. Python deliberately breaks it *across runs* (more on that in a second).

**2. Uniform distribution.** Outputs should spread evenly across the range. If your hash sends 90% of keys to bucket 0, you've effectively built a linked list with extra steps. Formally, the ideal is **simple uniform hashing**: each key is equally likely to land in any of the `m` buckets, independent of where other keys land. We almost never achieve this perfectly, but a good hash gets close for typical inputs.

**3. Fast.** We compute the hash on *every* operation. If hashing is slow, the constant factor in our "O(1)" balloons and the whole point is lost. A hash that takes O(length-of-key) is fine, that's unavoidable, since you have to look at the whole key, but it should be a tight pass over the bytes, nothing fancier.

**4. Avalanche.** A tiny change in the input (flip one bit, change one character) should change roughly half the output bits, unpredictably. Without avalanche, similar keys like `"user1"`, `"user2"`, `"user3"` produce similar hashes that, after `% m`, cluster into nearby buckets. Avalanche is what makes the output *look* random even though it's fully deterministic.

### A first stab: why naive hashes are terrible

Let's hash a string the dumb way, summing the character codes, to see why we need something better.

```python
def bad_hash(s: str) -> int:
    return sum(ord(c) for c in s)

print(bad_hash("listen"))  # 649
print(bad_hash("silent"))  # 649  -- collision!
print(bad_hash("abc"))     # 294
print(bad_hash("cba"))     # 294  -- order ignored!
```

Summing throws away *order*, so every anagram collides. It also produces a small range (a 10-character ASCII string maxes out around 1270), so after `% m` everything jams into the low buckets. No avalanche, no uniformity. Useless. This is the cautionary baseline.

---

## A real hash: polynomial rolling hash

The fix for the order problem is to weight each character by its position using powers of a base `b`. This is the **polynomial hash**, and it's the same idea behind Java's `String.hashCode()` and Rabin-Karp string matching.

For a string `s = s₀ s₁ s₂ … s_{k-1}`, define:

```
h(s) = s₀·b^(k-1) + s₁·b^(k-2) + … + s_{k-1}·b^0
```

Equivalently, evaluated with Horner's method (which is how you'd actually compute it):

```
h = 0
for each character c:
    h = h · b + ord(c)
```

Why this works: multiplying the running total by `b` *shifts* all previous contributions up by one "digit," so position matters: `"abc"` and `"cba"` now differ. Choosing `b` as a prime-ish odd number (31 is the classic; we'll use 31) spreads things out and gives decent avalanche. We also reduce modulo a large prime or just let it grow and `% m` at the end.

### Build it: a polynomial string hash from scratch

```python
def poly_hash(s: str, base: int = 31, mod: int = 2**61 - 1) -> int:
    """Polynomial rolling hash. mod is a large Mersenne prime to keep
    the number bounded and to mix bits well."""
    h = 0
    for c in s:
        h = (h * base + ord(c)) % mod
    return h

# Anagrams no longer collide:
print(poly_hash("listen"))  # some big number
print(poly_hash("silent"))  # a DIFFERENT big number
print(poly_hash("abc") != poly_hash("cba"))  # True

# Avalanche check: one-character change moves the hash a lot.
print(poly_hash("user1"))
print(poly_hash("user2"))   # wildly different, not "+1"
```

Let's quick-test that it's deterministic and order-sensitive:

```python
def test_poly_hash():
    # deterministic
    assert poly_hash("hello") == poly_hash("hello")
    # order-sensitive (fixes the anagram bug)
    assert poly_hash("abc") != poly_hash("cba")
    assert poly_hash("listen") != poly_hash("silent")
    # nonnegative and bounded
    assert 0 <= poly_hash("anything") < 2**61 - 1
    print("poly_hash tests passed ✓")

test_poly_hash()
```

That's your hash function. Notice it's kept as a free function; the hash table could use `poly_hash` for strings, but in real code you'd defer to Python's built-in `hash()` so the table works for ints, tuples, and any hashable type. We built `poly_hash` so you understand what `hash()` is doing under the hood: it's a fast, deterministic, avalanching map from key to big integer.

### The compression step, and why we `% m`

The hash is a giant integer. Your array has `m` buckets. You need to fold the giant integer into `[0, m)`. The standard move is `hash(key) % m`.

Why modulo? Because `% m` partitions all integers into `m` residue classes, and if the hash bits are well-mixed (avalanche!), those classes are hit roughly uniformly. A subtle gotcha: if `m` is a power of two, `hash % m` only keeps the **low-order bits** of the hash. If your hash function has weak low bits, you get clustering. That's why the classic textbook advice is to make `m` prime: a prime modulus uses information from all the bits. (Python's `dict` uses power-of-two tables but compensates with a clever perturbation scheme. We'll get there.)

### Why Python randomizes string hashing

Try this in two separate Python runs:

```python
# Run 1: $ python3 -c "print(hash('hello'))"
#  ->  4471074340315749979
# Run 2: $ python3 -c "print(hash('hello'))"
#  ->  -892374610293847562   (different!)
```

`hash("hello")` changes between runs. That violates "deterministic"... across runs. Within a single run it's perfectly stable, which is all a `dict` needs. The cross-run randomization (controlled by `PYTHONHASHSEED`) is a security feature. Without it, an attacker who knows your hash function can craft thousands of keys that *all* hash to the same bucket, collapsing your O(1) dict into an O(n) linked list and DoS-ing your web server with one malicious request, a "hash flooding" attack. Randomizing the seed per process makes those collision sets unpredictable. The lesson: hashing for data structures and hashing for security overlap, and Python takes the safe default.

## Collisions are not bad luck: they're guaranteed

Collisions are mathematically inevitable: two distinct keys will hash to the same bucket. Two arguments prove it.

### Pigeonhole principle

You have infinitely many possible keys (all strings) but only `m` buckets. By the **pigeonhole principle**: if you put `n` pigeons into `m` holes and `n > m`, at least one hole has ≥ 2 pigeons. Since the universe of keys vastly exceeds `m`, some keys *must* share a bucket. There is no hash function that avoids this for all inputs. Collision resolution isn't optional polish; it's the core of the data structure.

### The birthday paradox: collisions come fast

Worse, collisions show up much earlier than intuition suggests. The **birthday paradox**: in a room of just 23 people, there's a >50% chance two share a birthday, even though there are 365 possible days. The reason is that we're comparing pairs: with `n` people there are `n(n-1)/2` pairs, and that count grows quadratically.

Same math for hash tables. With `m` buckets, the expected number of insertions before the first collision is only about `√(π·m/2)` ≈ `1.25·√m`. So a table with `m = 1,000,000` buckets gets its first collision after roughly **1,250 insertions**, not 500,000. Collisions aren't a rare edge case to handle eventually; they start almost immediately and never stop. Our strategy has to make them cheap.

So: two well-known strategies. **Separate chaining** (each bucket holds a list of all colliding entries) and **open addressing** (collisions spill into *other* buckets in the same array). We'll build both.

## Build it: Strategy 1 - Separate Chaining

The idea: each bucket holds a small list (a "chain") of `(key, value)` pairs that hashed there. To look up a key, hash to the bucket, then scan its short list. If the hash is good, chains stay tiny, length ~1 on average, so the scan is O(1) expected.

Let's design the invariants first, because writing them down keeps us honest:

> **Invariants of the chaining HashMap**
> 1. Every key appears in exactly one bucket, namely `hash(key) % capacity`.
> 2. Within a bucket, each key appears at most once (no duplicate keys).
> 3. `_size` equals the total number of `(key, value)` pairs across all buckets.
> 4. After any operation, load factor `_size / capacity ≤ MAX_LOAD`, if it would exceed, we resize.

Here's the full implementation.

```python
class ChainingHashMap:
    """A hash map using separate chaining. Each bucket is a Python list
    of [key, value] pairs. Built from scratch - no dict inside."""

    def __init__(self, initial_capacity: int = 8, max_load: float = 0.75):
        self._capacity = initial_capacity
        self._max_load = max_load
        self._size = 0
        # Each bucket is a list of [key, value] pairs.
        self._buckets: list[list] = [[] for _ in range(self._capacity)]

    # --- internal helpers ------------------------------------------------

    def _bucket_index(self, key) -> int:
        # Use Python's hash() so any hashable key works, then compress.
        return hash(key) % self._capacity

    def _load_factor(self) -> float:
        return self._size / self._capacity

    def _resize(self, new_capacity: int) -> None:
        """Allocate a bigger table and re-insert every pair. Buckets
        are recomputed because capacity (the modulus) changed."""
        old_buckets = self._buckets
        self._capacity = new_capacity
        self._buckets = [[] for _ in range(new_capacity)]
        self._size = 0
        for bucket in old_buckets:
            for key, value in bucket:
                self.put(key, value)  # re-hashes against new capacity

    # --- public API ------------------------------------------------------

    def put(self, key, value) -> None:
        idx = self._bucket_index(key)
        bucket = self._buckets[idx]
        # If key already present, update in place (invariant 2).
        for pair in bucket:
            if pair[0] == key:
                pair[1] = value
                return
        bucket.append([key, value])
        self._size += 1
        # Maintain invariant 4: resize when too full.
        if self._load_factor() > self._max_load:
            self._resize(self._capacity * 2)

    def get(self, key, default=None):
        idx = self._bucket_index(key)
        for k, v in self._buckets[idx]:
            if k == key:
                return v
        return default

    def delete(self, key) -> None:
        idx = self._bucket_index(key)
        bucket = self._buckets[idx]
        for i, (k, _) in enumerate(bucket):
            if k == key:
                bucket.pop(i)
                self._size -= 1
                return
        raise KeyError(key)

    def __contains__(self, key) -> bool:
        idx = self._bucket_index(key)
        return any(k == key for k, _ in self._buckets[idx])

    def __len__(self) -> int:
        return self._size

    def items(self):
        for bucket in self._buckets:
            for k, v in bucket:
                yield (k, v)

    def keys(self):
        return (k for k, _ in self.items())

    def values(self):
        return (v for _, v in self.items())

    # Make it feel like a dict.
    def __getitem__(self, key):
        sentinel = object()
        result = self.get(key, sentinel)
        if result is sentinel:
            raise KeyError(key)
        return result

    def __setitem__(self, key, value):
        self.put(key, value)

    def __repr__(self):
        pairs = ", ".join(f"{k!r}: {v!r}" for k, v in self.items())
        return f"ChainingHashMap({{{pairs}}})"
```

A few design notes worth remembering:

- Pairs are stored as mutable **lists** `[key, value]` (not tuples) so you can update a value in place without rebuilding the entry.
- `_resize` doesn't just copy buckets, it *re-hashes everything*, because the bucket index depends on `capacity`, which just changed. This is the expensive-but-rare operation whose cost we'll amortize below.
- `put` checks for an existing key first so updating `d[k] = newval` doesn't grow `_size` or create duplicates (invariant 2).

### Tests for chaining

```python
def test_chaining():
    m = ChainingHashMap(initial_capacity=4)

    # basic put/get
    m.put("a", 1)
    m.put("b", 2)
    m.put("c", 3)
    assert m.get("a") == 1
    assert m.get("b") == 2
    assert m.get("missing") is None
    assert m.get("missing", -1) == -1

    # update existing key doesn't grow size
    m.put("a", 99)
    assert m.get("a") == 99
    assert len(m) == 3

    # __contains__ and __len__
    assert "a" in m
    assert "z" not in m
    assert len(m) == 3

    # delete
    m.delete("b")
    assert "b" not in m
    assert len(m) == 2
    try:
        m.delete("b")
        assert False, "expected KeyError"
    except KeyError:
        pass

    # dict-style access
    m["x"] = 42
    assert m["x"] == 42

    # force several resizes and confirm nothing is lost
    big = ChainingHashMap(initial_capacity=2)
    for i in range(1000):
        big.put(f"key{i}", i)
    assert len(big) == 1000
    for i in range(1000):
        assert big.get(f"key{i}") == i
    # every key landed in its correct bucket (invariant 1)
    for i in range(1000):
        assert f"key{i}" in big

    # items() round-trips
    pairs = dict(big.items())
    assert len(pairs) == 1000
    assert pairs["key500"] == 500

    print("ChainingHashMap tests passed ✓")

test_chaining()
```

When you run this, all assertions pass. The 1000-key loop is the important one: it forces the table to resize many times (2 → 4 → 8 → … → 2048) and proves that re-hashing preserves every entry.

### Traced walkthrough - buckets filling and a resize

The tests prove it works; now let's watch it work. Here's a hand-trace of a tiny chaining table, capacity 4, `max_load = 0.75` (so we resize once `_size / capacity > 0.75`, i.e. once we'd hold more than 3 entries in 4 buckets). To make the trace reproducible instead of leaning on Python's randomized string hashing, we'll use *integer* keys, whose hash in CPython is just the integer itself. Then `bucket = key % capacity` is something you can compute in your head.

Insert, in order: `put(10, "a")`, `put(22, "b")`, `put(31, "c")`, `put(14, "d")`.

**Start:** empty table, capacity 4, size 0.

```
index:   0      1      2      3
       [ ]    [ ]    [ ]    [ ]
```

**`put(10, "a")`** → `10 % 4 = 2`. Bucket 2 is empty, append. size = 1, load = 1/4 = 0.25 (fine).

```
index:   0      1      2              3
       [ ]    [ ]    [ (10,a) ]     [ ]
```

**`put(22, "b")`** → `22 % 4 = 2`. Bucket 2 already holds `(10,a)`. Different key, so this is a **collision**, append to the same chain. size = 2, load = 0.50 (fine).

```
index:   0      1      2                       3
       [ ]    [ ]    [ (10,a) -> (22,b) ]    [ ]
```

Notice both `10` and `22` live in bucket 2, chained together. A lookup of `22` hashes to bucket 2, scans the chain `(10,a)` (key mismatch), then `(22,b)` (match). Two comparisons, still tiny.

**`put(31, "c")`** → `31 % 4 = 3`. Bucket 3 is empty, append. size = 3, load = 3/4 = 0.75. The condition is `load > 0.75`, and 0.75 is *not* greater than 0.75, so no resize yet.

```
index:   0      1      2                       3
       [ ]    [ ]    [ (10,a) -> (22,b) ]    [ (31,c) ]
```

**`put(14, "d")`** → `14 % 4 = 2`. Another collision in bucket 2, append. size = 4, load = 4/4 = 1.0. Now `1.0 > 0.75`, so we **resize**: new capacity `4 * 2 = 8`, and we re-insert every pair against the *new* modulus.

State *just before* the resize fires (the offending insert has landed, the threshold check now triggers):

```
index:   0      1      2                                   3
       [ ]    [ ]    [ (10,a) -> (22,b) -> (14,d) ]      [ (31,c) ]
```

Now the rehash. Every key gets `key % 8` instead of `key % 4`. This is the part you must never shortcut by copying buckets, the modulus changed, so *home buckets move*:

- `10 % 8 = 2`  → bucket 2
- `22 % 8 = 6`  → bucket 6  (was bucket 2 under mod 4, it relocated!)
- `14 % 8 = 6`  → bucket 6  (collides with 22 in the new table)
- `31 % 8 = 7`  → bucket 7  (was bucket 3, relocated)

Final table after resize, capacity 8, size 4, load = 4/8 = 0.5:

```
index:   0     1     2            3     4     5     6                       7
       [ ]   [ ]   [ (10,a) ]   [ ]   [ ]   [ ]   [ (22,b) -> (14,d) ]   [ (31,c) ]
```

Two things to notice. First, `22` and `14` shared bucket 2 with `10` under mod 4, but after the resize they sit together in bucket 6 while `10` stays alone in bucket 2. The collision structure completely reshuffled, which is why a resize must rehash rather than copy. Second, doubling capacity roughly halved the load factor (1.0 → 0.5), which buys us headroom before the next resize. That's the engine behind amortized O(1), which we'll prove with a sum later.

### Traced walkthrough - linear probing with a collision

Open addressing has no chains, so a trace looks different: a collision doesn't grow a list, it *walks to the next slot*. Let's trace `OpenAddressingHashMap` with capacity 8, again with integer keys so you can compute `key % 8` by hand. Insert `put(5,"a")`, `put(13,"b")`, `put(21,"c")`.

**`put(5,"a")`** → home `5 % 8 = 5`. Slot 5 is EMPTY, drop it there.

```
index:   0     1     2     3     4     5          6     7
       [ E ] [ E ] [ E ] [ E ] [ E ] [ (5,a) ] [ E ] [ E ]
```

**`put(13,"b")`** → home `13 % 8 = 5`. Slot 5 is occupied by a *different* key (5 ≠ 13), collision. Probe forward: slot 6 is EMPTY, land there.

```
index:   0     1     2     3     4     5          6           7
       [ E ] [ E ] [ E ] [ E ] [ E ] [ (5,a) ] [ (13,b) ] [ E ]
```

**`put(21,"c")`** → home `21 % 8 = 5`. Slot 5 occupied (key 5, no match) → probe to 6, occupied (key 13, no match) → probe to 7, EMPTY → land there. That's three probes for one insert; this is **primary clustering** forming, a run of consecutive filled slots that lengthens every future probe starting anywhere inside it.

```
index:   0     1     2     3     4     5          6           7
       [ E ] [ E ] [ E ] [ E ] [ E ] [ (5,a) ] [ (13,b) ] [ (21,c) ]
```

Now watch deletion break a naive implementation, then watch tombstones fix it. **`delete(13)`** the *middle* of the run. If you set slot 6 to EMPTY:

```
index:   ...   5          6        7
             [ (5,a) ] [ E ]    [ (21,c) ]      <-- WRONG approach
```

Then `get(21)`: home 5 (key 5, no match) → probe 6 → **EMPTY**, so you conclude "chain ended, 21 isn't here" and return `None`. But 21 *is* in slot 7. The empty slot severed the probe path. The fix is a **tombstone** (`D` = DELETED): searches treat it as "keep probing," inserts treat it as "reusable."

```
index:   ...   5          6        7
             [ (5,a) ] [ D ]    [ (21,c) ]      <-- correct: tombstone
```

Now `get(21)`: home 5 (no match) → 6 is a tombstone (keep probing) → 7 (match!). Correct. This is the single subtlest thing about open addressing, and tracing it once is the best way to remember why it matters.

## Build it: Strategy 2 - Open Addressing (linear probing)

Chaining is simple but it stores a separate list object per non-empty bucket, which costs memory and pointer-chasing (bad for CPU caches). **Open addressing** keeps everything in one flat array: when a key's home bucket is occupied by a *different* key, we **probe**: walk to other slots by a fixed rule until we find an empty one.

The simplest rule is **linear probing**: try `h(key)`, then `h(key)+1`, `h(key)+2`, … (all mod `m`) until we hit an empty slot.

```
probe sequence:  h, h+1, h+2, h+3, ...   (mod m)
```

### The deletion problem and tombstones

Deletion is sneaky here. Suppose `A`, `B`, `C` all hash to slot 5. Linear probing puts `A`@5, `B`@6, `C`@7. Now you delete `B` and set slot 6 to empty. Later you search for `C`: you hash to 5 (occupied by A, not C), probe to 6 (now empty!), and conclude `C` isn't in the table. Wrong: the empty slot broke the probe chain.

Fix: when deleting, don't mark the slot truly empty, mark it a **tombstone** (`DELETED`). Searches treat tombstones as "keep probing, this slot was used"; insertions treat them as "free, you can reuse me." We just have to distinguish three slot states: `EMPTY`, `DELETED`, and occupied.

> **Invariants of the open-addressing HashMap**
> 1. A key, if present, sits somewhere along its probe sequence starting at `hash(key) % capacity`, with no truly-`EMPTY` slot between its home and its actual slot.
> 2. `_size` counts only live (non-tombstone, non-empty) entries.
> 3. Load factor accounting includes tombstones (they occupy space and lengthen probes), so we resize on `(_size + _tombstones) / capacity`.
> 4. We keep load factor well below 1 (e.g. ≤ 0.5-0.7); open addressing degrades sharply as it fills.

```python
class _Empty:
    """Sentinel for a never-used slot. Search stops here."""
    __slots__ = ()
    def __repr__(self): return "EMPTY"

class _Deleted:
    """Tombstone: a slot whose entry was removed. Search continues
    past it; insert may reuse it."""
    __slots__ = ()
    def __repr__(self): return "DELETED"

EMPTY = _Empty()
DELETED = _Deleted()


class OpenAddressingHashMap:
    """Hash map using open addressing with linear probing and tombstones.
    Everything lives in one flat array of [key, value] slots."""

    def __init__(self, initial_capacity: int = 8, max_load: float = 0.6):
        self._capacity = initial_capacity
        self._max_load = max_load
        self._size = 0          # live entries
        self._tombstones = 0    # deleted-but-not-reclaimed slots
        self._slots = [EMPTY] * self._capacity

    def _home(self, key) -> int:
        return hash(key) % self._capacity

    def _load_factor(self) -> float:
        # Tombstones count: they still cost probes.
        return (self._size + self._tombstones) / self._capacity

    def _resize(self, new_capacity: int) -> None:
        old = self._slots
        self._capacity = new_capacity
        self._slots = [EMPTY] * new_capacity
        self._size = 0
        self._tombstones = 0      # resizing purges tombstones for free
        for slot in old:
            if slot is not EMPTY and slot is not DELETED:
                self.put(slot[0], slot[1])

    def put(self, key, value) -> None:
        # Resize BEFORE inserting if we'd cross the threshold, so there's
        # always an empty slot to land in (probing must terminate).
        if self._load_factor() > self._max_load:
            self._resize(self._capacity * 2)

        idx = self._home(key)
        first_tombstone = None
        for _ in range(self._capacity):
            slot = self._slots[idx]
            if slot is EMPTY:
                # Key not present. Reuse an earlier tombstone if we passed one.
                target = first_tombstone if first_tombstone is not None else idx
                self._slots[target] = [key, value]
                self._size += 1
                if first_tombstone is not None:
                    self._tombstones -= 1
                return
            if slot is DELETED:
                if first_tombstone is None:
                    first_tombstone = idx
            elif slot[0] == key:
                slot[1] = value   # update in place
                return
            idx = (idx + 1) % self._capacity
        # Should be unreachable because we keep load factor < 1.
        raise RuntimeError("hash table full - resize logic broken")

    def get(self, key, default=None):
        idx = self._home(key)
        for _ in range(self._capacity):
            slot = self._slots[idx]
            if slot is EMPTY:
                return default            # stop: probe chain ended
            if slot is not DELETED and slot[0] == key:
                return slot[1]
            idx = (idx + 1) % self._capacity
        return default

    def delete(self, key) -> None:
        idx = self._home(key)
        for _ in range(self._capacity):
            slot = self._slots[idx]
            if slot is EMPTY:
                raise KeyError(key)
            if slot is not DELETED and slot[0] == key:
                self._slots[idx] = DELETED   # tombstone, not EMPTY!
                self._size -= 1
                self._tombstones += 1
                return
            idx = (idx + 1) % self._capacity
        raise KeyError(key)

    def __contains__(self, key) -> bool:
        sentinel = object()
        return self.get(key, sentinel) is not sentinel

    def __len__(self) -> int:
        return self._size

    def items(self):
        for slot in self._slots:
            if slot is not EMPTY and slot is not DELETED:
                yield (slot[0], slot[1])

    def __getitem__(self, key):
        sentinel = object()
        result = self.get(key, sentinel)
        if result is sentinel:
            raise KeyError(key)
        return result

    def __setitem__(self, key, value):
        self.put(key, value)
```

The fiddly bit is in `put`: you scan for the key (to update it) but *remember the first tombstone you saw*. If you reach an `EMPTY` slot without finding the key, the key isn't present, so you insert it, preferably reusing that earlier tombstone to reclaim space. This keeps tombstones from accumulating forever.

```python
def test_open_addressing():
    m = OpenAddressingHashMap(initial_capacity=8)

    m.put("a", 1)
    m.put("b", 2)
    m.put("c", 3)
    assert m.get("a") == 1
    assert m.get("c") == 3
    assert m.get("nope") is None

    # update in place
    m.put("a", 100)
    assert m.get("a") == 100
    assert len(m) == 3

    # THE tombstone test: force collisions, delete a middle key,
    # confirm a later key on the same probe chain is still findable.
    class FixedHash:
        """Keys that all hash to the same value -> guaranteed collisions."""
        def __init__(self, name): self.name = name
        def __hash__(self): return 42          # everybody collides
        def __eq__(self, other): return isinstance(other, FixedHash) and self.name == other.name

    t = OpenAddressingHashMap(initial_capacity=8, max_load=0.9)
    a, b, c = FixedHash("a"), FixedHash("b"), FixedHash("c")
    t.put(a, 1); t.put(b, 2); t.put(c, 3)   # chain: a, b, c in consecutive slots
    t.delete(b)                              # tombstone in the middle
    assert t.get(c) == 3, "tombstone broke the probe chain!"
    assert t.get(b) is None
    # reinserting b should reuse the tombstone, not grow tombstone count
    t.put(b, 22)
    assert t.get(b) == 22

    # stress: many keys, with deletes interleaved, across resizes
    big = OpenAddressingHashMap(initial_capacity=4)
    for i in range(2000):
        big.put(f"k{i}", i)
    for i in range(0, 2000, 2):     # delete all evens
        big.delete(f"k{i}")
    assert len(big) == 1000
    for i in range(2000):
        if i % 2 == 0:
            assert f"k{i}" not in big
        else:
            assert big.get(f"k{i}") == i

    print("OpenAddressingHashMap tests passed ✓")

test_open_addressing()
```

The `FixedHash` trick (a class whose `__hash__` always returns 42) is the cleanest way to force the exact collision scenario that breaks naive deletion. If your tombstone logic were wrong, `t.get(c)` would return `None` and the assert would fire. It passes.

## Probing strategies: linear, quadratic, double hashing

Linear probing is simple and cache-friendly (it scans contiguous memory), but it suffers from **primary clustering**: once a run of occupied slots forms, any key hashing anywhere into that run extends it, and long runs make *every* nearby key slower. Clusters snowball. Two alternatives reduce clustering.

**Linear probing.** Probe sequence: `h(k) + i` for `i = 0, 1, 2, …` (mod `m`).
- Pro: best cache locality, simplest code.
- Con: **primary clustering**, long contiguous runs of filled slots.

**Quadratic probing.** Probe sequence: `h(k) + c₁·i + c₂·i²` (often just `h(k) + i²`) for `i = 0, 1, 2, …` (mod `m`).
- Pro: probes spread out, avoiding primary clustering: keys don't pile into one long run.
- Con: **secondary clustering**: any two keys with the same home bucket follow the identical probe sequence, so they still collide repeatedly down the line. Also, the probe sequence doesn't necessarily hit every slot, so you need `m` prime and load factor < 0.5 to guarantee an empty slot is reachable.

**Double hashing.** Probe sequence: `h₁(k) + i·h₂(k)` (mod `m`) for `i = 0, 1, 2, …`, where `h₂` is a *second, independent* hash function.
- Pro: the step size `h₂(k)` differs per key, so even keys sharing a home bucket take different paths, which kills secondary clustering too. Closest to the ideal "uniform hashing" assumption.
- Con: two hashes per operation (slower constant factor); `h₂(k)` must never be 0 and should be coprime to `m` (easy if `m` is prime, pick `h₂(k) = 1 + (hash2(k) % (m-1))`).

Here's the relationship at a glance:

| Strategy | Probe at step `i` | Clustering | Notes |
|---|---|---|---|
| Linear | `(h + i) mod m` | Primary | Best cache locality |
| Quadratic | `(h + i²) mod m` | Secondary | Need m prime, α < 0.5 |
| Double hashing | `(h₁ + i·h₂) mod m` | (mostly) None | Two hashes, h₂ coprime to m |

We built linear because it's the clearest and what you'd reach for first; swapping in quadratic is a one-line change to the index update (`idx = (home + i*i) % cap`), and double hashing means computing a step once per call. The correctness concerns (tombstones, terminating on EMPTY) are identical across all three.

## Load factor, resizing, and amortized cost

The **load factor** is `α = n / m`, entries divided by buckets. It's the single number that controls performance.

- **Chaining:** average chain length *is* `α`. At `α = 0.75`, the average bucket holds 0.75 entries, so lookups scan well under one entry on average. Chaining still works (slowly) at `α > 1`.
- **Open addressing:** there are only `m` slots for `n` entries, so `α < 1` is mandatory, and performance craters as `α → 1` because the last few empty slots are hard to find. We keep `α` low (0.5-0.7).

When `α` exceeds the threshold, we **resize**: allocate a table roughly twice as big and re-insert everything. Doubling (not adding a constant) is the key choice; amortized analysis shows why.

### The amortized cost of doubling

A single resize is O(n): we touch every entry. That sounds like it ruins our O(1). It doesn't, because resizes are rare and get rarer. Suppose you insert `n` keys one at a time into a table that doubles whenever it fills. Resizes happen at sizes 1, 2, 4, 8, …, n. The total work across *all* resizes is:

```
1 + 2 + 4 + 8 + … + n  =  2n − 1  =  O(n)
```

That geometric series sums to less than `2n`. So `n` insertions cost O(n) total *including* every resize, which means the **amortized cost per insertion is O(1)**. Any single `put` might trigger an expensive O(n) resize, but spread across all the cheap inserts that came before it, the average is constant. This is the same "doubling array" amortization as a dynamic array / Python `list`. It's why doubling beats adding a fixed amount (which would give O(n) amortized, death by a thousand resizes).

## The expected-O(1) argument (and when it dies)

Time to justify the headline claim, not just assert it. The whole analysis rests on one assumption:

> **Simple Uniform Hashing Assumption (SUHA):** each key is equally likely to hash to any of the `m` buckets, independently of the others.

### Chaining: expected chain length is α

Under SUHA, for any bucket, each of the `n` keys lands there with probability `1/m`. By **linearity of expectation**, the expected number of keys in a bucket is:

```
E[chain length] = n · (1/m) = n/m = α
```

A search scans the home bucket's chain. Expected work = `1` (compute hash, index) `+ α` (scan the chain) = **O(1 + α)**. If we keep `α` bounded by a constant (say ≤ 0.75 via resizing), this is **O(1) expected**. The connection to discrete math is direct: it's an expected-value calculation over independent indicator random variables.

### Open addressing: expected probes ≈ 1/(1−α)

For open addressing under uniform hashing, the analysis is a bit more involved but the result is clean. The expected number of probes for an **unsuccessful** search (or an insertion) is:

```
E[probes]  ≤  1 / (1 − α)
```

**Intuition:** the first probe hits an occupied slot with probability ≈ `α`. *Given* that, the next probe is occupied with probability ≈ `α` again, and so on, roughly a geometric process. The expected number of probes until we hit an empty slot is the expected value of a geometric-ish distribution, which sums to `1/(1−α)`. Plug in numbers and the danger of high load factor jumps out:

| α | 1/(1−α) ≈ expected probes |
|---|---|
| 0.50 | 2.0 |
| 0.75 | 4.0 |
| 0.90 | 10.0 |
| 0.95 | 20.0 |
| 0.99 | 100.0 |

At α = 0.5 we expect ~2 probes, basically constant. At α = 0.9 it's already 10, and at 0.99 it's 100. This is why open-addressing tables resize at a much lower threshold (0.5-0.7) than chaining tables (0.75-1.0). As long as α stays bounded below 1 by a constant, expected probes is a constant: **O(1) expected**.

### When O(1) degrades to O(n)

The "expected" in "expected O(1)" is load-bearing. Three ways to fall off the cliff:

1. **Adversarial keys / hash flooding.** An attacker crafts `n` keys that all hash to the same bucket. Now one chain has length `n`, and every lookup of those keys is O(n). This is the real-world attack that motivated Python's per-run hash randomization. SUHA is false against an adversary.
2. **A bad hash function.** The `bad_hash` (sum of chars) sends all anagrams to one bucket. Even with friendly inputs, a hash that doesn't spread keys uniformly creates long chains / probe runs. Garbage hash → garbage performance, regardless of resizing.
3. **Letting α get too high.** If you never resize, `α` grows without bound; chains become O(n) and open-addressing probe runs explode toward `1/(1−α) → ∞`. Resizing is what *enforces* the bounded-α precondition the whole proof depends on.

The honest one-line summary: hash tables are O(1) expected, O(n) worst case, and you stay in the happy case by (a) using a good, ideally randomized hash and (b) resizing to keep α bounded.

## What Python actually does

Now that you've built it twice, you can appreciate `dict` and `set` for what they are.

- **`dict` uses open addressing**, not chaining. Everything is in one flat array, which is cache-friendly.
- It uses a clever **perturbation probe sequence** instead of linear or pure quadratic. Roughly: `j = (5*j + 1 + perturb) % m`, where `perturb` starts as the *full* hash and is shifted right each step. Early probes depend on the low bits of the hash (fast, cache-local); as probing continues, the higher bits of the hash get mixed in, so even keys that collide in their low bits eventually diverge. It's a pragmatic blend that avoids both primary and secondary clustering without a second full hash.
- Table sizes are **powers of two** (so `% m` is a cheap bitmask), and it resizes to keep the load factor under ~2/3.
- Since 3.6, `dict` is **insertion-ordered** and split into a compact "entries" array plus a sparse "index" array, a memory optimization on top of the open-addressing scheme.
- **`set`** is essentially the same machinery storing only keys (no values).
- Keys must be **hashable** (implement `__hash__` and `__eq__`, and be immutable in practice). If you mutate a key after insertion so its hash changes, you've violated invariant 1 and the entry becomes unfindable, the same bug as our `_home` recomputation, exposed.

When you write `d[key]`, Python computes `hash(key)`, masks it into the table, perturbation-probes past collisions, and compares keys with `==` to confirm. Exactly the dance you just implemented, only in optimized C with a smarter probe sequence and a randomized seed.

Let's tie it all together. We'll build a minimal in-memory KV store on top of the `ChainingHashMap`, then (1) benchmark it against Python's `dict` and (2) empirically watch chain lengths grow with the load factor, confirming the `E[chain] = α` theory with real numbers.

## Extra practice: a tiny inverted index for search

The KV-store mini-project shows a hash map as storage. This one shows it as the engine of search. An **inverted index** is the data structure behind every search engine, from Google down to the search box in a notes app: instead of mapping a document to its words (the "forward" direction), it maps each word to the set of documents that contain it (the "inverted" direction). A query for `"hash table"` then becomes "look up `hash`, look up `table`, intersect the two document sets," and every one of those lookups is an O(1) hash-map hit.

We'll build it on a plain `dict` of `word -> set of doc ids` (you could swap in the `ChainingHashMap`; the interface is the same). The intersection of doc-id sets is itself a hash-set operation, so the whole thing is hash tables all the way down.

```python
import re

class InvertedIndex:
    """Tiny full-text search index: word -> set of document ids.
    Supports adding documents and AND / OR queries over terms."""

    def __init__(self):
        self._index = {}            # word -> set[int]   (the inverted index)
        self._docs = {}             # doc_id -> original text (for display)
        self._next_id = 0

    @staticmethod
    def _tokenize(text):
        # lowercase, split on non-letters -> a list of word tokens
        return re.findall(r"[a-z0-9]+", text.lower())

    def add(self, text) -> int:
        doc_id = self._next_id
        self._next_id += 1
        self._docs[doc_id] = text
        for word in set(self._tokenize(text)):      # set() dedupes within a doc
            # setdefault is the idiomatic "get the bucket, create if absent"
            self._index.setdefault(word, set()).add(doc_id)
        return doc_id

    def search_and(self, query):
        """Return doc ids containing ALL query terms (intersection)."""
        terms = self._tokenize(query)
        if not terms:
            return set()
        # Start from the first term's set, then intersect the rest.
        # A missing term -> empty set -> empty result.
        result = self._index.get(terms[0], set()).copy()
        for term in terms[1:]:
            result &= self._index.get(term, set())
            if not result:
                break
        return result

    def search_or(self, query):
        """Return doc ids containing ANY query term (union)."""
        result = set()
        for term in self._tokenize(query):
            result |= self._index.get(term, set())
        return result

    def documents(self, doc_ids):
        return [self._docs[i] for i in sorted(doc_ids)]


def test_inverted_index():
    idx = InvertedIndex()
    d0 = idx.add("Hash tables give average O(1) lookup")
    d1 = idx.add("Binary search trees keep keys sorted")
    d2 = idx.add("A hash function maps a key to a bucket")
    d3 = idx.add("Sorted arrays allow binary search lookup")

    # single term
    assert idx.search_and("hash") == {d0, d2}
    assert idx.search_and("lookup") == {d0, d3}

    # AND query: both terms must appear in the same doc
    assert idx.search_and("hash key") == {d2}          # only d2 has both
    assert idx.search_and("binary search") == {d1, d3} # both terms in d1 and d3

    # OR query: union of docs
    assert idx.search_or("hash sorted") == {d0, d1, d2, d3}

    # missing term yields empty AND result, ignored in OR
    assert idx.search_and("hash nonexistent") == set()
    assert idx.search_or("hash nonexistent") == {d0, d2}

    # human-readable output
    hits = idx.search_and("binary search")
    print("Query 'binary search' matched:")
    for doc in idx.documents(hits):
        print("  -", doc)

    print("InvertedIndex tests passed ✓")

test_inverted_index()
```

Expected output:

```
Query 'binary search' matched:
  - Binary search trees keep keys sorted
  - Sorted arrays allow binary search lookup
InvertedIndex tests passed ✓
```

Why this is such a good hash-table showcase: building the index is O(total words), because each word insertion is an O(1) `setdefault` + `set.add`. A query is O(number of query terms + size of the matched sets); it never scans the documents at all. A naive search that re-reads every document for every query would be O(documents × document length) per query; the inverted index pays that cost once at indexing time and then answers queries in roughly the time it takes to read out the answers. That trade, do the expensive work once, store it in a hash map, answer cheaply forever after, is the same space-for-time instinct that runs through the whole chapter. The `setdefault(word, set())` and `result &= ...` lines carry the whole design, and both lean on hash tables (`dict` lookup, then `set` intersection).

## Common mistakes

Most of these are easy to hit. They're written down here so you don't re-discover them at 2 a.m.

1. **Mutating a key after you insert it.** The table stored the entry at `hash(key) % m` *as the key was when inserted*. If the key is mutable and you change it, its hash changes, so the next lookup computes a different bucket and finds nothing: the entry is silently orphaned. This is why keys should be immutable. Python's `dict` refuses built-in mutable types at insert time, but a custom class whose hash depends on a mutable field will compile fine and betray you at runtime. Rule: **a key's hash must never change while it's in the table.**

2. **Using an unhashable / mutable type as a key.** `d[[1,2]] = 5` throws `TypeError: unhashable type: 'list'`. Lists, dicts, and sets are unhashable on purpose (they're mutable, see mistake 1). Use a `tuple` for a composite key (`d[(row, col)] = ...`), or `frozenset` for an unordered one. If you *need* to key on a custom object, define both `__hash__` and `__eq__` and make them depend only on immutable fields.

3. **Deleting in open addressing by setting the slot to EMPTY instead of a tombstone.** This is the bug traced above. An EMPTY slot in the middle of a probe run severs the chain, so a later key on that run becomes unfindable. You must use a `DELETED` tombstone that searches probe past and inserts may reuse. Setting EMPTY "works" until the first delete-then-lookup of a displaced key, then fails intermittently, which is the worst kind of bug.

4. **Forgetting to rehash on resize, just copying buckets over.** The bucket index is `hash(key) % capacity`, and a resize *changes capacity*. If `_resize` copies the old bucket array into a bigger one without recomputing each key's home, every key is now in the wrong place and lookups fail. The resize must re-`put` every entry against the new modulus (which is exactly what the `_resize` method does, and what the traced 4→8 walkthrough showed relocating keys).

5. **Power-of-two table size with a hash that has weak low bits.** `hash % m` for `m = 2^k` keeps only the low `k` bits of the hash. If your hash function doesn't mix its low bits well (e.g. integer keys that are all multiples of 8, so their low 3 bits are always 0), everything collides into a few buckets. Fixes: use a prime table size so the modulus mixes all bits, use a hash with good avalanche, or do what CPython does: a perturbation probe that folds in high bits over time.

6. **Never resizing, letting the load factor blow up.** If you skip the `if load > max_load: resize()` check, the table fills, α climbs past 1 (chaining) or toward 1 (open addressing), chains/probe-runs grow O(n), and your "O(1)" structure quietly becomes a linked-list scan. Resizing is not optional housekeeping; it's the mechanism that enforces the bounded-α precondition the O(1) proof depends on.

7. **Assuming `hash()` is stable across runs, or relying on dict ordering pre-3.7.** Python randomizes string/bytes hashing per process (the hash-flooding defense), so `hash("x")` differs between runs: never persist a hash value to disk or across machines and expect it to match. Separately, `dict` only became guaranteed insertion-ordered in 3.7 (an implementation detail in 3.6); code that relied on ordering before that, or on any particular order from a `set`, is buggy. If you need order, say so explicitly (`OrderedDict`, or sort).

8. **Comparing keys with `is` instead of `==`.** During a lookup, after probing to a candidate slot, you must confirm the key with `==` (value equality), not `is` (identity). Two equal-but-distinct objects (`"".join(["ab", "c"])` vs a literal `"abc"`) hash the same and compare `==` without being `is`. Using `is` would fail to find a logically present key. The contract: equal keys (`a == b`) must have equal hashes, and lookup must use `==` to confirm; `is` is a shortcut you can try first, but never the only check.

## On the job / interview angle

If you had to bet on a single data structure showing up in a coding interview, it's the hash table, by a mile. The reason: the hash map unlocks the most common optimization in interviewing, trading space for time by remembering what you've already seen. A huge fraction of "can you do better than O(n²)?" problems are solved by replacing an inner loop ("search the rest of the array") with an O(1) hash-map lookup ("have I seen the thing I need?"). Once that pattern clicks, a whole genre of problems becomes easy.

Two mental templates cover most of it:
- **"Remember what you've seen."** Walk the input once, and at each element ask the map a question about the elements *before* it (seen this value? seen its complement? seen this prefix-sum?). One pass, O(n).
- **"Count / group by a key."** Use a `dict` (or `Counter`, or `defaultdict`) to bucket items by some derived key (the value itself, a sorted-letters signature, a remainder). O(n) to build, then read off the answer.

Six classic questions and how to reason about each:

1. **Two-sum (find indices `i, j` with `nums[i] + nums[j] == target`).** Brute force checks every pair, O(n²). The hash-map insight: as you scan, for each `x` you need to know if `target - x` (its *complement*) appeared earlier. Keep a `dict` of `value -> index`; for each `x`, check if `target - x` is in the map before inserting `x`. One pass, O(n) time, O(n) space. This is the canonical "remember what you've seen" problem.

2. **Group anagrams (cluster words that are rearrangements of each other).** The trick is choosing a *canonical key* that's identical for all anagrams. Sorting a word's letters works (`"eat" -> "aet"`, `"tea" -> "aet"`). Use `defaultdict(list)` mapping `sorted-signature -> list of words`. O(n·k log k) for n words of length k (the log k is the per-word sort). A character-count tuple as the key avoids the sort: O(n·k).

3. **First unique character in a string.** Two passes: first build a `Counter` of character frequencies (O(n)), then scan the string again and return the first character whose count is 1 (O(n)). The hash map turns "is this character unique?" from an O(n) rescan into an O(1) lookup. Total O(n).

4. **Subarray sum equals k (count contiguous subarrays summing to `k`).** The clever one. Track a running **prefix sum**; a subarray `(i, j]` sums to `k` exactly when `prefix[j] - prefix[i] == k`, i.e. `prefix[i] == prefix[j] - k`. So as you scan, you keep a `dict` of `prefix-sum -> how many times you've seen it`, and at each step add the count of `prefix - k` seen so far. One pass, O(n). Brute force is O(n²). This generalizes the two-sum complement idea to *running sums*.

5. **LRU cache (`get`/`put` both O(1), evict least-recently-used when full).** The signature combo: a `dict` for O(1) lookup plus a doubly linked list for O(1) recency reordering. The dict maps `key -> node`; the DLL keeps nodes in use-order (most recent at one end). On access, splice the node out and move it to the front (O(1) because the dict gave you the node directly); on eviction, drop the tail. Neither structure alone suffices: the dict can't track order cheaply, and the list can't look up cheaply. (In Python, `OrderedDict.move_to_end` / `popitem` is this combo.)

6. **Design a HashMap from scratch.** Exactly this chapter. Be ready to: pick chaining vs open addressing and justify it, handle collisions, explain the load factor and when/why you resize (and that resize rehashes, doubling for amortized O(1)), and use tombstones if you went open-addressing. Knowing why, the expected-O(1) argument, the birthday-paradox reason collisions must be handled from the start, is what separates a memorized answer from understanding.

A couple more that recur: **detect duplicates** ("does this array contain any repeat?") is a one-liner, `len(set(nums)) != len(nums)`, or a scan into a set that returns early on the first repeat, O(n). And know your three tools: a `set` when you only care about membership/uniqueness (no values), a `dict` when you need to map keys to values, and a `Counter` when you're tallying frequencies (a `dict` subclass with `.most_common()` and additive merging built in). Reaching for the right one signals fluency.

The throughline: when you catch yourself writing a nested loop where the inner loop searches for something, ask "could a hash map remember that instead?" Nine times out of ten, yes, and you just turned O(n²) into O(n).

## Exercises

Working these by hand (then checking against the solutions) is how you make the patterns reflexive. They go roughly easy → hard. Try each before peeking. Every solution below is runnable and states its complexity.

1. **Word frequencies.** Given a string of text, return a dict mapping each word to how many times it appears (case-insensitive, split on whitespace).

2. **Two-sum.** Given a list `nums` and an integer `target`, return indices `i, j` (`i != j`) such that `nums[i] + nums[j] == target`, or `None` if no pair exists. One pass.

3. **Group anagrams.** Given a list of strings, group them so that anagrams are in the same sublist. Return a list of groups.

4. **First non-repeating character.** Given a string, return the first character that appears exactly once, or `None` if every character repeats.

5. **Intersection of two arrays.** Given two lists, return a list of the distinct values that appear in *both*. Order doesn't matter.

6. **Subarray sum equals k.** Given a list of integers `nums` and an integer `k`, return the number of contiguous subarrays whose elements sum to exactly `k`. (Values may be negative.)

7. **Implement a set on top of the hash map.** Using the `ChainingHashMap` from this chapter (store every key with a dummy value), implement a `MySet` supporting `add`, `__contains__`, `discard`, and `__len__`.

8. **Longest substring without repeating characters.** Given a string, return the length of the longest substring containing no repeated character. (Sliding window + a set.)

9. **Find all duplicates.** Given a list, return a list of all values that appear more than once (each such value listed once).

### Solutions

```python
from collections import Counter, defaultdict

# 1. Word frequencies -------------------------------------------------------
def word_frequencies(text):
    """O(n) over the characters: one pass to split, one to count.
    Counter does the tallying in C."""
    return dict(Counter(text.lower().split()))

assert word_frequencies("the cat the dog the") == {"the": 3, "cat": 1, "dog": 1}
# (Equivalent manual version, to show there's no magic:)
def word_frequencies_manual(text):
    counts = {}
    for w in text.lower().split():
        counts[w] = counts.get(w, 0) + 1   # get-with-default is the idiom
    return counts
assert word_frequencies_manual("a b a") == {"a": 2, "b": 1}


# 2. Two-sum ----------------------------------------------------------------
def two_sum(nums, target):
    """O(n) time, O(n) space. Remember each value's index as we go;
    for each x, look up its complement target - x among earlier values."""
    seen = {}                       # value -> index
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:            # O(1) lookup replaces an inner loop
            return (seen[need], i)
        seen[x] = i
    return None

assert two_sum([2, 7, 11, 15], 9) == (0, 1)
assert two_sum([3, 2, 4], 6) == (1, 2)
assert two_sum([1, 2, 3], 100) is None


# 3. Group anagrams ---------------------------------------------------------
def group_anagrams(words):
    """O(n * k log k) for n words of length k. Anagrams share a sorted
    signature, so we bucket by that canonical key in a hash map."""
    groups = defaultdict(list)
    for w in words:
        signature = "".join(sorted(w))   # 'eat' and 'tea' both -> 'aet'
        groups[signature].append(w)
    return list(groups.values())

result = group_anagrams(["eat", "tea", "tan", "ate", "nat", "bat"])
# normalize for a stable assert (order of groups/words isn't specified)
normalized = sorted(sorted(g) for g in result)
assert normalized == [["ate", "eat", "tea"], ["bat"], ["nat", "tan"]]


# 4. First non-repeating character ------------------------------------------
def first_unique_char(s):
    """O(n): one pass to count, one pass to find the first count==1."""
    counts = Counter(s)
    for c in s:
        if counts[c] == 1:
            return c
    return None

assert first_unique_char("leetcode") == "l"
assert first_unique_char("aabbcc") is None
assert first_unique_char("loveleetcode") == "v"


# 5. Intersection of two arrays ---------------------------------------------
def intersection(a, b):
    """O(len(a) + len(b)). Set membership is O(1), so converting one list
    to a set turns the cross-check into a single linear pass."""
    set_a = set(a)
    return list({x for x in b if x in set_a})   # set comp dedupes the result

assert sorted(intersection([1, 2, 2, 3], [2, 3, 3, 4])) == [2, 3]
assert intersection([1, 2], [3, 4]) == []


# 6. Subarray sum equals k --------------------------------------------------
def subarray_sum_equals_k(nums, k):
    """O(n). prefix[j]-prefix[i]==k  <=>  prefix[i]==prefix[j]-k.
    Count previously-seen prefix sums in a hash map as we scan."""
    count = 0
    running = 0
    seen = {0: 1}                    # one empty-prefix sum of 0, seen once
    for x in nums:
        running += x
        count += seen.get(running - k, 0)   # how many starts complete a sum of k
        seen[running] = seen.get(running, 0) + 1
    return count

assert subarray_sum_equals_k([1, 1, 1], 2) == 2       # [1,1] and [1,1]
assert subarray_sum_equals_k([1, 2, 3], 3) == 2       # [1,2] and [3]
assert subarray_sum_equals_k([1, -1, 1, -1], 0) == 4  # negatives work too


# 7. A set on top of ChainingHashMap ----------------------------------------
class MySet:
    """A set built on the chapter's ChainingHashMap. We store each element
    as a key with a dummy value; the map's O(1) ops give us O(1) set ops."""
    _PRESENT = True                 # dummy value

    def __init__(self, iterable=()):
        self._map = ChainingHashMap()
        for x in iterable:
            self.add(x)

    def add(self, x):
        self._map.put(x, MySet._PRESENT)

    def __contains__(self, x):
        return x in self._map

    def discard(self, x):
        try:
            self._map.delete(x)     # remove if present
        except KeyError:
            pass                    # discard is a no-op if absent

    def __len__(self):
        return len(self._map)

s = MySet([1, 2, 2, 3])
assert len(s) == 3                  # duplicate 2 collapsed
assert 2 in s and 4 not in s
s.add(4); assert 4 in s
s.discard(2); assert 2 not in s
s.discard(99)                       # no error on absent
assert len(s) == 3


# 8. Longest substring without repeating chars ------------------------------
def longest_unique_substring(s):
    """O(n) sliding window. 'last[c]' remembers where each char last
    appeared; when we hit a repeat inside the window, jump the left edge
    past it. The hash map makes 'where did I last see c?' O(1)."""
    last = {}                       # char -> last index seen
    left = 0
    best = 0
    for right, c in enumerate(s):
        if c in last and last[c] >= left:
            left = last[c] + 1      # shrink window past the duplicate
        last[c] = right
        best = max(best, right - left + 1)
    return best

assert longest_unique_substring("abcabcbb") == 3   # "abc"
assert longest_unique_substring("bbbbb") == 1      # "b"
assert longest_unique_substring("pwwkew") == 3     # "wke"
assert longest_unique_substring("") == 0


# 9. Find all duplicates ----------------------------------------------------
def find_duplicates(nums):
    """O(n): count with a Counter, return values seen 2+ times."""
    return [val for val, cnt in Counter(nums).items() if cnt > 1]

assert sorted(find_duplicates([1, 2, 3, 2, 1, 4])) == [1, 2]
assert find_duplicates([1, 2, 3]) == []

print("All exercise solutions passed ✓")
```

The thread running through almost every solution: a hash map (or set, or Counter) lets you replace a *search* with a *lookup*, dropping an O(n²) brute force to O(n). Two-sum's complement, subarray-sum's prefix counts, and the sliding window's "last seen" position are three faces of the same "remember what you've seen, ask the map O(1) questions about it" idea.

## Complexity summary

| Operation | Chaining (avg) | Chaining (worst) | Open addr. (avg) | Open addr. (worst) |
|---|---|---|---|---|
| `put` | O(1) amortized | O(n) | O(1) amortized | O(n) |
| `get` | O(1) | O(n) | O(1) | O(n) |
| `delete` | O(1) | O(n) | O(1) | O(n) |
| `in` | O(1) | O(n) | O(1) | O(n) |
| space | O(n + m) | O(n + m) | O(m) | O(m) |

"Average" assumes a good hash and bounded load factor α. "Amortized" on `put` folds in the rare O(n) resize. "Worst" is all-keys-collide (adversarial or terrible hash). Open addressing wins on memory and cache locality; chaining is simpler and tolerates α > 1.

## The mental model to keep

- A hash table is an array plus a function that turns keys into indices.
- Collisions are guaranteed (pigeonhole) and arrive early (birthday paradox), so collision resolution *is* the data structure.
- **Chaining**: bucket = list of colliding entries; average chain length = α.
- **Open addressing**: collisions probe to other slots in one flat array; it must use tombstones for deletion and must keep α well under 1.
- **Resize by doubling** to keep α bounded → amortized O(1) inserts.
- The O(1) is *expected* under uniform hashing; it degrades to O(n) with adversarial keys, a bad hash, or an unbounded load factor.
- Python's `dict`/`set` = open addressing + perturbation probing + power-of-two tables + randomized seed. Everything you built, faster and safer.
- In interviews, the reflex: replace a search with an O(1) lookup, remembering what you've seen, or grouping/counting by a key.

## Teach it back

If you can answer these cold, you own this chapter.

1. **Why are collisions inevitable, and why do they appear so much earlier than the table-size would suggest?** (Pigeonhole says the key universe exceeds `m` buckets so some must collide; the birthday paradox says collisions in pairs grow quadratically, so the first collision is expected after only ~`√m` insertions, not `m/2`.)

2. **Walk through exactly why deleting a key in an open-addressing table needs a tombstone instead of just emptying the slot. Construct the bug.** (If `A,B,C` all probe-chain through consecutive slots and you empty `B`'s slot, a later search for `C` hits the empty slot, assumes the chain ended, and wrongly reports `C` absent. A tombstone says "keep probing" to searches while signaling "reusable" to inserts.)

3. **Derive the expected chain length for separate chaining, and state the analogous result for open addressing.** (Under SUHA each of `n` keys lands in a given bucket with prob `1/m`; by linearity of expectation `E[chain] = n/m = α`, so search is O(1+α). For open addressing, expected probes for an unsuccessful search ≈ `1/(1−α)`.)

4. **Why do we resize by *doubling*, and why doesn't the O(n) cost of a resize break our O(1) claim?** (Doubling makes resizes geometrically rarer; total resize work over `n` inserts is `1+2+4+…+n < 2n = O(n)`, so the per-insert *amortized* cost is O(1). Adding a constant amount instead would give O(n) amortized.)

5. **Name three situations that turn a hash table's O(1) into O(n), and how each is mitigated.** (Adversarial/colliding keys → randomized per-run hash seed; a bad/non-uniform hash function → use a good avalanching hash; unbounded load factor → resize to keep α bounded. All three break the uniform-hashing precondition the O(1) proof relies on.)

6. **What probing strategy does CPython's `dict` use, and how does it avoid both primary and secondary clustering?** (Open addressing with a *perturbation* sequence roughly `j = (5j + 1 + perturb) % m`, where `perturb` is seeded from the full hash and shifted right each step, so early probes use low hash bits for cache-locality and later probes mix in high bits, making even low-bit-colliding keys diverge, avoiding the long runs of linear probing and the identical-sequence trap of quadratic probing.)

7. **A function is O(n²) because of a nested loop where the inner loop searches a list. What's the reflex to make it O(n), and name three problems it solves?** (Replace the search with an O(1) hash-map lookup, "remember what you've seen." It solves two-sum via complements, subarray-sum-equals-k via stored prefix sums, and longest-substring-without-repeats via last-seen positions.)
