## 🌱 Start here - plates and coffee lines

Spencer, before any of the rigor, let me build the gut feeling first. Stacks and queues are just two answers to one question: *when I take something out, which one comes out?* That's it. Everything else is bookkeeping.

### A stack is a pile of plates

Picture a stack of clean plates in a cupboard. I add a plate by setting it on **top**. I take a plate by lifting one off the **top**. I never reach into the middle, and I never pull from the bottom, that would topple the pile. The plate I most recently put down is the plate I'll grab first.

That's a **stack**, and that "most recent out first" rule has a name: **LIFO, Last In, First Out.**

I already use stacks all day without naming them:

- **The browser back button.** Every page I visit gets "pushed" onto a pile. Hitting *Back* pops the most recent page off and shows me the one underneath. The page I saw most recently is the first one Back returns to, LIFO.
- **Undo (Ctrl+Z).** Each edit I make gets pushed onto an undo pile. Undo pops the *most recent* edit and reverses it. If I type "cat" then "dog", undo removes "dog" first, then "cat". Most recent first, LIFO again.
- **Stacking trays at a cafeteria.** Fresh trays go on top of the spring-loaded holder; you take from the top. Same idea.

### A queue is the line at a coffee shop

Now picture the morning line at a coffee shop. I join at the **back**. The barista serves from the **front**. Whoever has been waiting *longest* gets served *next*. Nobody jumps the line (in a fair shop, anyway).

That's a **queue**, and its rule is **FIFO, First In, First Out.** First to arrive is first to be served.

Queues are everywhere too:

- **A printer's job list.** I hit print, you hit print after me; my document prints first because it was first in. The printer processes jobs in arrival order, FIFO.
- **A ticket line, a checkout lane, a drive-through.** All fairness machines. The whole *point* of a line is "first come, first served."
- **Messages waiting to be processed** by a server, network packets waiting to be sent, customers on hold for support, all queues, all FIFO, all for the same fairness reason.

### Why LIFO vs. FIFO actually matters

This isn't trivia, the choice of rule *is* the choice of behavior, and picking the wrong one gives wrong results:

- **When I want to reverse or backtrack, I want LIFO (a stack).** Undo *must* reverse the most recent action first, or it's nonsense. Exploring a maze and hitting a dead end, I want to back up to my *most recent* decision point, that's a stack. Matching nested brackets `([{}])`, the most recently opened bracket must close first, LIFO.
- **When I want fairness or to preserve arrival order, I want FIFO (a queue).** A print spooler that served the *newest* job first would let a flood of new jobs starve my document forever. A support line that helped the *last* caller first would be chaos. Order-preserving, fair processing is FIFO.

Here's the one-sentence test I use: **"Do I want the newest thing or the oldest thing next?"** Newest → stack. Oldest → queue.

| | Stack | Queue |
|---|---|---|
| Rule | LIFO (newest out first) | FIFO (oldest out first) |
| Add to | top | back |
| Remove from | top | front |
| Real-world feel | pile of plates, undo, Back button | coffee line, printer jobs |
| Use it when | reversing, backtracking, nesting | fairness, arrival order, scheduling |

With that intuition locked in, the rest of this chapter makes the idea precise: I'll define the formal contracts, build each structure from raw arrays and linked lists, derive the cost of every operation, and prove the rules can't break. No black boxes.

## 📐 ADT vs. implementation - the distinction that unlocks everything

Spencer, before any code, lock this in: an **Abstract Data Type (ADT)** is a *contract*. It says what operations exist and what they promise, nothing about *how*. An **implementation** is the *machinery* that honors the contract.

A **Stack** is an ADT with this contract:

- `push(x)`, add `x` to the top.
- `pop()`, remove and return the top element.
- `peek()`, look at the top without removing.
- `is_empty()`, is there nothing left?

The defining law is **LIFO, Last In, First Out**. The last thing I push is the first thing I pop. Think of a stack of plates: I add to the top, I take from the top.

A **Queue** is an ADT with:

- `enqueue(x)`, add `x` to the back.
- `dequeue()`, remove and return the front element.
- `peek()` / `front()`, look at the front.
- `is_empty()`.

The defining law is **FIFO, First In, First Out**. Like a line at a coffee shop: first to arrive is first served.

Here's the punchline that took me too long to appreciate: *the same ADT can be implemented many ways*, and the implementation determines the performance. A Stack on a dynamic array and a Stack on a linked list satisfy the identical contract, but they have different memory layouts and different constant factors. The ADT is the idea; the implementation is the engineering. I'll build both for each, every time.

## 📐 The Stack - intuition and invariants

A stack only ever touches *one* end. That single-endedness is exactly why it's so cheap: I never have to shuffle elements around. Whatever structure I pick, I just need *one* end where add and remove are both O(1).

**Invariants I must keep true at all times:**

1. **Order invariant.** If I push `a` then `b`, then `pop()` returns `b` before `a`. (LIFO.)
2. **Size invariant.** `len(stack)` equals the number of pushes minus the number of pops, and is never negative.
3. **Top accessibility.** `peek()` always returns the element that the *next* `pop()` would return, they agree.

I'll write these as assertions in tests so they're not just words.

## 💻 Build it - Stack on a dynamic array

Python's `list` is already a dynamic (growable) array. Its `append` and `pop()` (no index) operate on the *end* of the array, which is the cheap end. So the array-backed stack is almost embarrassingly simple, but I'll wrap it so the ADT boundary is explicit and I'm not tempted to index into the middle.

```python
class ArrayStack:
    """LIFO stack backed by a dynamic array (Python list).

    The 'top' of the stack is the END of the list, because appending to
    and popping from the end of a dynamic array are amortized O(1).
    """

    def __init__(self):
        self._data = []  # the end of this list is the top of the stack

    def push(self, x):
        self._data.append(x)          # add to the top (end)

    def pop(self):
        if self.is_empty():
            raise IndexError("pop from empty stack")
        return self._data.pop()       # remove from the top (end)

    def peek(self):
        if self.is_empty():
            raise IndexError("peek from empty stack")
        return self._data[-1]         # look at the top (end)

    def is_empty(self):
        return len(self._data) == 0

    def __len__(self):
        return len(self._data)
```

### Why the end and not the front?

This is the whole reason the array-backed stack is fast, so let me reason it out. A dynamic array stores elements in *contiguous* memory and tracks a `length` separately from its allocated `capacity`.

- **Appending to the end:** write to slot `length`, bump `length`. That's O(1), *unless* `length == capacity`, in which case the array reallocates to a bigger block (typically doubling) and copies everything. A single append can therefore be O(n). But across `n` appends, the total copying work is `n + n/2 + n/4 + ... < 2n`, so the **amortized** cost per append is O(1). (This is the doubling/amortization argument from Chapter 2.2, I'm leaning on it here.)
- **Removing from the end:** just decrement `length`. Always O(1).

If instead I made the *front* the top, every `push` would need to shift all `n` existing elements one slot right (O(n)) and every `pop` would shift them left (O(n)). Same ADT, catastrophically worse implementation. The lesson generalizes: **with a contiguous array, only the end is cheap.**

### Complexity - `ArrayStack`

| Operation   | Time (amortized) | Time (worst single) | Space  |
|-------------|------------------|---------------------|--------|
| `push`      | O(1)             | O(n) on resize      | O(1)*  |
| `pop`       | O(1)             | O(1)                | O(1)   |
| `peek`      | O(1)             | O(1)                | O(1)   |
| `is_empty`  | O(1)             | O(1)                | O(1)   |

\* Amortized extra space per element is O(1); total structure space is O(n).

### Traced walkthrough - a stack in motion

Tables and Big-O are abstract; let me *watch* a stack work one operation at a time. I'll draw the stack vertically, top at the top (where the action is), and show its full contents after each step. Start with an empty `ArrayStack` (the trace is identical for `LinkedStack`, the ADT is the same).

```

   (top)
   ┌─────┐
   │     │   empty - is_empty() == True
   └─────┘

   (top)

   │ 10  │ ← top
   └─────┘
   contents bottom→top: [10]

push(20)
   (top)
   ┌─────┐
   │ 20  │ ← top   (newest, will leave first)
   ├─────┤
   │ 10  │
   └─────┘
   contents bottom→top: [10, 20]

push(30)
   (top)
   ┌─────┐
   │ 30  │ ← top
   ├─────┤
   │ 20  │
   ├─────┤
   │ 10  │
   └─────┘
   contents bottom→top: [10, 20, 30]

pop()  ->  returns 30   (the LAST one pushed leaves FIRST - LIFO)
   (top)
   ┌─────┐
   │ 20  │ ← top
   ├─────┤
   │ 10  │
   └─────┘
   contents bottom→top: [10, 20]

peek() ->  returns 20   (looks at the top, does NOT remove it)

   ├─────┤

   └─────┘

```

Three things this trace makes concrete:

1. **All the action is at one end.** Every push and pop touched only the top. The `10` at the bottom never moved, that's why a stack is O(1): no shuffling.
2. **`pop()` returned `30`, the most recent push.** That *is* LIFO, seen rather than asserted.
3. **`peek()` left the stack unchanged.** After `peek()` the top is still `20`, and `len` is still 2. Peek reads; pop removes. Mixing these up is a classic bug (see Common Mistakes).

### A second trace - "is this string balanced?"

The single most common real use of a stack is checking **balanced brackets**. The rule: scan left to right, **push** every opening bracket, and on every **closing** bracket, **pop** and check it matches. If the string is balanced, the stack is empty at the end. The most-recently-opened bracket must close first, pure LIFO.

Let me trace `"([])"`:

```
input: ( [ ] )      stack (top on right)

read '(' → push      stack: [ (
read '[' → push      stack: [ (, [
read ']' → pop '['   matches ']' ✓   stack: [ (
read ')' → pop '('   matches ')' ✓   stack: [ ]   (empty)

end of string, stack empty → BALANCED ✅
```

Now an *unbalanced* one, `"(]"`:

```
input: ( ]          stack (top on right)

read '(' → push      stack: [ (
read ']' → pop '('   '(' does NOT match ']'  ✗  → NOT BALANCED ❌
```

And a different failure, `"(("`, brackets left open:

```
input: ( (          stack (top on right)

read '(' → push      stack: [ (
read '(' → push      stack: [ (, (

end of string, stack NOT empty → NOT BALANCED ❌
```

Notice the two distinct ways to fail: a **mismatch** mid-scan (close doesn't match the top), and a **non-empty stack** at the end (opens with no matching close). The full coded version is Exercise 2 below.

## 💻 Build it - Stack on a linked list

A singly linked list makes the front (head) the cheap end: inserting and removing at the head are *always* O(1), no resizing, no amortization caveats. So here the **top of the stack is the head of the list.**

```python
class _Node:
    """A single link in a singly linked list."""
    __slots__ = ("value", "next")  # __slots__ saves memory: no per-node __dict__

    def __init__(self, value, nxt=None):
        self.value = value
        self.next = nxt


class LinkedStack:
    """LIFO stack backed by a singly linked list.

    The 'top' is the HEAD of the list. Head insert/remove are O(1) always.
    """

    def __init__(self):
        self._head = None   # points at the top node, or None if empty
        self._size = 0

    def push(self, x):
        # New node becomes the head; its 'next' is the old head.
        self._head = _Node(x, self._head)
        self._size += 1

    def pop(self):
        if self.is_empty():
            raise IndexError("pop from empty stack")
        node = self._head
        self._head = node.next        # unlink the old head
        self._size -= 1
        return node.value

    def peek(self):
        if self.is_empty():
            raise IndexError("peek from empty stack")
        return self._head.value

    def is_empty(self):
        return self._head is None

    def __len__(self):
        return self._size
```

### Why this is correct - walking the invariant

When I `push(a)` then `push(b)`:

- After `push(a)`: `head -> [a] -> None`.
- After `push(b)`: `head -> [b] -> [a] -> None`.

`pop()` returns `head.value` = `b`, then relinks `head` to `[a]`. Next `pop()` returns `a`. That's LIFO, the order invariant holds by construction, because every push prepends and every pop removes the most recently prepended node.

### Complexity - `LinkedStack`

| Operation   | Time | Worst single | Space per element |
|-------------|------|--------------|-------------------|
| `push`      | O(1) | O(1)         | one node + pointer |
| `pop`       | O(1) | O(1)         |, |
| `peek`      | O(1) | O(1)         |, |
| `is_empty`  | O(1) | O(1)         |, |

### Array vs. linked stack - the real tradeoff

Both honor the identical contract. So which do I reach for?

- **`ArrayStack`** has *better cache locality* (contiguous memory → the CPU prefetcher loves it) and lower per-element overhead. Its only blemish is the occasional O(n) resize, hidden by amortization. **In Python, this is what I'd actually use**, a plain `list` *is* an array stack.
- **`LinkedStack`** has *true* O(1) worst-case push/pop (no resize spikes), which matters in hard real-time systems where a single slow operation is unacceptable. But each node costs a pointer plus allocation, and the nodes are scattered in memory, so it's slower in practice for most workloads.

## 📐 The Queue - and why the naive version is a trap

The queue is where implementation choice actually *bites*. FIFO means I add at one end (the back) and remove from the *other* end (the front). A queue is inherently **two-ended**, and that's the source of all the difficulty.

### The naive array queue (and why it's bad)

The tempting first attempt: use a Python list, `enqueue` with `append` (add at the back/end), `dequeue` with `pop(0)` (remove from the front/index 0).

```python
class NaiveArrayQueue:
    def __init__(self):
        self._data = []

    def enqueue(self, x):
        self._data.append(x)      # O(1) amortized - fine

    def dequeue(self):
        return self._data.pop(0)  # O(n) - DISASTER

    def is_empty(self):
        return len(self._data) == 0
```

Why is `pop(0)` O(n)? Because a list is a contiguous array. Removing index 0 leaves a hole at the front, and to keep the array contiguous, *every* remaining element must shift one slot left. With `n` elements, that's `n - 1` moves, O(n). Do `n` dequeues and the total cost is O(n²). For a queue, whose entire job is enqueue/dequeue, that's a fatal flaw.

The root problem: **a plain array only has one cheap end, but a queue needs two.** I have two good ways out:
1. A **circular buffer** (ring), keep the array but track *two* moving indices and wrap around with modular arithmetic. Both ends become O(1).
2. A **linked list with head and tail pointers**, remove from head, add at tail, both O(1).

I'll build both.

## 💻 Build it - the circular buffer (ring) queue

The brilliant idea: don't shift elements, *move the indices instead*. Keep a fixed-capacity array and two indices:

- `head`, index of the front element (next to be dequeued).
- `tail`, index of the next *free* slot at the back (where the next enqueue writes).

When an index runs off the end of the array, it **wraps around** to 0. The array is treated as a circle. That wraparound is just `index = (index + 1) % capacity`.

### Deriving the index math carefully

Let `cap` be the capacity. The slots are `0 .. cap-1`. I want, after using a slot, the next index to be:

```
next = (current + 1) % cap
```

Let me convince myself the modulo is exactly right. If `current` is `cap - 1` (the last slot), then `current + 1 = cap`, and `cap % cap = 0`, it wraps to the front. For any `current < cap - 1`, `current + 1 < cap`, so `(current + 1) % cap = current + 1`, it just advances. So one formula handles both the normal step and the wrap. 

**The full-vs-empty ambiguity.** Here's the classic trap. If I only track `head` and `tail`, then `head == tail` is *ambiguous*: it's true both when the queue is empty (nothing stored) and when it's completely full (`tail` wrapped all the way around back to `head`). Two different states, one index configuration. I can't tell them apart from `head` and `tail` alone.

Standard fixes are (a) keep an explicit `size` counter, or (b) waste one slot so full means `(tail + 1) % cap == head`. I'll use the **explicit `size` counter**, it's the clearest and lets me use the *whole* array.

I also want the queue to *grow* when it fills, so capacity isn't a hard limit. When full, I allocate a bigger array and copy elements in logical (front-to-back) order, resetting `head = 0`.

```python
class RingQueue:
    """FIFO queue backed by a growable circular buffer.

    Invariants:
      * Logical front element lives at index `head`.
      * `tail` is the index of the next free slot.
      * `size` elements are stored, occupying head, head+1, ..., (mod cap).
      * Stored slots are exactly { (head + k) % cap : 0 <= k < size }.
    """

    def __init__(self, initial_capacity=8):
        self._cap = max(1, initial_capacity)
        self._data = [None] * self._cap
        self._head = 0   # index of front element
        self._tail = 0   # index of next free slot at back
        self._size = 0   # number of stored elements

    def is_empty(self):
        return self._size == 0

    def __len__(self):
        return self._size

    def enqueue(self, x):
        if self._size == self._cap:
            self._resize(2 * self._cap)   # grow before we'd overflow
        self._data[self._tail] = x        # write into the free slot
        self._tail = (self._tail + 1) % self._cap  # advance with wraparound
        self._size += 1

    def dequeue(self):
        if self.is_empty():
            raise IndexError("dequeue from empty queue")
        x = self._data[self._head]
        self._data[self._head] = None              # release reference (GC hygiene)
        self._head = (self._head + 1) % self._cap  # advance front with wraparound
        self._size -= 1
        return x

    def peek(self):
        if self.is_empty():
            raise IndexError("peek from empty queue")
        return self._data[self._head]

    def _resize(self, new_cap):
        # Copy elements out in LOGICAL order (front to back), unrolling the ring.
        new_data = [None] * new_cap
        for k in range(self._size):
            new_data[k] = self._data[(self._head + k) % self._cap]
        self._data = new_data
        self._head = 0
        self._tail = self._size   # next free slot is right after the last element
        self._cap = new_cap
```

### Walking through a wraparound by hand

Let `cap = 4`. Start empty: `head=0, tail=0, size=0`.

```
enqueue(A): data=[A, _, _, _]  head=0 tail=1 size=1
enqueue(B): data=[A, B, _, _]  head=0 tail=2 size=2
enqueue(C): data=[A, B, C, _]  head=0 tail=3 size=3
dequeue() -> A: data=[_, B, C, _]  head=1 tail=3 size=2
dequeue() -> B: data=[_, _, C, _]  head=2 tail=3 size=1
enqueue(D): data=[_, _, C, D]  head=2 tail=0 size=2   # tail wrapped: (3+1)%4 = 0
enqueue(E): data=[E, _, C, D]  head=2 tail=1 size=3   # E written at slot 0!
```

See it? After `D` filled the last physical slot, `tail` wrapped to 0, and `E` landed at the *front of the array*, but logically it's at the *back of the queue*. The data is physically split across the wrap point (`C, D` then `E`), yet logically contiguous: front-to-back is `C, D, E`. That's the ring working exactly as intended, no shifting, ever.

The `_resize` unrolls this: it reads `(head + k) % cap` for `k = 0..size-1`, which yields `C, D, E` in order, and lays them flat starting at index 0.

### Why every operation is O(1) amortized

- `enqueue`: one write, one modulo, one increment → O(1), except when it triggers `_resize` (O(n) copy). By the same doubling argument as the dynamic array, resizes are rare enough that the **amortized** cost is O(1).
- `dequeue`: one read, one modulo, one decrement → O(1), always.
- `peek` / `is_empty`: O(1), always.

The naive queue's O(n) dequeue is *gone*, replaced by an index bump.

### Complexity - `RingQueue`

| Operation   | Time (amortized) | Worst single   | Space |
|-------------|------------------|----------------|-------|
| `enqueue`   | O(1)             | O(n) on resize | O(1)* |
| `dequeue`   | O(1)             | O(1)           | O(1)  |
| `peek`      | O(1)             | O(1)           | O(1)  |
| `is_empty`  | O(1)             | O(1)           | O(1)  |

\* Total structure space O(n); the buffer may hold up to ~2x slack between resizes.

## 💻 Build it - linked-list queue (true O(1) both ends)

The other escape from the naive queue: a singly linked list with pointers to *both* the head and the tail. Dequeue from the head (O(1)), enqueue at the tail (O(1)). No resizing, no amortization caveat, genuinely O(1) worst case.

The subtlety is keeping `head` and `tail` consistent in the edge cases: enqueue into an empty queue (must set *both* pointers) and dequeue the last element (must reset `tail` to `None`).

```python
class LinkedQueue:
    """FIFO queue backed by a singly linked list with head AND tail pointers.

    Invariants:
      * head points at the front node (next dequeue), or None if empty.
      * tail points at the back node (last enqueued), or None if empty.
      * head is None  <=>  tail is None  <=>  size == 0.
    """

    def __init__(self):
        self._head = None
        self._tail = None
        self._size = 0

    def is_empty(self):
        return self._head is None

    def __len__(self):
        return self._size

    def enqueue(self, x):
        node = _Node(x, None)         # new node always goes at the back
        if self._tail is None:        # queue was empty: head and tail both = node
            self._head = node
            self._tail = node
        else:
            self._tail.next = node    # link old back to new node
            self._tail = node         # new node is the new back
        self._size += 1

    def dequeue(self):
        if self.is_empty():
            raise IndexError("dequeue from empty queue")
        node = self._head
        self._head = node.next        # advance front
        if self._head is None:        # we removed the last element
            self._tail = None         # keep the empty-state invariant
        self._size -= 1
        return node.value

    def peek(self):
        if self.is_empty():
            raise IndexError("peek from empty queue")
        return self._head.value
```

The invariant `head is None <=> tail is None` is the one to guard. The two branches I added, setting both pointers on enqueue-into-empty, and clearing `tail` on dequeue-the-last, are precisely what preserve it. If I forgot to clear `tail` on the last dequeue, the next enqueue would link onto a node that's no longer in the queue. Easy bug; the invariant catches it.

### Complexity - `LinkedQueue`

| Operation   | Time | Worst single | Space per element  |
|-------------|------|--------------|--------------------|
| `enqueue`   | O(1) | O(1)         | one node + pointer |
| `dequeue`   | O(1) | O(1)         |, |
| `peek`      | O(1) | O(1)         |, |
| `is_empty`  | O(1) | O(1)         |, |

## 🧪 Tests - both queues satisfy the contract

```python
def test_queue(QueueClass):

    # FIFO must give a strictly increasing 0..99 sequence.
```

## 💻 Build it - the deque (double-ended queue)

A **deque** ("deck") generalizes both: O(1) insert and remove at *both* ends. A deque can act as a stack (use one end) or a queue (push one end, pop the other). The cleanest from-scratch implementation is a **doubly** linked list, each node knows its `prev` and `next`, so I can splice at either end in O(1).

```python
class _DNode:
    __slots__ = ("value", "prev", "next")

    def __init__(self, value, prev=None, nxt=None):
        self.value = value
        self.prev = prev
        self.next = nxt


class Deque:
    """Double-ended queue: O(1) push/pop at both front and back.

    Backed by a doubly linked list. head = front, tail = back.
    Invariant: head is None <=> tail is None <=> size == 0.
    """

    def __init__(self):
        self._head = None
        self._tail = None
        self._size = 0

    def is_empty(self):
        return self._head is None

    def __len__(self):
        return self._size

    def push_front(self, x):
        node = _DNode(x, prev=None, nxt=self._head)
        if self._head is None:
            self._head = self._tail = node
        else:
            self._head.prev = node
            self._head = node
        self._size += 1

    def push_back(self, x):
        node = _DNode(x, prev=self._tail, nxt=None)
        if self._tail is None:
            self._head = self._tail = node
        else:
            self._tail.next = node
            self._tail = node
        self._size += 1

    def pop_front(self):
        if self.is_empty():
            raise IndexError("pop_front from empty deque")
        node = self._head
        self._head = node.next
        if self._head is None:        # deque is now empty
            self._tail = None
        else:
            self._head.prev = None
        self._size -= 1
        return node.value

    def pop_back(self):
        if self.is_empty():
            raise IndexError("pop_back from empty deque")
        node = self._tail
        self._tail = node.prev
        if self._tail is None:        # deque is now empty
            self._head = None
        else:
            self._tail.next = None
        self._size -= 1
        return node.value

    def peek_front(self):
        if self.is_empty():
            raise IndexError("empty deque")
        return self._head.value

    def peek_back(self):
        if self.is_empty():
            raise IndexError("empty deque")
        return self._tail.value
```

Each of the four mutating operations touches only a constant number of pointers, so all are **O(1) worst case**. The mirror symmetry between `push_front`/`push_back` and `pop_front`/`pop_back` is a good correctness check: if one direction works, the other is its mirror image.

## 📐 Where these actually show up

These aren't toys, they're load-bearing in real systems:

- **The call stack *is* a stack.** Every function call pushes a *stack frame* (parameters, locals, return address); returning pops it. LIFO is exactly right: the most recently called function is the first to finish. When recursion goes too deep, the frames overflow the allocated region, that's literally a *stack overflow*. The structure I built is the mental model for how my own programs run.
- **Undo/redo uses two stacks.** Each action pushes onto an *undo* stack. Undo pops from undo and pushes onto a *redo* stack. Redo reverses it. LIFO matches intuition: undo reverses the *most recent* action first.
- **BFS uses a queue.** Breadth-first search explores a graph level by level: dequeue a node, enqueue its unvisited neighbors. FIFO guarantees nodes are visited in non-decreasing distance from the start, which is *why* BFS finds shortest paths in unweighted graphs. (DFS, by contrast, uses a stack, explicit, or the call stack via recursion.)
- **Schedulers, buffers, message pipelines** are queues, print spoolers, network packet buffers, task queues. FIFO gives fairness: first request in, first served.
- **Deques** power sliding-window algorithms (e.g., the sliding-window-maximum trick) and work-stealing schedulers.

## 🧪 Mini-project - an expression evaluator (shunting-yard + RPN)

Time to make a stack earn its keep. I'll evaluate arithmetic expressions like `3 + 4 * 2 / (1 - 5)`, respecting precedence and parentheses. The classic two-phase approach, both phases stack-driven:

1. **Shunting-yard** (Dijkstra): convert *infix* (`3 + 4 * 2`) to **RPN / postfix** (`3 4 2 * +`) using an operator stack.
2. **Evaluate RPN** with a value stack.

### Why two phases? The intuition

Infix is hard because precedence and parentheses mean I can't evaluate strictly left-to-right. RPN has *no parentheses and no precedence rules*, operators apply to the two values right before them, period. So I first reshuffle infix into RPN (the hard part, done once), then evaluating RPN is trivial. The stack is what lets me "hold" operators until their operands are ready.

### Phase 1 - Shunting-yard

The rule for precedence/associativity: when I meet an operator `o1`, I pop operators off the stack to the output **while** the operator `o2` on top has *higher* precedence, OR *equal* precedence and `o1` is *left-associative*. `+ - * /` are all left-associative (`8 - 4 - 2` means `(8 - 4) - 2`), so equal precedence pops. Parentheses are handled specially: `(` always pushes; `)` pops until the matching `(`.

```python
# precedence: higher number binds tighter
PRECEDENCE = {"+": 1, "-": 1, "*": 2, "/": 2}
LEFT_ASSOCIATIVE = {"+": True, "-": True, "*": True, "/": True}


def tokenize(expr):
    """Split an expression string into number / operator / paren tokens."""
    tokens = []
    i = 0
    while i < len(expr):
        c = expr[i]
        if c.isspace():
            i += 1
        elif c in "+-*/()":
            tokens.append(c)
            i += 1
        elif c.isdigit() or c == ".":
            j = i
            while j < len(expr) and (expr[j].isdigit() or expr[j] == "."):
                j += 1
            tokens.append(expr[i:j])   # the whole number as one token
            i = j
        else:
            raise ValueError(f"unexpected character: {c!r}")
    return tokens


def to_rpn(tokens):
    """Convert infix tokens to RPN using the shunting-yard algorithm."""
    output = []                 # the RPN result
    op_stack = ArrayStack()     # operators and parentheses wait here

    for tok in tokens:
        if tok in PRECEDENCE:                       # it's an operator
            while (not op_stack.is_empty()
                   and op_stack.peek() != "("
                   and (PRECEDENCE[op_stack.peek()] > PRECEDENCE[tok]
                        or (PRECEDENCE[op_stack.peek()] == PRECEDENCE[tok]
                            and LEFT_ASSOCIATIVE[tok]))):
                output.append(op_stack.pop())
            op_stack.push(tok)
        elif tok == "(":
            op_stack.push(tok)
        elif tok == ")":
            # Pop until the matching '(' is found.
            while not op_stack.is_empty() and op_stack.peek() != "(":
                output.append(op_stack.pop())
            if op_stack.is_empty():
                raise ValueError("mismatched parentheses: extra ')'")
            op_stack.pop()      # discard the '('
        else:                   # it's a number
            output.append(tok)

    # Drain any remaining operators.
    while not op_stack.is_empty():
        top = op_stack.pop()
        if top == "(":
            raise ValueError("mismatched parentheses: extra '('")
        output.append(top)

    return output
```

### Phase 2 - Evaluate the RPN

Scan the RPN left to right. Push numbers onto a value stack. On an operator, pop the **two** top values (mind the order, the *second* pop is the *left* operand), apply, push the result.

```python
def eval_rpn(rpn):
    """Evaluate a list of RPN tokens, returning a float."""
    values = ArrayStack()
    for tok in rpn:
        if tok in PRECEDENCE:
            if len(values) < 2:
                raise ValueError("malformed expression: not enough operands")
            right = values.pop()        # second operand popped FIRST
            left = values.pop()         # first operand popped SECOND
            if tok == "+":
                values.push(left + right)
            elif tok == "-":
                values.push(left - right)
            elif tok == "*":
                values.push(left * right)
            elif tok == "/":
                if right == 0:
                    raise ZeroDivisionError("division by zero")
                values.push(left / right)
        else:
            values.push(float(tok))     # a number

    if len(values) != 1:
        raise ValueError("malformed expression: leftover operands")
    return values.pop()


def evaluate(expr):
    """Full pipeline: string -> tokens -> RPN -> value."""
    return eval_rpn(to_rpn(tokenize(expr)))
```

Why does the **order of pops** matter? For non-commutative `-` and `/`, `left - right != right - left`. RPN preserves left-to-right operand order, so on the stack the *left* operand was pushed first and sits *underneath* the right operand. Therefore the first pop gives the right operand, the second gives the left. Getting this backwards is the single most common bug here, so I test it explicitly below.

### Complexity of the evaluator

Let `n` be the number of tokens. In shunting-yard, each token is pushed and popped from the operator stack at most once, so the conversion is **O(n)**. Evaluating the RPN likewise touches each token once, **O(n)**. Total: **O(n) time, O(n) space** (the stacks). Linear, thanks to the stack doing the bookkeeping a more naive parser would do with expensive rescanning.

## 🧪 Extra practice - a browser history (two stacks)

The expression evaluator showed one stack carrying a whole algorithm. This mini-project shows the *two-stacks* pattern, the same one undo/redo uses, by building something I touch every day: **browser back/forward navigation.**

### The design intuition

A browser's Back and Forward buttons are just two stacks plus the current page:

- A **back stack** holds pages I can return to (everything behind the current one).
- A **forward stack** holds pages I can go forward to (everything ahead).
- `current` is the page I'm looking at right now.

The three operations map cleanly:

- **`visit(url)`**, I navigate somewhere new. The page I was on gets pushed onto the *back* stack, the new page becomes `current`, and, crucially, the *forward* stack is **cleared**. (Once I take a new path, the old "forward" history is gone. Every browser does this; it's why Forward greys out after you click a fresh link.)
- **`back()`**, push `current` onto the *forward* stack, pop the *back* stack into `current`.
- **`forward()`**, push `current` onto the *back* stack, pop the *forward* stack into `current`.

Why stacks and not queues? Because navigation is LIFO: Back returns to the *most recent* page first, not the oldest. That's the whole reason this is a stack problem.

```python
class BrowserHistory:
    """Back/forward navigation modeled with two stacks + a current page.

    Invariants:
      * `current` is None only before the first visit.
      * back stack top  = the page Back would go to.
      * fwd  stack top  = the page Forward would go to.
      * a fresh visit() clears the forward stack (new branch).
    """

    def __init__(self, homepage):
        self.current = homepage
        self._back = ArrayStack()      # pages behind the current one
        self._fwd = ArrayStack()       # pages ahead of the current one

    def visit(self, url):
        self._back.push(self.current)  # current becomes "behind"
        self.current = url
        # New branch: anything we could have gone forward to is now unreachable.
        self._fwd = ArrayStack()

    def back(self):
        if self._back.is_empty():
            return self.current        # can't go back; stay put
        self._fwd.push(self.current)   # current becomes "ahead"
        self.current = self._back.pop()
        return self.current

    def forward(self):
        if self._fwd.is_empty():
            return self.current        # can't go forward; stay put
        self._back.push(self.current)  # current becomes "behind"
        self.current = self._fwd.pop()
        return self.current

    def can_back(self):
        return not self._back.is_empty()

    def can_forward(self):
        return not self._fwd.is_empty()
```

## ⚠️ Common mistakes

These are the bugs I will actually write if I'm not careful. I'm collecting them so future-me recognizes the symptom fast.

1. **Using `list.pop(0)` to dequeue.** It *looks* like a queue and passes small tests, but `pop(0)` shifts every remaining element left, O(n) per dequeue, O(n²) overall. The whole reason this chapter exists. Use `collections.deque.popleft()`, a `RingQueue`, or a `LinkedQueue`.

2. **Forgetting the empty-check before `pop`/`peek`/`dequeue`.** Calling these on an empty structure should raise a clear error, not return `None` or blow up with an obscure `IndexError` deep in the internals. Every remove/peek I wrote starts with `if self.is_empty(): raise IndexError(...)`, that's not optional.

3. **Mixing up which end is the "top."** In `ArrayStack` the top is the *end* of the list (`[-1]`); in `LinkedStack` the top is the *head*. If I absent-mindedly index `_data[0]` for the array stack's top, I'll get LIFO and FIFO confused and every order will be backwards. The top is wherever push and pop both act, keep them on the *same* end.

4. **The full-vs-empty ambiguity in a ring buffer.** With only `head` and `tail`, `head == tail` means *both* "empty" and "completely full", indistinguishable. Forgetting to disambiguate (via an explicit `size` counter or a wasted slot) gives a queue that silently overwrites live data when full, or refuses to enqueue when actually empty. I use an explicit `size`.

5. **Forgetting to reset `tail` to `None` on the last dequeue (linked queue).** When I dequeue the final element, `head` becomes `None` but if I don't *also* set `tail = None`, the next `enqueue` links a new node onto a stale, no-longer-in-the-queue node. The invariant `head is None <=> tail is None` is the tripwire; the `if self._head is None: self._tail = None` line is the fix.

6. **Wrong operand order in RPN / postfix evaluation.** On `-` and `/`, order matters: `left - right != right - left`. The *first* value popped is the *right* operand (it was pushed last, sits on top); the *second* pop is the *left* operand. Swapping them gives `8 - 4 = -4` and `10 / 2 = 0.2`. Pop right first, then left.

7. **Off-by-one / forgetting the modulo in ring wraparound.** Advancing an index with `tail += 1` instead of `tail = (tail + 1) % cap` runs off the end of the array and either crashes or skips the wrap. The modulo is what makes the array circular; every index advance needs it.

8. **Using a queue where I needed a stack (or vice versa).** The deepest mistake, getting the *order semantics* wrong. If I use a queue (FIFO) for backtracking or bracket-matching, I'll process the *oldest* item when I needed the *newest*, and the logic is silently wrong even though the code runs. Always ask: newest-out (stack) or oldest-out (queue)?

## 💼 On the job / interview angle

Stacks and queues come up in interviews far more than their simplicity suggests, and that's *because* they're simple. They're the smallest data structures rich enough to test whether I can (a) pick the right tool from the order semantics, and (b) compose a tool into a non-obvious algorithm. The interviewer isn't checking whether I can write `push`/`pop`; they're checking whether I *recognize* that a problem is secretly a stack/queue problem. Here are the classics, each with the reasoning that cracks it.

1. **Valid parentheses / balanced brackets.** *"Given a string of `()[]{}`, is it balanced?"* The signal: nesting means the most-recently-opened bracket must close first, LIFO. Push opens, and on each close, pop and check it matches the corresponding open. Balanced iff every close matched *and* the stack ends empty. O(n) time, O(n) space. (Coded in Exercise 2.)

2. **Min-stack, `getMin()` in O(1).** *"Design a stack that also returns its minimum in O(1)."* The naive scan is O(n). The trick: keep a *second* stack of running minimums, pushing `min(x, current_min)` alongside every push. The min stack's top is always the min of everything currently in the main stack, and it pops in lockstep. This "augment the stack with a parallel stack" idea generalizes. (Exercise 3.)

3. **Implement a queue using two stacks.** *"You only have stacks. Build a FIFO queue."* Reversing a stack gives FIFO order, so use an *in* stack for enqueues and an *out* stack for dequeues; when `out` is empty, pour all of `in` into it (which reverses the order). Each element moves between stacks at most once → **amortized O(1)** per operation even though a single dequeue can be O(n). The amortized-analysis story is the real point. (Exercise 4.)

4. **Implement a stack using two queues.** The mirror puzzle. Either make push O(n) (enqueue, then rotate the queue so the new element is at the front) and pop O(1), or the reverse. It mostly tests whether I understand that you can simulate one order discipline with the other at a cost.

5. **Evaluate Reverse Polish Notation.** *"Evaluate `["2","1","+","3","*"]`."* A single value stack: push numbers, and on an operator pop two, apply, push the result. The catch everyone hits is operand order on `-`/`/` (pop right first). This is literally Phase 2 of the mini-project. O(n). (Exercise 9.)

6. **Daily temperatures / next greater element, the monotonic stack.** *"For each day, how many days until a warmer temperature?"* The brute force is O(n²). The pattern that makes it O(n) is the **monotonic stack**: a stack kept in sorted (here, decreasing) order. I push indices; before pushing a new element, I pop every smaller element off the top, and *each pop is resolved by the current element* (it's that element's "next greater"). Each index is pushed and popped at most once → O(n). Recognizing "for each element, find the next bigger/smaller one" → reach for a monotonic stack. (Exercise 7.)

7. **Sliding window maximum, the monotonic deque.** *"Max of every window of size k as it slides across the array."* The pattern is the **monotonic deque**: a deque holding indices whose values are in decreasing order. The front always holds the current window's max; I pop expired indices off the front and pop smaller indices off the back before adding each new one. Each index enters and leaves the deque once → O(n) for the whole sweep, versus O(n·k) naive. This is *the* reason deques exist in many people's toolkits. (Exercise 8.)

8. **BFS vs. DFS framing.** Many graph/tree questions reduce to *"explore this structure"*, and the data structure I pick *is* the traversal order. A **queue** gives breadth-first (level by level, shortest path in unweighted graphs, because FIFO visits nodes in non-decreasing distance). A **stack** (or recursion, which uses the call stack) gives depth-first. When an interviewer asks for "shortest number of steps," that's a flashing neon sign for BFS-with-a-queue.

**The meta-pattern to internalize: the monotonic stack/deque.** Whenever a problem says *"for each element, find the nearest larger/smaller element"* or *"the max/min over a sliding window,"* the answer is almost always a stack or deque maintained in monotonic order, turning an O(n²) scan into O(n). Spotting that family of problems is worth more than memorizing any single solution.

```python
# ---------------------------------------------------------------------------
# 1. Reverse a string using a stack.
#    A stack reverses by construction: pushing pushes in order, popping
#    yields reverse order (LIFO). That IS string reversal.
# ---------------------------------------------------------------------------
def reverse(s):
    st = ArrayStack()
    for ch in s:
        st.push(ch)
    out = []
    while not st.is_empty():
        out.append(st.pop())
    return "".join(out)

assert reverse("hello") == "olleh"
assert reverse("") == ""
assert reverse("a") == "a"
# Time: O(n) - each char pushed once, popped once. Space: O(n) for the stack.


# ---------------------------------------------------------------------------
# 2. Balanced parentheses, multiple bracket types.
#    Push opens; on a close, pop and check it matches the corresponding open.
#    Balanced iff every close matched AND the stack ends empty.
# ---------------------------------------------------------------------------
def is_balanced(s):
    pairs = {")": "(", "]": "[", "}": "{"}   # close -> matching open
    opens = set(pairs.values())
    st = ArrayStack()
    for ch in s:
        if ch in opens:
            st.push(ch)
        elif ch in pairs:                    # it's a closing bracket
            if st.is_empty() or st.pop() != pairs[ch]:
                return False                 # mismatch, or nothing to match
        # any other char is ignored
    return st.is_empty()                     # leftover opens => unbalanced

assert is_balanced("([])") is True
assert is_balanced("([)]") is False          # crossed nesting
assert is_balanced("(((") is False
assert is_balanced("") is True
assert is_balanced("a(b)[c]{d}") is True
# Time: O(n). Space: O(n) worst case (all opens).


# ---------------------------------------------------------------------------
# 3. Min-stack - O(1) get_min via a parallel stack of running minimums.
# ---------------------------------------------------------------------------
class MinStack:
    def __init__(self):
        self._data = ArrayStack()
        self._mins = ArrayStack()            # _mins.peek() == min of _data

    def push(self, x):
        self._data.push(x)
        cur_min = x if self._mins.is_empty() else min(x, self._mins.peek())
        self._mins.push(cur_min)

    def pop(self):
        self._mins.pop()                     # pop in lockstep
        return self._data.pop()

    def top(self):
        return self._data.peek()

    def get_min(self):
        return self._mins.peek()

ms = MinStack()
ms.push(5); ms.push(3); ms.push(7); ms.push(3)
assert ms.get_min() == 3
assert ms.pop() == 3 and ms.get_min() == 3
assert ms.pop() == 7 and ms.get_min() == 3
assert ms.pop() == 3 and ms.get_min() == 5
# Every op is O(1): two stacks moving together. Space: O(n).


# ---------------------------------------------------------------------------
# 4. Queue from two stacks. 'in' takes enqueues; 'out' serves dequeues.
#    When 'out' is empty, pour 'in' into it (reversing order -> FIFO).
# ---------------------------------------------------------------------------
class QueueFromStacks:
    def __init__(self):
        self._in = ArrayStack()
        self._out = ArrayStack()

    def enqueue(self, x):
        self._in.push(x)

    def _transfer(self):
        if self._out.is_empty():
            while not self._in.is_empty():
                self._out.push(self._in.pop())   # reverse into 'out'

    def dequeue(self):
        self._transfer()
        if self._out.is_empty():
            raise IndexError("dequeue from empty queue")
        return self._out.pop()

    def is_empty(self):
        return self._in.is_empty() and self._out.is_empty()

qs = QueueFromStacks()
for i in range(5):
    qs.enqueue(i)
assert [qs.dequeue() for _ in range(3)] == [0, 1, 2]   # FIFO
qs.enqueue(5)
assert [qs.dequeue() for _ in range(3)] == [3, 4, 5]
assert qs.is_empty()
# Amortized O(1): each element is pushed onto 'in' once, moved to 'out' once,
# popped from 'out' once -> 3 ops total, spread over its lifetime. A single
# dequeue can be O(n) (when it triggers a transfer), but amortized it's O(1).


# ---------------------------------------------------------------------------
# 5. Decimal to binary using a stack.
#    Repeated division by 2 yields bits LEAST-significant first; a stack
#    reverses them to most-significant first. That's why a stack fits.
# ---------------------------------------------------------------------------
def to_binary(n):
    if n == 0:
        return "0"
    st = ArrayStack()
    while n > 0:
        st.push(n % 2)        # remainder is the next bit (LSB first)
        n //= 2
    bits = []
    while not st.is_empty():
        bits.append(str(st.pop()))   # pop reverses -> MSB first
    return "".join(bits)

assert to_binary(0) == "0"
assert to_binary(1) == "1"
assert to_binary(5) == "101"
assert to_binary(13) == "1101"
assert to_binary(256) == "100000000"
# Time: O(log n) (one push/pop per bit). Space: O(log n).


# ---------------------------------------------------------------------------
# 6. Next greater element - monotonic (decreasing) stack of indices.
#    Each element is pushed once and popped once -> O(n).
# ---------------------------------------------------------------------------
def next_greater(nums):
    res = [-1] * len(nums)
    st = ArrayStack()                 # holds indices; values are decreasing
    for i, x in enumerate(nums):
        # x is the "next greater" for every smaller value waiting on the stack.
        while not st.is_empty() and nums[st.peek()] < x:
            res[st.pop()] = x
        st.push(i)
    return res

assert next_greater([2, 1, 2, 4, 3]) == [4, 2, 4, -1, -1]
assert next_greater([5, 4, 3, 2, 1]) == [-1, -1, -1, -1, -1]
assert next_greater([1, 2, 3]) == [2, 3, -1]
# Time: O(n) - each index pushed/popped at most once. Space: O(n).


# ---------------------------------------------------------------------------
# 7. Sliding window maximum - monotonic (decreasing) deque of indices.
#    Front of the deque is always the current window's max.
# ---------------------------------------------------------------------------
from collections import deque as _stddeque

def max_sliding_window(nums, k):
    if not nums or k <= 0:
        return []
    dq = _stddeque()                  # indices, values decreasing front->back
    out = []
    for i, x in enumerate(nums):
        # Drop indices that have slid out of the window on the left.
        while dq and dq[0] <= i - k:
            dq.popleft()
        # Drop smaller values from the back - they can never be the max now.
        while dq and nums[dq[-1]] < x:
            dq.pop()
        dq.append(i)
        if i >= k - 1:                # first full window complete
            out.append(nums[dq[0]])   # front is the window max
    return out

assert max_sliding_window([1, 3, -1, -3, 5, 3, 6, 7], 3) == [3, 3, 5, 5, 6, 7]
assert max_sliding_window([4, 4, 4], 2) == [4, 4]
assert max_sliding_window([], 3) == []
# Time: O(n) - each index enters and leaves the deque once. Space: O(k).


# ---------------------------------------------------------------------------
# 8. Palindrome check with a deque - compare front and back, moving inward.
# ---------------------------------------------------------------------------
def is_palindrome(s):
    d = Deque()
    for ch in s.lower():
        if ch.isalnum():
            d.push_back(ch)
    while len(d) > 1:
        if d.pop_front() != d.pop_back():
            return False
    return True

assert is_palindrome("racecar") is True
assert is_palindrome("A man, a plan, a canal: Panama") is True
assert is_palindrome("hello") is False
assert is_palindrome("") is True
# Time: O(n). Space: O(n) for the deque.


# ---------------------------------------------------------------------------
# 9. Evaluate postfix (RPN) -> integer, truncate-toward-zero division.
#    One value stack; pop RIGHT first, then LEFT (operand-order trap).
# ---------------------------------------------------------------------------
def eval_postfix(tokens):
    st = ArrayStack()
    ops = {"+", "-", "*", "/"}
    for tok in tokens:
        if tok in ops:
            right = st.pop()
            left = st.pop()
            if tok == "+":   st.push(left + right)
            elif tok == "-": st.push(left - right)
            elif tok == "*": st.push(left * right)
            else:            st.push(int(left / right))   # truncate toward 0
        else:
            st.push(int(tok))
    return st.pop()

assert eval_postfix(["2", "1", "+", "3", "*"]) == 9       # (2+1)*3
assert eval_postfix(["4", "13", "5", "/", "+"]) == 6      # 4 + (13//5=2)
assert eval_postfix(["10", "6", "-"]) == 4                # order matters!
# Time: O(n). Space: O(n).
```
