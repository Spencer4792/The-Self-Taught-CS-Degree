# Chapter 2.2 - Linked Lists

> _Goal: Stop treating "linked list" as a vocabulary word and start seeing the chain of nodes in your head. By the end of this chapter you'll be able to draw the pointers, build both flavors from scratch, derive every Big-O from first principles, prove the classic interview tricks (cycle detection, middle node) instead of memorizing them, and hand-roll the doubly linked list that an LRU cache rides on._

It's easy to know the words "node" and "pointer" and nod along when someone says "O(1) insertion." But if someone asked you to prove why Floyd's tortoise and hare must collide, you might mumble. This chapter fixes that. We build everything, test everything, and prove the non-obvious bits.

## Start here - a chain of clues

Before any code, let's build the picture you'll carry through the chapter. Forget memory and pointers for a second.

Imagine someone has set up a **treasure hunt** in the backyard. They hand you the first clue. That clue says two things:

1. A prize is taped to the back of this card (the value).
2. "The next clue is buried under the oak tree" (the address of the next node).

You read the prize, then walk to the oak tree and dig up the next card. That card has its own prize and its own instruction: "next clue is in the mailbox." And so on, until you reach a card that says "this is the last one, there is no next clue." That final "no next clue" is `None` (or `nullptr` in C++). The whole hunt is a starting clue plus each clue pointing you to the next.

That is exactly a linked list. Each card = a **node**. The prize on the card = the **value**. The instruction "next clue is at location X" = the **next pointer**. The thing handed to you to start = the **head**.

Now contrast that with the organized version from last chapter: a row of numbered lockers, 0, 1, 2, 3. If you want locker 47, you don't read 46 clues; you walk straight to it, because the lockers are physically lined up and you can compute where #47 is. That's an array: contiguous and instantly indexable, but rigid - to squeeze a new locker in between #2 and #3, you'd have to shove every later locker down by one.

The clue-hunt is the opposite: you can splice in a new clue anywhere by rewriting one instruction ("the next clue is actually under the rosebush now, and that one points to the old oak-tree clue"). No shoving. But you can never jump to the 47th clue without walking the whole chain.

### Why this matters

Three reasons, each of which pays off well beyond this chapter:

- **It's your first taste of indirection.** A node doesn't contain the next node; it contains where to find it. Once "a thing that holds the location of another thing" clicks, trees, graphs, hash-table buckets, and file systems all become variations on the same theme. Linked lists are the gentlest on-ramp to pointer thinking.
- **It makes the array trade-off real.** Until you've felt how cheap "splice into the middle" is for a list and how cheap "jump to index 47" is for an array, Big-O is just symbols. This chapter turns both into something you can see.
- **It's the engine under familiar tools.** The LRU cache at the end of this chapter - the pattern behind web caches, OS page replacement, and `functools.lru_cache` - rides on a linked list. Build it once and the box stops being black.

The takeaway to carry into the formal sections: a linked list is a chain of clues, each holding a value plus the location of the next clue, and the list itself is just the first clue. Everything below makes that precise.

## The mental model: a node holds data and an address

An array is one contiguous slab of memory. Element `i` lives at `base + i * size`. That's why `arr[i]` is O(1): it's just arithmetic.

A **linked list** throws that contiguity away. Instead, each element is a little box (a **node**) that holds two things:

1. the **value** (the payload), and
2. a **pointer** (a reference / an address) to the *next* node.

The list itself is just a reference to the first node, the **head**. You walk the chain by following `next` pointers until you hit `None` (the end).

```
head
 │
 ▼
┌─────┬───┐   ┌─────┬───┐   ┌─────┬───┐
│  3  │ ●─┼──▶│  7  │ ●─┼──▶│  9  │ ✕ │   (✕ = None)
└─────┴───┘   └─────┴───┘   └─────┴───┘
```

The crucial mental shift: the nodes are not next to each other in memory. Node `7` could be at address `0x1000` and node `9` at `0x40`; the only thing connecting them is that `7`'s pointer field literally stores `9`'s address. The list has *structure* (an order) without *contiguity*.

### Making the pointer concrete with C++

Python hides pointers behind names, which is why the idea can stay fuzzy. In C++ the pointer is explicit, so let's look at the raw `struct`:

```cpp
// A node is data + the address of the next node.
struct Node {
    int data;
    Node* next;   // a POINTER: literally stores the memory address of another Node
};

// Build 3 -> 7 -> 9 by hand:
Node* c = new Node{9, nullptr};   // tail: points to nothing
Node* b = new Node{7, c};         // 7 stores the address of node c
Node* a = new Node{3, b};         // 3 stores the address of node b
Node* head = a;                   // the list IS just this one pointer

// Walking it:
for (Node* cur = head; cur != nullptr; cur = cur->next) {
    std::cout << cur->data << " ";
}
// prints: 3 7 9
```

`Node* next` is the part that matters. `cur = cur->next` means "replace your hand-position with the address the current node is pointing at." When `next` is `nullptr`, the chain ends. In Python, a variable bound to a `Node` object is that reference: assigning `b = a` makes both names point at the same object, with no copy. Same idea, no asterisks.

> Note: in Python, `node.next = other` does not copy `other`. It makes `node.next` an alias to the same object. Linked lists are basically an exercise in aliasing on purpose.

## Complexity: why this trade exists at all

Here's the comparison that justifies the whole data structure. Let `n` be the number of elements.

| Operation | Array (dynamic) | Singly Linked | Doubly Linked | Why |
|---|---|---|---|---|
| Index access `a[i]` | **O(1)** | O(n) | O(n) | Array = arithmetic; list = walk i nodes |
| Insert/delete at **front** | O(n) | **O(1)** | **O(1)** | Array shifts everything; list just relinks head |
| Insert/delete at **back** | O(1)* amortized | O(n) / **O(1)†** | **O(1)** | †if you keep a `tail` pointer |
| Insert/delete at known node | O(n) (shift) | O(n) to find prev / O(1) if you have prev | **O(1)** | doubly list knows its `prev` |
| Search by value | O(n) | O(n) | O(n) | both scan linearly |
| Space overhead | low | +1 pointer/node | +2 pointers/node | the cost of flexibility |

\* amortized; a single resize is O(n) but it's rare, so on average O(1).

**Deriving the O(1) front-insert:** to prepend, you create a node, set its `next` to the old head, and reassign `head`. Three pointer writes, none of which depends on `n` - therefore O(1). Contrast the array: inserting at index 0 must shift all `n` existing elements one slot to the right, O(n).

**Deriving the O(n) index access:** to reach node `i`, you start at `head` and follow `next` exactly `i` times. That's `i` steps, and in the worst case (`i = n-1`) it's `n-1` ≈ O(n). There is no arithmetic shortcut because the nodes aren't contiguous; you have no idea where node `i` lives until you've walked there.

### The plot twist: arrays are usually faster in practice

On paper a linked list looks great. In practice, for most workloads, an array (`list` in Python, `std::vector` in C++) beats a linked list even for operations where the list has the better asymptotic complexity. Why?

**Cache locality.** Modern CPUs don't read one byte from RAM; they pull in a whole **cache line** (typically 64 bytes) at a time, betting you'll want the neighbors next. An array stores elements contiguously, so iterating it is a dream: each cache line holds ~16 ints, and the prefetcher sees the linear pattern and loads the next line before you ask. You get near-zero cache misses.

A linked list scatters nodes all over the heap. Following `next` is a **pointer chase**: the address you need next isn't known until you've read the current node, and it lands on a totally different cache line. Every hop is a potential cache miss, and a cache miss can cost ~100x a cache hit. So "O(n) traversal" for an array and "O(n) traversal" for a list have the same Big-O but wildly different constant factors.

The takeaway: Big-O hides the constant. Use a linked list when you need O(1) splice given a node reference and you're not iterating constantly - the LRU cache at the end of this chapter is the poster child. Otherwise reach for an array.

## Build it: a singly linked list from scratch

Let's build the real thing. We'll keep a `head` and a `tail` (so `append` is O(1)) and a `_size` counter (so `__len__` is O(1) instead of O(n)).

**Invariants** to maintain (write these down; they're how you reason about correctness):
- `head is None` **iff** the list is empty **iff** `_size == 0`.
- If non-empty, `tail` is the last node and `tail.next is None`.
- Following `next` from `head` visits exactly `_size` nodes and terminates at `None` (no cycles).

```python
class Node:
    """One link in the chain: a value plus a pointer to the next node."""
    __slots__ = ("value", "next")  # tiny memory win; also documents the fields

    def __init__(self, value, next=None):
        self.value = value
        self.next = next

    def __repr__(self):
        return f"Node({self.value!r})"


class SinglyLinkedList:
    def __init__(self, iterable=None):
        self.head = None
        self.tail = None
        self._size = 0
        if iterable is not None:
            for x in iterable:
                self.append(x)

    # ---- O(1) housekeeping --------------------------------------------
    def __len__(self):
        return self._size

    def is_empty(self):
        return self._size == 0

    def __iter__(self):
        """Yield values front-to-back. Lets us do `for v in lst` and list(lst)."""
        cur = self.head
        while cur is not None:
            yield cur.value
            cur = cur.next

    def __repr__(self):
        return "SinglyLinkedList([" + ", ".join(repr(v) for v in self) + "])"

    # ---- mutation -----------------------------------------------------
    def prepend(self, value):
        """Insert at the front. O(1)."""
        node = Node(value, next=self.head)
        self.head = node
        if self.tail is None:        # was empty -> new node is also the tail
            self.tail = node
        self._size += 1

    def append(self, value):
        """Insert at the back. O(1) thanks to the tail pointer."""
        node = Node(value)
        if self.tail is None:        # empty list
            self.head = self.tail = node
        else:
            self.tail.next = node
            self.tail = node
        self._size += 1

    def insert(self, index, value):
        """Insert so that the new value ends up at position `index`. O(n)
        because we must walk to index-1 first."""
        if index < 0 or index > self._size:
            raise IndexError(f"index {index} out of range for size {self._size}")
        if index == 0:
            self.prepend(value)
            return
        if index == self._size:
            self.append(value)
            return
        # Walk to the node BEFORE the insertion point.
        prev = self.head
        for _ in range(index - 1):
            prev = prev.next
        prev.next = Node(value, next=prev.next)
        self._size += 1

    def delete(self, value):
        """Remove the first node whose value == `value`. Returns True if found.
        O(n) to locate it."""
        prev, cur = None, self.head
        while cur is not None:
            if cur.value == value:
                if prev is None:               # deleting the head
                    self.head = cur.next
                else:
                    prev.next = cur.next
                if cur is self.tail:           # deleted the tail -> fix it
                    self.tail = prev
                self._size -= 1
                return True
            prev, cur = cur, cur.next
        return False

    def search(self, value):
        """Return the 0-based index of `value`, or -1. O(n)."""
        for i, v in enumerate(self):
            if v == value:
                return i
        return -1
```

### Traced walkthrough - pointers changing step by step

Reading the code is one thing; watching the pointers move is what makes it stick. Let's build a list from empty and then delete from the middle, drawing the exact state after every operation. We'll start with a brand-new empty list:

```
head = None
tail = None
_size = 0
```

**Step 1, `prepend(2)`** into an empty list. We make a node `2`, point its `next` at the old head (`None`), set `head = node`, and because `tail` was `None`, `tail` also becomes this node.

```
head ─┐
tail ─┴─▶ ┌───┬───┐
          │ 2 │ ✕ │   (✕ = None)
          └───┴───┘
_size = 1
```

**Step 2, `prepend(1)`.** New node `1` gets its `next` set to the current head (the `2` node), then `head` moves to `1`. `tail` is untouched; it still points at `2`.

```
head ─▶ ┌───┬───┐   ┌───┬───┐
        │ 1 │ ●─┼──▶│ 2 │ ✕ │ ◀─ tail
        └───┴───┘   └───┴───┘
_size = 2
```

**Step 3, `append(3)`.** New node `3` with `next = None`. We hook the *old tail's* `next` to it (`tail.next = node`), then advance `tail` to `3`. Head is untouched.

```
head ─▶ ┌───┬───┐   ┌───┬───┐   ┌───┬───┐
        │ 1 │ ●─┼──▶│ 2 │ ●─┼──▶│ 3 │ ✕ │ ◀─ tail
        └───┴───┘   └───┴───┘   └───┴───┘
_size = 3
```

**Step 4, `append(4)`.** Same dance: `tail.next` (the `3` node) gets pointed at the new `4`, then `tail` advances.

```
head ─▶ ┌───┬───┐   ┌───┬───┐   ┌───┬───┐   ┌───┬───┐
        │ 1 │ ●─┼──▶│ 2 │ ●─┼──▶│ 3 │ ●─┼──▶│ 4 │ ✕ │ ◀─ tail
        └───┴───┘   └───┴───┘   └───┴───┘   └───┴───┘
_size = 4
```

Now the interesting one: `delete(3)`, removing a node in the middle. The walk uses two cursors, `prev` and `cur`. Watch them slide.

**Walk, iteration 0:** `prev = None`, `cur` = the `1` node. `cur.value (1) != 3`, so we step: `prev, cur = cur, cur.next`.

```
        prev=None
                 cur
                  ▼
head ─▶ ┌───┬───┐   ┌───┬───┐   ┌───┬───┐   ┌───┬───┐
        │ 1 │ ●─┼──▶│ 2 │ ●─┼──▶│ 3 │ ●─┼──▶│ 4 │ ✕ │
        └───┴───┘   └───┴───┘   └───┴───┘   └───┴───┘
```

**Iteration 1:** `prev` = `1` node, `cur` = `2` node. `2 != 3`, step again.

```
          prev      cur
            ▼         ▼
head ─▶ ┌───┬───┐   ┌───┬───┐   ┌───┬───┐   ┌───┬───┐
        │ 1 │ ●─┼──▶│ 2 │ ●─┼──▶│ 3 │ ●─┼──▶│ 4 │ ✕ │
        └───┴───┘   └───┴───┘   └───┴───┘   └───┴───┘
```

**Iteration 2:** `prev` = `2` node, `cur` = `3` node. A match: `cur.value == 3`. `prev` is not `None`, so we splice: `prev.next = cur.next`. That makes the `2` node point straight at the `4` node, skipping `3` entirely. The `3` node is now unreachable (Python's GC will reclaim it).

```
                    prev      cur (about to be unlinked)
                      ▼         ▼
head ─▶ ┌───┬───┐   ┌───┬───┐   ┌───┬───┐   ┌───┬───┐
        │ 1 │ ●─┼──▶│ 2 │ ●─┐   │ 3 │ ●─┼──▶│ 4 │ ✕ │
        └───┴───┘   └───┴─│─┘   └───┴───┘   └───┴───┘
                          └──────────────────▲
                          (prev.next = cur.next bypasses node 3)
```

`cur` (the `3` node) is **not** the tail, so `tail` stays on `4`. We decrement `_size`. After the dust settles and the orphaned `3` is collected:

```
head ─▶ ┌───┬───┐   ┌───┬───┐   ┌───┬───┐
        │ 1 │ ●─┼──▶│ 2 │ ●─┼──▶│ 4 │ ✕ │ ◀─ tail
        └───┴───┘   └───┴───┘   └───┴───┘
_size = 3
```

Two lessons from this trace: (1) the only way to remove `cur` in a singly linked list is to reach in from `prev` and re-route its pointer - `cur` can't excise itself because it doesn't know who points at it; and (2) the tail-fixup check (`if cur is self.tail`) only fires when we delete the last node. It didn't fire here, which is exactly why deleting the actual tail is the bug-prone case to test separately.

### The unobvious part: why `prev` matters in a singly list

In `delete`, you track `prev` as you walk. That's forced by the structure: to splice out `cur`, you need to set `prev.next = cur.next`. But a singly linked node has no back-pointer; from `cur` alone you can't find who points at it. So you have to carry `prev` along during the walk. (The doubly linked list fixes this; that's its whole reason to exist.)

### Tests (pytest-style)

```python
def test_singly_linked_list():
    # build + iterate + repr
    lst = SinglyLinkedList([1, 2, 3])
    assert list(lst) == [1, 2, 3]
    assert len(lst) == 3
    assert repr(lst) == "SinglyLinkedList([1, 2, 3])"

    # prepend / append touch head & tail correctly
    lst.prepend(0)
    lst.append(4)
    assert list(lst) == [0, 1, 2, 3, 4]
    assert lst.head.value == 0
    assert lst.tail.value == 4
    assert len(lst) == 5

    # insert in the middle, at front, at end
    lst.insert(2, 99)
    assert list(lst) == [0, 1, 99, 2, 3, 4]
    lst.insert(0, -1)
    assert list(lst)[0] == -1
    lst.insert(len(lst), 100)
    assert list(lst)[-1] == 100 and lst.tail.value == 100

    # search
    assert lst.search(99) == 3
    assert lst.search(12345) == -1

    # delete head, middle, tail; check tail/head stay consistent
    assert lst.delete(-1) is True          # head
    assert lst.head.value == 0
    assert lst.delete(99) is True          # middle
    assert lst.delete(100) is True         # tail
    assert lst.tail.value == 4
    assert lst.delete(100) is False        # already gone
    assert list(lst) == [0, 1, 2, 3, 4]

    # empty-list edge cases
    empty = SinglyLinkedList()
    assert empty.is_empty() and len(empty) == 0
    assert empty.search(1) == -1 and empty.delete(1) is False

    assert empty.head is empty.tail and empty.head.value == 7
    print("singly: all tests passed")

test_singly_linked_list()
```

Run it; it passes. The empty-list and tail-deletion cases are exactly where bugs sneak in when the invariants aren't written down.

## Build it: a doubly linked list from scratch

The doubly linked list adds a `prev` pointer to every node. Now each node knows both its neighbors, which buys us O(1) deletion given a node reference - no `prev`-tracking walk required. We'll use a sentinel-free design with explicit `head`/`tail` here for clarity (we'll see sentinels in the mini-project, where they remove edge cases).

**Invariants:**
- `head is None` iff `tail is None` iff `_size == 0`.
- `head.prev is None` and `tail.next is None`.
- For any interior node `x`: `x.prev.next is x` and `x.next.prev is x`. (The links are mutually consistent; this is the property to check after every operation.)

```python
class DNode:
    __slots__ = ("value", "prev", "next")

    def __init__(self, value, prev=None, next=None):
        self.value = value
        self.prev = prev
        self.next = next

    def __repr__(self):
        return f"DNode({self.value!r})"


class DoublyLinkedList:
    def __init__(self, iterable=None):
        self.head = None
        self.tail = None
        self._size = 0
        if iterable is not None:
            for x in iterable:
                self.append(x)

    def __len__(self):
        return self._size

    def is_empty(self):
        return self._size == 0

    def __iter__(self):
        cur = self.head
        while cur is not None:
            yield cur.value
            cur = cur.next

    def __reversed__(self):
        """A doubly linked list can be walked backwards for free."""
        cur = self.tail
        while cur is not None:
            yield cur.value
            cur = cur.prev

    def __repr__(self):
        return "DoublyLinkedList([" + ", ".join(repr(v) for v in self) + "])"

    # ---- mutation -----------------------------------------------------
    def prepend(self, value):
        """O(1)."""
        node = DNode(value, prev=None, next=self.head)
        if self.head is None:
            self.head = self.tail = node
        else:
            self.head.prev = node
            self.head = node
        self._size += 1
        return node

    def append(self, value):
        """O(1)."""
        node = DNode(value, prev=self.tail, next=None)
        if self.tail is None:
            self.head = self.tail = node
        else:
            self.tail.next = node
            self.tail = node
        self._size += 1
        return node

    def remove_node(self, node):
        """Unlink a node we already hold a reference to. THE key operation: O(1).
        No search, no prev-tracking - the node knows both neighbors."""
        p, n = node.prev, node.next
        if p is not None:
            p.next = n
        else:                      # node was the head
            self.head = n
        if n is not None:
            n.prev = p
        else:                      # node was the tail
            self.tail = p
        node.prev = node.next = None   # detach fully (helps GC, prevents misuse)
        self._size -= 1

    def delete(self, value):
        """Find by value (O(n)) then unlink (O(1))."""
        cur = self.head
        while cur is not None:
            if cur.value == value:
                self.remove_node(cur)
                return True
            cur = cur.next
        return False

    def insert(self, index, value):
        """Insert at position `index`. O(n) walk to the spot, O(1) splice.
        Small optimization: walk from whichever end is closer."""
        if index < 0 or index > self._size:
            raise IndexError(f"index {index} out of range for size {self._size}")
        if index == 0:
            self.prepend(value); return
        if index == self._size:
            self.append(value); return
        # locate the node currently at `index`; we'll insert before it
        if index <= self._size // 2:
            cur = self.head
            for _ in range(index):
                cur = cur.next
        else:
            cur = self.tail
            for _ in range(self._size - 1 - index):
                cur = cur.prev
        # splice new node in BEFORE cur
        node = DNode(value, prev=cur.prev, next=cur)
        cur.prev.next = node
        cur.prev = node
        self._size += 1

    def search(self, value):
        for i, v in enumerate(self):
            if v == value:
                return i
        return -1
```

### Why `remove_node` matters

Look at `remove_node`: given only the node, you rewire four pointers (`p.next`, `n.prev`, plus head/tail fixups) and you're done, with zero dependence on `n`. That O(1) removal by reference is impossible in a singly linked list and is exactly what an LRU cache needs. Hold that thought.

### Tests

```python
def test_doubly_linked_list():
    d = DoublyLinkedList([10, 20, 30])
    assert list(d) == [10, 20, 30]
    assert list(reversed(d)) == [30, 20, 10]
    assert len(d) == 3
    assert repr(d) == "DoublyLinkedList([10, 20, 30])"

    d.prepend(5)
    d.append(40)
    assert list(d) == [5, 10, 20, 30, 40]
    assert d.head.value == 5 and d.tail.value == 40

    # insert from both halves (exercises the "closer end" optimization)
    d.insert(1, 7)          # near front
    d.insert(5, 99)         # near back
    assert list(d) == [5, 7, 10, 20, 30, 99, 40]

    # the marquee operation: O(1) removal by reference
    mid = d.head.next.next   # node holding 10
    assert mid.value == 10
    d.remove_node(mid)
    assert list(d) == [5, 7, 20, 30, 99, 40]
    assert mid.prev is None and mid.next is None   # fully detached

    # delete by value at head / tail / missing
    assert d.delete(5) is True and d.head.value == 7
    assert d.delete(40) is True and d.tail.value == 99
    assert d.delete(123) is False

    # invariant check: every link is mutually consistent
    cur = d.head
    while cur is not None and cur.next is not None:
        assert cur.next.prev is cur
        cur = cur.next
    assert d.tail is cur          # walked to the actual tail

    # remove the only element
    one = DoublyLinkedList([42])
    one.remove_node(one.head)
    assert one.is_empty() and one.head is None and one.tail is None
    print("doubly: all tests passed")

test_doubly_linked_list()
```

## Classic problem 1 - reverse a singly linked list in place

Reverse the chain so `1→2→3→None` becomes `3→2→1→None`, reusing the same nodes (no new allocations). This is the canonical pointer-walk exercise.

The intuition: you sweep through the list flipping each `next` pointer to point backwards. The danger is that the instant you do `cur.next = prev`, you've destroyed your link to the rest of the list. So before flipping, you must stash `cur.next` in a temp.

The three-pointer dance - `prev`, `cur`, `nxt`:

```
prev   cur        nxt
 │      │          │
✕    ┌──▼──┐    ┌──▼──┐    ┌─────┐
None │  1  │───▶│  2  │───▶│  3  │──▶ None
     └─────┘    └─────┘    └─────┘

Step: save nxt = cur.next; flip cur.next = prev; advance prev=cur, cur=nxt.
```

```python
def reverse(self):
    """Reverse the singly linked list in place. O(n) time, O(1) extra space."""
    prev = None
    cur = self.head
    self.tail = self.head          # old head becomes the new tail
    while cur is not None:
        nxt = cur.next             # 1. stash the rest of the list
        cur.next = prev            # 2. flip this node's pointer backwards
        prev = cur                 # 3. advance prev
        cur = nxt                  # 4. advance cur
    self.head = prev               # prev now sits on the old last node
    return self

# attach to the class
SinglyLinkedList.reverse = reverse
```

**Why O(n)/O(1):** each node is visited exactly once and does a constant amount of pointer-shuffling → O(n) time. You only ever hold three pointers regardless of list size → O(1) extra space. (Compare to building a new reversed list, which would be O(n) space.)

**Why it's correct (invariant):** at the top of each loop iteration, `prev` heads a correctly-reversed prefix of the nodes already consumed, and `cur` heads the untouched suffix. The body extends the reversed prefix by one node while shrinking the suffix by one. When `cur` becomes `None`, the suffix is empty and `prev` heads the fully reversed list.

```python
def test_reverse():
    lst = SinglyLinkedList([1, 2, 3, 4, 5])
    lst.reverse()
    assert list(lst) == [5, 4, 3, 2, 1]
    assert lst.head.value == 5 and lst.tail.value == 1
    assert lst.tail.next is None          # new tail terminates cleanly

    # edge cases
    single = SinglyLinkedList([7]); single.reverse()
    assert list(single) == [7] and single.head is single.tail
    empty = SinglyLinkedList(); empty.reverse()
    assert list(empty) == [] and empty.head is None
    print("reverse: all tests passed")

test_reverse()
```

## Classic problem 2 - detect a cycle (Floyd's tortoise & hare), with proof

A cycle means some node's `next` points back to an earlier node, so a naive walk loops forever. **Floyd's algorithm** detects this in O(n) time and O(1) space using two pointers moving at different speeds:

- **Tortoise** advances 1 node per step.
- **Hare** advances 2 nodes per step.

If there's no cycle, the hare runs off the end (`None`) and we return `False`. If there is a cycle, the hare gets trapped in the loop, the tortoise eventually enters too, and - this is the claim we'll prove - the hare must catch the tortoise.

```python
def has_cycle(head):
    """Floyd's tortoise & hare. O(n) time, O(1) space."""
    slow = fast = head
    while fast is not None and fast.next is not None:
        slow = slow.next            # +1
        fast = fast.next.next       # +2
        if slow is fast:            # identity check - same node object
            return True
    return False                    # fast reached the end -> no cycle
```

### Proof that the hare *must* meet the tortoise

This is the part that's easy to hand-wave. Let's actually prove it.

Suppose the list has a "tail" of `μ` non-cycle nodes leading into a cycle of length `λ`. Once **both** pointers are inside the cycle, label positions by distance around the loop mod `λ`. Let the tortoise be at position `t` and the hare at position `h` (both mod `λ`).

Each step, the tortoise moves `+1` and the hare moves `+2`. Define the **gap** the hare needs to close as `d = (t - h) mod λ` - how far ahead the tortoise is, going around the loop. After one step:

```
new gap = ((t + 1) - (h + 2)) mod λ = (t - h - 1) mod λ = (d - 1) mod λ
```

So the gap shrinks by exactly 1 (mod λ) every step. Starting from some gap `d₀` with `0 ≤ d₀ < λ`, after exactly `d₀` steps the gap is `0`, meaning `t ≡ h (mod λ)`, i.e. they occupy the same node. Since the gap strictly decreases by 1 each step and is bounded below by 0 inside a finite cycle, collision is guaranteed in at most `λ` steps once both are in the loop.

Intuition restated: relative to the tortoise, the hare gains exactly 1 position per step. In a circular track of length `λ`, gaining 1 per step means you close any gap in at most `λ` steps; you can't jump over the tortoise without landing on it, because the closing speed is exactly 1, not 2 or more. (If the hare moved 3x, it could leapfrog and you'd need a number-theory argument about `gcd`; at speed difference exactly 1, collision is forced.) ∎

```python
def test_cycle():
    # no cycle
    a, b, c = Node(1), Node(2), Node(3)
    a.next, b.next = b, c
    assert has_cycle(a) is False

    # cycle: c points back to b  (1 -> 2 -> 3 -> back to 2)
    c.next = b
    assert has_cycle(a) is True

    # single node pointing to itself
    s = Node(0); s.next = s
    assert has_cycle(s) is True

    # empty / single acyclic
    assert has_cycle(None) is False
    lone = Node(9)
    assert has_cycle(lone) is False
    print("cycle: all tests passed")

test_cycle()
```

## Classic problem 3 - find the middle node in one pass

You could find the length (one pass) then walk to `n//2` (another pass). But the two-pointer trick does it in a single pass. Same tortoise/hare idea, different purpose:

- Slow moves 1 step, fast moves 2.
- When fast reaches the end, slow is at the middle.

Why? Fast covers twice the ground. When fast has travelled `n` nodes (the end), slow has travelled `n/2` - the middle. It's just a rate argument.

```python
def middle_node(head):
    """Return the middle node in one pass. For even length, returns the
    SECOND of the two middles (LeetCode convention). O(n) time, O(1) space."""
    slow = fast = head
    while fast is not None and fast.next is not None:
        slow = slow.next
        fast = fast.next.next
    return slow

def test_middle():
    odd = SinglyLinkedList([1, 2, 3, 4, 5])
    assert middle_node(odd.head).value == 3
    even = SinglyLinkedList([1, 2, 3, 4, 5, 6])
    assert middle_node(even.head).value == 4   # second middle
    one = SinglyLinkedList([99])
    assert middle_node(one.head).value == 99
    assert middle_node(None) is None
    print("middle: all tests passed")

test_middle()
```

> For "first middle" on even lengths, start `fast = head.next` instead. A tiny tweak, but worth knowing which convention an interviewer wants.

## Mini-project - a doubly linked list that backs an LRU cache

Time to cash in everything. An **LRU (Least Recently Used) cache** holds up to `capacity` key→value pairs. On every access (get or put), the touched item becomes "most recently used." When the cache is full and a new key arrives, we **evict the least recently used** item. The contract: `get` and `put` should both be **O(1)**.

**How a linked list makes this O(1):** keep a doubly linked list ordered by recency, most-recently-used at the front, least-recently-used at the back. Pair it with a dict mapping `key → node` so we can find any node in O(1). Then:
- **Touch an item:** O(1) `remove_node` + O(1) `prepend`. This is "move-to-front."
- **Evict:** drop the `tail` node, O(1).
- **Find:** the dict gives us the node instantly, O(1).

This is precisely why we built `remove_node` to take a node reference and run in O(1). A singly linked list couldn't do the move-to-front in O(1) (no back-pointer to splice cleanly), and an array couldn't either (move-to-front = O(n) shift). The doubly linked list is the right tool.

We'll use **sentinel** head/tail dummy nodes here. Sentinels are fake boundary nodes that always exist, so you never have to special-case "is this the head/tail?" - every real node has real neighbors. Fewer `if` branches, fewer bugs.

```python
class _LRUNode:
    __slots__ = ("key", "value", "prev", "next")
    def __init__(self, key=None, value=None):
        self.key = key
        self.value = value
        self.prev = None
        self.next = None


class LRUCache:
    def __init__(self, capacity):
        if capacity <= 0:
            raise ValueError("capacity must be positive")
        self.capacity = capacity
        self.map = {}                      # key -> _LRUNode
        # sentinel boundary nodes: head <-> ... <-> tail
        self.head = _LRUNode()             # MRU side
        self.tail = _LRUNode()             # LRU side
        self.head.next = self.tail
        self.tail.prev = self.head

    # ---- O(1) doubly-linked primitives -------------------------------
    def _remove(self, node):
        """Unlink a real node. O(1). (Sentinels mean prev/next are never None.)"""
        node.prev.next = node.next
        node.next.prev = node.prev

    def _add_front(self, node):
        """Insert right after head (the MRU position). O(1)."""
        node.prev = self.head
        node.next = self.head.next
        self.head.next.prev = node
        self.head.next = node

    def _move_to_front(self, node):
        """The LRU 'touch'. O(1): remove + re-add at front."""
        self._remove(node)
        self._add_front(node)

    # ---- public API ---------------------------------------------------
    def get(self, key):
        """Return value & mark most-recently-used, or None if absent. O(1)."""
        node = self.map.get(key)
        if node is None:
            return None
        self._move_to_front(node)
        return node.value

    def put(self, key, value):
        """Insert/update & mark most-recently-used; evict LRU if over capacity. O(1)."""
        node = self.map.get(key)
        if node is not None:               # update existing
            node.value = value
            self._move_to_front(node)
            return
        node = _LRUNode(key, value)        # brand new key
        self.map[key] = node
        self._add_front(node)
        if len(self.map) > self.capacity:  # evict LRU = node before tail sentinel
            lru = self.tail.prev
            self._remove(lru)
            del self.map[lru.key]

    def __len__(self):
        return len(self.map)

    def keys_mru_to_lru(self):
        """Helper for tests: real keys from most- to least-recently-used."""
        out, cur = [], self.head.next
        while cur is not self.tail:
            out.append(cur.key)
            cur = cur.next
        return out
```

### Tests

```python
def test_lru_cache():
    c = LRUCache(2)
    c.put(1, "a")
    c.put(2, "b")
    assert c.keys_mru_to_lru() == [2, 1]      # 2 is most recent

    assert c.get(1) == "a"                     # touch 1 -> now MRU
    assert c.keys_mru_to_lru() == [1, 2]

    c.put(3, "c")                              # over capacity -> evict LRU (2)
    assert c.get(2) is None                    # 2 was evicted
    assert c.keys_mru_to_lru() == [3, 1]
    assert len(c) == 2

    c.put(1, "A")                              # update existing -> MRU, no growth
    assert c.get(1) == "A"
    assert c.keys_mru_to_lru() == [1, 3]
    assert len(c) == 2

    c.put(4, "d")                              # evict LRU (3)
    assert c.get(3) is None
    assert c.keys_mru_to_lru() == [4, 1]

    # capacity-1 cache: every put evicts the previous
    tiny = LRUCache(1)
    tiny.put("x", 1); tiny.put("y", 2)
    assert tiny.get("x") is None and tiny.get("y") == 2
    print("LRU: all tests passed")

test_lru_cache()
```

Every public operation here is O(1): the dict gives O(1) lookup, and the doubly linked list gives O(1) splice. That's the payoff of the chapter: the data structure isn't academic - it's the engine behind `functools.lru_cache`, OS page caches, and database buffer pools.

> Reality check, same as before: Python's own `OrderedDict` (and `functools.lru_cache`) already do this in C, so in real code you'd reach for those. But building it once means you now know what's inside the box.

## Extra practice - a music-playlist doubly linked list

The LRU cache showed off `remove_node`. This second mini-project shows off the other thing a doubly linked list does well: walking in both directions and cycling around. A music playlist is a natural fit: you hit "next" and "previous" constantly, you want the list to wrap around when you reach the end, and "shuffle" should rearrange the chain without losing your place.

We'll build it on top of the same `DNode` idea, but the cursor (`current`) is what makes it a playlist rather than a plain list: it remembers which song is "now playing," and `next_track`/`prev_track` move that cursor. When the cursor would fall off either end, it wraps, so this behaves like a circular traversal even though the underlying links are a normal doubly linked list with `None` at both ends.

```python
import random


class _Track:
    __slots__ = ("title", "prev", "next")
    def __init__(self, title):
        self.title = title
        self.prev = None
        self.next = None

    def __repr__(self):
        return f"_Track({self.title!r})"


class Playlist:
    """A doubly linked list of songs with a 'now playing' cursor.

    next_track / prev_track move the cursor and WRAP around the ends, so
    the playlist plays in an endless loop like a real music app.
    """
    def __init__(self, titles=None):
        self.head = None          # first song
        self.tail = None          # last song
        self.current = None       # the 'now playing' cursor
        self._size = 0
        if titles:
            for t in titles:
                self.add(t)

    def __len__(self):
        return self._size

    def __iter__(self):
        cur = self.head
        while cur is not None:
            yield cur.title
            cur = cur.next

    def add(self, title):
        """Append a song to the end. O(1). The first song added becomes
        'now playing'."""
        node = _Track(title)
        if self.tail is None:
            self.head = self.tail = node
            self.current = node          # first song auto-selected
        else:
            node.prev = self.tail
            self.tail.next = node
            self.tail = node
        self._size += 1
        return node

    def now_playing(self):
        """Title of the current song, or None if the playlist is empty."""
        return self.current.title if self.current else None

    def next_track(self):
        """Advance the cursor; wrap to the head after the tail. O(1)."""
        if self.current is None:
            return None
        self.current = self.current.next or self.head   # wrap-around
        return self.current.title

    def prev_track(self):
        """Back the cursor up; wrap to the tail before the head. O(1)."""
        if self.current is None:
            return None
        self.current = self.current.prev or self.tail   # wrap-around
        return self.current.title

    def remove(self, title):
        """Remove the first song with this title. O(n) to find, O(1) to unlink.
        If the removed song was 'now playing', the cursor advances to the next
        (wrapping), or becomes None if the playlist is now empty."""
        cur = self.head
        while cur is not None and cur.title != title:
            cur = cur.next
        if cur is None:
            return False
        # decide where the cursor goes if we're deleting the current song
        if cur is self.current:
            self.current = cur.next or cur.prev   # next, else prev, else None
        # unlink cur (O(1) thanks to prev/next)
        if cur.prev is not None:
            cur.prev.next = cur.next
        else:
            self.head = cur.next
        if cur.next is not None:
            cur.next.prev = cur.prev
        else:
            self.tail = cur.prev
        cur.prev = cur.next = None
        self._size -= 1
        return True

    def shuffle(self, seed=None):
        """Randomly reorder the songs and rebuild the chain. O(n).
        Keeps the SAME song 'now playing' (cursor follows its node)."""
        if self._size <= 1:
            return
        nodes = []
        cur = self.head
        while cur is not None:
            nodes.append(cur)
            cur = cur.next
        rng = random.Random(seed)
        rng.shuffle(nodes)
        # relink in the new order
        self.head = nodes[0]
        self.tail = nodes[-1]
        for i, node in enumerate(nodes):
            node.prev = nodes[i - 1] if i > 0 else None
            node.next = nodes[i + 1] if i < len(nodes) - 1 else None
        # self.current still points at the SAME node object, now relinked,
        # so "now playing" is preserved across the shuffle.
```

### Tests with expected output

```python
def test_playlist():
    pl = Playlist(["Intro", "Verse", "Chorus", "Outro"])
    assert list(pl) == ["Intro", "Verse", "Chorus", "Outro"]
    assert len(pl) == 4
    assert pl.now_playing() == "Intro"          # first song auto-selected

    # walk forward with wrap-around
    assert pl.next_track() == "Verse"
    assert pl.next_track() == "Chorus"
    assert pl.next_track() == "Outro"
    assert pl.next_track() == "Intro"           # wrapped past the tail
    print("forward+wrap ok ->", pl.now_playing())

    # walk backward with wrap-around
    assert pl.prev_track() == "Outro"           # wrapped before the head
    assert pl.prev_track() == "Chorus"
    print("backward+wrap ok ->", pl.now_playing())

    # remove the currently-playing song -> cursor advances
    assert pl.now_playing() == "Chorus"
    assert pl.remove("Chorus") is True
    assert list(pl) == ["Intro", "Verse", "Outro"]
    assert pl.now_playing() == "Outro"          # advanced to next
    assert pl.remove("Nope") is False

    # remove the tail while it's current -> cursor falls back to prev
    pl.current = pl.tail                          # now playing "Outro"
    assert pl.now_playing() == "Outro"
    pl.remove("Outro")
    assert list(pl) == ["Intro", "Verse"]
    assert pl.now_playing() == "Verse"           # no next, so prev

    # shuffle is deterministic with a seed and preserves 'now playing'
    pl2 = Playlist(["a", "b", "c", "d", "e"])
    pl2.current = pl2.head.next                   # now playing "b"
    pl2.shuffle(seed=42)
    order = list(pl2)
    assert sorted(order) == ["a", "b", "c", "d", "e"]   # same songs
    assert pl2.now_playing() == "b"                       # cursor preserved
    # links are mutually consistent after shuffle
    cur = pl2.head
    while cur is not None and cur.next is not None:
        assert cur.next.prev is cur
        cur = cur.next
    assert pl2.tail is cur
    print("shuffle order (seed=42):", order)
    print("playlist: all tests passed")

test_playlist()
```

**Expected output when you run it:**

```
forward+wrap ok -> Intro
backward+wrap ok -> Chorus
shuffle order (seed=42): ['d', 'b', 'c', 'e', 'a']
playlist: all tests passed
```

(The exact shuffle order depends on your Python version's `random` implementation; the `sorted()` and consistency asserts are what actually matter. On CPython 3.x the seed-42 order above is what you get; if yours differs, that's fine - the structural invariants still hold.)

Two design notes worth remembering. First, the cursor surviving a shuffle for free is the payoff of object identity: `self.current` points at a node object, and `shuffle` only rewires `prev`/`next` on those same objects - it never creates new ones - so the cursor keeps "playing" the same song. Second, wrap-around is just `or`: `self.current.next or self.head` reads as "the next node, but if that's `None`, loop back to the head." That single idiom turns a plain doubly linked list into a ring without ever storing an actual back-edge from tail to head.

## Common mistakes

These are the bugs you will write if you're not careful, collected so you can pattern-match the symptom back to the cause.

1. **Losing the rest of the list by reassigning `next` before saving it.** In `reverse`, if you write `cur.next = prev` before `nxt = cur.next`, you've overwritten your only link to the remainder; the rest of the list is unreachable and the loop dies after one node. **Always stash `nxt = cur.next` first.** This is the single most common pointer bug.

2. **Forgetting to update `tail` on delete.** If you delete the last node but only fix `prev.next = cur.next` (= `None`), `self.tail` still points at the removed node. The next `append` then hooks onto a node that's no longer in the list and silently corrupts everything. The guard `if cur is self.tail: self.tail = prev` exists for exactly this. (Mirror bug: forgetting the `head` update when deleting the first node.)

3. **`None` / null dereference on the empty list.** Calling `head.next` when `head is None` throws `AttributeError`. Every traversal and every "peek at the first/last node" must check the empty case first. In Floyd's, this is why the loop condition is `while fast is not None and fast.next is not None` - order matters, because `fast.next` would blow up if `fast` were already `None`.

4. **Off-by-one walking to "index − 1".** To insert at index `k`, you must stop at the node before it, so you loop `range(k - 1)`, not `range(k)`. Loop `range(k)` and you land on index `k` and insert in the wrong place; handle `k == 0` separately (there is no "node before the head"). This one is easy to get wrong when tired; count the steps on a 3-node example before trusting the loop.

5. **Using `==` instead of `is` for node identity in cycle detection.** Floyd's collision test is `if slow is fast`: you're asking "are these the same node object?", not "do they hold equal values?". If you write `slow == fast` and two different nodes happen to hold the same value, you'll report a phantom cycle. Identity (`is`) for nodes, equality (`==`) for payloads.

6. **Creating a cycle accidentally.** Writing `tail.next = head` "to be circular," or splicing a node back in without clearing its old `next`, quietly turns a linear list into a cyclic one. Then any value-search or `list(lst)` loops forever. If a normally-instant traversal hangs, suspect an accidental self-link.

7. **Forgetting to decrement (or increment) `_size`.** Every mutation must keep `_size` in lockstep with reality. Delete a node but skip `self._size -= 1` and now `__len__` lies, "is empty?" checks go wrong, and the doubly linked list's walk-from-the-closer-end math in `insert` runs off the end. The counter is an invariant, not a convenience; update it on every path, including early returns.

8. **Infinite loop when traversing a cyclic list.** A plain `while cur is not None` assumes the list terminates. If a cycle ever sneaks in (see #6), that loop never ends. When you're unsure whether input is acyclic, especially in interview "given an arbitrary list" problems, either run Floyd's first or cap the walk at `_size` steps so a bug fails loudly instead of hanging.

## On the job / interview angle

Linked lists are the classic pointer-manipulation interview topic, and it's not an accident. They strip away the comfort of `arr[i]` and force you to manipulate references directly - track `prev`, splice nodes, juggle two cursors - which is precisely the skill interviewers are probing. The data structure is small enough to whiteboard from scratch in a minute, yet the operations expose every bug class above. If you can do these clean, under pressure, you've demonstrated you can reason about references and mutation, which transfers to trees and graphs.

Almost every linked-list problem is solved by one of three moves: (a) the runner / two-pointer technique (one cursor ahead of another), (b) careful in-place pointer rewiring with a saved temp, or (c) a dummy/sentinel head to kill the "what if it's the first node?" edge case. Spot which move a problem wants and most of the work is done.

The six (plus a couple bonus) questions you should be able to derive cold:

1. **Reverse a linked list (iterative + recursive).** *Iterative:* the three-pointer `prev/cur/nxt` dance from this chapter, O(n) time, O(1) space, and it's the one to lead with because of the space win. *Recursive:* recurse to the end, then on the way back set `cur.next.next = cur; cur.next = None`. Elegant but O(n) stack space, so mention that trade-off. Reasoning to say out loud: "you flip each pointer backwards, but you must save the next node first or you lose the tail."

2. **Detect a cycle (Floyd's tortoise & hare).** Two pointers, +1 and +2; they collide iff there's a cycle. O(n)/O(1). The reasoning - and you should offer the proof - is the "closing speed is exactly 1" argument from earlier: the hare gains one position per step on the tortoise inside the loop, so it can't leap over; it must land on it.

3. **Find the start of the cycle (Floyd phase 2).** After they meet, reset one pointer to `head` and advance both one step at a time; they meet at the cycle's entry node. The reasoning is a distance equation: if the tail before the loop has length `μ` and they met `k` steps into the loop, then `μ ≡ -k (mod λ)`, which is exactly why a head-start of `μ` from the top lands on the entry. Knowing why (not just the recipe) is what separates a pass from a "memorized it" flag.

4. **Merge two sorted lists.** Use a **dummy head** and a `tail` cursor; repeatedly attach the smaller of the two front nodes, advance that list, then attach whatever remains. O(m + n) time, O(1) extra space (it splices existing nodes). The dummy head is the trick: it means you never special-case "which list does the result start with?"

5. **Remove the Nth node from the end (two-pointer gap).** Advance a `fast` pointer `N` nodes ahead, then move `fast` and `slow` together until `fast` hits the end; now `slow` sits just before the target. One pass, O(n)/O(1). Reasoning: a fixed gap of `N` between the pointers means when the leader reaches the end, the follower is exactly `N` from it. Use a dummy head so removing the first node (N == length) isn't a special case.

6. **Find the middle.** Slow +1, fast +2; when fast reaches the end, slow is at the middle - one pass, the rate argument from this chapter. This is also the setup move for the palindrome and merge-sort-on-a-list problems, so it's high-use.

**Bonus: check palindrome.** Find the middle (above), reverse the second half in place, then walk the two halves in lockstep comparing values; optionally restore. O(n)/O(1). It composes "find middle" and "reverse," which is why interviewers like it as a combo question.

And the curveball they love: "why do arrays usually beat linked lists in practice?" Cache locality. Arrays are contiguous, so iteration streams through cache lines with the prefetcher's help; a linked list is a pointer chase across scattered heap addresses, so nearly every hop risks a ~100x cache miss. Same Big-O, brutally different constants. The right answer: reach for a list only when you need O(1) splice given a node reference (LRU caches, intrusive lists in kernels) and you're not iterating constantly; otherwise an array wins. That answer shows you understand the gap between asymptotics and hardware, which is exactly what they're fishing for.

## Exercises

Work these top to bottom; they ramp from warm-up to tricky. All of them assume the `Node` / `SinglyLinkedList` classes from this chapter. Try each before peeking; solutions (fully runnable, with complexity) follow.

1. `get(index)` - return the value at a 0-based position, raising `IndexError` if out of range. (Warm-up: just walking.)
2. `length_no_counter(head)` - count the nodes by walking, without using `_size`. Also write `sum_values(head)`.
3. `remove_duplicates(head)` - remove duplicate values from an unsorted singly linked list, keeping first occurrences.
4. `reverse_recursive(head)` - reverse a singly linked list recursively, returning the new head.
5. `remove_nth_from_end(head, n)` - remove the n-th node counting from the end (1-based), return the (possibly new) head.
6. `cycle_start(head)` - return the node where a cycle begins, or `None` (Floyd's phase 2).
7. `merge_sorted(a, b)` - merge two sorted singly linked lists into one sorted list, returning its head.
8. `is_palindrome(head)` - return whether the values read the same forwards and backwards, in O(n)/O(1).
9. `partition(head, x)` - reorder so all nodes with value `< x` come before all nodes `>= x` (relative order within each group preserved).
10. `rotate(head, k)` - rotate the list to the right by `k` places (e.g. `1→2→3→4→5`, k=2 → `4→5→1→2→3`).

### Solutions

```python
# Shared helpers so every solution is runnable on its own ----------------
def build(values):
    """Make a raw Node chain from a list; return its head (or None)."""
    head = None
    for v in reversed(values):
        head = Node(v, next=head)
    return head

def to_list(head):
    """Walk a raw Node chain into a Python list."""
    out, cur = [], head
    while cur is not None:
        out.append(cur.value)
        cur = cur.next
    return out


# 1. get(index) ----------------------------------------------------------
def get(head, index):
    """O(n): walk `index` steps. Raise if we fall off the end."""
    if index < 0:
        raise IndexError("negative index")
    cur = head
    for _ in range(index):
        if cur is None:
            raise IndexError("index out of range")
        cur = cur.next
    if cur is None:
        raise IndexError("index out of range")
    return cur.value
# Time O(n), space O(1).

assert get(build([10, 20, 30]), 0) == 10
assert get(build([10, 20, 30]), 2) == 30
try:
    get(build([10, 20, 30]), 5); assert False
except IndexError:
    pass


# 2. length & sum without a counter -------------------------------------
def length_no_counter(head):
    """O(n): one walk, increment a tally."""
    n, cur = 0, head
    while cur is not None:
        n += 1
        cur = cur.next
    return n

def sum_values(head):
    """O(n): accumulate values during the walk."""
    total, cur = 0, head
    while cur is not None:
        total += cur.value
        cur = cur.next
    return total
# Both O(n) time, O(1) space.

assert length_no_counter(build([1, 2, 3, 4])) == 4
assert length_no_counter(None) == 0
assert sum_values(build([1, 2, 3, 4])) == 10


# 3. remove duplicates from an UNSORTED list ----------------------------
def remove_duplicates(head):
    """Keep first occurrence of each value, drop later ones.
    Use a set for O(1) membership. O(n) time, O(n) space."""
    if head is None:
        return None
    seen = {head.value}
    prev, cur = head, head.next
    while cur is not None:
        if cur.value in seen:
            prev.next = cur.next      # splice out the dup
        else:
            seen.add(cur.value)
            prev = cur                # only advance prev when we KEEP cur
        cur = cur.next
    return head
# Time O(n), space O(n) for the set.
# (Without extra space it's O(n^2): for each node, scan the prefix for a match.)

assert to_list(remove_duplicates(build([1, 2, 1, 3, 2, 4]))) == [1, 2, 3, 4]
assert to_list(remove_duplicates(build([5, 5, 5]))) == [5]
assert remove_duplicates(None) is None


# 4. reverse recursively -------------------------------------------------
def reverse_recursive(head):
    """Recurse to the end, then flip pointers on the way back.
    O(n) time, O(n) stack space."""
    if head is None or head.next is None:
        return head                   # base case: empty or single node
    new_head = reverse_recursive(head.next)
    head.next.next = head             # make the next node point back at me
    head.next = None                  # I'm the new tail (for now)
    return new_head
# Time O(n), space O(n) (call stack). Iterative version is O(1) space.

assert to_list(reverse_recursive(build([1, 2, 3, 4, 5]))) == [5, 4, 3, 2, 1]
assert to_list(reverse_recursive(build([7]))) == [7]
assert reverse_recursive(None) is None


# 5. remove Nth node from the end (two-pointer gap) ---------------------
def remove_nth_from_end(head, n):
    """Open a gap of n between fast and slow, then advance together.
    Dummy head removes the 'remove the first node' special case.
    O(n) time, O(1) space, single pass."""
    dummy = Node(0, next=head)
    fast = slow = dummy
    for _ in range(n):                # open the gap
        if fast.next is None:
            return head               # n bigger than the list -> no-op
        fast = fast.next
    while fast.next is not None:      # move both until fast hits the last node
        fast = fast.next
        slow = slow.next
    slow.next = slow.next.next        # slow is just before the target
    return dummy.next

assert to_list(remove_nth_from_end(build([1, 2, 3, 4, 5]), 2)) == [1, 2, 3, 5]
assert to_list(remove_nth_from_end(build([1, 2, 3]), 3)) == [2, 3]   # removes head
assert to_list(remove_nth_from_end(build([1]), 1)) == []


# 6. find the start of a cycle (Floyd phase 2) --------------------------
def cycle_start(head):
    """Phase 1: find a meeting point with tortoise/hare.
    Phase 2: reset one pointer to head; advance both by 1; they meet at
    the cycle entry. O(n) time, O(1) space."""
    slow = fast = head
    while fast is not None and fast.next is not None:
        slow = slow.next
        fast = fast.next.next
        if slow is fast:              # phase 1 collision
            ptr = head
            while ptr is not slow:    # phase 2
                ptr = ptr.next
                slow = slow.next
            return ptr
    return None                       # no cycle

# build a list 1->2->3->4 with 4 looping back to node "2"
n1, n2, n3, n4 = Node(1), Node(2), Node(3), Node(4)
n1.next, n2.next, n3.next, n4.next = n2, n3, n4, n2
assert cycle_start(n1) is n2
assert cycle_start(build([1, 2, 3])) is None


# 7. merge two sorted lists ---------------------------------------------
def merge_sorted(a, b):
    """Dummy head + tail cursor; splice the smaller front each step.
    O(m + n) time, O(1) extra space."""
    dummy = Node(0)
    tail = dummy
    while a is not None and b is not None:
        if a.value <= b.value:
            tail.next, a = a, a.next
        else:
            tail.next, b = b, b.next
        tail = tail.next
    tail.next = a if a is not None else b   # attach the leftover run
    return dummy.next

assert to_list(merge_sorted(build([1, 3, 5]), build([2, 4, 6]))) == [1, 2, 3, 4, 5, 6]
assert to_list(merge_sorted(build([]), build([1, 2]))) == [1, 2]
assert to_list(merge_sorted(build([1, 2]), build([]))) == [1, 2]


# 8. palindrome check (find middle + reverse second half) ---------------
def is_palindrome(head):
    """O(n) time, O(1) space: find middle, reverse the back half,
    compare halves. (Restores the list afterward.)"""
    if head is None or head.next is None:
        return True
    # find middle (slow ends at start of 2nd half for even length)
    slow = fast = head
    while fast is not None and fast.next is not None:
        slow = slow.next
        fast = fast.next.next
    # reverse the second half starting at slow
    prev = None
    cur = slow
    while cur is not None:
        nxt = cur.next
        cur.next = prev
        prev = cur
        cur = nxt
    # compare front half with reversed back half
    second, first = prev, head
    ok = True
    second_head = prev
    while second is not None:
        if first.value != second.value:
            ok = False
            break
        first = first.next
        second = second.next
    # (optional) restore the second half so we don't mutate the input
    cur, prev = second_head, None
    while cur is not None:
        nxt = cur.next; cur.next = prev; prev = cur; cur = nxt
    return ok

assert is_palindrome(build([1, 2, 3, 2, 1])) is True
assert is_palindrome(build([1, 2, 2, 1])) is True
assert is_palindrome(build([1, 2, 3])) is False
assert is_palindrome(build([7])) is True


# 9. partition around x -------------------------------------------------
def partition(head, x):
    """Build two sublists (< x and >= x), preserving relative order,
    then concatenate. Two dummy heads keep it clean.
    O(n) time, O(1) extra space."""
    less_dummy, more_dummy = Node(0), Node(0)
    less, more = less_dummy, more_dummy
    cur = head
    while cur is not None:
        if cur.value < x:
            less.next = cur; less = cur
        else:
            more.next = cur; more = cur
        cur = cur.next
    more.next = None                  # terminate the >= list
    less.next = more_dummy.next       # stitch < list before >= list
    return less_dummy.next

assert to_list(partition(build([3, 5, 8, 5, 10, 2, 1]), 5)) == [3, 2, 1, 5, 8, 5, 10]
assert to_list(partition(build([1, 2, 3]), 0)) == [1, 2, 3]   # all >= x


# 10. rotate right by k --------------------------------------------------
def rotate(head, k):
    """Make it a ring, then break the ring at the new tail.
    O(n) time, O(1) space."""
    if head is None or head.next is None or k == 0:
        return head
    # find length and the old tail
    length, tail = 1, head
    while tail.next is not None:
        tail = tail.next
        length += 1
    k %= length
    if k == 0:
        return head                   # full rotations -> unchanged
    tail.next = head                  # close into a ring
    # new tail is (length - k - 1) steps from head; new head is right after it
    steps = length - k - 1
    new_tail = head
    for _ in range(steps):
        new_tail = new_tail.next
    new_head = new_tail.next
    new_tail.next = None              # break the ring
    return new_head

assert to_list(rotate(build([1, 2, 3, 4, 5]), 2)) == [4, 5, 1, 2, 3]
assert to_list(rotate(build([1, 2, 3]), 3)) == [1, 2, 3]   # k == length
assert to_list(rotate(build([1, 2]), 3)) == [2, 1]          # k > length wraps

print("exercises: all solutions pass")
```

## Quick reference: when do you actually reach for a linked list?

- **Yes:** you need O(1) insert/delete given a node reference (LRU cache, certain queues, the "deque" splice pattern), or you're constantly adding/removing at the ends and don't index randomly.
- **No (use an array/`list`):** you index by position a lot, you iterate frequently (cache locality wins), or memory overhead matters. This is most of the time.
- **The honest summary:** linked lists are a precision tool, not a default. Big-O made them look universally great; cache reality narrows them to specific jobs. Knowing which jobs is the actual skill.
