## 🌱 Start here - family trees and folders

Before any code or jargon, let's build the picture in plain language, because once the *shape* feels obvious the formal terms are just labels stuck onto things you already understand.

Think of a **family tree**. At the top there's an ancestor, call her Grandma. Grandma has children, each child can have their own children, and so on down. Everybody (except Grandma) has exactly **one** parent directly above them. You never see someone with two mothers in the diagram, and you never see a loop where your grandchild is somehow also your grandparent. That "one parent each, no loops" rule is *exactly* what makes something a tree instead of a tangled web.

Now swap the picture for an **org chart** at a company. The CEO sits at the top. Below her are VPs, below them managers, below them individual contributors. Same structure: one boss directly above you, a clear chain of command up to the CEO, and the people with nobody reporting to them sit at the bottom edge.

Or, the one you touch every single day, **folders on your computer**. There's a top folder (on a Mac, `/`). Inside it are more folders, inside those are more folders and files. A file or an empty folder is a dead end; you can't go deeper. To find any file there's exactly one path of folders to open. That's a tree, and you've been navigating one with Finder your whole life without calling it that.

Here's the vocabulary mapped onto those everyday pictures, so the formal table in the next section reads like review instead of new information:

- **Root** = Grandma / the CEO / the top folder `/`. The one thing at the top with nothing above it.
- **Parent** = your mom, your direct boss, the folder that contains this folder.
- **Child** = your kid, your direct report, a folder/file *inside* this folder.
- **Leaf** = someone with no children, an employee with no reports, an empty folder or a plain file. A *dead end*, nothing hangs below it.
- **Hierarchy** = the whole top-to-bottom arrangement. Every node sits at some level below the root.

So why do programmers reach for this shape constantly instead of just a flat list? Two reasons, and the second is the heartbeat of this entire chapter.

**Reason 1, hierarchy is how the world is actually organized.** Files live in folders. Comments have replies. A web page is tags nested inside tags (the DOM is a tree). A company has departments. Whenever the data *itself* has an "inside-of" or "reports-to" relationship, a tree stores it without you forcing it into an awkward flat shape.

**Reason 2, a balanced tree lets you "throw away half the data on every step."** This is the magic, so let's make it physical. Imagine a guessing game: someone is thinking of a number between 1 and 1000, and you guess. If you guess "500?" and they say "too high," you just eliminated 500 numbers in one question, you'll *never* check any of them. Guess 250 next, they say "too low," another 125 gone. Each question roughly **halves** what's left. You'll corner the number in about 10 questions, not 1000. That's the difference between O(n) (ask about every number) and O(log n) (halve each time).

A search tree is that guessing game frozen into a data structure. Every node says "smaller stuff is to my left, bigger stuff is to my right." So when you're hunting for a value, each node you visit lets you ignore an *entire* branch, half the remaining tree, and walk down the other side. Visit a node, throw away half, repeat. Ten steps to find one item among a thousand. That's why trees matter, and why the back half of this chapter obsesses over keeping them *balanced*, because the "throw away half" trick only works if the two halves are actually roughly equal in size. A lopsided tree is just the guessing game where you foolishly guess 1, then 2, then 3...

Hold those two pictures, the family tree for the *shape*, the guessing game for the *payoff*, and everything below is detail.

## 📐 Terminology - the words people keep mixing up

A **tree** is a collection of **nodes** connected by **edges**, with one special node called the **root** at the top. Each node holds a value and references to its **children**. The defining property: there is exactly **one path** from the root to any node, no cycles, no node with two parents. That's what separates a tree from a general graph.

Here's the family vocabulary, all of it, on one small tree:

```
            (A)          <- root (no parent)
           /   \
        (B)     (C)      <- B and C are children of A; A is their parent
        /  \       \
      (D)  (E)      (F)  <- D, E, F are leaves (no children)
```

Let's pin down each term precisely, because it's easy to conflate height and depth under pressure:

| Term | Definition | Example (above) |
|------|-----------|-----------------|
| **Root** | The topmost node, the only one with no parent | `A` |
| **Leaf** | A node with no children | `D`, `E`, `F` |
| **Internal node** | A node with at least one child | `A`, `B`, `C` |
| **Parent / child** | Directly-connected nodes; the upper is parent | `A` is parent of `B` |
| **Sibling** | Nodes sharing the same parent | `B` and `C` |
| **Ancestor** | Any node on the path up to the root | `A` is an ancestor of `E` |
| **Descendant** | Any node reachable going down | `E` is a descendant of `A` |
| **Degree** of a node | Number of children it has | `A` has degree 2, `C` has degree 1 |
| **Depth** of a node | Number of edges from the **root** to that node | depth(`A`)=0, depth(`D`)=2 |
| **Height** of a node | Number of edges on the longest path **down** to a leaf | height(`A`)=2, height(`D`)=0 |
| **Height of the tree** | Height of the root | 2 |

The two most often swapped are **depth** and **height**. A handy mnemonic: *depth measures how far you've fallen from the root; height measures how far you can still fall.* Depth counts upward toward the root; height counts downward toward the leaves.

A **binary tree** is a tree where every node has **at most two** children, conventionally named `left` and `right`. That "at most two" is the whole restriction, and it's what makes binary trees easy to reason about and to code. Almost everything in this chapter is a binary tree.

A quick but important size fact we'll use to justify Big-O later: a binary tree of height `h` has **at most** `2^(h+1) − 1` nodes (a "perfect" tree, every level full). Flip that around: a tree with `n` nodes has height **at least** `⌈log₂(n+1)⌉ − 1`, i.e. height is **at least about log₂ n**. But the height can also be as large as `n − 1` if the tree is a sad diagonal line. Holding both of those facts in your head is the key to understanding why *balance* matters.

## 💻 Build it - the binary tree node

Everything starts with the node. Dead simple:

```python
class Node:
    """A single binary-tree node: a value plus left/right child pointers."""
    def __init__(self, value):
        self.value = value
        self.left = None
        self.right = None

    def __repr__(self):
        return f"Node({self.value!r})"
```

Let's hand-build the tree from the diagram above so we have something concrete to traverse:

```python
def sample_tree():
    """
            1
          /   \
         2      3
        / \      \
       4   5      6
    """
    root = Node(1)
    root.left = Node(2)
    root.right = Node(3)
    root.left.left = Node(4)
    root.left.right = Node(5)
    root.right.right = Node(6)
    return root
```

Two utilities we'll lean on, height and node count, written recursively, which is the natural way to think about trees:

```python
def height(node):
    """Height in EDGES. An empty tree is -1 so a single leaf is 0."""
    if node is None:
        return -1
    return 1 + max(height(node.left), height(node.right))

def count(node):
    """Total number of nodes."""
    if node is None:
        return 0
    return 1 + count(node.left) + count(node.right)
```

Why is empty-tree height `-1`? Because then a single leaf node works out to `1 + max(-1, -1) = 0`, which matches the table above (a leaf has height 0). Off-by-one conventions like this cause real bugs, so it's worth nailing down now.

```python
t = sample_tree()
assert count(t) == 6
assert height(t) == 2
print("node + utilities OK")
```

The recursion mirrors the structure exactly: do something with the current node, then recurse on the two subtrees. Almost every tree algorithm has this shape.

## 📐 Traversals - four ways to visit every node

A traversal is just an order for visiting every node exactly once. There are four standard orders, and knowing which to reach for is half of tree fluency.

The first three, **preorder**, **inorder**, **postorder**, are **depth-first**: they dive all the way down one branch before backing up. They differ only in *when* you "visit" (process) the current node relative to its children:

- **Preorder**: visit **N**ode, then **L**eft subtree, then **R**ight subtree. (NLR)
- **Inorder**: **L**eft, then **N**ode, then **R**ight. (LNR)
- **Postorder**: **L**eft, **R**ight, then **N**ode. (LRN)

The fourth, **level-order** (a.k.a. **breadth-first**), visits the tree row by row, top to bottom, left to right.

Here's what each produces on the sample tree:

```
            1
          /   \
         2      3
        / \      \
       4   5      6
```

| Traversal | Order on sample tree | One-line intuition |
|-----------|----------------------|--------------------|
| Preorder (NLR) | `1 2 4 5 3 6` | Root first, good for **copying** a tree |
| Inorder (LNR) | `4 2 5 1 3 6` | For a BST this prints values **sorted** |
| Postorder (LRN) | `4 5 2 6 3 1` | Children before parent, good for **deleting/freeing** |
| Level-order (BFS) | `1 2 3 4 5 6` | Row by row, shortest-path-ish, **closest first** |

The "use case" column is worth memorizing. Postorder deleting a node means its children are already gone, so you never free a parent whose children still point at it. Preorder hands you the root first, which is exactly what you need to reconstruct or clone a tree top-down.

## 💻 Build it - traversals, recursively first

Recursive versions read almost like the definitions. We'll collect values into a list so we can test them.

```python
def preorder(node, out=None):
    if out is None:
        out = []
    if node is not None:
        out.append(node.value)      # N
        preorder(node.left, out)    # L
        preorder(node.right, out)   # R
    return out

def inorder(node, out=None):
    if out is None:
        out = []
    if node is not None:
        inorder(node.left, out)     # L
        out.append(node.value)      # N
        inorder(node.right, out)    # R
    return out

def postorder(node, out=None):
    if out is None:
        out = []
    if node is not None:
        postorder(node.left, out)   # L
        postorder(node.right, out)  # R
        out.append(node.value)      # N
    return out
```

Notice the only thing that changes between the three is the *position of the `append`*. Move the visit line up, middle, or down, that's the entire difference. (Quick Python gotcha: default `out=None` and create the list inside, never `out=[]` in the signature, because a mutable default argument is shared across calls and would accumulate garbage between separate traversals.)

Tests:

```python
t = sample_tree()
assert preorder(t)  == [1, 2, 4, 5, 3, 6]
assert inorder(t)   == [4, 2, 5, 1, 3, 6]
assert postorder(t) == [4, 5, 2, 6, 3, 1]
print("recursive traversals OK")
```

**Complexity for all of these:** every node is visited exactly once with O(1) work, so **time is O(n)**. Space is the recursion stack, which is **O(h)**, proportional to the height. For a balanced tree that's O(log n); for a degenerate one it's O(n).

## 💻 Build it - traversals, iteratively (the real test of understanding)

Recursion hides a stack; doing it iteratively means *you* manage that stack. This is where you prove you actually understand traversal order.

### Iterative preorder - push right before left

Preorder is NLR. With an explicit stack you pop a node, visit it, then push its children so that **left comes off next**, which means you push **right first**, then left (stack is LIFO).

```python
def preorder_iter(root):
    out = []
    if root is None:
        return out
    stack = [root]
    while stack:
        node = stack.pop()
        out.append(node.value)          # visit N
        if node.right:                  # push R first...
            stack.append(node.right)
        if node.left:                   # ...so L is popped first
            stack.append(node.left)
    return out
```

### Iterative inorder - go left as far as possible, then visit

Inorder is LNR. The trick: walk left pushing every node, and only when you can't go left do you pop, visit, and pivot right.

```python
def inorder_iter(root):
    out = []
    stack = []
    node = root
    while stack or node:
        while node:                 # dive left, remembering the path
            stack.append(node)
            node = node.left
        node = stack.pop()          # leftmost unvisited node
        out.append(node.value)      # visit N
        node = node.right           # now do its right subtree
    return out
```

### Iterative postorder - the tricky one (two stacks, or reverse a modified preorder)

Postorder (LRN) is the hard one because the parent must be visited *after both* children. The cleanest mental trick: a postorder is the **reverse** of a "modified preorder" that goes Node-Right-Left (NRL). So do an NRL preorder pushing results, then reverse:

```python
def postorder_iter(root):
    out = []
    if root is None:
        return out
    stack = [root]
    while stack:
        node = stack.pop()
        out.append(node.value)          # collecting in N-R-L order
        if node.left:                   # push L first...
            stack.append(node.left)
        if node.right:                  # ...so R is popped first -> N R L
            stack.append(node.right)
    out.reverse()                       # reverse N-R-L  ->  L-R-N = postorder
    return out
```

Why does that work? NLR reversed is RLN, not postorder. But NRL reversed *is* LRN, which is exactly postorder. So you just mirror the preorder's child-push order (right pushed last so it pops first) and reverse at the end. Slick.

### Level-order - a queue, not a stack

Breadth-first means process a whole row before the next. That's a FIFO **queue**: enqueue the root, then repeatedly dequeue a node, visit it, and enqueue its children.

```python
from collections import deque

def level_order(root):
    out = []
    if root is None:
        return out
    q = deque([root])
    while q:
        node = q.popleft()              # FIFO: oldest first
        out.append(node.value)
        if node.left:
            q.append(node.left)
        if node.right:
            q.append(node.right)
    return out
```

The single difference between BFS and iterative-preorder DFS is **stack vs queue**, `pop()` (LIFO) versus `popleft()` (FIFO). That one swap changes the entire visiting order. It's genuinely beautiful.

Now let's test the iterative versions against the recursive ones, they must agree exactly:

```python
t = sample_tree()
assert preorder_iter(t)  == preorder(t)  == [1, 2, 4, 5, 3, 6]
assert inorder_iter(t)   == inorder(t)   == [4, 2, 5, 1, 3, 6]
assert postorder_iter(t) == postorder(t) == [4, 5, 2, 6, 3, 1]
assert level_order(t)    == [1, 2, 3, 4, 5, 6]

# Edge cases: empty tree and single node
assert preorder_iter(None) == []
assert level_order(None) == []
single = Node(42)
assert inorder_iter(single) == [42]
assert postorder_iter(single) == [42]
print("iterative traversals OK")
```

| Traversal | Structure used | Time | Extra space |
|-----------|---------------|------|-------------|
| Preorder (iter) | stack | O(n) | O(h) |
| Inorder (iter) | stack | O(n) | O(h) |
| Postorder (iter) | stack | O(n) | O(h) |
| Level-order | queue | O(n) | O(w) width |

For level-order the extra space is O(w) where w is the maximum **width** of the tree (a full bottom row), which can be up to ~n/2. For the DFS stacks it's O(h). Same time, different space profile.

## 📐 Binary Search Trees - adding an ordering invariant

A plain binary tree has no rules about *where* values go. A **Binary Search Tree (BST)** adds one powerful invariant:

> **BST invariant:** For every node `N`, every value in `N`'s **left** subtree is **less than** `N.value`, and every value in `N`'s **right** subtree is **greater than** `N.value`. (We'll assume no duplicates.)

Crucially this holds for the *entire* subtree, not just immediate children. That's what makes search work: at any node, if your target is smaller you go left, if larger you go right, and you correctly discard the *whole* other subtree because everything in it is on the wrong side.

The immediate payoff: an **inorder traversal of a BST yields the values in sorted order.** That's a free correctness check, if your BST is built right, `inorder` is sorted.

Searching is binary search over the tree shape. Each comparison eliminates one subtree, so the number of steps equals the path length, i.e. **O(h)**, the height. Here's the whole point of the chapter in one sentence: *every BST operation is O(h), so the game is keeping h small.*

---

## 💻 Build it - a full BST with insert, search, and delete

We'll wrap everything in a class. Insert and search are gentle warm-ups; delete is where the real care lives.

```python
class BST:
    def __init__(self):
        self.root = None

    # ---------- INSERT ----------
    def insert(self, value):
        self.root = self._insert(self.root, value)

    def _insert(self, node, value):
        if node is None:                    # found the empty slot
            return Node(value)
        if value < node.value:
            node.left = self._insert(node.left, value)
        elif value > node.value:
            node.right = self._insert(node.right, value)
        # value == node.value: duplicate, ignore
        return node

    # ---------- SEARCH ----------
    def search(self, value):
        node = self.root
        while node is not None:
            if value == node.value:
                return True
            node = node.left if value < node.value else node.right
        return False

    def inorder(self):
        return inorder(self.root)
```

The insert returns the (possibly new) subtree root and the parent re-attaches it. That "return the subtree, parent reassigns" pattern keeps you from juggling parent pointers, and it'll make delete dramatically cleaner.

Let's verify insert + search + the sorted-inorder property:

```python
bst = BST()
for v in [50, 30, 70, 20, 40, 60, 80, 10]:
    bst.insert(v)

assert bst.search(40) is True
assert bst.search(99) is False
assert bst.inorder() == [10, 20, 30, 40, 50, 60, 70, 80]   # sorted = correct!
print("BST insert/search OK")
```

### Delete - the careful part, all three cases

Deleting from a BST has to preserve the invariant. There are exactly three cases depending on how many children the doomed node has.

**Case 1, leaf (no children):** just remove it. Return `None` to the parent so it drops the link.

**Case 2, one child:** splice the node out by returning its single child up to the parent. The child (and its whole subtree) slides into the node's old position, and ordering is preserved because that subtree was already on the correct side.

**Case 3, two children:** you can't just remove it, both subtrees need a home. The trick: replace the node's *value* with its **inorder successor** (the smallest value in its right subtree), then delete that successor from the right subtree. Why the inorder successor? Because it's the very next value in sorted order, so dropping it into this slot keeps everything left-smaller / right-larger. The successor is always the leftmost node of the right subtree, and that node has **at most one child** (no left child, by definition of "leftmost"), so deleting *it* reduces to Case 1 or Case 2, the recursion terminates.

(Symmetric alternative: the inorder *predecessor*, the max of the left subtree. Either works. We'll use the successor.)

```python
    # ---------- DELETE ----------
    def delete(self, value):
        self.root = self._delete(self.root, value)

    def _delete(self, node, value):
        if node is None:
            return None                      # value not in tree

        if value < node.value:
            node.left = self._delete(node.left, value)
        elif value > node.value:
            node.right = self._delete(node.right, value)
        else:
            # Found the node to delete.
            # Case 1 & 2: zero or one child.
            if node.left is None:
                return node.right            # works for leaf too (right is None)
            if node.right is None:
                return node.left
            # Case 3: two children.
            # Find inorder successor = smallest in right subtree.
            succ = node.right
            while succ.left is not None:
                succ = succ.left
            node.value = succ.value          # copy successor's value up
            # Delete the successor from the right subtree.
            node.right = self._delete(node.right, succ.value)
        return node
```

Notice how Case 1 collapses into Case 2 elegantly: if `node.left is None` you return `node.right`, and for a true leaf `node.right` is also `None`, so you return `None`, exactly the leaf behavior. One line covers two cases.

Now the test that matters, exercise every deletion case and confirm the BST stays sorted and correct after each:

```python
def fresh():
    b = BST()
    for v in [50, 30, 70, 20, 40, 60, 80]:
        b.insert(v)
    return b

# Case 1: delete a leaf (20)
b = fresh()
b.delete(20)
assert b.inorder() == [30, 40, 50, 60, 70, 80]
assert b.search(20) is False

# Case 2: delete a node with one child.
#   Make 80 have a single child (75), then delete 80.
b = fresh()
b.insert(75)                 # 75 < 80 -> becomes 80's left child
b.delete(80)
assert b.inorder() == [20, 30, 40, 50, 60, 70, 75]
assert b.search(80) is False
assert b.search(75) is True  # child survived and slid up

# Case 3: delete a node with two children (root 50).
#   Successor is 60 (smallest in right subtree). 60 takes 50's place.
b = fresh()
b.delete(50)
assert b.root.value == 60
assert b.inorder() == [20, 30, 40, 60, 70, 80]
assert b.search(50) is False

# Delete everything; tree should empty out and stay sorted throughout.
b = fresh()
for v in [50, 30, 70, 20, 40, 60, 80]:
    b.delete(v)
    assert b.inorder() == sorted(b.inorder())   # invariant holds each step
assert b.root is None
print("BST delete (all 3 cases) OK")
```

### Traced walkthrough - building and pruning a BST

The code is correct, but you don't *feel* it until you run it by hand. Let's slow all the way down and trace, step by step, what the tree looks like after each operation, and, crucially, *which comparison* sent each value left or right. We'll build with the sequence `50, 30, 70, 20, 40`, then delete the root (a Case-3, two-children delete).

**Insert 50.** Tree is empty, so 50 becomes the root. No comparisons, there's nothing to compare against.

```
   50
```

**Insert 30.** Start at root 50. Compare: is `30 < 50`? **Yes → go left.** Left is empty, so 30 lands there.

```
     50
    /
  30
```

**Insert 70.** Start at root 50. Is `70 < 50`? No. Is `70 > 50`? **Yes → go right.** Right is empty, 70 lands there.

```
     50
    /  \
  30    70
```

**Insert 20.** Start at root 50. `20 < 50`? **Yes → left**, to node 30. Now at 30: `20 < 30`? **Yes → left**, which is empty. 20 lands as 30's left child. Notice you made **two** decisions, one per level, that's the path length, that's the O(h).

```
       50
      /  \
    30    70
   /
  20
```

**Insert 40.** Start at root 50. `40 < 50`? **Yes → left**, to 30. At 30: `40 < 30`? No. `40 > 30`? **Yes → right**, which is empty. 40 lands as 30's right child.

```
       50
      /  \
    30    70
   /  \
  20   40
```

Five inserts, and the tree built itself purely from those left/right comparisons. Let's sanity-check the invariant by reading off the inorder traversal, it must come out sorted: `20, 30, 40, 50, 70`. It does. The shape encodes the order.

Now the interesting part: **delete 50, the root, which has two children.** This is Case 3, and we want to watch the inorder-successor swap happen.

Step 1, *find the doomed node.* It's the root, 50. It has a left child (30) and a right child (70), so neither "no child" shortcut applies. Case 3.

Step 2, *find the inorder successor:* the smallest value in 50's **right** subtree. Go right to 70, then walk left as far as you can. 70 has no left child, so 70 *is* the leftmost, the successor is **70**. (The successor is "the very next value in sorted order after 50," and indeed sorted order is `...40, 50, 70...`, 70 is next. Good.)

Step 3, *copy the successor's value up* into the node being deleted. 50's slot now holds 70:

```
       70        <- value copied up; this node USED to be 50
      /  \
    30    70     <- the original 70 is still here, must be removed
   /  \
  20   40
```

Step 4, *delete the successor from the right subtree.* Recurse into the right subtree and delete 70. That original 70 was a leaf (no children at all), so it's a trivial Case-1 delete, return `None` to its parent, snapping the link.

```
       70
      /
    30
   /  \
  20   40
```

Read the inorder traversal of the result: `20, 30, 40, 70`. Still sorted, still a valid BST, and 50 is gone. The reason this always works: the successor is the *next* value in sorted order, so dropping it into the vacated slot keeps everything to the left smaller and everything to the right larger. And the successor is always the leftmost node of the right subtree, so it has **no left child**, meaning removing *it* is always the easy one-child-or-leaf case. The recursion can never spiral into another two-children delete. That's the whole trick, traced.

Here's that exact trace as a runnable check:

```python
b = BST()
for v in [50, 30, 70, 20, 40]:
    b.insert(v)
assert b.inorder() == [20, 30, 40, 50, 70]
assert b.root.value == 50

b.delete(50)                       # Case 3: two children, successor = 70
assert b.root.value == 70          # successor took the root's place
assert b.inorder() == [20, 30, 40, 70]
assert b.search(50) is False
print("traced BST build + Case-3 delete OK")
```

| Operation | Average (balanced) | Worst (degenerate) |
|-----------|-------------------|--------------------|
| Search | O(log n) | O(n) |
| Insert | O(log n) | O(n) |
| Delete | O(log n) | O(n) |
| Inorder (full) | O(n) | O(n) |

Every single operation is **O(h)**. When the tree is balanced, h ≈ log₂ n and life is good. When it isn't... read on.

---

## 📐 Why balance matters - watching a BST rot into a linked list

Here's the catastrophe. The BST has *no mechanism* to stay bushy. If you insert values in **sorted order**, every new value is larger than everything so far, so it always goes right. The tree degenerates into a single rightward chain, a linked list wearing a tree costume:

```
Insert 1,2,3,4,5 into a plain BST:

   1
    \
     2
      \
       3
        \
         4
          \
           5      height = 4 = n-1  ->  search is O(n)!
```

Let's prove it with code by measuring the height for sorted vs. shuffled insertion:

```python
import random

def build_and_measure(values):
    b = BST()
    for v in values:
        b.insert(v)
    return height(b.root)

n = 1000
sorted_vals = list(range(n))
shuffled = sorted_vals[:]
random.seed(0)
random.shuffle(shuffled)

h_sorted = build_and_measure(sorted_vals)
h_shuffled = build_and_measure(shuffled)

print(f"sorted insert    -> height {h_sorted}")    # ~999: a pure chain
print(f"shuffled insert  -> height {h_shuffled}")  # ~20-25: roughly log2(n)

assert h_sorted == n - 1          # perfectly degenerate, O(n) operations
assert h_shuffled < 3 * (n).bit_length()   # comfortably O(log n)-ish
print("balance demo OK")
```

The sorted insert gives height `n−1` exactly, a linked list, O(n) everything. The shuffled insert gives height around 20 for n=1000 (log₂ 1000 ≈ 10, with random trees a small constant factor above that). **Same data, same code, radically different performance, purely because of insertion order.**

This is unacceptable for anything where you don't control input order (which is basically always). The fix: **self-balancing trees** that automatically restructure on insert/delete to *guarantee* h = O(log n). Two famous ones below.

---

## 📐 AVL trees - strict balance via rotations

An **AVL tree** is a BST with one extra invariant enforced after every insert/delete:

> **AVL invariant:** For every node, the heights of its left and right subtrees differ by **at most 1**.

Each node tracks a **balance factor** = `height(left) − height(right)`. Legal values are `−1, 0, +1`. The moment an insert pushes some node to `+2` or `−2`, the tree is "unbalanced" there and you fix it with a **rotation**, a local, O(1) pointer rearrangement that lowers the tree while preserving the BST ordering.

Maintaining balance-factor ∈ {−1,0,1} mathematically forces the height to stay below ~1.44·log₂(n), so all operations are guaranteed **O(log n)**. That's the whole reason AVL exists.

### The single rotation (the primitive)

A right rotation pivots a node down to the right, pulling its left child up:

```
Right rotation around y:

      y                 x
     / \              /   \
    x   C    --->    A     y
   / \                    / \
  A   B                  B   C

BST order A < x < B < y < C is preserved in BOTH shapes.
```

A left rotation is the exact mirror image. Each is a constant-pointer shuffle: reattach `x.right` as `y.left`, make `y` the right child of `x`. O(1).

### The four cases

When a node `z` becomes unbalanced after an insertion, exactly one of four patterns describes *where* the offending insertion landed. The fix is one or two rotations:

```
LL  (left-left, heavy left, inserted into left's LEFT):
        z                    y
       /                   /   \
      y          --->     x     z      single RIGHT rotation on z
     /
    x

RR  (right-right, mirror of LL):
    z                        y
     \                     /   \
      y        --->        z     x      single LEFT rotation on z
       \
        x

LR  (left-right, heavy left, inserted into left's RIGHT):
      z              z               x
     /              /              /   \
    y      -->     x     -->      y     z   LEFT-rotate y, then RIGHT-rotate z
     \            /
      x          y

RL  (right-left, mirror of LR):
    z            z                  x
     \            \               /   \
      y    -->     x     -->      z     y   RIGHT-rotate y, then LEFT-rotate z
     /              \
    x                y
```

The rule that makes this memorable:
- **LL → one right rotation.**
- **RR → one left rotation.**
- **LR → left rotation on the child, then right rotation on the node** (turn it into an LL first, then fix).
- **RL → right rotation on the child, then left rotation on the node** (turn it into an RR first).

LR and RL are "the zig-zag cases", a single rotation won't fix them, so you first rotate the child to straighten the zig-zag into a straight line (LL or RR), then do the matching single rotation.

Here's the rotation core and a working balanced-insert so this isn't hand-waving:

```python
class AVLNode:
    def __init__(self, value):
        self.value = value
        self.left = None
        self.right = None
        self.height = 0          # height in edges; leaf = 0

def avl_height(n):
    return n.height if n else -1

def balance_factor(n):
    return avl_height(n.left) - avl_height(n.right)

def update_height(n):
    n.height = 1 + max(avl_height(n.left), avl_height(n.right))

def rotate_right(z):
    y = z.left
    z.left = y.right
    y.right = z
    update_height(z)             # z first: it's now lower
    update_height(y)
    return y                     # y is the new subtree root

def rotate_left(z):
    y = z.right
    z.right = y.left
    y.left = z
    update_height(z)
    update_height(y)
    return y

def avl_insert(node, value):
    # 1) ordinary BST insert
    if node is None:
        return AVLNode(value)
    if value < node.value:
        node.left = avl_insert(node.left, value)
    elif value > node.value:
        node.right = avl_insert(node.right, value)
    else:
        return node              # no duplicates

    # 2) update height of this ancestor
    update_height(node)

    # 3) rebalance using the four cases
    bf = balance_factor(node)
    if bf > 1 and value < node.left.value:        # LL
        return rotate_right(node)
    if bf < -1 and value > node.right.value:      # RR
        return rotate_left(node)
    if bf > 1 and value > node.left.value:        # LR
        node.left = rotate_left(node.left)
        return rotate_right(node)
    if bf < -1 and value < node.right.value:      # RL
        node.right = rotate_right(node.right)
        return rotate_left(node)
    return node
```

Now the proof it actually keeps balance, feed it the **sorted** sequence that destroyed the plain BST and confirm the height stays logarithmic:

```python
root = None
for v in range(1, 16):           # 1..15 sorted - worst case for plain BST
    root = avl_insert(root, v)

# Plain BST would be height 14 (a chain). AVL must be ~log2(15) ≈ 3.
assert avl_height(root) == 3
# Inorder still sorted -> BST invariant preserved through all rotations.
assert inorder(root) == list(range(1, 16))
# Every node satisfies |balance factor| <= 1.
def check_balanced(n):
    if n is None:
        return True
    assert abs(balance_factor(n)) <= 1
    return check_balanced(n.left) and check_balanced(n.right)
assert check_balanced(root)
print("AVL stays balanced on sorted input OK")
```

Fifteen sorted inserts that gave the naive BST a height of 14 give the AVL tree a height of **3**. That's the entire promise of self-balancing, demonstrated. (We've shown insert; AVL delete uses the same rotation cases after a normal BST delete, checking balance on the way back up, same machinery, more bookkeeping, so the full delete is left as an exercise.)

## 📐 Red-black trees - balance with a lighter touch

AVL trees are *strictly* balanced, which makes lookups slightly faster but means more rotations on insert/delete. **Red-black trees** trade a little height for fewer rotations, which is why they back many standard libraries (Java's `TreeMap`, C++ `std::map`, the Linux kernel scheduler). You don't need to implement one here, but the model is worth having.

A red-black tree is a BST where every node is colored **red** or **black**, obeying five properties:

1. **Every node is either red or black.**
2. **The root is black.**
3. **Every leaf (the `NIL` null sentinels) is black.**
4. **A red node's children are both black.** (No two reds in a row, "no red-red.")
5. **Every path from a given node down to any descendant `NIL` leaf contains the same number of black nodes.** (Equal "black-height.")

Why do these five rules guarantee **O(log n)** height? Property 5 says every root-to-leaf path has the same black-height `b`. Property 4 says reds can't be consecutive, so on any path at most half the nodes are red, meaning the total path length is at most `2b`. The shortest possible path is all black (length `b`); the longest is alternating red/black (length `≤ 2b`). So **the longest path is at most twice the shortest**, the tree can never be more than 2× out of balance. Combined with the black-height being at least `log₂(n+1)`, the overall height is bounded by `2·log₂(n+1)` = **O(log n)**. Operations stay logarithmic, guaranteed.

| | AVL | Red-Black |
|---|---|---|
| Balance strictness | Strict (heights differ ≤ 1) | Looser (path ≤ 2× shortest) |
| Height bound | ~1.44 log n | ~2 log n |
| Lookups | Slightly faster (shorter) | Slightly slower |
| Insert/delete rotations | More | Fewer |
| Typical use | Read-heavy workloads | General-purpose library maps/sets |

The one-line takeaway: **AVL = tightly balanced, great for lots of reads; red-black = looser but cheaper to modify, the default in most standard libraries.** Both guarantee O(log n), they just pick different points on the balance-vs-rebalance-cost curve.

## 📐 Tries - when the *key* is a sequence

A **trie** (pronounced "try," from re**trie**val) is a tree specialized for **string keys**. Instead of storing whole strings at nodes and comparing them, a trie stores **one character per edge**, so a word is a *path* from the root. Shared prefixes share nodes.

```
Insert "cat", "car", "card", "dog":

        (root)
        /     \
       c       d
       |       |
       a       o
      / \      |
     t   r     g*
     *   |
         d*   ( * marks end-of-word )
```

"cat", "car", "card" all share the `c → a` path, then branch. That sharing is the whole point: storing 10,000 words that share prefixes costs far less than 10,000 separate strings, and, critically, you can find **every word starting with a given prefix** by walking to the end of that prefix and collecting everything below. That's exactly autocomplete.

Complexity is delightful: for a key of length `L`, **insert and search are O(L)**, independent of how many words are in the trie. A hash set is also ~O(L) for exact lookup, but a hash set *cannot* answer "give me all words with this prefix," and that's the trie's superpower.

## 🧪 Mini-project - an autocomplete engine built on a trie

Let's build something real: insert a dictionary, then given any prefix return all completions, sorted. This is the data structure behind search bars and IDE suggestions.

```python
class TrieNode:
    def __init__(self):
        self.children = {}          # char -> TrieNode
        self.is_word = False        # True if a word ends exactly here

class Trie:
    def __init__(self):
        self.root = TrieNode()

    def insert(self, word):
        """O(L): walk/extend the path one char at a time."""
        node = self.root
        for ch in word:
            if ch not in node.children:
                node.children[ch] = TrieNode()
            node = node.children[ch]
        node.is_word = True

    def search(self, word):
        """Exact-match lookup. O(L). True only if the full word was inserted."""
        node = self._find(word)
        return node is not None and node.is_word

    def starts_with(self, prefix):
        """Is there ANY word with this prefix? O(L)."""
        return self._find(prefix) is not None

    def _find(self, s):
        """Walk down following s; return the node we land on, or None."""
        node = self.root
        for ch in s:
            if ch not in node.children:
                return None
            node = node.children[ch]
        return node

    def autocomplete(self, prefix):
        """All inserted words beginning with `prefix`, sorted."""
        results = []
        start = self._find(prefix)
        if start is None:
            return results                      # no word has this prefix
        # DFS from the prefix node, rebuilding suffixes as we go.
        self._collect(start, prefix, results)
        return sorted(results)

    def _collect(self, node, path, results):
        if node.is_word:
            results.append(path)
        for ch, child in node.children.items():
            self._collect(child, path + ch, results)
```

`insert`, `search`, and `starts_with` are each a straight walk down the trie following characters, O(L). `autocomplete` walks to the prefix node, then does a DFS over everything below it, reconstructing each full word by accumulating the path string. The work for autocomplete is O(L + size of the matching subtree), which is essentially optimal: you can't return k completions faster than touching them.

Now the tests, a small dictionary plus all the edge cases worth covering:

```python
trie = Trie()
words = ["cat", "car", "card", "care", "dog", "do", "dot", "a", "apple", "app"]
for w in words:
    trie.insert(w)

# ---- exact search ----
assert trie.search("car") is True
assert trie.search("ca") is False        # "ca" is a prefix, not an inserted word
assert trie.search("cards") is False     # longer than any word on that path
assert trie.search("a") is True          # single-char word
assert trie.search("zebra") is False

# ---- starts_with ----
assert trie.starts_with("car") is True
assert trie.starts_with("ca") is True
assert trie.starts_with("xyz") is False
assert trie.starts_with("app") is True

# ---- autocomplete: the headline feature ----
assert trie.autocomplete("car") == ["car", "card", "care"]
assert trie.autocomplete("ca")  == ["car", "card", "care", "cat"]
assert trie.autocomplete("do")  == ["do", "dog", "dot"]
assert trie.autocomplete("app") == ["app", "apple"]
assert trie.autocomplete("a")   == ["a", "app", "apple"]
assert trie.autocomplete("z")   == []          # no completions
assert trie.autocomplete("")    == sorted(words)  # empty prefix -> every word

print("autocomplete trie OK")
print("Suggestions for 'ca':", trie.autocomplete("ca"))
```

A few subtleties these tests pin down, the kind that are easy to get wrong on a first pass:
- `search("ca")` is **False** even though `"ca"` is a valid path, because `is_word` is False there. Search demands an exact inserted word, not merely a reachable path. That `is_word` flag is the entire distinction between `search` and `starts_with`.
- `autocomplete("")` returns **everything**, because the empty prefix lands at the root and collects the whole tree. That's a sensible default (an empty search box could show all options).
- The prefix itself is included when it's a complete word, `autocomplete("do")` includes `"do"`, because `_collect` checks `is_word` on the start node too.

That's a working autocomplete engine in about 40 lines, every operation linear in the length of the query rather than the size of the dictionary. This is genuinely the structure shipping in production search boxes.

## ⚠️ Common mistakes

These are the traps people fall into with trees. They're written down so the same bug doesn't cost you twice.

1. **Confusing height with depth, and botching the empty-tree convention.** *Depth* counts edges *down from the root* to a node; *height* counts edges *down to the deepest leaf*. They are not the same number for the same node. The sneaky part is the base case: define an **empty tree's height as `-1`** so that a single leaf computes to `1 + max(-1, -1) = 0`. If you instead make empty-tree height `0`, every leaf reports height 1 and all your AVL balance-factor math drifts by one. Pick a convention, write it in the docstring, never improvise it mid-function.

2. **Mutable default argument in a traversal helper.** Writing `def preorder(node, out=[]):` looks harmless but the `[]` is created **once**, at function-definition time, and *shared across every call*. The second traversal appends onto the first one's leftover list. Always `out=None` then `if out is None: out = []` inside. This bug is silent, tests pass in isolation and fail when run together.

3. **Thinking the BST invariant only constrains immediate children.** The rule is *every value in the entire left subtree* < node < *every value in the entire right subtree*, not just the two direct kids. A tree where each node beats its own children but a deep-left grandchild is larger than the root is **not** a valid BST, and naive "check node vs its two children" validation will wrongly accept it. (The bounds technique in the exercises is the fix.)

4. **Forgetting a plain BST degenerates on sorted input.** Insert `1, 2, 3, …, n` and you get a right-leaning chain of height `n−1`, a linked list with extra steps, O(n) per operation. Real-world data arrives sorted *constantly* (timestamps, IDs, alphabetized names). If you don't control insertion order, you need a self-balancing tree (AVL / red-black), not a hand-rolled BST.

5. **Deleting Case 3 with the wrong child / wrong direction.** The inorder *successor* is the **leftmost node of the RIGHT subtree** (smallest-larger). It is easy to slip and grab the right subtree's *root*, or to walk into the *left* subtree, or to forget to actually delete the successor from below after copying its value up, which duplicates the value. Trace it: copy successor's value up, *then* recurse to delete that value from the right subtree.

6. **Not returning the subtree root from recursive insert/delete.** The clean pattern is `node.left = self._insert(node.left, v)`, the recursive call **returns** the (possibly new) subtree root and the parent reassigns it. Forget the `return node` at the bottom (or forget to capture the return) and links silently vanish: new nodes don't attach, deletions don't splice. The function must return the root of the subtree it just (maybe) modified, on *every* path.

7. **Infinite recursion on a cyclic / non-tree structure.** All the recursion here assumes a true tree, one path to each node, no cycles. If you accidentally point a child back at an ancestor (e.g. building a graph by mistake, or a buggy rotation), every traversal loops forever and blows the stack. If you're not 100% sure the input is acyclic, track a `visited` set.

8. **Off-by-one in level-order grouping.** Plain BFS gives a flat list. To get *list-of-lists* (one inner list per level), you must snapshot `len(queue)` at the **start** of each level and pop exactly that many, *before* enqueuing the next level's children. Reading the length after you've started enqueuing children mixes two levels together. (See the level-order exercise.)

9. **Comparing nodes when you mean values (and vice versa).** `if node.left < node` compares `Node` objects, not their `.value`s, usually a `TypeError`, or worse, silently wrong if you've defined `__lt__`. And in lowest-common-ancestor problems the answer is typically a **node**, not a value, returning `node.value` when the caller wanted the `Node` (to keep walking from it) is a classic mismatch. Be deliberate about which one each line is handling.

## 💼 On the job / interview angle

Trees are arguably *the* most-tested data structure in technical interviews, and it's not an accident. A tree question simultaneously checks whether you're comfortable with **recursion**, whether you understand **two traversal paradigms** (DFS and BFS), and whether you can reason about **invariants** (the BST property). One whiteboard problem probes three skills at once, great signal-per-question for an interviewer, which is exactly why they lean on it. On the job, the same shapes show up everywhere: the DOM, file systems, JSON/XML parse trees, database indexes (B-trees, a tree cousin), dependency graphs, and abstract syntax trees in every compiler.

Here are the questions that come up over and over, with the *reasoning*, because memorizing the code without the why means you're sunk the moment they tweak the problem.

1. **Validate a BST.** The naive "is each node bigger than its left child and smaller than its right child" is **wrong**, the invariant spans whole subtrees (mistake #3 above). Two correct approaches: (a) **min/max bounds**, recurse carrying a `(low, high)` range; the root is unbounded `(−∞, +∞)`, going left tightens the *upper* bound to the parent's value, going right tightens the *lower* bound. Each node must fall strictly inside its inherited range. (b) **inorder must be sorted**, do an inorder traversal and check it's strictly increasing; equivalent and sometimes cleaner. Mention both; the bounds method is the one they usually want to see reasoned out.

2. **Lowest common ancestor (LCA).** For a **BST**, it's beautiful: walk from the root, and the first node whose value sits *between* the two targets (one target ≤ it ≤ other) is the LCA, because that's where the search paths to the two values diverge. O(h). For a **general binary tree** (no ordering), recurse: if the current node is either target, return it; otherwise recurse both sides, if both sides return non-null, *this* node is the split point and thus the LCA; if only one side does, bubble that up. Knowing the BST shortcut *and* the general fallback is the flex here.

3. **Maximum depth / check if balanced.** Max depth is the one-liner `1 + max(depth(left), depth(right))`, base case 0 for null, pure post-order recursion. "Is it height-balanced?" builds on it: a tree is balanced iff both subtrees are balanced *and* their heights differ by ≤ 1. The trick to do it in **O(n)** instead of O(n²) is to have the recursion return the height *and* signal imbalance in one pass (e.g. return `-1` as a sentinel meaning "already unbalanced") rather than recomputing height at every node.

4. **Level-order / zigzag traversal.** Level-order is BFS with a queue, grouped per level by snapshotting the queue length each round (mistake #8). **Zigzag** is the same but you reverse the direction every other level, left-to-right, then right-to-left, alternating. Easiest implementation: do normal level-order, then reverse the odd-indexed level lists. They're testing whether you default to a queue for breadth-first and whether you handle the per-level boundary cleanly.

5. **Invert / mirror a tree.** Famously the "Homebrew author got rejected for not being able to whiteboard this" problem. Swap every node's left and right children, recursively. Three lines. The point isn't difficulty, it's whether you can translate "mirror the tree" into a clean recursive swap without flailing.

6. **Serialize and deserialize a tree.** Turn a tree into a string and back. Preorder with explicit null markers (e.g. `1,2,#,#,3,#,#`) is the standard trick: the nulls make the structure unambiguous so deserialize can rebuild it with a single preorder pass over the tokens. This tests whether you understand that *plain* preorder alone loses shape information, you need the null sentinels (or two traversals) to reconstruct uniquely.

7. **Kth smallest element in a BST.** Inorder traversal of a BST yields sorted order, so the kth element visited inorder is the kth smallest. Don't materialize the whole list, do an **iterative inorder** and stop after popping the kth node. O(h + k). The insight they want: "inorder of a BST is sorted, so this is just counting."

8. **Path sum.** "Is there a root-to-leaf path summing to a target?" Recurse subtracting the current value from the target; at a leaf, success iff the remaining target equals the leaf's value. Variants (count all such paths, find paths anywhere not just root-to-leaf) build on the same DFS-with-running-sum skeleton. Tests careful base-case handling, a leaf is "no children," not "null."

The meta-lesson for interviews: almost every tree problem is *"recurse, do something with the node, combine the results from the two subtrees."* If you're stuck, write that skeleton first and then ask "what do you do at the node, and how do you combine left and right?" That frame solves the large majority of them.

10. **Identical trees.** Write `same_tree(p, q)` returning `True` iff two trees have identical structure and values.

### Solutions

```python
from math import inf
from collections import deque

# Reuse the chapter's Node and BST. A small fixture:
def make_bst(values):
    b = BST()
    for v in values:
        b.insert(v)
    return b

# ---- 1. Count leaves ----
def count_leaves(node):
    if node is None:
        return 0
    if node.left is None and node.right is None:
        return 1
    return count_leaves(node.left) + count_leaves(node.right)
# Time O(n), space O(h) recursion stack.

# ---- 2. Max depth (in nodes) ----
def max_depth(node):
    if node is None:
        return 0
    return 1 + max(max_depth(node.left), max_depth(node.right))
# Time O(n), space O(h).

# ---- 3. Sum of all values ----
def tree_sum(node):
    if node is None:
        return 0
    return node.value + tree_sum(node.left) + tree_sum(node.right)
# Time O(n), space O(h).

# ---- 4. Mirror / invert (in place) ----
def invert(node):
    if node is None:
        return None
    node.left, node.right = node.right, node.left   # swap
    invert(node.left)
    invert(node.right)
    return node
# Time O(n), space O(h).

# ---- 5. Validate a BST (bounds method) ----
def is_bst(node, low=-inf, high=inf):
    if node is None:
        return True
    if not (low < node.value < high):       # must fall strictly inside the range
        return False
    # going left tightens the UPPER bound; going right tightens the LOWER bound
    return is_bst(node.left, low, node.value) and is_bst(node.right, node.value, high)
# Time O(n), space O(h). Correct because each node inherits the constraints
# of EVERY ancestor, not just its parent.

# ---- 6. Min and max in a BST ----
def bst_min(node):
    if node is None:
        raise ValueError("empty tree")
    while node.left is not None:     # smallest is the leftmost node
        node = node.left
    return node.value

def bst_max(node):
    if node is None:
        raise ValueError("empty tree")
    while node.right is not None:    # largest is the rightmost node
        node = node.right
    return node.value
# Time O(h), space O(1).

# ---- 7. Kth smallest in a BST (iterative inorder, early stop) ----
def kth_smallest(root, k):
    stack, node, count = [], root, 0
    while stack or node:
        while node:
            stack.append(node)
            node = node.left
        node = stack.pop()
        count += 1
        if count == k:              # kth node visited inorder == kth smallest
            return node.value
        node = node.right
    raise ValueError("k larger than tree size")
# Time O(h + k), space O(h). Stops as soon as we've seen k nodes.

# ---- 8. Lowest common ancestor in a BST ----
def lca_bst(root, a, b):
    node = root
    while node is not None:
        if a < node.value and b < node.value:
            node = node.left            # both targets are smaller -> go left
        elif a > node.value and b > node.value:
            node = node.right           # both larger -> go right
        else:
            return node.value           # split point (or one equals node): LCA
    raise ValueError("targets not found")
# Time O(h), space O(1). The first node that sits between a and b is where
# their search paths diverge -> the lowest common ancestor.

# ---- 9. Level-order as list-of-lists ----
def level_order_levels(root):
    levels = []
    if root is None:
        return levels
    q = deque([root])
    while q:
        size = len(q)                   # snapshot THIS level's count first
        row = []
        for _ in range(size):           # pop exactly that many
            node = q.popleft()
            row.append(node.value)
            if node.left:
                q.append(node.left)
            if node.right:
                q.append(node.right)
        levels.append(row)
    return levels
# Time O(n), space O(w) for the queue.

# ---- 10. Identical trees ----
def same_tree(p, q):
    if p is None and q is None:
        return True
    if p is None or q is None:          # one ran out before the other
        return False
    return (p.value == q.value
            and same_tree(p.left, q.left)
            and same_tree(p.right, q.right))
# Time O(n), space O(h).

# ---- 11. Count nodes in a range [lo, hi] in a BST ----
def range_count(node, lo, hi):
    if node is None:
        return 0
    if node.value < lo:                 # whole left subtree is too small: prune it
        return range_count(node.right, lo, hi)
    if node.value > hi:                 # whole right subtree is too big: prune it
        return range_count(node.left, lo, hi)
    # lo <= node.value <= hi: count this node and recurse both sides
    return 1 + range_count(node.left, lo, hi) + range_count(node.right, lo, hi)
# Time O(h + m) where m = matches, space O(h). Pruning skips entire subtrees
# that can't contain values in range.

# ---------- TESTS ----------
b = make_bst([50, 30, 70, 20, 40, 60, 80])
root = b.root

assert lca_bst(root, 20, 40) == 30          # diverge at 30
```

## 🧪 Extra practice - an expression tree (build, evaluate, pretty-print)

Here's a second mini-project, distinct from the autocomplete trie. An **expression tree** represents an arithmetic expression as a binary tree: each **leaf is a number** and each **internal node is an operator** whose two children are its operands. The structure *is* the precedence, no parentheses needed, because the shape already encodes what binds to what.

```
   (3 + 4) * 5   becomes:

        *
       / \
      +   5
     / \
    3   4
```

The three classic things to do with one:
- **Build** it from **postfix** (Reverse Polish) notation, postfix is the perfect input because it's exactly the order a stack-based builder wants.
- **Evaluate** it, pure postorder recursion: evaluate both children, then apply the operator. (Children-before-parent is *literally* what evaluation needs, which is why postorder's use case is "deleting/computing.")
- **Pretty-print** it, an inorder traversal with parentheses reconstructs the human-readable infix form.

Building from postfix is the elegant bit. You scan left to right pushing nodes onto a stack: a number becomes a leaf node and gets pushed; an operator pops the **two** most recent nodes as its right and left children (right first, it was pushed last), then pushes the new operator node. When the scan ends, the single node left on the stack is the root.

```python
class ExprNode:
    """Leaf holds a number; internal node holds an operator string."""
    def __init__(self, value, left=None, right=None):
        self.value = value      # a number (leaf) or an operator like '+'
        self.left = left
        self.right = right

    def is_leaf(self):
        return self.left is None and self.right is None


OPS = {
    '+': lambda a, b: a + b,
    '-': lambda a, b: a - b,
    '*': lambda a, b: a * b,
    '/': lambda a, b: a / b,
}


def build_from_postfix(tokens):
    """
    tokens: list like ['3', '4', '+', '5', '*']  (postfix / RPN)
    Returns the root of the expression tree.
    """
    stack = []
    for tok in tokens:
        if tok in OPS:
            # operator: pop two operands. The LAST pushed is the RIGHT operand.
            right = stack.pop()
            left = stack.pop()
            stack.append(ExprNode(tok, left, right))
        else:
            stack.append(ExprNode(float(tok)))   # number -> leaf
    if len(stack) != 1:
        raise ValueError("malformed postfix expression")
    return stack.pop()


def evaluate(node):
    """Postorder: compute both children, then apply this node's operator."""
    if node.is_leaf():
        return node.value
    left_val = evaluate(node.left)      # L
    right_val = evaluate(node.right)    # R
    return OPS[node.value](left_val, right_val)   # N (apply operator)


def to_infix(node):
    """Inorder with parentheses -> human-readable infix string."""
    if node.is_leaf():
        # print whole numbers without a trailing .0 for readability
        v = node.value
        return str(int(v)) if v == int(v) else str(v)
    left_str = to_infix(node.left)      # L
    right_str = to_infix(node.right)    # R
    return f"({left_str} {node.value} {right_str})"   # N in the middle
```

Now tests with expected output spelled out:

```python
# (3 + 4) * 5  ==  35
tree = build_from_postfix(['3', '4', '+', '5', '*'])
assert evaluate(tree) == 35.0
assert to_infix(tree) == "((3 + 4) * 5)"

# 3 + 4 * 5  ==  23   (note the DIFFERENT tree shape encodes precedence)
tree2 = build_from_postfix(['3', '4', '5', '*', '+'])
assert evaluate(tree2) == 23.0
assert to_infix(tree2) == "(3 + (4 * 5))"

# a bigger one: ((10 - 2) / 4) + (6 * 3)  ==  2 + 18  ==  20
#   postfix:  10 2 - 4 / 6 3 * +
tree3 = build_from_postfix(['10', '2', '-', '4', '/', '6', '3', '*', '+'])
assert evaluate(tree3) == 20.0
assert to_infix(tree3) == "(((10 - 2) / 4) + (6 * 3))"

# division producing a float
tree4 = build_from_postfix(['7', '2', '/'])
assert evaluate(tree4) == 3.5
assert to_infix(tree4) == "(7 / 2)"

print("expression tree OK")
print("  (3 4 + 5 *) ->", to_infix(tree), "=", evaluate(tree))
print("  (3 4 5 * +) ->", to_infix(tree2), "=", evaluate(tree2))
```

Expected console output:

```
expression tree OK
  (3 4 + 5 *) -> ((3 + 4) * 5) = 35.0
  (3 4 5 * +) -> (3 + (4 * 5)) = 23.0
```

What's beautiful about this project: the *same data structure* serves three jobs just by traversing it differently. **Build** is a stack scan, **evaluate** is postorder (children first, you can't apply `+` until you know both operands), and **pretty-print** is inorder (operator sits between its operands, exactly where infix wants it). The two trees for `3 4 + 5 *` versus `3 4 5 * +` evaluate to 35 and 23 from the *same numbers and operators*, because the tree shape, not the symbols, encodes precedence. That's the same lesson as the BST: in tree-land, the shape is doing the work.
