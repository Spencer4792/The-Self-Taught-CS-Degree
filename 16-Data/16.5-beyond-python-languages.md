# Chapter 16.5 - Beyond Python: Go, C++, R, Node.js

> Goal: Stop being a "Python developer" and become a *programmer* who reaches for the right language. If your resume already lists Go, C++, R, and Node.js, this chapter turns "I've touched them" into "I can read, reason about, and pick between them on purpose." For each language you'll get the mental model, where it shines and who runs it in production, the type/memory story in one paragraph, and the *same small program* across all of them so the syntax stops being noise and the concepts shine through. By the end you can drop into an unfamiliar codebase in any of these four and be productive in an afternoon.

The big realization: **languages are mostly the same ideas wearing different clothes.** Variables, functions, loops, types, collections, error handling, concurrency, every language has them. Learning a new language fast is *not* memorizing syntax; it's *mapping the concepts you already own onto new spelling.* This chapter builds that map.

## Start here - the on-ramp (read this even if you're brand new)

Why would anyone learn five languages? Isn't one enough? Here's the honest answer: **languages are tools, and tools have shapes.** You *can* hammer a screw with a wrench, but it's miserable. Python is a wonderful all-rounder, but:
- Need a tiny, blazing-fast network service that deploys as a single file? **Go** was built for exactly that.
- Need to control every byte and squeeze a GPU/embedded device for maximum speed? **C++**.
- Doing serious statistics and publication-quality plots from a data frame? **R** speaks that natively.
- Building a web frontend *and* its backend in one language, sharing types? **Node.js/TypeScript**.

The deeper reason: **knowing multiple languages teaches you which ideas are universal and which are accidents of one language.** Once you've seen Go's explicit `if err != nil`, Python's exceptions stop feeling like "the way" and start feeling like "a choice with tradeoffs." Multilingualism makes you a better Python programmer too.

The on-ramp skill, **reading a new language fast**, is a *translation* skill. Every language answers the same handful of questions, and if you find those answers, you can read anything:
1. How do you declare a variable and a function?
2. How do you loop and branch?
3. What are the collection types (list/array, map/dict)?
4. How does it handle errors (exceptions? return values?)?
5. How does it manage memory (garbage-collected? manual? ownership?)?
6. How do you run it (interpreter? compiler? build step?)?

Answer those six and the rest is library lookups. Keep this in mind: **you already know the concepts; you're just learning new spellings for them.** The "Rosetta stone" programs below print the *same* logic in four languages side by side so the concepts line up and only the spelling differs.

## How to read code in a new language, fast

A concrete drill to run on any unfamiliar codebase or snippet:

1. **Find the entry point.** `main()` in Go/C++, the top-level script in Python/Node, `if __name__`. Where does execution start?
2. **Map the six questions** above by skimming: how are variables/functions declared, how are errors handled, what's the collection syntax.
3. **Identify the type discipline.** Are types written explicitly (`int x`), inferred (`x := 5`), or absent (`x = 5`)? Static (checked at compile time) or dynamic (checked at run time)?
4. **Spot the idioms.** Every language has 3-4 signature patterns (Go's `if err != nil`, C++'s RAII, R's vectorized ops, Node's callbacks/promises). Once you recognize them, the code reads like prose.
5. **Run it / read the tests.** Tests show *intended* behavior and usage in real shape.

Do this and an unfamiliar language is approachable in an afternoon, because, again, **it's the same concepts in new clothes.**

### The four languages at a glance

| | C++ | Go | R | Node.js / TS |
|---|---|---|---|---|
| **Born for** | max performance, control | simple concurrent services | statistics & data | web (front + back) |
| **Typing** | static, manual | static, inferred | dynamic | dynamic (TS: static) |
| **Memory** | manual / RAII | garbage-collected | garbage-collected | garbage-collected |
| **Concurrency** | threads, std::async | goroutines + channels | mostly single-thread | event loop (async) |
| **Compiled?** | yes (to native) | yes (to native, 1 binary) | interpreted | JIT (V8) |
| **Typical use** | perf-critical kernels | Go microservices | data/stats work | Next.js / Node APIs |

## C++ - when performance demands it

### Where it shines & who uses it

C++ is the language of **maximum control and maximum speed**: game engines (Unreal), browsers (Chrome's core), databases, high-frequency trading, embedded/real-time systems, ML framework internals (PyTorch/TensorFlow are C++ under the Python skin), and anything where you must account for every microsecond and every byte. If Python is "I'll let the runtime manage memory and pay the overhead," C++ is "I manage everything and pay nothing I didn't ask for."

### The mental model

**You are the runtime.** There's no interpreter and (by default) no garbage collector standing between your code and the machine. You decide where data lives (stack vs. heap), when memory is freed, and you can take the *address* of anything. The compiler turns your code straight into native machine instructions, which is why it's fast and why mistakes (use-after-free, buffer overruns) are *your* bug, not a caught exception. Ties directly to **05.1 (memory)**: stack vs. heap, pointers, and layout are first-class concerns here, not abstractions.

### Type system / memory model in brief

**Statically and manually typed**, every variable's type is fixed at compile time and usually written out (`int`, `double`, `std::vector<int>`), though `auto` infers. Memory is **manual**: objects on the stack die at end of scope; objects on the heap (`new`) live until you `delete` them, or, idiomatically, until a smart pointer does. **Pointers** hold an address (`int* p = &x;`); **references** (`int& r = x;`) are an alias that can't be null or reseated. The killer idiom is **RAII (Resource Acquisition Is Initialization)**: tie a resource's lifetime to an object's scope, so the destructor frees it automatically when the object goes out of scope, *deterministic* cleanup without a GC. Modern C++ does this with `std::unique_ptr`/`std::shared_ptr` so you rarely write raw `new`/`delete`:

```cpp
#include <memory>
{
    auto p = std::make_unique<int>(42);   // heap int, owned by p
    use(*p);
}   // <-- p goes out of scope HERE; its destructor frees the int. No leak, no GC.
```

That scope-bound cleanup is *why* C++ can be both fast and safe-ish: no GC pauses, but no manual `delete` to forget either. (Reach for C++ when profiling proves a kernel needs it, see **16.4** "going native.")

### Hands-on example - pointers, references, a vector

```cpp
#include <iostream>
#include <vector>

void addOne(int& r) { r += 1; }       // reference: modifies caller's variable in place

int main() {
    std::vector<int> nums {3, 1, 4, 1, 5};   // dynamic array
    int x = 10;
    int* p = &x;                              // p holds the ADDRESS of x
    std::cout << "x via pointer: " << *p << "\n";   // *p dereferences -> 10
    addOne(x);                                 // pass by reference
    std::cout << "x after addOne: " << x << "\n";   // 11

    int sum = 0;
    for (int n : nums) sum += n;              // range-based for
    std::cout << "sum: " << sum << "\n";      // 14
}
// build: g++ -std=c++20 -O2 demo.cpp -o demo && ./demo
```

## Go - simple, concurrent services

### Where it shines & who uses it

Go was built at Google to make **simple, fast, concurrent network services**, and that's exactly where it dominates: microservices, CLIs, DevOps tooling (Docker, Kubernetes, Terraform are all Go), API servers, anything cloud-native. It compiles to a **single static binary** (no runtime to install, just `scp` and run), starts instantly, and its concurrency model is the easiest in the industry. This is the Go-microservices wheelhouse.

### The mental model

**Boring on purpose, concurrent by design.** Go deliberately omits features (no inheritance, no generics until recently, no exceptions) to keep code uniform and readable across a big team, there's usually one obvious way to do a thing. The standout idea: **goroutines and channels**. A goroutine is a function running concurrently, but it's *cheap*, you can spin up hundreds of thousands (they're scheduled onto OS threads by the Go runtime, not 1:1). Goroutines communicate by **passing messages over channels** rather than sharing memory and locking: *"Don't communicate by sharing memory; share memory by communicating."*

### Type system / memory model in brief

**Statically typed with inference**, types are checked at compile time but `x := 5` infers the type, so it reads almost as light as Python. **Garbage-collected**, so no manual memory management, but with a low-latency GC tuned for services. Errors are **values, not exceptions**: functions return an `error` as the last value and you check it explicitly with `if err != nil { ... }`, verbose, but it makes every failure path visible (no invisible `try/except` to forget). Interfaces are *structural* ("if it has these methods, it satisfies the interface", no `implements` keyword).

### Hands-on example - goroutines + channels

```go
package main

import (
    "fmt"
    "sync"
)

// each worker pulls jobs off `jobs`, sends squares to `results`
func worker(id int, jobs <-chan int, results chan<- int, wg *sync.WaitGroup) {
    defer wg.Done()
    for n := range jobs {       // receive until channel closed
        results <- n * n        // send result
    }
}

func main() {
    jobs := make(chan int, 100)
    results := make(chan int, 100)
    var wg sync.WaitGroup

    for w := 1; w <= 3; w++ {           // launch 3 concurrent workers
        wg.Add(1)
        go worker(w, jobs, results, &wg)   // `go` = run concurrently as a goroutine
    }
    for j := 1; j <= 9; j++ { jobs <- j }  // feed work
    close(jobs)
    wg.Wait(); close(results)              // wait for workers, then close results

    sum := 0
    for r := range results { sum += r }    // 1+4+9+...+81 = 285
    fmt.Println("sum of squares:", sum)
}
// run: go run demo.go    |    build: go build -o demo demo.go && ./demo
```

That's the whole Go concurrency story in 30 lines: launch goroutines with `go`, hand work and results over channels, synchronize with a `WaitGroup`. No locks, no race conditions to reason about, the channel *is* the synchronization. Concepts tie back to **05.2 (concurrency)**.

## R - vectors, data frames, statistics

### Where it shines & who uses it

R is a language **by statisticians, for statisticians.** Where Python is a general language that *grew* data tools, R was *born* for data analysis, every design decision favors interactive stats, modeling, and publication-quality plots. It dominates academic statistics, biostatistics/clinical trials, econometrics, and anywhere the work is "load a data frame, model it, visualize it, write the paper." It ties straight into your data work and the stats/EDA in **16.1**.

### The mental model

**Everything is a vector, and operations are vectorized by default.** In R there's no scalar, `x <- 5` is really a length-1 vector. So `c(1,2,3) * 2` gives `c(2,4,6)` with no loop, and this vector-thinking pervades the language (the way NumPy *adds* it to Python, R *is* it). The other pillar is the **data frame**: a table of columns where each column is a typed vector, the direct ancestor of pandas' DataFrame. Modern R revolves around the **tidyverse**: `dplyr` for data manipulation with a readable pipe (`%>%` or `|>`), `ggplot2` for grammar-of-graphics plots (the *very* grammar from **16.3**), `tidyr` for reshaping.

### Type system / memory model in brief

**Dynamically typed and garbage-collected** (like Python, no type declarations, runtime checks). The unusual bits: it's **copy-on-modify** (assigning/passing a vector behaves as a copy, so functions can't accidentally mutate your data, safe but can be memory-heavy), and it's **1-indexed** (`v[1]` is the first element, a constant gotcha coming from 0-indexed languages). The core types are vectors, lists, matrices, and data frames; `NA` is a first-class "missing value" baked into the language, which is *why* it's so good for messy real data.

### Hands-on example - vectors, a data frame, the tidyverse pipe

```r
library(dplyr)

# everything's a vector; operations vectorize with no loop
prices <- c(120, 150, 180, 240)
withTax <- prices * 1.08              # -> 129.6 162.0 194.4 259.2

# a data frame = typed columns (ancestor of pandas)
df <- data.frame(
  quarter  = c("Q1","Q2","Q3","Q4"),
  revenue  = prices,
  region   = c("US","US","EU","EU")
)

# tidyverse pipe: read top-to-bottom like a sentence
summary <- df |>
  filter(revenue > 130) |>            # keep big quarters
  group_by(region) |>                 # group
  summarise(total = sum(revenue))     # aggregate
print(summary)
#   region total
#   EU      420
#   US      150

# stats + plot are one-liners, the reason R exists
fit <- lm(revenue ~ seq_along(revenue), data = df)   # linear model
print(coef(fit))
# library(ggplot2); ggplot(df, aes(quarter, revenue)) + geom_col()
```

That `lm(y ~ x)` formula syntax and built-in `summary()`/plotting are R's superpower, statistics is *in the language*, not a library afterthought.

## Node.js / TypeScript - the event loop and the web

### Where it shines & who uses it

Node.js runs JavaScript *outside* the browser, which means **one language for the frontend and backend.** It dominates web backends, real-time apps (chat, collaborative tools), API gateways, build tooling, and serverless functions, anywhere I/O concurrency matters more than raw CPU. With **TypeScript** (JS + a static type layer) on top, you can share types between your Next.js frontend and your Node API, exactly the full-stack stack, and it ties to **08.1/08.2 (frontend/backend)**.

### The mental model

**Single-threaded, but never blocks.** Node runs your JS on *one* thread with an **event loop**: when you hit an I/O operation (read a file, query a DB, call an API), Node doesn't sit and wait, it registers a callback, moves on to other work, and comes back when the I/O finishes. So one thread juggles thousands of concurrent connections by never blocking on any of them. This is *why* Node is fantastic for I/O-bound web work (lots of waiting) and *poor* for CPU-bound work (a heavy computation blocks the single thread and freezes everything). The modern syntax for this is `async`/`await` over **Promises** (a Promise = "a value that will arrive later"). Same I/O-bound-vs-CPU-bound distinction as **05.2** and **16.4**, Node just bakes the async model into the language.

### Type system / memory model in brief

JavaScript is **dynamically typed and garbage-collected**; **TypeScript** adds a *static, structural* type layer that's checked at compile time and then erased (it compiles to plain JS, types vanish at runtime). Structural typing means "if the shape matches, it fits" (like Go's interfaces). The ecosystem is **npm**, the world's largest package registry, `npm install` pulls dependencies into `node_modules`, and `package.json` declares them.

### Hands-on example - a tiny async API

```typescript
// server.ts  -  run: npx ts-node server.ts   (or compile with tsc)
import http from "node:http";

type Item = { id: number; name: string };
const items: Item[] = [{ id: 1, name: "NYX" }, { id: 2, name: "Anneava" }];

async function fakeDbLookup(id: number): Promise<Item | undefined> {
  // simulate async I/O - the event loop is free during this wait
  return new Promise((resolve) =>
    setTimeout(() => resolve(items.find((it) => it.id === id)), 50)
  );
}

const server = http.createServer(async (req, res) => {
  const id = Number(new URL(req.url!, "http://x").searchParams.get("id"));
  const item = await fakeDbLookup(id);          // non-blocking await
  res.writeHead(item ? 200 : 404, { "Content-Type": "application/json" });
  res.end(JSON.stringify(item ?? { error: "not found" }));
});

server.listen(3000, () => console.log("listening on :3000"));
// curl 'localhost:3000?id=1'  ->  {"id":1,"name":"NYX"}
```

While `fakeDbLookup` "waits" 50ms, the event loop serves *other* requests, that's the whole non-blocking model in one example.

## The Rosetta stone - one program, four languages

Same logic everywhere: **build a list of numbers, keep the evens, sum their squares.** Watching the *same* concepts (declare, collection, loop/filter, function) line up across syntaxes is how the spelling stops being scary.

**Python:**
```python
def sum_even_squares(nums):
    return sum(n*n for n in nums if n % 2 == 0)
print(sum_even_squares([1, 2, 3, 4, 5, 6]))   # 4+16+36 = 56
```

**Go**, static types, explicit loop:
```go
func sumEvenSquares(nums []int) int {
    sum := 0
    for _, n := range nums {        // _ ignores the index
        if n%2 == 0 { sum += n * n }
    }
    return sum
}
// sumEvenSquares([]int{1,2,3,4,5,6}) -> 56
```

**C++**, static types, range-for, manual accumulation:
```cpp
int sumEvenSquares(const std::vector<int>& nums) {
    int sum = 0;
    for (int n : nums)              // const& : no copy of the vector
        if (n % 2 == 0) sum += n * n;
    return sum;
}
// sumEvenSquares({1,2,3,4,5,6}) -> 56
```

**R**, vectorized, no explicit loop at all (the R way):
```r
sum_even_squares <- function(nums) {
  evens <- nums[nums %% 2 == 0]    # logical-index filter, vectorized
  sum(evens^2)                     # vectorized square + sum
}
# sum_even_squares(1:6) -> 56
```

**Node/TypeScript**, methods chained, functional style:
```typescript
const sumEvenSquares = (nums: number[]): number =>
  nums.filter((n) => n % 2 === 0)
      .reduce((acc, n) => acc + n * n, 0);
// sumEvenSquares([1,2,3,4,5,6]) -> 56
```

Five spellings, one idea. Notice the *flavors*: Python's generator expression, Go/C++'s explicit typed loop, R's "no loop, just vectorize," Node's method-chain. Each reveals the language's personality, and once you see the shared skeleton, reading any of them is easy.

## Error handling across languages - the deepest "same idea, different clothes"

How a language handles failure shapes how its whole codebase *feels*, and it's one of the sharpest contrasts between these four. There are two big philosophies:

**Exceptions (Python, Node/JS, C++):** failures *throw* and unwind the stack until something *catches* them. Pro: the happy path stays clean (no error-checking clutter); error handling is centralized. Con: failures are *invisible* in the code, any line might throw, and a missing `catch` crashes the program or silently swallows the problem.

```python
try:
    data = json.loads(text)          # might throw
    result = process(data)
except (ValueError, KeyError) as e:  # catch specific failures
    log.error(f"bad input: {e}"); result = None
```

```typescript
try { const data = JSON.parse(text); }
catch (e) { console.error("bad input", e); }   // JS: catch is untyped (any error)
```

**Errors as values (Go, and Rust):** a function *returns* its error alongside its result, and you check it explicitly. Pro: every failure path is *visible* in the code, you can't accidentally ignore an error without literally writing `_`. Con: verbose; the `if err != nil` appears constantly.

```go
data, err := json.Unmarshal(text)
if err != nil {                       // EVERY failure is right here, in your face
    return fmt.Errorf("bad input: %w", err)   // wrap and propagate
}
result, err := process(data)
if err != nil { return err }
```

**C++ has both**, exceptions *and* error codes / `std::optional` / `std::expected`, which is part of why C++ codebases vary so much in style. **R** uses `tryCatch()` (exceptions) plus a "condition system" with warnings and the `NA` value for missing data, so a lot of "errors" are just `NA` flowing through a computation.

The lesson: **once you've seen errors-as-values, you understand the tradeoff Python's exceptions make**, clean happy path *bought with* invisible failure points. Neither is "right"; Go optimizes for "no surprise failures in a 24/7 service," Python optimizes for "readable scripts." Knowing both makes you write more careful Python (catch *specific* exceptions, never bare `except:`).

## Build tooling and dependencies - the unglamorous part you must know

You can't be productive in a language without knowing how to install a dependency and build/run the code. The one-paragraph survival guide per language:

- **Python:** `pip install` into a **virtual environment** (`python -m venv`, or `uv`/`poetry` for modern dependency locking). `requirements.txt` / `pyproject.toml` declare deps. Interpreted, just `python script.py`.
- **Go:** `go mod init` creates a module; `go get` adds deps to `go.mod`; `go build` produces **one static binary**, `go run` runs without a separate build, `go test` runs tests. Tooling is built-in and uniform, a huge Go selling point.
- **C++:** the messy one. No standard package manager historically; you use **CMake** (the de-facto build system) plus a package manager like **vcpkg** or **Conan**, and link libraries explicitly. Compile with `g++`/`clang++`. The build complexity is real and a genuine cost of the language.
- **Node/TS:** `npm install` (or `pnpm`/`yarn`) pulls deps into `node_modules`; `package.json` declares them and defines `scripts`. TypeScript adds a compile step (`tsc`) or you run directly with `ts-node`/`tsx`. The npm registry is vast, and so is the dependency-bloat and supply-chain-risk surface, which you manage with lockfiles and audits.
- **R:** `install.packages()` from CRAN (the vetted central repo); `library()` to load. `renv` for reproducible project environments. Interpreted, usually run interactively or via `Rscript`.

The transferable insight: **every ecosystem has the same three things**, a *registry* (PyPI / pkg.go.dev / vcpkg / npm / CRAN), a *manifest* declaring dependencies, and a *lockfile* pinning exact versions for reproducibility. Find those three and you can manage any project's dependencies.

## How to pick a language for a task

The decision is mostly about the *shape of the problem*:

| If the task is... | Reach for... | Because |
|---|---|---|
| Data analysis, ML, scripting, glue | **Python** | huge ecosystem, fastest to write, readable |
| Heavy statistics, modeling, stats plots | **R** | stats & ggplot2 are native; tidyverse |
| A small fast network service / CLI | **Go** | single binary, instant start, easy concurrency |
| Max performance, control, embedded/games | **C++** | native speed, manual memory, zero-overhead |
| Web app (front + back, real-time, I/O) | **Node/TS** | one language full-stack, async I/O, shared types |
| A hot kernel inside a Python program | **C++/Rust/Numba** | drop down only for the proven bottleneck (16.4) |

Practical wisdom: **start in the highest-level language that fits (usually Python), and drop to a lower one only where measurement says you must.** Most systems are "Python/Node for 95% of the code, a fast Go service or C++ kernel for the 5% that's hot." Don't pick C++ for a CRUD API or Python for a 1ms-latency trading loop, match the tool to the shape. And factor in the *team* and *ecosystem*, not just the language: the best language is often the one your team can maintain and the one with the library you need.

## Concurrency models, compared

"Do many things at once" looks different in each language, and the model shapes what the language is *good for*. Lining them up makes the design tradeoffs obvious:

- **C++, OS threads + manual synchronization.** `std::thread`, `std::async`, mutexes, atomics. True parallelism, maximum control, *maximum footgun*: data races and deadlocks are yours to prevent. You reach for this when you need to squeeze every core and are willing to reason about locks carefully.
- **Go, goroutines + channels (CSP).** The easiest model in the industry: spawn with `go f()`, coordinate by passing messages over channels. The runtime multiplexes hundreds of thousands of goroutines onto a few OS threads, so concurrency is *cheap* and *parallel*. "Don't communicate by sharing memory; share memory by communicating." This is *why* Go owns the concurrent-services niche.
- **Node/JS, single-threaded event loop.** No threads in your code at all (by default); concurrency comes from *never blocking*, async/await over Promises while the event loop juggles I/O. Brilliant for I/O-bound web work, useless for parallel CPU (one thread). Worker threads exist for CPU work but are not the idiom.
- **Python, threads (GIL-limited), async, or multiprocessing.** Threads for I/O overlap only (the GIL blocks parallel CPU); `asyncio` for high-concurrency I/O; `multiprocessing` for true CPU parallelism via separate processes. The most fragmented story of the four, you pick the tool per workload (see **16.4**).
- **R, mostly single-threaded**, with `parallel`/`future` packages for embarrassingly-parallel work (e.g., parallel cross-validation). Concurrency isn't R's focus; data analysis usually isn't latency-bound.

The pattern across all of them: every model is trading **safety vs. control vs. simplicity**. C++ gives control at the cost of safety; Go gives simplicity *and* safety by constraining how you share; Node gives simplicity by removing threads entirely. Knowing the spectrum lets you say *why* a concurrent service is easier to write in Go than C++, a high-signal thing to articulate.

## Build it - read an unfamiliar snippet using the six questions

Drill: here's Go you've "never seen." Apply the six questions and decode it without docs.

```go
m := map[string]int{}
for _, w := range strings.Fields(text) {
    m[w]++
}
```

1. **Declare?** `m := ...`, `:=` declares-and-infers a variable. 2. **Collection?** `map[string]int{}`, a map (dict) from string→int, empty. 3. **Loop?** `for _, w := range ...`, iterate, ignoring the index (`_`), binding each value to `w`. 4. **What's `strings.Fields(text)`?** library call, splits a string on whitespace into a slice. 5. **`m[w]++`?** increment the count for key `w` (Go zero-initializes missing map entries to 0). **Conclusion:** it's a **word-frequency counter**, the exact pattern as Python's `collections.Counter`. You read unfamiliar Go correctly by mapping it onto concepts you own.

## Mini-project: word-frequency counter in Python, Go, and Node

Implement the *same* program, count word frequencies in a text and print the top 3, in three languages, then compare the experience. This is the perfect Rosetta exercise because it touches I/O, strings, a map/dict, sorting, and output in each.

**Python** (`wf.py`):
```python
import sys, re
from collections import Counter

text = sys.stdin.read().lower()
words = re.findall(r"[a-z']+", text)
for word, n in Counter(words).most_common(3):
    print(f"{word}\t{n}")
# echo "the cat the dog the bird" | python wf.py  ->  the 3 / cat 1 / dog 1
```

**Go** (`wf.go`), explicit map, manual sort:
```go
package main

import (
    "bufio"; "fmt"; "os"; "regexp"; "sort"; "strings"
)

func main() {
    data, _ := bufio.NewReader(os.Stdin).ReadString(0)   // read all stdin
    words := regexp.MustCompile(`[a-z']+`).FindAllString(strings.ToLower(data), -1)
    counts := map[string]int{}
    for _, w := range words { counts[w]++ }

    type pair struct{ word string; n int }
    pairs := make([]pair, 0, len(counts))
    for w, n := range counts { pairs = append(pairs, pair{w, n}) }
    sort.Slice(pairs, func(i, j int) bool { return pairs[i].n > pairs[j].n })   // desc

    for i := 0; i < 3 && i < len(pairs); i++ {
        fmt.Printf("%s\t%d\n", pairs[i].word, pairs[i].n)
    }
}
// echo "the cat the dog the bird" | go run wf.go
```

**Node / TypeScript** (`wf.ts`), object as map, functional sort:
```typescript
let text = "";
process.stdin.on("data", (c) => (text += c));
process.stdin.on("end", () => {
  const words = text.toLowerCase().match(/[a-z']+/g) ?? [];
  const counts: Record<string, number> = {};
  for (const w of words) counts[w] = (counts[w] ?? 0) + 1;
  Object.entries(counts)
    .sort((a, b) => b[1] - a[1])          // desc by count
    .slice(0, 3)
    .forEach(([w, n]) => console.log(`${w}\t${n}`));
});
// echo "the cat the dog the bird" | npx ts-node wf.ts
```

**The comparison to write up** (the real deliverable):
- **Lines of code / ceremony:** Python ~6, Node ~10, Go ~20. Python's `Counter.most_common` does in one call what Go does in ~12 lines, that's Python's "batteries included" data ergonomics.
- **Types:** Go forces you to declare the `pair` struct and the map type up front (caught at compile time); Python/Node infer and check at runtime.
- **Error handling:** Go's `_` discards errors explicitly (you *see* there's an error to ignore); Python/Node would throw.
- **Concurrency potential:** none needed here, but if the input were 100 files, Go's goroutines would parallelize the cleanest, Node would use async file reads, Python would reach for multiprocessing (the GIL, **16.4**).
- **Deployment:** `go build` gives one binary you can ship anywhere; Python/Node need their runtime installed.
- **Performance:** on a huge file, Go and (surprisingly often) Node beat CPython on this string-crunching; for the typical small file, all three are instant and *developer time* dominates, which is exactly why you'd pick Python unless something forces otherwise.

That table *is* the lesson: same concepts, different ergonomics and tradeoffs. Picking a language is picking which tradeoffs you want.

## Common mistakes

- **Memorizing syntax instead of mapping concepts.** Find the six answers (declare/loop/collection/errors/memory/run) and the language opens up. Syntax is lookup-able.
- **Writing Python *in* another language.** Each has idioms, Go's `if err != nil`, C++'s RAII, R's vectorization, Node's async. Fighting them produces ugly, slow code. Learn the idiom.
- **R's 1-indexing.** `v[1]` is the first element, not the second. Burns every 0-indexed transplant.
- **Blocking the Node event loop** with CPU-heavy work, it freezes *all* requests. Offload to a worker thread or another language.
- **Manual memory bugs in C++**, use-after-free, leaks, dangling pointers. Use RAII/smart pointers and avoid raw `new`/`delete`.
- **Reaching for C++/Go too early.** Most code should stay in the high-level language; drop down only where measurement (16.4) proves a bottleneck.
- **Confusing JS and TypeScript.** TS types are compile-time only and *erased* at runtime, they don't validate external input. You still validate at the boundary.
- **Ignoring the team/ecosystem.** The "best" language is often the one your team maintains and the one with the library you need, not the theoretically fastest.

## On the job / interview angle

- **"Why would you use Go over Python here?"** Answer with *shape*: concurrent network service, low latency, single-binary deploy, easy goroutine concurrency. The reverse (Python over Go): rich data/ML ecosystem, faster to write, glue work.
- **Explain Go's concurrency model.** Goroutines (cheap, runtime-scheduled) + channels ("share memory by communicating"). It's a favorite Go interview question; contrast with Python's GIL-limited threads (**16.4**).
- **Explain Node's event loop** and why it's great for I/O-bound but bad for CPU-bound work. Single-threaded, non-blocking, async/await over Promises. Core full-stack interview material.
- **RAII / manual memory in C++.** Be able to say what RAII is (resource lifetime tied to scope, destructor frees it) and why it gives deterministic cleanup without a GC. Ties to **05.1**.
- **Static vs dynamic typing tradeoffs.** Static (Go/C++/TS) catches errors at compile time and documents intent; dynamic (Python/R/JS) is faster to write and more flexible. Know when each pays off.
- **"How do you ramp on an unfamiliar language/codebase?"** The six-question framework + read the tests + map onto concepts you know. Demonstrates you're a *programmer*, not a one-language specialist, which is exactly the signal a polyglot resume should send.

## Exercises

Solutions follow.

1. **(Easy)** Match each task to the best-fit language: (a) a 1ms-latency order-matching kernel, (b) a clinical-trial statistical analysis, (c) a real-time chat backend, (d) a Kubernetes-style CLI tool.
2. **(Easy)** In Go, what does `x := 5` do that `var x int = 5` also does, and what's the difference?
3. **(Easy)** Why does R give `c(1,2,3) + c(10,20,30)` as `c(11,22,33)` with no loop?
4. **(Medium)** Explain why heavy CPU work freezes a Node server but many slow DB queries don't.
5. **(Medium)** In C++, what does RAII guarantee, and how does `std::unique_ptr` implement it? What problem does it solve vs. raw `new`/`delete`?
6. **(Medium)** Go and Python both "do concurrency," but a goroutine-heavy program scales across cores while a Python-thread-heavy CPU program doesn't. Why?
7. **(Hard)** You're handed an unfamiliar Rust file. Walk through your six-question framework and name what you'd look for to answer each (even without knowing Rust).
8. **(Hard)** Your Python data pipeline has one numeric kernel that's 90% of runtime. Argue whether to rewrite it in Go, C++, or neither, and how you'd decide.

### Solutions

1. (a) **C++**, max performance/control, no GC pauses, every microsecond counts. (b) **R**, native statistics, modeling, publication plots; the domain's lingua franca. (c) **Node.js**, I/O-bound, real-time, async event loop, JS on both ends. (d) **Go**, single static binary, fast start, the cloud-native tooling standard (Docker/K8s/Terraform are Go).

2. Both declare an `int` `x` equal to 5. `x := 5` uses **type inference** (Go figures out it's `int`) and only works *inside* a function; `var x int = 5` writes the type explicitly and works at package scope too. `:=` is the lighter, more common form inside functions.

3. R is **vectorized by default**, there are no scalars, everything is a vector, and arithmetic operators apply element-wise across vectors automatically. So the `+` adds position-by-position with no explicit loop (the loop runs in compiled C underneath, like NumPy in Python).

4. Node is **single-threaded with an event loop**. A slow DB query is *I/O*, Node registers a callback and the event loop keeps serving other requests during the wait, so concurrency is high. But heavy *CPU* work runs *on* the event-loop thread and never yields, so the loop can't process any other request until it finishes, and every connection freezes. I/O = non-blocking; CPU = blocking. (Fix: worker threads or another language.)

5. **RAII** guarantees a resource is released exactly when its owning object goes out of scope, deterministic cleanup with no GC. `std::unique_ptr` owns a heap object and frees it in its **destructor**, which the compiler calls automatically at end of scope (or on exception unwinding). Vs. raw `new`/`delete`: you can forget the `delete` (leak), `delete` twice (corruption), or skip it on an early `return`/exception. RAII makes those impossible because cleanup is tied to scope, not to you remembering.

6. Goroutines are scheduled by the Go runtime onto multiple OS threads with **no global lock**, so CPU-bound goroutines genuinely run in parallel across cores. Python threads are throttled by the **GIL**, only one thread executes Python bytecode at a time, so CPU-bound Python threads time-slice on one core and don't speed up (you'd need multiprocessing). Go was designed for parallel concurrency; CPython's threading is mainly for I/O overlap (**16.4**).

7. **(1) Entry point:** look for `fn main()`. **(2) Declare:** `let x = 5` (immutable) / `let mut x` (mutable); functions are `fn name(args) -> Ret`. **(3) Collections:** `Vec<T>` (list), `HashMap<K,V>` (dict). **(4) Errors:** look for `Result<T, E>` and `?`/`match` (errors are values, like Go, no exceptions). **(5) Memory:** the distinctive bit, **ownership/borrowing** (`&`, `&mut`, lifetimes); no GC, freed when the owner goes out of scope (RAII-like). **(6) Run:** `cargo run` / `cargo build`. Even without knowing Rust, finding these six answers makes the file readable.

8. The kernel is the hot 90%, so by Amdahl (**16.4**) rewriting it could approach a `1/0.1 = 10×` ceiling, worth considering. **Decision process:** first try staying in Python, **vectorize with NumPy or `@njit` (Numba)**, which often gets most of the win for almost no integration cost. If that's not enough and the kernel is *numeric/tight-loop*, drop to **C++ (or Rust) as a compiled extension** called from Python, maximum speed, keeps the rest of the pipeline in Python. **Go is the wrong choice here**: it's built for concurrent *services*, has GC pauses, and crossing the Python↔Go boundary (cgo) is clunky for an in-process numeric kernel. So: NumPy/Numba first; C++/Rust extension if proven necessary; not Go. And only after the profiler confirms the kernel really is the dominant cost.

## Teach it back

1. **State the six questions for reading any new language fast, and why this beats memorizing syntax.** (Declare variables/functions? loop/branch? collections? error handling? memory management? how to run? Answering these maps the language onto concepts you already own, syntax is lookup-able, concepts are universal.)

2. **Explain Go's goroutines-and-channels model and contrast it with Python threads.** (Goroutines = cheap, runtime-scheduled concurrent functions; channels pass messages, "share memory by communicating." They run in parallel across cores; Python threads are serialized by the GIL for CPU work.)

3. **Explain Node's event loop: why it's great for I/O and bad for CPU.** (Single thread, non-blocking, registers callbacks on I/O and serves other work during the wait, so thousands of concurrent connections; but CPU-heavy work blocks the one thread and freezes everything. async/await over Promises.)

4. **What is RAII in C++, and what does it buy you over a garbage collector?** (Resource lifetime tied to object scope; the destructor frees it automatically at end of scope. Deterministic, immediate cleanup with no GC pauses and no forgotten `delete`, `unique_ptr`/`shared_ptr` implement it.)

5. **Why is R so good for data work, name two language-level reasons.** (Everything is a vector so operations vectorize with no loops; the data frame and formula/stats syntax (`lm(y ~ x)`) plus the tidyverse/ggplot2 make modeling and grammar-of-graphics plots native, not bolt-ons. Plus first-class `NA` for missing data.)

6. **Give the decision framework for picking a language, and the "start high, drop down" rule.** (Match the *shape* of the problem: data→Python, stats→R, fast service/CLI→Go, max perf→C++, full-stack web→Node. Start in the highest-level language that fits, and drop to a lower one only where measurement proves a bottleneck, plus weigh team and ecosystem.)
