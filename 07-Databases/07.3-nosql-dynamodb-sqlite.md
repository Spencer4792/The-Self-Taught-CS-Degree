## Start here

Before any theory, let's ground this with a picture you can hold in your head.

Picture a **rigid metal filing cabinet**, the kind in an old office. Every drawer is labeled, every folder inside has the *exact same printed form*: Name, Address, Account #, Balance. To file anything, you must fill in every field of the form. If a new kind of customer shows up who needs an extra field, say "preferred pronoun" or "crypto wallet", you have to reprint *every form in the building* and re-file everything. But the payoff is enormous: because every folder has the same shape, you can ask wild, unplanned questions, "show me everyone in Ohio with a balance over $10k who opened an account last March", and the cabinet's design lets you answer it. That's **SQL / relational**. Rigid shape up front, total query freedom later.

Now picture a wall of **flexible labeled boxes**. Each box has a label on the front, `user:42`, `cart:99`, `session:abc123`, and inside you can throw *whatever you want*: a slip of paper, a photo, a whole folder, a different shape every time. Grabbing a box by its label is instant, even if there are a billion boxes, because you just walk to the label. That's **NoSQL key-value / document**. Flexible shape, instant fetch-by-label, but if someone asks "which boxes contain a photo taken in March?" you'd have to open *every single box* to find out, because the labels don't know what's inside.

That contrast *is* the whole chapter:

- **Filing cabinet (SQL):** pay the cost of a rigid schema up front; get unlimited ad-hoc querying forever.
- **Labeled boxes (NoSQL):** pay nothing up front for shape; get blistering fetch-by-key at any scale, but you must *know your questions in advance*, because you only get to ask the ones the labels support.

**Why this matters for a tech job specifically:** almost every junior engineer reaches for SQL by reflex, and almost every system-design interview has a moment where the *correct* answer is "I'd put this in a cache / key-value store, not the relational DB." The skill that gets you hired isn't knowing one tool, it's being the person who says, out loud, "this workload is fetch-by-key at huge scale with no ad-hoc queries, so a relational DB is the wrong tool here; let's use DynamoDB and here's why." Knowing *when NOT to use SQL* is a senior instinct you can demonstrate as a junior. That's worth a lot.

Keep the two pictures in mind as we go. Everything below is just making them precise.

## Theory

### Why NoSQL exists

Relational databases assume a *fixed schema*, *strong consistency*, and that JOINs across normalized tables are affordable. Those assumptions strain when:

- **Scale of writes/data exceeds one machine.** A single Postgres node has limits. Horizontally scaling a relational DB with cross-node JOINs and distributed transactions is genuinely hard.
- **The schema is fluid or sparse.** Product catalogs where every category has different attributes; event blobs with varying shapes.
- **Access patterns are simple and known.** "Give me this user's session by key" doesn't need a query planner, it needs a hash lookup that's fast at any scale.
- **You'd trade strict consistency for availability/latency.** A shopping cart that's occasionally a few seconds stale is fine if the site never goes down.

"NoSQL" (now read as "Not *only* SQL") is an umbrella for stores that drop one or more relational assumptions to win on a different axis, usually horizontal scalability and flexibility. The cost is almost always *you give up something*: JOINs, ad-hoc queries, transactions, or consistency. There is no free lunch; there's just choosing which lunch.

### The four families

**1. Key-value** (Redis, DynamoDB-as-KV, Memcached). The simplest model: a dictionary. `put(key, value)`, `get(key)`. Value is opaque to the DB. Blazing fast, trivially partitionable by key. Fits: caches, sessions, feature flags, leaderboards. Limit: you can only fetch by key, no querying inside the value.

**2. Document** (MongoDB, Couchbase, DynamoDB-as-doc). Values are structured documents (JSON/BSON) the DB *can* index and query inside. Flexible schema; store a whole aggregate (an order with its line items) as one document. Fits: content, catalogs, user profiles, anything that's read/written as a unit. Limit: cross-document JOINs are awkward; you model around access patterns.

**3. Column-family / wide-column** (Cassandra, HBase, Bigtable). Data is stored by column families, optimized for massive write throughput and range scans over a partition key. Sparse rows (millions of columns, most empty) are cheap. Fits: time-series, event logging, IoT, write-heavy analytics at scale. Limit: query flexibility is low; you design tables per query.

**4. Graph** (Neo4j, Amazon Neptune). First-class nodes and edges; traversals (`friends-of-friends`, shortest path) are O(degree) hops instead of recursive JOINs. Fits: social graphs, recommendations, fraud rings, knowledge graphs. Limit: not for bulk aggregation or high-write throughput workloads.

A quick decision heuristic:

| If your workload is... | Reach for |
|---|---|
| "fetch one thing by id, super fast, huge scale" | Key-value |
| "store/retrieve self-contained aggregates, flexible shape" | Document |
| "enormous write volume, time-ordered, range scans" | Wide-column |
| "relationships and traversals are the point" | Graph |
| "complex ad-hoc queries, JOINs, transactions, integrity" | **Relational** (don't abandon it!) |

A second framing worth having: each family is a different answer to "what do you give up?" Key-value gives up querying-inside-the-value. Document gives up cheap cross-document JOINs. Wide-column gives up query flexibility for write throughput. Graph gives up bulk aggregation for cheap traversal. Relational gives up effortless horizontal scale for query freedom and integrity. There's no winner, there's a fit.

### CAP theorem - stated correctly

CAP says: a **distributed** data store can guarantee at most **two** of:

- **C**onsistency, every read sees the most recent write (linearizability).
- **A**vailability, every request gets a non-error response (without guaranteeing it's the latest).
- **P**artition tolerance, the system keeps working despite the network dropping/delaying messages *between nodes*.

The crucial, often-mangled point: **in a real distributed system, network partitions WILL happen, so P is not optional.** That means the real choice, *during a partition*, is between C and A. When two nodes can't talk:

- A **CP** system refuses to answer (or blocks) on the side that can't confirm it has the latest data, it sacrifices availability to stay consistent. (e.g. a system requiring quorum; HBase.)
- An **AP** system answers from whatever node you reached, possibly returning stale data, it sacrifices consistency to stay available. (e.g. Cassandra, DynamoDB in its default mode.)

So "pick two" is really "P is mandatory; pick C or A *when partitioned*." When there's no partition, you can have both.

### PACELC - the part CAP leaves out

CAP only describes behavior *during a partition*. But systems make trade-offs even when everything's healthy. **PACELC** completes the picture:

> **If** there's a **P**artition, trade between **A** and **C**; **E**lse (normal operation), trade between **L**atency and **C**onsistency.

This matters because strong consistency in a distributed system requires coordination (waiting for replicas to agree), which costs **latency** even with no partition. DynamoDB is **PA/EL**: it favors availability under partition and low latency normally, accepting eventual consistency, though it *offers* strongly-consistent reads as an opt-in (paying more RCU and latency). A system like Spanner is **PC/EC**: consistent always, at a latency cost. PACELC is the more honest model; it's worth thinking in PACELC from here on.

Here's a small classification table worth keeping, so the labels stop feeling abstract:

| System | Under partition (P → A/C) | Normal (E → L/C) | PACELC label |
|---|---|---|---|
| DynamoDB (default reads) | Availability | Latency | **PA/EL** |
| Cassandra (tunable) | Availability | Latency | **PA/EL** |
| Google Spanner | Consistency | Consistency | **PC/EC** |
| HBase | Consistency | Consistency | **PC/EC** |
| MongoDB (default) | Consistency (primary) | Latency-ish | **PC/EL** (roughly) |
| Single-node Postgres | (no partition, one node) | Consistency | **EC** (CAP doesn't really apply) |

That last row is worth pausing on: CAP and PACELC are about *distributed* systems. A single-node Postgres isn't "CP" or "AP", it's just consistent, because there's no partition to survive. If that node dies, you have a downtime problem, not a CAP trade-off. People misapply CAP to single-node databases constantly; don't be one of them.

### Eventual vs. strong consistency

- **Strong**: after a write commits, every subsequent read (anywhere) returns that value. Simple to reason about; costs coordination/latency.
- **Eventual**: replicas converge "eventually" (usually milliseconds). A read right after a write *might* see the old value. You must design the UX to tolerate it (e.g. read-your-own-writes by reading the leader, or showing optimistic local state).

Neither is "better", they're points on the PACELC trade. For a "like count" eventual is fine; for an account balance, you want strong (or a transaction).

A consistency vocabulary worth having, because interviewers use these words:

- **Read-your-writes:** *you* always see *your own* recent writes, even if others might briefly not. Often implemented by pinning your session to the leader/primary, or to a particular replica. This is the one users notice the most, nothing feels more broken than posting a comment and not seeing it.
- **Monotonic reads:** once you've seen a value, you never see an *older* value on a later read. Without this, refreshing a page can make data appear to go backwards in time.
- **Causal consistency:** if write B depends on write A (you replied to a comment), everyone who sees B also sees A. Stronger than eventual, weaker (and cheaper) than full linearizability.

For Anneava, where the data is HIPAA-aligned health records inside Postgres with row-level security, you want **strong** consistency, a clinician must never see a stale medication list. For a "trending posts" widget in some future NYX marketing page, eventual is completely fine and far cheaper. The store you pick should match the consistency the *workload* actually needs, not the strongest one available.

## Build it

### DynamoDB in depth

DynamoDB is AWS's managed key-value/document store. It gives single-digit-millisecond latency at effectively unlimited scale, *if* you model around its constraints. Those constraints are the whole skill.

**Primary key = partition key (+ optional sort key).**
- **Partition key (PK / hash key):** DynamoDB hashes it to choose a physical partition. Determines *distribution*. Items with the same PK live together.
- **Sort key (SK / range key):** orders items *within* a partition. Enables range queries (`begins_with`, `between`, `>`) and storing many related items under one PK.

The pair `(PK, SK)` must be unique. A table with only a PK is pure key-value; PK+SK is a wide-column/document hybrid.

**Capacity, RCU/WCU.**
- **RCU** (Read Capacity Unit): 1 strongly-consistent read of up to 4KB/sec (or 2 eventually-consistent reads).
- **WCU** (Write Capacity Unit): 1 write of up to 1KB/sec.
Provisioned mode = you set RCU/WCU; on-demand = pay per request, auto-scales. Exceeding capacity → throttling. This pricing model *forces* you to think about access patterns up front.

**Hot partitions:** if your PK concentrates traffic (e.g. PK = today's date, so all writes hit one partition), you saturate that partition's capacity while others idle. Choose high-cardinality, evenly-distributed partition keys. This is the #1 DynamoDB footgun.

**GSIs and LSIs:**
- **LSI (Local Secondary Index):** same PK, *different* SK. Lets you query the same partition sorted differently. Must be created at table creation; shares the partition's capacity.
- **GSI (Global Secondary Index):** *different* PK and SK entirely, a whole alternate access pattern. Eventually consistent, own capacity, can be added anytime. GSIs are how you support "query by a non-key attribute."

**Single-table design.** The relational instinct is one table per entity. DynamoDB's philosophy is the opposite: **put multiple entity types in ONE table**, using a generic `PK`/`SK` and overloading them, so that a single `Query` returns a whole related object graph in one round trip (no JOINs, DynamoDB has none). You pre-join at write time by co-locating related items under the same partition key.

Example: model users and their orders in one table.

```
PK              SK                  attributes
--------------  ------------------  -------------------------------
USER#42         PROFILE             name=Ana, email=ana@acme.io
USER#42         ORDER#2026-01-01    amount=49.00, status=paid
USER#42         ORDER#2026-02-01    amount=49.00, status=paid
USER#99         PROFILE             name=Ben, ...
```

One `Query(PK = "USER#42")` returns Ana's profile *and* all her orders in a single call. `Query(PK="USER#42", SK begins_with "ORDER#")` returns just orders. That co-location is the single-table trick.

**boto3 code:**

```python
import boto3
from boto3.dynamodb.conditions import Key

ddb = boto3.resource("dynamodb")

# Create a single-table design
ddb.create_table(
    TableName="AppData",
    KeySchema=[
        {"AttributeName": "PK", "KeyType": "HASH"},   # partition key
        {"AttributeName": "SK", "KeyType": "RANGE"},   # sort key
    ],
    AttributeDefinitions=[
        {"AttributeName": "PK", "AttributeType": "S"},
        {"AttributeName": "SK", "AttributeType": "S"},
    ],
    BillingMode="PAY_PER_REQUEST",   # on-demand, no RCU/WCU to guess
)

table = ddb.Table("AppData")

# Write a profile and orders for user 42 (pre-joined by shared PK)
table.put_item(Item={"PK": "USER#42", "SK": "PROFILE",
                     "name": "Ana", "email": "ana@acme.io"})
table.put_item(Item={"PK": "USER#42", "SK": "ORDER#2026-01-01",
                     "amount": 49, "status": "paid"})

# Fetch the user's entire item collection in ONE query
resp = table.query(KeyConditionExpression=Key("PK").eq("USER#42"))
for item in resp["Items"]:
    print(item["SK"], item)

# Just the orders, via sort-key prefix
orders = table.query(
    KeyConditionExpression=Key("PK").eq("USER#42") & Key("SK").begins_with("ORDER#")
)
```

**When DynamoDB shines:** known access patterns, key-based lookups, massive scale, predictable latency, serverless. **When it hurts:** ad-hoc analytics, queries you didn't design for ("count orders over $40 across all users" requires a scan or a GSI you planned ahead), complex transactions, or when your access patterns keep changing. For NYX's exploratory analytics, DynamoDB would be the *wrong* tool, Postgres wins. For a session store or a high-throughput write log, it'd shine.

### DynamoDB GSIs - querying by a non-key attribute

The single-table example answers "give me this user's stuff." But what about "give me all orders with status = `pending`, newest first", a query on an attribute that *isn't* the partition key? In a relational DB you'd just add an index and write `WHERE status = 'pending'`. In DynamoDB, the equivalent is a **Global Secondary Index (GSI)**: you nominate a different attribute (or a synthetic one) as the GSI's partition key, and DynamoDB maintains a second, automatically-updated copy of the data keyed that way.

Let's extend `AppData` with a GSI so you can query orders by status. The trick is to add two extra attributes to order items, `GSI1PK` and `GSI1SK`, that you control. (Naming GSI keys generically like `GSI1PK`/`GSI1SK` instead of `status` is a single-table convention: it keeps the index reusable for *multiple* access patterns later.)

```python
import boto3
from boto3.dynamodb.conditions import Key

ddb = boto3.resource("dynamodb")

# Add a GSI named "GSI1" keyed by GSI1PK (hash) and GSI1SK (range).
ddb.meta.client.update_table(
    TableName="AppData",
    AttributeDefinitions=[
        {"AttributeName": "GSI1PK", "AttributeType": "S"},
        {"AttributeName": "GSI1SK", "AttributeType": "S"},
    ],
    GlobalSecondaryIndexUpdates=[{
        "Create": {
            "IndexName": "GSI1",
            "KeySchema": [
                {"AttributeName": "GSI1PK", "KeyType": "HASH"},
                {"AttributeName": "GSI1SK", "KeyType": "RANGE"},
            ],
            # ALL = copy every attribute into the index (simplest, costs storage)
            "Projection": {"ProjectionType": "ALL"},
        }
    }],
)

table = ddb.Table("AppData")

# When writing an order, ALSO set the GSI keys so it appears in the index.
# GSI1PK groups by status; GSI1SK sorts by created date.
table.put_item(Item={
    "PK": "USER#42", "SK": "ORDER#1001",
    "status": "pending", "total": 149, "created": "2026-06-01",
    "GSI1PK": "STATUS#pending",          # <-- the GSI partition key
    "GSI1SK": "2026-06-01#ORDER#1001",   # <-- the GSI sort key (date-prefixed)
})

# Now query the GSI: "all pending orders, newest first"
resp = table.query(
    IndexName="GSI1",
    KeyConditionExpression=Key("GSI1PK").eq("STATUS#pending"),
    ScanIndexForward=False,   # descending => newest first
)
for item in resp["Items"]:
    print(item["SK"], item["created"], item["total"])
```

Stepping through what just happened:

1. You declared a second key space (`GSI1PK`, `GSI1SK`) that lives alongside the table's real key. DynamoDB now maintains a *second physical structure* sorted by those keys.
2. On every write of an order, you populate the GSI keys. Items that don't set `GSI1PK` simply don't appear in the index (a "sparse index", useful: only orders get indexed, not profiles).
3. The `query(IndexName="GSI1", ...)` is now a normal partition-key query *against the index*, so it's fast and cheap, no scan. `ScanIndexForward=False` reverses the sort-key order to get newest-first.

Two things to remember, because they bite people: **GSIs are eventually consistent**, you cannot request a strongly-consistent read on a GSI, so an order you just wrote may take a beat to show up in a GSI query. And the **GSI partition key can go hot** exactly like the table's can: `STATUS#pending` is a single partition; if 99% of orders are pending, that GSI partition is a bottleneck. For high-cardinality status fanout you'd shard it (`STATUS#pending#7` where 7 = `order_id % 10`) and query all shards.

### DynamoDB access-pattern table

Here's the discipline that separates working DynamoDB designs from broken ones: **write down every access pattern first, then design keys to serve them.** You do not start from entities; you start from queries. Here's how the `AppData` model (extended with the GSI above) maps every pattern to a concrete key/index. This is the artifact you'd bring to a design review.

| # | Access pattern | Key / index used | Query expression |
|---|---|---|---|
| 1 | Get a user's profile | Table, PK + SK | `PK = USER#42, SK = PROFILE` |
| 2 | Get a user + all their orders | Table, PK | `PK = USER#42` (whole item collection) |
| 3 | Get just a user's orders | Table, PK + SK prefix | `PK = USER#42, SK begins_with ORDER#` |
| 4 | Get one order's line items | Table, PK + SK prefix | `PK = ORDER#1001, SK begins_with ITEM#` |
| 5 | List all `pending` orders, newest first | **GSI1**, GSI1PK | `GSI1PK = STATUS#pending` (desc) |
| 6 | List `paid` orders in a date range | **GSI1**, GSI1PK + GSI1SK between | `GSI1PK = STATUS#paid, GSI1SK between dates` |
| 7 | Get a single order by id | Table, PK | `PK = ORDER#1001` |

Notice every row resolves to a `Query` (or `GetItem`) on a partition key, *never* a `Scan`. If an access pattern can only be served by a `Scan`, that's a design smell: either it's a genuinely rare admin/analytics query (acceptable, run it off-hours or export to Athena/S3), or you're missing an index. The table above is what "modeling around access patterns" actually produces.

### Redis sorted-set leaderboard

Key-value stores are more than `get`/`set`. Redis ships rich value types, and the **sorted set** (ZSET) is the perfect example of "the right data structure beats a clever query." A sorted set keeps members ordered by a numeric **score**, and every score-based operation is O(log N). That makes it the canonical leaderboard.

Real Redis commands first (this is `redis-cli` syntax), then the Python:

```
# Add/update players with scores (ZADD is idempotent per member)
ZADD game:leaderboard 1500 "ana"
ZADD game:leaderboard 2200 "ben"
ZADD game:leaderboard  900 "cy"
ZADD game:leaderboard 2200 "dee"

# Top 3, highest first, WITH scores
ZREVRANGE game:leaderboard 0 2 WITHSCORES
# => 1) "ben"  2) "2200"  3) "dee"  4) "2200"  5) "ana"  6) "1500"

# Where does "ana" rank? (0-based, highest = rank 0)
ZREVRANK game:leaderboard "ana"      # => 2

# Bump ana's score by 400 atomically (race-free)
ZINCRBY game:leaderboard 400 "ana"   # => 1900

# How many players scored between 1000 and 2000 inclusive?
ZCOUNT game:leaderboard 1000 2000    # => 1  (just ana at 1900)
```

```python
import redis
r = redis.Redis(decode_responses=True)

KEY = "game:leaderboard"

def record_score(player: str, points: int) -> None:
    # ZINCRBY adds to the existing score atomically - no read-modify-write race.
    r.zincrby(KEY, points, player)

def top_players(n: int = 10):
    # withscores=True returns [(member, score), ...], highest first.
    return r.zrevrange(KEY, 0, n - 1, withscores=True)

def player_rank(player: str):
    rank = r.zrevrank(KEY, player)        # None if not present
    score = r.zscore(KEY, player)
    return None if rank is None else (rank + 1, score)   # 1-based for humans

record_score("ana", 1500)
record_score("ben", 2200)
record_score("ana", 400)                 # ana now 1900
print(top_players(3))                     # [('ben', 2200.0), ('ana', 1900.0)]
print(player_rank("ana"))                 # (2, 1900.0)
```

Stepping through why this is the right tool: maintaining a live "top N by score" in a relational table means an `ORDER BY score DESC LIMIT N` that either scans or relies on an index that gets churned on every score update, and computing a single player's *rank* means counting how many rows outrank them (expensive). Redis keeps the set permanently ordered, so `ZREVRANGE` is a slice off the front and `ZREVRANK` is a tree position lookup, both fast regardless of how many millions of players exist. And `ZINCRBY` is atomic, so two simultaneous score updates can't clobber each other. The data structure *is* the feature.

### SQLite proves it's real SQL - JOINs and window functions

A common misconception is that SQLite is a "toy" or "just key-value with SQL syntax sprinkled on." It is a full relational engine. To prove it, here's a JOIN *and* a window function, the kind of analytical query you'd expect only from a "real" database, running entirely inside a single local file.

```python
import sqlite3

con = sqlite3.connect(":memory:")     # ephemeral DB, lives in RAM
con.execute("CREATE TABLE customers (id INTEGER PRIMARY KEY, name TEXT, region TEXT)")
con.execute("""CREATE TABLE orders (
    id INTEGER PRIMARY KEY, customer_id INTEGER, amount REAL, created TEXT
)""")

con.executemany("INSERT INTO customers VALUES (?,?,?)", [
    (1, "Ana", "West"), (2, "Ben", "West"), (3, "Cy", "East"),
])
con.executemany("INSERT INTO orders VALUES (?,?,?,?)", [
    (101, 1, 120.0, "2026-01"), (102, 1,  80.0, "2026-02"),
    (103, 2, 200.0, "2026-01"), (104, 3,  50.0, "2026-01"),
    (105, 3, 300.0, "2026-02"),
])

# A JOIN + a window function: each customer's total, AND their rank
# within their region by total spend. This is genuinely analytical SQL.
rows = con.execute("""
    WITH totals AS (
        SELECT c.name, c.region, SUM(o.amount) AS spent
        FROM customers c
        JOIN orders o ON o.customer_id = c.id      -- a real JOIN
        GROUP BY c.id
    )
    SELECT
        name, region, spent,
        RANK() OVER (PARTITION BY region ORDER BY spent DESC) AS rank_in_region
    FROM totals
    ORDER BY region, rank_in_region
""").fetchall()

for name, region, spent, rank in rows:
    print(f"{region:5} #{rank}  {name:4} ${spent:.0f}")
# West  #1  Ana  $200
# West  #2  Ben  $200   <- RANK ties both at 1 if equal; here Ana=200, Ben=200 -> both #1
# East  #1  Cy   $350
```

Stepping through it: the CTE (`WITH totals AS ...`) does a `JOIN` between `customers` and `orders` and aggregates each customer's spend, exactly the multi-table logic people assume SQLite can't do. Then `RANK() OVER (PARTITION BY region ORDER BY spent DESC)` is a **window function**: it ranks each customer *within their region* without collapsing the rows, the same construct you'd use in Postgres for NYX analytics. Everything from Chapters 7.1 and 7.2, JOINs, GROUP BY, CTEs, window functions, indexes, transactions, works here, in a file, with zero server. SQLite isn't SQL-lite; it's SQL that fits in your pocket.

### MongoDB aggregation pipeline

Document DBs aren't only `find()` by key. MongoDB's **aggregation pipeline** is a sequence of stages, each takes the output of the previous one, that does grouping, joining, reshaping, and computing. It's the document-world answer to "I need a GROUP BY with some JOINs." Here's "revenue per author for paid orders, top authors first," over an `orders` collection.

```javascript
// Sample documents in the "orders" collection:
// { _id: 1, author: "ana", status: "paid", total: 149, items: 3 }
// { _id: 2, author: "ben", status: "paid", total:  50, items: 1 }
// { _id: 3, author: "ana", status: "paid", total: 200, items: 2 }
// { _id: 4, author: "ana", status: "cart", total:  90, items: 1 }  // not paid

db.orders.aggregate([
  // 1. $match - filter first (cheapest stage; lets indexes help)
  { $match: { status: "paid" } },

  // 2. $group - one output doc per author, with computed fields
  { $group: {
      _id: "$author",
      revenue:    { $sum: "$total" },
      orderCount: { $sum: 1 },
      avgItems:   { $avg: "$items" }
  }},

  // 3. $lookup - the document-DB "JOIN": pull author profile from users
  { $lookup: {
      from: "users", localField: "_id",
      foreignField: "_id", as: "profile"
  }},

  // 4. $sort - highest revenue first
  { $sort: { revenue: -1 } },

  // 5. $project - shape the final output
  { $project: { _id: 0, author: "$_id", revenue: 1, orderCount: 1, avgItems: 1 } }
]);

// Result:
// { author: "ana", revenue: 349, orderCount: 2, avgItems: 2.5 }
// { author: "ben", revenue:  50, orderCount: 1, avgItems: 1   }
```

Stepping through the pipeline: `$match` runs first on purpose, filtering early shrinks everything downstream and can use an index, exactly like putting the selective `WHERE` clause first. `$group` is the GROUP BY: `_id` is the grouping key and the other fields are aggregations (`$sum`, `$avg`). `$lookup` is MongoDB's JOIN, yes, it exists, but it's heavier than a relational JOIN and a sign you might have over-normalized (often you'd *embed* the author snapshot instead). `$sort` and `$project` reshape the result. The pipeline metaphor, data flowing stage to stage, is the mental model; once it clicks, complex Mongo reports stop being scary.

### Document DBs - MongoDB modeling

MongoDB stores BSON documents in collections. The modeling decision is **embed vs. reference**:

- **Embed** when the child is owned by and read with the parent, and bounded in size: put `comments` inside a `post` document. One read gets everything.
- **Reference** when the child is large, unbounded, or shared: store `author_id` and look up the author separately, like a foreign key.

```javascript
// Embedded: one read returns the post and its comments
db.posts.insertOne({
  _id: "p1",
  title: "Indexing in Postgres",
  author: { id: "u42", name: "Ana" },     // denormalized snapshot
  tags: ["db", "perf"],
  comments: [
    { user: "Ben", text: "great post", at: ISODate("2026-01-02") }
  ]
});

// Query: documents are queryable inside
db.posts.find({ tags: "db", "author.id": "u42" });
db.posts.createIndex({ "author.id": 1, "tags": 1 });   // composite index
```

The same rule as DynamoDB applies: **model around your reads.** Document DBs reward storing what you read together, together.

A practical heuristic for embed-vs-reference:
- **Read together + bounded + owned → embed.** (Comments on a post, line items on an order, a user's address.)
- **Unbounded growth → reference** (or embed a *recent slice* and reference the rest). An array that grows without limit eventually blows the 16MB document size cap and makes every read of the parent fat. A post with 2 million comments must reference.
- **Shared/independently-updated → reference.** If many documents point at the same entity and it changes (a product's price referenced by thousands of orders), referencing avoids updating thousands of embedded copies. But note: orders often *want* the price frozen at purchase time, in which case embedding the snapshot is correct *because* it shouldn't update. The question "should this change when the source changes?" decides it.

### SQLite - the right call for embedded

SQLite is a full relational SQL engine that lives as a *library inside your process* and stores the whole database in a **single file**. No server, no network, no daemon. It's the most deployed database on earth (every phone, browser, and app uses it).

**When an embedded DB is right:** local app storage, mobile, desktop apps, CLI tools, test fixtures, edge/IoT, single-writer workloads, or anything where running a server is overkill. **When it's wrong:** high write concurrency from many processes (SQLite uses file-level write locking, one writer at a time), or client-server access over a network.

**File-format intuition:** the file is a sequence of fixed-size **pages** (default 4KB). Page 1 holds the header and the schema (stored as rows in `sqlite_master`). Tables and indexes are stored as B-trees laid out across pages, *the same B-tree idea from Chapter 7.2*, just in one file instead of a server's storage. Reading a row = seeking to the right page(s). A write-ahead log (`-wal`) file gives durability and lets reads proceed during a write.

```python
import sqlite3

con = sqlite3.connect("app.db")            # creates the file if missing
con.execute("PRAGMA journal_mode=WAL;")    # better read/write concurrency
con.execute("""
    CREATE TABLE IF NOT EXISTS notes (
        id INTEGER PRIMARY KEY,            -- rowid alias, auto-increment
        body TEXT NOT NULL,
        created_at TEXT NOT NULL DEFAULT (datetime('now'))
    )""")

with con:                                   # transaction; commits or rolls back
    con.execute("INSERT INTO notes (body) VALUES (?)", ("first note",))

for row in con.execute("SELECT id, body FROM notes ORDER BY id"):
    print(row)
con.close()
```

Note it's *real* SQL, `CREATE`, `INSERT`, `SELECT`, indexes, transactions, even window functions all work. Everything from 7.1 and 7.2 transfers. SQLite is a great go-to for prototypes and tests: you can build a NYX feature against an in-memory SQLite (`sqlite3.connect(":memory:")`) in a unit test, then run it against Postgres in prod.

### Redis - key-value cache preview

Redis is an in-memory key-value store (optionally persisted). Because data lives in RAM, it's *microsecond* fast, used as a cache, session store, rate limiter, queue, or pub/sub. It has rich value types beyond strings: lists, sets, sorted sets (leaderboards!), hashes.

```python
import redis
r = redis.Redis()

# Cache-aside pattern: check cache, fall back to DB, populate cache
def get_user(uid):
    cached = r.get(f"user:{uid}")
    if cached:
        return cached                      # fast path, RAM hit
    user = fetch_from_postgres(uid)        # slow path
    r.setex(f"user:{uid}", 300, user)      # cache for 300s with TTL
    return user
```

The `setex` TTL is key: caches must expire or they serve stale data forever. Redis is a *preview* here, it's the natural companion to a relational primary store: Postgres for truth, Redis for speed.

## Common mistakes

These are the ones you'll see (or make) for real. Each is **wrong → right**.

**1. A low-cardinality / time-based partition key (hot partition).**
- ❌ `PK = "2026-06-26"` so every write today lands on one physical partition while the rest idle → throttling under load.
- ✅ Use a high-cardinality key (`PK = USER#<id>` or `PK = ORDER#<id>`), or if you must group by day, *shard* it: `PK = "2026-06-26#" + (hash(id) % 10)` and read all 10 shards. Distribution is the whole game.

**2. Using `Scan` where you should `Query`.**
- ❌ `table.scan(FilterExpression=Attr("status").eq("pending"))`, reads (and bills for) the *entire table*, then filters in memory. Fine on 100 rows, ruinous on 100 million.
- ✅ Design a key or GSI so the lookup is a `Query` on a partition key. `Scan` is for one-off admin/migration jobs, never for an app hot path.

**3. Treating DynamoDB like relational and trying to JOIN.**
- ❌ Querying users, then looping to query each user's orders one-by-one ("N+1"), or expecting a server-side JOIN. DynamoDB has no JOIN.
- ✅ Pre-join at write time via single-table design: co-locate the user and their orders under one PK so one `Query` returns the whole graph.

**4. Cache entries with no TTL (stale-forever).**
- ❌ `r.set(f"user:{uid}", data)`, no expiry. The user updates their email; the cache serves the old one indefinitely.
- ✅ `r.setex(f"user:{uid}", 300, data)`, always set a TTL, *and* invalidate on write (`r.delete(f"user:{uid}")` inside the update path). Belt and suspenders.

**5. Unbounded item collections / documents.**
- ❌ Every event for a tenant under `PK = TENANT#1` forever, the partition grows without limit and one tenant's collection dominates. Same in Mongo: a `post.comments` array that grows to millions blows the 16MB doc cap.
- ✅ Bound it. Add time to the key (`PK = TENANT#1#2026-06`) so collections roll over, or reference overflow into separate items/documents.

**6. Modeling before knowing access patterns.**
- ❌ Designing DynamoDB tables from an ER diagram ("one table per entity") because that's the SQL habit. You end up unable to answer queries cheaply.
- ✅ List every access pattern *first* (like the access-pattern table above), then design keys/GSIs to serve them. In DynamoDB, queries come before schema.

**7. Expecting strong consistency by default on a GSI.**
- ❌ Writing an order then immediately querying a GSI and asserting it's there. GSIs are *eventually* consistent, you cannot request a strong read on them.
- ✅ Read the base table (which *can* be strongly consistent) for read-your-writes; treat GSI results as possibly-slightly-stale, or re-check after a beat.

**8. SQLite for multi-writer concurrency.**
- ❌ Pointing a fleet of web workers at one `app.db` over a network share and expecting concurrent writes. SQLite is single-writer (file lock); writers serialize and a network filesystem corrupts locks.
- ✅ Use SQLite for single-writer/embedded/local/test workloads. The moment you need many concurrent writers over a network, that's Postgres.

**9. Putting secrets in a document/item.**
- ❌ Storing a plaintext API key, password, or PHI in a Mongo doc or DynamoDB item "because it's convenient." For Anneava that's a HIPAA violation waiting to happen.
- ✅ Secrets go in a secrets manager (AWS Secrets Manager / Vault); store only a reference. Hash passwords (bcrypt/argon2). Encrypt sensitive fields; rely on at-rest encryption *plus* field-level controls.

**10. Ignoring read-your-writes under eventual consistency.**
- ❌ User posts a comment, you read from an eventually-consistent replica, the comment isn't there yet, UI looks broken.
- ✅ For the writer's own immediate reads, hit the leader/primary (DynamoDB strong read on the base table, Mongo `readConcern`/primary, or optimistic UI showing the local write). Match consistency to UX expectations.

## On the job / interview angle

System-design and DB rounds love this material because it reveals whether you choose tools on purpose. Here are answers you could give, tightened to interview length.

**Q: Explain CAP.**
"In a distributed store, when the network partitions, and it will, you can't have both consistency and availability for the affected data. A CP system refuses or blocks reads it can't confirm are current (stays consistent, drops availability); an AP system answers from whatever node you reached (stays available, may be stale). P isn't optional in the real world, so CAP is really 'during a partition, pick C or A.' When there's no partition you can have both, which is why I prefer PACELC, which also covers the latency-vs-consistency trade during *normal* operation."

**Q: When would you pick NoSQL over SQL?**
"When the access patterns are simple, known, and stable, and the dominant requirement is huge scale or predictable low latency, sessions, carts, feature flags, high-volume event logs, leaderboards. NoSQL trades ad-hoc query flexibility for scale and flexibility-of-shape. I keep relational as the default for anything with rich relationships, transactions, integrity, or queries I haven't thought of yet, analytics especially. For NYX's analytics it's Postgres; for a global session store I'd reach for DynamoDB or Redis."

**Q: What's a partition key, and what's a hot partition?**
"The partition key is the attribute DynamoDB hashes to decide which physical partition an item lives on, it controls data *distribution* and throughput. A hot partition happens when one key value gets a disproportionate share of traffic (e.g. keying by today's date), so that one partition throttles while others sit idle. You fix it by choosing a high-cardinality, evenly-distributed key, or by sharding a naturally-skewed key across N suffixes."

**Q: Eventual vs strong consistency?**
"Strong means every read after a committed write sees that write, everywhere, simple to reason about, but it costs coordination and therefore latency. Eventual means replicas converge after a short delay, so a read right after a write might be stale, cheaper and more available. I pick per workload: a like-count can be eventual; an account balance or a medication list (Anneava) needs strong or a transaction. The subtle one users notice is read-your-writes, which I'd guarantee even on an eventually-consistent store by routing the writer's own reads to the primary."

**Q: What is a document database?**
"A store whose values are structured documents, JSON/BSON, that the database can index and query *inside*, unlike an opaque key-value blob. MongoDB is the canonical example. The big modeling decision is embed vs reference: embed bounded, owned, read-together data (an order's line items) so one read gets the whole aggregate; reference unbounded or shared data. You model around how you read, not around normal forms."

**Q: How does single-table design avoid joins?**
"DynamoDB has no JOINs, so you pre-join at *write* time: you put multiple entity types in one table with generic PK/SK and co-locate related items under the same partition key. A user and all their orders share `PK = USER#42`, so one `Query` returns the whole object graph in a single round trip. You overload the keys and use GSIs for alternate access patterns. The cost is you must know your access patterns up front."

**Q: What is a cache, and what's the cache-aside pattern?**
"A cache is a fast, usually in-memory store (Redis, Memcached) holding a copy of hot data so you don't hit the slow source of truth every time. Cache-aside (lazy loading) is: on read, check the cache; on a miss, read the database, populate the cache with a TTL, and return. The app owns the caching logic, the cache only holds what's actually been requested, and the TTL bounds staleness. Postgres stays the source of truth; Redis just makes the hot path fast."

**Q: How do you handle cache invalidation?**
"Three levers, usually combined. **TTL**, every entry expires, bounding worst-case staleness even if you forget everything else. **Write-through / explicit invalidation**, on a write, update or delete the cache key in the same path so the next read repopulates fresh. **Event-driven**, emit a change event that busts the relevant keys. The classic trap is no TTL plus forgetting to invalidate, which serves stale data forever; I default to a TTL *and* delete-on-write. And I watch for the thundering-herd problem, when a hot key expires and a thousand requests stampede the DB at once, which you soften with a short lock or 'stale-while-revalidate.'"

## Mini-project: same app, relational vs. DynamoDB single-table

Model a simple e-commerce app, **users, orders, order line items**, two ways, then compare access patterns.

**Relational (Postgres):**

```sql
CREATE TABLE users  (id BIGINT PRIMARY KEY, name TEXT, email TEXT UNIQUE);
CREATE TABLE orders (id BIGINT PRIMARY KEY, user_id BIGINT REFERENCES users(id),
                     status TEXT, created_at TIMESTAMPTZ);
CREATE TABLE items  (order_id BIGINT REFERENCES orders(id), sku TEXT,
                     qty INT, price NUMERIC, PRIMARY KEY(order_id, sku));
```

Access patterns:
- *Get a user with all orders + items:* JOIN across 3 tables, easy, one query, the planner optimizes it.
- *All orders over $100 last month:* trivial, `WHERE` + index, ad-hoc and flexible.
- *Add a brand-new query later:* just write SQL. No migration of structure.

**DynamoDB (single table `Shop`):**

```
PK            SK                    attributes
------------  --------------------  ----------------------------
USER#42       PROFILE               name, email
USER#42       ORDER#1001            status=paid, total=149, created=...
ORDER#1001    ITEM#sku-A            qty=2, price=49
ORDER#1001    ITEM#sku-B            qty=1, price=51
```

```python
from boto3.dynamodb.conditions import Key
# Get user profile + their orders: ONE query on PK=USER#42
table.query(KeyConditionExpression=Key("PK").eq("USER#42"))
# Get an order's line items: ONE query on PK=ORDER#1001 with SK prefix ITEM#
table.query(KeyConditionExpression=Key("PK").eq("ORDER#1001")
            & Key("SK").begins_with("ITEM#"))
```

Access patterns:
- *Get a user with orders:* one query, single-digit ms, scales infinitely. **Faster than the JOIN at scale.**
- *Orders over $100 last month across ALL users:* **painful**, no global query by amount/date unless you pre-built a GSI (e.g. `GSI: PK=MONTH#2026-01, SK=total`). Otherwise it's a full table `Scan`. You must *know this query in advance.*
- *Add a brand-new query later:* may require a new GSI and backfilling all items, a real migration.

**The comparison to write up:**

| Dimension | Relational | DynamoDB single-table |
|---|---|---|
| Known key-based reads | Fast | Fastest, scales flat |
| Ad-hoc / unforeseen queries | Trivial | Hard (scan or new GSI) |
| JOINs / aggregations | Native | Must pre-join at write time |
| Scale ceiling | Single-node-ish (until sharding) | Effectively unlimited |
| Schema evolution | `ALTER TABLE` | Re-model + backfill |
| Transactions | First-class | Limited |

**The lesson:** DynamoDB trades *query flexibility* for *predictable scale*. Choose it when access patterns are known and stable and scale is the dominant concern; choose relational when you'll ask questions you haven't thought of yet, which, for analytics, is always. For NYX you'd keep Postgres; for a global session/cart store you'd reach for DynamoDB.

## Mini-project 2: session store + rate limiter + leaderboard in Redis

This one is fully runnable against a local Redis (`docker run -p 6379:6379 redis`). It builds the three things almost every web backend needs from a fast key-value store: **sessions**, **rate limiting**, and a **leaderboard**, the kind of thing you'd bolt onto a NYX or Anneava API gateway. Each uses a different Redis primitive on purpose.

```python
import json, secrets, time
import redis

r = redis.Redis(decode_responses=True)

# ---------------------------------------------------------------------------
# 1) SESSION STORE  - strings with SETEX (auto-expiring sessions)
# ---------------------------------------------------------------------------
SESSION_TTL = 60 * 30   # 30 minutes

def create_session(user_id: str) -> str:
    token = secrets.token_urlsafe(24)            # opaque, unguessable
    payload = json.dumps({"user_id": user_id, "created": time.time()})
    # SETEX = set value WITH an expiry in one atomic op. The session
    # simply vanishes after 30 min of inactivity - no cron cleanup needed.
    r.setex(f"session:{token}", SESSION_TTL, payload)
    return token

def get_session(token: str):
    raw = r.get(f"session:{token}")
    if raw is None:
        return None                              # expired or never existed
    # "Sliding window" - touch it to extend the TTL on each use.
    r.expire(f"session:{token}", SESSION_TTL)
    return json.loads(raw)

def destroy_session(token: str) -> None:
    r.delete(f"session:{token}")                 # logout

# ---------------------------------------------------------------------------
# 2) RATE LIMITER  - INCR + EXPIRE (fixed-window counter)
# ---------------------------------------------------------------------------
def allow_request(user_id: str, limit: int = 100, window: int = 60) -> bool:
    """Allow up to `limit` requests per `window` seconds per user."""
    key = f"rate:{user_id}:{int(time.time()) // window}"  # window-bucketed key
    pipe = r.pipeline()
    pipe.incr(key)            # atomically bump the counter (creates at 1)
    pipe.expire(key, window)  # ensure the bucket self-destructs
    count, _ = pipe.execute()
    return count <= limit     # over the limit? reject (HTTP 429)

# ---------------------------------------------------------------------------
# 3) LEADERBOARD  - sorted set (ZSET), reused from the Build-it section
# ---------------------------------------------------------------------------
def add_points(player: str, pts: int) -> None:
    r.zincrby("leaderboard", pts, player)        # atomic increment

def top(n: int = 5):
    return r.zrevrange("leaderboard", 0, n - 1, withscores=True)

# ---------------------------------------------------------------------------
# Demo
# ---------------------------------------------------------------------------
if __name__ == "__main__":
    tok = create_session("user-42")
    print("session:", get_session(tok))          # {'user_id': 'user-42', ...}

    allowed = sum(allow_request("user-42", limit=5, window=60) for _ in range(8))
    print("allowed of 8:", allowed)               # 5  (3 rejected, over limit)

    for p, s in [("ana", 1500), ("ben", 2200), ("ana", 400)]:
        add_points(p, s)
    print("top:", top())                          # [('ben', 2200.0), ('ana', 1900.0)]

    destroy_session(tok)
    print("after logout:", get_session(tok))      # None
```

Why each primitive fits, stepped through:

- **Sessions → `SETEX` string.** A session is fetch-by-token (the token *is* the key) and should die on its own. `SETEX` bakes in the TTL so there's no cleanup job, and `EXPIRE`-on-read gives a sliding window, active users stay logged in, idle ones time out. This is textbook key-value: opaque value, fetch by key, auto-expire.
- **Rate limiting → `INCR` + `EXPIRE`.** You bucket the key by time window (`now // 60`), so each minute gets a fresh counter that auto-expires. `INCR` is atomic, so concurrent requests can't undercount, critical, because the whole point is correctness under concurrency. Wrapping both commands in a `pipeline` sends them in one round trip. (A fixed window has an edge-burst flaw at boundaries; a sliding-log or token-bucket variant fixes it, but fixed-window is the right *first* answer in an interview.)
- **Leaderboard → ZSET.** Covered above, ordered-by-score is a *data structure*, not a query, so ranks and top-N stay O(log N) at any size.

The takeaway: Redis isn't "a cache", it's a toolbox of in-memory data structures, and picking the right structure (string vs counter vs sorted set) is what makes each feature trivial and fast. The source of truth stays in Postgres; Redis handles the hot, ephemeral, latency-sensitive paths.

### Solutions

**1.**
   (a) **Key-value** (e.g. DynamoDB), fetch-by-key, needs to survive node loss → a replicated KV store; AP availability is fine for a cart.
   (b) **Wide-column** (Cassandra/Bigtable), built for massive write throughput and time-range scans over a partition key.
   (c) **Graph** (Neo4j/Neptune), friends-of-friends is a traversal, cheap as hops, painful as recursive JOINs.
   (d) **Relational** (Postgres), ad-hoc, JOIN-heavy, integrity-critical; exactly NYX's case. Don't NoSQL this.
   (e) **Embedded** (SQLite), single user, local, no server needed.

**2.**
```python
import json, redis
r = redis.Redis(decode_responses=True)
TTL = 600  # 10 minutes

def get_product(pid):
    key = f"product:{pid}"
    cached = r.get(key)
    if cached is not None:
        return json.loads(cached)             # cache hit
    data = db_fetch_product(pid)              # miss → source of truth
    r.setex(key, TTL, json.dumps(data))       # populate with TTL
    return data

def update_product(pid, data):
    db_update_product(pid, data)              # write truth FIRST
    r.delete(f"product:{pid}")                # invalidate; next read repopulates
    # (Alternatively r.setex(...) to write-through, but delete-on-write is safest.)
```
Key points: TTL bounds staleness even if invalidation is ever missed; writing the DB *before* touching the cache avoids caching a value that didn't persist.

**3.** `PK = current_date` means *every* write all day hashes to the *same* partition → that one partition's WCU saturates and throttles while all other partitions idle. Fix: make the PK high-cardinality, e.g. `PK = request_id` (or `PK = "DAY#2026-06-26#" + hash(request_id) % 10` to shard the day across 10 partitions). To still query "all calls on a day," add a **GSI** with `GSI1PK = "DAY#2026-06-26"` (or query the 10 shard keys and merge). The partition key must spread writes; a per-day grouping belongs on an index/sort key, not the base PK.

**4.**
   (a) **Embed**, tags are small, bounded, read with the post.
   (b) **Reference**, comments are unbounded and would blow the 16MB document limit; store them as their own collection keyed by `post_id`.
   (c) **Embed a snapshot**, denormalize `{name, avatar}` onto the post so rendering needs no second read; accept that a name change won't retro-update old posts (often fine, sometimes you re-sync).
   (d) **Reference**, the full account is large, shared across many posts, and independently updated; store `author_id`.

**5.** One workable layout:
```
PK                SK              notes
----------------  --------------  --------------------------------
PROJECT#<pid>     META            project attributes
PROJECT#<pid>     TASK#<tid>      a task (co-located w/ project)
                                  + GSI1PK = USER#<assignee>
                                  + GSI1SK = DUE#<yyyy-mm-dd>#<tid>
```
- Get a project: `GetItem(PK=PROJECT#pid, SK=META)`.
- All tasks in a project: `Query(PK=PROJECT#pid, SK begins_with "TASK#")`.
- A single task by id: `GetItem(PK=PROJECT#pid, SK=TASK#tid)` (if you only have `tid`, also store a lookup item or a second GSI keyed by task id).
- Tasks assigned to a user by due date: `Query(GSI1, GSI1PK=USER#uid)`, sorted by `GSI1SK` which is due-date-prefixed, so it's chronological for free.

**6.** `Scan` reads (and bills for) all 50M items, then filters in memory, O(table size) per login, catastrophic latency and cost, and it'll throttle. Fix: support email lookup as a *key* access pattern, either make email part of the key, or add a **GSI** with `GSI1PK = EMAIL#<email>`, then `Query(GSI1, GSI1PK=EMAIL#x)` is O(1)-ish. Never `Scan` on a hot path.

**7.** Not a bug, **GSIs are eventually consistent**, and you *cannot* request a strongly-consistent read on a GSI. The write hasn't propagated to the index yet. Fix: read the user's own photo from the **base table** with `ConsistentRead=True` (base-table strong reads are supported), or show the just-written value optimistically from the client. Route the writer's own immediate reads to a path that supports read-your-writes.

**8.**
   (a) DynamoDB default reads → **PA/EL**: available under partition, low-latency (eventual) when healthy.
   (b) Spanner → **PC/EC**: consistent under partition, consistent (latency-costly) when healthy.
   (c) Single-node SQLite → **EC** essentially, but CAP/PACELC barely apply, there's no partition with one node; it's just consistent, and if the node dies you have downtime, not a CAP trade.

**9.**
```
key = "pwreset:{account}:{ floor(now/3600) }"   # hourly bucket
INCR key            # atomic
EXPIRE key 3600     # bucket self-destructs
allow if value <= 5
```
Flaw: **fixed-window edge burst**, a user can send 5 at 1:59:59 and 5 more at 2:00:01 (two buckets), i.e. 10 within ~2 seconds. A sliding-window log or token bucket smooths this out, at higher cost/complexity.

**10.** Behave **CP**: refuse to process the charge on the side that can't confirm the authoritative state, rather than risk a double-charge from two partitioned nodes both accepting. User experience: the payment is rejected or held ("we couldn't process that right now, try again") during the partition, annoying but correct. For money, correctness/consistency beats availability; you never want AP "answer from whatever node" semantics on a charge.
