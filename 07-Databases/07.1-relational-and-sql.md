## Start here

Before any of the formal stuff, let's get the plain-English picture, because the formal stuff makes much more sense once the intuition is in place.

A table is a spreadsheet with rules: picture a single sheet in Excel or Google Sheets. The columns have names across the top (`email`, `country`, `created_at`), and every row underneath is one record: one user, one order, one event. That's a database table. The difference is that a database table is strict in ways a spreadsheet isn't:

- Every value in a column must be the same type: the `monthly_usd` column can't have the word "free" sitting where a number should be.
- A column can be marked *required* (can't be blank) or *unique* (no two rows share that value, like email).
- One column (or a small set) is the **primary key**, the guaranteed-unique handle for each row, like a customer number.

A relational database is a filing cabinet full of those sheets, plus the wiring between them. Imagine one drawer labeled `users`, another labeled `orders`. Each order slip has a little field that says "this belongs to user #42." That cross-reference, a **foreign key**, is the "relational" part. Instead of copying a customer's whole profile onto every single order (and then having five slightly-different copies of their email when they update it once), you store each fact in exactly one place and link to it. The database itself enforces that you can't write an order for a customer who doesn't exist. That idea is what Codd gave us in 1970, and it's why we don't keep everything in one giant messy sheet.

SQL is the language you use to ask that filing cabinet questions. "Show me every US customer who paid more than \$100 last month, sorted by how much they spent." You describe *what* you want, not *how* to fetch it, and the database figures out the fastest way to get it. That declarative quality is why the same skill transfers everywhere.

Why does this matter for any tech job? SQL is the single most common technical skill across software roles: backend, data, analytics, even a lot of "non-technical" PM and ops jobs touch it. Almost every product on earth stores its data in a relational database (Postgres, MySQL, SQL Server, SQLite). When you build NYX Finance, the analytics literally are SQL queries against Postgres. When you work on Anneava, the multi-tenant isolation and HIPAA-aligned access rules are enforced at the database layer with Postgres Row-Level Security.

If you can read and write SQL confidently, you can answer your own data questions instead of waiting on someone else, you can debug production data issues, and you can pass the SQL screen that shows up in basically every entry-level interview (more on that later). It's a skill that compounds for the rest of your career, which is why this chapter is worth doing slowly and actually typing out.

If a term below feels abstract, come back here and remember: *spreadsheet with rules, filing cabinet with wiring, a language for asking it questions.*

## Theory: The Relational Model

### What a relation actually is

In 1970 Edgar Codd published "A Relational Model of Data for Large Shared Data Banks." The big idea: store data as mathematical relations, and let users describe what they want declaratively instead of writing procedural code to walk pointers. Before Codd, databases were navigational: you literally followed links from record to record. Codd's model decoupled the logical view of data from the physical storage.

A **relation** is, formally, a subset of a Cartesian product of domains. Let's unpack that with no hand-waving.

- A **domain** is a set of allowed values, e.g. `INTEGER`, `TEXT`, `DATE`. Think of it as a type.
- A **tuple** is an ordered list of values, one drawn from each domain: `(42, 'spencer@nyx.io', '2026-01-15')`.
- A **relation** is a *set* of such tuples. Because it's a set: no duplicate tuples, and no inherent ordering.

In SQL-speak:

| Relational term | SQL term |
|---|---|
| Relation | Table |
| Tuple | Row |
| Attribute | Column |
| Domain | Data type |
| Cardinality | Number of rows |
| Degree / arity | Number of columns |

One critical subtlety: a true relation is a set, so it has no duplicates and no order. SQL tables are actually **bags** (multisets): they can contain duplicate rows unless you constrain them, and the engine is free to return rows in any order unless you say `ORDER BY`. This gap between "pure relational" and "what SQL actually does" explains a lot of gotchas.

### Keys: how we identify tuples

- **Superkey**: any set of attributes whose values uniquely identify a tuple.
- **Candidate key**: a *minimal* superkey (remove any attribute and it stops being unique).
- **Primary key**: the candidate key we pick as *the* identifier. Cannot be NULL, must be unique.
- **Foreign key**: an attribute (or set) in one relation that references the primary key of another. This is how relations link without pointers.

Example from a NYX-style schema: `users.id` is a primary key. `accounts.user_id` is a foreign key pointing at `users.id`. The database can now *enforce* that you never create an account for a non-existent user. That guarantee, **referential integrity**, is something application code is terrible at maintaining on its own.

### Relational algebra (the engine under SQL)

SQL is declarative, but the query planner internally thinks in **relational algebra**, a small set of operators that take relations and produce relations. Knowing them makes SQL transparent:

| Operator | Symbol | Meaning | SQL |
|---|---|---|---|
| Selection | σ (sigma) | keep rows matching a predicate | `WHERE` |
| Projection | π (pi) | keep only certain columns | `SELECT col1, col2` |
| Cartesian product | × | every row of A paired with every row of B | `CROSS JOIN` |
| Join | ⋈ | product + selection on a condition | `JOIN ... ON` |
| Union | ∪ | rows in A or B | `UNION` |
| Difference | − | rows in A not in B | `EXCEPT` |
| Intersection | ∩ | rows in both | `INTERSECT` |
| Rename | ρ (rho) | rename a relation/attribute | `AS` |

The key insight: a JOIN is just a Cartesian product followed by a selection. `A JOIN B ON A.x = B.y` is conceptually `σ(A.x = B.y)(A × B)`. The query planner is far smarter than literally building the product, but that's the semantics. When a JOIN confuses you, mentally expand it to "pair everything, then filter."

These operators compose: the output of one is a valid input to the next, just like function composition. That closure property is why you can nest subqueries arbitrarily.

## Build it: SQL from the ground up

We'll use **PostgreSQL** syntax throughout (it's what NYX runs on). Let's build a realistic schema for a small SaaS analytics product, then hammer it with queries.

### DDL vs DML

- **DDL** (Data Definition Language): defines structure: `CREATE`, `ALTER`, `DROP`.
- **DML** (Data Manipulation Language): operates on data: `INSERT`, `SELECT`, `UPDATE`, `DELETE`.

### The schema

```sql
-- Users of the platform
CREATE TABLE users (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email       TEXT NOT NULL UNIQUE,
    full_name   TEXT NOT NULL,
    country     TEXT NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Subscription plans
CREATE TABLE plans (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name        TEXT NOT NULL UNIQUE,          -- 'free', 'pro', 'enterprise'
    monthly_usd NUMERIC(10,2) NOT NULL
);

-- Each user has zero or more subscriptions over time
CREATE TABLE subscriptions (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id     BIGINT NOT NULL REFERENCES users(id),
    plan_id     BIGINT NOT NULL REFERENCES plans(id),
    started_at  DATE NOT NULL,
    ended_at    DATE                            -- NULL = still active
);

-- Orders / payments
CREATE TABLE orders (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id     BIGINT NOT NULL REFERENCES users(id),
    amount_usd  NUMERIC(10,2) NOT NULL CHECK (amount_usd >= 0),
    status      TEXT NOT NULL CHECK (status IN ('paid','refunded','failed')),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Product usage events
CREATE TABLE events (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id     BIGINT NOT NULL REFERENCES users(id),
    event_type  TEXT NOT NULL,                  -- 'login','report_run','export'
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

A few choices worth noting:

- `GENERATED ALWAYS AS IDENTITY` is the modern SQL-standard auto-increment (prefer it over `SERIAL`).
- `REFERENCES` declares foreign keys → referential integrity for free.
- `CHECK` constraints push business rules (status must be valid, amounts non-negative) into the DB. The database becomes the last line of defense, not just a dumb store.
- `TIMESTAMPTZ` stores UTC instants. Always use it over `TIMESTAMP` to avoid timezone hell.

### SELECT, WHERE, ORDER BY

The fundamental query. Logical evaluation order matters: even though we write `SELECT` first, the engine conceptually processes

```
FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT
```

This explains why you can't use a `SELECT` alias in a `WHERE` (WHERE runs first) but you *can* in `ORDER BY`.

```sql
SELECT full_name, country
FROM users
WHERE country = 'US'
ORDER BY full_name ASC;
```

Result:

| full_name | country |
|---|---|
| Ana Ramos | US |
| Ben Cho | US |

`WHERE` is selection (σ); `SELECT full_name, country` is projection (π).

A note on **NULL**: NULL means "unknown," not "zero" or "empty." Comparisons with NULL yield *unknown*, not true/false. So `WHERE ended_at = NULL` matches nothing; you must write `WHERE ended_at IS NULL`. This trips everyone up at least once.

### JOINs - the heart of relational querying

A JOIN combines rows from two tables based on a related column. Let's draw each kind with the same two toy tables:

```
LEFT (L)            RIGHT (R)
 id | val            id | val
----+-----          ----+-----
  1 |  A              1 |  X
  2 |  B              3 |  Y
```

**INNER JOIN**: only rows where the key matches in both:

```
L INNER JOIN R ON L.id = R.id
   matches: id=1
┌────────────┐
│  L ∩ R     │   → (1, A, X)
└────────────┘
```

**LEFT (OUTER) JOIN**: all left rows; right columns NULL when no match:

```
L LEFT JOIN R
   (1, A, X)
   (2, B, NULL)   ← B has no match on the right
```

**RIGHT JOIN**: the mirror image, all right rows, left NULLed:

```
L RIGHT JOIN R
   (1, A, X)
   (NULL, NULL, Y)  ← Y has no match on the left
```

**FULL OUTER JOIN**: everything from both, NULLs filling gaps:

```
   (1,    A,    X)
   (2,    B,    NULL)
   (NULL, NULL, Y)
```

**CROSS JOIN**: the Cartesian product, every pairing (2 × 2 = 4 rows). No `ON`.

```
(1,A,1,X) (1,A,3,Y) (2,B,1,X) (2,B,3,Y)
```

Now real queries against our schema.

**Inner join**: users with their active plan:

```sql
SELECT u.full_name, p.name AS plan, p.monthly_usd
FROM users u
JOIN subscriptions s ON s.user_id = u.id
JOIN plans p         ON p.id = s.plan_id
WHERE s.ended_at IS NULL
ORDER BY u.full_name;
```

| full_name | plan | monthly_usd |
|---|---|---|
| Ana Ramos | pro | 49.00 |
| Ben Cho | free | 0.00 |
| Cara Diaz | enterprise | 499.00 |
| Eva Ivanova | pro | 49.00 |

Notice Dan is absent: his only subscription has `ended_at` set, so the `WHERE` filters him out. He churned.

**Left join**: all users and whether they have any paid order:

```sql
SELECT u.full_name,
       COUNT(o.id) FILTER (WHERE o.status = 'paid') AS paid_orders
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.full_name
ORDER BY paid_orders DESC, u.full_name;
```

| full_name | paid_orders |
|---|---|
| Ana Ramos | 2 |
| Cara Diaz | 1 |
| Dan Eze | 1 |
| Eva Ivanova | 1 |
| Ben Cho | 0 |

The LEFT JOIN keeps Ben even though he has zero orders, which is exactly what we hired it for. With an INNER JOIN he'd vanish, and "find users with no orders" is a classic LEFT-JOIN-then-`WHERE o.id IS NULL` pattern:

```sql
SELECT u.full_name
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;   -- → Ben Cho
```

### GROUP BY, HAVING, aggregates

Aggregates collapse many rows into one summary value: `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`. `GROUP BY` defines the buckets. `HAVING` filters *after* aggregation (whereas `WHERE` filters *before*).

```sql
SELECT u.country,
       COUNT(*)                              AS n_orders,
       SUM(o.amount_usd)                      AS gross_usd,
       ROUND(AVG(o.amount_usd), 2)            AS avg_order
FROM orders o
JOIN users u ON u.id = o.user_id
WHERE o.status = 'paid'
GROUP BY u.country
HAVING SUM(o.amount_usd) > 50
ORDER BY gross_usd DESC;
```

| country | n_orders | gross_usd | avg_order |
|---|---|---|---|
| CA | 1 | 499.00 | 499.00 |
| US | 2 | 98.00 | 49.00 |

The mental model: `WHERE` thins the rows → `GROUP BY` piles them into buckets → aggregates compute one number per bucket → `HAVING` drops whole buckets → `ORDER BY` sorts the survivors.

### Subqueries

A subquery is a query nested inside another. Three flavors:

**Scalar subquery** (returns one value):

```sql
SELECT full_name, amount_usd
FROM orders o JOIN users u ON u.id = o.user_id
WHERE amount_usd > (SELECT AVG(amount_usd) FROM orders);
```

**IN / NOT IN subquery:**

```sql
-- Users who have run at least one report
SELECT full_name FROM users
WHERE id IN (SELECT user_id FROM events WHERE event_type = 'report_run');
```

**Correlated subquery** (references the outer row, runs conceptually per outer row):

```sql
SELECT u.full_name,
       (SELECT COUNT(*) FROM orders o
        WHERE o.user_id = u.id AND o.status = 'paid') AS paid_count
FROM users u;
```

Correlated subqueries can be slow (they re-evaluate per row), so prefer JOINs/aggregates when you can. But they read well, and the planner often rewrites them anyway.

### CTEs (`WITH`)

Common Table Expressions name a subquery so you can reference it like a table. They make complex queries readable, and you'll lean on them constantly in NYX dashboards. Build a pipeline of named steps:

```sql
WITH paid AS (
    SELECT user_id, SUM(amount_usd) AS revenue
    FROM orders
    WHERE status = 'paid'
    GROUP BY user_id
),
ranked AS (
    SELECT u.full_name, p.revenue,
           RANK() OVER (ORDER BY p.revenue DESC) AS revenue_rank
    FROM paid p JOIN users u ON u.id = p.user_id
)
SELECT * FROM ranked WHERE revenue_rank <= 3;
```

CTEs can also be **recursive**, great for hierarchies (org charts, category trees):

```sql
WITH RECURSIVE countdown(n) AS (
    SELECT 5                       -- anchor
    UNION ALL
    SELECT n - 1 FROM countdown WHERE n > 1   -- recursive step
)
SELECT n FROM countdown;   -- 5,4,3,2,1
```

### Window functions

A window function computes a value across a set of rows related to the current row, *without collapsing them* the way `GROUP BY` does. For analytics work, it's the most powerful and most underused feature in SQL.

Anatomy:

```
function() OVER (PARTITION BY ... ORDER BY ... frame)
```

- `PARTITION BY` = the groups (like GROUP BY, but rows stay).
- `ORDER BY` (inside OVER) = ordering within each partition, needed for ranking and running totals.
- *frame* = which rows in the partition count (e.g. running vs. whole partition).

**Ranking:**

```sql
SELECT u.full_name, u.country, o.amount_usd,
       ROW_NUMBER() OVER (PARTITION BY u.country ORDER BY o.amount_usd DESC) AS rn,
       RANK()       OVER (PARTITION BY u.country ORDER BY o.amount_usd DESC) AS rnk,
       DENSE_RANK() OVER (PARTITION BY u.country ORDER BY o.amount_usd DESC) AS drnk
FROM orders o JOIN users u ON u.id = o.user_id
WHERE o.status = 'paid';
```

`ROW_NUMBER` is always unique (1,2,3…). `RANK` leaves gaps on ties (1,1,3). `DENSE_RANK` doesn't (1,1,2). Pick based on whether ties should consume rank slots.

**Running total** (cumulative revenue over time):

```sql
SELECT created_at::date AS day, amount_usd,
       SUM(amount_usd) OVER (ORDER BY created_at
                             ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total
FROM orders
WHERE status = 'paid'
ORDER BY created_at;
```

| day | amount_usd | running_total |
|---|---|---|
| 2026-01-01 | 49.00 | 49.00 |
| 2026-01-10 | 49.00 | 98.00 |
| 2026-02-01 | 49.00 | 147.00 |
| 2026-02-01 | 499.00 | 646.00 |
| 2026-03-01 | 49.00 | 695.00 |

**LAG / LEAD** (compare a row to its neighbors, month-over-month growth):

```sql
SELECT day, revenue,
       LAG(revenue) OVER (ORDER BY day) AS prev_month,
       revenue - LAG(revenue) OVER (ORDER BY day) AS delta
FROM (
    SELECT date_trunc('month', created_at)::date AS day,
           SUM(amount_usd) AS revenue
    FROM orders WHERE status = 'paid'
    GROUP BY 1
) m
ORDER BY day;
```

### Set operations

- `UNION` (dedupes) / `UNION ALL` (keeps dupes, faster, use when you know there are none)
- `INTERSECT` (rows in both)
- `EXCEPT` (rows in first not in second)

```sql
-- Everyone who EITHER paid OR logged in, deduped
SELECT user_id FROM orders WHERE status = 'paid'
UNION
SELECT user_id FROM events WHERE event_type = 'login';
```

The two queries must have the same number of columns with compatible types: they're literally relational ∪, ∩, −.

### More worked examples - stepping through real queries

The best way to internalize this is to watch the logic flow one query at a time. These all run against the schema seeded above, with the result set shown every time.

**W1. Three-table join: every order with the customer's name, country, and the plan they were on.**

This chains two joins. Read joins left to right: start with `orders`, attach the matching `users` row, then attach that user's *active* plan via `subscriptions` → `plans`.

```sql
SELECT o.id          AS order_id,
       u.full_name,
       u.country,
       p.name        AS plan,
       o.amount_usd,
       o.status
FROM orders o
JOIN users u         ON u.id = o.user_id
JOIN subscriptions s ON s.user_id = u.id AND s.ended_at IS NULL
JOIN plans p         ON p.id = s.plan_id
ORDER BY o.id;
```

| order_id | full_name | country | plan | amount_usd | status |
|---|---|---|---|---|---|
| 1 | Ana Ramos | US | pro | 49.00 | paid |
| 2 | Ana Ramos | US | pro | 49.00 | paid |
| 3 | Cara Diaz | CA | enterprise | 499.00 | paid |
| 6 | Eva Ivanova | DE | pro | 49.00 | paid |
| 7 | Eva Ivanova | DE | pro | 49.00 | failed |

Step through why Dan's orders (4 and 5) vanished: his only subscription has `ended_at` set, so the predicate `s.ended_at IS NULL` on the join finds no active subscription, and an INNER JOIN drops the row entirely. This is a classic trap: putting a filter in the `ON` of an inner join behaves like putting it in `WHERE`. If you wanted to keep Dan's orders and just show NULL for the plan, you'd switch that join to a LEFT JOIN.

**W2. GROUP BY with two HAVING variations.**

We already found countries whose paid revenue exceeds \$50. Now a different HAVING: countries with more than one paid order.

```sql
SELECT u.country,
       COUNT(*)            AS paid_orders,
       SUM(o.amount_usd)   AS revenue
FROM orders o
JOIN users u ON u.id = o.user_id
WHERE o.status = 'paid'
GROUP BY u.country
HAVING COUNT(*) > 1
ORDER BY revenue DESC;
```

| country | paid_orders | revenue |
|---|---|---|
| US | 2 | 98.00 |

Only the US has more than one paid order (Ana's two). The other countries each have exactly one, so HAVING drops their whole bucket. The lesson: `WHERE` filters individual rows *before* grouping; `HAVING` filters whole groups *after* aggregating. You can't write `WHERE COUNT(*) > 1`; the count doesn't exist yet at WHERE time.

**W3. A self-join: pair up users from the same country.**

A self-join is just a table joined to itself under two aliases. Useful for "find rows related to other rows in the same table." Here you find all distinct pairs of users who share a country:

```sql
SELECT a.full_name AS user_a,
       b.full_name AS user_b,
       a.country
FROM users a
JOIN users b ON b.country = a.country
            AND a.id < b.id           -- a.id < b.id avoids dupes & self-pairs
ORDER BY a.country, user_a;
```

| user_a | user_b | country |
|---|---|---|
| Ana Ramos | Ben Cho | US |

Trace it: `a.country = b.country` would normally pair Ana with Ana (self), Ana with Ben, and Ben with Ana (the mirror). The `a.id < b.id` predicate keeps only one direction and removes the self-pair. Cara, Dan, and Eva are each alone in their country, so they produce no pair. Self-joins show up constantly for "employees and their managers" (same `employees` table), so keep the alias trick handy.

**W4. COALESCE and CASE: turn churn dates and statuses into readable labels.**

`COALESCE(a, b, ...)` returns the first non-NULL argument, perfect for "show ended_at, but if it's NULL print 'active'." `CASE` is SQL's if/else expression.

```sql
SELECT u.full_name,
       p.name AS plan,
       COALESCE(s.ended_at::text, 'still active') AS ended,
       CASE
         WHEN s.ended_at IS NULL              THEN 'current'
         WHEN s.ended_at < DATE '2026-03-01'  THEN 'early churn'
         ELSE                                       'late churn'
       END AS status_label
FROM subscriptions s
JOIN users u ON u.id = s.user_id
JOIN plans p ON p.id = s.plan_id
ORDER BY u.full_name;
```

| full_name | plan | ended | status_label |
|---|---|---|---|
| Ana Ramos | pro | still active | current |
| Ben Cho | free | still active | current |
| Cara Diaz | enterprise | still active | current |
| Dan Eze | pro | 2026-04-01 | late churn |
| Eva Ivanova | pro | still active | current |

Dan churned on 2026-04-01, which is after the 2026-03-01 cutoff, so the `CASE` falls through to `ELSE` → "late churn." Everyone else has a NULL `ended_at`, so `COALESCE` prints "still active" and the first `WHEN` catches them as "current." `CASE` is how you get conditional logic inside a SELECT without leaving SQL.

**W5. DISTINCT vs GROUP BY: which countries do we have customers in?**

```sql
SELECT DISTINCT country FROM users ORDER BY country;
```

| country |
|---|
| CA |
| DE |
| GB |
| US |

`DISTINCT` collapses duplicate rows: there are five users here but only four distinct countries, since two are US. Note that `SELECT DISTINCT country` and `SELECT country FROM users GROUP BY country` produce the same result here: `DISTINCT` is essentially "GROUP BY every selected column with no aggregates." Use `DISTINCT` when you just want unique values; reach for `GROUP BY` the moment you also need a `COUNT`/`SUM` per group.

**W6. EXISTS vs IN: users who have ever run a report.**

Both of these answer "which users appear in the events table with `report_run`?" They're logically equivalent here, but they behave differently around NULLs and performance.

```sql
-- Version A: IN with a subquery
SELECT full_name FROM users
WHERE id IN (SELECT user_id FROM events WHERE event_type = 'report_run');

-- Version B: correlated EXISTS (usually the safer default)
SELECT u.full_name FROM users u
WHERE EXISTS (
  SELECT 1 FROM events e
  WHERE e.user_id = u.id AND e.event_type = 'report_run'
);
```

Both return the same names. The important difference is `NOT IN` vs `NOT EXISTS`: if the subquery for a `NOT IN` ever returns a NULL, the *entire* `NOT IN` evaluates to unknown and you silently get **zero rows**. `NOT EXISTS` doesn't have that landmine. A good rule of thumb: default to `EXISTS`/`NOT EXISTS` for membership tests, and only use `IN` with a literal list or a subquery you're certain is NULL-free.

**W7. Window function: each order's share of its country's total revenue.**

Earlier you saw ranking and running totals. Here's a window aggregate: `SUM() OVER (PARTITION BY ...)` computes a per-group total without collapsing rows, so you can put each order next to its country's total and compute a percentage:

```sql
SELECT u.country,
       u.full_name,
       o.amount_usd,
       SUM(o.amount_usd) OVER (PARTITION BY u.country) AS country_total,
       ROUND(100.0 * o.amount_usd
             / SUM(o.amount_usd) OVER (PARTITION BY u.country), 1) AS pct_of_country
FROM orders o
JOIN users u ON u.id = o.user_id
WHERE o.status = 'paid'
ORDER BY u.country, o.amount_usd DESC;
```

| country | full_name | amount_usd | country_total | pct_of_country |
|---|---|---|---|---|
| CA | Cara Diaz | 499.00 | 499.00 | 100.0 |
| DE | Eva Ivanova | 49.00 | 49.00 | 100.0 |
| GB | Dan Eze | 49.00 | 49.00 | 100.0 |
| US | Ana Ramos | 49.00 | 98.00 | 50.0 |
| US | Ana Ramos | 49.00 | 98.00 | 50.0 |

This is the thing `GROUP BY` can't do: each US row keeps its own 49.00 amount *and* sees the country total of 98.00 alongside it, so each is 50% of US revenue. If you'd used `GROUP BY country` you'd have lost the individual order rows. Window functions let you aggregate while keeping the detail, and that's the trick that makes them so valuable for analytics.

## Common mistakes

These are the bugs you'll actually make (or watch bite a query in code review). For each: the wrong version, why it's wrong, and the fix.

**1. Comparing to NULL with `=`.**

```sql
-- Wrong: Returns ZERO rows, always - NULL = NULL is "unknown", not true
SELECT * FROM subscriptions WHERE ended_at = NULL;
-- Right:
SELECT * FROM subscriptions WHERE ended_at IS NULL;
```
NULL means "unknown." Any comparison with `=`, `<`, `<>` against NULL yields *unknown*, and `WHERE` only keeps rows that are *true*. Use `IS NULL` / `IS NOT NULL`.

**2. `COUNT(*)` vs `COUNT(column)`.**

```sql
-- These can disagree!
SELECT COUNT(*)        FROM subscriptions;   -- counts all rows (5)
SELECT COUNT(ended_at) FROM subscriptions;   -- counts NON-NULL ended_at (1)
```
`COUNT(*)` counts rows; `COUNT(col)` counts rows where `col` is not NULL. People reach for `COUNT(*)` meaning "how many have a value" and get surprised. And `COUNT(DISTINCT col)` is different again, unique non-null values.

**3. GROUP BY missing a selected column.**

```sql
-- Wrong: Postgres errors: "column u.full_name must appear in GROUP BY or aggregate"
SELECT u.country, u.full_name, SUM(o.amount_usd)
FROM orders o JOIN users u ON u.id = o.user_id
GROUP BY u.country;
-- Right: every non-aggregated SELECT column must be in GROUP BY
GROUP BY u.country, u.full_name
```
Postgres is strict (MySQL historically wasn't, which let people write silently-wrong queries). Every column in `SELECT` must either be aggregated or appear in `GROUP BY`.

**4. Ambiguous column names in a join.**

```sql
-- Wrong: "column reference 'id' is ambiguous" - both tables have id
SELECT id, full_name FROM users u JOIN orders o ON o.user_id = u.id;
-- Right: qualify with the table alias
SELECT u.id, u.full_name FROM users u JOIN orders o ON o.user_id = u.id;
```
Once two joined tables share a column name, you must qualify it. Honestly, alias and qualify everything in multi-table queries: it's free readability.

**5. Forgetting `WHERE` on UPDATE / DELETE.**

```sql
-- Wrong: updates EVERY row in the table
UPDATE orders SET status = 'refunded';
-- Right:
UPDATE orders SET status = 'refunded' WHERE id = 5;
```
This is the one that ends careers. There's no undo on a committed statement. Habits that save you: write the `WHERE` first, run it as a `SELECT` to confirm the row count, *then* swap `SELECT` for `UPDATE`/`DELETE`. Wrap risky changes in a transaction (`BEGIN; ... ; COMMIT;`) so you can `ROLLBACK` if the row count looks wrong.

**6. INNER JOIN silently dropping rows you wanted to keep.**

```sql
-- Wrong: Users with zero orders disappear - only 4 of 5 users come back
SELECT u.full_name, COUNT(o.id)
FROM users u JOIN orders o ON o.user_id = u.id
GROUP BY u.full_name;
-- Right: LEFT JOIN keeps every user; Ben shows 0
SELECT u.full_name, COUNT(o.id)
FROM users u LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.full_name;
```
If the "driving" table's rows must all appear regardless of matches, use a LEFT JOIN. With the inner join, Ben Cho (no orders) silently vanishes and your "users by order count" report is quietly wrong.

**7. Integer division.**

```sql
-- Wrong: 1/4 in integer math is 0, so this is always 0
SELECT 1 / 4;                         -- → 0
SELECT COUNT(*) FILTER (WHERE status='paid') / COUNT(*) FROM orders;  -- → 0
-- Right: make one side numeric
SELECT 1.0 / 4;                       -- → 0.25
SELECT ROUND(100.0 * COUNT(*) FILTER (WHERE status='paid') / COUNT(*), 1) FROM orders;
```
Dividing two integers in Postgres does integer division and truncates. Multiply by `1.0` / `100.0` or cast (`::numeric`) to force real division. This silently ruins conversion-rate and percentage queries.

**8. `SELECT *` in production code.**

```sql
-- Wrong: in app/report code
SELECT * FROM users;
-- Right: name the columns you actually use
SELECT id, email, full_name FROM users;
```
`SELECT *` breaks when someone adds/reorders a column, pulls more data over the wire than you need, and can leak sensitive columns (in Anneava, a stray `SELECT *` could surface PHI you never meant to fetch). Fine for ad-hoc exploration at the psql prompt; name your columns anywhere it's committed.

**9. Dividing without guarding zero.**

```sql
-- Wrong: division by zero error when last month's revenue was 0
revenue / LAG(revenue) OVER (ORDER BY month)
-- Right:
revenue / NULLIF(LAG(revenue) OVER (ORDER BY month), 0)
```
`NULLIF(x, 0)` turns a 0 denominator into NULL, so the whole expression becomes NULL instead of throwing. Standard hygiene for any growth/ratio metric.

**10. Assuming row order without `ORDER BY`.**

```sql
-- Wrong: "the first row" is meaningless without an explicit order
SELECT * FROM orders LIMIT 1;
-- Right:
SELECT * FROM orders ORDER BY created_at DESC LIMIT 1;
```
SQL tables are unordered bags (remember the theory section). Without `ORDER BY`, the engine may return rows in any order, and it can change between runs after an index change or a vacuum. If order matters, say so.

## On the job / interview angle

SQL questions show up in almost every entry-level software, data, and analyst interview. It's the most reliably-tested technical skill because it's universal, it's quick to assess in 20 minutes, and it cleanly separates "memorized syntax" from "actually understands the relational model." A typical SQL screen gives you a small schema (a lot like the one in this chapter) and asks you to write 2-4 queries live, talking through your logic. Below are the questions you should be able to answer cold.

**1. What's the difference between `WHERE` and `HAVING`?**

`WHERE` filters individual rows *before* grouping/aggregation; `HAVING` filters groups *after* aggregation. You can't reference an aggregate (`COUNT(*)`) in `WHERE` because it doesn't exist yet at that point in the logical evaluation order (`FROM → WHERE → GROUP BY → HAVING → SELECT`). Use `WHERE` to cut rows cheaply first; use `HAVING` only for conditions on aggregates.

**2. INNER JOIN vs LEFT JOIN?**

INNER returns only rows with a match in *both* tables. LEFT (outer) returns *all* rows from the left table, filling right-side columns with NULL where there's no match. Practical tell: if a question says "all customers, *including* those with no orders," you need a LEFT JOIN. The "find rows with no match" trick is `LEFT JOIN ... WHERE right.id IS NULL`.

**3. Primary key vs foreign key?**

A **primary key** uniquely identifies each row in its own table; it's unique and non-NULL. A **foreign key** is a column that references another table's primary key, enforcing referential integrity (you can't insert an order for a user that doesn't exist, and depending on the rule you can't delete a user who still has orders). PK = "who am I"; FK = "who do I point at."

**4. Write a query to find the second-highest order amount.**

The robust, dialect-portable way uses a window function:

```sql
SELECT amount_usd FROM (
  SELECT amount_usd,
         DENSE_RANK() OVER (ORDER BY amount_usd DESC) AS rnk
  FROM orders
) t
WHERE rnk = 2;
```

Use `DENSE_RANK` so ties at the top don't skip the "second" slot. A quick alternative is `ORDER BY amount_usd DESC OFFSET 1 LIMIT 1`, but that mishandles ties. Mention the tradeoff out loud; interviewers love that. (The "Nth highest" generalization is just `WHERE rnk = N`.)

**5. Find duplicate rows (e.g. duplicate emails).**

```sql
SELECT email, COUNT(*)
FROM users
GROUP BY email
HAVING COUNT(*) > 1;
```

Group by the column(s) that define a duplicate, then keep groups with a count over 1. To find duplicates across multiple columns, group by all of them. To *delete* dupes keeping one, you'd use a window `ROW_NUMBER() OVER (PARTITION BY email ORDER BY id)` and delete where `rn > 1`.

**6. Explain a self-join with an example.**

A self-join is a table joined to itself using two aliases, for relating rows to other rows in the same table. Classic example: an `employees(id, name, manager_id)` table where `manager_id` points back at `employees.id`.

```sql
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.id = e.manager_id;
```

The LEFT JOIN keeps the CEO, whose `manager_id` is NULL. You could also mention the "same country pairs" example from earlier where `a.id < b.id` dedupes the pairs.

**7. What does `GROUP BY` do, and what can appear in the `SELECT`?**

`GROUP BY` collapses rows that share the grouped values into one row per group, so aggregates compute per group. Every column in the `SELECT` must be either one of the grouped columns or wrapped in an aggregate, otherwise Postgres errors because it wouldn't know which row's value to show.

**8. `UNION` vs `UNION ALL`?**

Both stack two result sets with matching column counts/types. `UNION` removes duplicate rows (which costs a sort/hash to dedupe); `UNION ALL` keeps everything and is faster. Use `UNION ALL` whenever you know the inputs are disjoint or you want the duplicates: don't pay for a dedupe you don't need.

**Interview meta-advice:** narrate the logical evaluation order as you build the query, qualify every column with an alias, call out NULL and tie edge cases before they ask, and sanity-check against the tiny example in your head ("with these 5 rows, does this return what I expect?"). Getting a slightly-imperfect query while reasoning clearly out loud beats a silent perfect one.

## Mini-project: An analytics schema and the questions it answers

Let's pretend the NYX product team drops these business questions on you. We'll answer each with one query, leaning on window functions where they earn their keep. (Schema above: `users`, `orders`, `events`, `subscriptions`, `plans`.)

**Q1. Monthly Recurring Revenue (MRR) by month, with month-over-month % change.**

```sql
WITH monthly AS (
    SELECT date_trunc('month', created_at)::date AS month,
           SUM(amount_usd) AS revenue
    FROM orders WHERE status = 'paid'
    GROUP BY 1
)
SELECT month, revenue,
       LAG(revenue) OVER (ORDER BY month) AS prev,
       ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY month))
             / NULLIF(LAG(revenue) OVER (ORDER BY month), 0), 1) AS mom_pct
FROM monthly
ORDER BY month;
```

`NULLIF(x, 0)` guards against divide-by-zero, a habit worth building.

**Q2. Top spender per country (no GROUP BY collapse needed):**

```sql
SELECT * FROM (
    SELECT u.country, u.full_name, SUM(o.amount_usd) AS spend,
           ROW_NUMBER() OVER (PARTITION BY u.country
                              ORDER BY SUM(o.amount_usd) DESC) AS rn
    FROM orders o JOIN users u ON u.id = o.user_id
    WHERE o.status = 'paid'
    GROUP BY u.country, u.full_name
) ranked
WHERE rn = 1;
```

This "GROUP BY then window-rank then filter rn=1" is the canonical "top-N-per-group" pattern. Memorize its shape.

**Q3. Customer lifetime: days between first and last paid order:**

```sql
SELECT u.full_name,
       MIN(o.created_at)::date AS first_order,
       MAX(o.created_at)::date AS last_order,
       MAX(o.created_at)::date - MIN(o.created_at)::date AS lifetime_days
FROM orders o JOIN users u ON u.id = o.user_id
WHERE o.status = 'paid'
GROUP BY u.id, u.full_name
ORDER BY lifetime_days DESC;
```

**Q4. Active vs. churned subscriptions per plan:**

```sql
SELECT p.name AS plan,
       COUNT(*) FILTER (WHERE s.ended_at IS NULL)  AS active,
       COUNT(*) FILTER (WHERE s.ended_at IS NOT NULL) AS churned
FROM subscriptions s JOIN plans p ON p.id = s.plan_id
GROUP BY p.name
ORDER BY active DESC;
```

**Q5. Funnel: of users who logged in, how many ran a report?** (correlated EXISTS):

```sql
SELECT
  COUNT(*) FILTER (WHERE EXISTS (
     SELECT 1 FROM events e WHERE e.user_id = u.id AND e.event_type='login'))  AS logged_in,
  COUNT(*) FILTER (WHERE EXISTS (
     SELECT 1 FROM events e WHERE e.user_id = u.id AND e.event_type='report_run')) AS ran_report
FROM users u;
```

Build the schema, seed it, and run all five. When the result sets feel obvious before you hit Enter, you've internalized the model.

## Mini-project #2: A bookstore schema from scratch

The first mini-project reused the SaaS schema. For this one we'll build something fresh and small, from `CREATE TABLE` to analytics, so you get reps on schema design too. A tiny online bookstore: books, authors, customers, and orders of books. It exercises a many-to-many relationship (a book can have several authors; an author writes several books), which the SaaS schema didn't.

### Schema

```sql
CREATE TABLE authors (
    id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name  TEXT NOT NULL
);

CREATE TABLE books (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title         TEXT NOT NULL,
    genre         TEXT NOT NULL,
    price_usd     NUMERIC(10,2) NOT NULL CHECK (price_usd >= 0),
    published_yr  INT NOT NULL
);

-- Many-to-many bridge between books and authors
CREATE TABLE book_authors (
    book_id   BIGINT NOT NULL REFERENCES books(id),
    author_id BIGINT NOT NULL REFERENCES authors(id),
    PRIMARY KEY (book_id, author_id)        -- composite key, no dupe pairs
);

CREATE TABLE customers (
    id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name  TEXT NOT NULL,
    city  TEXT NOT NULL
);

-- One row per book sold (a line item)
CREATE TABLE sales (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id  BIGINT NOT NULL REFERENCES customers(id),
    book_id      BIGINT NOT NULL REFERENCES books(id),
    qty          INT NOT NULL CHECK (qty > 0),
    sold_at      DATE NOT NULL
);
```

The `book_authors` table is the standard **junction (bridge) table** for a many-to-many relationship: its primary key is the *pair* `(book_id, author_id)`, which guarantees you can't link the same author to the same book twice.

### Seed data


### Analytical queries

**B1. Revenue per book (price × quantity), best sellers first.**

```sql
SELECT b.title,
       b.genre,
       SUM(s.qty)                  AS units,
       SUM(s.qty * b.price_usd)    AS revenue
FROM sales s
JOIN books b ON b.id = s.book_id
GROUP BY b.id, b.title, b.genre
ORDER BY revenue DESC;
```

One row per sold book:

| title | genre | units | revenue |
|---|---|---|---|
| Concurrency Tales | tech | 2 | 90.00 |
| Indexes Explained | tech | 2 | 78.00 |
| Normal Forms | tech | 2 | 58.00 |
| Window Seat | fiction | 3 | 36.00 |
| The Join Mystery | fiction | 1 | 14.00 |

(Concurrency Tales: 2 units × \$45 = \$90. Note that `qty * price` happens before the SUM, which is what we want.)

**B2. Each author's total attributed revenue (joins across the junction table).**

Because a sale is of a *book*, and a book may have multiple authors, this query fans a sale out to every author of that book. Splitting revenue evenly is overkill for now, so here we just attribute the full line revenue to each author (common in "books touched" reporting):

```sql
SELECT a.name AS author,
       SUM(s.qty * b.price_usd) AS attributed_revenue
FROM authors a
JOIN book_authors ba ON ba.author_id = a.id
JOIN books b         ON b.id = ba.book_id
LEFT JOIN sales s    ON s.book_id = b.id
GROUP BY a.id, a.name
ORDER BY attributed_revenue DESC NULLS LAST;
```

One row per author; the LEFT JOIN ensures an author with unsold books still appears with NULL revenue.

**B3. Genre mix per city (window: each genre's share within the city).**

```sql
SELECT c.city,
       b.genre,
       SUM(s.qty * b.price_usd) AS revenue,
       ROUND(100.0 * SUM(s.qty * b.price_usd)
             / SUM(SUM(s.qty * b.price_usd)) OVER (PARTITION BY c.city), 1) AS pct_of_city
FROM sales s
JOIN books b      ON b.id = s.book_id
JOIN customers c  ON c.id = s.customer_id
GROUP BY c.city, b.genre
ORDER BY c.city, revenue DESC;
```

The nested `SUM(SUM(...)) OVER (...)` looks scary but is mechanical: the inner `SUM` is the group aggregate (revenue per city+genre), and the window `SUM(...) OVER (PARTITION BY city)` totals those group values per city, so the ratio is each genre's slice of its city. This is the "aggregate, then window over the aggregates" pattern.

**B4. Co-authored books (via the junction table).**

Find books with more than one author:

```sql
SELECT b.title, COUNT(*) AS author_count
FROM book_authors ba
JOIN books b ON b.id = ba.book_id
GROUP BY b.id, b.title
HAVING COUNT(*) > 1;
```

Expected: only *The Join Mystery* (Boris + Cleo) → `author_count = 2`. Same `HAVING COUNT(*) > 1` shape as the duplicate-finder interview question, applied to legitimate multiplicity.

**B5. Repeat customers and their first vs. latest purchase.**

```sql
SELECT c.name,
       c.city,
       COUNT(*)                AS orders,
       MIN(s.sold_at)          AS first_purchase,
       MAX(s.sold_at)          AS latest_purchase,
       MAX(s.sold_at) - MIN(s.sold_at) AS days_active
FROM sales s
JOIN customers c ON c.id = s.customer_id
GROUP BY c.id, c.name, c.city
HAVING COUNT(*) > 1
ORDER BY orders DESC;
```

Expected: Mara Lin (3 orders), Theo Park (2), and Nina Ortega (2) all appear. The `HAVING COUNT(*) > 1` keeps only repeat buyers, and `MAX - MIN` on dates gives a tenure in days.

Build it, seed it, run all five. Designing the schema yourself (choosing the junction table, the composite key, the CHECK constraints) is where the relational model finally clicks.

## Exercises

These run against the **SaaS schema** (`users`, `plans`, `subscriptions`, `orders`, `events`) unless noted. Ordered roughly easy → hard. Try each before peeking at the solutions.

1. List every user's `full_name` and `email`, sorted by `full_name`.
2. Show all `paid` orders with an `amount_usd` of 49.00 or more.
3. Count how many users are in each country.
4. Total `paid` revenue (sum of `amount_usd` where status = 'paid').
5. List each user and their number of paid orders, *including* users with zero (hint: LEFT JOIN).
6. Find users who have **no** events at all.
7. For each plan, show the count of currently-active subscriptions (`ended_at IS NULL`).
8. Compute, per country, the conversion rate = paid orders ÷ total orders, as a percentage rounded to 1 decimal (watch out for integer division).
9. Rank users by total paid spend using `RANK()`, showing name, spend, and rank.
10. Find the second-highest single `amount_usd` among paid orders, handling ties correctly.

### Solutions

**1.**
```sql
SELECT full_name, email
FROM users
ORDER BY full_name;
```
Pure projection + sort. Aliasing the table isn't needed since it's single-table.

**2.**
```sql
SELECT *
FROM orders
WHERE status = 'paid' AND amount_usd >= 49.00;
```
Two predicates joined with `AND`. (In committed code you'd name the columns instead of `*`.)

**3.**
```sql
SELECT country, COUNT(*) AS n_users
FROM users
GROUP BY country
ORDER BY n_users DESC;
```
`GROUP BY country` buckets rows; `COUNT(*)` counts each bucket. US → 2, the rest → 1.

**4.**
```sql
SELECT SUM(amount_usd) AS paid_revenue
FROM orders
WHERE status = 'paid';
```
`WHERE` filters before the aggregate, so failed/refunded orders don't count. Result: 695.00.

**5.**
```sql
SELECT u.full_name,
       COUNT(o.id) FILTER (WHERE o.status = 'paid') AS paid_orders
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.full_name
ORDER BY paid_orders DESC, u.full_name;
```
The LEFT JOIN keeps Ben (zero orders). `COUNT(o.id)` ignores the NULL row the LEFT JOIN produces for Ben, so he correctly shows 0. `FILTER` restricts the count to paid orders.

**6.**
```sql
SELECT u.full_name
FROM users u
LEFT JOIN events e ON e.user_id = u.id
WHERE e.id IS NULL;
```
The "anti-join" pattern: LEFT JOIN, then keep only rows where the right side failed to match (its `id` is NULL). Equivalently `WHERE NOT EXISTS (SELECT 1 FROM events e WHERE e.user_id = u.id)`.

**7.**
```sql
SELECT p.name AS plan,
       COUNT(*) FILTER (WHERE s.ended_at IS NULL) AS active_subs
FROM plans p
LEFT JOIN subscriptions s ON s.plan_id = p.id
GROUP BY p.id, p.name
ORDER BY active_subs DESC;
```
LEFT JOIN from `plans` so a plan with no subscriptions still shows up with 0. The `FILTER` counts only active ones.

**8.**
```sql
SELECT u.country,
       ROUND(100.0 * COUNT(*) FILTER (WHERE o.status = 'paid')
             / COUNT(*), 1) AS conversion_pct
FROM orders o
JOIN users u ON u.id = o.user_id
GROUP BY u.country
ORDER BY conversion_pct DESC;
```
The `100.0 *` forces numeric division; without it, `paid_count / total` would be integer-truncated to 0. `COUNT(*)` is total orders per country; the filtered count is paid orders.

**9.**
```sql
WITH spend AS (
  SELECT u.id, u.full_name, SUM(o.amount_usd) AS total_spend
  FROM users u
  JOIN orders o ON o.user_id = u.id
  WHERE o.status = 'paid'
  GROUP BY u.id, u.full_name
)
SELECT full_name, total_spend,
       RANK() OVER (ORDER BY total_spend DESC) AS spend_rank
FROM spend
ORDER BY spend_rank;
```
A CTE computes spend per user; the window `RANK()` ranks them without collapsing rows. Cara (499) ranks #1, Ana (98) #2, etc. `RANK` (not `ROW_NUMBER`) so genuine ties would share a rank.

**10.**
```sql
SELECT amount_usd
FROM (
  SELECT amount_usd,
         DENSE_RANK() OVER (ORDER BY amount_usd DESC) AS rnk
  FROM orders
  WHERE status = 'paid'
) t
WHERE rnk = 2;
```
`DENSE_RANK` so that if several orders tie for the highest amount, "second" still means the next distinct value down, not just the next physical row. The top paid amount is 499; the second distinct is 49 → that's the answer. (Generalizes to Nth-highest with `WHERE rnk = N`.)
