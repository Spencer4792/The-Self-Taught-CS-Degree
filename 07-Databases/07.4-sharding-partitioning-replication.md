# Chapter 7.4 - Sharding, Partitioning & Replication

> Goal: Understand how data scales beyond one machine, partitioning vs. sharding, how to pick a shard key, why resharding hurts, and how consistent hashing solves it (we'll derive *and* implement it). Then replication topologies, sync vs. async, replication lag, and failover. End state: you can design a data tier for a high-write app and defend every choice.

Everything so far assumed one database server. That's fine until the data or the traffic outgrows the biggest machine you can rent. This chapter is about what happens next: splitting data across machines (partitioning/sharding) and copying it across machines (replication). These are the techniques behind every system that serves millions of users, and the trade-offs reappear constantly in system-design interviews and real architecture decisions.

## Start here

Before any of the jargon, here's the whole chapter as two everyday pictures. Hold onto these, every fancy term below collapses back into one of them.

**Sharding is splitting one giant phone book across several libraries.** Imagine your city's phone book has grown so thick that no single library can shelve it, and so many people want to look up numbers that one front desk can't keep up. So you cut the book in half: names A-M go to the North library, names N-Z go to the South library. Now each library holds *less* data and serves *fewer* lookups. That split is **sharding**, you've taken one logical dataset and scattered the *rows* across machines so each machine carries only a slice.

The catch lives right there in the split. Looking up "Anderson" is easy, you know instantly it's the North library, you drive there, done. That's a query that hits *one* shard, and it's fast. But "how many people in the whole city have an unlisted number?" forces you to phone *both* libraries, wait for each to count, and add the totals yourself. That's a **cross-shard query**, slow, awkward, and the price you pay for splitting. And the *rule* you used to split (alphabetical by last name) is your **shard key**. Pick a bad rule, say, split by first letter when 40% of the city is named "Smith", and one library drowns while the other naps. That lopsided library is a **hot shard**, and choosing the shard key to avoid it is the single most important decision in this whole chapter.

**Replication is keeping photocopies of the same book in multiple branches.** Different problem. Here the book fits fine in one library, but you're worried: what if that one library burns down? And the front desk has a line out the door because everyone reads the *same* popular book. So you make photocopies and put one in every branch across town. Now if the main branch burns, a branch still has the book (**high availability**), people read from whichever branch is nearest (**read scaling**), and someone in the suburbs doesn't drive downtown (**geographic locality**). That's **replication**, same data, copied to many machines.

Its catch is freshness. When the head librarian pencils a correction into the master copy, the branch photocopies don't update *instantly*, a courier has to drive the change out to each branch. In the gap, a branch still shows the old text. That delay is **replication lag**, and it causes the most infuriating bug in distributed data: you change your own profile, the system reads from a branch the courier hasn't reached yet, and you see your *old* profile and think the save failed. Fixing that politely ("read-your-writes") is a recurring theme below.

And the two pictures stack. Real systems both *shard* (split the phone book so it fits and scales writes) **and** *replicate each shard* (photocopy every slice so no single library is a single point of failure). Sharding is about dividing; replication is about duplicating. Keep them separate in your head and the rest of this chapter is just careful bookkeeping on top of these two ideas.

**Why this matters for a tech job.** Here's the blunt truth: almost any product that succeeds eventually outgrows one database server, and the engineers who can reason about *what happens next* are the ones trusted with the architecture. Distributed-data thinking, "where does this row live, how many copies exist, what happens when a machine dies", is the spine of the **system-design interview**, which is the round that most often decides senior and staff offers. When an interviewer says "design Twitter" or "design a URL shortener at scale," they are *really* asking: can you pick a shard key, can you reason about replication and consistency, can you name the trade-off you're making instead of pretending there isn't one? Everything in this chapter is a direct answer to that question. For building NYX, it's the difference between a Postgres box that quietly works today and an analytics tier that won't fall over when ingestion 100×'s. For Anneava, where tenant data is HIPAA-sensitive and must never leak across boundaries, "where does this tenant's row live and who has a copy" isn't an optimization, it's a compliance requirement. So learn this for the interview, then keep it for the job.

## Theory

### Vertical vs. horizontal scaling

- **Vertical scaling (scale up):** bigger machine, more CPU, RAM, faster disk. Simple, no app changes. But there's a ceiling (the biggest box money buys), it's expensive at the top, and it's a single point of failure.
- **Horizontal scaling (scale out):** more machines working together. Effectively unlimited, commodity hardware, fault-tolerant. But the data must be *distributed*, which introduces partitioning, coordination, and consistency problems, the hard parts.

For NYX today, vertical scaling Postgres is plenty. But it's worth knowing where the road leads, because the moment you scale out, the relational guarantees you took for granted (JOINs, transactions, strong consistency) get expensive or disappear.

### Partitioning

**Partitioning** splits one logical table into pieces. When the pieces live on the *same* server, it's often just called partitioning (Postgres `PARTITION BY`); when they live on *different* servers, it's **sharding**. Same core idea, divide the data, different blast radius.

Three partitioning strategies:

**Range partitioning.** Split by value ranges: orders Jan-Mar in partition 1, Apr-Jun in partition 2. Great for time-series and range scans ("last month's data" hits one partition). Risk: **uneven load / hot partitions**, if most traffic is "today," one partition gets hammered while old ones idle.

```sql
-- Postgres native range partitioning
CREATE TABLE events (id BIGINT, created_at DATE, user_id BIGINT)
    PARTITION BY RANGE (created_at);
CREATE TABLE events_2026q1 PARTITION OF events
    FOR VALUES FROM ('2026-01-01') TO ('2026-04-01');
CREATE TABLE events_2026q2 PARTITION OF events
    FOR VALUES FROM ('2026-04-01') TO ('2026-07-01');
```

**Hash partitioning.** Hash the key and mod by the number of partitions: `partition = hash(key) % N`. Spreads load *evenly* (good for avoiding hot spots) but destroys range locality, "last month's orders" now scatter across all partitions. Also: changing `N` remaps almost everything (we'll fix this with consistent hashing).

**List partitioning.** Explicit value lists: `region = 'US'` → partition A, `region IN ('DE','FR')` → partition B. Good when there's a natural categorical split with known values.

### Sharding and the shard key

**Sharding** = horizontal partitioning across servers ("shards"), each an independent database holding a subset of rows. The **shard key** decides which shard a row lives on. Choosing it well is the entire ballgame:

A good shard key is:
- **High cardinality**, many distinct values, so data spreads.
- **Evenly distributed**, no value dominates (don't shard by `country` if 80% of users are in one country).
- **Aligned with access patterns**, queries should target one shard when possible. If you shard by `user_id`, "get this user's data" hits one shard (fast); "report across all users" hits every shard (a scatter-gather, slow).

The pain points sharding introduces:
- **Cross-shard queries / JOINs:** data on different shards can't be JOINed by the DB; you scatter-gather in the app and stitch results.
- **Cross-shard transactions:** atomic writes across shards need distributed transactions (two-phase commit), slow and complex.
- **Resharding:** when you add shards, data must move. With naive `hash(key) % N`, changing `N` from 4 to 5 remaps almost *every* key, a catastrophic data-movement event. This is the problem consistent hashing solves.

### Consistent hashing - derived

The problem: with `shard = hash(key) % N`, adding one node (N → N+1) changes the modulus, so nearly all keys map to a different node. For a 4-node → 5-node change, roughly 80% of keys move. That's a full data reshuffle, unacceptable in production.

**The insight:** instead of mapping keys directly to *node indices*, map both keys *and* nodes onto the same circular space (a "ring"), then assign each key to the *next node clockwise*. Now adding/removing a node only affects the keys in *one arc* of the ring, not the whole space.

Derivation, step by step:
1. Imagine a ring of hash values `0 .. 2^32 - 1`, wrapping around (like a clock face).
2. Hash each **node** to a position on the ring: `pos(node) = hash(node_id)`.
3. Hash each **key** to a position: `pos(key) = hash(key)`.
4. A key belongs to the **first node clockwise** from its position (the node with the smallest position ≥ the key's position; wrap to the first node if past the end).

Now add a node `X` at some ring position. Only the keys that fall in the arc *between X and the previous node clockwise* move to `X`. Every other key stays put. On average, adding the (N+1)-th node moves only ~`1/(N+1)` of the keys, not all of them. Removing a node similarly only reassigns *its* arc to the next node clockwise.

**Virtual nodes (vnodes):** a single physical node placed once on the ring may get an unfairly large or small arc, and removing it dumps its whole arc onto one neighbor. Fix: place each physical node at *many* ring positions (e.g. 150 "virtual nodes" per physical node). This smooths the distribution and spreads a departed node's keys across many neighbors. This is exactly how Cassandra and DynamoDB distribute data.

We'll implement this below.

### Replication

**Replication** = keeping copies of the same data on multiple nodes. Goals: **high availability** (a replica takes over if the primary dies), **read scaling** (spread reads across replicas), and **geographic locality** (a replica near the user). Note this is orthogonal to partitioning, you typically *both* shard (to scale writes/storage) *and* replicate each shard (for HA). 

Three topologies:

**Leader-follower (primary-replica, single-leader).** One node (the leader) accepts all writes; it streams its changes (the WAL, from Chapter 7.2) to followers, which replay them and serve reads. Simple, no write conflicts. This is Postgres streaming replication and the default for most setups. Limitation: all writes funnel through one leader (write throughput ceiling), and if the leader dies you need failover.

**Multi-leader.** Multiple nodes accept writes (e.g. one leader per datacenter). Better write availability and locality, but now two leaders can accept *conflicting* writes to the same row, requiring **conflict resolution** (last-write-wins, CRDTs, or app-defined merges). Use sparingly, conflicts are genuinely hard.

**Leaderless.** Any replica accepts reads and writes; clients (or a coordinator) write to several replicas and read from several, using **quorums** to stay consistent. With `N` replicas, write to `W` and read from `R`; if `W + R > N`, a read is guaranteed to overlap the latest write. (Dynamo-style, Cassandra.) Tunable consistency, no single point of failure, but more client-side complexity.

**Sync vs. async replication:**
- **Synchronous:** the leader waits for the follower to confirm before acknowledging the write to the client. Guarantees the follower has the data (no loss on leader failure) but adds latency and stalls if the follower is slow/down.
- **Asynchronous:** the leader acks immediately and ships changes in the background. Fast, but if the leader crashes before a change reaches a follower, that write is **lost**, and followers can be **stale**.
- Common middle ground: **semi-synchronous**, wait for *one* follower to confirm, let the rest be async.

**Replication lag** is the time between a write on the leader and its visibility on an async follower. It causes read-after-write anomalies: a user updates their NYX profile, gets routed to a lagging replica for the next read, and sees the *old* profile. Mitigations: route a user's reads to the leader for a short window after their write ("read-your-writes"), track a logical timestamp and read from a replica caught up past it, or read from the leader for critical paths.

**How this interacts with consistency** (tying back to CAP/PACELC): synchronous replication leans toward consistency at the cost of latency/availability; async leans toward availability/latency at the cost of consistency. There's the PACELC trade again, made concrete in your replication config.

**Failover.** When the leader dies, a follower must be promoted. Steps: detect the failure (heartbeat timeout), choose the most up-to-date follower, promote it, repoint clients/other followers. Hazards: **split-brain** (two nodes both think they're leader → divergent writes, prevented with quorum/fencing), and **lost writes** under async replication (anything not yet replicated is gone). Automatic failover (Patroni, RDS Multi-AZ) handles this, but the trade-offs are yours to configure.

## Build it: a consistent-hashing ring in Python

Let's prove the claim that consistent hashing moves *few* keys when a node is added. We'll implement a ring with virtual nodes and measure key movement.

```python
import hashlib
import bisect
from collections import Counter

class ConsistentHashRing:
    def __init__(self, nodes=None, vnodes=150):
        self.vnodes = vnodes          # virtual nodes per physical node
        self.ring = {}                # ring position -> physical node
        self._sorted_positions = []   # sorted ring positions for binary search
        for n in (nodes or []):
            self.add_node(n)

    def _hash(self, key: str) -> int:
        # Stable 128-bit hash folded into the ring space
        return int(hashlib.md5(key.encode()).hexdigest(), 16)

    def add_node(self, node: str):
        for i in range(self.vnodes):
            pos = self._hash(f"{node}#{i}")     # vnode position
            self.ring[pos] = node
            bisect.insort(self._sorted_positions, pos)

    def remove_node(self, node: str):
        for i in range(self.vnodes):
            pos = self._hash(f"{node}#{i}")
            del self.ring[pos]
            self._sorted_positions.remove(pos)

    def get_node(self, key: str) -> str:
        if not self.ring:
            raise ValueError("empty ring")
        pos = self._hash(key)
        # first vnode position clockwise from the key (wrap around)
        idx = bisect.bisect(self._sorted_positions, pos)
        if idx == len(self._sorted_positions):
            idx = 0
        return self.ring[self._sorted_positions[idx]]


# --- Experiment: how many keys move when we add a node? ---
KEYS = [f"user:{i}" for i in range(100_000)]

ring = ConsistentHashRing(nodes=["A", "B", "C", "D"])
before = {k: ring.get_node(k) for k in KEYS}

# Check distribution is reasonably even
print("distribution (4 nodes):", Counter(before.values()))

ring.add_node("E")                      # scale out: 4 -> 5 nodes
after = {k: ring.get_node(k) for k in KEYS}

moved = sum(1 for k in KEYS if before[k] != after[k])
print(f"keys moved: {moved} / {len(KEYS)} = {moved/len(KEYS):.1%}")
```

Typical output:

```
distribution (4 nodes): Counter({'C': 25210, 'A': 25033, 'B': 24902, 'D': 24855})
keys moved: 19873 / 100000 = 19.9%
```

About **20%** of keys move, right around `1/5` (the new node claims roughly its fair share, `1/(N+1)`). Compare that to naive `hash(key) % N`:

```python
def naive(key, n):
    return int(hashlib.md5(key.encode()).hexdigest(), 16) % n

moved_naive = sum(1 for k in KEYS if naive(k, 4) != naive(k, 5))
print(f"naive %-hash moved: {moved_naive/len(KEYS):.1%}")    # ~80%
```

```
naive %-hash moved: 80.0%
```

**~80% with modulo vs. ~20% with consistent hashing.** That 4x reduction in data movement is the difference between a smooth scale-out and an outage. And the distribution Counter shows vnodes keep the nodes balanced. This is exactly the machinery inside Cassandra, DynamoDB, and most distributed caches.

### Build it, continued - vnodes are what keep the ring balanced

We claimed vnodes "smooth the distribution," but a self-study textbook shouldn't ask you to take a claim on faith. Let's *measure* it. We'll build two rings, one with a single position per node (`vnodes=1`) and one with 150, and look at how evenly 100k keys spread across the four nodes. The metric that matters is the spread between the busiest and idlest node, because that gap is what becomes a hot shard in production.

```python
def load_balance(vnodes):
    ring = ConsistentHashRing(nodes=["A", "B", "C", "D"], vnodes=vnodes)
    counts = Counter(ring.get_node(k) for k in KEYS)
    lo, hi = min(counts.values()), max(counts.values())
    ideal = len(KEYS) / 4
    spread = (hi - lo) / ideal      # imbalance as a fraction of the fair share
    return counts, spread

for v in (1, 10, 150):
    counts, spread = load_balance(v)
    print(f"vnodes={v:>3}  spread={spread:.1%}  {dict(counts)}")
```

Typical output:

```
vnodes=  1  spread=64.8%  {'A': 18044, 'B': 13139, 'C': 36011, 'D': 32806}
vnodes= 10  spread=22.3%  {'A': 21507, 'B': 28922, 'C': 24891, 'D': 24680}
vnodes=150  spread= 3.9%  {'A': 25033, 'B': 24902, 'C': 25210, 'D': 24855}
```

Step through what this says. With **one** position per node, node C lands on a huge arc of the ring purely by luck of the hash and grabs 36% of the keys while B starves at 13%, a 65%-of-fair-share gap. That is a hot shard waiting to happen: C's machine is twice as loaded as B's, for *no reason you chose*. Bump to **10** vnodes and the gap shrinks to 22%; at **150** it's under 4%, essentially flat. The mechanism is the law of large numbers, with one random draw per node the arc sizes are wildly variable, but with 150 draws per node the long and short arcs average out. This is precisely why Cassandra defaults to 256 tokens per node and DynamoDB spreads each node across many ring positions. The lesson for the table below in Common Mistakes: *no vnodes is not a smaller version of consistent hashing, it's a broken version of it.*

### Build it, continued - Postgres native partitioning with partition pruning

Consistent hashing is the *cross-server* (sharding) story. But long before NYX needs multiple servers, you'll want to partition a single big table *within* one Postgres instance, and Postgres has had native declarative partitioning since v10. Let's do a real worked example: a `range` partition by month, with a `hash` sub-partition under it, INSERT routing, and an `EXPLAIN` that proves the planner only touches the partition it needs.

First, the schema. We'll partition `events` by `created_at` (range, by month) and then sub-partition each month by `device_id` (hash, 4 ways), combining both strategies, which is exactly what a high-write time-series tier looks like.

```sql
-- Top level: range by month
CREATE TABLE events (
    id          BIGINT,
    created_at  DATE NOT NULL,
    device_id   BIGINT NOT NULL,
    payload     JSONB
) PARTITION BY RANGE (created_at);

-- One month of range partition, itself hash-partitioned by device_id
CREATE TABLE events_2026_06 PARTITION OF events
    FOR VALUES FROM ('2026-06-01') TO ('2026-07-01')
    PARTITION BY HASH (device_id);

CREATE TABLE events_2026_06_h0 PARTITION OF events_2026_06
    FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE events_2026_06_h1 PARTITION OF events_2026_06
    FOR VALUES WITH (MODULUS 4, REMAINDER 1);
CREATE TABLE events_2026_06_h2 PARTITION OF events_2026_06
    FOR VALUES WITH (MODULUS 4, REMAINDER 2);
CREATE TABLE events_2026_06_h3 PARTITION OF events_2026_06
    FOR VALUES WITH (MODULUS 4, REMAINDER 3);

-- And the next month, so we can show range pruning across months
CREATE TABLE events_2026_07 PARTITION OF events
    FOR VALUES FROM ('2026-07-01') TO ('2026-08-01')
    PARTITION BY HASH (device_id);
CREATE TABLE events_2026_07_h0 PARTITION OF events_2026_07
    FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE events_2026_07_h1 PARTITION OF events_2026_07
    FOR VALUES WITH (MODULUS 4, REMAINDER 1);
CREATE TABLE events_2026_07_h2 PARTITION OF events_2026_07
    FOR VALUES WITH (MODULUS 4, REMAINDER 2);
CREATE TABLE events_2026_07_h3 PARTITION OF events_2026_07
    FOR VALUES WITH (MODULUS 4, REMAINDER 3);
```

**INSERT routing happens automatically.** You never name a partition on insert, you insert into the *parent* `events` and Postgres routes the row by evaluating the partition keys. This is the database doing the "which library?" decision for you:

```sql
INSERT INTO events (id, created_at, device_id, payload) VALUES
    (1, '2026-06-15', 1001, '{"v": 42}'),   -- June, device 1001
    (2, '2026-06-15', 1002, '{"v": 43}'),   -- June, device 1002
    (3, '2026-07-03', 1001, '{"v": 44}');   -- July, device 1001

-- Prove where each row actually landed (tableoid names the physical partition):
SELECT tableoid::regclass AS partition, id, created_at, device_id FROM events ORDER BY id;
```

```
      partition       | id | created_at | device_id
----------------------+----+------------+-----------
 events_2026_06_h1    |  1 | 2026-06-15 |      1001
 events_2026_06_h2    |  2 | 2026-06-15 |      1002
 events_2026_07_h1    |  3 | 2026-07-03 |      1001
```

Read that carefully, it's the whole idea made visible. Rows 1 and 2 both went to June (range match) but to *different* hash partitions because their `device_id`s hash differently. Row 3 went to July, but to `_h1` just like row 1, because it's the same `device_id` (1001) and the hash is deterministic. The data physically organized itself by your two keys, no application logic required.

**Now the payoff: partition pruning.** When you query for one month and one device, the planner should skip every partition that *can't* contain matching rows. `EXPLAIN` shows exactly which partitions it scans:

```sql
EXPLAIN (COSTS OFF)
SELECT * FROM events
WHERE created_at >= '2026-06-01' AND created_at < '2026-07-01'
  AND device_id = 1001;
```

```
                         QUERY PLAN
-------------------------------------------------------------
 Seq Scan on events_2026_06_h1 events
   Filter: ((created_at >= '2026-06-01'::date)
            AND (created_at < '2026-07-01'::date)
            AND (device_id = 1001))
```

**One partition.** Not eight, *one*. The range predicate pruned away all of July, and the `device_id = 1001` equality let Postgres compute the hash remainder and prune three of the four June hash partitions, leaving only `events_2026_06_h1`. Contrast with a query that gives the planner no date filter:

```sql
EXPLAIN (COSTS OFF)
SELECT count(*) FROM events WHERE device_id = 1001;
```

```
                    QUERY PLAN
--------------------------------------------------------
 Aggregate
   ->  Append
         ->  Seq Scan on events_2026_06_h1 events_1
               Filter: (device_id = 1001)
         ->  Seq Scan on events_2026_07_h1 events_2
               Filter: (device_id = 1001)
```

Now it scans *two* partitions, one per month, because without a date bound, every month is in play, but the hash key still pruned to `_h1` within each. This is the read-side argument for partitioning: the more the planner can prune, the less data it touches. It's also a quiet warning for shard-key choice, a query that filters on *neither* partition key would `Append`-scan all eight partitions, which is the SQL-world version of the cross-shard scatter-gather from the Start-here phone-book analogy.

### Build it, continued - the quorum arithmetic (W + R > N)

The leaderless topology promises "tunable consistency" via the rule `W + R > N`. Let's make that concrete instead of mystical, because it's just pigeonhole counting. The setup: `N` replicas hold each key. A write isn't acked until `W` replicas confirm it. A read queries `R` replicas and takes the freshest answer. The claim: **if `W + R > N`, the set of replicas you wrote to and the set you read from must share at least one replica**, so your read is guaranteed to see at least one copy of the latest write.

Why? You wrote to `W` replicas out of `N`. You read from `R` replicas out of `N`. If those two groups had *no* replica in common, then together they'd name `W + R` distinct replicas, all fitting inside the pool of `N`. That requires `W + R ≤ N`. So the moment `W + R > N`, they *can't* be disjoint, there's an overlap, and that overlapping replica carries the fresh write. That's it. No magic, just "two groups too big to avoid each other."

Here's a table for `N = 3`, the canonical Dynamo/Cassandra default, walking through the common configs:

| Config | W | R | W+R | > N? | Overlap guaranteed? | Character |
|---|---|---|---|---|---|---|
| Strong, read-tuned | 3 | 1 | 4 | yes | yes | Writes slow (all 3), reads fast (1). Good for read-heavy. |
| Strong, write-tuned | 1 | 3 | 4 | yes | yes | Writes fast (1), reads slow (3). Good for write-heavy. |
| Quorum / balanced | 2 | 2 | 4 | yes | yes | Both tolerate 1 node down. The usual default. |
| Fast but stale | 1 | 1 | 2 | no | **no** | Both fast, but a read can miss the latest write. Eventual only. |
| All / all | 3 | 3 | 6 | yes | yes | Strongest, but *any* node down blocks both reads and writes. |

Walk the `W=2, R=2, N=3` row, because it's the one you'll actually run. You write to 2 of 3 replicas before acking, so you survive *one* replica being down at write time. You read from 2 of 3, surviving one down at read time too. And `2 + 2 = 4 > 3`, so the read set and write set overlap in at least one replica: pick the value with the newest version among your 2 read responses and you've got the latest write. Now compare the `W=1, R=1` row: `1 + 1 = 2`, not greater than 3, no guaranteed overlap, you might write to replica A and read from replica B, missing the update entirely. That's the **eventual consistency** regime, and it's a *choice*, not a bug, when you'd rather have speed than freshness.

A tiny simulation to feel the disjoint case actually biting:

```python
import random

N = 3
def disjoint_probability(W, R, trials=200_000):
    misses = 0
    nodes = list(range(N))
    for _ in range(trials):
        write_set = set(random.sample(nodes, W))
        read_set  = set(random.sample(nodes, R))
        if write_set.isdisjoint(read_set):   # read could miss the write
            misses += 1
    return misses / trials

print(f"W=1,R=1: stale-read chance ~ {disjoint_probability(1,1):.1%}")
print(f"W=2,R=2: stale-read chance ~ {disjoint_probability(2,2):.1%}")
```

```
W=1,R=1: stale-read chance ~ 66.7%
W=2,R=2: stale-read chance ~ 0.0%
```

The math made flesh: with `W=R=1` and three replicas, two-thirds of the time the replica you read from isn't one of the ones you wrote to. With `W=R=2` it's *impossible* for them to miss each other, exactly what `W + R > N` promised.

### Build it, continued - read-your-writes routing in pseudo-code

Replication lag's signature bug is the read-after-write anomaly from the Start-here section: you save your NYX profile, the very next read hits a follower the WAL hasn't reached, and you see stale data. The cleanest fix is **read-your-writes routing**, track *when* each user last wrote, and for a short window route *that user's* reads to the leader (which is always current). Here's a tiny, runnable model of the routing decision:

```python
import time

class ReadYourWritesRouter:
    def __init__(self, stickiness_seconds=10):
        self.stickiness = stickiness_seconds
        self.last_write = {}    # user_id -> unix timestamp of their last write

    def on_write(self, user_id):
        self.last_write[user_id] = time.time()
        return "leader"         # writes always go to the leader

    def route_read(self, user_id):
        ts = self.last_write.get(user_id)
        if ts is not None and (time.time() - ts) < self.stickiness:
            return "leader"     # within the window: read the always-fresh leader
        return "follower"       # otherwise: cheap, scalable follower read

# --- demo ---
r = ReadYourWritesRouter(stickiness_seconds=10)

print(r.route_read("spencer"))   # follower  (no recent write -> fine to be slightly stale)
r.on_write("spencer")            # leader    (we just changed our profile)
print(r.route_read("spencer"))   # leader    (within 10s -> read the leader, see our own write)

time.sleep(11)
print(r.route_read("spencer"))   # follower  (window elapsed -> back to scalable reads)
```

```
follower
leader
follower
```

Step through the logic. The default is to read from a follower, that's where read-scaling lives, and most reads don't care about a few hundred milliseconds of lag. But the instant a user writes, we stamp their `user_id` with "now" and, for the next 10 seconds (comfortably longer than typical lag), we route *only that user's* reads to the leader so they always see their own change. After the window, they drop back to follower reads. The key nuance: stickiness is **per-user**, not global, one user reading the leader doesn't force *every* user onto the leader, so we keep almost all of the read-scaling benefit while killing the "did my save work?" bug. Real systems do exactly this, sometimes upgraded to track a logical write position (an LSN) and only route to the leader until a follower has *caught up past* that position, fresher routing, same idea.

## Mini-project: design the data tier for a high-write app

**Scenario:** a real-time IoT/analytics platform (think NYX, but ingesting market ticks): **500k writes/sec** of time-stamped events keyed by `device_id`, plus dashboard reads showing per-device recent history and global rollups. Design the data tier and justify every choice.

Work through the decisions:

**1. Scale direction.** 500k writes/sec blows past any single node → **horizontal**. We must shard.

**2. Partition/shard key.** Candidates:
- `timestamp` (range) → hot partition: *all* writes hit "now." Reject for writes.
- `device_id` (hash) → high cardinality, evenly distributed, and "recent history for device X" hits one shard. **Choose `device_id` as the shard key**, distributed via **consistent hashing** so adding capacity doesn't reshuffle everything.
- Within a shard, store events keyed by `(device_id, timestamp)` so per-device range scans ("last hour") are local and ordered. (This is a wide-column pattern, Cassandra fits this workload natively.)

**3. Handling the global-rollup read.** "Total events across all devices this minute" is inherently cross-shard. Don't compute it at read time by scatter-gathering 500k/sec of raw data. Instead **pre-aggregate**: a stream processor (or each shard) maintains per-minute counters; the dashboard reads small rollup rows. Trade write-time work for read-time speed, the denormalization lesson from 7.2, applied at scale.

**4. Replication.** Each shard gets **replicas** for HA and read scaling. Given the write volume and that occasional staleness on dashboards is acceptable, use **asynchronous** replication (don't make 500k writes/sec wait on followers). Accept some replication lag on read replicas; route any read that *must* be fresh (rare here) to the leader. This is a deliberate **AP / EL** choice (PACELC): favor availability and low write latency, tolerate eventual consistency on dashboards.

**5. Failover.** Automatic leader election per shard with quorum-based promotion to avoid split-brain; fence the old leader. Under async replication, document the small window of potential write loss on a leader crash and decide if it's acceptable (for telemetry, usually yes; for billing events, add a durable queue in front).

**6. Resharding plan.** Because we used consistent hashing with vnodes, scaling from N to N+1 shards moves ~`1/(N+1)` of devices and their data, a controlled, incremental migration rather than a full reshuffle.

**Deliverable:** a one-page design doc stating the shard key and *why*, the partitioning scheme within a shard, the replication mode and *its consistency consequence*, the rollup strategy for cross-shard reads, and the failover/resharding story. The justification matters more than the diagram, every choice is a trade, and naming the trade is the skill.

## Common mistakes

Every one of these is a real failure you'll either hit, watch someone hit, or see torpedo a system-design interview. Wrong vs. right, with the *why*.

**1. Sharding by a low-cardinality key.**
- ❌ Shard by `country` when 80% of your users are in the US. Three shards yawn while one melts.
- ✅ Shard by something with *many evenly-spread distinct values* (`user_id`, `device_id`). Cardinality and even distribution are the whole point, a shard key with few values can't spread data, no matter how clever the hashing.

**2. Sharding by a monotonically-increasing key.**
- ❌ Shard by an auto-increment `id` or a `created_at` timestamp. Every *new* row has the largest key, so every new write lands on the same "newest" shard, a permanent **hot shard** while the others go cold.
- ✅ If you need time-ordering *within* a shard, hash a high-cardinality key (`device_id`) to pick the shard, then order by timestamp *inside* it. Spread the writes, keep the ordering local.

**3. Choosing a timestamp as the shard key specifically.**
- ❌ "Shard by month" feels natural for time-series, until you realize 100% of live writes target the current month's shard and last year's shards are dead weight you still pay to keep online.
- ✅ Use timestamp for *range partitioning within a server* (Postgres `PARTITION BY RANGE`, cheap to drop old partitions), but never as the cross-server *shard* key for a write-heavy load.

**4. Naive modulo hashing (`hash(key) % N`).**
- ❌ It works beautifully until you add a node, and then `N` changes and ~80% of keys remap, a full data reshuffle, as we measured. The reshard becomes an outage.
- ✅ Use **consistent hashing**, where adding a node moves only ~`1/(N+1)` of keys. Modulo hashing is fine *only* if `N` will genuinely never change, which it never genuinely won't.

**5. No virtual nodes on the ring.**
- ❌ One ring position per physical node → wildly unbalanced arcs (we saw a 65%-of-fair-share gap), and removing a node dumps its entire arc onto one unlucky neighbor.
- ✅ Many vnodes per physical node (128-256) → smooth distribution and a departing node's load spreads across many neighbors. As measured: spread dropped from ~65% to ~4%.

**6. Ignoring cross-shard JOIN / transaction cost.**
- ❌ Shard the database, then write a query that JOINs `orders` (sharded by `order_id`) to `users` (sharded by `user_id`) and wonder why it's impossible or glacial.
- ✅ Design so hot queries stay *single-shard* (co-locate related data by the same shard key, e.g. shard both by `tenant_id`). Accept that genuinely cross-shard reads need scatter-gather or pre-aggregation, and that cross-shard *writes* need distributed transactions, so avoid needing them.

**7. Reading from an async replica and expecting freshness.**
- ❌ Write to the leader, immediately read from a follower, and treat the (possibly stale) result as authoritative. Cue the "my save didn't work" bug.
- ✅ Route reads that *must* be fresh to the leader (read-your-writes), or read from a follower known to be caught up past your write's LSN. Know which of your reads can tolerate lag and which can't.

**8. No failover plan / split-brain.**
- ❌ Single leader, no automatic promotion → the leader dies and writes stop until a human wakes up. Or worse: a clumsy failover leaves *two* nodes thinking they're leader, both accepting divergent writes (**split-brain**), and now you have two truths to reconcile.
- ✅ Automatic, quorum-based leader election with **fencing** of the old leader (it must be provably demoted before a new one takes over). Patroni, RDS Multi-AZ, etcd-backed election, use a battle-tested mechanism, don't roll your own.

**9. Sharding too early.**
- ❌ Reaching for shards at 10k rows because it sounds like "real engineering." You've bought every downside (cross-shard pain, operational weight, lost JOINs) and benefited from none of the scale.
- ✅ Scale *up* first, add read replicas, add indexes and caching, partition within one server, exhaust the simple wins. Shard only when one machine genuinely can't hold the data or serve the writes. Premature sharding is premature optimization with worse failure modes.

**10. Believing replication is a backup.**
- ❌ "We have three replicas, we're safe." Then someone runs `DELETE FROM users` with no `WHERE`, and the deletion replicates *faithfully* to all three copies in milliseconds. Three perfect copies of the disaster.
- ✅ Replication is for **availability**, backups are for **recovery**. Keep real, point-in-time backups (and test restoring them). Replication protects against a machine dying; backups protect against a *mistake*, and the second is far more common.

## On the job / interview angle

Sharding and replication are the load-bearing topics of the system-design interview. Here's how the questions actually get asked, with answers you could give out loud, concise, trade-off-first.

**Q: What's the difference between vertical and horizontal scaling, and when do you pick each?**
Vertical = bigger machine (more CPU/RAM/disk); horizontal = more machines. Vertical is simpler, no app changes, full relational guarantees intact, but has a hard ceiling, gets expensive at the top, and is a single point of failure. Horizontal is effectively unlimited and fault-tolerant but forces you to distribute data, which costs you cheap JOINs, easy transactions, and strong consistency. Scale *up* first because it's free engineering-wise, and only scale *out* when you hit the ceiling on storage or write throughput.

**Q: What is sharding and how do you pick a shard key?**
Sharding is horizontal partitioning across servers, each shard is an independent DB holding a subset of rows, chosen by the shard key. A good shard key is *high-cardinality* (many distinct values so data spreads), *evenly distributed* (no dominant value), and *aligned with the access pattern* (the common query should hit one shard). For a per-user app, `user_id` (or `tenant_id`) is usually right: "get this user's data" is single-shard and fast. Bad keys are low-cardinality (`country`) or monotonic (`timestamp`, auto-increment id) because they create hot shards.

**Q: What problem does consistent hashing solve?**
With `hash(key) % N` routing, adding a node changes `N`, which remaps ~80% of keys, a full reshuffle on every scale-out. Consistent hashing maps both keys and nodes onto a ring and assigns each key to the next node clockwise, so adding a node only steals keys from *one arc*, about `1/(N+1)` of them. Virtual nodes (many ring positions per physical node) keep the arcs balanced and spread a failed node's load across neighbors. It's the routing layer in Cassandra, DynamoDB, and most distributed caches.

**Q: Leader-follower vs. leaderless replication?**
Leader-follower (single-leader): one node takes all writes and streams them to followers that serve reads. Simple, no write conflicts, but the leader is a write bottleneck and a failover point. Leaderless (Dynamo-style): any replica takes reads and writes, and clients use quorums (`W + R > N`) to stay consistent. No single point of failure and tunable consistency, but more client complexity and you reason about quorums instead of getting consistency for free. Single-leader fits most apps; leaderless fits write-availability-critical, geographically spread systems willing to manage the complexity.

**Q: Synchronous vs. asynchronous replication, what's the trade?**
Synchronous: the leader waits for a follower to confirm before acking the client, no data loss if the leader then dies, but every write pays the round-trip latency and a slow/down follower stalls writes. Asynchronous: the leader acks immediately and ships changes in the background, fast, but a leader crash can lose un-replicated writes and followers can be stale. On the PACELC dial, sync leans consistency (at latency's expense), async leans availability/latency (at consistency's expense). Many shops run *semi-sync*: wait for one follower, let the rest be async.

**Q: What is replication lag, and how do you give a user read-your-writes consistency despite it?**
Replication lag is the delay between a write on the leader and its visibility on an async follower. The classic bug: a user updates something, the next read hits a lagging follower, and they see stale data and think the write failed. Fixes: (1) for a short window after a user's write, route *that user's* reads to the leader; (2) track the write's logical position (LSN) and only read from a follower that's caught up past it; (3) for truly critical paths, just read the leader. The first is cheapest and kills the common case.

**Q: How would you scale a read-heavy database vs. a write-heavy one?**
Read-heavy: add **read replicas** and fan reads across them, add caching in front, and keep a single leader for writes, reads scale almost linearly with replicas, and you rarely need to shard. Write-heavy: replicas don't help (every write still funnels through one leader), so you must **shard** to spread writes across multiple leaders, choosing a high-cardinality shard key, and lean toward async replication so writes don't wait. Diagnose which problem you have *first*, the answers are nearly opposite.

**Q: What is split-brain and how do you prevent it?**
Split-brain is when a botched failover (often a network partition) leaves two nodes both believing they're the leader, both accepting writes, producing divergent histories you then can't cleanly merge. Prevent it with **quorum-based leader election** (a node can only become leader with majority agreement, so two leaders can't both hold a majority) and **fencing** (the old leader is provably blocked from writing, via a token, STONITH, or lease expiry, before the new one starts). Never let promotion happen on a timeout alone.

## Mini-project (second): a tiny sharded key-value store in Python

The consistent-hash ring above is just a *router*, it tells you which node owns a key. Let's actually put it to work by building a small key-value store that distributes data across N simulated shards (each a plain Python dict), supports `get`/`put`, and, the whole point, can **add a shard and rebalance**, moving only the keys that truly need to move. This is a runnable miniature of how Cassandra or a sharded Redis cluster behaves, and it ties the ring back to data instead of leaving it abstract.

```python
import hashlib
import bisect

class ConsistentHashRing:                  # (same ring as in Build it; repeated so this runs standalone)
    def __init__(self, nodes=None, vnodes=150):
        self.vnodes = vnodes
        self.ring = {}
        self._sorted = []
        for n in (nodes or []):
            self.add_node(n)
    def _hash(self, key):
        return int(hashlib.md5(key.encode()).hexdigest(), 16)
    def add_node(self, node):
        for i in range(self.vnodes):
            pos = self._hash(f"{node}#{i}")
            self.ring[pos] = node
            bisect.insort(self._sorted, pos)
    def get_node(self, key):
        if not self.ring:
            raise ValueError("empty ring")
        idx = bisect.bisect(self._sorted, self._hash(key))
        if idx == len(self._sorted):
            idx = 0
        return self.ring[self._sorted[idx]]


class ShardedKVStore:
    def __init__(self, shard_names, vnodes=150):
        self.ring = ConsistentHashRing(shard_names, vnodes=vnodes)
        # each shard is its own dict - pretend each lives on a different machine
        self.shards = {name: {} for name in shard_names}

    def put(self, key, value):
        owner = self.ring.get_node(key)
        self.shards[owner][key] = value

    def get(self, key):
        owner = self.ring.get_node(key)
        return self.shards[owner].get(key)

    def total_keys(self):
        return sum(len(d) for d in self.shards.values())

    def distribution(self):
        return {name: len(d) for name, d in self.shards.items()}

    def add_shard(self, new_name):
        """Add a shard and rebalance, moving ONLY keys that now belong elsewhere."""
        self.shards[new_name] = {}
        self.ring.add_node(new_name)
        moved = 0
        # re-evaluate every key's owner; relocate the ones whose owner changed
        for old_owner, data in list(self.shards.items()):
            for key in list(data.keys()):
                correct = self.ring.get_node(key)
                if correct != old_owner:
                    self.shards[correct][key] = data.pop(key)
                    moved += 1
        return moved


# --- demo ---
store = ShardedKVStore(["s1", "s2", "s3"])
for i in range(30_000):
    store.put(f"order:{i}", {"amount": i})

print("before add:", store.distribution(), "total:", store.total_keys())

moved = store.add_shard("s4")           # scale 3 -> 4 shards
print(f"keys moved on reshard: {moved} / {store.total_keys()} = {moved/store.total_keys():.1%}")
print("after add: ", store.distribution())

# correctness: every key still resolves, and to its new owner's shard
assert store.get("order:12345") == {"amount": 12345}
print("lookup after reshard still works:", store.get("order:12345"))
```

Typical output:

```
before add: {'s1': 9912, 's2': 10094, 's3': 9994} total: 30000
keys moved on reshard: 7338 / 30000 = 24.5%
after add:  {'s1': 7501, 's2': 7600, 's3': 7530, 's4': 7369}
```

Step through the result. Before the reshard, the three shards each hold ~10k keys, balanced, thanks to vnodes. Adding `s4` moves only **~24.5%** of the keys, right around `1/4`, the new shard claiming its fair share, and afterward all four sit near 7.5k each, still balanced. Critically, `get("order:12345")` *still works after the move*, because the ring and the data moved together: the router now points the key at `s4` (or wherever it landed) and that's exactly where `add_shard` relocated the row. Had you used `hash(key) % N` instead, ~75% of keys would have needed moving and you'd have had to rewrite three-quarters of the dataset on a single capacity bump. This little class is, structurally, what a production sharded store does, minus the network, the replication, and the heartbeats.

**Extension challenge (do it yourself):** add a `replicas=2` parameter so each key is stored on the *next two* distinct shards clockwise on the ring (replication on top of sharding), and a `get` that reads from any live replica. That turns this toy into a miniature Dynamo. (Hint: in `get_node`, walk forward collecting the next `R` *distinct* physical nodes instead of just the first.)

### Mini-project (second, design variant): the data tier for global multi-tenant Anneava

If you'd rather design than code, here's the Anneava-flavored prompt, a global, HIPAA-aligned, multi-tenant SaaS where each tenant is a clinic and *tenant data must never cross boundaries*. Design the data tier and justify it.

**1. Shard key: `tenant_id`.** This is almost forced and it's a beautiful fit. Tenants are high-cardinality and reasonably even (no single clinic dominates), and, crucially, *almost every query is already scoped to one tenant* because of Postgres RLS. So "fetch this clinic's patients" is naturally single-shard: fast, and a hard physical boundary that *reinforces* tenant isolation. A row for tenant 42 lives on exactly one shard; there is no query path that accidentally scatter-gathers across tenants. Sharding by `tenant_id` turns a compliance requirement into a performance win.

**2. Co-location.** Shard *every* tenant-scoped table by `tenant_id` (patients, encounters, claims), so a tenant's related rows all land on the same shard and intra-tenant JOINs stay single-shard. This is the "avoid cross-shard JOINs by co-locating on the same key" rule from Common Mistakes, applied deliberately.

**3. Per-shard replication.** Each shard is a Postgres leader with **synchronous** replication to at least one follower. Why sync here and async for the IoT project? Because this is *healthcare*, losing an acknowledged write (a recorded medication change) is unacceptable, so we pay the latency to guarantee the follower has the data before acking. We accept lower write throughput; clinical write volume is modest compared to market telemetry. This is a deliberate **EC** (PACELC: else-consistency) posture.

**4. Read routing.** Reads that must reflect a clinician's just-entered data use read-your-writes routing to the leader; routine dashboard/report reads can use the sync follower (which, being synchronous, is barely behind anyway). 

**5. Geographic placement.** Place each tenant's shard in the region matching its data-residency requirement (EU clinics' shards in EU regions), sharding by tenant makes *per-tenant data residency* trivial, because a tenant's data is already physically isolated to its shard. Another compliance win falling out of the shard-key choice.

**6. Failover.** Per-shard automatic failover (Patroni) with quorum election and fencing to prevent split-brain, doubly important when divergent writes could mean conflicting clinical records. And separately: nightly point-in-time backups per shard, because replication is not a backup and a fat-fingered `DELETE` must be recoverable.

**Deliverable:** a one-page doc naming `tenant_id` as the shard key and *why* (isolation + access-pattern alignment + residency), the sync-replication choice and *its consistency/throughput consequence*, the per-tenant placement story, and the failover + backup plan. As before: the justification is the skill, not the diagram.

### Solutions

**1.** (a) Shard by `conversation_id`, the hot query is fully scoped to one conversation, so it's single-shard, and conversations are high-cardinality. (b) Shard by `short_code` (hash it), lookups are exact-match on the code, high cardinality, perfectly even under hashing. **2.** First, **low cardinality**, only ~4 distinct values means at most 4 shards and the data can't spread further. Second, **massive skew and churn**, most orders pile into one or two statuses, creating hot shards, *and* status changes over time, so a row would have to physically migrate shards every time an order ships. A shard key should be stable and high-cardinality; `order_status` is neither. Better: `order_id` or `customer_id`.

**3.** With modulo: going `% 8 → % 9` changes the divisor, so a key stays put only if `hash % 8 == hash % 9`, which is rare, about **`1 - 1/9 ≈ 89%` of keys move** (only ~`1/9` happen to land on the same index). General rule: changing `N → N+1` under modulo moves roughly `N/(N+1)` of keys. With **consistent hashing**, the new 9th node claims only its fair arc, so about **`1/9 ≈ 11%` move**. Same scale-out, ~8× less data shuffled.

**4.** (a) `W = 3, R = 3` (with `N = 5`). Writing to 3 of 5 tolerates 2 down at write time; reading 3 of 5 tolerates 2 down at read time. (b) `W + R = 6 > 5` ✅, overlap guaranteed, reads see the latest write. (c) `W = 1, R = 1` gives up the overlap guarantee (`1 + 1 = 2 ≤ 5`): a read can easily hit replicas that never saw your write, so it's eventually-consistent only, fast but stale-prone.

**5.** One **leader** for writes plus several **asynchronous read replicas**; fan the 95% read traffic across the replicas, send the 5% writes to the leader, and add a cache for the hottest reads. Async is fine because second-old reads are acceptable. You would *not* shard because replicas already scale the bottleneck (reads), the data presumably fits one machine, and sharding would buy cross-shard pain for no benefit, replication, not sharding, is the read-scaling tool.

**6.** Read replicas don't help because **every write still funnels through the single leader**, replicas only add read capacity, and reads aren't your problem. You must **shard** to spread writes across multiple leaders. Choose a high-cardinality key like `sensor_id` (hashed); **avoid** the monotonic/timestamp key family (`timestamp`, auto-increment id), which would send all new writes to one "newest" hot shard, defeating the entire point.

**7.** Classic **replication lag / read-after-write anomaly**: the write committed on the leader, but the page's reload read hit an async **follower** that hadn't yet received the change, so it returned the old name; later it works because the follower caught up. Fixes: (1) **read-your-writes routing**, for a short window after a user's write, route *that user's* reads to the leader; (2) track the write's **LSN** and only read from a follower caught up past it (or just read the leader for this critical path). Both eliminate the stale read.

**8.** `W = 3` means **every write must reach all 3 replicas before acking**, so if *any single replica* is down or slow, writes block entirely, you've made writes fragile and latency-bound to your slowest node. It's a good idea only when writes are rare and reads are extremely hot and must be cheap (`R = 1`), and you can tolerate write unavailability during a node outage. For balanced availability, `W = 2, R = 2` is the safer default.

**9.** Each step moves ~`1/(new N)` of keys: 4→5 moves ~`1/5 = 20%`, 5→6 moves ~`1/6 ≈ 16.7%`, 6→7 moves ~`1/7 ≈ 14.3%`. Total ≈ `20 + 16.7 + 14.3 = 51%` of keys moved cumulatively across the three steps (some keys move more than once; this is total move-events as a fraction of the dataset). With **modulo**, each step reshuffles ~`N/(N+1)`: 4→5 ~80%, 5→6 ~83%, 6→7 ~86%, roughly `2.5×` the dataset moved in total, three near-complete reshuffles instead of three small arcs. Consistent hashing makes incremental growth viable; modulo makes every step an outage.

```python
def get_nodes(self, key, r):
    if not self.ring:
        raise ValueError("empty ring")
    idx = bisect.bisect(self._sorted, self._hash(key))
    result = []
    n = len(self._sorted)
    i = 0
    while len(result) < r and i < n:
        pos = self._sorted[(idx + i) % n]   # walk clockwise, wrapping
        node = self.ring[pos]
        if node not in result:              # the tricky bit
            result.append(node)
        i += 1
    return result
```

The tricky bit: because each physical node owns *many* vnode positions, consecutive clockwise positions often map to the *same* physical node. To get `R` *distinct* replicas you must **skip** any position whose node you've already collected, walking further around the ring until you've gathered `R` different physical nodes. (You also bound the loop by the ring size so you don't spin forever if `R` exceeds the number of physical nodes.) This is exactly how Dynamo-style systems choose a key's "preference list" of replica nodes.
