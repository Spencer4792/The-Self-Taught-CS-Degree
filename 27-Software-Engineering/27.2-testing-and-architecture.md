## Start here

The mental shift for this whole chapter: **working code is the floor, not the ceiling.** Anyone can write code that passes a manual smoke test once. The senior skills are: *proving* it works repeatedly and automatically (testing), *structuring* it so changes stay cheap (architecture), and *collaborating* so a team of people doesn't trip over each other (practices).

Two analogies worth keeping:

**Tests are the seatbelt that lets you drive fast.** Without tests, every change is terrifying, you tiptoe, you manually re-click everything, you ship on Fridays with dread. With a good test suite, you change boldly: the suite catches your mistakes in seconds, so you refactor freely (that's the whole engine behind 27.1's refactoring). Tests don't slow you down; *the lack of them* slows you down, because fear is slow. The faster you want to move, the more you need the seatbelt.

**Architecture is a city's zoning.** A small town with no zoning is fine, house next to shop next to factory, walk anywhere. But as it grows, the lack of structure becomes gridlock: you can't change the factory without disturbing the houses. Architecture is the discipline of deciding *what goes where and what's allowed to depend on what*, so the city can grow without everything tangling. Layers, the dependency rule, hexagonal, they're all zoning laws for code.

**Why this matters for a tech job.** Every team you'll join already has a test suite (or painfully wishes it did), an architecture (good or accidental), and a set of practices (a review culture, a git workflow, a way of estimating). Your value is measured by how well you operate *within* those, and how well you improve them. Interviews probe this directly: "how do you test this?", "design the architecture for X", "walk me through your code review process." On the job, the engineer who writes tests reflexively, who can navigate a codebase they didn't write, and who gives thoughtful reviews is the one who gets trusted with bigger things. This is the difference between *a programmer* and *a software engineer*.

## Testing, deeply

### Why we test (and what tests buy us)

Tests do four things: **catch regressions** (you didn't break old behavior changing new code), **document behavior** (a test is an executable spec of what the code *should* do), **enable refactoring** (the seatbelt), and **drive design** (writing the test first forces you to design a usable interface, more on TDD below). The first one is what most people think of; the last is the most underrated.

### The test pyramid

Not all tests are equal in cost or speed. The **test pyramid** (Mike Cohn) is the guidance for *how many of each*:

```
        /\        E2E / UI tests      few   - slow, brittle, high-confidence, full system
       /  \
      /----\      Integration tests   some  - medium speed, real collaborators (DB, HTTP)
     /      \
    /--------\    Unit tests          many  - fast, isolated, one unit at a time
```

- **Unit tests**, test one unit (a function/class) in isolation, with collaborators faked. Milliseconds each. You have *thousands*. They pinpoint exactly what broke. The base of the pyramid.
- **Integration tests**, test that units work together *and* with real external pieces (a real database, a real HTTP route). Slower (seconds), fewer. They catch the "each unit works but the wiring is wrong" bugs that units miss.
- **End-to-end (E2E)** tests, drive the whole system as a user would (a browser clicking through the UI, a request hitting the real stack). Slowest, flakiest, most expensive to maintain, so you have *few*, covering only critical user journeys (login, checkout).

The **anti-pattern is the "ice cream cone"** (or "testing trophy gone wrong): mostly slow E2E tests, few units. The suite takes an hour, is flaky, and when it fails you have no idea *where*. Invert it: push tests down the pyramid. Most logic should be testable as a fast unit; reserve integration and E2E for the seams and the critical paths.

### What makes a good test - FIRST

A good test is **FIRST**:

- **Fast**, milliseconds. A slow suite is a suite people skip. If a unit test touches the network or sleeps, it's not a unit test.
- **Isolated / Independent**, no test depends on another's state or order. Each sets up its own world and tears it down. Shared mutable state between tests is a top source of flakiness.
- **Repeatable / Deterministic**, same result every run, on any machine, at any time. No dependence on the clock, network, randomness, or timezone. (Flaky tests are *worse than no test*, they train the team to ignore red.)
- **Self-validating**, the test asserts pass/fail itself; no human reads output to judge. `assert`, not `print`.
- **Timely**, written close to (ideally before) the code, not bolted on months later when you've forgotten the edge cases.

You can add two more: a good test is **readable** (a teammate understands what behavior it pins from the test name and body alone) and tests **behavior, not implementation** (it asserts *what* the unit does, not *how*, so a refactor that preserves behavior keeps the test green).

**Arrange-Act-Assert** is the structure to write every test in:

```python
def test_final_price_applies_percent_discount():
    # Arrange
    cart = Cart(subtotal=100.0, item_count=1, customer_tier="standard")
    strategy = PercentOff(0.20)
    # Act
    result = final_price(cart, strategy)
    # Assert
    assert result == 80.0
```

Name tests as sentences: `test_<thing>_<condition>_<expected>`. `test_withdraw_more_than_balance_raises` tells you exactly what broke without reading the body.

### TDD - red, green, refactor (full worked example)

**Test-Driven Development** inverts the usual order: write the test *first*, watch it fail, then write the minimum code to pass, then refactor. The cycle:

1. **Red**, write a failing test for the next small bit of behavior. (It must fail, a test that passes before you write code tests nothing.)
2. **Green**, write the *simplest* code that makes it pass. Don't gold-plate; just go green.
3. **Refactor**, now that you're green and safe, clean up (27.1), both the code and the test. Tests stay green.

Repeat in tiny loops. TDD's real gift isn't the tests (though you get them free), it's *design pressure*: you experience your API as a *caller* before you build it, so you build something usable. Let's build a `BankAccount` TDD-style.

```python
# Loop 1 - RED: write the test first, before any BankAccount exists.
def test_new_account_starts_at_zero():
    account = BankAccount()
    assert account.balance == 0
# Run it: NameError / fails. Good - that's red.
```

```python
# Loop 1 - GREEN: simplest code that passes.
class BankAccount:
    def __init__(self):
        self.balance = 0
# Test passes. Green.
```

```python
# Loop 2 - RED: next behavior.
def test_deposit_increases_balance():
    account = BankAccount()
    account.deposit(50)
    assert account.balance == 50

# GREEN:
class BankAccount:
    def __init__(self): self.balance = 0
    def deposit(self, amount):
        self.balance += amount
```

```python
# Loop 3 - RED: an edge case (this is where TDD shines - you spec errors up front).
import pytest
def test_deposit_negative_amount_raises():
    account = BankAccount()
    with pytest.raises(ValueError):
        account.deposit(-10)

# GREEN:
    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("deposit must be positive")
        self.balance += amount
```

```python
# Loop 4 - RED: withdrawal + overdraft protection.
def test_withdraw_decreases_balance():
    account = BankAccount(); account.deposit(100)
    account.withdraw(30)
    assert account.balance == 70

def test_withdraw_more_than_balance_raises():
    account = BankAccount(); account.deposit(100)
    with pytest.raises(ValueError):
        account.withdraw(200)

# GREEN:
    def withdraw(self, amount):
        if amount <= 0:
            raise ValueError("withdraw must be positive")
        if amount > self.balance:
            raise ValueError("insufficient funds")
        self.balance -= amount
```

```python
# REFACTOR: now that tests are green, notice deposit/withdraw both validate positivity.
# Extract a guard (27.1's Extract Function). Tests stay green - proof we didn't break behavior.
class BankAccount:
    def __init__(self):
        self.balance = 0
    def deposit(self, amount):
        self._require_positive(amount)
        self.balance += amount
    def withdraw(self, amount):
        self._require_positive(amount)
        if amount > self.balance:
            raise ValueError("insufficient funds")
        self.balance -= amount
    @staticmethod
    def _require_positive(amount):
        if amount <= 0:
            raise ValueError("amount must be positive")
```

Notice the rhythm: you never write code without a failing test demanding it, and you never refactor without a green suite protecting you. The edge cases (negative deposit, overdraft) got *specified as tests* before the code existed, that's TDD pushing you to think about failure up front instead of discovering it in production.

### Test doubles - stubs, mocks, fakes, spies

When the unit under test has collaborators (a database, an HTTP client, a clock), you replace them with **test doubles** to keep the test fast, isolated, and deterministic. The four kinds (Gerard Meszaros's taxonomy) differ by *what they're for*:

| Double | Purpose | "Pass when…" |
|---|---|---|
| **Stub** | Provides canned answers to calls | the unit gets the input it needs |
| **Mock** | Pre-programmed with *expectations*; verifies *interactions* | the right calls were made (behavior verification) |
| **Fake** | A working but lightweight implementation | the real collaborator's behavior is needed, cheaply |
| **Spy** | Records calls for later assertion | you check afterward what happened |

The key distinction: **stubs/fakes feed the unit data (state verification, assert on the result)**; **mocks/spies record interactions (behavior verification, assert on the calls)**. Use the lightest one that does the job. Here's each in Python with `unittest.mock` and pytest:

```python
from unittest.mock import Mock, MagicMock
import pytest

# The unit under test:
class OrderService:
    def __init__(self, gateway, repo):
        self.gateway, self.repo = gateway, repo
    def place(self, order):
        charge_id = self.gateway.charge(order["total"], order["card"])
        self.repo.save({**order, "charge_id": charge_id})
        return charge_id

# STUB - canned answer, we only care the result flows through correctly:
def test_place_returns_charge_id_with_stub():
    gateway = Mock()
    gateway.charge.return_value = "ch_123"   # stubbed canned response
    repo = Mock()
    service = OrderService(gateway, repo)
    assert service.place({"total": 50, "card": "x"}) == "ch_123"

# MOCK - we verify the INTERACTION: was the gateway charged correctly?
def test_place_charges_the_correct_amount():
    gateway = Mock()
    gateway.charge.return_value = "ch_123"
    repo = Mock()
    OrderService(gateway, repo).place({"total": 50, "card": "x"})
    gateway.charge.assert_called_once_with(50, "x")   # behavior verification

# FAKE - a real, lightweight in-memory implementation (not a mock library object):
class FakeRepo:
    def __init__(self): self.saved = []
    def save(self, record): self.saved.append(record)

def test_place_persists_order_with_fake():
    gateway = Mock(); gateway.charge.return_value = "ch_9"
    repo = FakeRepo()
    OrderService(gateway, repo).place({"total": 50, "card": "x"})
    assert repo.saved[0]["charge_id"] == "ch_9"   # state verification on the fake

# SPY - record calls, assert later (mock's call recording acts as a spy):
def test_repo_save_called_once():
    gateway = Mock(); gateway.charge.return_value = "ch_1"
    repo = Mock()
    OrderService(gateway, repo).place({"total": 50, "card": "x"})
    assert repo.save.call_count == 1
```

**`mock.patch` for replacing things you don't own** (a module-level dependency, a clock):

```python
from unittest.mock import patch

def get_greeting():
    import datetime
    hour = datetime.datetime.now().hour
    return "Good morning" if hour < 12 else "Good afternoon"

def test_greeting_in_morning():
    with patch("datetime.datetime") as mock_dt:
        mock_dt.now.return_value.hour = 9
        assert get_greeting() == "Good morning"
```

**Over-mocking is a real trap.** If your test mocks *everything*, it tests that your code calls the mocks the way you told the mocks to expect, a tautology that passes even when the real integration is broken, and breaks every time you refactor. Mock at the *boundaries* (network, DB, time, external services); use real objects for your own domain logic. A test that's all mocks is usually testing the wrong thing. Prefer fakes over mocks when you can, they're more realistic and less brittle.

### Property-based testing with Hypothesis

Example-based tests check the cases *you thought of*. **Property-based testing** checks *invariants* across hundreds of generated inputs, finding the edge cases you didn't. You state a property that must always hold; Hypothesis generates inputs trying to break it, and *shrinks* any failure to a minimal example.

```python
from hypothesis import given, strategies as st

def encode(s: str) -> bytes:
    return s.encode("utf-8")
def decode(b: bytes) -> str:
    return b.decode("utf-8")

# Property: decode(encode(s)) == s for ANY string. (Round-trip invariant.)
@given(st.text())
def test_encode_decode_roundtrip(s):
    assert decode(encode(s)) == s

# Property: sorting is idempotent and length-preserving, for ANY list of ints.
@given(st.lists(st.integers()))
def test_sorted_is_idempotent_and_preserves_length(xs):
    once = sorted(xs)
    assert sorted(once) == once
    assert len(once) == len(xs)
```

If a property fails, Hypothesis hands you the *smallest* counterexample (e.g. `xs=[0, -1]`), far more useful than a random huge input. Use property tests for anything with invariants: serialization round-trips, sort/parse/format, math, data-structure laws. They complement example tests; they don't replace them.

### Coverage - and why 100% isn't the goal

**Coverage** measures which lines/branches your tests execute. Run it with `pytest --cov`. It's a useful *signal*, coverage of 20% means huge swaths are untested, but a dangerous *target*. Coverage measures lines *run*, not behavior *verified*: a test with no meaningful assertions can hit 100% coverage and test nothing. And chasing the last 5% drives you to write brittle tests for trivial getters and error branches that don't matter. A good rule: **aim for high coverage of the code that carries risk** (business logic, money, auth, edge cases), and don't sweat coverage of glue and boilerplate. Coverage tells you what you *haven't* tested; it can't tell you whether what you tested is *correct*. Treat it as a flashlight, not a finish line.

### Testing async, APIs, and databases

**Async** (recap concurrency in 05.2), use `pytest-asyncio`:

```python
import pytest, asyncio

async def fetch_total(client, url):
    return await client.get(url)

@pytest.mark.asyncio
async def test_fetch_total():
    client = Mock()
    async def fake_get(url): return 42
    client.get = fake_get
    assert await fetch_total(client, "/x") == 42
```

**APIs**, FastAPI/Flask give you a test client so you exercise the real routing/validation stack without a network (this is an *integration* test; recap backend 08.2):

```python
from fastapi.testclient import TestClient
# from main import app
def test_create_user_returns_201():
    client = TestClient(app)
    resp = client.post("/users", json={"name": "Spencer"})
    assert resp.status_code == 201
    assert resp.json()["name"] == "Spencer"
```

**Databases**, test against a *real* database (SQLite in-memory, or a throwaway Postgres in CI via Docker, 10.1), inside a transaction you roll back after each test so tests stay isolated:

```python
import sqlite3, pytest

@pytest.fixture
def db():
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT)")
    yield conn          # test runs here
    conn.close()        # teardown - fresh DB per test = isolation

def test_insert_user(db):
    db.execute("INSERT INTO users (name) VALUES (?)", ("Spencer",))
    row = db.execute("SELECT name FROM users").fetchone()
    assert row[0] == "Spencer"
```

### Snapshot tests and fixtures

**Snapshot tests** assert that output matches a stored "golden" snapshot; on first run they record it, after that they diff against it. Great for large structured output (rendered HTML, serialized API responses) where writing assertions by hand is tedious. The risk: people approve snapshot updates without reading the diff, so a bug gets "blessed." Use them for output that's stable and tedious to assert, and *review every snapshot change*.

**Fixtures** (pytest's `@pytest.fixture`) are reusable, composable setup/teardown, the `yield` splits setup from teardown, and fixtures can depend on other fixtures. They keep tests DRY and isolated (each test gets its own fresh fixture instance by default). The `db` fixture above is the canonical example.

## Software architecture

Architecture is the set of decisions about structure that are *expensive to change later*, what the major pieces are, what depends on what, where the boundaries sit. Get it roughly right and the system stays soft; get it wrong and every feature fights you.

### Separation of concerns

The foundational idea: **each part of the system handles one concern, and concerns don't bleed into each other.** Web handling is one concern; business rules are another; persistence is a third. When they're separated, you can change the database without touching business rules, change the API framework without touching the domain, and test business logic with no web server or DB at all. When they're tangled (SQL in your route handler, HTML in your domain object, see 27.1's smelly `legacy_report`), every change ripples. Almost all of architecture is separation of concerns applied at the system scale.

### Layered architecture

The classic structure: stack the system in horizontal layers, each depending only on the one below.

```
┌────────────────────────┐
│ Presentation (API/UI)  │  HTTP routes, serialization, request/response
├────────────────────────┤
│ Application / Service  │  use cases, orchestration ("place an order")
├────────────────────────┤
│ Domain                 │  entities, business rules (the heart)
├────────────────────────┤
│ Infrastructure (DB)    │  persistence, external services
└────────────────────────┘
```

Simple and widely understood. Its weakness: the domain ends up depending *downward* on infrastructure (the DB), so the heart of your app is coupled to a database detail. Hexagonal and clean architecture fix exactly that.

### Hexagonal (ports & adapters) and clean architecture

**Hexagonal architecture** (Alistair Cockburn, "ports and adapters") and **Clean Architecture** (Robert C. Martin) share one powerful idea, embodied in **the Dependency Rule**:

> **Source-code dependencies point *inward*, toward the domain. Inner layers know nothing about outer layers.**

The domain (business rules) sits at the center and depends on *nothing*. Around it, the application defines **ports**, interfaces it needs (`OrderRepository`, `PaymentGateway`). The outer ring holds **adapters**, concrete implementations of those ports (a Postgres repo, a Stripe gateway, a FastAPI controller). The database and the web framework are *details* on the *outside*, plugged in. The domain never imports the database; the database imports (implements) the domain's interface. This is the **Dependency Inversion Principle** (27.1) applied as an architectural law.

```
            ┌─────────── adapters (outer) ───────────┐
            │  FastAPI controller    Postgres repo    │
            │        │                    │           │
            │     [port: in]         [port: out]      │
            │        ▼                    ▲            │
            │   ┌──────── application ────────┐       │
            │   │   use cases / services      │       │
            │   │   ┌───── domain ──────┐     │       │
            │   │   │  entities, rules  │     │       │
            │   │   └───────────────────┘     │       │
            │   └─────────────────────────────┘       │
            └─────────────────────────────────────────┘
               dependencies point INWARD ───────►
```

The payoff is enormous: your business logic is testable with zero infrastructure (inject fakes for the ports), and you can swap Postgres for DynamoDB, or FastAPI for a CLI, by writing a new adapter, the core never changes. The cost is more indirection and ceremony, which is why a tiny app doesn't need the full hexagon (don't over-engineer, 27.1). We'll build a small clean-layered app in **Build it**.

### Dependency injection & inversion (in Python)

**Dependency Inversion** (the principle) says depend on abstractions. **Dependency Injection** (the technique) is *how*: a component receives its dependencies from outside (usually the constructor) instead of constructing them itself. We saw the core move in 27.1; here's the architectural framing.

```python
from typing import Protocol

# Port (abstraction the domain owns):
class Clock(Protocol):
    def now(self) -> float: ...

# Adapters (details):
import time
class SystemClock:
    def now(self) -> float: return time.time()
class FixedClock:
    def __init__(self, t): self._t = t
    def now(self) -> float: return self._t   # deterministic, for tests

# Domain logic depends on the PORT, never the concrete clock:
class TokenIssuer:
    def __init__(self, clock: Clock):   # injected
        self.clock = clock
    def issue(self) -> dict:
        return {"issued_at": self.clock.now(), "expires_at": self.clock.now() + 3600}

# Composition root - the ONE place that wires concretes to abstractions:
issuer = TokenIssuer(SystemClock())                 # production
test_issuer = TokenIssuer(FixedClock(1_000_000.0))  # test - time is frozen
```

Python rarely needs a DI *framework*, constructor injection with `Protocol` types is enough, and the "composition root" (your `main.py` / app factory) is where all wiring happens. (FastAPI's `Depends` is a built-in DI mechanism for request-scoped dependencies; see 08.2.) The discipline: **construct nothing deep inside; receive everything; wire at the edge.** That single rule makes your whole system testable.

### Domain modeling

Before structure comes *understanding the problem*. Domain modeling is naming the real-world concepts (entities, value objects, aggregates) and their rules in code, so the code speaks the language of the business.

- **Entity**, has identity that persists through change (a `User` with an id; two users with the same name are still different users).
- **Value object**, defined entirely by its attributes, immutable, no identity (`Money(amount, currency)`, an `Email`; two `Money(10, "USD")` are interchangeable). Prefer these, they kill primitive obsession (27.1).
- **Aggregate**, a cluster of objects treated as one unit for consistency, with a single root entry point (an `Order` and its `LineItem`s, you change line items *through* the order, which enforces invariants like "total must match").

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Money:          # value object - immutable, equality by value
    cents: int
    currency: str = "USD"
    def __add__(self, other):
        if self.currency != other.currency:
            raise ValueError("currency mismatch")
        return Money(self.cents + other.cents, self.currency)
```

Good domain models put the *rules* on the *objects* (a `Order` won't let you add a line item that breaks its invariant), so business logic can't be bypassed. This is the heart that the architecture protects.

### Monolith vs modular monolith vs microservices

A decision interviewers love and teams agonize over (recap 09 system design, and 26 if present). The tradeoffs:

| | Monolith | Modular monolith | Microservices |
|---|---|---|---|
| **Structure** | one deployable, one codebase | one deployable, strong internal module boundaries | many independently deployable services |
| **Pros** | simplest to build/deploy/debug; one transaction; fast local dev | monolith's simplicity *plus* enforced boundaries; can later split | independent scaling/deploy; team autonomy; fault isolation |
| **Cons** | boundaries erode into a "big ball of mud" over time | boundaries take discipline to enforce | distributed-systems pain: network failures, eventual consistency, ops complexity, distributed transactions, harder debugging |
| **When** | almost always start here | when the monolith is big and you want clean seams | when you have real scaling/org reasons and the ops maturity |

The honest take, the one worth giving every team: **start with a (well-structured, modular) monolith.** Microservices solve *organizational* and *extreme-scale* problems at the cost of enormous *operational* complexity (you trade in-process function calls for unreliable network calls and distributed transactions). Most products never need them, and premature microservices are the most expensive over-engineering there is. A **modular monolith**, one deployable with strict internal module boundaries (each module owns its data, talks to others through interfaces), gives you most of the benefit and lets you extract a service *later* if a specific module truly needs independent scaling. Conway's Law is real: your architecture will end up mirroring your org chart, so let the org's actual shape (not architecture fashion) drive the split.

### Event-driven architecture

Instead of services calling each other directly (synchronous, coupled), components **emit events** and others **react** (asynchronous, decoupled). It's the Observer pattern (27.1) across a network, on a message broker (09.5). "Order placed" is published; inventory, email, and analytics each consume it independently, the order service doesn't know they exist.

- **Pros:** loose coupling, independent scaling of producers/consumers, natural audit log, resilience (a down consumer just processes later).
- **Cons:** eventual consistency (the world isn't instantly in sync), harder to reason about end-to-end flow, debugging spans services, you need to handle duplicate/out-of-order events (idempotency, recall 08.2).
- **When:** workflows with many independent reactions, decoupling teams, smoothing load spikes. Don't event-drive a simple CRUD app, synchronous is simpler to reason about.

## Engineering practices - the human layer

Code is half the job. The other half is working effectively *with people* on a shared codebase over time. This is the part no course teaches and every senior engineer lives.

### Code review

A pull request (recap 11.1) is reviewed before merge. Done well, review catches bugs, spreads knowledge, and keeps quality consistent. Done badly, it's a bottleneck and a morale sink.

**Giving a review:**
- **Be kind and specific.** Critique the code, never the person. "This function does two things; could we split it?" not "this is messy." Asphyxiate ego; you're both on the same side.
- **Distinguish blocking from optional.** Prefix nits: "nit: name" (optional) vs "this will null-crash on empty input" (blocking). Don't bikeshed style a linter should own (automate formatting, black/ruff, so review is about *substance*).
- **What to look for, in priority order:** correctness (does it do the right thing, edge cases, error handling) → tests (are they there, do they test behavior) → security (injection, auth, secrets, 12.x) → design (cohesion, coupling, the right abstraction, 27.1) → readability → performance (only where it matters). Approve when it's *better than before and safe*, not when it's perfect, perfect is the enemy of merged.
- **Review small PRs.** A 2000-line PR gets a rubber-stamp; a 200-line PR gets real eyes. Keep changes small (this is partly the author's job).

**Receiving a review:**
- Assume good intent; reviewers are protecting the codebase, not attacking you.
- Don't be defensive, a confused reviewer means the *code* is confusing, which is useful data.
- Push back with reasons when you disagree; reviews are a conversation, not a verdict. Resolve disagreements in the code or a quick call, not a comment war.

### Version control workflows (recap 11.1)

How a team branches and merges. Two dominant models:

- **Trunk-based development**, everyone commits to `main` (trunk) frequently, in small increments, behind feature flags for unfinished work. Short-lived branches (hours to a day). Pairs naturally with CI/CD (10.3) and continuous deployment. Fewer, smaller merges = fewer painful conflicts. A solid default for small fast teams.
- **Gitflow**, long-lived branches: `main`, `develop`, `feature/*`, `release/*`, `hotfix/*`. More ceremony and structure; suited to scheduled releases and versioned software (e.g. shipping desktop apps with explicit release versions). Heavier; long-lived branches mean painful merges.

The trend, and the better fit for web products, is trunk-based with short-lived feature branches and PRs, it keeps integration continuous and conflicts small. Gitflow earns its weight when you have real release trains and multiple supported versions.

### Documentation - READMEs, ADRs, docstrings

Documentation is a gift to future-you and your team. Three tiers:

- **README**, the front door. How to set up, run, test, and deploy the project; what it is and who owns it. If a new hire can't get the project running from the README, it's broken. (Recap setup, 00.1.)
- **Docstrings**, the *why* and contract of a function/module, close to the code (so they're more likely to stay current). Document non-obvious behavior, params, raises, returns, not the obvious.
- **ADRs (Architecture Decision Records)**, short markdown docs capturing a significant decision: the *context*, the *decision*, the *alternatives considered*, and the *consequences*. They answer the question that haunts every codebase: "*why* did we do it this way?" Six months later, an ADR saves a team from relitigating a decision or, worse, reversing it without knowing why it was made. They're cheap to write and enormously valuable. (Template in the mini-project.)

The rule: document *decisions and intent* (which don't live in the code), not mechanics (which do). Out-of-date docs are worse than none, keep them lean enough to maintain.

### Technical debt

**Technical debt** is the implied cost of future rework caused by choosing an easy-now solution over a better-but-slower one. The metaphor (Ward Cunningham) is financial: you "borrow" speed now and "pay interest" later in slower changes and more bugs.

- **Deliberate vs inadvertent; prudent vs reckless.** "We'll ship the hack to hit the deadline and fix it next sprint" is *deliberate, prudent*, fine, if you actually pay it back. "What's layering?" is *reckless, inadvertent*, the bad kind.
- **Recognizing it:** changes that should be small take forever; the same bug class recurs; everyone fears touching one module; onboarding is slow. That friction *is* the interest payment.
- **Paying it down:** the **boy-scout rule** (leave code cleaner than you found it, small refactors as you pass through, 27.1) pays it down continuously. For bigger debt, make it *visible* (track it), and pay it down where it *hurts* (high-churn, high-risk areas), not everywhere (paying down debt in code that never changes is wasted effort). Some debt is fine to keep; the skill is knowing which.

### Estimation, pairing, and the rest

- **Estimation**, estimates are guesses, and they're systematically *too optimistic* (planning fallacy). Estimate in *relative* terms (story points, t-shirt sizes) rather than hours; break big tasks down (small things estimate better); communicate *ranges and uncertainty*, not false precision; and track actuals to calibrate. An estimate is a forecast, not a promise, say so.
- **Pairing**, two engineers, one task (driver types, navigator reviews in real time). Expensive in headcount but pays off on hard/risky/unfamiliar work, onboarding, and knowledge spread. Not for routine work. It's continuous code review, so the change ships pre-reviewed.
- **The boy-scout rule**, leave it cleaner than you found it. Small, opportunistic improvements compound; they're how a codebase gets *better* over time instead of rotting.
- **Working in a codebase you didn't write**, the most common real situation, and a genuine skill. The playbook: read the tests first (they're an executable spec of intended behavior); change one small thing and run the tests to learn the feedback loop; trace one request end to end to learn the layers; *don't* rewrite what you don't understand (Chesterton's Fence, don't remove a thing until you know why it's there); add a characterization test before changing untested code (27.1); ask "why" before "this is wrong." Respect that the people before you had context you don't.

## Build it - a feature TDD-style, in clean layers, with DI

Let's build a **URL shortener** the way you'd actually structure it: clean layers (domain / application / infrastructure / presentation), dependency injection, and TDD throughout. This is the capstone, so we'll show the layered structure and the TDD loop together.

### Layout (separation of concerns)

```
shortener/
  domain.py          # entities + value objects + business rules (depends on NOTHING)
  ports.py           # interfaces the application needs (the abstractions)
  application.py     # use cases (orchestration), depends on ports
  infrastructure.py  # adapters: concrete repo implementations (depend on ports)
  api.py             # presentation: FastAPI controller (depends on application)
  tests/
```

### Domain (the center - no infrastructure)

```python
# domain.py
import re
from dataclasses import dataclass

_VALID_SCHEME = re.compile(r"^https?://")

@dataclass(frozen=True)
class ShortLink:          # value-ish entity; identity is the code
    code: str
    target: str

def validate_url(url: str) -> None:
    if not _VALID_SCHEME.match(url):
        raise ValueError("url must start with http:// or https://")
```

### Ports (abstractions the app owns - the dependency-inversion seam)

```python
# ports.py
from typing import Protocol, Optional
from domain import ShortLink

class LinkRepository(Protocol):
    def save(self, link: ShortLink) -> None: ...
    def get(self, code: str) -> Optional[ShortLink]: ...

class CodeGenerator(Protocol):
    def generate(self) -> str: ...
```

### Application (use cases - depends only on ports, TDD-driven)

We write the test first.

```python
# tests/test_application.py - RED first
import pytest
from application import Shortener
from domain import ShortLink

class FakeRepo:                       # fake adapter, in-memory (state verification)
    def __init__(self): self.store = {}
    def save(self, link): self.store[link.code] = link
    def get(self, code): return self.store.get(code)

class StubGenerator:                  # stub - deterministic code for the test
    def __init__(self, code): self.code = code
    def generate(self): return self.code

def test_shorten_saves_and_returns_code():
    svc = Shortener(FakeRepo(), StubGenerator("abc123"))
    assert svc.shorten("https://nyx.com") == "abc123"

def test_shorten_rejects_bad_url():
    svc = Shortener(FakeRepo(), StubGenerator("x"))
    with pytest.raises(ValueError):
        svc.shorten("not-a-url")

def test_resolve_returns_target():
    repo = FakeRepo()
    svc = Shortener(repo, StubGenerator("abc"))
    svc.shorten("https://nyx.com")
    assert svc.resolve("abc") == "https://nyx.com"

def test_resolve_unknown_code_raises():
    svc = Shortener(FakeRepo(), StubGenerator("x"))
    with pytest.raises(KeyError):
        svc.resolve("nope")
```

```python
# application.py - GREEN: simplest code to pass the tests above
from domain import ShortLink, validate_url
from ports import LinkRepository, CodeGenerator

class Shortener:
    def __init__(self, repo: LinkRepository, codes: CodeGenerator):  # DI
        self.repo, self.codes = repo, codes
    def shorten(self, url: str) -> str:
        validate_url(url)                          # domain rule
        code = self.codes.generate()
        self.repo.save(ShortLink(code, url))
        return code
    def resolve(self, code: str) -> str:
        link = self.repo.get(code)
        if link is None:
            raise KeyError(code)
        return link.target
```

The application logic is fully tested with **zero infrastructure**, no DB, no web server, no network. Fast, isolated, deterministic. That's the dependency rule paying off.

### Infrastructure (adapters - depend on the ports)

```python
# infrastructure.py
import secrets, sqlite3
from domain import ShortLink

class SqliteLinkRepository:            # real adapter - implements LinkRepository
    def __init__(self, conn):
        self.conn = conn
        conn.execute("CREATE TABLE IF NOT EXISTS links (code TEXT PRIMARY KEY, target TEXT)")
    def save(self, link):
        self.conn.execute("INSERT INTO links VALUES (?, ?)", (link.code, link.target))
    def get(self, code):
        row = self.conn.execute("SELECT code, target FROM links WHERE code=?", (code,)).fetchone()
        return ShortLink(row[0], row[1]) if row else None

class RandomCodeGenerator:             # real adapter - implements CodeGenerator
    def generate(self) -> str:
        return secrets.token_urlsafe(6)
```

### Presentation + composition root (wiring)

```python
# api.py - the composition root wires concretes to abstractions in ONE place
import sqlite3
from fastapi import FastAPI, HTTPException
from application import Shortener
from infrastructure import SqliteLinkRepository, RandomCodeGenerator

def build_app(conn) -> FastAPI:
    app = FastAPI()
    service = Shortener(SqliteLinkRepository(conn), RandomCodeGenerator())  # DI wiring
    @app.post("/shorten")
    def shorten(body: dict):
        try:
            return {"code": service.shorten(body["url"])}
        except ValueError as e:
            raise HTTPException(422, str(e))
    @app.get("/{code}")
    def resolve(code: str):
        try:
            return {"target": service.resolve(code)}
        except KeyError:
            raise HTTPException(404, "not found")
    return app

app = build_app(sqlite3.connect(":memory:", check_same_thread=False))
```

```python
# tests/test_api.py - INTEGRATION test through the real stack
import sqlite3
from fastapi.testclient import TestClient
from api import build_app

def test_shorten_and_resolve_end_to_end():
    client = TestClient(build_app(sqlite3.connect(":memory:")))
    code = client.post("/shorten", json={"url": "https://nyx.com"}).json()["code"]
    assert client.get(f"/{code}").json()["target"] == "https://nyx.com"

def test_bad_url_returns_422():
    client = TestClient(build_app(sqlite3.connect(":memory:")))
    assert client.post("/shorten", json={"url": "ftp://x"}).status_code == 422
```

Look at the test pyramid we just built: many fast unit tests on `application.py` (fakes/stubs, no infra), a handful of integration tests on `api.py` (real routing, real SQLite). The domain never imports the DB or FastAPI; we could swap SQLite for Postgres or FastAPI for a CLI by writing a new adapter, and the tested core wouldn't change a line. *That's* clean architecture and DI earning their keep.

## Mini-project - ship a real feature, TDD + layers + ADR

Build a small but real feature end to end, applying everything in this chapter. Two good options: extend the **URL shortener** above (add click-count analytics + a custom-alias feature), or build a **todo API** (create/list/complete/delete todos with due dates and priorities). Requirements:

1. **TDD throughout**, every behavior gets a failing test first (red), minimal code to pass (green), then refactor. Commit on each green step (11.1).
2. **Layered architecture**, domain / application / infrastructure / presentation, with the dependency rule respected (domain depends on nothing; infra implements ports; wiring at the composition root).
3. **Dependency injection**, repositories and any external collaborators (clock, code generator) injected against `Protocol` ports; fakes in tests, real adapters in prod.
4. **A full test suite**, *unit* tests on the application/domain with fakes (fast, no infra), *integration* tests through the API with a real in-memory DB. Include at least one property-based test (Hypothesis) for an invariant (e.g. "a shortened-then-resolved URL round-trips," or "a created todo always appears in the list").
5. **One ADR** documenting a key decision. Use this template:

```markdown
# ADR 001: Use SQLite (not Postgres) for the URL shortener MVP

## Status
Accepted

## Context
We're building an MVP URL shortener. We need persistence. The team is small,
expected traffic is low (<100 req/s), and we want zero ops overhead to start.

## Decision
Use SQLite via a SqliteLinkRepository behind the LinkRepository port. The domain
and application layers depend only on the port, not on SQLite.

## Alternatives considered
- Postgres: more scalable and concurrent, but adds ops/hosting overhead we don't
  need at MVP scale, and slows local dev/CI.
- In-memory dict: simplest, but loses data on restart - unacceptable even for MVP.

## Consequences
+ Zero-ops, fast local dev and CI, trivial test setup (:memory:).
+ Because persistence is behind a port, swapping to Postgres later means writing
  one new adapter - the domain/application/tests are untouched.
- SQLite's write concurrency is limited; if traffic grows we revisit (and the ADR
  for that migration will reference this one).
```

6. **A README** that gets a new contributor from clone to running tests to running the server (00.1).

Deliverable: a working feature, a green test suite spanning the pyramid, an ADR, and a short reflection on *which layer each test targeted* and *why you injected what you injected*. This is what shipping a feature on a healthy team looks like.

## Common mistakes

- **Testing implementation, not behavior.** Asserting on internals (private methods, exact call sequences) so every refactor breaks tests. Test the observable behavior; let the inside be free to change.
- **Over-mocking.** A test that's all mocks tests your mocks, not your code, passes when the real thing is broken, breaks on every refactor. Mock at boundaries; prefer fakes; use real objects for your own logic.
- **Flaky tests tolerated.** A test that fails 1-in-20 trains the team to ignore red, which defeats the entire suite. Fix or delete flaky tests immediately. Determinism is non-negotiable.
- **Coverage as a target.** Chasing 100% breeds assertion-free tests and brittle ones for trivial code. Coverage is a flashlight, not a finish line.
- **Big PRs.** 2000-line reviews get rubber-stamped. Keep changes small for real review.
- **Premature microservices.** Splitting a tiny app into services trades simple function calls for distributed-systems pain. Start with a modular monolith.
- **Skipping the composition root.** Constructing dependencies deep inside classes (instead of injecting) makes everything untestable. Construct at the edge, inject everywhere.
- **No ADRs.** Six months later nobody remembers *why*, so the team relitigates or reverses sound decisions. Write the cheap doc.
- **Refactoring without the seatbelt.** (From 27.1, worth repeating.) No tests = no safe refactoring.

## On the job / interview angle

- **"How would you test this?"** is one of the most common interview questions. Strong answer: name the pyramid level, the cases (happy path + edges + errors), what you'd mock (boundaries only), and how you'd keep it deterministic. Bonus: mention a property-based test for an invariant.
- **TDD in interviews**, even when not asked, narrating "let me write a failing test first" signals senior process. It also catches your own bugs live.
- **System design rounds** (recap 15.2) are architecture: separation of concerns, where boundaries go, monolith vs services tradeoffs, event-driven vs synchronous, the dependency rule. Have an *opinion* and *justify it with tradeoffs*, "I'd start with a modular monolith because…".
- **Behavioral rounds** probe practices: "tell me about a code review disagreement," "how do you handle technical debt," "a time you worked in unfamiliar code." Use the frameworks here (kind+specific reviews, prudent vs reckless debt, read-the-tests-first).
- **On the job**, the engineers who get trusted are the ones who test reflexively, leave code cleaner (boy-scout), write the ADR, give kind precise reviews, and can safely change code they didn't write. None of that is about being a faster typist, it's this chapter.

## Exercises

**1.** Classify each as stub, mock, fake, or spy:
(a) An in-memory dict standing in for a database. (b) An object pre-told to expect `charge(50, "x")` exactly once. (c) `gateway.charge.return_value = "ch_1"`. (d) Asserting `repo.save.call_count == 1` after the fact.

<details><summary>Solution</summary>

(a) **Fake**, a working lightweight implementation. (b) **Mock**, pre-programmed with interaction expectations (behavior verification). (c) **Stub**, provides a canned answer. (d) **Spy**, records calls for later assertion. Remember: stubs/fakes feed data (assert on *result*); mocks/spies record interactions (assert on *calls*).
</details>

**2.** Write the red-green-refactor loop for a `FizzBuzz` function (returns "Fizz" for multiples of 3, "Buzz" for 5, "FizzBuzz" for 15, else the number as a string).

<details><summary>Solution</summary>

```python
# RED → GREEN, one behavior at a time:
def test_returns_number(): assert fizzbuzz(1) == "1"
def fizzbuzz(n): return str(n)                          # green

def test_fizz(): assert fizzbuzz(3) == "Fizz"
def fizzbuzz(n):
    if n % 3 == 0: return "Fizz"
    return str(n)                                       # green

def test_buzz(): assert fizzbuzz(5) == "Buzz"
def test_fizzbuzz(): assert fizzbuzz(15) == "FizzBuzz"
# REFACTOR to the clean final form (tests stay green):
def fizzbuzz(n):
    if n % 15 == 0: return "FizzBuzz"   # check 15 BEFORE 3 and 5
    if n % 3 == 0:  return "Fizz"
    if n % 5 == 0:  return "Buzz"
    return str(n)
```
The order of checks (15 first) is the subtlety the tests caught.
</details>

**3.** Your domain `OrderService` imports `psycopg2` and connects to Postgres in its constructor. What's wrong and how do you fix it?

<details><summary>Solution</summary>

It violates the **Dependency Rule / DIP**: a high-level domain/application class depends on a low-level infrastructure detail (Postgres), so it can't be unit-tested without a database and can't swap storage. Fix: define an `OrderRepository` *port* (Protocol) the service depends on; move Postgres into an adapter (`PostgresOrderRepository`) that *implements* the port; **inject** the repo into the service's constructor; wire the concrete adapter at the composition root. Now tests inject an in-memory fake.
</details>

**4.** Why is a flaky test worse than no test?

<details><summary>Solution</summary>

A flaky test (non-deterministic pass/fail) erodes trust in the *whole* suite: people start ignoring red builds ("oh, that one's just flaky"), so real failures slip through unnoticed. It also blocks CI/CD and wastes time on false alarms. A missing test is an honest gap; a flaky test is active misinformation. Fix the determinism (remove dependence on time/network/randomness/order) or delete it.
</details>

**5.** When would you choose a modular monolith over microservices?

<details><summary>Solution</summary>

Almost always at the start, and for most products throughout. A modular monolith gives you a single deployable (simple ops, easy local dev, in-process calls, one transaction) *plus* enforced internal boundaries (each module owns its data, talks via interfaces). You only move to microservices when you have a real driver, a specific module needs independent scaling, or separate teams need independent deploy cadence, *and* the ops maturity to handle distributed-systems complexity (network failure, eventual consistency, distributed transactions, harder debugging). The modular boundaries make a later extraction cheap, so you don't pay the microservices tax until you must.
</details>

**6.** A teammate's PR works but mixes a refactor with a new feature in 1500 lines. What feedback do you give?

<details><summary>Solution</summary>

Kindly ask to **split it**: separate the refactor (behavior-preserving, 27.1) from the feature (new behavior) into distinct PRs, and shrink each. Reasons to give: (1) a 1500-line PR can't get real review, mixing the two means a reviewer can't tell which diff is a structural change vs a behavior change, so bugs hide; (2) if something breaks later, separate commits make `git bisect` / revert clean; (3) small PRs merge faster and lower risk. Frame it as protecting the codebase and making *their* change easier to land, not as criticism.
</details>
