# Chapter 27.1 - Clean Code, SOLID & Design Patterns

> Goal: Learn what separates code that *works* from code a team can *live with*. Master the clean-code fundamentals (naming, small focused functions, comments that earn their place, DRY vs premature abstraction, cohesion & coupling, recognizing smells); internalize the SOLID principles with a bad→good Python example each; understand composition over inheritance; implement the design patterns that actually matter in real Python (and learn when they're abused); and practice **refactoring** as a disciplined sequence of small, safe, test-backed steps. End state: you can take a smelly module and refactor it, under tests, into something clean, and you can reach for the right pattern (or correctly decide *not* to) without cargo-culting.

You've probably shipped a lot of code, and the code that *works* is the easy part: making a thing run is the part you've already proven you can do. The harder, more valuable skill is writing code that the *next* person (often you, six months later) can read, change, and trust. It's common to write code that works and then spend the review explaining *why it's hard to live with*. This chapter is about getting the vocabulary and the patterns crisp enough to teach, and to stop you from over-engineering, which is the senior-developer failure mode you fall into when you get clever.

The throughline of this whole chapter: **NO BLACK BOXES.** Every principle gets a runnable before→after. Every pattern gets a real Python implementation, a clear statement of *when* to use it, and an honest abuse warning. Patterns are tools, not trophies.

## Start here

Here's the mental shift that makes all of this click: **you write code once, but you read it a hundred times.** The cost of software isn't typing it, it's *understanding* it well enough to change it safely. Every clean-code rule is really a rule about *future reading and future changing*.

Two analogies worth coming back to:

**Code is a letter to a colleague who happens to be a computer.** The computer will run anything syntactically valid. The colleague, the human reading it next, needs names that mean things, functions short enough to hold in their head, and structure that matches how they think about the problem. When you write `for x in d: process(x)` the computer is happy and the colleague is lost. When you write `for invoice in unpaid_invoices: send_reminder(invoice)` both are served. Clean code is the discipline of serving the colleague *without* lying to the computer.

**A codebase is a kitchen you share with a team.** A smelly function is a dirty pan left in the sink. One is annoying; a sink full of them means nobody can cook. The **boy-scout rule** (we'll meet it again in 27.2) is "leave the kitchen cleaner than you found it", wipe down the counter you used. Refactoring is the deliberate cleaning session: you don't change *what* you cook (behavior), you reorganize *how* the kitchen is laid out so the next dish is easier.

**Why this matters for a tech job.** Junior engineers are hired to make features work. Senior engineers are trusted to make features work *in a way the team can build on*. The difference is almost entirely this chapter: clean code, sound design, knowing the patterns and, crucially, knowing when *not* to reach for them. In interviews, the moment you finish a coding problem and the interviewer asks "how would you make this more maintainable?" or "what if requirements change to X?", that's them probing for exactly this. On the job it's every code review you'll ever give or get. This is the craft layer, and it's what gets you promoted.

A warning worth putting up front: **clean code and design patterns are easy to over-apply.** A three-line script does not need a factory. The skill is not "use patterns", it's "apply the smallest amount of structure that makes the code clear and changeable, and not one ounce more." Keep that tension alive through the whole chapter.

## Clean code: the fundamentals

Clean code isn't a style guide you bolt on at the end. It's a set of habits that make code communicate its intent. Let's go principle by principle, each with a concrete Python example.

### Naming

Names are the single highest-use thing you control. A good name removes the need for a comment. A bad name is a tiny lie you tell on every line that uses it.

```python
# ❌ Names that hide intent
def calc(d, r, t):
    return d * r * t

# ✅ Names that reveal intent
def total_interest(principal: float, rate: float, years: float) -> float:
    return principal * rate * years
```

Rules worth holding yourself to:

- **Use intention-revealing names.** `elapsed_seconds`, not `t`. `active_users`, not `lst2`.
- **Pronounceable and searchable.** `genymdhms` is a riddle; `generation_timestamp` you can say out loud and grep for. Avoid single letters except for trivial loop indices and well-known math (`i`, `j`, `x`, `y`).
- **Avoid encodings and noise.** No Hungarian notation (`strName`), no `data`, `info`, `manager`, `processor` as standalone names, they say nothing. `user_data` is barely better than `data`.
- **Class names are nouns** (`Invoice`, `PaymentGateway`); **function names are verbs** (`send`, `calculate_total`, `is_valid`).
- **One word per concept.** Don't have `fetch`, `get`, and `retrieve` all meaning the same thing across the codebase. Pick one.
- **Booleans read as predicates.** `is_active`, `has_permission`, `should_retry`, so `if is_active:` reads like English.

A name should answer three questions at once: *why does this exist, what does it do, how is it used.* If the name can't, the thing it names is probably doing too much.

### Functions that do one thing

This is the rule that fixes the most code. A function should do **one thing**, do it well, and do it at **one level of abstraction**. If you have to scroll, or you find yourself mentally inserting "...and then..." while reading, it's too big.

```python
# ❌ One function doing four things at three abstraction levels
def process_order(order):
    # validate
    if not order.get("items"):
        raise ValueError("no items")
    total = 0
    # compute total with tax
    for item in order["items"]:
        total += item["price"] * item["qty"]
    total *= 1.08
    # charge
    resp = requests.post("https://pay.example.com/charge",
                         json={"amount": total, "card": order["card"]})
    if resp.status_code != 200:
        raise RuntimeError("charge failed")
    # email
    smtp = smtplib.SMTP("mail.example.com")
    smtp.sendmail("noreply@shop.com", order["email"], f"Paid ${total:.2f}")
    return total
```

```python
# ✅ A coordinator that reads like a table of contents
def process_order(order: dict) -> float:
    validate_order(order)
    total = order_total_with_tax(order["items"])
    charge_card(order["card"], total)
    send_receipt(order["email"], total)
    return total

def validate_order(order: dict) -> None:
    if not order.get("items"):
        raise ValueError("order has no items")

def order_total_with_tax(items: list[dict], tax_rate: float = 0.08) -> float:
    subtotal = sum(item["price"] * item["qty"] for item in items)
    return subtotal * (1 + tax_rate)

def charge_card(card: str, amount: float) -> None:
    resp = requests.post("https://pay.example.com/charge",
                         json={"amount": amount, "card": card})
    if resp.status_code != 200:
        raise RuntimeError("charge failed")

def send_receipt(email: str, amount: float) -> None:
    smtp = smtplib.SMTP("mail.example.com")
    smtp.sendmail("noreply@shop.com", email, f"Paid ${amount:.2f}")
```

The `process_order` coordinator now reads like prose. Each helper is independently testable, independently nameable, and operates at one level of abstraction (the coordinator talks in business steps; the helpers talk in HTTP and SMTP). Notice we also pulled the magic `1.08` and `0.08` into a named, defaulted parameter, magic numbers are a smell.

Companion rules:

- **Few arguments.** Zero is ideal, one or two is fine, three is a yellow flag, four+ means you probably want a parameter object (we'll do this refactoring later). **Avoid boolean flag arguments**, `render(report, True)` is unreadable; a flag argument is usually a sign the function does two things. Split it: `render_pdf(report)` and `render_html(report)`.
- **No side effects the name doesn't promise.** `check_password(user, pw)` should not also initialize the user's session. That's a lie of omission.
- **Command/query separation.** A function either *does* something (command, returns nothing) or *answers* something (query, returns a value, no side effects), not both. `if set_and_check(x):` is a trap.

### Comments that earn their place

The best comment is the one you didn't need to write because the code says it. Most comments are apologies for unclear code. But some comments are genuinely valuable.

```python
# ❌ Comments that restate the obvious (noise - they rot and lie)
i += 1  # increment i by one
# loop over the users
for user in users:
    ...

# ❌ Commented-out code (delete it - that's what git is for, see 11.1)
# old_total = compute_legacy(order)

# ✅ Comments that explain WHY, not WHAT
# Stripe requires amounts in cents; their API rejects floats silently (see SHOP-412).
amount_cents = round(total * 100)

# ✅ Comments that warn of consequences
# WARNING: this query does a full table scan; do not call in a request handler.
def reindex_all(): ...

# ✅ Legal/source comments where required, and intent for genuinely non-obvious math
# Welford's online algorithm - numerically stable single-pass variance.
```

Good comments: explain *why* (the business reason, the workaround, the ticket number), warn of consequences, clarify genuinely obscure algorithms, and provide legal headers. Bad comments: restate the code, narrate the obvious, sit on top of commented-out code, or, worst, go stale and now actively mislead. If you can rename a variable or extract a well-named function to make the comment unnecessary, do that instead. **Code is the truth; comments are a promise you have to keep updating.**

### DRY - and its evil twin, premature abstraction

**DRY (Don't Repeat Yourself):** every piece of *knowledge* should have a single, authoritative representation. If the tax rate lives in four places, the day it changes you'll fix three of them and ship a bug. So you extract it.

But DRY is about *knowledge*, not about *characters that happen to look alike*. Two pieces of code that look identical *today* but represent *different decisions* should NOT be merged, because the day one needs to change and the other doesn't, the shared abstraction becomes a prison. This is the most common over-engineering mistake you'll see (and make).

```python
# These LOOK identical - but are they the same knowledge?
def format_invoice_id(n): return f"INV-{n:06d}"
def format_order_id(n):   return f"ORD-{n:06d}"
```

The naive DRY move is to extract `format_id(prefix, n)`. But ask: *is it a coincidence that invoices and orders use the same format, or a rule?* If product decides next month that order IDs should be 8 digits and include the year, your shared function now needs a flag, then two flags, and you've coupled two unrelated decisions. The rule of thumb: **prefer duplication over the wrong abstraction.** Sandi Metz's line is the one worth keeping on a sticky note, "duplication is far cheaper than the wrong abstraction." Wait until you've seen the *third* occurrence and you understand the *shape* of the variation before you unify. (This is the **Rule of Three.**)

### Cohesion and coupling

These two words explain *most* of what "good design" means at the module level.

- **Cohesion**, how focused a module/class is. *High* cohesion means everything in it belongs together, serving one clear purpose. A `User` class with `change_password`, `update_email`, `deactivate` is cohesive. A `Utils` class with `parse_date`, `send_email`, `compute_tax`, `resize_image` is the opposite, it's a junk drawer (low cohesion).
- **Coupling**, how much modules depend on each other's *internals*. *Loose* coupling means modules talk through small, stable interfaces and can change independently. *Tight* coupling means changing one forces changes in another. If your billing module reaches into the user object's private `_subscription_rows` list, they're tightly coupled, a billing change can break user code and vice versa.

**The goal is always: high cohesion, loose coupling.** Almost every design pattern in this chapter is, underneath, a technique for raising cohesion and lowering coupling. When you can't articulate *why* a refactor is better, "it increases cohesion / loosens coupling" is usually the real reason.

### A field guide to code smells

A **code smell** is a surface symptom that often (not always) points to a deeper design problem. Smells are *hints to investigate*, not laws. Keep this list in your head during code review:

| Smell | What it looks like | Likely fix |
|---|---|---|
| **Long function** | Scrolling to read it | Extract function |
| **Long parameter list** | 4+ args | Introduce parameter object |
| **Duplicated code** | Same logic in N places | Extract (after Rule of Three) |
| **Large class / God object** | One class does everything | Extract class, split responsibilities |
| **Feature envy** | Method uses another object's data more than its own | Move method to that object |
| **Primitive obsession** | Passing `str`/`dict` where a type belongs | Introduce a small class / dataclass |
| **Shotgun surgery** | One change forces edits in many files | Consolidate the responsibility |
| **Divergent change** | One class changes for many unrelated reasons | Split by reason-to-change (SRP) |
| **Switch on type** | `if kind == "a" ... elif kind == "b"` repeated | Replace conditional with polymorphism |
| **Magic numbers/strings** | `total * 1.08` | Named constant |
| **Comments as deodorant** | Comments explaining bad code | Refactor so the comment is unneeded |
| **Temporal coupling** | "call `init()` before `run()`" | Make the API enforce order |

These map almost one-to-one onto refactorings, which is the whole point: a smell names the problem, a refactoring is the cure, and a test is what keeps you safe while you apply it.

## SOLID - five principles, five before→after examples

SOLID is five object-oriented design principles (Robert C. Martin coined the acronym). They're not gospel and they're not Python-specific, but they're a genuinely useful checklist for *why* a design feels brittle. We'll do each as a bad→good Python pair, because principles in the abstract are forgettable and code is not.

### S - Single Responsibility Principle

> A class should have **one reason to change**, one responsibility, owned by one actor.

```python
# ❌ This class has THREE reasons to change: business rules, persistence, formatting.
class Report:
    def __init__(self, rows): self.rows = rows
    def total(self): return sum(r["amount"] for r in self.rows)       # business
    def save_to_db(self, conn): conn.execute("INSERT ...")            # persistence
    def to_html(self): return "<table>...</table>"                   # presentation
```

If the DBA changes the schema, the accountant changes the totaling rule, or design changes the HTML, all three force edits to the *same class*. That's **divergent change**, and it means three unrelated teams collide in one file.

```python
# ✅ Each responsibility lives where its reason-to-change lives.
from dataclasses import dataclass

@dataclass
class Report:                       # pure domain: changes only if the BUSINESS rule changes
    rows: list[dict]
    def total(self) -> float:
        return sum(r["amount"] for r in self.rows)

class ReportRepository:             # changes only if PERSISTENCE changes
    def __init__(self, conn): self.conn = conn
    def save(self, report: Report) -> None:
        self.conn.execute("INSERT INTO reports (total) VALUES (?)", (report.total(),))

class ReportHtmlRenderer:           # changes only if PRESENTATION changes
    def render(self, report: Report) -> str:
        return f"<table><tr><td>Total</td><td>{report.total():.2f}</td></tr></table>"
```

Now each class has one job and one audience. **Abuse warning:** SRP taken to the extreme gives you a thousand one-method classes and an unreadable explosion of indirection. "One reason to change" means *one axis of business change*, not "one method."

### O - Open/Closed Principle

> Software entities should be **open for extension, closed for modification.** You should be able to add new behavior without editing existing, tested code.

```python
# ❌ Every new shipping method means editing this function (and re-testing it all).
def shipping_cost(order):
    if order.method == "standard":
        return 5.00
    elif order.method == "express":
        return 15.00
    elif order.method == "overnight":     # <-- adding this edits a tested function
        return 30.00
    raise ValueError("unknown method")
```

```python
# ✅ Add a new method by adding a class - existing classes stay untouched.
from abc import ABC, abstractmethod

class ShippingMethod(ABC):
    @abstractmethod
    def cost(self, order) -> float: ...

class Standard(ShippingMethod):
    def cost(self, order): return 5.00

class Express(ShippingMethod):
    def cost(self, order): return 15.00

class Overnight(ShippingMethod):          # NEW: zero edits to existing classes
    def cost(self, order): return 30.00

def shipping_cost(order, method: ShippingMethod) -> float:
    return method.cost(order)
```

This is literally the Strategy pattern (coming up). **Abuse warning:** you can't make *everything* open for extension, that's infinite abstraction. Apply OCP to the axes that you *know* vary (here: shipping methods, which marketing invents constantly). Don't pre-build extension points for variation you're only imagining. (Recall the long `if/elif` chain on a type, that's the "switch on type" smell, and OCP via polymorphism is the cure.)

### L - Liskov Substitution Principle

> Subtypes must be **substitutable** for their base type without breaking the program. If code works with a `Bird`, it must work with any subclass of `Bird`.

```python
# ❌ The classic violation: a subclass that breaks the parent's contract.
class Rectangle:
    def __init__(self, w, h): self.w, self.h = w, h
    def set_width(self, w): self.w = w
    def set_height(self, h): self.h = h
    def area(self): return self.w * self.h

class Square(Rectangle):                  # "a square IS-A rectangle," right?
    def set_width(self, w):  self.w = self.h = w   # forced to keep sides equal
    def set_height(self, h): self.w = self.h = h

def stretch_and_check(rect: Rectangle):
    rect.set_width(5); rect.set_height(4)
    assert rect.area() == 20              # holds for Rectangle, FAILS for Square (gives 16)
```

`Square` violates the *behavioral* contract clients rely on. The fix is usually to stop forcing a false IS-A: model them as separate shapes, or make them immutable so the mutating contract never exists.

```python
# ✅ Honor the contract. Immutable shapes, no false inheritance.
from dataclasses import dataclass

@dataclass(frozen=True)
class Rectangle:
    w: float
    h: float
    def area(self) -> float: return self.w * self.h

@dataclass(frozen=True)
class Square:
    side: float
    def area(self) -> float: return self.side ** 2
```

LSP smells: a subclass that throws `NotImplementedError` for a method the base promises, that tightens preconditions (rejects inputs the base accepts), or that weakens postconditions. **The practical takeaway:** inheritance is a promise of *substitutability*, not just code reuse. If your subclass can't honor the parent's full contract, you don't have an IS-A relationship, reach for composition instead.

### I - Interface Segregation Principle

> Don't force clients to depend on methods they don't use. Many small, focused interfaces beat one fat one.

```python
# ❌ A fat interface forces every printer to implement everything.
class Machine(ABC):
    @abstractmethod
    def print(self, doc): ...
    @abstractmethod
    def scan(self, doc): ...
    @abstractmethod
    def fax(self, doc): ...

class OldPrinter(Machine):
    def print(self, doc): ...
    def scan(self, doc): raise NotImplementedError   # forced to fake it
    def fax(self, doc):  raise NotImplementedError   # - and that's an LSP violation too
```

```python
# ✅ Segregate into role interfaces; classes implement only what they are.
from typing import Protocol     # Protocols = structural typing, the Pythonic ISP tool

class Printer(Protocol):
    def print(self, doc) -> None: ...
class Scanner(Protocol):
    def scan(self, doc) -> None: ...
class Fax(Protocol):
    def fax(self, doc) -> None: ...

class OldPrinter:                 # implements ONLY Printer - no fake methods
    def print(self, doc) -> None: ...

class AllInOne:                   # implements all three, by choice
    def print(self, doc) -> None: ...
    def scan(self, doc) -> None: ...
    def fax(self, doc) -> None: ...
```

In Python, `typing.Protocol` is the idiomatic ISP tool: a function can ask for "anything with a `.print()`" via structural typing, without forcing a class hierarchy. (See the Python data model and protocols in 04.1, duck typing *is* interface segregation by default.)

### D - Dependency Inversion Principle

> High-level modules shouldn't depend on low-level modules; **both should depend on abstractions.** And abstractions shouldn't depend on details, details depend on abstractions.

This is the most important one for testability and architecture (we'll lean on it heavily in 27.2's dependency injection section).

```python
# ❌ High-level OrderService is welded to a concrete, low-level Postgres class.
class PostgresOrderRepo:
    def save(self, order): ...   # talks to a real DB

class OrderService:
    def __init__(self):
        self.repo = PostgresOrderRepo()    # <-- hard dependency, can't test without a DB
    def place(self, order):
        self.repo.save(order)
```

`OrderService` (high-level policy) now *requires* Postgres to even instantiate. You can't unit-test it without a database; you can't swap storage; the dependency arrow points the wrong way (policy → detail).

```python
# ✅ Both depend on an abstraction; the concrete detail is injected.
from typing import Protocol

class OrderRepo(Protocol):                 # the abstraction (owned by the domain)
    def save(self, order) -> None: ...

class PostgresOrderRepo:                    # a detail that depends on the abstraction
    def save(self, order) -> None: ...

class InMemoryOrderRepo:                     # another detail - perfect for tests
    def __init__(self): self.saved = []
    def save(self, order) -> None: self.saved.append(order)

class OrderService:
    def __init__(self, repo: OrderRepo):    # dependency INJECTED, not constructed
        self.repo = repo
    def place(self, order) -> None:
        self.repo.save(order)

# Wiring (composition root): real in prod, fake in tests.
service = OrderService(PostgresOrderRepo())          # production
test_service = OrderService(InMemoryOrderRepo())     # test - no DB needed
```

The arrow now points *toward* the abstraction. `OrderService` no longer knows or cares that Postgres exists. This single move, **inject dependencies through the constructor against an interface**, buys you testability, swappability, and the "dependency rule" that underpins clean architecture (27.2). **Abuse warning:** you don't need a DI framework or a Protocol for *every* dependency. Invert the dependencies that you want to *swap* or *fake* (databases, payment gateways, clocks, email), not your `math.sqrt`.

## Composition over inheritance (recap & sharpen)

We met this in 04.1; here's the design-level version. **Inheritance** models IS-A and shares implementation down a hierarchy. **Composition** models HAS-A and assembles behavior from parts. The guidance, "favor composition over inheritance", comes from inheritance's costs: it's the tightest coupling there is (a subclass depends on the parent's *internals*), it's static (fixed at class-definition time), and deep hierarchies become rigid and surprising (the LSP `Square` problem, the "fragile base class").

```python
# ❌ Inheritance to share behavior leads to a combinatorial hierarchy.
class Logger: ...
class FileLogger(Logger): ...
class FileLoggerWithTimestamp(FileLogger): ...        # and now a CONSOLE timestamped one?
class FileLoggerWithTimestampAndJson(FileLoggerWithTimestamp): ...   # explosion
```

```python
# ✅ Compose behavior from small interchangeable parts (Strategy + Decorator in disguise).
from typing import Protocol

class Sink(Protocol):
    def write(self, line: str) -> None: ...

class FileSink:
    def __init__(self, path): self.path = path
    def write(self, line): open(self.path, "a").write(line + "\n")

class ConsoleSink:
    def write(self, line): print(line)

class Logger:
    def __init__(self, sink: Sink, *, timestamp: bool = False):
        self.sink, self.timestamp = sink, timestamp
    def log(self, msg: str) -> None:
        import datetime
        prefix = f"[{datetime.datetime.now():%H:%M:%S}] " if self.timestamp else ""
        self.sink.write(prefix + msg)

# Mix and match at RUNTIME - no class explosion.
Logger(FileSink("app.log"), timestamp=True).log("started")
Logger(ConsoleSink()).log("hello")
```

Rule of thumb: **use inheritance only for genuine IS-A with true substitutability; use composition for "needs the behavior of."** When you catch yourself subclassing just to reuse a method, that's the tell, compose instead.

## Design patterns that actually matter

Design patterns (from the 1994 "Gang of Four" book) are *named solutions to recurring design problems.* Their real value is twofold: (1) they're a **vocabulary**, saying "let's use a Strategy here" in review communicates a whole design in two words; (2) they're **battle-tested shapes** so you don't reinvent a leaky one.

Two honest caveats before we implement them:

1. **Many GoF patterns exist to work around limitations of static OO languages** (Java/C++). Python has first-class functions, duck typing, decorators, and dynamic attributes, so some patterns collapse into "just pass a function" or "just use a closure." We'll flag these.
2. **A pattern is a means, never an end.** Reaching for a pattern because it's elegant, rather than because the problem demands it, is over-engineering. The smell is "I built a `AbstractFactoryBuilderStrategy` for a script that reads one CSV."

We'll cover them in the three GoF categories, and for the three most valuable we'll do full **Build it** implementations with tests below.

### Creational patterns (how objects get made)

**Factory (Factory Method / Simple Factory).** Centralize object creation so callers don't hardcode concrete classes. Use when the type to create depends on input/config and you want one place that knows the mapping.

```python
from abc import ABC, abstractmethod

class Notifier(ABC):
    @abstractmethod
    def send(self, msg: str) -> None: ...

class EmailNotifier(Notifier):
    def send(self, msg): print(f"email: {msg}")
class SmsNotifier(Notifier):
    def send(self, msg): print(f"sms: {msg}")

def make_notifier(channel: str) -> Notifier:        # the factory
    registry = {"email": EmailNotifier, "sms": SmsNotifier}
    try:
        return registry[channel]()
    except KeyError:
        raise ValueError(f"unknown channel {channel!r}")
```

*When:* you have a family of types and the choice is data-driven. *Abuse:* a factory that only ever makes one class is pure ceremony, just call the constructor.

**Builder.** Construct a complex object step by step, especially when there are many optional parameters and you want readable, validated, immutable results. Use when a constructor would have a dozen arguments.

```python
from dataclasses import dataclass, field

@dataclass
class HttpRequest:
    method: str
    url: str
    headers: dict = field(default_factory=dict)
    body: bytes | None = None
    timeout: float = 30.0

class RequestBuilder:
    def __init__(self, url: str):
        self._method, self._url = "GET", url
        self._headers, self._body, self._timeout = {}, None, 30.0
    def method(self, m): self._method = m; return self          # fluent: return self
    def header(self, k, v): self._headers[k] = v; return self
    def body(self, b): self._body = b; return self
    def timeout(self, t): self._timeout = t; return self
    def build(self) -> HttpRequest:
        if self._body and self._method == "GET":
            raise ValueError("GET cannot have a body")          # validation in build()
        return HttpRequest(self._method, self._url, self._headers, self._body, self._timeout)

req = (RequestBuilder("https://api.nyx.com/charge")
       .method("POST").header("Idempotency-Key", "abc").body(b"{}").build())
```

*When:* many optional fields, step-wise construction, or you want validation at `build()`. *Abuse:* in Python, a dataclass with keyword defaults or `**kwargs` often beats a builder. Reach for a builder when there's real assembly logic or invariants to enforce.

**Singleton, and why it's usually a mistake.** Singleton guarantees one instance globally. It's the pattern most worth *talking teams out of*. It's a global variable wearing a costume: it hides dependencies (callers reach for the global instead of receiving it), it makes tests order-dependent and hard to isolate (shared mutable state leaks between tests), and it fights the Dependency Inversion Principle (you can't inject a fake).

```python
# The "pattern" - module-level state in Python is already a de facto singleton:
class _Config:
    def __init__(self): self.settings = {}
config = _Config()        # import this; everyone shares it

# Why it bites: a test that mutates config.settings poisons the next test.
```

*When (rarely):* a genuinely process-wide resource with no per-test variation, a logging root, a connection pool. *Better default:* create one instance at your **composition root** and *inject* it (DIP). You get the "one instance" benefit without the global-state pain. If you remember one thing: **prefer "one instance, injected" over "one instance, globally reachable."**

### Structural patterns (how objects compose into bigger structures)

**Adapter.** Wrap an incompatible interface so it fits the one your code expects. The textbook use: integrating a third-party library whose API you don't control.

```python
class StripeGateway:                       # third-party shape you can't change
    def create_charge(self, cents, token): return {"id": "ch_1", "amount": cents}

class PaymentGateway(Protocol):            # the shape YOUR code wants
    def charge(self, dollars: float, card: str) -> str: ...

class StripeAdapter:                        # adapts one to the other
    def __init__(self, stripe: StripeGateway): self._stripe = stripe
    def charge(self, dollars: float, card: str) -> str:
        result = self._stripe.create_charge(round(dollars * 100), card)
        return result["id"]
```

*When:* bridging a vendor SDK to your domain interface, keeps the vendor's quirks in one quarantined class. *Abuse:* don't adapt code you own; just change it.

**Decorator (the pattern), and Python's `@decorator`.** Add behavior to an object *dynamically* by wrapping it, without touching its class. This is the pattern that *Python's syntax is named after*, and Python's function decorators are a direct, idiomatic implementation.

```python
import functools, time

def timed(fn):                              # a Python decorator IS the Decorator pattern
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:
            print(f"{fn.__name__} took {time.perf_counter()-start:.4f}s")
    return wrapper

@timed
def fetch_report(): time.sleep(0.1); return "data"
```

You can stack decorators (`@timed`, `@cached`, `@retry`) to compose orthogonal behaviors, the runtime alternative to the class explosion we saw earlier. *When:* cross-cutting concerns (timing, caching, retry, auth) you want to add/remove independently. *Abuse:* a tower of five decorators on one function is hard to debug; keep the stack shallow and each layer single-purpose.

**Facade.** Provide a simple, unified interface over a complicated subsystem. Use when callers shouldn't need to know about ten internal classes to do one common task.

```python
class Facade:                               # one front door over messy internals
    def __init__(self):
        self._validator, self._charger, self._mailer = Validator(), Charger(), Mailer()
    def checkout(self, order):              # callers see ONE method, not three subsystems
        self._validator.check(order)
        charge_id = self._charger.charge(order.total, order.card)
        self._mailer.receipt(order.email, charge_id)
        return charge_id
```

*When:* you want to hide subsystem complexity and reduce coupling between clients and internals. (Our `process_order` coordinator from the clean-code section was a tiny facade.) *Abuse:* a facade that just forwards one call to one object adds nothing.

**Proxy.** A stand-in that controls access to the real object, for lazy loading, caching, access control, or remoting. Ties directly to reverse proxies and the proxy concepts in 09.3 (a reverse proxy is this pattern at the network layer: a stand-in in front of your real servers doing auth, caching, rate limiting).

```python
class ExpensiveReport:
    def __init__(self): print("...heavy init..."); self.data = "big"
    def get(self): return self.data

class LazyReportProxy:                       # virtual proxy: defer creation until needed
    def __init__(self): self._real = None
    def get(self):
        if self._real is None:               # access control / lazy init happens here
            self._real = ExpensiveReport()
        return self._real.get()
```

*When:* control access, defer cost, add caching/logging/auth transparently. *Abuse:* don't proxy when a decorator or plain caching dict is simpler.

### Behavioral patterns (how objects communicate and share responsibility)

These are the workhorses. We'll summarize each, then implement Strategy, Observer, and Decorator fully in **Build it**.

**Strategy.** Define a family of interchangeable algorithms and select one at runtime. (Our Open/Closed shipping example was exactly this.) *When:* you have multiple ways to do one thing (sort orders, price shipping, compress data) chosen by context. In Python, a strategy is often *just a function you pass in.*

**Observer.** Let objects subscribe to events from a subject and get notified on change, the heart of event-driven systems (recap 09.5 message queues, which are Observer scaled across the network). *When:* one change must fan out to many reactions (UI updates, audit logs, cache invalidation) without the subject knowing who's listening.

**State.** Let an object change its behavior when its internal state changes, replace a sprawling `if status == ...` with one class per state. *When:* an object behaves like a state machine (an order: pending → paid → shipped → delivered, each with different allowed actions).

```python
class State(ABC):
    @abstractmethod
    def pay(self, order): ...

class Pending(State):
    def pay(self, order): order.state = Paid(); print("paid")
class Paid(State):
    def pay(self, order): raise ValueError("already paid")

class Order:
    def __init__(self): self.state: State = Pending()
    def pay(self): self.state.pay(self)
```

**Command.** Encapsulate a request as an object, enabling undo/redo, queuing, logging, and replay. *When:* you need to parameterize, queue, or reverse operations (an editor's undo stack, a task queue).

```python
class Command(ABC):
    @abstractmethod
    def execute(self): ...
    @abstractmethod
    def undo(self): ...

class AddText(Command):
    def __init__(self, doc, text): self.doc, self.text = doc, text
    def execute(self): self.doc.append(self.text)
    def undo(self): self.doc.pop()
```

**Iterator.** Provide sequential access to a collection without exposing its internals. **Python has this built in**, `__iter__`/`__next__` and generators *are* the Iterator pattern. You almost never implement it by hand; you write a generator.

```python
def fibonacci():                  # a generator IS an iterator - the Pythonic version
    a, b = 0, 1
    while True:
        yield a
        a, b = b, a + b
```

**Template Method.** Define the skeleton of an algorithm in a base method, letting subclasses fill in specific steps. *When:* several variants share the same overall flow but differ in a step or two (a data-export pipeline: same load→transform→write skeleton, different transforms).

```python
class Exporter(ABC):
    def export(self, data):                  # the template - fixed skeleton
        rows = self.load(data)
        formatted = self.format(rows)        # the hook subclasses override
        return self.write(formatted)
    def load(self, data): return data
    @abstractmethod
    def format(self, rows): ...
    def write(self, s): return s

class CsvExporter(Exporter):
    def format(self, rows): return "\n".join(",".join(r) for r in rows)
```

*Abuse:* Template Method uses inheritance; if the steps vary a lot, Strategy (composition) is more flexible.

**Visitor.** Separate an algorithm from the object structure it operates on, add new operations over a fixed class hierarchy without modifying those classes. This is *the* pattern in compilers (recap 24.1): an AST has a fixed set of node types, and you want many operations over it (type-check, optimize, generate code) without bloating every node class with every operation.

```python
class Node(ABC):
    @abstractmethod
    def accept(self, visitor): ...

class Num(Node):
    def __init__(self, val): self.val = val
    def accept(self, v): return v.visit_num(self)
class Add(Node):
    def __init__(self, left, right): self.left, self.right = left, right
    def accept(self, v): return v.visit_add(self)

class Evaluator:                       # one visitor = one operation over the whole tree
    def visit_num(self, node): return node.val
    def visit_add(self, node):
        return node.left.accept(self) + node.right.accept(self)

# Add(Num(3), Num(4)).accept(Evaluator()) -> 7
# A new operation (a Printer visitor) needs ZERO changes to Num/Add.
```

*When:* a stable set of node types and a *growing* set of operations (compilers, ASTs, document trees). *Abuse:* if you add node *types* often (not operations), Visitor is the wrong trade, every new type forces editing every visitor.

### Anti-patterns and over-engineering - the other half of the skill

Knowing patterns is half the craft; knowing when *not* to use them is the senior half. Watch for:

- **Golden hammer:** "I know Strategy, so everything is a Strategy." Every problem looks like the pattern you just learned.
- **Premature abstraction / YAGNI violation:** building extension points, plugin systems, and generic frameworks for requirements that don't exist yet. "You Aren't Gonna Need It."
- **God object:** one class that accumulates everything (low cohesion). The opposite of SRP.
- **Spaghetti / lasagna:** no structure, or so many indirection layers you can't trace a call.
- **Cargo culting:** copying a pattern's *form* without its *intent*, an `AbstractSingletonProxyFactoryBean` energy.
- **Speculative generality:** parameters, hooks, and interfaces "in case we need them." You won't; delete them.

The rule worth repeating: **add structure in response to pain you actually feel, not pain you imagine.** Write the simple thing. When it hurts to change (you feel the smell), refactor toward the pattern that relieves *that specific* pain. Patterns are the *destination* of refactoring, not the *starting point* of design.

## Refactoring - the disciplined version

**Refactoring** has a precise definition (Martin Fowler's): *changing the internal structure of code to make it easier to understand and cheaper to modify, **without changing its observable behavior**.* That last clause is everything. Refactoring is not "rewriting" and not "adding features", it's behavior-preserving restructuring.

The discipline that makes it safe:

1. **Have tests first.** Refactoring without tests is just "changing code and hoping." The tests are your safety net, they prove behavior didn't change. (If there are no tests, your first job is *characterization tests*, see the mini-project.)
2. **Take small steps.** Extract one function. Run the tests. Rename one variable. Run the tests. Each step is so small you can't break much, and if a test goes red you know *exactly* which tiny step did it. Never refactor for an hour and *then* run tests.
3. **Separate refactoring from feature work.** Two hats: the "refactoring hat" (structure changes, behavior constant, tests stay green) and the "feature hat" (behavior changes, new tests go red→green). Don't wear both at once, it's how you ship subtle bugs.
4. **Commit often.** Each green refactoring step is a commit point (11.1). If a later step goes wrong, you reset to the last green commit, not back to the swamp.

**Common refactorings** you'll use constantly (each maps to a smell from the field guide):

- **Extract Function**, pull a coherent block into a named function. Cures long functions; *the* most common refactoring.
- **Inline Function**, the reverse, when a function's body is clearer than its name.
- **Rename**, make a name reveal intent. Trivial, underrated, highest ratio of clarity-gained to risk.
- **Extract Class**, split a class that grew too many responsibilities (cures God object / low cohesion).
- **Introduce Parameter Object**, bundle a clump of arguments that always travel together into one object (cures long parameter list / primitive obsession).
- **Replace Conditional with Polymorphism**, turn a `switch`/`if-elif` on a type into a class hierarchy or strategy (cures "switch on type"; this is OCP in action).
- **Replace Magic Number with Named Constant**, `total * TAX_RATE`.
- **Decompose Conditional**, extract the condition and branches into named functions so `if is_eligible(user):` reads plainly.

Let's see two of these worked, then we'll do a full multi-step refactor in the mini-project.

```python
# Introduce Parameter Object - before
def book_flight(origin, destination, depart_date, return_date, passengers, cabin_class):
    ...
def price_flight(origin, destination, depart_date, return_date, cabin_class):
    ...   # the same clump of args travels everywhere - a smell

# after: the clump that always travels together becomes a thing with a name and a type

```

```python

def area(shape):
    if shape["type"] == "circle":
        return 3.14159 * shape["r"] ** 2
    elif shape["type"] == "rect":
        return shape["w"] * shape["h"]
    # every new shape edits this function - closed for extension, OCP violated
```

### Strategy: pluggable discount algorithms

```python
# discounts.py
from typing import Protocol
from dataclasses import dataclass

@dataclass(frozen=True)
class Cart:
    subtotal: float
    item_count: int
    customer_tier: str   # "standard" | "gold"

class DiscountStrategy(Protocol):
    def discount(self, cart: Cart) -> float:
        """Return the dollar discount for this cart."""
        ...

class NoDiscount:
    def discount(self, cart: Cart) -> float:
        return 0.0

class PercentOff:
    def __init__(self, pct: float):
        self.pct = pct
    def discount(self, cart: Cart) -> float:
        return cart.subtotal * self.pct

class BulkDiscount:
    """10% off when buying 10+ items."""
    def discount(self, cart: Cart) -> float:
        return cart.subtotal * 0.10 if cart.item_count >= 10 else 0.0

def final_price(cart: Cart, strategy: DiscountStrategy) -> float:
    return round(cart.subtotal - strategy.discount(cart), 2)

# In Python a strategy can also be a plain function - sometimes the cleanest form:
def gold_tier_discount(cart: Cart) -> float:
    return cart.subtotal * 0.15 if cart.customer_tier == "gold" else 0.0
```

```python

def test_percent_off():
    cart = Cart(subtotal=100.0, item_count=2, customer_tier="standard")
    assert final_price(cart, PercentOff(0.20)) == 80.0

def test_bulk_discount_applies_at_threshold():
    cart = Cart(subtotal=200.0, item_count=10, customer_tier="standard")
    assert final_price(cart, BulkDiscount()) == 180.0

def test_bulk_discount_below_threshold():
    cart = Cart(subtotal=200.0, item_count=9, customer_tier="standard")

```

The power: `final_price` never changes when marketing invents a new promotion. New algorithm = new class implementing the protocol = new strategy passed in. That's Open/Closed and Strategy in one.

### Observer: an event-driven order pipeline

```python
# orders.py
from typing import Protocol
from dataclasses import dataclass, field

@dataclass
class OrderPaidEvent:
    order_id: str
    amount: float

class Observer(Protocol):
    def on_order_paid(self, event: OrderPaidEvent) -> None: ...

class OrderSubject:
    """The subject doesn't know or care who's listening."""
    def __init__(self):
        self._observers: list[Observer] = []
    def subscribe(self, observer: Observer) -> None:
        self._observers.append(observer)
    def unsubscribe(self, observer: Observer) -> None:
        self._observers.remove(observer)
    def pay_order(self, order_id: str, amount: float) -> None:
        # ... real payment logic would go here ...
        event = OrderPaidEvent(order_id, amount)
        for observer in self._observers:        # fan out to all listeners
            observer.on_order_paid(event)

# Concrete observers - each one orthogonal, added/removed independently:
class ReceiptEmailer:
    def __init__(self): self.sent: list[str] = []
    def on_order_paid(self, event): self.sent.append(event.order_id)

class AnalyticsTracker:
    def __init__(self): self.revenue = 0.0
    def on_order_paid(self, event): self.revenue += event.amount

class AuditLog:
    def __init__(self): self.entries: list[str] = []
    def on_order_paid(self, event):
        self.entries.append(f"order {event.order_id} paid ${event.amount}")
```

```python
# test_orders.py
from orders import OrderSubject, ReceiptEmailer, AnalyticsTracker, AuditLog

def test_all_observers_notified():
    subject = OrderSubject()
    emailer, analytics, audit = ReceiptEmailer(), AnalyticsTracker(), AuditLog()
    for obs in (emailer, analytics, audit):
        subject.subscribe(obs)

    subject.pay_order("ORD-1", 99.50)

    assert emailer.sent == ["ORD-1"]
    assert analytics.revenue == 99.50
    assert audit.entries == ["order ORD-1 paid $99.5"]

def test_unsubscribe_stops_notifications():
    subject = OrderSubject()
    analytics = AnalyticsTracker()
    subject.subscribe(analytics)
    subject.unsubscribe(analytics)

    subject.pay_order("ORD-2", 50.0)
    assert analytics.revenue == 0.0   # never notified after unsubscribe
```

This is exactly how you'd decouple side effects from a core action: paying an order *publishes an event*; emailing, analytics, and auditing *react*, and none of them knows about the others. Scale this across a network boundary and you have a message queue (09.5). The pattern is the same.

### Decorator: composable cross-cutting behavior

```python
# decorators.py
import functools, time

def retry(times: int = 3):
    """Retry a flaky call up to `times` attempts."""
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            last_exc = None
            for attempt in range(times):
                try:
                    return fn(*args, **kwargs)
                except Exception as exc:          # noqa: BLE001 (intentional broad catch)
                    last_exc = exc
            raise last_exc
        return wrapper
    return deco

def timed(fn):
    """Record elapsed time on the wrapper for inspection/testing."""
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:
            wrapper.last_elapsed = time.perf_counter() - start
    return wrapper

# Stack them - orthogonal concerns compose cleanly:
@timed
@retry(times=3)
def fetch(url, _state={"calls": 0}):
    _state["calls"] += 1
    if _state["calls"] < 2:
        raise ConnectionError("flaky")
    return "ok"
```

```python
# test_decorators.py
import pytest
from decorators import retry, timed

def test_retry_succeeds_after_failures():
    calls = {"n": 0}
    @retry(times=3)
    def flaky():
        calls["n"] += 1
        if calls["n"] < 3:
            raise ValueError("not yet")
        return "done"
    assert flaky() == "done"
    assert calls["n"] == 3

def test_retry_exhausts_and_raises():
    @retry(times=2)
    def always_fails():
        raise RuntimeError("nope")
    with pytest.raises(RuntimeError):
        always_fails()

def test_timed_records_elapsed():
    @timed
    def work(): return 42
    assert work() == 42
    assert work.last_elapsed >= 0
```

Note `functools.wraps`, without it the decorator clobbers the wrapped function's name and docstring, breaking introspection and other tooling. That's a real bug that ships easily; it's why the test could check `work.__name__` and you should in production code.

### A worked refactor: messy function → clean, tested code

Here's a function in a style you'll often inherit, it works, the tests (once we write them) pass, but it's a brick.

```python
# BEFORE - works, but: long, mixed levels, magic numbers, no separation of concerns
def handle(req):
    if "user_id" not in req or "items" not in req:
        return {"status": 400, "error": "bad request"}
    total = 0
    for it in req["items"]:
        if it["qty"] <= 0:
            return {"status": 400, "error": "bad qty"}
        total += it["price"] * it["qty"]
    if req.get("tier") == "gold":
        total = total * 0.85
    total = total * 1.08
    if total > 1000:
        total = total - 50
    return {"status": 200, "total": round(total, 2)}
```

Step 1: **Pin behavior with characterization tests** (capture what it does *now*, before touching it):

```python
def test_handle_basic():
    req = {"user_id": 1, "items": [{"price": 100, "qty": 2}]}
    assert handle(req) == {"status": 200, "total": 216.0}   # 200 * 1.08

def test_handle_gold_and_bulk():
    req = {"user_id": 1, "tier": "gold", "items": [{"price": 1000, "qty": 2}]}
    # 2000 * 0.85 = 1700, * 1.08 = 1836, - 50 (over 1000) = 1786.0

def test_handle_bad_request():
```

Step 2: refactor in small green steps, extract validation, extract subtotal, name the constants, separate the pricing rules. Behavior stays identical; the characterization tests stay green the whole way.

```python
# AFTER - same behavior (tests still pass), now readable and changeable
from dataclasses import dataclass

TAX_RATE = 0.08
GOLD_DISCOUNT = 0.15
BULK_THRESHOLD = 1000.0
BULK_DISCOUNT = 50.0

class BadRequest(Exception): ...

@dataclass
class LineItem:
    price: float
    qty: int

def parse_request(req: dict) -> tuple[str, list[LineItem]]:
    if "user_id" not in req or "items" not in req:
        raise BadRequest("bad request")
    items = []
    for it in req["items"]:
        if it["qty"] <= 0:
            raise BadRequest("bad qty")
        items.append(LineItem(it["price"], it["qty"]))
    return req.get("tier", "standard"), items

def subtotal(items: list[LineItem]) -> float:
    return sum(i.price * i.qty for i in items)

def apply_pricing(amount: float, tier: str) -> float:
    if tier == "gold":
        amount *= (1 - GOLD_DISCOUNT)
    amount *= (1 + TAX_RATE)
    if amount > BULK_THRESHOLD:
        amount -= BULK_DISCOUNT
    return round(amount, 2)

def handle(req: dict) -> dict:
    try:
        tier, items = parse_request(req)
    except BadRequest as e:
        return {"status": 400, "error": str(e)}
    total = apply_pricing(subtotal(items), tier)
    return {"status": 200, "total": total}
```

Every piece now has a name and a test surface. `apply_pricing` is independently testable; the magic numbers are named business constants; `handle` reads like a sentence. And because the characterization tests stayed green through every step, you *know* you didn't change behavior. That confidence, "I improved the code and provably didn't break it", is the entire payoff of refactoring under tests.

Target end state:

```python
from typing import Protocol
from dataclasses import dataclass

@dataclass(frozen=True)
class SalesRow:
    name: str
    amount: float

class SalesRepository(Protocol):
    def fetch_sales(self) -> list[SalesRow]: ...

class Filter(Protocol):
    def keep(self, row: SalesRow) -> bool: ...

class Formatter(Protocol):
    def render(self, rows: list[SalesRow], total: float) -> str: ...

class ReportService:
    def __init__(self, repo: SalesRepository, filt: Filter, fmt: Formatter):
        self.repo, self.filt, self.fmt = repo, filt, fmt
    def generate(self) -> str:
        rows = [r for r in self.repo.fetch_sales() if self.filt.keep(r)]
        total = sum(r.amount for r in rows)
        return self.fmt.render(rows, total)
```

Write the concrete `Filter`s, `Formatter`s, an `InMemorySalesRepository` for tests and a `SqliteSalesRepository` for production, and a full pytest suite. When you're done, the original 30-line brick is a set of tiny, individually-tested, single-responsibility classes, and adding a new format or filter never touches existing code. Write a short paragraph reflecting on *which smell each step removed* and *which SOLID principle each move served*. That reflection is what cements the skill.

## Common mistakes

- **Cargo-culting patterns.** Adding a factory/builder/singleton because it's "professional." A pattern with no problem is just complexity. Add structure to relieve *felt* pain.
- **Premature abstraction (DRY gone wrong).** Unifying two things that look alike but aren't the same *knowledge*. Prefer duplication over the wrong abstraction; wait for the Rule of Three.
- **Refactoring without tests.** That's not refactoring, it's gambling. Pin behavior first.
- **Wearing both hats.** Mixing a refactor and a feature in one change. When a test goes red you won't know if you broke behavior or that's the new behavior. Separate them, separate commits.
- **Big-bang refactors.** Refactoring for an hour, then running tests, then debugging a red wall. Tiny steps, run tests after each.
- **Inheritance for code reuse.** Subclassing to grab a method leads to fragile hierarchies and LSP violations. Compose instead.
- **God `utils.py`.** The junk drawer of unrelated functions. Low cohesion. Give things homes.
- **Boolean flag arguments.** `process(data, True)`, the call site is unreadable and the function does two things. Split it.
- **Comments instead of names.** A comment explaining a confusing line is a refactoring you skipped. Rename or extract.

## On the job / interview angle

- **"How would you make this more maintainable?"** is the standard follow-up after you solve a coding problem. Reach for: extract functions, name things, separate concerns, identify the axis that varies and make *that* extensible (Strategy/OCP). Narrate the *why* (cohesion, coupling, testability), not just the *what*.
- **"Design X" object-design questions** (parking lot, elevator, deck of cards, vending machine) are SOLID-and-patterns exams in disguise. State your interfaces, justify composition vs inheritance, name the patterns (State for the vending machine, Strategy for pricing, Observer for events).
- **"What's wrong with Singleton?"** is a real interview question. Answer: hidden global state, hard to test/isolate, fights dependency injection. Better: one instance created at the composition root and injected.
- **In code review** (much more in 27.2), the most valuable comments you give are clean-code and design ones: "this function does two things," "this `if` chain on type wants polymorphism," "let's inject this dependency so it's testable." Speaking the pattern vocabulary makes reviews fast and precise.
- **The trap to avoid:** over-engineering in an interview. If asked for a simple thing, building an AbstractFactory signals poor judgment, not seniority. Right-size the design and *say* you're right-sizing it.

## Exercises

**1.** Name the dominant smell and the refactoring that cures it:
```python
def f(a, b, c, d, e, f, g): ...
```

<details><summary>Solution</summary>

Smell: **long parameter list** (and likely **primitive obsession**). Cure: **Introduce Parameter Object**, bundle the arguments that travel together into a dataclass. Seven positional args is also a readability and call-site-error hazard (easy to transpose).
</details>

**2.** Is this a Liskov violation? Why?
```python
class Bird:
    def fly(self): ...
class Penguin(Bird):
    def fly(self): raise NotImplementedError("penguins can't fly")
```

<details><summary>Solution</summary>

Yes. Any code that takes a `Bird` and calls `fly()` will break on a `Penguin`, so `Penguin` is not substitutable for `Bird`, an LSP violation. The model is wrong: not all birds fly. Fix by segregating the interface (ISP): a `FlyingBird` type with `fly()`, and `Bird` without it; `Penguin` is a `Bird`, not a `FlyingBird`. This is a case where the *taxonomy* (biology) doesn't match the *behavioral contract* (can fly), and the contract wins.
</details>

**3.** Refactor this with Replace-Conditional-with-Polymorphism and name the SOLID principle it satisfies:
```python
def sound(animal):
    if animal == "dog": return "woof"
    elif animal == "cat": return "meow"
    elif animal == "cow": return "moo"
```

<details><summary>Solution</summary>

```python
from abc import ABC, abstractmethod
class Animal(ABC):
    @abstractmethod
    def sound(self) -> str: ...
class Dog(Animal):
    def sound(self): return "woof"
class Cat(Animal):
    def sound(self): return "meow"
class Cow(Animal):
    def sound(self): return "moo"
```
Adding a new animal is a new class, existing classes are untouched. This satisfies the **Open/Closed Principle** (open for extension, closed for modification). Caveat: for a fixed, tiny set that never grows, the original dict-lookup (`{"dog": "woof", ...}`) is simpler and fine, don't over-engineer. Use polymorphism when each type has *behavior*, not just a return value.
</details>

**4.** Which pattern fits: "I need to add logging and caching to an existing function without modifying it, and be able to turn each on/off independently"?

<details><summary>Solution</summary>

**Decorator**, wrap the function to add orthogonal behaviors that compose and can be stacked/removed independently. In Python, literally `@logged` and `@cached` decorators. (Strategy is about swapping *the* algorithm; Decorator is about *adding* behavior around it.)
</details>

**5.** Why is "prefer duplication over the wrong abstraction" not a contradiction of DRY?

<details><summary>Solution</summary>

DRY is about not duplicating *knowledge* (a single business rule, a single fact), having one authoritative source so a change happens in one place. It is *not* about deduplicating code that merely *looks* similar. Two code blocks that are identical today but represent *different decisions* will diverge tomorrow; merging them prematurely couples unrelated things, and the shared abstraction becomes a prison full of flags. So: dedupe knowledge (real DRY), tolerate incidental similarity until the Rule of Three reveals the true shared shape.
</details>

**6.** You inherit a 200-line function with no tests and need to add a feature. What's your first move?

<details><summary>Solution</summary>

**Write characterization tests** that pin the current behavior (capture what it actually does now, even if that includes bugs). Only once you have a green safety net do you refactor, in small steps, tests green throughout, to make room for the feature. Then, *separately* (feature hat on), add the new behavior with new tests. Never refactor untested legacy code by inspection alone; the tests are what let you change it safely.
</details>
