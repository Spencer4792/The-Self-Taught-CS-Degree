# Chapter 29.4 - Industrial and Embedded C++: the Software Inside a Fab Tool

> _Goal: See what C++ looks like when the program controls a physical machine and a bug scraps product or bends metal. You'll learn why industrial code bans allocation, blocking, and exceptions from its hot path, how a fixed-rate control loop and a state machine together form the skeleton of nearly every equipment controller, and how watchdogs and fail-safe design keep a tool from hurting itself when the software goes wrong. You'll build a complete simulated CMP polisher controller (state machine, control loop, sensors, ring-buffer telemetry) with tests that inject sensor faults and prove the code handles them._

So far in this track you've learned C++ the language: values and references, RAII and ownership, and in Chapter 29.3, manual memory strategies like pools and arenas. This chapter is about where all of that discipline gets used for real. The multi-million-dollar machines inside a semiconductor fab (polishers, etchers, deposition chambers, wafer-handling robots) are run by C and C++ programs, and those programs are written in a style that can look strange the first time you see it: no `new` after startup, no exceptions, functions that return error codes like it's 1985. By the end of this chapter you'll understand that this style isn't backwardness. It's the same engineering judgment you've been building all along, applied to a world where the cost of a surprise is measured in scrapped wafers.

Our running example is the controller for a **CMP** (chemical mechanical planarization) tool: the machine that polishes a wafer flat between process layers by pressing it against a rotating pad flooded with abrasive slurry. You saw where CMP fits in the fab loop in [17.5](../17-Semiconductors/17.5-semiconductor-manufacturing.md), and you'll meet the machine itself (the pad, the carrier, the slurry chemistry) in Chapter 17.7. Here we care about its brain.

## Start here: the program that can never shrug

Think about the software you've written so far in this book. A web scraper that crashes gets rerun. A server that leaks memory gets restarted by a supervisor at 3 a.m. and nobody notices. Even a database that goes down mostly just makes people wait. Software culture is built around a comforting fact: for most programs, failure is cheap and retry is free.

Now put your program in charge of a CMP polisher. A wafer carrier is pressing a nearly finished wafer, one that has already absorbed weeks of processing and carries real monetary value, face-down against a pad spinning at highway-tire speeds, with the pressure held to a tight tolerance. If your process hangs for two seconds, the tool doesn't wait patiently. Physics keeps happening. The pad keeps spinning, the pressure stays wherever your last command left it, and the wafer polishes past its target. That wafer is scrap. If the fault is uglier (a carrier that descends when it shouldn't), you can gouge the pad or crash the robot arm, and now the tool is down for repair while a production line waits behind it.

That is the defining fact of industrial software: **the machine does not pause when the program does.** Every design rule in this chapter falls out of that one sentence. The program must respond on a fixed schedule (because physics runs on a fixed schedule), it must never do anything with unpredictable timing (because a rare 100 ms hiccup is indistinguishable from a hang, as far as the wafer is concerned), and when something does go wrong, it must fail toward safety: lift the head, stop the platen, hold still, and yell for a human.

The two vendors whose CMP tools dominate fabs, Applied Materials and Ebara, compete on exactly this kind of thing. Process performance sells tools, but uptime and repeatability keep them sold, and both are largely software qualities. A fab expects a tool to run around the clock for months, doing the same recipe thousands of times with the same result. The controller's job is to be boring, forever.

## What makes industrial software different

It helps to name the differences explicitly, because they invert several instincts you've built writing application code.

**The cost model is inverted.** In application software, developer time is expensive and CPU time is cheap, so we optimize for flexibility and speed of change. In equipment software, a single field failure can cost more than a year of developer time: scrapped product, tool downtime billed by the hour, an engineer flown to a fab on another continent. So the code optimizes for predictability, reviewability, and provability, even where that makes it more tedious to write.

**Throughput doesn't matter; the worst case does.** Your Python performance work in [16.4](../16-Data/16.4-performance-optimization.md) chased averages: mean request latency, total runtime. A control loop couldn't care less about the average. If the loop meets its deadline 999,999 times out of a million and misses badly once, the tool faults once, maybe once a day at typical loop rates. All the interesting engineering is about the slowest iteration you will ever have, called the **worst-case execution time** (WCET).

**The program runs for months.** A memory leak of one small allocation per wafer is invisible in testing and kills the tool in month three. Fragmentation, drifting clocks, counters that wrap: every slow-burn failure mode gets its chance. This is why the discipline from 29.3 (allocate everything up front, from pools you control) stops being a performance trick and becomes a correctness requirement.

**Failure must be designed, not just handled.** Application code treats errors as exceptional paths to log and limp past. Equipment code treats faults as first-class states with their own entry conditions, safe outputs, and exit procedures. A good controller spends more of its source code on what happens when things go wrong than on the happy path, and that ratio is a sign of maturity, not paranoia.

## Hard and soft real time

"Real-time software" does not mean "fast software." It means software whose correctness depends on *when* answers arrive, not just what they are. The field splits the idea in two:

- A **hard real-time** deadline is one where a late answer is a wrong answer. The loop that holds polish downforce at 100 Hz is hard real-time: if this tick's valve command arrives 50 ms late, the pressure wandered unsupervised for five ticks, and no amount of correct arithmetic afterward undoes that. Miss the deadline and you have failed, full stop.
- A **soft real-time** deadline is one where lateness degrades value but doesn't destroy it. The tool's operator screen updating at 10 Hz is soft real-time: a stuttering display is annoying, and chronically stale data is a problem, but one late frame harms nothing.

A real tool controller is layered accordingly. The innermost loops (servo control, pressure regulation, interlock checking) run on a real-time operating system or a dedicated microcontroller, where the scheduler can *guarantee* that the control task gets the CPU on schedule. The outer layers (recipe management, the operator interface, the link to the fab's host computers) run as ordinary software on an ordinary OS, because their deadlines are soft. The skill is knowing which ring of the onion each piece of code lives in, and never letting soft-ring habits (allocation, file I/O, "it's usually fast") leak into the hard ring.

A general-purpose OS like Linux or Windows makes no hard guarantees at all: as you saw in [5.3](../05-Systems/05.3-operating-systems.md), the scheduler may preempt you whenever it likes, for as long as it likes. We'll demonstrate that concretely in a moment, and it's why none of this chapter's code pretends to be truly hard real-time. We simulate the timing structure with `std::chrono`, which teaches the pattern honestly; making the guarantees real is what an RTOS is for.

## The control loop: read, decide, actuate

Strip away everything else and an equipment controller is one pattern repeated at a fixed period, forever:

```text
every tick (say, every 10 ms):
    READ     all sensors            (pressure, rotation, position, switches)
    DECIDE   what to do             (state machine + control laws)
    ACTUATE  write all outputs      (valves, motors, indicators)
    RECORD   a telemetry snapshot
```

The fixed period is the metronome the whole design keeps time to. Control theory assumes it: a controller tuned for 10 ms ticks misbehaves if ticks arrive at 10, 10, 47, 10 ms. Fault detection assumes it: "pressure out of band for 25 consecutive ticks" only means something if ticks are evenly spaced. So the first skill is pacing a loop correctly. Here is the canonical shape, with a detail that matters more than it looks:

```cpp
#include <chrono>
#include <cstdio>
#include <thread>

int main() {
    using clock = std::chrono::steady_clock;
    constexpr auto period = std::chrono::milliseconds(10);

    auto next = clock::now() + period;
    long long worst_late_us = 0;

    for (int tick = 0; tick < 200; ++tick) {
        volatile double sum = 0.0;                 // stand-in for real work
        for (int i = 0; i < 1000; ++i) sum = sum + i * 0.5;

        std::this_thread::sleep_until(next);       // wait for the deadline
        long long late = std::chrono::duration_cast<std::chrono::microseconds>(
                             clock::now() - next).count();
        if (late > worst_late_us) worst_late_us = late;
        next += period;   // schedule from the deadline, not from now()
    }
    std::printf("200 ticks at 10 ms; worst wake-up lateness: %lld us\n",
                worst_late_us);
    return 0;
}
```

```text
(one run on a busy Linux machine; your numbers will differ)
200 ticks at 10 ms; worst wake-up lateness: 9101 us
```

Two lessons hide in that output. First, the scheduling detail: `next += period` advances the deadline from the *previous deadline*, so any lateness on one tick gets absorbed instead of accumulating. The tempting alternative, sleeping for a fixed duration after the work, drifts, because it adds the work time to every period. Watch:

```cpp
#include <chrono>
#include <cstdio>
#include <thread>

int main() {
    using clock = std::chrono::steady_clock;
    using std::chrono::duration_cast;
    using std::chrono::milliseconds;
    constexpr auto period = milliseconds(5);
    constexpr int ticks = 200;   // intended runtime: exactly 1000 ms

    auto t0 = clock::now();
    for (int i = 0; i < ticks; ++i) {
        volatile double sum = 0.0;
        for (int j = 0; j < 40000; ++j) sum = sum + j;   // the "work"
        std::this_thread::sleep_for(period);             // BUG: ignores work time
    }
    long long drift_for =
        duration_cast<milliseconds>(clock::now() - t0).count() - 1000;

    t0 = clock::now();
    auto next = t0 + period;
    for (int i = 0; i < ticks; ++i) {
        volatile double sum = 0.0;
        for (int j = 0; j < 40000; ++j) sum = sum + j;
        std::this_thread::sleep_until(next);             // wait for the deadline
        next += period;
    }
    long long drift_until =
        duration_cast<milliseconds>(clock::now() - t0).count() - 1000;

    std::printf("sleep_for   drift after 200 ticks: +%lld ms\n", drift_for);
    std::printf("sleep_until drift after 200 ticks: +%lld ms\n", drift_until);
    return 0;
}
```

```text
(one run; the exact sleep_for drift depends on the machine)
sleep_for   drift after 200 ticks: +426 ms
sleep_until drift after 200 ticks: +0 ms
```

The `sleep_for` version ran 43% long over just one second. That clock is useless as a metronome. The second lesson is in the first program's "worst lateness" number: nine *milliseconds* late on a 10 ms period, courtesy of the ordinary OS scheduler. A general-purpose OS will occasionally park your thread for about as long as your entire budget. That single measurement is the argument for real-time operating systems, condensed.

### The three sins of the hot path

Once the loop is paced, the body of the loop must be able to *keep* the pace on every tick, including the unluckiest one. Three categories of operation are banned from the hot path because their worst case is unbounded or wildly larger than their average:

1. **Allocation.** `new`, `malloc`, and everything that hides them: growing a `std::vector`, building a `std::string`, copying a `std::function` with captured state. As you learned in 29.3, a general-purpose allocator searches free lists, may take a lock shared with other threads, and may ask the OS for pages. Usually 100 nanoseconds; occasionally a page fault and a trip through the kernel. "Occasionally" is the problem.
2. **Blocking.** File writes, prints to a console, mutex waits, anything touching the network. Any of these can stall for milliseconds. The classic beginner's version of this sin is a `printf` for debugging inside the loop, which works fine until the terminal buffer fills and one call blocks for an entire tick.
3. **Throwing.** A thrown exception walks the stack running destructors, and on mainstream implementations the unwind machinery's timing is unpredictable, and some of it may even allocate. Worse, an exception is a non-local jump: it abandons the rest of the tick, meaning the ACTUATE step never runs and the outputs are whatever last tick left them. Most equipment codebases compile hot-path code with `-fno-exceptions` and make the question moot.

Notice what these have in common: each is a convenience that trades a great average case for a bad worst case. That's exactly the trade real-time code refuses. The rule of thumb in industry is simple to state: *all allocation happens at startup; the loop only ever touches memory that already exists.* The next section is about how to live comfortably under that rule.

## Deterministic memory: everything pre-allocated

If the loop can't allocate, every container it uses must have its capacity fixed before the loop starts. There are three standard moves.

**Pre-size the standard containers.** `std::vector::reserve(n)` at startup, then never exceed `n`. This works but is fragile: nothing stops a later edit from pushing element `n+1` and triggering a silent reallocation in the hot path.

**Use pools and arenas** from 29.3 for objects with dynamic lifetimes: allocate a fixed block at startup and hand out slots from it, so "allocation" becomes a couple of pointer operations with a known worst case.

**Use fixed-capacity containers**: containers whose storage lives inside the object itself, like a `std::array` with a count, so overflow is impossible by construction rather than by promise. This is the most common idiom in equipment code, and it takes twenty lines to build:

```cpp
#include <cstddef>
#include <cstdio>

template <typename T, std::size_t N>
class FixedVector {
public:
    bool push_back(const T& value) {
        if (count_ == N) return false;   // full: refuse, never reallocate
        data_[count_++] = value;
        return true;
    }
    void clear() { count_ = 0; }
    std::size_t size() const { return count_; }
    static constexpr std::size_t capacity() { return N; }
    T&       operator[](std::size_t i)       { return data_[i]; }
    const T& operator[](std::size_t i) const { return data_[i]; }
    T* begin() { return data_; }
    T* end()   { return data_ + count_; }

private:
    T data_[N]{};            // storage lives inside the object: no heap
    std::size_t count_ = 0;
};

int main() {
    FixedVector<int, 4> readings;
    for (int i = 1; i <= 6; ++i) {
        bool ok = readings.push_back(i * 100);
        std::printf("push %d -> %s\n", i * 100, ok ? "ok" : "REJECTED (full)");
    }
    std::printf("size=%zu capacity=%zu\n", readings.size(), readings.capacity());
    return 0;
}
```

```text
push 100 -> ok
push 200 -> ok
push 300 -> ok
push 400 -> ok
push 500 -> REJECTED (full)
push 600 -> REJECTED (full)
size=4 capacity=4
```

Look at the interface, because it encodes the philosophy: `push_back` returns `bool` instead of growing or throwing. A full container is a normal, expected condition that the caller must decide about (drop the item, overwrite the oldest, raise a fault), not an emergency the container resolves on its own by grabbing memory. (This simple version requires `T` to be default-constructible, which is fine for the plain sensor-record structs equipment code traffics in; the raw-storage-plus-placement-`new` version that lifts that restriction is exactly the arena machinery from 29.3.) The C++ community has standardized this idea as `inplace_vector` in C++26; every equipment codebase has carried its own for decades.

## The state machine: the backbone of tool control

The control loop gives the tool its heartbeat; a **state machine** gives it its story. At any instant a CMP tool is doing exactly one nameable thing (sitting idle, accepting a wafer, polishing, handing the wafer back, or sitting in a fault waiting for a human), and huge amounts of correctness hang on the transitions between those things being explicit. The head must never descend unless a wafer is confirmed clamped. The platen must never spin during a handoff. Writing this as a pile of booleans (`is_running`, `has_wafer`, `is_paused`...) breeds impossible combinations; writing it as one enum with one transition function makes the impossible states unrepresentable.

You've met state machines as a theory object in [23](../23-Theory-of-Computation/); here is the working form they take in equipment code:

```cpp
#include <cstdio>

enum class ToolState { Idle, Load, Process, Unload, Fault };

const char* name(ToolState s) {
    switch (s) {
        case ToolState::Idle:    return "Idle";
        case ToolState::Load:    return "Load";
        case ToolState::Process: return "Process";
        case ToolState::Unload:  return "Unload";
        case ToolState::Fault:   return "Fault";
    }
    return "?";
}

struct Inputs {
    bool start_requested;
    bool wafer_clamped;
    bool recipe_done;
    bool wafer_removed;
    bool fault_detected;
};

ToolState step(ToolState s, const Inputs& in) {
    if (in.fault_detected) return ToolState::Fault;  // fault beats everything
    switch (s) {
        case ToolState::Idle:    return in.start_requested ? ToolState::Load    : s;
        case ToolState::Load:    return in.wafer_clamped   ? ToolState::Process : s;
        case ToolState::Process: return in.recipe_done     ? ToolState::Unload  : s;
        case ToolState::Unload:  return in.wafer_removed   ? ToolState::Idle    : s;
        case ToolState::Fault:   return s;   // only an operator clears a fault
    }
    return s;
}

int main() {
    ToolState s = ToolState::Idle;
    Inputs script[] = {
        {true,  false, false, false, false},   // operator presses Start
        {false, true,  false, false, false},   // robot reports wafer clamped
        {false, false, false, false, false},   // polishing, nothing new
        {false, false, true,  false, false},   // recipe finished
        {false, false, false, true,  false},   // wafer removed
    };
    std::printf("%s", name(s));
    for (const Inputs& in : script) {
        s = step(s, in);
        std::printf(" -> %s", name(s));
    }
    std::printf("\n");
    return 0;
}
```

```text
Idle -> Load -> Process -> Process -> Unload -> Idle
```

Three design choices here are the ones professionals will look for. The fault check comes *before* the switch, so a fault preempts every state; there is no state from which the tool can ignore a fault. The `Fault` state has no automatic exit; leaving it requires a deliberate operator action, because software that "helpfully" resumes after a fault is software that resumes into the same hazard. And `step` is a pure function from (state, inputs) to state, which makes the machine trivially testable (you just ran a five-line integration test in `main`) and makes the transition rules reviewable by someone who isn't a programmer, like the process engineer who owns the tool. Real controllers have more states (initializing, homing, warming up, paused, maintenance) and often nested machines per subsystem, but the shape never changes: one enum, one transition function, called once per tick from DECIDE.

## Error handling without exceptions

If the hot path can't throw, errors must travel through return values, and the pattern equipment code has converged on looks like this:

```cpp
#include <cstdint>
#include <cstdio>

enum class Err : std::uint8_t {
    Ok = 0,
    SensorTimeout,
    OutOfRange,
    NotCalibrated,
};

struct Reading {
    double value;   // meaningful only when err == Err::Ok
    Err err;
};

const char* to_string(Err e) {
    switch (e) {
        case Err::Ok:            return "Ok";
        case Err::SensorTimeout: return "SensorTimeout";
        case Err::OutOfRange:    return "OutOfRange";
        case Err::NotCalibrated: return "NotCalibrated";
    }
    return "?";
}

[[nodiscard]] Reading read_pressure(int raw) {
    if (raw < 0)    return {0.0, Err::SensorTimeout};   // no reply from the ADC
    if (raw > 4095) return {0.0, Err::OutOfRange};      // impossible 12-bit value
    return {raw * (50.0 / 4095.0), Err::Ok};            // counts -> kPa
}

int main() {
    const int samples[] = {2048, -1, 5000};
    for (int raw : samples) {
        Reading r = read_pressure(raw);
        if (r.err != Err::Ok) {
            std::printf("raw=%5d  error: %s\n", raw, to_string(r.err));
        } else {
            std::printf("raw=%5d  pressure=%.1f kPa\n", raw, r.value);
        }
    }
    return 0;
}
```

```text
raw= 2048  pressure=25.0 kPa
raw=   -1  error: SensorTimeout
raw= 5000  error: OutOfRange
```

The pieces: a small `enum class` of error codes where `Ok` is zero, a result struct that pairs the value with its status, and `[[nodiscard]]` so the compiler warns anyone who calls `read_pressure` and ignores the answer, which restores the one property of exceptions worth keeping: errors can't be silently dropped. This is the hand-rolled ancestor of `std::expected` (C++23), and either form is fine; what matters is the convention. Python taught you "easier to ask forgiveness than permission," and in Python that's right. Here the philosophy inverts, for a concrete reason: an error code is handled *at the call site, this tick*, so the ACTUATE step still runs and still writes sane outputs. An exception would fly up the stack past ACTUATE entirely. In a control loop, "handle it here and now" isn't a style preference. It's what keeps the outputs fresh.

One more convention worth noticing: a failed read still returns a defined `value` (zero), never garbage. Downstream code that forgets to check `err` gets a boring wrong answer instead of an undefined one. Defense in depth.

## Watchdogs and fail-safe design

Everything so far assumes the loop is running. Now assume it isn't: a deadlock, an infinite loop in a rarely taken branch, a crashed process. The machine, remember, does not pause with you. The last valve commands stay latched, the platen keeps spinning, and nothing in the dead program can help.

The answer is a **watchdog**: a mechanism *outside* the code being watched that must be positively told, on a schedule, that all is well. The loop "kicks" the watchdog once per healthy tick; if the kicks stop, the watchdog independently forces safe outputs. It's a dead man's switch: the vigilance is proven by action, so silence itself becomes the alarm. In real equipment the final watchdog is a hardware timer that yanks the outputs to their de-energized state with no software involved at all; the logic, though, you can hold in ten lines:

```cpp
#include <cstdint>
#include <cstdio>

class Watchdog {
public:
    explicit Watchdog(std::uint32_t timeout_ticks) : timeout_(timeout_ticks) {}
    void kick(std::uint32_t now) { last_kick_ = now; }
    bool expired(std::uint32_t now) const { return now - last_kick_ > timeout_; }
private:
    std::uint32_t timeout_;
    std::uint32_t last_kick_ = 0;
};

int main() {
    Watchdog dog(3);                    // must be kicked at least every 3 ticks
    for (std::uint32_t tick = 1; tick <= 10; ++tick) {
        bool loop_healthy = (tick < 6); // the control task hangs at tick 6
        if (loop_healthy) dog.kick(tick);
        if (dog.expired(tick)) {
            std::printf("tick %u: WATCHDOG EXPIRED -- forcing safe state\n", tick);
            break;
        }
        std::printf("tick %u: ok\n", tick);
    }
    return 0;
}
```

```text
tick 1: ok
tick 2: ok
tick 3: ok
tick 4: ok
tick 5: ok
tick 6: ok
tick 7: ok
tick 8: ok
tick 9: WATCHDOG EXPIRED -- forcing safe state
```

The watchdog is one instance of a broader principle: **fail-safe design** means choosing, for every output, what state it falls to when control is lost, and arranging the physical system so that state is harmless. The polish-head valve is plumbed so that no signal means head up. The clamp is chosen so that power loss means wafer held, not wafer dropped. Then the software convention follows: in every state except the ones actively processing, command the safe outputs explicitly, every tick. You'll see that rule enforced in the controller we build below: the ACTUATE step has exactly one `else` branch, and it writes zeros.

Notice also what the demo shows about placement: kick the watchdog at the *end* of the tick, after ACTUATE, so a tick that read sensors and then hung halfway through still counts as missing. A kick at the top of the loop certifies only that the loop started, which is a much weaker claim.

## Talking to hardware

How does a C++ program actually touch a pressure sensor? Two answers cover most of industry.

**Memory-mapped I/O.** On microcontrollers and many industrial boards, device registers are wired into the address space: reading address `0x40020000` doesn't read RAM, it reads the sensor's status register, and writing a certain address opens a valve. The lockers-with-addresses picture from [2.1](../02-Data-Structures/02.1-arrays.md) gains a twist: some lockers are portals, and the hardware on the other side changes their contents on its own schedule.

That last fact breaks an assumption the compiler normally relies on: that memory only changes when the program changes it. Given `while ((regs->status & 1) == 0) {}`, an optimizing compiler sees no writes to `status` in the loop, hoists the read, and spins forever on a stale value. The fix is the `volatile` qualifier, whose actual meaning is narrow and precise: *every read and write of this object is an observable effect; perform each one exactly as written, no caching, no reordering among volatile accesses, no elimination.* Here is the idiom, with the hardware played by a simulator so you can run it anywhere:

```cpp
#include <cstdint>
#include <cstdio>

// The register block exactly as the datasheet lays it out.
struct PressureSensorRegs {
    std::uint32_t status;    // bit 0: DATA_READY
    std::uint32_t data;      // latest raw sample
    std::uint32_t command;   // write 1 to start a conversion
};

// On real hardware this struct is never constructed -- it is *placed*:
//     auto* regs = reinterpret_cast<volatile PressureSensorRegs*>(0x40020000);
// Here we simulate: an ordinary object plays the memory, and a function
// plays the silicon that changes it behind the program's back.
static PressureSensorRegs sim_regs = {0, 0, 0};

void simulate_hardware() {                    // the "silicon" side
    static int busy_cycles = 0;
    if (sim_regs.command == 1) { sim_regs.command = 0; busy_cycles = 3; }
    if (busy_cycles > 0 && --busy_cycles == 0) {
        sim_regs.data = 2048;
        sim_regs.status = sim_regs.status | 1u;   // raise DATA_READY
    }
}

int main() {
    volatile PressureSensorRegs* regs = &sim_regs;

    regs->command = 1;                        // kick off a conversion
    int polls = 0;
    while ((regs->status & 1u) == 0) {        // poll DATA_READY
        simulate_hardware();   // real hardware needs no help; the device acts on its own
        ++polls;
    }
    std::uint32_t raw = regs->data;
    regs->status = regs->status & ~1u;        // acknowledge, clear the flag

    std::printf("data ready after %d polls, raw=%u\n", polls, raw);
    return 0;
}
```

```text
data ready after 3 polls, raw=2048
```

The start-conversion / poll-ready / read-data / acknowledge dance is the universal grammar of device registers; you'll recognize it in every datasheet you ever open. One warning belongs in bold because the mistake is so common: **`volatile` is not a thread-synchronization tool.** It tells the compiler about hardware, nothing more: no atomicity, no memory barriers between threads. For data shared between threads you want `std::atomic` and the machinery from [5.2](../05-Systems/05.2-concurrency.md). Confusing the two compiles fine and fails intermittently, the worst combination.

**Serial protocols.** Sensors and sub-controllers that sit farther away (a slurry flow meter a cable-run from the main controller) talk over serial buses (RS-485, CAN, and industrial protocols layered on them). Conceptually you're back in [Chapter 6](../06-Networking/) with the layers shrunk: bytes arrive one at a time, so the two problems are *framing* (where does a message start and end?) and *integrity* (did the bytes survive the electrically noisy trip through a machine full of motors?). The standard answer is a start byte, a length, a payload, and a checksum, and you'll build exactly that in the exercises.

## Telemetry without disturbing the loop

When a wafer scraps at 2 a.m., the first question the fab asks is "what was the tool doing?" So the controller must keep a record. But the RECORD step lives inside the hot loop, and writing to a file or a socket is blocking, sin number two. The resolution is a structure you already own: the **ring buffer** from [2.3](../02-Data-Structures/02.3-stacks-and-queues.md). The loop appends fixed-size records to a pre-allocated circular array (a couple of stores and an index increment, nothing more), and a separate, low-priority path drains it to disk or network whenever it gets around to it.

One policy decision distinguishes a telemetry ring from the queue you built in 2.3. When the ring fills, this one *overwrites the oldest record* rather than refusing the newest, and it never, ever blocks the writer: the loop's schedule outranks the completeness of the log. Losing thirty stale telemetry records is a shrug; delaying a valve command is a scrapped wafer. It does count what it dropped, though, because a healthy system should also be able to report how lossy its own logging is:

```cpp
#include <cstddef>
#include <cstdint>
#include <cstdio>

struct TelemetryRecord {
    std::uint32_t tick;
    float pressure_kpa;
    float platen_rpm;
    std::uint8_t state;
};

template <std::size_t N>
class TelemetryRing {
public:
    void push(const TelemetryRecord& r) {   // overwrite-oldest; never blocks
        buf_[head_] = r;
        head_ = (head_ + 1) % N;
        if (count_ < N) ++count_;
        else ++dropped_;
    }
    std::size_t size() const { return count_; }
    std::uint64_t dropped() const { return dropped_; }

    // Visit records oldest-to-newest. For the dump path, outside the loop.
    template <typename Fn>
    void for_each(Fn fn) const {
        std::size_t start = (head_ + N - count_) % N;
        for (std::size_t i = 0; i < count_; ++i) fn(buf_[(start + i) % N]);
    }

private:
    TelemetryRecord buf_[N]{};   // fixed storage, allocated with the object
    std::size_t head_ = 0;
    std::size_t count_ = 0;
    std::uint64_t dropped_ = 0;
};

int main() {
    TelemetryRing<4> ring;
    for (std::uint32_t t = 1; t <= 6; ++t) {
        ring.push({t, 20.0f + t, 90.0f, 2});
    }
    std::printf("kept=%zu dropped=%llu; ticks now in ring:", ring.size(),
                static_cast<unsigned long long>(ring.dropped()));
    ring.for_each([](const TelemetryRecord& r) { std::printf(" %u", r.tick); });
    std::printf("\n");
    return 0;
}
```

```text
kept=4 dropped=2; ticks now in ring: 3 4 5 6
```

Note that `TelemetryRecord` is a plain struct of fixed-size fields: no strings, no formatting in the hot path. Rendering numbers into human-readable text is (perhaps surprisingly) expensive and variable-timed; the loop stores raw values and the drain path does the pretty-printing later. This same ring, sized to hold the last several seconds of history, is what makes a "flight recorder" possible: when a fault trips, freeze the ring, and you have a tick-by-tick record of everything leading up to the event. You'll build that in the mini-project.

## Why plant code looks the way it does: a note on standards

Put the pieces together and you can now read industrial C++ for what it is. Codebases in this world usually follow written standards such as **MISRA C++** (born in automotive, adopted widely across safety-conscious industries), the Joint Strike Fighter coding standard, or an in-house equivalent, and the rules sound draconian out of context: no dynamic memory after initialization. No exceptions. No recursion. Every `switch` covers every case. No function pointers where a `switch` will do. Warnings are errors; the compiler runs with everything on (you've been using `-Wall -Wextra` all track; these shops go further, plus static analyzers that enforce the standard mechanically).

Each rule is one of this chapter's lessons frozen into law. No allocation after init: deterministic memory. No exceptions: the hot path must not jump. No recursion: stack depth must be provable at compile time, because a stack overflow in a controller isn't an error message, it's undefined behavior in charge of a machine. The style favors "dumb" constructs (plain structs, explicit switches, fixed arrays), not because the authors don't know the clever alternatives, but because every construct in the codebase must be *reviewable*: a colleague, an auditor, or you-in-five-years must be able to bound its behavior by reading it. Cleverness that resists that reading is a liability regardless of how well it works.

It's a different aesthetic from application C++, and it's worth respecting rather than merely tolerating. Constraints this tight are also, honestly, clarifying: you always know where memory lives, what every state means, and what happens when things fail. Plenty of engineers who could work anywhere choose this world for exactly that reason.

## Build it: a simulated CMP controller

Time to assemble everything (state machine, paced loop structure, sensors and actuators, error codes, telemetry, watchdog) into one working controller with tests, including tests that break the sensors on purpose. We'll build a single file, `cmp_controller.cpp`, in four pieces; each block below continues the same file, and the whole thing compiles with `g++ -std=c++17 -Wall -Wextra`.

Rather than sleeping in real time, the simulation drives ticks as fast as the CPU allows and lets a tick *represent* 10 ms, the standard trick for testing control logic, since the logic only ever sees "one tick elapsed" either way. This is also why the tests are perfectly deterministic and can assert exact tick counts.

**Piece one: configuration and plumbing.** All the magic numbers in one place with names, plus the types you've already built this chapter:

```cpp
// cmp_controller.cpp -- a simulated CMP polisher controller.
// Everything the hot loop touches is pre-allocated; the loop itself never
// allocates, blocks, or throws.
#include <cassert>
#include <cstddef>
#include <cstdint>
#include <cstdio>

// ---------- configuration (one screen, all named, all fixed) ----------------
constexpr double kTickSeconds  = 0.010;   // 100 Hz control loop
constexpr double kTargetKpa    = 30.0;    // recipe downforce at the pad
constexpr double kTargetRpm    = 90.0;    // platen speed
constexpr double kToleranceKpa = 2.0;     // acceptable band while polishing
constexpr std::uint32_t kLoadTicks    = 50;    // 0.5 s simulated robot handoff
constexpr std::uint32_t kUnloadTicks  = 50;
constexpr std::uint32_t kProcessTicks = 500;   // 5 s recipe
constexpr std::uint32_t kSettleTicks  = 150;   // grace period for pressure ramp
constexpr int kMaxSensorErrors  = 5;      // consecutive bad reads -> fault
constexpr int kMaxOutOfTolTicks = 25;     // consecutive out-of-band ticks -> fault

enum class Err : std::uint8_t { Ok = 0, SensorTimeout, OutOfRange };
struct Reading { double value; Err err; };

enum class ToolState : std::uint8_t { Idle, Load, Process, Unload, Fault };
const char* name(ToolState s) {
    switch (s) {
        case ToolState::Idle:    return "Idle";
        case ToolState::Load:    return "Load";
        case ToolState::Process: return "Process";
        case ToolState::Unload:  return "Unload";
        case ToolState::Fault:   return "Fault";
    }
    return "?";
}

struct TelemetryRecord {
    std::uint32_t tick;
    float pressure_kpa;   // -1 when the sensor read failed
    float platen_rpm;
    std::uint8_t state;
};

template <std::size_t N>
class TelemetryRing {
public:
    void push(const TelemetryRecord& r) {
        buf_[head_] = r;
        head_ = (head_ + 1) % N;
        if (count_ < N) ++count_;
        else ++dropped_;
    }
    std::size_t size() const { return count_; }
    std::uint64_t dropped() const { return dropped_; }
    template <typename Fn>
    void for_each(Fn fn) const {
        std::size_t start = (head_ + N - count_) % N;
        for (std::size_t i = 0; i < count_; ++i) fn(buf_[(start + i) % N]);
    }
private:
    TelemetryRecord buf_[N]{};
    std::size_t head_ = 0;
    std::size_t count_ = 0;
    std::uint64_t dropped_ = 0;
};

class Watchdog {
public:
    explicit Watchdog(std::uint32_t timeout_ticks) : timeout_(timeout_ticks) {}
    void kick(std::uint32_t now) { last_kick_ = now; }
    bool expired(std::uint32_t now) const { return now - last_kick_ > timeout_; }
private:
    std::uint32_t timeout_;
    std::uint32_t last_kick_ = 0;
};
```

The debounce thresholds deserve a comment before we move on. One bad sensor read must not fault a production tool: electrical noise guarantees occasional glitches, and a tool that faulted on every one would never finish a wafer. So a fault requires *persistence*: five consecutive failed reads (50 ms of blindness), or twenty-five consecutive ticks out of pressure tolerance. Setting these numbers is real engineering, a trade between nuisance trips and slow reactions, and process engineers argue about them for good reason.

**Piece two: the plant.** A stand-in for the physical polisher. The one modeling idea: real actuators lag their commands. When the controller opens the downforce valve, pressure doesn't jump to the new value. It approaches it, closing a fixed fraction of the remaining gap each tick (a first-order response, the same exponential-approach shape you've met in charging capacitors and moving averages). That lag is what makes the control problem nontrivial and the simulation honest:

```cpp
// ---------- the plant: a fake polisher with real-ish physics ----------------
class SimulatedTool {
public:
    // Actuators (what the controller commands).
    void command_valve(double percent) { valve_pct_ = clamp(percent, 0.0, 100.0); }
    void command_rpm(double rpm)       { cmd_rpm_ = clamp(rpm, 0.0, 150.0); }

    // Sensors (what the controller reads).
    [[nodiscard]] Reading read_pressure() const {
        if (pressure_dead_) return {0.0, Err::SensorTimeout};
        return {actual_kpa_, Err::Ok};
    }
    [[nodiscard]] Reading read_rpm() const { return {actual_rpm_, Err::Ok}; }

    // One tick of physics: both quantities lag their commands (first-order).
    void advance() {
        double driven_kpa = valve_pct_ * 0.5;   // 0..100 % valve -> 0..50 kPa
        actual_kpa_ += (driven_kpa - actual_kpa_) * 0.08;
        actual_rpm_ += (cmd_rpm_   - actual_rpm_) * 0.05;
    }

    // Fault injection for tests.
    void kill_pressure_sensor() { pressure_dead_ = true; }

private:
    static double clamp(double v, double lo, double hi) {
        return v < lo ? lo : (v > hi ? hi : v);
    }
    double valve_pct_  = 0.0;
    double cmd_rpm_    = 0.0;
    double actual_kpa_ = 0.0;
    double actual_rpm_ = 0.0;
    bool pressure_dead_ = false;
};
```

The `kill_pressure_sensor` method is the part to imitate in your own projects: the simulator exists *so that* tests can do cruel things no one can do to real hardware on demand. Fault injection isn't an afterthought bolted onto the plant model: it's half the reason the plant model exists.

**Piece three: the controller.** One `step` method, called once per tick, containing the READ → DECIDE → ACTUATE → RECORD sequence in that order:

```cpp
// ---------- the controller: state machine + control law + telemetry ---------
class CmpController {
public:
    void request_start() { start_requested_ = true; }

    void step(SimulatedTool& tool) {
        ++tick_;

        // 1. READ every sensor exactly once per tick.
        Reading p = tool.read_pressure();
        Reading r = tool.read_rpm();
        if (p.err != Err::Ok) {
            if (++sensor_errors_ >= kMaxSensorErrors) enter_fault(p.err);
        } else {
            sensor_errors_ = 0;
        }

        // 2. DECIDE: state machine plus the pressure control law.
        switch (state_) {
            case ToolState::Idle:
                if (start_requested_) {
                    start_requested_ = false;
                    change_state(ToolState::Load);
                }
                break;

            case ToolState::Load:
                if (++ticks_in_state_ >= kLoadTicks) {
                    valve_pct_ = 0.0;
                    out_of_tol_ = 0;
                    change_state(ToolState::Process);
                }
                break;

            case ToolState::Process:
                ++ticks_in_state_;
                if (p.err == Err::Ok) {
                    // Integrating control law: nudge the valve toward the
                    // command that holds the target downforce.
                    valve_pct_ += 0.05 * (kTargetKpa - p.value);
                    if (valve_pct_ < 0.0)   valve_pct_ = 0.0;
                    if (valve_pct_ > 100.0) valve_pct_ = 100.0;

                    bool in_band = p.value > kTargetKpa - kToleranceKpa &&
                                   p.value < kTargetKpa + kToleranceKpa;
                    if (ticks_in_state_ > kSettleTicks && !in_band) {
                        if (++out_of_tol_ >= kMaxOutOfTolTicks)
                            enter_fault(Err::OutOfRange);
                    } else {
                        out_of_tol_ = 0;
                    }
                }
                if (state_ == ToolState::Process &&
                    ticks_in_state_ >= kProcessTicks) {
                    change_state(ToolState::Unload);
                }
                break;

            case ToolState::Unload:
                if (++ticks_in_state_ >= kUnloadTicks) {
                    ++wafers_completed_;
                    change_state(ToolState::Idle);
                }
                break;

            case ToolState::Fault:
                break;   // parked; only an operator reset leaves this state
        }

        // 3. ACTUATE. Exactly one place writes the outputs.
        if (state_ == ToolState::Process) {
            tool.command_valve(valve_pct_);
            tool.command_rpm(kTargetRpm);
        } else {
            tool.command_valve(0.0);   // safe outputs in every other state
            tool.command_rpm(0.0);
        }

        // 4. RECORD.
        telemetry_.push({tick_,
                         static_cast<float>(p.err == Err::Ok ? p.value : -1.0),
                         static_cast<float>(r.value),
                         static_cast<std::uint8_t>(state_)});
    }

    ToolState state() const { return state_; }
    std::uint32_t tick() const { return tick_; }
    int wafers_completed() const { return wafers_completed_; }
    Err last_fault() const { return last_fault_; }
    const TelemetryRing<1024>& telemetry() const { return telemetry_; }

private:
    void change_state(ToolState next) {
        state_ = next;
        ticks_in_state_ = 0;
    }
    void enter_fault(Err cause) {
        last_fault_ = cause;
        change_state(ToolState::Fault);
    }

    ToolState state_ = ToolState::Idle;
    std::uint32_t tick_ = 0;
    std::uint32_t ticks_in_state_ = 0;
    bool start_requested_ = false;
    double valve_pct_ = 0.0;
    int sensor_errors_ = 0;
    int out_of_tol_ = 0;
    int wafers_completed_ = 0;
    Err last_fault_ = Err::Ok;
    TelemetryRing<1024> telemetry_;   // pre-allocated with the controller
};
```

Walk through `step` with this chapter's checklist in hand and you'll find every idea in its place. No allocation anywhere: the telemetry ring is a member, its storage born with the controller. No exceptions; the sensor error travels in `p.err` and is judged with debouncing right where it's read. The fault check happens during READ, so a dying sensor faults the tool from any state. The control law is a one-liner (nudge the valve in proportion to the pressure error: an integrating controller, the "I" of the PID family, chosen because it settles on whatever valve position the target requires without us knowing it in advance), and the out-of-tolerance check pointedly ignores the first `kSettleTicks` of the recipe, because pressure ramping up toward target is normal then, not a fault. ACTUATE happens in exactly one place with a default of zeros, the fail-safe rule as code structure. And RECORD runs unconditionally, faults included, which is precisely when you'll want the data.

**Piece four: the tests.** Three of them, each staging a different disaster:

```cpp
// ---------- tests -----------------------------------------------------------
int main() {
    // Test 1: one clean wafer, start to finish.
    {
        SimulatedTool tool;
        CmpController ctrl;
        ctrl.request_start();
        std::uint32_t ticks = 0;
        while (ctrl.wafers_completed() < 1 && ticks < 2000) {
            ctrl.step(tool);     // controller runs...
            tool.advance();      // ...then the world responds
            ++ticks;
        }
        assert(ctrl.wafers_completed() == 1);
        assert(ctrl.state() == ToolState::Idle);

        float mid_pressure = -1.0f;
        ctrl.telemetry().for_each([&](const TelemetryRecord& rec) {
            if (rec.tick == 400) mid_pressure = rec.pressure_kpa;
        });
        assert(mid_pressure > 28.0f && mid_pressure < 32.0f);
        std::printf("test 1: wafer done in %u ticks (%.1f s simulated), "
                    "mid-recipe pressure %.1f kPa\n",
                    ticks, ticks * kTickSeconds, mid_pressure);
    }

    // Test 2: the pressure sensor dies mid-recipe.
    {
        SimulatedTool tool;
        CmpController ctrl;
        ctrl.request_start();
        for (int i = 0; i < 300; ++i) { ctrl.step(tool); tool.advance(); }
        assert(ctrl.state() == ToolState::Process);

        tool.kill_pressure_sensor();
        int extra = 0;
        while (ctrl.state() != ToolState::Fault && extra < 100) {
            ctrl.step(tool); tool.advance(); ++extra;
        }
        assert(ctrl.state() == ToolState::Fault);
        assert(ctrl.last_fault() == Err::SensorTimeout);
        assert(extra == kMaxSensorErrors);   // debounce worked exactly

        // Fault state must drive the plant to rest.
        for (int i = 0; i < 200; ++i) { ctrl.step(tool); tool.advance(); }
        assert(tool.read_rpm().value < 5.0);
        std::printf("test 2: faulted %d ticks after sensor loss; platen wound "
                    "down to %.2f rpm\n", extra, tool.read_rpm().value);
    }

    // Test 3: the watchdog catches a stalled control task.
    {
        SimulatedTool tool;
        CmpController ctrl;
        Watchdog dog(5);                 // supervisor: 5 ticks max between kicks
        std::uint32_t now = 0;
        for (int i = 0; i < 10; ++i) {
            ctrl.step(tool); tool.advance();
            dog.kick(++now);             // healthy loop kicks every tick
        }
        now += 8;                        // the control task stalls for 8 ticks
        assert(dog.expired(now));
        tool.command_valve(0.0);         // supervisor forces safe outputs
        tool.command_rpm(0.0);
        std::printf("test 3: watchdog tripped after stall; outputs forced safe\n");
    }

    std::printf("all tests passed\n");
    return 0;
}
```

```text
test 1: wafer done in 601 ticks (6.0 s simulated), mid-recipe pressure 30.0 kPa
test 2: faulted 5 ticks after sensor loss; platen wound down to 0.00 rpm
test 3: watchdog tripped after stall; outputs forced safe
all tests passed
```

Read the output against the configuration and the numbers reconcile exactly: 601 ticks is one tick of Idle-to-Load plus 50 of Load plus 500 of Process plus 50 of Unload. Mid-recipe pressure sits at 30.0 kPa, meaning the integrating control law found and held the valve position that delivers target downforce through the plant's lag. The loop is closed for real, not scripted. Test 2 confirms the fault fired on precisely the fifth consecutive bad read, and that Fault state really does wind the machine down to rest, because ACTUATE writes zeros there every tick. Test 2's structure is worth internalizing beyond this chapter: *make the failure happen, then assert the response*, rather than hoping failures stay theoretical. It's the same instinct as chaos engineering in distributed systems, applied one machine at a time. And test 3 shows the supervisor's view: kicks stop, timeout passes, outputs get forced safe from outside the (pretend-dead) control task.

## Mini-project: fault recovery and a flight recorder

The controller you just built treats `Fault` as the end of the line, and its telemetry evaporates when the process exits. Real tools do better on both counts, and fixing both makes this a portfolio-worthy artifact. Extend `cmp_controller.cpp` as follows.

**1. A `Recovering` state.** Add an operator-facing `request_reset()` and a new state between `Fault` and `Idle`. The rules that make it more than busywork: reset requests are ignored unless the underlying condition has cleared (add a `revive_pressure_sensor()` to the simulated tool so tests can model a technician reseating a connector); `Recovering` runs a fixed-length "homing" sequence (some number of ticks with safe outputs while the tool verifies its sensors read sane values) and transitions to `Idle` only if verification passes, back to `Fault` if it doesn't. A wafer that was mid-polish when the fault hit is scrap; count it in a `wafers_scrapped_` counter, because the fab absolutely counts it.

**2. A replayable telemetry dump.** When a fault trips, the ring holds the last 1024 ticks: ten simulated seconds of history ending at the moment of failure. Dump it in a machine-readable form. Here's a starter to add above `main` (it reuses the `name` function so states print as words):

```cpp
// Mini-project starter: dump the ring as CSV (call it from a cold path only).
void dump_csv(const TelemetryRing<1024>& ring) {
    std::printf("tick,pressure_kpa,platen_rpm,state\n");
    ring.for_each([](const TelemetryRecord& r) {
        std::printf("%u,%.2f,%.1f,%s\n", r.tick,
                    static_cast<double>(r.pressure_kpa),
                    static_cast<double>(r.platen_rpm),
                    name(static_cast<ToolState>(r.state)));
    });
}
```

Then build the *replay* half: a second program (Python is the right tool; this is a data problem now) that reads the CSV, plots pressure and rpm against tick with the state transitions marked, and prints a one-line diagnosis such as `fault at tick 305: last good pressure 29.9 kPa at tick 304`. Run your test-2 scenario, dump, replay, and you should be able to point at the exact tick the sensor died without ever having watched it live. That end-to-end trip (deterministic controller, injected fault, flight-recorder dump, offline analysis) is a miniature of how real tool escalations get debugged, and it demonstrates C++ systems discipline and Python analysis chops in one repo.

**3. Stretch.** Add a second, redundant pressure sensor to the simulated tool and make the controller fault only when *both* disagree with expectations. Then write the test proving one dead sensor no longer stops the tool. Congratulations: you've discovered why aircraft carry three of everything.

## Common mistakes

1. **Pacing the loop with `sleep_for` instead of `sleep_until`.** Fixed-duration sleeps add the work time to every period, so the loop drifts: our demo drifted 426 ms in one second. Compute each deadline from the previous deadline and sleep until it.

2. **Hidden allocation in the hot path.** Nobody writes `new` in a control loop on purpose; it arrives disguised as `vector::push_back` past capacity, `std::string` concatenation, a lambda captured into a `std::function`, or formatting a log message. Audit for what code *does*, not what it says. The blunt instrument works: hot paths that never touch owning containers or strings have nothing to hide.

3. **`volatile` as a threading tool.** `volatile` tells the compiler that hardware may change memory; it provides zero atomicity and zero ordering between threads. Code that "works" with volatile flags shared between threads is working by accident. Hardware registers: `volatile`. Shared state: `std::atomic` (see [5.2](../05-Systems/05.2-concurrency.md)).

4. **Faulting on a single bad reading.** Sensors glitch; electrically noisy machines guarantee it. A tool that faults on one bad sample never finishes a wafer, so operators will demand the check be removed entirely, which is the worst outcome. Debounce: require the condition to persist for N consecutive ticks, and choose N deliberately.

5. **Automatic recovery from faults.** "The error cleared, so resume polishing" is how tools damage themselves twice. A fault means the software's model of the machine lost contact with reality; only a deliberate reset, human-initiated and run through a verification sequence, should rebuild that trust. Make `Fault` sticky.

6. **Kicking the watchdog in the wrong place, or from a timer.** A kick at the top of the loop proves only that the loop started; kick after ACTUATE so a mid-tick hang counts as missing. Worse is kicking from a separate timer or interrupt "so it doesn't trip during debugging": that certifies the timer's health, not the loop's, and quietly deletes your last line of defense.

7. **Scattering output writes across the code.** When five functions can each command the valve, no one can say what the tool will do in a given state, and the fail-safe guarantee dissolves. Route every output through the single ACTUATE step; everything else records *intent* for ACTUATE to enact.

8. **Logging with formatted, blocking I/O from the loop.** One `printf` per tick works on your desk and fails in the field when the console blocks. Store fixed-size binary records in a pre-allocated ring; format and persist them from a cold path. If the ring overflows, drop old data and count the drops. Never stall the writer.

5. **Pause and resume.** Extend the standalone state-machine program (the five-state one, not the full controller) with a `Paused` state: reachable only from `Process`, returning only to `Process`, with fault still preempting everything. Print a trace showing pause and resume.

7. **Watchdog placement.** A teammate moves the `kick` call from the end of `step` to the beginning, arguing "it's one line, what's the difference?" Explain the failure mode that is now invisible to the watchdog. Then explain what a *hardware* watchdog provides that our software `Watchdog` class cannot, no matter where it's kicked.

8. **Measure your WCET.** Write a harness that calls a small control-step function 100,000 times, timing each call with `std::chrono::steady_clock`, and reports the mean and worst-case duration. 9. **Redundant sensors.** The tool grows a second pressure sensor. Design (in prose or pseudocode) the read logic: when do you average, when do you prefer one, and when do you fault? 10. **Justify the standard.** MISRA-style rulesets ban (a) dynamic memory after initialization, (b) recursion, and (c) implicit fallthrough between `switch` cases. For each, name the concrete field failure the rule prevents: not "it's safer," but the specific bad afternoon at a fab.

### Solutions

**1.** (a) Hard: a late valve command means unregulated pressure this tick; the damage is done regardless of later correctness. (b) Soft: a late frame degrades the operator's view, harms nothing physical. (c) Hard, and safety-rated on real tools: the interlock's whole meaning is a bounded response time (in practice it's also enforced in hardware, precisely so software lateness can't matter). (d) Soft, with a deadline measured in hours. (e) The canonical hard deadline: a late airbag is equivalent to no airbag, arguably worse.

**2.** Line by line: `std::vector<double> samples` plus eight `push_back` calls is heap allocation in the loop, sin 1 (and it happens *every tick*, since the vector is local). `std::to_string` and the `+` concatenation: more allocation, sin 1. `log_file << msg`: file I/O that can block, sin 2. `std::endl`: flushes the stream, a second and often worse blocking operation, sin 2. `throw OverpressureError{}`: sin 3, and note the structural harm: the throw abandons the tick before any actuation happens. There's also a subtler timing sin, `adc.read()` inside a loop with no stated bound. If that's a blocking bus transaction, eight of them might not fit the tick. The repaired version: read into a fixed `std::array<double, 8>`, store raw values to a telemetry ring (no formatting), and return an error code that this tick's DECIDE step turns into a fault transition.

**3.** (a) Each period is work plus sleep: 2 + 10 = 12 ms. (b) The metronome expects a tick every 10 ms: 360,000 ticks per hour. The drifting loop delivers one per 12 ms: 300,000. It is 60,000 ticks (a full ten minutes) behind after an hour. (c) `sleep_until` computes each deadline from the schedule (`next += period`), not from when the work happened to finish, so work time is absorbed into the sleep rather than added to the period; the deadlines stay pinned to the ideal grid.

**4.**

```cpp
#include <cstdio>

class Debounce {
public:
    explicit Debounce(int threshold) : threshold_(threshold) {}
    // Feed one raw sample per tick; reports true only after the condition
    // has held for `threshold` consecutive ticks.
    bool update(bool raw) {
        count_ = raw ? count_ + 1 : 0;
        return count_ >= threshold_;
    }
private:
    int threshold_;
    int count_ = 0;
};

int main() {
    Debounce overpressure(3);
    const bool samples[] = {false, true, true, false, true, true, true, true};
    for (bool s : samples) {
        std::printf("raw=%d filtered=%d\n", s, overpressure.update(s));
    }
    return 0;
}
```

```text
raw=0 filtered=0
raw=1 filtered=0
raw=1 filtered=0
raw=0 filtered=0
raw=1 filtered=0
raw=1 filtered=0
raw=1 filtered=1
raw=1 filtered=1
```

The two-tick glitch (samples 2–3) never trips the filter; the single `false` at sample 4 resets the count, and only three consecutive `true`s fire it. This is the same logic as `sensor_errors_` in the CMP controller, extracted into a reusable unit.

**5.** The changes: a new enum value, two new inputs, one new case, and one modified case. Everything else, including the fault-preemption line, is untouched, which is exactly the maintainability argument for the single-transition-function style.

```cpp
#include <cstdio>

enum class ToolState { Idle, Load, Process, Paused, Unload, Fault };

const char* name(ToolState s) {
    switch (s) {
        case ToolState::Idle:    return "Idle";
        case ToolState::Load:    return "Load";
        case ToolState::Process: return "Process";
        case ToolState::Paused:  return "Paused";
        case ToolState::Unload:  return "Unload";
        case ToolState::Fault:   return "Fault";
    }
    return "?";
}

struct Inputs {
    bool start_requested;
    bool wafer_clamped;
    bool recipe_done;
    bool wafer_removed;
    bool fault_detected;
    bool pause_requested;
    bool resume_requested;
};

ToolState step(ToolState s, const Inputs& in) {
    if (in.fault_detected) return ToolState::Fault;
    switch (s) {
        case ToolState::Idle:    return in.start_requested ? ToolState::Load    : s;
        case ToolState::Load:    return in.wafer_clamped   ? ToolState::Process : s;
        case ToolState::Process:
            if (in.pause_requested) return ToolState::Paused;
            return in.recipe_done ? ToolState::Unload : s;
        case ToolState::Paused:  return in.resume_requested ? ToolState::Process : s;
        case ToolState::Unload:  return in.wafer_removed   ? ToolState::Idle    : s;
        case ToolState::Fault:   return s;
    }
    return s;
}

int main() {
    ToolState s = ToolState::Idle;
    Inputs script[] = {
        {true,  false, false, false, false, false, false},
        {false, true,  false, false, false, false, false},
        {false, false, false, false, false, true,  false},  // operator pauses
        {false, false, false, false, false, false, false},  // still paused
        {false, false, false, false, false, false, true},   // resume
        {false, false, true,  false, false, false, false},
        {false, false, false, true,  false, false, false},
    };
    std::printf("%s", name(s));
    for (const Inputs& in : script) {
        s = step(s, in);
        std::printf(" -> %s", name(s));
    }
    std::printf("\n");
    return 0;
}
```

```text
Idle -> Load -> Process -> Paused -> Paused -> Process -> Unload -> Idle
```

(In the real controller you'd also decide what ACTUATE does in `Paused` (head up, platen stopped, but the wafer stays clamped) and whether the recipe timer freezes. It should.)

**6.**

```cpp
#include <cstddef>
#include <cstdint>
#include <cstdio>

// Frame layout: [0x7E] [len] [payload bytes...] [checksum]
// checksum = XOR of len and every payload byte.
std::size_t encode(const std::uint8_t* payload, std::uint8_t len,
                   std::uint8_t* out) {
    out[0] = 0x7E;
    out[1] = len;
    std::uint8_t x = len;
    for (std::uint8_t i = 0; i < len; ++i) {
        out[2 + i] = payload[i];
        x = static_cast<std::uint8_t>(x ^ payload[i]);
    }
    out[2 + len] = x;
    return static_cast<std::size_t>(len) + 3;
}

bool decode(const std::uint8_t* frame, std::size_t n,
            std::uint8_t* payload_out, std::uint8_t* len_out) {
    if (n < 3 || frame[0] != 0x7E) return false;
    std::uint8_t len = frame[1];
    if (n != static_cast<std::size_t>(len) + 3) return false;
    std::uint8_t x = len;
    for (std::uint8_t i = 0; i < len; ++i) {
        x = static_cast<std::uint8_t>(x ^ frame[2 + i]);
        payload_out[i] = frame[2 + i];
    }
    if (x != frame[2 + len]) return false;   // checksum mismatch
    *len_out = len;
    return true;
}

int main() {
    const std::uint8_t msg[] = {0x01, 0x2A, 0xFF};   // "set valve to 42"
    std::uint8_t frame[16];
    std::size_t n = encode(msg, 3, frame);
    std::printf("frame:");
    for (std::size_t i = 0; i < n; ++i) std::printf(" %02X", frame[i]);
    std::printf("\n");

    std::uint8_t out[16];
    std::uint8_t out_len = 0;
    std::printf("decode clean frame:     %s\n",
                decode(frame, n, out, &out_len) ? "ok" : "REJECTED");

    frame[3] = 0x2B;   // one bit flipped on the wire
    std::printf("decode corrupted frame: %s\n",
                decode(frame, n, out, &out_len) ? "ok" : "REJECTED");
    return 0;
}
```

```text
frame: 7E 03 01 2A FF D7
decode clean frame:     ok
decode corrupted frame: REJECTED
```

An XOR checksum catches any single-bit error but misses some multi-bit patterns (two flips of the same bit position in different bytes cancel); real industrial protocols use CRCs for exactly that reason. The structure (delimiter, length, payload, integrity check) is the part that transfers everywhere, from RS-485 up through Ethernet frames in [Chapter 6](../06-Networking/).

**7.** With the kick at the top, this sequence is invisible: the loop wakes, kicks the dog, reads sensors, and *then* hangs (in DECIDE, or blocked on a misbehaving device read) before ACTUATE. The watchdog was just fed, so for one full timeout period the outputs sit stale with the watchdog perfectly content; if the hang recurs each tick (wake, kick, hang, get rescheduled...), the watchdog may never trip at all while the tool effectively runs open-loop. Kicking after ACTUATE makes the kick a certificate that the *entire* tick completed, outputs included. As for hardware: our software watchdog runs in the same process it monitors, so if the whole process is killed, deadlocked at a lower level, or the OS itself stalls, the checker dies with the checked. A hardware watchdog is a separate timer circuit that cuts the outputs to their de-energized (fail-safe) state with no software in the path; it's the only watchdog that still works when the answer to "what failed?" is "everything."

**8.**

```cpp
#include <chrono>
#include <cstdio>

double control_step(double measured) {          // the code under test
    static double valve = 0.0;
    valve += 0.05 * (30.0 - measured);
    if (valve < 0.0)   valve = 0.0;
    if (valve > 100.0) valve = 100.0;
    return valve;
}

int main() {
    using clock = std::chrono::steady_clock;
    const int runs = 100000;
    long long worst_ns = 0;
    long long total_ns = 0;
    volatile double sink = 0.0;

    for (int i = 0; i < runs; ++i) {
        auto t0 = clock::now();
        sink = control_step(25.0 + (i % 10));
        long long dt = std::chrono::duration_cast<std::chrono::nanoseconds>(
                           clock::now() - t0).count();
        total_ns += dt;
        if (dt > worst_ns) worst_ns = dt;
    }
    (void)sink;
    std::printf("mean %.0f ns, worst %lld ns over %d runs\n",
                static_cast<double>(total_ns) / runs, worst_ns, runs);
    return 0;
}
```

```text
(one run on desktop Linux; your numbers will differ)
mean 27 ns, worst 11750 ns over 100000 runs
```

A 400-to-1 ratio between worst and mean, for a function that is pure arithmetic with no allocation, no I/O, nothing. The spikes come from the environment: the OS preempting the thread mid-measurement, timer interrupts, cache misses after another process evicted our lines. That's the chapter's thesis in one number: on a general-purpose OS even innocent code has terrible tail latency, which is why hard real-time systems change the *platform* (RTOS, locked memory, reserved cores, interrupt discipline), not just the code. (Measurement caveat: `clock::now()` itself costs tens of nanoseconds, so the mean here is inflated; the worst case is real.)

**9.** A workable policy, per tick: if both sensors return `Ok` and agree within a disagreement tolerance, use the average (averaging reduces noise). If one returns errors and the other is healthy, use the healthy one, raise a maintenance alarm (not a fault, since the tool can still run safely), and debounce the dead sensor's condition like any other. If both return errors, fault, debounced as usual. The scariest case is both healthy but *disagreeing*: each sensor vouches for itself, and you have no way to know which one describes reality: the true pressure might be dangerously off-target while one sensor swears everything is fine. With two sensors the only safe response to sustained disagreement is to fault; you cannot out-vote a liar with one witness. That is precisely why safety-critical systems use *three* sensors: two-against-one identifies the liar, and the tool keeps running. Redundancy isn't about having spares; it's about making disagreement diagnosable.

**10.** (a) Dynamic memory after init: month-three failures, meaning a slow leak or heap fragmentation that never appears in a two-week test cycle and then takes down a production tool at random, plus the unbounded worst-case allocation latency inside control loops. Banning it converts "might run out of memory someday" into "either boots or doesn't." (b) Recursion: stack depth becomes input-dependent, so no static analysis can prove the stack won't overflow; an embedded stack overflow doesn't produce a nice traceback like Python's `RecursionError`, it silently corrupts whatever memory sits past the stack, possibly the variables holding your output commands. Iteration with an explicit fixed-size worklist makes the bound visible and checkable. (c) Implicit fallthrough: a maintenance edit adds a case, forgets `break`, and now one state's actuation code runs a second state's too: the compiler is happy, the tests that don't cover that state pass, and the tool does something no one designed. Requiring explicit termination (or an explicit fallthrough annotation) turns that silent behavior change into a compile-time conversation.
