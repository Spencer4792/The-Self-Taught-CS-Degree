## Start here: the interpreter at your side vs. the translated book

Think about what happens every single time you run a Python script. The interpreter, a large C program, reads your source, turns it into bytecode, and then sits in a loop executing that bytecode one instruction at a time: fetch an instruction, figure out what it means, check the types of the operands, do the work, repeat. It's like giving a speech through a live interpreter. Every sentence you say gets translated on the spot, and if you give the same speech tomorrow, the interpreter translates the whole thing again from scratch.

C++ works like publishing a translated book. You hand the entire text to a translator once, ahead of time. The translator (the **compiler**) reads all of it, checks it for consistency, agonizes over the best phrasing, and produces a finished translation in the machine's native language: the actual CPU instructions you met in 25.2. From then on, anyone can read the book directly. No interpreter in the room, no per-sentence overhead, nothing standing between the text and the reader.

That one difference explains most of what makes C++ feel foreign at first:

- The translation step is where type errors surface. The compiler reads everything before anything runs, so `"3" + 4` is rejected at translation time, not discovered mid-speech.
- The finished book can't be edited live. There's no REPL-style "just try it" loop; you edit, recompile, rerun. The cycle is longer, and in exchange the running program is fast.
- The translator is allowed to be slow and clever. A compiler can spend seconds rewriting your loops into better ones, because it only pays that cost once. An interpreter has to be quick and literal, because it pays on every execution.

Keep the two pictures side by side, live interpreter and translated book, and the rest of this chapter is filling in details.

## Why C++ exists, and where it runs

Python's pitch is programmer time: you trade machine efficiency for expressiveness, and most of the time that's the right trade. C++ makes the opposite trade. It exists for the situations where the machine's time, memory, or predictability is the scarce resource:

- **Latency floors.** A garbage collector can pause your program for milliseconds at unpredictable moments. In a web app nobody notices. In a control loop that fires every millisecond, a pause is a missed deadline.
- **Throughput ceilings.** When a data structure processes billions of items, the interpreter overhead on each item (the fetch-decode-typecheck loop above) dominates the actual work. Compiled code deletes that overhead entirely.
- **Memory budgets.** An embedded controller might have kilobytes of RAM. Python's runtime alone won't fit. C++ programs carry no runtime to speak of; you get roughly the memory footprint you wrote.

Concretely, C++ is the working language of game engines, browsers (Chrome's core), databases, high-frequency trading systems, and the internals of the ML frameworks you drive from Python: PyTorch and TensorFlow are C++ wearing a Python interface.

It is also, and this matters if the semiconductor track from 17.1–17.6 caught your interest, the language of the equipment that makes chips. A CMP polisher of the kind Ebara or Applied Materials builds (17.5) is a machine that presses a spinning wafer against a spinning pad with slurry in between, and it has to hold pressures, flows, and rotation speeds inside tight tolerances continuously. The software doing that is a set of real-time control loops: read sensors, compute corrections, command motors, every few milliseconds, forever, without missing a beat. The wafer-handling robots that move product between stations are the same story: trajectory control with hard deadlines, because the arm is carrying something worth thousands of dollars over hardware worth millions. That whole world runs on C and C++, precisely because there's no garbage collector or interpreter that can decide to take a break at the wrong moment. If "software engineer at an equipment company" is on your list from 17.6, this chapter and the ones after it are the on-ramp.

The honest caveat: C++ gives you control by giving you responsibility. The runtime services Python performs silently (bounds checking, memory management, type checking at every operation) become your job or the compiler's, and the failure mode for getting them wrong is not a friendly traceback. That's the subject of 29.2. For now we stay on the sunny side of the street: modern C++ written with the standard library is far safer than its reputation.

## The compilation model: preprocessor, compiler, linker

When you type `python3 script.py`, one program does everything. When you type `g++ hello.cpp`, you're launching a three-stage pipeline. You saw the interpreter/compiler split conceptually in 16.5; here's the actual machinery.

```text
hello.cpp
   |
   |  1. PREPROCESSOR   textual copy-paste: #include, #define
   v
expanded source (one huge file)
   |
   |  2. COMPILER       checks types, generates machine code
   v
hello.o  (object file: compiled code with unresolved names)
   |
   |  3. LINKER         connects your code to the library code it calls
   v
a.out / hello  (the executable: the "translated book")
```

**Stage 1: the preprocessor.** Lines starting with `#` aren't C++ at all. They're instructions to a text-manipulation pass that runs first. `#include <iostream>` literally means "paste the contents of the file `iostream` here." That's why a five-line hello-world balloons to about 32,000 lines by the time the compiler proper sees it (you can watch this with `g++ -E hello.cpp`). Python's `import` is a runtime operation that loads a module object; `#include` is a copy-paste that happens before compilation even starts. The declarations it pastes in are what let the compiler check your calls against the library's actual signatures.

**Stage 2: the compiler.** This is the translator. It parses the expanded source, enforces the type rules, and emits machine code for your functions into an **object file**. One thing it does not do: it doesn't need the machine code for the functions you call, only their declarations. When you call `std::sort`, the compiler checks the call against `sort`'s declared signature and emits "call sort, address to be filled in later."

**Stage 3: the linker.** Someone has to fill in "later." The linker gathers your object files and the precompiled standard library, matches every "call X, address unknown" against a definition of X, and stitches the result into one executable. When you see the infamous `undefined reference` error, that's the linker telling you a promise was made (a declaration) that nobody kept (no definition). We'll read one of those errors later in the chapter.

The day-to-day command hides all three stages:

```text
g++ -std=c++17 -Wall -Wextra -o hello hello.cpp
./hello
```

`-std=c++17` picks the language version. `-Wall -Wextra` turns on warnings, and you should treat them as part of the language: the compiler offering to catch your bugs at translation time is the entire point of having a compiler. `-o hello` names the output. From here on, every runnable block in this chapter was compiled with exactly that command line.

Your first program, for completeness:

```cpp
#include <iostream>

int main() {
    std::cout << "hello from a compiled binary\n";
    return 0;
}
```

```text
hello from a compiled binary
```

Three Python-to-C++ notes packed into six lines. Execution starts at `main`, always; there's no top-level script. `std::cout << x` is the print statement, with `<<` chaining values left to right. And the `std::` prefix means "from namespace std," the standard library's equivalent of a package name; writing it out (rather than `using namespace std;`) keeps names honest, the same instinct as preferring `import numpy as np` over `from numpy import *`.

## Static types and what they buy you

In Python, a variable is a name tag, and the tag can move: `x = 42` then `x = "hello"` is legal because the type lives on the object, not the name. In C++, the type belongs to the variable itself, is written at birth, and never changes:

```cpp
#include <iostream>
#include <string>

int main() {
    int count = 42;              // an integer, and only ever an integer
    double ratio = 0.75;         // 64-bit floating point
    std::string name = "wafer";  // a real string object
    bool ready = true;

    count = count + 1;           // fine: still an int
    // count = "wafer";          // won't compile: can't assign a string to an int

    std::cout << name << " " << count << " " << ratio << " " << ready << "\n";
    return 0;
}
```

```text
wafer 43 0.75 1
```

(Yes, `true` prints as `1`. C++'s defaults are close to the machine.)

What does the annotation tax buy? Three things:

1. **Errors move earlier.** A whole class of bugs that Python discovers at runtime, on whichever execution path finally hits them, C++ rejects before the program exists. The compiler checks every path, including the ones your tests never run. If you've used type hints with `mypy`, you've already tasted this; C++ is that idea made mandatory and airtight.
2. **Speed.** This is the one people underrate. When the compiler knows `count` is an `int`, `count + 1` compiles to a single ADD instruction. When Python sees `count + 1`, it must check `count`'s type at runtime, look up its `__add__`, allocate a new integer object, and adjust reference counts (all the machinery from 5.1). Static types are what let the translated book dispense with the interpreter's per-operation bookkeeping.
3. **Documentation that can't rot.** A signature like `double average(const std::vector<double>&)` tells you what goes in and what comes out, and the compiler guarantees it stays true.

There's also `int` versus Python's `int` to internalize: a C++ `int` is a fixed-width machine word (typically 32 bits), not an arbitrary-precision object. It can overflow. Python quietly promotes `2**100` to a big integer; C++ gives you exactly the hardware's arithmetic, wraparound cliffs and all. When you need bigger, you say so (`long long` is 64 bits), and when a benchmark result looks impossibly wrong, overflow should be your first suspect.

One comfort: C++ can often infer types with `auto` (`auto x = 42;` makes an `int`), so you won't be writing `std::unordered_map<std::string, int>::const_iterator` by hand. The type is still fixed at compile time: `auto` is inference, not dynamism.

## Value semantics: the single biggest mental shift

Everything else in this chapter is spelling. This section is the part that will actually bite you if you skip it, so slow down here.

Recall the model from 5.1: a Python variable is an arrow to an object living on the heap. Assignment copies the arrow, never the object. Passing an argument copies the arrow. Two names, one list. And the consequence you proved there was the mutate-vs-rebind distinction:

```python
def mutate(lst):
    lst.append(99)     # reaches the shared object; the caller sees it

def rebind(lst):
    lst = [0, 0, 0]    # re-points the local name; the caller does not see it

data = [1, 2, 3]
mutate(data)
print(data)            # [1, 2, 3, 99]
rebind(data)
print(data)            # [1, 2, 3, 99]  -- unchanged
```

C++'s default is the opposite, and it's called **value semantics**: a variable is not an arrow to a box, it *is* the box. Assignment copies the contents. Passing an argument copies the contents. There is no shared object unless you explicitly ask for sharing.

Watch what that does to the experiment:

```cpp
#include <iostream>
#include <vector>

void try_to_mutate(std::vector<int> v) {    // pass by value: v is a copy
    v.push_back(99);                        // grows the copy, then the copy dies
}

void really_mutate(std::vector<int>& v) {   // pass by reference: v IS the caller's vector
    v.push_back(99);
}

int main() {
    std::vector<int> data = {1, 2, 3};

    try_to_mutate(data);
    std::cout << "after try_to_mutate:  " << data.size() << " elements\n";

    really_mutate(data);
    std::cout << "after really_mutate:  " << data.size() << " elements\n";
    return 0;
}
```

```text
after try_to_mutate:  3 elements
after really_mutate:  4 elements
```

In Python, `mutate` sees the caller's list because arrows are copied and objects are shared. In C++, `try_to_mutate` receives a full, independent copy of the vector (all three elements duplicated), grows the copy, and then the copy is destroyed when the function returns. The caller's data never moves. To get Python-like sharing you must write the `&` and ask for a **reference**, which is exactly what `really_mutate` does.

Assignment follows the same rule:

```cpp
#include <iostream>
#include <vector>

int main() {
    std::vector<int> a = {1, 2, 3};
    std::vector<int> b = a;        // a full, independent copy of all three elements

    b.push_back(4);

    std::cout << "a has " << a.size() << " elements\n";
    std::cout << "b has " << b.size() << " elements\n";
    return 0;
}
```

```text
a has 3 elements
b has 4 elements
```

The Python version of `b = a` gives you two names for one list, and `b.append(4)` changes both. The C++ version photocopies the box. This cuts both ways:

- The aliasing bugs from 5.1 ("I passed my list to a function and it trashed it") largely disappear. If you didn't hand out a reference, nobody can touch your data.
- A new cost appears. Copying a million-element vector is a million-element copy. Innocent-looking code can be slow because it photocopies boxes it only meant to glance at. The idiom you'll see everywhere, and the fix, is coming in the `const` section.

One more consequence worth saying out loud: in C++, mutate-vs-rebind stops being a distinction you need. Python needed it because names and objects are separate things that can disagree. In C++ the variable is the object, so "assigning to the parameter" and "mutating through the parameter" collapse into the same question: did you receive a copy or a reference?

## References and pointers: asking for sharing explicitly

Since sharing is no longer the default, C++ gives you two tools for requesting it. Both should feel familiar. They're the "arrow" from Python's model, made visible and put under your control.

A **reference** (`int&`) is a permanent second name for an existing box. It must be initialized at birth, can never be re-pointed at a different box, and cannot be null. After the binding, using the reference is using the original:

```cpp
#include <iostream>

int main() {
    int x = 10;
    int& r = x;      // r is another name for x, starting now and forever

    r = 20;          // writes through to x
    std::cout << "x = " << x << "\n";

    int y = 99;
    r = y;           // does NOT re-point r at y; copies y's value into x
    std::cout << "x = " << x << ", y = " << y << "\n";
    return 0;
}
```

```text
x = 20
x = 99, y = 99
```

The second assignment is the trap for Python programmers. In Python, `r = y` would re-bind the name. In C++, a reference can never be re-bound, so `r = y` means "assign y's value into the box r names." Value semantics again: assignment moves contents, not arrows.

A **pointer** (`int*`) is a box whose contents are an address: a Python arrow you can hold in your hand, inspect, and reassign. You take an address with `&x` and follow the arrow ("dereference") with `*p`:

```cpp
#include <iostream>

int main() {
    int x = 10;
    int* p = &x;     // p holds the address of x

    std::cout << "p points at " << p << ", which holds " << *p << "\n";

    *p = 20;         // write through the pointer: x changes
    std::cout << "x = " << x << "\n";

    int y = 99;
    p = &y;          // unlike a reference, a pointer CAN be re-pointed
    std::cout << "*p = " << *p << "\n";
    return 0;
}
```

```text
p points at 0x7ffd4b2a1398, which holds 10   (address varies per run)
x = 20
*p = 99
```

This is the same pointer arithmetic machinery you saw prove the array address formula in 2.1 (`a[i]` is `*(a + i)`), now available for everyday variables. The working rule for choosing between the two: use references when you can (they can't be null and can't dangle mid-function, so there's less to verify), and pointers when you must: when "points at nothing" is a meaningful state, or when you need to re-aim mid-flight. Pointers are also the doorway to manual memory management, which is 29.2's territory; in this chapter we don't allocate anything by hand.

## const: promises the compiler enforces

Python has conventions for "don't change this" (SHOUTY_NAMES, leading underscores), and they're enforced by politeness. C++ has `const`, enforced by the compiler. Mark a variable `const` and any attempt to modify it is a compile error, on every path, forever.

The place `const` earns its keep is in function signatures, because it resolves the tension value semantics created. You want to pass a big vector without photocopying it, so you pass by reference; but a plain reference hands the function permission to modify your data. `const&` gives you both: no copy, no touching.

```cpp
#include <iostream>
#include <vector>

double average(const std::vector<double>& readings) {
    double total = 0.0;
    for (double r : readings) total += r;
    return readings.empty() ? 0.0 : total / readings.size();
}

int main() {
    const double target = 0.82;    // a promise: this never changes
    // target = 0.83;              // won't compile

    std::vector<double> readings = {0.81, 0.83, 0.82};
    std::cout << "target " << target
              << ", average " << average(readings) << "\n";
    return 0;
}
```

```text
target 0.82, average 0.82
```

(Two smaller sights in that block: `for (double r : readings)` is the range-for, C++'s `for r in readings`, and `cond ? a : b` is the conditional expression, `a if cond else b`.)

Read `const std::vector<double>&` as one unit, because you will see it hundreds of times: "I need to look at your vector, I won't copy it, and I promise not to change it." The compiler holds the function to the promise: call `readings.push_back(...)` inside `average` and the program won't compile. That's the passing rule of thumb complete: small things (ints, doubles, pointers) by value; big things you're reading by `const&`; things you're deliberately modifying by `&`, with the `&` serving as the visible warning label at the call site's declaration.

## The containers you already know, wearing new names

The three collections you use daily in Python map directly onto the C++ standard library. Same big-O, same role, stricter rules:

| Python | C++ | Notes |
|---|---|---|
| `list` | `std::vector<T>` | contiguous, geometric growth: the dynamic array you built in 2.1 |
| `str` | `std::string` | mutable, unlike Python's |
| `dict` | `std::unordered_map<K, V>` | hash table, no insertion-order guarantee |

The `<T>` in angle brackets is the element type, stated up front: a `std::vector<int>` holds ints and nothing else, ever. That's the static-typing story applied to collections: a heterogeneous grab-bag list has no direct equivalent, and in practice you rarely miss it.

```cpp
#include <iostream>
#include <string>
#include <unordered_map>
#include <vector>

int main() {
    // list -> std::vector
    std::vector<int> nums = {3, 1, 4};
    nums.push_back(1);                          // append
    std::cout << nums[0] << " ... " << nums.size() << " elements\n";

    // str -> std::string (mutable!)
    std::string s = "wafer";
    s += "-42";                                 // modifies s in place
    std::cout << s << " has " << s.size() << " chars\n";

    // dict -> std::unordered_map
    std::unordered_map<std::string, int> counts;
    counts["polish"] = 3;
    counts["rinse"] += 1;    // "rinse" didn't exist; it appears as 0, then becomes 1
    for (const auto& [word, n] : counts) {
        std::cout << word << ": " << n << "\n";
    }
    return 0;
}
```

```text
3 ... 4 elements
wafer-42 has 8 chars
rinse: 1
polish: 3
```

Differences worth pinning down now, because each one is a future debugging session:

- **`vector[i]` does not bounds-check.** Python raises `IndexError`; `nums[10]` on a 4-element vector reads whatever bytes happen to sit there. Use `nums.at(10)` when you want a checked access that throws. This is the "you are the runtime" trade from 16.5 in its purest form.
- **Strings mutate.** `s += "-42"` modifies `s` in place, with no new object and none of Python's string-immutability ceremony. Cheap appends without `join` tricks.
- **`map[key]` inserts on miss.** Reading `counts["typo"]` doesn't raise a `KeyError`; it creates the key with a zero value and returns it. Wonderful for counting (`counts[word] += 1` needs no `Counter` or `setdefault`), hazardous when you only meant to look. Use `counts.count(key)` (0 or 1) or `counts.find(key)` to test membership without inserting.
- **Iteration order is unspecified.** Python dicts preserve insertion order as of 3.7; `unordered_map` promises nothing, as the output above shows. Need order? Sort, or use `std::map` (a balanced tree, O(log n), sorted by key: the structure from chapter 2's BST material, productionized).

The loop syntax `for (const auto& [word, n] : counts)` is worth reading twice: range-for over the map, structured bindings unpacking each pair like Python's `for word, n in counts.items()`, and `const auto&` applying the passing rule: look, don't copy, don't touch.

## Functions and overloading

A C++ function declares the type of everything crossing its boundary, parameters and return value alike:

```text
double average(const std::vector<double>& readings)
^^^^^^ return   ^^^^^^^^^^^^^^^^^^^^^^^^^^ parameter type and name
```

Because types are part of the signature, C++ can do something Python can't: define several functions with the same name, distinguished by parameter types. The compiler picks the right one at each call site by matching argument types. This is **overloading**:

```cpp
#include <iostream>
#include <string>

std::string describe(int n)    { return "an int: " + std::to_string(n); }
std::string describe(double d) { return "a double: " + std::to_string(d); }
std::string describe(const std::string& s) { return "a string: " + s; }

int main() {
    std::cout << describe(42) << "\n";
    std::cout << describe(2.5) << "\n";
    std::cout << describe(std::string("polish")) << "\n";
    return 0;
}
```

```text
an int: 42
a double: 2.500000
a string: polish
```

In Python you'd write one function full of `isinstance` checks, or lean on duck typing. In C++ the dispatch happens at compile time, costs nothing at runtime, and each variant's body stays simple. You've been using overloads all chapter without noticing: `<<` printing ints, doubles, and strings correctly is operator overloading, the same mechanism (and the C++ answer to Python's `__str__`-style dunder protocol).

The resolution rules have depth (exact match beats conversion; ambiguity is a compile error, not a coin flip), but the everyday experience is that it does what you'd expect. Default arguments also exist (`int f(int x, int scale = 1)`); keyword arguments do not, so calls are positional.

## A first taste of RAII: files that close themselves

Here's a Python idiom you use daily:

```python
with open("readings.txt") as f:
    for line in f:
        ...  # process each line
# file is closed here, even if the loop body raised
```

The `with` statement exists because "acquire a resource, use it, release it even on the error path" is such a common shape that it deserves syntax. C++ solves the same problem with no dedicated syntax at all, using a rule the language already has: objects run a special function, the **destructor**, at the exact moment they go out of scope. Tie "release the resource" to the destructor, and cleanup becomes automatic and unskippable. The pattern is called **RAII** (Resource Acquisition Is Initialization), and 16.5 flagged it as C++'s signature idiom. File streams are the friendliest place to meet it:

```cpp
#include <fstream>
#include <iostream>
#include <string>

int main() {
    {
        std::ofstream out("readings.txt");   // constructor opens the file
        out << "0.81\n0.83\n0.82\n";
    }   // out dies here; its destructor flushes and closes. No close() call needed.

    std::ifstream in("readings.txt");        // constructor opens for reading
    if (!in) {
        std::cerr << "could not open readings.txt\n";
        return 1;
    }
    std::string line;
    while (std::getline(in, line)) {
        std::cout << "read: " << line << "\n";
    }
    return 0;
}   // in closes itself here, even if we returned early or an exception flew past
```

```text
read: 0.81
read: 0.83
read: 0.82
```

Walk through the mechanics. The bare `{ }` braces open an inner scope; `out` is born inside it, so `out` dies at the closing brace, and dying runs its destructor, which flushes and closes the file. Every path out of a scope (normal fall-through, early `return`, an exception unwinding past) runs the destructors of that scope's objects. It's `with`, but ambient: you can't forget to use it, because it isn't a thing you use, it's how object lifetime works.

Note the error handling, too: `std::ifstream` doesn't throw on a missing file. The stream goes into a failed state, `if (!in)` detects it, and we print to `std::cerr` (stderr, as in 5.3) and return a nonzero exit code. Streams as conditions and explicit status checks are the idiomatic C++ default, closer to Go's style from 16.5 than to Python's exceptions.

The reason RAII gets top billing this early: in 29.2 the resource being released won't be a file handle, it'll be memory, and RAII is the difference between modern C++ and the leak-prone folklore version. `std::vector` is already RAII (its destructor frees its elements), which is why this chapter never needed a single manual cleanup.

## Compiling with g++, and reading what it says back

The compiler is chatty, and new C++ programmers routinely bounce off the volume of its error messages. The skill (and it is a learnable skill, like reading tracebacks was) is knowing which lines matter. Take this deliberately broken program (it won't compile; that's the point):

```cpp
#include <vector>

int main() {
    std::vector<int> v = {1, 2, 3};
    v.push_back("hello");
    return 0;
}
```

Here's what `g++ -std=c++17 -Wall -Wextra` says, trimmed:

```text
broken.cpp: In function 'int main()':
broken.cpp:5:16: error: no matching function for call to 'push_back(const char [6])'
    5 |     v.push_back("hello");
      |     ~~~~~~~~~~~^~~~~~~~~
/usr/include/c++/11/bits/stl_vector.h:1187:7: note: candidate:
      'void std::vector<_Tp>::push_back(const value_type&) [with _Tp = int; ...]'
/usr/include/c++/11/bits/stl_vector.h:1187:7: note:
      conversion of argument 1 would be ill-formed:
broken.cpp:5:17: error: invalid conversion from 'const char*' to 'int'
```

The real output runs a couple dozen lines. The reading protocol:

1. **Find the first line tagged `error:` that names your file.** Everything before it is context; everything after the first error may be noise caused by it. Here that's `broken.cpp:5:16`, which reads as file, line 5, column 16.
2. **Read the error sentence in types.** "No matching function for call to `push_back(const char [6])`" means you called `push_back` with a string literal (an array of 6 chars, counting the terminator).
3. **Skim the `note:` lines as suggestions.** They list the candidates the compiler considered and why each lost. The last line is the plainest statement of the mismatch: a `const char*` is not an `int`. Vector of int, string pushed in, case closed.
4. **Fix the first error and recompile.** One real mistake often spawns ten downstream errors; never trust the count, only the first message.

Linker errors read differently because they arrive after compilation succeeded. Declare a function but never define it, and the compile stage passes (the promise was well-formed) while the link stage fails:

```text
/usr/bin/ld: /tmp/ccvR2CGI.o: in function `main':
prog.cpp:(.text+0x70): undefined reference to `average(std::vector<double> const&)'
collect2: error: ld returned 1 exit status
```

The tells: the complaint comes from `ld` (the linker), and the phrase is `undefined reference`. Translation: someone calls `average`, and no object file or library contains its body. The usual causes are a typo'd definition, a forgotten source file on the command line, or a missing library. Distinguishing "compiler error, my types are wrong" from "linker error, something's missing from the build" will save you real time.

Two flags to add to your habits now, both cheap: `-Wall -Wextra` always (warnings are bugs on layaway: an unused variable, a signed/unsigned comparison, a function path with no return), and `-O2` whenever you measure performance. That second one has teeth, as the mini-project is about to demonstrate.

## Build it: porting word-count from Python to C++

Time to assemble the pieces. Here's a small, honest Python program in the style of this book: read a file, count word frequencies, print the top five. It's the shape of half the scripting you'll ever do:

```python
import sys
from collections import Counter

def word_count(path):
    counts = Counter()
    with open(path) as f:
        for line in f:
            for raw in line.lower().split():
                word = raw.strip(".,;:!?\"'()")
                if word:
                    counts[word] += 1
    return counts

if __name__ == "__main__":
    if len(sys.argv) < 2:                       # usage: python wordcount.py <file>
        raise SystemExit(f"usage: {sys.argv[0]} <file>")
    counts = word_count(sys.argv[1])
    pairs = sorted(counts.items(), key=lambda kv: (-kv[1], kv[0]))
    for word, n in pairs[:5]:
        print(f"{n:4d}  {word}")
```

(We spell out the sort instead of using `Counter.most_common` because `most_common` hides a sort we're about to write by hand, and the explicit key, count descending then word ascending, makes ties deterministic in both languages.)

We'll port it in two pieces and then assemble the full file.

**Piece 1: cleaning a token.** Python's `raw.strip(punctuation)` and `.lower()` need to be written out. Lowercase each character, then find the first and last characters that aren't punctuation and take the substring between them. This is the top of our C++ file (includes first, then the helper):

```cpp
#include <algorithm>
#include <cctype>
#include <fstream>
#include <iostream>
#include <string>
#include <unordered_map>
#include <utility>
#include <vector>

// Lowercase a token and strip punctuation from both ends.
std::string clean(const std::string& raw) {
    std::string word;
    for (char c : raw) {
        word += static_cast<char>(std::tolower(static_cast<unsigned char>(c)));
    }
    const std::string junk = ".,;:!?\"'()";
    size_t start = word.find_first_not_of(junk);
    if (start == std::string::npos) return "";          // all punctuation
    size_t end = word.find_last_not_of(junk);
    return word.substr(start, end - start + 1);
}
```

Everything here is a section of this chapter in action. The parameter is `const std::string&`: look, don't copy, don't touch. The build-up `word += ...` is cheap because strings mutate. `find_first_not_of` returns `std::string::npos` (a sentinel meaning "not found," C++'s `-1` from `str.find`) when the token is pure punctuation, and we return an empty string that the caller will skip. The one ugly line, `std::tolower(static_cast<unsigned char>(c))`, is a C inheritance: `tolower`'s argument must be non-negative, and `char` can be signed, so we convert explicitly. `static_cast` is C++'s spelling of a deliberate conversion, loud on purpose.

**Piece 2: `main`.** Add this below `clean` and the file is complete. This is the rest of the program, compiled and run as one unit with the piece above:

```cpp
int main(int argc, char* argv[]) {
    if (argc < 2) {
        std::cerr << "usage: " << argv[0] << " <file>\n";
        return 1;
    }

    std::ifstream in(argv[1]);
    if (!in) {
        std::cerr << "could not open " << argv[1] << "\n";
        return 1;
    }

    std::unordered_map<std::string, int> counts;
    std::string raw;
    while (in >> raw) {                    // >> splits on whitespace, like .split()
        std::string word = clean(raw);
        if (!word.empty()) counts[word] += 1;
    }

    // A map has no notion of order, so copy into a vector and sort that.
    std::vector<std::pair<std::string, int>> pairs(counts.begin(), counts.end());
    std::sort(pairs.begin(), pairs.end(),
              [](const auto& a, const auto& b) {
                  if (a.second != b.second) return a.second > b.second;
                  return a.first < b.first;   // tie-break alphabetically
              });

    int shown = 0;
    for (const auto& [word, n] : pairs) {
        std::cout << n << "  " << word << "\n";
        if (++shown == 5) break;
    }
    return 0;
}
```

Top to bottom:

- **Arguments.** `sys.argv` becomes the pair `argc` (count) and `argv` (array of C strings). `argv[0]` is the program name, same convention.
- **The read loop.** `in >> raw` extracts one whitespace-delimited token per iteration and, in true stream style, the expression is falsy at end-of-file, so the loop condition reads "while another token arrives." It replaces both the line loop and the `.split()` from Python.
- **Counting.** `counts[word] += 1` works with no `Counter` import, because `operator[]` on a miss inserts a zero: the sharp edge from the containers section, here doing exactly what we want.
- **Sorting.** `sorted(counts.items(), key=...)` becomes three explicit steps: copy the map's pairs into a vector (maps can't be reordered), then `std::sort` with a comparator. The `[](...) { ... }` is a **lambda**, C++'s anonymous function: same idea as Python's `lambda`, allowed to have a full body. Note it's a two-argument "is a before b?" comparator rather than Python's one-argument key. `.first` and `.second` are the pair's key and value.
- **Printing.** Structured bindings unpack each pair, and we stop after five.

On a small sample file, both versions print the identical report:

```text
9  the
4  and
3  pad
3  polish
2  wafer
```

Read the two programs side by side once more before moving on. Every line of the C++ maps onto a line of the Python; nothing was reorganized. The port is longer (types written out, sort spelled out, error paths explicit), but it is the same program, and you understood every mechanism in it before you got here.

## Mini-project: `wordfreq`, a timed CLI tool

Now make it a real tool and answer the question this whole chapter has been implying: what does the speed actually look like? You'll build parallel Python and C++ versions of `wordfreq` (file in, frequency report out, top-N configurable, self-timing), then race them on a corpus big enough to mean something.

The Python version:

```python
"""wordfreq.py -- word frequency report for a text file."""
import sys
import time
from collections import Counter

JUNK = ".,;:!?\"'()"

def count_words(path):
    counts = Counter()
    total = 0
    with open(path) as f:
        for line in f:
            for raw in line.lower().split():
                word = raw.strip(JUNK)
                if word:
                    counts[word] += 1
                    total += 1
    return counts, total

def main():
    if len(sys.argv) < 2:
        print(f"usage: {sys.argv[0]} <file> [top_n]", file=sys.stderr)
        return 1
    top_n = int(sys.argv[2]) if len(sys.argv) > 2 else 10

    start = time.perf_counter()
    counts, total = count_words(sys.argv[1])
    elapsed = time.perf_counter() - start

    print(f"{total} words, {len(counts)} unique ({elapsed:.3f}s)")
    pairs = sorted(counts.items(), key=lambda kv: (-kv[1], kv[0]))
    for word, n in pairs[:top_n]:
        print(f"{n:8d}  {word}")
    return 0

if __name__ == "__main__":
    sys.exit(main())
```

The C++ version is the Build-it program plus three upgrades: a `top_n` argument parsed with `std::stoi` (C++'s `int(string)`), a running total, and timing with `std::chrono`, the standard library's clock, with `steady_clock` playing the role of `perf_counter` (monotonic, made for measuring intervals):

```cpp
// wordfreq.cpp -- word frequency report for a text file.
// Build:  g++ -std=c++17 -O2 -Wall -Wextra -o wordfreq wordfreq.cpp
#include <algorithm>
#include <cctype>
#include <chrono>
#include <fstream>
#include <iostream>
#include <string>
#include <unordered_map>
#include <utility>
#include <vector>

std::string clean(const std::string& raw) {
    std::string word;
    for (char c : raw) {
        word += static_cast<char>(std::tolower(static_cast<unsigned char>(c)));
    }
    const std::string junk = ".,;:!?\"'()";
    size_t start = word.find_first_not_of(junk);
    if (start == std::string::npos) return "";
    size_t end = word.find_last_not_of(junk);
    return word.substr(start, end - start + 1);
}

int main(int argc, char* argv[]) {
    if (argc < 2) {
        std::cerr << "usage: " << argv[0] << " <file> [top_n]\n";
        return 1;
    }
    int top_n = (argc > 2) ? std::stoi(argv[2]) : 10;

    auto start = std::chrono::steady_clock::now();

    std::ifstream in(argv[1]);
    if (!in) {
        std::cerr << "could not open " << argv[1] << "\n";
        return 1;
    }

    std::unordered_map<std::string, int> counts;
    long long total = 0;
    std::string raw;
    while (in >> raw) {
        std::string word = clean(raw);
        if (!word.empty()) {
            counts[word] += 1;
            total += 1;
        }
    }

    std::chrono::duration<double> elapsed =
        std::chrono::steady_clock::now() - start;

    std::cout << total << " words, " << counts.size() << " unique ("
              << elapsed.count() << "s)\n";

    std::vector<std::pair<std::string, int>> pairs(counts.begin(), counts.end());
    std::sort(pairs.begin(), pairs.end(),
              [](const auto& a, const auto& b) {
                  if (a.second != b.second) return a.second > b.second;
                  return a.first < b.first;
              });

    int shown = 0;
    for (const auto& [word, n] : pairs) {
        std::cout << n << "  " << word << "\n";
        if (++shown == top_n) break;
    }
    return 0;
}
```

For a test corpus, generate about 12 MB of text with a 30,000-word vocabulary (a few lines of Python with `random.choices`, or use any large text you have; Project Gutenberg's complete Shakespeare a few times over works fine). Then race them. On the Linux box these numbers came from (yours will differ, the ratios less so):

```text
$ g++ -std=c++17 -O2 -Wall -Wextra -o wordfreq wordfreq.cpp
$ ./wordfreq corpus.txt 3
1800000 words, 29510 unique (0.217s)
256  drl
202  xwe
201  ucm
$ python3 wordfreq.py corpus.txt 3
1800000 words, 29510 unique (0.382s)
     256  drl
     202  xwe
     201  ucm
```

Same answer, and C++ wins, but by less than 2x. If the chapter's framing led you to expect 50x, this result deserves an explanation, and the explanation is worth more than the benchmark. Two experiments dig it out.

**Experiment 1: drop `-O2`.** Rebuild with plain `g++ -std=c++17 -Wall -Wextra` and rerun. Measured here: 0.67 seconds. The unoptimized C++ *loses to Python*. Without optimization the compiler emits naive, debuggable code, while Python's hot paths in this program (`str.split`, `str.strip`, `Counter.__setitem__`) are not Python at all; they're the interpreter's C internals, from 5.1. This benchmark is mostly a race between g++'s output and CPython's C guts, and unoptimized g++ output is slow. Hence the rule: never benchmark without `-O2`. It's the difference between the translator's rough draft and the published edition.

**Experiment 2: race pure loops.** Make the work per-iteration tiny and Python-level, so the interpreter's fetch-decode-typecheck overhead is the whole cost:

```cpp
#include <chrono>
#include <iostream>

int main() {
    auto start = std::chrono::steady_clock::now();
    long long total = 0;
    for (long long i = 0; i < 100'000'000; ++i) {
        total += i % 7;      // the % keeps the compiler from collapsing the loop
    }
    std::chrono::duration<double> elapsed =
        std::chrono::steady_clock::now() - start;
    std::cout << total << " in " << elapsed.count() << "s\n";
    return 0;
}
```

```text
299999995 in 0.073s        # C++ with -O2
299999995 in 5.373s        # the same loop in Python: ~73x slower
```

(The digit separators in `100'000'000` are C++'s `100_000_000`. And that innocent `% 7` is there because without it, `-O2` recognizes the sum of consecutive integers and replaces the entire loop with the closed-form answer. The translated book doesn't just read faster, it sometimes rewrites the argument.)

Now the full picture snaps into place. When your Python program spends its time inside C-implemented built-ins, C++ buys you a modest constant factor. When your program does its real work in Python-level loops (per-element arithmetic, per-record logic, simulation steps), C++ is one to two orders of magnitude faster. That's exactly the "going native" judgment from 16.4: profile first, port the loops that are actually made of Python. For your portfolio, keep both `wordfreq` versions in one repo with a README table of your measurements, a small artifact that proves you can write both languages and reason honestly about performance, which is rarer than either skill alone.

## Common mistakes

1. **Forgetting `&` on a parameter, then wondering why nothing changed.** You write `void update(Config c)`, mutate `c` inside, and the caller's config is untouched, because you edited a photocopy. The reflex to build: at every function boundary ask "copy, `&`, or `const&`?" If you meant to modify the caller's object, you need `&`.
2. **Expecting `b = a` to alias.** Python habits say `b` and `a` now share; C++ made a copy. Neither of your subsequent edits will appear in the other. If you want two names for one object, that's a reference (`auto& b = a;`). And if you find yourself wanting shared ownership, that's 29.2's problem, arriving shortly.
3. **Probing an `unordered_map` with `[]`.** `if (counts["maybe"] > 0)` silently inserts `"maybe"` with value 0. Your map grows on every lookup, and code that iterates the map later sees ghost keys. Test with `counts.count(key)` or `find`; reserve `[]` for when insert-if-absent is what you want (like counting).
4. **Indexing out of bounds and getting garbage instead of an exception.** `v[v.size()]` doesn't throw; it reads memory beyond the array, which may work, crash, or corrupt something quietly. During development, `.at(i)` gives you Python-style checked access for the cost of a branch.
5. **Fighting signed/unsigned comparison warnings.** `for (int i = 0; i < v.size(); ++i)` draws a warning because `.size()` returns an unsigned `size_t` and comparing it with a signed `int` has trap cases. Use `size_t i = 0`, or sidestep indices entirely with a range-for. Don't silence the warning; it's flagging a real class of bug (`v.size() - 1` on an empty vector is a gigantic positive number, not `-1`).
6. **Trusting a fixed-width `int` like a Python `int`.** Sum a hundred million squares into an `int` and it overflows without a word. Signed overflow isn't even guaranteed to wrap; it's undefined behavior. When totals can grow, use `long long`, and treat impossible-looking benchmark numbers as an overflow alarm.
7. **Declaring but never defining, then panicking at the linker.** `undefined reference to 'average(...)'` is not a compiler error and no amount of editing your `#include`s fixes it. Something is missing from the link: the function's body, a source file on the command line, or a library flag.
8. **Benchmarking a debug build.** Unoptimized C++ can lose to Python, as you saw. If you're about to conclude anything from a timing, check that `-O2` was on the command line first.

## On the job / interview angle

**On the job.** The Python-plus-C++ combination is a specific and valuable profile: teams that keep the product logic in Python and the performance-critical core in C++ (ML infrastructure, quant finance, robotics, graphics) need people fluent on both sides of the boundary. In semiconductor equipment (the 17.6 career path), C++ is closer to mandatory: tool-control software, motion planning for wafer handlers, and data paths for high-rate sensor streams are C++ codebases, and interviews there will probe whether you understand what the machine is doing, not just the syntax. Day one on any such team, the skills from this chapter are the ones in play: reading signatures to know what's copied versus shared, respecting `const`, and reading compiler output without flinching.

**In interviews.** "You know Python, so how is passing a list to a function different in C++?" is a real screening question, and the answer is this chapter's core: Python copies a reference to a shared object, C++ copies the object unless you write `&`, and `const&` is the read-only middle path. Expect follow-ups on reference versus pointer (can't be null/reseated versus can), on what RAII buys over garbage collection (deterministic cleanup at scope exit; worth contrasting with `with`, which shows you understand both), and on the compile/link distinction ("what's the difference between a compiler error and a linker error?" separates people who've built C++ from people who've read about it). If you can also explain *why* your word-count port was only 2x faster while a pure loop was 70x (interpreter overhead lives per-operation, and Python built-ins are already C), you'll be giving a stronger answer than most working C++ programmers.

### Solutions

1. It prints `run`. `shout` receives a copy of `msg`; the `+= "!"` grows the copy, which is destroyed when the function returns, and the caller's string is untouched. (Verified: the program compiles and prints `run`.)

2. (a) Compiles: reassignment of a non-const variable is fine, as long as the type stays `int`. (b) Does not compile: `x` is `const`, and the compiler enforces the promise. (c) Does not compile: a string literal can't convert to `int`; this is the static-typing wall. (d) Does not compile: a reference must be bound to an existing object at initialization; there's nothing to bind to.

3. Fix one: change the parameter to a reference, `void shout(std::string& s)`, so that `s += "!"` edits the caller's string. Fix two: keep pass-by-value but return the result:

   ```cpp
   #include <iostream>
   #include <string>

   std::string shout(std::string s) {
       s += "!";
       return s;
   }

   int main() {
       std::string msg = "run";
       msg = shout(msg);
       std::cout << msg << "\n";   // run!
       return 0;
   }
   ```

   The second style (take a copy, modify it, return it) is the value-semantics idiom, and it mirrors how you'd handle an immutable string in Python.

4. ```cpp
   #include <iostream>

   void swap_ints(int& a, int& b) {
       int tmp = a;
       a = b;
       b = tmp;
   }

   int main() {
       int x = 1, y = 2;
       swap_ints(x, y);
       std::cout << "x = " << x << ", y = " << y << "\n";   // x = 2, y = 1
       return 0;
   }
   ```

   Without references, `swap_ints(int a, int b)` would receive copies, dutifully swap the copies, and destroy them at return. The caller's `x` and `y` never move. The references make `a` and `b` alternate names for the caller's actual variables, so the swap happens in the caller's boxes. (A pointer version, `swap_ints(int*, int*)` called as `swap_ints(&x, &y)`, also works. That's the C way, and the visible `&` at the call site is its one advantage.)

5. ```cpp
   #include <algorithm>
   #include <iostream>
   #include <vector>

   // Pass by value ON PURPOSE: sorting mutates, and we want to sort a copy
   // so the caller's data stays in its original order.
   double median(std::vector<double> v) {
       std::sort(v.begin(), v.end());
       size_t n = v.size();
       if (n % 2 == 1) return v[n / 2];
       return (v[n / 2 - 1] + v[n / 2]) / 2.0;
   }

   int main() {
       std::vector<double> readings = {0.83, 0.81, 0.82, 0.85};
       std::cout << "median = " << median(readings) << "\n";       // 0.825
       std::cout << "first is still " << readings[0] << "\n";      // 0.83, unsorted
       return 0;
   }
   ```

   The function needs a scrambled (sorted) version of the data without scrambling the caller's copy. `const&` won't do (you can't sort through it), so you'd otherwise write `&` plus a manual copy inside. Taking the parameter by value is that copy, made honestly in the signature.

6. ```cpp
   #include <iostream>
   #include <string>
   #include <unordered_map>

   std::unordered_map<char, int> char_counts(const std::string& s) {
       std::unordered_map<char, int> counts;
       for (char c : s) counts[c] += 1;
       return counts;
   }

   int main() {
       auto counts = char_counts("slurry");
       std::cout << "'r' appears " << counts['r'] << " times\n";   // 2
       std::cout << "'z' appears " << counts['z'] << " times\n";   // 0 (created just now)
       return 0;
   }
   ```

   The prediction to make: `counts['z']` doesn't raise anything. It inserts `'z'` with count 0 and returns it, so after that line the map has one more key than the string had distinct letters. Harmless here, but the mechanism behind common mistake #3.

7. ```cpp
   #include <iostream>

   double area(double radius) { return 3.14159265 * radius * radius; }
   double area(double width, double height) { return width * height; }

   int main() {
       std::cout << area(2.0) << "\n";        // circle: 12.5664
       std::cout << area(3.0, 4.0) << "\n";   // rectangle: 12
       return 0;
   }
   ```

   In Python, `def area(...)` the second time simply rebinds the name `area`: the module dict has one entry per name, so the circle version is gone. Python's substitutes are default/keyword arguments (`def area(w, h=None)` with an `if`), separate names, or `functools.singledispatch`. C++ keeps both because the parameter types are part of each function's identity, and the compiler resolves each call site to one of them at compile time.

8. ```cpp
   #include <fstream>
   #include <iostream>

   int main() {
       std::ifstream in("readings.txt");
       if (!in) {
           std::cerr << "could not open readings.txt\n";
           return 1;
       }
       double total = 0.0;
       double value = 0.0;
       while (in >> value) {     // >> parses a double, like float(token)
           total += value;
       }
       std::cout << "sum = " << total << "\n";
       return 0;
   }
   ```

   On the sample `readings.txt` from the RAII section this prints `sum = 2.46`. The file closes at the closing brace of `main`, when `in` goes out of scope and its destructor runs, including on the early `return 1` path, where the destructor also runs (a not-yet-open stream has nothing to release, but the rule is uniform). That uniformity is RAII's pitch.

9. Parse the extra argument and gate the counting on length:

   ```text
   int min_len = (argc > 3) ? std::stoi(argv[3]) : 1;
   ...
   std::string word = clean(raw);
   if (word.size() >= static_cast<size_t>(min_len)) {
       counts[word] += 1;
       total += 1;
   }
   ```

   (A fragment: drop the first line in with the `top_n` parsing and replace the counting `if` in `wordfreq.cpp`.) The defensible choice made here: filtered-out words count toward neither `counts` nor `total`, so "N words, M unique" describes the report the user actually sees. Counting them in `total` but not `counts` is also defensible. What's not defensible is not deciding. Note the `static_cast<size_t>`: comparing `word.size()` (unsigned) against a signed `int` without it is exactly the warning from common mistake #5.

10. Representative numbers from the machine used throughout this chapter: C++ with `-O2`, 0.073 s; C++ without, 0.215 s; Python, 5.37 s. Ratio: about 73x with `-O2`, and all three agree the answer is 299999995. With `total += i` instead of `total += i % 7`, the `-O2` binary reports a time near zero (tens of nanoseconds): the optimizer recognizes the sum of `0..n-1`, replaces the entire loop with the closed-form `n(n-1)/2`, and your "benchmark" measures two clock reads. Lesson one of performance measurement in a compiled language: make sure the work you're timing can't be computed away, because the translator reads the whole book and is allowed to improve it.
