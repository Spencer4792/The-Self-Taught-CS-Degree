## Start here: the storage-unit key

Chapter 5.1 gave you the kitchen: countertop for cache, pantry for RAM, a stack of plates for call frames, and a shared storage room for the heap. Keep all of that; it's still true. What changes in C++ is who runs the storage room.

Think of the heap as a self-storage warehouse. When you ask for heap memory, you rent a unit and get a key. The key is the pointer: it tells you where your unit is, and it's the only way back in. In Python, the warehouse has a manager. He watches who's holding copies of each key (reference counting), sweeps for units whose keyholders only reference each other (the cycle collector), and clears out anything unreachable. You never think about keys at all.

The C++ warehouse has no manager. You rent a unit with `new`, and you are personally responsible for handing the key back with `delete`. Every classic memory bug is a key-handling failure:

- Lose the key without returning it, and the unit stays rented forever. Nobody can reclaim it. That's a **memory leak**.
- Hand the key back twice. After the first return, the clerk may have re-let the unit to someone else, and your second "return" clears out a stranger's belongings. That's a **double free**.
- Photocopy the key, return the original, then sneak back in with the copy. The unit might be empty, or it might be somebody else's now. That's a **use-after-free**.

Doing this by hand at scale is hopeless, and the C++ community figured that out decades ago. The fix is not discipline; it's design. You attach each key to an object whose destructor returns it automatically the moment the object dies. Once every key rides inside such an object, there is no key-handling code left to get wrong. That idea is called RAII, it's the center of this chapter, and it's the reason well-written modern C++ contains almost no `new` or `delete` at all.

## The stack and the heap, without the net

The mechanics are the ones you already know from 5.1: each function call pushes a frame onto the stack; local variables live in the frame; returning pops the frame and everything in it evaporates. The heap is the big open region where allocations live until someone frees them. Watch both from C++:

```cpp
#include <iostream>

void frame_b() {
    int b = 2;
    std::cout << "frame_b's b lives at " << &b << "\n";
}

void frame_a() {
    int a = 1;
    std::cout << "frame_a's a lives at " << &a << "\n";
    frame_b();
}

int main() {
    int m = 0;
    int* h = new int(7);
    std::cout << "main's m lives at    " << &m << "\n";
    std::cout << "heap int lives at    " << h << "\n";
    frame_a();
    delete h;
}
```

One run printed (your addresses will differ, since the OS randomizes layout each run):

```text
main's m lives at    0xffffdab8c53c
heap int lives at    0xbd0be8f94eb0
frame_a's a lives at 0xffffdab8c514
frame_b's b lives at 0xffffdab8c4f4
```

Two things to notice. The three stack addresses are near each other and step *downward* as calls nest: `main`'s frame, then `frame_a`'s below it, then `frame_b`'s below that, exactly the plate-stack picture (the stack grows toward lower addresses on most machines, as you saw in 25.2). And the heap address is off in a different region of the address space entirely.

The deep difference from Python is what a variable *is*. In Python, every variable is a name bound to an object that lives on the heap; even `x = 5` binds a name to a heap-allocated int object. In C++, `int m = 0` puts four actual bytes in the current stack frame. No box, no header, no reference count, just the bytes. Heap memory only enters the picture when you ask for it, and when you ask for it, you own it.

## Object lifetime and storage duration

C++ is precise about when objects are born and die, and the language gives that precision a name: every object has a **storage duration**, which determines who allocates it, where, and when it's destroyed.

- **Automatic** storage: ordinary local variables. Born when execution reaches their definition, destroyed (in reverse order of construction) when their scope ends. They live in the stack frame.
- **Static** storage: globals and `static` locals. Born once (globals before `main`, static locals on first use), destroyed after `main` returns.
- **Dynamic** storage: anything from `new`. Born when you say so, destroyed when you say so, and *only* when you say so.

The word "destroyed" is doing real work here. When a C++ object dies, its **destructor** runs, a function named `~ClassName()` that gets called automatically at the moment of death. You can watch the whole schedule by giving a class a noisy constructor and destructor:

```cpp
#include <iostream>

struct Noisy {
    const char* name;
    Noisy(const char* n) : name(n) { std::cout << "construct " << name << "\n"; }
    ~Noisy() { std::cout << "destroy " << name << "\n"; }
};

Noisy global{"global"};

void func() {
    Noisy local{"local"};
    static Noisy once{"static-local"};
    std::cout << "  (func body runs)\n";
}

int main() {
    std::cout << "main begins\n";
    func();
    func();
    Noisy* dyn = new Noisy{"heap"};
    (void)dyn;   // never deleted -- watch which destructor lines are missing
    std::cout << "main ends\n";
}
```

```text
construct global
main begins
construct local
construct static-local
  (func body runs)
destroy local
construct local
  (func body runs)
destroy local
construct heap
main ends
destroy static-local
destroy global
```

Read that output slowly; it is the whole lifetime model in twelve lines. The global is constructed before `main` and destroyed after it. The automatic `local` is constructed and destroyed on *every* call. The static local is constructed on the first call only and cleaned up at program exit. And the heap object? `construct heap` appears, but there is no `destroy heap` anywhere. We rented the unit and walked away with the key. Its destructor never ran, and whatever cleanup it was supposed to do never happened.

That last observation is bigger than it looks. In Python, `__del__` runs "eventually, probably": when the refcount hits zero or the GC gets around to it, with no guarantees about ordering or timing. In C++, destruction is *deterministic*: automatic objects die at the closing brace, in reverse order, every time. Everything good in this chapter flows from that guarantee.

## new, delete, and the bug factory

The manual interface first, because you must be able to read it even though you'll rarely write it. `new T(args)` rents heap space for one `T`, constructs it, and hands you the key; `delete p` runs the destructor and returns the space. Arrays have their own pair:

```cpp
#include <iostream>

int main() {
    int* p = new int(41);        // one int on the heap
    *p += 1;
    std::cout << *p << "\n";     // 42
    delete p;                    // hand it back

    int* arr = new int[5]{1, 2, 3, 4, 5};   // five ints, contiguous
    std::cout << arr[4] << "\n";            // 5
    delete[] arr;                // array form MUST use delete[]
}
```

This looks manageable in a ten-line program. It stops being manageable the moment allocations and frees are separated by function boundaries, early returns, exceptions, and time. A raw pointer that owns memory (a **raw owning pointer**) carries an invisible obligation ("someone must delete this, exactly once, after everyone is done with it") that the compiler does not check and the type does not express. Here are the three ways that obligation gets violated, each demonstrated for real. For all three we'll compile with **AddressSanitizer**, a runtime checker built into gcc and clang that instruments every allocation and memory access:

```text
g++ -std=c++17 -Wall -Wextra -fsanitize=address program.cpp -o program && ./program
```

Get in the habit of running your C++ under ASan during development. It turns silent corruption into loud, precise crash reports, and it's the closest thing C++ has to Python's friendly tracebacks.

### Failure 1: the leak

This program is deliberately buggy: `process_batch` rents and never returns:

```cpp
#include <iostream>

void process_batch() {
    int* data = new int[1000];
    data[0] = 1;
    std::cout << "processed batch starting with " << data[0] << "\n";
    // ... forgot: delete[] data;
}

int main() {
    for (int i = 0; i < 3; ++i) process_batch();
}
```

It runs "fine", because leaks don't crash, they accumulate. But under ASan, at exit:

```text
==34==ERROR: LeakSanitizer: detected memory leaks

Direct leak of 12000 byte(s) in 3 object(s) allocated from:
    #0 ... in operator new[](unsigned long)
    #1 ... in process_batch()
    #2 ... in main

SUMMARY: AddressSanitizer: 12000 byte(s) leaked in 3 allocation(s).
```

Three calls, three lost keys, 12,000 bytes rented forever, and the report walks you straight to the allocation site. In a script that exits in a second, who cares; the OS reclaims everything at process death. In a server that runs for months, this is the bug that pages you at 3 a.m. as memory climbs a few kilobytes per request until the machine falls over. Remember from 5.1 that even Python leaks when you accumulate references by accident; C++ additionally leaks when you simply *forget*.

### Failure 2: the double free

Again deliberately broken:

```cpp
#include <iostream>

int main() {
    int* p = new int(7);
    std::cout << *p << "\n";
    delete p;
    delete p;   // double free: the second delete corrupts the allocator
}
```

```text
==42==ERROR: AddressSanitizer: attempting double-free on 0xebb6314007b0
    #0 ... in operator delete(void*, unsigned long)
    #1 ... in main
0xebb6314007b0 is located 0 bytes inside of 4-byte region
freed by thread T0 here:    ... in main
previously allocated by thread T0 here:    ... in main
```

Without ASan, a double free may not crash at the second `delete`. The allocator's bookkeeping gets corrupted, and the program falls over later, somewhere unrelated, in a way that doesn't reproduce in the debugger. Handing back a key for a unit that's already been re-let means someone else's data gets clobbered. Double frees are also a classic security hole: attackers deliberately trigger them to trick the allocator into handing out overlapping memory.

The everyday way this happens isn't typing `delete` twice in a row. It's two different objects both believing they own the same pointer, each dutifully deleting it once. Hold that thought; it's the "rule of three" bug and we'll meet it properly below.

### Failure 3: the use-after-free

```cpp
#include <iostream>

int main() {
    int* p = new int[4]{1, 2, 3, 4};
    delete[] p;
    std::cout << p[2] << "\n";   // use-after-free: reading a dead buffer
}
```

```text
==49==ERROR: AddressSanitizer: heap-use-after-free on address 0xe480362007b8
READ of size 4 at 0xe480362007b8 thread T0
    #0 ... in main
0xe480362007b8 is located 8 bytes inside of 16-byte region
freed by thread T0 here:              ... in main
previously allocated by thread T0 here: ... in main
```

Note what `delete` does *not* do: it doesn't null your pointer, and it doesn't erase your copies of it. `p` still holds the old address: a photocopy of a returned key. Reading through it might return the old data (if the unit hasn't been re-let yet), garbage, or another object's live data; writing through it corrupts whoever lives there now. Use-after-free is the single most exploited memory bug in real-world software. Microsoft and Google have both reported that around 70 percent of their serious security vulnerabilities are memory-safety bugs, with use-after-free at the front of the pack.

### Dangling references: the stack version

You don't need `new` to point at dead memory. Automatic variables die at the closing brace, and C++ will let you keep a reference to the corpse. This function is broken by construction:

```cpp
int& broken() {
    int local = 5;
    return local;   // returns a reference to a variable about to die
}

int main() { return 0; }
```

Here the compiler can see the whole crime in one function, so `-Wall` catches it:

```text
warning: reference to local variable 'local' returned [-Wreturn-local-addr]
```

This is why the flags in this book's compile line aren't optional decoration. But the compiler only catches the obvious cases. The sneaky version is a reference into a container that *relocates*:

```cpp
#include <iostream>
#include <vector>

int main() {
    std::vector<int> v = {1, 2, 3};
    int& first = v.front();               // points into v's current buffer
    for (int i = 0; i < 1000; ++i)
        v.push_back(i);                   // growth reallocates the buffer
    std::cout << first << "\n";           // 'first' points at freed memory
}
```

No warning here, yet under ASan this is a heap-use-after-free, with the stack trace showing the free happened inside `push_back`'s reallocation. When a vector outgrows its capacity it rents a bigger unit, moves everything over, and returns the old one; every pointer, reference, and iterator into the old buffer silently becomes a photocopy of a returned key. This is **iterator invalidation**, and "which operations invalidate what" is documented for every standard container. The Python analogue simply cannot happen: a Python list holds references to objects that the GC keeps alive as long as anyone can reach them.

## RAII: the big idea

Everything above has one root cause: cleanup was a separate line of code that someone had to remember to run, on every path, exactly once. The fix is to make cleanup not be a line of code. Make it a *consequence of scope*.

**RAII** (Resource Acquisition Is Initialization, an awkward name for a simple discipline) says: wrap every resource in a class. Acquire the resource in the constructor. Release it in the destructor. Then let the deterministic lifetime rules you saw earlier do the rest: when the wrapper object dies, the resource is released, automatically, no matter *how* the scope was left: normal fall-through, early `return`, or an exception unwinding the stack. The key is welded to an object that cannot die without returning it.

Here is RAII applied to a file handle, the classic first example:

```cpp
#include <cstdio>
#include <stdexcept>

class File {
public:
    File(const char* path, const char* mode) : f_(std::fopen(path, mode)) {
        if (!f_) throw std::runtime_error("could not open file");
    }
    ~File() {
        std::fclose(f_);   // cleanup lives here, and ONLY here
    }

    // no copying: two Files closing the same handle would be a double-close
    File(const File&) = delete;
    File& operator=(const File&) = delete;

    std::FILE* get() { return f_; }

private:
    std::FILE* f_;
};

int main() {
    {
        File f("demo.txt", "w");
        std::fputs("RAII wrote this\n", f.get());
    }   // f dies here -> ~File() -> fclose(), guaranteed, no matter what

    File g("demo.txt", "r");
    char buf[64];
    if (std::fgets(buf, sizeof buf, g.get()))
        std::printf("read back: %s", buf);
}
```

```text
read back: RAII wrote this
```

Notice the two deleted functions. A `File` must not be copyable, because two `File` objects holding the same handle would each close it, a double free wearing a different hat. Declaring the copy operations `= delete` makes the compiler reject any attempt at compile time. Expressing "this type owns something uniquely" in the type itself, so misuse won't even compile, is very much the C++ way.

You have seen this idea before, in Python:

```python
with open("demo.txt", "w") as f:
    f.write("with wrote this\n")
# the with-block guarantees close -- but only because you wrote 'with'

f2 = open("demo.txt")      # forget the with, and...
data = f2.read()           # ...this file stays open until the GC
assert data == "with wrote this\n"      # gets around to it. Maybe.
```

Python's `with` is RAII bolted on at the call site: it exists precisely because Python destructors aren't deterministic, so scope-based cleanup needs special syntax and the caller's cooperation. The comparison is worth internalizing. In Python, the *user* of a file must remember `with`, at every use. In C++, the *author* of `File` decided the cleanup policy once, and every user gets it automatically; there is no way to use a `File` and forget to close it. RAII is opt-out-impossible; `with` is opt-in.

And RAII generalizes far past memory and files: mutex locks (`std::lock_guard` unlocks in its destructor; you met the deadlock dangers in 5.2), database transactions (commit or roll back in the destructor), timers, socket handles, GPU buffers. Any resource with an acquire/release pair fits the pattern. C++ programmers reach for it reflexively; you should too.

## The rule of zero and the rule of five

RAII puts serious weight on a class's special member functions: the destructor, the copy operations, and (as of C++11) the move operations. Two rules of thumb govern them.

The **rule of zero**: most classes should define *none* of them. If your class's members are themselves RAII types (`std::string`, `std::vector`, smart pointers), the compiler-generated destructor destroys each member, the generated copy copies each member, and everything just works. A class holding a `std::string` and a `std::vector<int>` needs zero special functions. This is where you should live by default: push all ownership down into vocabulary types that already handle it, and your own classes stay boring.

The **rule of five**: if your class directly owns a raw resource (a raw pointer from `new`, a file descriptor, anything the compiler doesn't understand), then the compiler-generated specials are all wrong for you, and you must write (or explicitly delete) all five:

1. destructor
2. copy constructor
3. copy assignment operator
4. move constructor
5. move assignment operator

Why all five as a package? Because they encode one coherent answer to one question: *what does ownership mean for this type?* If you wrote a destructor, you own something. If you own something, the compiler's memberwise copy, which just duplicates the pointer rather than the thing it points to, creates two owners of one resource, and you've manufactured the double-free from earlier. (Before C++11 this was the "rule of three"; moves added two more.) You'll write all five for real in the Build it section. First, though, you need to know what those two move operations actually are.

## Copy vs move: why moves exist

Start from what Python does, because it's neither of these. In Python, assignment copies nothing:

```python
a = [1, 2, 3]
b = a                # no copy: b is a second name for the same list
b.append(4)
assert a == [1, 2, 3, 4]   # "assignment" never copied anything
```

That's name binding: two names, one heap object, and the manager (refcounting) keeps the object alive while either name exists. C++ has no manager, so "two variables, one buffer, whoever dies last cleans up" isn't expressible with plain ownership. Instead C++ gives you two honest options.

A **copy** duplicates the resource: rent a second unit, haul over duplicates of everything in the first. Correct, independent, and expensive when the resource is a megabyte of buffer.

A **move** transfers the resource: hand your key to the new owner and keep nothing. The buffer doesn't budge; only the ownership changes. The source object is left in a valid but empty state: alive, destructible, assignable, but not holding anything. Moves exist because so many objects are *transferred* rather than shared: returned from functions, passed into containers, shuffled during a vector's reallocation. Paying a deep copy at each hand-off is pure waste when the giver is done with the goods.

The syntax: a move happens when the source is an rvalue, meaning a temporary or something you've explicitly marked with `std::move`. Despite its name, `std::move` moves nothing; it's a cast that says "I'm done with this one; you may cannibalize it." Watch the compiler choose:

```cpp
#include <iostream>
#include <utility>

struct Tracer {
    Tracer()                         { std::cout << "construct\n"; }
    Tracer(const Tracer&)            { std::cout << "COPY\n"; }
    Tracer(Tracer&&) noexcept        { std::cout << "MOVE\n"; }
    Tracer& operator=(const Tracer&) { std::cout << "copy-assign\n"; return *this; }
    Tracer& operator=(Tracer&&) noexcept { std::cout << "move-assign\n"; return *this; }
    ~Tracer()                        { std::cout << "destroy\n"; }
};

Tracer make() { return Tracer{}; }

int main() {
    Tracer a;                  // construct
    Tracer b = a;              // COPY: a is still needed afterwards
    Tracer c = std::move(a);   // MOVE: you promised a is done for
    Tracer d = make();         // construct only: copy elision, no move at all
    (void)b; (void)c; (void)d;
    std::cout << "--- main ending ---\n";
}
```

```text
construct
COPY
MOVE
construct
--- main ending ---
destroy
destroy
destroy
destroy
```

Line four is a bonus fact: returning a fresh object from a function doesn't even move. Since C++17 the compiler is required to construct it directly in the caller's slot (copy elision). Moves are the fallback for the hand-offs elision can't cover.

To see that a move really does steal the buffer rather than copy it, catch `std::string` in the act:

```cpp
#include <iostream>
#include <string>
#include <utility>

int main() {
    std::string s(1'000'000, 'x');       // one megabyte on the heap
    const char* before = s.data();       // remember where the buffer lives

    std::string t = std::move(s);        // "move" = steal that buffer

    std::cout << (t.data() == before ? "same buffer, zero bytes copied\n"
                                     : "copied\n");
    std::cout << "t.size() = " << t.size() << "\n";
}
```

```text
same buffer, zero bytes copied
t.size() = 1000000
```

One million characters changed owners and not one byte of them moved. That's the entire pitch. One warning to take seriously: after `std::move(s)`, the standard only promises `s` is in a "valid but unspecified state." You may destroy it or assign it something new; don't read from it and expect anything in particular. A moved-from object is an empty storage unit with the lights off.

## Smart pointers: RAII for the heap itself

RAII wrapped a file handle; the standard library ships RAII wrappers for the most common resource of all: heap allocations. These are the reason modern C++ codebases contain almost no naked `new`.

### std::unique_ptr: one owner, zero overhead

**`std::unique_ptr<T>`** is a pointer that owns what it points to. Its destructor calls `delete`; its copy operations are deleted (like our `File`); its move operations transfer ownership. It costs exactly what a raw pointer costs (same size, same speed), so there is no performance excuse for raw owning pointers.

```cpp
#include <iostream>
#include <memory>

struct Sensor {
    Sensor()  { std::cout << "sensor online\n"; }
    ~Sensor() { std::cout << "sensor offline\n"; }
    int read() const { return 42; }
};

std::unique_ptr<Sensor> make_sensor() {
    return std::make_unique<Sensor>();   // ownership moves out to the caller
}

int main() {
    auto s = make_sensor();
    std::cout << "reading: " << s->read() << "\n";
}   // s goes out of scope -> ~Sensor() runs. No delete anywhere in this file.
```

```text
sensor online
reading: 42
sensor offline
```

Use `std::make_unique<T>(args)` rather than `unique_ptr<T>(new T(args))`: it's shorter, and it can't leak even in the middle of a complicated expression. Because `unique_ptr` can't be copied, ownership transfers are explicit and visible: `return` moves it out, `std::move` passes it on, and the type system guarantees that at any instant exactly one owner exists. Leaks, double frees, and ownership confusion all become compile errors instead of 3 a.m. incidents. This should be your default for anything heap-allocated.

### std::shared_ptr: counted owners, Python-style

Sometimes there really is no single owner: several subsystems share an object and the last one out should turn off the lights. **`std::shared_ptr<T>`** does what CPython does for every object: it keeps a reference count. Copying bumps the count; each destructor decrements it; zero triggers the delete.

```cpp
#include <iostream>
#include <memory>

int main() {
    auto p = std::make_shared<int>(7);
    std::cout << "owners: " << p.use_count() << "\n";   // 1
    {
        auto q = p;                                     // second owner
        std::cout << "owners: " << p.use_count() << "\n";   // 2
    }                                                   // q dies, count drops
    std::cout << "owners: " << p.use_count() << "\n";   // 1
}   // count hits 0, the int is freed
```

Unlike Python's, this counting isn't free or ambient: the count lives in a separately allocated control block, and increments are atomic so threads can share safely, which makes copying a `shared_ptr` meaningfully more expensive than copying a raw pointer. Reach for it when ownership is truly shared, not as a default. "When in doubt, `shared_ptr`" is how codebases end up with ownership graphs nobody can reason about.

### The cycle problem, and std::weak_ptr

Chapter 5.1 showed you why CPython needs a tracing garbage collector *on top of* reference counting: two objects that reference each other hold each other's counts above zero forever. `shared_ptr` is reference counting with no tracing collector behind it, so in C++ the cycle just leaks. This program is deliberately buggy:

```cpp
#include <iostream>
#include <memory>

struct Node {
    std::shared_ptr<Node> next;
    ~Node() { std::cout << "node destroyed\n"; }
};

int main() {
    auto a = std::make_shared<Node>();
    auto b = std::make_shared<Node>();
    a->next = b;
    b->next = a;   // the cycle: each node keeps the other's count at >= 1
    std::cout << "main ending\n";
}   // a and b (the stack handles) die, but each Node still has one owner
```

```text
main ending
```

No `node destroyed` lines: the destructors never ran. ASan confirms the two `Node` allocations leak at exit. Each node dies only when its count hits zero, and each count can't hit zero until the *other* node dies. Stalemate.

The fix is the same idea as Python's `weakref` from 5.1: make one direction of the relationship non-owning. **`std::weak_ptr<T>`** observes an object managed by `shared_ptr`s without counting as an owner. Because the object might be gone by the time you look, you can't dereference a `weak_ptr` directly. Instead you call `.lock()`, which returns a real `shared_ptr` if the object is still alive and an empty one if it isn't:

```cpp
#include <iostream>
#include <memory>

struct Node {
    std::shared_ptr<Node> next;   // owning direction
    std::weak_ptr<Node> prev;     // observing direction: no count, no cycle
    ~Node() { std::cout << "node destroyed\n"; }
};

int main() {
    auto a = std::make_shared<Node>();
    auto b = std::make_shared<Node>();
    a->next = b;
    b->prev = a;

    if (auto p = b->prev.lock())          // promote weak -> shared, safely
        std::cout << "prev is still alive\n";
    std::cout << "main ending\n";
}
```

```text
prev is still alive
main ending
node destroyed
node destroyed
```

Both destructors run. The design rule: draw your ownership graph and make sure the *owning* edges form no cycles; back-edges (child to parent, cache to entry, observer to subject) should be `weak_ptr` or raw non-owning pointers. In C++ a raw pointer is perfectly respectable as long as it doesn't *own*. "I can see this object but its lifetime is someone else's problem" is exactly what a raw pointer should mean in modern code.

## Build it: DynArray, a rule-of-five owning container

Time to earn the rule of five by writing it. We'll build the dynamic array from Chapter 2.1 (the growable locker row that doubles its capacity) as a proper C++ class that owns its heap buffer. This is essentially what `std::vector<int>` is under the hood, minus twenty years of refinements.

The design: three members (`size_`, `capacity_`, and an owning `int* data_`), `push_back` with doubling growth, and all five special members written out with intent.

```cpp
#include <algorithm>
#include <cassert>
#include <cstddef>
#include <iostream>
#include <utility>

class DynArray {
public:
    DynArray() = default;

    // -- the rule of five ------------------------------------------

    // 1. destructor: give the buffer back
    ~DynArray() {
        delete[] data_;
    }

    // 2. copy constructor: deep copy -- new buffer, same contents
    DynArray(const DynArray& other)
        : size_(other.size_),
          capacity_(other.size_),
          data_(other.size_ ? new int[other.size_] : nullptr) {
        std::copy(other.data_, other.data_ + size_, data_);
    }

    // 3. copy assignment: copy-and-swap (build the copy, then trade places)
    DynArray& operator=(const DynArray& other) {
        DynArray tmp(other);   // copy ctor does the deep copy
        swap(tmp);             // now *this owns the copy...
        return *this;          // ...and tmp's destructor frees our OLD buffer
    }

    // 4. move constructor: steal the buffer, leave the corpse empty
    DynArray(DynArray&& other) noexcept
        : size_(other.size_),
          capacity_(other.capacity_),
          data_(other.data_) {
        other.size_ = 0;
        other.capacity_ = 0;
        other.data_ = nullptr;   // so other's destructor deletes nothing
    }

    // 5. move assignment: free ours, steal theirs
    DynArray& operator=(DynArray&& other) noexcept {
        if (this != &other) {
            delete[] data_;
            size_ = other.size_;
            capacity_ = other.capacity_;
            data_ = other.data_;
            other.size_ = 0;
            other.capacity_ = 0;
            other.data_ = nullptr;
        }
        return *this;
    }

    // -- the actual array interface --------------------------------

    void push_back(int value) {
        if (size_ == capacity_)
            grow();
        data_[size_++] = value;
    }

    std::size_t size() const { return size_; }
    int& operator[](std::size_t i) { return data_[i]; }
    int operator[](std::size_t i) const { return data_[i]; }

    void swap(DynArray& other) noexcept {
        std::swap(size_, other.size_);
        std::swap(capacity_, other.capacity_);
        std::swap(data_, other.data_);
    }

private:
    void grow() {
        std::size_t new_cap = capacity_ ? capacity_ * 2 : 4;
        int* new_data = new int[new_cap];
        std::copy(data_, data_ + size_, new_data);
        delete[] data_;
        data_ = new_data;
        capacity_ = new_cap;
    }

    std::size_t size_ = 0;
    std::size_t capacity_ = 0;
    int* data_ = nullptr;
};

int main() {
    DynArray a;
    for (int i = 0; i < 10; ++i) a.push_back(i * i);
    assert(a.size() == 10 && a[9] == 81);

    DynArray b = a;              // copy: independent buffers
    b[0] = 999;
    assert(a[0] == 0 && b[0] == 999);

    DynArray c = std::move(a);   // move: c stole a's buffer
    assert(c.size() == 10 && a.size() == 0);

    DynArray d;
    d = b;                       // copy assignment
    d = std::move(c);            // move assignment (frees the copy of b first)
    assert(d.size() == 10 && d[9] == 81);

    std::cout << "all DynArray checks passed\n";
}
```

```text
all DynArray checks passed
```

Run it under ASan too; it comes back clean, with every `new[]` matched by exactly one `delete[]` on every path. Walk through the choices, because each one earns its keep:

- **Destructor.** One line, but it's the line that makes everything else matter: whoever ends up holding `data_` when the object dies frees it. `delete[]` on `nullptr` is legal and does nothing, which is why moved-from objects (whose `data_` we nulled) destruct safely.
- **Copy constructor.** A deep copy: new buffer, contents copied over. Note it copies only `size_` elements and sets `capacity_` to match, since there's no reason to duplicate empty growth room.
- **Copy assignment** uses the *copy-and-swap* idiom: build the deep copy as a temporary, swap our guts with it, and let the temporary's destructor free our old buffer on the way out. Three lines, and self-assignment, exception safety during allocation, and old-buffer cleanup all handle themselves. Compare that with the pointer-juggling in move assignment, which has to check `this != &other` by hand.
- **Move constructor.** Pointer theft, then scrubbing the source. Forgetting to null `other.data_` is the classic bug: both objects would then hold the same key, and the second destructor is a double free. Note the `noexcept`: moves that can't throw matter beyond politeness, as one of the exercises demonstrates with a surprise.
- **Move assignment.** Free what we held, steal what they hold, scrub the source.

The payoff for this care is the rule of zero for everyone else. A class holding a `DynArray` member needs no special functions at all: the compiler's memberwise copy calls our deep copy, its move calls our theft, its destructor calls ours. Ownership handled once, at the bottom, correctly.

## Mini-project: an allocation counter that makes leaks visible

ASan finds leaks at exit; sometimes you want a live gauge: how many allocations has this program made, how many has it returned, and what's still out? C++ has a hook that makes this a page of code: you can replace the global `operator new` and `operator delete`, and *every* `new` in the program, yours and the standard library's alike, routes through your versions.

The project: build the counter, point it at a small deliberately careless program, watch it report the leak, then fix the program with smart pointers and watch the gauge read zero.

```cpp
// memcount.cpp -- every new/delete in the program passes through here
#include <cstdio>
#include <cstdlib>
#include <new>

static std::size_t g_news = 0;
static std::size_t g_deletes = 0;
static std::size_t g_bytes = 0;

void* operator new(std::size_t n) {
    void* p = std::malloc(n);
    if (!p) throw std::bad_alloc{};
    ++g_news;
    g_bytes += n;
    return p;
}
void* operator new[](std::size_t n) {
    void* p = std::malloc(n);
    if (!p) throw std::bad_alloc{};
    ++g_news;
    g_bytes += n;
    return p;
}
void operator delete(void* p) noexcept                { if (p) ++g_deletes; std::free(p); }
void operator delete(void* p, std::size_t) noexcept   { if (p) ++g_deletes; std::free(p); }
void operator delete[](void* p) noexcept              { if (p) ++g_deletes; std::free(p); }
void operator delete[](void* p, std::size_t) noexcept { if (p) ++g_deletes; std::free(p); }

void report() {
    std::printf("news:    %zu (%zu bytes)\n", g_news, g_bytes);
    std::printf("deletes: %zu\n", g_deletes);
    std::printf("leaked:  %zu allocation(s)\n", g_news - g_deletes);
}

// --- a small "sensor log" program with careless memory habits ---

struct Reading {
    double value;
    int sensor_id;
};

Reading* take_reading(int id) {
    return new Reading{20.0 + id, id};
}

double average_of(int n) {
    double sum = 0;
    for (int i = 0; i < n; ++i) {
        Reading* r = take_reading(i);
        sum += r->value;
        if (r->value > 22.0)
            continue;          // oops: skips the delete below
        delete r;
    }
    return sum / n;
}

int main() {
    std::printf("average: %.1f\n", average_of(5));
    report();
}
```

```text
average: 22.0
news:    5 (80 bytes)
deletes: 3
leaked:  2 allocation(s)
```

The gauge catches exactly the bug pattern that makes manual memory management untenable: `average_of` *has* a `delete`, placed conscientiously at the bottom of the loop, but the `continue` on hot readings jumps right over it. Two of five readings leak. Early returns, `continue`, `break`, and thrown exceptions are all ways to leave a scope, and a hand-written `delete` guards only one of them. (A note on the machinery: we count with `printf` and `malloc` rather than `cout`, because the counter must not itself allocate through `operator new` while we're inside it. We supply all four sized and unsized `delete` forms so every deallocation path is counted.)

Now the fix. The RAII lesson says: don't add a smarter `delete`, remove the manual key-handling entirely. Replace the two careless functions (the counting machinery stays identical):

```cpp
// same counting machinery as before, fixed program logic
#include <cstdio>
#include <cstdlib>
#include <new>
#include <memory>

static std::size_t g_news = 0;
static std::size_t g_deletes = 0;
static std::size_t g_bytes = 0;

void* operator new(std::size_t n) {
    void* p = std::malloc(n);
    if (!p) throw std::bad_alloc{};
    ++g_news; g_bytes += n;
    return p;
}
void* operator new[](std::size_t n) {
    void* p = std::malloc(n);
    if (!p) throw std::bad_alloc{};
    ++g_news; g_bytes += n;
    return p;
}
void operator delete(void* p) noexcept                { if (p) ++g_deletes; std::free(p); }
void operator delete(void* p, std::size_t) noexcept   { if (p) ++g_deletes; std::free(p); }
void operator delete[](void* p) noexcept              { if (p) ++g_deletes; std::free(p); }
void operator delete[](void* p, std::size_t) noexcept { if (p) ++g_deletes; std::free(p); }

void report() {
    std::printf("news:    %zu (%zu bytes)\n", g_news, g_bytes);
    std::printf("deletes: %zu\n", g_deletes);
    std::printf("leaked:  %zu allocation(s)\n", g_news - g_deletes);
}

struct Reading {
    double value;
    int sensor_id;
};

std::unique_ptr<Reading> take_reading(int id) {
    return std::make_unique<Reading>(Reading{20.0 + id, id});
}

double average_of(int n) {
    double sum = 0;
    for (int i = 0; i < n; ++i) {
        auto r = take_reading(i);
        sum += r->value;
        if (r->value > 22.0)
            continue;          // fine now: r's destructor still runs
    }
    return sum / n;
}

int main() {
    std::printf("average: %.1f\n", average_of(5));
    report();
}
```

```text
average: 22.0
news:    5 (80 bytes)
deletes: 5
leaked:  0 allocation(s)
```

Same `continue`, same control flow, zero leaks, because leaving a scope by *any* exit runs the destructors of everything in it. The diff is telling: we didn't add cleanup code, we deleted it. The signature change from `Reading*` to `std::unique_ptr<Reading>` also upgraded the documentation: the old signature couldn't tell callers whether they were supposed to delete the result; the new one is unambiguous: you own this now.

Extensions worth trying: track peak outstanding bytes (a high-water mark updated in `new`); print the size of each allocation to spot allocation storms in a hot loop; wrap the counters in an RAII `MemCheck` object that reports the delta between its construction and destruction, so you can audit one scope at a time. That last trick is a homemade version of what ASan and Valgrind do industrially, and Chapter 29.3 builds on this exact hook to study *where* allocations land in memory and what that does to the cache.

## Common mistakes

1. **Mismatched `new`/`delete` forms.** `new T[]` must pair with `delete[]`, plain `new` with plain `delete`. Mixing them is undefined behavior; ASan calls it `alloc-dealloc-mismatch`. Fix: don't hand-roll arrays; use `std::vector` or your own RAII container.
2. **Writing a destructor and stopping there.** If a destructor frees a resource, the compiler-generated copy still just duplicates the pointer, and the two owners double-free it. Fix: rule of five. Define or `= delete` all five specials the moment you write any of them.
3. **Forgetting to null the source in a move.** A move constructor that steals `data_` but leaves `other.data_` set produces a double free when both destructors run. Fix: steal, then scrub; run the tests under ASan, which catches it instantly.
4. **Using a moved-from object as if nothing happened.** After `std::move(x)`, `x` is valid but unspecified. Reading from it isn't a crash, which makes it worse: it's a wrong-answer generator. Fix: treat `std::move` as the end of that variable's story; reassign it before any reuse.
5. **Holding references into a growing vector.** `push_back` can reallocate and turn every outstanding reference, pointer, and iterator into a dangling one. Fix: re-acquire references after mutation, use indexes, or `reserve()` capacity up front.
6. **`shared_ptr` everywhere.** Shared ownership as a default produces reference-count traffic, unclear lifetimes, and eventually a cycle that leaks. Fix: `unique_ptr` by default; `shared_ptr` only when ownership is actually shared; `weak_ptr` for back-edges.
7. **Returning a reference or pointer to a local.** The frame dies at the closing brace; the reference outlives it. Heed `-Wreturn-local-addr`; it's a bug report, not a suggestion. Fix: return by value and let moves and copy elision make it cheap.
8. **Calling `delete` on the same pointer from two owners "just to be safe."** Cleanup code duplicated across paths or objects is how double frees happen. Fix: exactly one owner per resource, expressed in the type (`unique_ptr` or a rule-of-five class), so "who deletes this" is never a judgment call.

## On the job / interview angle

- **"Implement a class that owns a resource"** is a C++ interview staple, and it is exactly the rule of five. Practice writing `DynArray` (or a `String` class, same shape) on a whiteboard until the five signatures come out without thinking. Interviewers watch for the details: `noexcept` on moves, nulling the source, self-assignment, copy-and-swap.
- **"What's the difference between `unique_ptr` and `shared_ptr`? When would you use `weak_ptr`?"** The expected answer covers ownership semantics and cost (unique is free, shared pays for an atomic control block), plus cycles for `weak_ptr`. Relating it to reference-counting GCs, as you now can, reads as depth.
- **"What does `std::move` actually do?"** is a favorite trap. The answer (nothing at runtime; it's a cast to rvalue reference that *permits* a move) separates people who've used the feature from people who understand it.
- On real teams, memory bugs are found with tooling, not staring. Fluency with AddressSanitizer (and Valgrind, and the leak counters you just built) is a practical, demonstrable skill; "I'd run it under ASan and read the free/alloc stacks" is the right first move in any use-after-free war story.
- Modern C++ codebases enforce most of this chapter in review: no owning raw pointers, rule of zero by default, `make_unique` over naked `new`. Knowing *why* each rule exists, not just the rule, is what distinguishes a senior review comment from a lint bot.

### Solutions

**1.**

```text
+a +b +c -c -b +d | -d -a
```

Construction order is source order: `a`, then the inner block's `b` and `c`. The inner block's closing brace destroys its locals in reverse order (`-c -b`); destructors always run opposite to constructors, because later objects may depend on earlier ones. Then `d` is built, `|` prints, and `main`'s brace destroys `d` then `a`, again newest-first.

**2.** Something else: undefined behavior from mismatched allocation and deallocation forms. `new[]` may store bookkeeping (like the element count, so destructors can run per element) that plain `delete` doesn't know to look for. ASan reports:

```text
ERROR: AddressSanitizer: alloc-dealloc-mismatch (operator new [] vs operator delete)
```

The modern fix is to not write either form: `std::vector<int>` (or `std::make_unique<int[]>(10)` when you truly want a bare array) makes the mismatch inexpressible.

**3.** The bug: `Name` owns a heap buffer and defines a destructor, but leaves copying to the compiler, whose memberwise copy duplicates the *pointer*. `a` and `b` share one buffer; at scope exit both destructors free it. ASan reports `attempting double-free` inside `Name::~Name()`. This violates the rule of three (rule of five, pre-move edition): destructor implies copy constructor and copy assignment. Two fixes:

   - Forbid copying, one line each: `Name(const Name&) = delete; Name& operator=(const Name&) = delete;` Misuse now fails at compile time.
   - Or make copying deep, as in `DynArray`'s copy constructor: allocate a fresh buffer and `strcpy` into it (plus a matching copy assignment).

   The third, best fix is the rule of zero: store `std::string data_;` and delete all the special members you wrote.

**4.**

```cpp
#include <chrono>
#include <iostream>

class ScopedTimer {
public:
    explicit ScopedTimer(const char* label)
        : label_(label), start_(std::chrono::steady_clock::now()) {}

    ~ScopedTimer() {
        auto end = std::chrono::steady_clock::now();
        auto us = std::chrono::duration_cast<std::chrono::microseconds>(
                      end - start_).count();
        std::cout << label_ << ": " << us << " us\n";
    }

    ScopedTimer(const ScopedTimer&) = delete;
    ScopedTimer& operator=(const ScopedTimer&) = delete;

private:
    const char* label_;
    std::chrono::steady_clock::time_point start_;
};

int main() {
    ScopedTimer whole("whole main");
    long sum = 0;
    {
        ScopedTimer loop("summing loop");
        for (int i = 0; i < 1000000; ++i) sum += i;
    }   // "summing loop: ... us" prints here
    std::cout << "sum = " << sum << "\n";
}       // "whole main: ... us" prints here -- destructors run inner-first
```

One run printed `summing loop: 2203 us`, then the sum, then `whole main: 2214 us`. The inner timer prints first: its scope closes first. Copying is deleted because two timers sharing one start time would double-report, the same reasoning as `File`.

**5.** `push_back(p)` would have to *copy* the `unique_ptr`, and its copy constructor is deleted: two `unique_ptr`s owning one int would double-delete it, so the type forbids it at compile time. The fix is an explicit transfer:

```cpp
#include <iostream>
#include <memory>
#include <vector>

int main() {
    std::vector<std::unique_ptr<int>> owners;

    auto p = std::make_unique<int>(1);
    // owners.push_back(p);            // won't compile: copy is deleted
    owners.push_back(std::move(p));    // fine: ownership transfers in

    owners.push_back(std::make_unique<int>(2));   // temporary moves in

    std::cout << "p is now " << (p ? "alive" : "null") << "\n";
    std::cout << "vector owns " << owners.size() << " ints\n";
}   // vector dies -> each unique_ptr dies -> each int is freed
```

```text
p is now null
vector owns 2 ints
```

After the move, `p` holds `nullptr`: for `unique_ptr` the moved-from state is specified to be empty. The vector is now the owner; when it dies, its elements' destructors free both ints.

**6.** Add to `DynArray`'s public section:

```cpp
void reserve(std::size_t new_cap) {
    if (new_cap <= capacity_)
        return;                       // never shrink, never invalidate early
    int* new_data = new int[new_cap];
    std::copy(data_, data_ + size_, new_data);
    delete[] data_;
    data_ = new_data;
    capacity_ = new_cap;
}
```

With `r.reserve(100)` before 100 `push_back`s, `grow()` never fires: one allocation instead of six rounds of allocate-copy-free. Never shrinking is the right contract because shrinking below `size_` would destroy live elements, and even shrinking spare capacity would reallocate and invalidate every outstanding pointer into the buffer, punishing a caller who asked for *more* room with dangling references. (`std::vector::reserve` makes the same promise, which is why `reserve` followed by `push_back`s is the standard defense against iterator invalidation.)

**7.**

```cpp
#include <iostream>
#include <map>
#include <memory>
#include <string>

struct Texture {
    std::string name;
    Texture(std::string n) : name(std::move(n)) {
        std::cout << "load " << name << "\n";
    }
    ~Texture() { std::cout << "unload " << name << "\n"; }
};

class TextureCache {
public:
    std::shared_ptr<Texture> get(const std::string& name) {
        auto& slot = cache_[name];
        if (auto alive = slot.lock())   // still loaded somewhere?
            return alive;               // hand out another owner
        auto fresh = std::make_shared<Texture>(name);
        slot = fresh;                   // cache observes, does NOT own
        return fresh;
    }
private:
    std::map<std::string, std::weak_ptr<Texture>> cache_;
};

int main() {
    TextureCache cache;
    {
        auto a = cache.get("wall");   // load wall
        auto b = cache.get("wall");   // cache hit: no second load
        std::cout << "owners: " << a.use_count() << "\n";   // 2
    }   // both owners die -> unload wall (cache didn't keep it alive)
    auto c = cache.get("wall");       // load wall (again, fresh)
    (void)c;
}
```

```text
load wall
owners: 2
unload wall
load wall
unload wall
```

If the cache held `shared_ptr`, every texture ever requested would stay loaded until the cache itself died, because the cache's own reference would pin the count above zero. With `weak_ptr` the users decide the lifetime and the cache merely remembers; `.lock()` is the safe "is it still alive?" check. This is the same pattern as Python's `weakref`-based caches from 5.1.

**8.**

```cpp
#include <iostream>
#include <vector>

struct Safe {
    Safe() {}
    Safe(const Safe&) { std::cout << "Safe copy\n"; }
    Safe(Safe&&) noexcept { std::cout << "Safe move\n"; }
};

struct Risky {
    Risky() {}
    Risky(const Risky&) { std::cout << "Risky copy\n"; }
    Risky(Risky&&) { std::cout << "Risky move\n"; }   // no noexcept!
};

int main() {
    std::vector<Safe> vs(3);
    std::cout << "-- growing vector<Safe> --\n";
    vs.push_back(Safe{});    // growth relocates the 3 old elements

    std::vector<Risky> vr(3);
    std::cout << "-- growing vector<Risky> --\n";
    vr.push_back(Risky{});
}
```

```text
-- growing vector<Safe> --
Safe move
Safe move
Safe move
Safe move
-- growing vector<Risky> --
Risky move
Risky copy
Risky copy
Risky copy
```

`Safe`: four moves, the temporary into the new buffer plus the three old elements relocated by move. `Risky`: the temporary still moves in (you passed an rvalue directly), but the three *relocations* are copies. The reasoning: during reallocation the vector promises that if anything throws, your data is untouched. If a throwing move died halfway through relocation, some elements would already be gutted and the promise broken. So the vector only moves during relocation when the move is declared `noexcept`, and copies otherwise. Forgetting `noexcept` on a move constructor silently turns your container growth back into deep copies, which is why `DynArray`'s moves carry it.

**9.** CPython backs its reference counting with a tracing cycle collector: periodically it walks container objects, finds groups that are reachable only from each other, and frees the whole group (Chapter 5.1). `shared_ptr` has counting but no tracer, so a cycle's counts simply never reach zero. C++ doesn't add a tracer because it would need what C++ deliberately lacks: a runtime that knows where every pointer lives so it can walk the object graph, plus pauses and per-object metadata, costs C++'s "you don't pay for what you don't use" charter refuses. Instead C++ asks the programmer to keep the *ownership* graph acyclic by design, demoting back-edges to `weak_ptr` (or non-owning raw pointers). The trade is explicit: Python spends runtime machinery to make cycles a non-issue; C++ spends a design rule to make them impossible.

## Teach it back

1. Explain the storage-unit analogy end to end: what are the key, the manager Python has, and the three key-handling failures? Which C++ tool retires each failure?
2. A Python friend asks why C++ people are obsessed with destructors. Using the `Noisy` output and the `with`-statement comparison, explain what deterministic destruction buys and why Python needed special syntax to approximate it.
3. State the rule of zero and the rule of five, and explain why writing a destructor obligates you to deal with the other four. Use the `Name` bug from the exercises as your cautionary tale.
4. Walk through what `std::string t = std::move(s)` does at the byte level, why it's cheap, what state `s` is left in, and how all of this differs from Python's `t = s`.
5. Draw the ownership diagram for the `shared_ptr` cycle, show why the counts never reach zero, and show how flipping one edge to `weak_ptr` fixes it. Connect it to why CPython needs a cycle collector on top of refcounting.
6. Your teammate's code returns `Widget*` from a factory function. Argue for changing the return type to `std::unique_ptr<Widget>`: what does the new signature communicate, and which entire bug classes does it delete?
