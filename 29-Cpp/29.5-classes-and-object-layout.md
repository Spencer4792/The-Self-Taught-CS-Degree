> _Goal: write real C++ classes and know, byte by byte, what they cost. You already speak object-oriented Python fluently from [4.1](../04-Programming-Mastery/04.1-python-deep-dive.md), and [29.1](29.1-cpp-for-python-programmers.md) got you compiling; this chapter translates your OOP instincts into a language where every member has a fixed offset decided at compile time. In [29.1](29.1-cpp-for-python-programmers.md) you worked with objects the standard library gave you: `std::string`, `std::vector`, `std::unordered_map`. This chapter is where you start making your own. The good news, again, is that you are not learning object-oriented programming from scratch. Classes, methods, constructors, inheritance, polymorphism: you know all of these from Python. What changes is the physics underneath. A Python object can grow new attributes at runtime because it is, at heart, a dictionary. A C++ object cannot, because it is, at heart, a fixed run of bytes whose floor plan was finalized before the program ever ran. Once you can see that floor plan, features that look like compiler folklore (padding, slicing, the vtable) become things you can predict and measure.

## Start here: the concierge desk and the shipping container

Think about what a Python attribute access actually does. When you write `valve.flow`, the interpreter walks to the object, asks its concierge desk "do you have anything filed under `flow`?", and the concierge checks the ledger: the instance `__dict__`, then the class, then the base classes, in order, at runtime, every single time. This is why Python objects are so flexible. You can hand the concierge a new item at any moment (`valve.extra = 1`), and the ledger just grows a line. It is also why every access has a price: even `self.x` inside a hot loop is a hash-table lookup, the fetch-decode-typecheck story from 29.1 all over again.

A C++ object is a shipping container packed to a printed **manifest**. The manifest is the class definition. When the compiler reads it, it decides, once and for all, that `name_` occupies bytes 0 through 31 and `flow_` occupies bytes 32 through 39, prints the manifest, and seals it. From then on, `valve.flow_` is not a question anyone asks at runtime. It compiles to "load 8 bytes from the container's address plus 32", a single machine instruction of the kind you met in [25.1](../25-Architecture/25.1-computer-architecture.md). Nothing can be added to the container later, because there is no empty slot and no clerk to record the addition. That freedom is gone; so is the price.

Keep both pictures in mind through this chapter:

- The **concierge desk**: lookup by name, at runtime, extensible, uniform. Everything is late-bound, so polymorphism is free (you pay for it on every call whether you use it or not).
- The **shipping container**: lookup by offset, at compile time, sealed, fast. Polymorphism is *not* free, and when you ask for it, C++ will charge you exactly one pointer per object and one indirect call per use. Seeing that charge on the receipt is the main event of this chapter.

## From struct to class

Here is a small Python class of the kind you have written a hundred times:

```python
class Valve:
    def __init__(self, name, flow):
        self.name = name
        self._flow = flow            # private by convention only

    def open_more(self, delta):
        self._flow += delta

    def flow(self):
        return self._flow

v = Valve("slurry-1", 2.5)
v.open_more(0.5)
print(f"{v.name} flows at {v.flow()} L/min")
v.extra = "surprise"                 # Python: add attributes any time
print(sorted(v.__dict__))            # the ledger, live at runtime
```

```text
slurry-1 flows at 3.0 L/min
['_flow', 'extra', 'name']
```

And its C++ twin:

```cpp
#include <iostream>
#include <string>

class Valve {
public:
    Valve(const std::string& name, double flow)
        : name_(name), flow_(flow) {}

    void open_more(double delta) {
        flow_ += delta;          // shorthand for this->flow_ += delta;
    }

    double flow() const { return flow_; }
    const std::string& name() const { return name_; }

private:
    std::string name_;
    double flow_;                // in liters per minute
};

int main() {
    Valve v{"slurry-1", 2.5};
    v.open_more(0.5);
    std::cout << v.name() << " flows at " << v.flow() << " L/min\n";
    // v.flow_ = 99.0;           // won't compile: 'flow_' is private
    // v.extra = 1;              // won't compile: no such member exists
    return 0;
}
```

```text
slurry-1 flows at 3 L/min
```

Walk through the differences, because each one is a manifest-versus-ledger difference:

- **Member variables are declared in the class body**, not created by assignment in `__init__`. The compiler needs the full list up front to print the manifest. That is also why `v.extra = 1` is a compile error rather than a feature: there is no slot for it.
- **`this` is Python's `self`, but implicit.** Inside a member function, writing `flow_` means `this->flow_`. `this` is a pointer to the object the method was called on, passed invisibly as a hidden first argument. Python makes the same argument visible and calls it `self`.
- **Access control is enforced, not suggested.** Python's `_flow` is a social convention; the interpreter will hand anyone the value. C++'s `private:` is checked by the compiler: code outside the class that touches `flow_` does not compile. Note what it is not: it is not security (the bytes are right there in memory), it is interface discipline, machine-checked.
- **`const` on a member function** (`double flow() const`) promises the method will not modify the object, extending the `const` story from 29.1 into classes. A `const Valve&` can only call `const` methods.
- **The trailing underscore** on `name_` and `flow_` is a common convention for private members, so they never collide with parameter names or accessor names. The book uses it from here on.

One vocabulary note that surprises people: in C++, `struct` and `class` are the *same feature*. The only difference is the default: members of a `struct` are `public` until you say otherwise, members of a `class` are `private`. Convention gives them different jobs. Use `struct` for open bags of data with no invariants to protect (like the layout specimens later in this chapter), and `class` when there is an interface guarding private state.

## Constructors: how objects are born

Python has one `__init__` per class, with default arguments covering the variations. C++ lets you overload constructors like any other function, and gives you specific machinery worth learning properly.

```cpp
#include <iostream>
#include <string>

class Recipe {
public:
    // parameterized constructor with a member-initializer list
    Recipe(std::string name, int steps)
        : name_(std::move(name)), steps_(steps) {
        std::cout << "built " << name_ << " with " << steps_ << " steps\n";
    }

    // delegating constructor: reuse the one above
    explicit Recipe(std::string name) : Recipe(std::move(name), 1) {}

    // default constructor
    Recipe() : Recipe("untitled", 0) {}

    int steps() const { return steps_; }

private:
    std::string name_;
    int steps_;
};

void run(const Recipe& r) {
    std::cout << "running a recipe with " << r.steps() << " steps\n";
}

int main() {
    Recipe a{"oxide-polish", 4};
    Recipe b{"touch-up"};      // delegates: steps = 1
    Recipe c;                  // default: "untitled", 0
    run(a);
    run(c);
    // run("copper-polish");   // won't compile: constructor is explicit
    run(Recipe{"copper-polish"});   // fine: the conversion is spelled out
    return 0;
}
```

```text
built oxide-polish with 4 steps
built touch-up with 1 steps
built untitled with 0 steps
running a recipe with 4 steps
running a recipe with 0 steps
built copper-polish with 1 steps
running a recipe with 1 steps
```

Three pieces of machinery to unpack.

**The member-initializer list.** The part after the colon, `: name_(std::move(name)), steps_(steps)`, is not a stylistic alternative to assigning inside the braces. By the time execution reaches the constructor's opening brace, every member has *already been constructed*. If you write this instead:

```text
Recipe(std::string name, int steps) {
    name_ = name;      // looks the same, isn't
    steps_ = steps;
}
```

then `name_` is first default-constructed as an empty string (work), and then assigned over (more work). Initialization-then-assignment instead of initialization. For an `int` nobody can measure the difference; for a string it is a wasted construction; for a member that is `const`, a reference, or a class without a default constructor, the assignment version does not compile at all. Habit to build now: constructors initialize in the list, and the body is for logic that needs the members to already exist.

**Delegating constructors.** `Recipe(std::string name) : Recipe(std::move(name), 1) {}` forwards to another constructor instead of duplicating its logic, the same instinct as Python's `def __init__(self, name, steps=1)` collapsing several signatures into one.

**`explicit`, and the trap it closes.** Without `explicit`, a one-argument constructor doubles as an *implicit conversion*. If the single-string constructor were not `explicit`, then `run("copper-polish")` would compile: the compiler would notice that `run` wants a `Recipe`, notice that a `Recipe` can be built from a string, and silently manufacture a temporary. That sounds convenient until it bites: a function expecting a `Recipe` accepts a stray string that was never meant to be one, and the bug hides behind a conversion you cannot see at the call site. The rule used across this book: mark single-argument constructors `explicit` unless the conversion is the point (as it is for, say, building a `std::string` from a literal).

## Destructors: `__del__` that actually runs

Python's `__del__` runs "whenever the garbage collector gets around to it, maybe." The C++ **destructor**, written `~ClassName()`, runs at a moment you can point to in the source code: when a local object's scope ends, in reverse order of construction.

```cpp
#include <iostream>

class Probe {
public:
    explicit Probe(const char* name) : name_(name) {
        std::cout << "  construct " << name_ << "\n";
    }
    ~Probe() {                       // the destructor: ~ClassName
        std::cout << "  destroy   " << name_ << "\n";
    }
private:
    const char* name_;
};

int main() {
    std::cout << "entering scope\n";
    {
        Probe a{"a"};
        Probe b{"b"};
        std::cout << "  ...work happens...\n";
    }                                 // b then a, reverse order, right here
    std::cout << "left scope\n";
    return 0;
}
```

```text
entering scope
  construct a
  construct b
  ...work happens...
  destroy   b
  destroy   a
left scope
```

That closing brace is a real event. You can set a breakpoint on it. This determinism is the foundation of RAII, which 29.1 previewed with self-closing files, and it is why C++ programmers care about destructors the way Python programmers care about `with` blocks. We will lean on destructors again in the virtual-dispatch section, because inheritance adds one important rule about them. Everything else about lifetime, copying an object that owns resources, moving one, the rule of five, `unique_ptr` and friends, is the business of [29.2](29.2-memory-and-object-lifetime.md); read that next after this chapter.

## The manifest: object layout and padding

Now let's read a manifest. You know from [29.3](29.3-allocators-arenas-cache.md) that every type has an **alignment**: an address boundary it must sit on, because that is how the memory system (25.1) likes its loads. On a typical 64-bit machine, `char` aligns to 1, `int` to 4, `double` and pointers to 8. Chapter 29.3 applied this at the allocator level, to whole blocks. Here the same rule applies *inside* an object, to each member, and the compiler enforces it by inserting invisible filler bytes called **padding**. In container terms: a crate that must sit on a pallet boundary gets foam stuffed in front of it, and the foam ships with the container whether you like it or not.

The rules the compiler follows are short enough to run by hand:

1. Members are placed in declaration order (more on why below).
2. Each member goes at the next offset that is a multiple of its alignment; the gap skipped over is padding.
3. The struct's own alignment is the largest alignment of any member.
4. The total size is rounded up to a multiple of the struct's alignment, so the elements of an array of these structs all stay aligned. That rounding is tail padding.

Let's predict, then verify. Take three members: a `char` tag (1 byte), a `double` value (8 bytes, align 8), an `int` count (4 bytes, align 4), declared in that order. Rule 2: `tag` at offset 0; `value` cannot start at 1, next multiple of 8 is 8, so bytes 1 through 7 are padding; `count` lands at 16. We are at 20 bytes; rule 4 rounds up to a multiple of 8: 24. Now sort the same members largest-alignment-first: `value` at 0, `count` at 8, `tag` at 12, running total 13, rounded up to 16. Same data, 24 versus 16 bytes, purely from declaration order. The program agrees, using **`offsetof`** (from `<cstddef>`) to print the manifest:

```cpp
#include <cstddef>
#include <cstdio>

struct Careless {           // members in "logical" order
    char tag;               // 1 byte
    double value;           // 8 bytes, must sit at a multiple of 8
    int count;              // 4 bytes, must sit at a multiple of 4
};

struct Packed {             // same members, sorted large-to-small
    double value;
    int count;
    char tag;
};

int main() {
    std::printf("Careless: sizeof=%zu alignof=%zu\n",
                sizeof(Careless), alignof(Careless));
    std::printf("  tag   at offset %zu\n", offsetof(Careless, tag));
    std::printf("  value at offset %zu\n", offsetof(Careless, value));
    std::printf("  count at offset %zu\n", offsetof(Careless, count));

    std::printf("Packed:   sizeof=%zu alignof=%zu\n",
                sizeof(Packed), alignof(Packed));
    std::printf("  value at offset %zu\n", offsetof(Packed, value));
    std::printf("  count at offset %zu\n", offsetof(Packed, count));
    std::printf("  tag   at offset %zu\n", offsetof(Packed, tag));
    return 0;
}
```

```text
Careless: sizeof=24 alignof=8
  tag   at offset 0
  value at offset 8
  count at offset 16
Packed:   sizeof=16 alignof=8
  value at offset 0
  count at offset 8
  tag   at offset 12
```

Byte-for-byte, the two containers look like this (`.` is padding):

```text
Careless (24 bytes):  [T]. . . . . . .[value  ][count ]. . . .
                       0               8        16      20
Packed   (16 bytes):  [value  ][count ][T]. . .
                       0        8       12
```

A third smaller: 33 percent of `Careless` is foam. Multiply by a `std::vector` holding ten million of them and the careless order costs 80 MB of RAM and, worse, a third of your cache-line budget from 29.3, since every 64-byte line you fetch is one-third filler.

**Why doesn't the compiler just reorder the members for you?** Because the language forbids it, and for load-bearing reasons. C++ guarantees that members (within the same access-control section) appear in memory in declaration order. C code, operating systems, network stacks, and device drivers all rely on structs as *layout specifications*: 29.4's hardware register maps and telemetry records only work because the source order is the byte order. Beyond the standard, there is the **ABI** (application binary interface): the platform-wide contract about layout and calling conventions that lets your program link against a library compiled last year. A compiler that reordered members would break every one of those contracts. So layout optimization stays a human job. Sorting members by alignment, largest first, is the standard move, and the mini-project below builds a tool that audits it.

**Packing pragmas.** Compilers offer `#pragma pack(1)` and friends to squeeze out all padding, and you will meet them in wire-format and file-format code. Know the cost before using one: the members become misaligned, so the CPU pays for split loads on every access, and on some embedded architectures a misaligned load is not slow but fatal, a hardware fault. The honest uses are at the edges of a program, serializing to a network or a file, not in the structs your hot loops chew on.

**The empty container still ships.** One more layout rule that looks odd until you see the reason:

```cpp
#include <cstdio>

struct Empty {};

struct Tag {};                    // another empty class
struct Wrapped { double x; Tag t; };   // empty member still costs a byte (plus padding)
struct Inherited : Tag { double x; };  // empty BASE can cost nothing

int main() {
    std::printf("sizeof(Empty)     = %zu\n", sizeof(Empty));
    Empty pair[2];
    std::printf("array of 2 Empty  = %zu bytes\n", sizeof(pair));
    std::printf("sizeof(Wrapped)   = %zu\n", sizeof(Wrapped));
    std::printf("sizeof(Inherited) = %zu\n", sizeof(Inherited));
    return 0;
}
```

```text
sizeof(Empty)     = 1
array of 2 Empty  = 2 bytes
sizeof(Wrapped)   = 16
sizeof(Inherited) = 8
```

An empty class has size 1, not 0, because every object must have a distinct address: in an array, element 0 and element 1 must not overlap, and `sizeof` of 0 would put them at the same byte. As a *member*, that phantom byte inflates `Wrapped` to 16 (1 byte of `Tag`, then 7 of padding before nothing). As a *base class*, the compiler is allowed to give it zero bytes, which is why `Inherited` is 8; this **empty base optimization** is why library code often inherits from empty helper classes (comparators, allocators) instead of storing them. C++20 added `[[no_unique_address]]` to get the same effect on members; this book targets C++17, so file that away as "the modern spelling."

## Inheritance without `virtual`

Python inheritance is ledger-chaining: the concierge checks the instance, then the class, then each base class. C++ inheritance, before any `virtual` keyword appears, is containment: a derived object *physically contains* a complete base object as its opening bytes, called the **base subobject**, with the derived members appended after it. We can verify that with offsets. (`offsetof` officially applies only to simple "standard-layout" types, and a class using inheritance the way we are about to is not one, so here we compute offsets directly: subtract the object's address from the member's address. Printing raw addresses would change run to run; differences are stable.)

```cpp
#include <cstdio>

struct Sensor {                  // the base: 12 bytes of payload
    int id;
    float reading;
    float limit;
};

struct LoggedSensor : Sensor {   // derived = base bytes, then new bytes
    long samples;
    float mean;
};

template <typename Obj, typename Member>
std::size_t offset_in(const Obj& o, const Member& m) {
    return reinterpret_cast<const char*>(&m) -
           reinterpret_cast<const char*>(&o);
}

int main() {
    LoggedSensor s{};
    std::printf("sizeof(Sensor)       = %zu\n", sizeof(Sensor));
    std::printf("sizeof(LoggedSensor) = %zu\n", sizeof(LoggedSensor));
    std::printf("id      at offset %zu\n", offset_in(s, s.id));
    std::printf("reading at offset %zu\n", offset_in(s, s.reading));
    std::printf("limit   at offset %zu\n", offset_in(s, s.limit));
    std::printf("samples at offset %zu\n", offset_in(s, s.samples));
    std::printf("mean    at offset %zu\n", offset_in(s, s.mean));

    Sensor* base_view = &s;      // a base pointer to a derived object
    std::printf("base subobject starts %td bytes into the object\n",
                reinterpret_cast<char*>(base_view) -
                reinterpret_cast<char*>(&s));
    return 0;
}
```

```text
sizeof(Sensor)       = 12
sizeof(LoggedSensor) = 32
id      at offset 0
reading at offset 4
limit   at offset 8
samples at offset 16
mean    at offset 24
base subobject starts 0 bytes into the object
```

Read the manifest: the first 12 bytes of a `LoggedSensor` *are* a `Sensor`, then 4 bytes of padding (the `long` needs an offset divisible by 8), then the derived members, then tail padding to 32. That containment is why a `Sensor*` can point at a `LoggedSensor` and everything just works: the pointer lands on a region that begins with a fully valid `Sensor`. No lookup, no runtime cleverness, just geometry. In the container picture, a derived container is a base container with an extension welded on the back; a crane certified for the base kind can grab the front of either.

When is plain, non-virtual inheritance the right tool? Less often than Python habits suggest. It buys you member reuse and the pointer-compatibility above, and it is fine for small closed designs (a `Sensor` family inside one file). But [27.1](../27-Software-Engineering/27.1-clean-code-and-design-patterns.md)'s guidance applies with extra force in C++: inheritance hard-wires an is-a claim into your types and, as we just measured, into your bytes. If a `LoggedSensor` merely *uses* a `Sensor`, make it a member (composition, has-a) and keep the coupling in one place you can change. The rest of this chapter is about the one job where inheritance is not just convenient but is the actual mechanism: runtime polymorphism.

## Virtual dispatch: the main event

Here is the problem polymorphism solves. You want one collection holding different kinds of things, and one loop that treats them uniformly:

```python
class Siren:
    def trigger(self): print("wail at 110 dB")

class QuietLog:
    def trigger(self): print("appended one line")

alarms = [Siren(), QuietLog(), Siren()]
for alarm in alarms:      # mixed types, one loop
    alarm.trigger()       # each does its own thing
```

```text
wail at 110 dB
appended one line
wail at 110 dB
```

Python gets this for free, and now you know exactly why: every call is a concierge lookup anyway, so `alarm.trigger()` naturally finds each object's own `trigger`. The concierge charges you on every call in the program to make this one loop effortless.

C++'s default is the opposite. A non-virtual call is resolved at compile time from the *static type*: if the compiler sees a `Alarm*`, it calls `Alarm::trigger`, end of discussion, even if the pointer actually aims at a derived object. To opt in to Python-style behavior you mark the function **`virtual`** in the base and **`override`** in the derived class:

```cpp
#include <iostream>
#include <memory>
#include <vector>

class Alarm {
public:
    virtual ~Alarm() = default;              // more on this shortly
    virtual void trigger() const {
        std::cout << "generic alarm\n";
    }
};

class Siren : public Alarm {
public:
    void trigger() const override {
        std::cout << "SIREN at 110 dB\n";
    }
};

class QuietLog : public Alarm {
public:
    void trigger() const override {
        std::cout << "appended one line to the log\n";
    }
};

int main() {
    std::vector<std::unique_ptr<Alarm>> alarms;
    alarms.push_back(std::make_unique<Siren>());
    alarms.push_back(std::make_unique<QuietLog>());
    alarms.push_back(std::make_unique<Alarm>());

    for (const auto& a : alarms) {
        a->trigger();          // one call site, three behaviors
    }
    return 0;
}
```

```text
SIREN at 110 dB
appended one line to the log
generic alarm
```

(`std::unique_ptr` is 29.2's pointer-that-cleans-up-after-itself; here it just means "a pointer we don't have to remember to `delete`." The vector stores pointers rather than `Alarm` values for a reason that gets its own section below.)

`override` deserves a word: it is not what makes dispatch happen (the base's `virtual` does that). It is a compile-time assertion that "this really overrides something." Misspell the name or botch the `const` and, without `override`, you silently create an unrelated function and the base version keeps getting called; with `override`, the compiler rejects the typo. Always write it. Its cousin **`final`** goes the other way: it forbids further overriding (or, on a class, further deriving), which documents intent and occasionally lets the compiler skip the dispatch machinery entirely.

### The hidden pointer, measured

How can one call site reach three functions? Something in the object itself must say what it is. The compiled code cannot ask a concierge; there isn't one. So the compiler smuggles the answer into the container: the moment a class has any virtual function, every object of that class carries one hidden pointer, conventionally called the **vptr**. Claiming that costs exactly one pointer is a measurable statement, so let's measure it:

```cpp
#include <cstdio>

struct Plain {
    double reading;
    void describe() const { std::printf("plain\n"); }
};

struct Poly {
    double reading;
    virtual void describe() const { std::printf("poly\n"); }
};

int main() {
    std::printf("sizeof(Plain) = %zu, alignof = %zu\n",
                sizeof(Plain), alignof(Plain));
    std::printf("sizeof(Poly)  = %zu, alignof = %zu\n",
                sizeof(Poly), alignof(Poly));
    std::printf("difference    = %zu bytes: one hidden pointer\n",
                sizeof(Poly) - sizeof(Plain));
    return 0;
}
```

```text
sizeof(Plain) = 8, alignof = 8
sizeof(Poly)  = 16, alignof = 8
difference    = 8 bytes: one hidden pointer
```

One keyword, eight bytes per object, forever. Note what stays cheap: the vptr does not point at a per-object copy of anything. It points at the **vtable** (virtual table), a small read-only array of function pointers that exists *once per class*, built at compile time and baked into the executable. Ten million `Siren` objects share one `Siren` vtable; each object pays only the 8-byte vptr. In the shipping picture: every container of a given type carries, in a fixed corner slot, a card naming that type's shared handling-instruction sheet. The sheets hang in the crane operator's office, one per container type, not one per container.

### One virtual call, step by step

```text
Siren object (16 bytes)              vtable for Siren
+--------------------+              (one per CLASS, read-only data)
|  vptr   o----------+------------> +--------------------------+
+--------------------+              | slot 0: &Siren::~Siren   |
|  decibels_ = 110.0 |              | slot 1: &Siren::trigger  |
+--------------------+              +--------------------------+

QuietLog object                      vtable for QuietLog
+--------------------+              +----------------------------+
|  vptr   o----------+------------> | slot 0: &QuietLog::~QuietLog |
+--------------------+              | slot 1: &QuietLog::trigger  |
+--------------------+              +----------------------------+
```

Every class in the hierarchy lays its vtable out with the same slot numbering, decided at compile time: destructor in slot 0, `trigger` in slot 1. That shared numbering is what makes the call compile to fixed offsets. When the compiler sees `a->trigger()` where `a` is an `Alarm*`, it emits three steps:

1. Load the vptr from the object (`a`'s first 8 bytes).
2. Load the function pointer from that vtable's `trigger` slot (vptr plus a constant slot offset).
3. Call through the pointer, passing `a` as `this`.

Two dependent memory loads and one **indirect call** (a call whose target sits in a register instead of being a constant in the instruction). Compare the concierge: Python hashes the string `"trigger"`, probes the instance dictionary, misses, probes the class dictionary, and finally calls, doing this from scratch every time. The vtable is what "compile the lookup" looks like: all the naming and searching happened when the manifest was printed, and what remains at runtime is pointer arithmetic. That is the whole mechanism. Everything else in this section is consequences.

### Virtual destructors, or: reading the delete instructions from the right sheet

Look back at `virtual ~Alarm() = default;` in the example. Destroying through a base pointer is a dispatch problem like any other: if the code holds an `Alarm*`, only the object itself knows whether a whole `Siren` needs tearing down. Make the destructor virtual and slot 0 solves it. Leave it non-virtual and `delete base_ptr` on a derived object is undefined behavior; in practice the derived part is simply never destroyed. Watch the correct version, using the `Noisy` tracer you will meet again in 29.2:

```cpp
#include <iostream>
#include <memory>

struct Noisy {
    Noisy() { std::cout << "  Noisy constructed\n"; }
    ~Noisy() { std::cout << "  Noisy destroyed\n"; }
};

class Base {
public:
    virtual ~Base() { std::cout << "~Base\n"; }
};

class Derived : public Base {
public:
    ~Derived() override { std::cout << "~Derived\n"; }
private:
    Noisy payload_;              // if ~Derived never runs, neither does this
};

int main() {
    std::cout << "with virtual destructor:\n";
    std::unique_ptr<Base> p = std::make_unique<Derived>();
    p.reset();                   // delete through the Base pointer
    std::cout << "done\n";
    return 0;
}
```

```text
with virtual destructor:
  Noisy constructed
~Derived
  Noisy destroyed
~Base
done
```

Full teardown, in order: derived destructor, then members, then base. Now delete the `virtual` and the output degrades to a lone `~Base`: no `~Derived`, no `Noisy destroyed`, and if `payload_` had owned memory or a file, it leaked. The compiler will warn you, which is one more reason `-Wall` is non-negotiable:

```text
warning: deleting object of polymorphic class type 'Base' which has
non-virtual destructor might cause undefined behavior
[-Wdelete-non-virtual-dtor]
```

The rule, worth memorizing verbatim because interviewers ask it verbatim: **if a class has any virtual function, give it a virtual destructor.** (Equivalently: if anyone might `delete` through a base pointer.)

### Pure virtual functions and abstract bases

Often the base class has no sensible default behavior: there is no such thing as a generic shape's area. Declaring a virtual function **pure**, with `= 0`, says "derived classes must provide this, and I provide nothing":

```text
class Shape {
public:
    virtual ~Shape() = default;
    virtual double area() const = 0;       // pure: no body required
};
```

A class with any pure virtual function is an **abstract base class**: you cannot create a plain `Shape`, only derived classes that fill every slot. This is C++'s version of the interface idea from 27.1, and mechanically it is exactly what it looks like: a vtable with holes that concrete classes must fill before objects can exist. Python's `abc` module with `@abstractmethod`, which you met in 4.1, is the concierge-world imitation of this feature.

### Object slicing: sawing the container in half

Now the payoff of the layout sections. You know two facts: a derived object is base bytes plus derived bytes, and a base-typed *value* has room for only the base bytes. Put them together and you can predict what happens when a derived object is passed by value as a base:

```cpp
#include <iostream>
#include <string>

class Alarm {
public:
    virtual ~Alarm() = default;
    virtual std::string sound() const { return "generic beep"; }
};

class Siren : public Alarm {
public:
    std::string sound() const override { return "110 dB wail"; }
private:
    double decibels_ = 110.0;    // the "derived half" of the object
};

void by_value(Alarm a)        { std::cout << "by value:     " << a.sound() << "\n"; }
void by_reference(const Alarm& a) { std::cout << "by reference: " << a.sound() << "\n"; }

int main() {
    Siren s;
    std::cout << "sizeof(Alarm) = " << sizeof(Alarm)
              << ", sizeof(Siren) = " << sizeof(Siren) << "\n";
    by_value(s);         // copies ONLY the Alarm part: sliced
    by_reference(s);     // refers to the whole Siren: dispatch works
    return 0;
}
```

```text
sizeof(Alarm) = 8, sizeof(Siren) = 16
by value:     generic beep
by reference: 110 dB wail
```

`by_value` receives an 8-byte `Alarm`. Initializing it from a 16-byte `Siren` copies the base subobject and discards the rest: `decibels_` is gone, and the new object is constructed *as an `Alarm`*, so its vptr points at the `Alarm` vtable. The wail is not suppressed; the part of the object that knew how to wail was never copied. This is **object slicing**, it compiles without a murmur, and it is why the practical rule exists: **polymorphism works through pointers and references, never through values.** A `std::vector<Alarm>` of "mixed" alarms is a vector of sliced stumps; a `std::vector<std::unique_ptr<Alarm>>` is the real thing, which is exactly why the first virtual example was written that way. Python cannot express this bug at all: every Python variable is already a reference, so the concierge desk never gets sawed off.

### What a virtual call costs, honestly

The three-step call sequence gives us the cost model. Relative to a direct call, a virtual call adds:

1. **Two dependent loads** (vptr, then slot). Usually cached, occasionally a cache miss each, and 29.3 taught you what a miss costs.
2. **An indirect branch.** The CPU's branch predictor (25.1) must guess the target before the loads finish. A stable target predicts perfectly; a call site that keeps switching between `Siren::trigger` and `QuietLog::trigger` in no pattern gets mispredicted, at roughly 15 to 20 cycles a time.
3. **A blocked inline.** The quiet, biggest one. The optimizer's favorite move is inlining a small function into its caller and then optimizing across the boundary; through a vtable it usually cannot prove the target, so a one-line `area()` stays a full call instead of dissolving into the loop.

Model in hand, we measure. Three ways to vary behavior per object: virtual dispatch, a plain tag-plus-branch, and `std::function` (a heavier type-erasing wrapper, Python-callable-shaped). Twenty million calls each over objects deliberately *shuffled* so the predictor cannot settle:

```cpp
#include <algorithm>
#include <chrono>
#include <cstdio>
#include <functional>
#include <memory>
#include <random>
#include <vector>

struct VBase {
    virtual ~VBase() = default;
    virtual double next(double x) const = 0;
};
struct VAdd : VBase { double next(double x) const override { return x + 1.25; } };
struct VMul : VBase { double next(double x) const override { return x * 1.0001; } };

struct Tagged {                  // no virtual: a tag and a branch
    int tag;                     // 0 = add, 1 = mul
    double next(double x) const { return tag == 0 ? x + 1.25 : x * 1.0001; }
};

template <typename F>
double time_ms(F&& f) {
    auto t0 = std::chrono::steady_clock::now();
    f();
    auto t1 = std::chrono::steady_clock::now();
    return std::chrono::duration<double, std::milli>(t1 - t0).count();
}

int main() {
    const int kObjects = 10000;
    const int kPasses = 2000;

    std::vector<int> kinds(kObjects);
    for (int i = 0; i < kObjects; ++i) kinds[i] = i % 2;
    std::mt19937 rng(42);
    std::shuffle(kinds.begin(), kinds.end(), rng);   // unpredictable order

    std::vector<std::unique_ptr<VBase>> vs;
    std::vector<Tagged> tags;
    std::vector<std::function<double(double)>> fns;
    for (int k : kinds) {
        if (k == 0) {
            vs.push_back(std::make_unique<VAdd>());
            tags.push_back({0});
            fns.push_back([](double x) { return x + 1.25; });
        } else {
            vs.push_back(std::make_unique<VMul>());
            tags.push_back({1});
            fns.push_back([](double x) { return x * 1.0001; });
        }
    }

    double acc1 = 0, acc2 = 0, acc3 = 0;
    double t_virtual = time_ms([&] {
        for (int p = 0; p < kPasses; ++p)
            for (const auto& v : vs) acc1 = v->next(acc1);
    });
    double t_switch = time_ms([&] {
        for (int p = 0; p < kPasses; ++p)
            for (const auto& t : tags) acc2 = t.next(acc2);
    });
    double t_function = time_ms([&] {
        for (int p = 0; p < kPasses; ++p)
            for (const auto& f : fns) acc3 = f(acc3);
    });

    std::printf("20 million calls each, shuffled order (times vary run to run):\n");
    std::printf("  virtual call:   %7.1f ms\n", t_virtual);
    std::printf("  tag + switch:   %7.1f ms\n", t_switch);
    std::printf("  std::function:  %7.1f ms\n", t_function);
    std::printf("checksums match: %d\n", acc1 == acc2 && acc2 == acc3);
    return 0;
}
```

Compiled with `g++ -std=c++17 -Wall -O2`, one run on the author's machine (absolute times vary; the ordering is the point):

```text
20 million calls each, shuffled order (times vary run to run):
  virtual call:     172.3 ms
  tag + switch:     104.3 ms
  std::function:    113.2 ms
checksums match: 1
```

Roughly 8 nanoseconds per virtual call here, versus 5 for the branch. Three honest caveats before you quote numbers like these:

- **The work is tiny on purpose.** These functions do one arithmetic operation, so dispatch overhead is a large *fraction*. Give each call a hundred microseconds of real work and the same absolute overhead rounds to zero. Virtual dispatch is a per-call toll; it matters when calls are many and small.
- **The optimizer fights back.** With a sorted (predictable) array instead of a shuffled one, the virtual and switch versions time nearly the same, because the indirect branch predicts perfectly. And when the compiler can *prove* the dynamic type (a `final` class, an object used in the same function that created it), it devirtualizes: the vtable is skipped and the call may inline after all. Microbenchmarks measure the worst case dressed as the typical case.
- **`std::function` costing about the same as virtual here is no accident**: internally it, too, makes an indirect call through stored pointers. Type erasure and vtables are the same trick in different clothes.

The takeaway is a cost model, not a ban: a virtual call is two loads and an indirect call, worst case a couple of cache misses plus a misprediction, and it blocks inlining. For a scene graph rendered 60 times a second, irrelevant. For the innermost loop of 29.4's millisecond control cycle, real money, which is exactly why that chapter's coding standards fence `virtual` out of the hot path.

## When not to use virtual: `std::variant` for closed sets

Virtual dispatch answers "callers must handle types *they cannot enumerate*": plugins, driver interfaces, anything where new derived classes appear after your code ships. That is the **open set** case. But a lot of real designs are **closed sets**: a message is a reading, a timeout, or a fault, and that list changes only when you edit the file.

For closed sets, C++17 offers a different deal, one you already know as 29.4's tagged state pattern grown up: `std::variant`, a type that holds exactly one of a fixed list of alternatives, plus `std::visit`, which branches to the right handler:

```cpp
#include <cstdio>
#include <variant>
#include <vector>

struct Reading  { double value; };
struct Timeout  { int after_ms; };
struct Fault    { int code; };

using Sample = std::variant<Reading, Timeout, Fault>;

struct Describe {
    void operator()(const Reading& r) const { std::printf("reading %.2f\n", r.value); }
    void operator()(const Timeout& t) const { std::printf("timeout after %d ms\n", t.after_ms); }
    void operator()(const Fault& f)   const { std::printf("fault code %d\n", f.code); }
};

int main() {
    std::vector<Sample> log = {Reading{3.14}, Timeout{250}, Fault{7}, Reading{2.71}};
    for (const auto& s : log) {
        std::visit(Describe{}, s);
    }
    std::printf("sizeof(Sample) = %zu (largest alternative + a tag, padded)\n",
                sizeof(Sample));
    return 0;
}
```

```text
reading 3.14
timeout after 250 ms
fault code 7
reading 2.71
sizeof(Sample) = 16 (largest alternative + a tag, padded)
```

Layout-wise a variant is the anti-vtable: one block of storage big enough for the largest alternative, plus a small tag saying which one is live. No hidden pointer, no per-class table, and, decisive for performance work: variants are *values*. A `std::vector<Sample>` is one contiguous slab, the cache-friendly layout 29.3 spent a chapter teaching you to want, while a `std::vector<std::unique_ptr<Base>>` scatters objects across the heap. The trade is symmetrical and worth writing on the wall:

- **Virtual**: adding a new *type* is easy (new derived class, no old code touched); adding a new *operation* is invasive (a new virtual function in the base, every class edited).
- **Variant**: adding a new *operation* is easy (new visitor, no type touched); adding a new *type* is invasive (edit the variant, and every visitor, though helpfully the compiler then errors on every visitor you forgot).

If you want the dispatch decided even earlier than a tag check, at compile time itself, that exists too: it is called CRTP, a template trick where the base class is parameterized on its own derived type, and it eliminates the indirect call entirely for code that never needed runtime mixing. It belongs to the templates chapter, [29.6](29.6-templates-and-compile-time-cpp.md), so park the acronym until then.

## Operator overloading essentials

Python taught you that `a == b` is `a.__eq__(b)` and `len` and friends are protocols (4.1). C++ has the same idea with different spelling: operators are functions named `operator==`, `operator<`, and so on, and you may define them for your own types. The workhorse set:

```cpp
#include <iostream>

struct Vec2 {
    double x, y;

    Vec2 operator+(const Vec2& o) const { return {x + o.x, y + o.y}; }
    bool operator==(const Vec2& o) const { return x == o.x && y == o.y; }
    bool operator!=(const Vec2& o) const { return !(*this == o); }
    bool operator<(const Vec2& o) const {          // lexicographic, like a tuple
        if (x != o.x) return x < o.x;
        return y < o.y;
    }
};

// operator<< is a free function: the left operand is the stream, not a Vec2
std::ostream& operator<<(std::ostream& os, const Vec2& v) {
    return os << "(" << v.x << ", " << v.y << ")";
}

struct ScaleBy {                    // a functor: an object you can call
    double factor;
    Vec2 operator()(const Vec2& v) const { return {v.x * factor, v.y * factor}; }
};

int main() {
    Vec2 a{1.0, 2.0}, b{3.0, -1.0};
    std::cout << "a + b = " << a + b << "\n";
    std::cout << "a == a: " << (a == a) << ",  a < b: " << (a < b) << "\n";
    ScaleBy doubler{2.0};
    std::cout << "doubler(a) = " << doubler(a) << "\n";
    return 0;
}
```

```text
a + b = (4, 1)
a == a: 1,  a < b: 1
doubler(a) = (2, 4)
```

Notes worth keeping:

- **`operator==` and `operator<` unlock the standard library.** `std::sort` and `std::map` use `<`; `std::find` uses `==`. Defining `<` as "compare fields in order, like a tuple" is the convention Python's `sorted` trained into you already.
- **`operator<<` must be a free function** because its left operand is the stream. Returning the stream reference is what lets `<<` chain.
- **`operator()`**, the call operator, makes a **functor**: an object callable like a function, C++'s `__call__`. The `Describe` visitor above was one, lambdas compile into them, and 29.6 will show why the standard library is built around them (they inline where function pointers cannot).
- C++20 adds `operator<=>`, the "spaceship," which generates all six comparisons from one definition; under C++17 we write `==` and `<` by hand and derive the rest as shown.
- The taste rule, same as Python's: **overload only when the meaning is obvious from math or long convention.** `vecA + vecB` explains itself; `configA + configB` is a riddle. If you have to document what the operator means, it wanted to be a named function.

## Build it: one scene, two dispatch designs

Time to use everything at once. We will build a `Shape` hierarchy twice: once as an open-set design with an abstract base and virtual dispatch, once as a closed-set design with `std::variant`. Both compute the same scene, and the totals must agree to the last digit, because a dispatch mechanism is plumbing and plumbing must not change the answer. Then we time them against each other.

```cpp
#include <chrono>
#include <cmath>
#include <cstdio>
#include <memory>
#include <random>
#include <variant>
#include <vector>

constexpr double kPi = 3.141592653589793;

// ---------- version A: open set, virtual dispatch ---------------------
class Shape {
public:
    virtual ~Shape() = default;
    virtual double area() const = 0;
    virtual double perimeter() const = 0;
};

class Circle : public Shape {
public:
    explicit Circle(double r) : r_(r) {}
    double area() const override { return kPi * r_ * r_; }
    double perimeter() const override { return 2.0 * kPi * r_; }
private:
    double r_;
};

class Rect : public Shape {
public:
    Rect(double w, double h) : w_(w), h_(h) {}
    double area() const override { return w_ * h_; }
    double perimeter() const override { return 2.0 * (w_ + h_); }
private:
    double w_, h_;
};

class Triangle : public Shape {
public:
    Triangle(double a, double b, double c) : a_(a), b_(b), c_(c) {}
    double area() const override {                 // Heron's formula
        double s = 0.5 * (a_ + b_ + c_);
        return std::sqrt(s * (s - a_) * (s - b_) * (s - c_));
    }
    double perimeter() const override { return a_ + b_ + c_; }
private:
    double a_, b_, c_;
};

// ---------- version B: closed set, std::variant ------------------------
struct VCircle   { double r; };
struct VRect     { double w, h; };
struct VTriangle { double a, b, c; };
using VShape = std::variant<VCircle, VRect, VTriangle>;

double area_of(const VShape& s) {
    return std::visit([](const auto& v) -> double {
        using T = std::decay_t<decltype(v)>;
        if constexpr (std::is_same_v<T, VCircle>) {
            return kPi * v.r * v.r;
        } else if constexpr (std::is_same_v<T, VRect>) {
            return v.w * v.h;
        } else {
            double s2 = 0.5 * (v.a + v.b + v.c);
            return std::sqrt(s2 * (s2 - v.a) * (s2 - v.b) * (s2 - v.c));
        }
    }, s);
}

double perimeter_of(const VShape& s) {
    return std::visit([](const auto& v) -> double {
        using T = std::decay_t<decltype(v)>;
        if constexpr (std::is_same_v<T, VCircle>)   return 2.0 * kPi * v.r;
        else if constexpr (std::is_same_v<T, VRect>) return 2.0 * (v.w + v.h);
        else                                         return v.a + v.b + v.c;
    }, s);
}

template <typename F>
double time_ms(F&& f) {
    auto t0 = std::chrono::steady_clock::now();
    f();
    auto t1 = std::chrono::steady_clock::now();
    return std::chrono::duration<double, std::milli>(t1 - t0).count();
}

int main() {
    // build the same random scene both ways
    std::mt19937 rng(7);
    std::uniform_real_distribution<double> dim(1.0, 10.0);
    std::uniform_int_distribution<int> kind(0, 2);

    const int kShapes = 10000;
    std::vector<std::unique_ptr<Shape>> scene_a;
    std::vector<VShape> scene_b;
    for (int i = 0; i < kShapes; ++i) {
        int k = kind(rng);
        if (k == 0) {
            double r = dim(rng);
            scene_a.push_back(std::make_unique<Circle>(r));
            scene_b.push_back(VCircle{r});
        } else if (k == 1) {
            double w = dim(rng), h = dim(rng);
            scene_a.push_back(std::make_unique<Rect>(w, h));
            scene_b.push_back(VRect{w, h});
        } else {
            double a = dim(rng), b = dim(rng);
            double c = std::abs(a - b) + 0.5 * std::min(a, b);  // valid triangle
            scene_a.push_back(std::make_unique<Triangle>(a, b, c));
            scene_b.push_back(VTriangle{a, b, c});
        }
    }

    // totals must agree
    double area_a = 0, perim_a = 0, area_b = 0, perim_b = 0;
    for (const auto& s : scene_a) { area_a += s->area(); perim_a += s->perimeter(); }
    for (const auto& s : scene_b) { area_b += area_of(s); perim_b += perimeter_of(s); }
    std::printf("virtual:  total area %.3f, total perimeter %.3f\n", area_a, perim_a);
    std::printf("variant:  total area %.3f, total perimeter %.3f\n", area_b, perim_b);

    // timing: 500 passes over the scene = 5 million area calls each
    const int kPasses = 500;
    double acc_a = 0, acc_b = 0;
    double t_a = time_ms([&] {
        for (int p = 0; p < kPasses; ++p)
            for (const auto& s : scene_a) acc_a += s->area();
    });
    double t_b = time_ms([&] {
        for (int p = 0; p < kPasses; ++p)
            for (const auto& s : scene_b) acc_b += area_of(s);
    });
    std::printf("5 million area calls (times vary run to run):\n");
    std::printf("  virtual pointers: %7.1f ms\n", t_a);
    std::printf("  variant values:   %7.1f ms\n", t_b);
    std::printf("accumulators agree: %d\n", std::abs(acc_a - acc_b) < 1e-6);
    return 0;
}
```

One `-O2` run (your times will differ; the agreement lines will not):

```text
virtual:  total area 529168.141, total perimeter 243519.834
variant:  total area 529168.141, total perimeter 243519.834
5 million area calls (times vary run to run):
  virtual pointers:    44.4 ms
  variant values:      26.9 ms
accumulators agree: 1
```

(The `if constexpr` / `decay_t` incantation inside the visitors is a compile-time type switch; 29.6 explains the machinery, here it just reads as "if this alternative is a circle...".)

The variant version wins here for two now-familiar reasons: its tag check predicts and inlines better than an indirect call, and, at least as important, `scene_b` is a contiguous vector of 32-byte values while `scene_a` chases a pointer to a separate heap allocation per shape, paying 29.3's locality tax on every element. So which design do you reach for?

- **Reach for virtual** when the set of types is open (users or other teams add shapes you will never see), when objects are large or expensive to copy, or when the hierarchy is the public seam of a library.
- **Reach for variant** when the set is closed and you control it, when objects are small values, and when the collection sits anywhere near a hot loop. Compiler-enforced exhaustiveness on visitors is a bonus correctness tool: add `VHexagon` and every forgotten visitor becomes a compile error, not a runtime surprise.

## Mini-project: an object X-ray machine

Two small tools you can put in a repo and keep reusing. The first X-rays layout: given a struct and its members, it prints the manifest as a table plus a byte map with the padding holes made visible, using nothing but `sizeof`, `alignof`, and `offsetof`.

```cpp
#include <cstddef>
#include <cstdio>
#include <cstdint>
#include <vector>

// ---- the reporting machinery -----------------------------------------
struct Field {
    const char* name;
    std::size_t offset;
    std::size_t size;
};

#define FIELD(S, m) Field{#m, offsetof(S, m), sizeof(S::m)}

void xray(const char* struct_name, std::size_t total, std::size_t align,
          std::vector<Field> fields) {
    std::printf("%s: sizeof = %zu, alignof = %zu\n", struct_name, total, align);
    std::printf("  %-12s %6s %5s\n", "member", "offset", "size");

    std::size_t cursor = 0;
    std::size_t wasted = 0;
    std::vector<char> map(total, '.');
    char letter = 'A';
    for (const Field& f : fields) {
        if (f.offset > cursor) {
            std::printf("  %-12s %6zu %5zu   <-- hole\n",
                        "(padding)", cursor, f.offset - cursor);
            wasted += f.offset - cursor;
        }
        std::printf("  %-12s %6zu %5zu\n", f.name, f.offset, f.size);
        for (std::size_t b = f.offset; b < f.offset + f.size; ++b) map[b] = letter;
        cursor = f.offset + f.size;
        ++letter;
    }
    if (cursor < total) {
        std::printf("  %-12s %6zu %5zu   <-- tail pad\n",
                    "(padding)", cursor, total - cursor);
        wasted += total - cursor;
    }
    std::printf("  bytes [");
    for (char c : map) std::putchar(c);
    std::printf("]  (%zu of %zu bytes are padding)\n\n", wasted, total);
}

#define XRAY(S, ...) xray(#S, sizeof(S), alignof(S), {__VA_ARGS__})

// ---- the specimens ----------------------------------------------------
struct Careless {
    char tag;
    double value;
    int count;
};

struct Packed {
    double value;
    int count;
    char tag;
};

struct Message {                 // a realistic protocol header, badly ordered
    std::uint8_t  version;
    std::uint64_t timestamp_ns;
    std::uint16_t length;
    std::uint32_t crc;
    std::uint8_t  flags;
};

int main() {
    XRAY(Careless, FIELD(Careless, tag), FIELD(Careless, value),
                   FIELD(Careless, count));
    XRAY(Packed,   FIELD(Packed, value), FIELD(Packed, count),
                   FIELD(Packed, tag));
    XRAY(Message,  FIELD(Message, version), FIELD(Message, timestamp_ns),
                   FIELD(Message, length),  FIELD(Message, crc),
                   FIELD(Message, flags));
    return 0;
}
```

```text
Careless: sizeof = 24, alignof = 8
  member       offset  size
  tag               0     1
  (padding)         1     7   <-- hole
  value             8     8
  count            16     4
  (padding)        20     4   <-- tail pad
  bytes [A.......BBBBBBBBCCCC....]  (11 of 24 bytes are padding)

Packed: sizeof = 16, alignof = 8
  member       offset  size
  value             0     8
  count             8     4
  tag              12     1
  (padding)        13     3   <-- tail pad
  bytes [AAAAAAAABBBBC...]  (3 of 16 bytes are padding)

Message: sizeof = 32, alignof = 8
  member       offset  size
  version           0     1
  (padding)         1     7   <-- hole
  timestamp_ns      8     8
  length           16     2
  (padding)        18     2   <-- hole
  crc              20     4
  flags            24     1
  (padding)        25     7   <-- tail pad
  bytes [A.......BBBBBBBBCC..DDDDE.......]  (16 of 32 bytes are padding)
```

The `#m` in the `FIELD` macro is the preprocessor's stringize operator (29.1's stage 1 doing something useful): it turns the member name into the string for the report. `Message` is the instructive specimen: a plausible telemetry header of the kind 29.4 ships through ring buffers, and *half* of it is padding. Exercise 2 has you fix it.

The second tool is a vtable explorer: a matched pair of classes one `virtual` apart, plus live demonstrations of slicing and destructor dispatch, with a `Noisy` member as the witness that teardown really happened.

```cpp
#include <cstdio>
#include <memory>

struct Noisy {
    const char* tag;
    explicit Noisy(const char* t) : tag(t) { std::printf("    + Noisy(%s)\n", tag); }
    ~Noisy() { std::printf("    - Noisy(%s)\n", tag); }
};

// a matched pair: identical members, one virtual keyword apart
struct MotorPlain {
    double rpm;
    double limit;
    void report() const { std::printf("plain motor at %.0f rpm\n", rpm); }
};

struct MotorPoly {
    double rpm;
    double limit;
    virtual ~MotorPoly() = default;
    virtual void report() const { std::printf("poly motor at %.0f rpm\n", rpm); }
};

struct ServoPoly : MotorPoly {
    Noisy diagnostics{"servo diagnostics buffer"};
    void report() const override { std::printf("servo at %.0f rpm\n", rpm); }
};

void report_by_value(MotorPoly m) { m.report(); }   // slicing on purpose

int main() {
    std::printf("== part 1: the hidden pointer ==\n");
    std::printf("sizeof(MotorPlain) = %zu\n", sizeof(MotorPlain));
    std::printf("sizeof(MotorPoly)  = %zu  (+%zu for the vtable pointer)\n",
                sizeof(MotorPoly), sizeof(MotorPoly) - sizeof(MotorPlain));

    std::printf("\n== part 2: slicing ==\n");
    ServoPoly s;
    s.rpm = 3000;
    report_by_value(s);          // copies only the MotorPoly bytes
    MotorPoly& ref = s;
    ref.report();                // full object, virtual dispatch works

    std::printf("\n== part 3: why destructors must be virtual ==\n");
    std::printf("deleting a ServoPoly through a MotorPoly*:\n");
    {
        std::unique_ptr<MotorPoly> p = std::make_unique<ServoPoly>();
        p->rpm = 1500;
    }   // ~MotorPoly is virtual, so ~ServoPoly runs and Noisy is freed
    std::printf("scope closed cleanly\n");
    return 0;
}
```

```text
== part 1: the hidden pointer ==
sizeof(MotorPlain) = 16
sizeof(MotorPoly)  = 24  (+8 for the vtable pointer)

== part 2: slicing ==
    + Noisy(servo diagnostics buffer)
poly motor at 3000 rpm
servo at 3000 rpm

== part 3: why destructors must be virtual ==
deleting a ServoPoly through a MotorPoly*:
    + Noisy(servo diagnostics buffer)
    - Noisy(servo diagnostics buffer)
scope closed cleanly
    - Noisy(servo diagnostics buffer)
```

(The last `- Noisy` line is the stack-allocated `s` from part 2 being destroyed at the end of `main`, after the "scope closed" message: reverse order of construction, exactly as the destructor section promised.) Extensions if you want to push either tool further: teach the X-ray to suggest an optimal member order automatically (sort by alignment and recompute), or make it emit a warning when padding exceeds a threshold and run it over structs in your own projects.

## Common mistakes

1. **Polymorphic base without a virtual destructor.** Any class with a virtual function gets `virtual ~Base() = default;`, or derived destructors silently never run when deleted through the base. `-Wall` warns (`-Wdelete-non-virtual-dtor`); fix the class, not the warning.
2. **Slicing by container or by parameter.** `std::vector<Base>` and `void f(Base b)` both quietly amputate derived objects. Polymorphic code takes `Base&`, `const Base&`, or a smart pointer, and stores pointers, never base-typed values.
3. **Calling virtual functions in constructors and expecting derived behavior.** During `Base`'s constructor, the object *is* a `Base`: the vptr is set in stages, base first, and rewritten as each level of the hierarchy finishes constructing. So a virtual call from a constructor dispatches to the current level, not the eventual derived override. Watch:

   ```cpp
   #include <iostream>

   class Base {
   public:
       Base() {
           std::cout << "Base constructor calls describe(): ";
           describe();              // which version runs?
       }
       virtual ~Base() = default;
       virtual void describe() const { std::cout << "I am a Base\n"; }
   };

   class Derived : public Base {
   public:
       void describe() const override { std::cout << "I am a Derived\n"; }
   };

   int main() {
       Derived d;
       std::cout << "after construction:          ";
       d.describe();
       return 0;
   }
   ```

   ```text
   Base constructor calls describe(): I am a Base
   after construction:          I am a Derived
   ```

   This is not a compiler quirk; it is safety. `Derived::describe` might touch `Derived` members that do not exist yet. Destructors unwind the same staging in reverse.
4. **Believing the initializer list's order.** Members initialize in *declaration* order, not the order you wrote in the list. This class compiles and computes garbage, because `cells_` (declared first) initializes first, reading `rows_` before it exists:

   ```text
   class Grid {
   public:
       Grid(int n) : rows_(n), cells_(rows_ * rows_) {}   // looks fine
   private:
       int cells_;      // declared first, so initialized first
       int rows_;
   };
   ```

   `-Wall` catches it:

   ```text
   warning: 'Grid::rows_' will be initialized after [-Wreorder]
   warning:   'int Grid::cells_' [-Wreorder]
   warning:   when initialized here
   warning: member 'Grid::rows_' is used uninitialized [-Wuninitialized]
   ```

   Fix: keep the list in declaration order (then dependencies are visible), and never initialize one member from another unless the depended-on member is declared earlier.
5. **Forgetting `explicit`** on single-argument constructors, leaving implicit-conversion trapdoors where a stray `int` or string silently becomes your class. Default to `explicit`; remove it only when conversion is the design.
6. **Forgetting `override`.** Without it, a typo in the name or signature creates a new unrelated function and the base version keeps running, with no diagnostic. `override` turns that silence into a compile error for free.
7. **Reaching for inheritance when composition answers.** If the honest sentence is "a `LoggedSensor` *has* a log," a member does the job with less coupling and no layout entanglement; revisit 27.1's guidance. Inheritance is for substitutability through a base interface, not for code reuse.
8. **Ignoring padding in hot or high-volume structs.** An extra 8 wasted bytes per element is invisible at 10 objects and a cache catastrophe at 10 million. Run the X-ray on anything you store in bulk, and sort members largest-alignment-first.

## On the job / interview angle

Vtable questions are C++ interview staples, asked less to test trivia than to check whether you have a mechanical model. Be ready to answer, at a whiteboard, with diagrams: *How does a virtual call work?* (vptr load, slot load, indirect call; one table per class, one pointer per object.) *What does `virtual` cost?* (8 bytes per object, two dependent loads and an indirect branch per call, blocked inlining; and know when that matters and when it rounds to zero.) *Why virtual destructors?* (Deleting through a base pointer must dispatch, or the derived half leaks; UB by the standard.) *What is slicing?* (Base-typed value copies only the base subobject; polymorphism needs pointers or references.) *Why did `sizeof` change when I added a virtual function?* If you can also sketch `Careless` versus `Packed` and explain why the compiler cannot reorder members, you are answering above the bar.

On the industrial side, the pattern from [29.4](29.4-industrial-embedded-cpp.md) is worth internalizing: real-time and embedded shops do not ban classes, they fence *dispatch* by context. Virtual interfaces are welcome at configuration time and in cold paths (a driver interface chosen once at startup); inside the millisecond loop, teams prefer tags, switches, variants, or templates, because an indirect call with a possible cache miss is jitter, and 29.4 taught you that jitter, not average speed, is the enemy. Layout literacy is daily bread in that world too: telemetry records, protocol frames, and register maps are all structs whose padding you must control, and a tool like this chapter's X-ray is the kind of thing engineers actually keep in their dotfiles.

## Exercises

1. **Manifest by hand.** Without compiling, predict `sizeof` and every member offset for `struct S { int a; char b; double c; short d; };` on a typical 64-bit machine. Then verify with an `offsetof` program. How many padding bytes are there, and where?
2. **Fix the Message.** Reorder the mini-project's `Message` struct to minimize its size without dropping any field. Predict the new `sizeof` first, then verify with `offsetof`. How much did you save per message, and per million messages?
3. **Does the vtable grow the object?** A colleague claims each additional virtual function adds another pointer to every object. Design an experiment with `sizeof` that settles it, run it, and explain the result using the one-table-per-class model.
4. **Slice hunt.** The following sketch is buggy: `std::vector<Alarm> alarms; alarms.push_back(Siren{}); alarms.front().trigger();`. Predict its output, explain the mechanism in terms of bytes copied and the vptr, and fix it so the siren wails.
5. **Sortable wafers.** Define `struct Wafer { std::string lot; int slot; };` with `operator==`, `operator<` (by lot, then slot), and `operator<<`. Use them to sort a batch with `std::sort` and print it.
6. **Constructor forensics.** Explain why `Grid` in Common mistakes computes garbage even though the initializer list "clearly" sets `rows_` first, and give two distinct fixes.
7. **Open or closed?** For each system, choose virtual or variant dispatch and justify in a sentence using this chapter's criteria: (a) a compiler's AST nodes, fixed by the language grammar; (b) an audio plugin host loading third-party effects; (c) the message types on 29.4's telemetry ring buffer; (d) a GUI toolkit's widget tree that applications extend.

### Solutions

**1.** Walk the rules: `a` (align 4) at 0..3; `b` (align 1) at 4; `c` (align 8) cannot start at 5, so bytes 5..7 pad and `c` sits at 8..15; `d` (align 2) at 16..17; struct alignment is 8 (from the `double`), so total rounds from 18 up to 24. Padding: 3 bytes internal (5..7) plus 6 tail bytes (18..23), 9 of 24. Verification prints `a=0 b=4 c=8 d=16 sizeof=24`.

**2.** Sort by alignment, largest first:

```cpp
#include <cstddef>
#include <cstdint>
#include <cstdio>

struct MessageTight {
    std::uint64_t timestamp_ns;   // 8, alignment 8: put it first
    std::uint32_t crc;            // 4
    std::uint16_t length;         // 2
    std::uint8_t  version;        // 1
    std::uint8_t  flags;          // 1
};

int main() {
    std::printf("sizeof(MessageTight) = %zu\n", sizeof(MessageTight));
    std::printf("timestamp_ns at %zu, crc at %zu, length at %zu, "
                "version at %zu, flags at %zu\n",
                offsetof(MessageTight, timestamp_ns),
                offsetof(MessageTight, crc),
                offsetof(MessageTight, length),
                offsetof(MessageTight, version),
                offsetof(MessageTight, flags));
    return 0;
}
```

```text
sizeof(MessageTight) = 16
timestamp_ns at 0, crc at 8, length at 12, version at 14, flags at 15
```

The payload is 8+4+2+1+1 = 16 bytes, so this order has *zero* padding, down from 32 bytes: 16 saved per message, about 15 MB per million messages, and every 64-byte cache line now carries 4 messages instead of 2.

**3.** Compare a class with one virtual function against one with five:

```cpp
#include <cstdio>

struct OneVirtual {
    double x;
    virtual ~OneVirtual() = default;
};

struct FiveVirtuals {
    double x;
    virtual ~FiveVirtuals() = default;
    virtual void a() {}
    virtual void b() {}
    virtual void c() {}
    virtual void d() {}
};

int main() {
    std::printf("sizeof(OneVirtual)   = %zu\n", sizeof(OneVirtual));
    std::printf("sizeof(FiveVirtuals) = %zu\n", sizeof(FiveVirtuals));
    return 0;
}
```

```text
sizeof(OneVirtual)   = 16
sizeof(FiveVirtuals) = 16
```

The colleague is wrong. The object carries exactly one vptr regardless of how many virtual functions exist; extra virtuals add *slots to the class's single shared vtable*, which lives once in the executable's read-only data, not in objects.

**4.** `push_back(Siren{})` constructs a vector element of type `Alarm` from a `Siren`: only the `Alarm` subobject's bytes are copied, and the new element's vptr is set to the `Alarm` vtable (it was constructed *as* an `Alarm`). The call prints the base behavior. Fix by storing pointers:

```cpp
#include <iostream>
#include <memory>
#include <vector>

class Alarm {
public:
    virtual ~Alarm() = default;
    virtual void trigger() const { std::cout << "beep\n"; }
};
class Siren : public Alarm {
public:
    void trigger() const override { std::cout << "WAIL\n"; }
};

int main() {
    // buggy version: std::vector<Alarm> slices every Siren pushed into it
    std::vector<Alarm> sliced;
    sliced.push_back(Siren{});          // compiles, silently copies base part
    sliced.front().trigger();           // prints "beep": the Siren is gone

    // fixed version: store pointers, dispatch survives
    std::vector<std::unique_ptr<Alarm>> ok;
    ok.push_back(std::make_unique<Siren>());
    ok.front()->trigger();              // prints "WAIL"
    return 0;
}
```

```text
beep
WAIL
```

**5.**

```cpp
#include <algorithm>
#include <iostream>
#include <string>
#include <vector>

struct Wafer {
    std::string lot;
    int slot;

    bool operator==(const Wafer& o) const {
        return lot == o.lot && slot == o.slot;
    }
    bool operator<(const Wafer& o) const {   // sort by lot, then slot
        if (lot != o.lot) return lot < o.lot;
        return slot < o.slot;
    }
};

std::ostream& operator<<(std::ostream& os, const Wafer& w) {
    return os << w.lot << "#" << w.slot;
}

int main() {
    std::vector<Wafer> batch = {{"L7", 3}, {"L2", 25}, {"L7", 1}, {"L2", 4}};
    std::sort(batch.begin(), batch.end());   // uses our operator<
    for (const auto& w : batch) std::cout << w << " ";
    std::cout << "\n";
    std::cout << "duplicate check: " << (batch[0] == batch[1]) << "\n";
    return 0;
}
```

```text
L2#4 L2#25 L7#1 L7#3 
duplicate check: 0
```

**6.** The initializer list's textual order is ignored; members initialize in declaration order, and `cells_` is declared before `rows_`. So `cells_(rows_ * rows_)` runs first, reading an uninitialized `rows_`. Fix one: reorder the declarations so `rows_` comes first (and rewrite the list to match, silencing `-Wreorder`). Fix two: remove the dependency, initializing `cells_` from the constructor parameter directly: `Grid(int n) : cells_(n * n), rows_(n) {}`, which is correct in any order because it reads only `n`.

**7.**

- (a) Variant. The grammar is a closed set the compiler team controls, and exhaustive visitors catch every unhandled node when the language grows. (Real compilers use both this and virtual visitors; the closed-set argument favors variant.)
- (b) Virtual. Third parties add effect types after your host ships: the definition of an open set.
- (c) Variant. 29.4's message set is closed, the loop is hot, and contiguous values beat pointer-chasing under a deadline.
- (d) Virtual. Applications derive new widgets from the toolkit's base classes; the toolkit cannot enumerate them, and per-frame call counts are modest.
