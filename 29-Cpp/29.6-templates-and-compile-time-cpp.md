# Chapter 29.6 - Templates, the STL, and Compile-Time C++

> _Goal: learn how C++ gives you Python's "works for any type" flexibility without giving up an ounce of speed. You'll write function and class templates from scratch, watch the compiler stamp out specialized code for each type, and prove with a benchmark that the abstraction costs nothing. You'll tour the STL as what it really is, a template library glued together by iterators, go deep on lambdas, then move real work to compile time with `constexpr`, `static_assert`, and `if constexpr`. You'll finish by building a fixed-capacity `RingBuffer<T, N>` with iterator support (the sequel to [29.4](29.4-industrial-embedded-cpp.md)'s telemetry ring) and a reusable benchmark harness. Everything here is machinery that [29.3](29.3-allocators-arenas-cache.md)'s allocators and [29.7](29.7-concurrency-atomics-memory-model.md)'s lock-free queue use on every line._

In [29.1](29.1-cpp-for-python-programmers.md) you met static types and probably felt the loss: in Python, one `max()` works for numbers, strings, and anything else comparable, while C++ seemed to demand a separate function per type. In [29.5](29.5-classes-and-object-layout.md) you saw one answer, virtual functions, and paid for it with a vtable pointer per object and an indirect call per use. This chapter is the other answer, the one C++ is actually famous for. Templates recover the "write it once, use it with anything" experience, but they resolve everything before the program exists, so the generic version runs exactly as fast as code you would have written by hand for each type. That claim sounds like marketing, so we will benchmark it instead of asserting it.

## Start here: the print shop

Think about how a Python function handles types. Duck typing is a restaurant with one menu and a very relaxed kitchen: anyone can order anything, and nobody checks whether the kitchen can actually make your dish until the order arrives at the stove. If you call `max(3, "seven")`, the failure happens at serving time, in front of the customer, as a `TypeError`. Flexible, friendly, and every single order carries the cost of those checks, because the interpreter re-asks "can this object do that?" on every operation.

A C++ template is the same restaurant with a different back office: a print shop. Before opening night, the shop looks at every order that will ever be placed (the compiler sees every call site in your program) and prints a brand-new specialized menu for each customer type: one menu where every dish is made with `int`, another where every dish is made with `std::string`, each menu fully checked during printing. If a dish can't be made for some type, the print job fails with a long complaint, before the restaurant ever opens. And at serving time there is nothing left to check. The waiter hands over a menu that was always going to work, and the kitchen runs at full speed.

Hold onto three consequences of the print-shop model, because they explain most of this chapter:

- **All flexibility, moved earlier.** The same source text serves every type, like Python. But every check happens at compile time, so type errors are build failures, not 3 a.m. exceptions.
- **Every printed menu is real paper.** Each instantiation is real machine code in your binary. Ten types means ten copies. That is the price, and we will be honest about it.
- **The complaint letters are long.** When a print job fails, the shop tells you about every dish on the menu that went wrong. Learning to read those letters from the bottom up is a skill we will practice.

## Function templates: one recipe, every type

Start with the function Python gave you for free. Here is a generic `max_of` and a generic swap, written from scratch:

```cpp
#include <cstdio>
#include <string>
#include <utility>

template <typename T>
T max_of(T a, T b) {
    return (b > a) ? b : a;
}

template <typename T>
void swap_vals(T& a, T& b) {
    T tmp = std::move(a);
    a = std::move(b);
    b = std::move(tmp);
}

int main() {
    printf("max_of(3, 7)           = %d\n", max_of(3, 7));
    printf("max_of(2.5, 1.5)       = %.1f\n", max_of(2.5, 1.5));

    std::string s1 = "pad", s2 = "wafer";
    printf("max_of(strings)        = %s\n", max_of(s1, s2).c_str());

    printf("max_of<double>(2, 3.5) = %.1f\n", max_of<double>(2, 3.5));

    int x = 1, y = 2;
    swap_vals(x, y);
    printf("after swap_vals: x=%d y=%d\n", x, y);
}
```

```text
max_of(3, 7)           = 7
max_of(2.5, 1.5)       = 2.5
max_of(strings)        = wafer
max_of<double>(2, 3.5) = 3.5
after swap_vals: x=2 y=1
```

The line `template <typename T>` says: what follows is not a function, it is a **template**, a recipe with a hole named `T`. When you call `max_of(3, 7)`, the compiler performs **template argument deduction**: it looks at the arguments, sees two `int`s, and concludes `T = int`.

It then instantiates the template, generating a real function `max_of<int>` with every `T` replaced by `int`. Call it with two `double`s and you get a second, completely separate function `max_of<double>`. This stamping-out process is called **monomorphization**: one polymorphic recipe becomes many monomorphic (single-type) functions. Each **instantiation** is compiled, optimized, and inlined exactly as if you had written it by hand. This is the print run. The menu for `int` customers and the menu for `std::string` customers share nothing at run time but the source text they came from.

Notice the swap uses `std::move` from [29.2](29.2-memory-and-object-lifetime.md): for an `int` that changes nothing, but the same recipe instantiated for `std::string` moves buffers instead of copying them. One recipe, and each printed menu automatically uses the best technique its type supports.

Deduction has one rule that trips everyone: all the clues must agree. `max_of(2, 3.5)` fails, because the first argument says `T = int` and the second says `T = double`, and the compiler refuses to guess which you meant:

```text
error: no matching function for call to 'max_of(int, double)'
note: candidate: 'template<class T> T max_of(T, T)'
note:   template argument deduction/substitution failed:
note:   deduced conflicting types for parameter 'T' ('int' and 'double')
```

The fix is in the listing above: name the type yourself with `max_of<double>(2, 3.5)`, which skips deduction and converts the `2` on the way in.

### Reading the wall of text

Now the failure mode you will actually meet. Suppose we call `max_of` on a struct that has no `operator>`:

```text
struct PadRecord { int hours_used; };
PadRecord p{40}, q{55};
max_of(p, q);
```

g++ says:

```text
err1.cpp: In instantiation of 'T max_of(T, T) [with T = PadRecord]':
err1.cpp:12:11:   required from here
err1.cpp:5:15: error: no match for 'operator>'
                (operand types are 'PadRecord' and 'PadRecord')
    5 |     return (b > a) ? b : a;
      |            ~~~^~~~
```

Two lines of context for a two-line problem is gentle; deep inside the STL the same shape of error can run to hundreds of lines, because the print shop reports every layer of menu that failed to print. The reading strategy never changes, and it is bottom-up:

1. **Find the last `error:` line.** That is the actual problem: here, no `operator>` for `PadRecord`. Everything above it is the trail of instantiations that led there.
2. **Find `[with T = ...]`.** That tells you which print job failed: `T = PadRecord`.
3. **Find `required from here`.** That is your call site, the order that triggered the job.

Nine times out of ten the fix is at the call site or in your type (give `PadRecord` an `operator>`, or pass a comparator), not in the template. The template was fine; you asked the shop to print a menu for a customer who can't eat anything on it.

### Explicit specialization

Occasionally the generic recipe is wrong for one specific type and you want to override that single print job. Comparing C strings with `>` compares pointer addresses, not text, so we supply a hand-written menu for exactly that case:

```cpp
#include <cstdio>
#include <cstring>

template <typename T>
T max_of(T a, T b) {
    return (b > a) ? b : a;
}

// Explicit specialization: for C strings, compare contents, not addresses.
template <>
const char* max_of<const char*>(const char* a, const char* b) {
    return (std::strcmp(b, a) > 0) ? b : a;
}

int main() {
    const char* a = "oxide";
    const char* b = "tungsten";
    printf("max_of(C strings) = %s\n", max_of(a, b));
}
```

```text
max_of(C strings) = tungsten
```

`template <>` reads as "this is still part of the template family, but with nothing left to deduce". Use specialization sparingly; most of the time an overload or a trait check (later in this chapter) is clearer.

## Class templates: Stack&lt;T&gt;, twice

You built stacks in [2.3](../02-Data-Structures/02.3-stacks-and-queues.md) and containers with the rule of five in [29.2](29.2-memory-and-object-lifetime.md). A **class template** is the same idea with the element type left as a hole:

```cpp
#include <cassert>
#include <cstdio>
#include <string>
#include <utility>
#include <vector>

template <typename T>
class Stack {
public:
    void push(T value) { items_.push_back(std::move(value)); }
    T pop() {
        assert(!items_.empty());
        T top = std::move(items_.back());
        items_.pop_back();
        return top;
    }
    const T& top() const { assert(!items_.empty()); return items_.back(); }
    bool empty() const { return items_.empty(); }
    std::size_t size() const { return items_.size(); }

private:
    std::vector<T> items_;
};

int main() {
    Stack<int> calls;                 // one instantiation
    calls.push(3);
    calls.push(7);
    printf("Stack<int>: top=%d\n", calls.top());
    int popped = calls.pop();
    printf("popped %d, size now %zu\n", popped, calls.size());

    Stack<std::string> undo;          // a second, totally separate class
    undo.push("deposit");
    undo.push("polish");
    std::string last = undo.pop();
    printf("Stack<string>: undo '%s', %zu left\n", last.c_str(), undo.size());
}
```

```text
Stack<int>: top=7
popped 7, size now 1
Stack<string>: undo 'polish', 1 left
```

`Stack<int>` and `Stack<std::string>` are two unrelated classes as far as the type system is concerned; they merely came off the same press. And here is the Python contrast worth savoring: a Python list happily holds a mix of ints and strings, and you find out it did when something crashes far from the cause. `Stack<int>` cannot hold a string. The menu was printed for one customer type, and the doorman checks at compile time.

### Non-type template parameters: Stack&lt;T, N&gt;

The holes in a template don't have to be types. They can be compile-time values, most usefully sizes. Here is a stack whose storage lives entirely inside the object, no heap in sight:

```cpp
#include <cstddef>
#include <cstdio>

template <typename T, std::size_t N>
class FixedStack {
public:
    bool push(const T& value) {
        if (count_ == N) return false;    // full: refuse, never allocate
        data_[count_++] = value;
        return true;
    }
    bool pop(T& out) {
        if (count_ == 0) return false;
        out = data_[--count_];
        return true;
    }
    std::size_t size() const { return count_; }
    static constexpr std::size_t capacity() { return N; }

private:
    T data_[N]{};                         // storage inside the object, no heap
    std::size_t count_ = 0;
};

int main() {
    FixedStack<int, 4> s;
    for (int i = 1; i <= 5; ++i)
        printf("push %d -> %s\n", i, s.push(i) ? "ok" : "REJECTED (full)");

    int v = 0;
    s.pop(v);
    printf("popped %d, size=%zu, capacity=%zu\n", v, s.size(), s.capacity());
    printf("sizeof(FixedStack<int,4>)    = %zu bytes\n", sizeof(FixedStack<int, 4>));
    printf("sizeof(FixedStack<double,8>) = %zu bytes\n", sizeof(FixedStack<double, 8>));
}
```

```text
push 1 -> ok
push 2 -> ok
push 3 -> ok
push 4 -> ok
push 5 -> REJECTED (full)
popped 4, size=3, capacity=4
sizeof(FixedStack<int,4>)    = 24 bytes
sizeof(FixedStack<double,8>) = 72 bytes
```

Because `N` is a compile-time constant, `data_[N]` is a plain array member, the capacity check compiles to a comparison against a literal, and `FixedStack<int, 4>` and `FixedStack<int, 8>` are different types, so you can never accidentally assign one to the other. This is exactly the pattern behind `FixedVector<T, N>` in [29.4](29.4-industrial-embedded-cpp.md), the fixed-capacity workhorse of equipment code, and behind `std::array<T, N>` in the standard library. The `bool` return instead of silent growth is the same philosophy 29.4 preached: in a control loop, "full" is a decision for the caller, not an excuse to touch the heap.

### Why templates live in header files

One structural rule before we move on. In [29.1](29.1-cpp-for-python-programmers.md) you learned the compile-then-link model: each `.cpp` file compiles separately, and the linker stitches the results. That model breaks for templates, because a template is not code, it is a recipe for code. The compiler can only run the print shop when it can see the full recipe and the concrete `T` at the same time. If `Stack<T>`'s member function bodies hide in `stack.cpp` while `main.cpp` asks for `Stack<int>`, the compiler processing `main.cpp` has the order but not the recipe, and the compiler processing `stack.cpp` has the recipe but no order. Nobody prints the menu, and the linker reports the missing function (you will see the exact error in Common Mistakes). So template definitions go in headers, fully visible to every file that uses them. The **one-definition rule** tolerates this on purpose: every translation unit may instantiate `Stack<int>::push`, the definitions are guaranteed identical because they came from the same header text, and the linker quietly keeps one copy and discards the duplicates.

## Zero cost, measured

Time to test the print shop's central promise: a generic function runs exactly as fast as the hand-written one. We sum 20 million doubles four ways: a raw loop, `std::accumulate` (a standard library template), our own iterator template, and, for contrast, the [29.5](29.5-classes-and-object-layout.md) way, a virtual `add()` call per element. Compile with optimization on, the way all benchmarks must be run: `g++ -std=c++17 -Wall -O2`.

```cpp
#include <chrono>
#include <cstdio>
#include <memory>
#include <numeric>
#include <vector>

// The virtual-dispatch contender. Two derived classes and a runtime choice,
// so the compiler cannot prove which add() runs and must keep the vtable call.
struct Accumulator {
    virtual ~Accumulator() = default;
    virtual void add(double x) = 0;
    virtual double total() const = 0;
};
struct SumAcc : Accumulator {
    double t = 0.0;
    void add(double x) override { t += x; }
    double total() const override { return t; }
};
struct AbsAcc : Accumulator {
    double t = 0.0;
    void add(double x) override { t += (x < 0 ? -x : x); }
    double total() const override { return t; }
};

// The template contender: generic over the iterator type, like std::accumulate.
template <typename It>
double sum_range(It first, It last) {
    double total = 0.0;
    for (; first != last; ++first) total += *first;
    return total;
}

template <typename F>
double time_ms(F&& f) {
    auto t0 = std::chrono::steady_clock::now();
    f();
    auto t1 = std::chrono::steady_clock::now();
    return std::chrono::duration<double, std::milli>(t1 - t0).count();
}

int main(int argc, char**) {
    const std::size_t n = 20'000'000;
    std::vector<double> data(n);
    for (std::size_t i = 0; i < n; ++i) data[i] = 0.5 + static_cast<double>(i % 7);

    double s1 = 0, s2 = 0, s3 = 0, s4 = 0;

    double t1 = time_ms([&] {
        double t = 0.0;
        for (double x : data) t += x;
        s1 = t;
    });
    double t2 = time_ms([&] {
        s2 = std::accumulate(data.begin(), data.end(), 0.0);
    });
    double t3 = time_ms([&] {
        s3 = sum_range(data.begin(), data.end());
    });
    double t4 = time_ms([&] {
        std::unique_ptr<Accumulator> acc;
        if (argc > 1) acc = std::make_unique<AbsAcc>();   // never taken, but
        else          acc = std::make_unique<SumAcc>();   // the compiler can't assume that
        for (double x : data) acc->add(x);
        s4 = acc->total();
    });

    printf("hand-written loop : %6.2f ms  (sum = %.0f)\n", t1, s1);
    printf("std::accumulate   : %6.2f ms  (sum = %.0f)\n", t2, s2);
    printf("sum_range template: %6.2f ms  (sum = %.0f)\n", t3, s3);
    printf("virtual dispatch  : %6.2f ms  (sum = %.0f)\n", t4, s4);
}
```

On the test machine (timings vary run to run and machine to machine):

```text
hand-written loop :  39.50 ms  (sum = 69999997)
std::accumulate   :  42.08 ms  (sum = 69999997)
sum_range template:  42.60 ms  (sum = 69999997)
virtual dispatch  :  57.63 ms  (sum = 69999997)
```

Read the table carefully, because both halves matter.

First, the top three rows are the same number within noise. `std::accumulate` and our `sum_range` are templates layered over iterators, yet they cost nothing over the raw loop. That is **zero-cost abstraction** demonstrated, not asserted: at `-O2` the compiler inlined the template code, saw the same operations as the hand loop, and emitted essentially identical machine code for all three. The abstraction existed at compile time and evaporated.

Second, the virtual version is about 1.4x slower here, not 10x, and honesty about why makes you better at benchmarks. This loop is limited by two hard constraints: 160 MB of data streaming through memory, and the fact that floating-point additions into one total form a serial dependency chain the CPU cannot reorder. Against that baseline, the per-element vtable load and indirect call add real work but not catastrophic work. The per-call cost of each dispatch mechanism, isolated from memory effects, is exactly what the mini-project measures at the end of this chapter, and there the ranking gets much sharper.

One tool-of-the-trade note: the website godbolt.org (Compiler Explorer) lets you paste a C++ snippet and see the generated assembly live, per compiler and per flag. Paste `sum_range` instantiated for `double*` next to the hand loop at `-O2` and you can watch them produce the same instructions. Professionals settle "does this abstraction cost anything?" arguments there daily, and it is the fastest way to build intuition for what the optimizer actually does.

## The STL: N + M, not N times M

Now you can see the standard library for what it is. **STL** originally meant Standard Template Library, and the name is exact: containers (`vector`, `list`, `deque`, `map`) are class templates, algorithms (`sort`, `find_if`, `accumulate`) are function templates, and the two families never mention each other by name. What connects them is the **iterator**: a small object that promises "I can be dereferenced with `*`, advanced with `++`, and compared with `==`". Containers produce iterators; algorithms consume them.

Count what that buys. With N containers and M algorithms, writing every algorithm for every container directly would take N times M implementations. With iterators in the middle, each container implements its iterators once and each algorithm is written once against the iterator interface: N + M implementations, and every algorithm works on every container automatically, including containers that didn't exist when the algorithm was written, like the `RingBuffer` you will build shortly. This is duck typing's flexibility again, run through the print shop: `std::sort` doesn't care what it sorts any more than a Python function does, but every combination is checked and specialized at compile time.

Iterators come in capability tiers, because algorithms differ in what they need:

| Category | Can do | Producers | Example consumer |
|---|---|---|---|
| Input | read once, `++` forward | input streams | `accumulate` |
| Forward | read/write, `++`, multiple passes | `forward_list`, our RingBuffer | `find_if` |
| Bidirectional | all above, plus `--` | `list`, `map`, `set` | `reverse` |
| Random access | all above, plus `it + n`, `it[n]`, `<` | `vector`, `deque`, arrays | `sort`, `lower_bound` |

`std::sort` demands random access, which is why you can sort a `vector` but not a `list` with it (a `list` iterator cannot jump; `list` provides its own `sort` member instead). The compiler enforces all of this during the print run.

Even the range-for loop you have used since 29.1 is iterator sugar. When you write `for (int x : v) { ... }`, the compiler rewrites it as roughly:

```text
auto __it  = v.begin();
auto __end = v.end();
for (; __it != __end; ++__it) {
    int x = *__it;
    // your loop body
}
```

Any type with `begin()` and `end()` returning something iterator-shaped gets range-for support automatically. That is the entire mechanism, and it is why twenty lines of iterator code will make our RingBuffer feel like a built-in.

### The algorithms tour

Here are the five algorithms you will use weekly, on a realistic record type. Note the comparator and predicates are **lambdas**, which get their own section next:

```cpp
#include <algorithm>
#include <cstdio>
#include <numeric>
#include <vector>

struct Reading {
    int tick;
    double pressure_kpa;
};

int main() {
    std::vector<Reading> log = {
        {5, 21.7}, {1, 20.3}, {4, 55.0}, {2, 20.9}, {3, 21.2},
    };

    // sort with a custom comparator: order by tick
    std::sort(log.begin(), log.end(),
              [](const Reading& a, const Reading& b) { return a.tick < b.tick; });

    // find_if: the first reading that violates a limit
    auto bad = std::find_if(log.begin(), log.end(),
                            [](const Reading& r) { return r.pressure_kpa > 30.0; });
    if (bad != log.end())
        printf("first bad reading: tick %d at %.1f kPa\n", bad->tick, bad->pressure_kpa);

    // transform: project out one field
    std::vector<double> pressures(log.size());
    std::transform(log.begin(), log.end(), pressures.begin(),
                   [](const Reading& r) { return r.pressure_kpa; });

    // accumulate: reduce to one number
    double mean = std::accumulate(pressures.begin(), pressures.end(), 0.0)
                  / static_cast<double>(pressures.size());
    printf("mean pressure: %.2f kPa\n", mean);

    // lower_bound: binary search on the sorted-by-tick log
    auto it = std::lower_bound(log.begin(), log.end(), 3,
                               [](const Reading& r, int tick) { return r.tick < tick; });
    printf("lower_bound(tick=3) landed on tick %d\n", it->tick);
}
```

```text
first bad reading: tick 4 at 55.0 kPa
mean pressure: 27.82 kPa
lower_bound(tick=3) landed on tick 3
```

`std::lower_bound` is the binary search you implemented in [3.3](../03-Algorithms/03.3-searching.md), templated over any random-access range: O(log n) comparisons, and it returns the first position not less than the target, which is also exactly where you would insert to keep the range sorted. `transform` is the STL's `map`, `accumulate` its `reduce`; between them and comprehension-style loops you already think this way from Python.

### The erase-remove idiom

One STL habit needs explicit teaching because it looks wrong until you see why it is right. `std::remove` cannot actually shrink a container: it only has iterators, and iterators don't know how to call `vector::erase`. So `remove` compacts the survivors to the front and returns an iterator to the new logical end, leaving garbage behind it. You then hand that iterator to the container's own `erase` to do the shrinking:

```cpp
#include <algorithm>
#include <cstdio>
#include <vector>

int main() {
    std::vector<int> v = {3, 0, 7, 0, 0, 9, 4};

    auto new_end = std::remove(v.begin(), v.end(), 0);  // compact, don't shrink
    printf("after remove: size is still %zu, live part is", v.size());
    for (auto it = v.begin(); it != new_end; ++it) printf(" %d", *it);
    printf("\n");

    v.erase(new_end, v.end());                          // now actually shrink
    printf("after erase : size %zu:", v.size());
    for (int x : v) printf(" %d", x);
    printf("\n");

    // The one-liner you will write from now on:
    v.erase(std::remove_if(v.begin(), v.end(),
                           [](int x) { return x > 5; }),
            v.end());
    printf("after erase-remove_if(>5): size %zu:", v.size());
    for (int x : v) printf(" %d", x);
    printf("\n");
}
```

```text
after remove: size is still 7, live part is 3 7 9 4
after erase : size 4: 3 7 9 4
after erase-remove_if(>5): size 2: 3 4
```

Why not erase elements one at a time in a loop? Because each single `erase` shifts everything after it, making the loop O(n squared), and because erasing while iterating invalidates your iterator, a classic bug. Erase-remove does one O(n) pass. C++20 finally wrapped the idiom as `std::erase_if(v, pred)`, one line; under C++17 you write the pair.

## Lambdas: functions as arguments, done properly

The algorithms above only became pleasant when C++11 added **lambdas**, so this is where they deserve full treatment. A lambda is an anonymous function object: `[capture](parameters) { body }`. The part Python never made you think about is the capture list, because Python closures always capture variables by reference and keep them alive. C++ makes you choose, and the choice has teeth:

```cpp
#include <cstdio>

int main() {
    int limit = 100;

    auto by_value = [limit](int x) { return x > limit; };   // copies limit now
    auto by_ref   = [&limit](int x) { return x > limit; };  // refers to the live variable

    limit = 500;
    printf("by_value(200) = %d  (still compares against 100)\n", by_value(200));
    printf("by_ref(200)   = %d  (sees the update to 500)\n", by_ref(200));

    // mutable: the captured copy can change between calls
    auto counter = [n = 0]() mutable { return ++n; };
    int c1 = counter();
    int c2 = counter();
    int c3 = counter();
    printf("counter: %d %d %d\n", c1, c2, c3);

    // generic lambda: 'auto' parameter makes the call operator a template
    auto twice = [](auto x) { return x + x; };
    printf("twice(21) = %d, twice(1.5) = %.1f\n", twice(21), twice(1.5));
}
```

```text
by_value(200) = 1  (still compares against 100)
by_ref(200)   = 0  (sees the update to 500)
counter: 1 2 3
twice(21) = 42, twice(1.5) = 3.0
```

What a lambda compiles to is nothing exotic: a small struct whose fields are the captures and whose `operator()` is the body, a **closure object**. `[limit]` copies `limit` into the field at creation; `[&limit]` stores a reference. Captured copies are `const` by default, and `mutable` lifts that, which is how `counter` keeps state between calls, like a tiny bound object. Capture by reference is cheaper and sees updates, but it stores a pointer to a local variable, so a by-reference lambda must never outlive the scope it captured from (a bug we will stage in Common Mistakes). A **generic lambda** with an `auto` parameter is a template in disguise: its `operator()` is a member template, so `twice` above got instantiated once for `int` and once for `double`, the print shop again.

### Storing callables: three tools, three costs

Passing a lambda straight into an algorithm is the easy case. Storing one for later, in a callback slot or a table, forces a choice between three mechanisms:

```cpp
#include <cstdio>
#include <functional>

int add_tax(int cents) { return cents + cents / 10; }

// Option 3: a template parameter. The exact callable type is known,
// so the call can be inlined like any direct call.
template <typename F>
int charge(F f, int cents) { return f(cents); }

int main() {
    // Option 1: a function pointer. One machine address, no state allowed.
    int (*fp)(int) = add_tax;

    // Option 2: std::function. A type-erased box that can hold anything
    // callable with the right signature, including stateful lambdas.
    int rate = 10;
    std::function<int(int)> fn = [rate](int cents) { return cents + cents / rate; };

    printf("fp(1000) = %d\n", fp(1000));
    printf("fn(1000) = %d\n", fn(1000));
    printf("charge(lambda, 1000) = %d\n",
           charge([](int c) { return c + c / 10; }, 1000));

    printf("sizeof(function pointer) = %zu bytes\n", sizeof(fp));
    printf("sizeof(std::function)    = %zu bytes\n", sizeof(fn));
}
```

```text
fp(1000) = 1100
fn(1000) = 1100
charge(lambda, 1000) = 1100
sizeof(function pointer) = 8 bytes
sizeof(std::function)    = 32 bytes
```

The trade is flexibility versus transparency. A **function pointer** is just a code address: cheap, but it cannot carry captured state (a capturing lambda will not convert to one). A **template parameter** preserves the callable's exact type, so the compiler can inline everything: fastest, but the type infects the signature, so you cannot put differently-typed callables in one variable or container.

`std::function` performs **type erasure**: it hides any callable behind one uniform 32-byte front (think of it as the print shop's one laminated menu cover that any card slides into), at the cost of an indirect call every invocation and possibly a heap allocation if the captures outgrow its internal buffer. The mini-project measures all of them head to head; the ranking is template, then function pointer and virtual roughly tied, then `std::function`. The rule that falls out: templates at API boundaries you control, `std::function` only where you truly need "store any callable, decide at run time".

## Compile-time computation: work done before the program exists

The print shop can do more than print specialized copies; it can cook. A **`constexpr`** function is one the compiler is allowed to evaluate during compilation, when its inputs are compile-time constants. Same source, two lives: called with constants in a constant context, it runs in the compiler; called with runtime values, it is a normal function.

```cpp
#include <cstdio>

constexpr long fib(int n) {
    long a = 0, b = 1;
    for (int i = 0; i < n; ++i) {
        long next = a + b;
        a = b;
        b = next;
    }
    return a;
}

// Compile-time unit tests. If fib is ever broken, the build fails.
static_assert(fib(0) == 0);
static_assert(fib(10) == 55);
static_assert(fib(50) == 12586269025L);

int main() {
    constexpr long f30 = fib(30);   // forced to compile time: f30 is a constant
    long f40 = fib(40);             // ordinary call: computed when the program runs
    printf("fib(30) = %ld (baked into the binary)\n", f30);
    printf("fib(40) = %ld (computed when the program runs)\n", f40);
}
```

```text
fib(30) = 832040 (baked into the binary)
fib(40) = 102334155 (computed when the program runs)
```

Look at those `static_assert` lines and recognize what they are: unit tests that run on every single build, cost zero at run time, and stop the compile cold on failure. `static_assert(cond)` accepts any compile-time boolean, which makes it the assertion tool for template code ("is this type trivially copyable?", "is this capacity a power of two?") as well as for `constexpr` logic.

### Table generation: the firmware trick

Where `constexpr` earns its keep in industrial code is precomputed lookup tables. [29.4](29.4-industrial-embedded-cpp.md)'s firmware world constantly needs tables (sine tables for motor control, CRC tables for checksumming telemetry frames) and the traditional options were bad: compute at startup (wasted boot time, mutable table) or paste 256 hex literals into the source (unreviewable, and one typo is a silent data-corruption bug). `constexpr` gives the third option: write the honest algorithm, have the compiler run it, and ship the result as read-only data with the checks machine-verified:

```cpp
#include <array>
#include <cstdint>
#include <cstdio>
#include <cstring>

// Build the classic CRC-32 lookup table (polynomial 0xEDB88320)
// entirely at compile time.
constexpr std::array<std::uint32_t, 256> make_crc32_table() {
    std::array<std::uint32_t, 256> table{};
    for (std::uint32_t i = 0; i < 256; ++i) {
        std::uint32_t c = i;
        for (int bit = 0; bit < 8; ++bit)
            c = (c & 1) ? (0xEDB88320u ^ (c >> 1)) : (c >> 1);
        table[i] = c;
    }
    return table;
}

constexpr auto kCrcTable = make_crc32_table();

// Spot-check the table against known values, at compile time.
static_assert(kCrcTable[0] == 0x00000000u);
static_assert(kCrcTable[1] == 0x77073096u);
static_assert(kCrcTable[255] == 0x2D02EF8Du);

std::uint32_t crc32(const char* data, std::size_t len) {
    std::uint32_t c = 0xFFFFFFFFu;
    for (std::size_t i = 0; i < len; ++i)
        c = kCrcTable[(c ^ static_cast<unsigned char>(data[i])) & 0xFFu] ^ (c >> 8);
    return c ^ 0xFFFFFFFFu;
}

int main() {
    const char* msg = "wafer 42 telemetry";
    printf("crc32(\"%s\") = 0x%08X\n", msg, crc32(msg, std::strlen(msg)));
}
```

```text
crc32("wafer 42 telemetry") = 0x1B65309F
```

The 1 KB table is data in the binary's read-only segment; the loops that built it never execute on the target machine. (You can check that value against Python: `hex(zlib.crc32(b"wafer 42 telemetry"))` prints the same `0x1b65309f`.) The identical pattern generates a sine table for a motor controller: a `constexpr` Taylor-series sine, a `constexpr std::array<float, N>` filled by a loop, and `static_assert`s pinning a few known values.

### if constexpr: branching inside the print shop

Ordinary `if` chooses a branch at run time, and both branches must compile for every `T`. **`if constexpr`** chooses during instantiation, and the not-taken branch is discarded before it is fully type-checked for that `T`. That means each printed menu contains only the dishes that make sense for its customer:

```cpp
#include <cstdio>
#include <string>
#include <type_traits>

template <typename T>
void describe(const T& value) {
    if constexpr (std::is_integral<T>::value) {
        printf("integral, %zu bytes, value %lld\n",
               sizeof(T), static_cast<long long>(value));
    } else if constexpr (std::is_floating_point<T>::value) {
        printf("floating point, %zu bytes, value %g\n",
               sizeof(T), static_cast<double>(value));
    } else if constexpr (std::is_pointer<T>::value) {
        printf("pointer, %zu bytes\n", sizeof(T));
    } else {
        printf("some class type, %zu bytes\n", sizeof(T));
    }
}

int main() {
    describe(42);
    describe('x');
    describe(3.5);
    const char* p = "hello";
    describe(p);
    describe(std::string("hello"));
}
```

```text
integral, 4 bytes, value 42
integral, 1 bytes, value 120
floating point, 8 bytes, value 3.5
pointer, 8 bytes
some class type, 32 bytes
```

Note what did not happen: `describe(std::string(...))` never tried to compile `static_cast<long long>(value)` for a string, which would be an error. With a plain `if` it would have, and the whole template would fail to instantiate. The conditions come from **`<type_traits>`**, the standard header of compile-time questions about types: `std::is_integral<T>`, `std::is_pointer<T>`, and dozens more, each answering as a compile-time `::value` boolean.

The trait with the most practical money attached is `std::is_trivially_copyable<T>`: may this type be copied as raw bytes? [29.3](29.3-allocators-arenas-cache.md) leaned on that property for its arena contract; here it selects a `memcpy` fast path, which is precisely what your standard library's `std::copy` and `std::vector` do internally for eligible types:

```cpp
#include <cstdio>
#include <cstring>
#include <string>
#include <type_traits>

template <typename T>
void copy_objects(const T* src, T* dst, std::size_t n) {
    if constexpr (std::is_trivially_copyable<T>::value) {
        std::memcpy(dst, src, n * sizeof(T));       // bulk byte copy: fast path
        printf("[memcpy path] ");
    } else {
        for (std::size_t i = 0; i < n; ++i)         // must run copy assignment
            dst[i] = src[i];
        printf("[element-by-element path] ");
    }
}

// The pre-C++17 way to constrain a template: SFINAE via enable_if.
// You will meet this in older codebases; read it as "only exists if T is integral".
template <typename T>
typename std::enable_if<std::is_integral<T>::value, bool>::type
is_even(T x) { return x % 2 == 0; }

int main() {
    int a[3] = {1, 2, 3};
    int b[3] = {};
    copy_objects(a, b, 3);
    printf("ints copied: %d %d %d\n", b[0], b[1], b[2]);

    std::string s[2] = {"slurry", "pad"};
    std::string t[2];
    copy_objects(s, t, 2);
    printf("strings copied: %s %s\n", t[0].c_str(), t[1].c_str());

    printf("is_even(42) = %d\n", is_even(42));
    // is_even(3.5) would not compile: the overload does not exist for double.
}
```

```text
[memcpy path] ints copied: 1 2 3
[element-by-element path] strings copied: slurry pad
is_even(42) = 1
```

That `is_even` signature deserves its one honest paragraph, because you will meet its kind in every codebase older than 2017. The technique is **SFINAE**, "substitution failure is not an error": when substituting a `T` into a template signature produces nonsense (here, `enable_if<false, bool>` has no `::type`), the compiler silently drops that candidate from overload resolution instead of erroring. People built a whole dialect of compile-time dispatch out of this loophole, and it works, but the intent hides inside type plumbing and the error messages are dreadful. `if constexpr` replaced most everyday uses with a readable branch, and C++20's **concepts** (`template <std::integral T>`) replaced the rest with actual named requirements; under C++17, reach for `if constexpr` first and keep `enable_if` in your reading vocabulary.

## Templates vs virtual: choosing your polymorphism

You now hold both of C++'s polymorphism tools, so let's put them side by side. Both answer "one interface, many types"; they differ in when the answer is decided.

| | Templates (static) | Virtual (dynamic) |
|---|---|---|
| Type resolved | compile time | run time, per call |
| Mixed types in one container | no, one `T` per instantiation | yes, via base pointers |
| Call cost | direct, inlinable, often zero | vtable load + indirect call |
| Per-object cost | none | vtable pointer (8 bytes) |
| Binary size | one code copy per type used | one code copy total |
| Errors appear | at compile time, verbosely | at run time, or never |
| Set of types | closed at build time | open: plugins, DLLs, user code |
| Natural home | performance-critical inner code | frameworks, heterogeneous collections |

The decision rule: if the set of types is known when you build (which numeric type, which container, which policy), templates win on speed, size-per-object, and compile-time checking. If the set of types is truly open at run time (a GUI holding widgets someone else wrote, a plugin architecture from [29.5](29.5-classes-and-object-layout.md)), virtual is the only tool that works.

### CRTP: a static interface

There is a pattern that gives you the shape of an interface without the vtable, called **CRTP** (curiously recurring template pattern): a derived class inherits from a base template instantiated with itself, `struct Circle : Shape<Circle>`. The base can then call "down" into the derived class through a `static_cast` that costs nothing, because the target type is known at compile time. Here is 29.5's shape example redone statically:

```cpp
#include <cstdio>

// Static interface: the base class template calls down into the derived
// class, and the "down" is resolved at compile time. No vtable anywhere.
template <typename Derived>
struct Shape {
    double area() const {
        return static_cast<const Derived*>(this)->area_impl();
    }
    void report() const {
        printf("%-9s area = %7.2f\n",
               static_cast<const Derived*>(this)->name(), area());
    }
};

struct Circle : Shape<Circle> {
    double r;
    explicit Circle(double radius) : r(radius) {}
    double area_impl() const { return 3.14159265358979 * r * r; }
    const char* name() const { return "circle"; }
};

struct Rectangle : Shape<Rectangle> {
    double w, h;
    Rectangle(double width, double height) : w(width), h(height) {}
    double area_impl() const { return w * h; }
    const char* name() const { return "rectangle"; }
};

// Generic code over any array of shapes: one instantiation per concrete
// type, and every s.area() call below is a direct, inlinable call.
template <typename D, std::size_t N>
double total_area(const D (&shapes)[N]) {
    double t = 0.0;
    for (const Shape<D>& s : shapes) t += s.area();
    return t;
}

// The dynamic version from 29.5, for a size comparison only.
struct VShape {
    virtual ~VShape() = default;
    virtual double area() const = 0;
};
struct VCircle : VShape {
    double r;
    explicit VCircle(double radius) : r(radius) {}
    double area() const override { return 3.14159265358979 * r * r; }
};

int main() {
    Circle circles[] = {Circle(1.0), Circle(2.0)};
    Rectangle rects[] = {Rectangle(3.0, 4.0), Rectangle(2.0, 5.0)};

    circles[0].report();
    rects[0].report();
    printf("total_area(circles) = %.2f\n", total_area(circles));
    printf("total_area(rects)   = %.2f\n", total_area(rects));

    printf("sizeof(Circle)  = %zu (just the double)\n", sizeof(Circle));
    printf("sizeof(VCircle) = %zu (double + vtable pointer)\n", sizeof(VCircle));
}
```

```text
circle    area =    3.14
rectangle area =   12.00
total_area(circles) = 15.71
total_area(rects)   = 22.00
sizeof(Circle)  = 8 (just the double)
sizeof(VCircle) = 16 (double + vtable pointer)
```

`Shape<Circle>` and `Shape<Rectangle>` are different base classes, so there is no common pointer type and you cannot put a `Circle` and a `Rectangle` in the same array; in exchange, `Circle` is half the size of `VCircle` and every `area()` call is direct. Note also the trap the base-pointer world would have set: an array of `Circle` is an array of 8-byte objects, and iterating it through a base-class pointer with pointer arithmetic would stride wrongly. The template version iterates the derived array itself, so the sizes always match.

Now the honesty the print shop demands: every instantiation is real code. Instantiate a 300-line algorithm for eight types and your binary carries eight copies, your compile carries eight print jobs. Template-heavy code is the main reason large C++ projects measure compile times in minutes, and binary bloat is a real cost on small flash parts. Yet embedded and equipment code, [29.4](29.4-industrial-embedded-cpp.md)'s world, loves templates anyway, and the table explains why: the alternatives cost run-time. In firmware there are typically three element types, not thirty, so the duplication is small, while templates deliver no vtables, no heap, capacities checked at compile time, and every call resolved at link time where the toolchain can verify the worst case. `FixedVector<T, N>`, `TelemetryRing<N>`, `Pool<T>`: every fixed-capacity structure in this book's industrial chapters is a template for exactly these reasons.

## Build it: RingBuffer&lt;T, N&gt;

Time to put the entire chapter into one component. [29.4](29.4-industrial-embedded-cpp.md)'s telemetry ring was a fine special-purpose tool; this is its general, reusable form, and [29.7](29.7-concurrency-atomics-memory-model.md) will upgrade the same design into a lock-free queue two threads can share. The build uses every idea so far:

- a type parameter `T` and a non-type parameter `N`,
- a `static_assert` requiring `N` to be a power of two, so index wrapping is a single bitwise AND (`i & (N-1)` equals `i % N` when `N` is a power of two, the trick from 29.3's alignment math) instead of a division,
- `constexpr` capacity,
- and an iterator, so range-for and every read-only STL algorithm work on it unchanged.

```cpp
#include <algorithm>
#include <cassert>
#include <cstddef>
#include <cstdio>
#include <iterator>
#include <numeric>

template <typename T, std::size_t N>
class RingBuffer {
    static_assert(N > 0 && (N & (N - 1)) == 0,
                  "RingBuffer capacity N must be a power of two");
    static constexpr std::size_t kMask = N - 1;

public:
    static constexpr std::size_t capacity() { return N; }

    // Overwrite-oldest policy, like 29.4's telemetry ring: push never fails
    // and never blocks; a full ring silently drops its oldest element.
    void push(const T& value) {
        buf_[head_ & kMask] = value;     // bitmask instead of % N
        ++head_;
        if (count_ < N) ++count_;
    }

    bool pop(T& out) {                   // remove the oldest element
        if (count_ == 0) return false;
        out = buf_[(head_ - count_) & kMask];
        --count_;
        return true;
    }

    std::size_t size() const { return count_; }
    bool empty() const { return count_ == 0; }

    // A minimal forward iterator, enough for range-for and most read-only
    // STL algorithms. It walks logical positions 0..size()-1, oldest first.
    class const_iterator {
    public:
        using iterator_category = std::forward_iterator_tag;
        using value_type        = T;
        using difference_type   = std::ptrdiff_t;
        using pointer           = const T*;
        using reference         = const T&;

        const_iterator(const RingBuffer* rb, std::size_t pos)
            : rb_(rb), pos_(pos) {}

        const T& operator*() const {
            return rb_->buf_[(rb_->head_ - rb_->count_ + pos_) & kMask];
        }
        const T* operator->() const { return &**this; }
        const_iterator& operator++() { ++pos_; return *this; }
        const_iterator operator++(int) { auto old = *this; ++pos_; return old; }
        bool operator==(const const_iterator& o) const { return pos_ == o.pos_; }
        bool operator!=(const const_iterator& o) const { return pos_ != o.pos_; }

    private:
        const RingBuffer* rb_;
        std::size_t pos_;
    };

    const_iterator begin() const { return const_iterator(this, 0); }
    const_iterator end()   const { return const_iterator(this, count_); }

private:
    T buf_[N]{};              // fixed storage inside the object, no heap
    std::size_t head_ = 0;    // total number of pushes ever, masked on use
    std::size_t count_ = 0;   // live elements, at most N
};

int main() {
    RingBuffer<int, 8> ring;
    static_assert(ring.capacity() == 8);
    // RingBuffer<int, 6> bad;  // fails to compile: 6 is not a power of two

    // Fill past capacity: 12 pushes into 8 slots drops the 4 oldest.
    for (int i = 1; i <= 12; ++i) ring.push(i * 10);
    assert(ring.size() == 8);

    printf("contents oldest to newest:");
    for (int x : ring) printf(" %d", x);       // range-for via our iterator
    printf("\n");

    // STL algorithms work because the iterator advertises its category.
    int sum = std::accumulate(ring.begin(), ring.end(), 0);
    auto biggest = std::max_element(ring.begin(), ring.end());
    long over_75 = std::count_if(ring.begin(), ring.end(),
                                 [](int x) { return x > 75; });
    printf("sum=%d, max=%d, count(>75)=%ld\n", sum, *biggest, over_75);

    // pop drains oldest-first.
    int v = 0;
    ring.pop(v);
    printf("popped %d, size now %zu\n", v, ring.size());

    // The wrap-around math survives many trips around the ring.
    for (int i = 0; i < 1000; ++i) ring.push(i);
    int newest_kept = *std::max_element(ring.begin(), ring.end());
    assert(ring.size() == 8 && newest_kept == 999);
    printf("after 1000 more pushes: size=%zu, newest=%d\n",
           ring.size(), newest_kept);
    printf("sizeof(RingBuffer<int,8>) = %zu bytes, all on the stack\n",
           sizeof(RingBuffer<int, 8>));
}
```

```text
contents oldest to newest: 50 60 70 80 90 100 110 120
sum=680, max=120, count(>75)=5
popped 50, size now 7
after 1000 more pushes: size=8, newest=999
sizeof(RingBuffer<int,8>) = 48 bytes, all on the stack
```

Three design points to study. First, `head_` counts every push ever made and is only masked at the moment of use; even when it eventually wraps around `size_t`, the arithmetic stays correct because `N` divides two to the sixty-fourth. Second, the iterator holds a pointer to the ring plus a logical position, and computes the physical slot on each dereference; that keeps oldest-to-newest order correct no matter where the ring's contents physically sit. Third, look at how little the iterator is: five type aliases and six tiny member functions, and in exchange `accumulate`, `max_element`, `count_if`, and range-for all work on a container the STL has never heard of. That is the N + M contract paying out in reverse: build one iterator, inherit every algorithm.

## Mini-project: a benchmark harness

Every performance claim in this chapter leaned on timing code, so the project is to build the tool properly and use it to settle two questions every C++ programmer should own the answers to: what does a call cost through each dispatch mechanism, and what does container choice cost? The methodology follows [16.4](../16-Data/16.4-performance-optimization.md): warm up first, take multiple trials, report the median so one scheduling hiccup can't skew the answer. Compile with `-O2` and put this on your GitHub.

```cpp
#include <algorithm>
#include <chrono>
#include <cstdio>
#include <deque>
#include <functional>
#include <list>
#include <memory>
#include <numeric>
#include <vector>

// ---------- the harness: a template that times any callable ----------
template <typename F>
double time_it_ms(F&& f, int trials = 5) {
    f();                                          // warmup, result discarded
    std::vector<double> times;
    times.reserve(trials);
    for (int t = 0; t < trials; ++t) {
        auto t0 = std::chrono::steady_clock::now();
        f();
        auto t1 = std::chrono::steady_clock::now();
        times.push_back(
            std::chrono::duration<double, std::milli>(t1 - t0).count());
    }
    std::sort(times.begin(), times.end());
    return times[times.size() / 2];               // median beats mean for timings
}

// ---------- part 1: what does one call cost? ----------
// The operation is deliberately not reducible to a closed form, so the
// optimizer cannot replace the whole loop with arithmetic.
long scramble(long x) { return (x ^ (x >> 3)) + 1; }
long scramble2(long x) { return (x ^ (x >> 5)) + 2; }

struct Op {
    virtual ~Op() = default;
    virtual long apply(long x) const = 0;
};
struct ScrambleOp : Op {
    long apply(long x) const override { return (x ^ (x >> 3)) + 1; }
};
struct Scramble2Op : Op {
    long apply(long x) const override { return (x ^ (x >> 5)) + 2; }
};

template <typename F>
long run_calls(std::size_t n, F&& f) {
    long acc = 0;
    for (std::size_t i = 0; i < n; ++i) acc += f(static_cast<long>(i));
    return acc;
}

// ---------- part 2: which container? ----------
template <typename C>
long fill_and_sum(std::size_t n) {
    C c;
    for (std::size_t i = 0; i < n; ++i) c.push_back(static_cast<int>(i & 1023));
    return std::accumulate(c.begin(), c.end(), 0L);
}

int main(int argc, char**) {
    const std::size_t calls = 10'000'000;
    long check = 0;   // every benchmark deposits its result here, and we
                      // print it, so no loop is dead code to the optimizer

    // direct call to a named function
    double t_direct = time_it_ms([&] { check += run_calls(calls, scramble); });

    // function pointer chosen at run time, so it stays an indirect call
    long (*fp)(long) = (argc > 1) ? scramble2 : scramble;
    double t_fnptr = time_it_ms([&] { check += run_calls(calls, fp); });

    // virtual dispatch through a base pointer, type unknown until run time
    std::unique_ptr<Op> op;
    if (argc > 1) op = std::make_unique<Scramble2Op>();
    else          op = std::make_unique<ScrambleOp>();
    double t_virtual = time_it_ms([&] {
        check += run_calls(calls, [&](long x) { return op->apply(x); });
    });

    // std::function holding a lambda
    std::function<long(long)> fn = [](long x) { return (x ^ (x >> 3)) + 1; };
    double t_stdfn = time_it_ms([&] { check += run_calls(calls, fn); });

    // lambda passed straight into the template: fully visible, fully inlinable
    double t_lambda = time_it_ms([&] {
        check += run_calls(calls, [](long x) { return (x ^ (x >> 3)) + 1; });
    });

    printf("dispatch cost, %zu calls each, median of 5 (ns/call in parens)\n",
           calls);
    auto row = [&](const char* name, double ms) {
        printf("  %-18s %7.2f ms  (%.2f ns/call)\n", name, ms,
               ms * 1e6 / static_cast<double>(calls));
    };
    row("direct call",      t_direct);
    row("template + lambda", t_lambda);
    row("function pointer", t_fnptr);
    row("virtual",          t_virtual);
    row("std::function",    t_stdfn);

    // ---------- container table ----------
    const std::size_t n = 1'000'000;
    double t_vec = time_it_ms([&] { check += fill_and_sum<std::vector<int>>(n); });
    double t_vecr = time_it_ms([&] {
        std::vector<int> v;
        v.reserve(n);                              // one allocation up front
        for (std::size_t i = 0; i < n; ++i) v.push_back(static_cast<int>(i & 1023));
        check += std::accumulate(v.begin(), v.end(), 0L);
    });
    double t_deque = time_it_ms([&] { check += fill_and_sum<std::deque<int>>(n); });
    double t_list = time_it_ms([&] { check += fill_and_sum<std::list<int>>(n); });

    printf("\nfill with %zu ints then sum, median of 5\n", n);
    printf("  %-24s %7.2f ms\n", "vector (no reserve)", t_vec);
    printf("  %-24s %7.2f ms\n", "vector (reserve)",    t_vecr);
    printf("  %-24s %7.2f ms\n", "deque",               t_deque);
    printf("  %-24s %7.2f ms\n", "list",                t_list);

    printf("\nchecksum (ignore, printed so nothing is optimized away): %ld\n",
           check);
}
```

On the test machine (your numbers will differ; the ratios should not, much):

```text
dispatch cost, 10000000 calls each, median of 5 (ns/call in parens)
  direct call           9.95 ms  (1.00 ns/call)
  template + lambda     9.42 ms  (0.94 ns/call)
  function pointer     16.02 ms  (1.60 ns/call)
  virtual              16.08 ms  (1.61 ns/call)
  std::function        22.36 ms  (2.24 ns/call)

fill with 1000000 ints then sum, median of 5
  vector (no reserve)         7.17 ms
  vector (reserve)            1.76 ms
  deque                       2.67 ms
  list                       39.62 ms

checksum (ignore, printed so nothing is optimized away): 1515520663860864
```

The dispatch table is the chapter's argument in five rows. Template-plus-lambda ties the direct call: zero cost, again, this time with the memory system out of the picture. Function pointer and virtual land together at about 1.6x, both paying for an indirect call the compiler cannot inline through (the branch predictor makes them cheap, not free). `std::function` costs the most: its call runs through type-erasure plumbing on top of the indirection. None of these numbers is large in absolute terms; all of them multiply by every element of every hot loop you put them in.

The container table repeats [29.3](29.3-allocators-arenas-cache.md)'s sermon with fresh data: `reserve` turns roughly twenty geometric reallocate-and-copy events into one allocation, a 4x win here; `deque` sits in between with its chunked pages; `list` is an order of magnitude behind because it makes one heap allocation per element and then defeats the cache while summing. And the two caveats printed into the program are part of the project. First, an optimizer deletes benchmarks whose results go nowhere, which is why every loop's result flows into `check` and `check` gets printed; a benchmark that prints nothing measures nothing. Second, medians of several trials, after a warmup, are the minimum honest methodology; single-shot timings lie.

Extensions worth committing: add a `RingBuffer` row to the container table, print ratios against the fastest row, and re-run the dispatch table at `-O0` and `-O3` to watch how much of the ranking is the optimizer's doing.

## Common mistakes

1. **Defining templates in a `.cpp` file, then blaming the linker.** The compiler error is nowhere near the cause, so learn to recognize it. Splitting `Stack<T>`'s member definitions into `stack.cpp` while `main.cpp` uses `Stack<int>` builds both files fine, then dies at the last step:

   ```text
   /usr/bin/ld: main.cpp:(.text+0x28): undefined reference to `Stack<int>::push(int)'
   /usr/bin/ld: main.cpp:(.text+0x34): undefined reference to `Stack<int>::pop()'
   collect2: error: ld returned 1 exit status
   ```

   No print job ever ran: `main.cpp` saw only the recipe's cover page, and `stack.cpp` had the recipe but no orders. Fix: move the definitions into the header. `undefined reference` plus angle brackets in the symbol name means "template body not visible at the point of use" almost every time.

2. **Reading template errors top-down.** The first screenful is the instantiation trail, not the problem. Jump to the last `error:` line, then find `[with T = ...]` and `required from here`. Bottom-up, always.

3. **`std::function` everywhere out of habit.** It reads like Python ("a variable that holds a function") so newcomers reach for it in every signature. You just measured the cost: slowest dispatch of the five, 32 bytes, possible heap allocation per assignment. When a function just needs to accept a callable, take a template parameter `F` like `time_it_ms` does. Reserve `std::function` for storage of heterogeneous callables chosen at run time: callback registries, undo stacks.

4. **Over-generic code nobody asked for.** Templating a function that has exactly one caller with exactly one type buys longer compiles and worse errors for zero benefit. Write the concrete version; make it generic when a second type actually shows up. The STL earns its generality by having millions of users. Your internal helper has three.

5. **Forgetting `typename` for dependent types.** Inside a template, `C::const_iterator` might name a type or a static member; the compiler will not guess, and the error says so plainly:

   ```text
   error: need 'typename' before 'C::const_iterator'
          because 'C' is a dependent scope
   ```

   Fix: `typename C::const_iterator it = c.begin();`, or sidestep with `auto it = c.begin();`, which is the modern habit anyway.

6. **Storing a by-reference lambda past its scope.** The capture holds a pointer to a stack variable from [29.2](29.2-memory-and-object-lifetime.md)'s doomed-stack-frame story:

   ```text
   std::function<int()> make_counter() {
       int n = 0;
       return [&n] { return ++n; };   // captures the address of a dead local
   }                                  // n's frame is gone when the caller calls
   ```

   Every later invocation reads freed stack memory: undefined behavior that often "works" in testing. Fix: capture state by value and mark the lambda `mutable`, like the `counter` example, or use `[n = 0]` init-capture so the state lives inside the closure object.

7. **Calling `std::remove` and stopping.** `remove` compacts and returns the new logical end; it cannot shrink the container. Without the `erase` half of erase-remove, the tail still holds stale duplicates and `size()` is unchanged, a bug that survives casual testing because the front of the data looks right.

## On the job / interview angle

Interviewers use this material to separate "writes C++" from "wrote C++ once". Standard questions: what happens when the compiler sees `std::vector<int>` (instantiation and monomorphization, one class stamped out per element type); templates versus virtual functions, with the trade-off table from this chapter as the model answer plus when each is the only correct choice; the cost of `std::function` versus a template parameter (you have measured numbers now, which is a stronger answer than folklore); why templates live in headers (the two-halves-of-the-print-job story, plus the one-definition rule); and the erase-remove idiom, which is close to a shibboleth. `constexpr` questions are rising: "how would you build a lookup table with no startup cost?" wants exactly the CRC example.

On the job, the split is cultural. Application and server codebases use templates mostly by consuming the STL well: fluent algorithms-plus-lambdas style, `reserve` reflexes, knowing which container fits. Library, HFT, game-engine, and embedded teams write templates: fixed-capacity containers, CRTP static interfaces, `if constexpr` fast paths keyed on type traits, compile-time tables in flash. Equipment-software shops in [29.4](29.4-industrial-embedded-cpp.md)'s world sit firmly in the second camp, for the reasons the polymorphism table made concrete: no vtables, no heap, everything resolved and verifiable at build time. Reading skills matter as much as writing skills: the day you join any of these teams, someone's `enable_if` wall from 2014 is waiting for you.

## Exercises

1. Write a function template `clamp_val(x, lo, hi)` that returns `x` limited to the range `[lo, hi]`, using only `operator<` on `T` (the STL's discipline: require the minimum). Show it working for `int` and `double`.

2. Write a function template `array_len(arr)` that returns the number of elements in a plain C array as a compile-time constant, deduced from the array's type, and prove with `static_assert` that it works. (Hint: a template can deduce both `T` and a non-type `N` from a reference to `T[N]`.)

4. Using only STL algorithms and lambdas (no hand-written loops): given `std::vector<double> rr = {210.0, 195.5, 205.2, 380.0, 199.8, 202.1, 401.5}` (polish removal rates, with two outliers), compute the mean, count how many readings exceed it, then erase-remove every reading above 300.0 and print the cleaned mean.

5. The pre-C++17 pair of `enable_if` overloads below halves integers with integer division and floats by multiplication. Rewrite it as a single function template using `if constexpr`, and make it fail to compile with a readable message for non-numeric types.

   ```text
   template <typename T>
   typename std::enable_if<std::is_integral<T>::value, T>::type
   halve(T x) { return x / 2; }

   template <typename T>
   typename std::enable_if<std::is_floating_point<T>::value, T>::type
   halve(T x) { return x * 0.5; }
   ```

6. Extend the CRTP `Shape` static interface with a `perimeter()` method, implement it for `Circle` and `Rectangle`, and confirm no vtable appears (check `sizeof`).

### Solutions

**Exercise 1.**

```cpp
#include <cstdio>

template <typename T>
T clamp_val(T x, T lo, T hi) {
    if (x < lo) return lo;
    if (hi < x) return hi;      // only operator< required, like the STL
    return x;
}

int main() {
    printf("%d %d %d\n", clamp_val(5, 0, 10), clamp_val(-3, 0, 10),
           clamp_val(42, 0, 10));
    printf("%.1f\n", clamp_val(7.5, 0.0, 5.0));
}
```

```text
5 0 10
5.0
```

Note `hi < x` instead of `x > hi`: by phrasing both tests with `<`, the template works for any type that defines that one operator, which is the same minimal requirement `std::sort` and `std::lower_bound` impose.

**Exercise 2.** The template deduces both the element type and the length from the reference-to-array parameter; the empty parameter name is fine because only the type matters.

```cpp
#include <cstdio>

template <typename T, std::size_t N>
constexpr std::size_t array_len(T (&)[N]) { return N; }

int main() {
    int readings[12];
    double temps[7];
    static_assert(array_len(readings) == 12);
    static_assert(array_len(temps) == 7);
    printf("readings has %zu slots, temps has %zu\n",
           array_len(readings), array_len(temps));
}
```

```text
readings has 12 slots, temps has 7
```

This is how the standard's `std::size` works, and it is immune to the classic `sizeof(arr)/sizeof(arr[0])` failure where `arr` has silently decayed to a pointer.

**Exercise 3.**

```cpp
#include <cstdio>

constexpr bool is_power_of_two(std::size_t n) {
    return n > 0 && (n & (n - 1)) == 0;
}

static_assert(is_power_of_two(1));
static_assert(is_power_of_two(64));
static_assert(!is_power_of_two(0));
static_assert(!is_power_of_two(6));
static_assert(!is_power_of_two(1023));

template <typename T, std::size_t N>
class RingBuffer {
    static_assert(is_power_of_two(N), "capacity must be a power of two");
    // ... rest as in the chapter ...
};

int main() {
    RingBuffer<int, 16> ok;   // compiles
    (void)ok;
    // RingBuffer<int, 12> nope;  // error: capacity must be a power of two
    printf("is_power_of_two checks passed at compile time\n");
}
```

```text
is_power_of_two checks passed at compile time
```

The `n > 0` guard matters: without it, `0 & (0 - 1)` is `0` and zero would wrongly pass, and `1` must pass because `1 & 0 == 0`.

**Exercise 4.**

```cpp
#include <algorithm>
#include <cstdio>
#include <numeric>
#include <vector>

int main() {
    std::vector<double> rr = {210.0, 195.5, 205.2, 380.0, 199.8, 202.1, 401.5};

    double mean = std::accumulate(rr.begin(), rr.end(), 0.0)
                  / static_cast<double>(rr.size());
    long above = std::count_if(rr.begin(), rr.end(),
                               [mean](double x) { return x > mean; });
    printf("mean = %.1f, %ld readings above the mean\n", mean, above);

    rr.erase(std::remove_if(rr.begin(), rr.end(),
                            [](double x) { return x > 300.0; }),
             rr.end());
    double clean_mean = std::accumulate(rr.begin(), rr.end(), 0.0)
                        / static_cast<double>(rr.size());
    printf("after dropping outliers: %zu readings, mean = %.1f\n",
           rr.size(), clean_mean);
}
```

```text
mean = 256.3, 2 readings above the mean
after dropping outliers: 5 readings, mean = 202.5
```

Only the two outliers exceed the raw mean, which they themselves inflated by 50 points: a small preview of why 30.4-style process engineers filter before averaging.

**Exercise 5.**

```cpp
#include <cstdio>
#include <type_traits>

template <typename T>
T halve(T x) {
    if constexpr (std::is_integral<T>::value) {
        return x / 2;               // integer division, rounds toward zero
    } else {
        static_assert(std::is_floating_point<T>::value,
                      "halve needs a number");
        return x * static_cast<T>(0.5);
    }
}

int main() {
    printf("halve(7)   = %d\n", halve(7));
    printf("halve(7.0) = %.1f\n", halve(7.0));
}
```

```text
halve(7)   = 3
halve(7.0) = 3.5
```

One function replaces two, the branch is visible logic instead of signature plumbing, and `halve(std::string("x"))` now fails with the plain message "halve needs a number" instead of an overload-resolution wall.

**Exercise 6.**

```cpp
#include <cstdio>

template <typename Derived>
struct Shape {
    double area() const {
        return static_cast<const Derived*>(this)->area_impl();
    }
    double perimeter() const {
        return static_cast<const Derived*>(this)->perimeter_impl();
    }
};

struct Circle : Shape<Circle> {
    double r;
    explicit Circle(double radius) : r(radius) {}
    double area_impl() const { return 3.14159265358979 * r * r; }
    double perimeter_impl() const { return 2.0 * 3.14159265358979 * r; }
};

struct Rectangle : Shape<Rectangle> {
    double w, h;
    Rectangle(double width, double height) : w(width), h(height) {}
    double area_impl() const { return w * h; }
    double perimeter_impl() const { return 2.0 * (w + h); }
};

int main() {
    Circle c(3.0);
    Rectangle r(3.0, 4.0);
    printf("circle: area %.2f, perimeter %.2f\n", c.area(), c.perimeter());
    printf("rect  : area %.2f, perimeter %.2f\n", r.area(), r.perimeter());
}
```

```text
circle: area 28.27, perimeter 18.85
rect  : area 12.00, perimeter 14.00
```

`sizeof(Circle)` remains 8 (one `double`): adding methods to a static interface never adds per-object cost, whereas the first virtual function would have added a vtable pointer to every instance. A derived class that forgets `perimeter_impl` fails at compile time, at the first call site that asks for it.
