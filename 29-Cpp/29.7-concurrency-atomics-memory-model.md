## Start here: two accountants, one ledger

Picture a small firm with one paper ledger and two accountants who both need to post entries to it all day. There are two ways to keep the books sane.

The first way is to hire a guard who holds the only pen. An accountant who wants to post an entry must ask the guard for the pen, and the guard hands it to exactly one accountant at a time. The books stay consistent because simultaneous writing is physically impossible. Progress is slow, since one accountant is always waiting, but nobody has to think very hard. That guard is Python's **GIL**, and you have been working under his protection since Chapter 5.2 without necessarily noticing.

The second way is to fire the guard and hand both accountants their own pens. Now they can work at full speed on different pages at once. But the firm's rulebook, read carefully, says something unsettling: *the books are only guaranteed to add up if the accountants follow a coordination protocol of their own design*. If both pens ever touch the same cell at the same moment without a protocol, the rulebook does not say "the last writer wins" or "you get a smudged number." It says all bets are off, about that cell, about the rest of the page, about the totals at the bottom.

C++ is the second firm. The pens are threads. The rulebook is the **C++ memory model**: the part of the language standard that defines what values a read may observe when threads share memory. And the unsettling clause is real: an unsynchronized concurrent access, a **data race**, is undefined behavior. This chapter teaches the protocols that keep the ledger sane: mutexes (a talking-stick pen the accountants pass around), atomics (special ledger cells that accept one-stroke updates), and the acquire/release rules (a sticky note that says "everything above row 40 is final," which the other accountant reads before trusting those rows). We will keep coming back to this ledger.

## Threads in C++

A thread in C++ is `std::thread`: construct it with a callable and arguments, and a new OS thread starts running immediately. There is no `start()` step and no thread pool by default, just the raw primitive from 5.2.

```cpp
#include <cstdio>
#include <thread>

void count_up(int n, long& out) {      // writes through a reference
    long total = 0;
    for (int i = 0; i < n; ++i) total += i;
    out = total;
}

int main() {
    std::printf("this machine reports %u hardware threads\n",
                std::thread::hardware_concurrency());

    long a = 0, b = 0;
    std::thread t1(count_up, 1000, std::ref(a));   // std::ref: t1 sees OUR a
    std::thread t2(count_up, 2000, std::ref(b));
    t1.join();                                     // wait for t1 to finish
    t2.join();
    std::printf("a=%ld b=%ld\n", a, b);
}
```

```text
this machine reports 2 hardware threads     <- varies by machine
a=499500 b=1999000
```

Three details deserve attention before anything shared enters the picture.

- **Arguments are copied by default.** The `std::thread` constructor copies its arguments into storage owned by the new thread, exactly the value semantics of [29.1](29.1-cpp-for-python-programmers.md). Pass `out` without `std::ref` and the code does not even compile here (the function wants a real reference), but with a function taking `long out` by value it would compile and silently update a copy nobody looks at. When a thread must see the caller's object, say so explicitly with `std::ref`, and then remember you have just created shared state that needs a protocol.
- **Every thread must be joined (or detached) before its object is destroyed**, or the program calls `std::terminate`. `join()` blocks until the thread finishes and is also a synchronization point: after `join()` returns, everything the thread did is visible to you. We will lean on that guarantee later.
- **`detach()` exists and you should almost never use it.** Detaching says "run on, I will never wait for you." The detached thread keeps running with references into a world that may be destructed underneath it, including at program exit, when static objects die while the thread still touches them. In the industrial domain this book keeps returning to, a thread nobody can join is a thread nobody can shut down cleanly, and [29.4](29.4-industrial-embedded-cpp.md) taught you what controlled shutdown is worth. Structure programs so every thread has an owner that joins it.

`hardware_concurrency()` reports how many threads the hardware can truly run at once (cores, or hyperthreads). More software threads than that is legal and often useful for I/O-bound work; for CPU-bound work it only adds scheduling overhead, the same lesson 5.2 taught with Python's thread pools.

## The first race: two pens, one cell

Now the experiment this chapter is named for. Two threads, each incrementing one shared `int` a million times. Under the ledger analogy: both accountants add 1 to the same cell a million times each, no protocol. The books should end at 2,000,000.

```cpp
#include <cstdio>
#include <thread>

int counter = 0;                       // shared, unprotected: a data race

void hammer() {
    for (int i = 0; i < 1000000; ++i) ++counter;
}

int main() {
    std::thread t1(hammer);
    std::thread t2(hammer);
    t1.join();
    t2.join();
    std::printf("expected 2000000, got %d\n", counter);
}
```

Compiled without optimization (`g++ -std=c++17 -Wall -pthread race.cpp`), one run on the author's two-core machine printed:

```text
expected 2000000, got 1078220     <- varies wildly run to run
```

Nearly half the increments vanished. To see why, drop to the level of [25.2](../25-Architecture/25.2-assembly-programming.md). `++counter` is not one instruction's worth of work; it is a **read-modify-write**: load the value into a register, add one, store it back. Two threads can interleave those steps:

```text
   thread 1                    thread 2                 counter in memory
   --------                    --------                 -----------------
   load  counter -> 41                                        41
                               load  counter -> 41            41
   add 1         -> 42                                        41
                               add 1         -> 42            41
   store 42                                                   42
                               store 42                       42   <- one increment lost
```

Both accountants read 41, both wrote 42, and one increment evaporated. A million iterations give the scheduler a million chances to interleave like this, so hundreds of thousands of updates are lost.

Here is the twist that separates C++ from the "stale value" story you might expect. Compile the same program with `-O2` and on the author's machine it prints `2000000`, every time. Fixed? No. The optimizer collapsed each thread's loop into a single `counter += 1000000`, shrinking the race window from a million interleavings to one. The bug is still there, it just stopped showing itself on this hardware, on this day, at this optimization level. That is worse, not better, and it is the door into the next section.

## A data race is undefined behavior, not a stale read

The standard's definition is precise. A **data race** occurs when two threads access the same memory location, at least one access is a write, at least one is non-atomic, and nothing orders one before the other. And the consequence is the sharpest sentence in this chapter: a data race is not "you might read an old value." It is **undefined behavior**, the same category as the dangling pointers of [29.2](29.2-memory-and-object-lifetime.md). The compiler is entitled to assume data races never happen and to optimize on that assumption, and it does.

Watch what that license does to the most innocent-looking synchronization ever written, the plain `bool` flag:

```cpp
// FRAGMENT, deliberately broken: do not ship this.
bool ready = false;            // shared with another thread, no protocol

void wait_for_ready() {
    while (!ready) {}          // what you wrote: poll until the other thread
    use_the_data();            //   sets ready = true
}
```

The compiler examines `wait_for_ready`, sees that nothing inside the loop writes `ready`, and reasons: "no other thread can be writing it either, because that would be a data race, which cannot happen." So it hoists the load out of the loop:

```cpp
// What -O2 may legitimately compile, and gcc really does:
if (!ready) { for (;;) {} }    // read once, then spin forever
```

Your program hangs, but only in the optimized build, and only when the flag was false at the moment of that single read. The unoptimized build works. The debugger build works. The test suite, compiled `-O0` for debuggability, works. Production hangs. There is no better recipe for a week-long investigation.

Chapter [29.4](29.4-industrial-embedded-cpp.md) already told you `volatile` is not the fix, and now you can see the full story. `volatile` does defeat the hoisting, because it forces every read to actually happen. But it fixes only the symptom the compiler caused and none of the ones the hardware causes: `volatile` gives no atomicity (the torn read-modify-write above still tears) and no ordering (writes made before the flag was set may still not be visible after you see it, the topic of the memory-model section). `volatile` is for hardware registers, where the memory itself is the device. For inter-thread data, the correct minimum tool is `std::atomic`, and the correct general tool is a mutex. A helpful mental rule: `volatile` talks to the compiler about the machine; `atomic` talks to the compiler *and the machine* about other threads.

## Mutexes done right

A **mutex** (mutual exclusion) is the talking-stick pen: at most one thread can hold it, everyone else waits. The rules of the C++ memory model make it work at both levels we need: while you hold the mutex nobody else can be between their lock and unlock of the same mutex, and everything you wrote before unlocking is guaranteed visible to the next thread that locks it. Here is the racing counter, repaired:

```cpp
#include <cstdio>
#include <mutex>
#include <thread>

int counter = 0;
std::mutex counter_mutex;              // the named guardian of counter

void hammer() {
    for (int i = 0; i < 1000000; ++i) {
        std::lock_guard<std::mutex> lock(counter_mutex);  // RAII: unlocks on scope exit
        ++counter;
    }
}

int main() {
    std::thread t1(hammer);
    std::thread t2(hammer);
    t1.join();
    t2.join();
    std::printf("expected 2000000, got %d\n", counter);
}
```

```text
expected 2000000, got 2000000
```

Never call `.lock()` and `.unlock()` by hand; that is the `new`/`delete` mistake of [29.2](29.2-memory-and-object-lifetime.md) all over again, and an early `return` or exception leaks a locked mutex, which deadlocks the program instead of leaking memory. The RAII wrappers do it right:

- **`std::lock_guard`**: locks in the constructor, unlocks in the destructor, nothing else. The default.
- **`std::unique_lock`**: same idea but can unlock early, relock, and be moved. Costs a little bookkeeping; use it when you need those extras, and condition variables require it.
- **`std::scoped_lock`** (C++17): locks *several* mutexes at once with a deadlock-avoidance algorithm.

That last one earns its keep the first time you need two locks. Consider transferring money between two accounts, each with its own mutex. The obvious code locks `from.m` then `to.m`. Run transfers in both directions on two threads and you have built the classic **deadlock**:

```cpp
// FRAGMENT, deliberately broken: can deadlock, do not run in anything you love.
void transfer_broken(Account& from, Account& to, long amount) {
    std::lock_guard<std::mutex> l1(from.m);   // thread 1 holds a.m, wants b.m
    std::lock_guard<std::mutex> l2(to.m);     // thread 2 holds b.m, wants a.m
    from.balance -= amount;                   // ...and both wait forever
    to.balance   += amount;
}
```

Thread 1 runs `transfer(a, b)`, thread 2 runs `transfer(b, a)`. Each grabs its first mutex, then blocks waiting for the other's. Two accountants, each clutching one of the two pens the job needs, each politely waiting for the other, forever. The fixes are either a global lock order (always lock the lower-addressed mutex first, and document it) or `std::scoped_lock`, which acquires all its mutexes without ever waiting while holding, so a cycle cannot form:

```cpp
#include <cstdio>
#include <mutex>
#include <thread>

struct Account {
    long balance = 0;
    std::mutex m;
};

void transfer(Account& from, Account& to, long amount) {
    std::scoped_lock lock(from.m, to.m);   // locks BOTH, deadlock-free
    from.balance -= amount;
    to.balance   += amount;
}

int main() {
    Account a, b;
    a.balance = 10000;
    b.balance = 10000;

    // Thread 1 moves money a->b, thread 2 moves money b->a, 100k times each.
    std::thread t1([&] { for (int i = 0; i < 100000; ++i) transfer(a, b, 1); });
    std::thread t2([&] { for (int i = 0; i < 100000; ++i) transfer(b, a, 1); });
    t1.join();
    t2.join();

    std::printf("a=%ld b=%ld total=%ld (must be 20000)\n",
                a.balance, b.balance, a.balance + b.balance);
}
```

```text
a=10000 b=10000 total=20000 (must be 20000)
```

### Granularity: how much ledger does one pen guard?

A mutex protects whatever you decide it protects; the language does not know or care. That decision, **lock granularity**, is a real performance lever. One coarse mutex over a whole data structure is simple and safe but serializes everything; one fine mutex per independent piece lets threads that touch different pieces proceed in parallel. Let's measure it: sixteen counters, two threads updating disjoint halves, guarded first by one shared mutex and then by one mutex per counter. Compile benchmarks in this chapter with `-O2` added to the usual flags.

```cpp
#include <chrono>
#include <cstdio>
#include <mutex>
#include <thread>

constexpr int kSlots = 16;
constexpr int kOps   = 2000000;   // per thread

long coarse_slots[kSlots] = {};
std::mutex coarse_mutex;                 // ONE lock for all 16 slots

struct FineSlot {
    long value = 0;
    std::mutex m;
};
FineSlot fine_slots[kSlots];             // one lock PER slot

template <class Fn>
double timed(Fn fn) {
    auto t0 = std::chrono::steady_clock::now();
    std::thread t1(fn, 0), t2(fn, 1);
    t1.join(); t2.join();
    auto t1c = std::chrono::steady_clock::now();
    return std::chrono::duration<double, std::milli>(t1c - t0).count();
}

int main() {
    // Thread 0 updates slots 0-7, thread 1 updates slots 8-15: disjoint data.
    double coarse_ms = timed([](int id) {
        for (int i = 0; i < kOps; ++i) {
            std::lock_guard<std::mutex> lock(coarse_mutex);
            ++coarse_slots[id * 8 + i % 8];
        }
    });
    double fine_ms = timed([](int id) {
        for (int i = 0; i < kOps; ++i) {
            int s = id * 8 + i % 8;
            std::lock_guard<std::mutex> lock(fine_slots[s].m);
            ++fine_slots[s].value;
        }
    });

    long coarse_total = 0, fine_total = 0;
    for (int s = 0; s < kSlots; ++s) {
        coarse_total += coarse_slots[s];
        fine_total   += fine_slots[s].value;
    }
    std::printf("coarse total=%ld  fine total=%ld  (each must be %d)\n",
                coarse_total, fine_total, 2 * kOps);
    std::printf("coarse: %.0f ms   fine: %.0f ms   ratio: %.1fx\n",
                coarse_ms, fine_ms, coarse_ms / fine_ms);
}
```

```text
coarse total=4000000  fine total=4000000  (each must be 4000000)
coarse: 218 ms   fine: 44 ms   ratio: 5.0x     <- times and ratio vary by machine
```

Five times faster on just two cores, and the gap widens with core count, because the threads never actually needed to exclude each other: the data was disjoint and only the coarse lock forced them to take turns. That waiting is called **contention**, and reducing it, not the raw cost of locking, is what granularity buys. The trade is complexity: sixteen locks are sixteen opportunities to lock the wrong one or to need two at once (see the deadlock above). Start coarse, measure, and refine only where contention shows up.

### Condition variables: waiting for the books to change

Locks let threads take turns; a **condition variable** lets a thread *sleep until some condition becomes true*, instead of burning CPU polling for it. The canonical use is a bounded queue: a consumer that finds the queue empty should sleep until a producer adds something.

The API has a famous trap. The OS is allowed to wake a waiting thread even when nobody notified it (a **spurious wakeup**), and even a real notification can be stale by the time the sleeper actually runs (another thread got there first and emptied the queue again). So the condition must always be re-checked after every wakeup, which is why the correct form is the **predicate loop**: `cv.wait(lock, predicate)` internally loops, re-checking the predicate each time it wakes, and only returns with the lock held and the predicate true. Write the predicate form always; a bare `wait()` with an `if` around it is a latent bug.

Here is a full bounded producer-consumer queue with a mutex and two condition variables. This is the baseline implementation the Build it section will race against, so read it closely.

```cpp
#include <condition_variable>
#include <cstdio>
#include <mutex>
#include <queue>
#include <thread>

class BoundedQueue {
public:
    explicit BoundedQueue(size_t cap) : cap_(cap) {}

    void push(int v) {
        std::unique_lock<std::mutex> lock(m_);
        not_full_.wait(lock, [&] { return q_.size() < cap_; });  // predicate loop
        q_.push(v);
        not_empty_.notify_one();
    }

    int pop() {
        std::unique_lock<std::mutex> lock(m_);
        not_empty_.wait(lock, [&] { return !q_.empty(); });
        int v = q_.front();
        q_.pop();
        not_full_.notify_one();
        return v;
    }

private:
    std::mutex m_;
    std::condition_variable not_full_, not_empty_;
    std::queue<int> q_;
    size_t cap_;
};

int main() {
    constexpr int kN = 200000;
    BoundedQueue q(64);

    std::thread producer([&] {
        for (int i = 0; i < kN; ++i) q.push(i);
    });

    long long sum = 0;
    int out_of_order = 0, prev = -1;
    std::thread consumer([&] {
        for (int i = 0; i < kN; ++i) {
            int v = q.pop();
            sum += v;
            if (v != prev + 1) ++out_of_order;   // single producer: order must hold
            prev = v;
        }
    });

    producer.join();
    consumer.join();

    long long expected = 1LL * kN * (kN - 1) / 2;
    std::printf("sum=%lld expected=%lld  order violations=%d\n",
                sum, expected, out_of_order);
    std::printf("%s\n", (sum == expected && out_of_order == 0) ? "PASS" : "FAIL");
}
```

```text
sum=19999900000 expected=19999900000  order violations=0
PASS
```

Note how `wait` takes the `unique_lock` itself: it atomically releases the mutex and goes to sleep, then reacquires the mutex before returning. That atomicity is the point of the whole mechanism; unlock-then-sleep as two separate steps would let a notification slip through the gap and be lost.

## Atomics: the one-stroke ledger cell

Sometimes a whole mutex is a heavyweight answer to a lightweight question. Our first race needed nothing but "make `++` indivisible." **`std::atomic<T>`** is exactly that: a ledger cell that only accepts complete, one-stroke updates, implemented not with a lock but with special CPU instructions (`lock add`, `cmpxchg` and friends on x86, which [25.2](../25-Architecture/25.2-assembly-programming.md) prepared you to believe in).

```cpp
#include <atomic>
#include <cstdio>
#include <thread>

std::atomic<int> counter{0};

void hammer() {
    for (int i = 0; i < 1000000; ++i)
        counter.fetch_add(1);          // one indivisible read-modify-write
}

int main() {
    std::thread t1(hammer);
    std::thread t2(hammer);
    t1.join();
    t2.join();
    std::printf("expected 2000000, got %d\n", counter.load());
}
```

```text
expected 2000000, got 2000000
```

`fetch_add` performs the load-add-store as one indivisible hardware operation, so the interleaving diagram from earlier simply cannot happen. The everyday atomic vocabulary is small: `load()`, `store(v)`, `exchange(v)` (store and return the old value), `fetch_add`/`fetch_sub`, and the star of lock-free programming, **compare-exchange**.

### Compare-exchange: optimistic bookkeeping

`compare_exchange_weak(expected, desired)` says: *if the cell still holds `expected`, replace it with `desired` and return true; otherwise write the cell's actual current value into `expected` and return false.* It is the hardware **CAS** (compare-and-swap) instruction with a C++ calling convention, and it enables a pattern mutexes cannot express cheaply: read, compute the new value, and commit only if nobody interfered, retrying if someone did. The accountant pencils in a correction, then checks the cell one last time as they ink it; if a colleague changed it meanwhile, erase and redo.

Here is a worked example with a real invariant to protect: a counter that must never exceed a cap, no matter how many threads increment it. `fetch_add` alone cannot do this (it would blow past the cap and need repair); CAS can, because the bound check and the update commit together or not at all.

```cpp
#include <atomic>
#include <cstdio>
#include <thread>

std::atomic<int> permits_issued{0};
constexpr int kCap = 1000000;          // never issue more than this many

// Returns how many permits this thread actually got.
int grab_permits(int want) {
    int got = 0;
    for (int i = 0; i < want; ++i) {
        int cur = permits_issued.load();
        for (;;) {
            if (cur >= kCap) return got;             // sold out
            // Try to move cur -> cur+1. On failure, cur is refreshed for us.
            if (permits_issued.compare_exchange_weak(cur, cur + 1)) {
                ++got;
                break;
            }
        }
    }
    return got;
}

int main() {
    int got1 = 0, got2 = 0;
    std::thread t1([&] { got1 = grab_permits(700000); });
    std::thread t2([&] { got2 = grab_permits(700000); });
    t1.join();
    t2.join();
    std::printf("issued=%d (cap %d)  t1+t2=%d  %s\n",
                permits_issued.load(), kCap, got1 + got2,
                (permits_issued.load() == kCap && got1 + got2 == kCap) ? "PASS"
                                                                       : "FAIL");
}
```

```text
issued=1000000 (cap 1000000)  t1+t2=1000000  PASS
```

Two threads request 1.4 million permits total; exactly 1.0 million are issued and every permit is accounted for. The `_weak` variant may fail spuriously (report failure even though the value matched) and is meant for exactly this kind of retry loop; `_strong` never fails spuriously and suits one-shot attempts.

`std::atomic<bool>` covers the honest version of the broken flag from earlier, and we will use it properly in the memory-model section. One structural note: atomics are neither copyable nor movable, because copying "a cell two threads are racing on" has no sane meaning.

### What is actually lock-free, and what does it cost?

`std::atomic<T>` works for any trivially copyable `T`, but if the hardware has no indivisible instruction for that size, the library silently falls back to an internal lock. Ask before you rely:

```cpp
#include <atomic>
#include <cstdio>
#include <cstdint>

struct Pair8  { uint32_t a, b; };          // 8 bytes
struct Pair16 { uint64_t a, b; };          // 16 bytes
struct Odd24  { uint64_t a, b; uint32_t c; };  // 24 bytes

int main() {
    std::printf("atomic<uint8_t>  lock-free: %d\n", std::atomic<uint8_t>::is_always_lock_free);
    std::printf("atomic<uint32_t> lock-free: %d\n", std::atomic<uint32_t>::is_always_lock_free);
    std::printf("atomic<uint64_t> lock-free: %d\n", std::atomic<uint64_t>::is_always_lock_free);
    std::printf("atomic<void*>    lock-free: %d\n", std::atomic<void*>::is_always_lock_free);
    std::printf("atomic<Pair8>    lock-free: %d\n", std::atomic<Pair8>::is_always_lock_free);
    std::printf("atomic<Pair16>   lock-free: %d\n", std::atomic<Pair16>::is_always_lock_free);
    std::printf("atomic<Odd24>    lock-free: %d\n", std::atomic<Odd24>::is_always_lock_free);
}
```

```text
atomic<uint8_t>  lock-free: 1
atomic<uint32_t> lock-free: 1
atomic<uint64_t> lock-free: 1
atomic<void*>    lock-free: 1
atomic<Pair8>    lock-free: 1
atomic<Pair16>   lock-free: 0
atomic<Odd24>    lock-free: 0
```

That is gcc on x86-64: everything up to 8 bytes is lock-free, including an 8-byte struct, and beyond that you get the lock fallback (16-byte atomics exist on x86-64 via `cmpxchg16b` but gcc does not use it by default). The practical rule: keep atomic variables at machine word size or below, and check `is_always_lock_free` with a `static_assert` when it matters, in the spirit of [29.6](29.6-templates-and-compile-time-cpp.md).

Now the cost question. An atomic increment is one instruction, but a special one: it must own the cache line exclusively and be visible machine-wide. A mutex is heavier still: at minimum an atomic operation to lock and another to unlock, plus a trip through the kernel when there is contention. Measured, two threads hammering one counter (the single-threaded plain increment uses `volatile` so `-O2` cannot collapse the loop, the same trick 29.4 used for stand-in work):

```cpp
#include <atomic>
#include <chrono>
#include <cstdio>
#include <mutex>
#include <thread>

constexpr int kOps = 2000000;   // per thread

volatile long plain_counter = 0;   // volatile: forces a real store per ++,
                                   // so -O2 cannot collapse the loop
std::atomic<long> atomic_counter{0};
long mutex_counter = 0;
std::mutex mutex_counter_mutex;

template <class Fn>
double run_two_threads(Fn fn) {
    auto t0 = std::chrono::steady_clock::now();
    std::thread t1(fn), t2(fn);
    t1.join(); t2.join();
    auto t1c = std::chrono::steady_clock::now();
    return std::chrono::duration<double>(t1c - t0).count() * 1e9 / (2.0 * kOps);
}

int main() {
    auto t0 = std::chrono::steady_clock::now();
    for (int i = 0; i < 2 * kOps; ++i) plain_counter = plain_counter + 1;
    auto t1 = std::chrono::steady_clock::now();
    double plain_ns =
        std::chrono::duration<double>(t1 - t0).count() * 1e9 / (2.0 * kOps);

    double atomic_ns = run_two_threads([] {
        for (int i = 0; i < kOps; ++i) atomic_counter.fetch_add(1);
    });
    double mutex_ns = run_two_threads([] {
        for (int i = 0; i < kOps; ++i) {
            std::lock_guard<std::mutex> lock(mutex_counter_mutex);
            ++mutex_counter;
        }
    });

    std::printf("totals: atomic=%ld mutex=%ld (each must be %d)\n",
                atomic_counter.load(), mutex_counter, 2 * kOps);
    std::printf("ns per increment:  plain(1 thread)=%.1f  atomic(2)=%.1f  mutex(2)=%.1f\n",
                plain_ns, atomic_ns, mutex_ns);
}
```

```text
totals: atomic=4000000 mutex=4000000 (each must be 4000000)
ns per increment:  plain(1 thread)=1.7  atomic(2)=12.6  mutex(2)=61.4   <- varies by machine
```

The ladder on this machine: roughly 2 ns for an uncontended plain increment, roughly 13 ns for a contended atomic, roughly 60 ns for a contended mutex. Order of magnitude apiece, and worth internalizing as ratios rather than absolutes: atomics are several times cheaper than mutexes under contention, and both are many times dearer than unshared work. The fastest synchronization remains not sharing, a point the false-sharing section will land harder.

## The memory model: what the rulebook actually promises

So far we have used atomics with their default behavior. Every atomic operation in C++ takes an optional `std::memory_order` argument, and the default is `memory_order_seq_cst`: **sequential consistency**. It is time to say precisely what that means, because this is the part of the chapter that separates "can use threads" from "can be trusted with them."

### Why ordering is a question at all

You might expect that if thread A writes `x` then writes `y`, thread B must see the writes in that order. On real machines, without help, it may not. Two independent actors conspire to reorder your memory operations:

- **The compiler** reorders and eliminates memory accesses whenever the single-threaded meaning is preserved, which you have already watched it do to the hoisted flag loop.
- **The CPU** buffers stores, satisfies loads early, and (on ARM and POWER especially) lets memory operations become visible to other cores out of program order. Chapter [25.1](../25-Architecture/25.1-computer-architecture.md)'s store buffers and cache hierarchy are exactly the mechanisms responsible.

Both reorderings are invisible to single-threaded code, which is why they are legal and why single-threaded programmers never notice. Only a second thread, peeking at memory mid-flight, can tell the difference. The memory model is the treaty that says which peeks are allowed to see what.

### Sequential consistency: the default, and the right default

Under `seq_cst`, all sequentially consistent atomic operations in the program behave as if they were interleaved into one single global timeline that every thread agrees on, consistent with each thread's own program order. That is precisely the "interleaving of steps" model you have been using to reason about concurrency since 5.2, made into a guarantee. Combined with the golden rule (no data races on non-atomic data), it means: *programs without data races behave as some interleaving of their threads.* You can reason by considering interleavings, and the machine must honor your reasoning.

This is why `seq_cst` as the default is the right engineering call, not timidity. Its cost is real but modest (on x86 it adds a fence to atomic stores; loads are nearly free), and the cost of reasoning about anything weaker is paid in human review hours and 2 a.m. debugging, the most expensive currency this book knows. Weaken only what you have measured and can justify in a comment.

### Message passing, and how weakening breaks it

The pattern that makes ordering concrete is **message passing**: one thread prepares data (plain, non-atomic), then sets a flag; another thread sees the flag and reads the data. The data is the ledger page, the flag is the sticky note that says "rows above here are final."

The rule pair that makes it correct:

- a **release store** (`store(v, memory_order_release)`) publishes: no read or write before it in program order may be reordered after it, and
- an **acquire load** (`load(memory_order_acquire)`) subscribes: no read or write after it may be reordered before it.

When an acquire load reads the value written by a release store, the two **synchronize**, and the standard's promise, in plain words, is: *everything the writing thread did before the release store is visible to the reading thread after that acquire load.* The relation is called **happens-before**, and the diagram is worth committing to memory:

```text
   producer thread                          consumer thread
   ---------------                          ---------------
   write payload (plain data)
        |  sequenced-before
        v
   flag.store(true, release)  ──────────►  flag.load(acquire) == true
                          synchronizes-with      |  sequenced-before
                                                 v
                                            read payload (plain data)

   everything above the release-store HAPPENS-BEFORE
   everything below the acquire-load that read it
```

Because the payload writes happen-before the payload reads, they are not a data race even though the payload is not atomic. The flag carries the ordering for all the data it publishes; the sticky note vouches for the whole page. Here is the pattern under test, ping-ponging 200,000 messages whose checksum would expose any stale read:

```cpp
#include <atomic>
#include <cstdio>
#include <thread>

struct Message {
    int payload[4];        // plain data: NOT atomic
};

Message mailbox;                       // written by producer, read by consumer
std::atomic<bool> ready{false};        // the flag that publishes the mailbox

int main() {
    constexpr int kRounds = 200000;
    long long checksum_errors = 0;

    std::thread producer([&] {
        for (int r = 1; r <= kRounds; ++r) {
            mailbox.payload[0] = r;            // 1. write the data...
            mailbox.payload[1] = r * 2;
            mailbox.payload[2] = r * 3;
            mailbox.payload[3] = r * 6;        //    (sum of first three)
            ready.store(true, std::memory_order_release);   // 2. ...THEN publish

            // Wait for the consumer to take it (acquire pairs with its release).
            while (ready.load(std::memory_order_acquire)) {}
        }
    });

    std::thread consumer([&] {
        for (int r = 1; r <= kRounds; ++r) {
            while (!ready.load(std::memory_order_acquire)) {}   // 3. subscribe
            // 4. Everything written before the release-store is now visible.
            const Message& m = mailbox;
            if (m.payload[0] + m.payload[1] + m.payload[2] != m.payload[3])
                ++checksum_errors;
            ready.store(false, std::memory_order_release);      // hand it back
        }
    });

    producer.join();
    consumer.join();
    std::printf("rounds=%d checksum errors=%lld  %s\n", kRounds, checksum_errors,
                checksum_errors == 0 ? "PASS" : "FAIL");
}
```

```text
rounds=200000 checksum errors=0  PASS
```

Now the cautionary half. Change both orderings to `memory_order_relaxed` and the program becomes wrong: **relaxed** guarantees only that each individual atomic operation is indivisible and that operations on *that one variable* have a consistent order. It orders nothing else. The consumer could see `ready == true` while the payload writes are still sitting in the producer core's store buffer, and would read stale rows off a page the sticky note falsely vouched for; since the payload accesses are then unordered plain accesses, the program has a data race, and we are back in undefined behavior. Run the relaxed version on an x86 machine and it will very likely still print PASS, because x86 hardware happens to keep stores in order; the same binary logic on ARM (your phone, a Mac, most embedded boards) can fail for real. "Passes on my machine" is not a memory-model argument, and this asymmetry between x86 and ARM is the classic source of ports that "worked for years" and then did not.

Where relaxed *is* correct: counters and statistics where only the final total matters and no other data hinges on the counter's value, like the event counter of a telemetry system. `fetch_add(1, relaxed)` is still indivisible, so no increments are lost; you simply must not treat the value as evidence that something else has happened. Reading the total after `join()` is safe because join itself establishes happens-before.

### The guidance ladder

Condensed into policy, this is how working engineers choose orderings:

1. **Default to `seq_cst`.** Correct first. It is also self-documenting: it says "I have not proven anything weaker safe."
2. **Use acquire/release for handoff patterns** (flags, queue indices, publish-subscribe of a payload), once you can draw the happens-before diagram for your code the way we just did. This is the workhorse weakening, and often all the performance there is to get.
3. **Use `relaxed` only for pure counters**, with a comment stating why no ordering is needed. An uncommented `relaxed` should fail your code review.
4. **Never use `memory_order_consume`.** It was designed for a real optimization (ordering only through pointer dependencies), but it turned out to be unimplementable as specified; every major compiler silently strengthens it to `acquire`, and the standards committee itself discourages it. Knowing *why* you never use it is a nice interview flourish; using it is not.

One paragraph on **fences**, for completeness: `std::atomic_thread_fence(memory_order_release)` and its acquire twin impose ordering without being attached to a particular variable, letting several relaxed operations share one ordering point. They are occasionally the right tool deep inside lock-free libraries and almost never in application code; everything in this chapter, including the Build it, is expressible with orderings on the operations themselves, which are easier to review because the ordering sits next to the data it protects.

## False sharing: two accountants, one page

Here is a performance trap that involves no race, no bug, and no shared variable, only shared *geometry*. Recall from [29.3](29.3-allocators-arenas-cache.md) that the hardware moves memory in 64-byte cache lines, and that a core must own a line exclusively to write to it. Now put two independent atomic counters next to each other in one struct: they share a line. Two threads, each hammering its *own* counter, are nevertheless fighting over the line, which ping-pongs between the cores on every write. The accountants write on different rows, but the rows are on one page, and they keep snatching the page out of each other's hands. The fix is `alignas(64)` from 29.3: give each counter its own line.

```cpp
#include <atomic>
#include <chrono>
#include <cstdio>
#include <thread>

constexpr long kOps = 20000000;   // per thread

struct SharedLine {               // both counters on ONE cache line
    std::atomic<long> a{0};
    std::atomic<long> b{0};
};

struct PaddedPair {               // one cache line EACH
    alignas(64) std::atomic<long> a{0};
    alignas(64) std::atomic<long> b{0};
};

template <class Pair>
double bench(Pair& p) {
    auto t0 = std::chrono::steady_clock::now();
    std::thread t1([&] { for (long i = 0; i < kOps; ++i)
                             p.a.fetch_add(1, std::memory_order_relaxed); });
    std::thread t2([&] { for (long i = 0; i < kOps; ++i)
                             p.b.fetch_add(1, std::memory_order_relaxed); });
    t1.join(); t2.join();
    auto t1c = std::chrono::steady_clock::now();
    return std::chrono::duration<double, std::milli>(t1c - t0).count();
}

int main() {
    SharedLine shared;
    PaddedPair padded;
    std::printf("sizeof(SharedLine)=%zu  sizeof(PaddedPair)=%zu\n",
                sizeof(SharedLine), sizeof(PaddedPair));
    double shared_ms = bench(shared);
    double padded_ms = bench(padded);
    bool totals_ok = shared.a.load() == kOps && shared.b.load() == kOps &&
                     padded.a.load() == kOps && padded.b.load() == kOps;
    std::printf("totals correct in both versions: %s\n", totals_ok ? "yes" : "NO");
    std::printf("same line: %.0f ms   padded: %.0f ms   ratio: %.1fx\n",
                shared_ms, padded_ms, shared_ms / padded_ms);
}
```

```text
sizeof(SharedLine)=16  sizeof(PaddedPair)=128
totals correct in both versions: yes
same line: 473 ms   padded: 111 ms   ratio: 4.3x    <- times and ratio vary by machine
```

Both versions compute identical answers; one is four times slower, and no profiler line will say "false sharing," just mysteriously hot increments. The `relaxed` orderings here are the guidance ladder's rule 3 in action (pure counters, comment in the code), so the entire 4x is cache-line traffic. This is why the SPSC ring buffer below pads its head and tail indices apart, and it is the standard trick for any per-thread statistics array.

## Tools and the guardian discipline

You cannot test your way out of data races: they depend on timing you do not control, and undefined behavior may look correct for years. Two disciplines compensate.

The first is mechanical: **ThreadSanitizer** (TSan), sibling of the AddressSanitizer you met in [29.3](29.3-allocators-arenas-cache.md). It instruments every memory access and every synchronization operation, tracks the happens-before relation at runtime, and reports any pair of unordered conflicting accesses, *even when the race did not misbehave on this run*. That last property is what testing alone cannot give you, and races are invisible to ASan, which checks where you touched memory, not when. Compile and run:

```text
g++ -std=c++17 -Wall -pthread -g -fsanitize=thread race.cpp -o race_tsan
./race_tsan
```

Representative output (trimmed; from the racing-counter program earlier):

```text
==================
WARNING: ThreadSanitizer: data race (pid=7754)
  Read of size 4 at 0x55579d6c001c by thread T2:
    #0 hammer() race.cpp:7
    ...
  Previous write of size 4 at 0x55579d6c001c by thread T1:
    #0 hammer() race.cpp:7
    ...
  Location is global 'counter' of size 4 at 0x55579d6c001c
SUMMARY: ThreadSanitizer: data race race.cpp:7 in hammer()
==================
```

Both accesses with stack traces, the variable by name, and the verdict. TSan costs roughly 5-15x in speed and several times in memory, so it is a CI-and-debug tool, not a production flag, and it can only flag races on code paths your test actually executed, so it pairs with stress tests like the one in Build it. (Running our SPSC ring under TSan reports nothing, which is meaningful evidence precisely because the stress test drives millions of handoffs through it.) If you cannot use sanitizers, valgrind's **helgrind** tool does a slower, unrecompiled version of the same job. TSan availability varies by platform and compiler build; on mainstream Linux gcc/clang it is a flag away.

The second discipline is organizational, and it is the one 29.4's plant code lives by: **every shared variable has a named guardian**, exactly one, chosen from three options: a specific mutex, an atomic protocol you can draw the happens-before diagram for, or confinement to a single thread. And the guardian is written down where the variable is declared:

```cpp
// FRAGMENT: the documentation habit, not a runnable program.
std::mutex recipe_mutex;
RecipeTable recipes;          // guardian: recipe_mutex
std::atomic<uint64_t> ticks;  // guardian: atomic; relaxed OK, total-only counter
SensorFilter filter_state;    // guardian: control thread only, never touched elsewhere
```

A reviewer who finds a shared variable without a guardian comment has found a bug, whether or not it has fired yet. This rule sounds bureaucratic and costs one comment per variable; it is the cheapest concurrency tool in this chapter.

## Build it: a lock-free SPSC ring buffer

Now we build the structure this chapter has been aiming at. Chapter [29.4](29.4-industrial-embedded-cpp.md)'s telemetry ring buffered records inside one thread; the moment a real logger thread drains it while the control loop fills it, it needs a concurrency protocol, and a mutex is the wrong one: the control loop must never wait on a lock the logger might be holding (priority inversion, unbounded worst case, every sin in 29.4's ledger). What we want is a **single-producer single-consumer (SPSC) ring buffer**: lock-free, wait-free on both sides in the common case, and, uniquely among lock-free structures, simple enough to write and *prove* by hand.

The design rests on one idea: **every variable has a single writer.**

- `head_` counts records ever pushed. Written only by the producer, read by both.
- `tail_` counts records ever popped. Written only by the consumer, read by both.
- Slot `i` of the array is written by the producer before it publishes `i` via `head_`, and read by the consumer only for `i` in `[tail_, head_)`.

Because no variable has two writers, there are no read-modify-write races to make atomic and no CAS loops; each index needs only a plain atomic store by its owner and an ordered load by the other side. The indices increase forever and are mapped into the array with `index & (N - 1)`, which is why the capacity must be a power of two, enforced at compile time with the `static_assert` technique from [29.6](29.6-templates-and-compile-time-cpp.md). The buffer is full when `head_ - tail_ == N`, empty when they are equal; unsigned wraparound keeps the subtraction correct even after `size_t` overflows (exercise 5 computes how long that takes; bring a calendar).

The memory orderings are the message-passing pattern, twice. The producer writes the slot (plain data), then release-stores `head_`: the sticky note that publishes the record. The consumer acquire-loads `head_`, which synchronizes with that store, so the slot contents are visible before it reads them. Symmetrically, the consumer's release-store of `tail_` publishes "this slot is free again," and the producer's acquire-load of `tail_` subscribes before overwriting the slot. Each side loads its *own* index relaxed, because reading a variable only you write needs no ordering.

The full implementation, the mutex+cv queue as a baseline, a stress test that pushes five million sequenced records through it, and a head-to-head throughput measurement:

```cpp
#include <atomic>
#include <chrono>
#include <condition_variable>
#include <cstddef>
#include <cstdint>
#include <cstdio>
#include <mutex>
#include <queue>
#include <thread>
#include <type_traits>

// ---------------------------------------------------------------------------
// The record we ship. Trivially copyable, so a plain assignment moves it.
// ---------------------------------------------------------------------------
struct TelemetryRecord {
    uint64_t seq;        // sequence number, the consumer checks these
    float    pressure;
    float    temperature;
};
static_assert(std::is_trivially_copyable<TelemetryRecord>::value,
              "records must be raw-copyable: no pointers, no owners");

// ---------------------------------------------------------------------------
// Single-producer single-consumer lock-free ring buffer.
// Ownership protocol (this comment is the design):
//   head_ : written ONLY by the producer, read by both.
//   tail_ : written ONLY by the consumer, read by both.
//   buf_[i % N] : written by the producer before it publishes i via head_,
//                 read by the consumer only for slots in [tail_, head_).
// Indices increase forever; the & mask maps them into the array.
// ---------------------------------------------------------------------------
template <typename T, size_t N>
class SpscRing {
    static_assert((N & (N - 1)) == 0 && N != 0, "capacity must be a power of two");
    static_assert(std::is_trivially_copyable<T>::value,
                  "SpscRing is for plain data records");

public:
    // Called by the producer thread only. Returns false if full (never blocks).
    bool try_push(const T& item) {
        const size_t head = head_.load(std::memory_order_relaxed);  // our own var
        const size_t tail = tail_.load(std::memory_order_acquire);  // consumer's
        if (head - tail == N) return false;                         // full
        buf_[head & (N - 1)] = item;             // 1. write the slot...
        head_.store(head + 1, std::memory_order_release);  // 2. ...then publish
        return true;
    }

    // Called by the consumer thread only. Returns false if empty (never blocks).
    bool try_pop(T& out) {
        const size_t tail = tail_.load(std::memory_order_relaxed);  // our own var
        const size_t head = head_.load(std::memory_order_acquire);  // producer's
        if (head == tail) return false;                             // empty
        out = buf_[tail & (N - 1)];              // 1. read the slot...
        tail_.store(tail + 1, std::memory_order_release);  // 2. ...then release it
        return true;
    }

    // Approximate size, safe to call from either thread (for monitoring).
    size_t size() const {
        return head_.load(std::memory_order_relaxed) -
               tail_.load(std::memory_order_relaxed);
    }

private:
    alignas(64) std::atomic<size_t> head_{0};   // own cache line (29.3)
    alignas(64) std::atomic<size_t> tail_{0};   // own cache line
    alignas(64) T buf_[N];
};

// ---------------------------------------------------------------------------
// The baseline to beat: the bounded mutex+cv queue from earlier.
// ---------------------------------------------------------------------------
class MutexQueue {
public:
    explicit MutexQueue(size_t cap) : cap_(cap) {}
    void push(const TelemetryRecord& r) {
        std::unique_lock<std::mutex> lock(m_);
        not_full_.wait(lock, [&] { return q_.size() < cap_; });
        q_.push(r);
        not_empty_.notify_one();
    }
    TelemetryRecord pop() {
        std::unique_lock<std::mutex> lock(m_);
        not_empty_.wait(lock, [&] { return !q_.empty(); });
        TelemetryRecord r = q_.front();
        q_.pop();
        not_full_.notify_one();
        return r;
    }
private:
    std::mutex m_;
    std::condition_variable not_full_, not_empty_;
    std::queue<TelemetryRecord> q_;
    size_t cap_;
};

constexpr uint64_t kRecords = 5000000;

int main() {
    // ---- stress test + timing: SPSC ring -------------------------------
    static SpscRing<TelemetryRecord, 1024> ring;
    uint64_t gaps = 0, received = 0;

    auto t0 = std::chrono::steady_clock::now();
    std::thread producer([&] {
        for (uint64_t s = 0; s < kRecords; ++s) {
            TelemetryRecord r{s, 1.0f * (s & 255), 25.0f};
            while (!ring.try_push(r)) {}         // retry until space (test only)
        }
    });
    std::thread consumer([&] {
        TelemetryRecord r;
        uint64_t expect = 0;
        while (received < kRecords) {
            if (ring.try_pop(r)) {
                if (r.seq != expect) ++gaps;
                expect = r.seq + 1;
                ++received;
            }
        }
    });
    producer.join();
    consumer.join();
    auto t1 = std::chrono::steady_clock::now();
    double ring_s = std::chrono::duration<double>(t1 - t0).count();

    std::printf("SPSC ring : received=%llu gaps=%llu  %s\n",
                (unsigned long long)received, (unsigned long long)gaps,
                (received == kRecords && gaps == 0) ? "PASS" : "FAIL");

    // ---- same job through the mutex+cv queue ---------------------------
    MutexQueue mq(1024);
    uint64_t mq_gaps = 0;
    t0 = std::chrono::steady_clock::now();
    std::thread mproducer([&] {
        for (uint64_t s = 0; s < kRecords; ++s)
            mq.push({s, 1.0f * (s & 255), 25.0f});
    });
    std::thread mconsumer([&] {
        uint64_t expect = 0;
        for (uint64_t s = 0; s < kRecords; ++s) {
            TelemetryRecord r = mq.pop();
            if (r.seq != expect) ++mq_gaps;
            expect = r.seq + 1;
        }
    });
    mproducer.join();
    mconsumer.join();
    t1 = std::chrono::steady_clock::now();
    double mq_s = std::chrono::duration<double>(t1 - t0).count();

    std::printf("mutex+cv  : received=%llu gaps=%llu  %s\n",
                (unsigned long long)kRecords, (unsigned long long)mq_gaps,
                (mq_gaps == 0) ? "PASS" : "FAIL");
    std::printf("throughput: ring %.1f M rec/s, mutex+cv %.1f M rec/s, ratio %.1fx\n",
                kRecords / ring_s / 1e6, kRecords / mq_s / 1e6, mq_s / ring_s);
}
```

```text
SPSC ring : received=5000000 gaps=0  PASS
mutex+cv  : received=5000000 gaps=0  PASS
throughput: ring 39.3 M rec/s, mutex+cv 5.1 M rec/s, ratio 7.7x   <- rates vary; the
                                                                     ratio was 4-8x
                                                                     across runs here
```

Five million records, every sequence number in order, zero losses, on both implementations; the lock-free ring moved them several times faster, tens of millions of records per second on a modest two-core machine. The stress test is doing real verification work: any ordering bug in the ring (say, storing `head_` before writing the slot, or demoting the acquires to relaxed) shows up as a consumer reading a stale or half-written record, which the strict sequence check converts into a loud `gaps != 0`. Try breaking it exactly those two ways and re-running, ideally under TSan, which flags the broken variants and stays silent on this one.

Why is SPSC the one lock-free structure a normal engineer should write, while anything multi-producer or multi-consumer belongs to a library (Boost.Lockfree, moodycamel, folly)? Because the single-writer rule is what made the proof fit in your head. Every claim we made reduced to one release/acquire pair per index, and you can draw both happens-before diagrams on a napkin. The moment two producers exist, they race to claim the same slot, which forces CAS loops on the indices; then a slot can be claimed but not yet written when a consumer arrives, so you need per-slot sequence numbers; then a slow producer can wrap around behind a fast one and a stale index can match a recycled slot, the **ABA problem**; and reclaiming memory that another thread might still be reading becomes its own research area (hazard pointers, epochs). Each complication is solvable, and library authors have solved them, with years of review and testing on many architectures. The working engineer's version of lock-free skill is knowing the SPSC pattern cold, and knowing to reach for a library one step beyond it.

## Mini-project: a telemetry pipeline with a watchdog

Time to assemble the chapter into the shape it will take in [29.4](29.4-industrial-embedded-cpp.md)'s world: a control thread that must never be delayed, a logger that drains its telemetry, and a watchdog keeping an eye on both. This is the architecture of real equipment software, compressed to one file you can put on GitHub.

The cast, and every shared variable's guardian:

- **Control thread** (producer): simulates a 1 kHz control loop pushing samples into the SPSC ring. Its policy is the one 29.4 demanded: `try_push`, and on failure *drop the sample and count it*. It never waits for the logger, because a delayed valve command costs a wafer and a lost log line costs nothing.
- **Logger thread** (consumer): drains the ring into its running totals, checking sequence numbers. Mid-run we make it stall, the way real sinks do (a disk hiccup, a network burp), to demonstrate the drop policy firing.
- **Watchdog thread**: 29.4's pattern, one level up: it watches heartbeat atomics and flags a logger that stops making progress while work is waiting.

To keep the run short and the output stable, each loop iteration stands for one 1 kHz tick, and instead of sleeping 1 ms per tick the control thread waits for queue headroom during healthy phases, compressing minutes of plant time into a fraction of a second while preserving the producer/consumer speed relationship. The stall is engineered so the arithmetic is exact: the ring (capacity 1024) is drained empty, the logger stops, and the control thread pushes a 4096-sample burst, so exactly 4096 - 1024 = 3072 samples must be dropped, then production resumes so the logger sees the sequence gap.

```cpp
#include <atomic>
#include <chrono>
#include <cstddef>
#include <cstdint>
#include <cstdio>
#include <thread>
#include <type_traits>

// ---- the ring from Build it, trimmed to what the pipeline needs ----------
template <typename T, size_t N>
class SpscRing {
    static_assert((N & (N - 1)) == 0 && N != 0, "capacity must be a power of two");
    static_assert(std::is_trivially_copyable<T>::value, "plain data only");
public:
    bool try_push(const T& item) {
        const size_t head = head_.load(std::memory_order_relaxed);
        const size_t tail = tail_.load(std::memory_order_acquire);
        if (head - tail == N) return false;
        buf_[head & (N - 1)] = item;
        head_.store(head + 1, std::memory_order_release);
        return true;
    }
    bool try_pop(T& out) {
        const size_t tail = tail_.load(std::memory_order_relaxed);
        const size_t head = head_.load(std::memory_order_acquire);
        if (head == tail) return false;
        out = buf_[tail & (N - 1)];
        tail_.store(tail + 1, std::memory_order_release);
        return true;
    }
    size_t size() const {
        return head_.load(std::memory_order_relaxed) -
               tail_.load(std::memory_order_relaxed);
    }
private:
    alignas(64) std::atomic<size_t> head_{0};
    alignas(64) std::atomic<size_t> tail_{0};
    alignas(64) T buf_[N];
};

struct Sample {
    uint64_t seq;
    float    pressure;
};

constexpr size_t   kCap          = 1024;
constexpr uint64_t kPhase1Ticks  = 200000;  // healthy operation
constexpr uint64_t kBurstTicks   = 4096;    // pushed while the logger is stalled
constexpr uint64_t kPhase3Ticks  = 2048;    // healthy again, after the stall
constexpr size_t   kPacingDepth  = 768;     // stand-in for real-time headroom

SpscRing<Sample, kCap> ring;

// Shared state. Guardian noted for every variable, 29.4-style:
std::atomic<uint64_t> control_heartbeat{0};  // atomic: written by control only
std::atomic<uint64_t> logger_heartbeat{0};   // atomic: written by logger only
std::atomic<bool>     logger_stalled{false}; // atomic: written by control only
std::atomic<bool>     stall_ack{false};      // atomic: written by logger only
std::atomic<bool>     done{false};           // atomic: written by control only

int main() {
    // ---- results, each written by exactly one thread, read after join ----
    uint64_t produced = 0, dropped = 0, consumed = 0, missing = 0;
    size_t   max_depth = 0;
    bool     order_ok = true, stall_detected = false;
    double   max_push_us = 0.0;

    std::thread control([&] {
        uint64_t seq = 0;
        // Phase 1: healthy. Each iteration stands for one 1 kHz tick; instead
        // of sleeping 1 ms we wait for headroom, which compresses 200 s of
        // plant time into a fraction of a second while keeping the ratio of
        // producer to consumer speed realistic.
        for (uint64_t t = 0; t < kPhase1Ticks; ++t) {
            while (ring.size() >= kPacingDepth) {}   // simulation pacing only
            Sample s{seq++, 3.5f};
            auto p0 = std::chrono::steady_clock::now();
            bool ok = ring.try_push(s);              // the real control policy:
            auto p1 = std::chrono::steady_clock::now();
            ++produced;
            if (!ok) ++dropped;                      //   push or drop, NEVER wait
            double us = std::chrono::duration<double, std::micro>(p1 - p0).count();
            if (us > max_push_us) max_push_us = us;
            if (ring.size() > max_depth) max_depth = ring.size();
            control_heartbeat.fetch_add(1, std::memory_order_relaxed);
        }

        // Let the logger fully catch up, so the stall experiment starts clean.
        while (ring.size() != 0) {}

        // Phase 2: the logger stalls (disk hiccup, GC pause in the UI process,
        // a helpful intern attaching a debugger). The control loop does not
        // care: it keeps its schedule and drops.
        logger_stalled.store(true);
        while (!stall_ack.load()) {}                 // logger confirms it stopped
        for (uint64_t t = 0; t < kBurstTicks; ++t) {
            Sample s{seq++, 3.5f};
            ++produced;
            if (!ring.try_push(s)) ++dropped;
            if (ring.size() > max_depth) max_depth = ring.size();
            control_heartbeat.fetch_add(1, std::memory_order_relaxed);
        }
        std::this_thread::sleep_for(std::chrono::milliseconds(60));  // hold the
        logger_stalled.store(false);                 // stall so the watchdog sees it

        // Phase 3: healthy again. The consumer will now see the gap the
        // dropped samples left in the sequence numbers.
        for (uint64_t t = 0; t < kPhase3Ticks; ++t) {
            while (ring.size() >= kPacingDepth) {}
            Sample s{seq++, 3.5f};
            ++produced;
            if (!ring.try_push(s)) ++dropped;
            control_heartbeat.fetch_add(1, std::memory_order_relaxed);
        }
        done.store(true);
    });

    std::thread logger([&] {
        Sample s;
        uint64_t expect = 0;
        for (;;) {
            if (logger_stalled.load()) {             // simulate the stalled sink
                stall_ack.store(true);
                std::this_thread::sleep_for(std::chrono::milliseconds(1));
                continue;
            }
            if (ring.try_pop(s)) {
                if (s.seq < expect) order_ok = false;    // must move forward
                missing += s.seq - expect;               // gaps = dropped samples
                expect = s.seq + 1;
                ++consumed;
                logger_heartbeat.fetch_add(1, std::memory_order_relaxed);
            } else if (done.load()) {
                return;                              // producer finished, ring empty
            }
        }
    });

    std::thread watchdog([&] {
        uint64_t last_logger = 0;
        while (!done.load()) {
            std::this_thread::sleep_for(std::chrono::milliseconds(10));
            uint64_t now_logger = logger_heartbeat.load(std::memory_order_relaxed);
            if (now_logger == last_logger && ring.size() > 0)
                stall_detected = true;               // work waiting, no progress
            last_logger = now_logger;
        }
    });

    control.join();
    logger.join();
    watchdog.join();

    std::printf("samples produced : %llu\n", (unsigned long long)produced);
    std::printf("samples consumed : %llu\n", (unsigned long long)consumed);
    std::printf("samples dropped  : %llu\n", (unsigned long long)dropped);
    std::printf("max queue depth  : %zu of %zu\n", max_depth, kCap);
    std::printf("produced == consumed + dropped : %s\n",
                produced == consumed + dropped ? "PASS" : "FAIL");
    std::printf("sequence gaps == dropped       : %s\n",
                missing == dropped && order_ok ? "PASS" : "FAIL");
    std::printf("watchdog saw the stall         : %s\n",
                stall_detected ? "yes" : "NO");
    std::printf("max push latency : %.2f us (varies run to run)\n", max_push_us);
}
```

```text
samples produced : 206144
samples consumed : 203072
samples dropped  : 3072
max queue depth  : 1024 of 1024
produced == consumed + dropped : PASS
sequence gaps == dropped       : PASS
watchdog saw the stall         : yes
max push latency : 73.89 us (varies run to run)
```

Walk through what the numbers prove. 206,144 samples were generated (200,000 + 4,096 + 2,048); exactly 3,072 were dropped, precisely the burst overflow we engineered, and the conservation law `produced == consumed + dropped` closes the books, our two accountants' totals reconciling to the cent. The logger's sequence check found gaps summing to exactly the drop count and never saw time run backwards, so nothing was duplicated, reordered, or silently lost: every missing record is one the control thread *chose* to drop, on its own schedule, in nanoseconds. The queue hit its exact capacity during the stall and never lost the control thread a single tick, and the watchdog independently noticed the logger's frozen heartbeat. The max push latency line is the one honest "varies" in the report: it is dominated by OS scheduling noise on an ordinary machine, which is 29.4's argument for real-time operating systems replayed in one number.

Extensions that would make this a stronger portfolio piece: replace the in-memory store with a file writer on the logger side and show the drop counter absorbing disk stalls; add a second SPSC ring carrying commands *to* the control thread; run the whole thing under TSan in CI; port the Sample struct to the `TelemetryRecord` of 29.4's controller and graft this pipeline onto it, which is exactly the upgrade that chapter's single-threaded ring was waiting for.

## Common mistakes

1. **"It's just a bool" synchronization.** A plain `bool` flag shared between threads is a data race, and the hoisted-loop example showed the compiler legally turning your polling loop into an infinite one. Any shared flag is `std::atomic<bool>` at minimum; if data rides behind it, the flag needs release/acquire semantics too.
2. **`volatile` as a substitute for atomic.** `volatile` forces the compiler to perform each access but provides no atomicity and no inter-thread ordering. It is for hardware registers ([29.4](29.4-industrial-embedded-cpp.md)); using it for threads produces code that fails rarely, unreproducibly, and only in the field.
3. **Holding a lock across slow work.** A mutex held during file I/O, a network call, or a big computation turns every other thread that needs it into a queue behind your disk. Copy what you need under the lock, release it, then do the slow thing. Lock scope should cover the shared-state touch, nothing more.
4. **`condition_variable` without a predicate.** Spurious wakeups are allowed, and a notification can be stale before the sleeper runs. `cv.wait(lock)` with an `if` check is a bug that passes tests; always use the predicate overload, which re-checks in a loop.
5. **Detaching threads.** A detached thread cannot be joined, so shutdown becomes a race against its access to dying objects. Give every thread an owner that joins it; if you think you want `detach`, you usually want a properly joined worker with a stop flag.
6. **Atomic pieces without an atomic protocol.** Two atomics do not compose into one atomic action: `if (count.load() < limit) count.fetch_add(1)` overshoots the limit under contention, because the check and the act are separate steps (that is why the permit example needed CAS). Audit for check-then-act sequences; each one needs a CAS loop, a mutex, or a redesign.
7. **False sharing.** Independent hot counters packed into one cache line cost 4x in our measurement with zero correctness symptoms. Pad per-thread hot data with `alignas(64)` ([29.3](29.3-allocators-arenas-cache.md)), and be suspicious when adding threads makes throughput worse.
8. **Weakening memory order by vibes.** `relaxed` sprinkled for speed, without a drawn happens-before argument, is how message-passing bugs are born, and x86 will hide them until the ARM port. Follow the ladder: `seq_cst` by default, acquire/release for handoffs you have diagrammed, `relaxed` only with a justifying comment.

## On the job / interview angle

**Where this lives at work.** The SPSC ring plus drop-counter pattern is close to universal in equipment software of the [29.4](29.4-industrial-embedded-cpp.md) kind: a hard-real-time producer, a soft-real-time consumer, and a policy that protects the producer's schedule at the log's expense. The same shape appears in audio (the render callback feeding a file writer), trading systems (market data thread feeding strategy threads), robotics, and game engines. Being able to say "single writer per variable, release publishes, acquire subscribes, and here is the stress test and the TSan run" is a working credential in all of them.

**What interviews probe.** Concurrency questions sort candidates into tiers quickly. Tier one is API fluency: mutex vs atomic, why `lock_guard`, the predicate loop. Tier two is the classic scenarios: produce the deadlock and fix it with lock ordering or `scoped_lock`; spot the check-then-act bug on two atomics. The senior tier is the memory model, and it is asked more often than people expect, in forms like "what does `memory_order_acquire` actually guarantee?", "why is a data race UB rather than just a stale read?", or "implement an SPSC queue and justify every ordering," which is this chapter's Build it verbatim. Candidates who can draw the happens-before diagram and who volunteer the honest caveat ("this passes on x86 even when it is wrong; that is why I would run it under TSan and reason from the model, not the test") stand out immediately. It is also fine, and respected, to say "beyond SPSC I use a library"; claiming you would write an MPMC queue from scratch is the wrong kind of confidence.

**The discipline transfers up the stack.** Even in Python and Go day jobs, the guardian rule (every shared variable has exactly one named protector) and the drop-policy mindset (decide *in advance* what loses when a consumer stalls) are the habits reviewers notice. The C++ memory model is just the place where you learn them with the safety net removed.

## Exercises

1. **Guardian audit.** A controller has: (a) a `std::deque<Command>` filled by a network thread and drained by the control thread; (b) a `uint64_t` count of loop iterations, read once per minute by a stats thread; (c) a 400-byte calibration table written once at startup before threads launch, read by everyone; (d) a `double` "latest temperature" written by the control thread at 1 kHz and read by a UI thread at 10 Hz. Assign each variable a guardian (specific mutex, atomic protocol, or single-thread confinement) and justify each in one sentence.

2. **The lost wakeup.** A colleague replaces `not_empty_.wait(lock, [&]{ return !q_.empty(); });` with `if (q_.empty()) not_empty_.wait(lock);` and their consumer occasionally pops from an empty queue or sleeps forever. Explain both failure modes and why the predicate form fixes them.

3. **Build a spinlock.** Implement a `SpinLock` class on `std::atomic_flag` with `lock()`/`unlock()`, choosing the memory orderings and defending them, then prove it with the two-thread million-increment test. When is a spinlock a reasonable choice over `std::mutex`, and when is it clearly worse?

4. **Relaxed, but right.** Rewrite the atomic counter using `memory_order_relaxed` everywhere and argue precisely why the final printed total is still guaranteed to be 2,000,000. Your argument must name the two separate guarantees involved.

5. **Wraparound math.** The SPSC ring's `size_t` indices increase forever. At the measured 39 million records per second, compute how long until `head_` wraps a 64-bit counter, and show why `head_ - tail_` still yields the correct occupancy at the moment of wraparound. Would the scheme survive 32-bit indices on that machine?

6. **Why not overwrite-oldest?** 29.4's single-threaded telemetry ring overwrites its oldest record when full, but our SPSC ring refuses the newest instead. Explain why overwrite-oldest is fundamentally at odds with the lock-free SPSC design. Name the invariant it would break.

7. **Deadlock geometry.** Threads T1, T2, T3 lock mutex pairs (A then B), (B then C), (C then A) respectively. Show a schedule that deadlocks all three, state the general condition for deadlock it illustrates, and give two distinct fixes.

### Solutions

**1.** (a) The deque gets a dedicated `std::mutex` (plus a condition variable if the control thread may sleep on it, or better, in this book's domain, replace it with the SPSC ring so the control thread never blocks): two threads, structural mutations, no atomic can cover a deque. (b) `std::atomic<uint64_t>` incremented with `relaxed`: it is a pure total-only counter, and the stats thread needs no ordering with any other data. (c) Single-thread confinement in time: written before `std::thread` construction, then treated as immutable; thread creation itself establishes happens-before, so no runtime guardian is needed, only a comment saying "const after startup." (d) `std::atomic<double>` (8 bytes, lock-free on mainstream 64-bit targets, worth a `static_assert(std::atomic<double>::is_always_lock_free)`); a mutex would risk the UI thread delaying the control thread, the one thing 29.4 forbids.

**2.** Failure one, the spurious wakeup: the OS may wake the waiter with no notification; the `if` has already been passed, so the code proceeds to pop from a still-empty queue. Failure two, the stale notification: consumer C1 is notified, but consumer C2 acquires the mutex first and empties the queue; C1 then wakes from `wait`, and with only an `if`, pops from nothing (a third variant sleeps forever when a notify fires in the gap before waiting begins with the state already changed back). The predicate overload re-evaluates the condition after *every* wakeup, under the mutex, and returns only when it is true, so no wakeup, spurious or stale, is ever trusted without re-checking the books.

**3.**

```cpp
#include <atomic>
#include <cstdio>
#include <thread>

class SpinLock {
public:
    void lock() {
        // test_and_set returns the OLD value: true means someone else holds it.
        while (flag_.test_and_set(std::memory_order_acquire)) {}
    }
    void unlock() { flag_.clear(std::memory_order_release); }
private:
    std::atomic_flag flag_ = ATOMIC_FLAG_INIT;
};

SpinLock spin;
long counter = 0;   // guardian: spin

int main() {
    auto work = [] {
        for (int i = 0; i < 1000000; ++i) {
            spin.lock();
            ++counter;
            spin.unlock();
        }
    };
    std::thread t1(work), t2(work);
    t1.join(); t2.join();
    std::printf("counter=%ld (must be 2000000)\n", counter);
}
```

```text
counter=2000000 (must be 2000000)
```

The orderings are the mutex contract rebuilt from parts: `acquire` on the successful `test_and_set` ensures nothing in the critical section floats above the lock, and `release` on `clear` ensures everything done inside is published before the next owner's acquire, giving the same happens-before chain a `std::mutex` provides. Reasonable when critical sections are tens of nanoseconds and threads are pinned to separate cores (kernels and real-time systems do this); clearly worse whenever a holder can be preempted, because waiters then burn their entire timeslice spinning against a lock that cannot be released, where `std::mutex` would have slept them.

**4.**

```cpp
#include <atomic>
#include <cstdio>
#include <thread>

std::atomic<long> events{0};

int main() {
    auto work = [] {
        for (int i = 0; i < 1000000; ++i)
            events.fetch_add(1, std::memory_order_relaxed);  // total is all we need
    };
    std::thread t1(work), t2(work);
    t1.join();   // join synchronizes: everything each thread did is visible now
    t2.join();
    std::printf("events=%ld (must be 2000000)\n", events.load());
}
```

Guarantee one: even relaxed, every `fetch_add` is an indivisible read-modify-write, and all modifications of a single atomic variable form one total modification order, so no increment can be lost; 2,000,000 increments yield 2,000,000. Guarantee two: `join()` establishes happens-before between everything each thread did and everything `main` does afterward, so the final `load` is ordered after all increments and must observe the completed total. Relaxed only surrendered *cross-variable* ordering, which this program never needed.

**5.** A 64-bit counter wraps after 2^64 ≈ 1.8 x 10^19 pushes. At 3.9 x 10^7 per second, that is 1.8 x 10^19 / 3.9 x 10^7 ≈ 4.7 x 10^11 seconds; a year is about 3.15 x 10^7 seconds, so roughly 1.5 x 10^4 years, order of ten thousand years of continuous full-rate pushing. Correctness at the wrap: unsigned arithmetic is modulo 2^64, so with `head_ = 3` (post-wrap) and `tail_ = 2^64 - 5`, the difference `head_ - tail_` computes 3 - (2^64 - 5) mod 2^64 = 8, the true occupancy, and the invariant `0 <= head_ - tail_ <= N` holds throughout because the producer and consumer only ever advance. With 32-bit indices the same modular argument still holds mathematically (occupancy stays correct across wraps), but the margin for *bugs elsewhere* shrinks and the wrap now arrives every 2^32 / 3.9 x 10^7 ≈ 110 seconds, so any latent assumption that indices only grow gets exercised constantly; 64-bit indices cost nothing here and make the wrap a non-event you compute rather than test.

**6.** Overwrite-oldest means the *producer* discards the record at `tail_`, which is an advance of `tail_` by the producer. That breaks the single-writer invariant, the load-bearing wall of the whole design: `tail_` would now have two writers (producer overwriting, consumer popping), turning every `tail_` update into a race that plain stores cannot resolve. You would need CAS on `tail_`, plus a protocol for the moment the consumer is mid-copy out of the very slot being overwritten, and the tractable napkin proof is gone. 29.4's ring could overwrite the oldest precisely because one thread did everything. With two threads, "refuse the newest and count it" preserves the proof, and the mini-project showed it also serves the domain: the producer keeps its schedule and the books still balance.

**7.** Schedule: T1 locks A, T2 locks B, T3 locks C (all succeed); then T1 waits for B (held by T2), T2 waits for C (held by T3), T3 waits for A (held by T1). Each thread holds one resource while waiting for another, and the waits-for edges T1 -> T2 -> T3 -> T1 form a cycle, the general deadlock condition (circular wait among hold-and-wait threads). Fix one, global lock ordering: impose the order A < B < C and require every thread to acquire in ascending order; T3 must then take A before C, so some thread can always complete, and no cycle can form. Fix two, all-or-nothing acquisition: each thread takes both mutexes in a single `std::scoped_lock(x, y)`, whose deadlock-avoidance algorithm never holds one lock while blocking indefinitely on another, which removes the hold-and-wait ingredient. (A third accepted answer: restructure so each pair is guarded by one mutex, removing multi-lock acquisition entirely.)
