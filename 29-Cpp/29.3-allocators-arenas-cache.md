# Chapter 29.3 - Allocators, Arenas, and the Cache

> _Goal: understand what `malloc` and `new` actually do, and why a general-purpose allocator is slow and unpredictable by design. Learn what alignment is and why it matters, then measure cache effects for real with two benchmarks you can run yourself. Build a working arena allocator and a fixed-size pool allocator from scratch, test them, and beat `new`/`delete` by 5-30x on realistic workloads. Finish by meeting `std::pmr`, AddressSanitizer, and valgrind, the standard-library and tooling versions of everything you just built by hand._

In Chapter 5.1 you learned that the heap is a shared storage room: you ask for shelf space, you get a pointer, and you're responsible for giving the space back. In Chapter 2.1 you learned why arrays are fast: elements sit side by side, so the machine can walk them without hunting. This chapter is where those two ideas collide. The heap, as `malloc` hands it to you, scatters your data all over the storage room, and the cache, which only rewards side-by-side data, punishes you for it. The fix is to stop treating allocation as a black box and start doing it yourself. By the end you will have written two allocators smaller than a page of code each that outperform the system allocator by an order of magnitude, and you'll know exactly why they do.

## Start here: the self-storage facility

Picture what a public self-storage business has to deal with. Customers show up in any order, wanting any size of unit: a closet for one, a garage for another. They keep their units for wildly different lengths of time: some clear out next week, some stay for a decade. The office can't refuse anyone, can't ask customers to coordinate, and can't move a customer's stuff to tidy up, because the customer holds a key to one specific unit (a pointer, and pointers must stay valid).

So the office keeps a ledger. When a unit is vacated, it goes on a list of available units, organized by size so the clerk can find a match quickly. When a new customer arrives, the clerk searches the list, maybe splits a big unit into two smaller ones, maybe merges adjacent empty units back together. Every rental and every move-out is a trip through the front office.

That is `malloc`. It is a hard problem being solved competently: any size, any order, any lifetime, no coordination, no moving. The price of that generality is bookkeeping on every call, and a facility that slowly develops gaps: empty units scattered between occupied ones, too small or too far apart to be useful.

Now picture the alternative this chapter builds toward. If you know that a whole batch of objects will be created together and die together (everything computed for one frame of a game, one web request, one wafer's trip through a polish step), you don't need the storage facility at all. You need a whiteboard: write each new thing immediately to the right of the last one, and when the batch is done, wipe the whole board in one motion. No ledger, no search, no gaps. That's an arena, and it's about twenty lines of C++.

## What malloc and new actually do

`malloc` manages a large region of memory the operating system has granted to your process (it asks the OS for more, via `sbrk` or `mmap` on Linux, only when it runs low, because a system call is far too slow to make on every allocation). Within that region, a typical allocator uses three mechanisms worth knowing. The details vary between glibc malloc, jemalloc, tcmalloc, and mimalloc, but these ideas appear in all of them.

**Free lists.** When you `free` a block, the allocator doesn't return it to the OS. It threads the block onto a linked list of available blocks, the ledger of vacated units. The next `malloc` searches a free list before asking the OS for anything. Where does the list's link pointer live? Inside the freed block itself. The memory you just released is immediately repurposed as the allocator's own bookkeeping. (Hold that thought; our pool allocator will use exactly this trick.)

**Size classes.** Searching one giant free list for a good fit is slow, so allocators keep many lists, one per size range: a list of 16-byte blocks, 24-byte, 32-byte, and so on. Your request is rounded up to the nearest class. You can watch the rounding happen. This program uses `malloc_usable_size`, a glibc extension (on macOS the equivalent is `malloc_size`), so it's Linux-specific:

```cpp
#include <cstdio>
#include <cstdlib>
#include <malloc.h>   // malloc_usable_size is glibc-specific

int main() {
    size_t requests[] = {1, 8, 24, 25, 100, 1000};
    for (size_t request : requests) {
        void* p = malloc(request);
        printf("asked for %4zu bytes, malloc reserved %4zu\n",
               request, malloc_usable_size(p));
        free(p);
    }
}
```

On the test machine (glibc on Linux) this prints:

```text
asked for    1 bytes, malloc reserved   24
asked for    8 bytes, malloc reserved   24
asked for   24 bytes, malloc reserved   24
asked for   25 bytes, malloc reserved   40
asked for  100 bytes, malloc reserved  104
asked for 1000 bytes, malloc reserved 1000
```

Ask for 1 byte, pay for 24. Ask for 25, pay for 40. Small objects can carry 30-90% overhead before you count the header malloc stores next to each block so `free` knows how big it is. This is why Chapter 5.1's `__slots__` trick saved so much memory in Python: every Python object is a small heap allocation, each one taxed like this.

**Splitting and coalescing.** If no block of the right size exists, the allocator splits a bigger one. When you free a block whose neighbor is also free, it merges them. This fights **fragmentation**: the state where total free memory is plentiful but scattered in pieces too small to satisfy a request. External fragmentation is the scattered gaps between blocks; internal fragmentation is the waste inside each block from size-class rounding, like the 23 unused bytes in that 1-byte allocation. A long-running process that allocates and frees mixed sizes in mixed orders will fragment; it can hold gigabytes of free memory it cannot use for a large request, and it cannot compact, because compacting would move objects and break every pointer to them. (CPython's garbage collector, from 5.1, has the same constraint for the same reason.)

And `new`? In C++, `new T(args)` does exactly two things: it calls `operator new(sizeof(T))`, which is `malloc` in a costume, to get raw memory, then runs `T`'s constructor in that memory. `delete p` runs the destructor, then frees the memory. Everything above about malloc applies verbatim to `new`.

### Why this is slow and, worse, non-deterministic

Slow is only half the complaint. Each `malloc`/`free` pair costs bookkeeping: round to a size class, pop a free list, write a header; then on free, read the header, maybe coalesce, push a list. Tens of nanoseconds each when things go well, and modern allocators keep per-thread caches so the fast path avoids locks. But "when things go well" is the problem. Sometimes the free list is empty and the allocator must split, or refill a per-thread cache, or take a lock another thread holds, or page in fresh memory from the OS. The same line of code costs 20 nanoseconds on one call and 20 microseconds on another, and you can't predict which.

For a script, who cares. For a game rendering a frame every 16 milliseconds, a trading system, or the motion controller sweeping a polish head across a wafer, an unpredictable 20-microsecond stall in a control loop is a bug, even if the average cost is tiny. Hard-real-time coding standards ban heap allocation after startup for exactly this reason. The arena and pool you'll build have a worst case you can state exactly: a handful of arithmetic instructions, every single time.

## Alignment: where a value is allowed to live

Before building an allocator you need one rule that Python never made you learn: a value of type `T` can't live at just any address. Every type has an **alignment**: a number, always a power of two, such that objects of that type must start at an address divisible by it. A `char` can live anywhere (alignment 1). A 4-byte `int` wants an address divisible by 4. An 8-byte `double` wants a multiple of 8.

The reason is hardware. The memory system moves data in aligned chunks; a value that straddles a chunk boundary needs two reads instead of one. On x86 that misaligned access merely costs extra cycles. On many ARM and embedded cores (the processors inside the controllers on real equipment), certain misaligned accesses raise a bus error and your process dies. And vector (SIMD) instructions often demand 16- or 32-byte alignment outright. So the compiler enforces the rule everywhere it controls layout, and the moment you take over allocation, enforcing it becomes your job.

C++ gives you two operators for this. `alignof(T)` tells you the required alignment; `alignas(N)` demands a stricter one. You can see the compiler enforcing alignment inside every struct you write: it inserts invisible padding bytes so each member lands on its own aligned offset:

```cpp
#include <cstdio>

struct Loose {
    char  tag;     // 1 byte, then 7 bytes of padding
    double value;  // 8 bytes, must start at a multiple of 8
    char  flag;    // 1 byte, then 7 bytes of tail padding
};

struct Tight {
    double value;  // 8 bytes
    char  tag;     // 1 byte
    char  flag;    // 1 byte, then 6 bytes of tail padding
};

int main() {
    printf("sizeof(Loose) = %zu, alignof(Loose) = %zu\n",
           sizeof(Loose), alignof(Loose));
    printf("sizeof(Tight) = %zu, alignof(Tight) = %zu\n",
           sizeof(Tight), alignof(Tight));
}
```

```text
sizeof(Loose) = 24, alignof(Loose) = 8
sizeof(Tight) = 16, alignof(Tight) = 8
```

Same three members, 24 bytes versus 16, purely from ordering. The `double` in `Loose` can't start at offset 1, so the compiler pads to offset 8; then the struct's total size must be a multiple of its alignment (so arrays of it stay aligned), which pads the tail too. The rule of thumb: order members from largest alignment to smallest and the padding mostly disappears. Across a million-element array, `Loose` wastes 8 MB.

`alignas` goes the other direction: you can demand more alignment than a type needs, which matters when you want each object on its own cache line (the next section explains why you'd want that):

```cpp
#include <cstdio>

struct Counter {
    long value;                       // 8 bytes
};

struct alignas(64) PaddedCounter {    // one counter per cache line
    long value;
};

int main() {
    Counter plain[4];
    PaddedCounter padded[4];
    printf("sizeof(Counter) = %zu, sizeof(PaddedCounter) = %zu\n",
           sizeof(Counter), sizeof(PaddedCounter));
    printf("plain counters span %zu bytes; padded span %zu\n",
           sizeof(plain), sizeof(padded));
}
```

```text
sizeof(Counter) = 8, sizeof(PaddedCounter) = 64
plain counters span 32 bytes; padded span 256
```

One guarantee to remember: `malloc` and plain `new` always return memory aligned for `std::max_align_t` (16 bytes on typical 64-bit systems), which satisfies every ordinary type. Your hand-rolled allocator must make the same promise, and you'll see the two lines of bit arithmetic that keep it in the arena below.

## Cache lines and locality, measured for real

Chapter 5.1's kitchen gave you the picture: the pantry (RAM) is a five-minute walk compared to the countertop (cache), so what matters is how often you have to make the trip. The mechanism that decides is the **cache line**: when the CPU touches any byte of memory, the hardware fetches the entire surrounding 64-byte block into cache. A trip to the pantry brings back the whole tray, not one ingredient. Touch address 1000 and addresses 960-1023 all become fast.

This makes memory layout a performance knob as powerful as your choice of algorithm. Data you use together should live together, and data you traverse should be traversed in address order, so that every 64-byte tray the hardware hauls back gets fully used. Two benchmarks make this concrete. Run them yourself. The absolute milliseconds depend on your CPU, cache sizes, and memory, so your numbers will differ from the ones printed here. The ratios are what matter, and the ratios are stubbornly reproducible.

### Benchmark 1: row-major vs column-major traversal

A two-dimensional grid in C++ is really one flat array, laid out row after row (row-major). Walking it row-by-row visits addresses in order (0, 8, 16, 24...), so eight consecutive `double`s share a cache line and one memory fetch covers eight elements. Walking it column-by-column visits element 0, then element 4096, then 8192: a 32 KB jump every step, a fresh cache line every single access, and by the time the loop wraps to column 1, the lines from column 0 have long been evicted.

```cpp
#include <chrono>
#include <cstdio>
#include <vector>

int main() {
    const size_t N = 4096;                       // 4096 x 4096 doubles = 128 MB
    std::vector<double> grid(N * N, 1.0);        // one flat block, row-major

    using clock = std::chrono::steady_clock;
    double sum = 0.0;

    auto t0 = clock::now();
    for (size_t row = 0; row < N; ++row)         // row-major: walk memory in order
        for (size_t col = 0; col < N; ++col)
            sum += grid[row * N + col];
    auto t1 = clock::now();

    for (size_t col = 0; col < N; ++col)         // column-major: jump 32 KB per step
        for (size_t row = 0; row < N; ++row)
            sum += grid[row * N + col];
    auto t2 = clock::now();

    auto ms = [](auto a, auto b) {
        return std::chrono::duration<double, std::milli>(b - a).count();
    };
    printf("row-major:    %6.1f ms\n", ms(t0, t1));
    printf("column-major: %6.1f ms\n", ms(t1, t2));
    printf("(sum = %.0f, printed so the compiler can't delete the loops)\n", sum);
}
```

Compiled with `g++ -std=c++17 -O2 -Wall -Wextra`, on the test machine:

```text
row-major:      21.1 ms
column-major:   82.9 ms
(sum = 33554432, printed so the compiler can't delete the loops)
```

Identical arithmetic, identical element count, 4x slower. The only difference is the order the addresses are visited. (That final `printf` of `sum` is not decoration. Without it, an optimizing compiler notices the sum is never used and deletes both loops, and you "measure" zero. Making the result observable is the standard defense, and forgetting it is the most common way benchmarks lie.)

### Benchmark 2: array-of-structs vs struct-of-arrays

The same effect shows up in how you group fields. Suppose you're simulating particles (or wafers, or orders) with eight `double` fields each, and one hot loop only touches two of the eight. The natural object-oriented layout, an array of structs (AoS), drags all 64 bytes of every particle through the cache to use 16 of them. The transposed layout, a struct of arrays (SoA), stores each field in its own contiguous array, so the hot loop reads only the bytes it actually needs:

```cpp
#include <chrono>
#include <cstdio>
#include <vector>

struct Particle {                 // array-of-structs layout
    double x, y, z;               // position
    double vx, vy, vz;            // velocity
    double mass, charge;          // 64 bytes total: one full cache line
};

struct Particles {                // struct-of-arrays layout
    std::vector<double> x, y, z, vx, vy, vz, mass, charge;
};

int main() {
    const size_t N = 20'000'000;
    const double dt = 0.001;

    std::vector<Particle> aos(N);
    Particles soa;
    for (auto* v : {&soa.x, &soa.y, &soa.z, &soa.vx,
                    &soa.vy, &soa.vz, &soa.mass, &soa.charge})
        v->assign(N, 1.0);

    using clock = std::chrono::steady_clock;

    auto t0 = clock::now();
    for (size_t i = 0; i < N; ++i)
        aos[i].x += aos[i].vx * dt;      // drags all 64 bytes/particle through cache
    auto t1 = clock::now();
    for (size_t i = 0; i < N; ++i)
        soa.x[i] += soa.vx[i] * dt;      // touches only the x and vx arrays
    auto t2 = clock::now();

    auto ms = [](auto a, auto b) {
        return std::chrono::duration<double, std::milli>(b - a).count();
    };
    printf("update x, AoS: %6.1f ms\n", ms(t0, t1));
    printf("update x, SoA: %6.1f ms\n", ms(t1, t2));
    printf("(checksum %.3f)\n", aos[7].x + soa.x[7]);
}
```

```text
update x, AoS:   29.9 ms
update x, SoA:   17.8 ms
(checksum 1.001)
```

About 1.7x on the test machine. The gap is smaller than the 4x of raw traffic would suggest because the hardware prefetcher hides part of the cost of the AoS stream, but the direction never flips, and in wider loops with SIMD in play, SoA's advantage grows: vector instructions want eight consecutive `x` values, which is literally what SoA stores. This layout choice is the founding idea of data-oriented design, and it's why game engines and physics codes look "un-object-oriented": the structs are organized for the loops, not the nouns.

Now connect this back to the storage facility. Even if `malloc` were instantaneous, a linked structure of individually heap-allocated nodes scatters those nodes wherever the free lists happened to have space: a treasure hunt (Chapter 2.2) across random pantry shelves, one cache miss per hop. An arena fixes both problems at once: allocation becomes three instructions, and consecutive allocations are physically adjacent, so traversing what you built walks memory in order. Speed of allocation and locality of the result come from the same design.

## Build it: an arena and a pool, from scratch

Two allocators cover most real needs. The **arena** (also called a bump or linear allocator) is the whiteboard: mixed sizes, no individual free, wipe everything at once. The **pool** is a muffin tin: one fixed size, every slot identical, and you can free any slot individually because a slot map (a free list, the same trick malloc uses) tracks the empties.

### The arena

The whole idea is one pointer that only moves forward. Allocation rounds the pointer up to the caller's alignment, claims `size` bytes, and bumps. `reset` moves the pointer back to zero, "freeing" every object ever allocated in one assignment.

```cpp
#include <cassert>
#include <cstddef>
#include <cstdint>
#include <cstdio>
#include <cstdlib>
#include <new>

class Arena {
public:
    explicit Arena(size_t capacity)
        : base_(static_cast<char*>(std::malloc(capacity))),
          capacity_(capacity), used_(0) {
        if (!base_) throw std::bad_alloc{};
    }
    ~Arena() { std::free(base_); }

    Arena(const Arena&) = delete;             // owning raw memory: no copies
    Arena& operator=(const Arena&) = delete;

    void* allocate(size_t size, size_t align = alignof(std::max_align_t)) {
        assert(align != 0 && (align & (align - 1)) == 0);  // power of two
        size_t start = (used_ + align - 1) & ~(align - 1); // round up
        if (start + size > capacity_) return nullptr;      // arena full
        used_ = start + size;
        return base_ + start;
    }

    template <typename T, typename... Args>
    T* create(Args&&... args) {
        void* p = allocate(sizeof(T), alignof(T));
        if (!p) return nullptr;
        return new (p) T(static_cast<Args&&>(args)...);    // placement new
    }

    void reset() { used_ = 0; }               // frees everything at once
    size_t used() const { return used_; }

private:
    char*  base_;
    size_t capacity_;
    size_t used_;
};

struct Vec3 { double x, y, z; };

int main() {
    Arena arena(1024);

    // Basic allocation: distinct, non-overlapping pointers.
    char* a = static_cast<char*>(arena.allocate(10, 1));
    char* b = static_cast<char*>(arena.allocate(10, 1));
    assert(a != nullptr && b != nullptr);
    assert(b == a + 10);                      // bump allocation is contiguous

    // Alignment: a 1-byte allocation followed by a double-aligned one.
    arena.reset();
    arena.allocate(1, 1);
    void* d = arena.allocate(sizeof(double), alignof(double));
    assert(reinterpret_cast<uintptr_t>(d) % alignof(double) == 0);

    // Typed helper runs the constructor.
    arena.reset();
    Vec3* v = arena.create<Vec3>(Vec3{1.0, 2.0, 3.0});
    assert(v && v->y == 2.0);

    // Exhaustion is reported, not fatal.
    arena.reset();
    assert(arena.allocate(2000) == nullptr);
    assert(arena.allocate(1024) != nullptr);  // exactly full is fine
    assert(arena.allocate(1) == nullptr);

    // Reset reclaims everything in O(1).
    arena.reset();
    assert(arena.used() == 0);
    assert(arena.allocate(1024) != nullptr);

    printf("all arena tests passed\n");
}
```

```text
all arena tests passed
```

Three details deserve a close look.

The alignment rounding is the line `(used_ + align - 1) & ~(align - 1)`. For power-of-two alignments this is the classic round-up-to-multiple trick: adding `align - 1` pushes any non-multiple past the next boundary, and masking off the low bits snaps down onto it. Rounding 13 up to a multiple of 8: 13 + 7 = 20, and 20 with its low three bits cleared is 16. A value already on the boundary survives unchanged (16 + 7 = 23, mask gives 16). Because `base_` came from `malloc`, it's 16-byte aligned, so an aligned offset from it is an aligned address. This is the same bit-trickery you met in Chapter 2.1's address arithmetic, now doing real work.

`create<T>` uses **placement new**, `new (p) T(...)`, which is `new`'s constructor half without its allocation half: run `T`'s constructor at the address `p` that I already own. This is the primitive every custom allocator, and every `std::vector`, is built on.

Notice what's missing: a `free(void*)` for individual objects, and any call to destructors. `reset` reclaims memory without running destructors, so an arena is only safe for objects whose destructors do nothing: trivially destructible types, in standard-speak. Put a `std::string` in an arena and its internal heap buffer leaks when you reset. This is the arena's contract, not a bug: it trades generality for speed, exactly the opposite of malloc's trade. (Exercise 7 makes the contract machine-checked.)

### The pool

The pool hands out fixed-size slots and takes them back in any order. Free slots form a singly linked free list threaded through the slots themselves, exactly like malloc's ledger: a vacant slot has no object in it, so its bytes are free to hold the "next vacant slot" pointer. The `union` says precisely that. A slot is either a live `T` or a link, never both:

```cpp
#include <cassert>
#include <cstddef>
#include <cstdio>
#include <cstdlib>
#include <new>

template <typename T>
class Pool {
    union Slot {                       // a slot is either a T or a link
        Slot* next;
        alignas(T) unsigned char storage[sizeof(T)];
    };

public:
    explicit Pool(size_t count)
        : slots_(static_cast<Slot*>(std::malloc(count * sizeof(Slot)))),
          count_(count) {
        if (!slots_) throw std::bad_alloc{};
        for (size_t i = 0; i + 1 < count; ++i)   // thread the free list
            slots_[i].next = &slots_[i + 1];
        slots_[count - 1].next = nullptr;
        free_head_ = &slots_[0];
    }
    ~Pool() { std::free(slots_); }

    Pool(const Pool&) = delete;
    Pool& operator=(const Pool&) = delete;

    template <typename... Args>
    T* create(Args&&... args) {
        if (!free_head_) return nullptr;         // pool exhausted
        Slot* slot = free_head_;
        free_head_ = slot->next;                 // pop the free list
        return new (slot->storage) T(static_cast<Args&&>(args)...);
    }

    void destroy(T* obj) {
        if (!obj) return;
        obj->~T();                               // run the destructor
        Slot* slot = reinterpret_cast<Slot*>(obj);
        slot->next = free_head_;                 // push back onto the free list
        free_head_ = slot;
    }

    size_t capacity() const { return count_; }

private:
    Slot*  slots_;
    size_t count_;
    Slot*  free_head_ = nullptr;
};

struct Wafer {
    int id;
    double thickness_nm;
    Wafer(int i, double t) : id(i), thickness_nm(t) {}
};

int main() {
    Pool<Wafer> pool(3);

    Wafer* w1 = pool.create(101, 775.0);
    Wafer* w2 = pool.create(102, 775.0);
    Wafer* w3 = pool.create(103, 775.0);
    assert(w1 && w2 && w3);
    assert(w1->id == 101 && w3->id == 103);

    assert(pool.create(104, 775.0) == nullptr);  // full: no hidden growth

    pool.destroy(w2);                            // free the middle one
    Wafer* w4 = pool.create(104, 775.0);
    assert(w4 == w2);                            // slot is recycled immediately

    pool.destroy(w1);
    pool.destroy(w3);
    pool.destroy(w4);

    // After freeing everything, all three slots are available again.
    assert(pool.create(1, 0.0) && pool.create(2, 0.0) && pool.create(3, 0.0));

    printf("all pool tests passed\n");
}
```

```text
all pool tests passed
```

Both `create` and `destroy` are a constant handful of instructions (pop a list, push a list) with no search, no size classes, no locks, no surprises. Unlike the arena, `destroy` does run the destructor, so pooled objects can own resources. And because every slot is the same size, a pool cannot fragment: any free slot satisfies any request, forever. The cost is the obvious one: a `Pool<Wafer>` can only ever hold `Wafer`-sized things, and this one refuses to grow past its capacity, which in embedded and real-time code is a feature, because memory exhaustion becomes a checkable return value at a defined ceiling rather than an OOM kill at 3 a.m.

Notice also what the constructor did: one `malloc` for the whole tin. A thousand live objects cost one allocation's worth of malloc metadata instead of a thousand, and the slots are contiguous in memory, so iterating live objects has the locality of an array.

### Benchmark: arena and pool vs new/delete

Time for the payoff. This is a fragment, not a standalone program: paste it below the `Arena` and `Pool` classes from above (drop their `main`s) and compile the combined file. The workload simulates 100 frames, each allocating 100,000 32-byte nodes and then releasing them all:

```cpp
#include <chrono>
#include <cstdio>
#include <vector>

struct Node {
    double payload[4];               // 32 bytes, roughly a small tree/list node
    explicit Node(double seed) { for (double& d : payload) d = seed; }
};

template <typename F>
double time_ms(F&& body) {
    auto t0 = std::chrono::steady_clock::now();
    body();
    auto t1 = std::chrono::steady_clock::now();
    return std::chrono::duration<double, std::milli>(t1 - t0).count();
}

int main() {
    const size_t kPerFrame = 100'000;    // objects allocated each "frame"
    const size_t kFrames   = 100;
    double checksum = 0.0;

    double heap_ms = time_ms([&] {
        std::vector<Node*> live(kPerFrame);
        for (size_t f = 0; f < kFrames; ++f) {
            for (size_t i = 0; i < kPerFrame; ++i) live[i] = new Node(1.0);
            checksum += live[0]->payload[0];
            for (Node* n : live) delete n;
        }
    });

    double arena_ms = time_ms([&] {
        Arena arena(kPerFrame * sizeof(Node) + 64);
        for (size_t f = 0; f < kFrames; ++f) {
            Node* first = nullptr;
            for (size_t i = 0; i < kPerFrame; ++i) {
                Node* n = arena.create<Node>(1.0);
                if (i == 0) first = n;
            }
            checksum += first->payload[0];
            arena.reset();               // one line frees all 100,000 nodes
        }
    });

    double pool_ms = time_ms([&] {
        Pool<Node> pool(kPerFrame);
        std::vector<Node*> live(kPerFrame);
        for (size_t f = 0; f < kFrames; ++f) {
            for (size_t i = 0; i < kPerFrame; ++i) live[i] = pool.create(1.0);
            checksum += live[0]->payload[0];
            for (Node* n : live) pool.destroy(n);
        }
    });

    printf("new/delete: %7.1f ms\n", heap_ms);
    printf("arena:      %7.1f ms\n", arena_ms);
    printf("pool:       %7.1f ms\n", pool_ms);
    printf("(checksum %.0f)\n", checksum);
}
```

On the test machine, with `-O2`:

```text
new/delete:   132.0 ms
arena:         13.4 ms
pool:          26.2 ms
(checksum 300)
```

Ten million allocations and ten million frees. The arena is about 10x faster than `new`/`delete` here; the pool about 5x. Your machine will print different milliseconds; the ratios are the durable result, and even those wobble between runs (the mini-project digs into why). And the timing understates the arena's advantage: its 100,000 nodes per frame sit in one contiguous block, so whatever the frame does next with those nodes runs at row-major speed, not treasure-hunt speed.

## When arenas shine

The arena's contract (everything dies together, no individual frees) sounds restrictive until you notice how much real software is shaped exactly like that. The pattern to look for is a batch lifetime: a unit of work that allocates freely while it runs and whose every allocation is garbage the moment it ends.

- Per-frame: a game or visualization allocates collision pairs, draw commands, and scratch strings while building frame N. At the start of frame N+1, all of it is dead. One arena, `reset()` once per frame, allocation cost near zero and no fragmentation growth over a ten-hour session.
- Per-request: a web server handling a request parses headers, builds intermediate objects, renders a response. When the response is sent, the whole graph is garbage. Give each request its own arena and cleanup is one pointer assignment. This is how high-performance servers and Apache's memory pools work.
- Per-pass, on equipment: a CMP tool's software plans a polish pass: zone pressures, sweep profile, endpoint-detection buffers for that wafer. When the wafer lifts off the pad, the plan is dead and the next wafer gets a fresh one. Sizing the arena at the worst-case pass makes memory use provably bounded across a million-wafer campaign, which is exactly the property a tool that must not fail mid-lot needs. The pool covers the same machine's other need: fixed-size event and message objects flowing between controller tasks, allocated and freed in any order, forever, with zero fragmentation.
- Compilers do it too: an AST is built during parsing and dies when the file is done. Tokens, nodes, scopes: one arena per compilation unit is standard practice in production compilers.

The common thread is that the program's structure already knows the lifetime; the arena just stops paying malloc to rediscover it one object at a time. When lifetimes actually vary and sizes actually mix (long-lived caches, user-driven documents), the general-purpose heap earns its keep, and that's fine. The skill is recognizing which situation you're in.

## The standard version: std::pmr

C++17 shipped this idea in the standard library under `std::pmr` (polymorphic memory resources). A **memory resource** is an abstract source of raw bytes; `std::pmr::monotonic_buffer_resource` is precisely our arena: bump allocation, no individual frees, everything released when the resource is destroyed or `release()`d (it even grows itself by grabbing bigger blocks upstream when it fills, one nicety our twenty-liner skipped). The containers in `std::pmr` (`pmr::vector`, `pmr::string`, `pmr::list`, ...) accept a resource pointer and draw all their memory from it:

```cpp
#include <chrono>
#include <cstdio>
#include <list>
#include <memory_resource>

int main() {
    const int kNodes = 200'000;
    using clock = std::chrono::steady_clock;

    auto t0 = clock::now();
    {
        std::list<int> heap_list;                 // every node is a malloc
        for (int i = 0; i < kNodes; ++i) heap_list.push_back(i);
    }
    auto t1 = clock::now();
    {
        std::pmr::monotonic_buffer_resource arena(1 << 20);  // starts at 1 MB
        std::pmr::list<int> arena_list(&arena);   // nodes come from the arena
        for (int i = 0; i < kNodes; ++i) arena_list.push_back(i);
    }   // arena destructor releases everything at once
    auto t2 = clock::now();

    auto ms = [](auto a, auto b) {
        return std::chrono::duration<double, std::milli>(b - a).count();
    };
    printf("std::list with malloc:   %6.1f ms\n", ms(t0, t1));
    printf("pmr::list with arena:    %6.1f ms\n", ms(t1, t2));
}
```

```text
std::list with malloc:      5.0 ms
pmr::list with arena:       1.8 ms
```

A 3x speedup for changing two lines, and the arena-backed list's nodes are contiguous in memory, so traversing it later is cache-friendly too: a linked list with most of an array's locality. The library also offers `std::pmr::unsynchronized_pool_resource`, the standard cousin of the pool you built. Knowing `pmr` exists matters because in production code you should reach for it before hand-rolling; knowing how to hand-roll matters because now `pmr`'s documentation ("deallocation is a no-op," "not thread-safe," "upstream resource") reads as obvious statements about a pointer being bumped, not incantations.

## Finding memory bugs: AddressSanitizer and valgrind

The moment you manage memory by hand (and an arena is memory managed by hand), you inherit C++'s classic bug family: use-after-free, buffer overflow, double free, leak. Chapter 5.1 showed why Python spares you these; here's the tooling that catches them in C++. Consider a program with a real bug:

```cpp
#include <cstdio>

int main() {
    int* readings = new int[8];
    for (int i = 0; i < 8; ++i) readings[i] = i * 10;
    delete[] readings;
    printf("%d\n", readings[3]);   // use-after-free: reads freed memory
}
```

Compiled normally, this runs without complaint and prints whatever happens to be in the freed memory: on one run of the test machine, `-645413000`. That's the nightmare scenario: not a crash, a plausible wrong number flowing onward into a pressure setpoint or a bank balance. The memory isn't wiped on `free`; it's just back on the free list, holding stale bytes until someone else claims it.

**AddressSanitizer** (ASan) is a compiler mode that instruments every memory access and quarantines freed memory so stale reads get caught. Recompile with `-fsanitize=address -g` (no other changes) and run:

```text
$ g++ -std=c++17 -g -fsanitize=address use_after_free.cpp -o uaf && ./uaf
==18==ERROR: AddressSanitizer: heap-use-after-free on address 0xfca257400b5c
READ of size 4 at 0xfca257400b5c thread T0
    #0 main use_after_free.cpp:7
0xfca257400b5c is located 12 bytes inside of 32-byte region
freed by thread T0 here:
    #0 operator delete[](void*)
    #1 main use_after_free.cpp:6
previously allocated by thread T0 here:
    #0 operator new[](unsigned long)
    #1 main use_after_free.cpp:4
```

Read what it hands you: the bad access with its line number, where that memory was freed, and where it was originally allocated: the three points you need to reconstruct any lifetime bug. ASan costs roughly 2x runtime and more memory, so it's a build mode for tests and CI, not production. Run your test suite under it routinely; it converts silent corruption into loud, located failures. (Its sibling `-fsanitize=undefined`, UBSan, catches misaligned casts and other undefined behavior the same way.)

**Valgrind** attacks the same bugs from the other side, with no recompile needed. It runs your unmodified binary on a synthetic CPU, checking every access. `valgrind --leak-check=full ./program` reports use-after-free and out-of-bounds errors in the same allocated-here/freed-here style, plus a leak summary at exit that classifies unfreed memory ("definitely lost" is the line to chase; each entry comes with the call stack that allocated it). It's 10-50x slower than native, so the usual division of labor is ASan in every test run and valgrind when you need its leak reports, its exactness, or can't rebuild the binary.

One warning specific to this chapter: custom allocators partially blind both tools. Once your arena grabs its megabyte, ASan sees one big legitimate allocation; a use-after-`reset` inside it touches memory you still validly own, so no alarm fires. Production arenas fix this by "poisoning" reclaimed regions when built under ASan (see `ASAN_POISON_MEMORY_REGION`), and by valgrind's equivalent client-request macros. Ours doesn't, which is worth remembering when you deploy one, and a good reason to keep a build flag that swaps the arena for plain `new` so the sanitizers can see every object individually.

## Mini-project: an allocator benchmark suite

Time to turn the one-off benchmark into an instrument and read what it says. The suite compares `new`/`delete`, the arena, and the pool across four object sizes, taking the best of three runs for each measurement. Portfolio-wise, this is the piece to show: a measurement harness plus a written analysis is worth more than either alone. This `main` (plus the small pieces above it) is a fragment like the last one. Paste it below your `Arena` and `Pool` classes:

```cpp
#include <chrono>
#include <cstdio>
#include <cstring>
#include <vector>

template <size_t Size>
struct Obj {
    alignas(8) unsigned char bytes[Size];
    Obj() { bytes[0] = 1; bytes[Size - 1] = 2; }   // touch both ends
};

template <typename F>
static double best_of_3_ms(F&& body) {
    double best = 1e30;
    for (int rep = 0; rep < 3; ++rep) {
        auto t0 = std::chrono::steady_clock::now();
        body();
        auto t1 = std::chrono::steady_clock::now();
        double ms = std::chrono::duration<double, std::milli>(t1 - t0).count();
        if (ms < best) best = ms;
    }
    return best;
}

template <size_t Size>
void run_row(size_t per_frame, size_t frames) {
    using T = Obj<Size>;

    double heap_ms = best_of_3_ms([&] {
        std::vector<T*> live(per_frame);
        for (size_t f = 0; f < frames; ++f) {
            for (size_t i = 0; i < per_frame; ++i) live[i] = new T();
            for (T* p : live) delete p;
        }
    });

    double arena_ms = best_of_3_ms([&] {
        Arena arena(per_frame * sizeof(T) + 64);
        for (size_t f = 0; f < frames; ++f) {
            for (size_t i = 0; i < per_frame; ++i) arena.create<T>();
            arena.reset();
        }
    });

    double pool_ms = best_of_3_ms([&] {
        Pool<T> pool(per_frame);
        std::vector<T*> live(per_frame);
        for (size_t f = 0; f < frames; ++f) {
            for (size_t i = 0; i < per_frame; ++i) live[i] = pool.create();
            for (T* p : live) pool.destroy(p);
        }
    });

    printf("%4zu B | %10.1f | %10.1f (%4.1fx) | %8.1f (%4.1fx)\n",
           Size, heap_ms, arena_ms, heap_ms / arena_ms,
           pool_ms, heap_ms / pool_ms);
}

int main() {
    const size_t per_frame = 100'000, frames = 50;
    printf("  size | new/delete |      arena (speedup) |    pool (speedup)  [ms]\n");
    printf("-------|------------|----------------------|-------------------\n");
    run_row<16>(per_frame, frames);
    run_row<64>(per_frame, frames);
    run_row<256>(per_frame, frames);
    run_row<1024>(per_frame, frames);
}
```

Output on the test machine (5 million allocations and frees per cell; again, your absolute numbers will differ, the pattern shouldn't):

```text
  size | new/delete |      arena (speedup) |    pool (speedup)  [ms]
-------|------------|----------------------|-------------------
  16 B |       65.0 |        2.2 (29.5x) |      8.5 ( 7.7x)
  64 B |       70.6 |        3.9 (18.2x) |     15.6 ( 4.5x)
 256 B |      376.9 |       18.1 (20.8x) |     60.4 ( 6.2x)
1024 B |     1040.4 |       31.7 (32.8x) |    148.3 ( 7.0x)
```

### Written analysis

Four observations, from the numbers to the design lessons.

First, the headline: the arena wins by 18-33x and the pool by 4.5-8x, at every size. The mechanism-level explanation is instruction count. The arena's allocation is an add, a mask, a compare; the pool's is a two-step list pop; `new` is a function call into a size-classed free-list machine, and `delete` is another. Nothing about this is subtle: the fast allocators simply do less.

Second, look down the `new/delete` column: 65 ms at 16 bytes, about the same at 64, then a 5x jump at 256 bytes and 16x at 1024. Cost scales with size for malloc far more than for the arena. Two things happen as objects grow: 100,000 live objects stop fitting in the smallest bins malloc optimizes hardest (its per-thread caches favor small sizes), and the working set (100 MB per frame at 1024 bytes) blows past the caches entirely, so the scattered writes malloc's layout produces become memory-bound. The arena writes the same bytes but sequentially, which is the row-major-versus-column-major experiment all over again, now happening inside the allocator comparison.

Third, the arena beats the pool everywhere, by about 4x. Both are constant-time, but the arena's constant is smaller (no per-object free at all, since `reset` is one store), and its allocation order is perfectly sequential while the pool hops wherever its free list points. After the first frame, this benchmark's pool free list happens to be in reversed order from the frame's frees, so its "hops" are still fairly regular; under truly random churn the gap widens. That's the pool's price for a capability the arena lacks: freeing objects one at a time, in any order. Pick by lifetime shape, not by the bigger speedup number.

Fourth, about honesty in measurement: run the suite five times and the speedup for any one cell moves noticeably: the ratios above wobbled between roughly 18x and 33x for the arena across runs on the same idle machine, and the earlier single-run benchmark showed 10x on a similar workload. The variance is itself data, and it's almost all on the `new/delete` side: page faults on first touch, per-thread cache refills, whatever else the general-purpose machinery decides to do this microsecond. The arena's times barely move between runs. Determinism, not the mean, is the property real-time systems buy with custom allocators. The benchmark demonstrates it accidentally, in its error bars.

Extensions if you want to push further: add a randomized alloc/free order to stress fragmentation (exercise 8 starts this); add `std::pmr::monotonic_buffer_resource` and `unsynchronized_pool_resource` columns and see how close the standard versions come to yours; run every configuration under ASan and confirm the tests still pass; plot the table with matplotlib and put the chart in the README.

## Common mistakes

1. **Arena-allocating objects with real destructors.** `arena.create<std::string>(...)` compiles, works, and leaks: `reset` never runs destructors, so the string's internal buffer is orphaned. Restrict arenas to trivially destructible types (enforce it with `static_assert(std::is_trivially_destructible_v<T>)` inside `create`), or track and run destructors explicitly before reset.
2. **Using a pointer after `reset()`.** Arena reset is a mass free: every pointer handed out before it is now dangling, even though the memory is still owned by the arena and readable. Bugs here are nastier than malloc use-after-free because sanitizers don't see them (the arena still validly owns the bytes). Discipline the lifetime: pointers into a per-frame arena must not outlive the frame, ever.
3. **Ignoring alignment in a hand-rolled allocator.** Bump `used_` by raw sizes and eventually a `double` lands at an odd offset: slow reads on x86, a crash on stricter cores, and undefined behavior everywhere by the standard. Always round with `(used_ + align - 1) & ~(align - 1)` and take `alignof(T)` from the caller.
4. **Benchmarking lies.** Timing at `-O0`, or at `-O2` without using the results, both produce garbage: the first measures a program nobody ships, the second measures loops the compiler deleted. Compile `-O2`, make results observable (print a checksum), run multiple times, and report ratios rather than treating one machine's milliseconds as truth.
5. **Assuming recycled memory is clean.** A pool slot returned by `create` holds whatever the previous occupant left, unless your constructor writes every field. Fields you forget to initialize don't read as zero; they read as stale data from a dead object, the same class of bug as the use-after-free demo, wearing a construction hat.
6. **Arena-sizing by optimism.** An arena that's too small returns null (or grows, if you built that) at the worst possible time. Size it from the workload's measured worst case plus margin, and treat allocation failure as a real code path: our `allocate` returns `nullptr` precisely so callers must decide what full means.
7. **Reordering struct members without checking.** Field order changes size (24 vs 16 bytes in the demo), but it also changes which fields share a cache line, and in AoS layouts that's a performance contract. When you reorder for packing, re-run the benchmark; when a struct is part of a binary protocol or shared memory, don't reorder at all without versioning.
8. **Reaching for a custom allocator first.** The order of operations is: measure, fix layout (SoA, fewer allocations, `reserve`), try `std::pmr`, and only then hand-roll. A bespoke allocator is a sharp tool you now maintain forever; the benchmark that justifies it should exist before the allocator does.

## On the job / interview angle

On the job, allocator awareness marks the line between "writes C++" and "writes the C++ that runs the machine." Game studios, HFT shops, database teams, and embedded/equipment firms all maintain arena and pool infrastructure, and their code reviews ask lifetime questions by reflex: who owns this, when does it die, why is this `new` in the hot loop? On real-time equipment software, "no heap allocation after init" is commonly a hard rule, enforced by code review and sometimes by linking in an allocator that aborts. Your pool is how dynamic-feeling behavior gets built under that rule. Layout work is equally routine: profiling shows a hot loop bound on memory, and the fix is an SoA transform or a packing pass, exactly the two benchmarks you ran.

In interviews, this chapter shows up three ways. "What happens when you call `malloc`?" wants free lists, size classes, splitting/coalescing, and fragmentation, plus the `new` = allocate + construct distinction. "Design an allocator for objects that die together" (or "for fixed-size messages") is the arena (or pool), and interviewers care that you state the contract: what it can't do, what alignment guarantee it makes, what happens when it's full. And "why is this loop slow?" with a strided access pattern is the cache-line question; the row-major/column-major numbers, quoted from your own machine, make a much better answer than the textbook diagram. Senior loops add the tooling follow-up: how would you find a use-after-free in production code? ASan in CI, valgrind for leak triage, and (the answer that signals real experience) knowing custom allocators mask both unless you poison.

## Exercises

1. Without compiling, predict `sizeof` for `struct A { char c; int i; char d; };` and `struct B { int i; char c; char d; };` on a typical 64-bit system (where `sizeof(int)` is 4 and `alignof(int)` is 4). Then verify with a program.
2. Work the arena's rounding formula by hand: with `used_ = 13`, compute `start` for alignments 1, 4, 8, and 16. Then explain in one sentence why the formula requires `align` to be a power of two.
3. A `4096 x 4096` array of `double` is traversed once. With 64-byte cache lines, how many cache lines does the row-major traversal load, and how many does the column-major traversal load (worst case, nothing survives in cache between uses)? Express the ratio.
4. Add `bool owns(const void* p) const` to `Arena`, returning whether `p` points into the arena's currently used region. Write two asserts that test it.
5. Add checkpoint/rewind to `Arena`: `mark()` returns an opaque `Marker`, and `rewind(m)` frees everything allocated after the mark. Explain a real workload where this beats a full `reset()`.
6. The pool's `destroy` then `create` returned the same address (`w4 == w2`). Explain why the free list guarantees this LIFO behavior, and name the bug class this recycling makes more dangerous.
7. Make the arena's contract machine-checked: modify `create<T>` so that arena-allocating a type with a nontrivial destructor fails to compile. Show the one-line change and a type that now gets rejected.
8. Modify the mini-project so each frame frees a random half of the objects, allocates replacements, and repeats: a churn workload. Predict, before running, how each allocator's numbers move relative to the die-together workload, and which allocator can't run this workload at all.
9. Your team's request handler does 40,000 small allocations per request, all dead by response time, but a few objects (session records) must outlive the request. Design the memory strategy: what comes from where, and what rule prevents the classic bug in this setup?
10. (Stretch) Wrap your `Arena` in the `std::pmr::memory_resource` interface (override `do_allocate`, `do_deallocate`, `do_is_equal`) so `std::pmr::vector` can use it. What should `do_deallocate` do, and why is that correct here?

### Solutions

**1.** `A`: offset 0 for `c`, pad 3, `i` at 4, `d` at 8, tail-pad to a multiple of 4 → `sizeof(A) = 12`. `B`: `i` at 0, `c` at 4, `d` at 5, pad to 8 → `sizeof(B) = 8`. Same members, 50% larger for the bad ordering. A verification program printing both sizes confirms 12 and 8 with g++ on x86-64 and ARM64.

**2.** `start = (13 + align - 1) & ~(align - 1)`. Align 1: `13 & ~0 = 13`. Align 4: `16 & ~3 = 16`. Align 8: `20 & ~7 = 16`. Align 16: `28 & ~15 = 16`. The mask `~(align - 1)` clears the low bits only when `align - 1` is all-ones below the alignment bit, which happens only when `align` is a power of two. For, say, align 12, `~(align - 1)` is not a "round down to multiple of 12" mask and the trick silently produces wrong addresses.

**3.** The array is 4096 × 4096 × 8 bytes = 128 MB = 2,097,152 cache lines of 64 bytes. Row-major loads each line once: 2,097,152 loads. Column-major loads a fresh line per element in the worst case: 4096 × 4096 = 16,777,216 loads. Ratio 8:1, exactly the 8 doubles per line, which is why the measured 4x (prefetching claws some back) has 8x as its ceiling.

**4.** Add to `Arena`:

```text
bool owns(const void* p) const {
    const char* c = static_cast<const char*>(p);
    return c >= base_ && c < base_ + used_;
}
```

Tests: `void* p = arena.allocate(64, 8); assert(arena.owns(p));` and `int x = 0; assert(!arena.owns(&x));`. (Strictly, ordered comparison of unrelated pointers is unspecified by the standard; a fully portable version compares `uintptr_t` values. On mainstream flat-memory platforms this form is what production arenas use.) Verified against the chapter's `Arena` with `g++ -std=c++17 -O2`.

**5.** Add:

```text
struct Marker { size_t used; };
Marker mark() const { return Marker{used_}; }
void rewind(Marker m) { used_ = m.used; }
```

Rewind is valid because bump allocation is strictly ordered: everything after the mark sits at higher offsets, so truncating `used_` frees exactly the post-mark allocations. Workload: a parser that speculatively parses an alternative. It marks, attempts, and on failure rewinds, discarding the failed subtree's nodes while keeping everything parsed before it. A full `reset` would destroy the good prefix too. (Tested: after `mark` at 32 bytes used, allocate 64 more, `rewind`, `used()` returns 32.)

**6.** `destroy` pushes the slot onto the head of the free list; the next `create` pops the head. Last freed is first reused: LIFO by construction. The dangerous bug class is stale-pointer aliasing: any pointer still held to the destroyed object now points at a live, different object of the same type. Reads through it return plausible values (right type, wrong object) and writes corrupt the new object, which is far harder to spot than a crash. This is also why the immediate-reuse property, great for cache warmth, argues for debug-mode tricks like memsetting destroyed slots to a poison pattern such as `0xDD`.

**7.** In `create<T>`, before the allocation:

```text
static_assert(std::is_trivially_destructible<T>::value,
              "Arena never runs destructors; this type needs one");
```

(plus `#include <type_traits>`). Now `arena.create<Vec3>(...)` still compiles, but `arena.create<std::string>("x")` fails at compile time with that message. This converts the arena's documentation-only contract into one the compiler enforces, the cheapest bug fix in this chapter.

**8.** Predictions: `new/delete` gets relatively worse over time: random-order frees of mixed positions defeat the per-thread cache's LIFO sweet spot and begin fragmenting the heap, so its numbers drift upward across frames. The pool is nearly unaffected: any free slot serves any request, so churn cannot fragment it, though its allocation order becomes scattered, cooling the cache for whoever traverses the objects. The arena cannot run this workload at all, because it has no way to free a random half; `reset` frees everything or nothing. That's the punchline the exercise is built for: churn is precisely the lifetime shape that disqualifies arenas, and the benchmark should make the disqualification concrete rather than theoretical. (Implementation: keep `std::vector<T*> live`, `std::shuffle` it with a seeded `std::mt19937`, free the back half, reallocate.)

**9.** Per-request arena for the 40,000 short-lived allocations, reset (or destroyed) when the response is sent; session records allocated from the long-lived heap (plain `new`/`delete` or a `Pool<Session>` if they're uniform, which also caps session memory). The rule that prevents the classic bug: nothing reachable after the response may point into the request arena: session records must not hold arena pointers; anything they need (a username parsed into an arena string, say) gets copied out into long-lived storage at the boundary. The classic bug is exactly that dangling reference: works in testing while the arena's stale bytes survive, corrupts a random later request in production.

**10.** Subclass `std::pmr::memory_resource`; `do_allocate(bytes, align)` forwards to `allocate(bytes, align)` (throwing `std::bad_alloc` on null, since `pmr` reports exhaustion by exception); `do_is_equal(other)` returns `this == &other` (two arenas are interchangeable only if they're the same arena, since memory from one can't be released to another); and `do_deallocate` does nothing. Empty deallocation is correct because it honestly implements the arena's contract (individual frees are deferred to `reset`/destruction), and it's exactly what `std::pmr::monotonic_buffer_resource::do_deallocate` does. A `pmr::vector` using this resource will "leak" its old buffer on every growth reallocation into the arena; that's expected arena behavior (transient garbage reclaimed at reset), and a good thing to say out loud in an interview.
