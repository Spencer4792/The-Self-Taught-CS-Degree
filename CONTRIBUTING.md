# Contributing

Thanks for wanting to help make this textbook better. It started as a personal study project, but it is open so anyone can learn from it and improve it. Corrections, clearer explanations, better examples, and new exercises are all welcome.

## Ways to contribute

- **Fix something wrong.** Typos, broken links, code that does not run, a definition that is off, or math that is stated incorrectly. These are the most valuable contributions of all.
- **Make something clearer.** If a section confused you, that is a signal. Rewrite it so the next reader gets it faster, and explain in your pull request what tripped you up.
- **Add examples or exercises.** More worked examples, more practice problems with solutions, or an extra mini-project for a chapter.
- **Suggest a topic.** Open an issue describing what is missing and why it matters.

## How to submit a change

1. Fork the repository and create a branch named for your change, for example `fix/hash-table-typo`.
2. Make your edit. Keep the voice and structure of the surrounding chapter (see the style notes below).
3. If you touched any code, run it and confirm it works. Code in this book is meant to actually run.
4. Open a pull request. Describe what you changed and why. Link the chapter and section.

If you are new to this workflow, the git tutorial in the book itself walks through the whole fork, branch, and pull request loop: [11.2 Git Hands-On Tutorial](11-Version-Control/11.2-git-hands-on-tutorial.md).

## Style notes

- **Plain, friendly, and direct.** The book speaks to the reader as "you," and uses "we"/"let's" when working through something together, like a good instructor at a whiteboard. Keep that tone.
- **No black boxes.** Explain why something works before showing the tool that does it. Derive the math. Build the simple version from scratch.
- **Runnable code.** Prefer Python. Test what you add. Do not paste code you have not run.
- **No em dashes.** Use commas, colons, or short sentences instead. This keeps the prose clean and consistent.
- **Keep the chapter rhythm.** Most chapters follow: a "Start here" on-ramp, theory, a "Build it" implementation, a mini-project, common mistakes, an interview angle, and exercises with worked solutions.
- **Accuracy over polish.** A correct, plain explanation beats an impressive but fuzzy one.

## Reporting issues

Open an issue if you find a mistake, something unclear, or a topic you think belongs in the book. Be specific: name the chapter, quote the line, and say what you expected.
