## 🌱 Start here (the gentle on-ramp)

Last chapter we climbed a ladder of machines and found that even a clever finite automaton hits walls, it can't count `aⁿbⁿ`. We added a stack and got context-free power. Now we add the *last* thing a machine could possibly want: an **unbounded scratchpad** it can read, write, and move around on freely. That machine is the **Turing machine**, and the staggering claim of this chapter is that *this simple device captures everything that can be computed by any process whatsoever*, your laptop, a supercomputer, a quantum computer (for *what's computable*, not how fast), pencil-and-paper math, all of it. Nothing computable lies beyond it.

Picture a person at an infinitely long strip of paper divided into cells, with a pencil and an eraser. They follow a tiny rulebook: "if you're in mood #3 and the cell under you says `1`, erase it, write `0`, shuffle one cell left, and switch to mood #7." That's the *entire* model, a finite rulebook (the "moods" are states), an infinite tape, and a head that reads/writes one cell and steps left or right. It looks absurdly weak. It is absurdly powerful. The whole theory of *what computers can and can't do* rests on it.

Two earth-shaking results follow, and they sound like science fiction but are airtight theorems:

1. **There are problems no program can ever solve**, not "no fast program," but *no program, ever*. The flagship is the **halting problem**: you cannot write a program that, given any program and input, always correctly says whether it halts or loops forever. We'll *prove* this with a beautiful self-referential trick (diagonalization), the same flavor of argument as "this sentence is false."
2. **Among the problems we *can* solve, some seem to require brute force.** The **P vs NP** question asks whether every problem whose answer is *easy to check* is also *easy to solve*. A million-dollar open problem, and the foundation under modern cryptography ([Chapter 12.1](../12-Security/12.1-cryptography.md)): if P = NP, the encryption protecting everything collapses.

So the chapter has two halves. **Computability** draws the outer boundary, the cliff edge beyond which *no* algorithm exists. **Complexity** maps the territory *inside* that boundary, sorting the feasible from the (apparently) hopeless. Both are built on the Turing machine, and as always we'll *implement the machine* so it's never a black box.

This is the chapter where CS becomes a *science* with permanent, proven limits, like thermodynamics for computation. I find it thrilling: not "we haven't figured it out yet," but "we *proved* it can't be figured out." Let's build the machine and earn those theorems.

## 📐 The Turing machine - the model

A **Turing machine (TM)** is a 7-tuple `M = (Q, Σ, Γ, δ, q₀, q_accept, q_reject)`:

- `Q`, finite set of **states**.
- `Σ`, the **input alphabet** (doesn't include the blank symbol).
- `Γ`, the **tape alphabet**, with `Σ ⊆ Γ` and a special **blank** symbol `␣ ∈ Γ \ Σ`.
- `δ : Q × Γ → Q × Γ × {L, R}`, the **transition function**. Given (current state, symbol under the head), it returns (new state, symbol to write, direction to move the head: Left or Right).
- `q₀`, start state.
- `q_accept`, `q_reject`, the **halting** states (distinct). Reaching either stops the machine.

**How it runs.** The input is written on the leftmost cells of a tape that is infinite to the right (cells start blank, `␣`). The head starts on the first cell in state `q₀`. At each step: read the symbol under the head, apply `δ` to (state, symbol) → write a symbol, move L or R, change state. Repeat until you enter `q_accept` (the machine **accepts**) or `q_reject` (**rejects**). The machine may also **never halt**, run forever, and *that possibility is the whole source of undecidability later.*

The leap from a PDA (one stack) to a TM (a full read/write tape with two-way movement) is the leap from "can recognize nesting" to "can compute anything." With a tape you can store intermediate results, revisit them, simulate counters and stacks and registers, you can build, in principle, any data structure and any algorithm. A TM is a stripped-to-the-studs model of *a computer with unlimited memory*.

### What a TM computes

- A TM **decides** a language `L` if it halts on *every* input and accepts exactly the strings in `L`. (Always gives an answer, "decidable.")
- A TM **recognizes** `L` if it accepts exactly the strings in `L`, but on strings *not* in `L` it may reject *or loop forever*. (Says "yes" eventually when the answer is yes, but might never say "no", "recognizable" / "recursively enumerable.")

That gap, *halts always* versus *might run forever*, is the crack through which undecidability enters. Hold it tight; it's the hinge of the whole chapter.

## 📐 The Church - Turing thesis & universal machines

**The Church-Turing thesis.** *Every function that can be computed by any effective/mechanical procedure can be computed by a Turing machine.* This is not a theorem, it can't be proved, because "effective procedure" is an informal notion. It's a thesis, and it's held up against every model anyone has invented: λ-calculus, recursive functions, register machines, your programming language, cellular automata, quantum circuits (for computability). All are **Turing-equivalent**, they compute exactly the same class of functions. So "computable" has one robust meaning: **computable by a Turing machine.** When we later prove "no TM can decide X," the thesis lets us say "no *program in any language* can decide X."

**Universal Turing machines.** A single TM, the **universal TM** `U`, can take as input *the description of any TM `M`* plus an input `w`, and simulate `M` on `w`, accepting iff `M` accepts `w`. In other words, there's *one* machine that can run *any* machine. This is the theoretical seed of the **stored-program computer**: your CPU is a universal machine; programs are data fed to it. (Von Neumann's architecture is this idea in silicon, ties to [Part 17](../17-Semiconductors/17.3-from-transistors-to-chips.md).) The Python interpreter running a Python program is literally a universal machine simulating another machine. We'll exploit `U`'s existence in the halting-problem proof: a program can take another program *as data* and run it.

### Why the model is so robust (and why the thesis holds up)

It's worth pausing on *why* the Church-Turing thesis has never cracked. The reason is that every "obvious upgrade" you could give a Turing machine turns out to add **zero** computational power, it can be simulated by the plain one-tape model. A few that have been proved equivalent:

- **Multiple tapes.** A TM with `k` tapes is no more powerful than one tape, you can store all `k` tapes interleaved on a single tape (with markers for each head position) and simulate a step of the `k`-tape machine by sweeping across. (It costs *time*, a quadratic slowdown, but computes the same functions. The *computability* is identical; only the *complexity* changes, which matters for the second half of this chapter.)
- **Two-way-infinite tape.** Our simulator extends the tape leftward on demand; that's exactly the standard "fold a two-way tape into a one-way tape with two tracks" trick. Same power.
- **Nondeterministic TMs** (guess at each step, accept if some path does). A deterministic TM can simulate one by *breadth-first searching* the tree of nondeterministic choices. Same languages decided, so nondeterminism adds no *computability* power (just like NFA = DFA in [23.1](23.1-automata-and-languages.md)). Crucially, the *known* simulation is **exponentially slower**, and whether that slowdown is avoidable is *precisely the P vs NP question* below.
- **Random-access machines (RAMs), your actual CPU, λ-calculus, register machines, even Conway's Game of Life and Minecraft redstone**, all Turing-equivalent.

This convergence is the empirical backbone of the thesis: wildly different notions of "mechanical computation" all land on the *same* class of computable functions. That's why we can say "undecidable for a TM" and mean "undecidable, full stop, for any computer or programming language ever."

## 💻 Build it - a Turing machine simulator

No black boxes, the TM is a `dict` for δ and a loop with a tape. Let's make it run.

```python
from dataclasses import dataclass, field

BLANK = "_"   # our blank symbol (␣)

@dataclass
class TM:
    states: set
    input_alphabet: set
    tape_alphabet: set
    transition: dict          # {(state, symbol): (new_state, write_symbol, 'L'|'R')}
    start: str
    accept: str
    reject: str

    def run(self, w, max_steps=100_000, trace=False):
        """Run on input w. Returns 'accept', 'reject', or 'loop?' (step cap hit)."""
        tape = list(w) if w else [BLANK]
        head = 0
        state = self.start
        for step in range(max_steps):
            if state == self.accept:
                return ("accept", "".join(tape).strip(BLANK))
            if state == self.reject:
                return ("reject", "".join(tape).strip(BLANK))
            if head < 0:                       # extend the tape leftward
                tape.insert(0, BLANK)
                head = 0
            if head == len(tape):              # extend the tape rightward
                tape.append(BLANK)
            symbol = tape[head]
            key = (state, symbol)
            if key not in self.transition:     # no rule => implicit reject
                return ("reject", "".join(tape).strip(BLANK))
            new_state, write, move = self.transition[key]
            if trace:
                shown = "".join(tape)
                print(f"{step:3} q={state:8} read={symbol} -> write={write} "
                      f"{move} q'={new_state} | {shown[:head]}[{shown[head]}]{shown[head+1:]}")
            tape[head] = write
            head += 1 if move == "R" else -1
            state = new_state
        return ("loop?", "".join(tape).strip(BLANK))    # hit the step cap
```

### Machine 1 - increment a binary number by 1

Algorithm: walk to the right end, then ripple-carry leftward, turn trailing `1`s into `0`s until you hit a `0` (or blank), which you turn into `1`.

```python
inc = TM(
    states={"go_right", "carry", "done"},
    input_alphabet={"0", "1"},
    tape_alphabet={"0", "1", BLANK},
    transition={
        # Phase 1: scan to the right end of the number.
        ("go_right", "0"): ("go_right", "0", "R"),
        ("go_right", "1"): ("go_right", "1", "R"),
        ("go_right", BLANK): ("carry", BLANK, "L"),   # reached the end, step back
        # Phase 2: ripple carry leftward.
        ("carry", "1"): ("carry", "0", "L"),          # 1 + carry = 0, carry on
        ("carry", "0"): ("done", "1", "R"),           # 0 + carry = 1, stop
        ("carry", BLANK): ("done", "1", "R"),         # all 1s: write a new leading 1
    },
    start="go_right", accept="done", reject="REJECT_NONEXISTENT",
)

for n in ["0", "1", "10", "11", "111", "1011"]:
    status, tape = inc.run(n)
    print(f"{n:5} + 1 -> {tape:6} (={int(tape,2)})")
# 0->1, 1->10, 10->11, 11->100, 111->1000, 1011->1100  ✓
```

Watch `111 → 1000`: the carry turns each `1` into `0` and finally writes a fresh `1` on the blank, binary carry, done by a head shuffling on a tape. That's *arithmetic from nothing but read/write/move.*

### Machine 2 - recognize `{ aⁿbⁿ : n ≥ 0 }` (which no DFA could do!)

The language [Chapter 23.1](23.1-automata-and-languages.md) proved non-regular. A TM nails it: repeatedly cross off the leftmost `a` and the leftmost `b` (mark them `X`/`Y`); if they pair up perfectly, accept.

```python
anbn = TM(
    states={"start", "find_b", "back", "check", "ACC", "REJ"},
    input_alphabet={"a", "b"},
    tape_alphabet={"a", "b", "X", "Y", BLANK},
    transition={
        # In 'start': mark an 'a' as X, go find a matching b. If we see Y/blank
        # first (no a's left), verify nothing but Y's remain.
        ("start", "a"): ("find_b", "X", "R"),
        ("start", "Y"): ("check", "Y", "R"),     # no more a's -> check tail
        ("start", BLANK): ("ACC", BLANK, "R"),   # empty / all matched -> accept
        # 'find_b': skip a's and Y's, find the first b, mark it Y, go back.
        ("find_b", "a"): ("find_b", "a", "R"),
        ("find_b", "Y"): ("find_b", "Y", "R"),
        ("find_b", "b"): ("back", "Y", "L"),
        ("find_b", BLANK): ("REJ", BLANK, "L"),  # an a with no b -> reject
        # 'back': walk left to the leftmost unmarked cell, then restart.
        ("back", "a"): ("back", "a", "L"),
        ("back", "Y"): ("back", "Y", "L"),
        ("back", "X"): ("start", "X", "R"),
        ("back", BLANK): ("start", BLANK, "R"),
        # 'check': after a's exhausted, the rest must be Y's only.
        ("check", "Y"): ("check", "Y", "R"),
        ("check", BLANK): ("ACC", BLANK, "R"),
        ("check", "b"): ("REJ", "b", "R"),       # leftover b -> more b than a
    },
    start="start", accept="ACC", reject="REJ",
)

for w in ["", "ab", "aabb", "aaabbb", "aab", "abb", "ba", "aabbb"]:
    status, _ = anbn.run(w)
    print(f"{w!r:8} -> {status}")
# '' accept, 'ab' accept, 'aabb' accept, 'aaabbb' accept,
# 'aab' reject, 'abb' reject, 'ba' reject, 'aabbb' reject  ✓
```

The TM *counts* by crossing off, using the tape as the memory the finite automaton never had. Run it with `trace=True` and you'll see the head march back and forth, pairing a's with b's. This is the concrete proof that the tape buys you genuine new power.

## 📐 Decidability - decidable vs recognizable, and the universe of languages

Now the conceptual map of computability.

- A language is **decidable** (recursive) if some TM *decides* it, halts on all inputs, answers correctly. These are the problems with a true **algorithm** in the everyday sense (always terminates with the right answer).
- A language is **recognizable** (recursively enumerable, r.e.) if some TM *recognizes* it, accepts the yes-instances (eventually), but may loop forever on no-instances.
- Every decidable language is recognizable (a decider is a recognizer that also always halts). The reverse is **false**, there are recognizable-but-undecidable languages, and the halting problem is the star example.

A key symmetry: **`L` is decidable iff both `L` and its complement `L̄` are recognizable.** (Run both recognizers in parallel, dovetailing steps; one must eventually accept, telling you the answer, and it always halts.) So an undecidable-but-recognizable language has a *non-recognizable complement*. That gives us the lay of the land:

```
        decidable  ⊊  recognizable  ⊊  all languages
        (always      (yes-instances    (most languages
         halts)       eventually        aren't even
                      accepted)         recognizable!)
```

**A counting argument shows undecidable problems must exist** (before we even name one). Programs are finite strings, so there are *countably many* programs (you can list them). But languages are arbitrary subsets of `Σ*`, and there are *uncountably many* of those (Cantor, [Chapter 1.3](../01-Foundations/01.3-discrete-math.md)). Countably many programs cannot cover uncountably many languages. So **most languages are not decidable, most aren't even recognizable.** The halting problem just gives us a *specific, natural* one and proves it by hand.

## 📐 The Halting Problem - stated and proved undecidable

**The problem.** Define the language
```
HALT = { ⟨M, w⟩ : M is a Turing machine that halts on input w }
```
(`⟨M, w⟩` means "an encoding of machine M together with input w", possible because a universal machine can read a machine as data.) The **Halting Problem** asks: is `HALT` decidable? I.e., can we write a program `halts(M, w)` that *always* returns, correctly, `True` if `M` halts on `w` and `False` if it loops forever?

**Theorem (Turing, 1936).** `HALT` is **undecidable.** No such `halts` can exist.

### The proof, with the self-reference made intuitive

The argument is a **diagonalization**, the same shape as the "this sentence is false" paradox, made rigorous. Here's the intuition first, then the airtight version.

**Intuition.** Suppose a perfect oracle `halts(M, w)` existed. Then I could build a "contrarian" program `D` that asks the oracle about *itself* and then deliberately does the *opposite*. If the oracle says "D halts," D loops; if the oracle says "D loops," D halts. Whatever the oracle predicts about D, D does the reverse, so the oracle is wrong about D. A perfect oracle that's wrong somewhere is a contradiction. Hence no perfect oracle.

**The rigorous version.** Assume for contradiction that a decider `H` for `HALT` exists:
```
H(⟨M, w⟩) = accept   if M halts on w
            reject   if M loops on w
   (and H always halts.)
```
Build a new machine `D` that takes a single input `⟨M⟩` (a machine description) and does:
```
D(⟨M⟩):
    if H(⟨M, ⟨M⟩⟩) == accept:    # "does M halt when run on its own description?"
        loop forever
    else:                        # H said M loops on ⟨M⟩
        halt
```
`D` is buildable *because* `H` is (we're just calling `H` and then branching). Now run `D` on its **own** description, `D(⟨D⟩)`:

- Suppose `D(⟨D⟩)` **halts**. By D's code, it halts only when `H(⟨D, ⟨D⟩⟩) = reject`, i.e. `H` says "D does *not* halt on ⟨D⟩." But we just supposed it *does* halt. `H` is wrong. ⨯
- Suppose `D(⟨D⟩)` **loops**. By D's code, it loops only when `H(⟨D, ⟨D⟩⟩) = accept`, i.e. `H` says "D *halts* on ⟨D⟩." But we supposed it loops. `H` is wrong. ⨯

Either way `H` gives the wrong answer about `D(⟨D⟩)`, contradicting the assumption that `H` is a correct decider. Therefore **no such `H` exists**: `HALT` is undecidable. ∎

The "diagonal" name: imagine an infinite table whose rows are machines and columns are inputs, entry = halts?/loops?. `D` is built to *disagree with the diagonal*, to differ from machine `Mᵢ` on input `⟨Mᵢ⟩`. So `D` differs from *every* machine in the table somewhere, yet `D` is itself a machine, impossible if the table were a complete catalog of deciders. The self-reference (running `D` on `⟨D⟩`) is the trick that makes a machine "point at itself."

`HALT` *is* recognizable (just simulate `M` on `w` with a universal machine; if it halts, accept), it's the *complement* (machines that loop) that isn't even recognizable. So `HALT` is the canonical recognizable-but-undecidable language.

```python
# We can't decide halting, but we can DEMONSTRATE why a step-bounded check is
# fundamentally incomplete: there's no safe step bound that works for all inputs.
def halts_within(steps, machine, w):
    status, _ = machine.run(w, max_steps=steps)
    return status != "loop?"        # 'accept'/'reject' = halted; 'loop?' = unknown

# For ANY fixed budget, some machine needs more steps than that. You can never
# turn 'loop?' into a definite 'loops forever'. That gap is the undecidability,
# made tangible: the only general method (simulate) can't prove non-halting.
```

## 📐 Reductions - spreading undecidability (and Rice's theorem)

Once we have *one* undecidable problem, we get a flood of them via **reductions**, without redoing diagonalization each time.

**Mapping (many-one) reduction.** `A ≤_m B` means: there's a *computable* function `f` translating instances of `A` into instances of `B` such that `x ∈ A ⟺ f(x) ∈ B`. Read it as "`A` is no harder than `B`": if I could decide `B`, I could decide `A` (translate, then ask the `B`-decider). Contrapositive, the useful direction: **if `A` is undecidable and `A ≤_m B`, then `B` is undecidable** (a decider for `B` would hand us one for `A`, contradiction).

**Example, the "empty language" problem is undecidable.** Let `E_TM = { ⟨M⟩ : M accepts no strings }`. Reduce `HALT` to (the complement of) it: given `⟨M, w⟩`, build a machine `M'` that, on *any* input, ignores it, simulates `M` on `w`, and accepts iff `M` halts on `w`. Then `M'` accepts *everything* (a non-empty language) iff `M` halts on `w`, and accepts *nothing* iff `M` loops. So deciding emptiness would decide halting. Undecidable. The pattern, *wrap the halting question inside a machine, then ask a property question about that machine*, is the engine behind most undecidability proofs.

**Rice's theorem (the big hammer), intuitively.** *Any non-trivial property of the **language** a program recognizes is undecidable.* "Non-trivial" = some machines have it, some don't; "property of the language" = depends only on *what* the machine computes, not *how* (so it's the same for two machines computing the same function). Examples that are therefore **undecidable**: "does this program ever output 42?", "do these two programs compute the same function?", "is this function the constant-zero function?", "does this program have any reachable dead code (semantically)?". The intuition: deciding any such property would let you smuggle in a halting decision (via a reduction like the `E_TM` one). **The practical upshot:** *perfect, general* program analysis is impossible, no tool can soundly-and-completely decide non-trivial semantic questions about arbitrary code. This is *why* compilers, linters, and verifiers are conservative (they approximate, with false positives/negatives) and why "does this program halt / is this code dead / can this overflow?" tools can never be perfect in general.

## 📐 Complexity theory - P and NP

We've drawn the cliff edge (undecidable problems). Now we zoom *inside* the decidable region and ask the practical question: **of the problems we *can* solve, which can we solve *efficiently*?** "Efficiently" gets a precise meaning: **polynomial time** in the input size, `O(nᵏ)` for some constant `k`. (Polynomial = "scales reasonably"; exponential = "blows up." This is the [Big-O](../01-Foundations/01.4-complexity-and-big-o.md) lens applied to whole *classes* of problems.)

We study **decision problems** (yes/no answers, a language) so the theory is clean; optimization problems get a yes/no twin ("is there a solution of size ≥ k?").

**P (Polynomial time).** The class of decision problems decidable by a (deterministic) TM in polynomial time. Informally: problems you can *solve* fast. Examples: is this number even? is there a path between two graph nodes ([BFS](../03-Algorithms/03.4-graph-algorithms.md))? is this list sorted? shortest paths, matching, linear programming, primality (AKS, 2002).

**NP (Nondeterministic Polynomial time).** Two equivalent definitions, the second is the one to *feel*:

1. *Via nondeterminism:* decidable by a **nondeterministic** TM in polynomial time (a machine that can "guess" and accepts if *some* guess-path accepts, like the NFA, but with a tape).
2. *Via verifiers (the intuitive one):* a problem is in NP if a proposed solution (a **certificate/witness**) can be **verified** in polynomial time. You might not be able to *find* the answer fast, but if someone *hands* you a candidate answer, you can *check* it fast.

**The verifier intuition is everything.** NP = "easy to check." A Sudoku you can't solve quickly, but a *filled-in* grid you can check in seconds. A 10,000-city tour you can't find optimally, but a *given* tour you can measure and compare to a budget instantly. NP is the class of problems where *recognizing* a good answer is easy even if *finding* one seems hard.

**P ⊆ NP** trivially: if you can *solve* it fast, you can verify a certificate fast (ignore the certificate and just solve). The trillion-dollar question is whether the containment is strict.

```python
# NP made concrete: SUBSET-SUM. Solving (find a subset summing to T) seems hard;
# VERIFYING a proposed subset is trivially polynomial.
def verify_subset_sum(numbers, target, certificate_indices):
    """Certificate = the indices of the chosen subset. Verification is O(n)."""
    chosen = [numbers[i] for i in certificate_indices]
    return sum(chosen) == target

nums = [3, 34, 4, 12, 5, 2]
print(verify_subset_sum(nums, 9, [2, 4]))   # 4 + 5 = 9  -> True, checked instantly
# Finding such a subset by brute force is 2^n. Checking one is linear. That gap = NP.
```

### The wider landscape of classes (and two theorems that anchor it)

P and NP are two landmarks in a much larger atlas of **complexity classes**, defined by bounding *time* or *space* on deterministic or nondeterministic machines:

```
  L      ⊆  P  ⊆  NP  ⊆  PSPACE  ⊆  EXPTIME  ⊆  EXPSPACE  ⊆ …
 (log                  (poly                 (exponential
  space)                space)                time)
```

- **PSPACE**, solvable using polynomial *memory* (time unbounded). Contains NP and co-NP; many two-player games ("does White have a forced win?") are PSPACE-complete.
- **EXPTIME**, exponential time. Provably *strictly* bigger than P (see below), so it contains genuinely intractable-by-proof problems.
- **co-NP**, problems whose *no*-instances have short certificates (the complement of NP, e.g. "is this formula *un*satisfiable?"). Whether NP = co-NP is open and tied to P vs NP.

Two facts give this hierarchy backbone:

1. **The Time/Space Hierarchy Theorems** prove the chain is *not* all collapse: giving a machine *more* time (or space) provably lets it solve *more* problems. Concretely, `P ⊊ EXPTIME` is a **theorem**, there exist decidable problems that *require* exponential time, no cleverness possible. So "provably intractable" problems genuinely exist (unlike NP-complete, whose hardness is only *conjectured*).
2. Almost every containment shown with `⊆` above is **not known to be strict.** We can't even prove `P ⊊ PSPACE`, though everyone believes it. The single most famous unproven gap is `P` vs `NP`. This is the embarrassing-yet-thrilling state of the field: we have a clean ladder, and can't prove most of its rungs are distinct.

The takeaway for the rest of this section: NP-completeness is about a *conjectured* wall (P ≠ NP). It's a different kind of claim from the *proven* walls (undecidability, the EXPTIME-hardness from the hierarchy theorem). Keep the three tiers straight: **proven-impossible** (undecidable), **proven-intractable** (EXPTIME-hard), and **conjectured-intractable** (NP-hard).

## 📐 NP-completeness - the hardest problems in NP (Cook - Levin, SAT)

Inside NP sits a special club: the **NP-complete** problems, the *hardest* problems in NP, in a precise sense. A problem `B` is **NP-complete** if:

1. `B ∈ NP`, **and**
2. *every* problem `A ∈ NP` reduces to `B` in polynomial time (`A ≤_p B`). (`B` is **NP-hard**.)

The magic of (2): if you find a polynomial algorithm for *one* NP-complete problem, you've got one for *all* of NP, because everything reduces to it. So **the NP-complete problems stand or fall together**: solve any one efficiently ⟹ P = NP; prove any one needs super-polynomial time ⟹ P ≠ NP. They're the linchpin.

**The Cook-Levin theorem (1971).** **SAT**, given a Boolean formula, is there an assignment of true/false to its variables making it true?, is **NP-complete**. This was the first NP-complete problem, proved from scratch. The idea (not the full proof): for *any* NP problem with a poly-time verifier running on an NP machine, you can encode "the machine has an accepting computation on this input" as one giant Boolean formula, variables describe the tape contents and machine state at each step, clauses enforce "each step follows the transition rules." The formula is satisfiable iff the machine accepts. Thus *every* NP problem is, under the hood, a SAT instance. SAT is NP's universal language.

**3-SAT** (SAT restricted to formulas in CNF with exactly 3 literals per clause) is also NP-complete and is the usual *starting point* for further reductions, it's structured enough to be convenient. From SAT/3-SAT, thousands of problems were shown NP-complete by chains of reductions: **CLIQUE, VERTEX-COVER, HAMILTONIAN-PATH, GRAPH-COLORING, SUBSET-SUM, KNAPSACK, TSP (decision form)**, and on and on, the famous Karp's 21 problems and far beyond.

## 💻 Build it - a brute-force SAT solver and a tiny DPLL

Let's make SAT real. A formula in **CNF** is an AND of clauses; each clause is an OR of literals; a literal is a variable or its negation. We'll represent a variable by a positive integer and its negation by the negative.

```python
# CNF as a list of clauses; each clause a list of literals (int; negative = NOT).
# e.g. (x1 OR ¬x2) AND (¬x1 OR x3)  ->  [[1, -2], [-1, 3]]

def is_satisfied(clauses, assignment):
    """assignment: {var: True/False}. Returns True iff all clauses are satisfied."""
    for clause in clauses:
        clause_ok = any(
            (assignment[abs(lit)] if lit > 0 else not assignment[abs(lit)])
            for lit in clause
        )
        if not clause_ok:
            return False
    return True

def brute_force_sat(clauses):
    """Try all 2^n assignments. Exponential - the naive NP search."""
    variables = sorted({abs(lit) for clause in clauses for lit in clause})
    n = len(variables)
    for bits in range(2 ** n):
        assignment = {variables[i]: bool((bits >> i) & 1) for i in range(n)}
        if is_satisfied(clauses, assignment):
            return assignment
    return None       # UNSAT

formula = [[1, -2], [-1, 3], [2, 3], [-3, 1]]
print(brute_force_sat(formula))   # e.g. {1: True, 2: True, 3: True} (a satisfying model)
```

Brute force is `O(2ⁿ · m)`, the unvarnished NP search ("try every certificate"). Real solvers are vastly smarter. The classic improvement is **DPLL** (Davis-Putnam-Logemann-Loveland): backtracking search ([Chapter 3.6](../03-Algorithms/03.6-greedy-and-backtracking.md)) plus two propagation rules that prune huge swaths of the tree.

```python
def dpll(clauses, assignment=None):
    """Backtracking SAT with unit propagation. Still worst-case exponential,
    but dramatically faster in practice - the skeleton of real SAT solvers."""
    if assignment is None:
        assignment = {}

    clauses = simplify(clauses, assignment)
    if clauses is None:               # a clause became empty -> conflict
        return None
    if not clauses:                   # all clauses satisfied
        return fill_in(clauses_vars(orig_vars), assignment)

    # Unit propagation: a clause with one unassigned literal forces its value.
    unit = find_unit(clauses)
    if unit is not None:
        var, val = abs(unit), unit > 0
        return dpll(orig, {**assignment, var: val})

    # Otherwise branch on an unassigned variable: try True, then False.
    var = pick_unassigned(clauses)
    for val in (True, False):
        result = dpll(orig, {**assignment, var: val})
        if result is not None:
            return result
    return None
```

(The helper functions, `simplify`, `find_unit`, etc., are straightforward bookkeeping; the *shape* is the point: **branch + propagate + backtrack**. A self-contained, runnable version:)

```python
def dpll_solve(clauses):
    all_vars = sorted({abs(l) for c in clauses for l in c})

    def value(lit, a):
        v = a.get(abs(lit))
        return None if v is None else (v if lit > 0 else not v)

    def search(a):
        # Evaluate clauses under partial assignment a.
        new = []
        for clause in clauses:
            vals = [value(l, a) for l in clause]
            if any(v is True for v in vals):
                continue                          # clause already satisfied
            remaining = [l for l, v in zip(clause, vals) if v is None]
            if not remaining:
                return None                       # clause fails -> backtrack
            new.append(remaining)
        if not new:                               # every clause satisfied
            return {v: a.get(v, False) for v in all_vars}
        # Unit propagation
        for clause in new:
            if len(clause) == 1:
                lit = clause[0]
                return search({**a, abs(lit): lit > 0})
        # Branch
        var = abs(new[0][0])
        for val in (True, False):
            res = search({**a, var: val})
            if res is not None:
                return res
        return None

    return search({})

print(dpll_solve([[1, -2], [-1, 3], [2, 3], [-3, 1]]))   # a satisfying model
print(dpll_solve([[1], [-1]]))                            # None  (UNSAT: x and ¬x)
```

DPLL (with modern extensions: clause learning, watched literals → **CDCL**) routinely solves SAT instances with *millions* of variables. Despite SAT being NP-complete, engineering crushes most *real* instances, a crucial lesson: NP-completeness is a statement about *worst case*, not a death sentence for every instance.

## 📐 Reductions between problems - 3-SAT → Vertex Cover (worked)

The way we prove a *new* problem NP-complete (or just NP-hard) is to reduce a *known* NP-complete problem to it in polynomial time. Let me do a clean, classic one: **3-SAT ≤_p VERTEX-COVER** (and the closely related CLIQUE). This is the heart of the theory, turning a logic question into a graph question.

**Vertex Cover (decision):** given a graph `G` and integer `k`, is there a set of `k` vertices touching every edge?

**The reduction.** From a 3-CNF formula `φ` with `n` variables and `m` clauses, build a graph `G`:

1. **Variable gadgets:** for each variable `xᵢ`, make two vertices `xᵢ` and `¬xᵢ` joined by an edge (a "choose one" gadget). To cover this edge you must pick at least one of the pair, that *encodes choosing the variable's truth value*.
2. **Clause gadgets:** for each clause (3 literals), make a triangle of 3 vertices, one per literal. A triangle needs ≥ 2 vertices to cover its 3 edges.
3. **Connect:** join each clause-vertex to the matching literal-vertex in the variable gadgets (the clause's "x₁" vertex connects to the variable gadget's `x₁`).

Set `k = n + 2m`. **Claim:** `G` has a vertex cover of size `k` iff `φ` is satisfiable.

- (⇒) From a satisfying assignment: in each variable gadget pick the **true** literal's vertex (`n` vertices, covers the variable edges). Each clause has ≥ 1 true literal; in its triangle pick the **other two** vertices (`2m` vertices, covers all triangle edges, and the connecting edge to the true literal is covered from the variable side). Total `n + 2m = k`. ✓
- (⇐) From a size-`k` cover: it must use exactly 1 per variable gadget and exactly 2 per triangle (any fewer leaves an edge uncovered, count forces it). The variable-gadget choices give a truth assignment; the one *uncovered* vertex in each triangle has its connecting edge covered only if its variable-side literal is chosen true ⟹ that clause has a satisfied literal ⟹ `φ` is satisfied. ✓

The map is clearly polynomial (build `2n + 3m` vertices and `O(n+m)` edges). So **if** we had a fast Vertex-Cover algorithm, we'd have a fast 3-SAT algorithm, hence Vertex Cover is NP-hard, and (it's in NP, verify a cover in poly time) **NP-complete**. The same gadget style maps 3-SAT → CLIQUE → INDEPENDENT-SET → etc. *This* is how the NP-complete galaxy was charted: one founding reduction (Cook-Levin), then a web of poly-time reductions.

```python
# Demo: solve VERTEX-COVER on a small graph by REDUCTION to SAT, then run our solver.
# "Is there a vertex cover of size <= k?" -> SAT formula (a tiny, didactic encoding).
from itertools import combinations

def vertex_cover_via_sat(edges, vertices, k):
    """Encode 'cover of size <= k' as CNF and hand it to dpll_solve.
       Variable v_i (i>=1) = 'vertex i is in the cover'."""
    idx = {v: i + 1 for i, v in enumerate(sorted(vertices))}
    clauses = []
    # (1) every edge is covered: for edge (u,w), clause (v_u OR v_w).
    for (u, w) in edges:
        clauses.append([idx[u], idx[w]])
    # (2) at most k chosen: forbid every (k+1)-subset all-true
    #     -> for each (k+1)-subset, clause "not all of them" = OR of negations.
    for combo in combinations(sorted(vertices), k + 1):
        clauses.append([-idx[v] for v in combo])
    model = dpll_solve(clauses)
    if model is None:
        return None
    return sorted(v for v in vertices if model.get(idx[v]))

V = {"a", "b", "c", "d"}
E = [("a", "b"), ("b", "c"), ("c", "d")]          # a path
print(vertex_cover_via_sat(E, V, k=2))            # e.g. ['b', 'c'] covers all edges
print(vertex_cover_via_sat(E, V, k=1))            # None - no single vertex covers a path of 3 edges
```

We literally **solved one NP problem by reducing it to another** and running a generic solver. That's the practical face of NP-completeness: a SAT solver is a universal weapon, encode your problem as SAT, and modern solvers attack it.

## 📐 What P vs NP MEANS, and why it matters

The **P vs NP** question: *Is P = NP?* Equivalently: if a problem's solutions can be **checked** quickly, can they also be **found** quickly? Almost everyone believes **P ≠ NP** (finding is genuinely harder than checking), but **no one has proved it**, it's one of the seven Clay Millennium Prize Problems ($1M), open since 1971.

Why it's not just academic:

- **Cryptography would collapse if P = NP.** Modern crypto ([Chapter 12.1](../12-Security/12.1-cryptography.md)) rests on problems easy to *verify* but (believed) hard to *solve*: factoring, discrete log. If P = NP, breaking RSA/ECC becomes as easy as using it, every encrypted secret, password hash, and blockchain falls. P ≠ NP is the *implicit assumption* under all of practical security.
- **Optimization would be trivialized.** Thousands of crucial NP-complete problems, scheduling, routing/TSP, protein folding (partially), chip layout, resource allocation, would all get efficient exact algorithms. Logistics, drug design, and operations research would transform overnight.
- **Mathematics itself**, finding proofs is in NP (a proof is a poly-checkable certificate). P = NP would, loosely, mean theorem-proving could be automated. That's how implausible P = NP feels.

So the *expected* answer P ≠ NP is load-bearing: we build security and complexity-based protections *assuming* certain problems are hard. The honest status: **we strongly suspect, but cannot prove, that some easy-to-check problems are hard to solve.**

**NP-hard vs NP-complete** (a common confusion):
- **NP-complete** = in NP **and** NP-hard. The hardest problems *inside* NP (SAT, 3-SAT, Vertex Cover, TSP-decision...). They're decision problems with poly-checkable certificates.
- **NP-hard** = "at least as hard as every NP problem" (everything in NP reduces to it) but **not necessarily in NP**, it might be harder, or not even a decision problem. E.g. the *optimization* TSP ("find the shortest tour," not "is there one ≤ k?") is NP-hard but not known to be in NP; the **halting problem is NP-hard but undecidable** (way beyond NP). So NP-complete ⊂ NP-hard.

```
        ┌──────────── NP-hard ───────────────┐
        │  (everything in NP reduces to me)   │
        │   ┌──── NP ────┐                     │
        │   │  ┌─ P ─┐   │     NP-complete =   │  halting problem
        │   │  └─────┘   │     NP ∩ NP-hard    │  (NP-hard, undecidable)
        │   │   [NP-complete = NP's boundary]  │
        │   └────────────┘                     │
        └─────────────────────────────────────┘
```

### Coping with NP-hardness (since we can't solve them exactly & fast)

Real engineers hit NP-hard problems constantly and ship anyway. The toolkit ([Chapter 3.6](../03-Algorithms/03.6-greedy-and-backtracking.md)):

- **Approximation algorithms**, provably near-optimal in poly time. E.g. a simple greedy gives a **2-approximation** for Vertex Cover (pick both endpoints of any uncovered edge; the result is ≤ 2× the optimum, *guaranteed*). Some problems (TSP with triangle inequality) have constant-factor approximations.
- **Heuristics / metaheuristics**, no guarantee, but great in practice: greedy, local search, simulated annealing, genetic algorithms, and modern **SAT/ILP solvers** (which routinely demolish "hard" real instances).
- **Exponential but pruned**, branch-and-bound, DPLL/CDCL, dynamic programming over subsets (`O(2ⁿ·n)` TSP beats `O(n!)`). Fine when `n` is modest.
- **Restrict the input**, many NP-hard problems are easy on special structure (trees, planar graphs, bounded "treewidth," fixed parameters). Parameterized/FPT algorithms exploit this.
- **Solve the instance you have, not the worst case**, NP-completeness is *worst-case*. Your actual scheduling or routing instance may be easy.

```python
def vertex_cover_2approx(edges):
    """Greedy: while an uncovered edge exists, add BOTH endpoints.
       Guaranteed cover of size <= 2 * optimal. Polynomial."""
    cover, remaining = set(), list(edges)
    while remaining:
        u, w = remaining.pop()
        if u in cover or w in cover:
            continue
        cover.add(u); cover.add(w)
    return cover

print(vertex_cover_2approx([("a","b"),("b","c"),("c","d"),("a","d")]))
# returns a cover within 2x of optimal, instantly - coping with NP-hardness in practice
```

**Part B, SAT solver as a universal weapon.** Use `dpll_solve` plus a reduction to solve a problem you *didn't* write a solver for. Example: **graph 3-coloring** ("can this graph be colored with 3 colors so no edge joins same-colored vertices?") is NP-complete. Reduce it to SAT: variable `c(v, k)` = "vertex v has color k"; clauses say each vertex gets ≥1 color, and adjacent vertices differ.

```python
def three_color_via_sat(vertices, edges):
    # var id for (vertex, color), colors 0,1,2
    vlist = sorted(vertices)
    vid = {(v, k): 1 + 3 * i + k for i, v in enumerate(vlist) for k in range(3)}
    clauses = []
    for v in vlist:
        clauses.append([vid[(v, k)] for k in range(3)])          # >=1 color
        for k1 in range(3):                                      # <=1 color
            for k2 in range(k1 + 1, 3):
                clauses.append([-vid[(v, k1)], -vid[(v, k2)]])
    for (u, w) in edges:                                         # adjacent differ
        for k in range(3):
            clauses.append([-vid[(u, k)], -vid[(w, k)]])
    model = dpll_solve(clauses)
    if model is None:
        return None
    return {v: next(k for k in range(3) if model.get(vid[(v, k)])) for v in vlist}

# A triangle (3-colorable) vs K4 (not 3-colorable):
print(three_color_via_sat({"a","b","c"}, [("a","b"),("b","c"),("a","c")]))  # a coloring
print(three_color_via_sat({"a","b","c","d"},
      [("a","b"),("a","c"),("a","d"),("b","c"),("b","d"),("c","d")]))       # None (K4 needs 4)
```

You solved an NP-complete problem you never wrote special-case code for, by *encoding it as SAT* and unleashing a generic solver. That is exactly how industrial tools (planners, verifiers, schedulers) work: **reduce to SAT/SMT/ILP, then let a powerful solver rip.** The theory of reductions isn't abstract, it's the architecture of real systems.

## ⚠️ Common mistakes

- **"Undecidable" ≠ "hard" / "slow."** Undecidable means *no algorithm exists, ever*, it's not a runtime issue. NP-hard problems, by contrast, *are* decidable (just apparently slow). Don't mix the two boundaries.
- **Thinking the step-bounded simulator "solves" halting.** Running `M` for a billion steps and seeing it not halt proves *nothing*, it might halt at step billion-and-one. That irreducible uncertainty *is* the undecidability.
- **Believing NP means "not polynomial."** NP means *verifiable* in poly time. **P ⊆ NP**, easy problems are in NP too! "NP-hard" is what captures "(probably) not poly."
- **Confusing NP-complete with NP-hard.** NP-complete = NP-hard *and in NP*. The halting problem is NP-hard but *not* in NP (it's undecidable). Optimization-TSP is NP-hard, not known to be in NP.
- **Reduction direction.** To prove `B` is hard, reduce a *known-hard* `A` **to** `B` (`A ≤ B`): "if B were easy, A would be too." Reducing `B` to something easy proves nothing about B's hardness. Getting the arrow backwards is the #1 error.
- **Assuming P ≠ NP is proved.** It's the *conjecture* everyone uses, but it is **open**. Crypto assumes it; no one has proven it.
- **"It's NP-complete, so it's hopeless."** No, NP-completeness is worst-case. Approximation, heuristics, SAT solvers, and structure routinely beat real instances.

## 💼 On the job / interview angle

- **Recognize NP-hardness and pivot.** The senior move when a problem smells NP-hard (scheduling, packing, routing, "find the optimal subset/assignment") is to *say so* and propose coping strategies: "This is essentially Set Cover / TSP, NP-hard. I'd use a greedy 2-approximation, or feed it to an ILP/SAT solver, rather than search for an exact poly algorithm." That signals real CS maturity.
- **Don't try to write a polynomial exact algorithm for an NP-complete problem in an interview**, it's a trap. Identify the reduction ("this is Knapsack / Vertex Cover"), give the DP or approximation, state the complexity honestly.
- **Halting/Rice shows up as "why can't the tool just...".** "Why can't the compiler detect all infinite loops / all dead code / whether two functions are equivalent?" Answer: Rice's theorem, non-trivial semantic properties are undecidable, so analyzers must be conservative. Great way to show depth.
- **Crypto interviews lean on P vs NP.** "Why is RSA secure?" ⟶ factoring is (believed) not in P though verification is easy; security rests on P ≠ NP-style hardness assumptions ([12.1](../12-Security/12.1-cryptography.md)).
- **SAT/SMT solvers are practical tools**, not just theory, used in verification, test generation, configuration, and program analysis. Knowing "reduce my problem to SAT and call a solver" is a genuine engineering skill.
- **Complexity vocabulary is table stakes.** Being fluent in P, NP, NP-complete, reductions, and "polynomial vs exponential" lets you communicate precisely about feasibility, exactly the language of [Chapter 1.4](../01-Foundations/01.4-complexity-and-big-o.md) scaled up to problem classes.

(c) **Not even recognizable**, if both HALT and its complement were recognizable, HALT would be decidable (parallel simulation), contradiction; since HALT is recognizable, its complement is *not*.

**4.** `D` is built to do the *opposite* of whatever the halting-oracle predicts about the machine it's handed. Feed `D` its *own* code: now `D` does the opposite of what the oracle predicts about `D` itself. If the oracle says "this halts," `D` loops; if it says "this loops," `D` halts. So the oracle's prediction about `D` is always wrong, but a correct oracle is never wrong. The self-reference (running `D` on `D`) forces the oracle into a prediction that `D` is specifically engineered to violate. No correct oracle can exist.

def independent_set_via_sat(vertices, edges, k):

    clauses = []

        clauses.append([-vid[u], -vid[w]])

1. **Turing machine** `(Q, Σ, Γ, δ, q₀, q_acc, q_rej)`: finite control + infinite read/write tape + a head that moves L/R. That tape is the unbounded memory that makes it strictly more powerful than a PDA, it can compute `aⁿbⁿ`, arithmetic, *anything computable*.
2. **Church-Turing thesis:** "computable" = "Turing-computable"; every reasonable model is Turing-equivalent. **Universal TM:** one machine simulates any machine (the stored-program idea, your CPU and your Python interpreter).
3. **Decidable** (halts always, right answer) vs **recognizable** (accepts yes-instances, may loop on no-instances). The gap is where undecidability lives; a counting argument (countably many programs, uncountably many languages) guarantees undecidable problems exist.
4. **Halting problem is undecidable**, proved by **diagonalization**: assume an oracle `H`, build a contrarian `D` that does the opposite of `H`'s prediction about itself; `D(⟨D⟩)` makes `H` wrong → contradiction.
5. **Reductions** (`A ≤ B`: "B is at least as hard as A") spread undecidability; **Rice's theorem** says *every non-trivial semantic property of programs is undecidable*, which is why perfect program analyzers can't exist.
6. **P** = solvable in poly time; **NP** = *verifiable* in poly time (certificate/witness). P ⊆ NP. **NP-complete** = in NP and everything in NP reduces to it; **SAT** is the founding one (Cook-Levin); reductions like **3-SAT → Vertex Cover** chart the rest.
7. **P vs NP**: does easy-to-check ⟹ easy-to-solve? Open, believed *no*. It's the bedrock under cryptography and the wall around exact optimization. **NP-hard ⊇ NP-complete** (NP-hard need not be in NP, e.g. halting).
8. **Coping with NP-hardness:** approximation (2-approx Vertex Cover), heuristics, SAT/ILP solvers, restricted inputs, exponential-but-pruned (DPLL/branch-and-bound). And in code I **built a TM simulator, a brute-force and a DPLL SAT solver, and solved coloring / vertex-cover by reducing them to SAT**, the real-world face of this whole theory.
