# Chapter 11.1 - Git & GitHub Deep Dive

> Goal: Stop treating Git as a set of memorized incantations. Understand its internal object model (it's a content-addressed key-value store), the three trees, what merge/rebase/cherry-pick/reset/revert *actually do* to those objects, and how to recover from any disaster with reflog. By the end you can do a full branch+merge+conflict+rebase+cherry-pick walkthrough and run a deliberate disaster-recovery lab.

If cherry-pick feels fuzzy, and you want reset vs revert vs restore nailed down, the fix for all of it is the same: understand the object model, and every command stops being mysterious.

---

## Start here (beginner on-ramp)

Before the internals, the everyday loop, because you'll use it ten times a day forever.

**The analogy: save points in a video game.** Git is a series of save points for your code. Each "commit" is a save point you can return to. Unlike a game, you can have *many* parallel save lines ("branches"), try something risky on one, and either keep it or throw it away without affecting the others. And you can share your save file with teammates and merge everyone's progress together. That's the whole pitch: **never lose work, experiment fearlessly, collaborate without overwriting each other.**

**The four words you'll say constantly:**

- **Repository (repo)**, a project folder that Git is tracking.
- **Commit**, a save point: a snapshot of all your files plus a message describing the change.
- **Branch**, a parallel line of save points, so you can work on a feature without disturbing the main code.
- **Remote**, a copy of the repo hosted elsewhere (GitHub), so you can back it up and share it.

**The everyday loop (memorize this rhythm):**

```
edit files  →  git add .   →  git commit -m "message"  →  git push
            (stage changes) (save a snapshot)         (send to GitHub)
```

**Your first ten minutes:**

```bash
# 1. Set your identity once (goes on every commit you ever make):
git config --global user.name  "Your Name"
git config --global user.email "you@example.com"

# 2. Start a repo and make your first commit:
mkdir myproject && cd myproject
git init                       # turns this folder into a repo
echo "# My Project" > README.md
git status                     # shows README.md as "untracked"
git add README.md              # stage it for the next commit
git commit -m "first commit"   # save the snapshot

# 3. See your history:
git log --oneline              # one line per commit
```

Expected: `git status` lists untracked/modified files in red, staged files in green; `git commit` prints something like `1 file changed`; `git log --oneline` shows your commit with its short hash and message.

**Connect it to GitHub** (create an empty repo on github.com first):

```bash
git remote add origin https://github.com/<you>/myproject.git
git branch -M main
git push -u origin main        # upload; -u remembers the target for next time
```

Refresh the GitHub page, your files are there. From now on, the loop is just `add → commit → push`, with `git pull` to grab teammates' changes.

**The single most reassuring fact in this whole chapter:** Git almost never truly deletes your work. Even after a scary command, there's usually a way back (the **reflog**, covered later). So you can experiment without fear. **Why it matters:** Git is non-negotiable on every software team: it's how all code is stored, reviewed, and shipped. "Walk me through your Git workflow" and "what's the difference between merge and rebase?" are among the most common interview questions for *any* engineering role. Everything below turns the mystery into a model so you're never stuck.

## Concept

### Git is a content-addressed key-value store

Forget "Git tracks diffs." Git stores **snapshots**, addressed by the SHA-1 (now also SHA-256) hash of their content. The `.git/objects` directory *is* the database; the hash *is* the key. There are four object types:

- **blob**, the raw bytes of a file (no name, no metadata, just content).
- **tree**, a directory listing: names + modes + pointers (hashes) to blobs and sub-trees.
- **commit**, a pointer to one tree (the snapshot) + parent commit hash(es) + author/committer + message.
- **tag** (annotated), a named pointer to a commit with its own metadata.

Because the key is the hash of the content, **identical content stores once** and any change produces a new hash. The whole history is a chain of immutable objects.

```
commit ──tree──▶ tree ──▶ blob (main.py)
  │                  └────▶ tree (app/) ──▶ blob (api.py)
  └─parent─▶ commit ──▶ ...
```

Let's prove it in `.git`:

```bash
git init demo && cd demo
echo "hello" > a.txt
git add a.txt
git commit -m "first"

# The commit, its tree, and its blob - all objects keyed by hash:
git cat-file -p HEAD            # shows: tree <hash>, author, message
git cat-file -p HEAD^{tree}     # shows: 100644 blob <hash>  a.txt
git cat-file -p HEAD:a.txt      # shows: hello

# Hash a blob by hand - same algorithm Git uses:
git hash-object a.txt           # prints the blob's SHA, == the one above

# Look in the object store directly:
ls .git/objects/                # dirs named by first 2 hex chars of the hash
```

A **commit points to a tree** (a full snapshot), and to its **parent**. A branch is *not* a copy of anything, see next.

### Refs: branches and HEAD are just pointers

A **ref** is a 41-byte file containing a commit hash. A **branch** is a ref that moves forward when you commit. **HEAD** is a ref pointing at your current branch (or, when "detached," directly at a commit).

```bash
cat .git/refs/heads/main        # the commit hash main points at
cat .git/HEAD                   # "ref: refs/heads/main"
```

This is why branching is **O(1) and cheap**: creating a branch writes a 41-byte file. Switching branches just moves HEAD and updates the working tree. No copying.

### The three trees

Git operations move data between three "trees":

```
 ┌──────────────┐  git add   ┌──────────────┐  git commit  ┌──────────────┐
 │ Working Dir  │ ─────────▶ │ Index/Staging│ ───────────▶ │ HEAD (repo)  │
 │ (your files) │            │ (next commit)│              │ (last commit)│
 └──────────────┘ ◀───────── └──────────────┘ ◀─────────── └──────────────┘
       git restore <file>           git reset           (commit objects)
```

- **Working directory**, the actual files you edit.
- **Index / staging area**, the proposed *next* snapshot. `git add` copies working-dir content here.
- **HEAD**, the last commit on the current branch (the *committed* snapshot).

`git status` is literally diffing these three against each other: "changes staged" = index vs HEAD; "changes not staged" = working dir vs index. Once you see reset/restore as *moving data between these three trees*, those commands stop being confusing (below).

### Branching, then merging

A branch is a movable pointer; commits form a DAG. Merging combines histories two ways:

**Fast-forward**, if the target branch hasn't diverged (your branch is strictly ahead), Git just slides the pointer forward. No merge commit, linear history.

```
before:  main → A      after FF merge of feature:  main, feature → C
feature → A→B→C                                      (main pointer just moves)
```

**3-way merge**, if both branches have new commits since they diverged, Git computes a merge using three inputs: the two branch tips **and their common ancestor** (the "merge base"). It produces a new **merge commit with two parents**.

```
   A───B───C   (main)
    \
     D───E     (feature)
merge → F (parents C and E)
```

**How conflicts arise:** a conflict happens only when *both sides changed the same region of the same file* relative to the merge base. Git can auto-merge non-overlapping changes; overlapping ones it can't decide, so it marks them:

```
<<<<<<< HEAD
the version on my current branch
=======
the version from the branch being merged
>>>>>>> feature
```

Resolve by editing to the intended result (removing the markers), `git add` the file, then `git commit` (or `git merge --continue`).

### Rebasing - what it *really* does

Rebase **replays** your commits onto a new base. It doesn't "move" commits; it creates **new commits** with the same changes but different parents (and therefore **different hashes**).

```
before:                         git rebase main (from feature):
A───B───C   (main)              A───B───C        (main)
 \                                       \
  D───E   (feature)                       D'──E'  (feature)  ← new commits!
```

`D'`/`E'` are copies of `D`/`E` re-applied on top of `C`. Result: a linear history, no merge commit. The tradeoff is that hashes change.

**The golden rule of rebase: never rebase commits that you've already pushed and others may have based work on.** Because rebase rewrites hashes, rebasing shared history forces everyone else into a painful divergence. Rebase *local, unpushed* work freely; merge (or only rebase your own un-shared branch) for anything shared.

### Interactive rebase - surgery on history

`git rebase -i <base>` opens an editor listing commits with actions:

```
pick   a1b2c3 add login endpoint
squash 4d5e6f fix typo in login        # fold into previous commit
reword 7g8h9i add logout               # change the message
drop   0j1k2l debug print              # remove the commit entirely
# reorder lines to reorder commits
```

Actions: `pick` (keep), `reword` (edit message), `edit` (stop to amend), `squash`/`fixup` (combine into the previous), `drop` (delete), and reordering by moving lines. Use it to clean up a messy feature branch into a tidy series of logical commits **before** opening a PR, never on shared history.

### Cherry-pick - apply one commit elsewhere (the one people fumble)

`git cherry-pick <commit>` takes the **diff introduced by that single commit** and applies it as a **new commit** on your current branch. It does *not* bring the commit's history or its parents, just that one change.

How it differs:

- **Merge** brings *all* commits of a branch and records the relationship (merge commit, shared ancestry).
- **Rebase** moves *your whole branch's* commits onto a new base.
- **Cherry-pick** copies *one (or a few) specific* commit(s), with no ancestry link, you get a brand-new commit (new hash) containing the same change.

Worked example, a hotfix made on `main` that you urgently need on a `release` branch, without dragging the rest of main:

```bash
git log --oneline main
#   e3f1a2 (HEAD -> main) add new dashboard      ← don't want this on release
#   c9d4b7 fix: null-pointer in auth (HOTFIX)    ← want THIS on release
#   a1b2c3 baseline

git switch release
git cherry-pick c9d4b7
#   Git applies ONLY the diff from c9d4b7 as a new commit on release.

git log --oneline release
#   f7a8c9 (HEAD -> release) fix: null-pointer in auth   ← new commit, new hash!
#   ...                                                    (the dashboard commit is NOT here)
```

When to reach for it: backporting a fix to a maintenance branch, grabbing one commit from an abandoned branch, or pulling a single commit out of a PR. If the picked commit conflicts, you resolve it just like a merge, then `git cherry-pick --continue`. (You can pick a range: `git cherry-pick A..B`.)

### reset vs revert vs checkout/restore

These confuse everyone because they touch *different* trees. Anchor on the three-trees model.

- **`git reset`**, moves the current **branch pointer** (and optionally the index/working dir) to a target commit. Three modes by *how far* the change reaches:
  - `--soft`, move HEAD only; index + working dir unchanged. (Commits become "uncommitted but staged", great for re-doing the last commit.)
  - `--mixed` (default), move HEAD + reset the **index**; working dir untouched. (Changes become "unstaged.")
  - `--hard`, move HEAD + reset index **and** working dir. **Destructive**, discards uncommitted work.

  ```
  reset --soft  HEAD~1   →  undo commit, keep changes STAGED
  reset --mixed HEAD~1   →  undo commit, keep changes UNSTAGED  (default)
  reset --hard HEAD~1 → undo commit, DISCARD changes destructive
  ```

- **`git revert <commit>`**, creates a **new commit that undoes** the changes of a previous commit. History is *preserved* (nothing rewritten). This is the **safe** way to undo something already pushed/shared, no force-push, no rewriting others' history.

  Use **reset** to rewrite *local, unshared* history; use **revert** to undo *shared/published* commits.

- **`git checkout` / `git restore`**, modern Git split the overloaded `checkout` into two: **`git switch`** (change branches) and **`git restore`** (restore file contents). `git restore <file>` copies the file from the index (or `--source=HEAD`) back into the working dir, discarding *uncommitted* edits to that file. It touches files, not branch pointers.

### Stash

`git stash` shelves uncommitted changes (working dir + index) so you have a clean tree, e.g. to switch branches mid-task. Internally it's just commits on a hidden ref.

```bash
git stash push -m "wip auth"   # save & clean working dir
git stash list
git stash pop                  # reapply most recent and drop it
git stash apply stash@{1}      # reapply a specific one, keep it in the list
```

### Reflog - your safety net

The **reflog** records every place HEAD (and each branch) has *been*, locally, even after "destructive" operations. Because Git objects aren't deleted immediately (they're unreachable, then garbage-collected later), the reflog lets you recover almost anything, a bad `reset --hard`, a deleted branch, a botched rebase.

```bash
git reflog
#   a1b2c3 HEAD@{0}: reset: moving to HEAD~3
#   d4e5f6 HEAD@{1}: commit: the work I just "lost"   ← here it is
git reset --hard d4e5f6        # or: git checkout -b recover d4e5f6
```

If you remember nothing else from this chapter: **`git reflog` first, panic never.**

### Tags & releases

Tags name a commit permanently, `v1.4.2`. Prefer **annotated** tags (they're real objects with metadata). GitHub Releases attach notes/artifacts to a tag.

```bash
git tag -a v1.4.2 -m "release 1.4.2"
git push origin v1.4.2
```

### .gitignore

Lists path patterns Git won't track (`node_modules/`, `.env`, `*.pyc`, build output). Note: it only affects **untracked** files, already-tracked files keep being tracked (use `git rm --cached` to stop).

### Remotes & tracking branches

A **remote** (`origin`) is a named pointer to another repo. **Remote-tracking branches** (`origin/main`) are local read-only mirrors of the remote's state, updated by `fetch`. An **upstream/tracking** relationship links your local `main` to `origin/main` so `git pull`/`git push` know the target.

```bash
git remote -v
git fetch origin                 # update origin/* refs (no merge)
git pull                         # fetch + merge (or --rebase) into current branch
git push -u origin feature       # push & set upstream tracking
```

`fetch` is always safe (just updates remote-tracking refs); `pull` changes your working branch.

### PR workflow & code review on GitHub

1. Branch off `main`, commit, `git push -u origin feature`.
2. Open a **Pull Request**, proposes merging `feature` → `main`.
3. CI runs (lint/test/scan, see 10.3); reviewers comment, request changes, approve.
4. Push fixes to the same branch (the PR updates automatically).
5. Merge: **merge commit** (preserves all commits), **squash** (one tidy commit, common for trunk-based), or **rebase-merge** (linear, no merge commit).
6. Delete the branch.

Branch protection requires passing checks + approvals before merge: this is where the CI gates from 10.3 enforce quality.

### Branching strategies

- **Trunk-based**, everyone integrates into `main` constantly via short-lived branches; small frequent PRs; pairs with feature flags + CI/CD. Favored for continuous delivery (less merge pain, faster integration).
- **Git-flow**, long-lived `main` + `develop` + `feature/*` + `release/*` + `hotfix/*` branches. Heavier; suits scheduled releases / versioned products, but more merge overhead.

Default to trunk-based unless you actually ship versioned releases on a cadence.

### Fixing mistakes & bisect

- **Recover lost commits** → reflog (above).
- **Undo a bad merge** → if unpushed, `git reset --hard ORIG_HEAD` (Git saves the pre-merge HEAD there); if pushed, `git revert -m 1 <mergecommit>` (the `-m 1` says "keep parent 1's line").
- **`git bisect`**, binary search for the commit that introduced a bug:
  ```bash
  git bisect start
  git bisect bad                 # current commit is broken
  git bisect good v1.3.0         # this old tag was fine
  # Git checks out the midpoint; you test and mark good/bad; it halves each time
  git bisect good   # or: git bisect bad
  # ... until it names the first bad commit
  git bisect reset
  ```
  With `git bisect run <test-script>` it automates the whole search.

## Build it: branch → merge (with conflict) → rebase → cherry-pick walkthrough

A full terminal session. Run it.

```bash
# --- setup ---
git init store && cd store
echo "line1" > app.txt
git add app.txt && git commit -m "init: app.txt"

# --- branch + diverge to force a conflict ---
git switch -c feature
echo "feature change" >> app.txt
git commit -am "feature: append feature line"

git switch main
echo "main change" >> app.txt          # same region as feature -> will conflict
git commit -am "main: append main line"

# --- 3-way merge that conflicts ---
git merge feature
# CONFLICT (content): Merge conflict in app.txt
cat app.txt
#   line1
#   <<<<<<< HEAD
#   main change
#   =======
#   feature change
#   >>>>>>> feature
# resolve: edit app.txt to the intended result, remove markers
printf "line1\nmain change\nfeature change\n" > app.txt
git add app.txt
git commit --no-edit                    # completes the merge commit
git log --graph --oneline               # see the merge commit with two parents

# --- rebase demo on a fresh branch (linear history) ---
git switch -c topic
echo "topic work" > topic.txt
git commit -am "topic: add topic.txt"
git switch main
echo "more main" >> app.txt
git commit -am "main: more main work"
git switch topic
git rebase main                         # replays topic's commit onto new main tip
git log --oneline --graph main topic    # topic now sits on top of main, linear

# --- cherry-pick a single commit between branches ---
git switch main
echo "URGENT FIX" > hotfix.txt
git commit -am "fix: urgent hotfix"
HOTFIX=$(git rev-parse HEAD)            # capture the hotfix commit hash
git switch -c release main~1            # release branch BEFORE the hotfix
git cherry-pick "$HOTFIX"               # bring ONLY the hotfix over
ls                                      # hotfix.txt is here; nothing else from main
git log --oneline                       # a NEW commit (different hash), same change

# --- interactive rebase cleanup (squash two commits) ---
git switch topic
echo "x" >> topic.txt && git commit -am "wip"
echo "y" >> topic.txt && git commit -am "more wip"
git rebase -i HEAD~2
#   change the second line from 'pick' to 'squash', save -> two commits become one
```

Things to notice while doing it: the merge produced a commit with **two parents**; the rebase **rewrote** topic's commit to a new hash; the cherry-pick produced a **brand-new commit** unrelated to main's history but carrying the same diff.

## Mini-project: Git disaster-recovery lab

Deliberately create messes, then recover each. This builds the muscle memory so a real incident is boring.

```bash
git init lab && cd lab
for i in 1 2 3 4; do echo "commit $i" > f$i.txt; git add .; git commit -m "c$i"; done
```

### Disaster 1 - bad `reset --hard` (lost commits)

```bash
git reset --hard HEAD~2          # "oops, blew away c3 and c4"
git log --oneline                # only c1, c2 remain
# RECOVER:
git reflog                       # find the hash that was HEAD before the reset (HEAD@{1})
git reset --hard HEAD@{1}        # back to c4
git log --oneline                # c1..c4 restored
```
Lesson: `--hard` is destructive *to the working tree*, but the commits live on in the object store and the **reflog** points to them until GC.

### Disaster 2 - detached HEAD with new work

```bash
git checkout HEAD~2              # detached HEAD on c2
echo "experiment" > exp.txt
git add . && git commit -m "experimental work"
git switch main                  # WARNING: that commit is now unreferenced/orphaned
# RECOVER:
git reflog                       # find the experimental commit's hash
git branch saved-experiment <hash>   # give the orphan a branch so it's safe
git log --oneline saved-experiment
```
Lesson: commits made in detached HEAD aren't on any branch; if you walk away they become unreachable. **reflog** finds them; create a branch to keep them.

### Disaster 3 - committed to the wrong branch

```bash
git switch main
echo "feature thing" > feat.txt
git add . && git commit -m "feat: should've been on a branch"   # oops, on main
# RECOVER: move it to a new branch, restore main
WRONG=$(git rev-parse HEAD)
git branch feature-x             # create branch pointing at the wrong commit
git reset --hard HEAD~1          # rewind main (commit still safe on feature-x)
git switch feature-x             # the commit is here now
git log --oneline                # feat commit lives on feature-x, main is clean
```
(If main was already pushed/shared, use `git revert` on main instead of `reset`, then re-apply via cherry-pick on the right branch.)

### Disaster 4 - undo a bad merge

```bash
git switch main
git switch -c badbranch && echo bad > bad.txt && git commit -am "bad work"
git switch main && git merge badbranch       # merged something we didn't want
# RECOVER (unpushed): ORIG_HEAD holds the pre-merge tip
git reset --hard ORIG_HEAD
# RECOVER (already pushed): don't rewrite history - revert the merge commit instead
#   git revert -m 1 <merge-commit-hash>
```

### Disaster 5 - find the commit that broke a test (bisect)

```bash
# Assume some commit broke things between a known-good tag and HEAD:
git bisect start
git bisect bad HEAD
git bisect good <known-good-hash>
# Git checks out midpoints; test each and mark good/bad until it names the culprit.
git bisect reset
```

Deliverable: run all five, and write yourself a one-line cheat for each ("wrong branch → branch here, reset main"; "lost commit → reflog then reset/branch"; "shared bad commit → revert, never reset").

## Guided walkthrough: a realistic feature-branch + pull-request day

The internals and disaster labs are essential, but here's the *boring, correct, everyday* flow, the one you'll do most on a real team. Each step with the expected result.

### Step 1 - start from an up-to-date main

```bash
git switch main
git pull                       # get teammates' latest before branching
```

Branching off stale `main` is how you create needless conflicts later. Always pull first.

### Step 2 - branch for the work

```bash
git switch -c feat/add-login   # create + switch in one command
```

Name branches descriptively (`feat/`, `fix/`, `chore/` prefixes are common). The branch is free: it's just a 41-byte pointer (you proved that earlier).

### Step 3 - commit in small, logical chunks

```bash
# ...edit files...
git add -p                     # stage HUNK BY HUNK - review each change as you go
git commit -m "feat: add login endpoint"
# ...more edits...
git commit -am "feat: validate login payload"
```

`git add -p` is a pro habit: it walks you through each change so your commits are intentional and reviewable, not a giant blob. Each commit should be a coherent step with a clear message.

### Step 4 - push and open a PR

```bash
git push -u origin feat/add-login
# GitHub prints a URL to open the PR, or use the GitHub CLI:
gh pr create --fill            # opens a PR with your commits/messages prefilled
```

On GitHub the PR shows the diff, runs CI (the pipeline from 10.3), and lets reviewers comment.

### Step 5 - respond to review and keep the branch current

```bash
# Address comments with more commits:
git commit -am "fix: handle empty password per review"
git push                       # the PR updates automatically

# If main moved while your PR was open, integrate it. Two options:
git fetch origin
git rebase origin/main         # linear history (rewrites YOUR unshared commits) - preferred for a solo branch
#   or:
git merge origin/main          # safe, creates a merge commit - fine for shared branches
```

A common review request is "rebase on main." Because *your* feature branch's commits aren't shared elsewhere, rebasing them is safe and gives a clean linear PR.

### Step 6 - clean up history before merge (optional but classy)

```bash
git rebase -i origin/main      # squash "fix typo"/"wip" commits into logical ones
git push --force-with-lease    # update the PR; --force-with-lease is the SAFE force
```

`--force-with-lease` refuses to overwrite the remote if someone else pushed in the meantime: it's the seatbelt version of `--force`. **Never plain `--force` a shared branch.**

### Step 7 - merge and tidy

The reviewer approves, CI is green, and you click **Squash and merge** (common for trunk-based: one tidy commit on main). Then:

```bash
git switch main
git pull
git branch -d feat/add-login           # delete the local branch (merged)
git push origin --delete feat/add-login # delete the remote branch
```

That's the loop a working engineer repeats every day: pull → branch → small commits → push → PR → review → rebase/squash → merge → delete. Master this and you're immediately productive on any team.

## Common mistakes

- **Committing as the wrong identity.** Forgetting `git config user.name/email` taints every commit's authorship. **Fix:** set it globally once (and per-repo if you mix work/personal).
- **Committing secrets or junk.** `.env`, API keys, `node_modules/`, build output. Once pushed, a secret is compromised *even if you delete it later* (it's in history). **Fix:** a good `.gitignore` *before* the first commit; if leaked, rotate the secret and scrub history.
- **`git add .` blindly.** Stages everything, including files you didn't mean to. **Fix:** `git status` first, `git add -p` to review hunks.
- **Giant, vague commits** ("stuff", "wip", "fixes"). Unreviewable and un-bisectable. **Fix:** small commits, imperative messages ("add login endpoint").
- **Rebasing shared/pushed history.** Rewrites hashes others have based work on → painful divergence. **Fix:** the golden rule, rebase only local, unpushed commits; use `merge` (or `revert`) on shared history.
- **`git push --force` on a shared branch.** Can erase teammates' commits. **Fix:** `--force-with-lease`, and never force-push `main`.
- **`git reset --hard` thinking it's safe.** Discards uncommitted work in the working tree. **Fix:** know it's destructive; `git stash` first if unsure; remember the reflog recovers *committed* work.
- **Pulling with uncommitted changes and getting conflicts.** **Fix:** commit or `git stash` before `git pull`.
- **Confusing `reset` and `revert`.** Using `reset` on published history rewrites it for everyone. **Fix:** `revert` (a new undo-commit) for anything already shared.
- **Working directly on `main`.** No isolation, no review. **Fix:** always branch; protect `main` with required reviews + CI.

## On the job / interview angle

Git is the one tool you'll use literally every working day, and "how comfortable are you with Git?" is asked in nearly every engineering interview. You won't usually be quizzed on obscure flags, they want to see that you understand branching, merging, PRs, and how to recover from mistakes without panicking. The disaster-recovery lab above is *exactly* the kind of competence that builds confidence (yours and the interviewer's).

**What you actually do with it at work:**
- The daily PR loop (the guided walkthrough above) on every change.
- Review teammates' PRs and respond to reviews on yours.
- Resolve merge conflicts calmly.
- Recover from mistakes (reflog, revert) instead of re-cloning in a panic.

**Representative interview questions (with crisp answers):**

1. *"merge vs rebase?"* → Merge combines branches with a merge commit (preserves true history, non-linear); rebase replays your commits onto a new base (linear history, but rewrites hashes). Golden rule: don't rebase shared history.
2. *"What's the difference between `git fetch` and `git pull`?"* → Fetch updates remote-tracking refs only (always safe); pull = fetch + merge/rebase into your current branch.
3. *"reset vs revert?"* → Reset moves the branch pointer (rewrites history; use on local/unshared work); revert adds a new commit that undoes a change (safe for shared/published commits).
4. *"What do `reset --soft/--mixed/--hard` do?"* → Move HEAD only (changes stay staged) / move HEAD + reset index (changes unstaged, default) / move HEAD + reset index + working dir (destructive).
5. *"What is cherry-pick and when do you use it?"* → Apply the diff of one specific commit as a new commit on your branch; for backporting a hotfix to a release branch without dragging the rest.
6. *"How do you resolve a merge conflict?"* → Edit the marked regions to the intended result, remove the `<<<</====/>>>>` markers, `git add` the file, then commit / `--continue`.
7. *"I lost commits after `git reset --hard`. Now what?"* → `git reflog` to find the prior HEAD, then `git reset --hard <hash>` or `git branch recover <hash>`.
8. *"What is HEAD / a branch, really?"* → A branch is a movable pointer (a ref = a file with a commit hash); HEAD points at your current branch (or a commit when detached).
9. *"Squash vs merge commit vs rebase-merge for PRs?"* → One tidy commit / preserve all commits + a merge commit / linear without a merge commit. Squash is common for trunk-based.
10. *"Trunk-based vs git-flow?"* → Short-lived branches integrated into main constantly (pairs with CI/CD + feature flags) vs long-lived develop/release/hotfix branches (suits scheduled versioned releases).
11. *"How would you find which commit introduced a bug?"* → `git bisect`, binary search marking commits good/bad (or automated with `git bisect run`).

**Tip:** if you can confidently say "first I'd run `git reflog`" to any "I lost my work" question, you signal real fluency, most people panic and re-clone.

## Exercises

Do these in throwaway repos. Solutions follow.

1. **(easy)** Initialize a repo, make three commits, and show the history with `git log --oneline --graph`.
2. **(easy)** Create a `.gitignore` that ignores `*.log` and `secrets.env`; create those files and confirm `git status` doesn't list them.
3. **(easy)** Stage only *part* of a file's changes using `git add -p`, commit, and show the remaining unstaged change.
4. **(medium)** Create a branch, commit on it, switch back to main, and use `git log --oneline --all --graph` to see both lines.
5. **(medium)** Force a merge conflict between two branches editing the same line, resolve it, and complete the merge.
6. **(medium)** Rebase a feature branch onto main and show with `git log` that the commits have *new hashes* but the same changes.
7. **(medium)** Cherry-pick a single commit from one branch onto another and confirm only that change came over (not the branch's other commits).
8. **(hard)** Make a commit, then "undo" it three different ways in three clones: `reset --soft`, `reset --hard`, and `revert`. Describe what each leaves in the working tree and history.
9. **(hard)** Simulate "committed to the wrong branch": commit on `main` by accident, move it to a new branch, and clean up `main`, without losing the commit.
10. **(hard)** Use `git bisect` to find a commit that introduced a failing test in a 8-commit history (write a tiny test script and use `git bisect run`).

### Solutions

1. ```bash
   git init r && cd r
   for i in 1 2 3; do echo $i > f$i.txt; git add .; git commit -m "c$i"; done
   git log --oneline --graph
   ```

2. ```bash
   printf "*.log\nsecrets.env\n" > .gitignore
   touch app.log secrets.env
   git status        # only .gitignore shows; app.log and secrets.env are ignored
   ```
   (`.gitignore` affects *untracked* files; already-tracked files keep being tracked.)

3. With a file that has two separate edits, `git add -p` prompts per hunk: press `y` to stage one, `n` to skip the other, then `git commit`. `git status` then shows the file as both "staged" and "not staged", the unstaged hunk remains.

4. ```bash
   git switch -c feature
   echo x > feat.txt && git add . && git commit -m "feat work"
   git switch main
   git log --oneline --all --graph   # two diverging lines: main and feature
   ```

5. ```bash
   git switch -c a; printf "L1\nMINE\n" > f.txt; git add .; git commit -m a
   git switch main; printf "L1\nTHEIRS\n" > f.txt; git add .; git commit -m main
   git merge a      # CONFLICT on f.txt
   printf "L1\nMINE+THEIRS\n" > f.txt   # resolve: remove markers, set final content
   git add f.txt && git commit --no-edit
   ```

6. ```bash
   git switch -c feat; echo w > w.txt; git commit -am "feat: w"
   git switch main; echo m >> f.txt; git commit -am "main: move on"
   git switch feat; git log --oneline           # note feat's commit hash
   git rebase main
   git log --oneline                            # SAME message, DIFFERENT hash, replayed
   ```

7. ```bash
   git switch -c src
   echo keep > keep.txt && git commit -am "want this"
   echo skip > skip.txt && git commit -am "do NOT want this"
   PICK=$(git rev-parse HEAD~1)                  # the "want this" commit
   git switch main && git cherry-pick "$PICK"
   ls            # keep.txt is here; skip.txt is NOT
   ```

8. With identical starting commit in three clones:
   - `git reset --soft HEAD~1` → commit undone, its changes remain **staged**; history rewound by one.
   - `git reset --hard HEAD~1` → commit undone, changes **discarded** from the working tree; history rewound. (Recoverable via reflog.)
   - `git revert HEAD` → a **new commit** is added that undoes the change; original commit **stays** in history. Safe for shared branches.

9. ```bash
   git switch main
   echo oops > feat.txt && git add . && git commit -m "should be on a branch"
   git branch feature-x          # branch points at the wrong commit (saves it)
   git reset --hard HEAD~1       # rewind main; commit is safe on feature-x
   git switch feature-x          # the work is here, main is clean
   ```

10. ```bash
    # test.sh exits non-zero when the bug is present:
    cat > test.sh <<'EOF'
    grep -q "BUG" file.txt && exit 1 || exit 0
    EOF
    chmod +x test.sh
    git bisect start
    git bisect bad HEAD
    git bisect good <first-commit-hash>
    git bisect run ./test.sh      # Git auto-runs the test, halving each time,
                                  # then prints "<hash> is the first bad commit"
    git bisect reset
    ```

## Mini-project 2: simulate a two-person team (conflicts, reviews, hotfixes)

The disaster lab built recovery muscle solo. This one rehearses *collaboration*, the part that actually trips people up on real teams, by playing both developers yourself with two clones of one "remote."

```bash
# Set up a shared "remote" (a bare repo) and two clones = two teammates
mkdir -p team && cd team
git init --bare central.git
git clone central.git alice
git clone central.git bob

# Alice seeds main
cd alice
printf "line1\nline2\nline3\n" > app.txt
git add . && git commit -m "init app.txt" && git push origin main
cd ../bob && git pull origin main
```

### Scenario 1 - concurrent work, then a real merge conflict

```bash
# Alice edits line2 on a branch and merges to main
cd ../alice
git switch -c alice/feature
sed -i '' 's/line2/line2 ALICE/' app.txt 2>/dev/null || sed -i 's/line2/line2 ALICE/' app.txt
git commit -am "alice: change line2"
git switch main && git merge alice/feature && git push origin main

# Bob, unaware, edited the SAME line on his own branch off the OLD main
cd ../bob
git switch -c bob/feature
sed -i '' 's/line2/line2 BOB/' app.txt 2>/dev/null || sed -i 's/line2/line2 BOB/' app.txt
git commit -am "bob: change line2"
git switch main && git pull origin main      # Bob now has Alice's change
git merge bob/feature                        # CONFLICT on line2
```

Bob resolves by choosing the intended final content (maybe both: `line2 ALICE+BOB`), `git add app.txt`, `git commit`, `git push`. **Lesson:** conflicts aren't errors; they're Git refusing to guess when two people changed the same region. The fix is always: read both sides, edit to the right answer, add, commit.

### Scenario 2 - a PR-style review with a fix requested

Simulate the review loop: Bob opens a PR (`gh pr create` if using GitHub, or just push a branch). Alice "reviews" and requests a change. Bob addresses it with another commit and pushes; the branch updates. Before merge, Bob tidies:

```bash
cd ../bob
git switch bob/feature
echo "extra" >> app.txt && git commit -am "wip address review"
echo "more" >> app.txt && git commit -am "wip more"
git rebase -i HEAD~2          # squash the two wip commits into one clean commit
git push --force-with-lease   # safe force to update the PR
```

**Lesson:** clean up *your own* branch's noisy commits with interactive rebase + `--force-with-lease` before merge, never the shared `main`.

### Scenario 3 - urgent hotfix backported with cherry-pick

A bug ships to a `release/1.0` branch, but the fix was just made on `main` along with unrelated work. Backport *only* the fix:

```bash
cd ../alice
git pull origin main
git switch -c release/1.0 main~2        # release branch at an older point
git push origin release/1.0
# the fix commit lives on main:
git switch main
echo "FIXED" >> app.txt && git commit -am "fix: critical bug"
FIX=$(git rev-parse HEAD)
git switch release/1.0
git cherry-pick "$FIX"                   # only the fix, not main's other commits
git push origin release/1.0
```

**Lesson:** cherry-pick is the backport tool, it grabs one commit's diff without dragging the rest of `main` onto the maintenance branch.

Deliverable: run all three scenarios and write a short `TEAM-NOTES.md` capturing (1) the conflict-resolution recipe, (2) when to rebase vs merge in a team, and (3) the cherry-pick backport pattern. This is the collaboration half of Git that the solo labs can't teach, and it's exactly what day-to-day team work feels like.
