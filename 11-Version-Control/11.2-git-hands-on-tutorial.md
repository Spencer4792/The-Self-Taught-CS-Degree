# Chapter 11.2 - Git Hands-On Tutorial (do it with me)

> Goal: by the end of this you'll have *typed* every core git command at a real terminal, init, commit, branch, merge, resolve a conflict, push to GitHub, open a Pull Request, undo mistakes safely, stash, cherry-pick, and recover with reflog. This is the muscle-memory companion to **Chapter 11.1**, which explains *why* git works the way it does (the DAG, blobs/trees/commits, the three areas). Here we just *do it*. Keep 11.1 open in another tab if you want the theory behind a step.

**Start here**

The deal with this chapter: open a terminal and *actually run* every command. Don't skim it. Git is a motor skill, reading about it builds zero ability. Typing it builds all of it. We'll show you the exact command and the exact output to expect, so you can sanity-check that you're on the rails. If your output differs, stop and figure out why before moving on.

A few conventions for this chapter:
- Lines starting with `$` are commands *you* type (don't type the `$`).
- Everything else is output the terminal prints back.
- `# like this` are comments, not something to type.
- When we say "a throwaway project," we mean it: we're making a folder you can delete at the end. Nothing here touches your real work.

Let's go.

## Build it

### Step 0 - Check git is installed

```
$ git --version
git version 2.43.0
```

Any version 2.30+ is fine. If you get "command not found":

- **macOS:** `xcode-select --install` (installs git), or `brew install git` for the latest.
- **Ubuntu/Debian:** `sudo apt update && sudo apt install git`
- **Windows:** install "Git for Windows" from git-scm.com, which gives you Git Bash, use that terminal so these commands match.

### Step 1 - One-time global configuration

Git stamps your name and email onto every commit. Set them once, globally, and never think about it again.

```
$ git config --global user.name "Your Name"
$ git config --global user.email "you@example.com"
```

Make the default branch `main` (the modern convention; older git defaulted to `master`):

```
$ git config --global init.defaultBranch main
```

Tell git to use your preferred editor for commit messages. VS Code:

```
$ git config --global core.editor "code --wait"
# or for vim:  git config --global core.editor "vim"
# or nano:     git config --global core.editor "nano"
```

A couple of quality-of-life settings worth turning on:

```
$ git config --global pull.rebase false       # merge on pull (predictable default)
$ git config --global push.autoSetupRemote true  # 'git push' just works on new branches
$ git config --global color.ui auto            # colorized output
```

Now set up a few **aliases**, these save thousands of keystrokes over a career:

```
$ git config --global alias.st status
$ git config --global alias.co checkout
$ git config --global alias.br branch
$ git config --global alias.cm "commit -m"
$ git config --global alias.lg "log --oneline --graph --decorate --all"
$ git config --global alias.last "log -1 HEAD --stat"
$ git config --global alias.unstage "restore --staged"
```

Verify everything stuck:

```
$ git config --global --list
user.name=Your Name
user.email=you@example.com
init.defaultbranch=main
core.editor=code --wait
pull.rebase=false
push.autosetupremote=true
color.ui=auto
alias.st=status
alias.co=checkout
alias.br=branch
alias.cm=commit -m
alias.lg=log --oneline --graph --decorate --all
alias.last=log -1 HEAD --stat
alias.unstage=restore --staged
```

These live in `~/.gitconfig`, open it and you'll see them as plain text. You can edit that file directly too.

### Step 2 - Create a throwaway project and `git init`

```
$ cd ~          # or wherever you keep scratch projects
$ mkdir git-playground
$ cd git-playground
$ git init
Initialized empty Git repository in /Users/spencerhales/git-playground/.git/
```

That `.git/` directory is the entire repository, every commit, branch, and config for *this* project lives in there. Delete `.git/` and it's just a normal folder again. Let's peek:

```
$ ls -a
.   ..   .git
$ git status
On branch main

No commits yet

nothing to commit (working tree clean)
```

Notice we're already on `main` (because of `init.defaultBranch`), and there are "No commits yet." Good.

### Step 3 - The add → commit loop (the heartbeat of git)

Create a file:

```
$ echo "# Git Playground" > README.md
$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        README.md

nothing added to commit but untracked files present (use "git add" to track)
```

**Read this every time.** Git is *telling you the next move*. Right now README.md is "untracked", git sees it but isn't managing it. Let's stage it:

```
$ git add README.md
$ git status
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
        new file:   README.md
```

Now it's in the **staging area** (a.k.a. the index), the holding pen for your next commit. Let's commit it:

```
$ git commit -m "Add project README"
[main (root-commit) a1b2c3d] Add project README
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
```

That `a1b2c3d` is the start of the commit's SHA-1 hash (yours will differ). You just made history. Check:

```
$ git status
On branch main
nothing to commit, working tree clean
$ git log
commit a1b2c3d4e5f6...  (HEAD -> main)
Author: Your Name <you@example.com>
Date:   Mon Jun 29 09:15:00 2026 -0600

    Add project README
```

### Step 4 - `git diff`: see exactly what changed

This is the skill that separates careful committers from sloppy ones. Always look before you stage. Edit the file:

```
$ echo "A repo for practicing git commands." >> README.md
$ git status
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
        modified:   README.md

no changes added to commit (working tree clean)
```

`git diff` shows **unstaged** changes (working tree vs. staging area):

```
$ git diff
diff --git a/README.md b/README.md
index 1d2e3f4..5a6b7c8 100644
--- a/README.md
+++ b/README.md
@@ -1 +1,2 @@
 # Git Playground
+A repo for practicing git commands.
```

The `+` line is what you added. Stage it, then look again:

```
$ git add README.md
$ git diff
# (no output - nothing unstaged)
$ git diff --staged
diff --git a/README.md b/README.md
...
+A repo for practicing git commands.
```

The mental model: **`git diff`** = "what haven't you staged yet?" **`git diff --staged`** = "what's about to go into the commit?" Commit it:

```
$ git commit -m "Describe the repo in README"
[main b2c3d4e] Describe the repo in README
 1 file changed, 1 insertion(+)
```

### Step 5 - Writing good commit messages

A commit message is a note to future you. The format that's universally understood:

```
Short summary in 50 chars or less, imperative mood

Optional body wrapped at ~72 chars explaining WHY this change
exists, not what it does (the diff already shows what). Reference
issues like "Fixes #42" if relevant.
```

- **Imperative mood:** "Add login button," not "Added" or "Adds." Read it as "This commit will _____." (git's own auto-generated messages use this, "Merge branch...").
- **Summary line under ~50 chars**, no trailing period.
- **Blank line** between summary and body (git treats line 1 specially).
- **Body explains the why.** Six months from now you'll thank yourself.

To write a multi-line message, run `git commit` (no `-m`) and your editor opens. Type summary, blank line, body, save, close.

Bad: `git commit -m "fix"`, `git commit -m "stuff"`, `git commit -m "asdf"`.
Good: `git commit -m "Fix off-by-one in pagination offset"`.

### Step 6 - Building more history & reading the log

Let's add a couple more commits so the history is interesting:

```
$ echo "print('hello')" > app.py
$ git add app.py
$ git commit -m "Add hello-world script"
$ echo "print('goodbye')" >> app.py
$ git add app.py
$ git commit -m "Add goodbye line"
```

Now explore history four ways:

```
$ git log --oneline
c4d5e6f Add goodbye line
b3c4d5e Add hello-world script
b2c3d4e Describe the repo in README
a1b2c3d Add project README
```

```
$ git log --oneline --graph --decorate --all
* c4d5e6f (HEAD -> main) Add goodbye line
* b3c4d5e Add hello-world script
* b2c3d4e Describe the repo in README
* a1b2c3d Add project README
```

(That's exactly the `git lg` alias we made, try `git lg` now.)

```
$ git log -p          # full diff for each commit (press q to quit the pager)
$ git log --stat      # files changed + line counts per commit
```

```
$ git show c4d5e6f    # everything about one commit: message + diff
```

### Step 7 - `.gitignore`: keep junk out of history

Some files should *never* be committed: build artifacts, dependencies, secrets, OS cruft. Create a `.gitignore`:

```
$ cat > .gitignore <<'EOF'
# Python
__pycache__/
*.pyc
.venv/
venv/

# Environment / secrets
.env
*.key

# OS
.DS_Store
Thumbs.db

# Editor
.vscode/
.idea/
EOF
```

Prove it works, make a file that matches a pattern:

```
$ mkdir __pycache__ && touch __pycache__/app.cpython-311.pyc
$ git status
On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
        .gitignore

nothing added to commit but untracked files present
```

Notice `__pycache__/` is **not** listed, git is ignoring it. Commit the `.gitignore` itself:

```
$ git add .gitignore
$ git commit -m "Add .gitignore"
```

**Gotcha:** `.gitignore` only affects *untracked* files. If you already committed a file, adding it to `.gitignore` does nothing, you must stop tracking it: `git rm --cached secret.env` then commit. (See 11.1 for the full tracked/untracked model.)

### Step 8 - Branching: `git switch -c`

Branches are how you work on something without touching `main`. Make one and switch to it in a single command:

```
$ git switch -c feature/greeting
Switched to a new branch 'feature/greeting'
$ git branch
* feature/greeting
  main
```

> Note: `git switch` (and `git restore`) are the modern, purpose-built commands. The old `git checkout` does both jobs and more, which made it confusing. We'll use `switch`/`restore`; you'll still *see* `checkout` everywhere in the wild, so know it's equivalent.

A branch is just a movable pointer to a commit, cheap and instant. Make a change *on this branch*:

```
$ echo "print('how are you?')" >> app.py
$ git add app.py
$ git commit -m "Add greeting question"
$ git log --oneline
d5e6f7a (HEAD -> feature/greeting) Add greeting question
c4d5e6f (main) Add goodbye line
...
```

See it: `feature/greeting` is now one commit ahead of `main`. Switch back to main and confirm `app.py` doesn't have the new line:

```
$ git switch main
Switched to branch 'main'
$ cat app.py
print('hello')
print('goodbye')
```

The greeting line is gone, it lives only on the branch. Switch back:

```
$ git switch feature/greeting
```

### Step 9 - Fast-forward merge

`main` hasn't moved since we branched, so merging the feature in is a **fast-forward**: git just slides the `main` pointer forward. No new commit needed.

```
$ git switch main
$ git merge feature/greeting
Updating c4d5e6f..d5e6f7a
Fast-forward
 app.py | 1 +
 1 file changed, 1 insertion(+)
$ git log --oneline
d5e6f7a (HEAD -> main, feature/greeting) Add greeting question
c4d5e6f Add goodbye line
...
```

Both `main` and `feature/greeting` now point at the same commit. Clean up the merged branch:

```
$ git branch -d feature/greeting
Deleted branch feature/greeting (was d5e6f7a).
```

### Step 10 - A real 3-way merge

A fast-forward only happens when `main` didn't move. Let's force a *real* merge by making commits on **both** branches after they diverge. (If you commit on `main` *before* branching, the branch starts from that commit, `main` never moves again, and the later merge is just another fast-forward, not what we want.)

Branch first, so both branches share the same starting point:

```
$ git switch -c feature/license
```

Now change a *different* file on the branch (no conflict yet):

```
$ echo "MIT License" > LICENSE
$ git add LICENSE
$ git commit -m "Add LICENSE file"
```

Switch back to `main` and make a commit there too, so both branches have moved apart:

```
$ git switch main
$ echo "# Setup" >> README.md
$ git add README.md
$ git commit -m "Add Setup heading to README"
```

Both branches have moved apart. Merge:

```
$ git merge feature/license
Merge made by the 'ort' strategy.
 LICENSE | 1 +
 1 file changed, 1 insertion(+)
```

Because both sides advanced, git created a **merge commit** with two parents. See the fork-and-join in the graph:

```
$ git lg
*   e6f7a8b (HEAD -> main) Merge branch 'feature/license'
|\
| * f7a8b9c (feature/license) Add LICENSE file
* | a8b9c0d Add Setup heading to README
|/
* d5e6f7a Add greeting question
...
```

That diamond shape is a 3-way merge. Delete the branch: `git branch -d feature/license`.

### Step 11 - Create a merge conflict ON PURPOSE and resolve it

This is the step people fear. Do it once deliberately and the fear evaporates. A conflict happens when two branches change **the same lines** of **the same file**.

Set it up. Edit line 1 of README on `main`:

```
$ git switch main
# Replace the whole README first line on main:
$ printf '# Git Playground (main edition)\nA repo for practicing git commands.\n# Setup\n' > README.md
$ git add README.md && git commit -m "Reword README title on main"
```

Now make a branch FROM AN EARLIER point and change the *same* first line differently. We'll branch off the previous commit:

```
$ git switch -c feature/title HEAD~1
$ printf '# Git Playground (feature edition)\nA repo for practicing git commands.\n# Setup\n' > README.md
$ git add README.md && git commit -m "Reword README title on feature branch"
```

Both branches rewrote line 1 of README.md differently. Merge and watch it blow up:

```
$ git switch main
$ git merge feature/title
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.
```

Don't panic: this is normal and expected. Check status:

```
$ git status
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
        both modified:   README.md
```

Open `README.md`. Git inserted **conflict markers**:

```
<<<<<<< HEAD
# Git Playground (main edition)
=======
# Git Playground (feature edition)
>>>>>>> feature/title
A repo for practicing git commands.
# Setup
```

Decode the markers:
- `<<<<<<< HEAD` → start of *your current branch's* version (main).
- `=======` → divider.
- `>>>>>>> feature/title` → end of the *incoming branch's* version.

**Resolving = editing the file so it's exactly how you want it, then deleting all three marker lines.** Suppose you want a combined title. Edit so the conflict region becomes:

```
# Git Playground (main + feature edition)
A repo for practicing git commands.
# Setup
```

No `<<<<<<<`, `=======`, or `>>>>>>>` anywhere. Now tell git you've resolved it by staging the file:

```
$ git add README.md
$ git status
On branch main
All conflicts fixed but you are still merging.
  (use "git commit" to conclude the merge)
```

Finish the merge with a commit (git pre-fills a sensible message):

```
$ git commit -m "Merge feature/title: combine README titles"
[main 1a2b3c4] Merge feature/title: combine README titles
```

And with that, you've resolved your first conflict.

Two escape hatches worth knowing:
- **Bail out entirely:** `git merge --abort` returns you to the pre-merge state, clean. Use it if you started a merge at a bad time.
- **Take one side wholesale:** `git checkout --ours README.md` (keep main's version) or `git checkout --theirs README.md` (keep incoming), then `git add` + commit. Handy for files where one side is simply correct.

Clean up: `git branch -d feature/title`.

### Step 12 - Connect to GitHub

Local git is complete on its own, but to back up and collaborate you push to a **remote** like GitHub.

1. On github.com, click **New repository**. Name it `git-playground`. **Do NOT** check "Add a README", your local repo already has history, and an empty remote merges cleanly. Create it.
2. GitHub shows you a URL. For pushing existing work, use these commands (HTTPS shown; SSH is `git@github.com:USER/repo.git`):

```
$ git remote add origin https://github.com/spencerhales/git-playground.git
$ git remote -v
origin  https://github.com/spencerhales/git-playground.git (fetch)
origin  https://github.com/spencerhales/git-playground.git (push)
```

`origin` is just the conventional nickname for "the main remote." Push, setting the upstream so future `git push`/`git pull` need no arguments:

```
$ git push -u origin main
Enumerating objects: 24, done.
...
To https://github.com/spencerhales/git-playground.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
```

Refresh the GitHub page, your commits are there.

> **Auth note:** HTTPS pushes need a **Personal Access Token** (not your password), generate one under GitHub → Settings → Developer settings → Personal access tokens, and paste it when prompted. Better long-term: set up an **SSH key** (`ssh-keygen -t ed25519 -C "your@email"`, add `~/.ssh/id_ed25519.pub` to GitHub → Settings → SSH keys) and use the SSH URL. A credential helper (`git config --global credential.helper osxkeychain` on macOS) saves you re-entering it.

### Step 13 - The full collaboration loop (clone → branch → push → PR → merge)

This is how every team works. Even solo, do it this way: it's good hygiene.

**Clone** (simulating a teammate, or a fresh machine). In a *different* folder:

```
$ cd ~/scratch
$ git clone https://github.com/spencerhales/git-playground.git
$ cd git-playground
```

Cloning gives you the full history *and* sets up `origin` automatically.

**Branch** for your change:

```
$ git switch -c feature/add-tests
$ echo "def test_truth(): assert True" > test_app.py
$ git add test_app.py
$ git commit -m "Add a trivial passing test"
```

**Push the branch** to GitHub:

```
$ git push -u origin feature/add-tests
...
remote: Create a pull request for 'feature/add-tests' on GitHub by visiting:
remote:   https://github.com/spencerhales/git-playground/pull/new/feature/add-tests
```

**Open a Pull Request:** click that link (or go to the repo → "Compare & pull request"). A PR is a *request to merge your branch into main*, with a diff, a discussion thread, and a place for CI checks to run. Write a title and description explaining the change. Click **Create pull request**.

**Review:** on a team, a colleague reads the diff, leaves comments, maybe requests changes. You push more commits to the same branch (`git commit` + `git push`) and the PR updates automatically. When approved...

**Merge:** click **Merge pull request** on GitHub. Three button options:
- *Merge commit*, keeps all commits + a merge commit (full history).
- *Squash and merge*, collapses the branch into one tidy commit on main (a good default for small features).
- *Rebase and merge*, replays commits onto main with no merge commit (linear history).

After merging, delete the branch on GitHub (there's a button).

### Step 14 - `git pull`: keep your local copy in sync

The branch you merged on GitHub means `main` on the remote is now ahead of your local `main`. Sync down:

```
$ git switch main
$ git pull
remote: ...
Updating 1a2b3c4..9z8y7x6
Fast-forward
 test_app.py | 1 +
 1 file changed, 1 insertion(+)
```

`git pull` = `git fetch` (download new commits) + `git merge` (integrate them). Do this at the **start of every work session** so you build on the latest code.

Delete your local copy of the merged branch:

```
$ git branch -d feature/add-tests
$ git fetch --prune     # remove stale remote-tracking refs for deleted branches
```

If `git pull` reports a conflict, resolve it exactly like Step 11, same markers, same process.

### Step 15 - Undoing things safely

Mistakes are routine. Git almost never truly loses work (Step 20 proves it). Here's the right tool for each situation.

**(a) Discard unstaged changes to a file**, "you edited this and want the committed version back":

```
$ echo "oops typo" >> app.py
$ git restore app.py        # throws away the edit
$ git status                # clean again
```

This is destructive, the edit is gone (it was never committed). That's the point.

**(b) Unstage a file**, "you `git add`ed something you didn't mean to":

```
$ git add app.py
$ git restore --staged app.py   # un-stages, keeps your edits in working tree
# (this is the 'git unstage' alias we made)
```

**(c) Amend the last commit**, "you forgot a file" or "your message has a typo." Only for commits you **haven't pushed**:

```
$ git commit --amend -m "Better message"
# To add a forgotten file: stage it first, then:
$ git add forgotten.py
$ git commit --amend --no-edit    # keeps the existing message
```

Amend *rewrites* the last commit (new hash). Never amend something already pushed and pulled by others.

**(d) `reset` vs `revert`**, the big one. Both "undo a commit" but opposite philosophies:

**`git reset`** *moves the branch pointer backward*, rewrites history. Three flavors:

```
$ git reset --soft HEAD~1    # undo commit, KEEP changes staged
$ git reset --mixed HEAD~1   # (default) undo commit, keep changes UNstaged
$ git reset --hard HEAD~1    # undo commit AND discard the changes (destructive!)
```

Concrete: you made a "wip garbage" commit and want it gone but keep the code:

```
$ git reset --soft HEAD~1    # commit vanishes, your code is staged, ready to re-commit properly
```

Only `reset` commits you haven't pushed. Rewriting shared history forces painful re-syncs on teammates.

**`git revert`** *makes a NEW commit that undoes a previous one*, history is preserved. This is the **safe, public** way to undo:

```
$ git revert d5e6f7a
# opens editor with "Revert 'Add greeting question'" - save & close
[main 3c4d5e6] Revert "Add greeting question"
 1 file changed, 1 deletion(-)
```

(Revert the *most recent* commit touching a file when you can. Reverting an older commit can still conflict, if a later commit changed the lines right next to it, git can't cleanly work out how to remove just that piece.)

Rule of thumb: **`reset` for local/unpushed mistakes, `revert` for anything already shared.**

### Step 16 - `git stash`: park work without committing

You're mid-change, and you need to switch branches *right now* (urgent bug). You don't want a half-baked commit. Stash it:

```
$ echo "half-done feature" >> app.py
$ git stash
Saved working directory and index state WIP on main: 1a2b3c4 ...
$ git status
nothing to commit, working tree clean      # your edit is tucked away
```

Now your tree is clean, go fix the bug, switch branches, whatever. Bring your work back:

```
$ git stash list
stash@{0}: WIP on main: 1a2b3c4 Merge feature/title...
$ git stash pop        # re-apply the most recent stash AND remove it from the list
```

Useful variants:
- `git stash` then `git stash apply`, re-apply but *keep* it in the stash list.
- `git stash -u`, also stash untracked files.
- `git stash drop stash@{0}`, delete a stash without applying.

### Step 17 - `git cherry-pick`: grab one commit from elsewhere

Sometimes you want *just one commit* from another branch, not the whole branch. Set it up:

```
$ git switch -c hotfix
$ echo "URGENT: patched" > hotfix.txt
$ git add hotfix.txt
$ git commit -m "Apply urgent hotfix"
$ git log --oneline -1
7a8b9c0 (HEAD -> hotfix) Apply urgent hotfix
```

Now you want that exact commit on `main` too, without merging the rest of `hotfix`:

```
$ git switch main
$ git cherry-pick 7a8b9c0
[main b9c0d1e] Apply urgent hotfix
 1 file changed, 1 insertion(+)
```

Cherry-pick copies the *change* from that commit onto your current branch as a brand-new commit (new hash). If it conflicts, resolve like Step 11, then `git cherry-pick --continue`. To bail: `git cherry-pick --abort`.

### Step 18 - `git reflog`: the time machine (recover "lost" work)

Here's the safety net that makes git fearless. The **reflog** records *every* place `HEAD` has pointed, even after a `reset --hard` or a deleted branch. Let's destroy something and get it back.

```
$ git log --oneline -1
b9c0d1e (HEAD -> main) Apply urgent hotfix
$ git reset --hard HEAD~1       # "accidentally" nuke that commit
HEAD is now at 1a2b3c4 Merge feature/title...
$ git log --oneline -1
1a2b3c4 ...                      # the hotfix commit is gone from history!
```

Panic? No. Look at the reflog:

```
$ git reflog
1a2b3c4 (HEAD -> main) HEAD@{0}: reset: moving to HEAD~1
b9c0d1e HEAD@{1}: cherry-pick: Apply urgent hotfix
1a2b3c4 HEAD@{2}: ...
```

There's `b9c0d1e` at `HEAD@{1}`. Recover it:

```
$ git reset --hard b9c0d1e
HEAD is now at b9c0d1e Apply urgent hotfix
$ git log --oneline -1
b9c0d1e (HEAD -> main) Apply urgent hotfix     # back from the dead
```

**Remember this exists.** Almost any time you think you've lost a commit, `git reflog` has the hash, and you can `git reset --hard <hash>` or `git branch rescue <hash>` to recover it. Git only garbage-collects unreachable commits after ~30 days, so you have a wide window. (11.1 explains *why*, every commit is immutable and content-addressed, so nothing is truly deleted until GC.)

## Common mistakes

- **Committing secrets.** A `.env` or API key in history is *still there* even after you delete it in a later commit, anyone can check out the old commit. Set up `.gitignore` *first*, before the first commit. If it happens, rotate the secret immediately (assume it's compromised).
- **`git add .` blindly.** It stages everything, including junk you didn't mean to. Run `git status` and `git diff` first; stage deliberately.
- **`reset --hard` on shared branches.** Rewrites history others depend on. Use `revert` for anything pushed.
- **Working directly on `main`.** Always branch. `main` should stay deployable.
- **Giant commits / vague messages.** "Update stuff" tells future-you nothing. Small, focused commits with imperative messages.
- **Forgetting to pull before starting.** You'll build on stale code and create avoidable conflicts. `git pull` at the start of every session.
- **Confusing `switch` and `restore`.** `switch` changes *branches*; `restore` changes *file contents*. (The old `checkout` did both, hence the confusion.)
- **Force-pushing carelessly.** `git push --force` can erase teammates' commits. If you must, use `git push --force-with-lease` (it refuses if the remote moved unexpectedly).

## On the job

- **PRs are the unit of work.** You rarely push to `main` directly; you open a PR, get a review, CI runs, then it merges. Treat the PR description as documentation.
- **Branch naming conventions** are usually enforced: `feature/...`, `fix/...`, `chore/...`, often with a ticket number (`feature/JIRA-123-add-login`).
- **Rebase to keep history clean.** Many teams ask you to `git pull --rebase` or rebase your feature branch onto latest `main` before merging, so history stays linear. (See 11.1 for what rebase actually does under the hood.)
- **`git blame <file>`** shows who last changed each line and in which commit, invaluable for "why is this line here?" archaeology (and not actually about blaming anyone).
- **`git bisect`** binary-searches your history to find the commit that introduced a bug, you'll reach for it on the day a regression appears and you've no idea which of 200 commits caused it.
- **Read commit history before changing code** you don't understand. `git log -p <file>` often answers "why was it done this way?" faster than asking around.

## Mini-project - "Simulate a team"

Goal: experience the full collaborative cycle, including a conflict and a cherry-pick, using **two clones** to play two developers. Budget ~30 minutes. You'll need your GitHub `git-playground` repo from Step 12.

**Setup, two working copies (two "developers"):**

```
$ cd ~/scratch
$ git clone https://github.com/spencerhales/git-playground.git dev-alice
$ git clone https://github.com/spencerhales/git-playground.git dev-bob
```

`dev-alice` is Alice's machine; `dev-bob` is Bob's. They share one remote.

**Part 1, Two branches touching the same line (engineer a conflict):**

```
# Alice:
$ cd ~/scratch/dev-alice
$ git switch -c alice/title
$ printf '# Git Playground - by Alice\n' > README.md
$ git add README.md && git commit -m "Alice: rewrite title"
$ git push -u origin alice/title

# Bob (same line, different content):
$ cd ~/scratch/dev-bob
$ git switch -c bob/title
$ printf '# Git Playground - by Bob\n' > README.md
$ git add README.md && git commit -m "Bob: rewrite title"
$ git push -u origin bob/title
```

**Part 2, Merge Alice's PR, then Bob hits a conflict:**

1. On GitHub, open and **merge Alice's PR** (`alice/title` → `main`). Now `main`'s README says "by Alice."
2. Bob tries to update his branch with the new `main`:

```
$ cd ~/scratch/dev-bob
$ git fetch origin
$ git merge origin/main
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
```

3. Bob resolves it (Step 11 process). Open README.md, combine into:

```
# Git Playground - by Alice & Bob
```

Remove all conflict markers, then:

```
$ git add README.md
$ git commit -m "Merge main into bob/title; combine titles"
$ git push
```

4. Open and merge **Bob's PR** on GitHub. `main` now reflects both. Pull it down in both clones with `git pull` and confirm the README matches.

**Part 3, Cherry-pick one commit across developers:**

Alice writes a handy utility commit on a throwaway branch; Bob wants *only that commit*.

```
# Alice makes two commits, but only one is useful to Bob:
$ cd ~/scratch/dev-alice
$ git switch main && git pull
$ git switch -c alice/experiments
$ echo "def slugify(s): return s.lower().replace(' ', '-')" > utils.py
$ git add utils.py && git commit -m "Add slugify helper"
$ echo "# scratch notes, not for prod" > notes.txt
$ git add notes.txt && git commit -m "Add Alice scratch notes"
$ git push -u origin alice/experiments
$ git log --oneline -2
abc1234 Add Alice scratch notes
def5678 Add slugify helper          # <-- Bob wants only THIS one
```

```
# Bob grabs just the slugify commit:
$ cd ~/scratch/dev-bob
$ git switch main && git pull
$ git fetch origin
$ git switch -c bob/use-slugify
$ git cherry-pick def5678            # use the slugify commit's hash
[bob/use-slugify ...] Add slugify helper
$ ls                                 # utils.py is here; notes.txt is NOT
```

Bob got `utils.py` (the slugify helper) without Alice's scratch notes. Push it and open a PR if you want to complete the loop.

**Cleanup when you're done playing:**

```
$ rm -rf ~/scratch/dev-alice ~/scratch/dev-bob ~/scratch/git-playground ~/git-playground
# and delete the repo on GitHub if you like
```

**What you should now be able to do without looking:** clone, branch, push, open/merge a PR, sync with `pull`, resolve a conflict from raw markers, and cherry-pick a single commit between developers. That's the daily reality of working on a team.

## Your daily git routine

Tape this to the wall. Most days are just these moves:

```
$ git switch main && git pull          # 1. start fresh on latest main
$ git switch -c feature/thing          # 2. branch for your task
   ... edit code ...
$ git status                           # 3. see what changed
$ git diff                             # 4. review it line by line
$ git add -p                           # 5. stage hunks deliberately (-p = interactive)
$ git commit -m "Clear imperative msg" # 6. commit small & focused (repeat 3-6 as you go)
$ git push -u origin feature/thing     # 7. push the branch
   ... open a PR on GitHub, get review, merge ...
$ git switch main && git pull          # 8. sync the merge back down
$ git branch -d feature/thing          # 9. tidy up the merged branch
```

## One-screen command summary

```
SETUP
  git config --global user.name "..."        identify yourself
  git config --global user.email "..."
  git init                                    new repo in current folder
  git clone <url>                             copy a remote repo

INSPECT
  git status                                  what's changed / staged
  git diff                                    unstaged changes
  git diff --staged                           staged changes (about to commit)
  git log --oneline --graph --all             history as a graph
  git show <hash>                             one commit's message + diff
  git blame <file>                            who changed each line

THE LOOP
  git add <file> / git add -p                 stage (interactively)
  git restore --staged <file>                 unstage
  git restore <file>                          discard unstaged edits (destructive)
  git commit -m "msg"                         commit staged changes
  git commit --amend                          fix the last (unpushed) commit

BRANCH & MERGE
  git switch -c <name>                        create + switch to branch
  git switch <name>                           switch branches
  git branch -d <name>                        delete merged branch
  git merge <name>                            merge a branch into current
  git merge --abort                           cancel a conflicted merge

REMOTE
  git remote add origin <url>                 link a remote
  git push -u origin <branch>                 push + set upstream
  git push / git pull                         send / receive commits
  git fetch --prune                           download refs, drop stale ones

UNDO / RECOVER
  git reset --soft HEAD~1                      undo commit, keep changes staged
  git reset --mixed HEAD~1                     undo commit, keep changes unstaged
  git reset --hard HEAD~1                      undo commit + discard (destructive)
  git revert <hash>                            new commit that undoes <hash> (safe)
  git stash / git stash pop                    park / restore uncommitted work
  git cherry-pick <hash>                       copy one commit onto current branch
  git reflog                                   history of HEAD - recover lost commits
```
