# Chapter 22.1 - Mac Minis, Home Labs & Building Server Farms

> Goal: Understand what a *server* actually is, why you'd ever run your own hardware instead of renting cloud, and how to go from one quiet box under your desk to a small humming cluster that runs CI, self-hosted apps, and local LLM inference. By the end you can stand up a hardened headless server behind Tailscale, model the 3-year economics of Mac minis vs cloud in code, and bootstrap a 3-node cluster running a real service.

You live in other people's clouds all day, Docker (10.1), Kubernetes (10.2), AWS (10.4). This chapter is about the thing *underneath* all of that: physical computers you own, in a room you're responsible for. No black boxes, not even the box itself. By the end of this chapter, "the cloud is just someone else's computer" stops being a meme and becomes something you can build.

---

## 🌱 Start here (beginner on-ramp)

Forget racks and data centers for a second. A **server is just a computer that exists to answer requests from other computers, instead of from a human sitting in front of it.** That's the whole definition. The laptop you're typing on is a *client*, it makes requests (open this page, run this build). A server *receives* requests (give me this page, run this build) and replies. The hardware can be identical; the *role* is what differs.

The everyday version: when you open `nyxfinance.com`, your browser (client) sends an HTTP request to a machine somewhere (server) that sends HTML back. That "machine somewhere" could be a $40,000 rack in an AWS data center, or it could be a $599 Mac mini sitting on a shelf in your apartment. To the browser, they're indistinguishable. That realization is the door into this entire chapter.

**Self-hosting** means *you* own and run that server, instead of renting it. Self-hosting your Git: you run a Git server on your own box instead of paying GitHub. Self-hosting an LLM: you run the model on your own GPU instead of calling OpenAI. The trade is always the same shape, you take on *responsibility* (power, cooling, backups, security, the 2am reboot) in exchange for *control, privacy, and cost-at-scale.*

**A home lab** is the friendly on-ramp to all of this: one or more computers at home that you run *to learn and to host your own stuff*. Not for customers, not for SLAs, for you. Most serious infrastructure engineers have one, because there's no substitute for breaking and fixing real hardware you own.

**The one mental model to carry through the chapter:** every infrastructure decision is a trade between **renting** (cloud: pay monthly, someone else handles the hardware, infinite elasticity) and **owning** (self-host: pay once, you handle the hardware, fixed capacity). Neither is "right." The skill is knowing *which one wins for a given workload*, and being able to prove it with numbers, not vibes.

If you remember one thing: **a server is a role, not a thing; self-hosting trades responsibility for control; and the rent-vs-own question is answered with a cost model, not a religion.**

## 📐 Concept - servers, self-hosting, and the rent-vs-own question

### What actually makes a "server" different from a desktop

The role is the real difference, but in practice server-grade machines and desktops *do* diverge on the things that matter when a computer must run unattended, 24/7, answering strangers:

| Property | Typical desktop | Server-oriented machine | Why it matters |
|---|---|---|---|
| **Uptime expectation** | Hours, then sleep | Months without reboot | A server that sleeps drops requests. |
| **Headless operation** | Has a monitor/keyboard | None, managed over the network | You manage 1 or 100 the same way: remotely. |
| **Remote management** | You walk to it | SSH, KVM, IPMI/BMC | You must reboot/reinstall a dead box without touching it. |
| **ECC memory** | Usually no | Often yes | Bit-flips silently corrupt data over months of uptime. |
| **Redundancy** | Single PSU/disk | Dual PSU, RAID disks | One component failing shouldn't take the service down. |
| **I/O priorities** | GPU for games | NICs, storage bandwidth, many cores | Servers move data and serve many clients at once. |

Note the Mac mini, our star of this chapter, is technically a *desktop*. It has no ECC, one power supply, no IPMI. That's a genuine limitation, but its perf-per-watt, silence, and size are so good that people deploy it as a server anyway, *for the workloads where those limitations don't bite.* Knowing which workloads those are is half the chapter.

### "The cloud" is a rental abstraction

When you `terraform apply` an EC2 instance (10.4), you're renting a slice of a server in someone's data center, by the second. AWS bought the hardware (capex), staffed the data center, ran the power and cooling, and resells it to you at a markup as a metered service (you pay opex). The genius of cloud is that it converts a *capital* problem (buy machines, predict demand, eat the depreciation) into an *operating* one (pay for exactly what you used this hour, scale to zero when idle).

That conversion is worth a lot, and you pay for it. The core question of this chapter is: **when is renting worth the markup, and when should you own?**

### Why own your own hardware? (the honest case for self-hosting)

1. **Cost at scale & steady-state.** Cloud is brilliant for *spiky, unpredictable* load. For a workload that runs *flat-out 24/7* (a CI farm, a render farm, an always-on inference box), you pay the rental markup every single hour forever. Owning amortizes a one-time purchase over years. The crossover is real and computable (we'll code it).
2. **No egress fees.** This is the cloud's dirty secret. Ingress (data *in*) is usually free; **egress (data *out*) is expensive**, often $0.05-$0.09/GB on AWS. Move 50 TB/month out and that's thousands of dollars *just to send your own data to your own users.* A home lab's egress fee is $0.00.
3. **Control.** You choose the exact kernel, the exact GPU, the exact network topology. No "that instance type isn't available in your region," no surprise deprecation of an API you depend on.
4. **Privacy & data residency, the Anneava/HIPAA angle.** For Anneava (health data), *where the data physically lives and who can touch it* is a compliance question, not a preference. Self-hosting on hardware you physically control gives you a clean story: PHI never leaves a machine you own, in a room you control, on a network you segment. (You *can* be HIPAA-compliant in cloud, AWS will sign a BAA, but for some orgs "the data never left the building" is the simpler, cheaper, more defensible posture. See security in 12.x.)
5. **Latency & locality.** A server in your building is microseconds away. Edge/on-prem inference (LLM in the same room as the user) beats a round-trip to us-east-1.
6. **Learning.** Frankly the biggest one for a home lab. You cannot deeply understand distributed systems (09), networking (06), or observability (13) by only ever clicking "launch instance." Owning the metal teaches you what the cloud abstracts away.

### Why rent the cloud instead? (the honest case against self-hosting)

1. **Elasticity.** Need 500 machines for one hour a month? Cloud gives you that and bills you for one hour. Owning 500 idle machines is insane.
2. **Managed services.** RDS, S3, SQS, EKS, someone else patches, backs up, replicates, and pages themselves at 2am. Self-hosting Postgres with real HA is a *job*.
3. **No capex, no depreciation.** Startups especially want to spend opex, not sink cash into hardware that's obsolete in 3 years.
4. **Global reach instantly.** Spin up in 30 regions today. You can't ship Mac minis to Frankfurt and São Paulo by tonight.
5. **You don't run a data center.** Power, cooling, fire suppression, physical security, redundant ISPs, hardware RMA, all someone else's problem.

### The economics: capex vs opex (and the worked comparison)

- **Capex (capital expenditure):** money spent up front on assets you own, the machines, the switch, the UPS. Depreciates over its useful life (~3-5 years).
- **Opex (operating expenditure):** ongoing costs, cloud bills, electricity, your own time.

Owning is mostly capex (+ small opex for power). Cloud is pure opex. The naive comparison ("$599 mini vs $X/month instance") is a trap because it ignores power, your labor, the cloud's egress, and the value of elasticity. We'll build a model that's honest about all of it in the mini-project. The headline result, worth feeling before we prove it: **for steady-state, always-on, egress-heavy compute, owning a few Mac minis can beat equivalent cloud by a wide margin over 3 years, and for spiky, occasional, or globally-distributed workloads, cloud wins easily.**

> 💼 **On the job:** The phrase "repatriation" describes companies *moving workloads back* from cloud to owned hardware once their load became steady and predictable (Dropbox famously did this with storage; 37signals/Basecamp publicized leaving the cloud and saving millions/year). The lesson isn't "cloud bad", it's "match the billing model to the load shape." A staff engineer who can do that math is worth a lot.

## 📐 Concept - the home lab

### Why every serious engineer benefits from one

The cloud is a great *destination* and a terrible *classroom*. When everything is a managed service, you never see the failure modes: a disk filling up, a DNS misconfiguration taking down your services, a runaway container eating all the RAM, a power blip corrupting a database. A home lab is a low-stakes environment where breaking things is *the point.* The mistakes you make on a $599 box you own teach you the lessons that, in production at NYX, would cost real money and real sleep.

It's also a portfolio. "I run a 3-node k3s cluster at home with Prometheus/Grafana monitoring, Tailscale networking, and a self-hosted LLM behind a reverse proxy" is a vastly stronger interview story than "I did the AWS tutorial."

### What you can run (one box does a *lot*)

Even a single machine can host an astonishing amount:

- **Git server**, Gitea or Forgejo: your own GitHub, private and free.
- **CI runners**, self-hosted GitHub Actions / GitLab runners (and for Apple, the killer use: iOS/macOS build runners, only a Mac can build/sign iOS apps legally).
- **Databases**, Postgres, Redis, a dev/staging copy of NYX's data (sanitized!).
- **Monitoring**, Prometheus + Grafana + Loki (ties straight to 13).
- **A local LLM**, Ollama serving a model for coding/chat with zero per-token cost and full privacy (20.3).
- **Media & files**, Jellyfin, Nextcloud, a Samba/NFS share.
- **Dev & staging environments**, a permanent place to deploy branches.
- **Home automation, DNS (Pi-hole), VPN exit node, a personal website**, the long tail.

### The mindset: start with one box

The single biggest home-lab mistake is buying a rack and three machines before you've run *one*. **Start with one box. Make it boringly reliable. Add a second only when the first one's limits are real.** Everything in the cluster section below is meaningless until you can confidently run, harden, back up, and monitor a *single* server. We'll do exactly that in the first mini-project.

## 📐 Concept - Mac minis as servers

### Why Apple Silicon Mac minis are beloved for this

The 2024 Mac mini (M4 / M4 Pro) is, pound for pound and watt for watt, one of the best small servers money can buy, for the right jobs. The reasons:

- **Perf per watt.** Apple Silicon is absurdly efficient. An M4 mini idles around a handful of watts and tops out far below a comparable x86 desktop. For an always-on box, the power bill *is* a big part of the lifetime cost (see the cost model), so efficiency compounds.
- **Silent & tiny.** A ~5"×5" box that you genuinely cannot hear. It lives on a shelf in a home, not a server room. Three of them stack in the space of one tower.
- **The unified-memory advantage for LOCAL LLM/ML inference.** This is the headline. Apple Silicon uses **unified memory**, the CPU and GPU share one pool of RAM (up to **64GB** on the M4 Pro) at high bandwidth (the M4 Pro pushes on the order of **~273 GB/s**). For LLM inference, the model weights must live in memory the GPU can read, and inference is heavily *memory-bandwidth-bound.* A consumer NVIDIA card might have far more raw FLOPS but only 8-24GB of VRAM, so a 70B-parameter model simply *doesn't fit* without quantization tricks or multiple cards. A 64GB M4 Pro can hold a big quantized model entirely in fast unified memory and serve it at usable speeds, drawing a fraction of the power. That's why "run a local LLM" and "Mac mini" show up together constantly (see the deep dive in 20.3).
- **Thunderbolt 5 & networking.** TB5 gives huge external-storage and machine-to-machine bandwidth; the mini ships with Gigabit Ethernet, **configurable to 10GbE** at purchase, important when you cluster them (you don't want the network to be the bottleneck between nodes).

> 🔭 **Looking ahead (2026):** M5 / M5 Pro Mac minis are expected around mid-to-late 2026, adding a **"Neural Accelerator" inside each GPU core** for stronger on-device AI. The direction is clear: these little boxes keep getting better at exactly the local-inference job that makes them special. (Always verify current specs and prices on Apple's site before you buy, these numbers move.)

### Running them headless

A server has no monitor. Two ways to drive a Mac mini headless:

- **SSH**, for everything scriptable. Enable in **System Settings → General → Sharing → Remote Login**. Then `ssh you@mini01.local`. This is how you'll do 95% of the work.
- **Screen Sharing (VNC)**, for the rare GUI task (some Xcode/notarization steps, accepting a macOS update prompt). Enable **Sharing → Screen Sharing**, connect from another Mac's Finder via `vnc://mini01.local`.

⚠️ A genuine gotcha: some macOS GUI/CI tasks (signing, the keychain, certain Xcode actions) historically misbehave when *no* user is graphically logged in. Many Mac-CI shops keep an *auto-login* user session running and a (sometimes virtual/dummy) display attached so the GUI session exists. This is the kind of macOS-as-server friction Linux doesn't have.

### macOS-as-server caveats (be honest)

Macs are wonderful, but macOS is a *desktop/laptop* OS wearing a server costume:

- **No real out-of-band management.** No IPMI/BMC. If macOS hangs, you cannot remotely power-cycle or reinstall the OS the way a server BMC lets you. You need a **smart PLC/PDU** (network-controlled power outlet) to force a reboot, or you walk to the box.
- **Licensing.** Apple's license permits virtualizing macOS **only on Apple hardware**, and limits VMs per host. You cannot legally run macOS on a cheap Linux VM in the cloud, this is *the* reason Mac-cloud rentals (MacStadium, AWS EC2 Mac) exist and cost what they do.
- **Updates & reboots.** macOS updates can be intrusive and occasionally require GUI interaction.
- **Not Linux.** Most server tooling assumes Linux. Docker on Mac runs Linux containers inside a lightweight VM (a layer of overhead and quirks). For pure container/Kubernetes work, a Linux box is simpler.

### When a Mac mini is the right tool - and when it isn't

**Mac mini wins when:**

- **iOS/macOS CI build farms, the #1 real-world use, by far.** You *legally must* build and sign iOS apps on Apple hardware. Companies rack dozens of Mac minis as CI runners. This is the dominant commercial Mac-server workload, full stop.
- **Local AI inference / ML.** The unified-memory + perf-per-watt story above. A great, quiet, cheap-to-run inference box.
- **Edge / small-footprint, low-power deployments** where silence and size matter and the workload is Apple-centric or inference.

**Reach for Linux x86/ARM boxes instead when:**

- You want maximum **containers/Kubernetes** with the least friction (Linux-native).
- You need **ECC memory, IPMI, dual PSUs, hot-swap disks**, real server-grade reliability features Macs lack.
- You want **discrete NVIDIA GPUs and CUDA** (the ML training ecosystem is still CUDA-first; Apple's MPS backend is good for inference, weaker for training).
- You want the **cheapest raw compute per dollar** for non-Apple workloads (used enterprise servers are dirt cheap).

**Reach for a NAS (Synology/TrueNAS) when:** the job is primarily *storage*, bulk files, backups, shared NFS/SMB, with light compute. Don't make a Mac mini be your file server when a purpose-built NAS does it better, with proper RAID and hot-swap bays.

## 📐 Concept - building a "farm"/cluster

A **cluster** is several machines coordinated to act, for some purpose, like one bigger machine. A **farm** usually means a cluster doing many independent jobs in parallel (render farm, CI/build farm). The pieces:

### 1. Networking the nodes (links to 06)

- **A switch.** Wire every node into a managed Gigabit (ideally with some 10GbE ports) switch. Don't run cluster traffic over Wi-Fi, latency and packet loss will wreck you.
- **Static IPs / DNS.** Nodes must find each other by stable names. Either assign static IPs, or (cleaner) configure **DHCP reservations** on your router so `mini01` always gets `10.0.10.11`, plus local DNS names (`mini01.lab`). See 06.2 for DNS.
- **VLANs.** A managed switch lets you put lab traffic on its own **VLAN**, segmenting the cluster from your laptop/IoT/family devices. This is a security boundary (12.2) and a sanity boundary.

### 2. Shared storage (NAS / NFS)

Stateless compute nodes are easy to replace; *state* is the hard part. A shared store everyone mounts means any node can pick up any job's data.

- **NFS** export from a NAS or a dedicated box: nodes mount `/mnt/shared`. Simple, ubiquitous, the classic render-farm pattern (everyone reads the same scene files, writes frames to the same place).
- Watch the network: shared storage over a 1GbE link becomes the bottleneck fast, this is where 10GbE earns its money.

### 3. Orchestration - how the cluster decides what runs where

Three rungs of a ladder, simplest first:

- **Ansible (config, not orchestration).** Not a scheduler, a way to push the *same* setup to N machines reproducibly from one control node. The first thing you'd add to any multi-box lab: "install Docker + configure firewall on all minis" becomes one command. (Sketch below.)
- **Docker Swarm.** The gentle on-ramp to clustering: it's *Docker you already know* (10.1) with `docker swarm init` + `docker stack deploy`. Built-in scheduling, service replicas, rolling updates, an overlay network, far less ceremony than Kubernetes. Perfect for a home lab.
- **Kubernetes / k3s.** The real deal (10.2). **k3s** is a lightweight, single-binary Kubernetes that runs beautifully on small ARM/Apple-class nodes, *the* home-lab k8s. Use it when you want to *practice* the thing you run at work, or when you've outgrown Swarm's simplicity.

### 4. Load distribution (links to 09.3)

Once N nodes run replicas of a service, something must spread requests across them. A reverse proxy / load balancer (nginx, HAProxy, Traefik, or the orchestrator's built-in service VIP) is the front door, round-robin or least-connections across healthy backends, with health checks pulling dead nodes out (the exact load-balancing material from 09.3, now on metal you own).

### 5. A job-scheduler idea (batch / farm)

For *batch* work (render frames, run 10,000 inference jobs, transcode a library) you don't want long-lived services, you want a **queue of jobs** and **workers** that pull from it:

- A queue (Redis, RabbitMQ, or SQS-style, see 09.5) holds work items.
- Each node runs a worker process that pulls a job, does it, writes the result to shared storage, marks it done.
- This *is* a render farm / CI farm at its core. It scales by adding workers; it's resilient because a dead worker's un-acked job goes back on the queue.

### 6. Distributing ML inference across nodes

Two flavors, don't confuse them:

- **Horizontal (easy, common): many independent requests across many nodes.** Run the same model on each of N minis, put a load balancer in front, and you've N×'d your throughput. This is the home-lab sweet spot and what most people mean by an "inference cluster." (20.2 covers serving patterns.)
- **Tensor/pipeline parallelism (hard): one model too big for one node, split across machines.** Tools like `llama.cpp`'s RPC mode or vLLM/distributed runtimes can shard a single huge model across nodes. Possible, but the inter-node network becomes the bottleneck, only worth it when the model genuinely won't fit on one box. *Prefer "buy one bigger-memory mini" over "split across two" until you truly can't.*

**Purposes a farm serves:** render farms, CI/build farms (Apple's killer case), batch compute, **self-hosted AI inference clusters**, and just plain hosting your own apps with redundancy.

## 📐 Concept - the physical & ops reality (the hidden cost)

This is the part cloud hides from you completely, and the part that bites home-labbers hardest.

- **Power.** Every watt runs 24/7/365. A box drawing 30W costs ~`30W × 24h × 365 / 1000 = 263 kWh/year` ≈ **$40-80/year** depending on your rate. Three boxes + switch + NAS adds up. (Apple Silicon's efficiency is a *real* line item here.)
- **Cooling & noise.** Heat must go somewhere. A few minis on a shelf are fine; a closet full of x86 servers needs airflow and gets loud and hot. Minis win hard here.
- **UPS / battery.** A power blip mid-write corrupts databases and filesystems. A **UPS** (uninterruptible power supply) rides through blips and signals nodes to shut down *gracefully* on a real outage. Non-negotiable if you care about your data.
- **Rack vs shelf.** A shelf (or a literal IKEA shelf, the classic homelab aesthetic) is fine for a handful of minis. A rack is for density/cable-management once you scale; overkill at three nodes.
- **Networking gear.** Managed switch, maybe a small firewall/router (OPNsense/pfSense), cabling. Buy a managed switch from day one if you can, VLANs are worth it.
- **Remote management (KVM/IPMI, Macs are trickier).** On Linux servers, IPMI/BMC lets you see the console and power-cycle a *dead* machine remotely. Macs have nothing equivalent, so people use a **network PDU** (remotely switch the outlet off/on) to force-reboot a hung mini, plus optionally a JetKVM/PiKVM for console access. Plan for "how do I reboot it when SSH is dead and I'm not home?"
- **Backups & RAID.** **RAID is not a backup**, it survives a *disk* failure, not a `rm -rf`, ransomware, or a flood. Follow **3-2-1**: 3 copies, 2 media, 1 offsite. RAID (or ZFS) for availability *and* real backups (e.g., Restic/Borg to an offsite or cloud bucket) for recovery.
- **Monitoring (links to 13).** You can't walk to a server room to "check if it's up." Prometheus + Grafana + alerting (node-exporter for CPU/RAM/disk/temp, alerts to your phone) is how you know a disk is filling up *before* it's full.
- **Security, don't expose things naively (links to 12).** The cardinal sin: port-forwarding a service straight to the internet. **Don't.** Default-deny firewall, nothing exposed publicly unless it absolutely must be, and reach everything over a **VPN/Tailscale** overlay instead. We do exactly this in the first mini-project.
- **Reliability / redundancy.** One box = one point of failure. Redundancy (N+1 nodes, dual ISPs, UPS) costs money and complexity; decide how much you actually need. A home lab can tolerate downtime a hospital can't.
- **The maintenance burden, the real hidden cost.** OS updates, security patches, dying fans, full disks, certificate renewals, that one container that OOMs every Tuesday. **Your time is the most expensive resource in the whole system,** and it's the line item the "$599 vs $X/month" comparison always forgets. Budget for it honestly.

> ⚠️ **Common mistakes (ops edition):** (1) No UPS → corrupted DB on the first power blip. (2) RAID treated as backup → one `rm -rf` and it's gone everywhere. (3) Exposing services to the internet via port-forward → your home network is now a target. (4) No monitoring → you find out it's down from a user. (5) Buying three nodes before mastering one. (6) Running cluster traffic over Wi-Fi.

## 📐 A decision framework - home lab vs colo vs cloud vs hybrid

| Option | What it is | Best for | Watch out for |
|---|---|---|---|
| **Home lab** | Your hardware, your home | Learning, personal hosting, cheap steady compute, privacy | Residential ISP (no static IP, ToS limits on hosting), your power/uptime, your time |
| **Colocation (colo)** | *Your* hardware in *their* data center | "I own the metal but want pro power/cooling/bandwidth/uptime" | Monthly rack/power/bandwidth fees; you still maintain the hardware (or pay remote hands) |
| **Cloud** | *Their* hardware, rented by the second | Spiky/unpredictable load, global reach, managed services, no capex, fast iteration | Egress fees, markup on steady-state, vendor lock-in, less control |
| **Hybrid** | Mix: own steady baseline, burst to cloud | The mature answer for most serious orgs | Complexity: two control planes, data gravity, networking between them |

**The honest decision rule:**

- **Spiky, occasional, global, or "I need a managed DB/queue tomorrow" → cloud.**
- **Steady-state, always-on, egress-heavy, privacy-sensitive, or "I'm learning" → own (home lab / colo).**
- **A real business with both shapes → hybrid:** own the predictable baseline (it's cheaper), burst the spikes to cloud (it's elastic). Best of both.

### When self-hosting is a *mistake*

Be honest with yourself. Self-hosting is the wrong call when:

- **It's load-bearing for customers and you can't do real on-call.** If revenue depends on it and you're the only one who can fix it, at 2am, from your apartment, on your residential ISP, that's a liability, not a flex.
- **The workload is genuinely spiky** (you'd own peak capacity that sits idle 95% of the time).
- **You need a managed service's guarantees** (durable object storage, multi-AZ DB failover) more than you need control. Rebuilding S3's 11-nines durability at home is a fool's errand.
- **Your time is worth more elsewhere.** If maintaining the lab steals the hours you'd spend on the actual product, rent the cloud and move on. The cloud's markup can be the cheapest thing you ever buy.

> 💼 **On the job:** Nobody will ask you to choose dogmatically. They'll ask "should this run in our cluster or in AWS?" and the *good* answer is always a small cost model + a risk assessment, not a preference. Show the math (next section) and the on-call story, and you'll sound like a senior engineer.

## 💻 Build it - mini-project (a): a single hardened headless server

> One box, done *right*: SSH hardening, Docker, a real service behind a reverse proxy, reachable only over Tailscale. This is the foundation; everything else is "more of this." We'll show Linux commands (works on a Linux mini, a NUC, a Pi, or a cloud VM); macOS notes inline. Start with one box (10.1 for Docker, 12.x for the security rationale, 06 for networking).

### Step 0 - fixed address and a name

Reserve the box's IP on your router (DHCP reservation) so it never moves, e.g. `10.0.10.11`, and give it a hostname:

```bash
sudo hostnamectl set-hostname mini01     # Linux
# macOS: sudo scutil --set HostName mini01
```

### Step 1 - SSH key auth, then harden the daemon

From your **laptop**, copy your key up so you never type a password again:

```bash
ssh-copy-id spencer@10.0.10.11      # pushes ~/.ssh/id_ed25519.pub
ssh spencer@10.0.10.11              # should log in with no password
```

Now lock SSH down on the **server**. Edit `/etc/ssh/sshd_config` (on macOS the file is the same path; restart with `sudo launchctl kickstart -k system/com.openssh.sshd`):

```bash
sudo tee /etc/ssh/sshd_config.d/99-hardening.conf >/dev/null <<'EOF'
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
AllowUsers spencer
EOF
sudo systemctl restart ssh    # Linux
```

⚠️ **Keep your current SSH session open** while you test a *new* one. Locking yourself out of a headless box you can't walk to is the classic self-own. Confirm a fresh `ssh spencer@10.0.10.11` works *before* you close the first session.

### Step 2 - firewall: default-deny

Allow only SSH (and, soon, Tailscale). Nothing else is exposed.

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp           # SSH from the LAN
sudo ufw enable
sudo ufw status verbose
```

### Step 3 - install Docker (the engine from 10.1)

```bash
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER        # run docker without sudo (re-login)
docker run --rm hello-world          # smoke test
```

(On macOS you'd install Docker Desktop or `colima`; for pure container work you'd honestly use a Linux box, per the caveats above.)

### Step 4 - a real service behind a reverse proxy

Let's run a tiny web app and put **Caddy** in front of it as a reverse proxy (Caddy auto-manages TLS and has a one-line config). `docker-compose.yml`:

```yaml
services:
  app:
    image: ghcr.io/spencer/nyx-status:latest   # any web app; nginx works to test
    restart: unless-stopped
    expose:
      - "8080"                # internal only - NOT published to the host

  caddy:
    image: caddy:2
    restart: unless-stopped
    ports:
      - "80:80"               # reachable only over Tailscale (step 5 keeps it off the internet)
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile
      - caddy_data:/data

volumes:
  caddy_data:
```

`Caddyfile`, proxy everything to the app, with a health check:

```caddyfile
mini01.tailnet-name.ts.net {
    reverse_proxy app:8080
    encode gzip
}
```

```bash
docker compose up -d
docker compose ps          # both healthy
```

The app is now *only* reachable through Caddy, and Caddy is *only* reachable over the LAN, not the internet. Now we make it reachable to *you*, securely, from anywhere.

### Step 5 - Tailscale instead of port-forwarding

**Never** port-forward this to the internet. Instead, join the box to a **Tailscale** tailnet (a WireGuard-based mesh VPN). Every device you own joins the tailnet and they talk over an encrypted overlay; nothing is exposed publicly.

```bash
curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up --hostname mini01
tailscale ip -4            # e.g. 100.x.y.z - my private overlay address
```

Install Tailscale on your laptop/phone too, and now `http://mini01.tailnet-name.ts.net` works from a coffee shop, but a port scan of your home IP shows **nothing**. (Tailscale can even provision real TLS certs for that `.ts.net` name, which is why the Caddyfile used it.)

**What you just built:** a headless box with key-only SSH, a default-deny firewall, Docker, a service safely behind a reverse proxy, reachable from anywhere only over an encrypted mesh, and invisible to the public internet. That's a *correct* single server. Add monitoring (13) next: a `node-exporter` + `prometheus` + `grafana` stack in the same compose file, alerting to your phone.

## 💻 Build it - mini-project (b): a 3-year cost model in Python

> Prove rent-vs-own with numbers, not vibes. This compares **N Mac minis you own** against **equivalent always-on cloud**, including the costs each side's marketing conveniently omits, power and your time on the owned side, egress and the rental markup on the cloud side.

```python
"""mac_mini_vs_cloud.py - honest 3-year TCO comparison.

Run: python3 mac_mini_vs_cloud.py
All prices are illustrative - plug in your real quotes. Verify Mac prices on apple.com.
"""
from dataclasses import dataclass

YEARS = 3
HOURS_PER_YEAR = 24 * 365

# ---------- knobs you should edit ----------
ELECTRICITY_USD_PER_KWH = 0.18      # your utility rate
YOUR_TIME_USD_PER_HOUR  = 75.0      # what an hour of your maintenance is worth

@dataclass
class OwnedPlan:
    num_minis: int
    mini_price_each: float          # capex, one-time
    watts_each_avg: float           # average draw under your real load
    upfront_networking: float       # switch + UPS + cabling, one-time
    maint_hours_per_month: float    # the hidden cost, per node

    def capex(self) -> float:
        return self.num_minis * self.mini_price_each + self.upfront_networking

    def power_cost(self) -> float:
        kwh = self.num_minis * self.watts_each_avg / 1000 * HOURS_PER_YEAR * YEARS
        return kwh * ELECTRICITY_USD_PER_KWH

    def labor_cost(self) -> float:
        hrs = self.maint_hours_per_month * 12 * YEARS * self.num_minis
        return hrs * YOUR_TIME_USD_PER_HOUR

    def total(self) -> float:
        return self.capex() + self.power_cost() + self.labor_cost()

@dataclass
class CloudPlan:
    instances: int
    instance_usd_per_hour: float    # on-demand; reserved/savings plans are cheaper
    egress_gb_per_month: float
    egress_usd_per_gb: float        # ~0.05-0.09 on AWS after free tier
    managed_services_per_month: float = 0.0   # RDS, load balancer, etc.

    def compute_cost(self) -> float:
        return self.instances * self.instance_usd_per_hour * HOURS_PER_YEAR * YEARS

    def egress_cost(self) -> float:
        return self.egress_gb_per_month * self.egress_usd_per_gb * 12 * YEARS

    def managed_cost(self) -> float:
        return self.managed_services_per_month * 12 * YEARS

    def total(self) -> float:
        return self.compute_cost() + self.egress_cost() + self.managed_cost()


def report(owned: OwnedPlan, cloud: CloudPlan) -> None:
    print(f"\n=== 3-YEAR TOTAL COST OF OWNERSHIP ===\n")
    print("OWNED (Mac minis):")
    print(f"  Capex (hardware+net):  ${owned.capex():>10,.0f}")
    print(f"  Power over 3y:         ${owned.power_cost():>10,.0f}")
    print(f"  Your time over 3y:     ${owned.labor_cost():>10,.0f}")
    print(f"  ----------------------------------")
    print(f"  TOTAL:                 ${owned.total():>10,.0f}\n")
    print("CLOUD (equivalent always-on):")
    print(f"  Compute over 3y:       ${cloud.compute_cost():>10,.0f}")
    print(f"  Egress over 3y:        ${cloud.egress_cost():>10,.0f}")
    print(f"  Managed svcs over 3y:  ${cloud.managed_cost():>10,.0f}")
    print(f"  ----------------------------------")
    print(f"  TOTAL:                 ${cloud.total():>10,.0f}\n")
    diff = cloud.total() - owned.total()
    winner = "OWNING" if diff > 0 else "CLOUD"
    print(f">>> {winner} is cheaper by ${abs(diff):,.0f} over {YEARS} years.\n")


if __name__ == "__main__":
    # 3 × M4 Pro minis (64GB), modest avg draw, light maintenance.
    owned = OwnedPlan(
        num_minis=3, mini_price_each=1999, watts_each_avg=25,
        upfront_networking=600, maint_hours_per_month=1.0,
    )
    # Roughly comparable always-on cloud (an inference/CI box class) + steady egress.
    cloud = CloudPlan(
        instances=3, instance_usd_per_hour=0.90,
        egress_gb_per_month=2000, egress_usd_per_gb=0.08,
        managed_services_per_month=50,
    )
    report(owned, cloud)
```

Running this with the sample numbers shows owning winning by a wide margin for *steady-state* compute, and the moment you cut the cloud to "only on 8 hours a day" or "only 30 days total," the cloud flips to winning. **That flip is the entire lesson.** Things to try: set `instance_usd_per_hour` to a *reserved*/savings-plan rate; crank egress to 50 TB/month (watch cloud explode); set `maint_hours_per_month` honestly high and watch owning lose its shine. The model doesn't tell you the answer, it tells you *which assumptions* drive the answer, which is the actually-useful thing.

> ⚠️ **Be honest about what the model omits:** cloud's *elasticity value* (scale to zero), the durability/SLA of managed services, the resale value of the minis after 3 years, and the *opportunity cost* if a self-hosted outage costs you customers. A model is a thinking tool, not an oracle.

## ✏️ Exercises

**1. Server vs desktop.** Name three concrete things server-grade hardware has that a Mac mini lacks, and for each, name one workload where its absence would actually bite.

<details><summary>Solution</summary>

(1) **ECC memory**, bites long-running databases/scientific compute where a silent bit-flip corrupts data over months of uptime. (2) **IPMI/BMC out-of-band management**, bites any remote/colo deployment: when the OS hangs you can't remotely see the console or power-cycle (you need a network PDU as a workaround). (3) **Redundant PSU / hot-swap RAID**, bites a high-availability service that must survive a single component failure without downtime. Note these are exactly the cases where a Mac mini is the *wrong* tool, which is the point.
</details>

**2. The egress trap.** A service serves 40 TB/month of outbound traffic from a cloud instance at $0.08/GB egress. What's the *annual* egress bill, and how does that reframe the rent-vs-own decision?

<details><summary>Solution</summary>

`40 TB = 40,000 GB`. Monthly: `40,000 × $0.08 = $3,200`. Annual: `$3,200 × 12 = $38,400`, **just for egress**, before any compute. Over 3 years that's ~$115k. A few minis on a home/colo connection (where egress is your flat ISP bill) make this disappear, which is precisely why egress-heavy, steady workloads are the textbook self-hosting win. It reframes the decision from "compute cost" to "data-movement cost," which is often the dominant term.
</details>

**3. Unified memory math.** A 70B-parameter model quantized to 4-bit needs roughly `70e9 × 0.5 bytes ≈ 35 GB` for weights (plus overhead for context/KV cache). Explain why a 64GB M4 Pro mini can serve it but a 24GB consumer GPU cannot, and what "memory-bandwidth-bound" means for the *speed* you'd get.

<details><summary>Solution</summary>

The model's weights (~35GB + several GB of KV cache/context) must fit in memory the accelerator can read. The 64GB unified-memory mini holds all of it in one pool the GPU accesses directly, it fits. A 24GB GPU can't hold 35GB+, so the model won't load without splitting across multiple cards or offloading layers to slow system RAM (which tanks performance). **Memory-bandwidth-bound** means each generated token requires streaming the relevant weights through the accelerator, so throughput is gated by how fast you can move bytes from memory, not by raw FLOPS, which is why the mini's ~273 GB/s bandwidth + "it all fits" beats a faster-FLOPS card that can't hold the model. (More in 20.3.)
</details>

**4. Cost-model sensitivity.** Using project (b)'s script, find the cloud `instance_usd_per_hour` at which cloud and 3 owned minis break even (hold all else at the sample values). Then explain conceptually why *running the cloud instances only part-time* changes the answer.

<details><summary>Solution</summary>

Set owned total ≈ cloud total and solve for the hourly rate (it'll land in the low-to-mid cents/hour range, well below typical on-demand prices, which is *why* owning wins for always-on). Conceptually: the owned cost is *fixed* (you paid the capex regardless of utilization), while cloud cost is *proportional to hours used*. If you only need the compute 8h/day or for occasional bursts, cloud's bill shrinks linearly (scale to zero when idle) while your owned cost stays the same, so at low utilization cloud wins, and at high/steady utilization owning wins. The crossover is a utilization question, which is the single most important variable in the whole decision.
</details>

**5. Security review.** A friend port-forwards their home Postgres (5432) to the internet "so they can reach it from work." List what's wrong and give the correct architecture.

<details><summary>Solution</summary>

What's wrong: (1) Postgres is now reachable by every scanner on the internet, automated bots hammer 5432 within minutes, brute-forcing credentials. (2) The database is the *crown jewels*; exposing it directly means one auth bypass or unpatched CVE compromises everything. (3) No network-layer barrier, the only thing between the attacker and your data is Postgres's own auth. (4) It advertises the home IP and invites the rest of the home network to be attacked.

Correct architecture: **do not port-forward anything.** Put the database on its own VLAN with a default-deny firewall (only the app hosts may reach 5432, LAN-only). To reach it remotely, join the laptop and the DB host to a **Tailscale tailnet** and connect over the encrypted overlay to the box's private 100.x address, Postgres is *never* exposed publicly; a port scan of the home IP shows nothing. This is exactly mini-project (a)'s pattern (Tailscale + default-deny firewall), and it ties to 12.x (defense in depth) and 06 (network segmentation).
</details>
