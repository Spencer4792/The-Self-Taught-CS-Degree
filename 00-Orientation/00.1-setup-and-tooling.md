An hour here saves dozens of hours later. ## Start here - if I've literally never done this before

Before any commands, let me ground myself with a plain-language picture. If I already have a terminal and Python working, I can skim to [0.1.1](#011-the-command-line-my-new-home). But I genuinely recommend reading this on-ramp once. It's short, and it makes every later step feel obvious instead of magical.

### What is a "program," really?

A program is just **a list of instructions a computer follows, one after another, very fast.** That's the whole idea. A recipe is a program for a cook: "preheat oven, mix flour and sugar, bake 20 minutes." A computer program is a recipe for a machine: "ask the user their name, store it, print 'Hello' plus that name."

The catch is that computers are *relentlessly literal*. A cook reading "add a pinch of salt" uses judgment. A computer has none. If I tell it to repeat a step and forget to tell it when to stop, it will repeat forever. This literalness is frustrating at first and then becomes the best thing about the job: the computer does *exactly* what I said, so when something's wrong, the answer is always somewhere in what I actually wrote. There's no luck involved. That's strangely comforting.

### What is "code"?

**Code is the program written in a language a human can read and a computer can be made to understand.** Here's a complete, real Python program:

```python
name = input("What's your name? ")
print("Hello, " + name + "! Welcome to programming.")
```

Two lines. The first asks me a question and remembers my answer in a labeled box called `name`. The second prints a greeting using that box. That is genuinely a program, not a toy version of one, the real thing. By the end of the next chapter ([0.2](00.2-programming-fundamentals.md)) I'll understand every piece of it. For now I just want to see that code is *not* an arcane wall of symbols. It's short, readable sentences telling the machine what to do.

### What is Python and why it first?

**Python is a programming language**, a specific set of words and grammar rules I write code in. There are hundreds of languages (JavaScript, Java, C, Go...). I'm starting with Python because it reads almost like English, it hides the boring machinery, and it's used everywhere from web servers to AI to data science. The thing that *runs* my Python code is a program called the **Python interpreter**. When I "install Python," I'm installing that interpreter, the engine that reads my `.py` file and actually does what it says.

### How do these pieces fit together?

Here's the whole pipeline I'm about to build, in one breath:

1. I **type code** into an **editor** (a text editor or an IDE like PyCharm).
2. I save it as a file ending in `.py`, a **Python file**.
3. I open a **terminal** (the typing-commands window) and tell the **Python interpreter** to run that file.
4. The interpreter reads my instructions and prints results or errors.

Every other tool in this chapter, virtual environments, git, the debugger, exists to make this loop smoother, safer, and reproducible. So if any later section feels abstract, I come back to this list and ask "which part of the loop is this helping?"

> ⚠️ **The single most reassuring fact for a beginner:** every mistake here is undoable. The terminal can feel scary because it doesn't ask "are you sure?", but on the files *you* create in a practice folder, the worst case is you delete something you can recreate in 10 seconds. We're going to make a `sandbox` folder precisely so I can mess around with zero fear.

## 0.1.1 The command line: my new home

Every serious engineer lives partly in a terminal. It feels intimidating because it's silent and unforgiving, but it's just a **REPL for your operating system**: you type a command, the OS runs a program, it prints output. That's the whole loop.

> 🌱 **New word, REPL.** It stands for Read-Eval-Print Loop. The thing *reads* what I type, *evaluates* (runs) it, *prints* a result, and *loops* back to wait for the next thing. A calculator is a REPL. The terminal is a REPL for your whole computer. Python has its own REPL too (type `python` and you get one). I'll use the word a lot, so it's worth owning now.

A **shell** is the program that reads what I type and runs it. On macOS and Linux the default is usually `zsh` or `bash`. On Windows it's PowerShell, though I'll want **WSL2** (Windows Subsystem for Linux) so I'm working in a real Linux environment like most servers.

### How do I even open the terminal? (described step by step)

I shouldn't assume this is obvious, I once didn't know either.

- **macOS:** Press `Cmd+Space` to open Spotlight (a search bar appears at the top-center of the screen). Type `Terminal` and press Enter. A window opens, usually white or black, showing a line of text ending in a `%` or `$` symbol, with a blinking cursor. That blinking cursor is the shell waiting for me. The line before the cursor (something like `spencer@Mac ~ %`) is called the **prompt**: it tells me my username, my computer's name, where I'm standing (`~` means home), and then the symbol.
- **Windows:** Click the Start menu (bottom-left), type `PowerShell`, and click "Windows PowerShell." For the Linux experience this book assumes, I'll install WSL2 (one command, see the box below) and then open "Ubuntu" from the Start menu, which gives me a real Linux shell with a `$` prompt.
- **Linux:** It's usually `Ctrl+Alt+T`, or search "Terminal" in your apps.

> 💡 **Installing WSL2 on Windows (one-time):** open PowerShell *as Administrator* (right-click → "Run as administrator") and run `wsl --install`. Reboot when it tells me to. After reboot it sets up Ubuntu and asks me to pick a username and password. From then on, "open the terminal" means "open Ubuntu." Everything in this book then works the same as on macOS/Linux.

When the window is open, the very first thing to try is harmless: type `pwd` and press Enter. It prints the folder I'm currently "standing in." Nothing broke. That's the loop, type, Enter, see output. Welcome home.

### The mental model

The filesystem is a tree. There's a **current working directory** ("where I'm standing"). Almost every command operates relative to where I'm standing unless I give an absolute path (one starting from the root, `/`).

> 🧭 **Analogy that made this click for me.** Think of the filesystem as a building. Folders are rooms; files are objects in those rooms. `pwd` is "which room am I in?" `ls` is "look around, what's in this room?" `cd` is "walk into another room." `cd ..` is "step back out into the hallway." An **absolute path** like `/Users/spencer/projects` is full directions from the front door of the building. A **relative path** like `projects` is "the projects room, from right here." Most early confusion is just not knowing which room you're standing in, so when in doubt, run `pwd`.

The commands I'll use constantly:

```bash
pwd              # print working directory - "where am I standing?"
ls               # list files here
ls -la           # list ALL files (including hidden) in long format
cd projects      # change directory into ./projects
cd ..            # go up one level
cd ~             # go to my home directory
mkdir notes      # make a directory
touch a.txt      # create an empty file
cp a.txt b.txt   # copy
mv a.txt c.txt   # move/rename
rm c.txt         # remove (careful - no trash can)
cat a.txt        # dump a file's contents to the screen
less a.txt       # page through a file (q to quit)
grep "TODO" *.py # search for "TODO" in all .py files
```

> 🌱 **A few beginner notes on the table above.** A "hidden" file is just one whose name starts with a dot (`.venv`, `.gitignore`); `ls` skips them unless I add `-a`. The `*` in `*.py` is a **wildcard** meaning "anything," so `*.py` means "every file ending in `.py`." And yes, `rm` really has no trash can, it deletes immediately and permanently. I'll be careful with it (see Common Mistakes below).

Two ideas that make the shell click:

**1. Everything is text, and text flows through pipes.** The `|` character takes the output of one program and feeds it as the input of the next. This is the Unix philosophy: small tools that do one thing, composed together.

```bash
ls -la | grep ".py" | wc -l    # count how many .py files are listed
```

`ls` lists, `grep` filters to lines containing `.py`, `wc -l` counts lines. Three tiny programs, composed into "how many Python files are here?"

> 🧭 **Picture the pipe as a conveyor belt.** `ls` dumps a list onto the belt. `grep` stands at the next station and throws away anything that doesn't contain `.py`. `wc -l` stands at the end and counts what's left. Each worker is dumb and specialized; the power is in lining them up.

**2. Redirection sends output to files instead of the screen.**

```bash
echo "hello" > log.txt     # write (overwrite) "hello" into log.txt
echo "world" >> log.txt    # append a second line
python script.py > out.txt 2> err.txt   # stdout to out.txt, stderr to err.txt
```

That `2>` is worth understanding now because it shows up everywhere: a process has three default streams, **stdin** (0, input), **stdout** (1, normal output), and **stderr** (2, error output). Keeping them separate is why you can pipe a program's results somewhere while still seeing its errors on screen.

> 🌱 One tiny but high-value distinction: `>` **overwrites** the file (wipes it, then writes), while `>>` **appends** (adds to the end). Reaching for `>` when I meant `>>` is a classic way to clobber a file. When unsure, use `>>`.

> 🧪 **Micro-exercise.** Create a folder `sandbox`, `cd` into it, create three text files, and write a single piped command that prints the number of files whose name contains the letter `a`. (Answer: `ls | grep a | wc -l`.)

## 0.1.2 Installing Python the right way

The biggest early trap: your system already has *a* Python, and you should almost never touch it, the OS depends on it. I want my own, managed versions.

> 🌱 **Wait, I already have Python?** Probably, macOS and Linux ship one for their own internal use. The problem is it's *the operating system's* Python; if I install packages into it or upgrade it, I can break system tools. So the rule is: leave the system one alone, install my own. The steps below do exactly that.

**Recommended approach, a version manager.** Use [`pyenv`](https://github.com/pyenv/pyenv) (macOS/Linux) so I can install and switch between Python versions per project:

```bash
# macOS (with Homebrew installed):
brew install pyenv
pyenv install 3.12.4      # install a specific version
pyenv global 3.12.4       # make it my default
python --version          # => Python 3.12.4
```

> 💡 **What's Homebrew?** It's the standard package manager for macOS, a tool that installs other tools from the terminal. If `brew` isn't found, install it by pasting the one-line command from [brew.sh](https://brew.sh) into the terminal and following the prompts. (It'll ask for my password; that's expected for installing software.)

On Windows, either use `pyenv-win` or install from python.org and **check "Add Python to PATH"** during install.

> ⚠️ **The "Add Python to PATH" checkbox is easy to miss and causes hours of pain.** When the python.org installer first appears on Windows, there's a small checkbox at the bottom of the *first* screen labeled **"Add python.exe to PATH."** Tick it before clicking "Install Now." If I forget, the terminal won't find `python` and I'll get "command not found." Fix: re-run the installer, choose "Modify," and ensure PATH is added, or just check the box and reinstall.

### The simplest possible path (if pyenv feels like too much right now)

Honestly, for my very first day, I don't *need* a version manager. I can:

1. Go to [python.org/downloads](https://www.python.org/downloads/), click the big yellow "Download Python 3.x" button.
2. Run the installer. **On Windows, check "Add Python to PATH."** On macOS, just click through.
3. Open a fresh terminal and type `python3 --version`. If it prints a version number like `Python 3.12.4`, I'm done.

I can come back and adopt `pyenv` later when juggling versions across projects actually becomes a thing I feel. Don't let perfect tooling block me from writing my first line of code.

### Why versions matter

Python the language evolves. Code written for 3.12 may use syntax that 3.8 doesn't understand. Servers run specific versions. A version manager means "this project uses 3.11, that one uses 3.12" never becomes a crisis.

### `python` vs `python3` - a beginner gotcha worth naming now

On many macOS/Linux systems, `python` either doesn't exist or points at an old version, while `python3` points at the modern one. If `python` gives "command not found," try `python3`. Same for `pip` vs `pip3`. Once I set up a virtual environment (next section), this confusion disappears, inside a venv, `python` reliably means *that project's* Python.

## 0.1.3 Virtual environments: the concept that prevents 80% of "it works on my machine"

Here's the problem a virtual environment solves. Project A needs version 1.0 of some library. Project B needs version 2.0 of the *same* library. If I install packages globally, these two projects fight, and one breaks.

> 🧭 **Analogy.** Imagine every project lives in its own apartment with its own kitchen. A virtual environment is that private kitchen: Project A can stock it with version 1.0 of a tool, Project B stocks its own kitchen with version 2.0, and neither raids the other's fridge. The alternative, one shared communal kitchen (the system Python), is where roommates fight over whose ingredients are whose. Private kitchens, always.

> 🌱 **What's a "library" or "package"?** It's pre-written code by someone else that I can install and use, so I don't reinvent everything. `requests` (for fetching web pages) is a package. `pip` is the tool that downloads and installs packages. "Dependencies" just means "the packages my project depends on."

A **virtual environment** is just a self-contained folder holding its own copy of Python and its own `site-packages` (where installed libraries live). Activate it, and `python` and `pip` point *inside that folder* instead of at the system. Each project gets its own isolated sandbox.

```bash
cd my-project
python -m venv .venv          # create a venv in a folder called .venv
source .venv/bin/activate     # activate it (macOS/Linux)
# .venv\Scripts\activate      # activate it (Windows PowerShell)

pip install requests          # installs ONLY into this venv
pip freeze > requirements.txt # record exact versions for reproducibility
deactivate                    # leave the venv
```

When the prompt shows `(.venv)` at the front, I'm inside the sandbox. `pip install` now only touches this project. `pip freeze > requirements.txt` writes down every package and its exact version so a teammate (or future me, or a server) can recreate the *exact* environment with `pip install -r requirements.txt`. This is reproducibility, and it's non-negotiable for real work.

> 🌱 **How do I know if I'm "in" the venv?** Look at the start of my prompt. After `source .venv/bin/activate`, it gains a `(.venv)` prefix, like `(.venv) spencer@Mac my-project %`. That prefix is the venv's way of waving at me. When it's gone, I'm back in the system environment. If I open a *new* terminal window, the venv is **not** active, I have to `source` it again. Forgetting this is the #1 reason "the package I just installed isn't found."

> **The rule I'll never break:** one virtual environment per project. Never `pip install` into the system Python. The instant a project starts, `python -m venv .venv` is the first move.

### A note on newer tooling

Tools like [`uv`](https://github.com/astral-sh/uv) and `poetry` manage environments and dependencies more ergonomically and are worth adopting later. But I'll learn `venv` + `pip` first because they're universal and they make the underlying mechanics visible. You can't appreciate the convenience of `uv` until you've felt the thing it automates.

## 0.1.4 PyCharm: setting up my IDE

An **IDE** (Integrated Development Environment) bundles an editor, a debugger, a test runner, and project tooling. PyCharm (from JetBrains) is excellent for Python. VS Code is the lighter, more general alternative, either is fine; I'll describe PyCharm since it's on my radar.

> 🌱 **Editor vs IDE vs terminal, what's the difference?** An **editor** is where I type and save code (even Notepad technically works). An **IDE** is a souped-up editor that *also* runs my code, debugs it, autocompletes as I type, and underlines mistakes in red before I even run it. The **terminal** is the separate command-typing window. A nice thing: PyCharm and VS Code have a terminal *built in* (a panel at the bottom), so I can edit and run in one window. I don't have to choose between them, I'll use all three together.

**First-time setup that matters:**

1. **Create a new project** and point its **interpreter** at the `.venv` I created (Settings → Project → Python Interpreter → Add → Existing → select `.venv/bin/python`). This is the single most important setting, it's what makes PyCharm use my isolated environment instead of the system Python.
2. **Learn the debugger before I think I need it.** Set a **breakpoint** by clicking in the gutter next to a line number. Run in debug mode (the little bug icon). Execution pauses at the breakpoint and I can inspect every variable, step **over** a line (F8), step **into** a function call (F7), and resume (F9). Print-statement debugging is fine for quick checks, but a real debugger lets me freeze the program and *look around*. I'll lean on this hard in the data structures chapters, watching a linked list mutate node by node is how it finally becomes real.
3. **Configure the test runner** (more on this below) so I can run tests with one click.

> 🌱 **What a breakpoint looks like, described.** The "gutter" is the thin vertical strip just to the *left* of the line numbers. When I hover there, a faint red dot appears; click it and it becomes a solid red dot, that's a breakpoint set on that line. When I run with the bug icon (top-right toolbar), the program runs normally until it hits that red dot, then *freezes*. A panel at the bottom lights up showing every variable's current value. It's like hitting pause on a movie to study a single frame.

> The keyboard shortcuts pay for themselves: `Shift+Shift` (search everything), `Cmd/Ctrl+B` (jump to definition), `Shift+F6` (rename a symbol everywhere safely), `Cmd/Ctrl+/` (toggle comment). Learning these turns the IDE from a fancy text editor into a power tool.

## 0.1.5 Git: version control, conceptually

I have a whole chapter later ([11.1](../11-Version-Control/11.1-git-and-github.md)) that goes deep, branching, rebasing, cherry-pick, the internal object model. Here I just want the minimum to not lose work, plus the right mental model so the deep chapter lands.

> 🌱 **What problem is git even solving?** Have I ever ended up with `essay_final.doc`, `essay_final_v2.doc`, `essay_FINAL_really.doc`? Git is the disciplined, infinite version of that, it remembers every saved state of my whole project so I can go back to any of them, see exactly what changed, and never lose work. It's also how teams work on the same code without overwriting each other.

**The mental model:** git is a tool that takes **snapshots** of my project over time. Each snapshot is a **commit**. A commit records the full state of the tracked files plus a message, an author, a timestamp, and a pointer to the previous commit. Because each commit points to its parent, the history is a chain (really a graph). That's it, git is "a graph of snapshots."

The everyday loop:

```bash
git init                      # turn the current folder into a git repo (once)
git status                    # what's changed?
git add .                     # stage all changes for the next snapshot
git commit -m "Add hash table" # take the snapshot with a message
git log --oneline             # see the history
```

There are three "places" a file can be, and confusing them is the #1 source of early git pain:

- **Working directory**, the actual files I'm editing right now.
- **Staging area (index)**, a holding pen for changes I've marked (`git add`) to include in the next commit.
- **Repository**, the committed history.

`git add` moves changes from working directory → staging. `git commit` moves staging → repository. Picture it as a two-step airlock, and git stops being mysterious.

> 🧭 **The airlock picture, expanded.** I'm packing a box to mail (a commit). The **working directory** is my messy desk with everything on it. **Staging** is me choosing specific items and setting them inside the box but not sealing it yet (`git add`). **Committing** is taping the box shut and labeling it with a description (`git commit -m "..."`). Two steps on purpose: I get to decide *exactly* what goes in each box instead of mailing my whole desk.

To back up to GitHub:

```bash
git remote add origin git@github.com:Spencer4792/my-project.git
git push -u origin main
```

> 🌱 **GitHub is not git.** Git is the tool on my computer; **GitHub** is a website that stores copies of git repositories online (a backup + a place to collaborate and show employers my work). `git push` uploads my commits there. I'll set up a free GitHub account early, a public profile with steady commits is a real asset when job hunting.

For now that's enough to never lose work. The deep dive comes in Part 11.

## 0.1.6 Writing my first real test (because I'll test everything in this book)

Throughout this book I implement data structures and algorithms from scratch. The way I'll *know* they work is by writing tests. Testing isn't an advanced topic to get to "later", it's how I get fast, trustworthy feedback. I'll use `pytest`.

> 🌱 **What's a "test"?** It's just a tiny extra bit of code that checks my real code did the right thing, automatically. Instead of running my program and eyeballing the output every time, I write `assert add(2, 3) == 5` once, and from then on the computer checks it for me in a fraction of a second. `assert X` means "I claim X is true; if it isn't, yell at me." A passing test is the computer saying "yep, still works."

```bash
pip install pytest
```

Make two files in a project folder:

```python
# mathy.py
def add(a, b):
    return a + b

def is_prime(n):
    if n < 2:
        return False
    for d in range(2, int(n ** 0.5) + 1):
        if n % d == 0:
            return False
    return True
```

```python
# test_mathy.py
from mathy import add, is_prime

def test_add():
    assert add(2, 3) == 5
    assert add(-1, 1) == 0

def test_is_prime():
    assert is_prime(2)
    assert is_prime(13)
    assert not is_prime(1)
    assert not is_prime(15)
```

Run it:

```bash
pytest -v
```

Green means every `assert` held. The pattern is **Arrange, Act, Assert**: set up inputs, run the thing, check the result. When I implement a stack later, I'll write the tests first describing how it *should* behave, then make them pass. That's test-driven development, and it's the closest thing to a cheat code for learning data structures, the tests force me to define correct behavior precisely before I build it.

> 🌱 If `pytest` itself isn't found after installing it, 9 times out of 10 my venv isn't active (no `(.venv)` in the prompt). Re-run `source .venv/bin/activate` and try again. This exact situation is in the Troubleshooting FAQ below.

> 🧪 **Micro-project.** Write a function `word_count(text)` that returns a dict mapping each word to how many times it appears (lowercased, punctuation stripped). Write the tests *first*, decide what `word_count("The cat the CAT.")` should return before you implement it, then make them pass. This tiny exercise touches strings, dicts, loops, and the test loop I'll use all book long.

## ⚠️ Common mistakes

These are the specific ways beginners (me included) get stuck. Knowing the *shape* of the mistake makes it a 30-second fix instead of a lost afternoon.

- **`rm` with a wildcard.** `rm *.txt` deletes every `.txt` file in the current folder, instantly, no trash can. `rm -rf` on the wrong folder is how people delete real work. Habit: before any `rm` with `*`, run the same pattern with `ls` first (`ls *.txt`) to *see* what would be hit. Never run `rm -rf` unless I can say out loud exactly what it'll destroy.
- **Editing in the wrong folder.** I create files but `ls` doesn't show them, because I `cd`'d somewhere else. Fix: `pwd` to confirm where I'm standing.
- **Installing into the system Python, not the venv.** I `pip install`, then my code says "module not found." Almost always: the venv isn't active. Look for `(.venv)` in the prompt.
- **Forgetting the venv in a new terminal.** Each new terminal window starts fresh with no venv active. Re-`source` it.
- **`python` vs `python3` (and `pip` vs `pip3`).** Outside a venv, `python` may be missing or old. Inside a venv, just use `python`. If "command not found," try the `3` variant.
- **The "Add Python to PATH" miss on Windows.** "python is not recognized as an internal or external command" = PATH wasn't set during install. Re-run installer → Modify → add to PATH.
- **`> ` instead of `>>`.** `>` overwrites; I lose the file's previous contents. When appending, use `>>`.
- **Saving the file but running the old version.** Some editors don't auto-save. If my changes "aren't taking effect," save (`Cmd/Ctrl+S`) and run again.
- **Smart quotes.** Copying code from a web page or doc sometimes turns `"` into curly `"` `"`, which Python rejects with a `SyntaxError`. Retype the quotes in a code editor.

## 🩺 Troubleshooting FAQ

When the environment fights me, it's almost always one of these. I'll work through them in order.

**Q: `command not found: python` (or `python3`).**
The shell can't find a Python interpreter on the **PATH**. PATH is just a list of folders the shell searches when I type a command name. Fixes, in order: (1) try `python3` instead of `python`; (2) confirm Python is installed (`which python3` should print a path); (3) on Windows, re-run the installer and check "Add Python to PATH"; (4) on macOS with pyenv, make sure pyenv's init lines are in my shell config (`~/.zshrc`), `pyenv init` prints what to add, then open a new terminal.

**Q: `pip install` worked, but `import that_package` says `ModuleNotFoundError`.**
I almost certainly installed into a *different* Python than the one running my code. Check: does my prompt show `(.venv)`? If not, `source .venv/bin/activate` and reinstall. To be 100% sure which Python and pip I'm using: `which python` and `which pip` (they should both point inside `.venv`). A bulletproof install command is `python -m pip install <package>`, it installs into *the same* Python you're invoking, sidestepping `pip`-points-elsewhere confusion.

**Q: PyCharm runs my code with the wrong Python / can't find my packages.**
PyCharm has its own interpreter setting, separate from my terminal. Go to Settings → Project → Python Interpreter and confirm it's pointed at `.venv/bin/python` (macOS/Linux) or `.venv\Scripts\python.exe` (Windows). If the package is installed in the terminal but PyCharm can't see it, the interpreter is mismatched, this fixes it.

**Q: `permission denied` when running a script or command.**
Two common causes. (1) The file isn't marked executable: that only matters for running a file *directly* like `./script.sh`; I can sidestep it entirely by running `python script.py` instead. If I do need it executable: `chmod +x script.sh`. (2) I'm trying to write somewhere the OS protects (like a system folder). Fix: work inside my home directory / project folder, not system paths.

**Q: Should I fix a permission error by adding `sudo`?**
Usually **no**. `sudo` runs a command as the all-powerful administrator and is exactly how people accidentally break their system Python or create root-owned files they can't later edit. If a normal `pip install` *seems* to need `sudo`, that's a signal I'm installing into the system Python instead of a venv, fix the venv, don't reach for `sudo`.

**Q: `source: no such file or directory: .venv/bin/activate`.**
The venv doesn't exist yet (or I'm not in the project folder). Run `python -m venv .venv` first, and `pwd`/`ls` to confirm `.venv` is actually here.

**Q: My terminal prompt shows `(.venv)` but `python` is still the old/system one.**
Rare, but happens after weird PATH edits. Close every terminal, open a fresh one, `cd` to the project, `source .venv/bin/activate` again. A fresh shell clears stale state more often than any clever fix.

**Q: `SyntaxError` on a line that looks fine.**
Check for smart/curly quotes (from copy-paste), mixing tabs and spaces for indentation (pick spaces; PyCharm does this by default), or a missing colon `:` at the end of an `if`/`for`/`def` line. The little red squiggle in the IDE usually points right at it.

**Q: It "doesn't work" and I have no idea why.**
Read the **last line** of the error first (the actual error type and message), then the line number it points to. Errors are not the enemy, they're the most specific help I'll ever get. The next chapter ([0.2](00.2-programming-fundamentals.md)) has a whole section on reading tracebacks, and [0.3](00.3-problem-solving.md) covers systematic debugging.

### Solutions

1. **Where am I?** `pwd` prints an absolute path like `/Users/spencer` (my home directory), that's the room I'm standing in. `ls` lists that room's contents (e.g., `Desktop Documents Downloads ...`). Together they answer "where am I and what's here?"

2. **Build a tiny tree.**
   ```bash
   cd ~
   mkdir practice
   cd practice
   mkdir code notes        # mkdir can take several names at once
   cd code
   touch hello.py
   ls                      # => hello.py
   cd ..
   ls                      # => code  notes
   ```

3. **Pipe practice.**
   ```bash
   touch apple.txt apricot.txt banana.txt cherry.txt avocado.txt
   ls | grep "^a" | wc -l   # => 3  (apple, apricot, avocado)
   ```
   `ls` lists the names, `grep "^a"` keeps only those starting with `a` (the `^` anchors to the start of the line), `wc -l` counts them.

4. **Redirection.**
   ```bash
   echo "Day 1: set up my environment" > journal.txt   # creates/overwrites
   echo "Day 1: ran my first commands" >> journal.txt  # appends
   cat journal.txt
   ```
   The second line uses `>>` (append). If I'd used `>` again, it would have **overwritten** the file, erasing the first line.

5. **Venv lifecycle.**
   ```bash
   mkdir venv-test && cd venv-test
   python -m venv .venv
   source .venv/bin/activate        # prompt now starts with (.venv)
   which python                     # => .../venv-test/.venv/bin/python
   pip install requests
   pip freeze                       # => requests==... plus its dependencies
   deactivate                       # prompt returns to normal
   ```
   **Before** activating, `which python` points at the system/pyenv Python (somewhere like `/usr/bin/python3` or a pyenv shim). **After** activating, it points *inside* `.venv`. That redirection is the entire trick of virtual environments.

6. **First commit.**
   ```bash
   git init
   touch readme.txt
   git add readme.txt   # file is now STAGED
   git commit -m "first commit"
   git log --oneline    # shows one commit
   ```
   After `git add` but before `git commit`, the file is in the **staging area (index)**, chosen for the next snapshot but not yet committed to the repository.

7. **Break it on purpose.** With no venv active, `python -c "import requests"` likely raises `ModuleNotFoundError`, unless `requests` happens to be installed in the system Python. The point: the `requests` I installed in exercise 5 lives *only* inside `venv-test/.venv`. Outside that venv, the interpreter doesn't see it. That isolation is the feature, not a bug.

8. **Diagnose a fake bug.** Two most likely causes: (a) the venv wasn't active when they ran the script, so `pip` installed into one Python and the script ran under another; (b) `pip` and `python` resolve to different interpreters even outside a venv. Single confirming command: `python -m pip install pandas` (forces install into *the* python they're using), or `which python && which pip` to see if the two diverge.
