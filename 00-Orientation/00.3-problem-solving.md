# Chapter 0.3 - Problem-Solving & Computational Thinking

> *Goal: by the end of this chapter I have a repeatable method for attacking a problem I don't immediately know how to solve, the actual skill that gets me hired, gets me through interviews, and carries me through the rest of this book. I'll learn the framework, then watch it solve four real problems from messy first thoughts to clean, tested code.*

Here's the secret nobody tells beginners: professional programmers do **not** look at a problem and instantly know the answer. They look at a problem and apply a *method*, a way of breaking the unknown into knowable pieces. The syntax from [Chapter 0.2](00.2-programming-fundamentals.md) is the vocabulary; *this* chapter is learning to write the essay. It's the difference between knowing words and being able to think.

This is the most important chapter in the orientation. Syntax I can always look up. The ability to face a blank screen and a problem I've never seen, and *make progress anyway*, that's the durable skill. So this chapter is mindset and method, and it's the connective tissue for everything that follows.

> 🧭 **The one idea to carry through the whole chapter.** Solving a hard problem is never one giant leap. It's a staircase of small, safe steps: understand it, play with examples, get *anything* working, then make it good. The people who seem brilliant aren't skipping steps, they've just done the staircase so many times it looks like a leap.

## 0.3.1 The four pillars of computational thinking

Before the framework, four mental moves underneath it. These are the "thinking tools", I'll use them without naming them once they're habit.

### 1. Decomposition - break it into smaller problems

A big problem is scary; a small problem is a Tuesday. **Decomposition** is splitting "build a to-do app" into "store a task," "list tasks," "mark one done," "remove one." Each piece is solvable alone, and the whole is just the pieces wired together.

> 🧭 *Analogy:* I don't "clean the house." I clean the kitchen, then the bathroom, then the bedroom. "Clean the house" is paralyzing; "wipe this counter" is doable. Code is identical.

### 2. Pattern recognition - "I've seen this shape before"

Most problems are variations on shapes I've met. "Count how many times each word appears" and "count how many of each product sold" are the *same shape*, tally things into a dict. The more problems I solve, the bigger my library of shapes, and the faster I recognize "oh, this is just a counting problem / a filtering problem / a transform-each-item problem."

### 3. Abstraction - ignore what doesn't matter right now

**Abstraction** is focusing on the essence and hiding the irrelevant detail. When deciding *how* to find duplicates, I don't care whether the items are names or numbers, I care that I need fast "have I seen this?" checks (→ a set). Stripping away specifics reveals the underlying problem. It's also why functions exist: `is_prime(n)` lets me *use* primality without re-thinking how it's computed.

### 4. Pseudocode / algorithms - the plan before the code

An **algorithm** is just a precise sequence of steps that solves a problem. **Pseudocode** is that plan written in plain language before I fight with syntax. Planning in English first means I solve the *logic* with my full brain, then translate to Python as a separate, easier step. Two hard things done one at a time instead of together.

```
# pseudocode for "find the largest number in a list"
set 'biggest' to the first number
for each number in the rest of the list:
    if this number is bigger than 'biggest':
        update 'biggest' to this number
return 'biggest'
```

Notice I solved it completely without a single line of Python. Translating that to code is now almost mechanical.

> 💼 **On the job / interview angle.** In an interview, *think out loud using these pillars.* "Let me decompose this... this looks like a counting pattern... I'll abstract the items as just keys... here's my pseudocode." Interviewers are hiring your *process*, not your ability to memorize answers. A candidate who narrates a clear method while occasionally fumbling syntax beats a silent one who eventually types something correct. The method *is* the signal.

## 0.3.2 The framework: a repeatable recipe for any problem

Here's the loop I'll run on every non-trivial problem for the rest of this book, and the rest of my career. Six steps. I'll abbreviate it **UEBOCT** (Understand, Examples, Brute force, Optimize, Code, Test) but I never skip steps even when it feels slow. Skipping is how I end up coding the wrong thing.

### Step 1 - UNDERSTAND the problem

Before touching the keyboard, I make sure I know *exactly* what's being asked. Restate it in my own words. Identify:
- **Inputs:** what am I given? What types? What ranges?
- **Outputs:** what exactly should I produce? What type/format?
- **Constraints & rules:** any special cases mentioned? Size limits?

If I can't restate the problem clearly, I'm not ready to solve it. Most "I'm stuck" is actually "I didn't fully understand."

### Step 2 - work concrete EXAMPLES (by hand)

I take a specific input and figure out the correct output *with pen and paper / in my head.* Then I deliberately pick **edge cases**, the weird inputs that break naive solutions:
- empty input (`[]`, `""`)
- one element
- duplicates
- negatives / zero
- the biggest/smallest allowed

Working examples by hand does two things: it confirms I understand, and it often *reveals the algorithm*, I notice what I'm naturally doing in my head, and that's the algorithm.

### Step 3 - BRUTE FORCE first

I find the simplest solution that *works*, even if it's slow or ugly. The obvious, dumb approach. **A working slow solution beats a broken clever one, always.** It also gives me something correct to compare against when I optimize, and in interviews it shows progress and a baseline. Never let "I want the elegant answer" stop me from writing the obvious one first.

### Step 4 - OPTIMIZE (only if needed)

Now I ask: is brute force good enough? Often *yes*, don't optimize what doesn't need it. If not, I look for the wasted work. Common moves: replace a slow lookup (scanning a list) with a fast one (a set/dict), avoid redoing work, trade a little memory for a lot of speed. This is where the data structures from later chapters earn their keep. (We'll quantify "fast vs slow" with Big-O in Part 2; for now, "scanning everything repeatedly = slow" is enough intuition.)

### Step 5 - CODE it

*Now* I write Python, translating my pseudocode. I keep it simple, name things well, build incrementally, get a piece working and run it before adding the next piece. I don't write 40 lines then run for the first time; I write 5, run, write 5 more.

### Step 6 - TEST it

I run my hand-worked examples from Step 2 through the code, especially the edge cases. If something's wrong, I debug systematically ([0.3.4](#034-debugging-systematically)). When all examples pass, including the nasty ones, I'm done. With `pytest` ([0.1.6](00.1-setup-and-tooling.md)) I can encode these checks permanently.

> 🧭 The framework feels heavy on tiny problems and you'll shortcut it there, fine. But the instant a problem makes me sweat, I slow *down* and run the full loop. Counterintuitive but true: on hard problems, going slower is faster, because flailing is the slowest thing of all.

## 0.3.3 How to read a problem statement

Problems (especially interview/practice problems) are written densely. I read them like a lawyer reads a contract:

1. **Read it twice.** Once for the gist, once for the details.
2. **Underline the inputs and outputs.** What goes in, what must come out, and their types.
3. **Hunt for hidden rules.** "distinct," "sorted," "non-empty," "may contain duplicates," "return the index, not the value," "case-insensitive", these tiny words change everything. Missing one is the #1 cause of "I solved the wrong problem."
4. **Note constraints.** "up to 1,000,000 items" is a hint that brute force may be too slow; "at most 10 items" says don't bother optimizing.
5. **Find the examples.** Trace the given example by hand. If your understanding produces a different output than the stated example, your understanding is wrong, fix it before coding.

> ⚠️ **Common mistakes when reading problems**
> - Assuming details not stated, or ignoring details that *are.* When unsure, ask (in an interview) or pick a reasonable assumption and *state it.*
> - Confusing "return the value" with "return the index." Reread the ask.
> - Forgetting the empty/single-element case exists. It almost always does.

## 0.3.4 Debugging systematically

Code rarely works first try; that's normal, not a sign of failure. Debugging is a *skill with a method*, not a vibe. When something's wrong:

1. **Read the error, bottom-up.** The last line of a traceback names the error and message; the lines above point to where ([0.2.11](00.2-programming-fundamentals.md#chapter-0211--reading-errors--basic-debugging)). Half of bugs are solved just by *actually reading* the error instead of recoiling from red text.
2. **Reproduce it reliably.** Find the smallest input that triggers the bug. A bug I can reproduce on demand is a bug I can kill.
3. **Form a hypothesis, then verify, don't guess-and-flail.** "I bet `count` is 0 here." Then *check* it with a `print` or a breakpoint. The cardinal sin is randomly changing code hoping it works. Every change should test a specific hypothesis.
4. **Bisect.** If a long pipeline is wrong, check the *middle.* Is the data correct halfway through? That halves the search space, is the bug in the first half or the second? Repeat. Ten steps of bisection narrows a 1000-line program to one line.
5. **Rubber-duck it.** Explain the code line-by-line, out loud, to a duck/wall/pet. Narrating forces me to confront the exact step where my assumption and reality diverge. Astonishingly effective.
6. **Print or breakpoint.** `print()` the values right before the failing spot to *see reality.* Or use the IDE debugger ([0.1.4](00.1-setup-and-tooling.md)) to pause and inspect. Either way: **don't guess what a value is, look at it.** Most bugs are "I assumed X; it was actually Y," and looking closes that gap instantly.
7. **Check your assumptions about the language.** Off-by-one (`range` stops early), `input()` returns a string, `int()` truncates, integer vs float division, modifying a list while looping. When baffled, suspect these classics.

> 🧭 **The debugging mantra:** *don't guess, verify.* Write it on a sticky note. Nearly every long debugging session I've ever had was me guessing repeatedly when one `print` would have shown me the truth in ten seconds.

## 0.3.5 Breaking a big project into tasks

The framework is for one problem. A *project* (the to-do app, a small game) is many problems. Same idea, one level up:

1. **Write the goal in one sentence.** "A terminal app to add, list, complete, and delete tasks."
2. **List the features.** add / list / complete / delete / save to file.
3. **Decompose each feature into tasks.** "save to file" → choose a format → write tasks to the file → read them back on startup → handle the file not existing yet.
4. **Order by dependency, build a thin slice first.** Get the *smallest end-to-end thing* working (add + list), run it, then add features one at a time, testing each. A working tiny app I grow beats a giant half-built one I can't run.
5. **Track it.** Even a checklist in a text file. Crossing things off sustains momentum, and momentum is most of finishing.

> 💼 **On the job.** This *is* the job: tickets/issues are decomposed tasks; pull requests are thin slices shipped one at a time. Practicing "break it down, ship a slice, repeat" on personal projects is direct rehearsal for professional work.

## 0.3.6 Reading documentation, asking good questions, searching effectively

I will not memorize every function, *nobody does.* The skill is finding answers fast.

**Reading docs.** Official docs (Python's at docs.python.org) and `help()` in the REPL are the source of truth. For a function, I look for: what it takes (parameters), what it returns, and an example. In the REPL, `help(str.split)` or `help(list)` prints the docs right there. Reading the *signature*, `str.split(sep=None, maxsplit=-1)`, tells me the arguments and their defaults at a glance.

**Searching effectively.**
- Search the **error message** nearly verbatim (strip out my specific variable names/paths). Someone has hit it before.
- Add the language: `python ...`. Include the library name if relevant.
- Describe the *goal*, not just the symptom: "python count occurrences of each item in list" beats "python list weird."
- Prefer official docs and reputable Q&A; sanity-check answers, adapt, don't blindly paste. Understand *why* a snippet works before trusting it.

**Asking good questions (to a person or forum).** A good question gets a fast answer; a vague one gets ignored. Include:
1. **What I'm trying to do** (the goal).
2. **What I tried** (the relevant code, minimal, not my whole file).
3. **What happened** (the exact error or wrong output).
4. **What I expected** instead.

This is the "minimal reproducible example." Producing one is itself debugging, *half the time I solve my own problem while writing the question down,* because shrinking it to the essentials reveals the bug. That's a feature, not a waste.

> 💼 **Interview angle.** "How would you find out?" is a legit interview answer when you don't know an API. "I'd check the docs for the exact method / I'd test it in a REPL" shows maturity. Nobody expects you to have memorized everything; they expect you to be resourceful.

### Problem A - FizzBuzz

> *Print the numbers 1 to 100. But for multiples of 3 print "Fizz", for multiples of 5 print "Buzz", and for multiples of both 3 and 5 print "FizzBuzz".*

**Step 1, Understand.** Input: nothing (or the range 1-100). Output: 100 lines. Rules: divisible by 3 → "Fizz", by 5 → "Buzz", by *both* → "FizzBuzz", otherwise the number. The phrase "by both" is the trap, that case must be handled *first* or it never triggers.

**Step 2, Examples.** Let me hand-trace a few: 1→`1`, 2→`2`, 3→`Fizz`, 4→`4`, 5→`Buzz`, 6→`Fizz`, ..., 15→`FizzBuzz` (3 and 5), ..., 30→`FizzBuzz`. Edge thinking: what makes 15 special? It's divisible by *both*. So "both" = "divisible by 15," or "divisible by 3 AND divisible by 5."

**Step 3, Brute force / pseudocode.** "Divisible by 3" is the modulo from [0.2.3](00.2-programming-fundamentals.md#chapter-023--operators-doing-things-to-values): `n % 3 == 0`.

```
for n from 1 to 100:
    if n divisible by 3 AND by 5: print "FizzBuzz"
    else if divisible by 3:       print "Fizz"
    else if divisible by 5:       print "Buzz"
    else:                          print n
```

My first instinct was to check `% 3` first, but then 15 would print "Fizz" and stop (only one branch of if/elif runs, [0.2.7](00.2-programming-fundamentals.md#chapter-027--conditionals-making-decisions)). The both-case **must** come first. That's the whole point of the problem; I caught it because I traced 15 by hand in Step 2. This is *why* we do examples.

**Step 4, Optimize.** Not needed, 100 iterations is instant. Resisting the urge to over-engineer is itself a skill.

**Step 5, Code.**

```python
def fizzbuzz(limit=100):
    for n in range(1, limit + 1):     # +1 so we include 'limit'
        if n % 3 == 0 and n % 5 == 0:
            print("FizzBuzz")
        elif n % 3 == 0:
            print("Fizz")
        elif n % 5 == 0:
            print("Buzz")
        else:
            print(n)

if __name__ == "__main__":
    fizzbuzz()
```

**Step 6, Test.** Run it; eyeball: line 3 is Fizz, 5 is Buzz, 15 is FizzBuzz, 1 is 1. All match my Step-2 trace. Done.

> 💼 FizzBuzz is a famous screening question precisely because it filters for "can handle the both-case ordering and modulo." If I nail the *reasoning* (both-first, why), I've shown the thing it tests.

### Problem B - Is a string a palindrome?

> *Given a string, return True if it reads the same forwards and backwards, ignoring case and spaces (e.g., "Race car" → True).*

**Step 1, Understand.** Input: a string. Output: a bool. Rules: ignore case ("Race" = "race") and ignore spaces. (Real versions sometimes ignore all punctuation; I'll note that as a possible extension and state my assumption: I'll strip spaces and lowercase.)

**Step 2, Examples.** `"racecar"`→True. `"Race car"`→ remove space, lowercase → `"racecar"`→True. `"hello"`→False. Edge cases: `""` (empty) → reads same both ways → True. `"a"` (single char) → True. `"ab"` → False. Good, empty and single are both palindromes.

**Step 3, Brute force.** Two ideas come to mind:
- *(a)* Clean the string, then compare it to its reverse. Reversing is `s[::-1]` from [0.2.5](00.2-programming-fundamentals.md#chapter-025--strings-working-with-text).
- *(b)* Two pointers: one at the start, one at the end, walk toward the middle, fail if any pair differs.

Approach (a) is dead simple and plenty fast. Pseudocode:

```
cleaned = lowercase the string with spaces removed
return cleaned equals cleaned reversed
```

**Step 4, Optimize.** Approach (a) creates a reversed copy (a little extra memory); the two-pointer approach (b) uses no extra string and can stop early on the first mismatch. For typical inputs (a) is totally fine and far clearer. I'll write (a), and show (b) too, because the two-pointer pattern is worth knowing for harder problems and interviews.

**Step 5, Code.**

```python
def is_palindrome(s):
    cleaned = s.lower().replace(" ", "")
    return cleaned == cleaned[::-1]
```

And the two-pointer version (same result, classic technique):

```python
def is_palindrome_two_pointer(s):
    cleaned = s.lower().replace(" ", "")
    left, right = 0, len(cleaned) - 1
    while left < right:
        if cleaned[left] != cleaned[right]:
            return False           # mismatch -> not a palindrome, stop early
        left += 1
        right -= 1
    return True                    # never mismatched -> palindrome
```

**Step 6, Test.**

```python
assert is_palindrome("racecar") is True
assert is_palindrome("Race car") is True
assert is_palindrome("hello") is False
assert is_palindrome("") is True          # edge: empty
assert is_palindrome("a") is True         # edge: single char
print("all passed")
```

I ran the exact edge cases I invented in Step 2. They pass. Note how Step 2's edge cases became Step 6's tests almost verbatim, that's not a coincidence, that's the framework working.

### Problem C - Two-sum (find two numbers that add to a target)

> *Given a list of numbers and a target, return the indices of the two numbers that add up to the target. Assume exactly one solution exists. E.g., `nums=[2, 7, 11, 15], target=9` → `[0, 1]` (because 2 + 7 = 9).*

**Step 1, Understand.** Input: a list of ints + a target int. Output: a list of *two indices* (not the values!, I underlined that). Exactly one answer exists, so I don't worry about "no solution" or "multiple."

**Step 2, Examples.** `[2,7,11,15]`, target 9: 2+7=9, at indices 0 and 1 → `[0,1]`. `[3,2,4]`, target 6: 2+4=6 → indices 1 and 2 → `[1,2]` (note 3+3 would be 6 but there's only one 3). `[3,3]`, target 6 → `[0,1]` (the two different 3s). That last one is a sneaky edge case, duplicates that are both needed.

**Step 3, Brute force.** The obvious approach: try every pair. For each `i`, for each `j` after it, check if `nums[i] + nums[j] == target`.

```
for i in range of indices:
    for j from i+1 to end:
        if nums[i] + nums[j] == target:
            return [i, j]
```

```python
def two_sum_brute(nums, target):
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):     # j starts after i: each pair once
            if nums[i] + nums[j] == target:
                return [i, j]
```

This *works.* It's correct. Done? For small lists, yes! Don't optimize prematurely.

**Step 4, Optimize.** But suppose the list is huge (the constraint says a million items). The double loop checks ~every pair, that's slow (it's O(n²); Part 2 makes this precise). Where's the wasted work? For each number `x`, I'm scanning the whole list to find `target - x`. **Pattern recognition:** "repeatedly asking 'is this value present, and where?'" screams *dictionary* ([0.2.9](00.2-programming-fundamentals.md#chapter-029--lists-tuples-dicts-sets-the-everyday-containers)), instant lookups.

New idea: walk the list once. For each number, the partner I need is `target - number`. If I've *already seen* that partner, I'm done. So I keep a dict mapping `value → index` as I go.

```
seen = empty dict {value: index}
for index, number in enumerate(nums):
    need = target - number
    if need is already in seen:
        return [seen[need], index]
    record seen[number] = index
```

Trace `[3,3], target 6`: index 0, number 3, need 3, not seen yet → record `{3:0}`. Index 1, number 3, need 3, *is* in seen (at 0) → return `[0,1]`. The duplicate edge case works because I check *before* recording the current one.

**Step 5, Code.**

```python
def two_sum(nums, target):
    seen = {}                              # value -> index
    for index, number in enumerate(nums):
        need = target - number
        if need in seen:
            return [seen[need], index]
        seen[number] = index
```

**Step 6, Test.**

```python
assert two_sum([2, 7, 11, 15], 9) == [0, 1]
assert two_sum([3, 2, 4], 6) == [1, 2]
assert two_sum([3, 3], 6) == [0, 1]        # the duplicate edge case
print("all passed")
```

All three pass, including the tricky duplicate. Notice the *shape* of the optimization, "replace repeated scanning with a dict/set lookup", is one of the most common moves in all of programming. I'll see it constantly. That's pattern recognition compounding.

> 💼 **Interview angle.** Two-sum is *the* canonical first interview question. The expected arc is exactly this: state brute force, recognize the wasted re-scanning, reach for a hash map (dict), explain the one-pass trick. Walking that arc out loud is a near-guaranteed pass. Memorizing the final code is *not* the point, the *move* is.

### Problem D - Count word frequency

> *Given a sentence, return a dict mapping each word to how many times it appears, lowercased, ignoring punctuation. E.g., "The cat sat. The cat ran!" → {"the": 2, "cat": 2, "sat": 1, "ran": 1}.*

**Step 1, Understand.** Input: a string. Output: a dict of word → count. Rules: lowercase ("The" and "the" are the same word), strip punctuation (so "ran!" counts as "ran"). Words are separated by whitespace.

**Step 2, Examples.** `"the the the"` → `{"the": 3}`. `""` → `{}` (empty). `"Hi, hi!"` → after lowering and stripping punctuation → both "hi" → `{"hi": 2}`. So I must handle punctuation attached to words.

**Step 3, Brute force / pseudocode.** This is the **counting pattern** from [0.2.9](00.2-programming-fundamentals.md#chapter-029--lists-tuples-dicts-sets-the-everyday-containers). The shape: for each item, add 1 to its tally in a dict.

```
counts = empty dict
lowercase the whole sentence
split it into words on whitespace
for each word:
    strip surrounding punctuation
    skip if the word is now empty
    counts[word] = counts.get(word, 0) + 1   # the safe-increment idiom
return counts
```

The `counts.get(word, 0) + 1` idiom is key: `.get(word, 0)` returns the current count or `0` if the word is new (avoiding `KeyError`, [0.2.11](00.2-programming-fundamentals.md#chapter-0211--reading-errors--basic-debugging)), then `+ 1`. This "get-or-default then increment" pattern shows up *everywhere* you tally things.

**Step 4, Optimize.** Not needed (one pass over the words is already efficient). I'll just note that Python's standard library has `collections.Counter` that does exactly this, but I'm building it by hand first to *understand* it, true to the no-black-boxes rule. Knowing the tool exists *and* how it works beats knowing only one.

**Step 5, Code.** For stripping punctuation I'll use `str.strip()` with a set of punctuation chars (it removes them from both ends of each word):

```python
import string   # gives string.punctuation = '!"#$%&...'

def word_count(text):
    counts = {}
    for raw_word in text.lower().split():           # lowercase, split on whitespace
        word = raw_word.strip(string.punctuation)   # trim punctuation from the ends
        if not word:                                # skip if it became empty
            continue
        counts[word] = counts.get(word, 0) + 1
    return counts
```

**Step 6, Test.**

```python
assert word_count("The cat sat. The cat ran!") == {"the": 2, "cat": 2, "sat": 1, "ran": 1}
assert word_count("") == {}                         # edge: empty
assert word_count("Hi, hi!") == {"hi": 2}           # edge: punctuation + case
print("all passed")
```

All pass. And look, this is essentially the `word_count` micro-project promised back in [0.1.6](00.1-setup-and-tooling.md). I just solved it the disciplined way: understand, examples (which became my tests), pattern-recognize it as counting, code the idiom, verify the edges.

## ✏️ Exercises

Solve each using the **full framework**. Actually write the Understand/Examples/Brute-force steps in words *before* coding, that's the part being practiced. Solutions follow.

1. **Sum of digits.** Given a non-negative integer `n`, return the sum of its digits. `1234` → `10`. (Hint: `%` and `//`, or convert to a string.)
2. **Count vowels.** Given a string, return how many vowels (a, e, i, o, u, case-insensitive) it contains. `"Hello"` → `2`.
3. **Find duplicates.** Given a list, return a list of the values that appear more than once (each once, any order). `[1,2,2,3,3,3,4]` → `[2, 3]`. (Hint: count, then filter, or use a set of "seen.")
4. **Reverse words.** Given a sentence, return it with the *word order* reversed but each word intact. `"the quick fox"` → `"fox quick the"`.

### Solutions

**1, Sum of digits.**
*Understand:* input non-negative int, output int sum of digits. *Examples:* `0`→0, `5`→5, `1234`→10. Edge: `0` should give 0. *Brute force:* peel digits with `% 10` and `// 10`, OR just iterate the string form.
```python
def digit_sum(n):
    total = 0
    for ch in str(n):           # convert to string, loop over characters
        total += int(ch)        # each char back to an int digit
    return total
# math version, no string conversion:
def digit_sum_math(n):
    total = 0
    while n > 0:
        total += n % 10         # last digit
        n //= 10                # drop the last digit
    return total
assert digit_sum(1234) == 10
assert digit_sum(0) == 0
```
The string version is clearer; the math version shows the `% 10 / // 10` digit-peeling trick worth knowing.

**2, Count vowels.**
*Examples:* `""`→0, `"xyz"`→0, `"AEIOU"`→5 (case-insensitive). *Pattern:* count items matching a condition.
```python
def count_vowels(s):
    vowels = set("aeiou")          # set -> fast membership check
    count = 0
    for ch in s.lower():
        if ch in vowels:
            count += 1
    return count
assert count_vowels("Hello") == 2
assert count_vowels("AEIOU") == 5
assert count_vowels("") == 0
```

**3, Find duplicates.**
*Examples:* `[]`→`[]`, `[1,2,3]`→`[]`, `[1,1]`→`[1]`. *Brute force:* count each, keep those with count > 1, reuse the counting pattern.
```python
def find_duplicates(items):
    counts = {}
    for x in items:
        counts[x] = counts.get(x, 0) + 1
    return [x for x, c in counts.items() if c > 1]   # filter to count>1
assert sorted(find_duplicates([1,2,2,3,3,3,4])) == [2, 3]
assert find_duplicates([1,2,3]) == []
```
(The `[x for ... if ...]` is a *list comprehension*, a compact filter; I'll meet these properly soon. Mentally it reads "give me each `x` where its count exceeds 1.")

**4, Reverse words.**
*Watch the trap:* reverse *word order*, not the characters. *Examples:* `"a b c"`→`"c b a"`, single word→itself, `""`→`""`. *Plan:* split into a list of words, reverse the list, join back with spaces.
```python
def reverse_words(sentence):
    words = sentence.split()        # list of words
    words.reverse()                 # reverse the LIST in place
    return " ".join(words)          # glue back with spaces
# or in one line: return " ".join(sentence.split()[::-1])
assert reverse_words("the quick fox") == "fox quick the"
assert reverse_words("hello") == "hello"
assert reverse_words("") == ""
```
