## Start here (the gentle on-ramp)

Picture a tiny office with one very fast but very literal clerk.

The clerk can only do **one small thing at a time**, but does each in a blink: "read what's in box #3," "add the numbers in your two hands," "write this number into box #7," "if your hands are equal, skip ahead to instruction 12." That's it. The clerk has no creativity, no memory of yesterday, just a handful of scratch slots (a few numbers held in hand) and a long shelf of numbered boxes (memory).

Sitting on the desk is a **stack of index cards**, each with one tiny instruction. The clerk's entire life is a loop:

1. **Fetch**, grab the next index card off the stack (the card you're "up to" is tracked by a little counter called the **program counter**).
2. **Decode**, read what the card says ("ADD", "LOAD box 3", "JUMP to card 12").
3. **Execute**, do exactly that one thing, then bump the counter and grab the next card.

Fetch, decode, execute. Over and over, **billions of times a second**. That loop *is* a CPU. There's a profound and slightly unsettling idea hiding here: the index cards (the program) live on the *same shelf of numbered boxes* as the data the program works on. Instructions and data are the same kind of stuff, numbers in memory. That's the **von Neumann model**, and it's why a program can be loaded, copied, and even (in principle) modify itself: code *is* data.

Everything in this chapter is about making that clerk faster *without changing what the cards mean*:
- **Pipelining**, instead of fully finishing one card before touching the next, overlap them like an assembly line.
- **Caches**, keep the boxes you use most on the desk (instant) instead of the far shelf (a long walk).
- **Parallelism**, hire more clerks (cores), or give one clerk wider hands (SIMD).

And one honest equation keeps everyone honest: a program's runtime is **how many instructions × how many clock cycles each takes × how long a cycle is**. Speed up *any* factor and you win; this is the iron law, and we'll lean on it constantly.

## The von Neumann model

Almost every general-purpose computer you'll ever touch is a **von Neumann machine**. The defining feature: a *single* memory holds both the program's instructions and its data, connected to a processor by a bus.

```
   THE VON NEUMANN MODEL

   ┌───────────────────────────────────────────┐
   │                  CPU                        │
   │   ┌──────────┐        ┌─────────────────┐  │
   │   │ CONTROL  │        │  DATAPATH       │  │
   │   │  UNIT    │◄──────►│  - registers     │  │
   │   │ (decodes │        │  - ALU           │  │
   │   │  instrs, │        │  - program counter│ │
   │   │  sets    │        └─────────────────┘  │
   │   │  knobs)  │                              │
   │   └──────────┘                              │
   └───────────────┬─────────────────────────────┘
                   │  BUS (address + data + control)
                   ▼
   ┌───────────────────────────────────────────┐
   │  MEMORY  (one address space)                │
   │  ...holds INSTRUCTIONS *and* DATA together  │
   │  [ instr ][ instr ][ instr ][ data ][ data ]│
   └───────────────────────────────────────────┘
            ▲                              ▲
            │                              │
        INPUT (keyboard, disk)        OUTPUT (screen, disk)
```

The five classical parts: **control unit**, **arithmetic/logic unit (ALU)**, **memory**, **input**, **output**. The control unit + ALU + registers together are the CPU; the bus carries addresses, data, and control signals between CPU and memory.

**The von Neumann bottleneck.** Because instructions *and* data share one path to memory, the CPU can stall waiting on that single channel, you can't fetch the next instruction and load a data word at the *exact* same instant on a strict von Neumann bus. The common fix is the **Harvard-style split** used *inside* real CPUs: separate **instruction cache** and **data cache** (we'll meet these below), so fetches and loads don't fight. So real chips are von Neumann at the system level (one main memory) but Harvard at the cache level (split I-cache/D-cache). That's not a contradiction; it's the bottleneck being engineered around.

```
💡 Why "code is data" matters: compilers, JITs, and interpreters (24.2) all
EXIST because programs are just numbers in memory you can read, transform, and
write. A JIT literally writes new machine-code bytes into memory and then jumps
into them. That's only possible in a world where instructions live in the same
memory as data - the von Neumann world.
```

## The ISA - the hardware/software contract

We named this in 17.3; let's make it precise, because it's the most important boundary in the whole stack.

An **Instruction Set Architecture (ISA)** is the *documented promise* a CPU makes to software. It specifies:

- The **instructions** that exist (`add`, `load`, `store`, `jump`, `compare`, …) and their exact bit encodings.
- The **registers** (how many, how wide, what they're named).
- The **memory model** (addressing, byte order/endianness, alignment rules).
- How **interrupts/exceptions** and privileged operations work.

Crucially, the ISA says *what* happens, not *how*. Two chips implementing the same ISA can have wildly different internals (the **microarchitecture**), different pipeline depths, cache sizes, out-of-order engines, yet run the *same* binaries. That separation is why your compiled program runs on a budget laptop and a server CPU alike, and why Apple could move Macs from x86 to ARM and most software just recompiled cleanly (17.3).

```
   ISA  vs  MICROARCHITECTURE

   ISA            = the contract: "add r1, r2, r3 means r1 = r2 + r3"
                    (visible to software; stable for decades)
   microarch      = the implementation: pipeline depth, caches, OoO,
                    branch predictor (invisible to software; changes
                    every chip generation)
```

### RISC vs CISC

Two historical philosophies for *designing* an ISA:

| | **CISC** (Complex Instruction Set) | **RISC** (Reduced Instruction Set) |
|---|---|---|
| Instructions | many, some very complex | few, simple, uniform |
| Encoding | variable length (1-15 bytes on x86) | fixed length (usually 4 bytes) |
| Memory access | many instructions can touch memory | only `load`/`store` touch memory (load-store architecture) |
| Per-instruction work | one instruction may do a lot | each does a little; you compose them |
| Examples | **x86 / x86-64** | **ARM, RISC-V, MIPS** |
| Philosophy | make the hardware do more per instruction | make instructions simple so the hardware can be fast & pipelined |

The old debate ("which is better?") has largely dissolved. Modern x86 chips are CISC *on the outside* (for compatibility) but internally **decode each complex instruction into small RISC-like "micro-ops"** and run those on a fundamentally RISC-style pipelined core. So today's reality: a RISC-y engine wearing a CISC costume for backward compatibility. RISC ideas won the *internals*; CISC won the *installed base*.

### x86 vs ARM vs RISC-V

- **x86-64**, the CISC giant from Intel/AMD. Dominates desktops, laptops, and servers. Enormous, decades-deep instruction set (great compatibility, complex decoders, higher power per the same work).
- **ARM**, the RISC workhorse. Dominates phones, tablets, embedded, and increasingly laptops/servers (Apple Silicon, AWS Graviton). Licensed IP: companies buy the ISA and design their own cores. Excellent performance-per-watt.
- **RISC-V**, the *open, royalty-free* RISC ISA. Anyone can implement it without a license fee. Rapidly growing in academia, embedded, and increasingly real silicon. It's the "Linux of ISAs", open contract, many implementations.

```
💼 On the job / interview angle: you rarely need to recite encodings, but
"what's the difference between an ISA and a microarchitecture?" and "why did
RISC ideas end up inside CISC chips?" are real systems-interview questions. The
one-liner: the ISA is the *stable software-visible contract*; the
microarchitecture is the *ever-changing implementation*. Conflating them is the
classic mistake.
```

## The fetch-decode-execute cycle

This is the heartbeat of the clerk. Let's name the registers involved, because we'll build them in code in a moment:

- **PC (Program Counter)**, address of the next instruction to fetch.
- **IR (Instruction Register)**, holds the instruction currently being decoded.
- **General-purpose registers**, the clerk's scratch slots (e.g., `R0..R7`).
- **ALU**, does the arithmetic/logic (built from the adder in 01.2).
- **Flags / status**, bits like "the last result was zero" used by branches.

```
   THE CYCLE (one instruction):

   ┌──────────┐   ┌──────────┐   ┌──────────────┐
   │  FETCH   │──►│  DECODE  │──►│   EXECUTE     │──┐
   │ IR ← M[PC]│   │ figure   │   │ ALU does it / │  │
   │ PC ← PC+1 │   │ out op + │   │ access memory/│  │
   │          │   │ operands │   │ write reg /   │  │
   └──────────┘   └──────────┘   │ change PC     │  │
        ▲                         └──────────────┘  │
        └───────────────────────────────────────────┘
                       repeat forever
```

Some textbooks split it finer (fetch, decode, **operand fetch**, execute, **memory access**, **write-back**), that 5-stage breakdown will matter enormously when we pipeline. For now, the three-beat version is the mental model: **get the instruction, understand it, do it, advance.**

## Build it - a single-cycle CPU simulator

Time to make the clerk real. We'll build a tiny CPU with 8 registers, a small RAM, and a handful of instructions. "Single-cycle" means each instruction completes fully before the next begins, exactly the clerk doing one index card at a time. This is the simplest correct CPU, and it's a faithful Python mirror of the datapath we sketched in 17.3.

Our toy ISA (a RISC-flavored, load-store design):

```
   Instr           Meaning
   ─────           ───────
   LOADI rd, imm   rd = imm                (load immediate constant)
   ADD   rd, ra, rb  rd = ra + rb
   SUB   rd, ra, rb  rd = ra - rb
   MUL   rd, ra, rb  rd = ra * rb
   LOAD  rd, addr  rd = MEM[addr]          (load from data memory)
   STORE rs, addr  MEM[addr] = rs          (store to data memory)
   JZ    ra, target  if ra == 0: PC = target   (jump if zero)
   JMP   target    PC = target
   HALT            stop
```

```python
class CPU:
    """A single-cycle CPU simulator. Each call to step() executes ONE
    instruction completely: fetch, decode, execute. We count 'cycles' so
    we can reason about performance later (the iron law)."""

    def __init__(self, program, data_mem_size=64):
        self.program = program          # list of (op, *operands) tuples = instruction memory
        self.regs = [0] * 8             # R0..R7  (the clerk's scratch slots)
        self.mem = [0] * data_mem_size  # data memory (the numbered boxes)
        self.pc = 0                     # PROGRAM COUNTER: index of next instruction
        self.cycles = 0                 # we charge cycles per instruction (CPI study below)
        self.halted = False

    def step(self):
        # ---- FETCH ----
        instr = self.program[self.pc]   # IR <- M[PC]
        op, *args = instr
        next_pc = self.pc + 1           # default: advance to next instruction

        # ---- DECODE + EXECUTE ----
        if op == "LOADI":
            rd, imm = args
            self.regs[rd] = imm
        elif op == "ADD":
            rd, ra, rb = args
            self.regs[rd] = self.regs[ra] + self.regs[rb]
        elif op == "SUB":
            rd, ra, rb = args
            self.regs[rd] = self.regs[ra] - self.regs[rb]
        elif op == "MUL":
            rd, ra, rb = args
            self.regs[rd] = self.regs[ra] * self.regs[rb]
        elif op == "LOAD":
            rd, addr = args
            self.regs[rd] = self.mem[addr]
        elif op == "STORE":
            rs, addr = args
            self.mem[addr] = self.regs[rs]
        elif op == "JZ":
            ra, target = args
            if self.regs[ra] == 0:
                next_pc = target        # branch taken: PC changes
        elif op == "JMP":
            (target,) = args
            next_pc = target
        elif op == "HALT":
            self.halted = True
        else:
            raise ValueError(f"unknown op {op}")

        self.pc = next_pc
        self.cycles += 1                # single-cycle: 1 cycle per instruction
        # R0 is hardwired to 0 in many RISC ISAs; we'll keep it free here for clarity.

    def run(self, max_steps=10_000):
        steps = 0
        while not self.halted and steps < max_steps:
            self.step()
            steps += 1
        return self
```

Let's run a program: compute `(3 + 4) * 5` and store it at memory address 0.

```python
program = [
    ("LOADI", 1, 3),     # R1 = 3
    ("LOADI", 2, 4),     # R2 = 4
    ("ADD",   3, 1, 2),  # R3 = R1 + R2  = 7
    ("LOADI", 4, 5),     # R4 = 5
    ("MUL",   5, 3, 4),  # R5 = R3 * R4  = 35
    ("STORE", 5, 0),     # MEM[0] = R5
    ("HALT",),
]

cpu = CPU(program).run()
print("R5  =", cpu.regs[5])     # -> 35
print("MEM[0] =", cpu.mem[0])   # -> 35
print("cycles =", cpu.cycles)   # -> 7  (7 instructions, 1 cycle each)
```

```
R5  = 35
MEM[0] = 35
cycles = 7
```

**That's a CPU.** It fetches index cards, decodes them, executes, advances the PC, and on `JZ`/`JMP` it changes the PC to loop or branch. Everything a real CPU does is an elaboration of this loop, the rest of the chapter is about making the *same instructions* run *faster*.

```
⚠️ Common mistake: thinking the PC "points at" instructions in some magic way.
It's just an integer index/address. Branches and loops are nothing more than
writing a new value into that integer. Once that clicks, control flow at the
hardware level stops being mysterious - `if`, `while`, and function calls all
bottom out in "set the PC to a different number."
```

## Pipelining - the assembly line

Our single-cycle CPU wastes the hardware. While the ALU is adding, the instruction-fetch logic sits idle; while we fetch, the ALU naps. **Pipelining** fixes this by overlapping instructions like an assembly line.

### The laundry analogy

You have 4 loads of laundry. Each load goes through 3 stages: **Wash** (30 min) → **Dry** (30 min) → **Fold** (30 min).

**Sequential (no pipeline):** finish load 1 entirely (90 min) before starting load 2. Four loads = **360 min**.

**Pipelined:** the moment load 1 leaves the washer, start load 2 washing while load 1 dries.

```
   time →   30   60   90   120  150
   Load1   Wash  Dry  Fold
   Load2         Wash Dry  Fold
   Load3              Wash Dry  Fold
   Load4                   Wash Dry  Fold
```

Now four loads finish in **180 min** (6 stages × 30) instead of 360. You didn't make any single load faster, wash still takes 30 min, but **throughput** doubled because the machines stay busy.

### Classic 5-stage CPU pipeline

Real CPUs split instruction processing into stages, each handled by its own hardware, separated by pipeline registers (flip-flops from 17.3):

```
   IF  →  ID  →  EX  →  MEM  →  WB
   Instr  Instr  Exec   Memory  Write
   Fetch  Decode (ALU)  access  Back
                                 (reg)
```

```
   cycle:   1    2    3    4    5    6    7    8    9
   I1:      IF   ID   EX   MEM  WB
   I2:           IF   ID   EX   MEM  WB
   I3:                IF   ID   EX   MEM  WB
   I4:                     IF   ID   EX   MEM  WB
   I5:                          IF   ID   EX   MEM  WB
```

After the pipeline "fills," one instruction *completes every cycle*. The clock period now only needs to cover *one stage*, not the whole instruction, so you can clock much faster.

### The speedup math (worked numbers)

Say each *stage* takes 1 ns.

- **Single-cycle**, where one instruction does all 5 stages' work in one long cycle: cycle time = 5 ns. For `N=1000` instructions: `1000 × 5 = 5000 ns`.
- **Pipelined**, cycle time = 1 ns (one stage). Time = `(N + stages − 1) × cycle = (1000 + 4) × 1 = 1004 ns`.

That's a **~4.98×** speedup, approaching the ideal `stages = 5×`. The `stages − 1 = 4` extra cycles are the **fill** cost (latency to get the first result); they're negligible when `N` is large. The general formula:

```
   pipelined cycles = N + (stages - 1)
   speedup → number_of_stages   (as N → ∞, if perfectly balanced)
```

```python
def pipeline_time(N, stages, stage_ns=1.0):
    single_cycle = N * stages * stage_ns         # one long cycle per instruction
    pipelined    = (N + stages - 1) * stage_ns   # one stage per cycle, after fill
    return single_cycle, pipelined

for N in (10, 100, 1000, 100_000):
    sc, pp = pipeline_time(N, stages=5)
    print(f"N={N:>6}: single={sc:>9.0f}ns  pipelined={pp:>9.0f}ns  speedup={sc/pp:5.2f}x")
```

```
N=    10: single=       50ns  pipelined=       14ns  speedup= 3.57x
N=   100: single=      500ns  pipelined=      104ns  speedup= 4.81x
N=  1000: single=     5000ns  pipelined=     1004ns  speedup= 4.98x
N=100000: single=   500000ns  pipelined=   100004ns  speedup= 5.00x
```

The fill cost matters for short bursts and *vanishes* for long runs, which is why pipelines love tight loops over big data.

### Hazards - why the ideal isn't free

The clean picture above assumes every instruction sails through independently. Reality has **hazards**, situations that force the pipeline to wait.

**1. Structural hazard**, two instructions want the *same hardware unit* in the same cycle (e.g., both need memory access). Fix: duplicate the resource (split I-cache/D-cache so IF and MEM don't collide) or schedule around it.

**2. Data hazard**, an instruction needs a result that an earlier instruction *hasn't finished computing yet*.

```
   ADD R1, R2, R3   ; R1 is produced in WB (cycle 5)
   SUB R4, R1, R5   ; but SUB needs R1 in EX (cycle 4) - too early!
```

Fixes:
- **Forwarding (bypassing):** wire the ALU's result *directly* to the next instruction's input, before it's even written back to the register file. Solves most data hazards with zero stalls.
- **Stalling (bubbles):** if forwarding can't help (e.g., a `LOAD` result isn't ready until MEM), insert a no-op "bubble" cycle to wait. Costs a cycle.

**3. Control hazard (branch hazard)**, when you hit a branch, you don't *know* which instruction comes next until the branch resolves (a few stages in). Do you fetch the fall-through or the target? Guess wrong and you've fetched instructions you must throw away (a **pipeline flush**).

Fixes:
- **Branch prediction:** guess the likely outcome and fetch speculatively. Modern predictors are *uncannily* good (often >95% accurate) using history tables. Right guess → no penalty. Wrong guess → flush the wrongly-fetched instructions (a **misprediction penalty**, often 10-20 cycles on deep pipelines).
- **Stall** until the branch resolves (simple, slow).

```
⚠️ Common mistake (and a famous Stack Overflow lesson): "why is processing a
SORTED array faster than an unsorted one with the same code?" Answer: branch
prediction. A predictable branch (e.g., `if (x > 128)` on sorted data) is
guessed right almost always → no flushes. On random data the predictor guesses
wrong half the time → constant flushes → much slower. Same instructions, same
CPI on paper, very different real speed. Pipelines make data *patterns* matter.
```

### Hazards + the iron law

Hazards raise the **average cycles per instruction (CPI)** above the ideal 1.0. If 20% of instructions are branches and 5% of *those* mispredict at a 15-cycle penalty, and 10% are loads that each cost a 1-cycle stall, your effective CPI creeps up, and the iron law (below) turns that directly into runtime. This is *why* architects obsess over predictors and forwarding: every avoided stall is real wall-clock time.

## The memory hierarchy at the architecture level

You felt this in 05.1 with a timing experiment; here's the architecture view of *why* it exists and *how* caches work mechanically.

The cruel fact: fast memory is expensive and small; cheap memory is huge and slow. You can't have one big fast memory, so you build a **pyramid** and let *locality* make it feel fast.

```
   THE MEMORY HIERARCHY (typical, rough numbers)

   level        size        latency        built from (17.3)
   ─────        ────        ───────        ─────────────────
   registers    ~kilobyte   0 cycles       flip-flops
   L1 cache     ~32-64 KB   ~3-4 cycles    SRAM (6T cell)
   L2 cache     ~256KB-1MB  ~10-15 cycles  SRAM
   L3 cache     ~8-32 MB    ~40-60 cycles  SRAM (shared across cores)
   RAM          ~8-64 GB    ~200-300 cycles DRAM (1T1C, leaky → refresh)
   SSD/disk     ~TB         ~100k+ cycles  flash / spinning rust
```

Each step down is roughly 10× bigger and 10× slower. The ~100× cliff between L1 and RAM is the SRAM-vs-DRAM cell tradeoff from 17.3, a stable latch vs. a leaky capacitor you must wait on.

### Why it works: locality

Programs don't touch memory randomly. They exhibit:
- **Temporal locality**, if you used an address, you'll likely use it again soon (loop variables, the top of the stack).
- **Spatial locality**, if you used an address, you'll likely use *nearby* ones soon (arrays, struct fields, sequential code).

The hierarchy exploits both: keep recently-used data close (temporal), and **fetch in chunks** so neighbors come along for free (spatial).

### Cache lines

The cache doesn't store individual bytes, it stores **cache lines** (blocks), typically **64 bytes**. When you miss and fetch address `A`, the cache pulls the whole 64-byte line containing `A`. So the *next* sequential access is already cached, that's spatial locality monetized.

```
💡 This is why row-major array traversal beats column-major (16.4), and why an
array beats a linked list for iteration (02.2): contiguous data shares cache
lines; scattered data wastes most of every 64-byte fetch. The hierarchy rewards
data that lives close together.
```

### Cache mapping: where can a line live?

When a line comes in, *where* in the cache does it go? Three schemes:

- **Direct-mapped:** each memory address maps to exactly *one* slot (`slot = (address / line_size) mod num_slots`). Simple and fast, but two hot addresses that map to the same slot keep evicting each other (**conflict misses**).
- **Fully associative:** a line can go *anywhere*. No conflict misses, but checking "is it here?" means searching every slot, expensive hardware.
- **Set-associative:** the practical middle. The cache is divided into **sets**; an address maps to one set, and within a set a line can go in any of `N` **ways** (an "N-way set-associative" cache). 8-way is common. Best of both, cheap-ish lookup, few conflicts.

### Hits, misses, and write policies

- **Hit**, the data is in the cache. Fast.
- **Miss**, not there; fetch from the next level down (slow), and evict something to make room (eviction policy, often approximate-LRU).
- **Write-through**, writes go to cache *and* memory immediately. Simple, but lots of memory traffic.
- **Write-back**, writes go only to cache; the line is marked **dirty** and written to memory only when evicted. Less traffic, more complex (must track dirty bits). Most caches are write-back.

The headline metric is the **hit rate**, and a small change in it dominates performance because of that 100× cliff:

```
   average access time = hit_rate × hit_cost + miss_rate × miss_cost
```

## Build it - a cache simulator

Let's *measure* hit rate instead of hand-waving it. We'll build a **direct-mapped** cache and feed it access patterns.

```python
class DirectMappedCache:
    """Direct-mapped cache simulator. Tracks which 64-byte line lives in
    each slot, and counts hits vs misses. line_size & num_slots are powers
    of two so we can use cheap bit math, exactly like real hardware."""

    def __init__(self, num_slots=16, line_size=64):
        self.num_slots = num_slots
        self.line_size = line_size
        self.tags = [None] * num_slots   # which memory line currently sits in each slot
        self.hits = 0
        self.misses = 0

    def access(self, address):
        line = address // self.line_size        # which 64-byte block
        slot = line % self.num_slots            # direct-mapped: one possible slot
        if self.tags[slot] == line:
            self.hits += 1                      # HIT: the right line is already here
        else:
            self.misses += 1                    # MISS: fetch it, evict whatever was there
            self.tags[slot] = line

    def hit_rate(self):
        total = self.hits + self.misses
        return self.hits / total if total else 0.0
```

**Experiment 1: sequential array scan** (great spatial locality):

```python
cache = DirectMappedCache(num_slots=16, line_size=64)
# walk a 4 KB array, 4 bytes per int, one int at a time
for i in range(1024):
    cache.access(i * 4)
print(f"sequential: {cache.hits} hits, {cache.misses} misses, "
      f"hit rate {cache.hit_rate():.1%}")
```

```
sequential: 960 hits, 64 misses, hit rate 93.8%
```

Only the *first* access to each 64-byte line misses (64 bytes / 4 bytes = 16 ints per line, so 1 miss then 15 hits). 1/16 = 6.25% miss → **93.8% hit rate**. The cache line did the work: one slow fetch buys 15 fast accesses.

**Experiment 2: large stride** (defeats spatial locality):

```python
cache = DirectMappedCache(num_slots=16, line_size=64)
# touch one int every 64 ints = every 256 bytes → a new line every time
for i in range(1024):
    cache.access(i * 256)
print(f"strided: {cache.hit_rate():.1%}")
```

```
strided: 0.0%
```

Every access lands on a fresh line *and* (because the stride aligns with the slot count) keeps evicting, pathological. Same loop count, **0% hit rate**. This is the cache-thrashing nightmare: technically-correct code that touches memory in a cache-hostile pattern.

**Experiment 3: a small hot working set** (temporal locality):

```python
cache = DirectMappedCache(num_slots=16, line_size=64)
import random
hot = list(range(8))         # 8 addresses we hammer repeatedly
for _ in range(10_000):
    cache.access(random.choice(hot) * 64)
print(f"hot working set: {cache.hit_rate():.1%}")
```

```
hot working set: 99.9%
```

A working set that *fits in cache* stays hot → near-100% hits. **This is the entire game of performance-critical code: keep your hot working set small enough to live in cache.** You just simulated, end to end, why "make it fit in L1" is the single most powerful low-level optimization.

```
⚠️ Common mistake: optimizing instruction count while ignoring memory access
patterns. A loop with FEWER instructions but a cache-hostile stride can be far
slower than a loop with MORE instructions and good locality. On modern hardware,
memory behavior often dominates. Measure, don't guess.
```

## Going wider: superscalar, out-of-order, SIMD, multicore

Pipelining gets you ~one instruction per cycle. To go *beyond* that, architects exploit more parallelism:

- **Superscalar**, issue *multiple* instructions per cycle by having multiple execution units (e.g., two ALUs + a load unit + a branch unit). CPI can drop *below* 1 (so we often quote **IPC**, instructions per cycle, instead). A 4-wide superscalar can ideally retire 4 instructions/cycle.
- **Out-of-order (OoO) execution**, instead of stalling on a slow `LOAD`, execute *later* independent instructions while waiting, then commit results in program order. This hides memory latency by finding other work to do. It's why a cache miss doesn't always freeze the whole CPU.
- **SIMD (Single Instruction, Multiple Data)**, one instruction operates on a *vector* of values at once (e.g., add eight 32-bit numbers in one op). This is the "wider hands" upgrade, x86's SSE/AVX, ARM's NEON. NumPy's speed (16.2) leans heavily on SIMD under the hood.
- **Multicore**, multiple full CPUs (cores) on one chip (17.3). Each runs its own instruction stream; software must be written to use them (threads, 05.2). This is the post-Dennard answer: more cores, not faster ones.
- **SMT / Hyper-Threading**, one core pretends to be two, interleaving two instruction streams to keep its units busy when one stream stalls.

```
   THE PARALLELISM LADDER

   1 instr/cycle  →  pipelining (overlap stages)
   N instr/cycle  →  superscalar (multiple units)
   reorder        →  out-of-order (hide latency)
   N data/instr   →  SIMD (vector ops)
   N cores        →  multicore (separate streams)
```

These are layered, a modern core is a *superscalar, out-of-order, SIMD-capable* pipeline, and a chip has *several* of those cores. The complexity is staggering, but it all serves one goal: keep the silicon busy.

## Performance equations - the iron law

Here's the equation that keeps everyone honest. Strip away the hype and a program's CPU time is:

```
   ┌─────────────────────────────────────────────────────────┐
   │  THE IRON LAW OF PERFORMANCE                              │
   │                                                          │
   │  CPU time = (# instructions) × (CPI) × (cycle time)      │
   │                                                          │
   │           = instructions × cycles/instr × seconds/cycle  │
   └─────────────────────────────────────────────────────────┘
```

- **# instructions**, how many instructions the program runs. Lowered by better compilers, better algorithms, richer instructions (CISC's pitch).
- **CPI (cycles per instruction)**, average cycles each takes. Lowered by pipelining, superscalar, caches (fewer stalls), good branch prediction.
- **cycle time**, seconds per clock tick = 1 / clock frequency. Lowered by faster transistors, shorter critical paths (pipelining helps here too).

**The trap:** you can't optimize one factor in isolation. Classic example, switching from CISC to RISC *increases* instruction count (more, simpler instructions) but *decreases* CPI and cycle time (simpler instructions pipeline cleanly and clock faster). Whether it's a net win depends on the *product*. The iron law forces you to account for all three.

```python
def cpu_time(instructions, cpi, clock_ghz):
    cycle_time_ns = 1.0 / clock_ghz          # 1/GHz = nanoseconds per cycle
    return instructions * cpi * cycle_time_ns

# Design A (CISC-ish): fewer instructions, higher CPI, lower clock
a = cpu_time(instructions=1_000_000, cpi=3.0, clock_ghz=2.0)
# Design B (RISC-ish): more instructions, lower CPI, higher clock
b = cpu_time(instructions=1_400_000, cpi=1.2, clock_ghz=3.5)

print(f"Design A: {a:>10.0f} ns")
print(f"Design B: {b:>10.0f} ns")
print(f"B is {a/b:.2f}x faster" if b < a else f"A is {b/a:.2f}x faster")
```

```
Design A:    1500000 ns
Design B:     480000 ns
B is 3.12x faster
```

Design B runs **40% more instructions** yet finishes **3× faster**, because its CPI and clock advantages dominate. *That* is why you never judge a CPU by instruction count or clock speed alone, and why "this chip is 4 GHz so it's faster than that 3 GHz chip" is a rookie claim. Always reason about the **product** of all three factors (and remember Amdahl's law: speeding up one part only helps in proportion to how much time that part took).

```
💼 Interview angle: "Is fewer instructions always faster?" No - the iron law.
"Is a higher clock always faster?" No - the iron law. "How would you make this
program faster?" Reason about which of the three factors you're moving and by
how much, and whether memory (cache) behavior is the real bottleneck. Showing
you think in the iron law instead of folk wisdom is a strong signal.
```

## Mini-project - sum an array, count cycles, then add a cache model

Let's tie it all together. We'll (1) extend our CPU simulator to charge *realistic per-instruction cycle costs*, (2) run a real program that **sums an array**, (3) report total cycles and CPI, and (4) layer a cache model on top so memory access cost reflects hits and misses.

```python
class CostedCPU(CPU):
    """Extends the single-cycle CPU with per-instruction cycle costs and an
    OPTIONAL data cache so LOAD/STORE pay the real memory price. This lets us
    compute a realistic CPI and SEE the cache's effect on cycle count."""

    # base cycle cost per instruction type (a simplified cost model)
    COST = {
        "LOADI": 1, "ADD": 1, "SUB": 1, "MUL": 3,   # MUL is pricier (real chips: multi-cycle)
        "JZ": 1, "JMP": 1, "HALT": 1,
        "LOAD": 1, "STORE": 1,                       # base cost; memory penalty added below
    }
    L1_HIT_CYCLES = 0      # extra cycles on a cache hit (already counted in base)
    MEM_MISS_CYCLES = 100  # extra cycles on a cache miss (the ~100x cliff)

    def __init__(self, program, data_mem_size=256, cache=None):
        super().__init__(program, data_mem_size)
        self.cache = cache          # a DirectMappedCache or None
        self.instr_count = 0

    def step(self):
        op = self.program[self.pc][0]
        # charge the base instruction cost (we override cycle accounting)
        before = self.cycles
        super().step()
        self.cycles = before + self.COST[op]        # replace the flat +1 with real cost
        self.instr_count += 1

        # memory penalty: if this was a LOAD/STORE and we have a cache, charge misses
        if op in ("LOAD", "STORE") and self.cache is not None:
            instr = self.program[self.pc - 1]       # the instruction we just ran
            data_addr = instr[-1] * 4               # int index -> byte address (4 bytes/int)
            before_miss = self.cache.misses
            self.cache.access(data_addr)
            if self.cache.misses > before_miss:     # it was a miss
                self.cycles += self.MEM_MISS_CYCLES

    def cpi(self):
        return self.cycles / self.instr_count if self.instr_count else 0.0
```

Now a program that sums a 5-element array stored in memory addresses 10..14, leaving the total in `R7`. We'll write the array, then loop with a counter. (Our toy ISA has no register-indirect load, so we *unroll* the loop, perfectly fine for illustrating cost.)

```python
# pre-load the array into data memory, then sum it.
program = [
    # --- set up the array values in memory (STORE writes them) ---
    ("LOADI", 1, 10), ("STORE", 1, 10),   # MEM[10] = 10
    ("LOADI", 1, 20), ("STORE", 1, 11),   # MEM[11] = 20
    ("LOADI", 1, 30), ("STORE", 1, 12),   # MEM[12] = 30
    ("LOADI", 1, 40), ("STORE", 1, 13),   # MEM[13] = 40
    ("LOADI", 1, 50), ("STORE", 1, 14),   # MEM[14] = 50
    # --- sum them into R7 ---
    ("LOADI", 7, 0),                       # R7 = running total = 0
    ("LOAD",  2, 10), ("ADD", 7, 7, 2),    # R7 += MEM[10]
    ("LOAD",  2, 11), ("ADD", 7, 7, 2),    # R7 += MEM[11]
    ("LOAD",  2, 12), ("ADD", 7, 7, 2),    # R7 += MEM[12]
    ("LOAD",  2, 13), ("ADD", 7, 7, 2),    # R7 += MEM[13]
    ("LOAD",  2, 14), ("ADD", 7, 7, 2),    # R7 += MEM[14]
    ("HALT",),
]

# --- Run WITHOUT a cache (every memory op is just base cost) ---
no_cache = CostedCPU(program, cache=None).run()
print("sum (R7)      =", no_cache.regs[7])         # 150
print("no cache: cycles =", no_cache.cycles, " CPI =", round(no_cache.cpi(), 2))

# --- Run WITH a cold cache (first touch of each line misses → big penalty) ---
cache = DirectMappedCache(num_slots=16, line_size=64)
with_cache = CostedCPU(program, cache=cache).run()
print("with cache: cycles =", with_cache.cycles, " CPI =", round(with_cache.cpi(), 2))
print(f"cache: {cache.hits} hits, {cache.misses} misses, "
      f"hit rate {cache.hit_rate():.1%}")
```

Output:

```
sum (R7)      = 150
no cache: cycles = 22  CPI = 1.0
with cache: cycles = 122  CPI = 5.55
cache: 9 hits, 1 misses, hit rate 90.0%
```

Read that carefully. With **no cache modeled**, every memory op is base cost, so CPI is a flat 1.0, the rosy textbook number. With a cache, the *first* memory access (the `STORE` to address 10 → byte 40) **misses** and pays the 100-cycle penalty; after that, addresses 10-14 are int indices → bytes 40-56, which **all live in the same 64-byte line** (bytes 0-63), so the remaining 9 memory ops are **hits** at no extra cost. That single cold miss alone drags the real CPI from 1.0 up to ~5.55, because one miss costs as much as 100 instructions. **This is the gap between the marketing CPI and the real CPI**, and it's *entirely* memory behavior. The lesson the iron law and the cache simulator teach together: on real hardware, **the memory hierarchy, not the instruction count, often decides your speed.** (Spread the array across many cache lines and the miss count, and the CPI, climbs fast; that's extension (a) below.)

**Extensions to try:**
- (a) Add a register-indirect `LOAD rd, [ra]` instruction so you can write a *real* loop with a pointer that increments, then sum a 1000-element array and watch the cache hit rate climb as sequential accesses share lines.
- (b) Swap the `DirectMappedCache` for a 2-way set-associative version and measure how conflict misses drop on a thrashing access pattern.
- (c) Add a tiny branch predictor: track each `JZ`'s last outcome, "predict" it next time, and charge a misprediction penalty when wrong, then measure CPI on a loop and confirm predictable loops are nearly free.
- (d) Print a per-instruction trace (PC, op, registers) so you can *watch* the fetch-decode-execute loop step by step.

## Teach it back

1. **Von Neumann model.** One memory holds both instructions and data; CPU (control unit + ALU + registers) talks to it over a bus. "Code is data" enables compilers, JITs, and self-modifying code. Real chips dodge the von Neumann bottleneck with split I-cache/D-cache (Harvard *inside*).
2. **ISA vs microarchitecture.** The ISA is the stable software-visible contract (instructions, registers, memory model); the microarchitecture is the ever-changing implementation. RISC (ARM, RISC-V, simple, fixed-length, load-store) vs CISC (x86, complex, variable-length); modern x86 is RISC-inside, CISC-outside.
3. **Fetch-decode-execute.** PC names the next instruction; fetch into IR, decode, execute (ALU / memory / write reg / change PC), repeat. Control flow is just *writing a new value into the PC*.
4. **Single-cycle CPU.** Each instruction completes fully before the next. We built one in Python: registers, data memory, PC, an ALU, and a handful of instructions running a real program.
5. **Pipelining.** Overlap instruction stages like a laundry assembly line. Throughput → ~one instr/cycle; speedup approaches the number of stages for long runs. **Hazards** (structural, data, control) force stalls; fixed by forwarding, bubbles, and branch prediction. Hazards raise effective CPI.
6. **Memory hierarchy.** registers→L1→L2→L3→RAM→disk; each ~10× bigger and slower. Caches exploit **temporal** and **spatial locality**, fetch **64-byte lines**, and use direct-mapped / set-associative / fully-associative mapping with write-through or write-back policies. Hit rate dominates performance because of the ~100× L1-vs-RAM cliff.
7. **Going wider.** Superscalar (multiple instr/cycle), out-of-order (hide latency), SIMD (vector ops), multicore (separate streams). All to keep the silicon busy.
8. **Iron law.** `CPU time = instructions × CPI × cycle time`. You must reason about all three (and memory behavior), never judge a CPU by clock speed or instruction count alone.

## Exercises

**1.** Explain the von Neumann bottleneck and how real CPUs work around it without abandoning the von Neumann model.

<details><summary>Solution</summary>

The von Neumann bottleneck: because instructions *and* data share a single memory and a single path (bus) to the CPU, you can't fetch an instruction and access a data word in the *exact same cycle* over that one channel, the CPU can stall waiting on the shared path. Real CPUs keep one unified main memory (still von Neumann at the system level) but add **separate L1 instruction and data caches** inside the chip (Harvard-style *internally*). Instruction fetches hit the I-cache while data loads/stores hit the D-cache, so the two don't contend. It's a microarchitectural fix that preserves the ISA-level von Neumann model. ✓
</details>

**2.** A program runs 2,000,000 instructions. On CPU X: CPI = 1.5, clock = 3 GHz. On CPU Y: the same program compiles to 2,600,000 instructions, CPI = 0.9, clock = 4 GHz. Which is faster, and by how much?

<details><summary>Solution</summary>

Use the iron law, `time = instructions × CPI × (1/clock)`.
- X: `2,000,000 × 1.5 × (1/3 ns) = 2,000,000 × 1.5 × 0.3333 ns = 1,000,000 ns = 1.00 ms`.
- Y: `2,600,000 × 0.9 × (1/4 ns) = 2,600,000 × 0.9 × 0.25 ns = 585,000 ns = 0.585 ms`.

**Y is faster**, by `1.00 / 0.585 ≈ 1.71×`, *despite running 30% more instructions*, its lower CPI and higher clock dominate. This is the iron-law trap: instruction count alone is misleading. ✓
</details>

**3.** A 5-stage pipeline runs 50 instructions, each stage 0.5 ns. How long does it take, and what's the speedup over a single-cycle design? When would the speedup be much smaller?

<details><summary>Solution</summary>

- Single-cycle: one long cycle = 5 stages = 2.5 ns each; `50 × 2.5 = 125 ns`.
- Pipelined: `(N + stages − 1) × stage = (50 + 4) × 0.5 = 54 × 0.5 = 27 ns`.
- Speedup ≈ `125 / 27 ≈ 4.63×` (approaching the ideal 5×; the `stages−1=4` fill cycles cost a bit).

The speedup shrinks when (a) `N` is *small* (fill cost is a bigger fraction), or (b) there are many **hazards**, data dependencies forcing stalls, or branch mispredictions causing flushes, which raise effective CPI above the ideal 1.0 and erode the throughput gain. ✓
</details>

**4.** A direct-mapped cache has 64-byte lines. You scan an array of 4-byte ints sequentially. What hit rate do you expect, and why? What single access pattern would crater it to ~0%?

<details><summary>Solution</summary>

64 bytes / 4 bytes = **16 ints per cache line**. Scanning sequentially, the first access to each line **misses** (pulls in the line), and the next **15 are hits** (spatial locality, the neighbors came along). So 1 miss per 16 accesses → miss rate 1/16 = 6.25% → **hit rate ≈ 93.75%**.

To crater it: use a **stride ≥ one cache line** (e.g., touch one int every 16+ ints, or every 64+ bytes), so *every* access lands on a fresh, uncached line and you get spatial locality of zero → near-0% hit rate (and possibly conflict-evicting if the stride aligns with the slot count). This is why column-major traversal of a row-major array, or a giant stride, destroys cache performance. ✓
</details>

**5.** Why is processing a *sorted* array sometimes dramatically faster than processing the same data unsorted, with identical code? Which architectural feature explains it?

<details><summary>Solution</summary>

**Branch prediction.** If the loop has a data-dependent branch like `if (value >= 128) sum += value;`, then on **sorted** data the branch outcome is highly predictable (all "false" until the threshold, then all "true"), the predictor guesses right nearly every time, so the pipeline never flushes. On **unsorted/random** data, the branch flips unpredictably, so the predictor is wrong ~50% of the time; each misprediction **flushes** the speculatively-fetched instructions (a penalty of ~10-20 cycles on a deep pipeline). Same instruction count, same paper-CPI, but the random case pays a constant misprediction tax → much slower real time. It's a vivid demonstration that on modern pipelined CPUs, *data patterns* affect speed, not just the code. ✓
</details>

**6.** Distinguish a structural hazard, a data hazard, and a control hazard, and give the standard fix for each.

<details><summary>Solution</summary>

- **Structural hazard:** two instructions need the *same hardware resource* in the same cycle (e.g., instruction fetch and a data memory access both want memory). Fix: **duplicate the resource**, split instruction and data caches so fetch (IF) and memory access (MEM) use different units.
- **Data hazard:** an instruction needs a result a prior, still-in-flight instruction hasn't produced yet (e.g., `SUB R4,R1,R5` right after `ADD R1,…`). Fix: **forwarding/bypassing** (route the ALU output straight to the dependent instruction before write-back); if that can't cover it (a load-use hazard), insert a **stall/bubble**.
- **Control hazard:** after a branch, the CPU doesn't yet know which instruction to fetch next. Fix: **branch prediction** (guess and fetch speculatively; flush on misprediction), or stall until the branch resolves.

All three raise effective CPI when they force stalls/flushes, which the iron law turns directly into slower runtime. ✓
</details>
