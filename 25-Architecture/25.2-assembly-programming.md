# Chapter 25.2 - Assembly Programming

> Goal: Stop treating compiled code as a black box and learn to read (and write) the language the CPU *actually* runs. By the end you'll be able to: explain *why* assembly is worth learning (debugging, performance, security, demystification); hold the mental model (registers, memory, flags); read and write **x86-64 assembly** (we'll pick **AT&T syntax**, with Intel-syntax and ARM64 notes); know the core instructions (`mov`, arithmetic, `cmp`/`test`, jumps, the stack, `call`/`ret`); explain the **System V AMD64 calling convention** (which registers pass arguments, who saves what, how a stack frame is built, tying to the stack from 05.1); write small programs (a syscall "hello", arithmetic, a loop, an `if`, a function); and, the big payoff, **compile C with `gcc -S` and disassemble with `objdump -d`** to read what the compiler generated at `-O0` vs `-O2`, seeing exactly how a for-loop, an array, and a function map to machine instructions. We'll also connect this to **security** (how buffer overflows work, defensively, 12.x) and **compilers** (codegen, 24.2). Hands-on, with exact commands; if you lack a toolchain you'll use an online assembler.

In 25.1 we built a *toy* CPU and watched fetch-decode-execute run a made-up instruction set. This chapter swaps the toy for the real thing. Assembly is the human-readable form of the actual machine code your processor executes, one short mnemonic per instruction, mapping almost 1:1 onto the bytes the CPU fetches. Learning it is the moment the whole stack stops being theoretical: you'll watch a C `for` loop turn into `cmp`, `jl`, and a counter in a register; you'll see a function call become `push`, `call`, `ret`; you'll understand *in your bones* what a pointer is and why a buffer overflow can hijack a program. There's no faster way to delete the words "magic" and "somehow" from your model of computing. Let's read what the machine really does.

## 🌱 Start here (the gentle on-ramp)

Imagine you're directing someone who can only follow *absurdly literal* one-line orders, and who has just **16 numbered cubbyholes** on their desk (the registers) plus a giant wall of numbered lockers down the hall (memory).

You can't say "add up this list." You have to say:
- "Put the number 0 in cubby A." (initialize a sum)
- "Go to locker 100, bring its number, add it to cubby A."
- "Go to locker 104, bring its number, add it to cubby A."
- … and so on, then "write cubby A's value to locker 200."

That's assembly. Every instruction is one tiny, literal step: move a number, add two numbers, compare two numbers, or jump to a different instruction. There are no loops, no `if` statements, no functions as language features, only **compare-and-jump** (which *builds* loops and ifs) and **call/return with a stack** (which *builds* functions). High-level languages are conveniences your compiler shreds into exactly these literal steps.

Two things make this tractable rather than overwhelming:

1. **The CPU has only a few moves.** Move data, do arithmetic, compare, jump, push/pop the stack, call/return. Master maybe twenty mnemonics and you can read most code.
2. **There are status flags.** After a comparison, the CPU sets little flag bits ("was the result zero? negative? did it carry?"). Conditional jumps read those flags. That `cmp` + `jump` pair is *the* mechanism behind every `if`, `while`, and `for` you've ever written.

And the single most clarifying exercise in all of low-level CS: write a three-line C function, run `gcc -S`, and read the assembly the compiler produced. You'll see your `return a + b;` become literally `add` then `ret`. After a few of these, the compiler stops being a wizard and becomes a (very good) translator whose output you can check.

## 📐 Why learn assembly?

You will almost never *write* large programs in assembly, it's tedious and the compiler is better than you at the bookkeeping. So why learn it?

- **Demystification (no black boxes).** This whole book's creed. You've built up from transistors (17.2) to gates (01.2) to a datapath and CPU (25.1). Assembly is the rung where *your code* meets *that hardware*. Reading it closes the loop from Python down to electrons.
- **Debugging.** When a crash dumps a stack trace with addresses and register values, or your optimized build behaves differently from the debug build, or you're staring at a core dump, assembly is the ground truth. Sometimes the *only* truth, when the source has been optimized beyond recognition.
- **Performance.** To make code fast (16.4) you must know what it compiles to: does that loop vectorize? Is the compiler keeping `i` in a register or spilling it to the stack? Did `-O2` hoist the bounds check out? You can only answer by reading the asm.
- **Security (12.x).** Buffer overflows, stack smashing, return-oriented programming, shellcode, these are *assembly-level* phenomena. You cannot understand (or defend against) them without understanding the stack, return addresses, and how `call`/`ret` work. We'll cover the defensive mental model below.
- **Compilers (24.2).** The back end of a compiler *is* a program that emits assembly. Understanding codegen, how source constructs lower to instructions, is the heart of that.

```
💼 On the job / interview angle: most jobs never have you hand-write asm, but
"can you read a disassembly and tell me what this function does?" and "walk me
through what happens on the stack during a function call" come up in systems,
security, and performance roles. Being *unafraid* of assembly is a real
differentiator. The skill isn't writing it fluently - it's reading it without
panic.
```

## 📐 The mental model - registers, memory, flags

Three things the CPU operates on:

**Registers**, a tiny set of ultra-fast storage slots *inside* the CPU (the flip-flops of 17.3, the top of the hierarchy in 25.1). On x86-64 there are 16 general-purpose 64-bit registers. They're the cubbyholes: almost all work happens *in* registers; memory is where you keep things you're not currently touching.

```
   x86-64 GENERAL-PURPOSE REGISTERS (64-bit, with their roles)

   rax   accumulator / return value
   rbx   (callee-saved general)
   rcx   counter / 4th arg
   rdx   data / 3rd arg
   rsi   source index / 2nd arg
   rdi   destination index / 1st arg
   rbp   base pointer (frame pointer)
   rsp   STACK POINTER (top of the stack)
   r8..r15   additional general regs (r8,r9 = 5th,6th args)

   Each has narrower aliases:
   rax (64-bit) → eax (32) → ax (16) → al (8)
   (writing eax zeroes the upper 32 bits of rax - a common gotcha)
```

**Memory**, the big addressable array of bytes (25.1's hierarchy / 05.1's address space). Registers hold a few values; memory holds everything else. The stack lives here, pointed to by `rsp`.

**Flags**, the `RFLAGS` register holds status bits set by operations, especially comparisons:
- **ZF (zero flag)**, set if the result was zero.
- **SF (sign flag)**, set if the result was negative.
- **CF (carry flag)**, set on unsigned overflow/borrow.
- **OF (overflow flag)**, set on signed overflow.

Conditional jumps read these flags. `cmp a, b` secretly computes `b - a` and sets the flags *without storing the result*; then `je` (jump if equal) fires when ZF=1, `jl` (jump if less) reads SF/OF, and so on. **This flag-then-jump dance is how all control flow works.**

```
   THE CONTROL-FLOW CORE

   cmp  rax, rbx     ; compare (sets ZF, SF, CF, OF)
   jl   .somewhere   ; conditional jump reads the flags
   ───────────────
   That pair builds every if / while / for. There is nothing else.
```

## 📐 Choosing a target & syntax

**Primary: x86-64 (a.k.a. AMD64)**, what most desktops, laptops, and cloud servers run. CISC (25.1), variable-length encoding, 16 GP registers.

**Two syntaxes, same machine.** x86 assembly comes in two dialects, which trips everyone up at first:

| | **AT&T syntax** | **Intel syntax** |
|---|---|---|
| Operand order | source, **dest** (`mov src, dst`) | **dest**, source (`mov dst, src`) |
| Registers | `%rax` (percent prefix) | `rax` (bare) |
| Immediates | `$5` (dollar prefix) | `5` |
| Memory | `8(%rbp)` | `[rbp+8]` |
| Used by | GNU tools (`gcc -S`, `gas`, default `objdump`) | Intel manuals, NASM, Windows |

**We'll use AT&T syntax** as the primary, because it's what `gcc -S` and `objdump` emit by default on Linux/Mac, and reading compiler output is half this chapter's payoff. The killer thing to remember: **in AT&T, the destination is on the right** (`mov $5, %rax` means "put 5 into rax"). That's backwards from how most of us read, so every example is annotated.

```
💡 Tip: you can force Intel syntax with `gcc -S -masm=intel` or
`objdump -d -M intel`. If you find AT&T's %/$ noise annoying, Intel syntax is
cleaner - but you MUST be able to read AT&T, because that's the Linux default
you'll meet in the wild. I'll note Intel equivalents where it helps.
```

**Secondary note: ARM64 (AArch64)**, phones, Apple Silicon Macs, AWS Graviton. RISC (25.1), fixed 4-byte instructions, 31 general registers (`x0`-`x30`), a *load-store* architecture (only `ldr`/`str` touch memory; arithmetic is register-only). Its calling convention passes the first 8 args in `x0`-`x7`. The *concepts* (registers, flags, compare-and-branch, a stack, call/return) are identical; only the spelling differs. We'll point out ARM64 contrasts as we go. If you're on an Apple Silicon Mac, your native `gcc -S` will emit ARM64, that's fine, the ideas transfer; we'll note where the listings differ.

## 📐 The core instructions

A working vocabulary. (AT&T syntax: `op src, dst`.)

**Data movement**
```asm
    mov  $5, %rax        # rax = 5            (Intel: mov rax, 5)
    mov  %rax, %rbx      # rbx = rax
    mov  (%rdi), %rax    # rax = MEM[rdi]     (dereference: load)
    mov  %rax, (%rdi)    # MEM[rdi] = rax     (store)
    lea  8(%rdi), %rax   # rax = rdi + 8      (compute ADDRESS, don't deref)
```
`lea` ("load effective address") is sneaky-useful: it does address arithmetic without touching memory, so compilers use it for fast `a = b*4 + c`-style math.

**Arithmetic & logic**
```asm
    add  %rbx, %rax      # rax = rax + rbx
    sub  $1, %rax        # rax = rax - 1
    imul %rbx, %rax      # rax = rax * rbx   (signed multiply)
    inc  %rax            # rax++
    dec  %rax            # rax--
    and  %rbx, %rax      # bitwise AND
    or   %rbx, %rax
    xor  %rax, %rax      # rax = 0   (idiomatic zeroing - shorter/faster than mov $0)
    shl  $2, %rax        # rax <<= 2  (multiply by 4)
```

**Compare & test**
```asm
    cmp  %rbx, %rax      # set flags from (rax - rbx); doesn't store
    test %rax, %rax      # set flags from (rax AND rax); test if rax==0 / sign
```

**Jumps (control flow)**
```asm
    jmp  .label          # unconditional
    je   .label          # jump if equal      (ZF=1)
    jne  .label          # jump if not equal  (ZF=0)
    jl   .label          # jump if less       (signed)
    jle  .label          # jump if <=         (signed)
    jg   .label          # jump if greater    (signed)
    jge  .label          # jump if >=         (signed)
```

**The stack**
```asm
    push %rax            # rsp -= 8; MEM[rsp] = rax   (stack grows DOWN)
    pop  %rax            # rax = MEM[rsp]; rsp += 8
```

**Function call & return**
```asm
    call func            # push return address; jmp func
    ret                  # pop return address into rip (jump back)
```

That's the bulk of it. `call`/`ret` and the stack are where it gets interesting, so let's go deep.

## 📐 Registers, the calling convention & how a function call REALLY works

When you write `int r = add(3, 4);` in C, *something* has to decide: where do the arguments go? Where does the return value come from? Who's responsible for not clobbering registers? That contract is the **calling convention**, and on 64-bit Linux/macOS it's the **System V AMD64 ABI**.

### Argument & return registers

```
   SYSTEM V AMD64 CALLING CONVENTION

   integer/pointer arguments, in order:
     1st → rdi
     2nd → rsi
     3rd → rdx
     4th → rcx
     5th → r8
     6th → r9
     (7th and beyond → pushed on the stack)

   return value → rax
   (floating-point args → xmm0..xmm7; return → xmm0)
```

So `add(3, 4)` puts 3 in `rdi`, 4 in `rsi`, `call`s, and reads the result from `rax`. That's it, the whole mystery of "how does a function get its arguments" is "the caller agreed to leave them in specific registers."

```
   ARM64 contrast: args go in x0..x7, return in x0. Same idea, more arg
   registers. Almost every architecture has this kind of convention.
```

### Caller-saved vs callee-saved

Registers are shared, so there are rules about who must preserve what across a call:

- **Caller-saved (volatile):** `rax, rcx, rdx, rsi, rdi, r8-r11`. A called function may freely clobber these. If the *caller* needs a value preserved across a call, *it* must save/restore it.
- **Callee-saved (non-volatile):** `rbx, rbp, r12-r15` (and `rsp`). A called function that uses these must save them first (push) and restore them before returning (pop). The caller can rely on them surviving the call.

This split is a performance compromise: most calls don't need every register preserved, so making *some* caller-saved avoids needless save/restore.

### The stack frame - the heart of it (tie to 05.1)

In 05.1 you drew the stack and watched it grow on a function call. Now we see the instructions that do it. The stack grows **downward** (toward lower addresses). Each function gets a **stack frame** for its local variables, saved registers, and the return address.

```
   A STACK FRAME (high address at top, stack grows DOWN)

   higher addresses
   │  ...caller's frame...        │
   ├──────────────────────────────┤
   │  argument 7+ (if any)         │  ← pushed by caller
   ├──────────────────────────────┤
   │  RETURN ADDRESS               │  ← pushed by `call`
   ├──────────────────────────────┤  ← rbp points here after prologue
   │  saved rbp (old frame ptr)    │
   ├──────────────────────────────┤
   │  local variables              │
   │  saved callee-saved regs      │
   ├──────────────────────────────┤  ← rsp points here (top of stack)
   lower addresses
```

A typical function **prologue** and **epilogue** look like:

```asm
my_func:
    push %rbp            # save caller's frame pointer
    mov  %rsp, %rbp      # set up our frame pointer
    sub  $16, %rsp       # reserve 16 bytes for locals
    # ... function body, locals at -8(%rbp), -16(%rbp), etc. ...
    mov  %rbp, %rsp      # tear down locals (or: `leave`)
    pop  %rbp            # restore caller's frame pointer
    ret                  # pop return address → jump back to caller
```

**Here is the whole story of `call`/`ret`, step by step:**

1. Caller puts args in `rdi, rsi, …` and executes `call my_func`.
2. `call` **pushes the return address** (the address of the instruction *after* `call`) onto the stack, then jumps to `my_func`.
3. `my_func` runs its prologue (saves `rbp`, sets up its frame, reserves locals).
4. Body executes; the return value goes in `rax`.
5. Epilogue restores `rbp` and `rsp`.
6. `ret` **pops the return address** off the stack into the instruction pointer (`rip`), execution resumes right after the original `call`.

```
⚠️ Security tie-in (12.x), stated defensively: notice the RETURN ADDRESS sits
on the stack, right above the local variables. If a local buffer (say
`char buf[64]`) is written past its end - a BUFFER OVERFLOW - the excess bytes
march UP the stack and can OVERWRITE that return address. Then `ret` jumps
wherever the attacker chose. That's "stack smashing." Defenses you've heard of
map directly onto this picture: STACK CANARIES (a secret value placed just below
the return address, checked before `ret` - if an overflow trampled it, abort),
NON-EXECUTABLE STACK / NX (so injected data on the stack can't be run as code),
and ASLR (randomize addresses so the attacker can't predict where to jump). You
now understand WHY each defense exists - because you can see the return address
sitting vulnerable on the stack. (Full treatment in Chapter 12; here we just
note the mechanism so the defenses make sense.)
```

## 💻 Build it - write, assemble, and run real assembly

Let's get our hands dirty, with exact commands. The toolchain is GNU `as`/`gcc`/`ld` and `objdump` (Linux, or macOS with the right targets; WSL works great on Windows). **If you have no toolchain, skip to the "online assembler" note below**, every program here runs on [godbolt.org](https://godbolt.org) (the Compiler Explorer) or an online x86 emulator without installing anything.

### Program 1: "Hello, world" via a raw syscall (Linux x86-64)

No libc, no `printf`, just ask the kernel directly to write to stdout and exit. This shows the *bare metal* path. (AT&T syntax; comments mark the destination.)

```asm
# hello.s  -  Linux x86-64, AT&T syntax. Assemble & run:
#   gcc -nostdlib -static -o hello hello.s && ./hello
    .global _start
    .section .data
msg:
    .ascii "Hello, assembly!\n"
    .set   msglen, . - msg          # length = current addr - msg

    .section .text
_start:
    # write(fd=1, buf=msg, count=msglen)  via syscall number 1
    mov  $1,      %rax              # rax = syscall #1 (write)
    mov  $1,      %rdi              # rdi = fd 1 (stdout)
    lea  msg(%rip), %rsi            # rsi = address of msg
    mov  $msglen, %rdx             # rdx = byte count
    syscall                         # invoke the kernel

    # exit(0)  via syscall number 60
    mov  $60, %rax                 # rax = syscall #60 (exit)
    xor  %rdi, %rdi                # rdi = 0  (exit status)
    syscall
```

Build and run:
```bash
gcc -nostdlib -static -o hello hello.s   # assemble + link, no libc
./hello
# -> Hello, assembly!
```

Notice the Linux **syscall convention** mirrors the function convention but uses `rax` for the syscall *number* and `rdi, rsi, rdx, r10, r8, r9` for arguments. You just talked to the kernel with nothing between you and the metal.

```
   ARM64 / macOS note: the syscall numbers and registers differ (macOS uses
   `svc #0` and different numbers; ARM64 Linux uses `svc #0`, syscall # in x8,
   args in x0..x5). The CONCEPT - load a number, load args, trap into the
   kernel - is identical. On Apple Silicon, easiest is to write the C version
   and read its asm (next section).
```

### Program 2: arithmetic and a return value

A function `add3(a, b, c)` returning `a + b + c`, callable from C:

```asm
# add3.s - System V AMD64. a in rdi, b in rsi, c in rdx; return in rax.
    .global add3
    .text
add3:
    mov  %rdi, %rax        # rax = a
    add  %rsi, %rax        # rax += b
    add  %rdx, %rax        # rax += c
    ret                    # return rax
```

Drive it from C and run:
```c
// driver.c
#include <stdio.h>
long add3(long, long, long);          // implemented in add3.s
int main(void) { printf("%ld\n", add3(10, 20, 30)); }
```
```bash
gcc -o prog driver.c add3.s && ./prog
# -> 60
```

That's a real function written in pure assembly, linked with C. The arguments arrived in `rdi/rsi/rdx`, the result left in `rax`, exactly the convention.

### Program 3: a loop and an `if` (sum 1..N, skipping odd numbers)

Watch how `cmp` + conditional jump *builds* both the loop and the `if`:

```asm
# sum_evens.s - sum the even numbers in [1, N]. N in rdi, result in rax.
    .global sum_evens
    .text
sum_evens:
    xor  %rax, %rax            # rax = sum = 0
    mov  $1,   %rcx            # rcx = i = 1
.Lloop:
    cmp  %rdi, %rcx            # compare i with N  (flags = i - N)
    jg   .Ldone               # if i > N, exit loop
    test $1, %rcx             # is i odd?  (low bit set)
    jnz  .Lnext               # if odd, skip the add  (this is the `if`)
    add  %rcx, %rax           # sum += i
.Lnext:
    inc  %rcx                 # i++
    jmp  .Lloop               # back to top of loop
.Ldone:
    ret                       # return sum
```

`cmp/jg` is the loop's exit test; `test/jnz` is the `if (i % 2 == 0)`. Every loop and branch you write is this, underneath. (For N=10 this returns 2+4+6+8+10 = 30.)

## 💻 Build it - read what the compiler generated

This is the payoff. We write plain C, compile it two ways, and *read the machine's mind*.

### `gcc -S`: get the assembly the compiler emits

```c
// sum.c
int sum_to(int n) {
    int total = 0;
    for (int i = 1; i <= n; i++) {
        total += i;
    }
    return total;
}
```

Compile to assembly, unoptimized:
```bash
gcc -S -O0 -fno-asynchronous-unwind-tables sum.c -o sum_O0.s
```

The `-O0` output (AT&T, trimmed of directives) looks roughly like:

```asm
sum_to:
    push %rbp
    mov  %rsp, %rbp           # prologue: set up frame
    mov  %edi, -20(%rbp)      # store arg n into a stack slot (no optimization!)
    movl $0,  -4(%rbp)        # total = 0   (on the stack)
    movl $1,  -8(%rbp)        # i = 1       (on the stack)
.L3:
    mov  -8(%rbp), %eax       # load i
    cmp  -20(%rbp), %eax      # compare i with n
    jg   .L2                  # if i > n, exit loop
    mov  -8(%rbp), %eax       # load i again
    add  %eax, -4(%rbp)       # total += i
    addl $1,  -8(%rbp)        # i++
    jmp  .L3                  # loop
.L2:
    mov  -4(%rbp), %eax       # return total
    pop  %rbp
    ret
```

Read it slowly. **Your `for` loop is right there**: `i` and `total` live in stack slots (`-8(%rbp)`, `-4(%rbp)`), the `cmp/jg` is the `i <= n` test, `add` is `total += i`, `addl $1` is `i++`, `jmp .L3` closes the loop. At `-O0` the compiler is *literal and dumb on purpose* (so debuggers can map every variable), it reloads `i` from the stack every iteration.

Now optimize:
```bash
gcc -S -O2 -fno-asynchronous-unwind-tables sum.c -o sum_O2.s
```

At `-O2`, GCC may keep everything in registers (no stack traffic), and modern GCC will often **recognize the closed-form sum** and replace the loop with the arithmetic formula `n*(n+1)/2`(!), emitting branch-free code with `lea` and `imul` and no loop at all. Even when it keeps a loop, it'll be tighter: `i` and `total` in registers, the redundant reload gone. **Seeing the same source produce wildly different asm at `-O0` vs `-O2` is the single best lesson in what an optimizing compiler does**, and why you must read the asm to reason about performance, not the source.

```
💡 Run BOTH and diff them. `-O0` shows you the literal, debuggable mapping of
your code; `-O2` shows you what actually runs in production. The gap between
them - strength reduction, loop-invariant hoisting, keeping values in registers,
vectorization, even replacing a loop with a formula - IS the optimizing
compiler's job (24.2 codegen + optimization). You can SEE every transformation.
```

### `objdump -d`: disassemble the finished binary

`gcc -S` shows the compiler's asm *before* assembly/linking. To see what's *actually* in the executable, the real bytes, disassemble it:

```bash
gcc -O2 -c sum.c -o sum.o          # compile to an object file
objdump -d sum.o                   # disassemble (AT&T by default)
# or Intel syntax:
objdump -d -M intel sum.o
```

You'll see each instruction with its **machine-code bytes** alongside the mnemonic:

```
0000000000000000 <sum_to>:
   0:  85 ff                  test   %edi,%edi        # n <= 0 ?
   2:  7e 13                  jle    17 <sum_to+0x17> # if so, skip
   4:  8d 47 ff               lea    -0x1(%rdi),%eax  # clever closed-form math...
   ...
  17:  31 c0                  xor    %eax,%eax        # return 0
  19:  c3                     ret
```

The left column (`85 ff`, `8d 47 ff`, …) is the **actual machine code**, the bytes the CPU fetches in 25.1's fetch step. The mnemonic on the right is `objdump` decoding them for you. This is the absolute ground floor: variable-length x86 encoding (notice some instructions are 2 bytes, some 3+), the literal numbers the CPU runs. **No black boxes left, you're reading the program as the processor sees it.**

```
   `objdump -d` on a whole program, plus `gdb` (or `lldb` on Mac), is how you
   debug optimized crashes: set a breakpoint, `disassemble`, `info registers`,
   step instruction-by-instruction, and watch rsp/rbp move as frames are built
   and torn down. This is THE skill for low-level debugging and reverse
   engineering (and security work, 12.x).
```

## 📐 How high-level constructs map down

A quick field guide to what your source becomes:

- **Local variables** → registers (fast) or stack slots like `-8(%rbp)` (when there are too many, or you took their address). At `-O2`, most stay in registers.
- **Arrays** → a base address + index arithmetic: `arr[i]` becomes `base + i*element_size`, often computed with `lea` or scaled addressing like `mov (%rdi,%rcx,4), %eax` (= `MEM[rdi + rcx*4]`, i.e., the i-th 4-byte int). **This scaled-index addressing is why contiguous arrays are cache-friendly (25.1):** sequential `i` walks sequential addresses.
- **Structs** → a base address + fixed byte **offsets** for each field (`field2` at `8(%rbase)`). Padding for alignment shows up as gaps.
- **`if`/`else`** → `cmp` + conditional jump skipping over a block (sometimes branchless via `cmov`).
- **Loops** → a label, a body, a `cmp` + conditional jump back (or fall-through past it to exit).
- **Function calls** → load args into `rdi/rsi/…`, `call`, read result from `rax`, per the convention above.
- **Recursion** → ordinary `call`/`ret`, but each call pushes a *new stack frame*. This is *literally why* deep recursion overflows the stack (05.1): each frame consumes stack space, and the stack has a finite size. You can watch `rsp` march downward in a debugger with every recursive call.

```
⚠️ Common mistakes when reading asm:
  - Forgetting AT&T's reversed operand order (dest is on the RIGHT). `sub $1, %rax`
    is rax -= 1, NOT 1 -= rax.
  - Thinking `cmp a, b` stores something. It only sets FLAGS; the next
    conditional jump reads them.
  - Missing that writing `eax` (32-bit) ZEROES the top 32 bits of `rax`. A common
    source of "where did the high bits go?" confusion.
  - Assuming `-O0` asm reflects real performance. It doesn't - always check `-O2`.
  - Confusing `lea` (computes an address, no memory access) with `mov (...)`
    (actually dereferences). `lea` is often just fast arithmetic.
```

## 🧪 Mini-project - write `factorial` in assembly, then compare the compiler's version

Two deliverables: (1) hand-write an assembly `factorial`, run it; (2) write the C version, compile it, and **compare the compiler's asm to yours**.

### Part A: hand-written `factorial` (iterative)

```asm
# factorial.s - long factorial(long n). n in rdi, return in rax.
# Computes n! iteratively: result = 1; for i in 2..n: result *= i.
    .global factorial
    .text
factorial:
    mov  $1, %rax            # rax = result = 1
    mov  $2, %rcx            # rcx = i = 2
.Lloop:
    cmp  %rdi, %rcx          # compare i with n  (flags = i - n)
    jg   .Ldone             # if i > n, done
    imul %rcx, %rax         # result *= i
    inc  %rcx               # i++
    jmp  .Lloop
.Ldone:
    ret                      # return result
```

Drive and run:
```c
// fac_driver.c
#include <stdio.h>
long factorial(long);
int main(void) {
    for (long n = 0; n <= 10; n++)
        printf("%ld! = %ld\n", n, factorial(n));
}
```
```bash
gcc -o fac fac_driver.c factorial.s && ./fac
# 0! = 1, 1! = 1, 2! = 2, ... 10! = 3628800
```

(Note: `factorial(0)` and `factorial(1)` correctly return 1 because the loop's `cmp/jg` exits immediately when `i=2 > n`.)

### Part B: the C version and the comparison

```c
// fac.c
long factorial(long n) {
    long result = 1;
    for (long i = 2; i <= n; i++)
        result *= i;
    return result;
}
```
```bash
gcc -S -O2 -fno-asynchronous-unwind-tables fac.c -o fac_O2.s
cat fac_O2.s
```

What you'll likely see, and how to compare:

- **Structure matches yours:** an `imul` accumulating into a register, a counter, a `cmp` + conditional jump loop. The compiler arrived at essentially the same algorithm.
- **Register choices differ:** GCC picks its own registers (maybe `rax` for result, `rdx` or `rcx` for `i`), and may handle the `n < 2` case with an up-front `cmp`/branch so the loop body is never entered for `n=0,1`.
- **Possible cleverness:** at `-O2`, GCC might **unroll** the loop (do several multiplies per iteration to reduce branch overhead), or reorder instructions to help the pipeline (25.1). Your hand version is simpler; the compiler's is tuned.

The lesson: a competent human and a good compiler converge on the *same algorithm*, but the compiler wins on the *micro-optimizations* (register allocation, unrolling, instruction scheduling), which is exactly why we let it do codegen and only drop to asm to *read*, *debug*, or *tune the rare hot spot*.

**Extensions to try:**
- (a) Write a **recursive** factorial in asm (each call does `call factorial`; watch the stack frames pile up in a debugger, `rsp` marching down) and compare to the iterative one's flat stack usage. This makes 05.1's "recursion uses the stack" concrete.
- (b) Compile the C factorial at `-O0`, `-O1`, `-O2`, `-O3` and diff the four. Watch optimizations turn on one by one.
- (c) Write a `sum_array(int *a, int n)` in asm using **scaled-index addressing** (`mov (%rdi,%rcx,4), %eax`), then compare to GCC's, and check at `-O3` whether GCC **vectorizes** it with SSE/AVX SIMD instructions (the `addps`/`paddd`-style ops, tying to 25.1's SIMD and 16.4's NumPy speed).
- (d) Use **godbolt.org** to compile the *same* C for x86-64 *and* ARM64 side by side, and see the same loop expressed in two ISAs (`x0..x7` args, `ldr`/`str`, `b.le` branches). Same logic, different spelling, the 25.1 ISA-vs-microarchitecture point made vivid.

## ✅ Teach it back

1. **Why assembly.** Demystification (closes the stack from Python to electrons), debugging (ground truth in crashes/optimized builds), performance (know what your code compiles to), security (overflows are an asm-level phenomenon, 12.x), compilers (codegen is emitting asm, 24.2). The skill is *reading without panic*, not fluent writing.
2. **Mental model.** Registers (16 fast slots inside the CPU), memory (the big array), flags (ZF/SF/CF/OF set by ops). `cmp`/`test` set flags; conditional jumps read them, that pair builds *all* control flow.
3. **Syntax.** x86-64 primary; **AT&T syntax** (`op src, dst`, destination on the right, `%reg`, `$imm`) is the GNU/`objdump` default. Intel is `op dst, src`. ARM64 is RISC, load-store, args in `x0..x7`, same concepts, different spelling.
4. **Core instructions.** `mov`/`lea` (move/address), `add`/`sub`/`imul`/`xor` (arithmetic & idiomatic zeroing), `cmp`/`test` (set flags), conditional/unconditional jumps, `push`/`pop` (stack), `call`/`ret` (functions).
5. **Calling convention (System V AMD64).** Integer args in `rdi, rsi, rdx, rcx, r8, r9`; return in `rax`. Caller-saved (`rax, rcx, rdx, rsi, rdi, r8-r11`) vs callee-saved (`rbx, rbp, r12-r15`). A function call = put args in registers, `call` (pushes return address), prologue builds a stack frame, body runs, epilogue tears it down, `ret` pops the return address. The return address sits on the stack above the locals, *which is why buffer overflows can hijack control flow*, and why canaries/NX/ASLR exist (12.x).
6. **Reading compiler output.** `gcc -S` emits the compiler's asm; compare `-O0` (literal, stack-heavy, debuggable) vs `-O2` (register-resident, hoisted, sometimes loop-eliminated). `objdump -d` disassembles the actual binary, showing the real machine-code bytes the CPU fetches. **godbolt.org** does all this in the browser.
7. **How HLL maps down.** Locals → registers/stack slots; arrays → base + scaled index (cache-friendly, 25.1); structs → base + offsets; `if` → `cmp`+jump; loops → label + `cmp`+jump-back; calls → convention; recursion → nested stack frames (why it can overflow, 05.1).

## ✏️ Exercises

**1.** In AT&T syntax, what does `sub $3, %rax` do? What's the Intel-syntax equivalent, and what's the #1 mistake people make reading it?

<details><summary>Solution</summary>

`sub $3, %rax` computes `rax = rax - 3` (subtract the immediate 3 *from* rax, store back in rax). In AT&T the operands are `op src, dst` with the **destination on the right**, and `$` marks an immediate. Intel equivalent: `sub rax, 3` (destination first, no `$`). The #1 mistake: reading it left-to-right as "3 minus rax." It is **rax minus 3**, into rax. Internalizing "AT&T destination is on the right" prevents a huge fraction of reading errors. ✓
</details>

**2.** Under System V AMD64, where do the arguments of `long f(long a, long b, long c)` arrive, where does the return value go, and what does `call f` push onto the stack?

<details><summary>Solution</summary>

Arguments: `a` → `rdi`, `b` → `rsi`, `c` → `rdx` (the first three integer/pointer arg registers, in order). The return value comes back in `rax`. The `call f` instruction **pushes the return address**, the address of the instruction immediately *after* the `call`, onto the stack (decrementing `rsp` by 8), then jumps to `f`. When `f` executes `ret`, that return address is popped back into the instruction pointer, resuming the caller right after the `call`. ✓
</details>

**3.** A C `for (int i = 0; i < n; i++)` loop compiles (at `-O0`) to roughly which instructions? Name the role of `cmp` and the conditional jump.

<details><summary>Solution</summary>

Roughly: initialize `i` (`movl $0, -X(%rbp)`); a loop label; load `i` and `cmp` it against `n` (`cmp -Y(%rbp), %eax`); a conditional jump to *exit* if the condition fails (`jge .exit`, jump if `i >= n`); the loop body; increment `i` (`addl $1, -X(%rbp)`); an unconditional `jmp` back to the label; then the exit label. The **`cmp`** subtracts to set the flags (it's the `i < n` test), and the **conditional jump** reads those flags to decide whether to run another iteration or exit. That `cmp`+conditional-jump pair *is* the loop's control. ✓
</details>

**4.** Explain, defensively, how a stack-based buffer overflow can redirect a program's execution, and name two mitigations and what each does. Tie it to the stack frame layout.

<details><summary>Solution</summary>

In a stack frame, local variables (e.g., `char buf[64]`) sit at lower addresses and the **return address** (pushed by `call`) sits at a higher address, above the locals. If code writes past the end of `buf` without bounds-checking (a buffer overflow), the excess bytes overwrite memory *upward*, eventually clobbering the saved return address. When the function executes `ret`, it pops that (now attacker-controlled) value into the instruction pointer and jumps wherever the attacker chose, hijacking control flow ("stack smashing").

Mitigations:
- **Stack canary:** the compiler places a secret random value just below the return address on entry and checks it right before `ret`; an overflow that reached the return address must have trampled the canary, so the mismatch is detected and the program aborts.
- **Non-executable stack (NX/DEP):** marks stack memory non-executable, so even if an attacker injects code bytes onto the stack, the CPU refuses to execute them.
- **ASLR:** randomizes the base addresses of the stack/heap/libraries each run, so the attacker can't reliably predict where to jump.

Each defense makes sense *because* you can see the return address sitting exposed on the stack. (Full treatment: Chapter 12.) ✓
</details>

**5.** You compile a function at `-O0` and `-O2` and the assembly is dramatically different, the `-O2` version has no loop where the `-O0` version did. What likely happened, and which version reflects real performance?

<details><summary>Solution</summary>

At `-O2` the optimizing compiler likely **recognized a closed form** or otherwise transformed the loop, e.g., a `sum_to(n)` loop replaced by the formula `n*(n+1)/2` (branch-free arithmetic), or a loop strength-reduced/unrolled/vectorized. `-O0` deliberately produces *literal, unoptimized* code (every variable in a predictable stack slot) so debuggers can map source to instructions one-to-one; it is **not** representative of production speed. The **`-O2` version reflects real performance**, it's what actually ships and runs. This is exactly why you must read the *optimized* asm (and benchmark) to reason about performance, never the source or the `-O0` output. ✓
</details>

**6.** What's the difference between `lea 8(%rdi), %rax` and `mov 8(%rdi), %rax`?

<details><summary>Solution</summary>

`mov 8(%rdi), %rax` **dereferences**: it computes the address `rdi + 8`, then **loads the 8-byte value stored at that memory address** into `rax` (a memory access). `lea 8(%rdi), %rax` ("load effective address") computes the **same address** `rdi + 8` but **stores the address itself** into `rax`, it does *not* touch memory. So `lea` is pure address arithmetic; compilers exploit it as a fast way to compute things like `rax = rdi + 8` (or scaled forms like `lea (%rdi,%rcx,4), %rax` = `rdi + rcx*4`) without a real `add`/`imul`. Mixing them up is a classic asm-reading error: one reads memory, the other just does math. ✓
</details>
