# Chapter 5.2 - Processes, Threads, Concurrency & Parallelism

> Goal: get the words right first (concurrency ≠ parallelism), then build the machinery: processes vs threads, race conditions you can reproduce, locks and deadlock, the GIL and why it makes Python threading weird, multiprocessing for real CPU parallelism, and async/await as cooperative scheduling. By the end you'll run the same web-fetch job sequentially, with threads, and with async, and understand why each number comes out the way it does.

Concurrency is the topic where many people *sound* like they know what they're talking about while secretly being fuzzy. "Use threads to go faster", except in Python that's often false. "Async is faster", except for CPU work it's not. The cure is precision. Let's define terms so sharply that the right tool for each job becomes obvious.

---

## Start here: the coffee-shop analogy

Forget code for a second. Picture a coffee shop with one barista.

- **One barista, taking turns** is concurrency without parallelism. A customer orders a pour-over; the barista starts the water heating and, while it heats, turns to take the next customer's order, then comes back. Only one person (the barista) is ever actually doing something at any instant, but several orders are in progress at once. The trick is that a lot of "work" is really waiting (water heating, milk steaming), and a smart barista fills the waiting time with other orders. This is **I/O-bound** work: the program spends most of its time waiting (on the network, the disk), so one worker can juggle many tasks by switching during the waits.
- **Two baristas** is parallelism. Now two drinks are actually being made at the same instant. To make more drinks per minute when each drink takes real hands-on effort (not just waiting), you need more baristas, more cores. This is **CPU-bound** work: the bottleneck is actual computation, so the only way to go faster is to literally do more at once.

That single distinction (is your work mostly waiting, or mostly computing?) decides every tool choice in this chapter. Mostly waiting → one worker juggling (threads or async). Mostly computing → more workers (multiprocessing). If you remember nothing else, remember the barista.

Why this matters: concurrency bugs are some of the most expensive bugs in the industry, since they're intermittent, hard to reproduce, and often visible only under production load. And the most common performance mistake is reaching for the wrong tool (threads for CPU work in Python gets you nothing). Getting the model right saves you from both.

---

## Concurrency vs parallelism (say it precisely)

These get used interchangeably and they are not the same.

- **Concurrency** is about dealing with many things at once: structure. A concurrent program is composed of independently progressing tasks. They may be interleaved on a single core (run a bit of A, pause, run a bit of B), so at any instant only one is actually executing.
- **Parallelism** is about doing many things at once: execution. Truly simultaneous, requires multiple cores/CPUs.

Rob Pike's line is the one to keep: *"Concurrency is about dealing with lots of things at once. Parallelism is about doing lots of things at once."*

```text
CONCURRENT, not parallel (1 core, time-sliced):
core:  [A][B][A][B][A][B]        tasks interleave; one at a time

PARALLEL (2 cores):
core0: [A][A][A][A][A][A]        truly simultaneous
core1: [B][B][B][B][B][B]
```

Concurrency is a way to *structure* a program so parts can make progress independently; parallelism is a hardware-level *speedup* you get when those parts literally run at the same moment. You can have concurrency without parallelism (one core, async), and parallelism is one possible way to *run* a concurrent design. This distinction is why Python threads are useful for I/O but not for CPU.

## Processes vs threads, and context switching

- A **process** is a running program with its own private address space (its own heap, stack, code, file descriptors). Processes are isolated: one can't scribble on another's memory. Creating one is relatively heavy.
- A **thread** is a unit of execution inside a process. Threads of the same process share the process's address space (same heap, same globals) but each has its own stack and registers. Threads are lighter to create and switch between, and they can communicate trivially through shared memory, which is exactly what makes them dangerous (race conditions).

```text
PROCESS (isolated memory)            ONE PROCESS, TWO THREADS (shared memory)
┌────────────────────┐               ┌─────────────────────────────┐
│ code | data | heap │               │ code | data | HEAP (shared) │
│ stack              │               │ ┌─────────┐  ┌─────────┐    │
└────────────────────┘               │ │T1 stack │  │T2 stack │    │  ← separate stacks
                                      │ └─────────┘  └─────────┘    │     shared heap
                                      └─────────────────────────────┘
```

**Context switching** is the OS saving one execution context (registers, program counter, stack pointer) and loading another's so a different thread/process can run on the core. It's how one core gives the *illusion* of running many things at once. It isn't free: saving/restoring state and (for processes) flushing caches/TLB costs microseconds. Switching between *threads* of one process is cheaper than between *processes* because the address space (and much of the cache) stays put.

## Race conditions, critical sections, locks

When two threads share mutable state and at least one writes, you can get a **race condition**: the result depends on the unpredictable timing of who runs when. The classic example is `count += 1`, which looks atomic but isn't: it's read, add, write (three steps), and a switch between them can lose an update:

```text
count = 0
Thread A: read count (0) ──┐                  ┌── write 1
Thread B:          read count (0) ── add 1 ───┴── write 1
                                                    ↑ both wrote 1; one increment LOST
```

The chunk of code that touches shared state and must not be interleaved is the **critical section**. We protect it with **mutual exclusion**, a **lock/mutex**. A thread *acquires* the lock before the critical section and *releases* it after; while held, no other thread can acquire it, so they serialize through that section.

We'll reproduce a race and then fix it with a lock in the Build-it section; demonstration beats description here.

## Deadlock: the four conditions, and how to avoid it

Locks fix races but introduce a new failure: **deadlock**, where threads wait forever for each other. The textbook recipe is two threads grabbing two locks in opposite orders:

```text
Thread A: holds Lock1, waits for Lock2
Thread B: holds Lock2, waits for Lock1
→ neither can proceed; both blocked forever
```

Deadlock requires all four **Coffman conditions** simultaneously; break any one and you can't deadlock:

1. **Mutual exclusion**: resources are non-shareable (only one holder).
2. **Hold and wait**: a thread holds resources while waiting for more.
3. **No preemption**: resources can't be forcibly taken away; only voluntarily released.
4. **Circular wait**: a cycle of threads each waiting on the next.

**Avoidance strategies** map to breaking a condition:
- **Lock ordering** (most practical): always acquire locks in a fixed global order → breaks *circular wait*. If everyone grabs Lock1 before Lock2, no cycle can form.
- **Acquire all at once** (try-lock all or back off and retry) → breaks *hold and wait*.
- **Timeouts / try-acquire** so a thread gives up and releases → introduces a form of *preemption*.
- Use higher-level constructs (queues) that avoid hand-rolled multi-lock logic entirely.

## Deadlock deep dive: reproduce it, then fix it three ways

Reading about deadlock is one thing; watching your own program freeze and then un-freezing it is what makes it stick. Here's a classic two-account bank transfer that deadlocks, plus a step-by-step trace and three fixes.

### The setup that deadlocks

```text
Two transfers running at the same instant, grabbing locks in OPPOSITE orders:

  transfer(A → B):  lock(A) ✓ ........ wants lock(B) ⛔ (held by other thread)
  transfer(B → A):  lock(B) ✓ ........ wants lock(A) ⛔ (held by other thread)

  Timeline (the unlucky interleaving):
    t0  T1: acquire A          T2: acquire B
    t1  T1: try acquire B →    T2: try acquire A →
        BLOCKED                    BLOCKED
    t2  ... both wait forever. Circular wait formed: T1→B→T2→A→T1.
```

```python
# deadlock.py - RUN THIS; it hangs (Ctrl-C to kill). Then run the fix below.
import threading, time

class Account:
    def __init__(self, name, balance):
        self.name, self.balance = name, balance
        self.lock = threading.Lock()

def transfer_BAD(src, dst, amount):
    with src.lock:                      # grab SOURCE's lock first
        time.sleep(0.1)                 # force the bad interleaving to show up reliably
        with dst.lock:                  # then DESTINATION's lock
            src.balance -= amount
            dst.balance += amount

a = Account("A", 100)
b = Account("B", 100)

# Two threads transfer in opposite directions → opposite lock orders → deadlock.
t1 = threading.Thread(target=transfer_BAD, args=(a, b, 10))
t2 = threading.Thread(target=transfer_BAD, args=(b, a, 10))
t1.start(); t2.start()
t1.join(timeout=2); t2.join(timeout=2)
print("deadlocked!" if (t1.is_alive() or t2.is_alive()) else "completed")
```

Run it: it prints `deadlocked!` after the 2-second join timeout (the threads are still alive, frozen). That's the bug reproduced on demand.

### Fix 1 - lock ordering (breaks *circular wait*, the practical default)

Impose a global total order on locks and always acquire in that order. Use a stable key like `id()`:

```python
def transfer_ORDERED(src, dst, amount):
    # Always acquire the lower-id lock first, no matter the transfer direction.
    first, second = sorted((src, dst), key=lambda acct: id(acct.lock))
    with first.lock:
        with second.lock:
            src.balance -= amount
            dst.balance += amount
```

Now both transfers grab the same lock first, so no cycle can ever form. This is what real codebases do: pick a canonical ordering (by id, by name, by a fixed hierarchy) and enforce it everywhere two locks are held together.

### Fix 2 - try-acquire with timeout + backoff (breaks *no-preemption* / *hold-and-wait*)

If you can't impose a clean order, you can refuse to wait forever: grab the first lock, *try* the second with a timeout, and if it fails, release everything and retry. This guarantees progress (no permanent hold-and-wait).

```python
def transfer_TRYLOCK(src, dst, amount, retries=100):
    for _ in range(retries):
        if src.lock.acquire(timeout=0.05):
            try:
                if dst.lock.acquire(timeout=0.05):   # try, don't block forever
                    try:
                        src.balance -= amount
                        dst.balance += amount
                        return True
                    finally:
                        dst.lock.release()
            finally:
                src.lock.release()                   # always let go before retrying
        time.sleep(0.01)                             # back off so the other thread can win
    return False                                      # gave up
```

### Fix 3 - one big lock (breaks the need for two locks at all)

Sometimes the right answer is to not hold two locks: protect the whole transfer with a single global lock. Simpler, correct, but lower concurrency (all transfers serialize). The engineering judgment is *contention vs simplicity*.

```python
GLOBAL = threading.Lock()
def transfer_ONELOCK(src, dst, amount):
    with GLOBAL:
        src.balance -= amount
        dst.balance += amount
```

Which to reach for? Lock ordering is the default: it keeps concurrency high and provably can't deadlock. Try-lock/backoff suits cases where you can't enumerate a clean order (dynamic resource sets). One big lock is fine when the critical section is short and contention is low. All three break at least one Coffman condition; that's the unifying principle.

## Semaphores and condition variables

A **lock/mutex** allows exactly one holder. Sometimes you want more nuance:

- A **semaphore** is a counter-based gate that allows up to N holders at once. `acquire()` decrements (blocks at 0); `release()` increments. A semaphore initialized to N=1 is essentially a lock (a *binary* semaphore). Use it to cap concurrency, e.g., "at most 5 threads hit this API at once."

  ```python
  import threading
  sem = threading.Semaphore(3)   # at most 3 concurrent holders
  def worker():
      with sem:                  # acquire on enter, release on exit
          do_limited_work()
  ```

- A **condition variable** lets threads wait for a state change and be notified when it happens, instead of busy-looping. A producer changes shared state and calls `notify()`; consumers `wait()` (releasing the lock while asleep) until woken. This is the backbone of producer/consumer.

  ```python
  cond = threading.Condition()
  # consumer:                          # producer:
  with cond:                           with cond:
      while not ready():                   make_ready()
          cond.wait()                      cond.notify()
      consume()
  ```

The `while`-not-`if` around `wait()` matters: spurious wake-ups and multiple consumers mean you must re-check the condition after waking.

## The GIL: what it actually is

Now for what makes Python concurrency special. CPython has a **Global Interpreter Lock (GIL)**, a single mutex that protects access to Python objects, ensuring only **one thread executes Python bytecode at a time** within a process. It exists because CPython's memory management (reference counting from the last chapter) isn't thread-safe; the GIL makes refcount updates safe without per-object locks, and keeps the interpreter simple and single-threaded-fast.

Consequences to internalize:

- **Threads give you no CPU parallelism for pure-Python code in CPython.** Two threads doing number-crunching won't run Python bytecode simultaneously; the GIL serializes them. You can even go slower than single-threaded due to lock contention and switching.
- **Threads still help for I/O-bound work.** When a thread blocks on I/O (network, disk), it releases the GIL, letting another thread run. So while one thread waits on a socket, others make progress. For "fetch 100 URLs," threads are great: the waiting overlaps.
- **C extensions can release the GIL** during heavy computation (NumPy, hashing, compression often do), so those can use multiple cores even from threads.
- **To parallelize CPU-bound Python, use multiple processes** (`multiprocessing`): each process has its own interpreter and its own GIL, so they run truly in parallel on separate cores.

The decision tree that resolves 90% of choices:

```text
Is the work I/O-bound (waiting on network/disk)?
   → threads or async/await   (overlap the waiting; GIL released during I/O)
Is the work CPU-bound (crunching numbers in pure Python)?
   → multiprocessing          (separate processes = separate GILs = real parallelism)
```

(Note: "free-threaded" / no-GIL CPython builds are arriving experimentally, but the mental model above is what to reason from today.)

## async/await and the event loop: cooperative scheduling

Threads use **preemptive** scheduling: the OS can pause a thread anywhere. `async/await` uses **cooperative** scheduling: tasks run on a single thread and voluntarily yield control at `await` points, where they'd otherwise be waiting on I/O.

The engine is the **event loop**: a single loop that runs ready tasks until they hit an `await` on something not-ready (a socket with no data yet). At that point the task says "wake me when this is ready" and yields; the loop runs another ready task. When the I/O completes, the loop resumes the parked task. No threads, no GIL contention, no locks needed *between coroutines* (because only one runs at a time and switches happen only at explicit `await` points, so there's no mid-operation interleaving).

```text
EVENT LOOP (1 thread):
  run TaskA ─ await(socket) ─► park A, run TaskB ─ await(socket) ─► park B,
  run TaskC ─ await(socket) ─► park C ... socket A ready ─► resume A ... etc.
```

- A **coroutine** is a function defined with `async def`; calling it returns a coroutine object that does nothing until awaited/scheduled.
- `await x` means "suspend me until x is ready; meanwhile run other tasks."

**When async wins:** massive I/O concurrency (thousands of simultaneous sockets) with low per-task memory, each task is cheap (no OS thread, no separate stack of MBs). Threads have higher per-task overhead, so 10,000 threads is painful but 10,000 coroutines is fine. **When async loses:** CPU-bound work (a coroutine that crunches numbers never yields and starves the loop), and it requires async all the way down (a blocking library call freezes the whole loop).

## Thread pools and `concurrent.futures`: stop hand-rolling threads

Spawning raw `threading.Thread`s by hand is fine for a demo but wrong for real code: you re-create the thread every time (expensive), you have no natural cap on concurrency, and collecting results is fiddly. The professional tool is a **pool**, a fixed set of reusable worker threads (or processes) fed by an internal queue. `concurrent.futures` gives a clean, uniform API over both.

```text
ThreadPoolExecutor(max_workers=4):

   submit(task) ─► [ internal work queue ]
                          │  │  │
                    ┌─────┘  │  └─────┐
                  worker0  worker1  worker2  worker3   ← 4 reusable threads
                    │        │        │        │
                    └──────► each returns a Future ◄───┘
                            (a handle to a result that isn't ready yet)
```

A **`Future`** is a promise: a handle you get *immediately* when you submit work, which later carries the result (or the exception). You ask it for `.result()` (blocks until ready) or iterate completed ones as they finish.

```python
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor, as_completed
import time

def fetch_size(url):                      # pretend-I/O: sleep stands in for a network wait
    time.sleep(0.5)
    return url, len(url) * 100

URLS = [f"https://site{i}.example" for i in range(12)]

# --- map: simplest, preserves input order, great when you just want all results ---
with ThreadPoolExecutor(max_workers=4) as pool:
    for url, size in pool.map(fetch_size, URLS):     # 12 tasks, 4 at a time
        pass
# the `with` block joins all workers on exit - no manual .join()

# --- submit + as_completed: process results in COMPLETION order (fastest-first) ---
with ThreadPoolExecutor(max_workers=4) as pool:
    futures = {pool.submit(fetch_size, u): u for u in URLS}
    for fut in as_completed(futures):                 # yields each as it finishes
        url, size = fut.result()                      # re-raises any exception here
```

Two patterns to know cold:
- **`executor.map(fn, iterable)`**, like `map`, but parallel. Results come back in **input order**. Use when you want everything and order matters.
- **`submit` + `as_completed`**, fire off tasks, then handle each **as soon as it finishes** (completion order). Use when you want to react to the fastest results first, or show progress.

The best part: switching between threads and processes is one word. `ThreadPoolExecutor` (I/O-bound, GIL released during I/O) and `ProcessPoolExecutor` (CPU-bound, real parallelism) share the exact same API. So you can write the logic once and pick the executor based on whether the work waits or computes:

```python
# CPU-bound? Swap one class name - same .map / .submit / as_completed code.
with ProcessPoolExecutor() as pool:       # separate processes = separate GILs = real cores
    results = list(pool.map(heavy_cpu_fn, work_items))
```

**Gotchas:** exceptions inside a worker are stored in the Future and only re-raised when you call `.result()` (or iterate `map`), silent until you look. And `max_workers` is a real tuning knob: too few underutilizes I/O concurrency; too many wastes memory and thrashes. For I/O-bound work you can go well above core count (dozens-hundreds); for CPU-bound, cap near the core count.

## asyncio deep dive: the event loop, gather vs as_completed, async context managers

Time to open the async box. The whole system is one **event loop** running on one thread, plus a set of **tasks** (wrapped coroutines) and a way to know when I/O is ready.

### What the event loop actually does, step by step

```text
THE EVENT LOOP (a single thread running this loop forever):

  ┌─────────────────────────────────────────────────────────────┐
  │ 1. Run every READY task until it hits `await something`.     │
  │ 2. When a task awaits not-ready I/O, it registers interest   │
  │    ("wake me when this socket is readable") and YIELDS.      │
  │ 3. Once no task is ready, the loop calls the OS selector     │
  │    (epoll/kqueue): "sleep until ANY registered fd is ready." │
  │ 4. The OS wakes the loop when an fd is ready; the loop marks  │
  │    the matching task READY again.                            │
  │ 5. Go to 1.                                                  │
  └─────────────────────────────────────────────────────────────┘
```

The key machinery is the **selector** (`select`/`epoll`/`kqueue`), a single OS call that says "watch these 10,000 file descriptors and wake me when *any* becomes ready." That's how one thread babysits thousands of sockets: it's not polling each one; the OS notifies it. A coroutine's `await` is the point where it hands a "wake condition" to the loop and steps aside.

Two consequences that explain async's whole personality:
- **Switches happen only at `await`.** Between two `await`s your code runs atomically with respect to other coroutines (no preemption), so no locks are needed between coroutines for ordinary in-memory state. (You still need `asyncio.Lock` to guard a critical section that *spans* an `await`.)
- **One blocking call freezes everyone.** A `time.sleep(5)` or a synchronous `requests.get` doesn't yield, so the loop can't run any other task for 5 seconds. The benefit (overlapping waits) collapses. Use `await asyncio.sleep`, an async client, or push blocking work to a thread via `asyncio.to_thread`.

### Tasks vs coroutines vs gather

A bare coroutine does nothing until it's scheduled. `asyncio.create_task(coro)` wraps it in a **Task** and hands it to the loop to run concurrently *right now*. `await`ing a coroutine directly runs it sequentially; wrapping in tasks (or `gather`) is what makes things overlap.

```python
import asyncio, time

async def work(name, secs):
    print(f"  {name} start")
    await asyncio.sleep(secs)        # yields the loop while "waiting"
    print(f"  {name} done in {secs}s")
    return name, secs

async def sequential():             # NO overlap - each await blocks the next start
    await work("A", 1); await work("B", 1); await work("C", 1)   # ~3s total

async def concurrent_gather():      # overlap via gather → ~1s total
    return await asyncio.gather(work("A", 1), work("B", 1), work("C", 1))
```

### `gather` vs `as_completed`: order and failure behavior

Both run coroutines concurrently; they differ in when you get results and what happens on error.

```text
gather(*coros):
  • returns a LIST of results in the SAME ORDER as the inputs
  • waits for ALL to finish before returning
  • by default, the first exception CANCELS the gather and propagates
    (use return_exceptions=True to collect errors as values instead)

as_completed(coros):
  • yields each result AS SOON AS it finishes (completion order, fastest-first)
  • lets you react to / display results incrementally (progress bars, streaming)
```

```python
async def demo_gather():
    # results come back in input order [A, B, C] even though C finishes first
    results = await asyncio.gather(work("A", 3), work("B", 2), work("C", 1))
    print("gather (input order):", [r[0] for r in results])

async def demo_as_completed():
    # prints C, then B, then A - completion order
    for fut in asyncio.as_completed([work("A", 3), work("B", 2), work("C", 1)]):
        name, secs = await fut
        print(f"as_completed got {name} (took {secs}s)")

# Robust gather: don't let one failure nuke the batch
async def robust():
    results = await asyncio.gather(work("A",1), might_fail(), return_exceptions=True)
    for r in results:
        if isinstance(r, Exception):
            print("one task failed:", r)     # handle, don't crash the whole gather
```

### Async context managers and `async with` / `async for`

`with` and `for` have async twins for resources whose *setup/teardown or iteration* involves I/O. `async with` calls `__aenter__`/`__aexit__` (which can `await`); `async for` calls `__anext__` (which can `await`), perfect for streaming results that arrive over time.

```python
class AsyncResource:                 # e.g., a DB connection or HTTP session
    async def __aenter__(self):
        await asyncio.sleep(0.1)     # "connect" - an awaitable setup
        print("  opened"); return self
    async def __aexit__(self, *exc):
        await asyncio.sleep(0.1)     # "close" - awaitable teardown
        print("  closed")
    async def stream(self):          # an async generator
        for i in range(3):
            await asyncio.sleep(0.1) # each item arrives after some I/O
            yield i

async def use_it():
    async with AsyncResource() as r:        # awaitable open/close, guaranteed cleanup
        async for item in r.stream():        # awaitable iteration
            print("  got", item)
```

This is exactly the shape of `aiohttp.ClientSession` (`async with`) and streaming responses (`async for`). The mental model: anywhere a synchronous resource would *block* on I/O during enter/exit/iteration, the async version *awaits* instead, keeping the loop free.

### `asyncio.to_thread`: escaping blocking code without freezing the loop

When you must call a blocking function (a legacy library, CPU-light blocking I/O), offload it to a thread so the loop keeps running:

```python
async def main():
    # runs blocking_fn in a worker thread; awaits its result without blocking the loop
    result = await asyncio.to_thread(blocking_fn, arg1, arg2)
```

For CPU-bound work the analogous escape is `loop.run_in_executor(ProcessPoolExecutor(), ...)`: push the crunching to a separate process so the GIL and the loop both stay unblocked.

## Common mistakes

Concurrency mistakes are subtle because the code often *looks* right and only breaks intermittently. Here are the ones that get everyone.

- **Using threads to speed up CPU-bound Python.** The GIL means it won't help, and contention can make it *slower* than single-threaded. CPU-bound → `multiprocessing` (or a C extension that releases the GIL, like NumPy).
- **Assuming `count += 1` is atomic.** It's read-modify-write. The GIL does not make it safe across threads; a switch can land between the read and the write. Always guard shared mutable state with a lock.
- **`if` instead of `while` around `cond.wait()`.** Spurious wake-ups and multiple consumers mean the condition can be false again by the time you wake. Re-check in a loop, always.
- **Inconsistent lock ordering.** Two code paths grab `L1` then `L2`, a third grabs `L2` then `L1` → eventual deadlock under load. Pick a global order and enforce it everywhere.
- **Forgetting `if __name__ == "__main__":` with `multiprocessing`.** On macOS/Windows (spawn start method), child processes re-import your module; without the guard they re-run your top-level code and you get a fork bomb of recursive process creation.
- **A blocking call inside async code.** `time.sleep(5)` (not `await asyncio.sleep(5)`), or a synchronous `requests.get`, freezes the entire event loop: every other coroutine stalls. Use the async equivalent, or push the blocking work to `loop.run_in_executor`/`asyncio.to_thread`.
- **Forgetting to `join()` (threads) or `await`/`gather` (coroutines).** Work you never wait for may not finish before the program exits, and you'll silently lose results.
- **Sharing a mutable object across processes expecting writes to propagate.** Processes have separate memory; a child mutating a copy doesn't change the parent's. Use `multiprocessing.Queue`, `Pipe`, or shared memory explicitly.

- **On the job:** real systems are concurrent by default: web servers handle many requests at once, background workers process queues, services call other services. The bugs you'll actually chase are deadlocks under load, data races corrupting shared state, and "why is our CPU-bound endpoint not getting faster with more threads?" The debugging instinct (is this I/O- or CPU-bound? is this shared state protected?) is a daily-use skill, not trivia.
- **Concurrency-safe data structures** (`queue.Queue`, `concurrent.futures.ThreadPoolExecutor`/`ProcessPoolExecutor`) are what you'll actually reach for in production rather than hand-rolling locks. Knowing they exist and when to use them signals maturity.

**Real questions with model answers** (rehearse these):

- **Q: "Your image-processing endpoint takes 8 seconds for 8 images. You add a `ThreadPoolExecutor` with 8 workers and it's still 8 seconds. Then you switch to `ProcessPoolExecutor` and it drops to ~1 second. Explain."**
  *Model answer:* "Image processing in pure Python is CPU-bound. The GIL lets only one thread execute Python bytecode at a time, so 8 threads still serialize through the interpreter: no speedup. A `ProcessPoolExecutor` runs 8 *processes*, each with its own interpreter and its own GIL, so they truly run in parallel on 8 cores, hence the ~8x drop. The fix worked because the bottleneck was computation, not waiting; for CPU-bound work you need separate processes (or a C extension like Pillow/NumPy that releases the GIL internally)."

- **Q: "What's the difference between `asyncio.gather` and `asyncio.as_completed`, and when would you pick each?"**
  *Model answer:* "Both run coroutines concurrently. `gather` returns all results in *input order* and waits for everything to finish; by default the first exception cancels the whole group, though `return_exceptions=True` collects errors as values. `as_completed` yields each result as soon as it finishes: completion order, fastest-first. I use `gather` when I need all results together and order matters; I use `as_completed` when I want to react incrementally: a progress bar, streaming partial results, or returning the first acceptable answer early."

- **Q: "You await ten coroutines but only want at most three hitting the API at once. How?"**
  *Model answer:* "Wrap each coroutine's network call in `async with asyncio.Semaphore(3)`. The semaphore admits only three holders; the rest await at the `async with` until a slot frees. You still `gather` all ten so they're all scheduled, but the semaphore throttles actual concurrency: clean back-pressure without changing the gather structure."

- **Q: "A coroutine in your async server occasionally makes everything else hang for a second. What's the likely cause?"**
  *Model answer:* "A blocking call inside async code: a synchronous `requests.get`, a `time.sleep`, or a CPU-heavy loop that never `await`s. Since the event loop is one thread and only switches at `await`, anything that doesn't yield freezes every other task for its whole duration. The fix is to use an async equivalent, or offload the blocking/CPU work with `asyncio.to_thread` (blocking I/O) or `run_in_executor` with a process pool (CPU)."

- **Q: "Two threads each increment their own counter, no shared state, no locks, yet it's slow. Why?"**
  *Model answer:* "Likely *false sharing*: the two counters sit in the same 64-byte cache line, so when one core writes its counter it invalidates the other core's copy of the whole line, forcing a re-fetch. The cores ping-pong the line via the cache-coherence protocol even though the data is logically independent. The fix is padding so each counter lands on its own cache line."

- **Q: "Reproduce a deadlock in words, then tell me your default fix."**
  *Model answer:* "Two threads, two locks, opposite acquisition orders: T1 holds A and waits for B; T2 holds B and waits for A, a circular wait, frozen forever. My default fix is *lock ordering*: impose a global total order (e.g., by object id) and always acquire in that order, so no cycle can form. That breaks the circular-wait Coffman condition while keeping concurrency high. Alternatives are try-lock-with-timeout-and-backoff or collapsing to a single lock."

## Build it: a race + its fix; async URL fetch; multiprocessing speedup

### 1. A real race condition, then fixed with a lock

```python
# race.py
import threading

# --- BROKEN: unsynchronized shared counter ---
counter = 0
def increment_unsafe(n):
    global counter
    for _ in range(n):
        counter += 1          # read-modify-write: NOT atomic → race

threads = [threading.Thread(target=increment_unsafe, args=(100_000,)) for _ in range(8)]
for t in threads: t.start()
for t in threads: t.join()
print("unsafe  counter:", counter, "(expected 800000) - usually WRONG")

# --- FIXED: protect the critical section with a lock ---
counter = 0
lock = threading.Lock()
def increment_safe(n):
    global counter
    for _ in range(n):
        with lock:            # only one thread in the critical section at a time
            counter += 1

threads = [threading.Thread(target=increment_safe, args=(100_000,)) for _ in range(8)]
for t in threads: t.start()
for t in threads: t.join()
print("safe    counter:", counter, "(expected 800000) - always correct")
```

The unsafe version usually prints something less than 800000: lost updates you can watch happen live. The locked version is always exactly right. (This also shows the GIL doesn't make `+=` atomic: the GIL can be released between the read and the write of a single `+=`.)

### 2. async fetching many URLs concurrently

```python
# async_fetch.py   (pip install aiohttp)
import asyncio, time
import aiohttp

URLS = ["https://example.com"] * 20

async def fetch(session, url):
    async with session.get(url) as resp:
        return len(await resp.text())     # await yields control while waiting on the network

async def main():
    async with aiohttp.ClientSession() as session:
        start = time.perf_counter()
        # gather schedules all coroutines on the loop; they overlap their waiting
        sizes = await asyncio.gather(*(fetch(session, u) for u in URLS))
        print(f"async fetched {len(sizes)} urls in {time.perf_counter()-start:.2f}s")

asyncio.run(main())
```

All 20 requests are in flight "at once" on a single thread: the loop runs whichever is ready while the others wait on the network.

### 3. multiprocessing CPU-bound speedup

```python
# mp_speedup.py
import time
from multiprocessing import Pool

def heavy(n):                              # pure-Python CPU work
    return sum(i * i for i in range(n))

WORK = [10_000_000] * 8

if __name__ == "__main__":                 # required guard on Windows/macOS spawn
    start = time.perf_counter()
    [heavy(n) for n in WORK]               # serial
    serial = time.perf_counter() - start

    start = time.perf_counter()
    with Pool() as pool:                   # one process per core, each with its own GIL
        pool.map(heavy, WORK)
    parallel = time.perf_counter() - start

    print(f"serial:   {serial:.2f}s")
    print(f"parallel: {parallel:.2f}s  ({serial/parallel:.1f}x speedup)")
```

On a multi-core machine the pool version is several times faster: this is real parallelism, because each process sidesteps the GIL. Try the same job with `threading` instead and you'll get **no** speedup (often a slowdown): the proof that threads can't parallelize CPU-bound Python.

## Mini-project: concurrent web-fetcher - sequential vs threads vs async

One script, three strategies, same workload, timed. This is the experiment that ties the whole chapter together.

```python
# fetcher_benchmark.py
import time, urllib.request
import threading
import asyncio

URLS = ["https://example.com"] * 30   # I/O-bound: each request mostly WAITS on the network

# ---------- 1. SEQUENTIAL ----------
def fetch_sync(url):
    with urllib.request.urlopen(url, timeout=10) as r:
        return len(r.read())

def run_sequential():
    start = time.perf_counter()
    for u in URLS:
        fetch_sync(u)
    return time.perf_counter() - start

# ---------- 2. THREADS ----------
def run_threads():
    start = time.perf_counter()
    results = [None] * len(URLS)
    def worker(i, url):
        results[i] = fetch_sync(url)      # blocks on I/O → releases GIL → others run
    threads = [threading.Thread(target=worker, args=(i, u)) for i, u in enumerate(URLS)]
    for t in threads: t.start()
    for t in threads: t.join()
    return time.perf_counter() - start

# ---------- 3. ASYNC ----------
async def fetch_async(session, url):
    async with session.get(url) as resp:
        return len(await resp.text())

async def _async_main():
    import aiohttp
    async with aiohttp.ClientSession() as session:
        await asyncio.gather(*(fetch_async(session, u) for u in URLS))

def run_async():
    start = time.perf_counter()
    asyncio.run(_async_main())
    return time.perf_counter() - start

if __name__ == "__main__":
    print(f"Fetching {len(URLS)} URLs three ways:\n")
    s = run_sequential(); print(f"  sequential : {s:6.2f}s   (baseline)")
    t = run_threads();    print(f"  threads    : {t:6.2f}s   ({s/t:.1f}x faster)")
    try:
        a = run_async();  print(f"  async      : {a:6.2f}s   ({s/a:.1f}x faster)")
    except ImportError:
        print("  async      : (install aiohttp to run)")

    print("""
WHY:
  sequential  = sum of all the waiting; each request's latency adds up.
  threads     = the WAITING overlaps. While one thread blocks on the socket
                it releases the GIL, so others fly. Big win for I/O-bound work.
  async       = same overlap, but on ONE thread via the event loop. Lower
                per-task overhead, so it scales to MANY more concurrent requests.
  (If this were CPU-bound, threads & async would NOT help - you'd need
   multiprocessing for real parallelism.)""")
```

Expected shape of results: sequential is slowest (latencies add up). Threads and async are both dramatically faster and roughly comparable here, because the bottleneck is *waiting on the network*, and both overlap that waiting. The distinguishing factor only shows at scale: push toward thousands of concurrent connections and async's lightweight tasks pull ahead of threads' heavier OS-thread overhead. And critically, if you swapped the URL fetch for a pure-Python CPU loop, *both* would flatten to sequential speed, and only `multiprocessing` would help. That contrast is the entire chapter in one benchmark.

## Mini-project: a thread-safe producer/consumer pipeline with a bounded queue

The race-and-lock demo shows the *problem* with shared state. This project shows the *professional solution*: instead of hand-rolling locks, use a thread-safe `queue.Queue` as the channel between producers and consumers. This is the pattern behind every job-processing system you'll ever build (web request queues, background workers, ETL pipelines).

```python
# pipeline.py - N producers feed a bounded queue; M consumers drain it. No manual locks.
import threading, queue, time, random

WORK_QUEUE = queue.Queue(maxsize=10)   # BOUNDED: blocks producers when full (back-pressure)
RESULTS = queue.Queue()                # thread-safe place to collect outputs
SENTINEL = object()                    # a unique "no more work" marker

def producer(pid, n_items):
    for i in range(n_items):
        item = (pid, i)
        WORK_QUEUE.put(item)           # blocks if the queue is full → natural back-pressure
        print(f"  producer {pid} queued {item}")
        time.sleep(random.uniform(0, 0.05))
    print(f"producer {pid} done")

def consumer(cid):
    while True:
        item = WORK_QUEUE.get()        # blocks until something is available
        if item is SENTINEL:           # shutdown signal
            WORK_QUEUE.task_done()
            break
        pid, i = item
        result = (pid, i, i * i)       # "process" the item
        RESULTS.put(result)
        WORK_QUEUE.task_done()         # tell the queue this item is fully handled
    print(f"consumer {cid} exiting")

def main(n_producers=3, n_consumers=4, items_each=5):
    producers = [threading.Thread(target=producer, args=(p, items_each))
                 for p in range(n_producers)]
    consumers = [threading.Thread(target=consumer, args=(c,))
                 for c in range(n_consumers)]
    for t in producers + consumers:
        t.start()
    for t in producers:
        t.join()                       # wait for all producers to finish enqueuing
    WORK_QUEUE.join()                  # wait until every queued item is task_done()'d
    for _ in consumers:                # now send one sentinel per consumer to stop them
        WORK_QUEUE.put(SENTINEL)
    for t in consumers:
        t.join()
    total = RESULTS.qsize()
    print(f"\nprocessed {total} items (expected {n_producers * items_each})")

if __name__ == "__main__":
    main()
```

Why this is the *right* way, and what each piece teaches:

- **`queue.Queue` is internally synchronized**, `put`/`get` are atomic and thread-safe. You never write a single `Lock` yourself, yet there are zero races. The lesson: *prefer a concurrency-safe data structure over hand-rolled locking.*
- **`maxsize=10` gives back-pressure.** If consumers fall behind, the queue fills and producers *block* on `put` instead of building an unbounded backlog that eats all memory. This is how real systems avoid being overwhelmed.
- **The sentinel pattern** is the clean way to shut down workers: one poison-pill per consumer so each wakes from its blocking `get`, sees "stop," and exits. No flags, no polling.
- **`task_done()` + `queue.join()`** let the main thread wait for *all work to be fully processed*, not just enqueued, the difference between "I handed out the work" and "the work is finished."

**Extension:** swap `threading` for `concurrent.futures.ThreadPoolExecutor` and `executor.map`, the same pipeline in a third of the lines, and reason about what the executor is doing for you (managing the pool, the queue, and the joins).

## Mini-project: an async web crawler with a bounded semaphore

This is the capstone async project, a real, respectful crawler that fetches a frontier of URLs, extracts links, and crawls outward **breadth-first**, but never hammers a server with more than N simultaneous requests. It ties together: the event loop, `gather`, `async with`, a `Semaphore` for concurrency limiting, and a visited-set to avoid re-crawling. (Uses `aiohttp`; falls back to a simulated fetcher if it's not installed, so you can run the *logic* offline.)

```python
# async_crawler.py   (pip install aiohttp  - or run as-is to use the offline simulator)
import asyncio, re, time

MAX_CONCURRENCY = 5          # the semaphore cap: at most 5 in-flight requests at once
MAX_PAGES       = 30         # stop after this many pages (don't crawl the whole web)

try:
    import aiohttp
    HAVE_AIOHTTP = True
except ImportError:
    HAVE_AIOHTTP = False

LINK_RE = re.compile(r'href="(https?://[^"]+)"')

class Crawler:
    def __init__(self, start_url, max_pages=MAX_PAGES, concurrency=MAX_CONCURRENCY):
        self.start_url   = start_url
        self.max_pages   = max_pages
        self.visited     = set()                       # de-dupe: never crawl a URL twice
        self.sem         = asyncio.Semaphore(concurrency)  # the back-pressure valve
        self.results     = []                          # (url, n_links) per crawled page

    async def fetch(self, session, url):
        # The semaphore caps concurrency: only `concurrency` coroutines hold it at once;
        # the rest AWAIT here until a slot frees - polite, bounded load on the server.
        async with self.sem:
            try:
                if HAVE_AIOHTTP:
                    async with session.get(url, timeout=10) as resp:   # async with = awaitable open/close
                        return await resp.text()
                else:
                    await asyncio.sleep(0.1)                            # simulate network latency
                    return f'<a href="{url}/a">x</a><a href="{url}/b">y</a>'
            except Exception as e:
                print(f"  ! failed {url}: {e}")
                return ""

    async def crawl(self):
        session = aiohttp.ClientSession() if HAVE_AIOHTTP else None
        try:
            frontier = [self.start_url]
            while frontier and len(self.visited) < self.max_pages:
                # take a batch of not-yet-visited URLs from the frontier
                batch = []
                for url in frontier:
                    if url not in self.visited and len(self.visited) + len(batch) < self.max_pages:
                        self.visited.add(url)
                        batch.append(url)
                # fetch the WHOLE BATCH concurrently - gather overlaps all the waits,
                # but the semaphore still caps simultaneous requests at MAX_CONCURRENCY
                pages = await asyncio.gather(*(self.fetch(session, u) for u in batch))

                next_frontier = []
                for url, html in zip(batch, pages):
                    links = LINK_RE.findall(html)
                    self.results.append((url, len(links)))
                    print(f"  crawled {url}  ({len(links)} links)")
                    next_frontier.extend(links)
                frontier = next_frontier
        finally:
            if session:
                await session.close()                  # always release the connection pool

async def main():
    start = "https://example.com"
    crawler = Crawler(start)
    t0 = time.perf_counter()
    await crawler.crawl()
    print(f"\ncrawled {len(crawler.visited)} pages in {time.perf_counter()-t0:.2f}s "
          f"(max {MAX_CONCURRENCY} concurrent, offline-sim={'no' if HAVE_AIOHTTP else 'yes'})")

if __name__ == "__main__":
    asyncio.run(main())
```

Why each piece matters, and what it teaches:

- **`asyncio.Semaphore(N)`** is the star. It's the async version of "at most N baristas." Without it, `gather`-ing a thousand URLs would open a thousand sockets at once, overwhelming the server and probably getting you rate-limited or banned. The `async with self.sem` makes excess coroutines *wait their turn* for a slot. This is the single most important pattern for a well-behaved network client.
- **`gather` per batch** overlaps all the waiting within a breadth-first level, that's where the speedup over a sequential crawler comes from.
- **The `visited` set** prevents infinite re-crawling and cycles in the link graph, the same de-duplication every BFS needs.
- **`async with session`** ties resource lifetime (the connection pool) to a scope, and the `finally: await session.close()` guarantees cleanup even on error, the async-context-manager discipline from the deep dive, applied for real.
- **The offline simulator** means you can run and reason about the *concurrency logic* without a network, a nice way to test the structure deterministically.

**Extensions:** (1) cap by *domain* with a dict of per-host semaphores so you're polite per-server. (2) Add a global timeout with `asyncio.wait_for`. (3) Swap `gather` for `as_completed` and print results fastest-first with a live progress count. (4) Add a `ProcessPoolExecutor` via `run_in_executor` to parse huge HTML pages off the event loop (CPU work shouldn't block the loop).

### Solutions

1. **Concurrency** = structuring a program as independently progressing tasks that may be interleaved (dealing with many things at once). **Parallelism** = literally executing multiple tasks at the same instant on multiple cores (doing many things at once). Concurrency without parallelism: one barista taking multiple orders by switching between them during waits, only one is ever acting at a time, but many orders progress.

2. **Shared:** the heap, global variables, code/text segment, open file descriptors. **Per-thread:** its own stack, its own registers (including the program counter and stack pointer), and its thread-local storage.

3. A process needs its own private address space, the OS must set up a new page table, copy/duplicate memory mappings, file descriptor tables, etc. A thread reuses the existing process's address space and just needs a new stack and register set, so it's far lighter to create and to context-switch (no address-space/TLB flush).

4. `+=` is three steps: read `counter`, add 1, write back. Interleaving that loses an update: Thread A reads `counter=5`; the OS switches; Thread B reads `counter=5`, adds 1, writes `6`; switches back; Thread A (still holding its stale `5`) adds 1, writes `6`. Two increments happened but the value rose by only 1: one update was lost. Across 800,000 such operations, many are lost, so the total is short. A lock around the whole read-modify-write makes it a single uninterruptible critical section.

5. The work is **CPU-bound** and it's **pure Python**, so the **GIL** serializes the threads, only one executes bytecode at a time, and you even pay lock-contention/switching overhead, hence "same or slower." Fix: use **`multiprocessing`** (each process has its own interpreter and GIL, so they run truly in parallel on separate cores), or push the hot loop into a C extension/NumPy that releases the GIL.

6. **Mutual exclusion** → make resources shareable where possible (e.g., read-only data, copies). **Hold-and-wait** → acquire all needed locks at once (all-or-nothing) so you never hold one while waiting for another. **No preemption** → use timeouts/try-acquire so a thread gives up and releases what it holds. **Circular wait** → impose a global lock-ordering so no cycle can form (the most practical fix).

7. Deadlock interleaving: `transfer()` does `acquire(accounts_lock)` then waits for `audit_lock`; concurrently `report()` does `acquire(audit_lock)` then waits for `accounts_lock`. Each holds what the other needs → frozen forever. Fix: enforce a global order, *both* functions acquire `accounts_lock` **then** `audit_lock`, regardless of what they're doing:
   ```python
   def safe(op):
       with accounts_lock:        # always accounts FIRST
           with audit_lock:       # then audit
               op()
   ```
   With a single consistent order, no cycle can form, so no deadlock.

8. `wait()` releases the lock and sleeps; when notified (or spuriously woken), it re-acquires the lock and returns, but by then *another* consumer may have already taken the item, or the wake may have been spurious, so the condition can be false again. With `if`, you'd proceed assuming the condition holds and process a non-existent item (or crash). With `while`, you re-check and go back to sleep if it's still not satisfied. Breaking scenario: two consumers both `wait()`; producer adds *one* item and `notify_all()`s; both wake; the first consumes the item; the second, under `if`, also tries to consume, but the queue is empty → error/garbage. `while` saves the second by re-checking.

9. **asyncio.** 50,000 OS threads at, say, ~1 MB of stack each is ~50 GB of memory just for stacks, plus enormous context-switch and scheduling overhead: completely impractical. 50,000 coroutines are cheap heap objects (kilobytes each), all multiplexed on one thread by the event loop; idle connections cost almost nothing because a parked coroutine isn't a thread. This is the canonical case where async's low per-task overhead wins decisively.

10. **`gather`** returns results in *input order* and waits for *all* coroutines to finish; by default the first exception cancels the group and propagates (use `return_exceptions=True` to collect errors as values). **`as_completed`** yields each result *as soon as it finishes*, completion order, fastest-first. A concrete need for `as_completed`: a "first good answer wins" race, query three replica servers for the same data and use whichever responds first, cancelling the rest; or a progress bar that updates as each of N downloads completes rather than only at the very end.

11.
   ```python
   import asyncio
   sem = asyncio.Semaphore(10)              # at most 10 in flight
   async def fetch(session, url):
       async with sem:                       # throttle HERE, per request
           async with session.get(url) as r:
               return await r.text()
   async def main(urls, session):
       return await asyncio.gather(*(fetch(session, u) for u in urls))
   ```
   The semaphore must wrap the actual network call *inside* each coroutine because `gather` schedules all 1,000 coroutines at once, if the semaphore were around `gather`, it would gate the *scheduling* (which is cheap and instant), not the *concurrent requests*. Placed inside `fetch`, only 10 coroutines can hold a slot and be mid-request at any moment; the other 990 are awaiting their turn at `async with sem`. That's true request-level back-pressure.

12. Prediction: serial = baseline; **threading ≈ same as serial or slightly worse** (GIL serializes CPU-bound bytecode + adds contention); **multiprocessing ≈ N× faster** (up to core count). Running confirms it. Explanation: threads can't execute Python bytecode in parallel (GIL), so for CPU work they don't help; separate processes have separate GILs, so they achieve real parallelism. The fourth variant, `ProcessPoolExecutor().map(heavy, WORK)`, matches `multiprocessing.Pool` because *both* spawn worker processes with independent interpreters, they're two front-ends over the same idea. The choice is API taste: `concurrent.futures` gives you the uniform `Executor`/`Future`/`as_completed` interface (and an easy thread↔process swap), while `multiprocessing.Pool` has a slightly lower-level, older API. Same parallelism, same GIL-sidestep, different ergonomics.

## Teach it back

1. **State the concurrency-vs-parallelism distinction in one precise sentence each.** Concurrency is *structuring* a program as independently progressing tasks that may be interleaved (dealing with many things at once); parallelism is *executing* multiple tasks literally simultaneously on multiple cores (doing many things at once). You can have concurrency without parallelism (async on one core).

2. **Why is `count += 1` a race condition across threads, and how does a lock fix it?** `+=` is read-modify-write, three non-atomic steps; a context switch between read and write lets two threads both read the old value and both write the same increment, losing one. A lock makes the whole read-modify-write a critical section that only one thread enters at a time, serializing access.

3. **List the four Coffman conditions and name the most practical one to break.** Mutual exclusion, hold-and-wait, no-preemption, circular-wait, all four must hold for deadlock. The most practical to break is **circular wait**, via a global **lock-ordering** rule (always acquire locks in the same order).

4. **What is the GIL and what does it imply for threads doing CPU-bound work?** The GIL is a single mutex in CPython that lets only one thread execute Python bytecode at a time (to keep refcounting thread-safe). So pure-Python CPU-bound work gets **no** parallelism from threads, it serializes (and may even slow down). CPU parallelism needs `multiprocessing` (separate interpreters, separate GILs).

5. **When do threads still help in CPython despite the GIL?** For **I/O-bound** work. A thread blocked on network/disk I/O *releases the GIL*, letting other threads run, so the waiting overlaps. Fetching many URLs, reading many files, threads shine because the bottleneck is waiting, not computing.

6. **How does the asyncio event loop achieve concurrency without threads or locks?** Coroutines run on one thread and **cooperatively yield** at `await` points (where they'd otherwise wait on I/O). The event loop runs ready tasks, parks ones that are waiting, and resumes them when their I/O completes. Because switches only happen at explicit `await`s, there's no mid-operation interleaving, so no locks are needed between coroutines. It wins for huge numbers of cheap, I/O-bound tasks; it's the wrong tool for CPU-bound work (a non-yielding coroutine starves the loop).
