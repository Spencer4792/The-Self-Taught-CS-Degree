> *Goal: understand the OS as the thing that turns one set of hardware into a safe, shared illusion for every program, and tie every concept to a command you can actually run. The OS is the most-used software you never think about. Every `print`, every file open, every network call quietly drops into the kernel and back. This chapter lifts the hood. The throughline: the OS is a **resource manager** and an **illusionist**, it gives every program the illusion of having the whole machine to itself (its own CPU, its own memory, its own files), while secretly multiplexing real, finite hardware among everyone and keeping them from stepping on each other.

## Start here: the OS as an apartment building manager

Here's the picture that makes the OS click. Think of the computer as an **apartment building**, the OS as the **building manager**, and each running program as a **tenant**.

- Every tenant *thinks* they have a private apartment with their own front door, their own utilities, their own mailbox. They don't see the other tenants' rooms. That privacy is **process isolation and virtual memory**, each program gets its own address space and physically *can't* peek into another's.
- There's exactly one set of real plumbing, wiring, and an elevator, the **CPU, RAM, disk, network**. The manager schedules who uses the shared elevator and when, so no single tenant hogs it. That's the **scheduler** time-slicing the CPU.
- Tenants can't rewire the building themselves. If they want something dangerous, turn on the water main, access the roof, they have to *ask the manager*, who checks it's allowed and does it for them. That request-to-the-manager is a **system call**: the only sanctioned way for an unprivileged program to get privileged work done.
- The manager keeps a ledger of who lives where, which mailboxes belong to whom, who has keys to what. That bookkeeping is **process tables, file descriptors, inodes, and permissions**.

**Why this matters:** every "permission denied," every "segmentation fault," every "out of memory," every mysteriously slow program traces back to the building manager doing (or refusing) its job. Understanding the OS turns these from scary error messages into "oh, I asked the manager for something it wouldn't allow, and here's why." It's also the layer beneath *everything*, once you see it, you stop treating your programs as mysterious and start seeing the machine they actually run on. The rest of this chapter makes the apartment-manager picture precise, and every concept is tied to a command you can run *right now* to watch the manager work.

## What an OS does

Four big jobs:

1. **Process management**, create, schedule, and tear down running programs; give each the illusion of its own CPU.
2. **Memory management**, give each process its own private address space; decide what's in RAM vs swapped to disk.
3. **File system / storage**, turn raw blocks on a disk into named files and directories with permissions.
4. **I/O & device management**, talk to keyboards, disks, network cards via drivers; handle interrupts.

Underneath all four sits the principle of **protection**: untrusted user programs must not be able to crash the machine, read each other's memory, or monopolize the CPU. The OS enforces that with a hardware-supported boundary.

## Kernel vs user space, and system calls

The CPU runs in (at least) two privilege levels:

- **Kernel mode** (privileged): can execute any instruction, touch any memory, talk to hardware directly. The **kernel**, the OS core, runs here.
- **User mode** (unprivileged): your programs run here. They *cannot* directly touch hardware, other processes' memory, or privileged instructions. If they try, the CPU traps and the kernel steps in (usually killing the offender).

```text
┌──────────────────────── USER SPACE (unprivileged) ────────────────────────┐
│  your_app   python   browser   shell   ...                                 │
└──────────────────────────────── │ system call (trap) ──────────────────────┘
                                   ▼
┌──────────────────────── KERNEL SPACE (privileged) ────────────────────────┐
│  scheduler │ memory mgr │ file systems │ device drivers │ network stack    │
└───────────────────────────────── │ ──────────────────────────────────────┘
                                    ▼
                              HARDWARE (CPU, RAM, disk, NIC)
```

So how does a user program ever read a file or send a packet? Through a **system call**, the *only* doorway from user space into the kernel. A syscall is a controlled trap: the program puts a syscall number and arguments in registers, executes a special instruction (`syscall`), and the CPU switches to kernel mode at a fixed entry point. The kernel validates the request, does the privileged work, and returns. Familiar ones: `read`, `write`, `open`, `close`, `fork`, `execve`, `mmap`, `socket`.

Every library function you call eventually bottoms out in syscalls. `print("hi")` → Python's I/O → C `write()` → the `write` syscall. You can *watch* this:

```bash
strace -c python3 -c 'print("hi")'    # Linux: count syscalls a program makes
# macOS equivalent: sudo dtruss python3 -c 'print("hi")'
strace -e trace=openat,read,write cat /etc/hostname   # trace just file syscalls
```

Seeing the syscall trace is the moment "the kernel is underneath everything" stops being a slogan.

## Process lifecycle & scheduling

A process moves through states:

```text
   NEW ──► READY ◄────────────────► RUNNING ──► TERMINATED
            ▲                          │
            │      I/O / event done    ▼
            └──────── WAITING ◄──── (blocks on I/O, lock, etc.)
```

- **Ready**: able to run, waiting for a CPU.
- **Running**: currently executing on a core.
- **Waiting/Blocked**: can't proceed until some event (I/O completes, a lock frees).
- **Terminated**: done; lingers briefly as a *zombie* until the parent collects its exit status (`wait`).

The **scheduler** decides which ready process runs next, and modern OSes are **preemptive**: a hardware **timer interrupt** fires periodically, yanking the CPU back to the kernel so no process can hog it. The scheduler then picks the next process. Classic policies (real schedulers like Linux's CFS are fancier, but these are the ideas):

- **Round-robin**: each ready process gets a fixed **time slice (quantum)**; cycle through them. Fair, simple, good for interactivity.
- **Priority scheduling**: higher-priority processes run first. Risk: **starvation** of low-priority tasks (mitigated by *aging*, slowly bumping a waiting task's priority).
- **Shortest-job-first / shortest-remaining-time**: minimizes average wait but needs to predict run lengths.
- **Multilevel feedback queues**: multiple priority queues; tasks that use their whole slice sink to lower priority (probably CPU-bound), interactive ones that block early stay high. This is roughly how real desktop schedulers favor responsiveness.

On Unix you can see and nudge scheduling:

```bash
ps aux                 # snapshot of all processes (PID, %CPU, %MEM, STAT)
top         # or htop  # live, sorted by CPU/memory
nice -n 10 mytask      # start a process with lower priority (nicer to others)
renice -n -5 -p 1234   # change a running process's priority (needs privileges to raise)
```

## Scheduling deep dive: four policies on one workload, with Gantt charts

The way to *feel* the difference between scheduling policies is to run the same set of jobs through each and compute the metrics. Let's do exactly that by hand. Here's the workload, four processes that all arrive at time 0 (to keep it clean), with these CPU **burst times**:

```text
 Process   Burst (ms)   Priority (lower = higher priority)
 ──────────────────────────────────────────────────────────
   P1          8             3
   P2          4             1
   P3          9             4
   P4          5             2
```

The two metrics that matter:
- **Turnaround time** = completion time − arrival time (here arrival = 0, so just completion time).
- **Waiting time** = turnaround − burst (time spent *not* running while present).

### FCFS (First-Come-First-Served) - run in arrival order P1,P2,P3,P4

```text
 |   P1    |  P2  |    P3     |  P4  |
 0         8     12          21     26      (time axis, ms)

 Completion:  P1=8,  P2=12,  P3=21,  P4=26
 Turnaround:  8, 12, 21, 26                 avg = 67/4 = 16.75 ms
 Waiting:     0,  8, 12, 21                 avg = 41/4 = 10.25 ms
```

FCFS is simple and fair-by-arrival, but suffers the **convoy effect**: a long job at the front (P1) makes everyone behind it wait. If P1 had been a 100 ms job, P2's 4 ms task would wait 100 ms, terrible for short interactive tasks stuck behind a hog.

### SJF (Shortest-Job-First, non-preemptive) - run shortest burst first: P2(4),P4(5),P1(8),P3(9)

```text
 | P2 |  P4  |   P1    |    P3     |
 0    4      9        17          26

 Completion:  P2=4, P4=9, P1=17, P3=26
 Turnaround:  4, 9, 17, 26                  avg = 56/4 = 14.0 ms
 Waiting:     0, 4,  9, 17                  avg = 30/4 = 7.5 ms
```

SJF gives the **provably minimum average waiting time** for a fixed batch, notice it beat FCFS (7.5 vs 10.25 ms average wait). The catch: you must *know or predict* burst lengths, and long jobs can **starve** if short ones keep arriving.

### Round-Robin (quantum = 4 ms) - cycle P1,P2,P3,P4, each gets 4 ms then re-queues

```text
 |  P1  |  P2  |  P3  |  P4  |  P1  |  P3  | P4 |  P3 |
 0      4      8     12     16     20     24   25    26
   P1 needs 8 → 4 now, 4 later.  P2 done at 8.  P3 needs 9 → 4,4,1.
   P4 needs 5 → 4, then 1.

 Completion:  P2=8,  P1=20,  P4=25,  P3=26
 Turnaround:  P1=20, P2=8, P3=26, P4=25       avg = 79/4 = 19.75 ms
 Waiting:     P1=12, P2=4, P3=17, P4=20       avg = 53/4 = 13.25 ms
```

RR has *worse* average turnaround here than SJF/FCFS, that's the price of fairness and **responsiveness**. No job waits more than `(n−1) × quantum` before getting *some* CPU, so interactive tasks feel snappy even though batch throughput suffers. **Quantum tuning** is the dial: too big → RR degrades toward FCFS; too small → context-switch overhead dominates (you spend all your time switching).

### Priority (non-preemptive) - run highest priority first: P2(1),P4(2),P1(3),P3(4)

```text
 | P2 |  P4  |   P1    |    P3     |
 0    4      9        17          26

 (same Gantt as SJF here, by coincidence of the numbers)
 Turnaround avg = 14.0 ms,  Waiting avg = 7.5 ms
```

Priority lets *importance* drive order rather than length, but low-priority jobs can **starve** if high-priority work keeps coming. The fix is **aging**: gradually raise a waiting job's priority so it eventually runs.

### Side-by-side

```text
 Policy          Avg turnaround   Avg waiting   Best at
 ───────────────────────────────────────────────────────────────────
 FCFS                16.75          10.25        simplicity; batch
 SJF                 14.00           7.50        min avg wait (needs predictions)
 Round-Robin (q=4)   19.75          13.25        responsiveness/fairness
 Priority            14.00           7.50        honoring importance (risk: starvation)
```

The takeaway: **there is no universally best policy**, it's a trade-off between throughput, fairness, responsiveness, and starvation-resistance. Real schedulers (Linux's CFS, multilevel feedback queues) blend these: they approximate "favor short/interactive jobs" (SJF-like responsiveness) while guaranteeing everyone *some* CPU (RR-like fairness) and aging to prevent starvation.

## Virtual memory & paging

Here's the illusion from the memory chapter, explained. Each process believes it owns a clean, contiguous **virtual address space** starting at 0. In reality, physical RAM is shared, fragmented, and smaller. The OS + the CPU's **MMU** (memory management unit) bridge the two.

Memory is divided into fixed-size **pages** (commonly 4 KB) in virtual space and matching **frames** in physical RAM. A per-process **page table** maps virtual pages → physical frames. Every memory access goes through this translation:

```text
virtual address ──► [page number | offset] ──► page table lookup ──► physical frame
                                                       │
                                  (cached in the TLB for speed)
```

- **Why virtual memory exists:** (1) **isolation**, each process's page table only maps *its* memory, so it physically *cannot* address another process's RAM; (2) **flexibility**, virtual pages can map to scattered physical frames, so no need for contiguous physical memory; (3) **over-commit**, pages not currently needed can live on disk (**swap**), letting the system run programs that need more memory than physical RAM.

- **TLB (Translation Lookaside Buffer):** walking the page table on *every* access would be brutally slow, so the MMU caches recent virtual→physical translations in the TLB. A **TLB hit** is fast; a **TLB miss** means a slower page-table walk.

- **Page fault:** when a process accesses a virtual page not currently in a physical frame, the MMU traps to the kernel. The kernel handles it: maybe the page is on disk (swap or a memory-mapped file) and gets loaded into a free frame (a *major* fault, slow), or it just needs a fresh zeroed frame (a *minor* fault). If the address is truly invalid (not mapped at all), that's the dreaded **segmentation fault**, the kernel kills the process. So a "segfault" is literally an unhandleable page fault on an unmapped address.

```bash
vmstat 1               # watch paging/swapping activity live (si/so = swap in/out)
cat /proc/meminfo      # Linux: memory + swap stats
/usr/bin/time -v ./prog  # reports page faults (major/minor) for a run
```

## Address translation worked by hand (paging deep dive)

Let's actually *do* a translation with numbers, because "the page table maps pages to frames" stays abstract until you've ground through one. We'll use small, friendly sizes.

**Setup:** a system with **16-bit virtual addresses** and a **page size of 256 bytes (2⁸)**.

```text
A virtual address is split into two fields:
   page size = 256 bytes = 2^8  →  OFFSET is the low 8 bits
   16-bit address           →  PAGE NUMBER is the high 8 bits

  ┌──────────────────┬──────────────────┐
  │  page number (8) │   offset (8)     │
  └──────────────────┴──────────────────┘
   bits 15..8           bits 7..0
```

The split is pure arithmetic: **offset = address mod page_size**, **page number = address ÷ page_size** (integer division). Say a tiny page table looks like:

```text
 PAGE  →  FRAME      (a page table is just this lookup)
 ────────────────
   0   →   5
   1   →   2
   2   →  (not present - on disk)
   3   →   7
```

**Translate virtual address `0x0A 3F` (= page 0x0A? no, let's use a real one): translate `0x013F`.**

```text
 0x013F = 0000 0001 0011 1111  (binary)
          └─── page = 0x01 ───┘└── offset = 0x3F ──┘
          page number = 0x01 (=1),  offset = 0x3F (=63)

 Step 1: look up page 1 in the page table → frame 2.
 Step 2: physical address = frame × page_size + offset
                          = 2 × 256 + 63
                          = 512 + 63 = 575  (= 0x023F)

 Notice: the OFFSET is copied through unchanged (0x3F → 0x3F); only the
 high bits change (page 0x01 → frame 0x02). Translation only swaps the
 page→frame part; the within-page offset never moves.
```

**Now translate `0x023A` (page 2):** page 2 is **not present** → the MMU raises a **page fault** → the kernel either loads the page from disk into a free frame (major fault) and updates the table, or kills the process if the address is actually invalid (segfault).

### TLB hit vs miss, with a worked hit-rate

Walking the page table on *every* access is slow (it's itself memory reads, and real tables are multi-level, so one translation can cost 3-4 memory accesses). The **TLB** caches recent page→frame translations.

```text
ACCESS to a virtual address:
  ┌─ TLB lookup ─┐
  │  HIT  ───────┼──► use cached frame immediately            (~1 cycle)
  │  MISS ───────┼──► walk the page table (multi-level)       (~100s of cycles)
  └──────────────┘    then install the result in the TLB
```

**Worked effective access time.** Suppose a TLB hit costs 1 ns, a miss (page-table walk) costs 100 ns, and the hit rate is 98%:

```text
EAT = 0.98 × 1 ns  +  0.02 × 100 ns
    = 0.98 + 2.00
    = 2.98 ns   (vs 1 ns if every access hit - the 2% misses dominate the cost!)
```

That's why TLB hit rate matters so much, and why locality helps twice over: good locality keeps both the *data* cache and the *TLB* warm. Code that strides across many pages thrashes the TLB even if the data cache copes.

### Demand paging and thrashing

- **Demand paging:** the OS doesn't load a program's whole image up front. It maps pages *lazily* and pulls each one in **on its first access** (a page fault). So a 1 GB program that only touches 50 MB only ever pages in ~50 MB. Startup is faster and RAM isn't wasted on untouched pages.
- **Thrashing:** the pathological state where the **working set** (the pages a process actively needs) doesn't fit in RAM, so the OS spends more time paging in/out than computing. Every access faults, evicts a page another access immediately needs back, and the disk becomes the bottleneck. Symptoms: CPU near idle, disk at 100%, everything molasses-slow.

```text
Healthy:   working set ⊆ RAM     → faults rare, CPU busy doing work
Thrashing: working set  > RAM    → constant page-in/page-out, CPU waits on disk
                                    "the machine is swapping itself to death"
```

```bash
# WATCH paging live; the si/so columns are swap-in / swap-out pages per second.
vmstat 1
# Under thrashing, si/so stay high and the `wa` (I/O wait) CPU column climbs while
# `us`+`sy` (useful work) collapses. That signature IS thrashing.

# See a program's actual fault counts:
/usr/bin/time -v python3 -c "x=[0]*50_000_000; print(sum(x))" 2>&1 | grep -i fault
# "Major (requiring I/O) page faults" vs "Minor" - minor faults are cheap (fresh frame),
# major faults touched disk.
```

## File systems: inodes, blocks, permissions

A file system turns a linear array of disk **blocks** into named files. The key structure is the **inode** (index node): a per-file record holding the file's *metadata* and *pointers to its data blocks*, but **not** its name.

```text
inode 4711
├─ type, permissions (rwx), owner, group
├─ size, timestamps (atime/mtime/ctime)
├─ link count
└─ block pointers ──► [block 102][block 103][block 580]...  (the actual bytes)
                       (large files use indirect blocks: a block of pointers
                        to more blocks, then double/triple-indirect for huge files)
```

The **name** lives separately, in a **directory**, which is just a file that maps names → inode numbers. This separation explains **hard links**: two names (directory entries) pointing at the *same* inode. The inode's **link count** tracks how many names refer to it; the data is freed only when the count hits 0 (and no process has it open). A **symbolic link** is different, a tiny file containing a *path string*, an indirection by name.

```bash
ls -i file.txt         # show the inode number
df -i                  # inode usage per filesystem (you can run out of inodes!)
stat file.txt          # dump an inode's metadata
ln  a.txt b.txt        # hard link: b.txt and a.txt share an inode
ln -s a.txt c.txt      # symlink: c.txt holds the path "a.txt"
```

**Permissions, the rwx / octal model.** Every file has three permission triples, for **owner**, **group**, and **others**, each granting **r**ead (4), **w**rite (2), e**x**ecute (1):

```text
   rwx  r-x  r--      symbolic
   owner group others
    7    5    4        octal  (rwx=4+2+1=7, r-x=4+0+1=5, r--=4+0+0=4)
```

For directories the bits mean: **r** = list names, **w** = create/delete entries, **x** = traverse into / access entries. (A directory you can read but not execute lets you see names but not `cd` into it, a common gotcha.)

```bash
chmod 755 script.sh    # rwxr-xr-x
chmod u+x script.sh    # add execute for owner (symbolic form)
ls -l                  # see the rwx triples in the leftmost column
chown user:group file  # change owner/group
umask                  # default permission mask for newly created files
```

## Lab: inodes, hard links vs symlinks, demonstrated end to end

This is the lab that makes inodes *click*, run every line and read the output. The whole thing is safe (it works in a throwaway directory).

```bash
# ---- set up a scratch dir ----
mkdir -p /tmp/inode_lab && cd /tmp/inode_lab
echo "original contents" > original.txt

# ---- 1. see the inode number and link count ----
ls -li original.txt
#  e.g.:  1234567 -rw-r--r-- 1 spencer staff 18 ... original.txt
#         ^inode#            ^link count = 1  (one name points at this inode)

stat original.txt          # full inode dump: size, blocks, atime/mtime/ctime, links

# ---- 2. HARD LINK: a second NAME for the SAME inode ----
ln original.txt hardlink.txt
ls -li original.txt hardlink.txt
#  BOTH lines show the SAME inode number, and link count is now 2.
#  They are not "copies" - they are two directory entries → one inode → one set of bytes.

# ---- 3. prove they share data: edit one, read the other ----
echo "changed via hardlink" >> hardlink.txt
cat original.txt           # shows the appended line - SAME underlying file!

# ---- 4. delete the original NAME; data survives via the other name ----
rm original.txt
ls -li hardlink.txt        # link count drops 2 → 1; inode # unchanged; data intact
cat hardlink.txt           # still works - the inode lives until link count hits 0

# ---- 5. SYMLINK: a tiny file holding a PATH string ----
ln -s hardlink.txt symlink.txt
ls -li hardlink.txt symlink.txt
#  symlink.txt has a DIFFERENT inode (it's its own little file), shows '-> hardlink.txt',
#  and an 'l' file type in the leftmost column.
readlink symlink.txt       # prints "hardlink.txt" - literally the stored path string

# ---- 6. break the symlink to prove it's by-NAME, not by-inode ----
mv hardlink.txt renamed.txt
cat symlink.txt            # ERROR: No such file or directory - symlink points at a NAME
                           # that no longer exists. A hard link would NOT have broken.
ls -l symlink.txt          # shows the dangling link in red on most terminals
```

What this lab demonstrates:

```text
 HARD LINK                          SYMLINK (symbolic link)
 ─────────────────────────          ──────────────────────────────
 two NAMES → one inode → one        a separate tiny file whose CONTENTS
 set of data blocks                 are the PATH string of the target

 same inode number                  its OWN inode number
 increments the link count          does not touch the target's link count
 survives deleting the "original"   BREAKS if the target is moved/deleted
 can't cross filesystems            can cross filesystems & point at dirs
```

```bash
# ---- bonus: you can run OUT of inodes even with disk space free ----
df -i .                    # inode usage per filesystem (IFree column)
df -h .                    # block (space) usage - these are INDEPENDENT limits
# Millions of tiny files can exhaust inodes while df -h still shows free space -
# a real production incident that confuses people who only check `df`.

# ---- bonus: deleted-but-open file keeps its space ----
python3 -c "
import os, time
f = open('/tmp/inode_lab/big.tmp','w'); f.write('x'*10_000_000); f.flush()
os.remove('/tmp/inode_lab/big.tmp')   # unlink the NAME while the fd is still open
print('removed name; fd still open - space NOT freed yet'); time.sleep(2)
f.close()                              # NOW link count is 0 AND no open fd → freed
print('closed - space reclaimed')
"
# This is why deleting a huge log file a daemon holds open doesn't reclaim disk
# until the daemon closes it (or you truncate via /proc/<pid>/fd/<n>).
```

## I/O, interrupts, and signals

**Interrupts** are how hardware grabs the CPU's attention *asynchronously*. Instead of the CPU constantly polling "is the disk done? is a key pressed?", the device raises an **interrupt**; the CPU stops, saves state, runs the kernel's **interrupt handler** for that device, then resumes. The timer interrupt that drives preemptive scheduling is one of these. This is why I/O can overlap computation: fire off a disk read, let the CPU do other work, and get interrupted when the data arrives.

**Signals** are the OS's way of delivering asynchronous notifications to *processes* (a software analog of interrupts). Each has a number and a default action:

```text
SIGINT  (2)   ← Ctrl-C; default: terminate (catchable)
SIGTERM (15)  ← polite "please exit"; default: terminate (catchable → clean shutdown)
SIGKILL (9)   ← forceful kill; CANNOT be caught or ignored
SIGSEGV (11)  ← invalid memory access (segfault)
SIGCHLD       ← a child process changed state (so the parent can reap it)
SIGSTOP/CONT  ← pause / resume a process
```

```bash
kill -TERM 1234        # ask process 1234 to terminate cleanly (default signal)
kill -9 1234           # SIGKILL - unconditional, last resort
kill -l                # list all signal names
```

A program can install a **signal handler** to clean up on `SIGTERM`/`SIGINT` (flush files, close sockets), which is exactly what graceful shutdown is.

**Useful diagnostic commands** that expose the kernel's bookkeeping:

```bash
lsof -p 1234           # list open files/sockets for a process
lsof -i :8080          # what's listening on port 8080
cat /proc/1234/status  # Linux: a process's state, memory, threads (the /proc window)
ls /proc/1234/fd       # the process's open file descriptors as symlinks
```

`/proc` on Linux is a clever idea: a virtual filesystem where the kernel exposes live process and system state *as files* you can `cat`. The kernel becomes browsable.

## Signals and IPC, in depth

The earlier list named the common signals; now let's make signal *handling* and the broader **IPC** (inter-process communication) toolkit concrete, because this is what real services use to shut down cleanly and talk to each other.

### Catching a signal for graceful shutdown

A long-running service shouldn't die mid-write when the orchestrator sends `SIGTERM`. It installs a **handler** that flips a flag (or runs cleanup), so the main loop finishes the current work, flushes, and exits. This *is* "graceful shutdown."

```python
# graceful.py - Ctrl-C (SIGINT) or `kill -TERM <pid>` triggers clean shutdown.
import signal, time, sys

running = True
def handle(signum, frame):
    global running
    name = signal.Signals(signum).name
    print(f"\n  received {name} - finishing current work, then exiting...")
    running = False                      # don't exit abruptly; let the loop wind down

signal.signal(signal.SIGINT,  handle)    # Ctrl-C
signal.signal(signal.SIGTERM, handle)    # `kill <pid>` default

print(f"PID {__import__('os').getpid()} working. Send SIGTERM or hit Ctrl-C.")
while running:
    print("  ...doing a unit of work..."); time.sleep(1)
print("  cleanup done (flushed buffers, closed sockets). Bye.")
sys.exit(0)
```

```bash
python3 graceful.py &       # run in background, note the printed PID
sleep 3
kill -TERM %1               # polite shutdown → handler runs → clean exit
# Contrast: kill -9 %1 would give NO chance to clean up (uncatchable).
```

The key rule from the signal table, demonstrated: `SIGTERM`/`SIGINT` are **catchable** (you get to clean up); `SIGKILL` (-9) is **not** (instant death, risks corruption). Always try `TERM` first.

### The IPC toolbox: how separate processes talk

Processes have *isolated* memory (the core idea of the apartment-building model), so they need explicit channels to communicate. The main mechanisms, from simplest to richest:

```text
 MECHANISM        SHAPE                      GOOD FOR
 ───────────────────────────────────────────────────────────────────────────
 pipe             unidirectional byte stream  parent↔child, shell `|`
 named pipe(FIFO) a pipe with a filesystem    unrelated processes by path
                  name (mkfifo)
 signal           a single async number       "interrupt me" notifications
 shared memory    a region both map           fastest; large data, no copy
 message queue    kernel-managed mailbox       structured messages, priorities
 socket           bidirectional, network-able  local OR across machines
```

- **Pipes** are the workhorse behind the shell's `|` (you built one with `os.pipe()` in the tiny shell). One process writes bytes; the other reads them; the kernel buffers in between and signals EOF when all writers close.
- **Named pipes (FIFOs)** give a pipe a *path* so two *unrelated* programs can rendezvous by filename:

  ```bash
  mkfifo /tmp/myfifo
  # terminal 1:
  cat /tmp/myfifo            # blocks, waiting for a writer
  # terminal 2:
  echo "hello over a FIFO" > /tmp/myfifo   # terminal 1 prints it, then both end
  ```

- **Shared memory** is the fastest IPC, two processes map the *same* physical pages, so writes by one are instantly visible to the other with *no copying*. The cost: you're back to needing your own synchronization (locks/semaphores), because now two processes really do touch the same bytes, the concurrency chapter's race conditions return. Python exposes it via `multiprocessing.shared_memory`:

  ```python
  # shared_mem.py - two processes, ZERO-copy shared buffer
  from multiprocessing import Process, shared_memory
  def writer(name):
      shm = shared_memory.SharedMemory(name=name)
      shm.buf[0:5] = b"HELLO"      # writes land in shared physical pages
      shm.close()
  if __name__ == "__main__":
      shm = shared_memory.SharedMemory(create=True, size=16)
      p = Process(target=writer, args=(shm.name,)); p.start(); p.join()
      print("parent sees:", bytes(shm.buf[0:5]))   # b'HELLO' - no copy crossed the boundary
      shm.close(); shm.unlink()
  ```

- **Sockets** are the most general: bidirectional, and they work both *locally* (Unix domain sockets) and *across the network* (TCP/IP). This is why "talk to another process on this box" and "talk to a service across the world" use the same API, the network chapter builds on exactly this.

### Interrupts vs signals - keep them straight

```text
 INTERRUPT                         SIGNAL
 ─────────────────────────         ────────────────────────────────
 HARDWARE → CPU                    KERNEL → PROCESS
 async hardware event (key,        async software notification
 disk done, timer tick)            (Ctrl-C, child died, SIGTERM)
 handled by the KERNEL's           handled by the PROCESS's signal
 interrupt handler                 handler (or a default action)
 drives preemptive scheduling      drives graceful shutdown, child reaping
```

Signals are the *user-space-visible analog* of interrupts: the same "stop what you're doing, jump to a handler, resume" shape, but delivered to your process by the kernel rather than to the CPU by hardware.

## The boot process (briefly)

Power on → **firmware** (BIOS/UEFI) runs, initializes hardware, finds a boot device → loads a **bootloader** (GRUB, systemd-boot) → the bootloader loads the **kernel** into memory and hands it control → the kernel initializes drivers, mounts the root filesystem, and starts the first user-space process, **PID 1** (`init` / `systemd`) → PID 1 starts all the services and eventually your login shell. Every other process descends from PID 1 via `fork`. That's the chain from "press button" to "I have a prompt."

## Build it: a tiny shell in Python

A shell is a wonderful OS teaching tool because it exercises the core process syscalls directly: **fork** (clone the current process), **exec** (replace the clone's program image), **wait** (parent collects the child's exit), plus **pipe** (connect one process's stdout to another's stdin). Let's build one.

```python
#!/usr/bin/env python3
# tinysh.py - a minimal shell: builtins, external commands, and a single pipe.
import os, sys

def execute(cmd_argv):
    """Run one external command via fork + exec + wait."""
    pid = os.fork()                       # clone this process; returns 0 in child, child-pid in parent
    if pid == 0:
        # --- CHILD ---
        try:
            os.execvp(cmd_argv[0], cmd_argv)   # REPLACE child image with the new program
        except FileNotFoundError:
            print(f"tinysh: command not found: {cmd_argv[0]}", file=sys.stderr)
            os._exit(127)                  # _exit, not exit: skip Python cleanup in the child
    else:
        # --- PARENT ---
        _, status = os.waitpid(pid, 0)     # block until the child finishes; reap the zombie
        return os.waitstatus_to_exitcode(status)

def execute_pipe(left_argv, right_argv):
    """Run  left | right  by wiring left.stdout → right.stdin with a pipe()."""
    read_fd, write_fd = os.pipe()          # a kernel pipe: a pair of connected fds

    if os.fork() == 0:                     # --- LEFT child: writes into the pipe ---
        os.dup2(write_fd, 1)               # make fd 1 (stdout) point at the pipe's write end
        os.close(read_fd); os.close(write_fd)
        os.execvp(left_argv[0], left_argv)
        os._exit(127)

    if os.fork() == 0:                     # --- RIGHT child: reads from the pipe ---
        os.dup2(read_fd, 0)                # make fd 0 (stdin) point at the pipe's read end
        os.close(read_fd); os.close(write_fd)
        os.execvp(right_argv[0], right_argv)
        os._exit(127)

    os.close(read_fd); os.close(write_fd)  # parent: close BOTH ends or the reader never sees EOF
    os.wait(); os.wait()                   # reap both children

def main():
    while True:
        try:
            line = input(f"tinysh:{os.getcwd().split('/')[-1]}$ ").strip()
        except EOFError:                   # Ctrl-D
            print(); break
        if not line:
            continue

        # ---- builtins MUST run in the shell process itself (a forked child's cd
        #      would change the child's cwd, not the shell's) ----
        parts = line.split()
        if parts[0] == "exit":
            break
        if parts[0] == "cd":
            target = parts[1] if len(parts) > 1 else os.path.expanduser("~")
            try:
                os.chdir(target)           # changes THIS process's working directory
            except FileNotFoundError:
                print(f"cd: no such directory: {target}", file=sys.stderr)
            continue
        if parts[0] == "pwd":
            print(os.getcwd()); continue

        # ---- pipe?  cmd1 args | cmd2 args ----
        if "|" in parts:
            i = parts.index("|")
            execute_pipe(parts[:i], parts[i+1:])
            continue

        # ---- external command ----
        execute(parts)

if __name__ == "__main__":
    main()
```

Run `python3 tinysh.py` and try it:

```text
tinysh:Desktop$ pwd
/Users/spencer/Desktop
tinysh:Desktop$ ls
tinysh.py  notes.txt
tinysh:Desktop$ cd ..
tinysh:Users$ ls | head -3        # ← a real pipe, wired with os.pipe() + dup2
spencer
shared
...
tinysh:Users$ exit
```

What each syscall teaches, made concrete:
- **`fork()`** returns *twice*, `0` in the brand-new child, the child's PID in the parent. That "one call, two returns" is the cleverest API in Unix.
- **`execvp()`** *replaces* the current process image, same PID, brand-new program. Fork-then-exec is *the* Unix idiom for "run a program."
- **`waitpid()`** is why the parent doesn't race ahead, and is how zombies get reaped.
- **`cd` must be a builtin**, if you forked a child to run it, the child's `chdir` would die with the child and the shell's directory wouldn't change. That single design constraint *proves* the process-isolation model from the memory chapter.
- **`os.pipe()` + `dup2()`** is the whole mechanism behind `|`: redirect a child's stdout/stdin onto the kernel pipe's ends. (And the parent must close both ends, or the reader never gets EOF.)

(For a portable version that skips raw `fork` on Windows, `subprocess.Popen([...], stdin=..., stdout=...)` wraps all of this, but doing it by hand is where the learning is.)

## Common mistakes

OS-level confusions tend to produce error messages that *look* unrelated to their cause. Here are the traps.

- **Thinking a segfault means "out of memory."** It almost never does. A segfault is an access to an *unmapped or protection-violating* virtual address, a wild pointer, a null dereference, a stack overflow. "Out of memory" is a different failure (allocation fails / the OOM killer fires).
- **Making `cd` an external command.** A forked child's `chdir` dies with the child; the shell's directory never changes. `cd`, `exit`, `export` must be **builtins** that run in the shell process itself. This trips up everyone writing their first shell.
- **Forgetting to `wait()` for children → zombies.** A terminated child lingers as a zombie holding its exit status until the parent reaps it. A parent that spawns and never waits accumulates zombies (and eventually exhausts the process table).
- **Forgetting to close *both* pipe ends in the parent.** If the parent keeps the write end open, the reader never sees EOF and hangs forever. Close what you don't use.
- **Confusing `kill -9` with a polite stop.** `SIGKILL` (9) is uncatchable, the process gets *no chance* to flush files, close sockets, or clean up, risking corruption. Try `SIGTERM` (15) first; reserve `-9` for the truly stuck.
- **Misreading directory permissions.** On a *directory*, `r` lets you list names, but `x` is what lets you *enter* it / access entries. A directory with `r` but no `x` shows names you can't actually use. And `w` on a directory lets you *delete files inside it* even files you don't own, surprising people constantly.
- **Assuming a deleted file's space is freed immediately.** If a process still has the file open, the inode's data survives (link count may be 0, but the open fd keeps it alive) until that process closes it. That's why `rm`-ing a huge log file a running daemon holds open doesn't reclaim disk space.
- **Confusing hard links and symlinks.** A hard link is another *name* for the same inode (same data, survives deleting the original). A symlink is a tiny file holding a *path string*, it breaks if the target moves.

## On the job / interview angle

OS knowledge is the backbone of systems interviews and of day-to-day debugging once you're employed.

- **"What happens when you run a program / type a command in a shell?"** is a classic open-ended interview question. The fork-exec-wait story (plus PATH lookup, file descriptors, and the kernel/user boundary) is exactly what they want.
- **"Kernel mode vs user mode, and what's a system call?"**, be ready to explain the privilege boundary and that syscalls are the only doorway across it.
- **"What is virtual memory / what is a page fault / what's a segfault?"**, extremely common; the page-table + TLB + fault story is the answer.
- **"Process vs thread"** bridges this chapter and the concurrency chapter, interviewers ask it both ways.
- **"How do you debug a process eating 100% CPU / leaking memory / hung?"**, the *on-the-job* version. The toolkit here (`top`/`htop`, `ps`, `strace`/`dtruss`, `lsof`, `/proc`, `vmstat`) is precisely what you'll use. Being able to say "I'd `strace` it to see which syscall it's stuck in" or "I'd `lsof -p` to see what files/sockets it has open" marks you as someone who can actually operate software, not just write it.
- **On the job:** production incidents are overwhelmingly OS-shaped, disk full (sometimes *inodes* full, which `df -i` reveals but `df` doesn't), too many open files (`ulimit`/fd exhaustion), a runaway process, a wedged service that needs the right signal. Every backend/DevOps/SRE role assumes fluency here. The shell project below isn't just a toy; the syscalls it uses (`fork`, `exec`, `wait`, `pipe`, `dup2`) are the literal mechanics every container runtime, CI system, and process manager is built on.

**Real questions with model answers** (say them out loud):

- **Q: "Translate the virtual address `0x013F` given a 256-byte page size and a page table where page 1 maps to frame 2."**
  *Model answer:* "256 bytes is 2⁸, so the low 8 bits are the offset and the rest is the page number. `0x013F` splits into page `0x01` and offset `0x3F`. Page 1 maps to frame 2, and the physical address is `frame × page_size + offset = 2 × 256 + 63 = 575` (`0x023F`). The offset passes through unchanged; only the page-to-frame part is translated."

- **Q: "What's the difference between a TLB miss and a page fault?"**
  *Model answer:* "Both come up during address translation but they're different layers. A **TLB miss** means the translation wasn't cached, so the MMU walks the page table, but the page *is* in RAM; it's just a slower lookup. A **page fault** means the page isn't in a physical frame at all: the MMU traps to the kernel, which either loads it from disk (major fault) or maps a fresh frame (minor fault), or kills the process if the address is invalid (segfault). TLB miss = slow translation; page fault = the data isn't resident."

- **Q: "Your server is using almost no CPU but feels frozen and the disk light is solid. Diagnosis?"**
  *Model answer:* "Classic thrashing. The working set exceeds physical RAM, so the OS is paging in/out constantly, `vmstat 1` would show high `si`/`so` (swap in/out) and a high `wa` (I/O wait) while `us`+`sy` are near zero. The CPU is idle because it's *waiting on the disk* for pages, not because there's no work. Fix: reduce memory pressure (cap the process, add RAM, fix a leak, or shrink the working set)."

- **Q: "Compare a hard link and a symlink, and give a case where only one works."**
  *Model answer:* "A hard link is a second directory entry pointing at the *same inode*, same data, increments the link count, and survives deleting the original name; the data is freed only when the link count hits zero. A symlink is a separate tiny file whose contents are a *path string*; it breaks if the target is moved or deleted, but it can cross filesystems and point at directories, which hard links can't. So: backing up by hard-linking unchanged files (rsync `--link-dest`) needs *hard* links to share inodes; linking to a config in another mounted filesystem needs a *symlink*."

- **Q: "Walk me through FCFS vs Round-Robin for one short job stuck behind one long job."**
  *Model answer:* "Under FCFS the short job waits for the entire long job to finish, the convoy effect; if the long job is 100 ms and the short one is 4 ms, the short job's response time is ~100 ms. Round-Robin with a small quantum interleaves them, so the short job gets the CPU within a quantum or two and finishes fast, much better responsiveness, at the cost of more context switches and slightly worse total throughput. That trade, throughput vs responsiveness, is the heart of scheduling."

- **Q: "Why must you `wait()` on child processes, and what's a zombie?"**
  *Model answer:* "When a child exits, the kernel keeps a small record (its exit status) so the parent can read it, that terminated-but-unreaped child is a **zombie**. The parent reaps it with `wait`/`waitpid`, which removes the record. A parent that spawns children and never waits accumulates zombies, and enough of them exhaust the process table. In a shell or server you reap children, often by handling `SIGCHLD` or calling `waitpid(-1, WNOHANG)` periodically."

## Mini-project: a process & system monitor (a mini `top`)

`top`/`htop` feel mysterious until you build a tiny version yourself, and then you realize it's just *reading files the kernel exposes*. On Linux, `/proc` is a virtual filesystem where the kernel publishes live state as readable text. This project reads it to build a refreshing process dashboard, which makes "the kernel is browsable" concrete.

```python
#!/usr/bin/env python3
# minitop.py - a tiny process monitor. Linux: reads /proc. (macOS: falls back to `ps`.)
import os, time, sys

def read_proc_linux():
    procs = []
    for pid in filter(str.isdigit, os.listdir("/proc")):
        try:
            with open(f"/proc/{pid}/status") as f:
                info = dict(line.split(":\t", 1) for line in f if ":\t" in line)
            name = info.get("Name", "?").strip()
            state = info.get("State", "?").strip()                 # R running, S sleeping, Z zombie...
            vmrss = info.get("VmRSS", "0 kB").strip()              # resident memory
            threads = info.get("Threads", "?").strip()
            procs.append((int(pid), name, state, threads, vmrss))
        except (FileNotFoundError, ProcessLookupError, PermissionError):
            continue   # process vanished or we lack permission - totally normal, skip it
    return procs

def read_ps_fallback():
    # macOS / non-Linux: parse `ps`
    out = os.popen("ps -axo pid,comm,state,rss").read().strip().splitlines()[1:]
    procs = []
    for line in out:
        parts = line.split(None, 3)
        if len(parts) >= 4:
            pid, comm, state, rss = parts[0], parts[1], parts[2], parts[3]
            procs.append((int(pid), os.path.basename(comm), state, "?", f"{rss} kB"))
    return procs

def collect():
    return read_proc_linux() if os.path.isdir("/proc") else read_ps_fallback()

def main():
    try:
        while True:
            procs = collect()
            # sort by resident memory (parse the leading number out of "12345 kB")
            def rss_kb(p):
                try: return int(p[4].split()[0])
                except (ValueError, IndexError): return 0
            procs.sort(key=rss_kb, reverse=True)

            os.system("clear" if os.name != "nt" else "cls")
            print(f"minitop - {len(procs)} processes - {time.strftime('%H:%M:%S')}  (Ctrl-C to quit)\n")
            print(f"{'PID':>7}  {'NAME':<20} {'ST':<3} {'THR':>4}  {'MEM':>12}")
            print("-" * 55)
            for pid, name, state, threads, mem in procs[:15]:    # top 15 by memory
                print(f"{pid:>7}  {name[:20]:<20} {state[:2]:<3} {threads:>4}  {mem:>12}")
            time.sleep(2)
    except KeyboardInterrupt:
        print("\nbye")

if __name__ == "__main__":
    main()
```

Run `python3 minitop.py` and watch your processes refresh live, sorted by memory. What it drives home:

- **`/proc/<pid>/status` is the kernel handing you a process's bookkeeping as text**, state, memory, thread count, exactly the fields `top` shows. The OS's internal tables are *browsable*.
- **Processes appearing and vanishing between reads is normal**, that `FileNotFoundError` skip is the real-world fact that the process list is a moving target.
- **Process states map to the lifecycle diagram**: `R` (running/ready), `S` (sleeping/waiting), `Z` (zombie, terminated, awaiting reap). Spotting a pile of `Z` states is how you diagnose a parent that forgot to `wait()`.

**Extensions:** add a `%CPU` column by sampling `/proc/<pid>/stat` utime+stime twice and dividing the delta by the time delta; add a key to send `SIGTERM` to a selected PID (now it's interactive like `htop`); add a system-wide memory bar from `/proc/meminfo`.

## Mini-project: a CPU scheduler simulator (FCFS / SJF / RR / Priority)

The scheduling deep-dive above worked the metrics *by hand*; this project makes the computer do it, so you can throw any workload at any policy and *see* the Gantt chart and metrics. Building it forces you to understand each policy precisely, you can't simulate what you can't define.

```python
# scheduler_sim.py - simulate 4 scheduling policies and print Gantt charts + metrics.
from dataclasses import dataclass, field
from collections import deque

@dataclass
class Proc:
    pid: str
    arrival: int
    burst: int
    priority: int = 0
    remaining: int = field(init=False)
    completion: int = 0
    def __post_init__(self): self.remaining = self.burst

def metrics(procs, gantt):
    print("  Gantt: " + "".join(f"|{p}" for p, _ in gantt) + "|")
    print("         " + "".join(f"{t:<{len(p)+1}}" for p, t in gantt) +
          f"{gantt[-1][1] + 0}")        # start times under each block
    tat = {p.pid: p.completion - p.arrival for p in procs}
    wait = {p.pid: tat[p.pid] - p.burst for p in procs}
    print(f"  turnaround avg = {sum(tat.values())/len(procs):.2f} ms   "
          f"waiting avg = {sum(wait.values())/len(procs):.2f} ms")

def fcfs(procs):
    procs = sorted(procs, key=lambda p: p.arrival)
    t, gantt = 0, []
    for p in procs:
        t = max(t, p.arrival)
        gantt.append((p.pid, t)); t += p.burst; p.completion = t
    return gantt

def sjf(procs):                          # non-preemptive shortest-job-first
    t, done, gantt = 0, [], []
    pool = list(procs)
    while pool:
        ready = [p for p in pool if p.arrival <= t] or pool
        p = min(ready, key=lambda p: p.burst)
        t = max(t, p.arrival)
        gantt.append((p.pid, t)); t += p.burst; p.completion = t
        pool.remove(p)
    return gantt

def priority(procs):                     # non-preemptive, lower number = higher priority
    t, gantt = 0, []
    pool = list(procs)
    while pool:
        ready = [p for p in pool if p.arrival <= t] or pool
        p = min(ready, key=lambda p: p.priority)
        t = max(t, p.arrival)
        gantt.append((p.pid, t)); t += p.burst; p.completion = t
        pool.remove(p)
    return gantt

def round_robin(procs, quantum=4):
    t, gantt = 0, []
    q = deque(sorted(procs, key=lambda p: p.arrival))
    while q:
        p = q.popleft()
        run = min(quantum, p.remaining)
        gantt.append((p.pid, t)); t += run; p.remaining -= run
        if p.remaining > 0: q.append(p)  # not done → back of the line
        else: p.completion = t
    return gantt

def fresh():
    return [Proc("P1",0,8,3), Proc("P2",0,4,1), Proc("P3",0,9,4), Proc("P4",0,5,2)]

for name, fn in [("FCFS", fcfs), ("SJF", sjf), ("Round-Robin q=4", round_robin),
                 ("Priority", priority)]:
    procs = fresh()
    print(f"\n=== {name} ===")
    metrics(procs, fn(procs))
```

```bash
python3 scheduler_sim.py
# You'll see each policy's Gantt order and its turnaround/waiting averages -
# matching (and letting you re-derive) the hand-worked numbers from the deep dive.
```

What it teaches by making you *implement* each policy:

- **FCFS** is a plain queue, trivial, but the convoy effect falls right out when a big job sits first.
- **SJF** and **Priority** are the same "pick-the-best-ready-job" loop with a different key function (`burst` vs `priority`), seeing that they're structurally identical is a real insight.
- **Round-Robin** *needs* a `remaining` counter and a re-queue, which is exactly why it requires a `quantum` and incurs more context switches.
- Swapping the input workload (add arrival times, change bursts) and re-running shows there's *no universal winner*, the central lesson of the deep dive, now interactive.

**Extensions:** add **preemptive** SRTF (shortest-remaining-time-first) and preemptive priority; add **aging** to the priority scheduler and show it prevents starvation; count and report the number of **context switches** each policy incurs (RR will dwarf the others).

### Solutions

1. Typical `ls` syscalls: `openat` (open the directory), `getdents`/`getdirentries` (read directory entries), `stat`/`statx` (get each file's metadata for `-l`), `write` (print output to stdout), `close` (release fds), `mmap` (map shared libraries at startup). Each is a controlled trap into the kernel.

2. `-rwxr-x---` = owner `rwx` (7), group `r-x` (5), others `---` (0) → **750**. The group can read and execute (enter, run) but **cannot write** (create/modify/delete entries).

3. `SIGTERM` (15) is catchable, the process can run a handler to flush buffers, close sockets, and exit cleanly (graceful shutdown). `SIGKILL` (9) is uncatchable and immediate, no cleanup, risking data corruption. Prefer `TERM` first; use `-9` only when the process is unresponsive to `TERM`.

4. After `ln a.txt b.txt`, both names share one inode (same `ls -i` number) and the inode's link count is 2. Deleting `a.txt` just removes one directory entry and drops the link count to 1; the data lives until the count hits 0, so `b.txt` still works. A symlink (`ln -s a.txt c.txt`) stores the *path string* `"a.txt"`, not the inode, deleting `a.txt` leaves `c.txt` pointing at a now-nonexistent path, so it's a dangling/broken link.

5. With `r--` (read, no execute) on a directory: `ls dir` *lists the names* (read works) but `ls -l dir` may fail to stat the entries, and `cd dir` **fails**, entering/traversing a directory requires the `x` bit. So you can see what's inside but can't actually use any of it.

6. The pipe has a read end and a write end; a reader only gets EOF when *all* write-end copies are closed. After forking, the parent (and the read-child) still hold the inherited write end. If the parent doesn't close its write end, the read-child can wait forever for EOF that never comes, because the kernel still sees an open writer (the parent). So the parent closes both ends, it uses neither, to let EOF propagate correctly.

7. The CPU issues a virtual address → the **MMU** checks the **TLB** for a cached translation → TLB miss, so it walks the **page table** → the page-table entry says "not present in RAM" → the MMU raises a **page fault** trap → the **kernel**'s fault handler runs, finds the page is in **swap on disk**, picks a free physical frame (evicting another page if needed), reads the page from **disk** into that frame, updates the page table, and returns → the instruction retries and now succeeds. Because it touched disk, it's a **major** fault (slow). A minor fault is when the page is already in memory or just needs a fresh zeroed frame (no disk I/O).

8. `fork()` creates a near-identical copy of the calling process, and execution continues in *both*, so the single call site returns once in the parent (with the child's PID) and once in the child (with `0`). The return value is how each copy knows which it is.
   ```python
   import os
   pid = os.fork()
   if pid == 0:
       print("I am the child")
   else:
       print(f"I am the parent; my child is {pid}")
   ```

9. `lsof -p <pid>` lists every file/socket the process has open; counting them (or `ls /proc/<pid>/fd | wc -l` on Linux) shows whether it's near the `ulimit -n` cap. Check `/proc/<pid>/limits` for the actual limit. Two common root causes: **(a)** a leak, opening files/sockets/connections without closing them in a loop; **(b)** a limit set too low for legitimate load (e.g., a high-concurrency server needing thousands of sockets). Fixes: close descriptors (use `with`/context managers), use connection pooling, and/or raise `ulimit -n`.

10. Page size 1 KB = 2¹⁰, so the low **10 bits** are the offset and the high **6 bits** are the page number (16 − 10 = 6). `0x0C8E = 0000 1100 1000 1110`. Split: page = top 6 bits = `000011` = `0x03` (=3); offset = low 10 bits = `00 1000 1110` = `0x08E` (=142). Page 3 maps to frame `0x0A` (=10), so physical address = `frame × page_size + offset = 10 × 1024 + 142 = 10240 + 142 = 10382` (`0x288E`). Note the low 10 bits (`0x08E`) are unchanged; only the page-to-frame high bits changed (`0x03` → `0x0A`).

11. SJF runs shortest-first: P2(2), P4(3), P1(6), P3(8).
   ```text
   | P2 |  P4  |    P1    |     P3     |
   0    2      5         11           19
   Completion: P2=2, P4=5, P1=11, P3=19
   Waiting (= start time, since arrival=0): P2=0, P4=2, P1=5, P3=11
   avg waiting = (0+2+5+11)/4 = 18/4 = 4.5 ms
   ```
   SJF minimizes average waiting time because putting a *shorter* job before a *longer* one reduces the total time the longer job's duration is added to everyone waiting behind it, any swap that puts a longer job earlier can only increase the cumulative wait. (Formally, it's an exchange-argument optimum for a fixed batch.)

12. In the child, before `execvp`:
   ```python
   fd = os.open("out.txt", os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 0o644)
   os.dup2(fd, 1)        # make stdout (fd 1) point at the file
   os.close(fd)
   os.execvp(argv[0], argv)
   ```
   It must happen *before* `execvp` because `execvp` replaces the entire process image, but the **file-descriptor table survives the exec**. So we rewire fd 1 first; then the new program, which writes to fd 1 as usual, transparently writes into the file. After exec it'd be too late (the new program is already running with the wrong stdout).

## Teach it back

1. **What is the kernel/user-space boundary, and how does a program cross it?** User mode is unprivileged (can't touch hardware or other processes' memory); kernel mode is privileged. A program crosses *only* via a **system call**, a controlled trap that switches to kernel mode at a fixed entry point, where the kernel validates the request, does the privileged work, and returns. Every file/network/process operation bottoms out in syscalls (watchable with `strace`/`dtruss`).

2. **What does "preemptive scheduling" mean and what hardware makes it possible?** A periodic **timer interrupt** forcibly returns control to the kernel, so no process can monopolize the CPU; the scheduler then picks the next ready process (e.g., round-robin time slices). Without the timer interrupt, a buggy infinite loop could freeze the whole machine.

3. **Why does virtual memory exist, and what is a page fault?** It gives each process an isolated, contiguous-looking address space (so processes can't address each other's RAM), lets virtual pages map to scattered physical frames, and allows over-commit via swap. A **page fault** is a trap when a process accesses a virtual page not in a physical frame; the kernel loads it from disk (major) or maps a fresh frame (minor). An access to an *unmapped* address is a segfault, the kernel kills the process.

4. **What's in an inode, and what's NOT?** An inode holds a file's metadata (type, permissions, owner, size, timestamps, link count) and pointers to its data blocks. It does **not** hold the file's name, names live in directories, which map names → inode numbers. This separation is what makes hard links (multiple names, one inode) possible.

5. **Decode `chmod 750` and explain what `x` means on a directory.** `750` = owner `rwx` (7), group `r-x` (5), others `---` (0). On a *directory*, `x` means permission to traverse into it / access its entries; without `x` you can't `cd` into it even if you can read the listing.

6. **Why must `cd` be a shell builtin instead of an external command?** Because the shell runs external commands by `fork`+`exec` in a *child* process. A child's `chdir` would only change the child's working directory, which dies with the child, leaving the shell's directory unchanged. So `cd` must run in the shell process itself. (Same reasoning applies to `exit`, `export`, etc.)
