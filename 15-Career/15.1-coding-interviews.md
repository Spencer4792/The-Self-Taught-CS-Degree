# Chapter 15.1 - Cracking the Coding Interview (the patterns)

> Goal: Turn the coding interview from a terrifying lottery into a solvable, repeatable skill. By the end of this chapter I understand how the interview pipeline actually works, I can recognize a problem's *pattern* from its signals, I have a structured way to solve any problem out loud, and I have an 8-week study plan with a curated ~100-problem list grouped by pattern. The whole book up to here gave me the data structures (Part 2) and algorithms (Part 3); this chapter is about *deploying* them under pressure.

Here's the thing I had to accept early: the coding interview is not a test of whether I'm a good engineer. It's a test of a *specific, learnable skill*, recognizing a small set of patterns fast, then implementing them cleanly while narrating my thinking. I already wrote BFS, DFS, DP, heaps, and hash tables from scratch in Parts 2-3. The gap between "I understand these" and "I can wield these in 35 minutes with someone watching" is exactly what this chapter closes.

Good news: there are maybe **13 patterns** that cover the overwhelming majority of questions. Learn to see them and you've turned an infinite problem space into a finite one.

## 📐 How the interview actually works

The pipeline for an entry-level (new-grad / junior) software role is roughly:

```
1. APPLICATION / REFERRAL        (covered in 15.3)
2. RECRUITER SCREEN              15-30 min, non-technical, "are you real + interested"
3. ONLINE ASSESSMENT (OA)        60-90 min, auto-graded, 1-3 problems on HackerRank/
                                  Codility/CodeSignal. Often the real first filter.
4. PHONE / VIDEO SCREEN          45-60 min, 1-2 coding problems, live, with a human,
                                  in a shared editor (CoderPad/HackerRank/Google Docs).
5. ONSITE / VIRTUAL "LOOP"       3-5 back-to-back interviews:
                                    • 2-3 coding rounds (the patterns below)
                                    • 1 system design (lighter for new-grad - Ch 15.2)
                                    • 1 behavioral (Ch 15.3)
6. HIRING COMMITTEE / OFFER      they debrief, decide, then negotiation (Ch 15.3)
```

What each stage is really testing:

- **OA**: Can you produce a *correct, passing* solution unaided, fast? Pure coding + pattern recognition. No partial credit for "good reasoning", the tests pass or they don't. Practice for OAs by doing timed problems.
- **Phone screen**: Same problems, but now they grade *communication* too. Can you clarify, talk through tradeoffs, and write clean code while a human watches?
- **Onsite coding**: The bar is highest. They want correctness, clean code, complexity analysis out loud, edge-case handling, and the ability to take a hint gracefully.

> 💼 The single biggest use point for a new grad: **the online assessment is often the hardest filter**, because it's purely you vs. the clock with no interviewer to throw you a lifeline. If you can crush timed OAs, the live rounds feel easier because now there's a human who *wants* you to succeed.

### What interviewers actually score

After every round, the interviewer fills out a rubric. It almost always has these axes:

1. **Problem solving**, did you find a working approach? Did you improve it?
2. **Coding**, is the code clean, correct, idiomatic, bug-free?
3. **Communication**, did you think aloud, clarify, explain tradeoffs?
4. **Complexity**, can you analyze time/space and reason about it?

Notice that **only #2 is "can you code."** Three of the four axes are about *how you think and communicate*. A candidate who talks through a clean O(n) solution beats a silent candidate who types a clever O(log n) solution nobody understood. I had to internalize that: **this is a conversation that happens to involve code.**

## 📐 How to practice effectively (quality over grinding)

The number one mistake is grinding hundreds of problems passively, reading the solution after 10 minutes, nodding, moving on. That builds the *illusion* of competence and none of the real thing (exactly the trap the whole book's "read with your hands" rule fights).

The principles I hold myself to:

**1. ~100-150 quality problems beats 500 rushed ones.** Past ~150 well-understood problems, you're in diminishing returns. Depth on the patterns is what transfers.

**2. Struggle first, then peek, with a timer.** Give every problem an honest **25-35 minutes** of real effort before looking at anything. The struggle is where learning happens; reading a solution you didn't fight for teaches almost nothing.

**3. The "peek the hint, not the solution" rule.** If stuck, reveal *one* nudge (the pattern name, or the key data structure), then go back to solving. Only read the full solution after you've either solved it or genuinely exhausted yourself.

**4. Re-solve, don't re-read (spaced repetition).** A problem isn't "done" the first time you solve it. Tag it and re-solve from a blank file after **1 day, then 1 week, then 1 month**. If you can't re-derive it cold, you never owned it. I keep this in a simple spaced-repetition log:

```
Problem            First solved   Re-solve 1d   Re-solve 1w   Re-solve 1m   Confident?
Two Sum            2026-01-03     ✓             ✓             ✓             yes
Course Schedule    2026-01-05     ✗ (forgot)    ✓             pending       no
```

**5. Learn by pattern, not randomly.** Do 6-10 problems of the *same pattern* back-to-back. The pattern fuses into a reflex. Random practice from day one just feels like flailing.

**6. Always say the complexity out loud, every time.** Even when practicing alone. It has to be automatic by interview day.

> ⚠️ Common mistakes when practicing
> - **Copy-typing solutions.** You learn nothing. Solve from a blank file.
> - **Skipping the re-solve.** First-solve recall is fool's gold; one month later it's gone.
> - **Only doing Easy problems** because they feel good. The interview is Mediums.
> - **Only doing Hard problems** to feel hardcore. Most interviews are Medium; Hards waste your time and crush morale.
> - **Practicing silently.** If you never talk while solving, you'll freeze when you have to do both at once.

## 📐 The core patterns (signals → approach → worked example)

This is the heart of the chapter. For each pattern: **when to reach for it** (the signal), the core idea, and a worked example with complexity. Most map directly back to a data structure or algorithm I already built earlier in the book.

### 1. Two Pointers

**Signal:** A **sorted array** (or one you can sort), or a problem about **pairs/triples** that satisfy a condition, or comparing from both ends. Also: in-place array manipulation, palindromes.

**Idea:** Use two indices that move toward each other (or in the same direction) so you scan in O(n) instead of checking all O(n²) pairs.

**Worked example, Two Sum on a sorted array.** Given a sorted array, find two numbers that add to `target`.

```python
def two_sum_sorted(nums, target):
    lo, hi = 0, len(nums) - 1
    while lo < hi:
        s = nums[lo] + nums[hi]
        if s == target:
            return [lo, hi]
        if s < target:        # need bigger sum -> move left pointer up
            lo += 1
        else:                 # need smaller sum -> move right pointer down
            hi -= 1
    return []
# Time O(n), Space O(1). The sortedness is what lets each comparison eliminate
# a whole pointer move instead of a whole pass.
```

### 2. Sliding Window

**Signal:** "**contiguous** subarray / substring," and a constraint like "longest/shortest/at most K/sum equals." If you catch yourself wanting nested loops over a contiguous range, it's almost always a window.

**Idea:** Maintain a window `[left, right]`. Expand `right` to include elements; when the window violates the constraint, shrink from `left`. Each element enters and leaves once → O(n).

**Worked example, longest substring without repeating characters.**

```python
def longest_unique(s):
    seen = {}            # char -> last index seen
    left = best = 0
    for right, c in enumerate(s):
        if c in seen and seen[c] >= left:
            left = seen[c] + 1      # jump left past the duplicate
        seen[c] = right
        best = max(best, right - left + 1)
    return best
# Time O(n), Space O(min(n, alphabet)). The window never moves backwards.
```

### 3. Fast & Slow Pointers (Floyd's tortoise/hare)

**Signal:** **Linked lists** (cycle detection, finding the middle, finding the start of a cycle), or "is there a cycle" on any functional graph. (Pairs with Part 2.2.)

**Idea:** One pointer moves 1 step, the other moves 2. If there's a cycle they meet; the middle is where slow lands when fast hits the end.

**Worked example, detect a cycle in a linked list.**

```python
def has_cycle(head):
    slow = fast = head
    while fast and fast.next:
        slow = slow.next
        fast = fast.next.next
        if slow is fast:
            return True
    return False
# Time O(n), Space O(1) - no hash set of visited nodes needed.
```

### 4. Hashing for O(1) Lookups

**Signal:** "Have I **seen** this before?", counting frequencies, grouping, complement lookups, deduping. The most common pattern of all. (Part 2.4, I built this from scratch.)

**Idea:** Trade space for time. A dict/set turns an O(n) "is it in here" scan into O(1).

**Worked example, Two Sum (unsorted).**

```python
def two_sum(nums, target):
    seen = {}                  # value -> index
    for i, x in enumerate(nums):
        if target - x in seen: # complement already seen?
            return [seen[target - x], i]
        seen[x] = i
    return []
# Time O(n), Space O(n). Classic time-space tradeoff.
```

### 5. Binary Search (including "on the answer")

**Signal:** A **sorted** structure, OR a problem where you can ask a yes/no question that's *monotonic* ("if X works, does X+1 work?"). The second form, binary search on the answer, is the one that separates strong candidates. (Part 3.3.)

**Idea:** Halve the search space each step → O(log n). For "on the answer": you're not searching the array, you're searching the *space of possible answers* using a feasibility check.

**Worked example, minimum eating speed (binary search on the answer).** Koko eats `piles` of bananas; she eats `k` per hour. Find the smallest `k` that lets her finish in `H` hours.

```python
import math
def min_eating_speed(piles, H):
    def hours_needed(k):
        return sum(math.ceil(p / k) for p in piles)

    lo, hi = 1, max(piles)         # answer space, not the array
    while lo < hi:
        mid = (lo + hi) // 2
        if hours_needed(mid) <= H: # feasible -> try slower
            hi = mid
        else:                      # too slow -> must eat faster
            lo = mid + 1
    return lo
# Time O(n log(max pile)). The monotonic check "can she finish at speed k?" is the key.
```

### 6. BFS / DFS (graphs & trees)

**Signal:** Trees, graphs, grids, "connected components," "shortest path in an unweighted graph" (BFS), "all paths / does a path exist / explore fully" (DFS), level-order traversal (BFS). (Parts 2.5, 2.7, 3.4.)

**Idea:** BFS uses a queue, explores level by level → shortest path in unweighted graphs. DFS uses recursion/stack, goes deep → good for exhaustive exploration and connectivity.

**Worked example, number of islands (DFS on a grid).**

```python
def num_islands(grid):
    if not grid: return 0
    rows, cols = len(grid), len(grid[0])

    def sink(r, c):
        if 0 <= r < rows and 0 <= c < cols and grid[r][c] == "1":
            grid[r][c] = "0"                 # mark visited
            for dr, dc in ((1,0),(-1,0),(0,1),(0,-1)):
                sink(r + dr, c + dc)

    count = 0
    for r in range(rows):
        for c in range(cols):
            if grid[r][c] == "1":
                count += 1
                sink(r, c)                   # drown the whole island
    return count
# Time O(rows*cols), Space O(rows*cols) worst case for recursion stack.
```

### 7. Backtracking

**Signal:** "Generate **all** combinations / permutations / subsets," constraint-satisfaction (Sudoku, N-Queens), "find all ways to..." (Part 3.6.)

**Idea:** Build a candidate incrementally; at each step try every option, recurse, then **undo** (backtrack) and try the next. It's DFS over the space of partial solutions.

**Worked example, all subsets (the power set).**

```python
def subsets(nums):
    res = []
    def backtrack(start, path):
        res.append(path[:])              # record current subset
        for i in range(start, len(nums)):
            path.append(nums[i])         # choose
            backtrack(i + 1, path)       # explore
            path.pop()                   # un-choose (backtrack)
    backtrack(0, [])
    return res
# Time O(n * 2^n) - 2^n subsets, O(n) to copy each.
```

### 8. Dynamic Programming

**Signal:** "Number of ways," "min/max cost to reach," "can you partition/make," problems with **overlapping subproblems** and **optimal substructure**, or where a greedy choice fails. (Part 3.5, I derived this in depth.)

**Idea:** Define a state, write the recurrence (how a state depends on smaller states), then either memoize (top-down) or build a table (bottom-up). The art is *defining the state*.

**Worked example, climbing stairs / Fibonacci (the DP "hello world").** Ways to climb `n` stairs taking 1 or 2 steps.

```python
def climb_stairs(n):
    # state: ways[i] = number of ways to reach step i
    # recurrence: ways[i] = ways[i-1] + ways[i-2]
    a, b = 1, 1                  # ways to reach step 0 and step 1
    for _ in range(2, n + 1):
        a, b = b, a + b         # roll the window, O(1) space
    return b
# Time O(n), Space O(1). Recognizing "ways to reach n" => DP is the whole game.
```

> The DP problem-solving recipe I drill: **(1)** brute-force recursion first; **(2)** spot the repeated subproblems; **(3)** add memoization; **(4)** *optionally* convert to bottom-up table; **(5)** *optionally* reduce space. Get to step 3 and you've already passed most interviews.

### 9. Heap / Top-K

**Signal:** "Top K," "K largest/smallest," "K closest," "median of a stream," "merge K sorted things." Any time you need the *extreme* elements without fully sorting. (Part 2.6.)

**Idea:** A heap gives you the min/max in O(1) and insert/pop in O(log k). For "top K," keep a heap of size K → O(n log k), beating a full O(n log n) sort.

**Worked example, K largest elements.**

```python
import heapq
def k_largest(nums, k):
    return heapq.nlargest(k, nums)
    # under the hood: a min-heap of size k. Push each element; if heap > k, pop
    # the smallest. What survives is the k largest. O(n log k) time, O(k) space.
```

### 10. Intervals

**Signal:** Inputs that are `[start, end]` pairs, "merge overlapping," "can attend all meetings," "insert interval," "minimum rooms." (Often pairs with sorting + a heap.)

**Idea:** **Sort by start.** Then sweep left to right; two intervals overlap when `current.start <= previous.end`.

**Worked example, merge overlapping intervals.**

```python
def merge(intervals):
    intervals.sort(key=lambda iv: iv[0])    # sort by start
    merged = [intervals[0]]
    for start, end in intervals[1:]:
        if start <= merged[-1][1]:          # overlaps the last merged one
            merged[-1][1] = max(merged[-1][1], end)
        else:
            merged.append([start, end])
    return merged
# Time O(n log n) (the sort dominates), Space O(n).
```

### 11. Stack / Monotonic Stack

**Signal:** "Matching/valid parentheses," "next greater/smaller element," "largest rectangle," anything where you process and need to remember/undo recent items, or expression evaluation. (Part 2.3.)

**Idea:** A plain stack for nesting/matching. A **monotonic** stack (kept increasing or decreasing) answers "next greater/smaller element" in one O(n) pass.

**Worked example, next greater element (monotonic stack).** For each element, find the next element to its right that's larger.

```python
def next_greater(nums):
    res = [-1] * len(nums)
    stack = []                       # holds indices, values decreasing
    for i, x in enumerate(nums):
        while stack and nums[stack[-1]] < x:
            res[stack.pop()] = x     # x is the "next greater" for those indices
        stack.append(i)
    return res
# Time O(n) - each index is pushed and popped at most once. Space O(n).
```

### 12. Prefix Sums

**Signal:** Many queries about **subarray sums/ranges**, "subarray sums to K," "range sum," running totals. (Pairs with hashing.)

**Idea:** Precompute cumulative sums so any range sum is an O(1) subtraction: `sum(i..j) = prefix[j+1] - prefix[i]`.

**Worked example, count subarrays summing to K (prefix sum + hash).**

```python
def subarray_sum(nums, k):
    count = 0
    running = 0
    seen = {0: 1}                    # prefix-sum 0 has occurred once (empty prefix)
    for x in nums:
        running += x
        count += seen.get(running - k, 0)   # how many earlier prefixes give a window = k
        seen[running] = seen.get(running, 0) + 1
    return count
# Time O(n), Space O(n). The combo of prefix sum + hash map is a top-5 interview move.
```

### 13. Greedy

**Signal:** "Maximize/minimize" where a **locally optimal choice is provably globally optimal**, scheduling, interval selection, jump games, assigning resources. (Part 3.6.)

**Idea:** Make the best choice at each step without reconsidering. The hard part is *proving* greedy works (often via an exchange argument); when it doesn't, you fall back to DP.

**Worked example, jump game (can you reach the end?).**

```python
def can_jump(nums):
    farthest = 0
    for i, jump in enumerate(nums):
        if i > farthest:            # can't even reach index i
            return False
        farthest = max(farthest, i + jump)   # greedily extend reach
    return True
# Time O(n), Space O(1). Greedy works because reach only ever needs the max so far.
```

> ⚠️ Greedy is the riskiest pattern, it *feels* right and is often *wrong*. If you can't argue why the local choice is safe, suspect DP instead.

## 📐 UMPIRE - a structured way to solve any problem live

Under pressure, having a *procedure* keeps me from freezing. I use **UMPIRE**:

```
U - UNDERSTAND   Restate the problem. Ask clarifying questions. Confirm input
                 types, ranges, duplicates, empty input, what to return.
M - MATCH        Which pattern(s) does this match? Say the signals out loud.
P - PLAN         Describe the approach in plain English BEFORE coding. Walk a tiny
                 example. Get a nod from the interviewer.
I - IMPLEMENT    Write clean code, narrating as you go. Meaningful names.
R - REVIEW       Trace your code on an example line by line. Hunt edge cases.
E - EVALUATE     State time & space complexity. Discuss tradeoffs / improvements.
```

The amateur move is to jump straight to **I**. The strong-candidate move is to spend real time on **U**, **M**, and **P**, that's where the interviewer decides whether you're a thinker or a code-monkey. **Never write a line of code before the interviewer agrees with your plan.**

### How to communicate while coding

This is graded as heavily as the code. My rules:

- **Think aloud constantly.** "I'm reaching for a hash map here because I need O(1) lookups of the complement..." Silence reads as being stuck.
- **Clarify early.** "Can the array be empty? Are there duplicates? Are values bounded? Should I return the index or the value?" Each question shows maturity and prevents wrong solutions.
- **State the brute force first**, then improve. "The naive approach is O(n²) checking all pairs; I can do better with a hash map in O(n)." This shows range and gets you a correct baseline on the board.
- **Announce complexity out loud**, unprompted, when you finish: "This is O(n) time, O(n) space because of the hash set."
- **Narrate edge cases** as you handle them: "I'll guard against an empty input here."

### Handling getting stuck (it will happen)

Being stuck is normal and *survivable*, how you handle it is itself graded:

1. **Say what you know and what's blocking you.** "I know this needs the K-largest, so a heap fits, but I'm not sure how to handle ties." This invites a hint and shows structured thinking.
2. **Go back to a concrete example** and work it by hand. The mechanical insight you need often falls out.
3. **Try the brute force.** A working O(n²) solution beats an elegant blank screen. You can optimize after.
4. **Take the hint gracefully.** Interviewers *want* to give hints, taking one well (not defensively) is a positive signal. "Oh, that's the nudge I needed, thank you" is a great response.
5. **Don't go silent.** Five seconds to think is fine; thirty seconds of silence is a red flag. Narrate even your confusion.

### Analyzing time/space out loud

A clean way to say it (cross-link Part 1.4):

> "This loop runs n times, and inside it the hash lookup is O(1) amortized, so it's **O(n) time**. I'm storing up to n entries in the map, so **O(n) space**. I could trade space for time by... / The bottleneck is the sort at O(n log n), which dominates the linear scan."

Naming the *dominant* term and *why* is what they're listening for.

### Mock-interview practice tips

The single highest-ROI activity in the last 2 weeks:

- **Use a real shared editor with no autocomplete** (CoderPad, or even Google Docs). Interview editors are bare, practicing in your IDE with autocomplete builds a false sense of fluency.
- **Get a human in the loop**: a friend, [Pramp](https://www.pramp.com), or [interviewing.io](https://interviewing.io). They mock you, you mock them. Practicing the *communication* under a watching human is irreplaceable.
- **Record yourself solving out loud** (just your voice). Play it back. You'll hear every place you went silent or hand-waved.
- **Time-box hard**: 35 minutes per problem, including narration. The clock is part of the skill.
- **Practice the opening 2 minutes** until it's a script: restate, clarify, state approach. A confident opening sets the tone for the whole round.

## 🧪 Mini-project - Build your Pattern Playbook + cheat sheet

Two artifacts I keep in my interview-prep repo and re-read before every loop.

### Part A - The Pattern Playbook (one entry per pattern)

Create `pattern-playbook.md`. For **each of the 13 patterns**, fill in a card. The act of writing it in *your own words* is the point, don't copy mine.

```markdown
## Pattern: <name>

**Signals that scream this pattern:**
- ...
- ...

**Core idea (one sentence):**
...

**Template (pseudocode I can write from memory):**
\`\`\`
...
\`\`\`

**Typical complexity:** time O(...), space O(...)

**My go-to example problem:** <name> - <one-line of the trick>

**Where I usually slip up:** ...
```

Fill it in by re-deriving each pattern from a blank file, not by copying. By the time all 13 cards are done in your words, you've half-internalized the whole interview.

### Part B - The 1-page cheat sheet (signals → approach)

A single page you can scan in 60 seconds before a round. Compress the table:

```
SIGNAL IN THE PROBLEM                          ->  REACH FOR
-------------------------------------------------------------------------
sorted array / pairs from both ends            ->  Two Pointers
contiguous subarray/substring + constraint     ->  Sliding Window
linked list cycle / middle                     ->  Fast & Slow Pointers
"seen before?" / counts / complement / dedupe  ->  Hashing
sorted, OR monotonic yes/no on the answer      ->  Binary Search (+on answer)
tree/graph/grid, shortest unweighted path      ->  BFS
tree/graph/grid, explore fully / connectivity  ->  DFS
"all combinations/permutations/subsets"        ->  Backtracking
"# ways" / "min/max cost" / overlapping subs   ->  Dynamic Programming
"top/closest K" / "median of stream"           ->  Heap / Top-K
inputs are [start, end] pairs                   ->  Intervals (sort first)
matching/nesting / next greater-smaller        ->  Stack / Monotonic Stack
many range-sum / subarray-sum queries          ->  Prefix Sums
local optimal seems globally optimal           ->  Greedy (then verify!)
```

Print it. Tape it above your desk for the 8 weeks. By the end you won't need it, and that's how you'll know you're ready.
