# Chapter 15.2 - System Design Interviews (entry-level)

> Goal: Walk into a junior/new-grad system design round and *drive* a structured conversation from requirements to a defensible architecture, without pretending to be a staff engineer. By the end I have a reusable answer template, the building-block vocabulary at my fingertips, three fully worked junior-level walkthroughs (URL shortener, Twitter-lite, rate-limited API), and the "design a class / OOP" style covered too. This chapter leans hard on **Part 9** (I already built every component there); here it's about *narrating the composition under interview conditions*.

The first thing to get straight: **at the entry level, nobody expects you to design Google.** The bar is *much* lighter than for a senior. What they're actually checking is:

- Can you **structure** an open-ended problem instead of panicking?
- Do you know the **building blocks** (load balancer, cache, database, queue) and *roughly* when each applies?
- Can you **reason about tradeoffs** at all, even simply?
- Can you **drive the conversation**, ask clarifying questions, make decisions, and explain them?

A new grad who calmly says "let me clarify the requirements, estimate the scale, sketch an API, then a high-level diagram, then go deeper on the hard part" has already passed the structure bar, which is most of the battle. You are *not* expected to know exact DynamoDB throughput numbers or design multi-region failover. You *are* expected to not freeze.

> 💼 The trap for new grads is the opposite of the coding round. In coding you can over-talk; in design you can **under-structure**. Show them a framework and stick to it religiously. Structure *is* the signal here.

## 📐 The framework (cross-link Part 9.6)

This is the exact path from Chapter 9.6, which I treat as a checklist I say out loud:

```
1. REQUIREMENTS   functional (what it does) + non-functional (scale, latency,
                  availability, consistency). ASK CLARIFYING QUESTIONS FIRST.
2. SCOPE          explicitly cut features. "I'll focus on X and Y; Z is out of scope
                  unless you want it." Shows judgment + protects your time.
3. ESTIMATES      back-of-envelope (Ch 9.1): QPS (avg + peak), storage, bandwidth.
                  These numbers JUSTIFY your later choices.
4. API            define the key endpoints / method signatures. Forces clarity.
5. DATA MODEL     entities + access patterns, THEN pick storage to fit the patterns.
6. HIGH-LEVEL     boxes + arrows: client -> CDN -> LB -> app -> cache/db/queue.
7. DEEP DIVE      zoom into the 1-2 hardest parts (the interviewer will steer this).
8. BOTTLENECKS    find the limiting resource; add cache/replica/shard/queue.
9. TRADEOFFS      say what you optimized for and what you gave up. Be explicit.
```

The two rules I never break (also from 9.6): **requirements before solutions** (don't design for a billion users when they said a thousand), and **estimates before architecture** (the math *tells* you whether you even need a cache or a shard).

For a ~35-minute junior round, a healthy time budget is roughly:

```
Requirements + scope   ~6 min     <- do NOT skip; this is where you show structure
Estimates              ~4 min
API + data model       ~7 min
High-level diagram     ~8 min
Deep dive (their pick) ~7 min
Tradeoffs + wrap       ~3 min
```

### Building blocks recap (the vocabulary)

Each of these I built or studied in Part 9. In the interview I just need to *name the right one for the right pressure*:

| Block | Solves | Built in | One-liner I say |
|---|---|---|---|
| **Load balancer** | many app servers → one service; survive node death | 9.3 | "L7 LB with health checks distributes traffic across stateless app servers." |
| **Cache** (Redis) | read-heavy load on the DB; latency | 9.2 | "Cache hot reads in Redis; cache-aside, with a TTL to bound staleness." |
| **CDN** | geographic latency; static/egress | 9.2 | "Serve static assets and cacheable GETs from the edge." |
| **DB + read replicas** | durable storage; scale reads | 7.x, 9.6 | "Primary takes writes; async read replicas scale reads (eventual consistency)." |
| **Queue** (Kafka/SQS) | slow/spiky/fan-out work; decoupling | 9.5 | "Push slow work to a queue; workers process async, smooths spikes." |
| **Rate limiter** | abuse/overload protection | 9.4 | "Token-bucket rate limiter at the gateway, keyed per user/IP." |
| **Sharding** | data/writes exceed one DB | 7.4 | "Shard by key (e.g., user_id) when one primary can't hold it." |

The recurring move (straight from 9.6): **find the bottleneck, apply the cheapest block that relieves it.** Reads hot → cache, then replicas. Writes hot → shard or queue+batch. Geography → CDN. Spikes → queue + autoscale. Abuse → rate limit.

### How to drive the conversation (clarifying questions)

You should *lead*, not wait to be fed. Open every design with clarifying questions. A reliable bank of them:

- **Scope**: "What are the core features I should focus on? Anything explicitly out of scope?"
- **Scale**: "Roughly how many users / requests per day? Read-heavy or write-heavy?"
- **Latency/availability**: "Is this latency-sensitive? How available does it need to be?"
- **Consistency**: "Is it OK if data is briefly stale, or does it need to be strongly consistent?"
- **Constraints**: "Any constraints on tech stack, regions, or budget?"

Then **restate what you heard** before designing: "OK, so it's a read-heavy service for ~1M daily users, latency matters for reads, and brief staleness is acceptable. Let me estimate the scale." That restatement is a strong signal all by itself.

## 💻 Three worked junior-level walkthroughs

I'll write these the way I'd *actually answer them*, narrating the reasoning, not just listing components.

### Design A - URL Shortener (the classic warm-up)

**Requirements (after clarifying).**
- Functional: `shorten(long_url) -> short_code`; `GET /{code} -> 301 redirect`. Optional: custom alias, expiry, click count.
- Non-functional: redirects must be **very low latency** (they sit in the user's click path) and **highly available**. Read-heavy. Links effectively permanent.

> "Let me confirm scope, I'll focus on shortening and redirecting; analytics I'll mention but treat as secondary."

**Estimates.** "Say 100M new links/month, and reads are ~100x writes (people click far more than they create). That's ~40 writes/sec average and ~4,000 reads/sec average, call it ~10k reads/sec at peak. Storage: 100M links/month × ~500 bytes × a few years ≈ low terabytes, fits in a single sharded DB. The takeaway: **read-heavy, modest write volume, so caching matters a lot, sharding maybe later.**"

**API.**
```
POST /shorten   { "long_url": "...", "alias": "?" }  -> { "short_url": "abc123" }
GET  /{code}                                          -> 301 Location: <long_url>
```

**Data model.** A single table; access pattern is "look up by code" → a key-value shape is ideal.
```
links( code PK, long_url, created_at, expires_at?, click_count )
```

**Generating the code.** Two clean options I'd offer:
1. **Base62 of an auto-increment ID**, take a counter, encode in `[0-9a-zA-Z]`. 7 chars of base62 = 62^7 ≈ 3.5 trillion codes. Simple, no collisions. Downside: codes are guessable/sequential.
2. **Random + collision check**, generate a random 7-char code, check the DB, retry on the rare collision. Non-sequential. Downside: a read on write.

"I'd go with **base62 of a counter** for simplicity and zero collisions, noting the guessability tradeoff."

**High-level diagram.**
```
client -> CDN (not really needed; redirects aren't cacheable safely) 
       -> Load Balancer -> [app servers] -> Redis cache (code -> long_url)
                                              |  (miss)
                                              v
                                          Database (links table)
```

**Deep dive, making redirects fast (the whole point).** "Redirects are read-heavy and latency-critical, so I cache `code -> long_url` in Redis. Hit rate will be high because link popularity is heavily skewed (a few links get most clicks). On a miss, read the DB and populate the cache. Writes are cheap, so the DB primary handles them; reads scale via cache first, read replicas second."

**Bottlenecks & tradeoffs.** "The read path is the pressure point, relieved by the cache. If write volume grew, I'd shard the `links` table by `code`. I optimized for **read latency and availability**, accepting that analytics (click counts) can be **eventually consistent**, I'd increment counts async via a queue rather than on the hot redirect path."

### Design B - Twitter-lite / a simple feed (a step up)

**Requirements.** Post a short message; follow users; see a home feed of people you follow, newest first. Out of scope (I'd say so): DMs, search, media transcoding, ads.

**Estimates.** "Say 10M daily active users, each posts ~2/day → ~20M posts/day ≈ ~230 writes/sec. Reads dominate hugely, people scroll far more than post, so call it ~10-50x reads. **Read-heavy with fan-out** is the defining characteristic, which makes *feed generation* the interesting problem."

**API.**
```
POST /tweets         { "text": "..." }        -> { "id": ... }
POST /follow         { "user_id": ... }
GET  /feed?cursor=   ->  [ tweets, newest first ]
```

**Data model.**
```
users(   id PK, handle, name )
tweets(  id PK, author_id, text, created_at )      -- index on (author_id, created_at)
follows( follower_id, followee_id )                 -- who follows whom
```

**The key decision, fan-out on write vs. read.** This is the deep dive interviewers want:
- **Fan-out on read (pull):** at feed time, fetch tweets from everyone you follow, merge by time. Simple writes, but feed reads are expensive (and reads dominate, bad).
- **Fan-out on write (push):** when you tweet, push the tweet id into each follower's precomputed feed list (in Redis). Feed reads become a cheap O(1) lookup. Costs more at write time and storage.

"Since the system is read-heavy, I'd favor **fan-out on write** so the common operation (reading the feed) is cheap. **But** I'd call out the *celebrity problem*: a user with 50M followers would trigger 50M writes per tweet. The standard fix is a **hybrid**, fan-out on write for normal users, and **fan-out on read for celebrities** (merge their tweets in at read time). That hybrid is exactly the kind of tradeoff awareness they're listening for."

**High-level diagram.**
```
client -> LB -> [app servers] --write--> tweets DB (primary)
                     |                        |
                     |                   (async via queue, Ch 9.5)
                     v                        v
              Redis feed lists  <----  fan-out workers push tweet ids to followers
                     ^
              GET /feed reads precomputed list (fast)
```

**Tradeoffs.** "Optimized for **feed read latency**. Accepted **eventual consistency**, a new tweet may take a second or two to appear in followers' feeds (fine for a social feed; a 1-2s delay is invisible). Used a **queue** to do fan-out async so posting stays fast. This is the same eventual-vs-strong reasoning from 9.6: a stale feed is fine; a wrong bank balance is not."

### Design C - A rate-limited API (ties directly to 9.4)

**Requirements.** Protect an API so each client gets at most N requests per window (say 100 req/min). Must be low-latency (it's on every request) and work across many app servers.

**Estimates.** "If the API does 10k req/sec, the limiter runs 10k times/sec, so it must be **O(1) and in-memory-fast**. That rules out hitting a SQL DB per request; it points at Redis."

**The algorithm (from 9.4).** "I'd use a **token bucket**: each client has a bucket of N tokens that refills at a steady rate. Each request spends a token; empty bucket → reject with `429 Too Many Requests`. It's O(1), allows short bursts, and is easy to reason about. Alternatives: fixed window (simple but has boundary bursts), sliding window log (accurate but more memory)."

**The distributed problem (the deep dive).** "With many app servers, a per-server in-memory counter is wrong, a client could get N requests *per server*. So the counter must be **shared in Redis**, keyed by client id. To avoid race conditions between the read and the decrement, I'd do it atomically, a small **Lua script** or `INCR` with `EXPIRE`, so the check-and-decrement is one atomic operation. This is the classic 'distributed counter' issue and naming it is the signal."

**Diagram.**
```
client -> API Gateway / LB
             |  (before forwarding)
             v
         Rate Limiter middleware --INCR/check--> Redis (client_id -> tokens, TTL)
             |  allowed?
        yes  v                no -> 429 Too Many Requests + Retry-After header
         app servers
```

**Tradeoffs.** "Centralizing the counter in Redis adds a network hop per request, but it's sub-millisecond and gives *correct* global limits. I'd note Redis is now a dependency on the hot path, I'd mitigate with a Redis replica for HA, and a 'fail-open' policy (allow traffic if Redis is briefly down) so the limiter never takes the whole API down. I optimized for **correctness of the limit and low latency**, accepting one extra dependency."

### Common follow-ups (be ready for these)

Interviewers extend the design. Have a one-liner ready:
- **"How do you handle a server dying?"** → "Stateless app servers behind the LB with health checks; the LB routes around dead nodes. State lives in the DB/Redis, not the app."
- **"How do you scale reads?"** → "Cache first, read replicas second, shard last."
- **"How do you make it consistent?"** → "Reserve strong consistency for the few invariants that need it (money, uniqueness); default to eventual for everything else."
- **"What's your single point of failure?"** → identify it honestly (often the DB primary or Redis) and propose replication/failover.
- **"How would you monitor this?"** → "SLIs like p99 latency, error rate, cache hit rate; alert on SLO breach" (cross-link Part 13).

### Red flags to avoid

> ⚠️ Things that tank a junior design round
> - **Jumping straight to a diagram** without requirements or estimates. The #1 mistake.
> - **Buzzword salad**, naming Kafka, Kubernetes, and microservices with no reason. Only introduce a component when a *pressure* demands it.
> - **Over-engineering**, designing for a billion users when they said a thousand. Match the design to the scale.
> - **Going silent** while you think. Narrate. "I'm weighing fan-out on read vs write because..."
> - **No tradeoffs.** Every choice has a cost; saying the cost out loud is the whole point.
> - **Refusing to commit.** "It depends" forever reads as indecision. Make a call, state the assumption, move on.

## 📐 The OOP / "design a class" style (also common at entry level)

A very common *junior* variant isn't distributed systems at all, it's **object-oriented / low-level design**: "design a parking lot," "design an elevator," "design a deck of cards," "design a vending machine." They're testing clean OO modeling: identifying classes, responsibilities, relationships, and a sensible API, basically applied SOLID.

**The approach:**
```
1. CLARIFY      requirements + scope (same discipline as above).
2. IDENTIFY     the nouns -> candidate classes. The verbs -> methods.
3. RELATIONSHIPS  has-a (composition) vs is-a (inheritance). Prefer composition.
4. DEFINE       each class: fields + key methods + responsibilities.
5. ENUMS/STATE  model fixed sets (sizes, states) with enums.
6. API          show the main flow as method calls.
7. EXTEND       discuss how a new requirement would slot in (open/closed principle).
```

### Worked example - design a deck of cards

**Clarify.** "Standard 52-card deck? Do we need shuffle and deal? Multiple decks? I'll do a single standard deck with shuffle/deal."

**Nouns → classes:** `Suit` (enum), `Rank` (enum), `Card`, `Deck`. **Verbs → methods:** shuffle, deal.

```python
from enum import Enum
import random

class Suit(Enum):
    HEARTS = "♥"; DIAMONDS = "♦"; CLUBS = "♣"; SPADES = "♠"

class Rank(Enum):
    TWO = 2; THREE = 3; FOUR = 4; FIVE = 5; SIX = 6; SEVEN = 7
    EIGHT = 8; NINE = 9; TEN = 10; JACK = 11; QUEEN = 12; KING = 13; ACE = 14

class Card:
    def __init__(self, rank: Rank, suit: Suit):
        self.rank = rank
        self.suit = suit
    def __repr__(self):
        return f"{self.rank.name.title()} of {self.suit.name.title()}"

class Deck:
    def __init__(self):
        # composition: a Deck HAS-A list of Cards
        self.cards = [Card(r, s) for s in Suit for r in Rank]
    def shuffle(self):
        random.shuffle(self.cards)
    def deal(self, n=1):
        if n > len(self.cards):
            raise ValueError("Not enough cards left")
        dealt, self.cards = self.cards[:n], self.cards[n:]
        return dealt
    def remaining(self):
        return len(self.cards)
```

**How I'd narrate it:** "I modeled `Suit` and `Rank` as **enums** because they're fixed sets, that prevents invalid cards. A `Card` is immutable data. A `Deck` **has-a** list of cards (composition over inheritance), and exposes `shuffle`/`deal` as its responsibilities. To extend to **multiple decks** (like blackjack shoes), `Deck.__init__` would take a `num_decks` param and multiply the list, the rest of the API is unchanged, which satisfies the **open/closed principle**."

**The same recipe scales:** for a **parking lot** you'd have `ParkingLot has-a list of Levels`, each `Level has-a list of Spots`, a `Spot` has a `SpotSize` enum and an occupying `Vehicle`; `Vehicle` is a base class with `Car`/`Motorcycle`/`Truck` subclasses (the one place inheritance fits). The lot's API is `park(vehicle) -> ticket` and `leave(ticket)`. Narrating *why* each class exists and *which relationship* you chose is what scores.


### Part B - The pre-flight checklist

A short list I scan before answering, so I never skip a step under pressure:

```
[ ] Did I ask clarifying questions BEFORE designing?
[ ] Did I explicitly state what's IN and OUT of scope?
[ ] Did I do back-of-envelope estimates, and did they JUSTIFY my choices?
[ ] Did I define an API and a data model before the diagram?
[ ] Did I only add components that a real pressure demanded?
[ ] Did I name the bottleneck and how I relieve it?
[ ] Did I state at least one explicit tradeoff (optimized X, gave up Y)?
[ ] Did I keep narrating the whole time (never went silent)?
[ ] Did I match the design to the SCALE they gave me (no over-engineering)?
```

**Do this:** pick one system not worked above (a pastebin, a notification service, or a chat app), and fill in the entire template end to end as if mid-interview, out loud, in under 35 minutes. Then redo it a week later from a blank template. Same spaced-repetition principle as the coding patterns.
