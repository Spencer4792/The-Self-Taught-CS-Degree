# Chapter 15.4 - Capstone & Portfolio Projects

> Goal: Build the *proof* that gets you hired. Interviews ask you to claim you can build things; portfolio projects let you show it. By the end of this chapter you'll know what separates an impressive project from a forgettable tutorial clone, how to scope and actually *ship*, how to write a README that sells the work, and you'll have **six fully-specified capstone briefs** of increasing ambition that integrate skills from across the *entire* book, full-stack, data/ML, systems, and automation, each mapped to the chapters it exercises. This is where Parts 1-14 stop being knowledge and become evidence.

Here's an asymmetry that's easy to underrate: an interviewer can't verify "I'm good at backend development." They *can* click a link to a deployed app, read its README, and browse clean commits. **A shipped project is the highest-bandwidth proof you have.** It's also the single best source of behavioral stories (15.3) and the thing that makes a resume bullet (15.3) credible instead of a claim.

---

## 📐 Why portfolio projects get you hired

For an entry-level candidate, projects do three jobs at once:

1. **Proof over claims.** Anyone can write "proficient in React/FastAPI." A deployed full-stack app *demonstrates* it, no trust required.
2. **Interview fuel.** Every behavioral question ("a hard bug," "a tradeoff you made," "something you're proud of") gets a real, specific answer when you've shipped something real. Hand-wavy candidates lose to candidates who can say "let me tell you about the time NYX's pipeline silently dropped records."
3. **Differentiation.** Thousands of new grads have the same coursework. A genuinely interesting, deployed project is what makes a recruiter stop scrolling.

> 💼 The bar isn't "did you use a lot of tech." It's "did you solve a real problem, end to end, and ship it." One deployed, tested, well-documented project beats five half-finished repos every time.

### What makes a project impressive vs. forgettable

| Impressive | Forgettable |
|---|---|
| Solves a **real problem** you (or someone) actually has | A todo app / tutorial clone with the tutorial's exact features |
| **End-to-end**: data → logic → API → UI (or the full systems path) | A single script with no edges |
| **Deployed** with a live URL anyone can click | Only runs on your laptop |
| **Tested** (unit + a couple integration tests, CI green) | No tests, no CI |
| **Documented**, a README that explains the why, the how, and a demo | A README that just says the project name |
| **Version-controlled well**, clean history, meaningful commits (Part 11) | One commit "final version final2" |
| Shows a **decision/tradeoff** you can talk about | Nothing to discuss in an interview |

The killer is the **tutorial clone**: if an interviewer recognizes it as "the FreeCodeCamp weather app," it actively *hurts* you, it signals you can follow instructions, not solve problems. Take any tutorial and **change the problem** until it's yours: different domain, real data, a deployment, a feature the tutorial didn't have.

### How to scope and ship (the part everyone gets wrong)

The #1 reason projects die is **scope**, building forever, never shipping. The discipline (borrowing the MVP thinking from 15.2):

1. **Define the MVP brutally.** The smallest version that solves the core problem end to end. For a "track my expenses" app: add an expense, list expenses, see a total. That's it. *Not* budgets, categories, charts, multi-user, yet.
2. **Ship the MVP first, deployed.** A deployed ugly MVP beats a beautiful unfinished thing on localhost. Deploying early also surfaces the hard parts (env config, secrets, CORS) while the app is still small.
3. **Then add stretch features** one at a time, each its own branch/PR (Part 11), each deployed.
4. **Timebox it.** Give a capstone ~3-5 weeks of real effort. Open-ended projects rot.
5. **Test as you go**, not at the end. Even a handful of tests + green CI says "I work like a professional" (Parts 10.3, and the testing habits throughout).

> ⚠️ Scope traps: rewriting it in a new framework halfway; adding auth/payments/AI before the core works; polishing CSS before the feature exists; "I'll deploy at the end" (you won't, deploy in week 1).

### How to write a great README

The README is the first (often *only*) thing a reviewer reads. Treat it as the project's landing page. A strong structure:

```markdown
# Project Name
One-sentence pitch: what it does and who it's for.
[ Live demo ](url) · [ Screenshot/GIF right here - show it working ]

## The problem
What real problem this solves, in 2-3 sentences. (The "why".)

## Features
- bullet the actual capabilities (MVP + stretch)

## Tech stack & why
- Backend: FastAPI (chosen because ...)
- DB: PostgreSQL (chosen because ...)
- ... - note WHY, briefly. Shows judgment.

## Architecture
A simple diagram (boxes + arrows) or a few sentences on how pieces fit.

## Running it locally
Exact, copy-pasteable steps. `docker compose up` is ideal.

## Testing
How to run the tests; what's covered.

## What I learned / tradeoffs
The honest, interesting part. A hard problem you hit and how you solved it,
or a decision you'd revisit. THIS is what an interviewer reads and asks about.
```

The two highest-value pieces: a **visible demo (GIF/screenshot or live link)** at the top, and a **"what I learned / tradeoffs"** section at the bottom. The first earns the click; the second hands the interviewer their questions and you your STAR stories.

### How to talk about the project in an interview

Mirror 15.3's project framing: **problem → your role & key decisions → a hard part → result/learning.** Lead with the problem and the user, not a stack dump. Have ready: the hardest technical decision and its tradeoff (your 15.2 design thinking), one nasty bug you fixed (a behavioral story), and "what I'd do differently" (growth signal). Practice the 2-minute version out loud, you'll give it in nearly every interview.

### Project 1 - Full-stack CRUD + Auth app (the must-have)

**Problem.** A real productivity app, say a **personal expense tracker** or a **habit tracker**. Users sign up, log in, and manage their own private data. This is the bread-and-butter app every full-stack role wants to see you can build *correctly* (auth done right is the part most new grads botch).

**Features.**
- *MVP:* email/password signup + login (hashed passwords, JWT sessions); authenticated CRUD on the core entity (expenses/habits) scoped to the logged-in user; a React UI to do it all.
- *Stretch:* categories + filtering; a summary chart; pagination; password reset; OAuth login (Google); role-based access (admin view); rate limiting on auth endpoints.

**Tech stack.** FastAPI (Python) backend, PostgreSQL, React (TypeScript) frontend, Docker Compose for local dev, deployed via a container platform with a GitHub Actions CI/CD pipeline.

**Architecture sketch.**
```
React SPA  --HTTPS-->  FastAPI (auth middleware, REST endpoints)
                            |                    |
                       JWT verify           SQLAlchemy
                            |                    v
                      (per-user scoping)    PostgreSQL (users, items)
   [Docker Compose runs all locally; CI builds + tests + deploys on push to main]
```

**Chapters it exercises.** 8.1 (frontend), 8.2 (backend/REST/FastAPI), 8.3 (auth & permissions), 7.1-7.2 (relational schema, indexing), 10.1 (Docker), 10.3 (CI/CD), 11.1 (git workflow), 12.3 (web app security, hash passwords, prevent injection/XSS). Bonus: 9.4 if you add rate limiting.

**Milestones.**
1. Week 1: schema + FastAPI CRUD (no auth yet) + Docker Compose + a few pytest tests + deploy the bare API.
2. Week 2: add auth (hashing, JWT, per-user scoping) + protect endpoints.
3. Week 3: React UI for signup/login/CRUD, wired to the API.
4. Week 4: one stretch feature (chart or filtering) + CI/CD green + README + demo GIF.

**How to present it.** Live demo link + a GIF of the login→CRUD flow at the top of the README. In interviews, talk about *how you secured it*: password hashing (bcrypt), JWT expiry, and scoping every query to the authenticated user (the classic IDOR bug, Part 12.3, and how you avoided it).

### Project 2 - A "Twitter-lite" / social or content app (full-stack, a notch up)

**Problem.** A small social app: post short messages, follow users, see a feed. Or a domain twist, a **book/movie log with a social feed**, a **dev-link sharing board**. It exercises the *exact* design you'd be asked in 15.2, which makes the interview story smooth.

**Features.**
- *MVP:* auth; create posts; follow/unfollow; a home feed of followed users' posts, newest first.
- *Stretch:* likes/comments; a fan-out feed in Redis (the 15.2 design, made real); image uploads to object storage (S3); notifications; full-text search.

**Tech stack.** FastAPI + PostgreSQL + React, Redis for feed/cache, S3 (or compatible) for images, Docker, CI/CD.

**Architecture sketch.**
```
React -> FastAPI -> PostgreSQL (users, posts, follows)
                 -> Redis (cached feed lists; fan-out on write)
                 -> S3 (uploaded images)
```

**Chapters it exercises.** Everything in Project 1, plus 9.2 (caching/Redis), 9.6 (the feed fan-out design, and you can *say* "I implemented the fan-out-on-write design from my system-design study"), 7.3 (Redis as a store), 10.4 (S3) if you add uploads.

**Milestones.** (1) auth + posts + follows + naive feed (fan-out on read). (2) React UI. (3) move to fan-out-on-write with Redis; measure the latency difference. (4) one stretch (likes or images) + README with the design writeup + deploy.

**How to present it.** The killer move: a README section titled **"Design: feed generation"** showing you considered fan-out on read vs. write, chose one, and *measured* it. That's a senior-flavored signal from a new grad, and it's literally your 15.2 answer with code behind it.

### Project 3 - Data/ML project: pipeline → model → dashboard (plays to a data/ML strength)

**Problem.** End-to-end ML on a real dataset you care about, fits a data/ML strength and a NYX Finance-style lineage. E.g., **predict [something] from public data** (housing prices, flight delays, energy usage), with an automated pipeline that ingests fresh data, a trained model served behind an API, and a dashboard that visualizes both the data and the model's predictions. This is *the* project for data/ML roles.

**Features.**
- *MVP:* a reproducible pipeline (ingest → clean → feature-engineer) on a real dataset; a trained model (scikit-learn) with honest evaluation; a FastAPI `/predict` endpoint; a simple dashboard showing data + predictions.
- *Stretch:* scheduled/automated retraining; model versioning + a metrics comparison; a deep-learning variant (PyTorch) benchmarked against the baseline; data-quality checks + observability on the pipeline (tie to your telemetry work); experiment tracking.

**Tech stack.** Python (Pandas, scikit-learn, optionally PyTorch), FastAPI to serve the model, PostgreSQL or Parquet for storage, a dashboard (Streamlit for speed, or React + a charting lib), Docker, a scheduler (cron / GitHub Actions) for the pipeline.

**Architecture sketch.**
```
[scheduled] ingest -> clean/feature-engineer -> store (Postgres/Parquet)
                                                     |
                                        train + evaluate (versioned model)
                                                     |
                                FastAPI /predict  <--+-->  Dashboard (data + predictions)
                              [data-quality checks + metrics/logging throughout]
```

**Chapters it exercises.** 14.1 (ML foundations + scikit-learn), 14.2 (deep learning, for the stretch), 4.3 (scraping/APIs to get data), 4.2 (files/data wrangling), 8.2 (FastAPI serving), 13.1 (observability/data-quality on the pipeline), 7.x (storage), 10.1/10.3 (Docker + scheduled CI).

**Milestones.** (1) get + clean the data, EDA. (2) train + *honestly* evaluate a baseline model (talk about train/test split, the metric choice, overfitting). (3) serve it via FastAPI + a Streamlit dashboard. (4) automate the pipeline + add data-quality checks + README.

**How to present it.** Lead with the problem and a screenshot of the dashboard. In the README, be *honest about the model's limits* (a thoughtful "here's where it fails and why" beats a fake 99% accuracy). This project pairs perfectly with NYX Finance-style work and your data/ML resume bullets (15.3), same narrative, more depth.

### Project 4 - A systems project: mini key-value store (or web server)

**Problem.** Build a piece of infrastructure *from scratch* to prove you understand what's under the libraries you use (the book's whole "no black boxes" ethos). A **persistent key-value store** with a network protocol, like a tiny Redis. Alternatively: a **concurrent HTTP server** from sockets, or a **rate-limited API gateway**. This is catnip for backend/infra-leaning roles and demonstrates real CS depth.

**Features (KV store version).**
- *MVP:* `GET`/`SET`/`DEL` over a TCP socket; in-memory hash map storage; a simple text protocol; handles multiple clients (threads or async).
- *Stretch:* persistence (append-only log + replay on startup, or snapshotting); TTL/expiry; an LRU eviction policy; a write-ahead log for durability; basic replication to a follower; benchmark its throughput.

**Tech stack.** Python (or Go/C++ to stretch, all worth having on your resume) using raw sockets and the concurrency primitives from Part 5.2; no Redis library, that's the point.

**Architecture sketch.**
```
clients --TCP--> [ server: accept loop ]
                       |  (thread/async per connection)
                  parse command -> hash map (the store)
                       |
                  append-only log on disk  --(replay on startup)-->  durability
```

**Chapters it exercises.** 2.4 (hash tables, you're *building the storage engine*), 5.1 (memory), 5.2 (concurrency, handling many clients), 6.1 (TCP sockets), 6.2/6.3 (protocol design), 9.2 (eviction/LRU concepts), plus 1.4 for the complexity analysis you'll narrate.

**Milestones.** (1) single-client GET/SET over a socket. (2) concurrency for many clients (and handle the race conditions, great behavioral story). (3) persistence via append-only log. (4) one stretch (LRU or TTL) + a benchmark + README.

**How to present it.** Include a **benchmark** ("handles ~X ops/sec on my laptop") and a clear protocol spec in the README. The interview gold: "I built a mini Redis, so I deeply understand caching, eviction, and the cost of persistence", it makes your 15.2 system-design answers far more credible because you've *been* inside the box.

### Project 5 - A rate-limited API gateway / backend service (systems + web)

**Problem.** A standalone **API gateway** that sits in front of backend services and provides cross-cutting concerns: authentication, **rate limiting**, request logging/metrics, and routing. Or framed as a public API product (e.g., a "weather/quotes/currency proxy API" with API keys and per-key limits). It directly realizes the 9.4 + 15.2 rate-limiter design and shows you understand production concerns.

**Features.**
- *MVP:* an API-key auth layer; a **token-bucket rate limiter** (per key) backed by Redis (the distributed-counter design from 15.2); request routing to one or more upstream services; structured logging.
- *Stretch:* metrics + a dashboard (requests/sec, 429 rate, latency); multiple limit tiers (free/pro); caching of upstream responses; circuit breaker / fail-open behavior; a usage/billing counter.

**Tech stack.** FastAPI (or Go), Redis for the rate-limit counters + cache, Docker Compose, plus metrics (Prometheus-style) and a Grafana dashboard for the observability stretch.

**Architecture sketch.**
```
client --(API key)--> [ Gateway: auth -> rate-limit (Redis token bucket) -> route ]
                              |                                    |
                         structured logs                     upstream service(s)
                              |
                         metrics -> Grafana dashboard
```

**Chapters it exercises.** 9.4 (rate limiting, the core), 9.2 (caching), 9.3 (proxy/routing), 8.2/8.3 (API + auth), 7.3 (Redis), 13.1 (metrics/logging/dashboards, an observability strength), 10.1 (Docker), 12.x (security).

**Milestones.** (1) API-key auth + simple proxy. (2) Redis token-bucket limiter with atomic check-and-decrement (the race-condition fix from 15.2). (3) structured logging + metrics. (4) a Grafana dashboard + README with the rate-limit design writeup.

**How to present it.** Demo it by hammering the API and showing the `429`s kick in, plus a Grafana panel of the request/limit metrics. This is a standout project for infra/backend/SRE-flavored roles and reinforces your telemetry/observability resume story (15.3).

### Project 6 - "Automate something real" (pragmatism that signals seniority)

**Problem.** Build a tool that automates a genuinely annoying real task in *your* life, that authenticity is the whole point and makes it memorable. Examples: a bot that scrapes job postings from new-grad sources and posts new matches to a Discord/Slack with a tracker (meta-useful for *your own* job search, 15.3!); a tool that watches a price/stock and alerts you; a personal-finance importer that pulls transactions, categorizes them, and emails a weekly summary (NYX-adjacent); a CLI that automates your project setup.

**Features.**
- *MVP:* the core automation runs on a schedule, does the useful thing, and notifies you (email/Slack/Discord).
- *Stretch:* a small web UI or dashboard; configurability; persistence + history; deployment as a always-on scheduled job; tests; error handling + alerting when *it* breaks (observability on your own tool).

**Tech stack.** Python (requests/BeautifulSoup or APIs from Part 4.3), a scheduler (cron / GitHub Actions / a cloud function), a notification integration, optional small DB, Docker.

**Architecture sketch.**
```
[scheduled trigger] -> fetch/scrape data -> process/filter -> store (dedupe) -> notify
                                                                   |
                                                        (optional) tiny dashboard
```

**Chapters it exercises.** 4.2 (files/OS), 4.3 (scraping & APIs), 4.4 (automation projects, this *is* its capstone), 10.x (deploy it as a scheduled job), 13.1 (alert when it breaks), 7.3 (a small store for dedupe/history).

**Milestones.** (1) the core fetch + notify, run manually. (2) scheduling + dedupe so it doesn't spam. (3) deploy it always-on. (4) error handling + a README showing the before/after time saved.

**How to present it.** Quantify the win in the README ("saves me ~3 hours/week" / "found me 12 roles I'd have missed"), that's an instant resume bullet with a real metric (15.3). Pragmatic automation tools signal an engineer who *ships value*, not just polishes toys, which interviewers love.

## 🧪 Mini-project - Pick one and build the full plan + repo scaffold

Choose the project that best fits your target roles (15.3 tailoring), then produce two things *before writing feature code*.

### Part A - The one-page project plan

Create `PLAN.md` in the repo:

```markdown
# <Project> - Plan

## Problem & users
Who has this problem, why it matters.

## MVP (brutally minimal - ship this first, deployed)
- [ ] feature 1
- [ ] feature 2
- [ ] feature 3   <- nothing beyond what's needed to solve the core problem once

## Stretch (after MVP ships)
- [ ] ...

## Tech stack & why
- ... (one line of WHY per choice)

## Architecture
(boxes + arrows)

## Chapters this exercises
8.2, 8.3, 7.2, 10.1, 11.1, ...

## Milestones (timeboxed ~4 weeks)
Week 1: ...  | Week 2: ...  | Week 3: ...  | Week 4: deploy + README + demo

## Definition of done
Deployed (live URL) · tested (CI green) · README with demo GIF · clean git history
```

### Part B - The repo scaffold + starter README

Initialize the repo (Part 11) with a sensible skeleton. For the Project 1 full-stack app it might be:

```
expense-tracker/
├── README.md            <- the template from this chapter, filled with the pitch
├── PLAN.md
├── docker-compose.yml
├── .github/workflows/ci.yml      <- runs tests on every push (Part 10.3)
├── .gitignore                    <- never commit .env / secrets (Part 12)
├── backend/
│   ├── app/ (main.py, models.py, auth.py, routes/)
│   ├── tests/
│   └── requirements.txt
└── frontend/
    ├── src/
    └── package.json
```

Write the **starter README first**, pitch, problem, planned features, stack-and-why, and a "Status: in progress" badge. Writing the README *before* the code forces you to clarify what you're actually building (the same "requirements before solutions" discipline from 15.2). Make the **first commit** the scaffold + README, so your git history tells a clean story from day one.

**Then build the MVP, deploy it in week 1, and iterate.** Ship beats perfect.
