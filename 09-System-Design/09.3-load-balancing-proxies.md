## 🌱 Start here

Before any of the network-stack jargon, here's the whole idea in one picture: **a load balancer is a restaurant host.**

Imagine you walk into a busy restaurant. You don't wander the floor looking for an open table and an idle waiter, you go to the host stand at the door. The host knows which waiters are slammed and which just cleared a table, and seats you with someone who can actually take care of you. If a waiter goes home sick, the host simply stops seating new diners in that section; the guests already there finish their meals and leave. From your chair, you never see any of this coordination, you just got seated and served.

```
   diners arriving                 requests arriving
        │                                 │
   ┌────▼────┐                       ┌────▼────┐
   │  HOST   │  =  load balancer     │   LB    │
   └─┬──┬──┬─┘                       └─┬──┬──┬─┘
     │  │  │                           │  │  │
   waiter waiter waiter            app  app  app
```

Or, if restaurants aren't your thing: it's the person at the supermarket who says "register 4 is open!" so the line doesn't all pile onto one cashier. Same job, spread the crowd, route around the broken-down register, and let the shoppers think there's just "one checkout."

**Why this matters.** A single server has a ceiling. At some point NYX gets more traffic than one box can serve, or that one box crashes at 9:30am on market open and the whole product is down. The load balancer is what lets you put *several* identical boxes behind one front door, so the system can (a) handle more load by adding boxes and (b) survive a box dying without anyone noticing. Almost every real internet system has a load balancer somewhere near the front, it is one of the most universal building blocks in all of system design.

## 📐 Theory

### What a load balancer does

A **load balancer (LB)** sits in front of a pool of backend servers and spreads incoming requests across them. It delivers four things:

```
        clients
           │
      ┌────▼────┐
      │   LB    │   1. Distribution: spread load evenly
      └─┬──┬──┬─┘   2. Health: stop sending to dead/sick nodes
        │  │  │     3. Availability: a node dies, others absorb it
     ┌──▼┐┌▼─┐┌▼──┐ 4. Single entry point: clients see one address/VIP
     │app││app││app│   (also: TLS termination, basic routing)
     └───┘└──┘└───┘
```

Without an LB, clients would need to know every backend address, and a dead node would mean broken clients. With it, backends are interchangeable cattle: add capacity by registering nodes, survive failures by draining dead ones, exactly the horizontal-scaling story from 9.1.

### L4 vs L7 load balancing

The big architectural fork is *which layer of the network stack the LB operates at.*

**Layer 4 (transport: TCP/UDP).** The LB routes by IP + port, forwarding packets/connections without looking at their contents.
```
Sees:    source/dest IP, port, TCP flags
Doesn't see: HTTP method, URL, headers, cookies (it's just bytes/connections)
```
- Pros: extremely fast, low overhead, low latency; protocol-agnostic (works for any TCP/UDP service, databases, gRPC, custom protocols); can preserve a single TCP connection to one backend.
- Cons: dumb routing, can't make decisions on URL/host/headers; no per-request HTTP smarts.
- Examples: AWS NLB, classic IPVS/LVS, HAProxy in TCP mode.

**Layer 7 (application: HTTP/HTTPS).** The LB terminates the connection, parses HTTP, and routes on content.
```
Sees:    URL path, Host header, cookies, method, headers, body
Can do:  /api/* -> service A, /static/* -> CDN/service B
         TLS termination, header rewriting, compression, request buffering,
         per-request retries, sticky sessions by cookie, WAF/auth
```
- Pros: smart content-based routing, the foundation of API gateways and modern microservice routing; per-request retries; observability per route.
- Cons: more CPU (parses + often re-encrypts); a tiny bit more latency; HTTP-specific.
- Examples: AWS ALB, nginx, Envoy, HAProxy in HTTP mode, Traefik.

**Rule of thumb:** L4 for raw throughput and non-HTTP protocols (or as a fast first hop in front of L7); L7 when you need to route on the *content* of the request. Many big systems use both: an L4 LB spreads to a fleet of L7 proxies (Envoy/nginx) that do the smart routing. For NYX's HTTP API you want L7 so you can route `/api/v1/quotes` differently from `/api/v1/reports` and terminate TLS centrally.

### Load-balancing algorithms

How the LB picks *which* backend gets the next request. Tradeoffs are about evenness vs awareness vs stability.

**Round-robin.** Hand requests out in rotation: 1, 2, 3, 1, 2, 3, …
- Simple, stateless, even *if* requests are uniform cost. Falls down when requests vary wildly in cost (one slow request can pile up on one node), round-robin is blind to load.

**Weighted round-robin.** Give beefier nodes a higher weight so they get proportionally more traffic (a 16-core box weight 2 vs an 8-core weight 1).
- Handles heterogeneous hardware. Still cost-blind per request.

**Least-connections.** Send the next request to the backend with the fewest *active* connections.
- Adapts to real load, a node stuck on slow requests accumulates connections and stops receiving new ones. Great when request durations vary. Needs the LB to track live connection counts (slightly stateful). "Least response time" is a refinement that also factors latency.

**IP hash / consistent hashing.** Route by a hash of a key (client IP, user ID, cache key) so the *same key* deterministically lands on the *same backend*.
- Enables session affinity without cookies, and is essential for sharded/stateful backends and distributed caches (so a given key always hits the node that caches it). Plain `hash(key) % N` is catastrophic when N changes, see consistent hashing below.

**Random / power-of-two-choices.** Pick two backends at random, send to the less-loaded of the two. Astonishingly close to least-connections in evenness with almost no coordination, a favorite at scale.

### The `mod N` problem and consistent hashing

Naive sharding: `server = hash(key) % N`. Problem: when N changes (a node dies or you add one), *almost every* key remaps to a different server. With a distributed cache that means a near-total cache miss storm; with a sharded DB it means re-shuffling almost all data. Example: going from 4 → 5 servers remaps ~80% of keys.

**Consistent hashing** fixes this. Map both servers and keys onto a circular hash space (the "ring", e.g., 0 .. 2³²−1). A key is owned by the *first server clockwise* from the key's hash. Adding/removing a server only affects keys between it and its neighbor, on average **K/N keys move**, not K.
```
        0
   S3 ●─────● S1       key k hashes here ─┐
      /       \                           ▼
     ●  ring   ●  ──── walk clockwise ──> next server owns k
      \       /
   S2 ●─────●
```
**Virtual nodes:** to avoid uneven load (a single point per server clumps badly), each physical server is placed at *many* points on the ring (e.g., 100-200 virtual nodes). This smooths the distribution and lets weighting work (more vnodes = more share). This is exactly how Memcached client sharding, Cassandra/DynamoDB partitioning, and Envoy's ring-hash LB stay stable under membership changes. We'll implement it below.

### Worked example 1 - exactly how many keys move (mod-N vs consistent hashing)

Let's actually do the arithmetic instead of waving at "~80%", because the gap between the two approaches is the whole reason consistent hashing exists.

**Setup.** NYX runs a distributed cache with `K = 1,000,000` cache keys spread across `N = 4` nodes. Traffic grows and you add a 5th node (4 → 5).

**Naive `hash(key) % N`.** A key stays put only if `hash(key) % 4 == hash(key) % 5`. For (effectively) random hashes, the fraction that happens to land on the same index under both moduli is small. Empirically (and intuitively, since `% 4` and `% 5` are almost independent), only about `1/5` of keys keep their home; the rest move. So:

```
keys that move ≈ K × (1 − 1/N_new)
              =  1,000,000 × (1 − 1/5)
              =  1,000,000 × 0.80
              =  800,000 keys move   (80%)
```

Every one of those 800,000 keys is now a cache miss until it's repopulated. On a cache that was absorbing, say, 90% of read traffic, the database suddenly eats a flood it was never sized for. This is the **cache stampede on resize**, adding capacity *causes an outage*. Absurd, but exactly what mod-N does.

**Consistent hashing.** Adding the 5th node only steals the arc of the ring that now falls "behind" the new node's positions. On average each node owns `1/N` of the ring, so the newcomer claims roughly `1/5` of the keyspace, taken proportionally from its neighbors:

```
keys that move ≈ K × (1 / N_new)
              =  1,000,000 × (1/5)
              =  200,000 keys move   (20%)
```

Same operation, **4× fewer keys disturbed** (200k vs 800k). And the keys that *do* move come from a small set of ring neighbors, not the entire fleet. Going the other direction, a node *dies* in a 4-node ring, only its ~`1/4` of keys (250,000) get reassigned to neighbors; the other 750,000 keys never notice. That's the `K/N` promise made concrete: membership changes touch a *bounded* slice, not the whole world.

```
mod-N, 4→5:           consistent hashing, 4→5:
████████████████ 80%  ████ 20%
        (moves)            (moves)
```

The lesson to take to every cache/shard design: if the node count can ever change (it always can), do **not** shard with `% N`. Use a ring.

### Worked example 2 - sizing the fleet behind the LB (N+2 redundancy + headroom)

The LB only helps if there are enough healthy boxes behind it. Here's how you'd size NYX's stateless API tier from first principles, the way you'd defend it in a design review.

**Givens.**
- Peak QPS at market open: `Q_peak = 9,000 req/s`.
- Measured per-node capacity at a *safe* utilization: one node handles `C = 1,500 req/s` while staying around 60% CPU (you deliberately measure the "comfortable" number, not the smoke-coming-out-of-the-box max, see the headroom point below).
- Availability target: survive **two** simultaneous node losses (one dead box + one mid-deploy) with no degradation. That's **N+2** redundancy.

**Step 1, base nodes to carry peak load.**
```
N_base = ceil(Q_peak / C)
       = ceil(9,000 / 1,500)
       = ceil(6.0) = 6 nodes
```
Six nodes at 1,500 req/s each = 9,000 req/s. That *exactly* meets peak with zero slack, fine on paper, dangerous in reality.

**Step 2, add redundancy (N+2).** You need peak load to still be servable when 2 nodes are gone:
```
N_total = N_base + 2 = 8 nodes
```
Sanity check the failure case: lose 2 of 8, leaving 6 healthy → `6 × 1,500 = 9,000 req/s` → still covers peak. Good.

**Step 3, check the steady-state utilization (headroom).** With all 8 nodes up at peak:
```
per-node load = Q_peak / N_total = 9,000 / 8 = 1,125 req/s
utilization   = 1,125 / 1,500   = 75%
```
75% at peak is a touch hot for a spiky workload (market open arrives in seconds, and autoscaling has lag, Chapter 9.1). Two reasonable moves:
- Provision **9 nodes** instead of 8 → peak per-node load `9,000/9 = 1,000 req/s` = **67% utilization**, comfortably inside the 50-70% steady-state band, and *still* N+2 (lose 2 → 7 nodes × 1,500 = 10,500 capacity ≥ 9,000). Pick this one.
- Or keep 8 and lean on autoscaling/warm pools for the open. Riskier given lag.

**Decision:** run **9 stateless nodes** behind the LB. Peak utilization ~67%, survives 2 concurrent losses, leaves headroom for the open-bell spike. Note the LB itself needs to be HA too (covered below), 9 perfectly-sized app nodes behind a single LB is just moving the single point of failure.

```
        clients (9,000 req/s peak)
              │
         ┌────▼────┐  (HA pair - see interview angle)
         │   LB    │
         └──┬──...─┘
   ┌──┬──┬──┼──┬──┬──┬──┬──┐
  n1 n2 n3 n4 n5 n6 n7 n8 n9   each ~1,000 req/s = 67% util
                                lose any 2 → remaining 7 still cover 9,000
```

The takeaway: "how many boxes?" is never just `peak/capacity`. It's `ceil(peak / safe_capacity) + redundancy`, then verify the *post-failure* fleet still fits and the *steady-state* utilization leaves room for spikes.

### Health checks

The LB must know which backends are alive, or it'll happily route to corpses.

- **Passive (in-band):** observe real traffic, if a backend errors/times out repeatedly, mark it down. Free, but reacts only when real users hit the bad node.
- **Active (out-of-band):** the LB periodically probes a dedicated endpoint (`GET /healthz`) on each backend; N consecutive failures → mark down, M consecutive successes → mark back up. Proactive; catches problems before users do.

Make `/healthz` *meaningful but cheap*: it should confirm the app can serve (process up, maybe DB/cache reachable) without being so heavy it falls over under probe load or marks the whole fleet down when a shared dependency blips. Distinguish **liveness** (is the process alive? restart if not) from **readiness** (can it serve traffic right now? pull from LB if not), Kubernetes formalizes both. Also: **connection draining / graceful shutdown**, when removing a node (deploy, scale-in), stop sending it *new* requests but let in-flight ones finish before killing it.

### Sticky sessions vs statelessness

**Sticky sessions (session affinity):** the LB pins a given client to the same backend (via cookie or IP hash) so that backend's *local* session memory stays valid.
- Why people use it: their app stores session state in local RAM, so a user must keep hitting the same node.
- Why it's bad: that node becomes a single point of failure for those users (it dies → they're logged out); load gets uneven (sticky users pile up); autoscaling is hampered (can't freely move users); rolling deploys are disruptive.

**The better answer: make the app stateless** (Chapter 9.1). Push session/auth state to a shared store (Redis, signed JWT, DB). Then *any* node serves *any* request, the LB can use plain round-robin/least-connections, and nodes are disposable. Stickiness becomes an optimization (cache warmth), not a correctness requirement. For NYX, sessions/JWTs and live state live in Redis; the app tier is fully stateless, so you never need sticky sessions for correctness.

### Forward proxy vs reverse proxy vs API gateway

These three are constantly confused. The distinction is *who they front and who they serve*.

```
FORWARD PROXY  - sits in front of CLIENTS, faces out to the internet.
   [clients] -> [forward proxy] -> [any server on the internet]
   Acts on behalf of the CLIENT. Hides client identity, enforces egress
   policy, caches outbound. Examples: corporate web filter, Squid, a VPN-ish egress.

REVERSE PROXY  - sits in front of SERVERS, faces the internet.
   [internet clients] -> [reverse proxy] -> [your backend servers]
   Acts on behalf of the SERVER. Hides backend topology, terminates TLS,
   caches, compresses, load-balances. Examples: nginx, Varnish, Envoy.

API GATEWAY    - a specialized reverse proxy for APIs (esp. microservices).
   [clients] -> [API gateway] -> [service A] [service B] [service C]
   Reverse-proxy PLUS: authn/authz, rate limiting (Ch 9.4), request
   transformation, routing/aggregation, API keys, quotas, versioning,
   observability. Examples: Kong, AWS API Gateway, Envoy + control plane.
```

Mental model:
- **Forward proxy** = the *client's* gatekeeper to the world (outbound).
- **Reverse proxy** = the *server's* gatekeeper from the world (inbound). A load balancer is essentially a reverse proxy whose main job is distribution.
- **API gateway** = a reverse proxy that's also taken on cross-cutting API concerns (auth, rate limiting, transformation) so individual services don't each reimplement them.

A load balancer and a reverse proxy heavily overlap: an L7 LB *is* a reverse proxy that load-balances; an API gateway is a reverse proxy with extra policy. They blur together in practice (nginx is all three depending on config).

### Horizontal scaling behind an LB, and autoscaling

The LB is what lets the fleet grow and shrink:
- **Scale out:** boot a new (stateless) app node, register it with the LB (or it self-registers via service discovery), health check passes, it starts taking traffic. Capacity rose with zero client changes.
- **Scale in:** drain a node (stop new requests, finish in-flight), deregister, terminate.

**Autoscaling** automates this against a signal:
- **Reactive / metric-based:** scale on CPU%, request rate, p95 latency, or queue depth crossing a threshold (e.g., "add a node when avg CPU > 60% for 5 min; remove when < 30%"). Tie the target to Chapter 9.1's utilization math, keep steady-state ~50-70% so spikes have headroom.
- **Scheduled / predictive:** scale ahead of known patterns (NYX scales up right before market open at 9:30, down after close) so you're not chasing the spike reactively (scaling has lag, boot time, warmup).

Caveats: scaling has *lag* (new instances take seconds-to-minutes to be ready), so set thresholds with headroom and use warm pools for spiky workloads; protect the DB (it usually can't autoscale as fast as the app tier, Chapter 9.6).

### Worked example 3 - load-balancing a stateful WebSocket fleet

So far the easy case has been stateless HTTP request/response. Now the hard one: NYX pushes live quotes to browsers over **WebSocket**. A WebSocket is a long-lived connection, once established it lives on *one specific backend* for minutes or hours. You can't re-balance it per request, because there are no per-request choices; there's one connection that has to stick where it landed. This breaks a few naive assumptions, so let's design it carefully.

**The shape of the problem.**
```
  browser ==════ persistent WS ══════> [ ws-node ]   (lives here for the whole session)
  60,000 concurrent connections, each subscribed to a set of symbols
```

**Decision 1, L4 or L7 for the front?** The TLS handshake + HTTP `Upgrade: websocket` is L7, so an L7 LB terminates TLS and recognizes the upgrade. But after the upgrade it must do a *transparent connection passthrough*, it can no longer inspect per-message content cheaply, so it's really acting like an L4 pipe for the lifetime of the socket. nginx and Envoy both support this (`proxy_pass` with upgrade headers). So: **L7 for the handshake, then a long-lived tunnel.**

**Decision 2, which node gets a new connection?** *Not* round-robin blindly, because connections are sticky and unevenly long-lived. **Least-connections** is the right primitive here: send each *new* WS connection to the node holding the fewest open sockets, so the fleet stays balanced even though connections never move once placed.

**Decision 3, what about the "state" (subscriptions / who-wants-what)?** Each ws-node knows the symbols its own connected clients care about. The price feed, though, is global. The clean pattern: ws-nodes are *fan-out edges*, and a shared **pub/sub bus** (Redis pub/sub or a message broker) carries price ticks. Every ws-node subscribes to the bus; when AAPL ticks, every node that has AAPL-watching clients pushes to them. The nodes stay individually disposable: the durable state (who's subscribed to what, auth) lives in Redis, not in node RAM.

```
        price feed ──► Redis pub/sub (topic per symbol) ──► all ws-nodes
                                                              │   │   │
   browsers ── WS ──► LB(least-conn) ──────────────────────► n1  n2  n3
                                                              (each fans out
                                                               to its own clients)
```

**Decision 4, draining on deploy.** This is where WS stings. You can't kill a ws-node holding 20,000 live connections without 20,000 reconnect storms. Strategy: stop sending it *new* connections (deregister from LB), then either (a) let connections drain naturally over a long window, or (b) send an application-level "please reconnect" nudge so clients reconnect (landing on other nodes via least-conn) in a controlled trickle rather than all at once. Always include client-side reconnect-with-jittered-backoff so a node loss doesn't become a thundering herd.

**What you'd actually build for NYX:** L7 LB doing TLS + upgrade, least-connections placement, Redis pub/sub for price fan-out, durable subscription/auth state in Redis, graceful drain with client reconnect-and-jitter. Sticky? Yes, but it's *intrinsic* stickiness (a connection physically lives somewhere), not the *bad* kind where correctness depends on the LB pinning you. The node is still disposable because nothing irreplaceable lives only in its memory.

### Worked example 4 - global load balancing across regions (GeoDNS / anycast)

One more level up. NYX grows to users in New York, London, and Singapore. A single regional LB can't help a Singapore user whose packets cross the planet to Virginia, that's ~200ms of round-trip latency before the app does *any* work. The fix is **global load balancing**: route each user to the *nearest healthy region*, and only then to a regional LB.

There are two classic mechanisms:

**(a) GeoDNS.** The DNS server answers `api.nyx.com` differently depending on where the query comes from. A resolver in Singapore gets the Singapore region's IP; a resolver in London gets London's.
```
  Singapore user ─ DNS query ─► GeoDNS ─► returns 13.x (ap-southeast LB)
  London    user ─ DNS query ─► GeoDNS ─► returns 18.x (eu-west LB)
  NY        user ─ DNS query ─► GeoDNS ─► returns 54.x (us-east LB)
```
- Pros: simple, works with plain DNS, no special network gear.
- Cons: DNS is *cached* (TTL). If a whole region dies, clients holding a cached answer keep trying the dead region until the TTL expires, failover is as slow as your TTL (so keep TTL low, e.g., 30-60s, accepting more DNS traffic). DNS also routes by the *resolver's* location, which isn't always the user's.

**(b) Anycast.** Advertise the *same IP* from multiple regions via BGP; the internet's routing fabric delivers each user's packets to the topologically nearest site automatically.
```
            announce 1.2.3.4 from ALL regions (BGP anycast)
  user packets to 1.2.3.4 ─► network routes to nearest PoP ─► regional LB
```
- Pros: failover is near-instant (if a region withdraws its BGP announcement, routes reconverge in seconds, no DNS cache to wait on). One IP, global.
- Cons: needs control of IP space + BGP (you get this from cloud global LBs / CDNs like Cloudflare, AWS Global Accelerator, GCP global LB rather than rolling it yourself). Long-lived TCP can occasionally re-path mid-connection (rare, mostly a non-issue for short requests).

**The full picture** is layered, global LB on top, regional LBs underneath, app tier under each:
```
                         users worldwide
                               │
                ┌──────── anycast / GeoDNS ────────┐   ← global load balancing
                ▼              ▼                    ▼
          us-east LB      eu-west LB         ap-southeast LB   ← regional LBs (L7)
          ┌──┬──┐         ┌──┬──┐             ┌──┬──┐
          n1 n2 n3        n1 n2 n3            n1 n2 n3         ← stateless app tier
             │               │                   │
          us-east DB ◄── replication ──► (region-local reads, Ch 9.6)
```

**Reasoning for NYX:** use a managed **global LB (anycast)** for fast cross-region failover, with each region running its own L7 LB + stateless fleet (sized via Worked example 2). Reads served region-locally; writes go to the primary region (or per-region with conflict handling, that's the data-layer chapter). Latency for the Singapore user drops from ~200ms to ~5-20ms intra-region, and a regional outage fails over in seconds instead of waiting on DNS TTLs.

### ⚠️ Common mistakes

The errors you (and approximately everyone) make with load balancers, and what to do instead:

1. **Round-robin when request cost is uneven.** RR assumes every request costs the same. If `/api/reports` takes 2s and `/api/quote` takes 5ms, RR will cheerfully stack slow reports on a node already drowning in them. *Fix:* least-connections or power-of-two-choices, which actually notice load.

2. **Sticky sessions as a correctness crutch.** Pinning users to a node "because the session lives in local RAM" makes that node a single point of failure for those users and wrecks even distribution + autoscaling. *Fix:* externalize session state (Redis/JWT) so the app is stateless; let stickiness be an optional cache optimization, never a requirement.

3. **No connection draining on deploy.** Killing a node with in-flight requests turns every deploy into a burst of 5xx errors and dropped connections. *Fix:* deregister → stop new traffic → let in-flight finish (a drain window) → then terminate. For WebSockets, add a controlled reconnect nudge.

4. **Health checks that are too heavy *or* too shallow.** Too heavy (`/healthz` runs a full DB report) and the probe traffic itself can knock nodes down, or one shared-dependency blip marks the *whole fleet* unhealthy at once → total outage. Too shallow (`return 200` from a process that can't actually reach its DB) and you route to a node that fails every real request. *Fix:* a cheap-but-meaningful readiness check; separate liveness (am I alive?) from readiness (can I serve *now*?).

5. **A single LB as a SPOF.** People carefully run 9 redundant app nodes behind *one* load balancer, which is itself one box that can die and take everything down. *Fix:* run the LB in an HA pair (active/passive with a floating VIP, or active/active), or use a managed LB that's redundant under the hood, fronted by DNS/anycast.

6. **Sharding with `hash(key) % N`.** Works great until N changes, then ~80% of keys remap and your cache/shard tier melts down *because you added capacity* (Worked example 1). *Fix:* consistent hashing with virtual nodes, bounds movement to ~K/N.

7. **Not preserving the client IP (dropping X-Forwarded-For).** Once a reverse proxy terminates the connection, the backend sees the *LB's* IP as the source. Forget to set `X-Forwarded-For` / `X-Real-IP` and your logs, rate limiters, geo-IP, and audit trails all think every request came from the LB. *Fix:* set forwarding headers at the proxy and have the app trust them (only from trusted proxies, clients can spoof these headers).

8. **TLS termination then plaintext over an untrusted network.** Terminating TLS at the LB is fine, but if the hop from LB to backend then crosses an untrusted network in cleartext, you've handed an eavesdropper everything. *Fix:* either keep that hop inside a trusted/private network, or re-encrypt (TLS re-origination / mTLS) between LB and backends.

### 💼 On the job / interview angle

Load balancing is the single most ubiquitous box in system-design interviews, it shows up in *nearly every* whiteboard diagram, usually as the first thing you draw after the clients. Interviewers expect you to place it without prompting and to say *why*. Here's how to talk about it:

- **Always put it in the diagram, and name it.** "Clients hit an L7 load balancer, which fans out to a stateless app tier." Drawing a single app box without an LB in front signals you haven't thought about scale or availability.

- **Justify L4 vs L7 out loud.** "You'll use L7 here because you want to route `/api/*` to the API service and `/ws` to the WebSocket fleet, terminate TLS centrally, and do per-request retries. If this were a raw TCP database proxy or you needed maximum throughput, you'd reach for L4." Showing you know *when not* to use L7 is what separates a real answer from a buzzword.

- **Pick an algorithm and defend it.** Don't just say "load balanced." Say "least-connections, because request costs vary," or "consistent hashing for the cache tier so resizes don't cause a stampede." Tie the choice to the workload.

- **Lead with statelessness.** When the interviewer asks "how do you scale the app tier?", the answer is "make it stateless, session/auth state in Redis or a JWT, so any node serves any request and the LB can use plain round-robin and freely autoscale." Statelessness is the unlock for *everything* else (scaling, failover, deploys), so say it early.

- **Expect the follow-up: "How do you make the load balancer itself HA?"** This is the classic gotcha, you've made the app redundant but the LB is now the single point of failure. Good answers:
  - **Redundant LBs** in an active/passive pair sharing a floating/virtual IP (VRRP-style), or active/active.
  - **DNS-based** failover across multiple LB IPs (cheap, but failover is bounded by TTL).
  - **Anycast** (announce one IP from multiple locations via BGP), near-instant failover; what cloud "global load balancers" use under the hood.
  - The crisp summary: *"a managed cloud LB is already internally redundant; for self-hosted, an HA pair with a VIP fronted by low-TTL DNS or anycast."*

- **Know the proxy taxonomy cold.** Be ready to distinguish forward proxy / reverse proxy / API gateway by *who they act for*, because interviewers love checking whether you actually understand the layers or just memorized "nginx = load balancer."

- **Mention health checks and draining unprompted** when discussing deploys and failures, it shows operational maturity, not just happy-path design.

## 💻 Build it

A tiny load balancer in Python with three pluggable algorithms (round-robin, least-connections) plus a standalone consistent-hash ring. Mock backends with variable latency expose the difference.

```python
# mini_lb.py
import threading, time, random, hashlib, bisect
from itertools import cycle


# ---------------- mock backend ----------------
class Backend:
    def __init__(self, name, base_latency):
        self.name = name
        self.base_latency = base_latency
        self.active = 0                 # current in-flight requests
        self.served = 0
        self.healthy = True
        self._lock = threading.Lock()

    def handle(self):
        with self._lock:
            self.active += 1
        try:
            # jittered latency; some requests are slow (heavy query)
            time.sleep(self.base_latency * random.uniform(0.5, 3.0))
            with self._lock:
                self.served += 1
            return self.name
        finally:
            with self._lock:
                self.active -= 1


# ---------------- balancers ----------------
class RoundRobin:
    def __init__(self, backends):
        self.backends = backends
        self._it = cycle(backends)
        self._lock = threading.Lock()
    def pick(self):
        with self._lock:
            # skip unhealthy nodes
            for _ in range(len(self.backends)):
                b = next(self._it)
                if b.healthy:
                    return b
        raise RuntimeError("no healthy backend")


class LeastConnections:
    def __init__(self, backends):
        self.backends = backends
    def pick(self):
        healthy = [b for b in self.backends if b.healthy]
        if not healthy:
            raise RuntimeError("no healthy backend")
        return min(healthy, key=lambda b: b.active)   # fewest in-flight


class PowerOfTwo:
    def __init__(self, backends):
        self.backends = backends
    def pick(self):
        healthy = [b for b in self.backends if b.healthy]
        a, c = random.sample(healthy, k=min(2, len(healthy)))
        return a if a.active <= c.active else c


# ---------------- consistent hash ring ----------------
class ConsistentHashRing:
    """Maps keys -> backends, stable under membership changes. Uses vnodes."""
    def __init__(self, backends=None, vnodes=150):
        self.vnodes = vnodes
        self.ring = {}                  # hash position -> backend name
        self.sorted_keys = []           # sorted positions for binary search
        for b in (backends or []):
            self.add(b)

    def _hash(self, s):
        return int(hashlib.md5(s.encode()).hexdigest(), 16) % (2**32)

    def add(self, name):
        for i in range(self.vnodes):
            pos = self._hash(f"{name}#{i}")
            self.ring[pos] = name
            bisect.insort(self.sorted_keys, pos)

    def remove(self, name):
        for i in range(self.vnodes):
            pos = self._hash(f"{name}#{i}")
            self.ring.pop(pos, None)
            idx = bisect.bisect_left(self.sorted_keys, pos)
            if idx < len(self.sorted_keys) and self.sorted_keys[idx] == pos:
                self.sorted_keys.pop(idx)

    def get(self, key):
        if not self.sorted_keys:
            return None
        h = self._hash(key)
        idx = bisect.bisect(self.sorted_keys, h) % len(self.sorted_keys)  # first node clockwise
        return self.ring[self.sorted_keys[idx]]


def drive(balancer, n=400, concurrency=40):
    """Fire n requests through the balancer; report distribution."""
    threads = []
    def one():
        b = balancer.pick()
        b.handle()
    t0 = time.perf_counter()
    for _ in range(n):
        t = threading.Thread(target=one); t.start(); threads.append(t)
        if len(threads) >= concurrency:
            for t in threads: t.join()
            threads = []
    for t in threads: t.join()
    wall = time.perf_counter() - t0
    return wall


if __name__ == "__main__":
    # One node is intentionally slow (3x) -> shows RR's blindness vs least-conn.
    def fresh():
        return [Backend("fast-1", 0.01), Backend("fast-2", 0.01), Backend("slow-3", 0.03)]

    for Algo in (RoundRobin, LeastConnections, PowerOfTwo):
        bks = fresh()
        wall = drive(Algo(bks), n=400, concurrency=40)
        dist = {b.name: b.served for b in bks}
        print(f"{Algo.__name__:18} wall={wall:5.2f}s  served={dist}")
    # Expect: RoundRobin sends equal counts to slow-3 (queues there);
    #         LeastConnections/PowerOfTwo route AWAY from the busy slow node.

    print("\n--- consistent hashing stability ---")
    ring = ConsistentHashRing(["A", "B", "C", "D"])
    keys = [f"user{i}" for i in range(10000)]
    before = {k: ring.get(k) for k in keys}
    ring.remove("C")                              # a node dies
    after = {k: ring.get(k) for k in keys}
    moved = sum(1 for k in keys if before[k] != after[k])
    print(f"removed 1 of 4 nodes -> {moved}/{len(keys)} keys moved "
          f"({moved/len(keys)*100:.1f}%); naive mod-N would move ~75%")
```

Running it shows the two lessons concretely: **round-robin** sends equal counts to `slow-3`, so requests queue there and wall time suffers; **least-connections / power-of-two** notice `slow-3` accumulating active connections and steer traffic to the fast nodes, finishing faster. And the consistent-hash demo shows ~25% of keys move when 1 of 4 nodes leaves (≈ K/N), versus the ~75% that `mod N` would shuffle.

### Going further: add active health checks and load balance the distribution

Two small extensions that make `mini_lb.py` behave more like a real LB.

**(a) An active health checker.** A background thread probes each backend and flips `healthy`. With `min(healthy, ...)` already in the balancers, an unhealthy node simply stops receiving traffic, and comes back automatically when it recovers.

```python
# add to mini_lb.py
class HealthChecker(threading.Thread):
    """Active out-of-band probing: N fails -> down, M successes -> up."""
    def __init__(self, backends, probe, interval=0.5, fail_threshold=2, rise_threshold=2):
        super().__init__(daemon=True)
        self.backends = backends
        self.probe = probe              # probe(backend) -> True/False
        self.interval = interval
        self.fail_threshold = fail_threshold
        self.rise_threshold = rise_threshold
        self._fails = {b.name: 0 for b in backends}
        self._oks   = {b.name: 0 for b in backends}
        self._stop = threading.Event()

    def run(self):
        while not self._stop.is_set():
            for b in self.backends:
                ok = False
                try:
                    ok = self.probe(b)
                except Exception:
                    ok = False
                if ok:
                    self._oks[b.name] += 1; self._fails[b.name] = 0
                    if not b.healthy and self._oks[b.name] >= self.rise_threshold:
                        b.healthy = True                       # mark back UP
                        print(f"[health] {b.name} -> UP")
                else:
                    self._fails[b.name] += 1; self._oks[b.name] = 0
                    if b.healthy and self._fails[b.name] >= self.fail_threshold:
                        b.healthy = False                      # mark DOWN
                        print(f"[health] {b.name} -> DOWN")
            self._stop.wait(self.interval)

    def stop(self):
        self._stop.set()

# example: a probe that just reads a flag we can toggle to simulate sickness
def make_probe():
    return lambda b: getattr(b, "_alive", True)
```

The point: **the balancer never changes**, it just keeps doing `min(healthy, ...)`. Health is a property of the backend; the checker maintains it. That separation (routing logic vs. health state) is exactly how nginx/Envoy/HAProxy are structured.

**(b) Measure ring evenness vs. vnode count.** Virtual nodes exist to smooth distribution. Here's the proof, with too few vnodes the load is lumpy; crank it up and it flattens.

```python
# quick experiment: how even is the ring at different vnode counts?
import statistics
for vn in (1, 10, 50, 150):
    ring = ConsistentHashRing(["A", "B", "C", "D"], vnodes=vn)
    counts = {}
    for i in range(20000):
        owner = ring.get(f"key{i}")
        counts[owner] = counts.get(owner, 0) + 1
    vals = list(counts.values())
    spread = (max(vals) - min(vals)) / statistics.mean(vals) * 100
    print(f"vnodes={vn:3}  per-node={sorted(vals)}  imbalance={spread:5.1f}%")
# Expect: vnodes=1 is wildly uneven (maybe 40%+ imbalance);
#         vnodes=150 is tight (single-digit % imbalance).
```

This is why production rings use ~100-200 vnodes per physical node: with 1 point each, four nodes can carve the ring into four very unequal arcs; with 150 points each, the law of large numbers flattens it. More vnodes for a node = bigger share, which is also how you implement **weighting** on a ring.

## 🧪 Mini-project: nginx as reverse proxy + load balancer over 3 app instances

Goal: front three identical NYX app instances with nginx doing L7 load balancing, health checks, and graceful behavior. Works locally or on one box with three ports.

**Step 1, three trivial app instances.** Save as `app.py`, run three on ports 9001-9003.
```python
# app.py  ->  PORT=9001 python app.py   (repeat for 9002, 9003)
import os
from http.server import BaseHTTPRequestHandler, HTTPServer
PORT = int(os.environ.get("PORT", "9001"))
class H(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/healthz":
            self.send_response(200); self.end_headers(); self.wfile.write(b"ok"); return
        self.send_response(200)
        self.send_header("Content-Type", "text/plain"); self.end_headers()
        self.wfile.write(f"served by instance on port {PORT}\n".encode())
    def log_message(self, *a): pass
HTTPServer(("127.0.0.1", PORT), H).serve_forever()
```

**Step 2, nginx config** (`nginx.conf`). This is the heart of it.
```nginx
worker_processes auto;
events { worker_connections 1024; }

http {
    # ---- the backend pool ----
    upstream nyx_app {
        least_conn;                       # algorithm: fewest active connections
        # round-robin is the default if you omit least_conn;
        # ip_hash;  # would enable sticky-by-IP (avoid - we're stateless)

        server 127.0.0.1:9001 weight=1 max_fails=3 fail_timeout=10s;
        server 127.0.0.1:9002 weight=1 max_fails=3 fail_timeout=10s;
        server 127.0.0.1:9003 weight=2 max_fails=3 fail_timeout=10s;  # beefier box -> 2x

        keepalive 32;                     # reuse upstream connections (less TCP churn)
    }

    server {
        listen 8080;

        location / {
            proxy_pass http://nyx_app;            # reverse-proxy to the pool
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header Connection "";       # required for upstream keepalive

            # passive health: retry the next backend on error/timeout
            proxy_next_upstream error timeout http_502 http_503;
            proxy_connect_timeout 2s;
            proxy_read_timeout 10s;
        }

        # a cheap health endpoint for an upstream LB to probe nginx itself
        location /healthz { return 200 "lb-ok\n"; }
    }
}
```
Notes on what each knob does:
- `least_conn` picks the algorithm; `weight=2` on instance 9003 implements **weighted** balancing (heterogeneous hardware).
- `max_fails=3 fail_timeout=10s` is nginx's **passive health check**: after 3 failures it stops sending to a node for 10s, then probes again. (Active health checks like `health_check` live in nginx Plus / can be done with `ngx_http_healthcheck` or an external checker; for active checks open-source-only, Envoy/HAProxy are common.)
- `proxy_next_upstream` gives **per-request retry** onto another backend, an L7 feature L4 can't do.
- `keepalive` reuses upstream TCP connections, cutting handshake overhead.
- `X-Forwarded-For` / `X-Real-IP` preserve the **original client IP** so the backend's logs, rate limiter, and geo-IP see the real user instead of nginx (Common mistake #7).

**Step 3, run and test.**
```bash
# start three app instances
PORT=9001 python app.py &
PORT=9002 python app.py &
PORT=9003 python app.py &

# start nginx with this config
nginx -c "$(pwd)/nginx.conf"            # or: docker run -p8080:8080 -v $(pwd)/nginx.conf:/etc/nginx/nginx.conf:ro nginx

# hammer it and watch the distribution
for i in $(seq 1 20); do curl -s localhost:8080/ ; done | sort | uniq -c
#   expect roughly: ~5 from 9001, ~5 from 9002, ~10 from 9003 (weight=2)

# simulate a failure: kill instance 9002, keep curling
kill %2
for i in $(seq 1 20); do curl -s localhost:8080/ ; done | sort | uniq -c
#   nginx detects failures and routes only to 9001 and 9003 - no 5xx to clients
```

**What this proves:** clients hit one address (`:8080`) and never see the topology; weighting sends 2× to the bigger box; killing a node degrades gracefully because nginx's passive health check + `proxy_next_upstream` route around the dead instance. That's horizontal scaling + availability from Chapter 9.1, made concrete. To go further: add a real active health check, put a cache layer (Chapter 9.2) in nginx with `proxy_cache`, and bolt on rate limiting (Chapter 9.4) with `limit_req`.

### Solutions

**1. L4 or L7?**
(a) **L4**, Postgres is a raw TCP protocol the LB has no reason to parse; L4 is faster and protocol-agnostic. (b) **L7**, routing on the URL path requires parsing HTTP, which only L7 sees. (c) **L4**, UDP + max throughput means you want the dumb, fast path with no per-packet HTTP parsing. (d) **L7**, TLS termination and per-request retries are application-layer features L4 fundamentally can't do.

**2. Algorithm choice.** Use **least-connections** (or power-of-two-choices). The danger with round-robin: it's blind to request *cost*. The rare 1.8s `/report` requests will, by bad luck of the rotation, sometimes land two-or-three-deep on the same node while other nodes sit idle serving 4ms quotes. That node's queue grows, its latency for *everything* (including the cheap quotes routed to it) spikes, and tail latency blows up, even though average load looks fine. Least-connections naturally steers new requests away from a node still busy with a slow report, because that node shows more active connections.

**3. Consistent hashing arithmetic.**
(a) Node dies from 6 → 5. Each node owns ≈ `1/6` of the ring, so ≈ `600,000 / 6 = 100,000` keys move. They go to the **clockwise neighbors** of the dead node's vnodes, *not* spread evenly across all survivors, just the adjacent arcs (vnodes smooth this so it's roughly even across survivors in aggregate).
(b) Add a node 6 → 7: the newcomer claims ≈ `1/7` of the ring = `600,000/7 ≈ 85,700` keys, pulled from its ring neighbors. Add another 7 → 8: ≈ `600,000/8 = 75,000` keys move. Each add only disturbs `K/N_new`.
(c) With `hash(key) % N` on 6 → 7: a key stays only if `h % 6 == h % 7`, which is ≈ `1/7` of keys; the other ≈ `6/7` move → `600,000 × 6/7 ≈ 514,000` keys remap. So mod-N moves ~514k vs the ring's ~86k, a **6× difference**, and the mod-N version means a near-total cache-miss storm on what should be a routine scale-up.

**4. Fleet sizing.**
```
N_base   = ceil(Q_peak / C) = ceil(22,000 / 2,000) = ceil(11.0) = 11 nodes
N_total  = N_base + 2 (for N+2 redundancy)         = 13 nodes
```
Failure check: lose 2 of 13 → 11 healthy × 2,000 = 22,000 req/s ≥ peak. ✅
Utilization check (all up at peak): `22,000 / 13 = 1,692 req/s` per node → `1,692 / 2,000 = 85%`. ❌ That's over the 70% ceiling.
So bump up until steady-state ≤ 70%: need `Q_peak / N ≤ 0.70 × C` → `N ≥ 22,000 / 1,400 = 15.7` → **16 nodes**. Recheck: peak per-node `22,000/16 = 1,375` = **69% util** ✅; failure case lose 2 → 14 × 2,000 = 28,000 ≥ 22,000 ✅ (and 14 nodes at peak load = `22,000/14 = 1,571` = 79%, hot but still serving). **Provision 16 nodes.**

**5. The LB is a SPOF.** The flaw: 12 redundant app nodes sit behind **one** nginx box, if that box (or its host/network/process) dies, the entire service is down regardless of how many healthy app nodes exist. Fixes:
- **HA LB pair with a floating VIP** (e.g., keepalived/VRRP, active/passive). *Tradeoff:* failover takes a few seconds and the standby is idle capacity.
- **Multiple LB IPs behind DNS** round-robin/failover. *Tradeoff:* client failover is bounded by DNS TTL, so a dead LB keeps getting hit until caches expire.
- **Managed cloud LB or anycast global LB** (internally redundant). *Tradeoff:* less control / vendor lock-in, but operationally the simplest and fastest-failover option.

**6. Sticky sessions.** The real bug: session state lives in each node's **local RAM**, so when a user's request lands on a *different* node (after a deploy, a scale event, or normal balancing) that node has no session → "random logout." Stickiness only *hides* it by pinning the user to their original node. Three things it makes worse: (1) that node is now a **SPOF for those users**, it dies, they're all logged out; (2) **uneven load**, long-lived sticky users pile onto specific nodes; (3) **autoscaling/deploys** become disruptive, you can't freely drain or replace a node without dropping its users' sessions. Correct fix: **externalize session state** (Redis or a signed JWT), making the app stateless; then any node serves any request, plain round-robin/least-connections works, and stickiness is unnecessary.

**7. Health check design.** A good `/readyz`: returns 200 only if the process can *actually serve a request right now*, e.g., a fast `SELECT 1` against Postgres (or a check of a cached, recently-refreshed connection-pool health flag) and a `PING` to Redis, both with tight timeouts (say 200-500ms). It must **not** run an expensive query, hold long locks, or fan out to every downstream, a heavy `/readyz` can self-DoS under probe load or mark the whole fleet down when one shared dependency blips. It differs from `/livez`: **liveness** answers "is the process wedged/should it be restarted?" and should depend on *nothing external* (so a DB outage doesn't trigger pointless restart loops of healthy app processes); **readiness** answers "should the LB send me traffic *now*?" and *does* consider dependencies (a node with no DB connection should be pulled from the LB but not killed).

**8. WebSocket deploy.** Roll **one node at a time** (or in small batches): (1) **deregister** the target ws-node from the LB so it gets no *new* connections; (2) optionally send its ~15,000 clients an application-level "please reconnect" message *staggered* over, say, 60-120s so they don't all reconnect at once; clients reconnect through the LB and land on other nodes via **least-connections**; (3) once drained (or the drain window elapses), deploy the new version and re-register it; (4) repeat for the next node. Crucially, clients must implement **reconnect with jittered exponential backoff** so any unexpected drop becomes a smooth trickle, not a thundering herd. Never kill all 5 nodes (or even a full node abruptly) at once, that's 75,000 simultaneous reconnects.
