## Start here

Before any theory, let's say what "system design" actually is, because the phrase sounds intimidating and it really isn't.

**System design is architecture for software.** When an architect designs a building, they don't start by picking bricks. They start by asking: How many people will use it? Is it a house or a stadium? Does it need to survive an earthquake? Only then, once they know the requirements, do they decide on materials, load-bearing walls, plumbing, and fire exits. Picking bricks first would be backwards: you'd build a fine brick wall and then discover you needed it to hold up a 40-story tower.

That's the whole mistake this chapter trains you out of. The natural instinct is to jump straight to "let's use Postgres" or "let's add Redis": that's picking bricks. The discipline is to design the city from its requirements: figure out how many people, how fast, how reliable, and let those numbers tell you which bricks to use.

Here's the city analogy made literal:

```
  building/city                 software system
  ──────────────                ───────────────
  "how many residents?"     →   how many users / requests per second?
  "rush hour traffic?"      →   peak QPS vs average QPS
  "house vs stadium?"       →   100 users vs 200 million users (totally different builds)
  "earthquake-proof?"       →   availability target (99.9%? 99.99%?)
  "highways & off-ramps"    →   load balancers routing traffic
  "warehouses near stores"  →   caches/CDN holding data close to users
  "the city archive"        →   the database (source of truth)
  "the postal service"      →   queues moving work in the background
  "toll booths / security"  →   rate limiters protecting everything
```

**Why the framework matters.** A beginner stares at "design Twitter" and freezes; it feels like it requires a flash of genius. It doesn't. It requires a checklist applied calmly. The 8-step framework below is that checklist. It's the same eight steps every time, whether you're designing a link shortener or a stock-market dashboard. The genius isn't in inventing an architecture from nothing; it's in asking the right questions, doing a little arithmetic, and then snapping together a small set of well-understood parts (the "bricks" from Chapters 9.1-9.5) against whatever the arithmetic says the bottleneck is.

**It's a repeatable process, not magic.** Internalize this early: there is no secret. Senior engineers don't have a bigger bag of tricks; they have the same eight steps, more practice asking clarifying questions, and a better feel for when a number is big enough to matter. All three of those are learnable, and this chapter is where you learn them.

What you'll be able to do by the end of this chapter:
- Take a vague prompt ("design a feed") and turn it into concrete requirements by asking the right questions.
- Do back-of-envelope math (QPS, storage, bandwidth) that *forces* the architecture instead of guessing it.
- Draw a boxes-and-arrows diagram with a CDN, load balancer, cache, database, and queue, and explain why each box is there.
- Identify the single bottleneck and apply the cheapest layer that relieves it.
- State out loud what you optimized for and what you gave up, the mark of someone who actually understands the design.
- Walk into a system-design interview and run the clock yourself instead of being run by it.

If that list feels like a lot right now, good: by the end it'll feel like a routine. Let's build the routine.

## Theory

### A framework for system design

Always follow the same path. It keeps you from jumping to a database choice before you know the read:write ratio, and it's exactly what interviewers grade.

```
1. REQUIREMENTS    functional (what it does) + non-functional (scale, latency,
                   availability, consistency). Ask clarifying questions. Scope it.
2. ESTIMATES       back-of-envelope (Ch 9.1): QPS (avg+peak), storage, bandwidth.
                   These numbers drive every later decision.
3. API             define the endpoints/contract. Forces clarity on what's exchanged.
4. DATA MODEL      entities, access patterns, then pick storage to fit the patterns.
5. HIGH-LEVEL      boxes + arrows: client -> CDN -> LB -> app -> cache/db/queue.
6. DEEP DIVES      zoom into the 1-2 hardest parts (the bottleneck, the tricky algo).
7. BOTTLENECKS     find the limiting resource; add cache/replica/shard/queue/LB.
8. TRADEOFFS       state what you optimized for and what you gave up. Be explicit.
```

Two rules to drill: **requirements before solutions** (don't design a globally-distributed system for 100 users), and **estimates before architecture** (the math *tells* you whether you need a CDN, sharding, or a queue, Chapter 9.1's media estimate did exactly this).

### The clarifying-questions playbook

Step 1 lives or dies on the questions you ask. A vague prompt ("design a feed") is *deliberately* underspecified, the interviewer wants to see whether you'll pin it down or charge off building the wrong thing. Here's a standing list of questions to ask for *any* design, grouped so you never forget a category:

```
SCALE
  - How many users (total, and daily-active)?
  - How many requests per second (and what's the peak vs average)?
  - How much data total, and how fast does it grow?

READ/WRITE SHAPE
  - What's the read:write ratio? (read-heavy → caches/replicas;
    write-heavy → sharding/queues/log)
  - Are reads/writes uniform or skewed (a few hot keys)?

LATENCY
  - What's the latency target for the critical path? (p50 and p99)
  - Is this path in the user's click path (must be fast) or background?

CONSISTENCY
  - Can reads be slightly stale (eventual) or must they see the latest write (strong)?
  - Are there invariants that must never break (money, inventory, uniqueness)?

AVAILABILITY & DURABILITY
  - What availability target? (99.9% = 8.8h/yr down; 99.99% = 53min/yr - Ch 9.1)
  - Is losing data acceptable, or must everything be durable?

SCOPE
  - Which features are in scope for this discussion vs out?
  - Single region or global? Mobile or web? Authenticated?
```

Don't fire all of these like a deposition, ask the 3-5 that most change the design, state your assumptions for the rest ("let's assume read-heavy, ~200M DAU, eventual consistency is fine for the feed"), and move on. **Stating assumptions out loud is itself a graded signal**: it shows you know the answer would change the design.

The single most load-bearing question is almost always the **read:write ratio**, because it splits the entire design space:

```
read-heavy   (e.g. 100:1)  →  cache, then read replicas, then CDN.  Reads are the load.
write-heavy  (e.g. 1:10)   →  shard the writes, queue + batch, use a log.  Writes are the load.
```

### A back-of-envelope refresher (tying to Ch 9.1)

Step 2 is just arithmetic, but it's the arithmetic that *forces* the architecture. Let's re-run the core move from Chapter 9.1 so it's fresh, because every design below leans on it.

The reusable conversions to keep in your head:

```
1 day      ≈ 86,400 seconds   (handy: ~100,000, round up when estimating peaks)
1 month    ≈ 2.6 million seconds   (30 × 86,400)
KB→MB→GB→TB→PB each ×1000 (decimal, for back-of-envelope)
peak ≈ 2-3× average   (use ×3 unless I know better)
```

Worked refresher, suppose a product has **10M daily-active users**, each making **20 requests/day**:

```
total requests/day = 10e6 × 20 = 200e6 = 200 million
average QPS        = 200e6 / 86,400 ≈ 2,315 req/s
peak QPS (×3)      ≈ 6,900 req/s
```

Now the *interpretation*, which is the actual skill: ~7k peak QPS is comfortably servable by a handful of stateless app boxes behind a load balancer (Ch 9.3), no exotic architecture needed yet. But if you then learn each request reads a 50 KB object:

```
read bandwidth at peak = 6,900 × 50 KB = 345 MB/s ≈ 2.8 Gbps
```

…that bandwidth number is what tells you that you need a **CDN** to offload egress (Ch 9.2), not a clever app trick. The number forced the component. That's the entire point of step 2: you don't *decide* to add a CDN, the math *hands* you a CDN. Every design below is just this move, repeated.

Keep a tiny reusable estimator in your head, and here it is as runnable Python so you can sanity-check the arithmetic instead of fumbling zeros on a whiteboard:

```python
def estimate(dau, reqs_per_user_per_day, bytes_per_req, peak_factor=3):
    """Back-of-envelope: turn user/scale assumptions into the numbers that pick components."""
    sec_per_day = 86_400
    total_per_day = dau * reqs_per_user_per_day
    avg_qps  = total_per_day / sec_per_day
    peak_qps = avg_qps * peak_factor
    avg_bw_bps  = avg_qps  * bytes_per_req * 8          # bits/sec
    peak_bw_bps = peak_qps * bytes_per_req * 8
    def human(bps):
        for unit in ("bps", "Kbps", "Mbps", "Gbps", "Tbps"):
            if bps < 1000: return f"{bps:.1f} {unit}"
            bps /= 1000
        return f"{bps:.1f} Pbps"
    print(f"requests/day : {total_per_day:,.0f}")
    print(f"avg QPS      : {avg_qps:,.0f}")
    print(f"peak QPS     : {peak_qps:,.0f}")
    print(f"avg bandwidth: {human(avg_bw_bps)}")
    print(f"peak bandwidth: {human(peak_bw_bps)}")

# the worked example above:
estimate(dau=10_000_000, reqs_per_user_per_day=20, bytes_per_req=50_000)
# requests/day : 200,000,000
# avg QPS      : 2,315
# peak QPS     : 6,944
# avg bandwidth: 925.9 Mbps
# peak bandwidth: 2.8 Gbps   <- this line is the one that says "you need a CDN"
```

The discipline isn't the Python; it's reading the *last line* and letting it dictate the architecture. Plug in any design's assumptions and the output tells you which of the Common Mistakes you're about to make.

### How the layers fit together

The canonical read/write path, assembled from this whole part:

```
                 ┌──────────────── CDN (Ch 9.2) static + cacheable GETs, edge, TLS
   client ───────┤
                 └──> [ Load Balancer (Ch 9.3) ] L7, health checks, TLS
                            │   ↑ rate limiting (Ch 9.4) at gateway
                       ┌────┴────┬────────┐
                    [app]     [app]     [app]   stateless tier (Ch 9.1) -> autoscale
                       │         │
            ┌──────────┼─────────┼───────────────┐
            ▼          ▼         ▼                ▼
       [ Cache ]   [ Primary DB ]──repl──>[ Read replicas ]   [ Queue (Ch 9.5) ]
       Redis (9.2)  writes          async      reads              │
                                                                  ▼
                                                            [ Workers ] async/slow work
```

Each layer answers a specific pressure:
- **CDN**, kills geographic latency and offloads static/cacheable egress (the 95% from 9.1).
- **LB**, turns N stateless app boxes into one service; survives node death (redundancy → availability math).
- **Cache**, absorbs read QPS so the DB isn't the bottleneck; the hit-rate math is the lever.
- **Read replicas**, scale *reads* horizontally (most systems are read-heavy); writes still go to the primary.
- **Sharding**, when writes or data size exceed one primary, split by key (consistent hashing, 9.3).
- **Queue**, decouples slow/spiky/fan-out work from the request path; smooths spikes (9.5).
- **Rate limiter**, protects all of the above from overload/abuse (9.4).

The recurring move: **find the bottleneck resource, then apply the cheapest layer that relieves it.** Reads hot? Cache, then replicas. Writes hot? Shard, or queue + batch. Geography? CDN/edge. Spikes? Queue + autoscale. Abuse? Rate limit.

The cache bullet hides the most-abused phrase in system design, "just add a cache." A cache only helps if you can name the hit rate it'll achieve, because the DB only sees the *misses*. Here's the lever as runnable Python so you never hand-wave it:

```python
def cache_relief(read_qps, db_capacity_qps, hit_rate):
    """How much read load actually reaches the DB after the cache, and is it safe?"""
    db_qps = read_qps * (1 - hit_rate)
    safe = db_qps <= db_capacity_qps
    # the minimum hit rate that keeps the DB under capacity:
    min_hit = max(0.0, 1 - db_capacity_qps / read_qps)
    print(f"reads={read_qps:,}/s  hit_rate={hit_rate:.0%}  -> DB sees {db_qps:,.0f}/s "
          f"({'OK' if safe else 'OVERLOADED'}); need hit_rate >= {min_hit:.1%}")

cache_relief(read_qps=50_000, db_capacity_qps=8_000, hit_rate=0.80)
# reads=50,000/s  hit_rate=80%  -> DB sees 10,000/s (OVERLOADED); need hit_rate >= 84.0%
cache_relief(read_qps=50_000, db_capacity_qps=8_000, hit_rate=0.90)
# reads=50,000/s  hit_rate=90%  -> DB sees 5,000/s (OK); need hit_rate >= 84.0%
```

So "add a cache" at 80% hit rate *still overloads the DB* here; you needed ≥84%. Whether 84% is achievable depends entirely on access skew (a few hot keys read over and over), which is why the redirect and feed designs work (heavily skewed) and a uniform-random lookup wouldn't.

### Consistency vs availability in practice (CAP/PACELC, lived)

CAP: under a network **partition** you must choose **C**onsistency or **A**vailability. PACELC adds: even without a partition, you trade **L**atency vs **C**onsistency. In real designs this becomes concrete choices:

- **Strong consistency** (every read sees the latest write): needed for money, inventory, auth, unique constraints. Costs latency and availability (must coordinate; a partition may force rejecting writes). NYX's *trade ledger* is strongly consistent.
- **Eventual consistency** (reads may be briefly stale, converge later): fine for feeds, like-counts, view-counts, search indexes, dashboards. Buys availability and low latency at scale. NYX's *dashboard analytics* are eventually consistent, a 1-2s stale chart is fine; a wrong balance is not.

The practical heuristic: **default to eventual consistency for scale, reserve strong consistency for the few invariants that truly require it**, and make those a small, well-bounded part of the system (often a single strongly-consistent service/DB). Replication itself is the everyday version of this: async replicas give you read scaling and HA but a small replication lag (eventual); sync replication gives consistency at write-latency cost.

### Availability math refresher (series vs parallel, from Ch 9.1)

Every "is this design highly available?" answer leans on two formulas from Chapter 9.1, and they explain *why* the layers above are shaped the way they are:

```
SERIES  (request must pass through ALL hops):   A_total = A1 × A2 × ... × An
PARALLEL/redundant (succeeds if ANY replica is up): A_total = 1 - (1-A)^k
```

Series multiplies *down* (more hops = less available), which is the math behind "shorten the critical synchronous path." Parallel multiplies *up* (more replicas = more available), which is the math behind redundant app boxes, replicated caches, and DB replicas. Runnable:

```python
def series(*avails):
    p = 1.0
    for a in avails: p *= a
    return p

def parallel(per_node, k):
    return 1 - (1 - per_node) ** k

def downtime_per_year(avail):
    mins = (1 - avail) * 365 * 24 * 60
    return f"{mins:,.0f} min/yr"

# A redirect path with 4 single-instance hops at 99.9% each:
chain = series(0.999, 0.999, 0.999, 0.999)
print(f"4 hops in series @99.9% -> {chain:.5f}  ({downtime_per_year(chain)})")
# 4 hops in series @99.9% -> 0.99601  (1,397 min/yr)  <- WORSE than any single hop!

# Make each hop redundant (2 replicas, succeeds if either is up):
hop = parallel(0.999, k=2)            # one redundant hop
chain2 = series(hop, hop, hop, hop)   # 4 such hops
print(f"4 redundant hops -> {chain2:.6f}  ({downtime_per_year(chain2)})")
# 4 redundant hops -> 0.999996  (2 min/yr)  <- now it's HA
```

That first result is the lesson that bites people: chaining four "three-nines" components in series gives you *less* than three nines overall (1,397 min/yr ≈ 23 hours). Availability isn't a property of one box; it's the *product down the path*. The fix is redundancy at each hop (parallel), which is exactly why the canonical diagram has multiple app boxes, replicated caches, and DB replicas, and why the URL-shortener and dashboard designs insist the read/ingest path be redundant end to end.

### Common mistakes

These are the traps most people fall into. Each one is a place where a design, or an interview, goes sideways. Keep this list mentally pinned.

1. **Jumping to a database (or any tech) before requirements.** "Let's use Cassandra" before you know the access patterns is picking bricks first. The data model and storage choice come from the *access patterns* (step 4), which come from requirements (step 1). Name the tech *last*, justified by the numbers.

2. **Designing for scale you don't have.** A globally-sharded, multi-region, microservice mesh for a product with 100 users is not impressive; it's a red flag. Match the architecture to the *estimated* load. If the math says 7k QPS, a couple of app boxes and one cache is the *correct* answer; reaching for Kafka would be over-engineering.

3. **Ignoring the estimates after computing them.** The classic sin: do the QPS/storage math in step 2, then design as if it didn't exist. The numbers are not a ritual, they are the *input* to every later decision. If you computed 500k writes/s, your data store had better be able to take 500k writes/s.

4. **No single bottleneck analysis.** Hand-waving "we'll scale it" without naming *the* limiting resource. Every system has one thing that breaks first under load. If you can't point to it ("the redirect read path," "the celebrity fan-out," "Kafka ingest throughput"), you haven't actually designed anything.

5. **"Just add a cache" without hit-rate reasoning.** A cache only helps if reads are *repeated and skewed*. Saying "add Redis" without asking "what's the hit rate, and what happens on a miss?" is cargo-culting. A 50% hit rate on a uniform-access workload barely helps; a 95% hit rate on a skewed one is transformative. Reason about the *number*.

6. **Forgetting the write path and consistency.** It's easy to design a clean read path and forget how data *gets in*, and whether two concurrent writes can corrupt an invariant. Always trace the write path explicitly and ask: what must be strongly consistent here? (Money? Uniqueness? Inventory?)

7. **Not stating tradeoffs.** Every choice gives something up. A design presented as having no downsides is a design that hasn't been understood. "You chose eventual consistency, which means a post can appear 1-2s late, acceptable here because it's a feed" is the sentence that demonstrates judgment.

8. **Over-engineering with microservices (or anything).** Splitting into 12 services, adding a service mesh, an event-sourcing layer, and CQRS for a CRUD app adds operational cost and failure modes with no benefit. Complexity is a cost, not a feature. Reach for the *simplest* thing the requirements justify, and add complexity only when a specific bottleneck demands it.

The meta-mistake behind most of these: **skipping steps of the framework.** The framework exists precisely to prevent them. Run all eight steps, in order, every time.

### On the job / interview angle

This is the chapter that gets people hired, so let's be precise about how a system-design interview actually runs and what's being graded, because once you know the rubric, the nerves drop and you can just *play the game well*.

**The format.** A system-design interview is typically **45 minutes** (sometimes 60), one interviewer, an open prompt like "Design a URL shortener" or "Design Twitter's feed." There's usually a whiteboard (physical or virtual). Importantly, **the interviewer is not looking for the one right answer**; there isn't one. They're watching *how you think*. It's a collaborative conversation, not an exam. You're expected to drive, ask questions, and check in.

**The time budget** (for a 45-minute slot, adjust proportionally for 60):

```
  STEP                         TIME      what I'm doing
  ──────────────────────────   ───────   ──────────────────────────────────
  1. Requirements + scope      ~5 min    ask clarifying Qs, state assumptions,
                                          write down functional/non-functional
  2. Estimates                 ~5 min    QPS (avg+peak), storage, bandwidth.
                                          Out loud. This sets up everything.
  3. API                       ~3 min    sketch the key endpoints/contract
  4. Data model                ~4 min    entities + access patterns → storage
  5. High-level design         ~8 min    boxes + arrows, the whole picture
  6. Deep dives                ~12 min   interviewer picks (or I pick) the
                                          1-2 hardest parts; go deep here
  7. Bottlenecks / scaling     ~5 min    name the limiter, apply the lever
  8. Tradeoffs / wrap-up       ~3 min    state what I optimized for / gave up
```

The deep dive (step 6) is where most of the *signal* is: it's where you prove you actually understand a component rather than just naming it. You should *budget for it* and not blow the clock on drawing a perfect high-level diagram.

**What interviewers look for (the rubric):**
- **Drives the conversation**, you structure your own time, you don't wait to be told what to do next.
- **Asks clarifying questions** before designing (and states assumptions for what you don't ask).
- **Does the math**, actual numbers, out loud, and then *uses* them.
- **Justifies every component**, "you're adding a cache *because* reads are 100:1 and skewed," not just "add a cache."
- **Identifies the bottleneck** and proposes the cheapest fix.
- **States tradeoffs** unprompted, the single strongest senior signal.
- **Handles follow-ups** gracefully, "what if traffic 10×'s?", "what if this node dies?" You should welcome these.
- **Communicates clearly**, clean diagram, clear narration, no mumbling into the whiteboard.

**Red flags they're watching for** (the inverse, the Common Mistakes above, especially): jumping to tech before requirements, never doing the math, no tradeoffs, over-engineering, going silent.

**Phrases to use** (they signal exactly the right thing):
- *"Before I design anything, let me ask a few questions to scope this."*
- *"Let me do some quick back-of-envelope math to figure out the load."*
- *"Since this is read-heavy at about 100:1, the reads are my main concern, so…"*
- *"The bottleneck here is going to be X; the cheapest way to relieve it is Y."*
- *"I'm optimizing for low redirect latency; the tradeoff is that I give up…"*
- *"Let me state my assumptions: I'm assuming …, does that match what you had in mind?"*
- *"There are two approaches here, A and B. Given the read:write ratio, I'd lean A because…"*

**The single best habit:** narrate the framework as you go. Literally say "Step one, requirements." It keeps you organized, keeps the interviewer with you, and makes the structured thinking *visible*, which is the thing being graded. On the job, the same structure is how you write a design doc (the headings *are* the eight steps) and how you lead a design review. The interview is just the design doc, spoken, under a clock.

## Build it - Three worked designs

### Design A - URL Shortener (e.g., bit.ly)

**1. Requirements.**
- Functional: `shorten(long_url) -> short_url`; `GET /{code} -> 301 redirect` to the long URL; optional custom alias, expiry, click analytics.
- Non-functional: redirects must be **very low latency** (it's in the user's click path) and **highly available** (read path); read-heavy; links effectively permanent.

**2. Estimates.** Assume 100M new URLs/month, read:write = 100:1.
```
Writes: 100M/month / (30·86400) ≈ 38 writes/s  (peak ×3 ≈ 115/s)  -> tiny
Reads:  100:1 -> 3,800 reads/s avg (peak ×3 ≈ 11,400/s)           -> the real load
Storage: 100M/mo × 5 yr = 6B URLs. Per row ~ (code 7B + URL 200B + meta) ≈ 500B
         6e9 × 500B = 3e12 B = 3 TB  -> fits a sharded DB; not huge.
```
Read-heavy + low-latency redirect → **cache the hot links; the DB is barely stressed on writes.**

**3. API.**
```
POST /api/shorten {url, alias?, ttl?} -> 201 {short_url, code}
GET  /{code}                          -> 301 Location: <long_url>   (or 404)
GET  /api/stats/{code}                -> click analytics (async-aggregated)
```

**4. The encoding math (the heart of it).** You need short, unique codes. Use **base62** (`[a-zA-Z0-9]`, 62 symbols) over an auto-increment ID or a hash.
```
chars per code   distinct codes (62^n)
   5             62^5  ≈ 916 million
   6             62^6  ≈ 56.8 billion
   7             62^7  ≈ 3.52 trillion
```
6B URLs over 5 years needs > 6e9 codes → **7 chars** (62^7 ≈ 3.5e12) gives enormous headroom; even 6 chars (56.8B) suffices. We'll use 7. Two ways to generate:
- **Counter + base62:** keep a global monotonically increasing 64-bit ID, encode it in base62. Guarantees uniqueness, no collision checks. Distribute the counter with a range-allocator (each app node claims a block of IDs, e.g., 1000 at a time, from a central source) to avoid a single-counter bottleneck. (Sequential codes are slightly guessable, if that matters, scramble the ID space with a reversible permutation/Feistel before encoding.)
- **Hash + truncate:** `base62(md5(url))[:7]`, check for collision, retry on conflict. Simpler but needs a uniqueness check (a read per write) and collision handling. Counter approach is cleaner at scale.

```python
ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
def base62_encode(n):
    if n == 0: return ALPHABET[0]
    s = []
    while n:
        n, r = divmod(n, 62)
        s.append(ALPHABET[r])
    return "".join(reversed(s))
# next_id() returns a globally-unique increasing int (range-allocated per node)
# code = base62_encode(next_id()).rjust(7, '0')

def base62_decode(s):
    n = 0
    for ch in s:
        n = n * 62 + ALPHABET.index(ch)
    return n

# round-trip check + a quick demo of the range-allocator idea:
class RangeAllocator:
    """Each app node calls take() to claim a block of IDs from a central counter,
    so code generation never bottlenecks on a single shared increment."""
    def __init__(self, block=1000):
        self._central = 0          # in reality: a row in a DB / Redis INCRBY
        self._block = block
        self._next = self._end = 0
    def take(self):
        if self._next >= self._end:                 # claim a fresh block (one central op)
            self._next = self._central
            self._central += self._block
            self._end = self._central
        nid = self._next
        self._next += 1
        return nid

alloc = RangeAllocator(block=1000)
for _ in range(3):
    nid = alloc.take()
    code = base62_encode(nid).rjust(7, "0")
    assert base62_decode(code.lstrip("0") or "0") == nid   # round-trip holds
    print(nid, "->", code)
# 0 -> 0000000
# 1 -> 0000001
# 2 -> 0000002
```

The decode function matters because with the counter approach you can recover the ID from the code without a lookup, useful for analytics and sharding. The `RangeAllocator` is the concrete fix for the "single counter is a write bottleneck" worry: each node touches the central counter once per *block* (1000 IDs), so the central op rate is 1000× lower than the write rate.

**5. Data model & storage.** Single table keyed by `code`: `{code (PK), long_url, created_at, ttl, owner}`. Access is point-lookup by `code` → a **key-value store** (DynamoDB / Cassandra / sharded MySQL by `code`) is ideal. Shard by `code` (consistent hashing) for the 3 TB / write distribution.

**6. High-level design.**
```
shorten:  client -> LB -> app -> next_id() -> base62 -> write {code->url} to KV -> return short_url
redirect: client -> CDN(?) -> LB -> app -> cache.get(code) ──hit──> 301 (sub-ms)
                                              └─miss─> KV.get(code) -> cache.set -> 301
clicks:   redirect also enqueues a click event -> queue -> worker -> analytics store (async)
```
- **Cache (Redis, cache-aside, Ch 9.2):** redirects are read-heavy and skewed (some links go viral) → a high cache hit rate makes the median redirect sub-millisecond and shields the KV store. This is the single most important optimization.
- **Click analytics async (Ch 9.5):** never block the redirect to record a click, enqueue it and aggregate in a worker. Keeps the hot path fast and survives analytics-store hiccups.
- **Availability:** redirect path = stateless app + replicated cache + replicated KV → push to 99.99% (the read path is the product).

**7. Bottlenecks / tradeoffs.** The redirect read path is the load; cache + KV handle it. The counter could bottleneck writes → range-allocation fixes it. Tradeoff: eventual consistency on click counts (fine) but exactly-once *code generation* (the counter guarantees it). 301 vs 302: 301 (permanent) lets browsers/CDN cache the redirect (fewer hits, but you lose per-click tracking); 302 keeps every click flowing through you (better analytics, more load). Choose per product need.

### Design B - News Feed / Timeline (e.g., Twitter/Instagram home feed)

**1. Requirements.**
- Functional: users post; a user's home feed shows recent posts from accounts they follow, newest-first.
- Non-functional: feed load must be **fast** (read path, in the app's main screen); read-heavy; eventual consistency acceptable (a post appearing 1-2s late is fine); handle celebrities with millions of followers.

**2. Estimates.** 200M DAU, each opens feed ~10×/day, posts ~2×/day.
```
Feed reads: 200M × 10 / 86400 ≈ 23,000 reads/s avg (peak ×3 ≈ 70,000/s)
Posts:      200M × 2  / 86400 ≈ 4,600 writes/s avg (peak ×3 ≈ 14,000/s)
```
Reads dominate by ~5:1, and a single feed read could otherwise require querying *all* the accounts a user follows and merging, expensive. This is the core problem: **how to assemble a feed cheaply.**

**3. API.**
```
POST /api/post {text, media?}            -> 201
GET  /api/feed?cursor=<ts/id>&limit=20   -> [posts] (paginated, newest-first)
POST /api/follow {target_user_id}
```

**4. The central tradeoff: fan-out on write vs fan-out on read.**

```
FAN-OUT ON WRITE ("push")               FAN-OUT ON READ ("pull")
on POST: write the post id into EACH      on POST: just store the post.
follower's precomputed feed cache.        on FEED READ: query all followed users'
on FEED READ: just read your ready feed.  recent posts and merge-sort at read time.
  + feed reads are O(1), super fast        + writes are cheap (one insert)
  + great for read-heavy (our case)        + no wasted work for inactive users
  - writes are expensive (a celeb with     - feed reads are expensive (fan-in,
    50M followers = 50M cache writes!)        merge across many users)
  - wastes work for inactive followers     - slow feeds for users following many
```

Because the system is read-heavy (5:1) and feed-read latency is the product, **fan-out on write is the default**, precompute feeds so reads are O(1). But it breaks on **celebrities**: pushing one post to 50M follower-feeds is a write storm. So real systems use a **hybrid**:
- **Most users:** fan-out on write, when they post, append the post id to each follower's feed list (in Redis), via a queue + workers (async, Ch 9.5). Reads are instant.
- **Celebrities (above a follower threshold):** do *not* fan out. At feed-read time, **merge** the user's precomputed feed (from normal accounts) with a *pull* of the few celebrities they follow (whose recent posts are heavily cached). Best of both: cheap writes for celebs, fast reads for everyone.

**5. Data model.**
```
posts:        {post_id (snowflake, time-sortable), author_id, text, media_url, created_at}
graph:        follows(follower_id, followee_id)   -> who follows whom
feed cache:   Redis list/sorted-set per user: user:{id}:feed -> [post_id, ...] (capped, e.g. 800)
post store:   posts in a sharded DB / KV by post_id; media in blob store + CDN
```
Snowflake-style IDs (timestamp-prefixed) make posts naturally sortable by time and shardable.

**6. High-level design.**
```
post:  client -> LB -> app -> write post (DB) -> enqueue fan-out job (Ch 9.5)
                                                     │
                                  workers: for each follower (non-celeb authors):
                                           LPUSH post_id into user:{follower}:feed (Redis), trim
read:  client -> CDN(media) / LB -> app ->
            read user:{id}:feed (Redis, O(1))         <- precomputed
            + merge recent posts of celebs they follow (cached pull)
            -> hydrate post_ids -> posts (cache -> DB) -> return page
```
- **Cache everywhere (Ch 9.2):** feeds, post bodies, and the social graph hot set live in Redis; media via CDN.
- **Queue for fan-out (Ch 9.5):** posting returns immediately; the heavy fan-out happens async in workers, smoothing the write spike and decoupling post latency from follower count.
- **Replicas/sharding:** posts and graph sharded by id; read replicas for the DB-backed lookups behind the cache.

**7. Bottlenecks / tradeoffs.** The celebrity fan-out is *the* bottleneck → solved by the hybrid (don't push, pull-and-merge for celebs). Eventual consistency: a post may take a second or two to appear in all feeds (the fan-out queue drains), acceptable. Storage vs compute tradeoff: fan-out on write trades extra storage (duplicated post ids across feeds) and write work for cheap reads, the right trade in a read-heavy product. Feed lists are capped (you don't precompute infinite history; older pages fall back to a pull query).

### Design C - Real-time Analytics Dashboard (NYX Finance)

**1. Requirements.**
- Functional: ingest a high-rate stream of market/trade events; compute time-series aggregations (OHLC bars, VWAP, rolling metrics); display live charts that **update in real time** and support historical queries.
- Non-functional: **high write throughput** (ingestion is write-heavy, opposite of the prior two), low-latency live updates (push, not poll), durable history, ingest path near 99.99% (lost market data during open is unacceptable, Ch 9.1).

**2. Estimates.** Say 50,000 instruments, each emitting ~10 ticks/s at peak (open bell).
```
Ingest peak: 50,000 × 10 = 500,000 events/s   -> write-heavy, the dominant load
Event size ~ 100 B -> ingest bandwidth = 500k × 100B = 50 MB/s ≈ 400 Mbps
Raw storage/day (tick-level): 500k × 100B × (6.5h trading × 3600) ≈ 500k×100×23400
   ≈ 1.17e12 B/day ≈ 1.2 TB/day raw  -> downsample/roll up aggressively for history
Dashboard reads: thousands of concurrent viewers, each watching a handful of charts,
   pushed updates ~1-4/s per chart -> WebSocket fan-out, modest per-connection.
```
Half a million writes/sec is the headline, this demands a **streaming ingestion log + a time-series store**, not a generic SQL primary.

**3. API.**
```
ingest: internal -> producers write to Kafka topic "ticks" (keyed by instrument)
query:  GET /api/series?symbol=AAPL&interval=1m&from=..&to=..  -> [OHLC bars]
live:   WS  /stream  subscribe {symbols:[...], interval} -> server pushes bar updates
```

**4. Data model & storage (where it gets interesting).**
- **Ingestion = a partitioned log (Kafka, Ch 9.5):** events land in a Kafka topic partitioned **by instrument** so all of one symbol's events are ordered in one partition (per-key ordering) and parallelism = partition count. Kafka's sequential-write throughput is built for 500k/s; retention gives replay for reprocessing.
- **Stream processing:** consumer groups (or Flink/Kafka Streams) read the log and compute rolling aggregations, 1s/1m/5m/1h OHLC bars, VWAP, as data flows. This is *fan-out on write* for analytics: compute the bars once at ingest, not per query.
- **Time-series storage:** write the computed bars to a **time-series DB** (TimescaleDB / ClickHouse / InfluxDB) optimized for time-ordered, append-heavy data, columnar compression, and time-range scans. Keep fine granularity recent, **downsample** older data (1s → 1m → 1h) to control the 1.2 TB/day growth (retention/rollup policy).
- **Hot cache (Redis):** the latest bar/price per instrument cached for instant reads and to seed new WebSocket subscribers.

**5. High-level design.**
```
ingest:  market feeds -> producers -> [ Kafka "ticks" (partitioned by symbol) ]
                                            │
                          stream processors (consumer groups): roll up OHLC/VWAP
                                            ├──> Time-Series DB (durable history, downsampled)
                                            ├──> Redis (latest value per symbol, hot cache)
                                            └──> publish updates -> WebSocket fan-out layer

query (historical): client -> LB -> app -> TSDB (time-range scan) [+ cache] -> chart data
live (real-time):   client --WebSocket--> push gateway
                       on connect: send latest bars from Redis (instant first paint)
                       then: subscribe to updates for the requested symbols ->
                       server PUSHES new bars as the stream processor emits them
```

- **Why WebSockets, not polling:** thousands of clients polling every second = thousands of QPS of mostly-unchanged data and seconds of staleness. A WebSocket holds an open connection and the server **pushes** only when a bar updates, lower latency, far less load. The push layer fans out updates (often via Redis pub/sub or Kafka → WS gateway, Ch 9.5's pub/sub shape). Stateful connections, so the WS layer scales horizontally with a shared pub/sub backbone (and the LB must support WS / sticky at the connection level, Ch 9.3).
- **Why a log for ingest:** Kafka decouples bursty 500k/s ingestion from downstream processors (load leveling, Ch 9.5), gives durability/replay (recompute bars after a bug), and lets multiple independent consumers (live push, history writer, alerting, audit) read the same stream, the fan-out a queue can't do.
- **Consistency:** the dashboard is **eventually consistent** by design, a bar may appear a few hundred ms after the tick; that's acceptable and buys the throughput. The *trade ledger* (a different NYX subsystem) is strongly consistent; keep them separate.

**6. Bottlenecks / tradeoffs.** Ingest throughput → Kafka partitioning (add partitions to scale). Storage growth → downsampling/retention (raw ticks short, bars long). Live fan-out → WebSocket gateway + pub/sub, scaled horizontally. Tradeoff: precomputing bars at ingest (fan-out on write) makes queries cheap but means you must decide intervals up front; ad-hoc intervals fall back to querying finer bars and aggregating. Cost vs freshness: 1s bars are pricier to store/compute than 1m, match granularity to product value.

### Design D - Chat / Messaging App (e.g., WhatsApp / Slack DMs)

A fourth full pass through the framework, because chat exercises a different muscle than the first three: **stateful long-lived connections, strict per-conversation ordering, and presence**. (This is also the alternate prompt mentioned in the mini-project, here it is, fully worked.)

**1. Requirements.**
- Functional: 1:1 and group messaging; messages delivered in **order within a conversation**; delivery/read receipts; online/offline **presence**; message history retrievable; push notifications when offline.
- Non-functional: **low-latency delivery** (a chat that lags feels broken, target sub-200ms in-app); high availability; durable message history (losing a message is unacceptable); ordering *within a conversation* must be correct (global ordering across conversations does not matter); huge fan-in of long-lived connections.

Clarifying questions you'd ask first: *How many DAU? Group size cap? Must messages be end-to-end encrypted? Is global ordering needed, or just per-conversation? How long is history retained?* Let's assume: 100M DAU, groups up to ~500, per-conversation ordering only, history kept indefinitely.

**2. Estimates.** 100M DAU, each sends ~40 messages/day, each message read by ~2 recipients on average (mix of 1:1 and groups).
```
Messages sent/day = 100e6 × 40 = 4e9 = 4 billion/day
avg send QPS      = 4e9 / 86,400 ≈ 46,000 sends/s
peak send QPS (×3)≈ 140,000 sends/s
deliveries        = sends × ~2 recipients ≈ 280,000 deliveries/s at peak

Concurrent connections: say 25% of DAU online at once = 25M live WebSocket connections
   at ~10k connections/server -> ~2,500 connection-gateway servers (this is a real cost)

Storage: 4e9 msgs/day × ~300 B/msg (text + metadata) ≈ 1.2e12 B/day ≈ 1.2 TB/day
   × 365 ≈ 440 TB/yr  -> sharded, append-heavy store; media offloaded to blob+CDN separately
```
Two headline numbers drive everything: **140k sends/s** (write-heavy at the storage layer → shard) and **25M concurrent connections** (the connection tier is the surprising cost → a dedicated, horizontally-scaled gateway).

**3. API.**
```
WS  /connect                         -> establish persistent connection (auth on handshake)
WS  send   {conv_id, client_msg_id, text}     -> server assigns seq, persists, fans out
WS  recv   {conv_id, seq, sender, text, ts}   <- pushed to recipients
WS  ack    {conv_id, seq, type:delivered|read}-> receipts
GET /api/conversations/{id}/messages?before=<seq>&limit=50  -> history page (paginated)
GET /api/presence?users=[...]        -> last-seen / online status
```
The `client_msg_id` is the client's idempotency key, it lets the server dedupe retries (at-least-once delivery + idempotent write, Ch 9.5) so a flaky network doesn't produce duplicate messages.

**4. Data model.**
```
conversations: {conv_id, type(1:1|group), member_ids[], created_at}
messages:      {conv_id (partition key), seq (sort key, monotonic per conv),
                msg_id, sender_id, body, created_at}     -- PK = (conv_id, seq)
members:       {user_id, conv_ids[]}   -- a user's conversation list
presence:      Redis: user:{id}:presence -> {status, last_seen}  (TTL'd heartbeat)
delivery:      per (conv, user): last_delivered_seq, last_read_seq  (for receipts/unread)
```
**The key modeling decision is the message store, keyed by `(conv_id, seq)`.** Partitioning by `conv_id` puts an entire conversation in one partition, which gives you two things at once: (a) all of a conversation's messages are co-located for cheap history reads, and (b) a single place to assign the monotonic `seq` → **per-conversation ordering** falls out naturally. You deliberately do *not* try to order messages globally; the requirements only need ordering *within* a conversation, and partitioning by conversation gives you exactly that for free (same trick as Kafka partition-by-key in Design C).

**5. High-level design (boxes and arrows).**
```
 client ──WebSocket──> [ Connection Gateway tier ]  (25M conns; ~2,500 nodes)
                              │   (LB must support sticky/WS, Ch 9.3)
        send a message       ▼
                       [ Chat service ] ── assign seq (per conv_id) ──┐
                              │                                        │
                              ├──> persist to [ Message store ]  (sharded by conv_id)
                              │
                              └──> publish "new msg" to recipients via
                                   [ Pub/Sub backbone ] (Redis pub/sub / Kafka, Ch 9.5)
                                          │
                              ┌───────────┴───────────────┐
                              ▼                            ▼
                   recipient ONLINE:              recipient OFFLINE:
                   gateway holding their conn      enqueue -> [ Push notif service ]
                   PUSHES msg over its WebSocket   (APNs/FCM) + store as unread
```
Trace it end to end: a send arrives on whatever gateway node holds the sender's connection → forwarded to the chat service → the chat service assigns the next `seq` for that `conv_id`, persists, and publishes the message to the pub/sub backbone keyed by recipients → for each recipient who is online, the gateway holding *their* connection receives the publish and pushes it down their WebSocket; for offline recipients, a push notification is enqueued and the message is marked unread for later sync.

- **Connection gateway (the surprising tier):** because connections are long-lived and stateful, you can't just put app boxes behind a round-robin LB. You need a tier whose whole job is holding millions of sockets, and a **pub/sub backbone** so that "deliver to user X" can reach *whichever gateway node* currently holds X's connection without every node knowing about every connection (Ch 9.5 pub/sub fan-out, same shape as Design C's WS layer).
- **Presence via heartbeats (Redis):** clients send a heartbeat every ~30s that refreshes a TTL'd key `user:{id}:presence`. If the key expires (no heartbeat), they're offline. Presence is **eventually consistent** and cheap, being shown online for an extra 30s after disconnect is fine.
- **Offline path:** if a recipient isn't connected, the message is already durably persisted (it was written before fan-out), so on reconnect the client just requests messages with `seq > last_read_seq` and catches up. A push notification nudges them.

**6. Deep dives.** (a) **Per-conversation ordering:** assigning `seq` monotonically within a single partition (keyed by `conv_id`) is what guarantees order, concurrent sends to the same conversation are serialized at that one partition, so every recipient sees the same sequence. No global clock needed. (b) **Exactly-once feel over at-least-once transport:** the client's `client_msg_id` dedupes server-side; recipients dedupe by `(conv_id, seq)`. Retries are therefore safe. (c) **Fan-out to the right gateway:** the pub/sub backbone decouples "who sent it" from "who holds the recipient's socket," so the connection tier can scale independently of the chat service.

**7. Bottlenecks / tradeoffs.**
- *Bottleneck, the connection tier:* 25M concurrent sockets is the dominant cost and the thing that breaks first; relieved by horizontal gateway nodes + a pub/sub backbone so no single node tracks all connections.
- *Bottleneck, a hot group:* a 500-member group means one send → ~500 deliveries; large/active groups concentrate fan-out on one conversation's partition. Mitigate by capping group size and fanning out group deliveries through the pub/sub layer (not a tight loop in one process).
- *Tradeoffs:* you optimized for **low delivery latency + per-conversation correctness + durability**. You gave up **global ordering** (intentionally, it's not required and would be enormously expensive), and presence is **eventually consistent** (a brief lag in online status, which nobody notices). Storage is the price of durable history (440 TB/yr), accepted because losing messages is unacceptable; old media is offloaded to blob+CDN to keep the message store lean.

**Cross-design pattern recognition (all four).** Notice the same primitives recur: the *feed* and *analytics* designs both precompute at write time (fan-out on write) to make reads cheap; *chat* and *analytics* both lean on a **pub/sub backbone + stateful WebSocket tier** for real-time push; *chat* and *analytics* both get ordering from **partition-by-key** (conversation / instrument); all four lean on caching for hot reads and push slow/spiky/fan-out work onto a queue or log. The shorter the critical synchronous path and the more redundant each hop (Ch 9.1's series/parallel availability math), the more available the system. That recurrence *is* the skill, system design is recombining a small set of levers against the bottleneck the estimates revealed.

8. **Tradeoffs.** Metering is *eventually consistent* (aggregated async), acceptable for billing if reconciled; rate limits are *globally consistent* via the atomic Lua script because over-serving a tier is a contract/cost issue. Run each of these through the 8-step framework. For the design prompts, you don't need to write a novel, aim for the *reasoning*: clarifying questions, the estimates that force the architecture, a boxes-and-arrows sketch, the named bottleneck, and explicit tradeoffs. Treat them like timed interview reps (~30-45 min each). Solutions follow.

1. **Read:write reflex.** For each of these, state whether it's read-heavy or write-heavy and the *first* layer you'd reach for: (a) a product catalog browsed by millions but updated nightly; (b) an IoT fleet of 1M sensors each posting a reading every 10s; (c) a comments section on a viral article; (d) an audit log that's written constantly and read rarely.
2. **The estimate that forces a component.** A video platform has 5M DAU, each watching 3 videos/day averaging 50 MB. Compute daily egress and peak bandwidth (×3). What single component does that number force, and why?
3. **Cache hit-rate reasoning.** Reads are 50,000 QPS. Behind the cache, the database can serve only 8,000 QPS before it falls over. What's the *minimum* cache hit rate you need so the DB isn't the bottleneck? Show the arithmetic.
4. **Design a pastebin** (like Design A's cousin, but for text blobs up to 1 MB with optional expiry and syntax highlighting). Full 8 steps. Where does it differ from the URL shortener?
5. **Design a ride-sharing matching service**, riders request a ride, the system matches them to the nearest available driver in real time. Full 8 steps. The deep dive should be the geospatial matching (how do you find "nearest available driver" at scale without scanning every driver?).
6. **Design a notification service** that other internal services call to send a user an email / SMS / push, with retries, deduplication, and user preferences (quiet hours, channel opt-outs). Full 8 steps. Deep dive: guaranteeing a notification is sent *at least once* but not *spammed* (dedupe).
7. **Consistency call.** For each, choose strong vs eventual consistency and justify in one sentence: (a) the "remaining seats" count on a concert-ticket page; (b) a user's profile bio; (c) the balance shown in NYX before placing a trade; (d) the like-count on a post.
8. **Pick the bottleneck.** A photo-sharing app suddenly goes viral. Given this stack, `CDN → LB → app tier (autoscaled) → Redis cache → Postgres primary + 2 read replicas`, with a brand-new feature that writes a row on *every* photo view, predict what breaks first and the cheapest fix.

### Solutions

**1. Read:write reflex.**
- (a) Product catalog: **read-heavy** (millions browse, nightly updates). First reach: **CDN/cache**, the catalog is highly cacheable and changes rarely.
- (b) IoT fleet: 1M sensors × (1 reading / 10s) = **100,000 writes/s → write-heavy.** First reach: a **partitioned log / time-series store** (like Design C), generic SQL primary won't take it.
- (c) Viral comments: **read-heavy and skewed** (one article gets hammered). First reach: **cache** the hot article's comments; the skew makes the hit rate excellent.
- (d) Audit log: **write-heavy, read-rarely.** First reach: an **append-only store / queue + batch writer**, optimize for cheap sequential writes, don't index it like a query store.

**2. The estimate that forces a component.**
```
videos/day = 5e6 DAU × 3 = 15e6 views/day
egress/day = 15e6 × 50 MB = 7.5e8 MB = 750 TB/day
avg egress = 750e12 B / 86,400 s ≈ 8.68e9 B/s ≈ 8.7 GB/s ≈ 70 Gbps
peak (×3)  ≈ 210 Gbps
```
210 Gbps of egress forces a **CDN** (Ch 9.2). Serving that from origin would require an absurd, expensive origin egress capacity; a CDN caches the popular videos at the edge so origin only serves the long tail. The number, not taste, mandates the component.

**3. Cache hit-rate reasoning.**
```
Reads hitting the DB = reads × (1 − hit_rate) = 50,000 × (1 − h)
Need that ≤ 8,000:
  50,000 × (1 − h) ≤ 8,000
  1 − h ≤ 0.16
  h ≥ 0.84
```
You need a **minimum 84% cache hit rate.** Below that, miss traffic alone overruns the DB. This is exactly the "just add a cache" mistake's antidote: a cache only saves you if the hit rate clears the threshold the math sets, so you reason about whether the access pattern (skew, repetition) can actually deliver 84%+.

**4. Pastebin (outline).**
- *Requirements:* `create(text, ttl?, syntax?) -> url`; `GET /{id} -> rendered/raw text`. Read-heavy (one paste read many times), eventual consistency fine, blobs up to 1 MB.
- *Estimates:* say 10M pastes/month → ~4 writes/s, ~400 reads/s (100:1). Storage: 10M/mo × avg 10 KB × 12 mo = ~1.2 TB/yr (bigger per-row than the shortener because of the body).
- *API:* `POST /api/paste {text, ttl, syntax}` → `{id, url}`; `GET /{id}`; `GET /raw/{id}`.
- *Data model:* `{id (PK), body, syntax, created_at, ttl}`. Same base62 id trick as Design A. **Difference from URL shortener:** the *body* is large (up to 1 MB), so store the blob in a **blob store / object storage** keyed by id, with metadata in a KV store, don't stuff 1 MB rows into the KV. Syntax highlighting is rendered at read time (or cached rendered HTML).
- *High-level:* `client → CDN (cache rendered pastes) → LB → app → KV(meta)+blob(body)`; cache hot pastes.
- *Bottleneck:* read path of popular pastes → CDN + cache. *Tradeoffs:* render-on-read (cheaper writes, repeated render cost, mitigate by caching rendered output) vs render-on-write; TTL expiry via a background sweeper.

**5. Ride-sharing matching (outline).**
- *Requirements:* riders request a ride at a location; match to nearest available driver fast (sub-second); drivers stream location updates. Write-heavy on location updates, latency-critical on match.
- *Estimates:* say 1M active drivers each sending location every 4s = **250,000 location writes/s** (write-heavy, like IoT). Ride requests far fewer (~thousands/s).
- *API:* `WS driver/location {driver_id, lat, lng}`; `POST /ride/request {rider_id, pickup}` → matched driver.
- *Data model:* driver locations in an in-memory **geospatial index** (Redis `GEO` / quadtree / geohash / S2 cells), keyed for fast nearest-neighbor; ride/trip records in a durable store.
- *Deep dive (the point):* **don't scan all 1M drivers per request.** Bucket the map into **geohash / S2 cells**; on a ride request, look only in the rider's cell and its neighbors → reduces "nearest driver" from O(N) to O(drivers in a few cells). Redis `GEORADIUS` or a quadtree does this. Location writes update the index in place.
- *High-level:* `drivers → WS gateway → geo-index (Redis); rider request → matching service → query geo-index for nearby available drivers → rank by ETA → offer → confirm → trip store`.
- *Bottleneck:* the 250k/s location write stream → in-memory geo-index sharded by region; the match query is cheap because the index localizes it. *Tradeoffs:* location data is **eventually consistent** (a driver's dot may be ~4s stale, fine); the match itself wants **strong-ish** handling so two riders don't get the same driver (atomically claim/lock the offered driver). Optimized for match latency; gave up perfectly-fresh driver positions.

**6. Notification service (outline).**
- *Requirements:* internal services call `notify(user, type, payload, channels)`; respect user prefs (quiet hours, opt-outs); deliver via email/SMS/push; retry on failure; **at least once but not duplicated**.
- *Estimates:* say 50M notifications/day = ~580/s avg, peak ×3 ≈ 1,700/s, modest, but bursty (a marketing blast spikes it) → **queue to absorb bursts.**
- *API:* `POST /notify {user_id, type, payload, channels, dedupe_key}` → `202 accepted`.
- *Data model:* `user_prefs{user_id, channel_optouts, quiet_hours, tz}`; `sent{dedupe_key}` (for idempotency); per-channel provider configs.
- *Deep dive (the point):* **at-least-once + dedupe.** Callers pass a `dedupe_key`; the service records sent keys (with TTL) and drops duplicates → at-least-once delivery (retries on provider failure) without spamming. Channel sends go through a **queue + workers** (Ch 9.5) so a slow SMS provider doesn't block callers; failed sends retry with backoff, then dead-letter.
- *High-level:* `service → notify API → enqueue → workers: apply prefs (skip if opted-out / in quiet hours) → check dedupe → call provider (email/SMS/push) with retry → record sent`.
- *Bottleneck:* downstream provider rate limits/latency → queue + per-provider rate limiting (Ch 9.4) + retries. *Tradeoffs:* eventual delivery (queued, retried) vs synchronous, chose async for resilience and burst absorption; dedupe window is finite (TTL) so an extremely late retry could theoretically re-send (accepted, bounded).

**7. Consistency call.**
- (a) Remaining concert seats: **strong**, overselling a seat is a hard invariant (money + a real chair). Coordinate the decrement.
- (b) Profile bio: **eventual**, if a bio edit takes a second to show everywhere, nobody is harmed.
- (c) NYX pre-trade balance: **strong**, trading on a stale/wrong balance is unacceptable (the trade ledger invariant from the chapter).
- (d) Like-count: **eventual**, an approximate, briefly-stale like-count is fine and buys huge scale (classic eventual-consistency use).

**8. Pick the bottleneck.**
The new feature **writes a row on every photo view**, and views are exactly what spikes when the app goes viral. Writes go only to the **Postgres primary** (replicas are read-only). So virality → millions of *view writes* → the **primary DB is the first thing that breaks** (the read replicas and cache don't help writes; the CDN/LB/app tier autoscale fine). *Cheapest fix:* take the view-counting off the synchronous write path, **enqueue view events (Ch 9.5) and aggregate counts in a worker** (batch/increment), exactly like Design A's async click analytics. This converts 1-row-per-view primary writes into batched, async aggregation, and the primary stops being the bottleneck. (If view counts later need their own scale, move them to a counter store / time-series store rather than the relational primary.)
