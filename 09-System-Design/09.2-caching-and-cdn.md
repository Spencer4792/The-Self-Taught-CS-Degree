## 🌱 Start here

Before any math, let's build the intuition with a kitchen.

Imagine you're cooking dinner. The **pantry across the room** has everything, but every trip costs you 30 seconds of walking. So what do you do? You keep the **salt, pepper, and olive oil right next to the stove**, the three things you reach for constantly. Now 90% of your "ingredient fetches" cost you half a second instead of 30. You didn't reorganize the whole pantry; you just kept the *hot set* within arm's reach.

That's caching. The "pantry across the room" is the database (or a slow computation, or a server on another continent). The "stuff next to the stove" is the cache, a small, fast place that holds the few things you keep asking for.

Two everyday observations make this work, and they're the whole game:

- **You keep reaching for the same things.** You don't use 400 different spices per meal; you use the same handful over and over. Real software is the same, a tiny fraction of data gets the overwhelming majority of requests (the trending ticker, the viral post, the homepage).
- **The fast place is *dramatically* faster than the slow place.** Half a second vs 30 seconds is a 60× gap. In computers the gap is bigger: memory is thousands to millions of times faster than a disk or a cross-country network trip.

Put those together and you get the magic: **a small cache (cheap) captures most of the traffic (because traffic is lopsided), and each capture is enormously faster.** You don't need to cache everything, you just need to cache the hot stuff.

There's a catch, and it's the one thing that makes caching genuinely hard: **the cache is a copy.** The moment the real data changes, your copy is a little lie. Keeping the copy honest (or knowing exactly how stale you're willing to be) is half of this chapter. The other half is *not falling over* when a hot cached thing suddenly disappears and everyone rushes the slow path at once.

**What you'll be able to do by the end of this chapter:**

- Estimate, with real numbers, how much faster an endpoint gets at a given hit rate, and how much load comes off the database.
- Size a cache: given how much hot data there is and how big each item is, compute how much Redis memory you need.
- Pick the right caching *strategy* (cache-aside, write-through, write-back, write-around) for a given read/write pattern.
- Pick the right *eviction policy* (LRU/LFU/TTL/...) and implement LRU from scratch at O(1).
- Keep the cache honest (invalidation) and keep the system alive when a hot key expires (stampede protection).
- Reason about CDNs and HTTP cache headers well enough to put NYX's assets and cacheable APIs on the edge.

If the only thing you take away is "cache the hot set close to the user, decide how stale you can tolerate, and protect the slow path from stampedes," you've got the spine of it. Everything below is the muscle.

## 📐 Theory

### Why caching works: locality + the cost gap

Two facts make caching a free lunch (almost):

1. **The cost gap is enormous.** From the latency table in 9.1: RAM is ~100 ns, a datacenter round trip ~0.5 ms (5,000× slower), an SSD random read ~150 µs, a cross-country round trip ~150 ms (1.5 million× slower than RAM). Anytime you can answer from a layer that's 100×-1,000,000× faster than the source, you win big.

2. **Locality of reference**, real workloads are not uniform:
   - **Temporal locality:** something accessed recently is likely accessed again soon (a trending NYX ticker, a viral post).
   - **Spatial locality:** data near recently-accessed data is likely needed (the next rows in a result set, adjacent bytes).
   - **Popularity skew (Zipf / 80-20):** a small fraction of items get the overwhelming majority of requests. Often ~20% of keys serve ~80% of traffic; sometimes far more skewed.

Because of skew, a *small* cache holding the hot set captures most of the traffic. That's the whole magic.

### The cache hit-rate math (why hit rate is everything)

Effective average latency with a cache:
```
T_avg = h · T_cache + (1 - h) · (T_cache + T_source)
      ≈ h · T_cache + (1 - h) · T_source      (if T_cache << T_source)

h        = hit rate (0..1)
T_cache  = latency to serve from cache (e.g., 1 ms)
T_source = latency to compute/fetch from source (e.g., 200 ms)
```
With T_cache=1 ms, T_source=200 ms:
```
h = 0.50 -> 1 + 0.5·200  = 101 ms
h = 0.80 -> 1 + 0.2·200  =  41 ms
h = 0.90 -> 1 + 0.1·200  =  21 ms
h = 0.95 -> 1 + 0.05·200 =  11 ms
h = 0.99 -> 1 + 0.01·200 =   3 ms   <- 66x faster than no cache
```
**Two takeaways:** (1) the relationship is nonlinear, going from 90% to 99% hit rate roughly *halves* latency again; (2) the misses dominate the average, so chasing the last few percent of hit rate is worth real effort. Equivalently, a 95% hit rate offloads 95% of QPS from the source, that's how 174k read QPS becomes ~9k at origin (Chapter 9.1's media service).

### Worked example A - sizing a Redis cache from the working set

The question you get asked in practice is never "is caching good?", it's "how much cache do you need to buy?" Here's the full computation, no hand-waving.

**Setup.** NYX has a "ticker analytics" endpoint. There are 50,000 distinct tickers total, but traffic is heavily skewed: you measure that **the top 5,000 tickers (10%) serve ~92% of requests.** Each cached analytics blob is ~4 KB serialized (JSON with VWAP, rolling stats, sparkline data). You want a hit rate of **~92%**, which means you need to hold that hot 5,000-key working set in cache.

**Step 1, raw data size of the working set.**
```
working_set_items = 5,000
item_size         = 4 KB
raw_data          = 5,000 × 4 KB = 20,000 KB ≈ 20 MB
```

**Step 2, add per-key overhead.** Redis doesn't store 4 KB; it stores 4 KB *plus* bookkeeping: the key string, an internal `dictEntry`, the object header, the expiry entry (for TTL), and allocator rounding. A safe rule of thumb is **~50-100 bytes of overhead per key**, more if keys are long strings. Say your keys are like `analytics:v3:AAPL` (~18 bytes) and total overhead is ~90 bytes/key.
```
overhead = 5,000 × 90 B = 450,000 B ≈ 0.45 MB    (tiny next to the 20 MB of values)
subtotal = 20 MB + 0.45 MB ≈ 20.45 MB
```

**Step 3, headroom for fragmentation + churn + safety.** Memory allocators fragment; a hot/cold churn means transient extra entries; and you never want to run Redis at 100% (eviction thrash, latency spikes, no room for replication buffers). Budget **~1.5× as a working headroom factor**, plus you want to leave room to occasionally hold 1.5× the working set during traffic shifts.
```
provisioned = 20.45 MB × 1.5 ≈ 31 MB
```

**Step 4, sanity check against the answer.** ~31 MB. That fits in the smallest Redis instance with room to spare. **The punchline: holding 92% of the traffic costs ~31 MB even though the full dataset (50k × 4 KB ≈ 200 MB) is 10× bigger.** You'd actually round up generously, provision **256 MB**, because the cost of an extra ~200 MB of RAM is trivial compared to the engineer-hours of getting paged when the cache starts evicting hot keys. **Caching is one of the few places where "buy more than you think you need" is correct**, RAM is cheap, hit-rate cliffs are expensive.

**What changes the answer:**
```
Bigger items (e.g., 40 KB blobs)      -> 10× more memory; consider compression or caching IDs only
Less skew (top 10% = only 60%)        -> need a bigger working set for the same hit rate
Want 99% not 92%                      -> must hold ~the top 20k keys -> ~80 MB raw -> ~120 MB provisioned
Long keys (UUIDs, full URLs)          -> overhead per key can rival the value; normalize/hash keys
```

### Worked example B - CDN offload: origin QPS & bandwidth before vs after

A CDN's whole pitch is *origin offload*. Let's prove it with the NYX chart-asset workload.

**Setup.** NYX serves a JS bundle `app.js` that's **300 KB**. At peak, **120,000 users/min** load the dashboard, each pulling that bundle once (cold browser). That's the request rate hitting *something*.
```
requests/sec at peak = 120,000 / 60 = 2,000 req/s for app.js
```

**Before CDN (origin serves everything):**
```
origin QPS       = 2,000 req/s
origin bandwidth = 2,000 req/s × 300 KB = 600,000 KB/s
                 = 600 MB/s ≈ 4.8 Gbps   (×8 bits/byte)
```
That's ~4.8 Gbps for *one asset*. The origin needs fat pipes, lots of egress cost, and headroom for spikes. Painful.

**After CDN at 96% hit rate** (static, content-hashed asset → near-100% cacheable; 96% is conservative, accounting for cold POPs and cache fills across many edge locations):
```
fraction served by edge   = 0.96  -> 1,920 req/s from edge POPs (origin never sees these)
fraction missing to origin= 0.04  ->    80 req/s reach origin

origin QPS       = 80 req/s            (down from 2,000 -> 25× less)
origin bandwidth = 80 × 300 KB = 24,000 KB/s = 24 MB/s ≈ 0.19 Gbps
```
**Result:** origin QPS drops **25×** (2,000 → 80) and origin egress drops from **~4.8 Gbps to ~0.19 Gbps**, a 96% reduction, exactly the hit rate. The edge absorbs the other 4.6 Gbps, spread across POPs near users, at CDN bandwidth prices (much cheaper per GB than origin cloud egress).

**Step, what hit rate do you actually need?** Suppose your origin can comfortably serve **150 req/s** for this asset. What's the minimum CDN hit rate?
```
origin_qps = (1 - h) × 2,000 ≤ 150
1 - h ≤ 150 / 2,000 = 0.075
h ≥ 0.925   -> you need at least ~92.5% hit rate to stay under origin's limit
```
This is the kind of number you'd actually put in a design doc: "we require ≥93% CDN hit rate; below that, origin saturates at peak." It turns a fuzzy "use a CDN" into a *measurable SLO*. And it's why **content-hashed, immutable, long-TTL filenames** matter so much, they push the asset hit rate toward 99%+, giving huge margin.

### Where caches live (the layers)

Requests pass through a *stack* of caches; each layer that hits saves all the layers below it.

```
[Browser/Client cache]  in-memory + disk; HTTP Cache-Control; cheapest, closest
        │ miss
[CDN / edge cache]       geographically near user; static assets, cacheable GETs
        │ miss
[Reverse proxy cache]    nginx/Varnish in front of app; shared across users
        │ miss
[Application cache]      in-process (LRU dict) OR distributed (Redis/Memcached)
        │ miss
[Database cache]         query/result cache, buffer pool (pages in RAM)
        │ miss
[Disk / source of truth] slowest
```

Guiding principle: **cache as close to the user as possible, and as early in the path as possible.** A browser cache hit costs ~0 ms and 0 server load; a DB buffer-pool hit still cost you a full network round trip and app CPU. For NYX you use: browser caching for static dashboard assets, a CDN for those assets + cacheable market-data snapshots, and Redis as the shared application cache for computed analytics.

### Caching strategies (read & write paths) with tradeoffs

There are five canonical patterns. The split is: how do reads populate the cache, and how do writes keep it consistent?

**1. Cache-aside (lazy loading)**, the app manages the cache. Most common.
```
READ:  data = cache.get(key)
       if miss: data = db.get(key); cache.set(key, data, ttl); 
       return data
WRITE: db.write(key, value); cache.delete(key)   # invalidate, don't update
```
- Pros: simple; cache only holds requested data; cache failure ≠ outage (just slower); cache and DB are decoupled.
- Cons: first read of each key is a miss (cold start); brief staleness possible; the read-miss-write sequence has a race (two readers both miss and fetch). On write, *delete* rather than update to avoid stale writes from racing.

**2. Read-through**, the cache library itself loads on miss (you call only the cache).
```
READ: data = cache.get(key)   # cache internally fetches from DB on miss
```
- Pros: app code is clean; load logic centralized.
- Cons: needs a cache that supports a loader; same cold-start misses; tighter coupling to the cache implementation.

**3. Write-through**, write to cache *and* DB synchronously on every write.
```
WRITE: cache.set(key, value); db.write(key, value)   # both, before returning
```
- Pros: cache is always consistent with DB; reads never serve stale.
- Cons: every write pays two writes (higher write latency); caches data that may never be read (cache churn).

**4. Write-back (write-behind)**, write to cache immediately, flush to DB asynchronously.
```
WRITE: cache.set(key, value); enqueue async db.write(key, value)
```
- Pros: very fast writes; can batch/coalesce writes to the DB (great for write-heavy, like view counters).
- Cons: **risk of data loss** if cache dies before flush; complex; DB temporarily inconsistent. Use only where some loss is tolerable (metrics, counters) or with durable write-ahead logging.

**5. Write-around**, write straight to DB, *skip* the cache; cache populates on later reads (via cache-aside).
```
WRITE: db.write(key, value)            # cache not touched
READ:  cache-aside as usual
```
- Pros: avoids polluting cache with write-once data that's rarely read (e.g., bulk imports, logs).
- Cons: a read right after a write is a guaranteed miss (read-after-write latency).

**How to choose:**
```
Read-heavy, tolerate slight staleness  -> cache-aside (default)
Need always-consistent reads           -> write-through (+ cache-aside reads)
Write-heavy, loss-tolerant counters     -> write-back
Write-once-rarely-read data             -> write-around
```
For NYX's computed analytics (expensive aggregations, read far more than written): **cache-aside with a short TTL**, plus stampede protection (below).

### Eviction policies

A cache is bounded; when full, something must go. The policy decides what:

- **LRU (Least Recently Used):** evict the item unused for the longest. Best general-purpose default, exploits temporal locality. Implemented below at O(1).
- **LFU (Least Frequently Used):** evict the least-accessed item. Better when popularity is stable (a perennially hot key shouldn't be evicted just because it wasn't touched in the last second). Downside: a once-popular item can be "sticky" forever; needs aging.
- **FIFO (First In First Out):** evict the oldest-inserted regardless of use. Simple but ignores access patterns, usually worse than LRU.
- **TTL (Time To Live):** every entry expires after a fixed duration. Not really an eviction policy for *space*, it's for *freshness*. Almost always combined with LRU/LFU (evict on space *and* on age).
- **Random:** evict a random entry. Surprisingly decent and trivially cheap; used at huge scale where bookkeeping cost matters.

Real systems combine them: Redis offers `allkeys-lru`, `allkeys-lfu`, `volatile-ttl`, etc. Modern caches use approximations (e.g., **W-TinyLFU** in Caffeine) that beat plain LRU on hit rate by tracking frequency cheaply.

### Cache invalidation - one of the two hard things

> "There are only two hard things in Computer Science: cache invalidation and naming things.", Phil Karlton

Invalidation is hard because the cache is a *copy*, and the moment the source changes, the copy is a lie. Your strategies:

- **TTL (expiry):** simplest. Accept staleness up to T seconds. Pick T from the business: NYX price snapshots maybe 1-5 s; a user's profile maybe 5 min; a country list maybe a day. Self-healing (wrong data fixes itself after T) but always somewhat stale.
- **Explicit invalidation:** on write, delete/update the key (cache-aside write path). Precise but you must find *every* key affected, including derived/aggregate keys and keys on other nodes. Easy to miss one → stale forever.
- **Versioned keys:** bake a version into the key (`user:42:v7`). Writing bumps the version, instantly orphaning old entries (which then age out). No coordinated delete needed.
- **Write-through:** keep cache in lockstep with DB (no invalidation needed, at write cost).

There's no free lunch, every approach trades freshness vs complexity vs write cost. A good default: **TTL + explicit delete-on-write** (belt and suspenders).

### Cache stampede / thundering herd

The nasty failure mode: a hot key expires (or the cache restarts cold), and *simultaneously* thousands of requests miss and all hammer the source to recompute the same value. The source, sized for the cached QPS, melts.

```
t=0   hot key TTL expires
t=0+  10,000 concurrent requests all MISS
      all 10,000 call db / recompute the SAME expensive value
      DB falls over -> cascading failure
```

Mitigations:
1. **Locking / single-flight:** the first miss acquires a lock and recomputes; everyone else waits for that one result (or briefly serves stale). Go's `singleflight`, a Redis `SETNX` lock, etc. Collapses N recomputes into 1.
2. **Stale-while-revalidate:** serve the *expired* value to readers while one background task refreshes it. Users never see a miss; the source sees one recompute. (HTTP even standardizes `stale-while-revalidate`.)
3. **Jittered / randomized TTL:** add random spread to expiry so a batch of keys cached together don't all expire at the same instant: `ttl = base + random(0, jitter)`. Prevents synchronized expiry storms.
4. **Probabilistic early expiration (XFetch):** refresh a key *before* it expires, with probability rising as expiry nears, so exactly one early request usually refreshes ahead of the herd.
5. **Cache warming:** preload known-hot keys after a deploy/restart so the cache is never fully cold.

We'll implement single-flight in the mini-project, it's the cleanest big win.

### ⚠️ Common mistakes

These are the ways caching bites people in production. Most teams make several of them.

1. **Caching personalized data on a shared cache (the scariest one).** If you cache a response that contains *user A's* data on a CDN, reverse proxy, or any cache keyed by URL alone, the *next* user B requesting that URL gets A's data served to them. This is a real, headline-making data leak. Fix: never cache responses with `Set-Cookie` or per-user content on a shared cache; use `Cache-Control: private` for browser-only caching, and make sure your cache key includes the user/auth dimension if you must cache per-user.

2. **No TTL jitter → synchronized expiry storms.** If you cache 10,000 keys in a tight loop all with `ttl=60`, then 60 seconds later all 10,000 expire in the same instant and the source eats a wall of misses at once. Fix: `ttl = base + random(0, jitter)` so expirations spread out.

3. **Updating the cache on write instead of invalidating it.** Doing `cache.set(key, new_value)` on a write *looks* right but races: two concurrent writers can interleave so the cache ends up holding the *older* value while the DB holds the newer one, stale forever until TTL. Fix: on write, `cache.delete(key)` (cache-aside) and let the next read repopulate from the DB's truth.

4. **Caching everything regardless of skew.** Caching cold, rarely-requested items just churns the cache, evicts hot keys, and wastes memory, you pay the write cost and get no hit benefit. Fix: cache the hot set; consider write-around for write-once-rarely-read data. A cache full of one-hit-wonders has a terrible hit rate.

5. **No stampede protection on expensive keys.** A single hot key expiring under load can take the whole source down (the thundering herd above). Fix: single-flight/locking, stale-while-revalidate, or probabilistic early refresh on any key whose recompute is expensive.

6. **Unbounded cache → OOM.** An in-process dict with no capacity limit and no eviction grows until the process runs out of memory and crashes (or the kernel OOM-kills it). Fix: always bound the cache (LRU with a capacity) and/or set a `maxmemory` + eviction policy in Redis. "It's just a cache" still needs a ceiling.

7. **Caching error responses.** If the source returns a 500 (or an empty result) during a blip and you cache it with the normal TTL, every user sees that error for the full TTL even after the source recovers. Fix: don't cache errors, or cache them with a tiny TTL (a few seconds), "negative caching" is fine but must be short.

8. **Ignoring cache-key normalization.** `/api/ticker?id=AAPL&debug=1` and `/api/ticker?debug=1&id=AAPL` are the *same* logical request but produce two different cache keys → near-zero hit rate, and tracking/debug params explode the keyspace. Fix: normalize keys, sort/whitelist query params, strip irrelevant ones, lowercase where appropriate, and `Vary` only on headers that actually change the response.

### 💼 On the job / interview angle

Caching is one of the most reliably *present* topics in system-design interviews, because almost every interesting system is read-heavy, and the moment you say "this endpoint is hit a million times a minute," the interviewer is waiting to hear "cache." If you design a read-heavy system and *don't* bring up caching, that's a red flag. If you bring it up *with numbers*, that's a strong signal.

Here's how to talk about it so it lands:

- **Lead with hit rate and offload, not just "add Redis."** Say: "Reads dominate at ~50k QPS. If you cache with a 95% hit rate, origin sees ~2.5k QPS, that's the number the DB has to handle." Now you've turned a vague idea into a capacity decision (ties directly to Chapter 9.1).
- **State the strategy explicitly.** "Cache-aside with a short TTL, delete-on-write for invalidation." Naming the pattern shows you know there *are* patterns and tradeoffs.
- **Justify the TTL from the business.** "Prices can be ~2s stale, so TTL=2s; user profiles tolerate ~5min." A TTL is a product decision about acceptable staleness, say so.
- **Name the invalidation story.** Interviewers love to ask "what happens when the data changes?" Have an answer: delete-on-write, versioned keys, or write-through, and the tradeoff you chose.
- **Pre-empt the stampede.** Almost no one mentions thundering herd unprompted; doing so is a differentiator. "On hot keys you'd add single-flight and TTL jitter so an expiry doesn't stampede the DB." This shows you've thought about failure, not just the happy path.
- **Mention the layers.** Browser → CDN → app cache (Redis) → DB cache. Pushing work to the edge for static/public content, Redis for computed/personalized-but-shareable, is the standard layered answer.

A clean one-liner worth keeping in your pocket: *"It's read-heavy with high skew, so you'd cache-aside in Redis with a short jittered TTL and single-flight on hot keys, target ~95% hit rate to bring origin from 50k to ~2.5k QPS, invalidate by delete-on-write, and serve all static assets from a CDN with content-hashed immutable URLs."* That single sentence hits hit-rate math, strategy, eviction/freshness, stampede, invalidation, and CDN, the whole chapter.

### Redis vs Memcached as caches

| | Redis | Memcached |
|---|---|---|
| Data types | strings, hashes, lists, sets, sorted sets, streams | strings/blobs only |
| Persistence | optional (RDB snapshots / AOF log) | none (pure cache) |
| Eviction | configurable (LRU/LFU/TTL/random) | LRU |
| Threading | mostly single-threaded core (atomic ops, Lua) | multi-threaded |
| Replication / cluster | yes (replicas, Cluster sharding) | client-side sharding |
| Extra powers | pub/sub, Lua scripting, atomic INCR, sorted sets for leaderboards/rate-limiters | dead-simple, very fast for plain KV |

**Pick Memcached** for a dumb, huge, multi-threaded blob cache. **Pick Redis** (the usual default) when you want data structures, atomic ops (rate limiting, Chapter 9.4), pub/sub, optional persistence, or built-in clustering. NYX uses Redis: it doubles as cache, session store, rate-limiter backend, and pub/sub for live updates.

### CDNs - caching at the edge

A **CDN** (Content Delivery Network) is a globally-distributed network of caching servers ("edge POPs", points of presence) that sit *physically near users*. It solves the problem that no CPU upgrade can: the speed-of-light tax on a cross-country/ocean round trip (~150 ms, Chapter 9.1).

```
Without CDN:  user (Sydney) ── 300 ms RTT ──> origin (Virginia)   every asset
With CDN:     user (Sydney) ── 10 ms RTT ──> edge POP (Sydney) ──(cache hit) done
                                              edge ──> origin only on MISS (fill)
```

**How it works:**
1. User requests `cdn.nyx.com/chart.js`. DNS/anycast routes them to the *nearest* edge POP.
2. Edge checks its cache by **cache key** (typically URL + selected headers/query params).
3. **Hit:** served from the edge in a few ms, never touching origin.
4. **Miss:** edge fetches from origin once, stores it (honoring `Cache-Control`/`s-maxage`), then serves it, and serves all subsequent nearby requests from cache.

**What to put on a CDN:** static assets (JS/CSS/images/fonts/video) always; cacheable API GETs (public, non-personalized) with appropriate `Cache-Control`; even dynamic content via edge compute / micro-caching (cache for 1 s to absorb spikes).

**Cache key control matters.** If your assets are personalized by a cookie or query param, the edge may cache per-variant (low hit rate) or, worse, serve user A's content to user B. Strip irrelevant query params; `Vary` only on headers that truly change the response; never cache responses with `Set-Cookie` unless you know what you're doing.

**Cache headers (the contract):**
```
Cache-Control: public, max-age=31536000, immutable   # static asset, 1 year, content-hashed name
Cache-Control: public, s-maxage=60, max-age=10        # CDN holds 60s, browser 10s
Cache-Control: private, no-store                       # never cache (personalized/secret)
ETag: "abc123"                                         # validation token for conditional GET
```
A common pattern: **content-hashed filenames** (`app.9f3c2.js`) with `max-age=31536000, immutable`. New deploy → new hash → new URL → no invalidation ever needed. This sidesteps the hard problem entirely for static assets.

**Purging / invalidation:** when you *must* evict (e.g., bad asset shipped), CDNs offer purge-by-URL, purge-by-tag/surrogate-key, or full purge. Purges are slower and rate-limited, prefer versioned URLs so you rarely purge. **Tag-based purging** is the pro move: tag responses (`Surrogate-Key: product-42`) and purge everything touching `product-42` in one call.

**Benefits beyond latency:** massive origin offload (the 95% in 9.1), DDoS absorption (edge soaks attack traffic), TLS termination near the user, and lower egress cost. CDNs are also where you put a WAF and bot protection (Security, see the security chapter cross-link).

### Worked design - caching the NYX hot-ticker endpoint, end to end

Let's put the whole chapter together on one real endpoint and design it with numbers, not vibes.

**The endpoint.** `GET /api/ticker/{symbol}/analytics` returns a computed analytics blob (VWAP, rolling stats, sparkline). The aggregation over the time-series DB takes **~180 ms** uncached. The blob is **~4 KB**.

**The traffic.** Peak **30,000 QPS** across the endpoint. Skew is brutal: the **top ~200 symbols serve ~90% of requests** (everyone watches the same megacaps). Data updates roughly every second as new trades arrive, but the business says **up to ~2 seconds of staleness is fine** for analytics (it's not the trade-execution path).

**Step 1, what does it cost with no cache?**
```
30,000 QPS × 180 ms each = the DB must sustain 30,000 concurrent 180ms aggregations
   -> ~5,400 "aggregation-seconds" of work per second. Hopeless; the DB melts.
```

**Step 2, pick the strategy.** Read-heavy, expensive recompute, tolerates ~2s staleness → **cache-aside with a short TTL.** No write-through (the data isn't written through your app; it's computed). Eviction: **LRU** (temporal locality is strong, hot symbols stay hot). Freshness: **TTL ≈ 2s** (matches the staleness budget), **with jitter** so the 200 hot keys don't all expire on the same tick.

**Step 3, estimate the hit rate and origin load.** With a 2s TTL and 30k QPS, in any 2-second window a hot key is requested thousands of times but only recomputed *once* (TTL refresh), *if* you protect against stampede. So origin recomputes ≈ (number of distinct keys) ÷ (TTL):
```
hot keys ≈ 200, refreshed every ~2s            -> ~100 recomputes/s from the hot set
long tail ≈ thousands of rarely-hit symbols    -> the misses (10% of traffic)
```
The 10% long-tail traffic = 3,000 QPS of mostly-misses, but many are distinct cold keys. Say after caching + LRU, overall **hit rate ≈ 0.94**.
```
origin QPS ≈ (1 - 0.94) × 30,000 = ~1,800 QPS reaching the DB   (down from 30,000 -> ~17×)
```
That's now a survivable DB load, *and* the hot 90% is served in ~1 ms.

**Step 4, size the cache.** You want to hold the hot set comfortably; LRU will keep the actually-hot keys resident. Provision for, say, the top 5,000 symbols to keep the long tail's recent items too:
```
5,000 keys × 4 KB ≈ 20 MB raw, ~31 MB provisioned (Worked example A)  -> round to 256 MB Redis
```

**Step 5, stampede protection on the hot keys.** Without it, every 2s TTL expiry on AAPL means thousands of simultaneous misses recompute AAPL at once → the 180ms aggregation gets called thousands of times in a burst. With **single-flight**, the first miss recomputes and everyone else waits for that one result; with **stale-while-revalidate**, readers get the slightly-stale value (well within the 2s budget) while one background task refreshes. You'd use **single-flight + jittered TTL** here.

**Step 6, the latency story.**
```
T_cache ≈ 1 ms, T_source ≈ 180 ms, h ≈ 0.94
T_avg ≈ 1 + 0.06 × 180 ≈ 11.8 ms     (vs 180 ms uncached -> ~15× faster on average)
p50  ≈ 1 ms   (cache hit)
p99  ≈ 180 ms (the misses -> the tail IS the misses, as always)
```

**The one-paragraph design doc:** *"Cache-aside in Redis, TTL≈2s with jitter, LRU eviction, single-flight on misses. ~256 MB provisioned holds the hot set. Target hit rate ≈94% brings origin from 30k QPS to ~1.8k QPS and average latency from 180ms to ~12ms. Staleness bounded by the 2s TTL, which the product accepts. No write-through, data is computed, not user-written; TTL is the invalidation mechanism."* Every number is defensible. That's the goal.

## 💻 Build it

### LRU cache from scratch - O(1) get and put (hashmap + doubly linked list)

The trick: a **hashmap** gives O(1) lookup `key → node`; a **doubly linked list** gives O(1) move-to-front and O(1) tail-eviction. Head = most recently used, tail = least recently used.

```python
# lru.py
class _Node:
    __slots__ = ("key", "val", "prev", "next")
    def __init__(self, key=None, val=None):
        self.key, self.val = key, val
        self.prev = self.next = None


class LRUCache:
    """O(1) get/put LRU cache. Sentinel head/tail nodes simplify edge cases."""
    def __init__(self, capacity):
        assert capacity > 0
        self.cap = capacity
        self.map = {}                  # key -> _Node
        self.head = _Node()            # sentinel: head.next = MRU
        self.tail = _Node()            # sentinel: tail.prev = LRU
        self.head.next = self.tail
        self.tail.prev = self.head
        self.hits = self.misses = 0

    # --- doubly-linked-list helpers (all O(1)) ---
    def _remove(self, node):
        node.prev.next = node.next
        node.next.prev = node.prev

    def _add_front(self, node):        # right after head = most recently used
        node.next = self.head.next
        node.prev = self.head
        self.head.next.prev = node
        self.head.next = node

    def _move_front(self, node):
        self._remove(node)
        self._add_front(node)

    # --- public API ---
    def get(self, key):
        node = self.map.get(key)
        if node is None:
            self.misses += 1
            return None
        self.hits += 1
        self._move_front(node)         # mark most-recently-used
        return node.val

    def put(self, key, val):
        node = self.map.get(key)
        if node:
            node.val = val
            self._move_front(node)
            return
        node = _Node(key, val)
        self.map[key] = node
        self._add_front(node)
        if len(self.map) > self.cap:   # evict LRU (the node before tail)
            lru = self.tail.prev
            self._remove(lru)
            del self.map[lru.key]

    def hit_rate(self):
        total = self.hits + self.misses
        return self.hits / total if total else 0.0


if __name__ == "__main__":
    c = LRUCache(2)
    c.put("a", 1); c.put("b", 2)
    print(c.get("a"))      # 1  (a now MRU)
    c.put("c", 3)          # capacity 2 -> evicts b (LRU)
    print(c.get("b"))      # None (evicted)
    print(c.get("c"))      # 3
    print("hit rate:", round(c.hit_rate(), 2))
```

### TTL cache (freshness, not just space)

```python
# ttl_cache.py
import time

class TTLCache:
    """Each entry expires after `ttl` seconds. Lazy expiry on read + sweep."""
    def __init__(self, ttl=5.0):
        self.ttl = ttl
        self.store = {}                 # key -> (value, expires_at)

    def get(self, key):
        entry = self.store.get(key)
        if entry is None:
            return None
        value, expires = entry
        if time.monotonic() >= expires:
            del self.store[key]         # lazy expiry
            return None
        return value

    def set(self, key, value, ttl=None):
        ttl = self.ttl if ttl is None else ttl
        self.store[key] = (value, time.monotonic() + ttl)

    def sweep(self):                    # optional active expiry of dead keys
        now = time.monotonic()
        dead = [k for k, (_, exp) in self.store.items() if exp <= now]
        for k in dead:
            del self.store[k]
        return len(dead)
```

### TTL with jitter (avoid synchronized expiry storms)

A tiny but important addition: when you cache a batch of keys together (e.g., warming the top 200 tickers after a deploy), giving them all the *same* TTL means they all expire at the same instant, and the source eats a wall of misses 2 seconds later. Jitter spreads expirations out so the load is smooth.

```python
# ttl_jitter.py
import time, random

class JitterTTLCache:
    """TTL = base + random spread, so co-cached keys don't expire in lockstep."""
    def __init__(self, base_ttl=2.0, jitter=0.5):
        self.base_ttl = base_ttl
        self.jitter = jitter            # max extra seconds, chosen uniformly
        self.store = {}

    def _ttl(self, ttl=None):
        base = self.base_ttl if ttl is None else ttl
        return base + random.uniform(0, self.jitter)

    def get(self, key):
        entry = self.store.get(key)
        if entry is None:
            return None
        value, expires = entry
        if time.monotonic() >= expires:
            del self.store[key]
            return None
        return value

    def set(self, key, value, ttl=None):
        self.store[key] = (value, time.monotonic() + self._ttl(ttl))


if __name__ == "__main__":
    c = JitterTTLCache(base_ttl=2.0, jitter=0.5)
    # 200 keys cached "at once" now expire spread across a 0.5s window (2.0..2.5s),
    # not all at the exact same instant -> no synchronized miss storm.
    for i in range(200):
        c.set(f"T{i}", i)
    print("cached 200 keys with jittered TTLs in [2.0, 2.5)s")
```

### Two-tier cache (in-process L1 + shared L2)

A pattern used at scale: a tiny, blazing-fast **L1 in-process cache** (per app server) in front of a **shared L2 cache** (Redis). L1 absorbs the very hottest keys at ~0 ns network cost; L2 is shared across all app servers so a miss on one server's L1 can still be a hit in the shared tier instead of always going to the slow source. The catch: L1 is per-server, so it can be slightly *more* stale than L2, keep L1 TTLs short.

```python
# two_tier.py
import time
from lru import LRUCache

class TwoTierCache:
    """
    L1: small, fast, per-process (LRU). Closest, but not shared.
    L2: larger, shared across servers (simulated here with a dict/TTLCache; in
        prod this is Redis). 
    Read order: L1 -> L2 -> source. Each level fills the levels above it on a hit.
    """
    def __init__(self, l1_capacity=64, l1_ttl=1.0, l2=None):
        self.l1 = LRUCache(l1_capacity)
        self.l1_ttl = l1_ttl
        self.l1_exp = {}                       # key -> l1 expiry (short, for freshness)
        self.l2 = l2 if l2 is not None else {} # stand-in for Redis (shared tier)
        self.stats = {"l1": 0, "l2": 0, "source": 0}

    def _l1_get(self, key):
        exp = self.l1_exp.get(key)
        if exp is None or time.monotonic() >= exp:
            return None
        return self.l1.get(key)

    def _l1_set(self, key, val):
        self.l1.put(key, val)
        self.l1_exp[key] = time.monotonic() + self.l1_ttl

    def get(self, key, source_fn):
        v = self._l1_get(key)
        if v is not None:
            self.stats["l1"] += 1
            return v
        v = self.l2.get(key)                   # shared tier (Redis GET in prod)
        if v is not None:
            self.stats["l2"] += 1
            self._l1_set(key, v)               # backfill L1
            return v
        # miss everywhere -> compute once, fill both tiers
        self.stats["source"] += 1
        v = source_fn(key)
        self.l2[key] = v                        # Redis SET in prod (with TTL)
        self._l1_set(key, v)
        return v


if __name__ == "__main__":
    calls = {"n": 0}
    def slow_source(key):
        calls["n"] += 1
        return f"value_for_{key}"

    c = TwoTierCache(l1_capacity=8, l1_ttl=1.0)
    # Hammer a few hot keys: first touch fills tiers, rest hit L1.
    for _ in range(1000):
        for k in ("AAPL", "TSLA", "NVDA"):
            c.get(k, slow_source)
    print(c.stats)          # source ~3 (one per hot key), the rest split l1/l2
    print("source calls:", calls["n"])   # ~3 -> the slow path ran ~3 times for 3000 reads
```

The win: of 3,000 reads on 3 hot keys, the slow source runs ~3 times. L1 catches the bulk at zero network cost; L2 would catch cross-server misses in a real fleet. The cost: more moving parts and a second staleness window (L1's short TTL), only worth it when even a Redis round trip (~0.5 ms) is too much for your hottest keys at very high QPS.

## 🧪 Mini-project: cache a slow function and measure the win (with stampede protection)

Let's wrap a deliberately slow "compute NYX analytics" function with cache-aside + single-flight, then measure hit rate and latency before/after using the load tester from Chapter 9.1.

```python
# cached_analytics.py
import time, threading, random
from lru import LRUCache
# (reuse percentile/load_test from Chapter 9.1's perf_toolkit if desired)

CALL_COUNT = {"source": 0}            # how many times we actually hit the "DB"

def expensive_query(ticker):
    """Pretend this is a 200 ms aggregation over time-series data."""
    CALL_COUNT["source"] += 1
    time.sleep(0.2)
    return {"ticker": ticker, "vwap": round(random.uniform(100, 200), 2)}


class CachedService:
    def __init__(self, capacity=128):
        self.cache = LRUCache(capacity)
        self._locks = {}                          # per-key single-flight locks
        self._locks_guard = threading.Lock()

    def _lock_for(self, key):
        with self._locks_guard:
            if key not in self._locks:
                self._locks[key] = threading.Lock()
            return self._locks[key]

    def get(self, ticker):
        val = self.cache.get(ticker)              # 1. try cache
        if val is not None:
            return val
        # 2. MISS -> single-flight: only ONE thread recomputes per key
        with self._lock_for(ticker):
            val = self.cache.get(ticker)          # double-check (another thread may have filled it)
            if val is not None:
                return val
            val = expensive_query(ticker)         # 3. compute once
            self.cache.put(ticker, val)           # 4. populate cache
            return val


def simulate(service, n=2000, hot_keys=8):
    """Zipf-ish: most traffic hits a few hot tickers (temporal/popularity locality)."""
    tickers = [f"T{i}" for i in range(hot_keys)] + [f"COLD{i}" for i in range(200)]
    weights = [10]*hot_keys + [1]*200             # hot keys 10x more likely
    latencies = []
    def worker():
        t = random.choices(tickers, weights=weights, k=1)[0]
        t0 = time.perf_counter()
        service.get(t)
        latencies.append(time.perf_counter() - t0)
    threads = []
    wall0 = time.perf_counter()
    for _ in range(n):
        th = threading.Thread(target=worker); th.start(); threads.append(th)
        if len(threads) >= 50:                    # cap concurrency
            for th in threads: th.join()
            threads = []
    for th in threads: th.join()
    wall = time.perf_counter() - wall0
    latencies.sort()
    p = lambda q: latencies[min(len(latencies)-1, int(q/100*len(latencies)))]
    return {
        "wall_s": round(wall, 2),
        "source_calls": CALL_COUNT["source"],
        "hit_rate": round(service.cache.hit_rate(), 3),
        "p50_ms": round(p(50)*1000, 1),
        "p95_ms": round(p(95)*1000, 1),
        "p99_ms": round(p(99)*1000, 1),
    }


if __name__ == "__main__":
    CALL_COUNT["source"] = 0
    svc = CachedService(capacity=64)
    print(simulate(svc, n=2000))
    # Expected shape:
    #   without cache: source_calls=2000, every request ~200ms
    #   with cache:    source_calls ~= number of distinct keys touched once (~200),
    #                  hit_rate ~0.9, p50 ~0ms (cache), p99 still ~200ms (the misses)
```

**What you should expect to see and why:**
- **source_calls** drops from 2000 (no cache) to roughly the number of distinct keys (~200), single-flight ensures even concurrent misses on the same key collapse to *one* source call, so a cold burst doesn't stampede.
- **hit_rate** ~0.9 because hot keys dominate (popularity locality), which by the hit-rate math gives ~21 ms average vs 200 ms uncached, a ~10× win.
- **p50 ≈ 0 ms** (served from cache) but **p99 still ≈ 200 ms**, the tail *is* the misses. That matches Chapter 9.1's lesson: averages improve dramatically, but the tail is the cost of the misses, so reducing miss rate (bigger cache, warming, longer TTL) is how you cut the tail.

To extend it: swap `LRUCache` for `TTLCache` to add freshness; add jittered TTL to avoid synchronized expiry; point it at a real Redis (`redis-py`) to make it distributed and shared across app nodes.

**Prove single-flight matters.** Try deleting the `with self._lock_for(ticker):` block (just compute inline on miss) and re-run. Now a cold burst of concurrent requests on the same hot key *each* call `expensive_query`, watch `source_calls` jump well past the number of distinct keys, because N concurrent misses on one key = N recomputes instead of 1. That spike *is* a stampede, and the lock is what flattens it.

### Solutions

**1. Hit-rate math.** `T_avg ≈ h·T_cache + (1-h)·(T_cache + T_source)`. Since `T_cache` is small you'll keep it for precision.
```
h=0.80: 0.80·2 + 0.20·(2+150) = 1.6 + 0.20·152 = 1.6 + 30.4 = 32.0 ms
h=0.95: 0.95·2 + 0.05·152     = 1.9 + 7.6       = 9.5 ms
h=0.99: 0.99·2 + 0.01·152     = 1.98 + 1.52     = 3.5 ms
```
From 0.95 → 0.99: 9.5 / 3.5 ≈ **2.7× faster**. The last 4 points of hit rate nearly tripled the speed, that's the nonlinearity: misses dominate, so cutting the miss rate from 5% to 1% cuts the dominant term by 5×.

**2. Required hit rate.** Origin sees `(1 - h) × 80,000 ≤ 4,000`.
```
1 - h ≤ 4,000 / 80,000 = 0.05
h ≥ 0.95  -> minimum 95% hit rate.
```
You'd design for a margin above this (say target 97-98%) so a normal hit-rate dip during a deploy or traffic shift doesn't immediately saturate the origin.

**3. Cache sizing.**
```
raw values  = 12,000 × 6 KB = 72,000 KB ≈ 72 MB
overhead    = 12,000 × 80 B = 960,000 B ≈ 0.96 MB
total       ≈ 72 + 0.96 ≈ 73 MB
provisioned = 73 MB × 1.5 ≈ 110 MB
```
Round up to a **256 MB** Redis instance (next sensible size, with generous headroom). Note the value bytes dominate; overhead is <2% here because items are large. If items were tiny (e.g., 50 B), the 80 B/key overhead would *exceed* the data, keys/overhead would dominate.

**4. CDN offload.**
```
No CDN:  3,000 req/s × 500 KB = 1,500,000 KB/s = 1,500 MB/s
         ×8 bits = 12,000 Mbps = 12 Gbps from origin.
97% hit: origin req/s = 0.03 × 3,000 = 90 req/s
         origin BW = 90 × 500 KB = 45,000 KB/s = 45 MB/s ≈ 0.36 Gbps
```
Origin bandwidth drops from **12 Gbps to ~0.36 Gbps** (a 97% cut, matching the hit rate), and only **90 req/s** reach origin. The CDN edge absorbs the other ~11.6 Gbps near users.

**5. Strategy choice.**
- (a) **Audit logs → write-around.** Written once, rarely read; caching on write would just pollute the cache with data nobody reads. Skip the cache on write; cache-aside the rare reads.
- (b) **Views counter → write-back.** Thousands of increments/sec; coalesce them in the cache and flush to the DB periodically (loss-tolerant, a few lost views is fine). Massive write reduction on the DB.
- (c) **Account balance → write-through** (or don't cache at all / cache-aside with delete-on-write and read-from-DB on critical paths). Must never serve stale money; write-through keeps cache in lockstep with the DB.
- (d) **Leaderboard → cache-aside with TTL ≈ 10s** (+ stampede protection). Expensive to build, read constantly, tolerates the stated staleness; TTL is the invalidation mechanism. A Redis sorted set is a natural fit.

**6. Spot the bug.** `db.write(key, v); cache.set(key, v)` races: two writers W1 (value A) and W2 (value B) can interleave so the DB ends at B but the *cache* ends at A, e.g., W1 writes DB=A, W2 writes DB=B, W2 sets cache=B, then W1 (delayed) sets cache=A. Now cache=A is stale until TTL, serving wrong data. **One-line fix:** invalidate instead of update, `db.write(key, v); cache.delete(key)`. The next read repopulates from the DB's authoritative value, so the cache can't get pinned to a stale write.

**7. TTL & stampede design.** Every 5 seconds the key expires and, with 20,000 QPS, a huge burst of requests all MISS in the same instant and *each* triggers the 300 ms recompute → potentially thousands of concurrent recomputes of the *same* value, hammering the source (classic thundering herd) and spiking latency for everyone. Mitigations (any two):
- **Single-flight / lock:** only the first miss recomputes; the rest wait for that one result. Collapses thousands of recomputes into **1** per expiry.
- **Stale-while-revalidate:** serve the just-expired value to readers while one background task refreshes it; readers never see a miss and the source does exactly one recompute.
- **TTL jitter** (helps when many keys share an expiry, less so for a single key) and **probabilistic early refresh** (one request refreshes *before* expiry, so the key is never actually cold) are also valid.

**8. Code, `peek`.**
```python
def peek(self, key):
    """Read the value WITHOUT counting hit/miss and WITHOUT promoting it."""
    node = self.map.get(key)
    return node.val if node is not None else None
```
It just looks up the hashmap and returns the value (or `None`), skipping both the `hits/misses` counters and the `_move_front` promotion, so it observes the cache without perturbing its LRU ordering or stats.
