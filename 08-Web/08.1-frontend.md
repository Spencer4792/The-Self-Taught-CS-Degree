## 🌱 Start here

Before any pipeline diagrams, let me give you the plain-English version, because every web page, NYX's dashboard, Anneava's patient portal, this very textbook if I rendered it, is built from exactly three layers, and they map to a body:

- **HTML is the skeleton.** It's the *structure*, what's actually there. A heading, a paragraph, a button, a list, an input box. If you stripped away all the styling and all the behavior, the HTML is the bare bones that say "here is a title, here is a form, here is a table." It carries *meaning*, not looks.

- **CSS is the clothing.** It's the *styling*, colors, fonts, spacing, where boxes sit, what's blue and what's bold, how it reflows on a phone vs. a monitor. The same skeleton can wear a dark theme or a light theme, a cramped layout or an airy one, just by changing the clothes. CSS never changes *what* is on the page, only how it *looks*.

- **JavaScript is the muscles.** It's the *behavior*, what happens when you click, type, scroll, or when data arrives from a server. The skeleton just stands there and the clothes just sit on it until JS makes things *move*: open a menu, validate a form, fetch revenue numbers and redraw a chart. React (which we'll get to) is a very organized way of writing those muscles.

Here's all three in one tiny page so it's concrete, not abstract:

```html
<!-- HTML: the skeleton - structure and meaning -->
<button id="greet">Say hi</button>
<p id="out"></p>

<style>
  /* CSS: the clothing - how it looks */
  #greet { background: #4f46e5; color: white; padding: 8px 16px; border: none; border-radius: 6px; }
  #out   { color: #16a34a; font-weight: 600; }
</style>

<script>
  // JavaScript: the muscles - what it does
  document.querySelector("#greet").addEventListener("click", () => {
    document.querySelector("#out").textContent = "Hi, Spencer 👋";
  });
</script>
```

Three layers, cleanly separated: structure, style, behavior. Hold that picture, everything else in this chapter is just *how* the browser turns those three layers into pixels and *how* React lets you write the muscle layer without losing your mind.

**Why this matters for a tech job.** Frontend is the part of the system a human actually touches, so it's disproportionately visible: when an interview asks you to "build a component" or "center this div" or "why is this page slow," they're testing whether you understand these three layers and the machine underneath them. Almost every product company, fintech like NYX, health tech like Anneava, anything with a screen, needs people who can turn a design and an API into a fast, accessible interface. And the mental models here (the event loop, the render pipeline, declarative UI) transfer directly to React Native, to performance debugging, and to reasoning about *any* interactive system. This is a high-use skill: you can see your work, and so can everyone else.

## 📐 Theory

### How the browser works: from bytes to pixels

When you navigate to a NYX page, the browser runs a pipeline called the **critical rendering path**:

1. **Parse HTML → DOM.** The HTML parser reads the bytes and builds the **DOM** (Document Object Model), a tree of node objects. `<body><h1>Hi</h1></body>` becomes a tree: `document → html → body → h1 → text("Hi")`. The DOM is the *live, in-memory representation* of the page; JS manipulates this tree, not the original HTML text.

2. **Parse CSS → CSSOM.** Stylesheets are parsed into the **CSSOM** (CSS Object Model), a tree of style rules. CSS is **render-blocking**: the browser won't paint until it has the CSSOM, because it can't know how anything looks. (This is why a big blocking stylesheet delays first paint.)

3. **Render tree.** The DOM and CSSOM are combined into the **render tree**, only the *visible* nodes with their computed styles. `display:none` nodes are excluded; `<head>` is excluded. Each node knows its content and its styling.

4. **Layout (reflow).** The browser computes the *geometry*, the exact position and size of every box, given the viewport. This is where the box model (below) is resolved into pixel coordinates. Changing something that affects geometry (width, font size, adding an element) triggers a **reflow**, which is expensive because it can cascade.

5. **Paint.** Each box is rasterized into pixels, text, colors, borders, shadows, images, onto layers.

6. **Composite.** Layers are combined in the right order (respecting `z-index`, transforms, opacity) and sent to the screen. Some changes (CSS `transform`, `opacity`) can be done purely at the composite step on the GPU, *no layout or paint*, which is why animating `transform` is buttery and animating `width` (which reflows) is janky. This is the single most useful performance fact on this list.

### The event loop and repaint

JavaScript in the browser is **single-threaded**, one call stack. So how does it handle clicks, timers, network responses, and rendering without freezing? The **event loop**.

- The **call stack** runs synchronous JS to completion.
- Async work (timers, `fetch`, events) is handed to the browser's Web APIs (which run off-thread). When done, their callbacks are queued.
- Two queues: the **macrotask queue** (timers, I/O, UI events) and the **microtask queue** (resolved Promises, `queueMicrotask`).
- The loop: run the current task to completion → drain *all* microtasks → render if needed → take the next macrotask.

```javascript
console.log("1");
setTimeout(() => console.log("2 (macrotask)"), 0);
Promise.resolve().then(() => console.log("3 (microtask)"));
console.log("4");
// Output: 1, 4, 3, 2
// sync runs first (1,4); microtasks drain before macrotasks (3 before 2)
```

The render step (style → layout → paint → composite) happens *between* tasks, roughly aligned to the display's refresh (~60fps = every 16.6ms). **Key consequence:** a long-running synchronous JS function *blocks the event loop*, so the page can't repaint or respond to input, the dreaded "frozen tab." This is why heavy work belongs in chunks, `requestIdleCallback`, or a Web Worker. `requestAnimationFrame` schedules a callback right before the next repaint, the correct place for animation logic.

### HTML semantics

HTML isn't just boxes, element *meaning* matters. Use `<header>`, `<nav>`, `<main>`, `<article>`, `<section>`, `<footer>`, `<button>`, `<h1>`-`<h6>` for what they *are*, not `<div>` for everything. Semantic HTML gives you:
- **Accessibility:** screen readers navigate by landmarks and headings; a `<button>` is focusable and keyboard-activatable for free, a `<div onclick>` is not.
- **SEO:** search engines weight semantic structure.
- **Maintainability:** the markup documents itself.

Rule of thumb: if there's a semantic element for it, use it; reach for `<div>`/`<span>` only when there's genuinely no meaning, just grouping/styling.

### The CSS mental model

**Box model.** Every element is a box: `content` → `padding` → `border` → `margin`, from inside out. The gotcha: by default `width` sets the *content* width, so padding and border are *added* on top, making the visual box wider than you set. The fix everyone applies globally:

```css
*, *::before, *::after { box-sizing: border-box; }
/* now width includes padding + border - width means what you expect */
```

**Layout: Flexbox and Grid.**
- **Flexbox** is *one-dimensional*, lay items along a row or column, distribute space, align. Perfect for toolbars, nav bars, centering. `display:flex; justify-content:space-between; align-items:center;`.
- **Grid** is *two-dimensional*, rows *and* columns simultaneously. Perfect for page layouts and dashboards. `display:grid; grid-template-columns: repeat(3, 1fr); gap:1rem;`.

Heuristic: content flowing in a line → Flexbox; a true grid of rows and columns (like a NYX dashboard of cards) → Grid.

**Specificity.** When rules conflict, the most *specific* selector wins. Specificity is scored as (inline, IDs, classes/attributes/pseudo-classes, elements): inline style `1,0,0,0` beats an ID `0,1,0,0` beats a class `0,0,1,0` beats an element `0,0,0,1`. Ties break by source order (last wins). `!important` overrides the cascade, a code smell, use sparingly. Understanding specificity ends the "why won't this style apply" mystery.

### JavaScript in the browser

**DOM manipulation:**

```javascript
const el = document.querySelector("#count");   // find a node
el.textContent = "42";                          // mutate it → triggers reflow/repaint
const li = document.createElement("li");        // create
document.querySelector("ul").appendChild(li);   // insert into the tree
```

Every DOM mutation can cost layout/paint, so batching matters (more below, this is the seed of why React exists).

**Events** propagate in phases: **capture** (root → target) then **bubble** (target → root). `addEventListener` listens in the bubble phase by default. **Event delegation**, one listener on a parent that inspects `event.target`, is efficient for many children:

```javascript
document.querySelector("ul").addEventListener("click", (e) => {
  if (e.target.matches("li")) console.log("clicked", e.target.textContent);
});
```

**Fetch and async.** Network requests are async (they don't block the event loop). Modern code uses Promises + `async/await`:

```javascript
async function loadUser(id) {
  const res = await fetch(`/api/users/${id}`);   // returns a Promise
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();                              // also async
}
loadUser(42).then(u => console.log(u)).catch(err => console.error(err));
```

`await` suspends the async function (without blocking the thread) until the Promise resolves, the event loop keeps running other tasks meanwhile.

### The SPA idea and React's component model

A traditional site fetches a new HTML page per click (full reload). A **Single-Page Application** loads one HTML shell + JS, then *re-renders parts of the DOM* in response to interaction and fetches data via APIs, no full reloads, app-like feel. NYX's frontend is an SPA built with Next.js/React.

**The component model.** Build UI from composable functions that take **props** (inputs) and hold **state** (memory), returning a description of what the UI should look like:

```jsx
function Counter({ label }) {              // label is a prop
  const [count, setCount] = useState(0);   // count is state
  return (
    <button onClick={() => setCount(count + 1)}>
      {label}: {count}
    </button>
  );
}
```

**Hooks** are functions that let function components use state and lifecycle:
- `useState`, local state.
- `useEffect`, run side effects (fetching, subscriptions) after render; the dependency array controls when.
- `useMemo` / `useCallback`, memoize expensive computations / stable function identities.
- `useRef`, mutable value / DOM handle that doesn't trigger re-render.

```jsx
function UserName({ id }) {
  const [user, setUser] = useState(null);
  useEffect(() => {
    let alive = true;
    fetch(`/api/users/${id}`).then(r => r.json())
      .then(u => { if (alive) setUser(u); });
    return () => { alive = false; };       // cleanup avoids setting state after unmount
  }, [id]);                                 // re-run only when id changes
  return <span>{user ? user.name : "…"}</span>;
}
```

### Reconciliation and the virtual DOM - *why it exists*

Here's the payoff for the render-pipeline section. Direct DOM mutation is slow and easy to get wrong: every change can trigger reflow/repaint, and manually computing the *minimal* set of DOM updates when state changes is error-prone.

React's answer: you write components that return a **virtual DOM**, a lightweight JS object tree describing the desired UI. When state changes, React re-runs the component to produce a *new* virtual tree, then **diffs** it against the previous one (**reconciliation**) and computes the minimal real-DOM operations needed, batching them. You describe *what the UI should be*; React figures out *how to mutate the DOM efficiently*.

This is why React feels declarative: you never write `el.textContent = ...`. You return UI as a function of state, and React reconciles. The `key` prop on lists exists to help the diff match elements across renders (so reordering doesn't recreate every node). Knowing the real DOM is expensive to mutate is *exactly* why this indirection earns its keep.

### Rendering strategies (Next.js)

Where and when does the HTML get generated? Next.js gives four strategies, a core NYX decision per page:

- **CSR (Client-Side Rendering):** server sends a near-empty HTML shell + JS; the browser renders everything. Fast server, but slow first paint and bad SEO (crawlers see an empty page). Good for private, highly interactive dashboards behind a login.
- **SSR (Server-Side Rendering):** server renders full HTML *per request*. Fresh data, good SEO, slower TTFB (work per request). Good for personalized, frequently-changing pages.
- **SSG (Static Site Generation):** HTML is rendered *at build time* and served as static files. Fastest possible delivery (CDN), great SEO, but data is frozen at build. Good for docs, marketing, blogs.
- **ISR (Incremental Static Regeneration):** SSG + a `revalidate` interval, pages are static but rebuilt in the background every N seconds. Static speed with periodically fresh data. Great for a NYX pricing or content page that changes hourly, not per request.

Choose by the data's freshness needs and the page's SEO importance: static when you can, server-render when you need per-request data, client-render the interactive private bits.

### Bundling and transpiling intuition

Browsers don't natively understand JSX, TypeScript, or (historically) the latest JS syntax, and shipping hundreds of separate module files would be slow. So a build step:
- **Transpiling** (Babel/SWC/tsc): converts JSX/TS/modern JS into plain JS the browser runs.
- **Bundling** (webpack/Vite/Turbopack): traces the import graph, combines modules, **tree-shakes** unused code, minifies, and **code-splits** into chunks loaded on demand (so a route only ships its own JS). Next.js does this for you, which is why a NYX route loads only what it needs.

### Accessibility & performance basics

- **A11y:** semantic HTML first; `alt` on images; labels on inputs; keyboard operability; sufficient color contrast; `aria-*` only to fill gaps semantics can't. Accessible UIs are also more robust and SEO-friendly.
- **Perf:** minimize render-blocking CSS/JS; lazy-load images and routes; animate `transform`/`opacity` (composite-only) not `width`/`top` (reflow); avoid long synchronous tasks that block the event loop; measure with the Core Web Vitals (LCP, CLS, INP).

## 💻 Build it: a vanilla-JS DOM app, then the same in React

A tiny "todo" to feel the difference. **Vanilla JS**, you manually mutate the DOM:

```html
<input id="todo-input" placeholder="new todo" />
<button id="add">Add</button>
<ul id="list"></ul>
<script>
  const list = document.querySelector("#list");
  const input = document.querySelector("#todo-input");
  let todos = [];

  function render() {                       // we re-draw the whole list by hand
    list.innerHTML = "";
    todos.forEach((t, i) => {
      const li = document.createElement("li");
      li.textContent = t;
      const del = document.createElement("button");
      del.textContent = "✕";
      del.onclick = () => { todos.splice(i, 1); render(); };
      li.appendChild(del);
      list.appendChild(li);
    });
  }

  document.querySelector("#add").onclick = () => {
    if (input.value.trim()) { todos.push(input.value.trim()); input.value = ""; render(); }
  };
</script>
```

Notice the pain: *we* call `render()`, *we* rebuild the DOM, *we* wire up handlers each time. The UI and the data can drift if we forget a `render()`.

**The same in React**, declarative, state-driven:

```jsx
import { useState } from "react";

function Todos() {
  const [todos, setTodos] = useState([]);
  const [text, setText] = useState("");

  const add = () => {
    if (text.trim()) { setTodos([...todos, text.trim()]); setText(""); }
  };
  const remove = (i) => setTodos(todos.filter((_, idx) => idx !== i));

  return (
    <div>
      <input value={text} onChange={(e) => setText(e.target.value)} placeholder="new todo" />
      <button onClick={add}>Add</button>
      <ul>
        {todos.map((t, i) => (
          <li key={i}>{t} <button onClick={() => remove(i)}>✕</button></li>
        ))}
      </ul>
    </div>
  );
}
```

No manual DOM calls. We update *state*; React reconciles the virtual DOM and patches the real DOM minimally. The UI is always a pure function of `todos` and `text`, it *can't* drift. That's the whole value proposition.

### More worked examples

The todo app exercises state and lists, but there are five more patterns I reach for constantly on NYX. Let's build each one and step through what it produces.

#### Example 1 - A Flexbox layout (one dimension)

Flexbox lays children out along a single axis and distributes the leftover space. The canonical use is a top bar: logo on the left, nav links in the middle, a button on the right, all vertically centered.

```html
<nav class="topbar">
  <span class="logo">NYX</span>
  <ul class="links">
    <li>Dashboard</li>
    <li>Reports</li>
    <li>Settings</li>
  </ul>
  <button class="cta">New report</button>
</nav>

<style>
  .topbar {
    display: flex;              /* turn this container into a flex container   */
    align-items: center;       /* center children on the CROSS axis (vertical) */
    justify-content: space-between; /* push children apart on the MAIN axis    */
    gap: 1rem;                 /* even spacing between items                    */
    padding: 0 1rem;
    height: 56px;
    background: #0f172a;
    color: white;
  }
  .links {
    display: flex;             /* nested flex: lay the links in a row           */
    gap: 1.25rem;
    list-style: none;
    margin: 0; padding: 0;
  }
</style>
```

Step through it: `display:flex` makes `.topbar` arrange its three children (logo, links, button) in a **row** by default. `justify-content:space-between` puts the first item hard left, the last hard right, and the spare space between them, so the logo hugs the left edge and the button hugs the right. `align-items:center` centers all three on the *cross* axis, so they line up vertically no matter their individual heights. The nested `.links` is *itself* a flex row, so the three nav items sit in a tidy horizontal line with `1.25rem` gaps. Resize the window and they stay centered and spread, that's the one-dimensional superpower: I told the browser the *intent* (spread, centered) and it does the arithmetic.

The four words that handle 90% of my flex work: `display:flex`, `align-items` (cross axis), `justify-content` (main axis), `gap`.

#### Example 2 - A Grid layout (two dimensions)

When I need rows *and* columns at once, like a NYX dashboard of metric cards, Grid is the tool. Flexbox can fake a grid but fights you; Grid is built for it.

```html
<div class="dashboard">
  <div class="card">Revenue</div>
  <div class="card">Active users</div>
  <div class="card">Churn</div>
  <div class="card">MRR</div>
  <div class="card">ARPU</div>
  <div class="card">Burn</div>
</div>

<style>
  .dashboard {
    display: grid;
    grid-template-columns: repeat(3, 1fr); /* 3 equal columns                  */
    gap: 1rem;                             /* gutters between every row + column */
  }
  /* responsive: auto-fit as many ~220px columns as will fit, then share extra  */
  @media (max-width: 720px) {
    .dashboard { grid-template-columns: repeat(2, 1fr); }
  }
  .card {
    background: white; border: 1px solid #e2e8f0; border-radius: 10px;
    padding: 1rem; min-height: 96px;
  }
</style>
```

Step through it: `display:grid` plus `grid-template-columns: repeat(3, 1fr)` declares three columns, each `1fr`, one fraction of the available space, so they're equal and stretch to fill. With six cards, the grid auto-wraps into **two rows of three**, and `gap:1rem` puts even gutters between *both* rows and columns (no margin hacks). The media query swaps to two columns on narrow screens, so the same six cards become three rows of two on a phone. I never positioned a single card by hand, I described the *grid* and the browser placed them. That's the two-dimensional superpower, and it's exactly how the NYX dashboard shell is built.

A slicker, query-less responsive version uses `repeat(auto-fit, minmax(220px, 1fr))`: "make as many columns as fit at ≥220px wide, then stretch them to share the leftover." Cards reflow fluidly with zero media queries.

#### Example 3 - A controlled form with validation (React)

A **controlled** input is one whose value lives in React state, React is the single source of truth, the DOM just reflects it. That makes validation trivial because I always have the current value.

```jsx
import { useState } from "react";

function SignupForm({ onSubmit }) {
  const [email, setEmail] = useState("");
  const [password, setPassword] = useState("");
  const [touched, setTouched] = useState({ email: false, password: false });

  // derive errors from state - never store them separately
  const emailError =
    email.length === 0 ? "Email is required"
    : !/^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(email) ? "Enter a valid email"
    : null;
  const passwordError =
    password.length < 8 ? "Password must be at least 8 characters" : null;
  const isValid = !emailError && !passwordError;

  const handleSubmit = (e) => {
    e.preventDefault();                       // stop the browser's full-page POST
    setTouched({ email: true, password: true });
    if (isValid) onSubmit({ email, password });
  };

  return (
    <form onSubmit={handleSubmit} noValidate>
      <label>
        Email
        <input
          type="email"
          value={email}                                   /* controlled */
          onChange={(e) => setEmail(e.target.value)}
          onBlur={() => setTouched((t) => ({ ...t, email: true }))}
        />
      </label>
      {touched.email && emailError && <p className="err">{emailError}</p>}

      <label>
        Password
        <input
          type="password"
          value={password}
          onChange={(e) => setPassword(e.target.value)}
          onBlur={() => setTouched((t) => ({ ...t, password: true }))}
        />
      </label>
      {touched.password && passwordError && <p className="err">{passwordError}</p>}

      <button type="submit" disabled={!isValid}>Create account</button>
    </form>
  );
}
```

Step through it: each input's `value` comes from state and `onChange` writes back to state, that's the controlled loop. Because the values live in state, I compute `emailError`/`passwordError` *on every render* as plain derived values (no separate error state to keep in sync, the same "derive, don't store" rule from the dashboard card). The `touched` map means I don't yell "email required" before the user has even focused the field, errors show only after blur or submit attempt. The submit button is `disabled` until valid, and `e.preventDefault()` stops the browser from doing a real form POST so React stays in control. This is the exact pattern behind NYX's login and Anneava's intake forms.

#### Example 4 - `useEffect` data fetch with loading / error / abort done carefully

The dashboard card below uses an `alive` flag; here's the more robust version using `AbortController`, which actually *cancels* the in-flight network request (not just ignores its result).

```jsx
import { useEffect, useState } from "react";

function UserProfile({ userId }) {
  const [state, setState] = useState({ status: "loading", data: null, error: null });

  useEffect(() => {
    const controller = new AbortController();
    setState({ status: "loading", data: null, error: null });

    fetch(`/api/users/${userId}`, { signal: controller.signal })
      .then((r) => {
        if (!r.ok) throw new Error(`HTTP ${r.status}`);
        return r.json();
      })
      .then((data) => setState({ status: "success", data, error: null }))
      .catch((err) => {
        if (err.name === "AbortError") return;          // expected on cleanup - ignore
        setState({ status: "error", data: null, error: err.message });
      });

    return () => controller.abort();   // cleanup: cancel the request if userId changes / unmounts
  }, [userId]);                        // re-run ONLY when userId changes

  if (state.status === "loading") return <p>Loading…</p>;
  if (state.status === "error")   return <p className="err">Error: {state.error}</p>;
  return <h2>{state.data.name}</h2>;
}
```

Step through it: I model the request as a tiny **state machine**, `status` is `"loading" | "success" | "error"`, which makes the three render branches exhaustive and impossible to forget. On each run I create an `AbortController`, pass its `signal` to `fetch`, and **return a cleanup function that calls `controller.abort()`**. When `userId` changes (user clicks a different profile), React runs the cleanup *before* the next effect, aborting the stale request so a slow old response can never overwrite the new one. The `AbortError` branch swallows the expected cancellation noise. The dependency array `[userId]` is the contract: "this effect depends on `userId`; re-run when it changes, not on every render." Get that array wrong and you get either stale data (too few deps) or an infinite loop (a dep that changes every render), see Common Mistakes.

#### Example 5 - `useMemo` / `useCallback`: when they actually help

These memoize to avoid wasted work, but they're frequently cargo-culted. The honest rule: reach for them when (a) a computation is genuinely expensive, or (b) you're passing a value/function to a `React.memo`'d child or to another hook's dependency array and you need *stable identity*.

```jsx
import { useMemo, useCallback, useState } from "react";
import { memo } from "react";

const HeavyList = memo(function HeavyList({ items, onPick }) {
  console.log("HeavyList render");        // we want to see this NOT fire on unrelated changes
  return <ul>{items.map((it) => <li key={it.id} onClick={() => onPick(it.id)}>{it.name}</li>)}</ul>;
});

function Report({ rows }) {
  const [query, setQuery] = useState("");
  const [selected, setSelected] = useState(null);

  // (a) expensive derivation - recompute only when rows or query change, not when `selected` changes
  const filtered = useMemo(() => {
    return rows.filter((r) => r.name.toLowerCase().includes(query.toLowerCase()));
  }, [rows, query]);

  // (b) stable function identity - so memo(HeavyList) doesn't re-render when `query` changes
  const handlePick = useCallback((id) => setSelected(id), []);

  return (
    <div>
      <input value={query} onChange={(e) => setQuery(e.target.value)} placeholder="filter…" />
      <p>Selected: {selected ?? "none"}</p>
      <HeavyList items={filtered} onPick={handlePick} />
    </div>
  );
}
```

Step through it: without `useMemo`, `filtered` would be recomputed on *every* render, including when only `selected` changes, which has nothing to do with filtering. With `useMemo([rows, query])`, the filter runs only when its inputs change. Separately, `HeavyList` is wrapped in `memo`, which skips re-rendering when its props are *referentially equal* to last time. But an inline `onPick={(id) => ...}` is a brand-new function every render, so `memo` would never see equal props. `useCallback([])` gives `handlePick` a stable identity, so changing `query` re-renders `Report` but **not** `HeavyList` (watch the console log). Without `memo` on the child, by the way, `useCallback` buys you nothing, they're a team. Don't sprinkle these everywhere; profile first, memoize the proven hot spots.

#### Example 6 - Event delegation (vanilla)

Back to the muscles layer. If I have a list where rows are added and removed dynamically, attaching a listener to every row is wasteful and breaks for rows added later. **Delegation** puts one listener on the stable parent and uses `event.target` to figure out what was actually clicked.

```html
<ul id="orders">
  <li data-id="101">Order #101 <button class="cancel">Cancel</button></li>
  <li data-id="102">Order #102 <button class="cancel">Cancel</button></li>
</ul>

<script>
  const list = document.querySelector("#orders");

  // ONE listener, even for <li>s added in the future
  list.addEventListener("click", (e) => {
    const btn = e.target.closest(".cancel");   // did the click land on (or inside) a Cancel button?
    if (!btn) return;                          // ignore clicks elsewhere in the list
    const row = btn.closest("li");
    console.log("cancel order", row.dataset.id);
    row.remove();
  });
</script>
```

Step through it: clicks **bubble** up from wherever they happen to the `<ul>`, where our single listener catches them. `e.target` is the deepest element clicked; `e.target.closest(".cancel")` walks up from there to find a matching Cancel button (or returns `null`, which we bail on). This works for rows that didn't exist when the listener was attached, because the listener is on the parent, not the children. One listener instead of N, and it survives dynamic content. This is precisely what React does for you internally (it attaches delegated listeners at the root), which is another reason the React event model feels so smooth.

## ⚠️ Common mistakes

The frontend bugs that bit me (or my teammates) most often. Each is *wrong → right* so you can pattern-match it later.

**1. Using array index as a React `key` when the list reorders or items are inserted/removed.**
Keys tell React which DOM node corresponds to which item across renders. Index keys lie when the order changes, causing wrong items to keep state (e.g., a checked checkbox jumps to the wrong row).
```jsx
// ❌ wrong - index changes when you delete/reorder
{todos.map((t, i) => <li key={i}>{t.text}</li>)}
// ✅ right - stable id that travels with the item
{todos.map((t) => <li key={t.id}>{t.text}</li>)}
```

**2. Missing `useEffect` dependency, or a dependency that causes an infinite loop.**
Too few deps → stale data. A dep that's recreated every render → effect runs forever.
```jsx
// ❌ infinite loop - `options` is a new object each render, so the effect re-runs, re-renders, repeat
useEffect(() => { fetchData(options); }, [options]);
// ✅ depend on the primitive that actually matters (or useMemo the object)
useEffect(() => { fetchData({ id }); }, [id]);
```

**3. Mutating state directly instead of creating a new object/array.**
React compares by reference; mutating in place means the reference is unchanged, so React skips the re-render.
```jsx
// ❌ wrong - same array reference, UI won't update
todos.push(newTodo); setTodos(todos);
// ✅ right - new array, new reference
setTodos([...todos, newTodo]);
// likewise for objects: setUser({ ...user, name }) not user.name = name
```

**4. Forgetting cleanup in `useEffect`.**
Subscriptions, timers, and in-flight fetches leak or fire after unmount without a cleanup return.
```jsx
// ❌ wrong - interval keeps running after the component is gone
useEffect(() => { setInterval(tick, 1000); }, []);
// ✅ right - clear it on unmount
useEffect(() => { const id = setInterval(tick, 1000); return () => clearInterval(id); }, []);
```

**5. `<div onClick>` instead of `<button>` (accessibility).**
A div isn't focusable, isn't keyboard-activatable, and isn't announced as a control to screen readers.
```jsx
// ❌ wrong - invisible to keyboard + screen reader users
<div onClick={save}>Save</div>
// ✅ right - focusable, Enter/Space activate it, announced as a button, free
<button onClick={save}>Save</button>
```

**6. Animating layout properties (`width`, `top`, `left`, `margin`) and getting jank.**
Those trigger reflow + repaint every frame. Animate composite-only properties.
```css
/* ❌ wrong - reflows every frame, drops below 60fps */
.panel { transition: left 0.3s; } .panel.open { left: 0; }
/* ✅ right - transform is GPU-composited, smooth */
.panel { transition: transform 0.3s; transform: translateX(-100%); }
.panel.open { transform: translateX(0); }
```

**7. Not handling loading and error states.**
Rendering `data.name` while `data` is still `null` throws; ignoring failures leaves users staring at a spinner forever.
```jsx
// ❌ wrong - crashes on first render before fetch resolves
return <h2>{data.name}</h2>;
// ✅ right - exhaustive branches
if (loading) return <Spinner />;
if (error)   return <Error msg={error} />;
return <h2>{data.name}</h2>;
```

**8. `==` vs `===`.**
`==` coerces types and surprises you; `===` compares without coercion. Use `===` (and `!==`) by default.
```js
0 == ""       // true  (😱 coercion)
0 === ""      // false (correct)
null == undefined  // true
null === undefined // false
```

**9. Blocking the event loop with heavy synchronous work.**
A long sync loop freezes clicks, scrolling, and repaint, the whole tab locks.
```js
// ❌ wrong - UI frozen for the duration
for (let i = 0; i < 1e9; i++) total += compute(i);
// ✅ right - chunk it, defer it, or move it to a Web Worker
const worker = new Worker("crunch.js"); worker.postMessage(data);
```

**10. Forgetting `box-sizing: border-box`.**
By default `width` excludes padding/border, so your "300px" box renders wider and layouts overflow.
```css
/* ✅ set it once, globally, and width means what you think it means */
*, *::before, *::after { box-sizing: border-box; }
```

## 💼 On the job / interview angle

Frontend interviews lean on a recurring set of concepts. Here are the ones I'd make sure I can answer cold, with the kind of answer that lands.

**Q1, Explain the event loop. What does this print?**
```js
console.log("A");
setTimeout(() => console.log("B"), 0);
Promise.resolve().then(() => console.log("C"));
console.log("D");
```
> Prints `A D C B`. Synchronous code runs first on the call stack (`A`, `D`). Then the loop drains *all* microtasks, the resolved Promise callback (`C`), before taking any macrotask. `setTimeout`'s callback (`B`) is a macrotask, so it runs after the microtask queue is empty. The rule: between tasks, microtasks fully drain before the next macrotask.

**Q2, What is the virtual DOM and why does it exist?**
> It's a lightweight in-memory JS object tree describing the desired UI. Direct DOM mutation is expensive (each change can trigger reflow/repaint) and computing the minimal set of updates by hand is error-prone. React re-renders your component to a *new* virtual tree, diffs it against the previous one (reconciliation), and applies the minimal batched real-DOM operations. So I write declarative UI as a function of state and React handles efficient mutation.

**Q3, `==` vs `===`?**
> `===` is strict equality: same type and value, no coercion. `==` performs type coercion before comparing, which produces surprising results (`0 == ""` is `true`, `null == undefined` is `true`). I default to `===`/`!==`; the only common, defensible use of `==` is `x == null` to catch both `null` and `undefined` at once.

**Q4, How does CSS specificity work?**
> Conflicts are resolved by a specificity score `(inline, IDs, classes/attrs/pseudo-classes, elements)`. Inline styles beat IDs beat classes beat element selectors. Ties break by source order, the last matching rule wins. `!important` overrides the normal cascade and should be avoided. So `#nav .link` (0,1,1,0) beats `.link` (0,0,1,0), which is why "my class won't apply" is usually a more specific selector winning.

**Q5, Flexbox vs Grid?**
> Flexbox is one-dimensional, content along a single row or column, distributing space and aligning (toolbars, nav, centering). Grid is two-dimensional, rows *and* columns at once (page layouts, dashboards). Rule of thumb: a line of content → Flexbox; a true grid of rows and columns → Grid. They compose, grid cells often contain flex layouts.

**Q6, What are React keys for?**
> Keys give list items a stable identity so React's diff can match elements across renders instead of recreating them. Without stable keys (e.g., using array index), reordering or inserting causes React to associate the wrong DOM nodes with the wrong data, so component state lands on the wrong row and you get unnecessary re-renders. Keys should be stable, unique IDs from the data.

**Q7, Controlled vs uncontrolled components?**
> A controlled input's value lives in React state (`value` + `onChange`), React is the single source of truth, which makes validation and conditional logic easy. An uncontrolled input keeps its value in the DOM and you read it via a ref when needed (`<input defaultValue=... ref=...>`). Controlled is the default I reach for; uncontrolled is fine for simple or performance-sensitive forms and integrating non-React widgets.

**Q8, CSR vs SSR vs SSG?**
> CSR: the browser renders everything from a JS bundle, fast server, slow first paint, weak SEO; good for private interactive apps. SSR: the server renders full HTML per request, fresh data and good SEO at the cost of per-request work; good for personalized, changing pages. SSG: HTML is built once at build time and served from a CDN, fastest and great SEO, but data is frozen at build; good for docs/marketing. (ISR adds a revalidate interval to SSG for periodic freshness.)

**Q9, What is a closure?**
> A closure is a function bundled with the variables from the scope where it was *defined*, so it keeps access to them even after that outer scope has returned.
```js
function counter() {
  let n = 0;                 // captured by the returned function
  return () => ++n;          // closes over n
}
const next = counter();
next(); next();              // 1, then 2 - n persists between calls
```
> Closures power data privacy, factory functions, and (relevantly) React hooks, each render's handlers close over that render's state, which is also the source of "stale closure" bugs.

**Q10, `var` vs `let` vs `const` and hoisting?**
> `var` is function-scoped and hoisted, initialized to `undefined` (so reading it before assignment gives `undefined`, not an error). `let`/`const` are block-scoped and hoisted but live in the "temporal dead zone" until declared, reading early throws. `const` can't be reassigned (though objects it points to can still mutate). Modern code: `const` by default, `let` when you must reassign, `var` essentially never.
```js
console.log(a); // undefined  (var hoisted + initialized)
var a = 1;
console.log(b); // ReferenceError (let in TDZ)
let b = 2;
```

## 🧪 Mini-project: a React dashboard card that fetches an API and renders a chart

Echoing my Recharts/D3 work on NYX, a self-contained revenue card with loading and error states and a line chart.

```tsx
import { useEffect, useState } from "react";
import { LineChart, Line, XAxis, YAxis, Tooltip, ResponsiveContainer } from "recharts";

type Point = { month: string; revenue: number };

export function RevenueCard({ endpoint }: { endpoint: string }) {
  const [data, setData] = useState<Point[] | null>(null);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    let alive = true;
    setData(null); setError(null);
    fetch(endpoint)
      .then((r) => {
        if (!r.ok) throw new Error(`HTTP ${r.status}`);
        return r.json() as Promise<Point[]>;
      })
      .then((d) => { if (alive) setData(d); })
      .catch((e) => { if (alive) setError(e.message); });
    return () => { alive = false; };          // cancel on unmount / endpoint change
  }, [endpoint]);

  if (error) return <div className="card error">Failed to load: {error}</div>;
  if (!data) return <div className="card">Loading revenue…</div>;

  const total = data.reduce((sum, p) => sum + p.revenue, 0);

  return (
    <div className="card">
      <h3>Monthly Revenue</h3>
      <p className="total">${total.toLocaleString()}</p>
      <ResponsiveContainer width="100%" height={220}>
        <LineChart data={data}>
          <XAxis dataKey="month" />
          <YAxis />
          <Tooltip formatter={(v: number) => `$${v.toLocaleString()}`} />
          <Line type="monotone" dataKey="revenue" stroke="#4f46e5" strokeWidth={2} dot={false} />
        </LineChart>
      </ResponsiveContainer>
    </div>
  );
}
```

The pattern to internalize: **state for data + error → effect to fetch keyed on the input → render branches for loading/error/success → derive view values (`total`) from state, never store them separately.** The cleanup flag (`alive`) prevents the classic "set state after unmount" warning when `endpoint` changes mid-flight. This is the exact shape of every data-driven NYX card.

Wire it up against the FastAPI endpoint we'll build in Chapter 8.2 (`GET /api/revenue`) and you've got a full frontend-to-backend slice.

## 🧪 Mini-project 2: a debounced search / autocomplete component (React + TypeScript)

This is the single most common "real" component in production apps, and it ties together almost everything in this chapter: controlled input, `useEffect`, debouncing (so we don't hammer the API on every keystroke), aborting stale requests (so a slow earlier query can't overwrite a newer one), and exhaustive loading/error/empty states. It's the search box in NYX's ticker lookup and Anneava's patient search.

First, a tiny reusable **debounce hook**. Debouncing means "wait until the user stops typing for N ms, *then* act", it collapses a burst of keystrokes into one call.

```tsx
import { useEffect, useState } from "react";

// Returns `value` but delayed: it only updates after `delay` ms of no further changes.
function useDebounced<T>(value: T, delay = 300): T {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);   // each new keystroke cancels the pending timer - that IS the debounce
  }, [value, delay]);
  return debounced;
}
```

Step through the hook: every time `value` changes (a keystroke), the effect schedules a timer to copy it into `debounced` after `delay` ms, but the cleanup `clearTimeout` runs first on the *next* keystroke, cancelling the previous timer. So the copy only lands once the user pauses. That cleanup-cancels-the-timer trick *is* debouncing.

Now the autocomplete itself:

```tsx
import { useEffect, useState } from "react";

type Result = { id: string; symbol: string; name: string };
type Status = "idle" | "loading" | "success" | "error";

export function TickerSearch() {
  const [query, setQuery] = useState("");
  const debouncedQuery = useDebounced(query, 300);
  const [results, setResults] = useState<Result[]>([]);
  const [status, setStatus] = useState<Status>("idle");
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const q = debouncedQuery.trim();
    if (q.length < 2) {                 // don't search on 0-1 chars
      setResults([]); setStatus("idle"); setError(null);
      return;
    }

    const controller = new AbortController();
    setStatus("loading"); setError(null);

    fetch(`/api/tickers?q=${encodeURIComponent(q)}`, { signal: controller.signal })
      .then((r) => {
        if (!r.ok) throw new Error(`HTTP ${r.status}`);
        return r.json() as Promise<Result[]>;
      })
      .then((data) => { setResults(data); setStatus("success"); })
      .catch((err) => {
        if (err.name === "AbortError") return;   // a newer query superseded this one - ignore
        setError(err.message); setStatus("error");
      });

    return () => controller.abort();    // cancel the in-flight request when the query changes / unmounts
  }, [debouncedQuery]);                 // re-run ONLY when the debounced value settles

  return (
    <div className="search">
      <label htmlFor="ticker-q">Search tickers</label>
      <input
        id="ticker-q"
        type="search"
        value={query}
        onChange={(e) => setQuery(e.target.value)}
        placeholder="e.g. AAPL"
        autoComplete="off"
        aria-busy={status === "loading"}
      />

      {status === "loading" && <p className="hint">Searching…</p>}
      {status === "error"   && <p className="err">Couldn’t search: {error}</p>}
      {status === "success" && results.length === 0 && <p className="hint">No matches.</p>}

      {results.length > 0 && (
        <ul className="results" role="listbox">
          {results.map((r) => (
            <li key={r.id} role="option">
              <strong>{r.symbol}</strong> - {r.name}
            </li>
          ))}
        </ul>
      )}
    </div>
  );
}
```

Step through the whole flow. The input is **controlled** (`query` in state). `useDebounced` gives me `debouncedQuery`, which only updates 300ms after the user stops typing, so typing "AAPL" fast triggers *one* search, not four. The effect keys on `debouncedQuery`: it short-circuits for queries under two characters, then fires a fetch with an `AbortController`. When the debounced query changes again, React runs the cleanup (`controller.abort()`) *before* the next effect, so an earlier slow response can never clobber a newer query's results, the classic race-condition bug, solved structurally. The render uses an explicit `Status` union so I cover **loading, error, empty, and success** exhaustively, no "spinner forever" and no crash on undefined. The `<label htmlFor>`, `role="listbox"/"option"`, and `aria-busy` make it keyboard- and screen-reader-friendly (Anneava-grade a11y). Wire `/api/tickers?q=` to a FastAPI route and this drops straight into a real product.

The pattern to internalize: **debounce the input → effect keyed on the debounced value → abort stale requests in cleanup → exhaustive status-driven rendering.** Once this is muscle memory, every "search as you type" feature is a 20-minute job.

```jsx
}
```

**8.** Two problems, same root cause: **no dependency array**, so the effect runs after *every* render. Each fetch calls `setResults`, which triggers a re-render, which runs the effect again → an infinite fetch loop.
```jsx
useEffect(() => {
  const controller = new AbortController();
  fetch(`/api/search?q=${term}`, { signal: controller.signal })
    .then(r => r.json()).then(setResults)
    .catch(e => { if (e.name !== "AbortError") console.error(e); });
  return () => controller.abort();

```

**9.** **Stale closure.** With empty deps `[]`, the effect runs once; the interval callback closes over `count` from that *first* render, where `count` is `0` forever, so it always sets `0 + 1 = 1`. Fix A, use the **functional updater**, which doesn't read the captured value:
```jsx
useEffect(() => {
  const id = setInterval(() => setCount(c => c + 1), 1000);  // c is the latest state
  return () => clearInterval(id);
}, []);
```
Fix B, add `count` to deps so the effect (and interval) is recreated each tick with the fresh value (less efficient, recreates the interval each second):
```jsx
useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000);
  return () => clearInterval(id);
}, [count]);
```
Fix A is the idiomatic one.

React compares by reference, sees no change, and skips the re-render, so the new tag never appears (it's actually in the data, just not rendered until some other re-render). Fix: create a new array.
```jsx
const addTag = () => setTags([...tags, "c"]);
```
