## Start here

Before any of the acronyms, here's the one analogy that makes APIs click. **An API is a restaurant.**

- **The menu is the set of endpoints.** It lists exactly what you can order: `GET /orders`, `POST /orders`, `GET /users/42`. You don't get to invent a dish that isn't on the menu, and you don't need to know *how* it's made to order it.
- **The waiter is the API contract.** You hand the waiter a precise request ("the salmon, no capers"). The waiter carries it to the kitchen and brings back exactly what was agreed. The contract is the promise: *if you ask in this shape, you get back that shape.* That promise is the whole reason the frontend team and the backend team can work in parallel.
- **The kitchen is the backend logic.** It has the database, the business rules, the secrets, the ovens. It's where the real work happens.
- **You never enter the kitchen.** This is the important part. The customer (the client: a browser, a mobile app, another service) is never allowed behind the counter. You can't reach in and grab a row from the database. You can't read the chef's recipes. Everything you're allowed to do passes through the menu and the waiter. That boundary is what keeps the system safe, swappable, and sane: the kitchen can rip out its old stove and buy a new one, and as long as the salmon still comes out the same, you never notice.

Extend this to NYX Finance: the Next.js dashboard is the customer reading a menu of analytics endpoints. The FastAPI service is the kitchen, talking to Postgres. The JSON contract is the waiter. For Anneava — HIPAA-aligned and multi-tenant — the "you never enter the kitchen" rule is load-bearing: a tenant must only ever see their own data, and the only way to enforce that is to make sure every dish leaves through a waiter who checks who you are first.

**Why these skills matter for a tech job.** Almost every product company runs on backend APIs. The frontend is a thin shell; the durable value — the data, the rules, the money — lives behind the API. If you can design a clean, predictable, well-documented API and implement it correctly, you can build the spine of a product. Interviewers know this, which is why "design an API for X" and "what status code would you return here?" are everyday questions. Backend/API fluency sits at the intersection of databases (Part 7), security (8.3), and the product itself. Master this chapter and you can own a vertical slice end to end, and owning a slice is what gets you hired and promoted.

## Theory

### What a backend does

A backend is a long-running program that:
- **Accepts requests** (usually HTTP) from clients (browsers, mobile, other services).
- **Authenticates/authorizes** the caller (Chapter 8.3).
- **Validates** input — never trust the client.
- **Executes business logic** and talks to data stores (Postgres, Redis, DynamoDB from Part 7).
- **Serializes** a response (usually JSON) with an appropriate status code.
- Handles **errors, logging, config, and observability** so you can run it in production.

The contract between frontend and backend is the **API**. A good API is a stable, predictable, well-documented surface that clients can build on without surprises.

### The request lifecycle (HTTP)

A request is: a **method** (verb) + **URL** (+ query string) + **headers** + optional **body**. The server routes it to a handler, which returns a **status code** + headers + body. Statelessness is a core REST tenet: each request carries everything needed to process it (e.g. an auth token), so the server keeps no per-client session in memory, which is what lets you run many identical backend instances behind a load balancer.

```
Client → [Method + Path + Headers + Body] → Load Balancer → Server instance
       → route → middleware (auth, logging) → validate → business logic → DB
       → serialize → [Status + Headers + Body] → Client
```

### Designing good REST APIs

REST models your domain as **resources** (nouns) addressed by URLs, manipulated with HTTP **verbs**.

**Resources are nouns, plural, hierarchical:**
```
/users                 collection of users
/users/42              a specific user
/users/42/orders       that user's orders (sub-resource)
/users/42/orders/1001  a specific order
```
Avoid verbs in paths (`/getUser`, `/createOrder` are anti-patterns); the HTTP method is the verb.

**Verbs and their semantics:**

| Verb | Meaning | Idempotent? | Safe? |
|---|---|---|---|
| `GET` | read | yes | yes (no side effects) |
| `POST` | create (or non-idempotent action) | no | no |
| `PUT` | replace entire resource | yes | no |
| `PATCH` | partial update | not necessarily | no |
| `DELETE` | remove | yes | no |

**Idempotency** = doing it N times has the same effect as doing it once. `GET`, `PUT`, `DELETE` are idempotent by definition; `POST` is not (two POSTs = two resources). This matters for retries: if a client times out and retries a `PUT`, no harm; retrying a `POST` could double-charge a NYX customer. The fix is an **idempotency key**: the client sends a unique header (`Idempotency-Key: <uuid>`), and the server stores the result for that key and returns the cached result on retry. (Stripe does exactly this.)

**Status codes say what happened:**
- `2xx` success: `200 OK`, `201 Created` (return the new resource + `Location` header), `204 No Content` (success, nothing to return, e.g. DELETE).
- `3xx` redirect: `301`/`302`, `304 Not Modified` (caching).
- `4xx` client error (their fault): `400 Bad Request` (malformed), `401 Unauthorized` (not authenticated), `403 Forbidden` (authenticated but not allowed), `404 Not Found`, `409 Conflict` (e.g. duplicate), `422 Unprocessable Entity` (validation failed), `429 Too Many Requests` (rate limit).
- `5xx` server error (your fault): `500 Internal Server Error`, `503 Service Unavailable`.

Returning the right code is a kindness to every client: they can branch on it without parsing your prose.

**Versioning.** APIs change; clients depend on stability. Version so you can evolve without breaking callers: URL-based (`/v1/users`) is the most explicit and common; header-based (`Accept: application/vnd.nyx.v2+json`) is cleaner but less visible. Pick one and be consistent. Never silently change a response shape in place.

**Pagination.** Never return an unbounded list. Two styles:
- **Offset/limit:** `?limit=20&offset=40`. Simple, supports "jump to page N," but slow on deep pages (the DB still scans the offset) and can skip/duplicate rows if data changes mid-paging.
- **Cursor (keyset):** `?limit=20&after=<opaque cursor>` where the cursor encodes the last seen key. Stable and fast at any depth (it's a `WHERE id > cursor`, uses the index). Preferred for large/changing datasets like NYX event feeds.

**Filtering & sorting** via query params: `GET /orders?status=paid&sort=-created_at&min_amount=50`. Document allowed fields; don't let clients sort/filter on arbitrary columns (perf + security).

**HATEOAS (lightly).** "Hypermedia as the Engine of Application State": responses include links to related actions/resources (`{"id":42, "_links":{"orders":"/users/42/orders"}}`) so clients discover the API by following links rather than hardcoding URLs. It's the most-ignored REST constraint; most APIs skip it. Worth knowing it exists; fine to omit in practice.

### Validation & serialization

- **Validation:** check incoming data against rules (types, ranges, required fields) and reject bad input with `400`/`422` *before* it touches your logic. Never trust the client.
- **Serialization:** convert internal objects (DB rows, domain models) into the wire format (JSON), and **deserialization** the reverse. A good framework (FastAPI + Pydantic) makes both declarative and automatic, and uses the same models to generate docs.

### GraphQL - when it beats REST

GraphQL is a query language for APIs: the client asks for *exactly* the fields it wants in one request, against a typed **schema**.

```graphql
# Schema
type User { id: ID!, name: String!, orders: [Order!]! }
type Order { id: ID!, amount: Float!, status: String! }
type Query { user(id: ID!): User }

# Client query - get a user and just the amounts of their orders, one round trip
query { user(id: "42") { name orders { amount } } }
```

- **Schema** = the typed contract (types, queries, mutations).
- **Queries** read, **mutations** write, **resolvers** are the server functions that fetch each field.

**When GraphQL beats REST:** clients with diverse data needs (mobile wants less, web wants more) avoid over-/under-fetching; aggregating many resources in one round trip (no waterfall of REST calls); rapidly evolving frontends that shouldn't wait on new backend endpoints. NYX-style dashboards with many widgets each needing different slices are a natural fit.

**Tradeoffs:** caching is harder (everything is usually one `POST /graphql`, so HTTP caching by URL doesn't apply); you must guard against expensive/deeply-nested queries (query depth/cost limits); and the famous **N+1 problem**:

A resolver for `user.orders` that runs one DB query, then a resolver for each order's `customer` that runs *another* query per order → 1 + N queries. With 100 orders that's 101 round trips. The fix is the **DataLoader** pattern: batch and dedupe the per-item lookups within a tick into a single `WHERE id IN (...)` query, and cache within the request. Every serious GraphQL server uses DataLoader-style batching. (REST has the dual problem — under-fetching forces clients into waterfalls — so neither is free.)

**The honest take:** REST is simpler, cacheable, and great for resource-shaped APIs and public APIs; GraphQL shines for rich, client-driven, aggregating UIs at the cost of server complexity. For NYX you'd default to REST and reach for GraphQL only when the over-fetching pain is real.

### FastAPI essentials

FastAPI is a modern async Python framework built on **Pydantic** (validation/serialization via type hints) and **Starlette** (ASGI). Its strengths:
- **Type hints drive everything.** Declare a Pydantic model and you get validation, serialization, *and* OpenAPI docs for free.
- **Dependency injection.** Declare what a handler needs (a DB session, the current user) as a parameter; FastAPI resolves and injects it, and it's testable/overridable.
- **Async endpoints.** `async def` handlers run on an event loop (like the browser's, Chapter 8.1), so one process handles many concurrent I/O-bound requests without threads.
- **Auto docs.** Interactive Swagger UI at `/docs` and ReDoc at `/redoc`, generated from your types. No separate doc-writing step.

## Build it: a complete FastAPI CRUD service with validation and tests

A small `items` API with full CRUD, Pydantic validation, proper status codes, and tests.

```python
# app.py
from fastapi import FastAPI, HTTPException, status, Depends, Query
from pydantic import BaseModel, Field
from typing import Annotated
import itertools

app = FastAPI(title="Items API", version="1.0.0")

# --- Pydantic models: validation + serialization + docs in one place ---
class ItemCreate(BaseModel):
    name: str = Field(min_length=1, max_length=100)
    price: float = Field(gt=0, description="Price in USD, must be positive")
    in_stock: bool = True

class ItemUpdate(BaseModel):          # all optional → PATCH semantics
    name: str | None = Field(default=None, min_length=1, max_length=100)
    price: float | None = Field(default=None, gt=0)
    in_stock: bool | None = None

class Item(ItemCreate):
    id: int

# --- Fake "database" (swap for Postgres in the mini-project) ---
_db: dict[int, Item] = {}
_ids = itertools.count(1)

def get_db():                          # dependency: injected & overridable in tests
    return _db

# --- Routes ---
@app.post("/items", response_model=Item, status_code=status.HTTP_201_CREATED)
def create_item(payload: ItemCreate, db: Annotated[dict, Depends(get_db)]):
    item = Item(id=next(_ids), **payload.model_dump())
    db[item.id] = item
    return item                        # 201 + the created resource

@app.get("/items", response_model=list[Item])
def list_items(
    db: Annotated[dict, Depends(get_db)],
    limit: int = Query(20, ge=1, le=100),
    offset: int = Query(0, ge=0),
    in_stock: bool | None = None,      # optional filter
):
    items = list(db.values())
    if in_stock is not None:
        items = [i for i in items if i.in_stock == in_stock]
    return items[offset : offset + limit]      # paginated

@app.get("/items/{item_id}", response_model=Item)
def get_item(item_id: int, db: Annotated[dict, Depends(get_db)]):
    if item_id not in db:
        raise HTTPException(status.HTTP_404_NOT_FOUND, "Item not found")
    return db[item_id]

@app.patch("/items/{item_id}", response_model=Item)
def update_item(item_id: int, patch: ItemUpdate, db: Annotated[dict, Depends(get_db)]):
    if item_id not in db:
        raise HTTPException(status.HTTP_404_NOT_FOUND, "Item not found")
    current = db[item_id]
    updated = current.model_copy(update=patch.model_dump(exclude_unset=True))
    db[item_id] = updated
    return updated

@app.delete("/items/{item_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_item(item_id: int, db: Annotated[dict, Depends(get_db)]):
    if db.pop(item_id, None) is None:
        raise HTTPException(status.HTTP_404_NOT_FOUND, "Item not found")
    # 204: success, no body
```

Notice how much we get for free: `price: float = Field(gt=0)` auto-rejects non-positive prices with a `422` and a clear error; the `response_model` controls exactly what's serialized out (and strips anything extra); `Query(20, ge=1, le=100)` validates pagination bounds; and `/docs` already documents all of this.

**Tests** (pytest + FastAPI's `TestClient`):

```python
# test_app.py
from fastapi.testclient import TestClient
from app import app

client = TestClient(app)

def test_create_and_get():
    r = client.post("/items", json={"name": "Widget", "price": 9.99})
    assert r.status_code == 201
    item = r.json()
    assert item["id"] and item["in_stock"] is True

    r2 = client.get(f"/items/{item['id']}")
    assert r2.status_code == 200
    assert r2.json()["name"] == "Widget"

def test_validation_rejects_bad_price():
    r = client.post("/items", json={"name": "Bad", "price": -1})
    assert r.status_code == 422            # Pydantic caught it before our code ran

def test_404_on_missing():
    assert client.get("/items/99999").status_code == 404

def test_patch_partial():
    created = client.post("/items", json={"name": "A", "price": 1}).json()
    r = client.patch(f"/items/{created['id']}", json={"price": 2.5})
    assert r.status_code == 200 and r.json()["price"] == 2.5
    assert r.json()["name"] == "A"         # untouched field preserved

def test_delete_204():
    created = client.post("/items", json={"name": "Z", "price": 5}).json()
    assert client.delete(f"/items/{created['id']}").status_code == 204
    assert client.get(f"/items/{created['id']}").status_code == 404
```

Run with `pytest`. These tests double as living documentation of the API's contract.

### Error handling, logging, config

```python
import logging
from pydantic_settings import BaseSettings
from fastapi import Request
from fastapi.responses import JSONResponse

# Config from environment, validated and typed
class Settings(BaseSettings):
    database_url: str = "sqlite:///./app.db"
    log_level: str = "INFO"
    class Config: env_file = ".env"

settings = Settings()
logging.basicConfig(level=settings.log_level)
log = logging.getLogger("items")

# Consistent error envelope for unhandled exceptions
@app.exception_handler(Exception)
async def unhandled(request: Request, exc: Exception):
    log.exception("Unhandled error on %s %s", request.method, request.url.path)
    return JSONResponse(status_code=500, content={"error": "internal_server_error"})
```

Principles: **config from environment** (never hardcode secrets/DB URLs, 12-factor); **structured logging** with levels; **never leak stack traces or internals to clients** (log them, return a generic `500`); validation errors should be specific and actionable (`422` with field paths, Pydantic does this automatically).

### A raw HTTP request and response, byte for byte

Frameworks hide the wire, but it helps to see it once so the abstraction never feels like magic. Here is what actually crosses the socket when the NYX frontend creates an order. The first line is the **request line** (method, path, HTTP version); then **headers**, a blank line, then the **body**.

```http
POST /v1/orders HTTP/1.1
Host: api.nyxfinance.com
Content-Type: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Idempotency-Key: 8f3c2b1a-2d44-4c9e-9a3b-2f1e0d6c7b88
Accept: application/json
Content-Length: 37

{"user_id": 42, "amount_usd": 199.00}
```

And the server's reply. The first line is the **status line** (HTTP version, status code, reason phrase); then response headers, a blank line, then the JSON body:

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /v1/orders/1001
Content-Length: 104

{"id": 1001, "user_id": 42, "amount_usd": 199.0, "status": "paid", "created_at": "2026-06-26T14:03:11Z"}
```

Read it top to bottom and every piece of theory above is right there: the verb (`POST`), the versioned path (`/v1/orders`), the auth token carrying the request's identity (statelessness: the server stores nothing about this client between requests), the idempotency key so a retried POST won't create two orders, the `201 Created` status, and the `Location` header pointing at the freshly created resource. When something breaks in production, this is the layer you drop down to with `curl -v` or browser dev tools.

### A custom validator and the 422 it produces

Field constraints (`gt=0`, `min_length`) cover a lot, but real domains have rules that span fields or need logic. Pydantic's `field_validator` and `model_validator` let you express those, and FastAPI turns a failure into a structured `422` automatically — you never write the error-formatting code.

```python
from pydantic import BaseModel, Field, field_validator, model_validator

class OrderCreate(BaseModel):
    user_id: int = Field(gt=0)
    amount_usd: float = Field(gt=0, le=1_000_000)
    currency: str = Field(default="USD", min_length=3, max_length=3)
    coupon_code: str | None = None

    @field_validator("currency")
    @classmethod
    def currency_upper_and_supported(cls, v: str) -> str:
        v = v.upper()
        if v not in {"USD", "EUR", "GBP"}:
            raise ValueError("unsupported currency; use USD, EUR, or GBP")
        return v                       # validators can also *normalize* (uppercasing here)

    @model_validator(mode="after")
    def coupon_requires_min_amount(self):
        # cross-field rule: coupons only valid on orders >= $10
        if self.coupon_code and self.amount_usd < 10:
            raise ValueError("coupon not valid on orders under $10")
        return self
```

Now send something that breaks two rules at once:

```bash
curl -i -X POST http://localhost:8000/v1/orders \
  -H "Content-Type: application/json" \
  -d '{"user_id": 42, "amount_usd": 5, "currency": "xrp", "coupon_code": "SAVE5"}'
```

FastAPI replies `422 Unprocessable Entity` with a body that pinpoints every problem by field path — which is what lets a frontend highlight the exact bad input:

```json
{
  "detail": [
    {
      "type": "value_error",
      "loc": ["body", "currency"],
      "msg": "Value error, unsupported currency; use USD, EUR, or GBP",
      "input": "xrp"
    },
    {
      "type": "value_error",
      "loc": ["body"],
      "msg": "Value error, coupon not valid on orders under $10",
      "input": {"user_id": 42, "amount_usd": 5, "currency": "xrp", "coupon_code": "SAVE5"}
    }
  ]
}
```

The `loc` array is a path into the request: `["body", "currency"]` means "the `currency` field of the request body." A model-level error has `loc: ["body"]` because it isn't tied to one field. You wrote two `raise ValueError(...)` lines; FastAPI did all the JSON shaping, the `422` status, and the docs.

### An idempotency-key implementation sketch

This is the concrete version of the theory: a retried `POST` must not create two orders. The client sends an `Idempotency-Key` header; the server remembers the response it produced for that key and replays it on a retry.

```python
from fastapi import Header
from uuid import UUID

# In production this is Redis with a TTL (e.g. 24h), not a dict.
# Value stores both the status and the body so the replay is byte-identical.
_idempotency: dict[str, tuple[int, dict]] = {}

@app.post("/v1/orders", status_code=201)
def create_order(
    payload: OrderCreate,
    db: Annotated[object, Depends(get_session)],
    idempotency_key: Annotated[UUID | None, Header()] = None,
):
    if idempotency_key is not None:
        key = str(idempotency_key)
        if key in _idempotency:
            status_code, body = _idempotency[key]
            return JSONResponse(status_code=status_code, content=body)  # replay, no new row

    row = db.execute(
        text("""INSERT INTO orders (user_id, amount_usd, status)
                VALUES (:u, :a, 'paid')
                RETURNING id, user_id, amount_usd, status, created_at"""),
        {"u": payload.user_id, "a": payload.amount_usd},
    ).mappings().one()
    db.commit()
    result = dict(row)

    if idempotency_key is not None:
        _idempotency[str(idempotency_key)] = (201, result)  # remember for retries
    return result
```

Step through it: the first request with key `8f3c…` finds no entry, so we insert and store the `(201, body)`. The client's network flickers and it retries with the same key; we find the entry and replay the stored `201` and body without touching the database. One logical order, no double charge. Two real refinements you'd add in NYX/Anneava: (1) store the key inside the same DB transaction as the insert (or use a unique constraint on the key column) so a crash between INSERT and "remember" can't lose the mapping; (2) give the cache a TTL so keys don't accumulate forever.

### A rate-limiting middleware sketch

Unbounded request volume from one caller can starve everyone else (and run up your bill). A simple fixed-window limiter, written as ASGI middleware so it runs for *every* request before the handler:

```python
import time
from collections import defaultdict
from fastapi import Request
from fastapi.responses import JSONResponse

WINDOW_SECONDS = 60
MAX_REQUESTS = 100                     # per client per window
_hits: dict[str, list[float]] = defaultdict(list)

@app.middleware("http")
async def rate_limit(request: Request, call_next):
    client = request.client.host       # in prod: use API key / user id / X-Forwarded-For
    now = time.time()
    # drop timestamps older than the window, then count what's left
    window = [t for t in _hits[client] if now - t < WINDOW_SECONDS]
    if len(window) >= MAX_REQUESTS:
        retry_after = WINDOW_SECONDS - int(now - window[0])
        return JSONResponse(
            status_code=429,
            content={"error": "rate_limited", "retry_after_seconds": retry_after},
            headers={"Retry-After": str(retry_after)},
        )
    window.append(now)
    _hits[client] = window
    return await call_next(request)    # under the limit → run the real handler
```

Walk through it: each client's request timestamps are kept in a list; on every request we discard timestamps older than 60 seconds, then check the count. Over the cap → `429 Too Many Requests` with a `Retry-After` header so a well-behaved client knows when to come back. Under the cap → we record the hit and call the real handler via `call_next`. In production you'd back this with Redis (so the count is shared across all server instances — statelessness means there are many) and use a sliding-window or token-bucket algorithm instead of a fixed window to avoid the burst-at-the-boundary problem.

### GraphQL resolvers and the DataLoader fix, in Python

Here's the N+1 problem made real and then fixed, using `strawberry` (a typed Python GraphQL library). First, the **naive** version that bites:

```python
import strawberry
from typing import List

# Pretend these hit Postgres. Each call is one round trip.
def fetch_orders_for_user(user_id: int) -> list[dict]:
    return db.execute(text("SELECT id, customer_id, amount FROM orders WHERE user_id=:u"),
                      {"u": user_id}).mappings().all()

def fetch_customer(customer_id: int) -> dict:           # <-- called once PER order
    return db.execute(text("SELECT id, name FROM customers WHERE id=:c"),
                      {"c": customer_id}).mappings().one()

@strawberry.type
class Customer:
    id: int
    name: str

@strawberry.type
class Order:
    id: int
    amount: float
    customer_id: strawberry.Private[int]

    @strawberry.field
    def customer(self) -> Customer:
        c = fetch_customer(self.customer_id)            # 1 query EACH → N+1!
        return Customer(id=c["id"], name=c["name"])
```

For a user with 100 orders, the query `user { orders { customer { name } } }` runs **1** query for the orders and then **100** more, one per order's `customer` resolver. 101 round trips for data that lives in two tables. That's the N+1 problem, and it scales linearly with the result size.

The fix is a **DataLoader**: instead of fetching each customer immediately, the resolver *registers* the id it wants; the loader collects all the ids requested within one tick of the event loop, fires a single batched `WHERE id IN (...)`, and hands each resolver back its row. It also dedupes (two orders sharing a customer = one fetch) and caches within the request.

```python
from strawberry.dataloader import DataLoader

async def load_customers(customer_ids: list[int]) -> list[dict]:
    # ONE batched query for every id requested this tick
    rows = db.execute(
        text("SELECT id, name FROM customers WHERE id = ANY(:ids)"),
        {"ids": customer_ids},
    ).mappings().all()
    by_id = {r["id"]: r for r in rows}
    # MUST return results in the SAME ORDER as the input ids
    return [by_id[cid] for cid in customer_ids]

customer_loader = DataLoader(load_fn=load_customers)

@strawberry.type
class Order:
    id: int
    amount: float
    customer_id: strawberry.Private[int]

    @strawberry.field
    async def customer(self) -> Customer:
        c = await customer_loader.load(self.customer_id)   # batched + deduped + cached
        return Customer(id=c["id"], name=c["name"])
```

Now the same `user { orders { customer { name } } }` runs **2** queries total — one for the orders, one batched `WHERE id IN (...)` for all the customers — whether there are 10 orders or 10,000. The contract the loader demands is the subtle part: `load_customers` **must return rows in the exact order of the input ids** (that's why you build a dict and re-index), because the loader matches results back to callers positionally.

## Common mistakes

The API mistakes you'll actually see (and make). Wrong vs right.

1. **Verbs in URLs.**
   - ✗ `POST /createOrder`, `GET /getUserById?id=42`, `POST /deleteOrder/7`
   - ✓ `POST /orders`, `GET /users/42`, `DELETE /orders/7`. The HTTP method *is* the verb; the URL names a resource.

2. **Returning `200 OK` for errors.**
   - ✗ `200 OK` with body `{"success": false, "error": "not found"}`. Now every client must parse the body to know if it worked, and caches/proxies think it succeeded.
   - ✓ Return the real status: `404` for missing, `422` for validation, `409` for conflict. Let the status line carry the truth.

3. **Leaking stack traces / internals.**
   - ✗ A `500` whose body is the Python traceback, the SQL that failed, and the connection string. That's a gift to an attacker and a HIPAA violation waiting to happen in Anneava.
   - ✓ Log the full trace server-side; return a generic `{"error": "internal_server_error"}` with a request id the user can quote to support.

4. **Trusting the client / no input validation.**
   - ✗ `amount = request.json["amount"]; db.charge(amount)` — the client can send `-100`, `"abc"`, or `1e308`.
   - ✓ Validate every field with Pydantic constraints *before* business logic; reject with `422`. Never trust anything that comes over the wire.

5. **No pagination at all (unbounded list).**
   - ✗ `SELECT * FROM events` returned as one giant array. One day the table has 50M rows and the endpoint (and the client) falls over.
   - ✓ Always bound the result: `limit` with a sane max (`le=100`), and return a cursor for "more."

6. **Offset pagination on huge tables.**
   - ✗ `?offset=2000000&limit=20` — the DB scans and discards two million rows for every deep page; latency grows with page depth, and concurrent inserts skip/duplicate rows.
   - ✓ Cursor/keyset pagination: `WHERE id > :cursor ORDER BY id LIMIT :limit`. Fast at any depth because it rides the index.

7. **Secrets in code, not env.**
   - ✗ `DATABASE_URL = "postgres://admin:hunter2@prod-db/..."` committed to git.
   - ✓ Read from the environment (`pydantic-settings`), keep secrets in a vault/secrets manager, and never commit `.env`. (12-factor.)

8. **No versioning.**
   - ✗ Renaming a JSON field in place. Every existing client breaks the moment you deploy.
   - ✓ Version the API (`/v1/...`); make additive changes within a version and breaking changes in a new one. Deprecate, don't yank.

9. **N+1 in GraphQL (or any resolver/ORM).**
   - ✗ A `customer` resolver that fires one query per order; or `for o in orders: o.customer.name` in an ORM with lazy loading.
   - ✓ Batch with DataLoader (GraphQL) or eager-load/`JOIN`/`WHERE id IN (...)` (ORM). Watch your query logs in dev.

10. **Inconsistent error shapes.**
    - ✗ One endpoint returns `{"error": "..."}`, another `{"message": "..."}`, a third a bare string. Clients can't write one error handler.
    - ✓ One error envelope everywhere: `{"error": {"code": "...", "message": "...", "details": [...]}}`.

11. **Blocking sync I/O in an async handler.**
    - ✗ `async def handler(): time.sleep(3)` or a blocking `requests.get(...)` / blocking DB driver inside an `async def`. It stalls the entire event loop, so *all* concurrent requests freeze.
    - ✓ Use async clients (`httpx.AsyncClient`, an async DB driver), or run blocking work in a threadpool (`await run_in_threadpool(...)`), or just make the handler a plain `def` so FastAPI runs it in a threadpool for you.

## On the job / interview angle

Backend/API questions are bread and butter for full-stack and backend interviews. Here are the ones to keep ready, with concrete answers.

**Q: What is REST and what are its core principles?**
REST (Representational State Transfer) is an architectural style for networked APIs. Core principles: **resources** identified by URLs (nouns, not verbs); a **uniform interface** using standard HTTP methods with consistent semantics; **statelessness** (each request is self-contained); **cacheability** (responses say whether they can be cached); a **client-server** separation; and **layered system** (clients can't tell if they're talking to the origin or a proxy/load balancer). HATEOAS (hypermedia links) is the sixth, most-ignored constraint.

**Q: What is idempotency, and which HTTP methods are idempotent?**
Idempotent means making the same request N times has the same effect as making it once. `GET`, `PUT`, `DELETE`, and `HEAD` are idempotent; `POST` and `PATCH` are not (necessarily). It matters for safe retries: a client can retry a timed-out `PUT` without fear, but a retried `POST` could create a duplicate, which is why we add an `Idempotency-Key` header to `POST`s that move money.

**Q: Explain the HTTP status code families and name some specifics.**
`1xx` informational; `2xx` success (`200 OK`, `201 Created`, `204 No Content`); `3xx` redirect (`301`, `304 Not Modified`); `4xx` client error (`400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found`, `409 Conflict`, `422 Unprocessable Entity`, `429 Too Many Requests`); `5xx` server error (`500 Internal Server Error`, `503 Service Unavailable`). Rule of thumb: `4xx` = the caller's fault, `5xx` = my fault.

**Q: PUT vs PATCH?**
`PUT` **replaces the entire resource**: you send the full representation, and any field you omit is reset/removed. It's idempotent. `PATCH` applies a **partial update**: you send only the fields you want to change. PATCH is the right call when you want to change one attribute (e.g. just an order's status) without resending the whole object. In FastAPI I model PATCH with an all-optional Pydantic model and `exclude_unset=True`.

**Q: What is statelessness and why does it help scaling?**
Stateless means the server keeps no per-client session in memory between requests; every request carries everything needed to process it (e.g. a bearer token). Because no instance "owns" a client, you can run many identical instances behind a load balancer and route any request to any instance, and add/remove instances freely. Session state, if needed, lives in a shared store (Redis/DB), not in process memory.

**Q: Offset vs cursor pagination?**
Offset (`?limit=20&offset=40`) is simple and supports "jump to page N," but it's slow on deep pages (the DB scans and discards the offset) and can skip/duplicate rows when data changes mid-paging. Cursor/keyset (`?limit=20&after=<cursor>`) encodes the last-seen key and translates to `WHERE id > :cursor ORDER BY id LIMIT N`, so it's fast at any depth (rides the index) and stable under concurrent writes. Use cursor for large/changing feeds; offset is fine for small, stable lists with a page picker.

**Q: REST vs GraphQL, when would you choose each?**
REST when the API is resource-shaped, public, or benefits from HTTP caching (caching by URL is easy), and when simplicity matters. GraphQL when clients have **diverse, evolving data needs** (mobile vs web), when you'd otherwise make a **waterfall of REST calls** to assemble one screen, or when over-/under-fetching is a real pain. GraphQL's costs: harder HTTP caching (usually one `POST /graphql`), the need for query depth/cost limits, and the N+1 problem requiring DataLoader. I default to REST and reach for GraphQL when the over-fetching pain is concrete.

**Q: What is the N+1 problem and how do you fix it?**
You fetch a list (1 query), then fetch a related entity for each item (N queries) — 1 + N round trips that scale with the result size. In GraphQL it shows up as a child resolver firing per-parent; in ORMs as lazy loading inside a loop. Fix with **batching**: a DataLoader that collects ids within a tick and issues one `WHERE id IN (...)`, or, in SQL/ORM land, an eager `JOIN` / `selectinload`. Two tables, two queries, not 101.

**Q: How do you validate input, and how do you version an API?**
Validation: declare a typed schema (Pydantic) with constraints (types, ranges, required fields, custom validators), reject bad input with `422` *before* business logic, and never trust the client. Versioning: most commonly **URL-based** (`/v1/users`) for explicitness; alternatively **header/media-type** (`Accept: application/vnd.nyx.v2+json`). Within a version make only additive, backward-compatible changes; breaking changes go in a new version, and you deprecate old ones with a timeline rather than yanking them.

Build a real `orders` API backed by the Postgres schema from Part 7, with proper status codes, pagination, filtering, and OpenAPI docs.

```python
from sqlalchemy import create_engine, text
from sqlalchemy.orm import sessionmaker
from fastapi import Depends

engine = create_engine(settings.database_url)
SessionLocal = sessionmaker(bind=engine)

def get_session():
    db = SessionLocal()
    try:
        yield db                 # injected into handlers; closed after the request
    finally:
        db.close()
```

**2. Endpoints** with pagination, filtering, and the right codes:

```python
from typing import Annotated, Literal

@app.get("/v1/orders")
def list_orders(
    db: Annotated[object, Depends(get_session)],
    limit: int = Query(20, ge=1, le=100),
    cursor: int | None = Query(None, description="last seen order id"),
    status_filter: Literal["paid", "refunded", "failed"] | None = Query(None, alias="status"),
):
    # Keyset pagination: fast at any depth (uses the PK index)
    sql = "SELECT id, user_id, amount_usd, status, created_at FROM orders WHERE TRUE"
    params: dict = {"limit": limit}
    if cursor is not None:
        sql += " AND id > :cursor"; params["cursor"] = cursor
    if status_filter:
        sql += " AND status = :st"; params["st"] = status_filter
    sql += " ORDER BY id ASC LIMIT :limit"
    rows = db.execute(text(sql), params).mappings().all()
    next_cursor = rows[-1]["id"] if len(rows) == limit else None
    return {"data": [dict(r) for r in rows], "next_cursor": next_cursor}

@app.post("/v1/orders", status_code=201)
def create_order(payload: OrderCreate, db: Annotated[object, Depends(get_session)]):
    # validate user exists → 422/404 if not; insert; return 201 + Location
    row = db.execute(
        text("""INSERT INTO orders (user_id, amount_usd, status)
                VALUES (:u, :a, 'paid') RETURNING id, user_id, amount_usd, status, created_at"""),
        {"u": payload.user_id, "a": payload.amount_usd},
    ).mappings().one()
    db.commit()
    return dict(row)
```

**3. Requirements to satisfy:**
- Correct status codes throughout (`201` on create with the new resource, `404` for missing, `422` for validation, `204` on delete).
- **Cursor pagination** with a `next_cursor` in the response so clients can page forever without `OFFSET` slowdown.
- **Filtering** by `status` (constrained to valid values via `Literal`, so invalid values 422 automatically).
- **OpenAPI docs** auto-generated: visit `/docs`, confirm every endpoint, model, and param is documented, then export the spec (`/openapi.json`) to hand to frontend teammates.
- A handful of `TestClient` tests covering the happy path and each error code.

**Deliverable:** a running service where `curl`-ing each endpoint returns the right code and shape, `/docs` is complete, and the frontend `RevenueCard` from Chapter 8.1 could fetch from it. That's a full vertical slice: DB (Part 7) → API (here) → UI (8.1).

## Mini-project 2: a paginated, filterable, versioned `/v1/users` API with idempotency and a structured error envelope

The first mini-project gave you Postgres-backed orders. This one you build **fully runnable in memory with tests**, so you can focus on the cross-cutting production concerns: a **versioned** path, **cursor pagination**, **filtering**, an **idempotency key on POST**, a **consistent error envelope**, and **TestClient tests** that prove each one. This is the shape every NYX/Anneava service ends up wanting.

**1. Models and a single error envelope.**

```python
# users_app.py
from fastapi import FastAPI, HTTPException, Header, Query, status, Request
from fastapi.responses import JSONResponse
from fastapi.exceptions import RequestValidationError
from pydantic import BaseModel, EmailStr, Field
from typing import Annotated, Literal
from uuid import UUID
import itertools, base64

app = FastAPI(title="Users API", version="1.0.0")

class UserCreate(BaseModel):
    name: str = Field(min_length=1, max_length=80)
    email: EmailStr
    role: Literal["admin", "member", "viewer"] = "member"

class User(UserCreate):
    id: int

# One error envelope for the whole service: {"error": {"code", "message", "details"}}
def error_body(code: str, message: str, details=None):
    return {"error": {"code": code, "message": message, "details": details or []}}

@app.exception_handler(HTTPException)
async def http_exc(request: Request, exc: HTTPException):
    return JSONResponse(status_code=exc.status_code,
                        content=error_body(f"http_{exc.status_code}", str(exc.detail)))

@app.exception_handler(RequestValidationError)
async def validation_exc(request: Request, exc: RequestValidationError):
    # reshape Pydantic's 422 into our envelope while keeping the field paths
    return JSONResponse(status_code=422,
                        content=error_body("validation_error", "Input failed validation",
                                           details=exc.errors()))
```

**2. Storage, cursor helpers, and the routes.**

```python
_users: dict[int, User] = {}
_ids = itertools.count(1)
_idempotency: dict[str, tuple[int, dict]] = {}

def encode_cursor(uid: int) -> str:
    return base64.urlsafe_b64encode(str(uid).encode()).decode()

def decode_cursor(c: str) -> int:
    return int(base64.urlsafe_b64decode(c.encode()).decode())

@app.post("/v1/users", status_code=status.HTTP_201_CREATED)
def create_user(
    payload: UserCreate,
    idempotency_key: Annotated[UUID | None, Header()] = None,
):
    if idempotency_key is not None and str(idempotency_key) in _idempotency:
        code, body = _idempotency[str(idempotency_key)]
        return JSONResponse(status_code=code, content=body)   # replay, no duplicate

    # reject duplicate emails with 409, in our envelope
    if any(u.email == payload.email for u in _users.values()):
        raise HTTPException(status.HTTP_409_CONFLICT, "email already exists")

    user = User(id=next(_ids), **payload.model_dump())
    _users[user.id] = user
    body = user.model_dump()
    if idempotency_key is not None:
        _idempotency[str(idempotency_key)] = (201, body)
    return body

@app.get("/v1/users")
def list_users(
    limit: int = Query(20, ge=1, le=100),
    cursor: str | None = Query(None, description="opaque cursor (last seen id)"),
    role: Literal["admin", "member", "viewer"] | None = None,   # filter
):
    rows = sorted(_users.values(), key=lambda u: u.id)
    if role is not None:
        rows = [u for u in rows if u.role == role]
    if cursor is not None:
        after = decode_cursor(cursor)
        rows = [u for u in rows if u.id > after]                # keyset: id > cursor
    page = rows[:limit]
    next_cursor = encode_cursor(page[-1].id) if len(page) == limit else None
    return {"data": [u.model_dump() for u in page], "next_cursor": next_cursor}

@app.get("/v1/users/{user_id}")
def get_user(user_id: int):
    if user_id not in _users:
        raise HTTPException(status.HTTP_404_NOT_FOUND, "user not found")
    return _users[user_id].model_dump()
```

```python
def test_404_in_envelope():

    assert r.status_code == 404 and r.json()["error"]["code"] == "http_404"
```

**5.**
```sql
SELECT id, type, created_at
FROM events
WHERE id > :c          -- keyset: everything after the last id we saw
ORDER BY id ASC        -- oldest first; rides the PK index
LIMIT 50;
```
The **next cursor** is the `id` of the last row returned (`rows[-1]["id"]`). If fewer than 50 rows come back, there's no next page — return a null cursor. (For the *first* page, omit the `WHERE id > :c` clause or pass a cursor of 0.)

**6.** The N+1: this `author` resolver runs **one query per parent** (per book/post), so listing N items fires N author queries plus the 1 to list the items. Fix with a DataLoader that batches the author ids into a single `WHERE id IN (...)`:
```python
from strawberry.dataloader import DataLoader

async def load_authors(ids: list[int]) -> list[dict]:
    rows = db.execute(text("SELECT id, name FROM authors WHERE id = ANY(:ids)"),
                      {"ids": ids}).mappings().all()
    by_id = {r["id"]: r for r in rows}
    return [by_id[i] for i in ids]        # same order as input ids - required!

author_loader = DataLoader(load_fn=load_authors)

@strawberry.field
async def author(self) -> Author:
    row = await author_loader.load(self.author_id)   # batched + deduped + cached
    return Author(id=row["id"], name=row["name"])
```
Result: 2 queries total regardless of N.

**7.**
```
GET    /posts/{post_id}/comments          → 200  (list, paginated)
POST   /posts/{post_id}/comments          → 201  (create, returns new comment + Location)
GET    /posts/{post_id}/comments/{id}     → 200  (read one)
PATCH  /posts/{post_id}/comments/{id}     → 200  (edit body - partial update)
DELETE /posts/{post_id}/comments/{id}     → 204  (delete, no body)
```
Comments are modeled as a sub-resource of a post; the verbs and statuses follow the table from Theory.

**8.** On the first request: the server checks key `K` in its idempotency store, finds nothing, inserts the charge, and **stores `K → (status, body)`**, ideally in the *same database transaction* as the insert. The response is lost. On the retry with `K`, the server finds `K` already recorded and replays the stored response without inserting again — one charge. Failure mode of the naive in-memory dict: if the server crashes (or the retry lands on a *different* instance behind the load balancer) between the INSERT and storing `K`, the mapping is gone, so the retry inserts a second charge. A DB-backed key (or a unique constraint on the key column) survives crashes and is shared across instances, so the duplicate is impossible.

**9.** Both use the index on `id`, but they use it differently. `WHERE id > :cursor` does an **index seek**: the B-tree jumps straight to the first key greater than the cursor and reads 20 rows — O(log n) to locate, then 20 reads, independent of how deep the page is. `OFFSET 100000` must still walk past 100,000 matching rows before it can return the next 20: the database can use the index for ordering, but it cannot skip the offset without counting through it, so the work grows linearly with the offset. Page 5,000 with offset means stepping over ~100,000 rows every single request; with a cursor it's the same tiny seek as page 1.

**10.** It freezes because `requests.get` is **blocking** I/O inside an `async def`. The event loop (single-threaded, see Chapter 8.1) is stuck waiting on that socket and cannot service *any* other concurrent request until it returns; one slow upstream stalls everyone. Two correct fixes:
```python
# Fix A: use an async HTTP client so the loop is free during the wait
import httpx
@app.get("/v1/fx")
async def fx_rate():
    async with httpx.AsyncClient() as c:
        resp = await c.get("https://api.example.com/usd-eur")
    return resp.json()

# Fix B: make it a plain `def` so FastAPI runs it in a threadpool
import requests
@app.get("/v1/fx")
def fx_rate():                      # no async → offloaded to a worker thread
    return requests.get("https://api.example.com/usd-eur").json()
```
(A third option: keep `async def` but offload the blocking call with `await fastapi.concurrency.run_in_threadpool(requests.get, url)`.)
