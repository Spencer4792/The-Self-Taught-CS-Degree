## 🌱 Start here - the one idea that unlocks the rest

If you only take *one* thing from this chapter, take this: **a variable in Python is a name tag, not a box.**

Picture a coat-check at a theater. The coat (a real object) hangs on a rack somewhere. You get a little ticket, a *name*, that points at that coat. If your friend takes a photo of your ticket number and now *also* holds a ticket for the same number, you both point at the *same coat*. If your friend uses their ticket to stuff something in the coat's pocket, you'll find it there too, because there was only ever one coat.

That's the whole trick. In Python:

```python
my_ticket = ["scarf"]      # a real list object hangs on the rack; my_ticket points at it
friend_ticket = my_ticket  # friend gets a ticket for the SAME coat (no new coat made)
friend_ticket.append("hat")
print(my_ticket)           # ['scarf', 'hat']  <- I see the hat too. Same coat!
```

**Why this matters:** almost every Python "gotcha", the famous mutable-default-argument bug, surprising shared lists between objects, "I changed `b` and `a` changed too?!", is the same misunderstanding wearing a different hat. Once you *see* names-as-tags, you stop being surprised, and you start predicting what code will do before you run it. That ability, reading code and knowing the answer in your head, is exactly what separates someone who *uses* Python from someone who *understands* it. Interviewers probe for it constantly.

Everything below is just zooming in on that picture and the small set of rules built on top of it. Don't rush. Run every snippet. If a result surprises you, that surprise is the lesson.

## 📐 Concept 1 - Names, objects, references

Here's the mental model that explains 80% of Python "gotchas."

**An object** is a blob of data that lives somewhere in memory. It has three things: an identity (its address, `id(x)`), a type (`type(x)`), and a value.

**A name** (what other languages call a variable) is *not* a box that holds a value. It's a label, a sticky note, that I stick onto an object. Assignment never copies a value; it just re-points the sticky note.

```python
a = [1, 2, 3]   # create a list object; stick the name "a" on it
b = a           # stick the name "b" on the SAME object. No copy!
b.append(4)
print(a)        # [1, 2, 3, 4]  -- "a" sees the change because it's the same object
print(a is b)   # True -- same identity
```

`is` asks "same object?" (identity). `==` asks "same value?" (equality). They are different questions and conflating them is a classic bug.

### Mutable vs. immutable

Some objects can be changed in place (mutable): `list`, `dict`, `set`, most custom objects. Some cannot (immutable): `int`, `float`, `str`, `tuple`, `frozenset`, `bytes`.

```python
x = 5
y = x
y += 1          # ints are immutable; y += 1 makes a NEW int object (6) and re-points y
print(x, y)     # 5 6  -- x is untouched
```

So `+=` on an immutable rebinds the name; `+=` on a mutable (like a list) mutates in place *and* rebinds to the same object. This is why `t = (1, [2]); t[1] += [3]` both works *and* raises a `TypeError`, the list is extended, but then Python tries to re-assign `t[1]` into the immutable tuple and fails. (Try it. It's a great party trick and a real lesson.)

### The mutable default argument bug

This one taught me more about the data model than any blog post. Default argument values are evaluated **once**, when the function is *defined*, not each time it's called. So a mutable default is shared across all calls.

```python
def add_item(item, basket=[]):   # BUG: that [] is created ONCE
    basket.append(item)
    return basket

print(add_item("apple"))   # ['apple']
print(add_item("banana"))  # ['apple', 'banana']  <- WAT. The same list persists.
```

The default list is an object created at definition time and stored on the function (`add_item.__defaults__`). Every call that doesn't pass `basket` reuses that one object. The fix is the canonical sentinel pattern:

```python
def add_item(item, basket=None):
    if basket is None:
        basket = []          # fresh list each call
    basket.append(item)
    return basket
```

The lesson generalizes: **anything that runs "once at definition time" and holds mutable state will surprise me.** Defaults, class attributes, module-level globals, same trap, same shape.

## 💻 Build it - proving the model

Let me write a tiny experiment harness so I *see* the model instead of taking my word for it.

```python
def show(label, obj):
    print(f"{label:>12}: id={id(obj):>16}  type={type(obj).__name__:<8}  value={obj!r}")

a = [1, 2, 3]
b = a
c = list(a)        # a real copy (new object, same values)

show("a", a)
show("b", b)
show("c", c)
print("a is b:", a is b)   # True  -> same object
print("a is c:", a is c)   # False -> different objects
print("a == c:", a == c)   # True  -> same value

# Small-int caching: CPython pre-makes ints -5..256, so identity surprises you
m, n = 256, 256
print("256 is 256:", m is n)   # True (cached)
m, n = 1000, 1000
print("1000 is 1000:", m is n) # often False -- DON'T rely on `is` for value equality
```

The 256-vs-1000 thing is an implementation detail (CPython interns small ints), and the takeaway is rule-shaped: **use `is` only for `None`, `True`, `False`, and genuine identity checks. Use `==` for value.**

## 📐 Concept 2 - Everything is an object

Functions, classes, modules, even types themselves are objects. That's not a slogan; it has cash value.

```python
def greet(name): return f"Hi {name}"

f = greet                 # functions are objects -> assign them to names
print(f("Spencer"))       # Hi Spencer
greet.tag = "a function"  # attach attributes to a function object
print(greet.tag)

funcs = [greet, str.upper, len]   # put them in lists
for fn in funcs:
    print(fn.__name__)

print(type(greet))        # <class 'function'>
print(type(int))          # <class 'type'>  -- even classes are objects (instances of `type`)
```

Because functions are first-class objects, I can pass them around, return them, and store them, which is the whole foundation for decorators and the strategy pattern later.

## 📐 Concept 3 - The data model (dunder methods)

This is the heart of the chapter. Python's syntax is mostly **sugar that calls double-underscore ("dunder") methods.** When I write `len(x)`, Python calls `x.__len__()`. When I write `a + b`, it calls `a.__add__(b)`. When I write `for i in x`, it calls `x.__iter__()`. The language defines the *grammar*; my objects define the *behavior* by implementing the protocol.

So "making my class feel Pythonic" = "implementing the right dunders." Let me build a class that grows up one dunder at a time.

```python
class Vector:
    def __init__(self, x, y):      # constructor: runs after the object is created
        self.x = x
        self.y = y

    def __repr__(self):            # what `repr(v)` and the REPL show -> aim for unambiguous
        return f"Vector({self.x!r}, {self.y!r})"

    def __str__(self):             # what `str(v)` / print() show -> aim for human-friendly
        return f"({self.x}, {self.y})"

    def __eq__(self, other):       # makes == work by value
        if not isinstance(other, Vector):
            return NotImplemented  # let Python try the other operand / fall back to identity
        return (self.x, self.y) == (other.x, other.y)

    def __hash__(self):            # required to put it in a set/dict key; must agree with __eq__
        return hash((self.x, self.y))

    def __add__(self, other):      # makes v1 + v2 work
        return Vector(self.x + other.x, self.y + other.y)

    def __abs__(self):             # makes abs(v) work -> magnitude
        return (self.x ** 2 + self.y ** 2) ** 0.5

    def __bool__(self):            # truthiness: `if v:` -> False only for the zero vector
        return bool(self.x or self.y)
```

Two rules I keep getting wrong, now nailed down:

1. **`__repr__` vs `__str__`.** `__repr__` is for *me* (debugging), ideally `eval(repr(v))` reconstructs the object. `__str__` is for the *user*. If I only define one, define `__repr__`; `str()` falls back to it.

2. **`__eq__` and `__hash__` travel together.** If two objects are equal, they must hash equal (so dicts/sets work). If I define `__eq__` and forget `__hash__`, Python sets `__hash__ = None` and the object becomes *unhashable*. Equal-but-different-hash silently breaks dict lookups, a brutal bug.

### `__getitem__`, `__len__`, `__contains__` - acting like a container

```python
class Deck:
    suits = "♠ ♥ ♦ ♣".split()
    ranks = [str(n) for n in range(2, 11)] + list("JQKA")

    def __init__(self):
        self._cards = [(r, s) for s in self.suits for r in self.ranks]

    def __len__(self):                 # len(deck)
        return len(self._cards)

    def __getitem__(self, position):   # deck[0], deck[-1], deck[12:15]  AND iteration!
        return self._cards[position]

    def __contains__(self, card):      # `card in deck` (optional; falls back to __getitem__)
        return card in self._cards

deck = Deck()
print(len(deck))         # 52
print(deck[0])           # ('2', '♠')
print(deck[-1])          # ('A', '♣')
print(deck[:3])          # slicing works because list slicing returns a list

# Surprise bonus: if __getitem__ accepts integer indices 0,1,2,..., the object is
# ITERABLE and supports `in` FOR FREE, because Python's old iteration protocol
# falls back to calling __getitem__(0), __getitem__(1), ... until IndexError.
for card in deck:
    pass
import random
print(random.choice(deck))   # random.choice only needs __len__ + __getitem__
```

That free iteration/`in`/`random.choice` is the data model paying off: by implementing two dunders, my object slots into the entire standard library that "speaks sequence."

## 📐 Concept 4 - Duck typing

> "If it walks like a duck and quacks like a duck, it's a duck."

Python rarely asks "are you of type X?" It asks "can you *do* the thing I need?" `len(x)` doesn't check `isinstance(x, list)`; it checks "do you have `__len__`?" This is duck typing, and it's *why* the dunder protocols matter: my class doesn't have to inherit from `list` to be list-like, it just has to implement the methods.

```python
def total_length(things):
    return sum(len(t) for t in things)   # works on str, list, dict, my Deck, anything with __len__

print(total_length(["abc", [1, 2], {"a": 1}]))   # 3 + 2 + 1 = 6
```

The practical guideline: **prefer "try it and handle the exception" (EAFP, Easier to Ask Forgiveness than Permission) over "check the type first" (LBYL, Look Before You Leap).** It's more Pythonic and avoids race conditions.

```python
# LBYL (less Pythonic)
if hasattr(obj, "read"):
    data = obj.read()

# EAFP (more Pythonic)
try:
    data = obj.read()
except AttributeError:
    data = str(obj)
```

When I *do* need a type-ish check that respects duck typing, reach for `collections.abc` (e.g. `isinstance(x, collections.abc.Iterable)`), which checks for the *protocol*, not a concrete class.

## 📐 Concept 5 - OOP done properly

### Classes & instances

A class is a factory and a namespace. `self` is just the first argument every method receives, the instance it's operating on. Nothing magic; if I write `Deck.__len__(deck)` it's the same as `deck.__len__()`.

**Class attributes vs instance attributes** (a real trap, same family as the mutable-default bug):

```python
class Dog:
    tricks = []          # CLASS attribute -> shared by ALL instances!
    def __init__(self, name):
        self.name = name # INSTANCE attribute -> unique per dog

a, b = Dog("Rex"), Dog("Fido")
a.tricks.append("roll")
print(b.tricks)          # ['roll']  <- shared list bug, again

# Fix: instance-level mutable state goes in __init__
class Dog:
    def __init__(self, name):
        self.name = name
        self.tricks = []  # each dog gets its own list
```

### Inheritance and `super()`

```python
class Animal:
    def __init__(self, name):
        self.name = name
    def speak(self):
        raise NotImplementedError    # "abstract" - subclasses must override

class Dog(Animal):
    def speak(self):
        return f"{self.name} says woof"

class Puppy(Dog):
    def __init__(self, name, age):
        super().__init__(name)       # call the parent's __init__; don't re-do its work
        self.age = age
```

`super()` doesn't literally mean "my parent", it means "the next class in the MRO" (see below). That distinction matters with multiple inheritance.

### Composition over inheritance

Inheritance says "*is-a*"; composition says "*has-a*." The industry hard-won lesson: deep inheritance trees become rigid and confusing. Prefer giving an object the *pieces* it needs.

```python
# Inheritance (fragile if Car needs to swap engines, or "is-a" is a lie)
class Engine:
    def start(self): return "vroom"

# Composition (flexible): a Car HAS an Engine, can swap it, can mock it in tests
class Car:
    def __init__(self, engine):
        self.engine = engine          # injected dependency
    def start(self):
        return self.engine.start()

class ElectricEngine:
    def start(self): return "hum"

print(Car(Engine()).start())          # vroom
print(Car(ElectricEngine()).start())  # hum  -- no new Car subclass needed
```

My rule of thumb: reach for inheritance only when there's a genuine "is-a" relationship *and* I want polymorphism; otherwise compose. It makes testing far easier (dependency injection).

### MRO (Method Resolution Order)

With multiple inheritance, which parent's method wins? Python uses the **C3 linearization** to compute a consistent order, viewable via `.__mro__` or `.mro()`.

```python
class A:
    def who(self): return "A"
class B(A):
    def who(self): return "B"
class C(A):
    def who(self): return "C"
class D(B, C):   # diamond
    pass

print([cls.__name__ for cls in D.__mro__])   # ['D', 'B', 'C', 'A', 'object']
print(D().who())                              # "B"  -- first match along the MRO
```

`super()` walks this exact order, which is why cooperative multiple inheritance (every class calling `super().__init__()`) works: each `super()` hands off to the *next* class in the linearized chain, not to a fixed parent.

### `@property` - computed attributes with no API change

```python
class Temperature:
    def __init__(self, celsius=0):
        self._celsius = celsius

    @property
    def celsius(self):               # access like an attribute: t.celsius
        return self._celsius

    @celsius.setter
    def celsius(self, value):        # but run validation on assignment: t.celsius = -300
        if value < -273.15:
            raise ValueError("Below absolute zero!")
        self._celsius = value

    @property
    def fahrenheit(self):            # derived, read-only
        return self._celsius * 9 / 5 + 32

t = Temperature(25)
print(t.fahrenheit)   # 77.0
t.celsius = 30        # goes through the setter (validation runs)
# t.celsius = -300    # ValueError
```

`@property` lets me start with a plain attribute and *later* add validation or computation without changing how callers use the class. That's encapsulation that doesn't punish me upfront.

### `classmethod` vs `staticmethod`

```python
class Pizza:
    def __init__(self, ingredients):
        self.ingredients = ingredients

    @classmethod                     # receives the CLASS (cls), great for alternative constructors
    def margherita(cls):
        return cls(["mozzarella", "tomatoes"])   # cls => works correctly for subclasses too

    @staticmethod                    # receives nothing special; just a namespaced helper
    def is_vegetarian(ingredients):
        return "pepperoni" not in ingredients

p = Pizza.margherita()               # named constructor - cleaner than Pizza(["...","..."])
print(Pizza.is_vegetarian(p.ingredients))
```

- `classmethod`: factory/alternative constructors (`dict.fromkeys`, `datetime.now`).
- `staticmethod`: a function that logically belongs to the class but needs no instance/class state.

### `dataclasses` - boilerplate killer

Writing `__init__`, `__repr__`, `__eq__` by hand for a "bag of fields" is tedious. `@dataclass` generates them.

```python
from dataclasses import dataclass, field

@dataclass(frozen=True, order=True)   # frozen -> immutable & hashable; order -> < > comparisons
class Point:
    x: int
    y: int
    label: str = "origin"             # default value
    tags: list = field(default_factory=list)   # mutable default done RIGHT (no shared-list bug)

p = Point(1, 2)
print(p)                # Point(x=1, y=2, label='origin', tags=[])
print(p == Point(1, 2)) # True -- __eq__ generated for free
print(sorted([Point(3, 0), Point(1, 9)]))  # works because order=True
```

Note `field(default_factory=list)`, the dataclass machinery refuses a bare mutable default precisely *because* of the bug from Concept 1. The language is teaching me the lesson by enforcing it.

## 📐 Concept 6 - Iterators & generators

This is where "lazy evaluation" stops being a buzzword.

### The iterator protocol, built by hand

Two dunders define it:
- `__iter__(self)` returns an *iterator* (often `self`).
- `__next__(self)` returns the next value, or raises `StopIteration` when exhausted.

A `for` loop is just sugar for: get an iterator via `iter(obj)`, then call `next()` repeatedly until `StopIteration`.

```python
class CountUp:
    """Iterator that yields 0, 1, ..., stop-1 - built from scratch."""
    def __init__(self, stop):
        self.stop = stop
        self.current = 0

    def __iter__(self):
        return self                      # I am my own iterator

    def __next__(self):
        if self.current >= self.stop:
            raise StopIteration          # the signal that ends the for-loop
        value = self.current
        self.current += 1
        return value

for n in CountUp(3):
    print(n)         # 0, 1, 2

# Manually, to see the machinery:
it = iter(CountUp(2))
print(next(it))      # 0
print(next(it))      # 1
# print(next(it))    # raises StopIteration
```

Notice the iterator is **stateful and single-use**, once exhausted, it's done. That's why an *iterable* (like a list) hands back a *fresh* iterator each time you loop, but a generator can only be looped once.

### The generator version - same behavior, a fraction of the code

A generator function is any function with `yield`. Calling it doesn't run the body; it returns a generator object. Each `next()` runs to the next `yield`, hands back that value, and **freezes the function's state** until the next `next()`.

```python
def count_up(stop):
    current = 0
    while current < stop:
        yield current        # pause here, return `current`, remember where we were
        current += 1
    # falling off the end raises StopIteration automatically

for n in count_up(3):
    print(n)     # 0, 1, 2
```

Same result, no class, no manual `StopIteration`, no explicit state variables, `yield` handles all of it. This is why generators are the idiomatic way to make iterators.

### Lazy evaluation - why I care

Generators produce values **on demand**, so they use O(1) memory and can be infinite. A list materializes everything up front.

```python
def naturals():           # INFINITE - impossible as a list
    n = 0
    while True:
        yield n
        n += 1

import itertools
print(list(itertools.islice(naturals(), 5)))   # [0, 1, 2, 3, 4] -- take only what I need

# Reading a 10GB log line-by-line uses ~one line of RAM:
def read_lines(path):
    with open(path) as f:
        for line in f:    # file objects are already lazy iterators
            yield line.rstrip("\n")
```

### Generator pipelines

Because each stage is lazy, I can chain generators into a pipeline that streams data through with tiny memory use, like Unix pipes (`cat | grep | wc`).

```python
def read(path):
    with open(path) as f:
        yield from f                       # yield from = re-yield every item of an iterable

def parse_ints(lines):
    for line in lines:
        line = line.strip()
        if line:
            yield int(line)

def running_total(nums):
    total = 0
    for n in nums:
        total += n
        yield total

# Nothing runs until I iterate the final stage. Data flows one item at a time.
# pipeline = running_total(parse_ints(read("nums.txt")))
# for t in pipeline: print(t)
```

A **generator expression** is the inline version: `(x*x for x in range(10))`. Same laziness as `[x*x for x in range(10)]` (a list comp) but without building the list. Use it whenever I'm just going to feed the result into `sum()`, `max()`, `any()`, etc., no need to materialize.

## 📐 Concept 7 - Decorators, built from scratch

A decorator is "a function that takes a function and returns a (usually enhanced) function." To build one I first need closures.

### Step 1: closures

A closure is a function that remembers variables from the scope where it was *defined*, even after that scope has returned.

```python
def make_multiplier(factor):
    def multiply(n):          # `multiply` closes over `factor`
        return n * factor     # `factor` is remembered after make_multiplier returns
    return multiply

double = make_multiplier(2)
triple = make_multiplier(3)
print(double(10), triple(10))   # 20 30
print(double.__closure__[0].cell_contents)  # 2 -- the captured value, made visible
```

### Step 2: a timing decorator

```python
import time

def timed(func):                       # takes a function
    def wrapper(*args, **kwargs):      # the replacement function (accepts any args)
        start = time.perf_counter()
        result = func(*args, **kwargs) # call the original
        elapsed = time.perf_counter() - start
        print(f"{func.__name__} took {elapsed:.6f}s")
        return result                  # don't forget to pass the result through!
    return wrapper                     # return the replacement

@timed                                  # sugar for: slow_square = timed(slow_square)
def slow_square(n):
    time.sleep(0.01)
    return n * n

print(slow_square(5))   # prints timing, then 25
```

`@timed` above the function is *exactly* `slow_square = timed(slow_square)`. The decorator runs once at definition time, replacing the name with `wrapper`.

### Step 3: a decorator that takes arguments

This needs one more layer, a "decorator factory" that returns a decorator.

```python
import functools

def retry(times=3, delay=0.0):          # the FACTORY: takes config, returns a decorator
    def decorator(func):                # the actual decorator: takes the function
        @functools.wraps(func)          # <-- copies __name__, __doc__ from func to wrapper
        def wrapper(*args, **kwargs):
            last_exc = None
            for attempt in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except Exception as e:
                    last_exc = e
                    print(f"attempt {attempt} failed: {e}")
                    time.sleep(delay)
            raise last_exc              # all attempts failed -> re-raise the last error
        return wrapper
    return decorator

@retry(times=3, delay=0.1)              # call the factory -> get a decorator -> apply it
def flaky():
    import random
    if random.random() < 0.7:
        raise ValueError("transient glitch")
    return "success"
```

### Step 4: why `functools.wraps`

Without it, the decorated function's identity gets clobbered:

```python
def plain_decorator(func):
    def wrapper(*a, **k):
        return func(*a, **k)
    return wrapper

@plain_decorator
def hello():
    """Say hi."""
    ...

print(hello.__name__)   # 'wrapper'  <- WRONG, lost the real name
print(hello.__doc__)    # None       <- lost the docstring
```

`@functools.wraps(func)` on the wrapper copies `__name__`, `__doc__`, `__module__`, etc. from the original, so debuggers, `help()`, and introspection still work. **Always use it** in real decorators.

## 📐 Concept 8 - Context managers, built two ways

`with` guarantees setup/teardown even if the body raises. The protocol is `__enter__` (runs on entry, its return value is bound by `as`) and `__exit__` (runs on exit, *always*, normal or exception).

### As a class

```python
import time

class Timer:
    def __enter__(self):
        self.start = time.perf_counter()
        return self                      # bound to the `as` variable

    def __exit__(self, exc_type, exc_val, exc_tb):
        self.elapsed = time.perf_counter() - self.start
        print(f"Block took {self.elapsed:.4f}s")
        return False                     # False/None -> propagate any exception; True -> swallow it

with Timer() as t:
    sum(range(1_000_000))
# "Block took ...s" prints even if the body had raised
```

`__exit__` receives the exception info (or three `None`s if all went well). Returning `True` suppresses the exception, powerful but use sparingly.

### With `contextlib` (the lazy, elegant way)

`@contextmanager` turns a generator into a context manager: everything before `yield` is "enter," everything after is "exit."

```python
from contextlib import contextmanager

@contextmanager
def timer():
    start = time.perf_counter()
    try:
        yield                            # the `with` body runs HERE; yielded value -> `as` var
    finally:
        print(f"Block took {time.perf_counter() - start:.4f}s")   # finally => runs even on error

with timer():
    sum(range(1_000_000))
```

The `try/finally` is what guarantees teardown on exceptions, it's the generator-style equivalent of `__exit__` always running. This is my go-to for quick, single-use managers (temporarily change a setting, open/close a resource, suppress an error).

## 📐 Concept 9 - Comprehensions, `*args`/`**kwargs`, exceptions, type hints

### Comprehensions

Declarative "build a collection" syntax. Faster and clearer than manual loops *for simple transforms*.

```python
squares   = [x*x for x in range(10)]                 # list
evens     = [x for x in range(20) if x % 2 == 0]     # with filter
grid      = [(r, c) for r in range(3) for c in range(3)]  # nested loops
by_len    = {w: len(w) for w in ["hi", "world"]}     # dict comprehension
uniq      = {x % 3 for x in range(10)}               # set comprehension
gen       = (x*x for x in range(10))                 # generator (lazy, parens)
```

Rule: if it doesn't fit on one readable line or needs side effects, use a real loop.

### `*args` / `**kwargs`

`*args` collects extra positional args into a tuple; `**kwargs` collects extra keyword args into a dict. In a *call*, `*` and `**` unpack.

```python
def f(*args, **kwargs):
    print(args)      # tuple of positionals
    print(kwargs)    # dict of keywords

f(1, 2, a=3, b=4)    # (1, 2)  /  {'a': 3, 'b': 4}

nums = [1, 2, 3]
print(max(*nums))    # unpack list as positional args -> max(1, 2, 3)
config = {"sep": "-", "end": "!\n"}
print("a", "b", **config)   # unpack dict as keyword args
```

This is exactly why decorator wrappers use `def wrapper(*args, **kwargs)`, to forward *any* signature transparently.

### Exceptions & custom exception classes

```python
try:
    risky()
except (ValueError, KeyError) as e:    # catch specific types; bind to e
    print("expected problem:", e)
except Exception as e:
    print("unexpected:", e)
    raise                              # re-raise after logging
else:
    print("ran with no exception")     # only if try block succeeded
finally:
    print("always runs (cleanup)")     # close files, release locks
```

Custom exceptions = a vocabulary for *my* errors. Make a base class so callers can catch the whole family:

```python
class OrderError(Exception):
    """Base for all order-related errors."""

class OutOfStock(OrderError):
    def __init__(self, item):
        super().__init__(f"{item} is out of stock")
        self.item = item                # attach structured data for the handler

try:
    raise OutOfStock("widget")
except OrderError as e:                 # catches OutOfStock and any future sibling
    print(e, "->", e.item)
```

Guidelines I'm committing to: catch *specific* exceptions (never bare `except:`), raise meaningful types, attach data to the exception object, and use `raise ... from e` to preserve the cause chain.

### Type hints (and why they help)

Hints are annotations; Python doesn't enforce them at runtime, but tools (mypy, pyright, my IDE) check them statically and catch whole classes of bugs *before* I run the code.

```python
from typing import Optional

def greet(name: str, times: int = 1) -> str:
    return (f"Hi {name}! " * times).strip()

def find_user(uid: int) -> Optional[dict]:   # Optional[dict] = dict | None
    ...

# Modern syntax (3.10+): dict | None instead of Optional[dict]; list[int] instead of List[int]
def total(xs: list[int]) -> int:
    return sum(xs)
```

Why they earn their keep: (1) editor autocomplete and refactoring get smarter; (2) `mypy myfile.py` flags `greet(42)` as a type error without executing; (3) they're documentation that can't drift out of date because the checker enforces it. The cost is a little verbosity. For anything beyond a throwaway script, worth it.

## 🧪 Mini-project - a retry decorator library (data model, all together)

Let me build something I'd actually reuse: a small, robust `@retry` decorator with exponential backoff, exception filtering, jitter, and a callback hook. It exercises closures, decorator factories, `functools.wraps`, `*args/**kwargs`, custom exceptions, type hints, and a context manager, the whole chapter in one file.

```python
"""retrylib.py - a tiny, production-ish retry decorator.

Demonstrates: decorator factories, closures, functools.wraps, *args/**kwargs,
custom exceptions, type hints, and a context manager for timing.
"""
from __future__ import annotations

import functools
import random
import time
from contextlib import contextmanager
from typing import Callable, Iterator, Type, TypeVar

F = TypeVar("F", bound=Callable[..., object])


class RetryError(Exception):
    """Raised when all retry attempts are exhausted."""
    def __init__(self, func_name: str, attempts: int, last_exc: BaseException):
        super().__init__(f"{func_name} failed after {attempts} attempts: {last_exc!r}")
        self.func_name = func_name
        self.attempts = attempts
        self.last_exc = last_exc          # structured data for the handler


@contextmanager
def _attempt_timer(label: str) -> Iterator[None]:
    """Context manager (generator style) that prints how long an attempt took."""
    start = time.perf_counter()
    try:
        yield
    finally:
        print(f"  [{label}] {time.perf_counter() - start:.4f}s")


def retry(
    times: int = 3,
    *,                                    # force the rest to be keyword-only -> readable calls
    exceptions: tuple[Type[BaseException], ...] = (Exception,),
    base_delay: float = 0.1,
    backoff: float = 2.0,                 # delay *= backoff each attempt (exponential)
    jitter: float = 0.0,                  # add up to `jitter` random seconds to avoid thundering herd
    on_retry: Callable[[int, BaseException], None] | None = None,
) -> Callable[[F], F]:
    """Decorator FACTORY. Returns a decorator that retries `func` on the given exceptions."""
    def decorator(func: F) -> F:
        @functools.wraps(func)            # preserve name/docstring of the wrapped function
        def wrapper(*args: object, **kwargs: object) -> object:
            delay = base_delay
            last_exc: BaseException | None = None
            for attempt in range(1, times + 1):
                try:
                    with _attempt_timer(f"{func.__name__} #{attempt}"):
                        return func(*args, **kwargs)     # success -> return immediately
                except exceptions as e:                  # only catch the requested types
                    last_exc = e
                    if on_retry is not None:
                        on_retry(attempt, e)             # callback hook (logging, metrics)
                    if attempt < times:
                        sleep_for = delay + random.uniform(0, jitter)
                        time.sleep(sleep_for)
                        delay *= backoff                 # exponential growth
            # All attempts failed:
            raise RetryError(func.__name__, times, last_exc)  # type: ignore[arg-type]
        return wrapper  # type: ignore[return-value]
    return decorator


# ---------------------------------------------------------------------------
# Demo / self-test
# ---------------------------------------------------------------------------
if __name__ == "__main__":
    attempts_seen = 0

    def log_retry(attempt: int, exc: BaseException) -> None:
        print(f"  retry #{attempt} because: {exc}")

    @retry(times=4, base_delay=0.05, backoff=2.0, jitter=0.02,
           exceptions=(ValueError,), on_retry=log_retry)
    def flaky_network_call() -> str:
        """Succeeds on the 3rd try; raises ValueError before that."""
        global attempts_seen
        attempts_seen += 1
        if attempts_seen < 3:
            raise ValueError(f"timeout (call {attempts_seen})")
        return "200 OK"

    print("Result:", flaky_network_call())   # should succeed on attempt 3
    print("wraps check -> name:", flaky_network_call.__name__)   # 'flaky_network_call', not 'wrapper'
    print("wraps check -> doc :", flaky_network_call.__doc__)

    # Now prove exhaustion raises our custom error
    @retry(times=2, base_delay=0.01, exceptions=(KeyError,))
    def always_fails():
        raise KeyError("nope")

    try:
        always_fails()
    except RetryError as e:
        print("Caught RetryError ->", e)
        print("  attempts:", e.attempts, "| last:", repr(e.last_exc))
```

Run it:

```bash
python retrylib.py
```

What I want to *notice* in this project, because each is a chapter concept earning its place:
- `retry(...)` is a **factory** (Concept 7, step 3): config in, decorator out.
- `wrapper(*args, **kwargs)` forwards any signature (`*args/**kwargs`, Concept 9).
- `@functools.wraps(func)` keeps the real name/docstring (Concept 7, step 4), the self-test proves it.
- `RetryError` is a **custom exception** carrying structured data (Concept 9).
- `_attempt_timer` is a **context manager** built with `@contextmanager` (Concept 8), and its `finally` guarantees the timing prints even when the attempt raises.
- Type hints throughout would let `mypy retrylib.py` catch a wrong-typed call before runtime (Concept 9).

That's the whole point of the data model: small, composable protocols that snap together. Once I see them as protocols rather than memorized syntax, I can build the features myself instead of importing magic.

## 🧪 Mini-project 2 - a tiny immutable `Money` type (the data model for real)

The retry library above showed decorators/closures/exceptions in one file. This second mini-project pins down the *object* half of the chapter: building a class that behaves like a real built-in by implementing the right dunders. I'll make a `Money` value type, the kind of thing you'd genuinely want in any app that touches dollars, because using `float` for money is a classic, costly bug (0.1 + 0.2 != 0.3 in floating point).

Goals it must satisfy: store money exactly (integer cents, no float drift), print nicely, compare and sort, add/subtract, multiply by a quantity, be usable as a dict key, and refuse nonsense (can't add USD to EUR).

```python
"""money.py - an exact, immutable Money value type built from the data model.

Demonstrates: __init__/__repr__/__str__, __eq__/__hash__ together, ordering
dunders, arithmetic dunders, a classmethod alternative constructor, and raising
clear custom errors. Money is stored as integer cents so there is NO float drift.
"""
from __future__ import annotations

from dataclasses import dataclass


class CurrencyMismatch(Exception):
    """Raised when two Money values of different currencies are combined."""


@dataclass(frozen=True, order=True)   # frozen -> immutable & hashable; order -> < <= > >=
class Money:
    cents: int                         # store EXACT integer cents, never a float
    currency: str = "USD"

    @classmethod
    def of(cls, dollars: float, currency: str = "USD") -> "Money":
        """Alternative constructor: Money.of(19.99) -> 1999 cents. Rounds correctly."""
        return cls(round(dollars * 100), currency)

    # --- display -------------------------------------------------------------
    def __str__(self) -> str:          # human-friendly: "$19.99"
        sign = "-" if self.cents < 0 else ""
        whole, frac = divmod(abs(self.cents), 100)
        symbol = {"USD": "$", "EUR": "€", "GBP": "£"}.get(self.currency, self.currency + " ")
        return f"{sign}{symbol}{whole}.{frac:02d}"

    # __repr__ is generated by @dataclass: Money(cents=1999, currency='USD')

    # --- a guard the arithmetic methods share --------------------------------
    def _check(self, other: "Money") -> None:
        if self.currency != other.currency:
            raise CurrencyMismatch(f"cannot combine {self.currency} and {other.currency}")

    # --- arithmetic ----------------------------------------------------------
    def __add__(self, other: "Money") -> "Money":
        self._check(other)
        return Money(self.cents + other.cents, self.currency)

    def __sub__(self, other: "Money") -> "Money":
        self._check(other)
        return Money(self.cents - other.cents, self.currency)

    def __mul__(self, qty: int) -> "Money":     # price * quantity
        return Money(self.cents * qty, self.currency)

    __rmul__ = __mul__                          # so 3 * price also works

    def __neg__(self) -> "Money":               # makes -price work (e.g. refunds)
        return Money(-self.cents, self.currency)


if __name__ == "__main__":
    coffee = Money.of(4.50)
    bagel = Money.of(2.25)
    print("coffee:", coffee)                 # $4.50
    print("repr  :", repr(coffee))           # Money(cents=450, currency='USD')
    print("total :", coffee + bagel)         # $6.75  (__add__)
    print("triple:", coffee * 3)             # $13.50 (__mul__)
    print("refund:", -coffee)                # -$4.50 (__neg__)

    # Equality and hashing travel together (frozen dataclass gives both):
    print("equal :", Money.of(4.50) == coffee)                # True
    basket = {coffee: 1, bagel: 2}                            # usable as dict KEYS
    print("basket:", {str(k): v for k, v in basket.items()})

    # Ordering for free (order=True): sort a price list
    prices = [Money.of(9.99), Money.of(0.99), Money.of(4.50)]
    print("sorted:", [str(p) for p in sorted(prices)])        # cheapest first

    # The guard stops a real bug:
    try:
        print(coffee + Money.of(1.00, "EUR"))
    except CurrencyMismatch as e:
        print("blocked:", e)                 # blocked: cannot combine USD and EUR
```

Run it with `python money.py`. What I want to notice, each is a chapter concept doing real work:

- **Integer cents** sidesteps float drift entirely. This is the actual lesson banks learned the hard way; "don't use float for money" is a real interview answer.
- `@dataclass(frozen=True)` generates `__init__`, `__repr__`, `__eq__`, **and** `__hash__` correctly together (Concept 5), so `Money` is safe as a dict key.
- `order=True` generates the comparison dunders, so `sorted()` just works (Concept 3, the data model).
- `__rmul__` covers `3 * price` as well as `price * 3`, Python tries the left operand's `__mul__` first, then the right operand's `__rmul__`.
- The shared `_check` guard raising a **custom exception** (Concept 9) turns a silent currency mix-up into a loud, debuggable error.

## ⚠️ Common mistakes

These are the traps that bite real people (including past me) the most. Read them now; you'll recognize the symptoms later.

- **Confusing `is` with `==`.** `is` asks "the exact same object?"; `==` asks "the same value?" Use `is` *only* for `None`, `True`, `False`. `if x == None:` is a code smell, write `if x is None:`. And never use `is` to compare numbers or strings; small-int/string interning makes it *seem* to work, then it silently fails for `1000 is 1000`.
- **The mutable default argument.** `def f(x, acc=[]):` shares one list across all calls. Use `acc=None` then `if acc is None: acc = []`. (See Concept 1.) The same shape bites you with class-level mutable attributes (`tricks = []` shared across all instances).
- **Defining `__eq__` but forgetting `__hash__`.** Python then sets `__hash__ = None` and your object becomes unhashable, it explodes the moment you put it in a `set` or use it as a dict key. They must agree: equal objects must hash equal.
- **A bare `except:`.** It swallows *everything*, including `KeyboardInterrupt` and `SystemExit`, hiding bugs and making the program impossible to stop. Catch the specific exception you expect; at minimum use `except Exception:`.
- **Forgetting `functools.wraps` in a decorator.** Your wrapped function loses its name and docstring; `help()`, debuggers, and some frameworks (pytest, Flask routing) break. Always `@functools.wraps(func)` on the wrapper.
- **Iterating a generator twice.** A generator is single-use, once exhausted, looping it again yields nothing, with no error. If you need to iterate more than once, materialize it into a `list` first (and accept the memory cost) or rebuild the generator.
- **Mutating a list while looping over it.** Removing items mid-loop skips elements. Iterate a copy (`for x in items[:]:`) or build a new list with a comprehension.
- **Catching the result you forgot to return.** In a decorator wrapper, forgetting `return func(...)` makes every decorated function return `None`. Easy to miss; always pass the result through.

import functools
def memoize(func):
    cache = {}
    hits = misses = 0
    @functools.wraps(func)
    def wrapper(*args):
        nonlocal hits, misses
        if args in cache:
            hits += 1
            return cache[args]
        misses += 1
        result = func(*args)
        cache[args] = result
        return result
    wrapper.cache_clear = lambda: cache.clear()
    wrapper.cache_info = lambda: {"hits": hits, "misses": misses, "size": len(cache)}
    return wrapper

@memoize
def slow_fib(n):
    return n if n < 2 else slow_fib(n - 1) + slow_fib(n - 2)

print(slow_fib(30))          # fast despite naive recursion, thanks to the cache
print(slow_fib.cache_info()) # mostly hits
slow_fib.cache_clear()

# (not as wrapper attributes) is why I read/write them via nonlocal here.
