# Chapter 6.1 - The Internet & the TCP/IP Stack

> Goal: stop treating "the network" as a magic cloud. By the end you'll be able to draw the four-layer TCP/IP stack and map it to OSI, explain IP addressing, subnets, and NAT, describe how TCP's handshake and acknowledgments build reliability on top of unreliable IP, know when to reach for UDP instead, and prove it with sockets: a TCP echo server, a UDP example, and a multi-client chat server with `selectors`.

The internet is the biggest machine humans have ever built, and it works because of layering: each layer does one job and trusts the layer below to do its own, so nobody has to understand the whole thing at once. Let's build that stack from the bottom up and then use it through sockets, because writing socket code is what makes the abstractions feel real.

## Start here: the postal system analogy

Before the acronyms, here's a picture worth keeping: the internet is a postal system, and the layered stack is the division of labor that gets a letter from your desk to someone else's.

- You write a letter (the actual message, your HTTP request). You don't think about trucks or sorting facilities; you just write what you want to say. That's the **application layer**.
- You put the letter in an envelope with a full address: house number, street, city, country. The postal network uses that address to route it across the world without you knowing the route. That's **IP** (the internet layer): host-to-host addressing and routing.
- You might want guaranteed, in-order delivery with a receipt — registered mail, where lost letters get re-sent and pages arrive in order. That extra reliability service is **TCP**. Or you might just drop a postcard in the box: cheap, fast, no guarantee it arrives. That's **UDP**. (Both ride the same postal roads.)
- The local mail carrier who walks the letter the last block to the right mailbox is the **link layer**: local delivery over the physical wire or Wi-Fi using hardware (MAC) addresses.

Each layer trusts the one below. You write a letter without knowing about trucks. TCP guarantees delivery without knowing about roads. IP routes without knowing what's inside the envelope. Because no layer depends on the internals of another, any one of them can be swapped — a new truck, a new road — without rewriting the rest.

**Why this matters:** essentially every modern job touches the network — web apps, APIs, microservices, cloud, mobile. "It works on my machine but not in production" is usually a networking issue: a firewall, a DNS problem, a port not open, a timeout. When you understand the stack, those stop being mysteries and become a checklist: is the name resolving? is the route reachable? is the port listening? The rest of this chapter makes the postal picture precise, and then we build the post office with sockets.

## The layered model (and mapping to OSI)

A message from your laptop to a server passes down through layers on your side, across the wire, and up through layers on theirs. Each layer adds its own header (encapsulation) and the matching layer on the other end reads it.

```text
TCP/IP (4 layers)        Does what                          OSI (7 layers)
─────────────────────────────────────────────────────────────────────────────
APPLICATION      HTTP, DNS, SSH - what the app actually     Application
                 wants to say                               Presentation
                                                            Session
TRANSPORT        TCP / UDP - process-to-process delivery,   Transport
                 (TCP adds reliability); ports
INTERNET         IP - addressing & routing host-to-host     Network
                 across networks
LINK             Ethernet/Wi-Fi - frames on the local       Data Link
                 wire; MAC addresses                        Physical
```

Encapsulation in one picture:

```text
[ Ethernet header [ IP header [ TCP header [ HTTP data ] ] ] ]
   link             internet     transport     application
```

As your HTTP request goes out: the app hands data to TCP (which adds a TCP header: ports, sequence numbers), which hands it to IP (source/dest IP addresses), which hands it to the link layer (MAC addresses for the next hop). The receiver peels these off in reverse. IP doesn't know or care that it's carrying TCP; TCP doesn't know it's carrying HTTP. That separation is why we could add HTTPS, or swap Wi-Fi for Ethernet, without rewriting the internet.

OSI's 7 layers are the academic reference model; TCP/IP's 4 layers are what's actually deployed. OSI's session/presentation layers mostly fold into TCP/IP's application layer in practice.

## IP addressing: IPv4, IPv6, subnets/CIDR, public vs private, NAT

An **IP address** identifies a host on a network. **IPv4** is 32 bits, written as four dotted decimals: `192.168.1.10` (each octet 0-255 → ~4.3 billion addresses, which we ran out of). **IPv6** is 128 bits, written in hex groups: `2001:0db8:85a3::8a2e:0370:7334`, astronomically more addresses, designed to outlast the shortage.

An address splits into a **network part** and a **host part**. **CIDR notation** (`/n`) says how many leading bits are the network:

```text
192.168.1.0/24
            └── /24 = first 24 bits are the network → 192.168.1.x
                      last 8 bits are the host → 256 addresses (254 usable)
                      .0 = network address, .255 = broadcast

10.0.0.0/8     → 16,777,216 addresses (first 8 bits fixed)
172.16.5.0/28  → only 16 addresses (first 28 bits fixed)
```

The **subnet mask** is the same idea as a bitmask: `/24` = `255.255.255.0`. A host ANDs its address with the mask to learn its network, then knows whether a destination is *local* (same network → deliver directly via the link layer) or *remote* (different network → send to the **default gateway**/router).

**Public vs private addresses.** Certain ranges are reserved for **private** networks (your home/office LAN) and are never routed on the public internet:

```text
10.0.0.0/8        ── big private range
172.16.0.0/12     ── medium
192.168.0.0/16    ── the classic home-router range
```

**NAT (Network Address Translation)** is the hack that let the world keep using IPv4 despite the shortage. Your home router has *one* public IP; all your devices share it via private addresses. When a device sends out, the router rewrites the source address/port to its own public IP and remembers the mapping in a table; when the reply comes back, it rewrites the destination back to the right private device. So a whole household of devices hides behind one public address.

```text
Laptop 192.168.1.10:51000 ──► Router (public 203.0.113.5) ──► Server
   router NAT table: 203.0.113.5:40001  ↔  192.168.1.10:51000
   reply to 203.0.113.5:40001 ──► router rewrites ──► 192.168.1.10:51000
```

```bash
ip addr           # Linux: your interfaces and addresses  (ifconfig on mac/older)
ipconfig getifaddr en0   # macOS: your LAN address
ip route          # routing table; the "default via ..." line is your gateway
```

## MAC addresses & ARP (briefly)

IP gets you *across* networks; the **link layer** gets you across the *local* wire. Every network interface has a **MAC address**, a 48-bit hardware identifier like `a4:83:e7:12:34:56`, unique to the NIC. On a local network, frames are addressed by MAC, not IP.

So when your laptop wants to send to `192.168.1.1` on the same LAN, it needs that host's *MAC* address. **ARP (Address Resolution Protocol)** does the lookup: the laptop broadcasts "who has `192.168.1.1`? tell me your MAC," the owner replies with its MAC, and the result is cached.

```bash
arp -a            # show the ARP cache: IP ↔ MAC mappings your machine has learned
```

The boundary to keep straight: MAC is local delivery (one hop, one wire); IP is end-to-end across many hops. As a packet travels router to router, the IP addresses stay the same source-to-destination, but the MAC addresses change at every hop, rewritten for each local link.

## Routing intuition

The internet is a mesh of routers. **Routing** is the process of moving a packet hop-by-hop from source network to destination network. Each router holds a **routing table** mapping destination prefixes → "next hop." When a packet arrives, the router looks up the *longest matching prefix* for the destination IP and forwards it to the corresponding next hop. No single router knows the whole path; each just knows the next step (like passing a letter through a chain of post offices that each know which neighbor is "more toward" the destination).

Routers learn these tables via routing protocols (BGP between networks/ISPs, OSPF within one). You can *see* the hop-by-hop path:

```bash
traceroute example.com    # (tracert on Windows) - each line is one router hop
ping example.com          # round-trip time + reachability
```

## UDP vs TCP

Both ride on top of IP, which is **unreliable** and **connectionless**: it makes a best effort to deliver each packet but guarantees nothing (packets can be lost, duplicated, reordered, corrupted). The transport layer decides how much of that to fix.

**UDP (User Datagram Protocol)** is thin and fast: essentially just ports and a checksum over IP. No connection, no acknowledgments, no ordering, no retransmission, no congestion control. Fire a datagram and hope. You use it when speed and low latency beat reliability, or when the app handles reliability itself: DNS queries, live video and voice (a dropped frame is better than a stalled stream), gaming, QUIC (the base of HTTP/3).

**TCP (Transmission Control Protocol)** is reliable, ordered, and connection-oriented. On top of unreliable IP, it builds a clean byte-stream abstraction with these mechanisms:

- **3-way handshake** to establish a connection:

  ```text
  Client                         Server
    │ ── SYN (seq=x) ─────────────► │   "let's talk; my sequence # starts at x"
    │ ◄── SYN-ACK (seq=y, ack=x+1) ─│   "ok, mine starts at y; I got your x"
    │ ── ACK (ack=y+1) ───────────► │   "got your y; connection ESTABLISHED"
    │ ────── data flows both ways ──│
  ```

- **Sequence & acknowledgment numbers**: every byte is numbered. The receiver ACKs the highest contiguous byte received, so the sender knows what arrived.
- **Reliability via retransmission**: unACKed data is resent after a timeout. Lost packets are recovered.
- **Ordering**: out-of-order packets are buffered and reassembled into the original byte stream before the app sees them.
- **Flow control** (via a *receive window*): the receiver advertises how much buffer space it has so a fast sender doesn't overwhelm a slow receiver.
- **Congestion control** (slow start, congestion avoidance): TCP probes the *network's* capacity, backing off when it detects loss (a congestion signal) and ramping up when things are clear, so senders collectively don't melt the shared internet.

**TCP head-of-line (HOL) blocking** falls straight out of the ordered-byte-stream guarantee: because TCP must deliver bytes in order, a lost segment forces every later segment that already arrived to wait in the buffer until the missing one is retransmitted, even though those later bytes are fine and the app could use them. One lost packet stalls everything behind it. This is a real cost of TCP's ordering promise, and it's why HTTP/3 moved to QUIC (over UDP) — more on that in the next chapter.

## Ports & sockets

An IP address gets you to a *host*; a **port** (16-bit number, 0-65535) gets you to a specific *process/service* on that host. `:80` = HTTP, `:443` = HTTPS, `:22` = SSH, `:53` = DNS. The pair **(IP, port)** is an **endpoint**.

A **socket** is the programming abstraction for one end of a network connection, the API your code uses to send/receive. A TCP connection is uniquely identified by the **4-tuple**: `(source IP, source port, dest IP, dest port)`. That's why one server on port 80 can handle thousands of simultaneous clients: each connection differs in the client's IP/port, so the tuples are all distinct.

```bash
netstat -an | grep LISTEN   # what's listening (or: ss -tlnp on Linux)
lsof -i :8080               # which process owns port 8080
```

## Build it: TCP echo server/client, a tiny chat, and UDP

Sockets are the hands-on payoff. Python's `socket` module is a thin wrapper over the OS syscalls (`socket`, `bind`, `listen`, `accept`, `connect`, `send`, `recv`).

### TCP echo server + client

```python
# echo_server.py - accepts one connection at a time, echoes back what it gets
import socket

HOST, PORT = "127.0.0.1", 9000
with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as srv:  # IPv4, TCP
    srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)   # reuse port quickly on restart
    srv.bind((HOST, PORT))     # claim the endpoint
    srv.listen()               # mark as a listening (passive) socket
    print(f"echo server on {HOST}:{PORT}")
    while True:
        conn, addr = srv.accept()        # BLOCKS until a client connects (3-way handshake done)
        with conn:
            print("connected by", addr)
            while True:
                data = conn.recv(1024)   # read up to 1024 bytes
                if not data:             # b"" means the client closed → EOF
                    break
                conn.sendall(data)       # echo it straight back
```

```python
# echo_client.py
import socket
with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as s:
    s.connect(("127.0.0.1", 9000))       # initiates the 3-way handshake
    s.sendall(b"hello, network!")
    print("got back:", s.recv(1024).decode())   # got back: hello, network!
```

Run the server, then the client. `accept()` returning is literally the handshake completing. To see the handshake itself, run `tcpdump` while you connect and watch SYN, SYN-ACK, ACK fly by:

```bash
sudo tcpdump -i lo0 -n 'port 9000'    # macOS loopback (lo on Linux). [S]=SYN, [S.]=SYN-ACK, [.]=ACK
```

(Wireshark gives the same packets in a GUI: filter `tcp.port == 9000` and the colored handshake is unmistakable. Watching the actual SYN/SYN-ACK/ACK is the moment TCP stops being abstract.)

### UDP - connectionless, no handshake

```python
# udp_server.py
import socket
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)   # SOCK_DGRAM = UDP
s.bind(("127.0.0.1", 9001))
print("udp server up")
while True:
    data, addr = s.recvfrom(1024)     # no connection: each datagram carries its sender
    print("from", addr, ":", data.decode())
    s.sendto(b"ack:" + data, addr)    # reply directly to that sender

# udp_client.py
import socket
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.sendto(b"ping", ("127.0.0.1", 9001))   # no connect() needed - just fire
print(s.recvfrom(1024))                  # (b'ack:ping', ('127.0.0.1', 9001))
```

The API difference is the conceptual difference: TCP is `connect`/`accept` then `send`/`recv` on a stream; UDP is `sendto`/`recvfrom` with the address on every datagram and no connection state. No handshake, no guarantee.

## Mini-project: multi-client chat server with `selectors`

The echo server above handles one client at a time — `accept()` and `recv()` block. A real chat server must juggle many clients at once. There are two ways: a thread per client, or **non-blocking sockets plus an event loop** via the `selectors` module (which wraps the OS's efficient I/O multiplexing, `epoll`/`kqueue`). The selectors approach is single-threaded and scales well; it's the same "watch many sockets, react when one is ready" idea from the asyncio chapter, at the raw level.

```python
# chat_server.py - single-threaded multi-client chat using selectors
import socket, selectors

sel = selectors.DefaultSelector()      # picks epoll/kqueue/select for your OS
clients = {}                           # conn -> nickname

def accept(server_sock):
    conn, addr = server_sock.accept()
    conn.setblocking(False)            # non-blocking: recv returns immediately
    sel.register(conn, selectors.EVENT_READ, read)   # watch this conn for "readable"
    clients[conn] = f"{addr[0]}:{addr[1]}"
    print("joined:", clients[conn])
    broadcast(f"* {clients[conn]} joined *\n", exclude=conn)

def broadcast(msg, exclude=None):
    for c in list(clients):
        if c is exclude:
            continue
        try:
            c.sendall(msg.encode())
        except OSError:
            drop(c)

def drop(conn):
    if conn in clients:
        name = clients.pop(conn)
        print("left:", name)
        try: sel.unregister(conn)
        except KeyError: pass
        conn.close()
        broadcast(f"* {name} left *\n")

def read(conn):
    try:
        data = conn.recv(1024)
    except ConnectionError:
        data = b""
    if not data:                       # client disconnected
        drop(conn); return
    text = data.decode(errors="replace").rstrip("\n")
    broadcast(f"[{clients[conn]}] {text}\n", exclude=conn)   # relay to everyone else

def main(host="127.0.0.1", port=9100):
    server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    server.bind((host, port))
    server.listen()
    server.setblocking(False)
    sel.register(server, selectors.EVENT_READ, accept)   # watch the listening socket too
    print(f"chat server on {host}:{port}  (connect with: nc {host} {port})")
    while True:
        # BLOCK until ANY registered socket is ready, then dispatch each to its handler
        for key, _ in sel.select():
            callback = key.data        # the function we registered (accept or read)
            callback(key.fileobj)

if __name__ == "__main__":
    main()
```

Test it with multiple terminals using `netcat` as the client:

```bash
# terminal 1
python3 chat_server.py
# terminals 2, 3, 4 - each is a client:
nc 127.0.0.1 9100
# type in one; it appears in the others. Ctrl-C a client → "* ... left *" broadcast.
```

What this drives home:
- **One thread, many clients.** `sel.select()` blocks until *any* watched socket is ready, then you handle exactly those. No thread-per-client, no locks. This is the `epoll`/`kqueue` model that powers high-performance servers (nginx, Redis, Node, asyncio), the same pattern as the OS-level event loop.
- **Non-blocking sockets are the prerequisite.** `setblocking(False)` means `recv` never freezes the loop waiting on one slow client.
- **The listening socket is "readable" when a new connection waits**, so `accept` and `read` are both just "this fd is ready" handlers, registered the same way.
- **Disconnect = `recv` returns `b""`**, the clean signal to unregister and remove the client.

A natural extension: add a `/nick name` command (parse it in `read`, update `clients[conn]`), or compare this to a thread-per-client version (`threading.Thread(target=handle, args=(conn,))`) and reason about which scales to 10,000 clients (the selectors one — no 10,000 OS threads).

## Common mistakes

Networking bugs are notorious for being intermittent and confusing. These are the ones that get everyone at least once.

- **Assuming one `recv()` gives you one complete message.** TCP is a **byte stream**, not a message stream. `recv(1024)` may return half a message, or two messages glued together. You must frame messages yourself (length prefix, or a delimiter like `\n`) and loop until you've read a full one. (UDP *is* message-oriented, one `recvfrom` = one datagram, which is a key difference.)
- **Forgetting `SO_REUSEADDR`.** Restart a server too quickly and `bind()` fails with "Address already in use" because the old socket lingers in `TIME_WAIT`. `setsockopt(SOL_SOCKET, SO_REUSEADDR, 1)` before `bind` fixes it.
- **Confusing `127.0.0.1` with `0.0.0.0`.** Binding to `127.0.0.1` (loopback) means *only this machine* can connect. To accept connections from other hosts you must bind `0.0.0.0` (all interfaces). "Why can't anyone else reach my server?" is almost always this.
- **Expecting UDP to be reliable.** It isn't: datagrams can be lost, duplicated, or reordered, and there's no connection. If you need reliability over UDP, you build it yourself (which is what QUIC does).
- **Not handling `recv()` returning `b""`.** Empty bytes means the peer closed the connection (EOF). Treat it as "done," not as "no data this time"; otherwise you spin forever.
- **Hardcoding buffer sizes and assuming the whole message fits.** `recv(1024)` caps at 1024 bytes; bigger messages need a loop. Same on the send side: use `sendall` (which loops) rather than `send` (which may send only part).
- **Confusing private and public IPs / forgetting NAT.** A `192.168.x.x` or `10.x.x.x` address is only reachable on the LAN; it's never routable on the public internet. Trying to connect to someone's private IP from across the world won't work.
- **Mixing up "port in use by another process" vs "firewall blocking."** `lsof -i :PORT` / `ss -tlnp` tells you if something's already listening; a connection that hangs with nothing listening locally is often a firewall/security-group issue.

## On the job / interview angle

The TCP/IP stack is foundational interview material and constant on-the-job reality.

- **"What happens when you type a URL and press Enter?"** is *the* canonical systems-design warmup, and the network half lives here: DNS → TCP handshake → (TLS) → HTTP request/response, with IP routing and the layered stack underneath. Being able to narrate it end-to-end signals broad competence.
- **"Explain the TCP three-way handshake"** and **"TCP vs UDP, when would you use each?"** are near-guaranteed. Have the SYN/SYN-ACK/ACK sequence and the reliability-vs-speed tradeoff memorized, plus concrete UDP use cases (DNS, video, gaming, QUIC).
- **"What's the difference between a process listening on a port and a connection?"** The 4-tuple answer (a connection is `src IP:port, dst IP:port`, which is why one port serves thousands of clients) shows real understanding.
- **"What is NAT / what's a private vs public IP / what's a subnet mask?"** appear in infra-leaning interviews.
- **On the job:** debugging connectivity is a weekly event. The tools here — `ping`, `traceroute`, `dig` (next chapter), `tcpdump`/Wireshark, `lsof -i`, `ss`/`netstat`, `ip addr`/`ip route` — are exactly what you reach for when a service can't reach a database, a deployment can't connect to an API, or latency spikes. "Is it DNS? is the route up? is the port open? is the handshake completing?" is a debugging ladder you'll climb constantly. Reading a `tcpdump` of a failed handshake (SYN sent, no SYN-ACK back → firewall/wrong host) is a genuinely valuable skill.
- The **selectors/epoll event-loop** pattern in the mini-project is the architecture behind nginx, Redis, Node.js, and asyncio; understanding it explains why those scale to enormous connection counts on few threads — a common systems-design discussion point.

## Mini-project: a tiny port scanner + a message-framed protocol

Two small builds that cement two big lessons: how connections actually probe a host, and how to turn TCP's raw byte stream into real messages.

### Part A - a concurrent TCP port scanner

This makes "a port is just an endpoint a process may or may not be listening on" tangible, and reuses the I/O-bound-concurrency idea from the OS/concurrency chapters.

```python
# portscan.py - check which TCP ports on a host are accepting connections
import socket
from concurrent.futures import ThreadPoolExecutor

def check_port(host, port, timeout=0.5):
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as s:
        s.settimeout(timeout)
        try:
            s.connect((host, port))     # success = the 3-way handshake completed = something is listening
            return port, True
        except (ConnectionRefusedError, socket.timeout, OSError):
            return port, False          # refused (nothing there) or filtered (firewall) or timed out

def scan(host, ports):
    open_ports = []
    # I/O-bound (mostly waiting on the network) → threads overlap the waiting
    with ThreadPoolExecutor(max_workers=100) as pool:
        for port, is_open in pool.map(lambda p: check_port(host, p), ports):
            if is_open:
                open_ports.append(port)
    return sorted(open_ports)

if __name__ == "__main__":
    host = "127.0.0.1"
    common = [22, 53, 80, 443, 3000, 5432, 8000, 8080, 9000, 9100, 6379]
    print(f"scanning {host} ...")
    found = scan(host, common)
    print("open ports:", found or "(none of the probed ports were open)")
    # Try it: run echo_server.py on 9000 in another terminal, then re-run - 9000 shows up.
```

What it teaches: a successful `connect()` is the handshake completing, which is the definition of "a service is listening here." `ConnectionRefusedError` means the host answered "nobody's home on that port" (an RST); a timeout often means a firewall silently dropped the SYN. And because each probe is mostly waiting, a thread pool overlaps all of them — the same I/O-bound concurrency lesson from the systems chapters, applied to the network. (Only scan hosts you own or have permission to test.)

### Part B - length-prefixed message framing over TCP

This fixes the #1 TCP beginner bug ("one recv ≠ one message") by implementing proper framing.

```python
# framing.py - send/receive whole messages over TCP's byte stream using a 4-byte length prefix
import socket, struct

def send_msg(sock, payload: bytes):
    # Prefix each message with its length (4-byte big-endian int) so the receiver knows where it ends.
    sock.sendall(struct.pack(">I", len(payload)) + payload)

def recv_exactly(sock, n):
    buf = b""
    while len(buf) < n:                 # loop until we've read exactly n bytes (recv may return less)
        chunk = sock.recv(n - len(buf))
        if not chunk:                   # peer closed mid-message
            raise ConnectionError("connection closed while reading")
        buf += chunk
    return buf

def recv_msg(sock):
    header = recv_exactly(sock, 4)      # first read the 4-byte length
    (length,) = struct.unpack(">I", header)
    return recv_exactly(sock, length)   # then read exactly that many bytes = one whole message

# --- demo: server echoes framed messages; client sends three of different sizes ---
def server(port=9200):
    srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    srv.bind(("127.0.0.1", port)); srv.listen()
    print("framed echo server on", port)
    conn, _ = srv.accept()
    with conn:
        while True:
            try:
                msg = recv_msg(conn)
            except ConnectionError:
                break
            print("server got a", len(msg), "byte message")
            send_msg(conn, msg.upper())

def client(port=9200):
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as s:
        s.connect(("127.0.0.1", port))
        for text in [b"hi", b"a much longer message " * 5, b"end"]:
            send_msg(s, text)
            print("client got back:", recv_msg(s)[:40], "...")

if __name__ == "__main__":
    import sys
    (server if sys.argv[1:] == ["server"] else client)()
    # run:  python3 framing.py server   (one terminal)
    #       python3 framing.py          (another terminal)
```

What it teaches, and why it matters professionally: TCP gives you a stream of bytes with no message boundaries — the boundaries are your job. The length-prefix protocol here (a 4-byte length, then that many bytes) is exactly how real binary protocols, including the WebSocket frames in chapter 6.3, delimit messages. `recv_exactly` looping until it has the full count is the single most important habit for correct TCP code.

9. **(Hard)** As a packet travels from your laptop through 3 routers to a server, which addresses (IP source/dest, MAC source/dest) stay the same and which change at each hop? Why?
10. **(Stretch)** Run `sudo tcpdump -i lo0 -n 'port 9000'` (or `lo` on Linux) while connecting the echo client to the echo server. Identify the SYN, SYN-ACK, and ACK in the output, then the data and the FIN.

### Solutions

1. `255.255.255.0` = **/24** (24 leading 1-bits: 8+8+8+0). A `/24` has 8 host bits → 256 total addresses, minus the network address (`.0`) and broadcast (`.255`) → **254 usable**.

2. `10.0.5.7` is **private**, it's in the `10.0.0.0/8` reserved range (never routed on the public internet). `93.184.216.34` is **public**, it's outside all three private ranges (`10/8`, `172.16/12`, `192.168/16`). You tell by checking membership in the reserved private ranges.

3. **DNS** (a lost query is just re-asked, and a single small datagram is faster than setting up a TCP connection) and **live video/voice or gaming** (a dropped frame is better than stalling the whole stream waiting for a retransmit — freshness beats completeness). Both either retry cheaply or prefer timeliness over guaranteed delivery.

4. Each line is one **router hop** on the path to the destination, with the round-trip times to that hop. `traceroute` works by sending packets with increasing TTL; each router that decrements TTL to 0 sends back an error revealing itself. `* * *` means a hop didn't reply (many routers deprioritize or block the ICMP/UDP probes traceroute uses); the packet still passes through, it just won't identify itself.

5. A TCP connection is identified by the full **4-tuple**: `(source IP, source port, dest IP, dest port)`. The server's side is fixed (`server IP:443`), but every client connects from a *different* source IP and/or source port, so every connection's 4-tuple is unique. The server demultiplexes incoming packets to the right connection by that tuple; the shared `:443` endpoint isn't the identity, the whole tuple is.

6. The bug is treating TCP as message-oriented: assuming one `recv()` returns exactly one message. TCP is a **byte stream**, so messages can be split across recvs or merged into one. Fix: implement **framing**, either length-prefix each message (read 4 bytes of length, then exactly that many bytes, looping until complete) or use a delimiter and buffer until you see it. (See `framing.py` above.)

7. **SYN** (client → server): client moves to SYN-SENT; it proposes its initial sequence number. **SYN-ACK** (server → client): server moves to SYN-RECEIVED; it acknowledges the client's seq and sends its own. **ACK** (client → server): client moves to ESTABLISHED; when the server receives it, server moves to ESTABLISHED too. After all three, both sides have synchronized sequence numbers and confirmed two-way reachability. On the server, `accept()` returning corresponds to this handshake completing: it hands back a new connected socket for that established connection.

8. TCP guarantees **in-order byte delivery**, so the receiver can't hand later bytes to the application until earlier bytes arrive. Scenario: server sends segments S1, S2, S3; S1 is lost in transit but S2 and S3 arrive fine. The receiver *has* S2 and S3 but must **buffer** them and stall the application until S1 is retransmitted and arrives, even though S2/S3 are perfectly usable. One loss blocks everything behind it (head-of-line blocking). HTTP/3 runs over **QUIC** (on UDP), which delivers each stream independently, so a loss in one stream only stalls that stream, not the others.

9. The **IP source and destination stay the same** end-to-end (your laptop's IP and the server's IP) — that's the point of IP addressing: it identifies the ultimate endpoints. The **MAC source and destination change at every hop**, because MAC addresses are for local delivery over a single link: at each router, the frame is re-addressed with that router's MAC as source and the next hop's MAC as destination. IP = end-to-end; MAC = hop-by-hop.

10. In the `tcpdump` output you'll see flags: `[S]` = SYN (client → server), `[S.]` = SYN-ACK (server → client), `[.]` = ACK (the bare ACK completing the handshake). Then `[P.]` (PSH+ACK) lines carrying the actual data ("hello, network!" and the echo), and finally `[F.]` = FIN as the connection closes, each FIN acknowledged.

## Teach it back

1. **Name the four TCP/IP layers bottom-to-top and one protocol at each.** Link (Ethernet/Wi-Fi, MAC frames) → Internet (IP, host-to-host addressing/routing) → Transport (TCP/UDP, process-to-process via ports) → Application (HTTP/DNS/SSH). Each adds its own header and trusts the layer below; that separation lets layers evolve independently.

2. **What does `192.168.1.0/24` mean, and is it public or private?** The `/24` means the first 24 bits are the network, leaving 8 host bits → 256 addresses (254 usable). It's in the `192.168.0.0/16` **private** range, so it's a LAN address never routed on the public internet; devices on it reach the internet through NAT.

3. **Walk through TCP's 3-way handshake and say what each message accomplishes.** SYN (client → server: "let's connect, my sequence starts at x"), SYN-ACK (server → client: "ok, mine starts at y, and I acknowledge your x"), ACK (client → server: "I acknowledge your y"). After the third message both sides have synchronized sequence numbers and the connection is established; each direction has confirmed the other can hear it.

4. **Give two mechanisms TCP uses to be reliable that UDP lacks.** Any two of: sequence/acknowledgment numbers (so the sender knows what arrived), retransmission of unACKed data (recovers losses), in-order reassembly (buffers out-of-order packets), flow control (receive window), congestion control (back off on loss). UDP has none of these — it's just ports plus a checksum over IP.

5. **What is TCP head-of-line blocking and why does it happen?** Because TCP guarantees in-order byte delivery, a single lost segment forces all later segments that already arrived to wait in the buffer until the missing one is retransmitted, even though those later bytes are fine. The ordering guarantee causes one loss to stall everything behind it; HTTP/3 (QUIC over UDP) was designed to escape this.

6. **Why can a single server on port 80 serve thousands of simultaneous clients?** Because a TCP connection is identified by the full 4-tuple `(src IP, src port, dst IP, dst port)`, not just the server's port. Every client connection has a different source IP/port, so all the tuples are distinct; the server demultiplexes them even though they share its `:80` endpoint.
