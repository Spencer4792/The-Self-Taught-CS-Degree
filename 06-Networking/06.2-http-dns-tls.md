## 🟢 Start here: ordering a pizza by phone

Three protocols, one familiar errand: **ordering a pizza over the phone.**

- First you need the pizzeria's **phone number**. You know the *name* ("Tony's Pizza") but not the digits, so you look it up in a directory. **That's DNS**, turning a human name (`example.com`) into a machine-routable number (an IP address). The directory is layered (you might ask information, who points you to a regional listing, who has the number) and the answer gets cached so you don't look it up every time.
- Then you have a **conversation in a structured format**: you say "I'd like to *order* a large pepperoni" (a request with a verb and details), and they reply "Got it, that'll be 20 minutes, $18" (a response with a status and data). There's an etiquette, you state your request a certain way, they answer a certain way. **That's HTTP**, the request/response protocol with methods (verbs like GET/POST), status codes (200 OK, 404 Not Found), and headers (the metadata).
- But what if you're discussing your credit card over the phone in a crowded room? You'd want the line **scrambled so eavesdroppers can't listen**, and you'd want to be **sure you're really talking to Tony's and not an impostor who'll steal your card**. **That's TLS**, encryption (confidentiality), tamper-detection (integrity), and proof-of-identity via certificates (authentication). HTTPS is just "HTTP, but on a secured phone line."

So `https://example.com` = look up the number (DNS), get on a scrambled+verified line (TLS), and have a structured conversation (HTTP). Three protocols, one errand.

**Why this matters:** these three are the literal foundation of the web and every web job. Reading an HTTP request/response, knowing what a status code means, understanding why a cert is invalid, knowing why a DNS change "hasn't propagated yet", this is daily bread for any developer who touches the web (which is almost all of them). And the best way to truly *get* them is to perform each one by hand, which is what the build sections do. The rest of the chapter makes the pizza picture precise.

## 📐 DNS: the internet's phonebook

Computers route by IP address, but humans use names. **DNS (Domain Name System)** is the distributed database that translates `example.com` → `93.184.216.34`. It's a phonebook, except no single book holds every number, it's a hierarchy of servers, each responsible for one slice.

**Recursive resolution**, how a name gets resolved, step by step:

```text
You ask your RESOLVER (e.g. your ISP's or 8.8.8.8): "what is www.example.com?"
The resolver, if it hasn't cached the answer, walks the hierarchy:

1. ROOT servers      → "I don't know www.example.com, but ask the .com servers (here)"
2. TLD servers (.com)→ "ask example.com's authoritative servers (here)"
3. AUTHORITATIVE     → "www.example.com is 93.184.216.34"  ← the answer
   (example.com's
    own nameservers)
resolver caches it (per the TTL) and returns it to you.
```

The hierarchy mirrors the name read right-to-left: root → `.com` (TLD) → `example.com` (authoritative). Your resolver does the legwork ("recursive"); each server it asks gives a referral ("iterative") until the authoritative server gives the real answer.

**Record types** (what kinds of "numbers" the phonebook holds):

```text
A      name → IPv4 address          (example.com → 93.184.216.34)
AAAA   name → IPv6 address
CNAME  name → another name (alias)  (www → example.com)
MX     mail server for a domain
TXT    arbitrary text (SPF, domain verification, etc.)
NS     which nameservers are authoritative for a zone
```

**Caching & TTL.** DNS would collapse if every lookup walked the whole hierarchy, so answers are cached at every level (your OS, your resolver, your browser). Each record carries a **TTL** (time-to-live, in seconds) saying how long it's safe to cache. Low TTL = changes propagate fast but more lookups; high TTL = efficient but slow to update. This is why a DNS change can take "up to 48 hours", old answers linger in caches until their TTL expires.

```bash
dig example.com            # full DNS answer, with the resolution path and TTL
dig +short example.com     # just the IP
dig example.com MX         # mail records
nslookup example.com       # simpler, cross-platform
```

## 📐 HTTP in depth

**HTTP (HyperText Transfer Protocol)** is the request/response protocol of the web. The client sends a **request**; the server sends a **response**. It's stateless by design (each request is independent), which is why we bolt on cookies for sessions.

**Request anatomy**, it's just text (in HTTP/1.1):

```text
GET /index.html HTTP/1.1        ← request line: METHOD  PATH  VERSION
Host: example.com               ← headers (key: value), one per line
User-Agent: curl/8.0
Accept: text/html
                                ← BLANK line separates headers from body
(optional body, e.g. for POST)
```

**Response anatomy:**

```text
HTTP/1.1 200 OK                 ← status line: VERSION  CODE  REASON
Content-Type: text/html         ← headers
Content-Length: 1256
                                ← blank line
<!doctype html>...              ← body
```

**Methods** (the verb, what to do with the resource):

```text
GET     read a resource (safe, no side effects, cacheable)
POST    create / submit data (not idempotent)
PUT     replace a resource entirely (idempotent)
PATCH   partially update a resource
DELETE  remove a resource (idempotent)
HEAD    like GET but headers only (no body)
OPTIONS ask what methods/capabilities are allowed (used by CORS preflight)
```

*Idempotent* = doing it twice has the same effect as once (GET, PUT, DELETE), important for safe retries. POST is not (two POSTs may create two records).

**Status codes** (grouped by first digit):

```text
1xx  informational   (100 Continue, 101 Switching Protocols ← used by WebSockets!)
2xx  success         (200 OK, 201 Created, 204 No Content)
3xx  redirection     (301 Moved Permanently, 302 Found, 304 Not Modified ← caching)
4xx  CLIENT error    (400 Bad Request, 401 Unauthorized, 403 Forbidden,
                      404 Not Found, 429 Too Many Requests)
5xx  SERVER error    (500 Internal Server Error, 502 Bad Gateway, 503 Unavailable)
```

The mnemonic: 4xx = "you messed up," 5xx = "I messed up."

**Headers** carry metadata. A few categories worth knowing:
- **Content**: `Content-Type` (MIME type like `application/json`), `Content-Length`, `Content-Encoding: gzip`.
- **Auth**: `Authorization: Bearer <token>`, `WWW-Authenticate`.
- **Cookies**: `Set-Cookie` (server → client) and `Cookie` (client → server).

**Cookies & state.** HTTP is stateless, so to remember a logged-in user the server sends `Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax` and the browser returns `Cookie: session=abc123` on every subsequent request. Flags matter: `HttpOnly` (JS can't read it → mitigates XSS theft), `Secure` (HTTPS only), `SameSite` (limits cross-site sending → mitigates CSRF).

**Caching headers.** To avoid re-fetching unchanged resources:
- `Cache-Control: max-age=3600`, cache for an hour; `no-store`, never cache.
- `ETag: "abc"`, a version fingerprint. The client later sends `If-None-Match: "abc"`; if unchanged, the server replies **`304 Not Modified`** with no body, saving bandwidth.
- `Last-Modified` / `If-Modified-Since`, the timestamp-based equivalent.

**HTTP versions, the evolution and *why*:**

```text
HTTP/1.0  one request per TCP connection - open, request, response, close. Slow.
HTTP/1.1  KEEP-ALIVE: reuse one connection for many requests (no re-handshake).
          But responses must come back IN ORDER on the connection →
          HTTP-level head-of-line blocking; browsers open ~6 connections to fake parallelism.
HTTP/2    MULTIPLEXING: many requests/responses interleaved as "streams" over ONE
          connection. Header compression (HPACK). Fixes HTTP-level HOL blocking...
          ...but still rides on TCP, so a lost TCP packet still stalls ALL streams
          (TCP-level HOL blocking from the last chapter).
HTTP/3    Runs over QUIC (built on UDP). Each stream is independently delivered, so
          one lost packet only stalls ITS stream, not the others. Escapes TCP HOL
          blocking entirely. Also folds in TLS for a faster handshake.
```

The throughline: each version chips away at **head-of-line blocking** at a higher level, until HTTP/3 swaps TCP for QUIC to kill it at the transport level too. This connects straight back to the TCP HOL discussion in 6.1.

## 📐 REST conventions (preview)

**REST** is a style for designing HTTP APIs around **resources** (nouns) addressed by URLs, manipulated with HTTP **methods** (verbs):

```text
GET    /users          → list users
POST   /users          → create a user
GET    /users/42       → fetch user 42
PUT    /users/42       → replace user 42
PATCH  /users/42       → update fields of user 42
DELETE /users/42       → delete user 42
```

The conventions: URLs name resources (not actions, it's `/users/42`, not `/getUser?id=42`), HTTP methods carry the verb, status codes carry the outcome, and it's stateless (each request self-contained, auth token included every time). We'll contrast this with RPC in the next chapter, where the mental model flips from "manipulate resources" to "call a remote function."

## 📐 TLS / HTTPS: confidentiality, integrity, authentication

Plain HTTP is sent in the clear, anyone on the path (your ISP, café Wi-Fi, a router) can read and modify it. **TLS (Transport Layer Security)** wraps the connection to provide three guarantees, and HTTPS = HTTP over TLS:

1. **Confidentiality**, the traffic is *encrypted*; eavesdroppers see ciphertext.
2. **Integrity**, *tampering is detectable* (message authentication codes); a flipped bit is caught.
3. **Authentication**, you're really talking to `example.com`, not an impostor (via **certificates**).

**The handshake (TLS 1.3, simplified):**

```text
Client                                    Server
  │ ── ClientHello ───────────────────────► │  "here are the cipher suites I support
  │     (+ key share)                        │   and my key-exchange public value"
  │ ◄── ServerHello + CERTIFICATE ────────── │  "chosen cipher, my key share, and
  │     (+ key share, + signature)           │   here's my certificate proving who I am"
  │  -- both derive the SAME shared secret --│  (via Diffie-Hellman key exchange:
  │                                          │   they agree on a secret without ever
  │                                          │   sending it on the wire)
  │ ── Finished (encrypted) ───────────────► │
  │ ◄── Finished (encrypted) ─────────────── │
  │ ═══════ all further traffic encrypted ═══│
```

Two crypto ideas combine: **asymmetric** crypto (the certificate + key exchange) is used *once* to authenticate and to agree on a shared secret; then fast **symmetric** crypto (with that shared secret) encrypts the actual data. Asymmetric is slow but solves "how do two strangers agree on a secret over a tapped wire"; symmetric is fast and does the bulk work. (TLS 1.3 trimmed this to one round trip, faster than the older 1.2 handshake.)

**Certificates & chains of trust.** How do you know the certificate `example.com` presents is legit and not forged? Trust is delegated through a chain:

```text
Root CA  (self-signed; pre-installed & trusted by your OS/browser)
   │ signs
Intermediate CA
   │ signs
example.com's certificate  (contains: the domain name + example.com's PUBLIC KEY,
                            signed by the intermediate)
```

Your browser ships with a list of trusted **root CAs**. When the server presents its cert (plus intermediates), the browser verifies each signature up the chain to a trusted root. The cert binds a **domain name** to a **public key**; the server proves it holds the matching private key during the handshake. So authentication = "a CA you trust vouches that this public key belongs to this domain, and the server proved it owns the private key." A self-signed cert (no trusted CA in the chain) is why browsers warn you. This certificate machinery is the foundation we build on in the security chapters.

## 💻 Build it: raw HTTP by hand, then `requests`; inspect a cert; resolve DNS

### Raw HTTP over a socket - see that it's just text

HTTP/1.1 is a text protocol over TCP, so you can speak it by hand with a raw socket. No library magic.

```python
# raw_http.py - send an HTTP/1.1 request as literal bytes over a socket
import socket

host = "example.com"
# Build the request manually. \r\n line endings; blank line ends the headers.
request = (
    f"GET / HTTP/1.1\r\n"
    f"Host: {host}\r\n"
    f"Connection: close\r\n"      # tell the server to close after responding
    f"\r\n"                       # blank line = end of headers (CRITICAL)
).encode()

with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as s:
    s.connect((host, 80))         # port 80 = plain HTTP
    s.sendall(request)
    response = b""
    while True:
        chunk = s.recv(4096)
        if not chunk:             # server closed → done
            break
        response += chunk

text = response.decode(errors="replace")
headers, _, body = text.partition("\r\n\r\n")
print("=== STATUS + HEADERS ===")
print(headers)
print("\n=== BODY (first 300 chars) ===")
print(body[:300])
```

Running this and seeing `HTTP/1.1 200 OK` come back, from a request you assembled by hand, demystifies the whole web. (For HTTPS you'd wrap the socket with `ssl`, `ssl.create_default_context().wrap_socket(sock, server_hostname=host)` and use port 443.)

### Same thing with `requests` (what you'd actually use)

```python
import requests
r = requests.get("https://example.com")
print(r.status_code)              # 200
print(r.headers["Content-Type"])  # text/html; charset=UTF-8
print(r.text[:300])
# requests handles TLS, redirects, keep-alive, encoding, cookies - all the
# tedium I did by hand above.
```

### Inspect a TLS certificate with `openssl`

```bash
# Pull the cert chain and show the negotiated handshake:
openssl s_client -connect example.com:443 -servername example.com </dev/null

# Just the human-readable cert details (issuer, subject, validity, SAN domains):
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -text | grep -A2 'Issuer:\|Subject:\|Not Before\|Not After\|DNS:'
```

This shows the real chain: the **Subject** (who the cert is for), the **Issuer** (which CA signed it), the validity dates, and the **Subject Alternative Names** (the domains it covers). Walking from the leaf cert up to a trusted root is exactly what your browser does silently on every HTTPS page.

### Resolve DNS in Python

```python
import socket
print(socket.gethostbyname("example.com"))          # → '93.184.216.34' (one A record)

# Richer: all addresses (IPv4 + IPv6), via getaddrinfo
for fam, _, _, _, sockaddr in socket.getaddrinfo("example.com", 443):
    print(fam.name, sockaddr[0])

# Specific record types need a library like dnspython (pip install dnspython):
# import dns.resolver
# for r in dns.resolver.resolve("example.com", "MX"): print(r)
```

## 🧪 Mini-project: a from-scratch HTTP/1.1 server on raw sockets

No framework, just the `socket` module, parsing requests and writing responses by hand. This forces you to *implement* the protocol you just learned to read. It serves static files and handles a couple of routes.

```python
# tiny_http_server.py - a minimal HTTP/1.1 server from raw sockets
import socket, os, datetime, mimetypes, threading

HOST, PORT = "127.0.0.1", 8080
WEBROOT = os.path.abspath("./www")     # files served from here; create it with an index.html
os.makedirs(WEBROOT, exist_ok=True)

def build_response(status, body, content_type="text/html; charset=utf-8", extra=None):
    """Assemble a valid HTTP/1.1 response: status line + headers + blank line + body."""
    if isinstance(body, str):
        body = body.encode()
    headers = [
        f"HTTP/1.1 {status}",
        f"Date: {datetime.datetime.utcnow():%a, %d %b %Y %H:%M:%S} GMT",
        "Server: tiny-http/0.1",
        f"Content-Type: {content_type}",
        f"Content-Length: {len(body)}",
        "Connection: close",
    ]
    if extra:
        headers += extra
    return ("\r\n".join(headers) + "\r\n\r\n").encode() + body   # \r\n\r\n = end of headers

def route(method, path):
    """Application routes - return (status, body, content_type, extra_headers)."""
    if path == "/" or path == "/index.html":
        return serve_file("index.html")
    if path == "/hello":
        return "200 OK", "<h1>Hello from a raw-socket server!</h1>", "text/html; charset=utf-8", None
    if path == "/api/time":
        import json
        body = json.dumps({"utc": datetime.datetime.utcnow().isoformat()})
        return "200 OK", body, "application/json", None
    # otherwise try to serve a static file by path
    return serve_file(path.lstrip("/"))

def serve_file(relpath):
    # Security: prevent path traversal (../../etc/passwd) by resolving and checking the prefix.
    full = os.path.abspath(os.path.join(WEBROOT, relpath))
    if not full.startswith(WEBROOT) or not os.path.isfile(full):
        return "404 Not Found", "<h1>404 Not Found</h1>", "text/html; charset=utf-8", None
    ctype = mimetypes.guess_type(full)[0] or "application/octet-stream"
    with open(full, "rb") as f:
        return "200 OK", f.read(), ctype, None

def handle(conn, addr):
    with conn:
        data = conn.recv(65536).decode(errors="replace")
        if not data:
            return
        request_line = data.split("\r\n", 1)[0]
        try:
            method, path, version = request_line.split()
        except ValueError:
            conn.sendall(build_response("400 Bad Request", "<h1>400</h1>"))
            return
        print(f"{addr[0]} -> {method} {path}")
        if method not in ("GET", "HEAD"):
            conn.sendall(build_response("405 Method Not Allowed", "<h1>405</h1>",
                                        extra=["Allow: GET, HEAD"]))
            return
        status, body, ctype, extra = route(method, path)
        resp = build_response(status, body, ctype, extra)
        if method == "HEAD":                 # HEAD = headers only, strip the body
            resp = resp.split(b"\r\n\r\n", 1)[0] + b"\r\n\r\n"
        conn.sendall(resp)

def main():
    # seed an index page if missing
    idx = os.path.join(WEBROOT, "index.html")
    if not os.path.exists(idx):
        with open(idx, "w") as f:
            f.write("<h1>It works.</h1><p>Served from raw sockets.</p>"
                    "<ul><li><a href='/hello'>/hello</a></li>"
                    "<li><a href='/api/time'>/api/time</a></li></ul>")
    srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    srv.bind((HOST, PORT)); srv.listen()
    print(f"serving http://{HOST}:{PORT}  (Ctrl-C to stop)")
    while True:
        conn, addr = srv.accept()
        threading.Thread(target=handle, args=(conn, addr), daemon=True).start()  # one thread/conn

if __name__ == "__main__":
    main()
```

Test it:

```bash
python3 tiny_http_server.py
# in another terminal - or just open http://127.0.0.1:8080 in a browser:
curl -i http://127.0.0.1:8080/            # -i shows status + headers (the bytes I built!)
curl    http://127.0.0.1:8080/api/time    # {"utc": "..."}
curl -I http://127.0.0.1:8080/hello       # HEAD: headers only, no body
curl    http://127.0.0.1:8080/nope        # 404 page
```

What building this teaches beyond reading specs:
- A response is *literally* `status line\r\n headers\r\n\r\n body`, you type every byte, so the format becomes permanent.
- **`Content-Length` matters**: it tells the client where the body ends. Get it wrong and the client hangs or truncates.
- **Routing** is just matching the method + path string and choosing a handler, exactly what Flask/Express do, minus the sugar.
- **Path traversal is a real attack**: serving files by user-supplied path without the `startswith(WEBROOT)` check would let `../../etc/passwd` leak. Security is in the plumbing.
- This is the conceptual core every web framework wraps. Now when you use Flask, you know what it's hiding.

(Extensions: add `Keep-Alive` instead of `Connection: close` and serve multiple requests per connection; add a tiny router table; gzip responses with `Content-Encoding`.)

## ⚠️ Common mistakes

These bite web developers constantly, often in production, where they're hardest to debug.

- **Using GET when you should use POST (or vice versa).** GET is *safe* (no side effects) and *cacheable*; never use it to change state (a crawler or prefetch could fire it). POST/PUT/DELETE change state. Putting sensitive data or mutations in a GET (it lands in logs, history, and URLs) is a classic security/correctness bug.
- **Confusing `Content-Length` and chunked encoding.** If you set `Content-Length` wrong, the client truncates or hangs waiting for bytes that never come. Get it from the actual byte length of the (encoded) body, not the string length.
- **Forgetting the blank line between headers and body.** HTTP requires `\r\n\r\n` to end the headers. Miss it and the server treats your body as more headers (or hangs).
- **Thinking a 200 means success in your app's terms.** A `200 OK` only means the HTTP transaction succeeded; the body can still contain an application-level error. Conversely, REST APIs *should* use proper status codes (404, 422, 500) rather than returning 200 with `{"error": ...}`.
- **Cookie flag mistakes.** Omitting `HttpOnly` exposes the session cookie to XSS theft; omitting `Secure` lets it leak over plain HTTP; omitting `SameSite` opens CSRF surface. Session cookies should almost always be `HttpOnly; Secure; SameSite=Lax`.
- **Assuming DNS changes are instant.** Caches hold old records until the **TTL** expires, that's why a change can take "up to 48 hours." Lower the TTL *before* a planned migration.
- **Mishandling certificates.** Disabling cert verification ("just make it work") in code (`verify=False`) is a real, common, dangerous shortcut, it removes the authentication guarantee and exposes you to man-in-the-middle attacks. Expired certs and missing intermediate certs are the usual real causes of "cert errors"; fix the cert, don't disable verification.
- **Path traversal in file-serving code.** Serving a user-supplied path without normalizing and checking it stays under the web root lets `../../etc/passwd` leak. Always resolve the absolute path and verify the prefix.
- **CORS confusion.** "Blocked by CORS" is a *browser* policy, not a server error, the server must send `Access-Control-Allow-*` headers; the request often isn't even failing on the server side.

## 🧪 Mini-project: a caching DNS-over-HTTP resolver + an HTTP request/response inspector

Two builds: one makes DNS caching and record types tangible; the other makes you *parse* HTTP, the inverse of generating it.

### Part A - a tiny caching resolver using DNS-over-HTTPS

No special libraries, just `requests` against a public DoH endpoint (Cloudflare/Google). It shows record lookups *and* the caching+TTL behavior that makes DNS scale.

```python
# mini_resolver.py - resolve names via DNS-over-HTTPS, with a TTL-respecting cache
import time, requests

_CACHE = {}   # (name, rtype) -> (expiry_epoch, answers)

def resolve(name, rtype="A"):
    key = (name, rtype)
    now = time.time()
    if key in _CACHE and _CACHE[key][0] > now:
        print(f"  [cache hit] {name} {rtype}")
        return _CACHE[key][1]

    # DoH: a normal HTTPS GET that returns JSON DNS answers
    r = requests.get("https://cloudflare-dns.com/dns-query",
                     params={"name": name, "type": rtype},
                     headers={"accept": "application/dns-json"}, timeout=5)
    data = r.json()
    answers = [(a["data"], a["TTL"]) for a in data.get("Answer", [])]
    if answers:
        min_ttl = min(ttl for _, ttl in answers)
        _CACHE[key] = (now + min_ttl, answers)   # cache until the smallest TTL expires
        print(f"  [resolved] {name} {rtype}  (caching for {min_ttl}s)")
    return answers

if __name__ == "__main__":
    for rtype in ["A", "AAAA", "MX", "TXT"]:
        print(f"\n{rtype} records for example.com:")
        for value, ttl in resolve("example.com", rtype):
            print(f"   {value}   (TTL {ttl})")
    print("\nResolve again (should hit cache):")
    resolve("example.com", "A")    # second call within TTL → cache hit, no network
```

What it teaches: DNS is just a lookup that returns typed records (A=IPv4, AAAA=IPv6, MX=mail, TXT=text), each with a **TTL** that says how long it's safe to cache. The second `resolve` call proves caching: it returns instantly with no network call. This is, in miniature, exactly what your OS resolver and browser do, and why a DNS change takes time to propagate (old answers linger until their TTL expires). DoH itself is a real, increasingly common privacy feature: DNS queries tunneled inside HTTPS so they can't be snooped or tampered with on the wire.

### Part B - an HTTP message parser

Generating HTTP (the chapter's server) teaches the format; *parsing* it teaches you to read what comes off the wire, the skill behind every proxy, framework, and debugging session.

```python
# http_parser.py - parse a raw HTTP request and a raw HTTP response into structured form
def parse_request(raw: bytes):
    head, _, body = raw.partition(b"\r\n\r\n")
    lines = head.decode("iso-8859-1").split("\r\n")
    method, path, version = lines[0].split()
    headers = {}
    for line in lines[1:]:
        k, _, v = line.partition(":")
        headers[k.strip().lower()] = v.strip()
    return {"method": method, "path": path, "version": version,
            "headers": headers, "body": body}

def parse_response(raw: bytes):
    head, _, body = raw.partition(b"\r\n\r\n")
    lines = head.decode("iso-8859-1").split("\r\n")
    version, code, *reason = lines[0].split()
    headers = {}
    for line in lines[1:]:
        k, _, v = line.partition(":")
        headers[k.strip().lower()] = v.strip()
    return {"version": version, "status": int(code), "reason": " ".join(reason),
            "headers": headers, "body": body}

if __name__ == "__main__":
    req = (b"POST /api/login HTTP/1.1\r\n"
           b"Host: example.com\r\n"
           b"Content-Type: application/json\r\n"
           b"Content-Length: 29\r\n"
           b"\r\n"
           b'{"user":"sam","pw":"secret"}')
    parsed = parse_request(req)
    print("method:", parsed["method"], "path:", parsed["path"])
    print("content-type:", parsed["headers"]["content-type"])
    print("body:", parsed["body"].decode())

    resp = (b"HTTP/1.1 404 Not Found\r\n"
            b"Content-Type: text/html\r\n"
            b"Content-Length: 22\r\n"
            b"\r\n"
            b"<h1>404 Not Found</h1>")
    pr = parse_response(resp)
    print("\nstatus:", pr["status"], pr["reason"])
    print("is client error?", 400 <= pr["status"] < 500)
```

What it teaches: an HTTP message is *just structured text*, a first line, `key: value` headers, a blank line, then the body. Parsing it (split on `\r\n\r\n`, split the head into lines, split each header on the first `:`) is exactly what every web server and proxy does on the way in. Pair this parser with the chapter's raw-socket client and you can both *speak* and *understand* HTTP at the byte level, which is the whole game.

**Extension:** combine Part B's parser with the chapter's `raw_http.py` client so you fetch a real page and parse the live response into a structured dict; then follow a `301`/`302` redirect by reading the `Location` header and re-requesting.

### Solutions

1. `404` = **4xx client** error ("you messed up"). `500` = **5xx server** error ("I messed up"). `301` = **3xx redirection**. `200` = **2xx success**. `429` = **4xx client** error (Too Many Requests). One-word categories: 1xx informational, 2xx success, 3xx redirection, 4xx client error, 5xx server error.

2. **GET, PUT, DELETE are idempotent** (doing them twice has the same effect as once: GET reads, PUT sets the full resource to a value, DELETE removes it, repeating doesn't change the outcome). **POST is not** (two POSTs may create two records). Idempotency matters because networks fail mid-request; if a response is lost, a client can safely **retry** an idempotent request without risking duplicate side effects, but retrying a POST might double-create.

3. `dig +short example.com` returns the **A record(s)**, the IPv4 address(es). `dig example.com MX` returns the **MX records**, the mail servers (with priorities) responsible for email to that domain. Different record *types* in the same DNS database.

4. The server sends **`Set-Cookie: session=<id>`** in a response; the browser stores it and returns it as **`Cookie: session=<id>`** on every subsequent request to that domain. The server maps the session id to the user's server-side state, so statelessness on the wire is preserved while state lives server-side keyed by the cookie. Harden with **`HttpOnly`** (JS can't read it → mitigates XSS theft), **`Secure`** (sent only over HTTPS), and **`SameSite=Lax/Strict`** (limits cross-site sending → mitigates CSRF).

5. From a cold cache, the resolver asks: **(1) a root server** → "I don't know `www.example.com`, ask the `.com` TLD servers (here they are)"; **(2) a `.com` TLD server** → "ask `example.com`'s authoritative nameservers (here they are)"; **(3) `example.com`'s authoritative server** → returns the **A record** with the IP. The resolver caches the answer for its TTL and returns it. The hierarchy is read right-to-left (root → TLD → authoritative).

6. **Confidentiality** (encryption, eavesdroppers see only ciphertext), **integrity** (tampering is detectable via message authentication codes), and **authentication** (you're talking to the real server). **Authentication** comes from the **certificate + chain of trust**: a CA you trust signs a certificate binding the domain name to a public key, and during the handshake the server proves it holds the matching private key.

7. **HTTP/1.0** opened a new TCP connection per request (slow). **HTTP/1.1** added keep-alive (reuse one connection) but responses come back *in order* → **HTTP-level head-of-line blocking** (one slow response blocks the queue; browsers opened ~6 connections to fake parallelism). **HTTP/2** multiplexed many interleaved streams over one connection, fixing HTTP-level HOL, but it still rides **TCP**, so a single lost TCP packet stalls *all* streams (**TCP-level HOL**, unfixed). **HTTP/3** runs over **QUIC** (on UDP) with independently delivered streams, so one lost packet only stalls its own stream, escaping TCP HOL blocking entirely.

8. **Asymmetric** crypto (certificate verification + Diffie-Hellman key exchange) is used *once* during the handshake to authenticate the server and let two strangers agree on a shared secret over a tapped wire, but it's computationally **slow**. **Symmetric** crypto, using that agreed shared secret, then encrypts all the actual application data **fast**. You don't use asymmetric for everything because it'd be far too slow for bulk data; you don't use symmetric alone because two strangers can't safely agree on the shared key over an open wire without asymmetric's help. So: asymmetric solves key-agreement/identity, symmetric does the bulk work.

9. **Subject** = who the certificate is *for* (the domain, e.g. `CN=example.com` plus Subject Alternative Names listing all covered domains). **Issuer** = which Certificate Authority *signed* it (an intermediate CA). **Validity dates** (`notBefore`/`notAfter`) = the window the cert is valid; outside it browsers reject it. Your browser trusts the cert by verifying the **chain**: the leaf cert is signed by an intermediate, the intermediate by a root, and the root is in the browser/OS's pre-installed trusted-root store. If every signature checks out up to a trusted root *and* the domain matches *and* it's within the validity window, the cert is trusted.

10.
   ```python
   import socket
   def fetch(host, path="/", max_redirects=5):
       for _ in range(max_redirects):
           req = (f"GET {path} HTTP/1.1\r\nHost: {host}\r\nConnection: close\r\n\r\n").encode()
           with socket.socket() as s:
               s.connect((host, 80)); s.sendall(req)
               raw = b""
               while (chunk := s.recv(4096)):
                   raw += chunk
           head, _, body = raw.partition(b"\r\n\r\n")
           lines = head.decode("iso-8859-1").split("\r\n")
           status = int(lines[0].split()[1])
           headers = dict(l.split(":", 1) for l in lines[1:] if ":" in l)
           headers = {k.strip().lower(): v.strip() for k, v in headers.items()}
           print("status:", status)
           if status in (301, 302, 303, 307, 308) and "location" in headers:
               loc = headers["location"]
               # (real code parses the URL; here assume same-host absolute path)
               path = loc.split(host, 1)[-1] if host in loc else loc
               continue
           return body
       raise RuntimeError("too many redirects")
   print(fetch("example.com")[:200])
   ```
   It reads the status line, and on a 3xx with a `Location` header it re-requests the new path, capping at 5 hops to avoid redirect loops, exactly what `requests`/browsers do under the hood.
