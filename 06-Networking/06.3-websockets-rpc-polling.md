HTTP has a built-in assumption: the client asks, the server answers. The server can't just speak up. ## Start here: how do you find out when the pizza is ready?

You ordered a pizza (last chapter). How do you learn the moment it's done? The four real-time techniques map onto four ways to find out.

- **Short polling** = calling the pizzeria every two minutes: "Ready yet?" "No." *Two minutes later.* "Ready yet?" "No." Simple, but you waste a lot of calls, and you might be up to two minutes late hearing the good news. (Client repeatedly asks on a timer.)
- **Long polling** = calling and saying "I'll hold the line; tell me the moment it's ready." They keep you on hold and tell you the instant it's done, then you hang up and call back to wait for the next thing. Near-instant, but each piece of news still costs a whole phone call. (Server holds the request open until there's data.)
- **Server-Sent Events (SSE)** = the pizzeria has your number and keeps a one-way line open to announce updates ("in the oven... boxed... out for delivery"), but you can't talk back on that line. (Server streams events down one long-lived connection; one-way only.)
- **WebSockets** = you and the pizzeria keep a continuous open line where either of you can speak at any time: they announce progress, you say "actually, add garlic bread," back and forth instantly. (Persistent, full-duplex channel.)

The progression goes from "fake it by asking over and over" to "a real two-way open line." The engineering judgment is deciding which one you actually need: don't open a full WebSocket if a one-way SSE feed will do; don't poll if you need instant bidirectional chat.

**Why this matters:** real-time features are everywhere — chat, live dashboards, notifications, collaborative editing, multiplayer games, sports and finance tickers. Picking the right transport, and designing a graceful fallback for when the fancy one is blocked, is the kind of judgment that separates someone who uses libraries from someone who understands what they're choosing. The chapter also covers RPC (the "call a remote function" alternative to REST) and where file transfer and webhooks fit. The rest makes the pizza picture precise.

## The real-time problem

The web's request/response model means the server is mute until asked. So "show me new data as it arrives" is fundamentally awkward over plain HTTP. Four approaches evolved, from worst hack to purpose-built:

```text
SHORT POLLING:  client asks "anything new?" every N seconds, over and over.
LONG POLLING:   client asks; server HOLDS the request open until there's news, then replies.
SSE:            client opens ONE long-lived connection; server streams events down it (one-way).
WEBSOCKETS:     client & server open a persistent, FULL-DUPLEX channel; either side speaks anytime.
```

Let's weigh each.

---

## Short polling vs long polling vs SSE vs WebSockets (tradeoffs)

**Short polling.** The client sends a request on a timer (e.g., every 5s) asking "anything new?"

```text
Client: GET /updates → []         (5s later)
Client: GET /updates → []         (5s later)
Client: GET /updates → [new!]
```

- *Pros*: dead simple, plain HTTP, works everywhere, stateless.
- *Cons*: wasteful (most polls return nothing), and laggy (news waits up to the poll interval). Tune the interval and you trade latency against load; you can't win both.
- *Use when*: updates are infrequent and a few seconds of delay is fine, or simplicity trumps efficiency.

**Long polling.** The client requests, and the server holds the connection open until it actually has something (or times out), then responds; the client immediately re-requests.

```text
Client: GET /updates ───────(server holds it, no data yet)───────► [new!] (replies when ready)
Client: GET /updates ───────(holds again)...
```

- *Pros*: near-real-time without constant empty requests; still plain HTTP (works through old proxies/firewalls). This is the classic **WebSocket fallback**.
- *Cons*: each message still costs a full request/response cycle (headers, reconnect); holding many open requests ties up server resources; trickier server logic.
- *Use when*: you need low latency but can't use WebSockets (legacy infra, restrictive proxies).

**Server-Sent Events (SSE).** The client opens one long-lived HTTP connection (`Content-Type: text/event-stream`) and the server streams events down it continuously — one-way only (server → client).

```text
Client: GET /stream  (connection stays open)
Server: data: {"price": 100}\n\n
Server: data: {"price": 101}\n\n     ← keeps pushing on the same connection
```

- *Pros*: simple (just HTTP), auto-reconnect built into the browser `EventSource` API, efficient for server→client streams, works over HTTP/2.
- *Cons*: server→client only (the client still uses normal requests to send up); text-only; limited connection count per domain on HTTP/1.1.
- *Use when*: you only need to *push* (live feeds, notifications, progress, stock tickers) and don't need the client to stream back.

**WebSockets**, a single TCP connection upgraded to a persistent, **full-duplex** channel. Either side can send a message at any time, with low per-message overhead (small frames, no HTTP headers per message).

- *Pros*: true bidirectional, low latency, low overhead per message, binary or text. The right tool for interactive real-time (chat, games, collaborative editing, live dashboards with client interaction).
- *Cons*: more complex (stateful connections to manage/scale), not plain HTTP (needs WebSocket-aware infra), you handle reconnection/heartbeats yourself.
- *Use when*: you need genuine two-way, frequent, low-latency messaging.

**The decision guide to actually use:**

```text
Need bidirectional, frequent, low-latency?           → WebSockets
Only need server→client push (one-way feed)?         → SSE
Need low latency but stuck on plain HTTP/old infra?  → Long polling
Infrequent updates, simplicity wins?                 → Short polling
```

(This maps directly to real WebSocket dashboards: interactive, frequently-updating, low-latency → WebSockets, with long polling as the graceful fallback when WebSockets can't connect.)

## 📐 The WebSocket upgrade handshake & frames

A WebSocket connection *starts life as an HTTP request* and then upgrades. This is clever, it reuses port 443/80 and passes through HTTP infrastructure to get established.

**The upgrade handshake:**

```text
Client → Server (an ordinary HTTP/1.1 request with upgrade headers):
   GET /chat HTTP/1.1
   Host: example.com
   Upgrade: websocket
   Connection: Upgrade
   Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==     ← random base64 nonce
   Sec-WebSocket-Version: 13

Server → Client (the 101 that flips the protocol):
   HTTP/1.1 101 Switching Protocols                ← remember 101 from the HTTP chapter!
   Upgrade: websocket
   Connection: Upgrade
   Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=  ← SHA-1(key + magic GUID), base64

After the 101, the TCP connection is no longer HTTP - it's a full-duplex WebSocket.
```

The `Sec-WebSocket-Accept` is computed by the server hashing the client's key plus a fixed "magic" GUID, proof the server actually understood the WebSocket handshake (not a cached/confused HTTP response). That `101 Switching Protocols` status is exactly the one flagged in the HTTP chapter.

**Frames.** After the handshake, data flows as lightweight **frames**, not HTTP messages. A frame header carries: a FIN bit (is this the last fragment?), an **opcode** (text / binary / close / ping / pong), a **mask** flag (client→server frames must be masked with a random key, an anti-cache-poisoning measure), and a payload length. The overhead is just a few bytes per message versus HTTP's hundreds of bytes of headers, which is why WebSockets are efficient for chatty traffic. **Ping/pong** frames are the built-in heartbeat to detect dead connections.

## 📐 RPC, gRPC & protocol buffers - a different mental model from REST

**REST** thinks in **resources (nouns)**: you GET/POST/PUT/DELETE *things* at URLs. **RPC (Remote Procedure Call)** thinks in **functions (verbs)**: you *call a function that happens to run on another machine*, as if it were local.

```text
REST mindset:   "operate on the user resource"
   PUT /users/42   {name: "Sam"}

RPC mindset:    "call a function on the server"
   updateUser(id=42, name="Sam")   ← looks like a normal function call;
                                      the network is hidden under the hood
```

The dream of RPC is **location transparency**: calling a remote function feels like calling a local one. Under the hood, a **client stub** serializes (marshals) the arguments, ships them over the network, the server unmarshals and runs the real function, and the result is shipped back. The plumbing is hidden, which is the appeal and the danger (network calls *aren't* really like local calls: they fail, they're slow, they time out).

**gRPC** is Google's modern RPC framework:
- Uses **Protocol Buffers (protobuf)**, a compact **binary** serialization format with a schema (`.proto` files). You define messages and services once; a code generator produces typed client and server stubs in many languages.
- Runs over **HTTP/2**, so it gets multiplexing and supports **streaming** RPCs (client-stream, server-stream, bidirectional).
- Strongly typed contracts (the `.proto` schema), much smaller/faster on the wire than JSON.

```protobuf
// example.proto - the contract both sides compile against
service UserService {
  rpc GetUser (UserRequest) returns (UserReply);   // a remote function signature
}
message UserRequest { int32 id = 1; }
message UserReply   { int32 id = 1; string name = 2; }
```

**gRPC/RPC vs REST, when each:**

```text
REST  → public APIs, browser-facing, human-debuggable (JSON over HTTP/1.1),
        loose coupling, caching via HTTP semantics.
gRPC  → internal service-to-service (microservices), high throughput, low latency,
        strict typed contracts, streaming. Binary protobuf is fast but not human-readable,
        and needs gRPC-aware tooling (less browser-friendly historically).
```

**JSON-RPC** is the simple middle ground: RPC semantics (call a named method with params, get a result) encoded as plain JSON, easy to implement over HTTP or a socket, we'll build one below.

**Message-passing preview.** RPC is *synchronous* request/response ("call and wait"). The other big paradigm is **asynchronous message passing** via a broker/queue (RabbitMQ, Kafka): a producer drops a message on a queue and moves on; consumers process it later. This decouples sender from receiver in time and is the backbone of event-driven architectures, a topic for later, but worth filing next to RPC as the *other* way services talk.

## 📐 FTP/SFTP (mostly legacy) & webhooks

**FTP (File Transfer Protocol)** is one of the oldest internet protocols, transfer files between hosts. It's largely **legacy** now because:
- It sends credentials and data **in plaintext** (no encryption), a security non-starter today.
- It uses **two connections** (a control channel and a separate data channel), which is awkward with NAT and firewalls.

The modern replacements:
- **SFTP (SSH File Transfer Protocol)**, file transfer tunneled over **SSH**, so it's encrypted and uses a single connection. This is what you actually use. (Confusingly named, it's not "FTP with S," it's a different protocol over SSH.)
- **FTPS**, FTP with TLS bolted on (less common than SFTP).
- In practice, file transfer today is mostly HTTPS APIs, object storage (S3), or SFTP for legacy/enterprise pipelines.

**Webhooks** flip the polling problem for *server-to-server*. Instead of service A polling service B "anything new?", B calls *you*: you register a URL, and when an event happens (payment succeeded, PR merged), B sends an HTTP POST to your URL with the event data. It's "**don't call us, we'll call you**", a reverse, event-driven HTTP callback. Cheaper and timelier than polling an API, widely used by Stripe, GitHub, etc. (The catch: you must expose a public endpoint and verify the payload's signature, since anyone could POST to it.)

## 💻 Build it: WebSocket echo, SSE, long polling, JSON-RPC

### WebSocket echo server + client (`websockets` library)

```python
# ws_echo_server.py   (pip install websockets)
import asyncio
import websockets

async def echo(websocket):
    async for message in websocket:        # async iterate over incoming frames
        print("recv:", message)
        await websocket.send(f"echo: {message}")   # push back over the same connection

async def main():
    async with websockets.serve(echo, "127.0.0.1", 8765):
        print("ws echo server on ws://127.0.0.1:8765")
        await asyncio.Future()             # run forever

asyncio.run(main())
```

```python
# ws_echo_client.py
import asyncio, websockets

async def main():
    async with websockets.connect("ws://127.0.0.1:8765") as ws:
        for msg in ["hello", "websockets", "are full-duplex"]:
            await ws.send(msg)
            print("got:", await ws.recv())

asyncio.run(main())
```

The `async for message in websocket` is the whole point: the connection stays open and either side sends whenever it wants, no polling, no re-requesting.

### Server-Sent Events (one-way push over plain HTTP)

```python
# sse_server.py - a raw SSE stream; open http://127.0.0.1:8200 and watch numbers stream in
import http.server, time, json

class SSEHandler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/stream":
            self.send_response(200)
            self.send_header("Content-Type", "text/event-stream")   # the SSE content type
            self.send_header("Cache-Control", "no-cache")
            self.end_headers()
            i = 0
            try:
                while True:
                    payload = json.dumps({"tick": i, "value": 100 + i})
                    self.wfile.write(f"data: {payload}\n\n".encode())  # "data: ...\n\n" per event
                    self.wfile.flush()
                    i += 1
                    time.sleep(1)
            except (BrokenPipeError, ConnectionResetError):
                pass   # client closed
        else:
            self.send_response(200); self.end_headers()
            self.wfile.write(b"""<script>
              const es = new EventSource('/stream');         // browser auto-reconnects
              es.onmessage = e => document.body.innerHTML += JSON.parse(e.data).value + '<br>';
            </script>SSE stream:<br>""")

http.server.HTTPServer(("127.0.0.1", 8200), SSEHandler).serve_forever()
```

Each event is literally `data: <payload>\n\n`. The browser's `EventSource` reconnects automatically if the stream drops, that built-in resilience is SSE's quiet superpower.

### Long polling (low latency over plain HTTP)

```python
# long_poll_server.py - server holds the request until data is ready (or times out)
import http.server, queue, threading, time, json

events = queue.Queue()

def producer():                       # simulate news arriving every few seconds
    n = 0
    while True:
        time.sleep(3); n += 1
        events.put({"news": n})

class LongPollHandler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/poll":
            try:
                item = events.get(timeout=25)     # BLOCK here until data OR 25s timeout
                body = json.dumps(item).encode()
            except queue.Empty:
                body = b'{"news": null}'          # nothing yet; client will re-poll
            self.send_response(200)
            self.send_header("Content-Type", "application/json")
            self.end_headers()
            self.wfile.write(body)

threading.Thread(target=producer, daemon=True).start()
print("long-poll server on http://127.0.0.1:8300/poll  (curl it; it hangs until news arrives)")
http.server.HTTPServer(("127.0.0.1", 8300), LongPollHandler).serve_forever()
```

`curl http://127.0.0.1:8300/poll`, notice it *hangs* (the server holds it) until the producer publishes, then returns instantly. That "hold the request open" is the entire long-polling trick.

### JSON-RPC server + client (RPC over a socket)

```python
# jsonrpc_server.py - minimal JSON-RPC 2.0 over a TCP socket
import socket, json

METHODS = {                            # the "remote functions" we expose
    "add":      lambda a, b: a + b,
    "multiply": lambda a, b: a * b,
    "greet":    lambda name: f"Hello, {name}!",
}

def handle(request):
    try:
        req = json.loads(request)
        method = METHODS[req["method"]]            # look up the named function
        result = method(*req.get("params", []))    # call it with the params
        return json.dumps({"jsonrpc": "2.0", "result": result, "id": req["id"]})
    except KeyError:
        return json.dumps({"jsonrpc": "2.0",
                           "error": {"code": -32601, "message": "Method not found"},
                           "id": req.get("id")})

srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("127.0.0.1", 8400)); srv.listen()
print("json-rpc server on 127.0.0.1:8400")
while True:
    conn, _ = srv.accept()
    with conn:
        data = conn.recv(4096).decode()
        if data:
            conn.sendall(handle(data).encode())
```

```python
# jsonrpc_client.py
import socket, json

def call(method, *params, _id=1):
    req = json.dumps({"jsonrpc": "2.0", "method": method, "params": list(params), "id": _id})
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as s:
        s.connect(("127.0.0.1", 8400))
        s.sendall(req.encode())
        resp = json.loads(s.recv(4096).decode())
    return resp.get("result", resp.get("error"))

print(call("add", 2, 3))           # 5      ← feels like a local function call...
print(call("greet", "Spencer"))    # Hello, Spencer!     ...but it ran on the server
print(call("nope"))                # {'code': -32601, 'message': 'Method not found'}
```

`call("add", 2, 3)` *looks* like calling a local function but executes on the server, that illusion of "the network isn't there" is the entire RPC idea, made tangible.

## 🧪 Mini-project: a live "ticker" dashboard over WebSockets (with long-polling fallback)

This mirrors real D3/WebSocket dashboards: the server pushes simulated price updates; the browser renders a live-updating ticker. One self-contained file: a `websockets` server that also serves the HTML page.

```python
# ticker_dashboard.py   (pip install websockets)
import asyncio, json, random, datetime
import websockets
from websockets.asyncio.server import serve
from http import HTTPStatus

SYMBOLS = {"AAPL": 180.0, "GOOG": 140.0, "TSLA": 250.0}

PAGE = """<!doctype html><meta charset=utf-8><title>Live Ticker</title>
<style>body{font:16px system-ui;padding:2rem}.up{color:#0a0}.down{color:#c00}
table{border-collapse:collapse}td,th{padding:.4rem 1rem;border-bottom:1px solid #ddd}</style>
<h1>Live Ticker <small id=status>connecting...</small></h1>
<table><thead><tr><th>Symbol<th>Price<th>Change</tr></thead><tbody id=rows></tbody></table>
<script>
const rows = document.getElementById('rows'), status = document.getElementById('status');
const cells = {};
function render(sym, price, change){
  if(!cells[sym]){ const tr=document.createElement('tr');
    tr.innerHTML=`<td>${sym}</td><td class=p></td><td class=c></td>`;
    rows.appendChild(tr); cells[sym]=tr; }
  const tr=cells[sym];
  tr.querySelector('.p').textContent = price.toFixed(2);
  const c = tr.querySelector('.c');
  c.textContent = (change>=0?'+':'') + change.toFixed(2);
  c.className = 'c ' + (change>=0?'up':'down');
}
// PRIMARY: WebSocket. Real apps fall back to long polling if this fails to connect.
const ws = new WebSocket(`ws://${location.host}/`);
ws.onopen  = () => status.textContent='● live (websocket)';
ws.onclose = () => { status.textContent='○ disconnected - would fall back to long polling';
                     /* fallbackLongPoll();  // see note below */ };
ws.onmessage = e => { const d=JSON.parse(e.data); render(d.symbol, d.price, d.change); };
</script>"""

async def process_request(connection, request):
    # If it's NOT a WebSocket upgrade, serve the HTML page over plain HTTP.
    if request.headers.get("Upgrade", "").lower() != "websocket":
        return connection.respond(HTTPStatus.OK, PAGE)
    return None   # None → let it proceed as a WebSocket upgrade

async def stream_prices(websocket):
    print("client connected")
    try:
        while True:
            sym = random.choice(list(SYMBOLS))
            change = round(random.uniform(-2, 2), 2)
            SYMBOLS[sym] = round(SYMBOLS[sym] + change, 2)
            await websocket.send(json.dumps({
                "symbol": sym, "price": SYMBOLS[sym], "change": change,
                "ts": datetime.datetime.utcnow().isoformat()}))
            await asyncio.sleep(0.7)        # push a new tick ~every 0.7s
    except websockets.ConnectionClosed:
        print("client disconnected")

async def main():
    async with serve(stream_prices, "127.0.0.1", 8500, process_request=process_request):
        print("ticker dashboard → http://127.0.0.1:8500")
        await asyncio.Future()

if __name__ == "__main__":
    asyncio.run(main())
```

Run it and open `http://127.0.0.1:8500`, prices update live, green/red by direction, with no polling: the server *pushes* each tick. This is the shape of every real-time dashboard.

**The fallback story (why you'd design it this way in production):** WebSockets are the primary transport, but some corporate proxies/firewalls block the upgrade. A robust client detects `ws.onclose`/connection failure and **falls back to long polling** the same data from an HTTP endpoint, slower and chattier, but it works through restrictive infra. So the architecture is: *try WebSockets first; degrade to long polling; degrade to short polling as a last resort.* Same data model, three transports of decreasing efficiency, graceful degradation, which is exactly the engineering judgment this whole chapter is about. (Implementing the actual `fallbackLongPoll()` against a `/poll` endpoint like the one in the Build-it section is a great extension.)

For the D3 version: swap the `<table>` render for a D3 line chart, `push` each tick into a rolling array, and re-draw, the data transport (WebSocket push) is identical; only the visualization layer changes.

## ⚠️ Common mistakes

Real-time systems have their own family of footguns. These are the recurring ones.

- **Reaching for WebSockets when SSE (or polling) would do.** WebSockets are stateful, harder to scale, and need WS-aware infrastructure. If you only push *one-way* (a feed, notifications, a read-only ticker), SSE is simpler and auto-reconnects. Don't pay for bidirectionality you don't use.
- **Forgetting that polling trades latency against load.** Shorten the interval for freshness and you hammer the server with mostly-empty requests; lengthen it to save load and news arrives late. You can't win both with short polling, that tradeoff *is* short polling.
- **No heartbeat / dead-connection detection on WebSockets.** TCP connections can silently die (a laptop sleeps, a NAT entry expires) without a clean close. Without ping/pong heartbeats, the server thinks ghosts are still connected. Use the built-in ping/pong frames.
- **No reconnection logic.** Networks drop. A production WebSocket/SSE client needs reconnect-with-backoff; SSE's `EventSource` does this for free, but raw WebSockets you handle yourself.
- **Holding too many long-poll requests open.** Each held request ties up a server worker/connection. At scale, thousands of held requests can exhaust the server's connection pool, long polling doesn't scale like SSE/WebSockets.
- **Treating RPC like a local function call.** The whole *appeal* of RPC (location transparency) is also its trap: remote calls fail, time out, and are orders of magnitude slower than local calls. Always handle network errors and timeouts; never assume a remote call "just returns."
- **Using FTP in anything new.** It sends credentials in plaintext and is NAT-hostile. Use SFTP (over SSH) or HTTPS-based transfer.
- **Not verifying webhook signatures.** Your webhook URL is public; anyone can POST to it. Always verify the signature (HMAC) the provider sends, or you'll process forged events.
- **Forgetting WebSockets ride the same ports as HTTP(S).** They start as an HTTP upgrade on 80/443, so they pass through most firewalls, but some corporate proxies still block the upgrade, which is exactly why you design a fallback.

## 💼 On the job / interview angle

Real-time and RPC topics come up in both interviews and real architecture decisions.

- **"How would you build a chat app / live notifications / a real-time dashboard?"** is a very common system-design prompt. The expected answer is the decision among polling/long-polling/SSE/WebSockets *with justification*, and bonus points for mentioning fallback/graceful degradation and scaling stateful connections.
- **"Difference between WebSockets and HTTP / what is the upgrade handshake?"**, know that WebSockets begin as an HTTP `Upgrade` request answered with `101 Switching Protocols`, then become a persistent full-duplex frame-based channel.
- **"SSE vs WebSockets, when each?"**, one-way push → SSE; bidirectional → WebSockets. A clean, frequently-asked distinction.
- **"REST vs RPC / gRPC, when would you choose each?"**, public/browser-facing/human-debuggable → REST; internal service-to-service, high-throughput, typed contracts, streaming → gRPC. Microservice-heavy companies love this question.
- **"What is a webhook and how do you secure it?"**, reverse callback ("don't call us, we'll call you"); secure it by verifying the signature.
- **On the job:** these are everyday architecture choices. You'll wire up notifications, build dashboards, integrate third-party webhooks (Stripe, GitHub, Slack), and call internal services over gRPC or JSON over HTTP. The judgment this chapter builds, match the transport to the actual communication pattern, and degrade gracefully when the ideal one is unavailable, is precisely the engineering maturity senior roles look for. The ticker dashboard mini-project mirrors real production dashboards; being able to explain *why* WebSockets with a long-poll fallback is a defensible architecture is exactly the kind of reasoning that lands offers.

## 🧪 Mini-project: a transport benchmark - short polling vs long polling vs SSE

The chapter shows each technique in isolation. This project puts the first three head-to-head on the *same* event source so the latency-vs-efficiency tradeoffs become numbers you can see. One server exposes all three endpoints against a shared event stream; a client driver measures, for each, how *fresh* the data is and how many requests it cost.

```python
# realtime_bench.py - one server, three transports, against a shared event source.
# Run the server, then run with `client` arg in another terminal.
import http.server, socketserver, threading, queue, time, json, sys, urllib.request

# ---- shared event source: a new "event" appears every ~2 seconds ----
LATEST = {"seq": 0, "ts": time.time()}
SUBSCRIBERS = []   # queues for long-poll / SSE waiters

def event_producer():
    while True:
        time.sleep(2)
        LATEST["seq"] += 1
        LATEST["ts"] = time.time()
        for q in list(SUBSCRIBERS):
            try: q.put_nowait(dict(LATEST))
            except queue.Full: pass

class Handler(http.server.BaseHTTPRequestHandler):
    def log_message(self, *a): pass   # quiet

    def do_GET(self):
        if self.path == "/short":                       # short poll: return latest immediately
            self._json(LATEST)
        elif self.path == "/long":                      # long poll: hold until a NEW event
            q = queue.Queue(maxsize=1); SUBSCRIBERS.append(q)
            try:
                item = q.get(timeout=30)                 # block until producer publishes
            except queue.Empty:
                item = {"seq": LATEST["seq"], "timeout": True}
            finally:
                SUBSCRIBERS.remove(q)
            self._json(item)
        elif self.path == "/sse":                       # SSE: stream events forever
            q = queue.Queue(); SUBSCRIBERS.append(q)
            self.send_response(200)
            self.send_header("Content-Type", "text/event-stream")
            self.end_headers()
            try:
                while True:
                    item = q.get()
                    self.wfile.write(f"data: {json.dumps(item)}\n\n".encode())
                    self.wfile.flush()
            except (BrokenPipeError, ConnectionResetError):
                SUBSCRIBERS.remove(q)
        else:
            self._json({"error": "unknown"}, 404)

    def _json(self, obj, code=200):
        body = json.dumps(obj).encode()
        self.send_response(code)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

class ThreadingServer(socketserver.ThreadingMixIn, http.server.HTTPServer):
    daemon_threads = True

def run_server():
    threading.Thread(target=event_producer, daemon=True).start()
    print("bench server on http://127.0.0.1:8600  (/short /long /sse)")
    ThreadingServer(("127.0.0.1", 8600), Handler).serve_forever()

# ---- client driver: measure freshness + request count over a window ----
def measure_short(seconds=12, interval=1.0):
    requests, lag_samples, end = 0, [], time.time() + seconds
    while time.time() < end:
        r = json.load(urllib.request.urlopen("http://127.0.0.1:8600/short"))
        requests += 1
        lag_samples.append(time.time() - r["ts"])   # how stale was the data we got?
        time.sleep(interval)
    return requests, sum(lag_samples)/len(lag_samples)

def measure_long(seconds=12):
    requests, lag_samples, end = 0, [], time.time() + seconds
    while time.time() < end:
        r = json.load(urllib.request.urlopen("http://127.0.0.1:8600/long", timeout=35))
        requests += 1
        if "ts" in r:
            lag_samples.append(time.time() - r["ts"])
    avg = sum(lag_samples)/len(lag_samples) if lag_samples else float("nan")
    return requests, avg

def run_client():
    print("measuring SHORT polling (1s interval, 12s)...")
    sreq, slag = measure_short()
    print(f"  short: {sreq} requests, avg staleness {slag:.2f}s")
    print("measuring LONG polling (12s)...")
    lreq, llag = measure_long()
    print(f"  long:  {lreq} requests, avg staleness {llag:.2f}s")
    print("\nTakeaway: short polling makes MANY requests for STALE data;")
    print("long polling makes FEW requests for FRESH data (it waited for events).")
    print("SSE would be 1 request total, streaming all events live (open /sse with curl to see).")

if __name__ == "__main__":
    (run_client if sys.argv[1:] == ["client"] else run_server)()
```

Run `python3 realtime_bench.py` in one terminal, then `python3 realtime_bench.py client` in another, and watch the numbers. Also `curl -N http://127.0.0.1:8600/sse` to see SSE stream events with a *single* request.

What it makes concrete:
- **Short polling**: many requests, and the data is often *stale* (you fetched between events, or just missed one), the load-vs-latency tradeoff in numbers.
- **Long polling**: far fewer requests, each returning *fresh* data the instant an event fired, because the server held the request until it had news.
- **SSE**: one request, all events streamed, the most efficient of the three for one-way push.

Seeing "short polling = N requests for stale data, long polling = few requests for fresh data" as actual measured numbers is the chapter's central tradeoff, proven rather than asserted.

**Extension:** add a `/ws` WebSocket endpoint (using the `websockets` library, as in the ticker project) and a client that counts frames received vs requests sent, it should be one connection carrying all events, the gold standard, and a natural lead-in to "WebSockets first, long-poll fallback."

## ✏️ Exercises

A mix of judgment calls (the core skill here) and mechanics. Easy → hard.

1. **(Easy)** In one line each, describe short polling, long polling, SSE, and WebSockets.
2. **(Easy)** You're building a read-only live stock ticker the user only watches (never sends data back). Which transport, and why?
3. **(Easy)** Which HTTP status code signals a successful WebSocket upgrade, and what header does the server return to prove it understood the handshake?
4. **(Medium)** A real-time chat app needs the client to also send messages, frequently, with low latency. Which transport, and what fallback would you design for restrictive corporate networks?
5. **(Medium)** Contrast the *mental model* of REST vs RPC with a concrete example of the same operation in each style.
6. **(Medium)** Why is FTP considered legacy, and what should you use instead? Name two specific problems with FTP.
7. **(Hard)** Explain the full WebSocket upgrade handshake: the client headers, the server's response, and how `Sec-WebSocket-Accept` is computed and why it exists.
8. **(Hard)** What does gRPC use for serialization and transport, and give two concrete reasons it can be faster/smaller on the wire than JSON-over-HTTP/1.1 REST. When would you still pick REST?
9. **(Hard)** A webhook endpoint you expose starts receiving forged events. Explain the vulnerability and exactly how you'd fix it.
10. **(Stretch)** Design (in prose + a small diagram) a notifications system that tries WebSockets first, degrades to long polling, then to short polling, sharing one data model. Describe how the client decides to degrade and how the server supports all three.

### Solutions

1. **Short polling**: the client re-requests on a fixed timer ("anything new?"), simple, wasteful, laggy. **Long polling**: the client requests and the server holds the connection open until it has data, then responds, low latency over plain HTTP. **SSE**: the client opens one long-lived connection and the server streams events down it, one-way (server→client), auto-reconnecting. **WebSockets**: a persistent full-duplex channel either side can send on at any time, true bidirectional, low per-message overhead.

2. **SSE.** It's purely server→client push (the user only watches), and SSE is simpler than WebSockets, runs over plain HTTP, and the browser's `EventSource` reconnects automatically. You don't need the bidirectionality (or the added complexity) of WebSockets.

3. **`101 Switching Protocols`.** The server returns `Sec-WebSocket-Accept`, computed from the client's `Sec-WebSocket-Key` plus a fixed magic GUID (SHA-1, base64), proving the server actually understood the WebSocket handshake rather than echoing a confused/cached HTTP response.

4. **WebSockets**, bidirectional, frequent, low-latency messaging is exactly their sweet spot. Fallback: **long polling** for environments where a corporate proxy/firewall blocks the WebSocket upgrade (and short polling as a last resort). The client detects the WS connection failing/closing and switches to long-polling the same data endpoint, graceful degradation.

5. **REST** thinks in **resources (nouns)**: you act on things at URLs with HTTP verbs, e.g., `PUT /users/42 {name:"Sam"}` to update user 42. **RPC** thinks in **functions (verbs)**: you call a named procedure that runs remotely, e.g., `updateUser(id=42, name="Sam")`, which *looks* like a local call but the client stub marshals the args over the network. REST is resource-oriented; RPC is action-oriented and aims for location transparency.

6. FTP is legacy because **(1)** it transmits credentials and data **in plaintext** (no encryption, trivially sniffable), and **(2)** it uses **two separate connections** (a control channel and a data channel), which is awkward and often broken behind NAT/firewalls. Use **SFTP** (file transfer over an encrypted SSH connection, single channel) instead, or HTTPS-based transfer / object storage for new systems.

7. The client sends an ordinary HTTP/1.1 GET with `Upgrade: websocket`, `Connection: Upgrade`, a random `Sec-WebSocket-Key` (base64 nonce), and `Sec-WebSocket-Version: 13`. The server, if it speaks WebSocket, replies `HTTP/1.1 101 Switching Protocols` with `Upgrade: websocket`, `Connection: Upgrade`, and `Sec-WebSocket-Accept`. **`Sec-WebSocket-Accept` = base64(SHA-1(client_key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"))**, the client appends the same magic GUID, computes the hash itself, and checks it matches. This proves the server is a genuine WebSocket server that processed *this* handshake (not a proxy replaying a cached response). After the 101, the TCP connection drops HTTP framing and carries lightweight WebSocket frames.

8. gRPC uses **Protocol Buffers** (a compact, schema-defined *binary* serialization) over **HTTP/2**. It's faster/smaller because **(1)** protobuf binary is much more compact than verbose JSON text and requires no string parsing, and **(2)** HTTP/2 multiplexes many calls over one connection and compresses headers (and supports streaming), avoiding HTTP/1.1's per-request overhead and head-of-line blocking. You'd still pick **REST** for public, browser-facing, human-debuggable APIs where JSON readability, HTTP caching semantics, and universal tooling matter more than raw throughput.

9. The vulnerability: your webhook URL is **publicly reachable**, so *anyone* can POST forged event payloads to it, and naive code processes them as if they came from the real provider (fake "payment succeeded" events, etc.). Fix: **verify the signature** the provider includes (typically an HMAC of the raw request body using a shared secret, sent in a header like `X-Signature`). Recompute the HMAC over the received body with your secret and reject the request if it doesn't match. Also validate timestamps to prevent replay, and use HTTPS.

10. **Design.** Same data model: a stream of notification events, each with an id/sequence number. The server exposes three endpoints over the *same* event source: `/ws` (WebSocket, full push), `/poll` (long poll, holds until a new event or timeout), and `/short` (returns latest immediately). The client attempts WebSockets first:
   ```text
   Client startup
      │
      ▼
   try WebSocket ──success──► stream events live (best)
      │ fail / onclose
      ▼
   try long poll ──success──► hold-and-fetch loop (good, plain HTTP)
      │ fail (proxy buffers/limits)
      ▼
   short poll every N s ─────► last resort (works everywhere)
   ```
   The client degrades on connection failure/close (and could send the last-seen sequence number so it doesn't miss or duplicate events across a switch). The server supports all three by reading from one shared event source (e.g., a pub/sub or in-memory queue per subscriber), so the *data* is identical across transports, only the delivery mechanism and efficiency differ. This is graceful degradation: best experience where possible, guaranteed function everywhere.

## ✅ Teach it back

1. **Contrast short polling, long polling, SSE, and WebSockets in one line each.** Short polling: client re-asks on a timer (simple, wasteful, laggy). Long polling: server holds the request open until it has data (low latency over plain HTTP, the classic WS fallback). SSE: one long-lived connection the server streams events down (one-way, server→client, auto-reconnect). WebSockets: a persistent full-duplex channel either side can send on anytime (true bidirectional, low overhead).

2. **When would you choose SSE over WebSockets, and vice versa?** SSE when you only need **server→client** push (live feeds, notifications, a read-only ticker), it's simpler and reconnects automatically. WebSockets when you need **bidirectional**, frequent, low-latency messaging (chat, games, interactive dashboards) where the client also sends data back.

3. **How does a WebSocket connection get established, and what HTTP status signals it?** It begins as an ordinary HTTP/1.1 GET with `Upgrade: websocket` and `Connection: Upgrade` headers plus a random `Sec-WebSocket-Key`. The server replies **`101 Switching Protocols`** with a `Sec-WebSocket-Accept` derived from the key + a magic GUID, proving it understood the handshake. After the 101, the TCP connection is a full-duplex WebSocket carrying lightweight frames instead of HTTP messages.

4. **Explain the mental-model difference between REST and RPC.** REST thinks in **resources/nouns**, you manipulate things at URLs with HTTP verbs (`PUT /users/42`). RPC thinks in **functions/verbs**, you call a named procedure that happens to run on another machine (`updateUser(42, ...)`), with the network plumbing hidden by a client stub. REST is resource-oriented; RPC is action-oriented and aims for location transparency.

5. **What does gRPC use for serialization and transport, and when would you pick it over REST?** gRPC uses **Protocol Buffers** (compact, schema-defined binary) over **HTTP/2** (multiplexing + streaming). Pick gRPC for internal service-to-service communication needing high throughput, low latency, strict typed contracts, and streaming. Pick REST for public, browser-facing, human-debuggable APIs where JSON-over-HTTP and HTTP caching matter more than raw speed.

6. **Why is FTP considered legacy, and what is a webhook?** FTP sends credentials/data in plaintext and uses two connections (control + data), which is insecure and NAT/firewall-hostile, replaced by **SFTP** (file transfer over encrypted SSH, single connection). A **webhook** inverts polling for server-to-server: instead of you polling a service, you register a URL and the service POSTs event data to you when something happens ("don't call us, we'll call you"), event-driven, timely, and cheaper than polling.
