## Theory

### The consensus problem, stated precisely

`N` processes each *propose* a value; they must all *decide* on one value. A correct consensus protocol satisfies:

- **Agreement (safety):** no two correct processes decide *different* values. (Never contradict.)
- **Validity (safety):** the decided value was *proposed* by some process. (No making up values.)
- **Integrity:** each process decides *at most once*.
- **Termination (liveness):** every correct process *eventually* decides.

The deep tension is **safety vs liveness**. Safety = "nothing bad ever happens" (never two leaders, never two conflicting decisions). Liveness = "something good eventually happens" (a decision *is* reached). Real protocols guarantee **safety always** and **liveness when the network behaves**, they will *pause* (sacrifice liveness) rather than ever violate safety. That priority, *correctness over progress*, is the single most important design principle in this whole area. A consensus system that's temporarily stuck is annoying; one that decided two different values is catastrophic.

Consensus is universal: leader election ("agree on who's leader"), atomic commit ("agree commit vs abort"), and the next log entry ("agree on entry #k") are all consensus instances. Solve it once, reuse forever.

### The FLP impossibility - intuition

In 1985, Fischer, Lynch, and Paterson proved a result that shaped the field:

> In a **fully asynchronous** system (no bounds on message delay or processing time), where even **one** process may crash, there is **no** deterministic algorithm that **guarantees** consensus (satisfies agreement, validity, *and* termination in all runs).

The intuition (not the formal proof): in a purely asynchronous world, you **cannot distinguish a crashed process from a merely slow one** (26.1's stubborn truth). So at the decisive moment, a protocol faces a fork: wait for the silent process (and risk waiting forever if it truly crashed, violating termination) or proceed without it (and risk that it was alive and about to send a value that would have changed the outcome, risking a violation of agreement). The proof shows an adversary controlling message timing can *always* keep the system in this "not yet decided" limbo forever. So no deterministic protocol can promise to *always* terminate.

**This is not a counsel of despair**, it says you can't have *all three* of {safety, liveness, full-async-with-a-failure} guaranteed simultaneously. Real systems keep **safety unconditionally** and *relax the model* to recover liveness. The three escape hatches:

1. **Timeouts (partial synchrony).** Assume the network is *eventually* timely. Use timeouts to suspect crashed nodes and make progress during good periods. If you're wrong (suspect a live node), you might delay a decision (lose liveness *temporarily*) but you *never* violate safety. Raft and Paxos take this route.
2. **Randomization.** Inject random choices (random election timeouts, random coin-flips). The adversary can't perfectly schedule against randomness, so the protocol terminates with probability 1 (Ben-Or's algorithm; Raft's randomized election timeouts).
3. **Failure detectors.** Assume an oracle that *eventually* correctly suspects crashed processes (the "◇S" detector). With it, consensus becomes solvable. In practice a failure detector is just timeouts wearing a tuxedo.

The takeaway to repeat in interviews: **FLP says guaranteed consensus is impossible in pure async with one failure; real systems escape by assuming partial synchrony (timeouts) and/or randomness, always preserving safety and accepting that liveness depends on the network behaving.**

### Leader election

Many designs simplify consensus by first electing **one** leader, then routing all decisions through it (turning a hard symmetric problem into a simple "the leader decides, others follow"). Election is itself a consensus instance: agree on *who*. Key hazards:

- **Split-brain:** two nodes both believe they're leader (e.g. after a partition heals, or a falsely-suspected leader that didn't actually die). Two leaders accepting writes = divergent state = corruption. Prevented with **majority quorums** (only a node with majority support can lead, and two majorities can't coexist in one cluster) and **fencing tokens** (a monotonically increasing leader epoch; storage rejects writes stamped with a stale epoch, so a deposed leader's late writes are ignored).
- **Term/epoch numbers:** every leadership reign gets a strictly increasing number. This lets nodes recognize and reject messages from *old* leaders. Both Raft (terms) and Paxos (ballot/proposal numbers) hinge on this monotonic counter.

### Paxos - the intuition (as clear as it gets)

Paxos (Lamport, 1998) is the foundational consensus algorithm, correct, minimal, and famously hard to grok. Let's build the intuition for **single-decree Paxos** (agreeing on *one* value). Three roles (a node can play several):

- **Proposers** propose values.
- **Acceptors** vote; a value is *chosen* when a **majority** of acceptors accept it. (Majority quorums again, any two majorities overlap, so two different values can't both be chosen.)
- **Learners** find out what was chosen.

Every proposal carries a unique, increasing **proposal number** `n` (the ballot). Two phases:

**Phase 1, Prepare / Promise.**
1. A proposer picks a number `n` higher than any it has used and sends **Prepare(n)** to a majority of acceptors.
2. An acceptor receiving Prepare(n): if `n` is the highest it has seen, it **Promises** not to accept any proposal numbered `< n`, and replies with the highest-numbered proposal it has *already accepted* (if any), value and its number.

**Phase 2, Accept / Accepted.**
3. If the proposer gets promises from a majority, it sends **Accept(n, v)**. The crucial safety rule: **`v` is NOT free**. If *any* promise reported an already-accepted value, the proposer **must** use the value with the *highest* reported proposal number. Only if *no* acceptor reported a prior value may it use its own.
4. An acceptor receiving Accept(n, v) accepts it *unless* it has since promised a higher number. When a majority accepts `(n, v)`, `v` is **chosen**.

**Why it's safe (the heart of Paxos).** Suppose value `v` is chosen by a majority at proposal number `n`. Any *later* proposal with number `n' > n` must run Phase 1 with a majority, and that majority **overlaps** the majority that chose `v` (two majorities always intersect). So at least one acceptor in the new majority already accepted `v` and reports it; by the rule in step 3, the new proposer is **forced** to re-propose `v`. Thus once a value is chosen, every subsequent proposal proposes the *same* value → **agreement holds forever.** That majority-overlap-forces-resends argument is the whole magic; everything else is bookkeeping.

**Why Paxos is hard to use directly.** Single-decree Paxos agrees on *one* value; real systems need a *sequence* (a log) → **Multi-Paxos**, which is underspecified in the paper, prone to **dueling proposers** (two proposers leapfrogging numbers, livelocking, a liveness loss, never a safety loss, consistent with FLP), and notoriously tricky to implement correctly. That pain is *exactly* why Raft was created.

### Raft - consensus designed to be understood (own this one)

Raft (Ongaro & Ousterhout, 2014) provides the *same* guarantees as Multi-Paxos but was explicitly designed for **understandability**. It decomposes consensus into three subproblems: **leader election**, **log replication**, and **safety**. This is the one to know cold.

**Core state.** Each node is in one of three roles: **Follower** (passive, default), **Candidate** (campaigning), or **Leader** (handles all client writes). Time is divided into **terms**, numbered periods, each beginning with an election. A term has *at most one* leader. Terms act as a logical clock and the fencing mechanism: every message carries a term; **any node seeing a higher term immediately steps down to follower and adopts that term**, and **any message from an older term is rejected**. This one rule kills most split-brain scenarios.

Each node persists (to survive crash-recovery, 26.1): `currentTerm`, `votedFor` (who it voted for this term), and its **log** (a sequence of `{term, command}` entries).

**Leader election.**
1. A follower that hears no heartbeat from a leader within its **election timeout** becomes a **candidate**: it increments `currentTerm`, votes for itself, and sends **RequestVote** RPCs to all peers.
2. A node grants its vote if (a) the candidate's term ≥ its own, (b) it hasn't already voted this term, and (c) the candidate's log is **at least as up-to-date** as its own (the *election restriction*, vital for safety, below).
3. A candidate that collects votes from a **majority** becomes **leader** and immediately sends heartbeats to assert authority and reset everyone's timers.
4. **Split votes** (two candidates, no majority) are resolved by **randomized election timeouts**, each node waits a random duration (e.g. 150-300 ms), so one candidate almost always starts first and wins before others wake. This randomization is Raft's FLP escape hatch, it makes livelock vanishingly unlikely.

**Log replication.**
1. Clients send commands to the leader. The leader appends `{currentTerm, command}` to its own log.
2. The leader sends **AppendEntries** RPCs to followers carrying the new entries plus a **consistency check**: the index and term of the entry *immediately preceding* the new ones (`prevLogIndex`, `prevLogTerm`).
3. A follower **rejects** AppendEntries if its log doesn't contain a matching entry at `prevLogIndex`/`prevLogTerm`. On rejection the leader **decrements** its `nextIndex` for that follower and retries, walking backward until the logs match, then overwriting any conflicting suffix. This guarantees the **Log Matching Property**: if two logs have an entry with the same index *and* term, all preceding entries are identical.
4. Once an entry is stored on a **majority** of nodes, the leader marks it **committed**, **applies** it to its state machine, returns success to the client, and tells followers the new `commitIndex` so they apply it too.

**Safety, the rules that make it correct.** Two subtle rules prevent committed data from ever being lost:

- **Election restriction:** a node only grants a vote if the candidate's log is *at least as up-to-date* (compare last entry's term, then length). This guarantees a new leader's log already contains *every committed entry*, so electing a leader never erases committed data.
- **Commit rule (never commit old terms by counting alone):** a leader only considers an entry committed by replica-count if it's from the leader's *current* term. Older-term entries become committed *indirectly*, once a current-term entry above them commits. This closes a famous subtle hole where an entry replicated to a majority could otherwise be overwritten after a leader change.

Together these give Raft its headline guarantee, the **State Machine Safety Property**: *if any node has applied a log entry at a given index, no other node will ever apply a different entry at that index.* Every node's state machine sees the **same commands in the same order** → identical state. That's the prize.

**Why to trust Raft over hand-rolling.** It's understandable enough to implement and test, it's what etcd/Consul/CockroachDB actually run, and its safety argument is airtight. When you need agreement in production, you reach for an etcd/Raft library, but only *because* you understand what it's doing, which is the point of simulating it below.

### State-machine replication (SMR)

The big idea that makes consensus *useful*: model your service as a **deterministic state machine**, same starting state + same sequence of commands ⇒ same resulting state, on every node. If you can get all replicas to **agree on the same ordered log of commands** (which is exactly what Raft/Paxos provide), then every replica, applying that log in order, ends in **identical state**. That's **state-machine replication**: turn "keep N copies of a service consistent" into "agree on one ordered command log." A replicated SQL database, a replicated lock service, a replicated KV store, all are SMR over a consensus-backed log. The determinism requirement is real: no `random()`, no wall-clock reads, no non-deterministic map iteration inside the state machine, or replicas diverge.

### Replicated logs and Kafka (tie to 09.5)

A **replicated log** is an append-only, ordered, durable sequence of records copied across nodes, the substrate of SMR and of streaming. This is exactly the **stream/log** abstraction from 09.5 ("a log is not a queue"): consumers read by **offset**, the data is retained and replayable, and *order within a partition is the contract.*

**Kafka's replication** is a great real-world contrast to Raft. Each partition has a **leader** and **followers**; the leader maintains an **ISR** (in-sync replica set) of followers caught up to it. A write is acknowledged based on `acks`: `acks=1` (leader only, fast, can lose data on leader failure), `acks=all` (all ISR, durable, slower), *that's the sync/async replication trade from 07.4, exposed as a knob*. Kafka historically used **ZooKeeper** (itself a consensus system, ZAB, a Paxos cousin) to elect partition leaders and store metadata; newer Kafka (**KRaft**) replaces ZooKeeper with a **Raft**-based metadata quorum. So Kafka is *consensus for the control plane* (who leads each partition) plus *quorum/ISR replication for the data plane* (the records). Recognizing that split, consensus for metadata, leader+followers for bulk data, is how most high-throughput systems are actually built.

### Distributed transactions - atomic commit across nodes

Consensus agrees on *one* value; a **distributed transaction** needs *multiple* nodes to *all commit or all abort* a set of changes, **atomic commit**. This is subtly different from consensus (everyone must agree on commit-vs-abort *and* honor any single "abort" vote).

**Two-phase commit (2PC).** A **coordinator** drives all **participants**:

- **Phase 1 (prepare/voting):** coordinator asks each participant "can you commit?" Each does the work, durably writes it to a "prepared" state (locks held), and votes **yes** or **no**.
- **Phase 2 (commit/abort):** if *all* voted yes, coordinator sends **commit**; if *any* voted no (or timed out), it sends **abort**. Participants finalize and release locks.

2PC gives atomicity, but it has a fatal flaw: **it blocks.** If the **coordinator crashes after participants voted "yes" but before sending the decision**, the participants are stuck **prepared**, holding locks, unable to safely commit *or* abort (they don't know what the others were told). They must *wait* for the coordinator to recover. During that window, locked rows are unavailable. 2PC is **not partition-tolerant** and chooses **C over A** (a CP protocol), a blocked transaction is the price of never violating atomicity. It's used in tightly-coupled settings (XA transactions, a single DB across shards) but avoided across loosely-coupled services for exactly this reason.

**Three-phase commit (3PC).** Adds a **pre-commit** phase between vote and commit, so participants can reach a *known* state from which they can safely time out and make progress without the coordinator, making it **non-blocking** under the assumption of synchronous, fail-stop-only behavior. But that assumption fails under network partitions (it can violate safety then), so **3PC is rarely used in practice**, it trades the blocking problem for incorrect behavior during partitions, which is worse. Know it as "the idea that fixes 2PC's blocking *if* the network is well-behaved, which it isn't."

**Sagas (tie to microservices).** The pragmatic answer for long-lived, cross-service workflows. Instead of one atomic transaction with held locks, a **saga** is a *sequence of local transactions*, each in its own service, with a **compensating transaction** that semantically undoes it. Run T1, T2, T3…; if T3 fails, run the compensations C2, C1 to roll back. *No distributed locks, no blocking*, you trade **atomicity + isolation** for **availability + eventual consistency**. The catch: there's a window where the system is partially done (so you need idempotency, dedup, and careful design for intermediate states). Example for NYX: "reserve funds → execute trade → update ledger"; if the trade fails, *compensate* by releasing the reservation rather than rolling back a held lock across services. Sagas are *the* default for microservice transactions, orchestrated centrally or choreographed via events on a queue (09.5).

**The unifying trade:** 2PC = strong (atomic + isolated) but blocking/CP; sagas = available + eventually consistent but no isolation, needs compensation. Pick by whether you can tolerate held locks/blocking (2PC) or need availability and can design compensations (sagas).

### Quorum / Dynamo-style systems (tie to 07.3 / 07.4)

Not every system wants a leader and a strict log. **Dynamo-style** leaderless stores (Cassandra, Riak, DynamoDB) skip consensus on the write path and use **tunable quorums** (`R + W > N`, derived in 26.1) for consistency, with **vector clocks** (26.1) or last-writer-wins to handle concurrent writes, plus **read-repair** and **anti-entropy** (Merkle-tree sync) to converge replicas. This is the **AP / PA-EL** corner of PACELC (07.3): no consensus round-trip per write means high availability and low latency, at the cost of eventual consistency and the need to merge conflicts. The contrast to internalize: **consensus systems (Raft/Paxos) = strong consistency via a leader+log (CP); Dynamo-style quorum systems = high availability via tunable quorums + conflict resolution (AP).** Many real databases offer *both* modes, strong reads via leader, eventual reads via quorum, and let you choose per operation.

### A word on distributed time - Spanner & TrueTime

26.1 said physical clocks can't order events. Google's **Spanner** is the audacious exception that proves the rule. It deploys **GPS receivers and atomic clocks** in every datacenter and exposes **TrueTime**: an API that returns *not* a timestamp but an **interval** `[earliest, latest]` that is *guaranteed* to contain the true time, with the uncertainty `ε` (typically a few milliseconds) made **explicit**. Spanner assigns each transaction a commit timestamp and then **waits out the uncertainty**, it deliberately pauses for `ε` (the "commit wait") so that by the time it proceeds, the chosen timestamp is *definitely* in the past everywhere. This lets Spanner provide **externally consistent (linearizable) globally-distributed transactions**, something 26.1 implied was impossibly expensive. The lesson: you *can* use physical time for ordering, but only if you **quantify and respect its uncertainty** rather than pretending clocks are exact. Spanner is **PC/EC** in PACELC, it pays latency (the commit wait) for global strong consistency, an extraordinary engineering choice enabled by bounding `ε`. For mortals without atomic clocks, Raft + logical ordering remains the path.

## Build it: a Raft-ish leader election + log replication simulator

No black boxes, let's simulate Raft's core: terms, votes, AppendEntries, commitment, and a leader crash with clean re-election. We'll use a deterministic, single-process event loop (no real network) so the output is reproducible and you can *see* the protocol work.

```python
"""
A simplified, synchronous Raft simulation focused on the CORE ideas:
terms, RequestVote, AppendEntries, majority commit, leader crash + re-election.
It is NOT production Raft (no real RPC timing, simplified backoff), but it
faithfully shows the safety-critical mechanics so I understand them.
"""
import random
from enum import Enum

random.seed(42)   # reproducible

class Role(Enum):
    FOLLOWER = "follower"
    CANDIDATE = "candidate"
    LEADER = "leader"

class Node:
    def __init__(self, nid, cluster):
        self.id = nid
        self.cluster = cluster          # reference to all nodes
        self.role = Role.FOLLOWER
        self.current_term = 0
        self.voted_for = None
        self.log = []                   # list of dicts: {"term": t, "cmd": c}
        self.commit_index = -1          # highest committed log index
        self.alive = True
        # leader-only bookkeeping:
        self.next_index = {}            # follower_id -> next log index to send
        self.match_index = {}           # follower_id -> highest replicated index

    # ---- helpers ----
    def last_log_index(self):
        return len(self.log) - 1

    def last_log_term(self):
        return self.log[-1]["term"] if self.log else -1

    def peers(self):
        return [n for n in self.cluster.nodes if n.id != self.id and n.alive]

    def majority(self):
        return len(self.cluster.nodes) // 2 + 1

    # ---- leader election ----
    def start_election(self):
        if not self.alive:
            return
        self.current_term += 1
        self.role = Role.CANDIDATE
        self.voted_for = self.id
        votes = 1                       # votes for self
        print(f"  [n{self.id}] starts election for term {self.current_term}")
        for peer in self.peers():
            if peer.request_vote(self.current_term, self.id,
                                 self.last_log_index(), self.last_log_term()):
                votes += 1
        if votes >= self.majority():
            self.become_leader()
        else:
            print(f"  [n{self.id}] lost election ({votes} votes, "
                  f"need {self.majority()})")
            self.role = Role.FOLLOWER

    def request_vote(self, term, cand_id, cand_last_idx, cand_last_term):
        """Peer decides whether to grant its vote."""
        if not self.alive:
            return False
        if term < self.current_term:
            return False                # stale candidate
        if term > self.current_term:    # adopt newer term, reset vote
            self.current_term = term
            self.voted_for = None
            self.role = Role.FOLLOWER
        # election restriction: candidate's log must be >= as up-to-date
        up_to_date = (cand_last_term > self.last_log_term() or
                      (cand_last_term == self.last_log_term() and
                       cand_last_idx >= self.last_log_index()))
        if self.voted_for in (None, cand_id) and up_to_date:
            self.voted_for = cand_id
            return True
        return False

    def become_leader(self):
        self.role = Role.LEADER
        print(f"  [n{self.id}] BECAME LEADER for term {self.current_term}")
        for peer in self.cluster.nodes:
            if peer.id != self.id:
                self.next_index[peer.id] = len(self.log)
                self.match_index[peer.id] = -1

    # ---- log replication ----
    def client_request(self, cmd):
        if self.role != Role.LEADER:
            print(f"  [n{self.id}] not leader; rejecting client cmd")
            return False
        self.log.append({"term": self.current_term, "cmd": cmd})
        print(f"  [n{self.id}] leader appended {cmd!r} at idx "
              f"{self.last_log_index()} (term {self.current_term})")
        self.replicate()
        return True

    def replicate(self):
        """Leader pushes entries to followers and advances commit on majority."""
        for peer in self.peers():
            ni = self.next_index.get(peer.id, len(self.log))
            prev_idx = ni - 1
            prev_term = self.log[prev_idx]["term"] if prev_idx >= 0 else -1
            entries = self.log[ni:]
            ok = peer.append_entries(self.current_term, self.id,
                                     prev_idx, prev_term, entries,
                                     self.commit_index)
            if ok:
                self.match_index[peer.id] = self.last_log_index()
                self.next_index[peer.id] = len(self.log)
            else:
                # log inconsistency: walk back and retry (simplified)
                self.next_index[peer.id] = max(0, ni - 1)
        self.advance_commit()

    def append_entries(self, term, leader_id, prev_idx, prev_term,
                       entries, leader_commit):
        if not self.alive or term < self.current_term:
            return False
        self.current_term = term
        self.role = Role.FOLLOWER
        self.voted_for = None
        # consistency check (Log Matching Property)
        if prev_idx >= 0:
            if prev_idx >= len(self.log) or self.log[prev_idx]["term"] != prev_term:
                return False            # leader will back up nextIndex and retry
        # append / overwrite conflicting suffix
        self.log = self.log[:prev_idx + 1] + entries
        if leader_commit > self.commit_index:
            self.commit_index = min(leader_commit, self.last_log_index())
        return True

    def advance_commit(self):
        """Commit an index once it's on a majority AND from the current term."""
        for idx in range(self.last_log_index(), self.commit_index, -1):
            if self.log[idx]["term"] != self.current_term:
                continue                # commit-rule: only current-term by count
            replicas = 1 + sum(1 for p in self.cluster.nodes
                               if p.id != self.id
                               and p.match_index.get  # guard
                               and self.match_index.get(p.id, -1) >= idx)
            if replicas >= self.majority():
                if idx > self.commit_index:
                    self.commit_index = idx
                    print(f"  [n{self.id}] COMMITTED up to idx {idx} "
                          f"({self.log[idx]['cmd']!r}) on majority")
                break


class Cluster:
    def __init__(self, n):
        self.nodes = []
        for i in range(n):
            self.nodes.append(Node(i, self))

    def leader(self):
        for n in self.nodes:
            if n.alive and n.role == Role.LEADER:
                return n
        return None


def simulate():
    print("=== Raft-ish simulation: 5 nodes ===")
    cluster = Cluster(5)

    print("\n-- Term 1: node 0 wins election --")
    cluster.nodes[0].start_election()
    leader = cluster.leader()

    print("\n-- Client writes replicated & committed --")
    leader.client_request("SET x=1")
    leader.client_request("SET y=2")

    print(f"\n  Leader n{leader.id} log: "
          f"{[e['cmd'] for e in leader.log]}  commit={leader.commit_index}")

    print("\n-- LEADER CRASHES --")
    leader.alive = False
    leader.role = Role.FOLLOWER
    print(f"  n{leader.id} is down.")

    print("\n-- A follower times out and starts a new election --")
    # pick an up-to-date survivor (election restriction ensures it has the log)
    candidate = next(n for n in cluster.nodes if n.alive)
    candidate.start_election()
    new_leader = cluster.leader()
    print(f"  New leader is n{new_leader.id} (term {new_leader.current_term})")

    print("\n-- New leader keeps the cluster consistent --")
    new_leader.client_request("SET z=3")
    new_leader.replicate()

    print("\n-- Final state of all live nodes --")
    for n in cluster.nodes:
        if n.alive:
            print(f"  n{n.id}: log={[e['cmd'] for e in n.log]} "
                  f"commit={n.commit_index} term={n.current_term}")


if __name__ == "__main__":
    simulate()
```

**What this demonstrates:**

- **Terms** increment with each election and act as the fencing clock; a node seeing a higher term steps down.
- **RequestVote** with the **election restriction**, a candidate only wins if its log is at least as up-to-date, so the new leader already holds all committed entries (nothing committed is lost across the crash).
- **AppendEntries** with the **consistency check** (Log Matching), followers reject mismatched logs and the leader backs up and retries.
- **Majority commit** with the **current-term rule**, an entry is committed only once it's on a majority *and* from the leader's current term.
- **Leader crash → clean re-election → continued consistent operation**, which is the headline behavior you need to trust in etcd/Consul.

This sim simplifies: real Raft has asynchronous RPC timing, randomized election timeouts running on real timers, heartbeats, snapshotting/log compaction, and persistent storage flushed before responding. But the *safety-critical mechanics* above are faithful, and now you understand what a Raft library is doing on your behalf.

## Mini-project: Raft with injected failures across N nodes

> Extend the simulator into a small interactive cluster and *prove the cluster stays consistent under failures*. This is the capstone that ties FLP-dodging, leader election, and log replication together.

Build these, in order:

1. **Randomized election timeouts + a tick loop.** Replace the hand-driven `start_election` with a discrete-time loop: each tick, every follower's timer counts down (random initial value per node); the first to expire becomes a candidate. *Demonstrate* that randomization makes split votes rare, count how many ticks until a stable leader emerges over many seeds.
2. **Heartbeats.** The leader sends empty AppendEntries each tick to reset followers' timers; stop them (crash the leader) and watch a *single* re-election fire.
3. **Network partition.** Split the 5 nodes into a majority side (3) and a minority side (2). Show that **only the majority side can elect a leader and commit** (the minority's candidate can never reach a majority), this is **CAP live**: the minority sacrifices availability to preserve consistency. Heal the partition and show the stale minority nodes catch up via AppendEntries back-up-and-retry.
4. **Consistency assertion.** After any sequence of crashes/partitions/heals, assert the **State Machine Safety Property**: for every committed index, *all* nodes that have that index agree on its `{term, cmd}`. If that assertion ever fails, the implementation has a safety bug, it should *never* fail.
5. **Stretch, a tiny replicated KV state machine.** Apply committed log entries (`SET k=v`, `DEL k`) to a per-node dict and assert all live, caught-up nodes have identical dicts. That's **state-machine replication** working end to end.

Success criterion: across hundreds of randomized fault-injection runs, the consistency assertion in step 4 **never** fails, and the cluster always converges to a single leader and identical committed logs once the network is healthy. When that holds, you've genuinely built (a faithful core of) the thing that powers etcd.

## Common mistakes

- **Thinking FLP means consensus is hopeless.** It says you can't *guarantee* termination in *pure async* with a failure. Real systems keep safety always and recover liveness via timeouts/randomness. Never sacrifice safety for liveness.
- **Letting a deposed leader keep writing (split-brain).** Always gate leadership on a **majority** and stamp writes with a **term/epoch (fencing token)** so storage rejects a stale leader's late writes.
- **Committing Raft entries by replica-count regardless of term.** The current-term commit rule exists for a reason; committing an old-term entry purely by majority count can be undone by a later leader, a genuine safety hole the rule closes.
- **Non-deterministic state machines.** SMR only works if applying the same log yields the same state. `random()`, wall-clock reads, or unordered iteration inside the state machine make replicas diverge. Keep it deterministic.
- **Reaching for 2PC across microservices.** It blocks when the coordinator dies (locks held indefinitely) and isn't partition-tolerant. For loosely-coupled services use **sagas with compensations**; reserve 2PC for tightly-coupled, low-latency, same-trust-domain cases.
- **Confusing consensus with atomic commit.** Consensus = agree on one value, tolerates minority failure and keeps going. Atomic commit (2PC) = *all* must agree to commit and *any* node can force abort, different problem, different (blocking) properties.
- **Believing "exactly-once" across services.** Same lesson as 26.1/09.5: build idempotent handlers + at-least-once; sagas especially demand idempotent steps and compensations.
- **Hand-rolling Paxos/Raft in production.** Understand it deeply (this chapter), then use a battle-tested library (etcd/raft, ZooKeeper). The bugs live in the edge cases you won't test.

## On the job / interview angle

- **"How do you avoid split-brain / elect a leader?"** Answer: majority-quorum leader election with monotonic terms/epochs and fencing tokens; cite Raft/etcd. This single answer covers a huge fraction of distributed follow-ups.
- **"How do you make these writes atomic across two services?"** Lead with **saga + compensating transactions** for microservices (no blocking, eventually consistent), and mention 2PC only for tightly-coupled cases while naming its **blocking** flaw. Naming the trade-off is what scores.
- **"Strong vs eventual, how?"** Strong = consensus/leader+log (Raft, Spanner) = CP/PC-EC; eventual = quorum/Dynamo (`R+W>N`, vector clocks) = AP/PA-EL. Tie to PACELC (07.3) and pick per *data*, not per *system*.
- **Know what's underneath the tools.** etcd/Consul/CockroachDB = Raft; ZooKeeper = ZAB (Paxos cousin); Kafka = leader+ISR replication with ZooKeeper/KRaft for metadata; Spanner = Paxos + TrueTime. Dropping these accurately signals real depth.
- **Cite FLP correctly.** "Consensus can't be *guaranteed* in a fully async system with one failure, so we use timeouts/randomness and keep safety unconditional", a crisp, senior-sounding sentence.
- **Distributed transactions are a design-interview staple.** "Reserve, then execute, then settle, with compensations on failure" (a saga) is a reusable answer for order/payment/booking systems.

## Exercises

**1. Why majority?** Explain, using set overlap, why Raft and Paxos both require a *majority* (more than half) rather than, say, "any 2 nodes" to elect a leader or choose a value. What goes wrong with a non-majority quorum?

<details><summary>Solution</summary>

Any two majorities of an `N`-node set *must* intersect in at least one node (two subsets each larger than `N/2` can't be disjoint, pigeonhole). That overlap is what guarantees uniqueness: two leaders can't *both* get a majority in the same term (the shared node only votes once), and a newly chosen value's majority overlaps any earlier chosen value's majority (forcing re-proposal in Paxos / carrying committed entries forward in Raft). A non-majority quorum (e.g. "any 2 of 5") can produce two *disjoint* quorums → two leaders / two different chosen values → split-brain and lost agreement. Majority is the smallest quorum that guarantees overlap.

</details>

**2. The 2PC blocking scenario.** Walk through exactly when 2PC blocks, who is stuck, and why they can't unilaterally decide. Propose one mitigation.

<details><summary>Solution</summary>

Block happens if the **coordinator crashes after participants voted "yes" but before broadcasting the decision**. Each participant is in the **prepared** state, it has voted yes, durably locked its changes, and *cannot* unilaterally commit (maybe someone voted no and the real decision was abort) *or* abort (maybe everyone voted yes and the decision was commit). It must wait for the coordinator to recover and resolve. During the wait, locked resources are unavailable → reduced availability (CP behavior). Mitigations: make the coordinator highly available (replicate it via Raft/Paxos so it survives crashes), add participant-to-participant communication to learn the decision, or avoid 2PC entirely for loosely-coupled services and use **sagas** (no prepared-and-waiting state, compensations instead).

</details>

**3. Raft commit rule.** Why does Raft refuse to mark an entry committed *purely* by majority replication if that entry is from a *previous* term? Sketch the danger it prevents.

<details><summary>Solution</summary>

An older-term entry can be replicated to a majority, yet a *later* leader (with a different, longer log path) could still overwrite it before it's protected, because leadership can change and logs can be repaired backward. If Raft committed it by count alone, a committed entry could later be erased, a safety violation. The fix: a leader only commits *by replica-count* entries from its **own current term**; older entries become committed **indirectly**, carried along once a current-term entry above them reaches a majority (at which point the Log Matching Property protects everything before it). This guarantees no committed entry is ever lost across leader changes.

</details>

**4. Saga design.** Design a saga for NYX's "execute trade" flow: (1) reserve funds, (2) place order with exchange, (3) record fill in ledger. Give the compensating action for each and explain what happens if step 2 fails.

<details><summary>Solution</summary>

Forward steps and compensations: T1 *reserve funds* → C1 *release reservation*; T2 *place order* → C2 *cancel order* (if cancellable) or *flag for reconciliation*; T3 *record fill* → C3 *reverse ledger entry*. If **T2 fails** (order rejected), run C1 to release the reserved funds; T3 never ran so no compensation needed. The saga is **available** (no distributed locks held across services) and **eventually consistent** (a brief window where funds are reserved but no order exists). Each step must be **idempotent** (retried T1 mustn't double-reserve) and compensations must tolerate being called after partial completion. Note T2 against an external exchange may be non-compensatable once filled, real designs add a *pivot transaction* after which only forward recovery is allowed, never compensation.

</details>

**5. Map the tool to the mechanism.** For each, name the consensus/replication mechanism it uses: (a) etcd, (b) Kafka partition leader election, (c) Cassandra writes, (d) Google Spanner transactions, (e) ZooKeeper.

<details><summary>Solution</summary>

(a) **etcd**, Raft. (b) **Kafka**, leader + ISR replication; leader election via ZooKeeper (older) or KRaft/Raft (newer) for metadata consensus. (c) **Cassandra**, leaderless Dynamo-style tunable quorums (`R+W>N`), last-writer-wins / lightweight transactions (Paxos) for the few strongly-consistent ops. (d) **Spanner**, Paxos per shard for replication + TrueTime (bounded clock uncertainty + commit wait) for external consistency. (e) **ZooKeeper**, ZAB (Zookeeper Atomic Broadcast), a Paxos-family atomic broadcast protocol.

</details>

**6. FLP in one paragraph.** A teammate says "FLP proves distributed consensus is impossible, so why do we even use etcd?" Correct them precisely.

<details><summary>Solution</summary>

FLP proves you can't write a *deterministic* algorithm that *guarantees* consensus (agreement + validity + termination) in a *fully asynchronous* system where even one node may crash, because you can never distinguish a crashed node from a slow one, so an adversarial scheduler can keep the system undecided forever. It does **not** say consensus is impossible in practice. Real networks are *partially synchronous* (timely most of the time), so etcd's Raft uses **timeouts** to suspect crashes and **randomized election timeouts** to break ties, achieving consensus quickly with overwhelming probability. Crucially it *never* sacrifices **safety**, under bad conditions it may *pause* (lose liveness temporarily) but it will never decide two different values. So FLP shapes the design (why we need timeouts/randomness and prioritize safety) rather than forbidding the system.

</details>
