# Chapter 1.4 - Algorithmic Complexity & Big-O (rigorous)

> Goal: After this chapter you'll be able to state the formal ε/n₀-style definitions of O, Ω, Θ (and little-o), *prove* a function is O(g) by exhibiting c and n₀, analyze loops/nested loops/recursion, solve recurrences three ways (substitution, recursion tree, Master Theorem), do amortized analysis (including the dynamic-array doubling argument), reason about space complexity and best/worst/average case, and, crucially, *measure* real code with `timeit` to SEE the growth curves and classify a mystery function empirically *and* prove the classification.

## 🌱 Start here (the gentle on-ramp)

Imagine two coffee shops. Shop A serves customers one at a time; if the line doubles, the wait roughly doubles. Shop B has a bizarre policy: every customer must shake hands with every *other* customer before ordering; if the line doubles, the waiting *quadruples*. With 5 people both shops feel fine. With 5,000 people, Shop A is annoying but Shop B has collapsed into chaos. The shops aren't "slow" or "fast" in some fixed way, they *scale* differently. Big-O is the language for describing exactly that: **how does the work grow as the input grows?**

That's the whole idea. Big-O is *not* about seconds, and it's *not* about your laptop being fast. It's about the *shape* of the curve. An algorithm that takes "about n steps" (linear) and one that takes "about n² steps" (quadratic) might tie on small inputs, but as n grows the quadratic one falls hopelessly behind, and no faster computer can rescue it, because the gap keeps widening. We deliberately throw away constants and small terms because, far enough out, only the shape matters.

A quick feel for the common shapes, worst (top) to best (bottom):
- **O(2ⁿ) / O(n!)**, "try every possibility." Dies past ~n=25-30. Avoid unless n is tiny.
- **O(n²)**, "every pair." Fine for thousands, painful for millions. (Shop B.)
- **O(n log n)**, "good sorting." Scales to huge inputs comfortably.
- **O(n)**, "one pass." (Shop A.) Great.
- **O(log n)**, "halve it each step." Binary search; absurdly scalable (a billion items in ~30 steps).
- **O(1)**, "instant, regardless of size." Array index, hash lookup.

**Why this matters for you (and a future job):** Big-O is the *lingua franca* of technical interviews, you will be asked "what's the time complexity?" about nearly every problem you solve, and a correct, confident answer is half the battle. On the job, it's how engineers predict whether code that works on 100 test rows will survive 100 million production rows *before* shipping it. The difference between an O(n²) and an O(n) solution to the same problem is the difference between a feature that works and one that takes the site down on launch day. This chapter makes Big-O precise enough to *prove*, and concrete enough to *measure with a stopwatch*.

For a long time "Big-O" can feel like a vibe, "n² bad, log n good." This chapter forces it to be *math*: precise definitions, real proofs, and recurrences you can actually solve, all cross-checked against a stopwatch. The big idea is simple and freeing: we don't care about seconds (those depend on your laptop, the language, the weather); we care about the *shape of the growth* as input size n → ∞. That shape is what survives all the noise.

## 📐 Why growth rates, not seconds

If you time two algorithms once, the faster machine wins, meaningless. But growth rate is intrinsic to the *algorithm*. Concrete: at n = 1,000,000, an O(n) algorithm doing 10⁶ steps finishes instantly; an O(n²) one does 10¹² steps and takes hours; an O(2ⁿ) one would outlast the universe. No hardware upgrade closes a gap like that, buy a machine 1000× faster and the n² algorithm just handles a √1000 ≈ 32× bigger input. **Asymptotic growth dominates everything else for large n.** That's why we measure it, and why constants and lower-order terms get dropped: they're noise next to the dominant term as n grows.

```
n        n        n log n      n²            2^n
10       10       33           100           1,024
100      100      664          10,000        1.3e30
1,000    1,000    9,966        1,000,000     ~1e301
1e6      1e6      ~2e7         1e12          (won't fit on this page)
```

**Read that table slowly.** At n=10, every column is small, you literally cannot tell these algorithms apart by eye. But scan *down* the `2^n` column: 1,024 → 1.3e30 (more than the number of atoms in your body) → 1e301 (more than atoms in the universe). The 2ⁿ algorithm didn't "get a little slower"; it left physical reality. Meanwhile the `n` and `n log n` columns stay civilized. *This* is why we obsess over growth rate and not the one-time stopwatch reading.

## 📐 Formal definitions (the quantifier versions)

These are the actual definitions, and you want to be able to *write the proof*, not just nod.

**Beginner translation first**, then the formal version. Big-O means "grows *no faster than*" (an upper bound / ceiling). Big-Omega means "grows *at least as fast as*" (a lower bound / floor). Big-Theta means "grows *exactly like*" (sandwiched between a floor and a ceiling of the same shape). little-o means "grows *strictly slower than*" (eventually negligible). The "c and n₀" business below is just the rigorous way to say "ignoring constant factors, and for large enough inputs."

**Big-O (asymptotic upper bound).**
> `f(n) = O(g(n))` iff there exist constants `c > 0` and `n₀ > 0` such that `0 ≤ f(n) ≤ c·g(n)` for all `n ≥ n₀`.

In words: past some point n₀, f is *bounded above* by a constant multiple of g. It's a *ceiling on growth*.

The `c` lets us ignore constant factors (a 5n algorithm and a 100n algorithm are both O(n)); the `n₀` lets us ignore small-input weirdness (we only care about the behavior "eventually," as n grows). Both knobs exist precisely to strip away the noise and keep the shape.

**Big-Omega (asymptotic lower bound).**
> `f(n) = Ω(g(n))` iff ∃ c > 0, n₀ such that `0 ≤ c·g(n) ≤ f(n)` for all n ≥ n₀.

f is *bounded below* by a multiple of g, a *floor*.

**Big-Theta (tight bound).**
> `f(n) = Θ(g(n))` iff `f = O(g)` AND `f = Ω(g)`. Equivalently ∃ c₁, c₂, n₀ with `c₁·g(n) ≤ f(n) ≤ c₂·g(n)` for n ≥ n₀.

f grows *exactly* like g (up to constants), sandwiched. Θ is what you should usually state when you can; O alone is just an upper bound (technically `n = O(n²)` is true but loose).

**little-o (strictly smaller).**
> `f(n) = o(g(n))` iff for *every* c > 0 there's an n₀ with `f(n) < c·g(n)` for n ≥ n₀. Equivalently `lim_{n→∞} f(n)/g(n) = 0`.

The difference from Big-O: Big-O allows f to grow *at the same rate* as g (one fixed c works); little-o demands f is *eventually negligible* compared to g (works for *all* c, ratio → 0). So `n = o(n²)` but `n ≠ o(n)`, whereas `n = O(n)`.

### Worked proof: prove `3n² + 5n + 2 = O(n²)`

You must *exhibit* a c and an n₀ and verify the inequality. Here's the standard "bound each term by the dominant one" technique:

> For all n ≥ 1: `5n ≤ 5n²` (since n ≤ n²) and `2 ≤ 2n²`. Therefore
> ```
> 3n² + 5n + 2 ≤ 3n² + 5n² + 2n² = 10n²   for all n ≥ 1.
> ```
> So with **c = 10** and **n₀ = 1**, `3n²+5n+2 ≤ c·n²` for all n ≥ n₀. By definition, `3n²+5n+2 = O(n²)`. ∎

And it's also Ω(n²): `3n²+5n+2 ≥ 3n²` for all n ≥ 0, so c = 3, n₀ = 0 works. Having both O(n²) and Ω(n²), it's **Θ(n²)**. The c isn't unique, any c ≥ 10 works for the upper bound; you just need *one* witness. That existential structure (∃ c, n₀) is what makes these proofs satisfying: produce one witness and you're done, exactly like the ∃ proofs from [Chapter 1.3](01.3-discrete-math.md).

**The general recipe these proofs follow** (so you can do it for any polynomial): to prove a polynomial is O of its highest-degree term, bound *every* lower term by the highest term (legal once n ≥ 1, since `n^j ≤ n^k` for j ≤ k), then add up the coefficients to get c. The dominant term always wins; the rest is bookkeeping.

## 📐 The common complexity classes (with intuition)

```
O(1)        constant     array index, hash lookup. Input size irrelevant.
O(log n)    logarithmic  binary search. Each step HALVES the problem.
O(n)        linear       one pass over the data.
O(n log n)  linearithmic mergesort, heapsort, good comparison sorts. The sort barrier.
O(n²)       quadratic    nested loop over all pairs. Bubble sort.
O(n³)       cubic        naive matrix multiply, triple nested loops.
O(2^n)      exponential  subsets / brute-force "try every combination."
O(n!)       factorial    permutations / brute-force traveling salesman.
```

The intuitions worth holding onto:
- **log n** = "how many times can you halve n before reaching 1?" = log₂ n. Doubling the input adds *one* step. That's why binary search of a billion items is ~30 comparisons. (Base of the log doesn't matter for Big-O, it's a constant factor: `log_a n = log_b n / log_b a`.)
- **n log n** = "do linear work at each of log n levels" (recursion that splits in half). The practical floor for comparison sorting.
- **2^n** = "for each of n items, 2 choices (in/out)" → the power set from Chapter 1.3. Brute force over subsets.
- **n!** = "arrange all n items in order" → permutations. Brute force over orderings.

Everything at O(n log n) or below scales to huge inputs; O(n²) is fine for thousands, painful for millions; anything exponential needs a cleverer algorithm or a tiny n.

**A practical "how big can n be?" cheat sheet** (rough, assuming ~10⁸ simple operations per second, the usual interview rule of thumb):
```
complexity   feasible n within ~1 second
O(log n)     basically unlimited
O(n)         ~100,000,000
O(n log n)   ~5,000,000
O(n²)        ~10,000
O(n³)        ~500
O(2^n)       ~25
O(n!)        ~11
```
This table is genuinely useful in interviews: if the input size is 10⁵ and you've got an O(n²) idea (10¹⁰ ops, too slow), the constraint is *telling you* to find an O(n log n) or O(n) approach. Reading complexity off the input bounds is a pro move.

## 📐 Analyzing loops and nested loops

The mechanical rules:

- **Sequential** statements: add (and keep the max), `O(n) + O(n²) = O(n²)`.
- **Single loop** running n times with O(1) body: `O(n)`.
- **Nested loops**: multiply (or sum the inner work). 

```python
# single loop: O(n)
for i in range(n):
    do_constant_work()

# nested, both full: O(n^2)
for i in range(n):
    for j in range(n):
        do_constant_work()

# triangular nested: inner runs i times -> Σ i = n(n+1)/2 = O(n^2)
for i in range(n):
    for j in range(i):       # 0, then 1, then 2, ... n-1
        do_constant_work()
```

That triangular case is *exactly* the summation `Σ_{i=0}^{n-1} i = n(n-1)/2` from Chapter 1.3, still Θ(n²), because the constant ½ drops. This is why summations are worth drilling: loop analysis *is* evaluating a sum.

A loop that shrinks multiplicatively is logarithmic:

```python
# O(log n): i doubles each step, so it takes log2(n) iterations to exceed n
i = 1
while i < n:
    do_constant_work()
    i *= 2
```

**A beginner-friendly procedure for "what's the Big-O of this code?":**
1. Find the loops. A loop running n times with constant work inside contributes a factor of n.
2. Nested loops *multiply* their counts (loop inside a loop = product of the two counts).
3. A loop variable that *multiplies/divides* (×2, //2) each step contributes log n, not n.
4. Add the costs of sequential pieces, then keep only the biggest term.
5. Drop constant factors and lower-order terms.

**Worked example, what's the complexity of this?**
```python
def example(arr):                 # n = len(arr)
    total = 0
    for x in arr:                 # (A) n iterations, O(1) body  -> O(n)
        total += x
    for i in range(len(arr)):     # (B) outer n
        for j in range(len(arr)): # (B) inner n  -> O(n^2)
            if arr[i] == arr[j]:
                total += 1
    return total
```
Block (A) is O(n); block (B) is O(n²). They're sequential, so we add: `O(n) + O(n²) = O(n²)` (keep the max). The whole function is **Θ(n²)**, the single pass is invisible next to the nested loop.

## 📐 Analyzing recursive code → recurrences

Recursive algorithms get a **recurrence relation**: T(n) expressed in terms of T on smaller inputs. Three examples:

```
Binary search:   T(n) = T(n/2) + O(1)      one half, constant glue work
Mergesort:       T(n) = 2 T(n/2) + O(n)     two halves, linear merge
Naive Fibonacci: T(n) = T(n-1) + T(n-2) + O(1)   ~ O(φ^n), exponential
```

**How to *write* a recurrence from recursive code** (this is the step people skip): look at one call and ask two questions. (1) *How many recursive calls does it make, and on inputs of what size?* That gives the `a·T(n/b)` or `T(n-1)+T(n-2)` part. (2) *How much non-recursive work does it do besides recursing* (loops, merges, comparisons)? That's the `+ f(n)` part. Binary search makes 1 call on half the input (`T(n/2)`) plus a constant comparison (`+O(1)`). Mergesort makes 2 calls on halves (`2T(n/2)`) plus a linear merge (`+O(n)`). Naive Fibonacci makes 2 calls on `n−1` and `n−2` plus constant work.

Let's solve these three ways.

### Method 1 - Substitution (unrolling / guess-and-verify)

Unroll binary search:
```
T(n) = T(n/2) + 1
     = T(n/4) + 1 + 1
     = T(n/8) + 3
     ...
     = T(n/2^k) + k
Stop when n/2^k = 1  =>  k = log₂ n.
T(n) = T(1) + log₂ n = O(log n).   ✓
```
The formal "substitution method" then *guesses* `T(n) = O(log n)` and verifies it by induction (plug the hypothesis into the recurrence), induction from Chapter 1.3 doing real work.

### Method 2 - Recursion tree

Draw the work at each level and sum. Mergesort, `T(n) = 2T(n/2) + cn`:

```
level 0:        cn                       = cn       work
level 1:    cn/2   cn/2                   = cn       work
level 2:  cn/4 cn/4 cn/4 cn/4            = cn       work
  ...        ...                          ...
level log n: cn/n × n nodes              = cn       work
```

Each level does `cn` total work (the halves' sizes add back to n), and there are `log₂ n + 1` levels (halving until size 1). So:
```
T(n) = cn · (log₂ n + 1) = Θ(n log n).   ✓
```
Mergesort's n log n, *derived*, not memorized, and it matches the "n work × log n levels" summation intuition from before.


### Method 3 - The Master Theorem

For divide-and-conquer recurrences of the form
```
T(n) = a · T(n/b) + f(n)        (a ≥ 1, b > 1)
```
let `c_crit = log_b(a)` (the "critical exponent", how fast the *number of subproblems* grows). Compare f(n) to `n^c_crit`:

```
Case 1: f(n) = O(n^(c_crit - ε))   →  T(n) = Θ(n^c_crit)
        (leaves dominate; recursion cost wins)
Case 2: f(n) = Θ(n^c_crit)         →  T(n) = Θ(n^c_crit · log n)
        (balanced; every level costs the same - the mergesort case)
Case 3: f(n) = Ω(n^(c_crit + ε))   →  T(n) = Θ(f(n))
        (root dominates; the top-level work wins; needs a regularity condition)
```

**The Master Theorem in plain English:** you're racing two things, the *recursion's branching* (which piles up work toward the leaves) against the *per-call work `f(n)`* (which piles up toward the root). `c_crit = log_b a` measures how fast the branching grows. If branching wins, Case 1. If per-call work wins, Case 3. If they tie, Case 2 (and the tie costs an extra `log n` factor, because *every* level costs the same and there are log n levels, exactly the mergesort tree).

**Apply to mergesort:** a=2, b=2, f(n)=n. `c_crit = log₂2 = 1`, and `f(n) = n = Θ(n¹) = Θ(n^c_crit)` → **Case 2** → `Θ(n log n)`. ✓ matches the tree.

**Apply to binary search:** a=1, b=2, f(n)=1. `c_crit = log₂1 = 0`, `f(n) = 1 = Θ(n⁰)` → **Case 2** → `Θ(n⁰ log n) = Θ(log n)`. ✓ matches the unrolling.

**Apply to "split into 2, linear merge, but recurse on both fully":** the Master Theorem is a fast machine for the common cases, when you see `aT(n/b)+f(n)` you can read off the answer. (For the messy Fibonacci recurrence the Master Theorem doesn't apply; that one solves to `Θ(φ^n)` via the characteristic equation, which is why naive Fib is a disaster and memoization rescues it to O(n).)

## ⚠️ Common mistakes

- **Saying "Big-O" when you mean "worst case."** Big-O is an *upper bound on a function*; worst/best/average describe *which input* you analyze. You can have a Big-O for the best case. They're orthogonal (more below). Conflating them is the most common conceptual error.
- **Keeping constants and lower-order terms.** `O(2n + 5)` is just `O(n)`. `O(3n²)` is `O(n²)`. Writing the constants signals you don't understand the notation. (They matter in *practice* for tuning, but not in the Big-O symbol.)
- **Adding nested-loop costs instead of multiplying.** Two independent loops add (`O(n)+O(n)=O(n)`); a loop *inside* another multiplies (`O(n·n)=O(n²)`).
- **Assuming nested loops are always O(n²).** If the inner loop runs a *constant* number of times, or the loop variable multiplies (log), it's not. Read what the loop actually does.
- **Forgetting the recursion stack in space complexity.** Recursive binary search is O(log n) *space* from its call stack, even though it allocates no data structures.
- **Treating `O(n)` and `O(n log n)` as cleanly distinguishable by timing.** The log factor is gentle; on noisy measurements they look similar. Confirm with analysis (the mini-project does exactly this).
- **Misapplying the Master Theorem.** It only fits `aT(n/b)+f(n)` with the right `f`. It does *not* apply to `T(n-1)` style recurrences (like Fibonacci), those need unrolling or the characteristic equation.
- **Counting Python "one-liners" as O(1).** `x in my_list` is O(n); `sorted(x)` is O(n log n); building a set from a list is O(n). Hidden loops inside library calls count.

## 💼 On the job / interview angle

- **"What's the time and space complexity?"** follows nearly every interview coding question. You must be able to state it *and justify it* (point at the loops/recursion). Getting the solution right but the complexity wrong is a real ding.
- **Reading complexity off the input constraints** is an interview superpower: "n ≤ 20" hints at an exponential/bitmask solution being acceptable; "n ≤ 10⁵" rules out O(n²) and points to O(n log n); "n ≤ 10⁹" demands O(log n) or math. Use the feasibility cheat sheet above.
- **The classic optimization arc**, "you have an O(n²) brute force; can you do better?", is the heart of most interviews. The expected move is usually trading time for space (a hash set/map to get O(n)), or sorting first (O(n log n)) to enable a two-pointer pass. Recognizing these patterns *is* the skill.
- **Amortized analysis** ("why is `append`/`push_back` O(1)?") is a known systems/fundamentals question; the dynamic-array doubling argument below is the canonical answer.
- **On the job:** complexity is how you predict whether code that's fine in a unit test will survive production scale. "This is O(n²) and `n` is the number of users, it'll be fine now but melt at 50k users" is the kind of foresight that gets you promoted. Database query plans, N+1 query bugs, and accidental quadratic loops over collections are real, frequent, expensive incidents rooted in this chapter.
- **Space complexity matters for real constraints:** memory limits, mobile devices, and large-data pipelines. The time/space tradeoff (memoization, caching) is a daily engineering decision.

## 📐 Amortized analysis (and the dynamic-array doubling argument)

Sometimes a single operation is occasionally expensive but *rarely* so, and averaging over a sequence gives a much better per-operation cost. That average-over-a-worst-case-sequence is **amortized** analysis (distinct from average-case, which averages over random inputs, amortized makes no probabilistic assumption).

**Beginner analogy:** a gym membership. The day you sign up you pay a big annual fee (expensive!), but you go 200 times that year. The *amortized* cost per visit is the annual fee spread across all visits, small and constant, even though one specific day had a huge charge. Amortized analysis spreads the rare expensive operation across the many cheap ones to find the true per-operation cost.

**Aggregate method:** total cost of n operations, divided by n.

**The headline example, dynamic array (Python `list`, C++ `vector`) append.** When the backing array fills, we allocate a bigger one and copy everything. If we grew by *1 each time*, copies would cost `1+2+…+n = O(n²)` total → O(n) per append. Terrible. The trick is to **double** capacity when full. Then resizes happen at sizes 1, 2, 4, 8, …, n, and the total copy cost is a *geometric series*:

```
total copies ≤ 1 + 2 + 4 + … + n
             = 2n − 1                      (geometric sum, from Chapter 1.3!)
             = O(n)
```

So n appends cost O(n) total → **O(1) amortized per append**, even though individual appends that trigger a resize cost O(n). That `1+2+4+…+n = 2n−1` is the *exact* geometric identity proved by induction earlier, it's load-bearing here. This is why `list.append` is "O(1)" and it sets up the dynamic-array deep dive in Chapter 2.1.

The **banker's / accounting method** reframes it: charge each append \$3, \$1 to do the insert, \$2 saved as "credit." When a resize copies an element, its saved credit pays for the move. The invariant (enough credit banked) is provable by induction, and it shows the amortized cost is the constant \$3 = O(1).

```python
# demonstrate amortized O(1): count total element-copies over n appends with doubling
def total_copies(n):
    cap, size, copies = 1, 0, 0
    for _ in range(n):
        if size == cap:           # full -> double and copy everything
            copies += size
            cap *= 2
        size += 1
    return copies

for n in [10, 100, 1000, 10000]:
    print(f"n={n:6d}  total copies={total_copies(n):6d}  per-append={total_copies(n)/n:.2f}")
# per-append stays below 2 - bounded by a constant => amortized O(1)
```

## 📐 Space complexity & best/worst/average case

**Space complexity** counts *extra* memory as a function of input size (often excluding the input itself, "auxiliary space"). Watch the recursion stack: it counts! Recursive binary search is O(log n) *space* from its call stack even though it touches O(log n) elements; merge sort needs O(n) auxiliary space for the merge buffer; an in-place sort like heapsort is O(1) auxiliary. There's often a **time/space tradeoff**, memoizing Fibonacci trades O(n) space for the leap from exponential to linear time.

**Best / worst / average case** describe *which input* you're analyzing, and are orthogonal to O/Θ (a common point of confusion, "worst case" is not the same as "Big-O"):
- **Worst case**, the most expensive input (usual default; gives a guarantee). Quicksort: O(n²) on already-sorted input with naive pivot.
- **Best case**, the cheapest input. Insertion sort on already-sorted data: O(n).
- **Average case**, expected cost over a distribution of inputs (needs probability, Chapter 1.3). Quicksort averages O(n log n), which is why it's used in practice despite the n² worst case.

**The cleanest way to keep these straight:** "best/worst/average" picks the *input*; "O/Ω/Θ" bounds the *function* once you've picked the input. They combine freely. You can say "insertion sort's *best case* is *Θ(n)*" and "its *worst case* is *Θ(n²)*", both are precise. Default to stating the *worst case* unless asked, because it's the only one that gives a *guarantee* (a promise it'll never be slower).

## 💻 Build it - an empirical complexity checker

We'll *time* a function across growing input sizes and fit the growth curve, so you can literally watch a curve bend. The idea: if `T(n) ≈ c · n^p`, then `log T ≈ log c + p · log n`, a straight line in log-log space whose **slope p is the exponent**. Fit that slope and you've classified polynomial complexity. (Logarithmic factors show up as gentle curvature, which you'll eyeball.)

```python
import timeit, math

def measure(func, sizes, repeats=3):
    """Return [(n, best_seconds), ...] timing func(make_input(n))."""
    results = []
    for n in sizes:
        data = list(range(n))                      # simple input; swap as needed
        t = min(timeit.repeat(lambda: func(data), number=1, repeat=repeats))
        results.append((n, t))
    return results

def fit_exponent(results):
    """Least-squares slope of log(time) vs log(n) => estimated polynomial degree p."""
    pts = [(math.log(n), math.log(t)) for n, t in results if t > 0 and n > 0]
    k = len(pts)
    sx = sum(x for x, _ in pts); sy = sum(y for _, y in pts)
    sxx = sum(x*x for x, _ in pts); sxy = sum(x*y for x, y in pts)
    slope = (k*sxy - sx*sy) / (k*sxx - sx*sx)
    return slope

def classify(p):
    if p < 0.3:  return "O(1) constant-ish"
    if p < 1.4:  return "O(n) linear (or n log n - check curvature)"
    if p < 2.4:  return "O(n^2) quadratic"
    if p < 3.4:  return "O(n^3) cubic"
    return f"super-cubic / exponential (slope {p:.2f})"

# --- demo on functions with KNOWN complexity ---
def linear(data):            # O(n)
    s = 0
    for x in data: s += x
    return s

def quadratic(data):         # O(n^2): count pairs
    c = 0
    for i in range(len(data)):
        for j in range(len(data)):
            c += 1
    return c

for name, fn, ns in [
    ("linear",    linear,    [1000, 2000, 4000, 8000, 16000]),
    ("quadratic", quadratic, [200, 400, 800, 1600]),
]:
    res = measure(fn, ns)
    p = fit_exponent(res)
    print(f"{name:10s} fitted exponent ≈ {p:.2f}  -> {classify(p)}")
```

The fitted exponent for `linear` lands near 1.0 and for `quadratic` near 2.0, the math made visible. The log-log slope trick is exactly "T ≈ c·n^p ⇒ straight line of slope p," and it's how you'll confirm any complexity claim against reality.

**Why the log-log trick works, intuitively:** if `T = c·n^p`, taking the log of both sides gives `log T = log c + p·log n`. That's the equation of a straight line `y = b + p·x` where `y = log T` and `x = log n`. The *slope* of that line is `p`, the exponent. So plotting time-vs-size on log-log axes turns a power law into a straight line, and the steepness tells you the complexity. A doubling-each-step (log n) factor isn't a clean power, so it shows up as slight upward *curvature* rather than a clean slope, which is why you eyeball it and confirm analytically.

## 🧪 Mini-project - classify 4 mystery functions, then prove it

Here are four black-box functions. You'll (1) **measure** each with the checker above, (2) **classify** empirically, then (3) **prove** the classification by reading the code and deriving the cost analytically. Empirical + analytic agreeing is the whole point.

```python
def mystery_a(data):
    total = 0
    for x in data:                      # one pass
        total += x
    return total

def mystery_b(data):
    n = len(data)
    seen = []
    for i in range(n):                  # outer n
        for j in range(n):              # inner n
            if data[i] == data[j]:
                seen.append((i, j))
    return seen

def mystery_c(data):
    n = len(data)
    target, lo, hi = data[-1], 0, n - 1
    while lo <= hi:                     # halving search (data is sorted range)
        mid = (lo + hi) // 2
        if data[mid] == target: return mid
        if data[mid] < target: lo = mid + 1
        else: hi = mid - 1
    return -1

def mystery_d(data):
    n = len(data)
    count = 0
    i = n
    while i >= 1:                       # outer: i halves -> log n iterations
        for _ in range(n):             # inner: full n each time
            count += 1
        i //= 2
    return count
```

**Step 1-2: measure & classify (run the checker):**

```python
suite = {
    "mystery_a": ("a", mystery_a, [2000, 4000, 8000, 16000, 32000]),
    "mystery_b": ("b", mystery_b, [200, 400, 800, 1600]),
    "mystery_c": ("c", mystery_c, [10000, 40000, 160000, 640000]),
    "mystery_d": ("d", mystery_d, [2000, 4000, 8000, 16000]),
}
for name, (_, fn, ns) in suite.items():
    p = fit_exponent(measure(fn, ns))
    print(f"{name}: exponent ≈ {p:.2f} -> {classify(p)}")
```

**Step 3: analytic proofs (what the measurements *should* confirm):**

- **mystery_a, Θ(n).** A single loop over `data` with O(1) body. Work = `Σ_{i=1}^{n} 1 = n`. Upper *and* lower bounded by linear ⇒ Θ(n). Fitted slope ≈ 1.0. ✓
- **mystery_b, Θ(n²).** Two nested full loops, O(1) body. Work = `Σ_{i=1}^{n} Σ_{j=1}^{n} 1 = n²`. To prove O(n²): the body runs at most n·n = n² times, so cost ≤ c·n² (take c = const-per-iteration, n₀ = 1). Ω(n²) similarly since it runs *exactly* n² times. ⇒ Θ(n²). Fitted slope ≈ 2.0. ✓
- **mystery_c, Θ(log n).** Binary search: the while loop halves `hi − lo` each iteration, so it runs at most `⌈log₂ n⌉ + 1` times (recurrence `T(n) = T(n/2)+O(1)`, Master Theorem Case 2 with c_crit=0 ⇒ Θ(log n)). Times barely grow as n quadruples (each ×4 adds ~2 comparisons) ⇒ near-flat log-log slope ≈ 0. ✓
- **mystery_d, Θ(n log n).** Outer loop runs `log₂ n` times (i halves); inner does n work each time. Total = `n · log₂ n` ⇒ Θ(n log n). Proof: work `= Σ_{level=0}^{log n} n = n(log₂ n + 1)`. To bound: `n log n ≤ work ≤ 2n log n` for large n ⇒ Θ(n log n). Fitted slope is *slightly above 1* (the log factor curves it up), which distinguishes it from pure linear `mystery_a`, exactly the curvature you watch for. ✓

That last contrast, `mystery_a` (slope ~1.0) vs `mystery_d` (slope ~1.0 but visibly curving up, and absolutely slower), is the practical lesson: pure log-log slope can't *cleanly* separate n from n log n, so you confirm with the analytic derivation. **Measurement proposes; proof disposes.**

## 🧪 Mini-project #2 - racing two algorithms for the same problem (the optimization arc)

This project recreates the single most common interview moment: "you have a brute-force solution; can you do better?" The problem is the classic **two-sum**: given a list and a target, do two elements add to the target? We'll implement it three ways with *different* complexities, verify they all give the same answer, then time them so the complexity gap is visible, the exact kind of time/space tradeoff interviewers want to see you reason about.

```python
import timeit, random

def two_sum_brute(nums, target):
    """O(n^2) time, O(1) space: check every pair."""
    n = len(nums)
    for i in range(n):
        for j in range(i + 1, n):
            if nums[i] + nums[j] == target:
                return (i, j)
    return None

def two_sum_sorted(nums, target):
    """O(n log n) time, O(n) space: sort, then two-pointer sweep."""
    indexed = sorted(range(len(nums)), key=lambda i: nums[i])   # O(n log n)
    lo, hi = 0, len(nums) - 1
    while lo < hi:                                              # O(n)
        s = nums[indexed[lo]] + nums[indexed[hi]]
        if s == target:
            return (indexed[lo], indexed[hi])
        if s < target:
            lo += 1
        else:
            hi -= 1
    return None

def two_sum_hash(nums, target):
    """O(n) time, O(n) space: one pass with a 'seen' hash map."""
    seen = {}                                                  # value -> index
    for i, x in enumerate(nums):
        if target - x in seen:                                # O(1) average lookup
            return (seen[target - x], i)
        seen[x] = i
    return None

# --- correctness: all three must agree on whether a pair EXISTS ---
random.seed(0)
for _ in range(1000):
    arr = [random.randint(-50, 50) for _ in range(random.randint(0, 30))]
    tgt = random.randint(-100, 100)
    found = [f(arr, tgt) is not None for f in (two_sum_brute, two_sum_sorted, two_sum_hash)]
    assert len(set(found)) == 1, (arr, tgt, found)
print("all three two-sum implementations agree on existence ✓")

# --- timing: watch the complexity gap open up as n grows ---
for n in [1000, 2000, 4000, 8000]:
    data = list(range(n))                       # worst-ish: target not present
    target = -1                                 # forces a full search
    tb = min(timeit.repeat(lambda: two_sum_brute(data, target),  number=1, repeat=3))
    ts = min(timeit.repeat(lambda: two_sum_sorted(data, target), number=1, repeat=3))
    th = min(timeit.repeat(lambda: two_sum_hash(data, target),   number=1, repeat=3))
    print(f"n={n:5d}  brute O(n^2)={tb:.4f}s  sorted O(n log n)={ts:.4f}s  hash O(n)={th:.5f}s")
```

What you'll see: as n doubles, the brute-force time roughly *quadruples* (n² shape), while the hash version barely moves (n shape). That widening gap, invisible at n=10, dramatic at n=8000, is the whole point of the chapter made tangible. The hash solution "buys" its speed with O(n) extra space (the `seen` map); the sorted solution is a middle ground. **Choosing among these based on the input size and memory budget is exactly the engineering judgment this chapter teaches.** Stretch goals: add an input where the pair is found early (best case) and watch brute force win for tiny n; fit the log-log slope of each with the checker above and confirm ≈2.0, ≈1.0, ≈1.0.

## ✏️ Exercises

1. **(easy)** Simplify to a single Big-O: `O(5n + 3)`, `O(2n² + 100n + 7)`, `O(n + log n)`, `O(n² + n³)`.
2. **(easy)** A loop runs `for i in range(n)` and inside does a *constant* amount of work. What's the complexity? What if the body itself loops `for j in range(n)`?
3. **(easy)** Binary search of a sorted array of 1,000,000 elements takes about how many comparisons in the worst case? What about 1,000,000,000 elements?
4. **(medium)** Prove `2n² + 3n = O(n²)` by exhibiting explicit constants c and n₀.
5. **(medium)** What is the time complexity of this loop, and why?
   ```python
   i = n
   while i > 0:
       do_constant_work()
       i //= 2
   ```
6. **(medium)** Is `n = O(n²)`? Is `n² = O(n)`? Is `n = Θ(n²)`? Justify each.
7. **(medium)** Give the recurrence for mergesort and solve it with the Master Theorem, identifying a, b, f(n), and c_crit.
8. **(hard)** Explain, using the geometric-series argument, why appending n elements to a dynamic array that *doubles* on resize is O(n) total, but appending to one that grows by a *fixed amount* (say +10) each resize is O(n²) total.
9. **(hard)** An algorithm has best case Θ(n), worst case Θ(n²). Can it be correct to also say it is "O(n²)"? Can you say it is "Θ(n²)"? Explain the difference between describing the *case* and bounding the *function*.
10. **(hard)** You're given that the input size is `n ≤ 10⁵`. A colleague proposes an O(n²) algorithm. Estimate the operation count, decide whether it's feasible within ~1 second, and suggest what complexity to target instead.

### Solutions

**1.** `O(5n+3) = O(n)`; `O(2n²+100n+7) = O(n²)`; `O(n + log n) = O(n)` (n dominates log n); `O(n² + n³) = O(n³)`. Always keep the single largest-growing term and drop constants.

**2.** Single loop, constant body: `O(n)`. With an inner `for j in range(n)`: the body runs n×n times → `O(n²)`.

**3.** Binary search is `⌈log₂ n⌉` comparisons. `log₂(10⁶) ≈ 20`, so about **20** comparisons. `log₂(10⁹) ≈ 30`, so about **30**. (1000× more data costs only ~10 extra comparisons, the magic of logarithmic growth.)

**4.** For all n ≥ 1, `3n ≤ 3n²` (since n ≤ n²). So `2n² + 3n ≤ 2n² + 3n² = 5n²`. Take **c = 5, n₀ = 1**: `2n² + 3n ≤ 5n²` for all n ≥ 1, hence `2n² + 3n = O(n²)`. ∎

**5.** `O(log n)`. The variable `i` is *halved* each iteration (`i //= 2`), so starting from n it reaches 0 after about `log₂ n` steps. Halving (or doubling) a loop counter is the signature of logarithmic time.

**6.** `n = O(n²)`: **yes**, `n ≤ 1·n²` for n ≥ 1, so c=1, n₀=1 works (it's a valid, if loose, upper bound). `n² = O(n)`: **no**, there's no constant c with `n² ≤ c·n` for all large n (that would require `n ≤ c`, impossible as n→∞). `n = Θ(n²)`: **no**, Θ requires both O and Ω; `n` is O(n²) but not Ω(n²) (n grows strictly slower), so it's not tight.

**7.** Mergesort: `T(n) = 2T(n/2) + Θ(n)`. So a=2, b=2, f(n)=n. `c_crit = log_b a = log₂ 2 = 1`. Compare f(n)=n to `n^c_crit = n¹`: they're the same order → **Case 2** → `T(n) = Θ(n^c_crit · log n) = Θ(n log n)`.

**8.** With *doubling*, resizes happen at capacities 1, 2, 4, …, n, and copying at each costs the current size, so total copies = `1 + 2 + 4 + … + n = 2n − 1 = O(n)` (a geometric series, which sums to about twice its last term). Amortized O(1) per append. With *fixed +10 growth*, resizes happen at sizes 10, 20, 30, …, n, copying `10 + 20 + … + n ≈ (n/10)·(n/2) = O(n²)` total (an *arithmetic* series, which sums to about half the count times the last term) → O(n) per append. The difference is geometric (cheap) vs arithmetic (expensive) series, which is exactly why real dynamic arrays multiply capacity rather than add a constant.

**9.** You can absolutely say it is "O(n²)", that's a true (and in this case tight, for the worst case) upper bound on its running time across all inputs. Saying it is "Θ(n²)" *unqualified* is misleading, because the best case is Θ(n), not Θ(n²), the function isn't sandwiched at n² for *all* inputs. The clean statements are: "*worst case* Θ(n²), *best case* Θ(n)." The "case" picks the input scenario; "O/Θ" bounds the running-time function within that scenario. Default to worst case because it's the only one that *guarantees* an upper bound.

**10.** O(n²) with n = 10⁵ means about `(10⁵)² = 10¹⁰` operations. At the rule-of-thumb ~10⁸ ops/second, that's roughly 100 seconds, far too slow for a ~1-second budget. The constraint is signaling an O(n log n) (≈ 10⁵ · 17 ≈ 1.7×10⁶ ops, instant) or O(n) target. Concretely: sort-then-sweep, or a hash-map single pass, the two-sum mini-project shows exactly this move.
