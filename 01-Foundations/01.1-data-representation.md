## 🌱 Start here (the gentle on-ramp)

Before any math, here's the one idea that this whole chapter rests on, in plain language.

Imagine a wall covered in light switches. Each switch is either **up** or **down**. That's all the wall can do, it can't display a number, spell a word, or show a photo. It just holds a pattern of ups and downs.

Now suppose we agree on a *secret code*: "to communicate a number, read the switches left to right as a binary number." Suddenly the same wall of dumb switches can communicate the number 42. Tomorrow we agree on a *different* code: "read the switches as letters." Now the identical wall spells "HI." **The switches never changed, only the agreement about how to read them changed.**

A computer is exactly this wall. Its "switches" are tiny electrical wires that are either *high voltage* (call it 1) or *low voltage* (call it 0). A computer does not "know" what a number, a letter, or a color is. It only holds patterns of high/low. Everything you've ever seen on a screen, this sentence, your bank balance, a cat video, is some pattern of high/low wires plus an *agreed-upon convention* for reading it.

So the entire subject of "data representation" boils down to one friendly question:

> **What convention turns these on/off wires into meaning?**

That's it. Once you stop thinking of it as magic and start thinking "it's just an agreement about how to read switches," every confusing thing in this chapter becomes approachable.

**Why this matters for you (and a future job):** every bug involving a weird number, a garbled emoji, a money calculation that's off by a penny, or a file that opens as gibberish traces back to a representation issue, a mismatch between how data was *written* and how it was *read*. Engineers who understand representation fix those bugs in minutes. Engineers who don't stare at them for days. This is genuinely one of the highest-use chapters in the book.

The thing that makes this click: a computer doesn't "know" about numbers, letters, or colors. It only has wires that are either *high* or *low*. Everything, this sentence, a photo, a bank balance, is a chosen **interpretation** of a pile of high/low wires. So the whole game of "data representation" is: *what convention turns these on/off wires into meaning?* Once you frame it as "conventions, not magic," it all opens up.

## 📐 Bits and bytes - the atoms

A **bit** is one wire: 0 or 1. That's the entire vocabulary. With *n* bits you can name 2^n distinct things, because each bit doubles the count:

```
1 bit  -> 2 states   (0, 1)
2 bits -> 4 states   (00, 01, 10, 11)
3 bits -> 8 states
n bits -> 2^n states
```

A **byte** is 8 bits, so a byte has 2^8 = 256 possible values (0-255). The byte is the standard unit of addressing, memory is a giant array of bytes, each with an address. Bigger groupings: a **nibble** is 4 bits (one hex digit, conveniently), a **word** is whatever the CPU's natural register width is (often 64 bits today).

Powers of two you should just *know* cold, because they show up everywhere:

```
2^0=1   2^1=2   2^2=4    2^3=8    2^4=16   2^5=32
2^6=64  2^7=128 2^8=256  2^10=1024 (~1K)  2^20 (~1M)  2^30 (~1G)
```

**Beginner intuition for "why doubling?"** Picture adding one more switch to your wall. Every pattern you could already make can now be made twice, once with the new switch down, once with it up. So one extra bit doubles the number of distinct patterns. That single observation explains the entire `2^n` formula, the size of a power set later in Chapter 1.3, and why adding one bit to a password roughly doubles the work to crack it.

A slow worked example so the formula isn't abstract. *How many distinct values fit in 3 bits?*

```
Start: 0 bits -> 1 pattern (the empty pattern)
Add a bit: 1 -> 2 patterns      (0, 1)
Add a bit: 2 -> 4 patterns      (00, 01, 10, 11)
Add a bit: 3 -> 8 patterns      (000, 001, 010, 011, 100, 101, 110, 111)
2^3 = 8. ✓
```

## 📐 Positional number systems

Decimal (base 10) is so automatic it's easy to forget it's a *convention*. The number 305 means:

```
3 * 10^2  +  0 * 10^1  +  5 * 10^0
= 300 + 0 + 5
```

Each digit's *position* carries a power of the **base**. That's the whole idea of a positional system, and it generalizes to *any* base b: the digit string d_k … d_2 d_1 d_0 means

```
value = Σ  d_i * b^i        (i from 0 to k)
```

with the rule that each digit is in range 0 … b-1. Base 2 uses digits {0,1}; base 16 uses {0..9, A..F} where A=10, …, F=15.

**Beginner framing:** the only thing that changes between bases is *how big each "place" is*. In decimal the places are 1, 10, 100, 1000 (powers of 10). In binary the places are 1, 2, 4, 8, 16 (powers of 2). In hex the places are 1, 16, 256 (powers of 16). The *idea*, "multiply each digit by its place value and add", is identical everywhere. You already do this fluently in base 10; you just have to retrain your eyes to new place values.

### Binary by hand

Binary `1011`:

```
1*2^3 + 0*2^2 + 1*2^1 + 1*2^0
= 8 + 0 + 2 + 1
= 11
```

Decimal → binary, the **repeated-division** method (divide by 2, collect remainders, read bottom-to-top):

```
13 / 2 = 6 r 1   <- least significant bit
 6 / 2 = 3 r 0
 3 / 2 = 1 r 1
 1 / 2 = 0 r 1   <- most significant bit
Read up:  1101  -> check: 8+4+0+1 = 13 ✓
```

The other direction, **subtract-largest-power**, is often faster mentally:

```
13: biggest power <=13 is 8 -> 1, leftover 5
     4 <= 5       -> 1, leftover 1
     2 <= 1? no   -> 0
     1 <= 1       -> 1, leftover 0
=> 1101
```

**One more fully-stepped example** so the method sticks. Convert decimal **42** to binary by subtract-largest-power:

```
42: biggest power <= 42 is 32 (2^5) -> bit5 = 1, leftover 42-32 = 10
    16 <= 10? no                    -> bit4 = 0
     8 <= 10? yes                   -> bit3 = 1, leftover 10-8 = 2
     4 <= 2?  no                    -> bit2 = 0
     2 <= 2?  yes                   -> bit1 = 1, leftover 0
     1 <= 0?  no                    -> bit0 = 0
Read bits high->low: 1 0 1 0 1 0 = 101010
Check: 32 + 8 + 2 = 42 ✓
```

(42 in binary being `101010` is a fun one to remember.)

### Hex by hand, and the binary↔hex shortcut

Hex is base 16. The magic is that **16 = 2^4**, so *every hex digit is exactly 4 binary bits.* Conversion is just grouping nibbles, no arithmetic:

```
binary:  1011 1110
nibble:   B    E
hex:     0xBE
```

And `0xBE` to decimal: `B=11, E=14` → `11*16 + 14 = 176 + 14 = 190`. That's why hex is the lingua franca of memory dumps: it's compact and trivially maps to bits. One byte is always exactly two hex digits (00-FF).

**A tiny lookup table** worth internalizing, the 16 nibble patterns. Once these are reflexive, binary↔hex is instant:

```
0=0000  1=0001  2=0010  3=0011   4=0100  5=0101  6=0110  7=0111
8=1000  9=1001  A=1010  B=1011   C=1100  D=1101  E=1110  F=1111
```

## 💻 Build it - int ↔ binary without `bin()`

To *prove* you understand the algorithms, no `bin()`/`hex()` cheating.

```python
def int_to_base(n: int, base: int, digits="0123456789ABCDEF") -> str:
    """Convert a non-negative int to a string in the given base (2..16)."""
    if n == 0:
        return "0"
    out = []
    while n > 0:
        n, r = divmod(n, base)   # repeated division, collect remainders
        out.append(digits[r])
    return "".join(reversed(out))  # remainders came out least-significant first

def base_to_int(s: str, base: int) -> int:
    """Parse a string in the given base back to an int (positional sum)."""
    value = 0
    for ch in s.upper():
        d = "0123456789ABCDEF".index(ch)
        assert d < base, f"digit {ch} not valid in base {base}"
        value = value * base + d   # Horner's method: shift left, add digit
    return value

# sanity checks
assert int_to_base(13, 2) == "1101"
assert int_to_base(190, 16) == "BE"
assert base_to_int("1101", 2) == 13
assert base_to_int("BE", 16) == 190
print("conversions OK")
```

Notice `base_to_int` uses **Horner's method**: instead of computing each `b^i` separately, you keep a running total and multiply by the base each step. `((1*2+1)*2+0)*2+1` = 13. Fewer multiplications, and it's the same trick used to evaluate polynomials efficiently.

**Walking Horner's method one step at a time** for `base_to_int("1101", 2)`, because it looks like magic until you trace it:

```
value = 0
read '1':  value = 0*2 + 1 = 1
read '1':  value = 1*2 + 1 = 3
read '0':  value = 3*2 + 0 = 6
read '1':  value = 6*2 + 1 = 13   <- done
```

See how each new digit "pushes" the existing total one place to the left (the `*2`) and then drops the new digit into the now-empty ones place (the `+ d`)? That's exactly what you do mentally when you read a number left to right.

## 📐 Unsigned integers and width

An *n*-bit **unsigned** integer holds 0 … 2^n − 1. An 8-bit unsigned byte holds 0…255. The crucial real-world fact: hardware registers have *fixed width*. When a computation exceeds the width, the high bits are simply dropped, arithmetic is done **modulo 2^n**:

```
255 + 1 in 8 bits:
  11111111
+ 00000001
=100000000   (9 bits)
   ^ this carry-out falls off the edge
=> 00000000 = 0     (wrapped around)
```

So unsigned 8-bit math is arithmetic mod 256. Python's own ints are *arbitrary precision* (they grow), which hides this, so to see wrapping you mask explicitly with `& 0xFF`. Keep that in your back pocket; it's how you simulate fixed-width hardware in Python.

**Beginner analogy:** it's an odometer. A car odometer with 6 digits rolls over from 999999 to 000000, it physically can't show a 7th digit, so the overflow just falls off. Fixed-width integers do the same thing, just in base 2 with however many bit-positions the register has. "Overflow" isn't an error the hardware reports; it's simply the most significant carry having nowhere to go.

## 📐 Signed integers - two's complement, derived

Now: how do you represent negatives with only 0s and 1s? Naive idea: steal the top bit as a sign flag ("sign-magnitude"). It works but has two warts: there are *two zeros* (+0 and −0), and addition needs special-casing. Computers almost universally use **two's complement** instead, and once you derive *why*, it stops being a memorized recipe.

**The defining idea:** in an *n*-bit two's complement system, the **most significant bit has a negative weight**. For 8 bits:

```
bit:    b7   b6   b5  b4  b3 b2 b1 b0
weight: -128  64  32  16   8  4  2  1
```

So `10000000` is exactly −128, and `11111111` is `−128+64+32+16+8+4+2+1 = −1`. That's it, that single sign-flip on the top weight *is* two's complement.

**Why this is genius:** addition works with *no special cases*. The hardware adder doesn't know or care about sign; the same binary addition that's correct for unsigned is correct for signed, because everything is arithmetic mod 2^n and we've just relabeled which residues we call "negative."

Concretely, in *n* bits, `−x` is represented by `2^n − x`. Check: `(−x) + x = 2^n ≡ 0 (mod 2^n)`. So −x added to x gives the carry-that-falls-off, i.e. zero. 

The **fast hand-trick** for negating: *invert all bits, then add 1.* Why does that equal `2^n − x`? Because inverting all bits computes `(2^n − 1) − x` (the all-ones value is `2^n − 1`, and flipping is subtracting from all-ones). Add 1 and you get `2^n − x`. The algebra *forces* the trick; it's not arbitrary.

```
Represent -5 in 8 bits:
   5         = 00000101
   invert    = 11111010
   add 1     = 11111011  = -5
   check via weights: -128 +64+32+16+8 +0+2+1 = -128+123 = -5 ✓
```

Range of *n*-bit two's complement: **−2^(n−1) … 2^(n−1) − 1**. For 8 bits that's −128…127. Note the asymmetry (one more negative), that's because zero "uses up" a slot on the positive side.

**Beginner intuition for the negative top bit.** Think of it as a price tag. The cheapest thing you can buy with the top bit alone is a debt of −128. Every *other* bit is a small positive coupon (64, 32, ...). So `11111111` is "I owe 128, but I've got 127 worth of coupons" = a net of −1. This "one big negative weight, then positive weights" picture is all two's complement is.

### Overflow (signed)

Signed overflow happens when the *true* result leaves the representable range. The tell: adding two positives yields a negative, or two negatives yields a positive.

```
127 + 1 in 8 bits:
  01111111
+ 00000001
= 10000000  = -128   <- overflowed from +127 to -128
```

```python
def to_signed(value: int, bits: int = 8) -> int:
    value &= (1 << bits) - 1            # keep only `bits` bits
    if value & (1 << (bits - 1)):       # top bit set => negative
        value -= (1 << bits)            # subtract 2^n
    return value

assert to_signed(0b11111011, 8) == -5
assert to_signed(0b10000000, 8) == -128
assert to_signed(0b01111111 + 1, 8) == -128   # overflow demo
print("two's complement OK")
```

## 📐 Bitwise operators - and *why* you'd use them

These operate bit-by-bit on the operands:

```
AND  &   1 only if BOTH bits 1      use: masking (keep some bits)
OR   |   1 if EITHER bit 1          use: setting flags
XOR  ^   1 if bits DIFFER           use: toggling, parity, swap
NOT  ~   flips every bit            use: building masks (~0 = all ones)
<<   left shift  (multiply by 2)    use: fast *2^k, building masks
>>   right shift (divide by 2)      use: fast /2^k, extracting fields
```

Real uses, concretely:

**Flags packed in one integer.** Instead of eight booleans, pack eight bits:

```python
READ, WRITE, EXEC = 1 << 0, 1 << 1, 1 << 2   # 0b001, 0b010, 0b100

perms = 0
perms |= READ | WRITE          # set bits        -> 0b011
has_write = bool(perms & WRITE) # test a bit      -> True
perms &= ~WRITE                # clear a bit      -> 0b001
perms ^= READ                  # toggle a bit     -> 0b000
```

This is literally how Unix file permissions and many config flags work.

**Masking, keep only certain bits.** `x & 0xFF` keeps the low byte. `(x >> 8) & 0xFF` extracts the *second* byte. That's how you pull RGBA channels out of a packed pixel.

**Fast multiply/divide by powers of two.** `x << 3` is `x * 8`; `x >> 3` is `x // 8` (for non-negative x). The compiler/CPU does shifts in basically one cycle. Caution: `>>` on negatives does *arithmetic* shift (sign-extends) in most languages, so it floors toward negative infinity, not toward zero.

**The XOR swap** (cute, rarely worth it, but illuminating):

```python
a, b = 5, 9
a ^= b; b ^= a; a ^= b   # now a==9, b==5, no temp variable
```

It works because XOR is its own inverse: `x ^ y ^ y == x`.

**Parity / counting set bits** uses XOR and AND too. A quick population count:

```python
def popcount(x: int) -> int:
    count = 0
    while x:
        x &= x - 1     # clears the lowest set bit each iteration
        count += 1
    return count
assert popcount(0b1011) == 3
```

`x & (x-1)` clearing the lowest set bit is a classic, subtracting 1 flips the lowest 1 to 0 and all the 0s below it to 1; AND-ing wipes exactly that lowest 1.

**Stepping through `x & (x-1)` once**, because "subtracting 1 flips the low run" is easier to *see* than to read:

```
x     = 0b101100   (the lowest set bit is the bit at position 2)
x - 1 = 0b101011   (the lowest 1 became 0; every 0 below it became 1)
x & (x-1) = 0b101000   (the lowest set bit is gone, nothing else changed)
```

Each loop iteration removes exactly one set bit, so the loop runs once per 1-bit, that's why it's a fast popcount.

## ⚠️ Common mistakes

These are the representation traps that bite real engineers (and probably will bite you):

- **Confusing bit-width with Python's behavior.** Python ints never overflow, they grow forever. If you're *simulating* an 8-bit or 32-bit machine, you MUST mask with `& 0xFF` / `& 0xFFFFFFFF`. Forgetting the mask is the #1 reason a "simulate the CPU" exercise gives wrong answers.
- **Mixing up MSB and LSB.** "Most significant" is the *biggest-value* bit (leftmost when written normally); "least significant" is the ones place (rightmost). Reading bits in the wrong order flips your whole number.
- **Assuming `>>` on a negative number divides toward zero.** In Python and most languages it's an *arithmetic* shift that floors toward negative infinity: `-7 >> 1 == -4`, not `-3`. Use `//` or be deliberate.
- **Comparing floats with `==`.** `0.1 + 0.2 == 0.3` is `False`. Always compare with a tolerance (see the float section).
- **Confusing a Unicode code point with its UTF-8 bytes.** `'€'` is *one* character (U+20AC) but *three* bytes in UTF-8. `len('€') == 1` but `len('€'.encode()) == 3`. Slicing bytes in the middle of a multi-byte character produces garbage.
- **Forgetting hex digits are 4 bits each, not some other size.** A byte is always exactly two hex digits. If your hex string has an odd number of digits, you've dropped a nibble somewhere.
- **Off-by-one on the signed range.** It's −128…**127**, not −128…128. Zero eats a positive slot, so there's one more negative than positive.

## 📐 Fixed point vs floating point

You have integers. How do you represent `3.14` or `0.001`?

**Fixed point**: pick a fixed number of fractional bits. E.g. treat an integer as "value × 2^−8", the low 8 bits are the fraction. Simple, exact for what fits, used in embedded/DSP and money (where you store integer *cents*). Downside: fixed range and fixed precision; can't represent huge and tiny numbers at once.

**Floating point**: store a number in (binary) scientific notation, `± mantissa × 2^exponent`, so the "point floats." This buys enormous dynamic range at the cost of *relative* (not absolute) precision. That tradeoff is the source of every floating-point surprise.

**Beginner picture.** Fixed point is like always writing money with exactly two decimal places: `$3.14`, `$0.01`, `$1000000.00`. Simple and exact, but you can't write `$0.000001` (too small for two places) or easily handle astronomical numbers. Floating point is like *scientific notation* you used in chemistry: `6.02 × 10^23` and `1.6 × 10^-19` both fit comfortably because the *decimal point moves* (it "floats") via the exponent. The cost is that you only keep a fixed number of *significant digits*, so very precise small adjustments to very large numbers get lost.

## 📐 IEEE 754 floats, from scratch

The standard (`float64`, Python's default) lays out 64 bits as:

```
[ sign : 1 ][ exponent : 11 ][ mantissa/fraction : 52 ]
```

The value (for "normal" numbers) is:

```
(-1)^sign  ×  1.fraction(in binary)  ×  2^(exponent - 1023)
```

Three pieces:

- **sign**: 0 = positive, 1 = negative.
- **exponent**: 11 bits, stored *biased* by 1023. So a stored value of 1023 means actual exponent 0; stored 1024 means +1; stored 1022 means −1. The bias lets a plain unsigned compare order the floats correctly.
- **mantissa**: 52 bits giving the fraction *after* an **implied leading 1**. Normalized scientific notation in base 2 always has a leading `1.` (just like decimal scientific notation always has one nonzero digit before the point), so we don't store it, we get 53 bits of precision for free from 52 stored bits.

Let's hand-encode `6.5`:

```
6.5 in binary = 110.1   (4+2+0 . 1/2)
normalize:    1.101 × 2^2
sign     = 0
exponent = 2 + 1023 = 1025 = 10000000001
mantissa = 101 0000...0   (the bits after "1.")
```

The killer insight: **most decimal fractions are infinite in binary.** `0.1` decimal is `0.0001100110011...` repeating forever in binary, exactly like `1/3 = 0.333…` is non-terminating in decimal. So `0.1` *cannot* be stored exactly in 52 bits; it's rounded. Same for `0.2`. Their rounding errors don't cancel, so:

```python
>>> 0.1 + 0.2
0.30000000000000004
>>> 0.1 + 0.2 == 0.3
False
```

Let's *see* the actual bits with `struct`, no hand-waving:

```python
import struct

def float_bits(x: float) -> str:
    [n] = struct.unpack(">Q", struct.pack(">d", x))   # double -> 64-bit uint
    bits = f"{n:064b}"
    return f"{bits[0]} {bits[1:12]} {bits[12:]}"       # sign | exp | mantissa

print(float_bits(6.5))
print(float_bits(0.1))
print(float_bits(0.2))
print(float_bits(0.1 + 0.2))
print(float_bits(0.3))           # NOTE: differs from 0.1+0.2 in the last bits

# show the true stored value of 0.1 in full decimal:
from decimal import Decimal
print(Decimal(0.1))   # 0.1000000000000000055511151231257827021181583404541015625
```

That `Decimal(0.1)` printout is the *exact* number the hardware is actually holding. It's not 0.1; it's the nearest representable double. Everything downstream inherits that tiny error.

**Walking the `0.1` problem slowly,** because this is the famous one. In decimal, fractions whose denominator is built only from the prime factors of 10 (2 and 5) terminate: `1/2 = 0.5`, `1/4 = 0.25`, `1/5 = 0.2`, clean. Anything else repeats: `1/3 = 0.333...`. Binary's only prime factor is 2, so *only* fractions with power-of-two denominators terminate in binary: `1/2`, `1/4`, `1/8` are clean (which is why `6.5 = 110.1` was exact above). But `0.1 = 1/10` has a factor of 5 in the denominator, so it *repeats forever* in binary, just like `1/3` repeats in decimal. We chop it off at 52 bits and round. That rounded value, plus the separately-rounded `0.2`, add up to something a hair above `0.3`, and the float closest to literal `0.3` is a *different* rounding, so they're not equal.

**Practical rules to follow:**
- Never `==` floats; compare with a tolerance: `abs(a-b) < 1e-9`.
- For money, use integer cents or `decimal.Decimal`.
- Beware catastrophic cancellation (subtracting two near-equal large floats loses precision).

Special bit patterns also exist: exponent all-zeros = subnormals/zero; exponent all-ones = ±infinity (mantissa 0) or NaN (mantissa nonzero). `float('inf')`, `float('nan')` are these. A famous gotcha: `float('nan') != float('nan')` is `True`, NaN is the only value not equal to itself, which is sometimes used as a sneaky NaN test.

## 📐 Text encoding - bytes to characters

Text is just *another convention* mapping numbers to glyphs.

**ASCII** (7 bits, 0-127) covers English letters, digits, punctuation, control codes. `'A' = 65`, `'a' = 97` (note: lowercase = uppercase + 32 = uppercase with bit 5 set, that's why `c | 0x20` lowercases a letter). `'0' = 48`.

**Unicode** is the universal catalog: every character gets a **code point**, written `U+XXXX`. `A` is U+0041, `€` is U+20AC, `😀` is U+1F600. Unicode is the *mapping from characters to numbers*; it does **not** say how to store those numbers as bytes. That's what an *encoding* does.

> **Keep these two ideas separate (a frequent confusion):** *Unicode* answers "which number is this character?" An *encoding* (like UTF-8) answers "how do I turn that number into bytes on disk?" One is a dictionary; the other is a packing scheme.

**UTF-8** is the dominant encoding, and it's beautiful: it's **variable-length** (1-4 bytes) and **backward-compatible with ASCII** (any code point ≤ 127 is one identical byte). The leading bits of the first byte announce the length:

```
code point range        bytes  pattern
U+0000  - U+007F          1     0xxxxxxx
U+0080  - U+07FF          2     110xxxxx 10xxxxxx
U+0800  - U+FFFF          3     1110xxxx 10xxxxxx 10xxxxxx
U+10000 - U+10FFFF        4     11110xxx 10xxxxxx 10xxxxxx 10xxxxxx
```

The `x` slots hold the code-point bits, packed big-endian. **Continuation bytes always start `10`**, which is how a decoder resyncs mid-stream and never confuses a continuation byte for a start byte. Self-synchronizing, really clever.

Hand-encode `€` = U+20AC. That's in the 3-byte range:

```
0x20AC = 0010 0000 1010 1100   (16 bits)
fit into 1110xxxx 10xxxxxx 10xxxxxx (4+6+6 = 16 bits):
   xxxx = 0010
 xxxxxx = 000010
 xxxxxx = 101100
bytes: 11100010 10000010 10101100 = E2 82 AC
```

Check in Python:

```python
>>> '€'.encode('utf-8')
b'\xe2\x82\xac'
```

## 💻 Build it - decode UTF-8 by hand

No `.decode()`. You'll read the leading bits, figure out the length, strip the header bits, and reassemble the code point.

```python
def utf8_decode(data: bytes) -> list[int]:
    """Return list of Unicode code points from raw UTF-8 bytes."""
    codepoints = []
    i = 0
    while i < len(data):
        b = data[i]
        if b >> 7 == 0b0:            # 0xxxxxxx  -> 1 byte (ASCII)
            cp, n = b & 0x7F, 1
        elif b >> 5 == 0b110:        # 110xxxxx  -> 2 bytes
            cp, n = b & 0x1F, 2
        elif b >> 4 == 0b1110:       # 1110xxxx  -> 3 bytes
            cp, n = b & 0x0F, 3
        elif b >> 3 == 0b11110:      # 11110xxx  -> 4 bytes
            cp, n = b & 0x07, 4
        else:
            raise ValueError(f"invalid lead byte {b:#x}")
        for k in range(1, n):        # fold in continuation bytes
            cont = data[i + k]
            if cont >> 6 != 0b10:    # must be 10xxxxxx
                raise ValueError("bad continuation byte")
            cp = (cp << 6) | (cont & 0x3F)
        codepoints.append(cp)
        i += n
    return codepoints

raw = "Hé€😀".encode("utf-8")
cps = utf8_decode(raw)
print([hex(c) for c in cps])              # ['0x48','0xe9','0x20ac','0x1f600']
print("".join(chr(c) for c in cps))       # Hé€😀
assert cps == [ord(c) for c in "Hé€😀"]
print("UTF-8 decode OK")
```

Each continuation byte contributes 6 fresh low bits, so you shift the accumulator left by 6 and OR them in, exactly reversing the encoding.

## 📐 Endianness

When a multi-byte value (say a 32-bit int) sits in memory, which byte comes first? Two conventions:

- **Big-endian**: most-significant byte at the lowest address (the way we write numbers left-to-right). Network protocols use this ("network byte order").
- **Little-endian**: least-significant byte first. x86/ARM (most machines you touch) are little-endian.

```python
import struct
n = 0x12345678
print(struct.pack(">I", n).hex())  # 12345678  big-endian
print(struct.pack("<I", n).hex())  # 78563412  little-endian
```

Endianness only matters at *boundaries*: reading binary files, network packets, or sharing memory between machines. Within one machine it's invisible. The `struct` format chars `>` and `<` pick byte order, get this wrong reading a binary file and you'll see garbage that's "byte-swapped."

**Beginner mnemonic** (from Gulliver's Travels, where the term comes from): big-endian breaks the egg at the *big* end first, the big (most significant) byte goes first. Little-endian breaks the little end first, the little (least significant) byte goes first.

## 🧪 Mini-project - a tiny hex viewer (like `xxd`)

Goal: dump any file as three columns, offset, hex bytes, ASCII gutter, exactly the format you see in real hex editors. This pulls together bytes, hex conversion, ASCII printability, and formatting.

```python
import sys

def hexdump(data: bytes, width: int = 16) -> str:
    lines = []
    for offset in range(0, len(data), width):
        chunk = data[offset:offset + width]

        # hex column: two hex digits per byte, space-separated,
        # with an extra space in the middle for readability
        hex_parts = []
        for i, b in enumerate(chunk):
            hex_parts.append(f"{b:02x}")
            if i == 7:
                hex_parts.append("")          # gap after 8 bytes
        hex_col = " ".join(hex_parts)
        hex_col = hex_col.ljust(width * 3 + 1)  # pad short last line

        # ASCII gutter: printable bytes shown, others as '.'
        ascii_col = "".join(
            chr(b) if 32 <= b < 127 else "." for b in chunk
        )

        lines.append(f"{offset:08x}  {hex_col} |{ascii_col}|")
    return "\n".join(lines)

if __name__ == "__main__":
    if len(sys.argv) > 1:
        with open(sys.argv[1], "rb") as f:
            data = f.read()
    else:
        data = b"Hello, hex!\n\x00\x01\x02\xff" + "café€".encode("utf-8")
    print(hexdump(data))
```

Run it:

```bash
$ python hexdump.py            # demo data
$ python hexdump.py myfile.png # any real file
```

Sample output for the demo bytes:

```
00000000  48 65 6c 6c 6f 2c 20 68  65 78 21 0a 00 01 02 ff  |Hello, hex! .....|
00000010  63 61 66 c3 a9 e2 82 ac                           |caf.....|
```

See it earn its keep: `café€` shows the multi-byte UTF-8 (`c3 a9` for é, `e2 82 ac` for €) as dots in the ASCII column but real bytes in hex. The offset is in hex too (`00000010` = 16). That ASCII gutter is incredibly handy for spotting strings inside binary files.

## 🧪 Mini-project #2 - a "number inspector" REPL

A second project to cement the *conversions* and *representations* into one tool. The idea: type any number, `42`, `0xBE`, `0b1011`, `-5`, `3.14`, and the inspector shows it in every form, plus its two's-complement byte pattern and (for floats) its IEEE-754 layout. This is the tool you'll wish you had while learning, and it forces you to wire together everything in this chapter.

```python
import struct

def inspect_int(n: int, width: int = 32):
    mask = (1 << width) - 1
    twos = n & mask                                   # two's-complement bit pattern
    print(f"  decimal : {n}")
    print(f"  hex     : {'-' if n < 0 else ''}0x{abs(n):X}")
    print(f"  binary  : {'-' if n < 0 else ''}0b{abs(n):b}")
    print(f"  {width}-bit two's complement: {twos:0{width}b}")
    print(f"  as bytes (big-endian)   : {twos.to_bytes(width // 8, 'big').hex()}")
    print(f"  popcount (set bits)     : {bin(twos).count('1')}")

def inspect_float(x: float):
    [bits] = struct.unpack(">Q", struct.pack(">d", x))
    s = f"{bits:064b}"
    sign, exp, mant = s[0], s[1:12], s[12:]
    biased = int(exp, 2)
    print(f"  value      : {x!r}")
    print(f"  sign|exp|mantissa: {sign} {exp} {mant}")
    print(f"  stored exponent  : {biased} (unbiased = {biased - 1023})")
    from decimal import Decimal
    print(f"  exact stored value: {Decimal(x)}")

def parse(token: str):
    """Parse user input in dec / 0x hex / 0b binary / float forms."""
    t = token.strip()
    try:
        if any(c in t for c in ".eE") and not t.lower().startswith("0x"):
            return float(t)
        return int(t, 0)            # base 0 auto-detects 0x / 0b / 0o prefixes
    except ValueError:
        return None

def repl():
    print("number inspector - type a number (42, 0xBE, 0b1011, -5, 3.14), 'q' to quit")
    while True:
        token = input("> ")
        if token.strip().lower() in ("q", "quit", "exit"):
            break
        val = parse(token)
        if val is None:
            print("  ?? couldn't parse that")
        elif isinstance(val, float):
            inspect_float(val)
        else:
            inspect_int(val)

# Demo without interactive input:
if __name__ == "__main__":
    print("== inspect 190 =="); inspect_int(190)
    print("== inspect -5  =="); inspect_int(-5)
    print("== inspect 0.1 =="); inspect_float(0.1)
    # repl()   # uncomment to run interactively
```

Sample output for `-5` (32-bit) shows the all-1s prefix that screams "negative in two's complement," and for `0.1` you'll see the unbiased exponent come out to `-4` and the exact stored value with its tell-tale `...0055511...` tail. **Stretch goals:** add `0o` octal output; add a "what character is this code point?" mode (`chr`/`ord`); show the UTF-8 bytes for any code point ≤ 0x10FFFF by calling `chr(n).encode('utf-8')`.

7. **(medium)** Hand-encode the character `é` (U+00E9) into UTF-8 bytes. Which length category is it in?
8. **(hard)** Explain in your own words, and with a short numeric argument, why `0.1 + 0.2 != 0.3` but `0.5 + 0.25 == 0.75` *is* exact.
9. **(hard)** A 32-bit register holds the bytes `78 56 34 12` in memory order. What 32-bit integer is this if the machine is little-endian? If big-endian?
10. **(hard)** Write `count_trailing_zeros(n)`, the number of 0 bits below the lowest set bit of a positive integer, using a bitwise trick, and explain it.

### Solutions

**1.** `0xB4`: `B = 1011`, `4 = 0100`, so binary is `1011 0100`. Decimal: `B=11`, so `11×16 + 4 = 176 + 4 = 180`. (Cross-check from binary: `128+32+16+4 = 180`. ✓)

**2.** Unsigned 12-bit max = `2^12 − 1 = 4095`. Signed 12-bit two's complement: range is `−2^11 … 2^11 − 1` = **−2048 … 2047**.

**3.**
```
100 = 01100100
200 = 11001000  (in 8 bits, 200 fits: 128+64+8 = 200)
sum = 100100100  (9 bits, true value 300)
keep low 8 bits: 00101100 = 44
```
`300 mod 256 = 44`. The 9th bit (the carry, value 256) falls off the fixed-width register, so 300 wraps to 44.

**4.**
```
 20        = 00010100
 invert    = 11101011
 add 1     = 11101100   = -20
 check: -128 +64+32+8+4 = -128 + 108 = -20 ✓
```

**5.**
```
5 = 0101, 3 = 0011
5 & 3 = 0001 = 1     (bits set in BOTH)
5 | 3 = 0111 = 7     (bits set in EITHER)
5 ^ 3 = 0110 = 6     (bits that DIFFER)
5 << 2 = 010100 = 20 (5 * 4)
20 >> 2 = 000101 = 5 (20 // 4)
```

**6.** `n > 0 and (n & (n - 1)) == 0`. A power of two has *exactly one* set bit (`1000...`). Subtracting 1 turns that bit into 0 and sets all lower bits (`0111...`), so the AND is 0. Any number with two or more set bits keeps at least one bit in common with `n-1`, so the AND is nonzero. The `n > 0` guard rejects 0 (which would falsely pass since `0 & -1 == 0`).

**7.** `é` = U+00E9 = `0x00E9` = `233`. That's in `U+0080, U+07FF`, the **2-byte** range (`110xxxxx 10xxxxxx`).
```
0x00E9 = 0000 1110 1001  -> 11 bits we need: 000 1110 1001
fill 110xxxxx 10xxxxxx (5 + 6 = 11 bits):
  xxxxx  = 00011
  xxxxxx = 101001
bytes: 11000011 10101001 = C3 A9
```
Check: `'é'.encode('utf-8') == b'\xc3\xa9'`. ✓

**8.** A binary fraction terminates *only* when its denominator is a power of two. `0.5 = 1/2` and `0.25 = 1/4` and `0.75 = 3/4` all have power-of-two denominators, so they're stored *exactly*, and exact + exact = exact, so `0.5 + 0.25 == 0.75`. But `0.1 = 1/10` has a factor of 5 in the denominator, so its binary expansion repeats forever and must be rounded to 52 bits; same for `0.2`. The two rounding errors don't cancel, and the result rounds to a double that is *not* the same double you get from the literal `0.3`. Hence `!=`.

**9.**
- Little-endian: the *first* byte is least significant, so the value is `0x12345678` = `305419896`.
- Big-endian: the first byte is most significant, so the value is `0x78563412` = `2018915346`.

**10.**
```python
def count_trailing_zeros(n: int) -> int:
    if n == 0:
        return 0          # convention: define for n>0
    # isolate the lowest set bit, then count its position
    low = n & (-n)        # -n is ~n + 1 (two's complement), so n & -n keeps ONLY the lowest set bit
    count = 0
    while low > 1:
        low >>= 1
        count += 1
    return count

assert count_trailing_zeros(0b101000) == 3   # lowest set bit at position 3
```
The trick `n & (-n)` works because `-n` in two's complement is `~n + 1`: inverting flips the low run of zeros to ones and the lowest 1 to 0, then `+1` carries back through, leaving exactly the lowest set bit aligned in both `n` and `-n`. AND-ing isolates that single bit; its position is the count of trailing zeros.
