## 🌱 Start here (the gentle on-ramp)

"Discrete math" sounds intimidating, but the name just means *math about separate, countable things*, whole numbers, yes/no facts, items in a list, dots connected by lines, as opposed to *continuous* math (calculus, smooth curves). Computers are discrete machines: they store distinct bits, take distinct steps, and hold finite collections. So discrete math is simply the math that fits how computers actually work. You've met most of it already without the fancy names:

- **Sets** are just collections with no duplicates, your contacts list, the unique words in a document. You "intersect" sets every time you ask "which friends do we have in common?"
- **Functions** are just reliable input→output machines, a vending machine maps button → snack, a dictionary maps word → definition.
- **Logic and quantifiers** are "for all" and "there exists", "*every* student passed" vs "*some* student passed." Knowing the difference is the difference between a tested program and a *proven* one.
- **Proof** is just convincing argument that something is true in *every* case, not just the few you tried. This is the single most valuable skill in the chapter, and it's less scary than it looks.
- **Counting (combinatorics)** answers "how many ways?" without listing them all, how many passwords, how many lottery outcomes, how many ways to seat guests.
- **Probability** is reasoning about uncertainty, spam filters, A/B tests, "is this test result trustworthy?"
- **Graphs** are dots-and-lines, your social network, a road map, the web's links.

**Why this matters for you (and a future job):** this is the chapter that makes the *rest of computer science* make sense. Big-O proofs (next chapter) are induction plus summations. Hash tables are modular arithmetic plus probability. Machine learning is probability. Databases, networks, and every data structure are graphs and trees wearing different hats. Interviewers test combinatorics ("how many ways..."), probability ("expected value of..."), and graph reasoning constantly. And the deepest payoff is *thinking in proofs*: the habit of asking "is this true for **all** inputs, or did I just get lucky on my test cases?" is what separates engineers whose code works from engineers who only *think* it works.

This is the chapter most people wish they'd actually *learned* instead of just memorizing names for. Discrete math is the grammar of computer science: complexity proofs are induction + summations, hashing is modular arithmetic + probability, cryptography is modular arithmetic, ML is probability, and every data structure is a graph or tree in disguise. The unifying skill is **proof**, being able to *justify* a claim for *all* cases, not just test a few. So we'll go slow on proofs and make every abstract idea runnable.

## 📐 Sets and set operations

A **set** is an unordered collection of distinct elements. `A = {1, 2, 3}`. Membership: `2 ∈ A`, `5 ∉ A`. The empty set is `∅` (or `{}`). Order and repetition don't matter: `{1,2,2} = {2,1} = {1,2}`.

Key operations (and their Python equivalents, Python's `set` maps almost 1:1):

```
Union          A ∪ B   = elements in A OR B          A | B
Intersection   A ∩ B   = elements in A AND B         A & B
Difference     A \ B   = in A but NOT B              A - B
Symmetric diff A △ B   = in exactly one             A ^ B
Subset         A ⊆ B   = every elem of A is in B     A <= B
Cardinality    |A|     = number of elements          len(A)
```

```python
A = {1, 2, 3, 4}
B = {3, 4, 5, 6}
assert A | B == {1, 2, 3, 4, 5, 6}
assert A & B == {3, 4}
assert A - B == {1, 2}
assert A ^ B == {1, 2, 5, 6}     # in exactly one
assert {1, 2} <= A               # subset
```

**Notice the echo of Chapter 1.2:** union is OR, intersection is AND, symmetric difference is XOR, difference is "A and not B." Set operations *are* Boolean logic applied to membership. If you understood the gates, you already understand sets.

The **power set** of A is the set of *all* subsets, and it has 2^|A| elements (each element is independently in or out, that doubling again, exactly like Chapter 1.1's bits). For `{a,b}` the power set is `{∅, {a}, {b}, {a,b}}`, 4 = 2^2 subsets.

```python
from itertools import combinations
def power_set(s):
    s = list(s)
    return [set(c) for r in range(len(s) + 1) for c in combinations(s, r)]
assert len(power_set({1, 2, 3})) == 2 ** 3      # 8 subsets
```

The **Cartesian product** `A × B` is the set of ordered pairs `(a,b)`. `|A × B| = |A| · |B|`. This is the multiplication principle in disguise, and it's the backbone of relations.

**Worked example, why power set is 2^n, slowly.** Take `{a, b, c}`. To *build* a subset, you make 3 independent yes/no decisions: "include a?", "include b?", "include c?" Each is 2 choices, and the choices are independent, so by the multiplication principle there are `2 × 2 × 2 = 2^3 = 8` subsets. This is the *exact same argument* as "n bits give 2^n patterns" from Chapter 1.1, a subset is just a bit-pattern saying which elements are in.

## 📐 Relations and functions

A **relation** from A to B is just a subset of `A × B`, a set of pairs saying "a is related to b." 

A **function** `f: A → B` is a special relation where *every* element of A maps to *exactly one* element of B. A is the **domain**, B the **codomain**, and the actual set of outputs is the **range** (range ⊆ codomain).

Three properties worth knowing by name (they show up in hashing, cryptography, type theory):

- **Injective** (one-to-one): different inputs → different outputs. No collisions. Formally `f(x)=f(y) ⇒ x=y`.
- **Surjective** (onto): every element of the codomain is hit by something.
- **Bijective**: both, a perfect pairing, so an inverse exists.

```python
# a function as a dict; check properties
f = {1: 'a', 2: 'b', 3: 'a'}                       # domain {1,2,3}, codomain {a,b,c}
codomain = {'a', 'b', 'c'}
injective  = len(set(f.values())) == len(f)        # False: 1 and 3 both -> 'a'
surjective = set(f.values()) == codomain           # False: 'c' never hit
print(injective, surjective)                        # False False
```

A hash function is a function from "all possible keys" to "a small set of buckets." Since the domain is way bigger than the codomain, it *cannot* be injective, pigeonhole guarantees collisions. That's why hash tables need collision handling. (More on this in probability below.)

**The pigeonhole principle**, stated plainly because it's a beloved interview tool: if you put `n+1` pigeons into `n` holes, some hole has at least two pigeons. Obvious, yet powerful, it instantly proves "any hash mapping more keys than buckets must collide," "in any group of 13 people two share a birth month," and "a lossless compressor cannot shrink *every* file." Whenever a problem says "show that two of these must be equal/share something," reach for pigeonhole.

**Everyday function intuition.** A function is a *promise*: "give me a valid input, I'll give you exactly one output, every time." Injective = "no two inputs share an output" (like unique usernames). Surjective = "every possible output is reachable" (every menu item can actually be ordered). Bijective = a perfect two-way matchup, so you can run it *backwards* (an encoder you can decode).

## 📐 Logic and quantifiers

From Chapter 1.2 you have ∧, ∨, ¬. Two more you need for proofs:

- **Implication** `P ⇒ Q` ("if P then Q"). It's *false only when P is true and Q is false*. Crucially, it's *true* whenever P is false ("vacuously true"). Its **contrapositive** `¬Q ⇒ ¬P` is logically equivalent, that equivalence powers the contrapositive proof technique.
- **Biconditional** `P ⇔ Q` ("P if and only if Q"): true when P and Q have the same truth value.

```
P Q | P⇒Q   contrapositive ¬Q⇒¬P
0 0 |  1            1
0 1 |  1            1
1 0 |  0            0
1 1 |  1            1     <- columns identical => equivalent
```

**Why "if P then Q" is true when P is false** trips up everyone, so here's the intuition: think of `P ⇒ Q` as a *promise*: "IF it rains, THEN I'll bring an umbrella." If it *doesn't* rain, you haven't broken your promise no matter what you do, the promise is only *broken* if it rains and you *don't* bring the umbrella. That single broken case (P true, Q false) is the only row where the implication is false. Everything else keeps the promise.

**Quantifiers** let you make statements about whole sets:

- **Universal** `∀x P(x)`, "for ALL x, P holds." Disproved by a single **counterexample**.
- **Existential** `∃x P(x)`, "there EXISTS an x with P." Proved by a single **witness**.

Negation flips them (this is the quantifier version of De Morgan):

```
¬(∀x P(x))  ≡  ∃x ¬P(x)      "not all" = "some don't"
¬(∃x P(x))  ≡  ∀x ¬P(x)      "none exist" = "all fail"
```

This matters constantly: "the algorithm is correct for all inputs" is a ∀ claim, testing a few inputs never proves it, but one failing input disproves it. That asymmetry is *why we prove things*.

## 📐 Proof techniques - worked out

Let's prove a small, concrete claim four different ways' worth of techniques.

**Before the techniques, the mindset.** A proof is just a chain of "therefore"s that any skeptic must accept, starting from things already agreed true and ending at the claim. The hard part isn't logic, it's choosing *which* technique fits. Rough guide: try a **direct** proof first; if "assume P, get Q" feels stuck, try the **contrapositive** (assume not-Q, get not-P); if even that's slippery, try **contradiction** (assume the claim is false and find an impossibility); and if the claim is "for all n ≥ something," reach for **induction**.

### Direct proof
Assume the hypotheses, deduce the conclusion step by step.

> **Claim.** If n is even, then n² is even.
>
> **Proof.** n even means `n = 2k` for some integer k (definition). Then `n² = (2k)² = 4k² = 2(2k²)`. Since `2k²` is an integer, n² is 2 × (an integer), i.e. even. ∎

### Proof by contrapositive
To prove `P ⇒ Q`, instead prove the equivalent `¬Q ⇒ ¬P`. Useful when the contrapositive is easier.

> **Claim.** If n² is even, then n is even.
>
> **Proof (contrapositive).** Prove instead: if n is *odd*, then n² is *odd*. Let `n = 2k+1`. Then `n² = 4k² + 4k + 1 = 2(2k²+2k) + 1`, which is odd. So `n odd ⇒ n² odd`, and by contraposition `n² even ⇒ n even`. ∎

### Proof by contradiction
Assume the claim is false, derive an impossibility.

> **Claim.** √2 is irrational.
>
> **Proof.** Suppose not: `√2 = a/b` in lowest terms (a, b share no common factor). Squaring: `2 = a²/b²`, so `a² = 2b²`, making a² even, hence a even (previous claim), so `a = 2c`. Then `2b² = 4c²`, so `b² = 2c²`, making b even too. But then a and b are both even, contradicting "lowest terms." The assumption is impossible, so √2 is irrational. ∎

### Mathematical induction - the workhorse
To prove `P(n)` holds for all integers `n ≥ n₀`:

1. **Base case:** show `P(n₀)` is true.
2. **Inductive step:** assume `P(k)` (the *inductive hypothesis*) and prove `P(k+1)`.

The intuition that sells it: it's *dominoes*. The base case knocks over the first domino; the inductive step guarantees each domino knocks over the next; therefore all of them fall. Or: it's recursion's correctness, written as math.

> **Claim.** `1 + 2 + … + n = n(n+1)/2` for all n ≥ 1.
>
> **Proof by induction.**
> - **Base (n=1):** LHS = 1; RHS = `1·2/2 = 1`. ✓
> - **Step:** Assume `1+…+k = k(k+1)/2`. Then
>   ```
>   1 + … + k + (k+1) = k(k+1)/2 + (k+1)              [inductive hypothesis]
>                     = (k+1)[ k/2 + 1 ]
>                     = (k+1)(k+2)/2                    [= P(k+1)'s RHS]
>   ```
>   which is exactly the formula with n = k+1. ✓
>
> Base + step ⇒ true for all n ≥ 1. ∎

> **Claim.** `1 + 2 + 4 + … + 2^n = 2^(n+1) − 1` (geometric sum we'll reuse for complexity).
>
> **Proof.** Base n=0: LHS = 1, RHS = `2¹−1 = 1`. ✓  Step: assume sum to `2^k` is `2^(k+1)−1`; then adding `2^(k+1)` gives `2^(k+1)−1 + 2^(k+1) = 2·2^(k+1) − 1 = 2^(k+2)−1`. ✓ ∎

### Proving a recursive function correct (induction in code)
This is where induction earns its keep for you as a programmer.

```python
def fact(n):
    if n == 0:           # base
        return 1
    return n * fact(n - 1)   # recurse
```

> **Claim.** `fact(n) == n!` for all n ≥ 0.
>
> **Proof by induction on n.**
> - **Base (n=0):** `fact(0)` returns 1, and `0! = 1`. ✓
> - **Step:** Assume `fact(k) == k!`. Then `fact(k+1) = (k+1) * fact(k) = (k+1) * k! = (k+1)!` by the inductive hypothesis. ✓ ∎

The recursive call structure *mirrors* the inductive step, that's not a coincidence; **recursion is induction made executable.** Whenever you write a recursive function you should be able to name the base case and the inductive step, and that *is* the correctness proof.

## ⚠️ Common mistakes

- **Confusing testing with proving.** Passing 100 test cases does *not* prove "for all n." It only takes one counterexample to demolish a ∀ claim, testing can disprove, never prove. This is the deepest lesson here.
- **Forgetting the base case in induction.** Without it, the dominoes never start falling. A "proof" with only the inductive step proves nothing. (Famous fake proofs that "all horses are the same color" sneak in by mishandling the base/step boundary.)
- **Using what you're trying to prove inside the proof (circular reasoning).** In the inductive *step*, you may assume `P(k)`, but you must derive `P(k+1)`, not assume it.
- **Negating quantifiers wrong.** `¬(∀x P(x))` is `∃x ¬P(x)`, *not* `∀x ¬P(x)`. "Not everyone is happy" means "someone is sad," not "everyone is sad."
- **Mixing up "if" and "if and only if."** `P ⇒ Q` does not give you `Q ⇒ P`. "If it's a dog, it's a mammal" doesn't mean "if it's a mammal, it's a dog."
- **Confusing permutations and combinations** (order matters vs not), see the combinatorics common-mistake note below.
- **Forgetting base rates in probability.** A "99% accurate" test for a rare disease is mostly false positives. Ignoring the base rate is the single most common probability error (worked below in the Bayes example).
- **Treating `a mod n` as possibly negative.** In math, `a mod n` lives in `0..n-1`. In some languages `%` can return a negative for negative inputs, know your language.

## 📐 Summations and how to manipulate them

Complexity analysis is mostly summations, so you need fluency. Notation: `Σ_{i=1}^{n} f(i)` means add up f(i) for i from 1 to n.

**Beginner decoder for sigma notation.** `Σ_{i=1}^{n} f(i)` is just a compact `for` loop: "start a running total at 0; for i from 1 to n, add f(i); return the total." In Python it's literally `sum(f(i) for i in range(1, n+1))`. Sigma is scarier-looking than it is.

Identities you must know cold:

```
Σ_{i=1}^{n} 1        = n
Σ_{i=1}^{n} i        = n(n+1)/2                  (proved above)
Σ_{i=1}^{n} i²       = n(n+1)(2n+1)/6
Σ_{i=0}^{n} r^i      = (r^(n+1) − 1)/(r − 1)     geometric, r ≠ 1
Σ_{i=0}^{∞} r^i      = 1/(1 − r)                 if |r| < 1
```

Manipulation rules: constants pull out `Σ c·f(i) = c·Σ f(i)`; sums split `Σ (f+g) = Σf + Σg`; re-indexing shifts bounds. 

Why a nested loop is O(n²): the inner loop runs `i` times on outer iteration `i`, so total work is `Σ_{i=1}^{n} i = n(n+1)/2 ≈ n²/2`, which is Θ(n²). Why mergesort is n log n: each of the `log n` levels does `n` work, so `Σ_{levels} n = n·log n`. We'll formalize all of this in [Chapter 1.4](01.4-complexity-and-big-o.md); here you just want the algebra reflexive.

```python
def sum_i(n):  return sum(range(1, n + 1))
def closed(n): return n * (n + 1) // 2
assert all(sum_i(n) == closed(n) for n in range(0, 1000))   # empirical check
```

**A famous quick derivation of `Σ i = n(n+1)/2`** (the "Gauss trick," allegedly discovered by Gauss as a schoolboy): write the sum forwards and backwards and add columns.
```
S =  1  +  2  + ... + (n-1) +  n
S =  n  + (n-1)+ ... +  2    +  1
2S = (n+1)+(n+1)+...+(n+1)+(n+1)     <- n copies of (n+1)
2S = n(n+1)   =>   S = n(n+1)/2
```
No induction needed, just clever pairing. (Induction *verifies* it; this *discovers* it.)

## 📐 Combinatorics - counting without enumerating

Two foundational principles:

- **Addition principle:** if a task can be done in *a* ways OR *b* mutually-exclusive ways, there are `a + b` ways.
- **Multiplication principle:** if a task is a sequence of independent choices with *a* then *b* options, there are `a · b` ways. (This is `|A × B| = |A|·|B|` again.)

**The one-sentence test for which to use:** "AND / sequential steps → multiply; OR / separate cases → add." Choosing an outfit (a shirt AND pants AND shoes) multiplies; choosing a single dessert that's either a cake OR a pie adds.

**Permutations**, ordered arrangements. Number of ways to arrange r items from n distinct items:

```
P(n, r) = n! / (n − r)!         (order matters)
P(n, n) = n!                     (arrange all of them)
```

**Combinations**, unordered selections. Number of ways to *choose* r from n:

```
C(n, r) = "n choose r" = n! / ( r! (n−r)! )
```

The intuition for why we divide by r!: every unordered combination corresponds to r! ordered permutations, so we collapse them by dividing. C(n,r) is the **binomial coefficient**, written `(n r)`, and it appears in `(x+y)^n = Σ_{k} C(n,k) x^k y^(n-k)`, the binomial theorem.

**Pascal's identity** (the recursive heart of binomials):

```
C(n, r) = C(n−1, r−1) + C(n−1, r)
```

Intuition: pick a specific element. Either it's in your chosen group (then choose r−1 from the rest) or it isn't (choose r from the rest). Add the two mutually-exclusive cases.

**Worked example, slowly, a 4-person committee from 10 people.** Order doesn't matter (a committee of {Ann, Bob} is the same as {Bob, Ann}), so it's a *combination*:
```
C(10, 4) = 10! / (4! · 6!) = (10·9·8·7) / (4·3·2·1) = 5040 / 24 = 210
```
But if the four roles were *distinct* (president, VP, secretary, treasurer), order *would* matter, so it's a *permutation*: `P(10,4) = 10·9·8·7 = 5040`, exactly `4! = 24` times larger, because each committee can be arranged into 24 ordered slates. That ratio is the "divide by r!" intuition made concrete.

**⚠️ Combinatorics-specific mistake:** the #1 error is using a permutation when you meant a combination (or vice versa). Always ask "does order matter?" Lottery numbers: order doesn't matter → combination. Race finishes (gold/silver/bronze): order matters → permutation. A second common slip is double-counting in "OR" problems where the cases overlap (then you need inclusion-exclusion: `|A ∪ B| = |A| + |B| − |A ∩ B|`).

## 💻 Build it - enumerate AND count, then verify identities

Let's compute combinatorics two ways, by *enumerating* (slow, obviously correct) and by *formula* (fast), and assert they agree. That's how you trust the formulas.

```python
from math import factorial
from itertools import permutations, combinations

def P(n, r): return factorial(n) // factorial(n - r)
def C(n, r): return factorial(n) // (factorial(r) * factorial(n - r))

# verify against brute-force enumeration
items = list(range(6))
for r in range(len(items) + 1):
    assert P(len(items), r) == len(list(permutations(items, r)))
    assert C(len(items), r) == len(list(combinations(items, r)))
print("P and C formulas match enumeration ✓")

# verify Pascal's identity empirically
for n in range(1, 30):
    for r in range(1, n):
        assert C(n, r) == C(n - 1, r - 1) + C(n - 1, r)
print("Pascal's identity holds ✓")

# verify the binomial theorem numerically: (x+y)^n = Σ C(n,k) x^k y^(n-k)
def binom_expand(x, y, n):
    return sum(C(n, k) * x**k * y**(n - k) for k in range(n + 1))
assert binom_expand(2, 3, 5) == (2 + 3) ** 5
print("binomial theorem verified ✓")
```

This "empirical check of a closed form" pattern is exactly the proof-helper mini-project below, generalized.

## 📐 Basic probability

A **sample space** Ω is the set of all possible outcomes. An **event** is a subset of Ω. For equally-likely outcomes, `P(event) = |event| / |Ω|`. Axioms: `0 ≤ P(E) ≤ 1`, `P(Ω) = 1`, and for disjoint events probabilities add.

A fair die: Ω = {1,…,6}, P(even) = |{2,4,6}|/6 = 1/2.

**Beginner framing:** probability for equally-likely outcomes is just *counting*, "favorable outcomes divided by total outcomes." It's combinatorics with a denominator. That's why this section follows counting.

**Conditional probability**, probability of A *given* B already happened:

```
P(A | B) = P(A ∩ B) / P(B)        (requires P(B) > 0)
```

We restrict the universe to B, then ask what fraction of B is also A.

**Independence:** A and B are independent iff `P(A ∩ B) = P(A)·P(B)`, equivalently `P(A|B) = P(A)`, knowing B tells you nothing about A.

**Bayes' theorem**, flipping a conditional, the single most useful formula in all of applied CS (spam filters, medical tests, ML classifiers):

```
P(A | B) = P(B | A) · P(A) / P(B)
```

It comes straight from the definition: both `P(A|B)P(B)` and `P(B|A)P(A)` equal `P(A∩B)`, so set them equal and divide.

### Worked Bayes example (the classic that breaks intuition)

> A disease affects 1% of people. A test is 99% accurate (99% true-positive rate, and 99% true-negative rate, so 1% false positive). You test positive. What's the probability you actually have the disease?

Let D = "has disease", + = "tests positive".
```
P(D) = 0.01            P(+|D) = 0.99
P(¬D) = 0.99           P(+|¬D) = 0.01     (false positive rate)

P(+) = P(+|D)P(D) + P(+|¬D)P(¬D)          [law of total probability]
     = 0.99·0.01 + 0.01·0.99
     = 0.0099 + 0.0099 = 0.0198

P(D | +) = P(+|D)P(D) / P(+)
         = 0.0099 / 0.0198
         = 0.5            <- only 50%!
```

Only 50%, even with a "99% accurate" test! Because the disease is rare, the false positives (from the huge healthy population) roughly equal the true positives. *This* is why base rates matter, and why a positive screening result usually warrants a confirmatory test. Worth burning into memory.

**The "count the people" version** that makes it click without algebra: imagine 10,000 people. 1% (100 people) have the disease; of them 99 test positive. The other 9,900 are healthy; 1% of them (99 people) *also* test positive (false positives). So 99 + 99 = 198 people test positive, but only 99 truly have it: `99/198 = 50%`. Turning probabilities into *natural frequencies* (whole people) makes Bayes intuitive, this is a genuinely useful trick in interviews and in life.

**Expectation**, the long-run average value of a random variable X:

```
E[X] = Σ_x  x · P(X = x)
```

Fair die: `E[X] = (1+2+…+6)/6 = 21/6 = 3.5`. **Linearity of expectation**, `E[X+Y] = E[X]+E[Y]` *even when X,Y aren't independent*, is a superpower for analyzing randomized algorithms (e.g., expected number of hash collisions, average-case quicksort).

**Tie to CS:** hashing relies on probability, with good hashing, collisions behave like the "birthday problem" and expected bucket occupancy is analyzable. ML is essentially "estimate P(label | features)", Bayes again. Randomized algorithms (quicksort's pivot, skip lists, bloom filters) are analyzed with expectation and these axioms.

## 📐 Modular arithmetic

`a mod n` is the remainder when a is divided by n; it lives in `{0, 1, …, n−1}`. We say `a ≡ b (mod n)` ("congruent") when `n` divides `a − b`, i.e. they have the same remainder. This is *clock arithmetic*: on a 12-hour clock, `15 ≡ 3 (mod 12)`.

It plays beautifully with arithmetic:

```
(a + b) mod n = ((a mod n) + (b mod n)) mod n
(a · b) mod n = ((a mod n) · (b mod n)) mod n
```

So you can reduce *as you go* and never overflow, essential for big-number crypto. (And it's exactly the fixed-width integer wraparound from Chapter 1.1: 8-bit math is arithmetic mod 256.)

**The clock is the whole intuition.** "What time is it 5 hours after 10 o'clock?" You compute `(10 + 5) mod 12 = 3`. You don't say "15 o'clock", you wrap around. Modular arithmetic is just doing math on a circle of size n instead of an infinite line. Days of the week (mod 7), array indices that wrap (mod length), and byte arithmetic (mod 256) are all clocks.

Why it matters: **hashing** maps a big key to a bucket index via `hash(key) mod table_size` (prime sizes reduce clustering). **Cryptography** (RSA, Diffie-Hellman) lives entirely in modular arithmetic, e.g. modular exponentiation `a^b mod n`, computed efficiently by **fast exponentiation** (square-and-multiply, O(log b) multiplications):

```python
def mod_pow(base, exp, mod):
    result = 1
    base %= mod
    while exp > 0:
        if exp & 1:                       # if current low bit set, multiply in
            result = (result * base) % mod
        base = (base * base) % mod        # square the base
        exp >>= 1                          # next bit
    return result

assert mod_pow(3, 13, 7) == pow(3, 13, 7)     # check vs Python's built-in
print("fast modular exponentiation OK")
```

Note this is the *same bit-by-bit structure* as the int conversions in 1.1 and ALU dispatch in 1.2, bits driving an algorithm.

A useful theorem to know by name: **Fermat's little theorem**, if p is prime and a not divisible by p, then `a^(p−1) ≡ 1 (mod p)`. It underlies primality testing and RSA.

## 📐 Graphs and trees as math objects

Let's define these precisely now because *everything* later (data structures, algorithms, networks) is built on them.

A **graph** `G = (V, E)` is a set of **vertices** V and a set of **edges** E ⊆ V × V connecting them.

- **Undirected** vs **directed** (edges as unordered `{u,v}` vs ordered `(u,v)`).
- **Degree** of a vertex: number of incident edges. In a directed graph, in-degree and out-degree.
- **Handshake lemma:** `Σ deg(v) = 2|E|` (each edge contributes to two vertices' degrees), a tiny but constantly-used counting fact, and a baby induction/counting exercise.
- **Path:** a sequence of vertices each adjacent to the next. **Cycle:** a path returning to its start. **Connected:** every pair has a path between them.
- **Weighted graph:** edges carry numbers (distances, costs), sets up shortest paths.

**Plain-language picture.** A graph is dots (vertices) connected by lines (edges). That's it. A subway map is a graph (stations + lines). Your friends list is a graph (people + friendships, undirected, since friendship is mutual). Twitter's follow network is a *directed* graph (you can follow someone who doesn't follow back). "Degree" is just "how many lines touch this dot", your number of friends. The handshake lemma says if you add up everyone's friend-counts, you get twice the number of friendships, because each friendship is counted once by each person in it.

A **tree** is a connected, **acyclic** undirected graph. Equivalent characterizations (any one implies the rest, and proving their equivalence is a great induction workout):

- A tree on n vertices has *exactly* `n − 1` edges.
- There's a *unique* path between any two vertices.
- Adding any edge creates exactly one cycle; removing any edge disconnects it.

A **rooted tree** designates a root; then we get parent/child, leaves (no children), depth, and height, the vocabulary for binary search trees, heaps, parse trees, file systems, etc.

**A tree is a family tree / folder structure.** A rooted tree is exactly your computer's folder hierarchy: one root folder, each folder has one parent and any number of children, no folder is its own ancestor (that's the "acyclic" part), and there's exactly one path from the root to any file. The "n−1 edges" fact, in folder terms: every folder/file except the root has exactly one parent link, so n items have n−1 links.

```python
# adjacency-list graph; compute degrees and verify the handshake lemma
graph = {
    'a': ['b', 'c'],
    'b': ['a', 'c'],
    'c': ['a', 'b', 'd'],
    'd': ['c'],
}
edges = sum(len(neighbors) for neighbors in graph.values()) // 2   # undirected
degree_sum = sum(len(n) for n in graph.values())
assert degree_sum == 2 * edges                                     # handshake lemma ✓
print(f"|V|={len(graph)} |E|={edges}, Σdeg={degree_sum}=2|E| ✓")
```

We'll revisit graphs hard later (BFS/DFS, Dijkstra, MSTs). For now you just need the definitions to be second nature.

## 🧪 Mini-project - a "proof helper" + Monte Carlo estimator

Two tools that capture this chapter's spirit: **empirically check a claimed closed form against brute force for many n**, and **estimate a probability by simulation** and see it match the math.

### Part 1 - closed-form checker

```python
def check_closed_form(brute, closed, lo=0, hi=500):
    """Assert brute(n) == closed(n) for n in [lo, hi). Returns first failure or None."""
    for n in range(lo, hi):
        if brute(n) != closed(n):
            return n, brute(n), closed(n)
    return None  # all matched

# sum of first n integers
ok = check_closed_form(lambda n: sum(range(1, n + 1)),
                       lambda n: n * (n + 1) // 2)
assert ok is None

# sum of first n squares
ok = check_closed_form(lambda n: sum(i*i for i in range(1, n + 1)),
                       lambda n: n * (n + 1) * (2 * n + 1) // 6)
assert ok is None

# sum of first n odd numbers == n^2  (a classic, provable by induction)
ok = check_closed_form(lambda n: sum(range(1, 2 * n, 2)),
                       lambda n: n * n)
assert ok is None
print("all closed-form conjectures survived brute-force checking ✓")
```

This is a *conjecture machine*: if a formula survives hundreds of n's it's almost certainly right and worth proving by induction. (It's empirical evidence, not a proof, but it tells you what to prove. If it *fails*, you just found your counterexample, disproving the ∀ claim instantly.)

### Part 2 - Monte Carlo: the Monty Hall problem

The famous puzzle: 3 doors, a car behind one, goats behind the other two. You pick a door. The host (who knows where the car is) opens a *different* door revealing a goat, then offers you the chance to switch. **Should you switch?**

The math: your initial pick is right with probability 1/3. The car is behind one of the *other two* doors with probability 2/3. The host's reveal concentrates that entire 2/3 onto the single remaining unopened door. So **switching wins 2/3 of the time**, double staying.

```python
import random

def monty_hall(switch: bool, trials: int = 200_000) -> float:
    wins = 0
    for _ in range(trials):
        car = random.randint(0, 2)
        pick = random.randint(0, 2)
        # host opens a door that's neither the pick nor the car
        host = next(d for d in range(3) if d != pick and d != car)
        if switch:
            pick = next(d for d in range(3) if d != pick and d != host)
        wins += (pick == car)
    return wins / trials

stay   = monty_hall(switch=False)
switch = monty_hall(switch=True)
print(f"stay  wins ≈ {stay:.3f}  (theory 1/3 ≈ 0.333)")
print(f"switch wins ≈ {switch:.3f} (theory 2/3 ≈ 0.667)")
assert abs(switch - 2/3) < 0.01 and abs(stay - 1/3) < 0.01
```

**Why simulation and math agree:** the **law of large numbers** says the empirical frequency of an event converges to its true probability as trials → ∞. The simulation is literally sampling the sample space; the proportion of "wins" estimates `P(win)`. When the analytic 2/3 and the simulated 0.667 match, each *validates* the other, the simulation catches errors in your reasoning, and the proof tells you the simulation isn't a fluke. That feedback loop is, honestly, how you'll want to sanity-check every probabilistic claim from now on.

**Stretch goals:** estimate π by throwing random darts in a square (ratio inside the unit circle is π/4); empirically verify the birthday paradox (23 people → >50% shared birthday) and connect it to hash collisions; estimate `E[X]` for a dice game and compare to the analytic expectation.

## 🧪 Mini-project #2 - graph reachability and "is it a tree?" checker

This project turns the graph/tree *definitions* into working code, and previews the traversal algorithms of later chapters. Given an undirected graph as an adjacency list, you'll (1) find everything reachable from a start vertex (a breadth-first sweep), (2) test whether the graph is connected, and (3) decide whether it's a **tree** using the rigorous criteria above, connected, and exactly `n−1` edges.

```python
from collections import deque

def reachable(graph, start):
    """All vertices reachable from `start` via BFS. Returns a set."""
    seen = {start}
    queue = deque([start])
    while queue:
        v = queue.popleft()
        for nbr in graph[v]:
            if nbr not in seen:
                seen.add(nbr)
                queue.append(nbr)
    return seen

def is_connected(graph):
    if not graph:
        return True                       # empty graph: vacuously connected
    start = next(iter(graph))
    return reachable(graph, start) == set(graph)

def edge_count(graph):
    return sum(len(nbrs) for nbrs in graph.values()) // 2   # undirected

def is_tree(graph):
    """A tree: connected AND |E| == |V| - 1 (which together forbid cycles)."""
    n = len(graph)
    return is_connected(graph) and edge_count(graph) == n - 1

# --- a tree (4 nodes, 3 edges, connected) ---
tree = {'a': ['b', 'c'], 'b': ['a'], 'c': ['a', 'd'], 'd': ['c']}
assert is_tree(tree)
assert reachable(tree, 'a') == {'a', 'b', 'c', 'd'}

# --- has a cycle (4 nodes, 4 edges) -> connected but NOT a tree ---
cyclic = {'a': ['b', 'c'], 'b': ['a', 'd'], 'c': ['a', 'd'], 'd': ['b', 'c']}
assert is_connected(cyclic)
assert not is_tree(cyclic)                # n-1 = 3 edges expected, but it has 4

# --- disconnected (two components) -> not a tree ---
forest = {'a': ['b'], 'b': ['a'], 'c': ['d'], 'd': ['c']}
assert not is_connected(forest)
assert not is_tree(forest)
print("graph reachability + tree detection verified ✓")
```

Why this works ties straight back to the theory: a connected graph with exactly `n − 1` edges *cannot* contain a cycle (a cycle would require at least n edges to stay connected), so "connected + (n−1) edges" is an iron-clad tree test, one of the equivalent characterizations listed above, now executable. **Stretch goals:** count connected components (number of BFS sweeps needed to cover all vertices); detect a cycle directly during DFS; verify the handshake lemma on each test graph by comparing `2*edge_count` to the degree sum.

## ✏️ Exercises

1. **(easy)** Let `A = {1,2,3,4,5}` and `B = {2,4,6}`. Compute `A ∪ B`, `A ∩ B`, `A − B`, and `A △ B`.
2. **(easy)** How many elements are in the power set of a 6-element set? How many subsets have exactly 2 elements?
3. **(easy)** A password is 4 characters, each a lowercase letter (26 options). How many possible passwords? What if no character may repeat?
4. **(medium)** Write the negation of "∀ students s, s passed the exam." Then write the negation of "∃ a number that is both even and prime and greater than 2."
5. **(medium)** Prove by induction that `1 + 3 + 5 + … + (2n−1) = n²` for all n ≥ 1.
6. **(medium)** A fair six-sided die is rolled twice. What is the probability the sum is 7? (List the favorable outcomes.)
7. **(medium)** Compute `7^100 mod 5` by hand using modular reduction (don't compute the giant number).
8. **(hard)** Prove by induction that a binary tree of height h has at most `2^(h+1) − 1` nodes.
9. **(hard)** In a class of 30 students, use the pigeonhole principle to argue that at least two students were born in the same month. Then state the more general "generalized pigeonhole" version for "at least 3 in the same month."
10. **(hard)** Two fair dice are rolled. Let A = "first die is even," B = "sum is 7." Are A and B independent? Show the computation.

### Solutions

**1.** `A ∪ B = {1,2,3,4,5,6}`. `A ∩ B = {2,4}`. `A − B = {1,3,5}`. `A △ B = {1,3,5,6}` (in exactly one, everything except the shared 2 and 4).

**2.** Power set has `2^6 = 64` elements. Subsets of size exactly 2: `C(6,2) = 15`.

**3.** With repetition allowed: each of 4 positions has 26 choices → `26^4 = 456,976`. With no repeats (a permutation): `26 × 25 × 24 × 23 = P(26,4) = 358,800`.

**4.** Negation of "∀s, s passed" is "∃s such that s did **not** pass", *some* student failed. Negation of "∃ a number even, prime, and > 2" is "∀ numbers, **not** (even and prime and > 2)", every number fails at least one of those conditions (which happens to be true: the only even prime is 2).

**5.** Base (n=1): LHS = 1, RHS = 1² = 1. ✓ Step: assume `1+3+…+(2k−1) = k²`. Then adding the next odd number `(2k+1)`:
```
k² + (2k+1) = k² + 2k + 1 = (k+1)²
```
which is the formula for n = k+1. ✓ By induction, true for all n ≥ 1. (The closed-form checker in the mini-project tests exactly this.)

**6.** Total outcomes = 36. Sum-7 outcomes: (1,6),(2,5),(3,4),(4,3),(5,2),(6,1) = 6. Probability = `6/36 = 1/6`.

**7.** Reduce the base first: `7 ≡ 2 (mod 5)`, so `7^100 ≡ 2^100 (mod 5)`. Powers of 2 mod 5 cycle: `2,4,3,1,2,4,3,1,...` with period 4. `100 mod 4 = 0`, which lands on the *end* of a cycle = `1`. So `7^100 ≡ 1 (mod 5)`. (Check with `pow(7, 100, 5)` → 1.)

**8.** A binary tree of height h: each node has ≤ 2 children. Base (h=0): a single node, and `2^1 − 1 = 1`. ✓ Step: assume a height-k tree has ≤ `2^(k+1) − 1` nodes. A height-(k+1) tree is a root plus at most two subtrees, each of height ≤ k:
```
nodes ≤ 1 + 2·(2^(k+1) − 1) = 1 + 2^(k+2) − 2 = 2^(k+2) − 1
```
which is the bound for height k+1. ✓ (This is why a balanced tree of height h holds up to ~2^h nodes, and why search is O(log n).)

**9.** 12 months are the "holes," 30 students the "pigeons." Since 30 > 12, at least two students share a month, pigeonhole. Generalized pigeonhole: with n pigeons in k holes, some hole has at least `⌈n/k⌉` pigeons. Here `⌈30/12⌉ = 3`, so in fact at least **three** students share a birth month.

**10.** `P(A) = 1/2` (first die even: 3 of 6). `P(B) = 6/36 = 1/6` (sum 7). `A ∩ B` = first die even AND sum 7 = {(2,5),(4,3),(6,1)} = 3 outcomes, so `P(A∩B) = 3/36 = 1/12`. Independence test: `P(A)·P(B) = (1/2)(1/6) = 1/12 = P(A∩B)`. They **are** independent. (A pleasant surprise, knowing the first die is even tells you nothing about whether the sum is 7.)
