# Chapter 24.1 - Lexing, Parsing & Abstract Syntax Trees

> *Goal: stop treating "the compiler" as a black box and build the **front end** of a real programming language from scratch in Python. By the end you'll take a string of source code like `var x = 1 + 2 * 3;` and turn it, with your own hands, into a stream of **tokens**, then into a tree-shaped **AST** that you can pretty-print and walk. For many people, "compiler" lives in the head as a wall of dragons, parsers, grammars, LALR tables, scary academic notation. A lexer is a loop with a few `if`s. A recursive-descent parser is *literally just recursion* (Chapter [03.1](../03-Algorithms/03.1-recursion.md)) walking a grammar. An AST is just a tree (Chapter [02.5](../02-Data-Structures/02.5-trees.md)). There is no magic here, and we're going to prove it by writing all of it ourselves.

We're building a small language, call it **Lox-ish**, after the teaching language in *Crafting Interpreters*. It will have numbers, strings, variables, arithmetic with correct precedence, comparisons, `print`, `if`/`while`, blocks, and (in 24.2) functions and closures. This chapter builds the **front end**: source → tokens → AST. Chapter [24.2](./24.2-interpreters-and-vms.md) builds the **back end**: AST → execution (a tree-walking interpreter, a type checker, and a bytecode VM). Same language, one coherent codebase across both chapters.

## 🌱 Start here

Before any code, let's ground the whole thing in something physical.

**Reading a sentence out loud.** When you read "The cat sat on the mat," your brain does three things so fast you never notice them. First, your eyes chunk the stream of letters into **words**, `The`, `cat`, `sat`, by noticing the spaces. That chunking is *lexing*: turning a flat stream of characters into a stream of meaningful units. Second, you fit those words into a **grammatical structure**, subject (`the cat`), verb (`sat`), prepositional phrase (`on the mat`). That structuring is *parsing*: discovering the tree hidden inside the flat sequence. Third, you *understand* it, you picture an actual cat on an actual mat. That's *evaluation* (Chapter 24.2).

A compiler does exactly this to source code:

```text
  source text          tokens                 AST                    result
 "1 + 2 * 3"   ──►  [1, +, 2, *, 3]  ──►       (+)            ──►       7
                                            /     \
   (lexer)            (parser)            1        (*)        (interpreter)
                                                 /   \
                                                2     3
```

The whole trick of this chapter is the middle step: notice that `2 * 3` is *grouped together under the `+`* even though in the flat token stream the `+` came first. The tree captures the fact that multiplication binds tighter than addition. The flat text doesn't know that; the tree does. **Parsing is the act of recovering structure from a sequence.**

**Why it matters.** Even if you never write a "real" compiler, this machinery is *everywhere*: every JSON parser, every regex engine, every SQL query planner, every template engine, every config-file reader, every "let users type a formula" feature in a spreadsheet, every linter and code formatter, every syntax highlighter. The instant a program has to *read structured text and act on it*, it has a lexer and a parser inside, whether the author knew the words or not. Learning to build one deliberately means you'll recognize the pattern forever, and you'll stop being afraid of the dragons. Let's build the pipeline one stage at a time.

## 📐 The pipeline: source → tokens → AST → execution

Let's name the stages precisely, because the rest of both chapters is just "implement each box."

```text
┌──────────┐   ┌─────────┐   ┌────────┐   ┌─────┐   ┌─────────────┐
│  SOURCE  │──►│  LEXER  │──►│ PARSER │──►│ AST │──►│ INTERPRETER │──► result
│ (string) │   │(scanner)│   │        │   │     │   │  or COMPILER│
└──────────┘   └─────────┘   └────────┘   └─────┘   └─────────────┘
                    │             │                       │
                 tokens       grammar                executes
                              (CFG, ch 23.1)         (chapter 24.2)
```

- **Source** is a flat string: `"var x = 1 + 2 * 3;"`.
- **Lexer** (a.k.a. **scanner** or **tokenizer**) groups characters into **tokens**, the "words" of the language: the keyword `var`, the identifier `x`, the operator `=`, the number `1`, and so on. It throws away whitespace and comments, and it tags each token with a **type** and a **line number** (so errors can point at the right line).
- **Parser** consumes the token stream and builds the **AST** by following the language's **grammar**, a context-free grammar, exactly the CFGs from Chapter [23.1](../23-Theory-of-Computation/23.1-automata-and-languages.md). This is where precedence and nesting get resolved.
- **AST** (Abstract Syntax Tree) is the structured, tree-shaped representation of the program. "Abstract" because it drops syntactic noise (parentheses, semicolons, the literal `var` keyword) and keeps only the *meaning*: "this is a binary `+` of these two subexpressions."
- **Interpreter / Compiler** (Chapter 24.2) either walks the AST and computes a result directly, or translates it into bytecode for a virtual machine.

Two terms to keep straight: a **compiler** translates source in one language into another (usually a lower-level one) *ahead of time*; an **interpreter** executes the source directly. In practice the line is blurry, CPython *compiles* your `.py` to bytecode and then *interprets* that bytecode (we'll literally build a tiny version of this in 24.2). The front end, lexer + parser, is **identical** for both. That's why we build it once, here, and reuse it.

## 📐 Tokens: the vocabulary of the language

A **token** is the smallest meaningful unit of source code, plus some metadata. When you lex `var x = 12;` you want five tokens:

```text
TOKEN(VAR,     "var", None, line 1)
TOKEN(IDENT,   "x",   None, line 1)
TOKEN(EQUAL,   "=",   None, line 1)
TOKEN(NUMBER,  "12",  12.0, line 1)
TOKEN(SEMICOLON,";",  None, line 1)
```

Each token carries four things:

1. **type**, a category from a fixed enumeration (`NUMBER`, `IDENT`, `PLUS`, `VAR`, `EOF`, ...). The parser makes decisions on *type*, never on raw text.
2. **lexeme**, the exact substring from the source (`"var"`, `"12"`). Useful for error messages and for identifiers.
3. **literal**, the *runtime value* for literal tokens: the number `12.0`, the string `"hello"`. `None` for everything else.
4. **line**, the line number, so an error can say "line 1" instead of "somewhere."

Let's define the token machinery in Python. We'll use an `Enum` for the type tags and a small class for tokens.

```python
from enum import Enum, auto


class TT(Enum):
    """TokenType - every category of token in our language."""
    # single-character tokens
    LEFT_PAREN = auto();  RIGHT_PAREN = auto()
    LEFT_BRACE = auto();  RIGHT_BRACE = auto()
    COMMA = auto();       SEMICOLON = auto()
    PLUS = auto();        MINUS = auto()
    STAR = auto();        SLASH = auto()

    # one- or two-character tokens
    BANG = auto();        BANG_EQUAL = auto()     # !  !=
    EQUAL = auto();       EQUAL_EQUAL = auto()     # =  ==
    GREATER = auto();     GREATER_EQUAL = auto()   # >  >=
    LESS = auto();        LESS_EQUAL = auto()      # <  <=

    # literals
    IDENT = auto();       STRING = auto();   NUMBER = auto()

    # keywords
    AND = auto();   OR = auto();    TRUE = auto();   FALSE = auto()
    NIL = auto();   IF = auto();    ELSE = auto();   WHILE = auto()
    VAR = auto();   PRINT = auto(); FUN = auto();    RETURN = auto()

    EOF = auto()          # sentinel: the end of the token stream


class Token:
    __slots__ = ("type", "lexeme", "literal", "line")

    def __init__(self, type_, lexeme, literal, line):
        self.type = type_          # a TT member
        self.lexeme = lexeme       # the raw text, e.g. "var"
        self.literal = literal     # runtime value for NUMBER/STRING, else None
        self.line = line           # 1-based line number for error reporting

    def __repr__(self):
        lit = "" if self.literal is None else f" {self.literal!r}"
        return f"Token({self.type.name} {self.lexeme!r}{lit} @L{self.line})"
```

The `EOF` token is a small but important trick: you *append* it to the end of every token stream so the parser always has "one more token" to look at and never falls off the end of the list. It's the same idea as a sentinel node in a linked list (Chapter [02.2](../02-Data-Structures/02.2-linked-lists.md)), a guard that removes a special case.

## 💻 Build it: the lexer (scanner) from scratch

The lexer's job: walk the source string left to right, one character at a time, and emit tokens. The core loop is "look at the current character, decide what token starts here, consume exactly that token, repeat." Whitespace gets skipped; comments get skipped; everything else becomes a token. If you hit a character you don't recognize, you report an error *with the line number* and keep going (so you can report multiple errors in one pass rather than dying on the first).

The two state variables that make it tick are `self.start` (index where the current lexeme began) and `self.current` (index of the next unconsumed character). The substring `source[start:current]` is always "the lexeme being built."

```python
class LexError(Exception):
    pass


# keyword lookup: text -> token type. If an identifier matches one of these,
# it's actually a keyword. This is how we avoid a giant if-chain.
KEYWORDS = {
    "and": TT.AND, "or": TT.OR, "true": TT.TRUE, "false": TT.FALSE,
    "nil": TT.NIL, "if": TT.IF, "else": TT.ELSE, "while": TT.WHILE,
    "var": TT.VAR, "print": TT.PRINT, "fun": TT.FUN, "return": TT.RETURN,
}


class Lexer:
    def __init__(self, source):
        self.source = source
        self.tokens = []
        self.start = 0      # start index of the lexeme currently being scanned
        self.current = 0    # index of the next char to consume
        self.line = 1
        self.errors = []    # collect errors instead of crashing on the first

    # --- low-level cursor helpers -------------------------------------------
    def _at_end(self):
        return self.current >= len(self.source)

    def _advance(self):
        """Consume the current char and return it."""
        ch = self.source[self.current]
        self.current += 1
        return ch

    def _peek(self):
        """Look at the current char without consuming it."""
        return "\0" if self._at_end() else self.source[self.current]

    def _peek_next(self):
        """Look one char past the current one (for two-char lookahead)."""
        if self.current + 1 >= len(self.source):
            return "\0"
        return self.source[self.current + 1]

    def _match(self, expected):
        """Consume the current char only if it equals `expected`."""
        if self._at_end() or self.source[self.current] != expected:
            return False
        self.current += 1
        return True

    def _add(self, type_, literal=None):
        lexeme = self.source[self.start:self.current]
        self.tokens.append(Token(type_, lexeme, literal, self.line))

    # --- the main driver -----------------------------------------------------
    def scan_tokens(self):
        while not self._at_end():
            self.start = self.current     # remember where this lexeme begins
            self._scan_token()
        self.tokens.append(Token(TT.EOF, "", None, self.line))
        return self.tokens

    def _scan_token(self):
        c = self._advance()

        # single-character tokens
        if   c == "(": self._add(TT.LEFT_PAREN)
        elif c == ")": self._add(TT.RIGHT_PAREN)
        elif c == "{": self._add(TT.LEFT_BRACE)
        elif c == "}": self._add(TT.RIGHT_BRACE)
        elif c == ",": self._add(TT.COMMA)
        elif c == ";": self._add(TT.SEMICOLON)
        elif c == "+": self._add(TT.PLUS)
        elif c == "-": self._add(TT.MINUS)
        elif c == "*": self._add(TT.STAR)

        # one- or two-character tokens: peek to decide
        elif c == "!": self._add(TT.BANG_EQUAL    if self._match("=") else TT.BANG)
        elif c == "=": self._add(TT.EQUAL_EQUAL   if self._match("=") else TT.EQUAL)
        elif c == "<": self._add(TT.LESS_EQUAL    if self._match("=") else TT.LESS)
        elif c == ">": self._add(TT.GREATER_EQUAL if self._match("=") else TT.GREATER)

        # slash is special: // starts a comment, otherwise it's division
        elif c == "/":
            if self._match("/"):
                # a line comment runs to the end of the line - consume & drop it
                while self._peek() != "\n" and not self._at_end():
                    self._advance()
            else:
                self._add(TT.SLASH)

        # whitespace: skip; track newlines for line numbers
        elif c in (" ", "\r", "\t"):
            pass
        elif c == "\n":
            self.line += 1

        # string literals
        elif c == '"':
            self._string()

        # numbers
        elif c.isdigit():
            self._number()

        # identifiers and keywords
        elif c.isalpha() or c == "_":
            self._identifier()

        else:
            self.errors.append(f"[line {self.line}] unexpected character {c!r}")

    # --- multi-character literal scanners -----------------------------------
    def _string(self):
        # we've already consumed the opening quote; consume until closing quote
        while self._peek() != '"' and not self._at_end():
            if self._peek() == "\n":
                self.line += 1        # strings may span lines
            self._advance()
        if self._at_end():
            self.errors.append(f"[line {self.line}] unterminated string")
            return
        self._advance()               # consume the closing quote
        # the literal value is the text *between* the quotes
        value = self.source[self.start + 1:self.current - 1]
        self._add(TT.STRING, value)

    def _number(self):
        while self._peek().isdigit():
            self._advance()
        # optional fractional part: a '.' followed by at least one digit
        if self._peek() == "." and self._peek_next().isdigit():
            self._advance()           # consume the '.'
            while self._peek().isdigit():
                self._advance()
        text = self.source[self.start:self.current]
        self._add(TT.NUMBER, float(text))   # all numbers are floats, Lox-style

    def _identifier(self):
        while self._peek().isalnum() or self._peek() == "_":
            self._advance()
        text = self.source[self.start:self.current]
        type_ = KEYWORDS.get(text, TT.IDENT)   # keyword? otherwise plain identifier
        self._add(type_)
```

Let's run it and *see* the tokens:

```python
src = 'var x = 1 + 2 * 3;  // compute something\nprint x >= 7;'
lexer = Lexer(src)
tokens = lexer.scan_tokens()
for t in tokens:
    print(t)
assert not lexer.errors, lexer.errors
```

Output:

```text
Token(VAR 'var' @L1)
Token(IDENT 'x' @L1)
Token(EQUAL '=' @L1)
Token(NUMBER '1' 1.0 @L1)
Token(PLUS '+' @L1)
Token(NUMBER '2' 2.0 @L1)
Token(STAR '*' @L1)
Token(NUMBER '3' 3.0 @L1)
Token(SEMICOLON ';' @L1)
Token(PRINT 'print' @L2)
Token(IDENT 'x' @L2)
Token(GREATER_EQUAL '>=' @L2)
Token(NUMBER '7' 7.0 @L2)
Token(SEMICOLON ';' @L2)
Token(EOF '' @L2)
```

Look at what happened: the comment vanished, whitespace vanished, `>=` became *one* token (not `>` then `=`), the number literals carry their `float` values, and the `print` keyword was recognized as `PRINT` rather than a plain identifier, all driven by the keyword table. The line number ticked from 1 to 2 across the `\n`. This is a complete, real scanner.

**The deep idea: a lexer is a finite automaton.** Every branch in `_scan_token` is a state transition. "Saw `<`; if the next char is `=` go to the `<=` state, otherwise emit `<`." That's *exactly* a DFA (Chapter [23.1](../23-Theory-of-Computation/23.1-automata-and-languages.md)), and it's why lexers are usually specified with **regular expressions**, since regexes and DFAs are equivalent. A number is `[0-9]+(\.[0-9]+)?`; an identifier is `[A-Za-z_][A-Za-z0-9_]*`. Tools like `lex`/`flex` literally take regexes and compile them to a DFA table. Our hand-written scanner *is* that DFA, just spelled out in Python `if`s. Tokens are the language a regular grammar can describe; the *nesting* of expressions needs something stronger, a context-free grammar, which is the parser's job.

## 📐 Grammars and parsing: recovering structure

Tokens are flat. `[1, +, 2, *, 3]` is a list. But `1 + 2 * 3` *means* `1 + (2 * 3)`, not `(1 + 2) * 3`, because `*` binds tighter than `+`. The parser's job is to turn the flat token list into a tree that encodes that grouping. To do that it needs **rules**, a grammar.

A **context-free grammar (CFG)** (straight from Chapter [23.1](../23-Theory-of-Computation/23.1-automata-and-languages.md)) is a set of production rules. Here's a first cut at the grammar for arithmetic expressions, written in a notation where `→` means "can be," `|` means "or", and lowercase names are the token types:

```text
expression → NUMBER
           | expression "+" expression
           | expression "*" expression
           | "(" expression ")"
```

This grammar is **ambiguous**: it can derive `1 + 2 * 3` two ways (group the `+` first, or the `*` first), and it gives no guidance about which. Ambiguity is fatal for a parser, it wouldn't know which tree to build. The fix is to **bake precedence and associativity into the shape of the grammar** by writing one rule per precedence level, lowest-precedence at the top:

```text
expression → equality
equality   → comparison ( ( "==" | "!=" ) comparison )*
comparison → term       ( ( ">" | ">=" | "<" | "<=" ) term )*
term       → factor     ( ( "+" | "-" ) factor )*
factor     → unary      ( ( "*" | "/" ) unary )*
unary      → ( "!" | "-" ) unary
           | primary
primary    → NUMBER | STRING | "true" | "false" | "nil"
           | IDENT
           | "(" expression ")"
```

Read it top to bottom: an `expression` is an `equality`; an `equality` is one or more `comparison`s joined by `==`/`!=`; ... down to `factor`, which is `unary`s joined by `*`/`/`; down to `primary`, the atoms. **Each rule that's "lower" in the grammar binds tighter**, because to even *reach* a `factor` you must descend *through* `term`, so `*` ends up nested deeper in the tree than `+`. Precedence becomes nesting depth. This single idea, *one grammar rule per precedence level*, is the whole secret of precedence.

The `( ... )*` "zero or more" pieces also encode **left-associativity**: `1 - 2 - 3` should be `(1 - 2) - 3`, and looping left-to-right builds exactly that left-leaning tree. Unary is **right-associative** (`- - x` is `-(-x)`), which is why `unary` recurses into *itself* instead of looping.

## 📐 The AST: node types and the visitor pattern

The output of parsing is the **Abstract Syntax Tree**. You need a class for each kind of node. For expressions:

- `Literal(value)`, a number, string, `True`/`False`, or `nil`.
- `Variable(name)`, a reference to a variable, like `x`.
- `Unary(op, right)`, `-x` or `!x`.
- `Binary(left, op, right)`, `a + b`, `a == b`, etc.
- `Grouping(expr)`, a parenthesized subexpression `( ... )`.
- `Assign(name, value)`, `x = expr`.
- `Logical(left, op, right)`, `and` / `or` (kept separate because they short-circuit; we'll use that in 24.2).
- `Call(callee, args)`, a function call `f(a, b)` (we lex/parse it now; we run it in 24.2).

These are plain data-holding nodes, the textbook use case for Python's `@dataclass`. We'll define them compactly.

```python
from dataclasses import dataclass, field
from typing import Any, List, Optional


class Expr:           # base class - every expression node subclasses this
    pass


@dataclass
class Literal(Expr):
    value: Any                       # a float, str, bool, or None (nil)

@dataclass
class Variable(Expr):
    name: Token                      # the IDENT token (carries lexeme + line)

@dataclass
class Assign(Expr):
    name: Token
    value: Expr

@dataclass
class Unary(Expr):
    op: Token                        # MINUS or BANG
    right: Expr

@dataclass
class Binary(Expr):
    left: Expr
    op: Token                        # PLUS, STAR, EQUAL_EQUAL, ...
    right: Expr

@dataclass
class Logical(Expr):
    left: Expr
    op: Token                        # AND or OR
    right: Expr

@dataclass
class Grouping(Expr):
    expr: Expr

@dataclass
class Call(Expr):
    callee: Expr
    paren: Token                     # the ')' token, for error line numbers
    args: List[Expr]
```

**The visitor pattern.** Once you have a tree, you'll want to do *lots of different things* to it: pretty-print it, type-check it, interpret it, compile it to bytecode. You do *not* want to scatter a `print_me()` and a `typecheck_me()` and an `eval_me()` method across every node class, that couples the nodes to every operation and means adding a new operation touches every class. Instead you use the **visitor pattern** (a Gang-of-Four design pattern): each *operation* is its own class with one method per node type, and nodes accept a visitor.

In Python you can do this cleanly with a single dispatch helper rather than the boilerplate `accept`/`visit` double-dispatch you'd write in Java. The idea: given a visitor object and a node, call the method named `visit_<ClassName>`.

```python
class Visitor:
    """Base visitor: dispatch on the node's class name.

    A subclass implements visit_Literal, visit_Binary, etc. Calling
    self.visit(node) routes to the right one automatically.
    """
    def visit(self, node):
        method = "visit_" + type(node).__name__
        fn = getattr(self, method, None)
        if fn is None:
            raise NotImplementedError(f"{type(self).__name__} has no {method}")
        return fn(node)
```

This is the single most important structural decision in the whole back end: the AST nodes stay dumb (just data), and *every* tree operation, printing here, type-checking and evaluating and compiling in 24.2, is a `Visitor` subclass with one `visit_X` method per node. Adding the interpreter later won't touch a single node class. (This is the trade-off the "expression problem" describes: the visitor pattern makes adding *operations* easy at the cost of making adding *node types* touch every visitor. For a language, operations come and go far more than node types, so it's the right call.)

Here's the first visitor: an **AST pretty-printer** that renders the tree as fully-parenthesized prefix notation, so you can *see* the structure the parser built.

```python
class AstPrinter(Visitor):
    """Render an AST as a Lisp-like parenthesized string, to verify structure."""

    def print(self, expr):
        return self.visit(expr)

    def visit_Literal(self, node):
        if node.value is None:
            return "nil"
        if node.value is True:  return "true"
        if node.value is False: return "false"
        return repr(node.value)

    def visit_Variable(self, node):
        return node.name.lexeme

    def visit_Assign(self, node):
        return f"(= {node.name.lexeme} {self.visit(node.value)})"

    def visit_Unary(self, node):
        return f"({node.op.lexeme} {self.visit(node.right)})"

    def visit_Binary(self, node):
        return f"({node.op.lexeme} {self.visit(node.left)} {self.visit(node.right)})"

    def visit_Logical(self, node):
        return f"({node.op.lexeme} {self.visit(node.left)} {self.visit(node.right)})"

    def visit_Grouping(self, node):
        return f"(group {self.visit(node.expr)})"

    def visit_Call(self, node):
        args = " ".join(self.visit(a) for a in node.args)
        return f"(call {self.visit(node.callee)} {args})".rstrip() + ")"[:0] or \
               f"(call {self.visit(node.callee)}{(' ' + args) if args else ''})"
```

(That last method looks awkward because it's being careful about the no-args case; keep it simple. The point is each node type knows how to stringify itself *through* the visitor.)

## 💻 Build it: a recursive-descent parser

Now the heart of the chapter. **Recursive-descent parsing** turns the grammar into code by the most beautiful one-to-one mapping in all of CS: **each grammar rule becomes one function, and a rule referring to another rule becomes a function call.** The grammar is recursive (`expression` eventually contains `expression` via `primary`'s `( expression )`), so the parser is recursive, this is recursion (Chapter [03.1](../03-Algorithms/03.1-recursion.md)) applied to grammar rules.

The parser holds the token list and a `current` index. A handful of helpers do the bookkeeping; then there's one method per grammar rule.

```python
class ParseError(Exception):
    pass


class Parser:
    def __init__(self, tokens):
        self.tokens = tokens
        self.current = 0
        self.errors = []

    # --- token cursor helpers ------------------------------------------------
    def _peek(self):
        return self.tokens[self.current]

    def _previous(self):
        return self.tokens[self.current - 1]

    def _at_end(self):
        return self._peek().type == TT.EOF

    def _check(self, type_):
        return not self._at_end() and self._peek().type == type_

    def _advance(self):
        if not self._at_end():
            self.current += 1
        return self._previous()

    def _match(self, *types):
        """If the current token is any of `types`, consume it and return True."""
        for t in types:
            if self._check(t):
                self._advance()
                return True
        return False

    def _consume(self, type_, message):
        """Demand a specific token; raise a ParseError if it isn't there."""
        if self._check(type_):
            return self._advance()
        raise self._error(self._peek(), message)

    def _error(self, token, message):
        where = "end" if token.type == TT.EOF else f"{token.lexeme!r}"
        msg = f"[line {token.line}] Error at {where}: {message}"
        self.errors.append(msg)
        return ParseError(msg)
```

Now the grammar rules, top of the grammar (lowest precedence) down to the atoms. Watch how literally each one mirrors the EBNF:

```python
    # expression → assignment
    def _expression(self):
        return self._assignment()

    # assignment → IDENT "=" assignment | logic_or
    def _assignment(self):
        expr = self._logic_or()
        if self._match(TT.EQUAL):
            equals = self._previous()
            value = self._assignment()           # right-assoc: recurse on self
            if isinstance(expr, Variable):
                return Assign(expr.name, value)
            self._error(equals, "invalid assignment target")
        return expr

    # logic_or → logic_and ( "or" logic_and )*
    def _logic_or(self):
        expr = self._logic_and()
        while self._match(TT.OR):
            op = self._previous()
            expr = Logical(expr, op, self._logic_and())
        return expr

    # logic_and → equality ( "and" equality )*
    def _logic_and(self):
        expr = self._equality()
        while self._match(TT.AND):
            op = self._previous()
            expr = Logical(expr, op, self._equality())
        return expr

    # equality → comparison ( ( "!=" | "==" ) comparison )*
    def _equality(self):
        expr = self._comparison()
        while self._match(TT.BANG_EQUAL, TT.EQUAL_EQUAL):
            op = self._previous()
            expr = Binary(expr, op, self._comparison())
        return expr

    # comparison → term ( ( ">" | ">=" | "<" | "<=" ) term )*
    def _comparison(self):
        expr = self._term()
        while self._match(TT.GREATER, TT.GREATER_EQUAL, TT.LESS, TT.LESS_EQUAL):
            op = self._previous()
            expr = Binary(expr, op, self._term())
        return expr

    # term → factor ( ( "+" | "-" ) factor )*   -- left-associative
    def _term(self):
        expr = self._factor()
        while self._match(TT.PLUS, TT.MINUS):
            op = self._previous()
            expr = Binary(expr, op, self._factor())
        return expr

    # factor → unary ( ( "*" | "/" ) unary )*   -- left-associative
    def _factor(self):
        expr = self._unary()
        while self._match(TT.STAR, TT.SLASH):
            op = self._previous()
            expr = Binary(expr, op, self._unary())
        return expr

    # unary → ( "!" | "-" ) unary | call         -- right-associative
    def _unary(self):
        if self._match(TT.BANG, TT.MINUS):
            op = self._previous()
            return Unary(op, self._unary())       # recurse on self
        return self._call()

    # call → primary ( "(" arguments? ")" )*
    def _call(self):
        expr = self._primary()
        while self._match(TT.LEFT_PAREN):
            args = []
            if not self._check(TT.RIGHT_PAREN):
                args.append(self._expression())
                while self._match(TT.COMMA):
                    args.append(self._expression())
            paren = self._consume(TT.RIGHT_PAREN, "expected ')' after arguments")
            expr = Call(expr, paren, args)
        return expr

    # primary → NUMBER | STRING | "true" | "false" | "nil" | IDENT | "(" expr ")"
    def _primary(self):
        if self._match(TT.FALSE): return Literal(False)
        if self._match(TT.TRUE):  return Literal(True)
        if self._match(TT.NIL):   return Literal(None)
        if self._match(TT.NUMBER, TT.STRING):
            return Literal(self._previous().literal)
        if self._match(TT.IDENT):
            return Variable(self._previous())
        if self._match(TT.LEFT_PAREN):
            expr = self._expression()
            self._consume(TT.RIGHT_PAREN, "expected ')' after expression")
            return Grouping(expr)
        raise self._error(self._peek(), "expected an expression")

    # --- public entry point (expression-only for now) ------------------------
    def parse_expression(self):
        try:
            expr = self._expression()
            if not self._at_end():
                self._error(self._peek(), "unexpected trailing tokens")
            return expr
        except ParseError:
            return None
```

Let's prove precedence works by lexing, parsing, and pretty-printing:

```python
def parse_expr(src):
    tokens = Lexer(src).scan_tokens()
    return Parser(tokens).parse_expression()

assert AstPrinter().print(parse_expr("(1 + 2) * 3")) == "(* (group (+ 1.0 2.0)) 3.0)"
assert AstPrinter().print(parse_expr("1 - 2 - 3")) == "(- (- 1.0 2.0) 3.0)"   # left-assoc

```

Look closely at the first two. `1 + 2 * 3` parsed to `(+ 1.0 (* 2.0 3.0))`, the multiplication is *nested under* the addition, exactly the right tree, **with no precedence table anywhere in the code.** The precedence is entirely a consequence of the *call order* of `_term → _factor → _unary`. And `1 - 2 - 3` came out left-leaning because the `while` loop in `_term` consumed `- 2` and `- 3` left to right. The grammar shape *is* the precedence logic.

## 📐 Pratt parsing / precedence climbing (the pro technique)

Recursive descent with one-rule-per-level is clean, but with 10 precedence levels you write 10 nearly-identical functions. The professional alternative, used in real compilers like Clang and in `tdop`-style parsers, is **Pratt parsing** (a.k.a. **precedence climbing** or **top-down operator precedence**). Instead of a function per level, you have **one** expression function that takes a *minimum binding power* and consults a table mapping each operator to its precedence.

The intuition: you parse a left operand, then loop. Each time you see an infix operator whose precedence is **at least** the minimum you were told to respect, you bind it, recursing with a *higher* minimum so that tighter operators on the right get grabbed first. When you see an operator that's too loose, you stop and hand control back to the caller.

```python
# binding power (precedence) for each binary operator; higher = binds tighter
BINDING = {
    TT.OR: 1, TT.AND: 2,
    TT.EQUAL_EQUAL: 3, TT.BANG_EQUAL: 3,
    TT.LESS: 4, TT.LESS_EQUAL: 4, TT.GREATER: 4, TT.GREATER_EQUAL: 4,
    TT.PLUS: 5, TT.MINUS: 5,
    TT.STAR: 6, TT.SLASH: 6,
}


class PrattParser(Parser):
    """Same token helpers as Parser, but one expression engine driven by a table."""

    def _expression(self, min_bp=0):
        # parse the left-hand side: a prefix unary or a primary atom
        if self._match(TT.MINUS, TT.BANG):
            op = self._previous()
            left = Unary(op, self._expression(7))   # 7 > any binary bp: tight
        else:
            left = self._primary()

        # consume infix operators whose binding power >= min_bp
        while True:
            op_type = self._peek().type
            bp = BINDING.get(op_type)
            if bp is None or bp < min_bp:
                break                       # operator too loose (or none) -> stop
            op = self._advance()
            # recurse with bp+1 so same-precedence ops are LEFT-associative
            right = self._expression(bp + 1)
            cls = Logical if op_type in (TT.AND, TT.OR) else Binary
            left = cls(left, op, right)
        return left

    def parse_expression(self):
        try:
            expr = self._expression(0)
            if not self._at_end():
                self._error(self._peek(), "unexpected trailing tokens")
            return expr
        except ParseError:
            return None
```

```python
def pratt(src):
    return PrattParser(Lexer(src).scan_tokens()).parse_expression()

assert AstPrinter().print(pratt("1 + 2 * 3")) == "(+ 1.0 (* 2.0 3.0))"
assert AstPrinter().print(pratt("1 - 2 - 3")) == "(- (- 1.0 2.0) 3.0)"   # left-assoc
assert AstPrinter().print(pratt("2 * 3 + 4 * 5")) == "(+ (* 2.0 3.0) (* 4.0 5.0))"
print("Pratt parser produces identical trees ✅")
```

Same trees, one function instead of seven. The `bp + 1` in the recursive call is the associativity knob: `bp + 1` (require *strictly* greater on the right) gives **left**-associativity; using plain `bp` would give **right**-associativity (handy for `^` exponentiation or `=` assignment). Pratt parsing is worth knowing cold, it's a frequent interview topic ("write a calculator that respects precedence") and it scales to any number of operators without grammar bloat. For the rest of the book we'll keep using the explicit recursive-descent `Parser` because its one-function-per-rule form is easier to read and extend, but they're interchangeable, they emit the same AST.

## ⚠️ Handling parse errors gracefully

A real parser can't just crash on the first mistake, it should report a *useful* message (line + what it expected) and, ideally, **recover** so it can find *more* errors in one run. The technique is **panic-mode recovery with synchronization**: when a parse rule fails, throw a `ParseError`, catch it at statement boundaries, then *discard tokens* until we reach a likely start of the next statement (a `;`, or a keyword like `if`/`while`/`var`). That way one bad line doesn't cause a cascade of bogus follow-on errors.

```python
    def _synchronize(self):
        """After an error, skip tokens until the likely start of a new statement."""
        self._advance()
        while not self._at_end():
            if self._previous().type == TT.SEMICOLON:
                return                       # just passed a ';' -> fresh statement
            if self._peek().type in (TT.IF, TT.WHILE, TT.VAR, TT.PRINT,
                                     TT.FUN, TT.RETURN):
                return                       # at a statement keyword -> resume here
            self._advance()
```

We'll wire `_synchronize` into the statement parser in the mini-project below. The key design principle: **errors are data, not crashes.** You collect them in `self.errors` with line numbers so the user sees `[line 3] Error at '}': expected ';' after expression` rather than a Python traceback. Good error messages are a huge part of what makes a language pleasant, and a huge part of what makes a *parser* hard, honestly. The happy path is the easy 30%.

The grammar grows a top layer for the program and statements:

```text
program     → declaration* EOF
declaration → varDecl | funDecl | statement
varDecl     → "var" IDENT ( "=" expression )? ";"
funDecl     → "fun" IDENT "(" params? ")" block
statement   → exprStmt | printStmt | block | ifStmt | whileStmt | returnStmt
block       → "{" declaration* "}"
ifStmt      → "if" "(" expression ")" statement ( "else" statement )?
whileStmt   → "while" "(" expression ")" statement
printStmt   → "print" expression ";"
returnStmt  → "return" expression? ";"
exprStmt    → expression ";"
```

Now add the statement-parsing methods. We subclass `Parser` to reuse all the expression machinery unchanged.

```python
class FullParser(Parser):
    """Parser extended to handle a full program of statements."""

    def parse(self):
        """Parse a whole program: a list of statements. Recovers from errors."""
        statements = []
        while not self._at_end():
            decl = self._declaration()
            if decl is not None:
                statements.append(decl)
        return statements

    def _declaration(self):
        try:
            if self._match(TT.VAR):
                return self._var_declaration()
            if self._match(TT.FUN):
                return self._function("function")
            return self._statement()
        except ParseError:
            self._synchronize()        # panic-mode recovery: skip to next statement
            return None

    def _var_declaration(self):
        name = self._consume(TT.IDENT, "expected variable name")
        initializer = None
        if self._match(TT.EQUAL):
            initializer = self._expression()
        self._consume(TT.SEMICOLON, "expected ';' after variable declaration")
        return VarDecl(name, initializer)

    def _function(self, kind):
        name = self._consume(TT.IDENT, f"expected {kind} name")
        self._consume(TT.LEFT_PAREN, f"expected '(' after {kind} name")
        params = []
        if not self._check(TT.RIGHT_PAREN):
            params.append(self._consume(TT.IDENT, "expected parameter name"))
            while self._match(TT.COMMA):
                params.append(self._consume(TT.IDENT, "expected parameter name"))
        self._consume(TT.RIGHT_PAREN, "expected ')' after parameters")
        self._consume(TT.LEFT_BRACE, "expected '{' before " + kind + " body")
        body = self._block()
        return FunctionDecl(name, params, body)

    def _statement(self):
        if self._match(TT.PRINT):   return self._print_statement()
        if self._match(TT.LEFT_BRACE): return Block(self._block())
        if self._match(TT.IF):      return self._if_statement()
        if self._match(TT.WHILE):   return self._while_statement()
        if self._match(TT.RETURN):  return self._return_statement()
        return self._expression_statement()

    def _print_statement(self):
        value = self._expression()
        self._consume(TT.SEMICOLON, "expected ';' after value")
        return PrintStmt(value)

    def _block(self):
        statements = []
        while not self._check(TT.RIGHT_BRACE) and not self._at_end():
            statements.append(self._declaration())
        self._consume(TT.RIGHT_BRACE, "expected '}' after block")
        return statements

    def _if_statement(self):
        self._consume(TT.LEFT_PAREN, "expected '(' after 'if'")
        condition = self._expression()
        self._consume(TT.RIGHT_PAREN, "expected ')' after condition")
        then_branch = self._statement()
        else_branch = None
        if self._match(TT.ELSE):
            else_branch = self._statement()
        return IfStmt(condition, then_branch, else_branch)

    def _while_statement(self):
        self._consume(TT.LEFT_PAREN, "expected '(' after 'while'")
        condition = self._expression()
        self._consume(TT.RIGHT_PAREN, "expected ')' after condition")
        body = self._statement()
        return WhileStmt(condition, body)

    def _return_statement(self):
        keyword = self._previous()
        value = None
        if not self._check(TT.SEMICOLON):
            value = self._expression()
        self._consume(TT.SEMICOLON, "expected ';' after return value")
        return ReturnStmt(keyword, value)

    def _expression_statement(self):
        expr = self._expression()
        self._consume(TT.SEMICOLON, "expected ';' after expression")
        return ExpressionStmt(expr)
```

Now extend the pretty-printer to indent statements, so you can *see* the whole program tree:

```python
class StmtPrinter(AstPrinter):
    """Pretty-print a list of statements as an indented tree."""

    def print_program(self, statements):
        return "\n".join(self._stmt(s, 0) for s in statements)

    def _ind(self, depth):
        return "  " * depth

    def _stmt(self, s, depth):
        i = self._ind(depth)
        if isinstance(s, VarDecl):
            init = "" if s.initializer is None else " = " + self.visit(s.initializer)
            return f"{i}var {s.name.lexeme}{init}"
        if isinstance(s, PrintStmt):
            return f"{i}print {self.visit(s.expr)}"
        if isinstance(s, ExpressionStmt):
            return f"{i}expr {self.visit(s.expr)}"
        if isinstance(s, Block):
            inner = "\n".join(self._stmt(x, depth + 1) for x in s.statements)
            return f"{i}block {{\n{inner}\n{i}}}"
        if isinstance(s, IfStmt):
            out = f"{i}if {self.visit(s.condition)}\n"
            out += self._stmt(s.then_branch, depth + 1)
            if s.else_branch is not None:
                out += f"\n{i}else\n" + self._stmt(s.else_branch, depth + 1)
            return out
        if isinstance(s, WhileStmt):
            return f"{i}while {self.visit(s.condition)}\n" + \
                   self._stmt(s.body, depth + 1)
        if isinstance(s, FunctionDecl):
            params = ", ".join(p.lexeme for p in s.params)
            inner = "\n".join(self._stmt(x, depth + 1) for x in s.body)
            return f"{i}fun {s.name.lexeme}({params}) {{\n{inner}\n{i}}}"
        if isinstance(s, ReturnStmt):
            v = "" if s.value is None else " " + self.visit(s.value)
            return f"{i}return{v}"
        return f"{i}<?{type(s).__name__}>"
```

## 💼 On the job / interview angle

Lexing and parsing show up in real engineering far more than people expect, and they're a beloved interview genre.

**Where this lives in real systems.** Every language's front end (the part of CPython that turns your `.py` into an AST is exactly this, try `import ast; ast.dump(ast.parse("1+2*3"))` and you'll see `BinOp` nodes nested by precedence, same as ours). Database engines parse SQL into a query AST before planning. Protobuf, GraphQL, and config formats (YAML/TOML/JSON) all have hand- or generated parsers. Linters and formatters (Black, Prettier, ESLint) parse to an AST, transform it, and print it back. Build tools parse expression languages. If you ever write a "let the user type a formula/filter/rule" feature, you'll reach for exactly this pipeline instead of the catastrophic `eval()`.

**Interview-frequent problems that are this chapter in disguise:**

1. **"Basic Calculator"** (evaluate `"3 + 2 * 2"` or with parentheses). This is a lexer + an expression parser/evaluator. Knowing precedence climbing makes it a five-minute problem instead of a stack-juggling nightmare.
2. **"Implement a calculator that respects `* / + -` and parentheses."** Literally `_term`/`_factor`/`_primary`. Say the words "recursive descent" and "one rule per precedence level" and you've demonstrated real depth.
3. **"Parse and evaluate a boolean expression"** or **"decode a nested/encoded string"** (`"3[a2[c]]"` → `"accaccacc"`), both are mini-parsers; recursion on a grammar is the clean solution.
4. **"Validate / match nested brackets."** This is the parsing instinct, a stack, or recursion, recovering structure from a flat sequence.

**Things to say that signal competence:** "I'd separate lexing from parsing." "Tokens are a regular language; nesting needs a context-free grammar." "Precedence falls out of the grammar shape, I don't need a precedence table if I write one rule per level, or I'd use Pratt parsing for many operators." "I'd collect errors with line numbers and synchronize rather than crash on the first one." That last point, graceful error handling, is what separates someone who's *read* about parsers from someone who's *built* one.

```python
# BINDING_POW[TT.CARET] = 8   # tighter than *, /
# In _expression's loop, special-case right-assoc:
#     right = self._expression(bp if op_type == TT.CARET else bp + 1)
# Result: 2 ^ 3 ^ 2 -> (^ 2.0 (^ 3.0 2.0))
print("4. right-assoc power: recurse with bp (not bp+1) ✅ (see notes)")
# Explanation: requiring strictly-greater bp on the right (bp+1) gives LEFT
# associativity; allowing equal bp (bp) lets the right side grab same-level
# operators first, producing RIGHT associativity - exactly what ^ wants.
```

```python
# 5. AST depth visitor -------------------------------------------------------
class DepthVisitor(Visitor):
    def visit_Literal(self, n):  return 1
    def visit_Variable(self, n): return 1
    def visit_Grouping(self, n): return 1 + self.visit(n.expr)
    def visit_Unary(self, n):    return 1 + self.visit(n.right)
    def visit_Assign(self, n):   return 1 + self.visit(n.value)
    def visit_Binary(self, n):
        return 1 + max(self.visit(n.left), self.visit(n.right))
    def visit_Logical(self, n):
        return 1 + max(self.visit(n.left), self.visit(n.right))
    def visit_Call(self, n):
        sub = [self.visit(a) for a in n.args] + [self.visit(n.callee)]
        return 1 + (max(sub) if sub else 0)

dv = DepthVisitor()
assert dv.visit(parse_expr("1")) == 1
assert dv.visit(parse_expr("1 + 2")) == 2
assert dv.visit(parse_expr("1 + 2 * 3")) == 3
assert dv.visit(parse_expr("(1 + 2) * 3")) == 4   # group adds a level
print("5. AST depth visitor ✅")
# Explanation: a leaf is depth 1; an internal node is 1 + the deeper child.
# This is just tree height (chapter 02.5) computed with the visitor pattern.
```

## ✅ Teach it back

If you can explain these without notes, the front end is yours:

1. **The pipeline.** Source string → **lexer** → tokens → **parser** → AST → (24.2) execution. Compiler vs interpreter share this front end. Why have a separate token stage? Because it lets the parser reason about *categories* (`NUMBER`, `PLUS`) instead of raw characters, and it's the natural place to handle whitespace, comments, and line tracking.
2. **The lexer is a DFA.** It walks characters, and each `if`/`peek` branch is a state transition. Tokens form a *regular* language (Chapter 23.1), which is why regexes describe them. It tags tokens with type, lexeme, literal value, and line number, and appends an `EOF` sentinel.
3. **Grammars and precedence.** A CFG defines the structure. Naïve grammars are *ambiguous*; the fix is **one rule per precedence level**, lowest at the top, so tighter operators end up nested deeper. Left-associativity comes from a `( ... )*` loop; right-associativity from recursing on the same rule.
4. **Recursive descent.** Each grammar rule becomes one function; rule references become function calls. It's recursion walking a grammar. **Pratt parsing** does the same job with one function plus a binding-power table, scaling to many operators.
5. **The AST + visitor pattern.** Nodes are dumb data (`@dataclass`); every *operation* (print, type-check, interpret, compile) is a `Visitor` subclass with `visit_X` methods. This keeps nodes decoupled from operations.
6. **Error handling.** Don't crash on the first mistake. Throw a `ParseError`, catch it at statement boundaries, **synchronize** by skipping to the next `;` or keyword, and collect messages with line numbers.

In Chapter [24.2](./24.2-interpreters-and-vms.md) we'll take these exact AST classes and *run* them: a tree-walking interpreter with environments, scopes, functions, and closures; a simple static type checker (another visitor); and then a bytecode compiler + stack VM. The front end is done, now we make the language *come alive*.
